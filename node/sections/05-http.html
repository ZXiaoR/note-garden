05.1 · 理解底层原理：原生 node:http 的 req / res 对象、URL 解析与流式读取请求体

05.1 先看清底层原理：原生 node:http 是怎么收发请求的

无论是 Express、Koa、Fastify 还是 NestJS，最底下都封装自内置的 node:http 模块。调用 http.createServer((req, res) => {}) 时，每次请求进来都会拿到两个基于流（Stream）构建的核心对象：

  • req（http.IncomingMessage，本质是一个可读流 Readable）：包含请求方法 req.method、原始路径 req.url、已全部自动转为小写的请求头 req.headers；而 POST 提交的请求体需要通过 for await (const chunk of req) 分块读取拼接。
  • res（http.ServerResponse，本质是一个可写流 Writable）：用 res.writeHead(状态码, 响应头) 设置元数据，用 res.end(内容) 发送响应并结束本次请求。
raw_http_server.mjs · 原生实现文章列表查询与新增接口 [Node.js 20+] 
import http from 'node:http';

const articles = [{ id: 1, title: 'Node.js 入门' }];

// 辅助函数：从可读流 req 中收集 JSON 请求体（带 1MB 体积保护防撑爆内存）
async function readJsonBody(req, maxBytes = 1024 * 1024) {
  const chunks = [];
  let size = 0;
  for await (const chunk of req) {
    size += chunk.length;
    if (size > maxBytes) throw new Error('Payload Too Large');
    chunks.push(chunk);
  }
  const raw = Buffer.concat(chunks).toString('utf8');
  return raw ? JSON.parse(raw) : {};
}

const server = http.createServer(async (req, res) => {
  res.setHeader('Content-Type', 'application/json; charset=utf-8');
  const urlObj = new URL(req.url, `http://${req.headers.host}`);

  // 1. GET /api/articles?page=1
  if (req.method === 'GET' && urlObj.pathname === '/api/articles') {
    const page = Number(urlObj.searchParams.get('page') || 1);
    res.writeHead(200);
    res.end(JSON.stringify({ code: 0, page, list: articles }));
    return;
  }

  // 2. POST /api/articles
  if (req.method === 'POST' && urlObj.pathname === '/api/articles') {
    const body = await readJsonBody(req);
    const created = { id: articles.length + 1, title: body.title };
    articles.push(created);
    res.writeHead(201);
    res.end(JSON.stringify({ code: 0, data: created }));
    return;
  }

  res.writeHead(404);
  res.end(JSON.stringify({ code: 404, message: '接口不存在' }));
});

server.listen(3000);
为什么理解了原生 node:http 后，真实项目一定要上框架？

观察左侧代码就会发现，一旦业务接口增加到几十个，纯手写原生 node:http 要重复处理大量样板细节：

  • 动态路由匹配：/api/articles/:id 这类带路径参数的路由靠 if / else 极难维护，框架底层会使用前缀树（Radix Tree）实现 O(路径长度) 的常数级匹配；
  • 请求体安全解析：框架默认内置请求体体积上限（如 1MB）、Content-Type 识别与畸形 JSON 异常捕获；
  • 生命周期钩子与插件复用：鉴权拦截、参数校验、跨域头与请求耗时日志可通过钩子统一挂载，不用在每个接口里复制粘贴。
05.2 · 主流 Web 框架实战：用 Fastify v5 重写接口与四大主流框架选型对比

05.2 用 Fastify 重写同一套接口，以及主流框架怎么选

在现代 Node.js 后端开发中，Fastify（v5）凭借原生 async / await 设计、内置高性能 pino 结构化日志、零配置 JSON 解析序列化与良好的 TypeScript 支持，成为新建独立 API 与微服务的热门选择。下面用 Fastify 重写上一节完全相同的两个接口：

fastify_articles.mjs · 用 Fastify v5 重写查询、动态参数与新增接口 [Node.js 20+] 
// 安装依赖: npm install fastify
import Fastify from 'fastify';

// 1. 创建实例：logger: true 直接启用内置的 pino JSON 结构化日志（自带请求 ID 与耗时）
const app = Fastify({ logger: true, bodyLimit: 1024 * 1024 });
const articles = [{ id: 1, title: 'Node.js 入门' }];

// 2. GET /api/articles?page=1 —— 直接 return 普通对象，Fastify 自动设 200 状态码并序列化 JSON
app.get('/api/articles', async (request) => {
  const page = Number(request.query.page || 1);
  return { code: 0, page, list: articles };
});

// 3. GET /api/articles/:id —— 自动提取动态路径参数 request.params.id
app.get('/api/articles/:id', async (request, reply) => {
  const item = articles.find((a) => a.id === Number(request.params.id));
  if (!item) return reply.code(404).send({ code: 404, message: '文章不存在' });
  return { code: 0, data: item };
});

// 4. POST /api/articles —— request.body 已自动完成 JSON 解析
app.post('/api/articles', async (request, reply) => {
  const created = { id: articles.length + 1, title: request.body.title };
  articles.push(created);
  return reply.code(201).send({ code: 0, data: created });
});

// 5. 监听 0.0.0.0（容器部署必需，默认只绑 127.0.0.1 会导致容器外部无法访问）
await app.listen({ host: '0.0.0.0', port: 3000 });

实际工作或面试中常会遇到其他几款主流框架，它们的定位与选型边界如下表所示：

框架 核心设计模型 优势与注意事项 推荐选用场景
Express（v5） 线性回调中间件链
(req, res, next)		 历史最久、社区教程与中间件最多；注意老版 v4 不会自动捕获 async 路由抛错，新用务必装 v5+。 快速原型、兼容老项目生态、轻量传统 Web 服务。

05.3 · 接口防线：zod 入参校验、全局统一错误处理与 CORS 跨域配置

05.3 生产接口必备三件套：参数校验（zod）、统一错误兜底与 CORS

刚写后端时最容易犯的错误是直接拿 request.body.price 去算账写库——一旦前端传了字符串 "abc"、负数或漏传字段，就会写出脏数据甚至把服务弄崩。可上线的接口必须在入口统一配齐三道防线：

  • ① 入参校验与自动转换（zod）：声明字段类型、长度范围与默认值（如用 z.coerce.number() 自动把 URL 字符串 "2" 转为数字 2），在 TypeScript 下还能直接用 z.infer<typeof Schema> 推导出静态类型，不用写两遍。
  • ② 全局统一错误处理（setErrorHandler）：业务代码只需抛出语义明确的自定义 AppError(403, '无权操作')；全局处理器统一区分「入参不合法 400」「已知业务错误 4xx」与「未知代码/数据库故障 500（只在服务端日志记录完整堆栈，对客户端隐藏内部表名与路径）」。
  • ③ CORS（Cross-Origin Resource Sharing，跨域资源共享）：当网页前端（如 https://web.example.com）跨域调用 API（https://api.example.com）时，浏览器会先发预检请求（OPTIONS）检查响应头；后端用 @fastify/cors 配置可信域名白名单即可放行。
production_api_guards.mjs · 完整集成 CORS + zod 参数校验 + 统一错误兜底 [Node.js 20+] 
// 安装依赖: npm install fastify @fastify/cors zod
import Fastify from 'fastify';
import cors from '@fastify/cors';
import { z, ZodError } from 'zod';

const app = Fastify({ logger: true });

// 1. 配置 CORS 跨域白名单（注意：当 credentials: true 允许带 Cookie 时，origin 绝不能写 '*'）
await app.register(cors, {
  origin: ['http://localhost:5173', 'https://app.example.com'],
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  credentials: true,
});

// 2. 自定义可预期的业务异常类（携带 HTTP 状态码与业务错误码）
class AppError extends Error {
  constructor(statusCode, message) {
    super(message);
    this.statusCode = statusCode;
  }
}

// 3. 全局统一错误处理：集中收敛 Zod 校验错、业务 AppError 与未知 500 崩溃
app.setErrorHandler((err, request, reply) => {
  if (err instanceof ZodError) {
    return reply.code(400).send({
      code: 400,
      message: '请求参数校验未通过',
      details: err.issues.map((i) => ({ field: i.path.join('.'), reason: i.message })),
    });
  }
  if (err instanceof AppError) {
    return reply.code(err.statusCode).send({ code: err.statusCode, message: err.message });
  }
  // 未知系统异常：服务端记录完整堆栈与 reqId 供排障，对外只返回脱敏提示
  request.log.error({ err }, '未预期的服务端内部错误');
  return reply.code(500).send({ code: 500, message: '服务器开小差了，请稍后重试', reqId: request.id });
});

// 4. 在路由中使用 zod 校验请求体
const CreateOrderSchema = z.object({
  skuId: z.string().min(1, '商品编码不能为空'),
  count: z.number().int().min(1).max(99),
});

app.post('/api/orders', async (request, reply) => {
  // parse 校验不通过会直接抛出 ZodError，自动进入上方的 setErrorHandler 返回 400
  const { skuId, count } = CreateOrderSchema.parse(request.body);
  if (skuId === 'SOLD_OUT') throw new AppError(409, '该商品已售罄');
  return reply.code(201).send({ code: 0, data: { skuId, count } });
});

await app.listen({ host: '0.0.0.0', port: 3000 });
05.4 · 发起外部请求：全局内置 fetch 基础用法与状态码判断避坑

05.4 作为客户端调外部接口：使用内置 fetch

Node.js 全局内置了与浏览器一致的 fetch()（底层基于官方高性能 HTTP 客户端 undici 实现，Node.js 20+ 稳定）。日常调用时只需牢记两点：必加 AbortSignal.timeout() 超时保护，以及显式检查 response.ok（更完整的指数退避重试封装见 07.5 · 调用第三方接口）：

fetch_client.mjs · 发起带超时保护与状态码校验的 POST 请求 [Node.js 20+] 
export async function createRemoteOrder(orderData) {
  const response = await fetch('https://httpbin.org/post', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': 'Bearer my-secret-token',
    },
    body: JSON.stringify(orderData),
    signal: AbortSignal.timeout(3000), // 3 秒超时自动中断请求
  });

  // 关键避坑：fetch 遇到 404 / 500 状态码不会自动抛异常，必须手动检查 response.ok (200~299)
  if (!response.ok) {
    throw new Error(`下游接口返回异常状态码: ${response.status}`);
  }
  return await response.json();
}

本章即时场景题（先想答案，再点击展开）

1. 本地用 Postman 调自己的 Node 接口一切正常，前端同事在浏览器里用 http://localhost:5173 调你的 http://localhost:3000 却报 CORS 错误，为什么 Postman 不报而浏览器报？

同源策略（协议 + 域名 + 端口三者完全一致才算同源）是浏览器为了保护用户浏览器端凭证安全而实施的限制，服务端对服务端调用或 Postman、curl 根本没有同源限制，其实请求已经到达你的 Node 服务甚至可能执行完了，只是响应头里缺少 Access-Control-Allow-Origin 被浏览器拦截不让前端 JS 读取结果。在后端注册 @fastify/cors 把 http://localhost:5173 加入 origin 白名单即可解决（开发环境前端也常用 Vite server.proxy 同源代理转发）。

2. 列表分页接口写了 const limit = Number(request.query.limit || 20)，恶意调用方传了 ?limit=99999999 或 ?limit=abc 会发生什么？怎么用 zod 一行防住？

传 99999999 会触发无上限全表拉取，一次请求就能把数据库和 Node 内存拖垮；传 abc 会算出 NaN 导致 SQL 报错返回 500。用 zod 定义 z.object({ limit: z.coerce.number().int().min(1).max(100).default(20) })，既能把字符串安全转成整数，又能强行把单页上限卡死在 100 条以内，非法入参直接拦截返回清晰的 400 提示。

3. 把 Fastify 服务打进 Docker 镜像运行后，容器日志明明打印了 Server listening at http://127.0.0.1:3000，为什么宿主机访问 localhost:3000 却提示连接被重置？

Fastify 的 app.listen({ port: 3000 }) 在不传 host 时默认只监听回环网卡 127.0.0.1——在 Docker 容器里，127.0.0.1 指的是“仅允许容器自己内部访问”，宿主机端口映射进来的流量走的是容器虚拟网卡 eth0，会被直接拒绝。容器化部署时必须显式写成 app.listen({ host: '0.0.0.0', port: 3000 })。
