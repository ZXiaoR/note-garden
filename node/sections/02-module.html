02.1 · 模块化语法：CommonJS（require / module.exports）与 ES Module（import / export）日常写法

02.1 模块化日常写法：CommonJS 与 ES Module 对照

在实际项目中，我们不会把所有代码都塞进一个文件，而是按功能拆分成多个模块文件。Node.js 支持两套模块化规范：

  • CJS（CommonJS，Node.js 早期传统模块规范）：使用 module.exports 导出、require() 同步导入；在不配置 package.json 的情况下，.js 和 .cjs 文件默认按此规范解析。
  • ESM（ECMAScript Modules，JavaScript 官方标准模块规范）：使用 export 导出、import 导入，与前端浏览器及 TypeScript 语法完全一致；只需在 package.json 中添加一行 "type": "module"（或使用 .mjs 扩展名）即可启用，新项目统一推荐使用 ESM。
CommonJS 写法 · module.exports 与 require() [Node.js 全版本] 
// --- math.cjs（导出模块）---
function add(a, b) {
  return a + b;
}
const PI = 3.14159;

// 将需要对外公开的函数和常量放到 module.exports 对象上
module.exports = { add, PI };

// --- app.cjs（导入模块）---
// 1. 导入内置模块：带上 node: 前缀更清晰
const path = require('node:path');

// 2. 导入本地文件：必须以 ./ 或 ../ 开头
const { add, PI } = require('./math.cjs');
console.log(add(2, 3), PI); // 输出: 5 3.14159
ES Module 写法 · export 与 import（现代项目推荐）[Node.js 20+] 
// --- math.js（package.json 已声明 "type": "module"）---
export function add(a, b) {
  return a + b;
}
export const PI = 3.14159;

// 也可以设置一个默认导出（每个文件最多一个 export default）
export default function multiply(a, b) {
  return a * b;
}

// --- app.js（在 ES Module 中导入本地文件须写完整扩展名）---
import multiply, { add, PI } from './math.js';
console.log(add(2, 3), multiply(4, 5)); // 输出: 5 20
导入路径写法分类 代码示例 Node.js 的查找规则说明
1. 内置核心模块 import fs from 'node:fs/promises' 以 node: 开头，直接加载 Node.js 编译在可执行文件内的系统模块，优先级最高，不会与 node_modules 中的同名第三方包冲突。
2. 本地相对路径文件 import { add } from './utils/math.js' 以 ./ 或 ../ 开头，按相对于当前文件的路径查找；在 ES Module 模式下要求显式写出文件扩展名（如 .js 或直跑 TS 时的 .ts）。
3. 第三方依赖包 import Fastify from 'fastify' 不带路径前缀的裸包名，Node.js 会自动在当前目录及上级目录的 node_modules/ 文件夹中查找对应的包。
02.2 · 工程配置与依赖管理：package.json 常用字段、语义化版本号与 npm / pnpm 命令

02.2 package.json 核心字段解析与 npm / pnpm 日常命令

每个 Node.js 项目的根目录下都有一个 package.json 文件，它是整个项目的配置清单——既声明了模块规范、运行引擎版本与快捷脚本（scripts），也记录了生产依赖与开发依赖的版本范围：

package.json · 标准后端项目配置文件逐行详解 [Node.js 22+] 
{
  "name": "user-service",
  "version": "1.0.0",
  // 声明当前项目下所有 .js 文件默认采用 ES Module (import/export) 语法
  "type": "module",
  // 约束团队与线上环境的最低 Node.js 版本
  "engines": { "node": ">=22.18.0" },
  // 自定义快捷脚本：通过 npm run <脚本名> 即可执行
  "scripts": {
    "dev": "node --watch --env-file=.env src/server.js",
    "start": "node src/server.js",
    "test": "node --test"
  },
  // 生产环境运行必需的依赖包（npm install <包名>）
  "dependencies": {
    "fastify": "^5.2.0",
    "zod": "^3.24.0"
  },
  // 仅在本地开发、类型检查或格式化时用到的工具包（npm install -D <包名>）
  "devDependencies": {
    "eslint": "^9.18.0"
  }
}
Terminal · 初始化项目与管理依赖常用命令 
# 1. 在新目录中快速生成默认的 package.json
$ npm init -y

# 2. 安装生产环境依赖（自动写入 dependencies 并更新 package-lock.json）
$ npm install fastify zod

# 3. 安装仅开发阶段使用的依赖（写入 devDependencies）
$ npm install -D eslint

# 4. 执行 package.json 中 scripts 定义的脚本
$ npm run dev
$ npm test

# 5. 线上构建或团队拉代码后，严格按锁文件原样还原依赖（不改写 lock 文件）
$ npm ci
管理依赖的两条工程规范与背后原理：
1. 读懂语义化版本号 SemVer（Semantic Versioning，主版本.次版本.补丁号）："^5.2.0" 中的插入符 ^ 允许在不跨大版本的前提下升级新特性与补丁（即 >=5.2.0 <6.0.0）；波浪号 "~5.2.0" 则只允许升级最后一位补丁号（<5.3.0）。
2. 必须把锁文件（package-lock.json 或 pnpm-lock.yaml）提交到 Git 仓库：锁文件锁定了整棵依赖树每个子包的精确版本与完整性哈希，防止本地能跑、线上部署时因某个次版本更新而报错。
背后的原理：为什么 CommonJS 里改了导出的变量外部感知不到，而 ES Module 却能实时同步？两个文件互相 import 循环依赖时谁先执行？详见 《核心原理篇 · 01 模块加载底层、值拷贝 vs 实时绑定与循环依赖》 ↗。

本章即时场景题（先想答案，再点击展开）

1. 新建 app.js 写了一行 import fs from 'node:fs/promises'，运行 node app.js 报错 SyntaxError: Cannot use import statement outside a module，怎么解决？

这是因为在没有配置的默认情况下，Node.js 会把 .js 文件当作旧版 CommonJS 模块解析。有两种标准改法：① 项目级推荐做法：在根目录 package.json 中加上 "type": "module"，此后整个项目的 .js 文件都默认支持 import / export（个别老脚本若仍需用 require，把后缀改成 .cjs 即可）；② 单文件脚本做法：直接把文件名改为 app.mjs。

2. 前端写 Vite/Webpack 习惯了省略后缀 import { sum } from './utils/math'，原封不动搬到 Node.js ESM 项目里为什么会报 ERR_MODULE_NOT_FOUND？

前端打包工具在构建期帮我们做了多次磁盘探测（依次尝试补全 .ts / .tsx / .js / index.js）；而 Node.js 的原生 ES Module 加载器为了与浏览器 URL 加载规范对齐并避免多余的磁盘查找开销，要求导入本地相对路径模块时必须显式写全文件扩展名（如 './utils/math.js'，在 Node 22.18+ 直接跑 TS 且开启对应 TS 配置时可写 './utils/math.ts'）。

3. 在 Dockerfile 或 CI（持续集成）流水线里安装依赖时，为什么应该用 npm ci（或 pnpm install --frozen-lockfile）代替 npm install？

npm install 在遇到 "^3.24.0" 这类范围版本号且锁文件不匹配时，可能会去拉取刚发布的 3.25.0 并静默改写锁文件，造成“我电脑上是 3.24.0 没问题，发到线上装了 3.25.0 崩了”。而 npm ci 会严格按照 package-lock.json 里的精确版本和校验和安装，一旦发现 package.json 与锁文件不一致就直接报错中止构建，确保测试环境与生产环境的依赖分毫不差。
