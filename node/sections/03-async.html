03.1 · 异步语法演进：错误优先回调（Error-First Callback）、Promise 与 async / await

03.1 异步编程写法：从回调函数到 async / await

在 Node.js 中，读取文件、查询数据库或请求外部接口都是非阻塞异步操作——发起调用后主线程不会停在原地等待，而是先去接待其他用户的请求，等底层结果准备好后再恢复后续逻辑。Node.js 的异步写法经历了两代演进：

  • 早期传统写法（Error-First Callback，错误优先回调）：把回调函数作为最后一个参数传入，约定固定签名 (err, data) => {}——操作出错时 err 为错误对象，成功时 err 为 null、data 为返回结果。
  • 现代标准写法（Promise + async / await）：Node.js 内置模块如今均提供了 Promise 版本（如 node:fs/promises、node:timers/promises），配合 async / await 可以用扁平的线性代码表达异步流程。
callback_vs_promisify.mjs · 传统回调与 util.promisify 转换 [Node.js 20+] 
import fs from 'node:fs';
import { promisify } from 'node:util';

// 1. 传统错误优先回调：第一个参数永远是 err，第二个参数是结果
fs.readFile('./package.json', 'utf8', (err, text) => {
  if (err) {
    console.error('读取失败:', err.message);
    return;
  }
  console.log('读取成功，字符数:', text.length);
});

// 2. 若遇到老旧第三方库只提供回调接口，可用 util.promisify 一键转为 Promise
const readFileAsync = promisify(fs.readFile);
async_await.mjs · 现代 async/await 与并行读取写法 [Node.js 20+] 
import fs from 'node:fs/promises';
import { setTimeout as sleep } from 'node:timers/promises';

async function loadProjectMeta() {
  // 1. 两个互不依赖的异步读取：用 Promise.all 同时发起，总耗时只取决于较慢的那个
  const [pkgRaw, readmeRaw] = await Promise.all([
    fs.readFile('./package.json', 'utf8'),
    fs.readFile('./README.md', 'utf8'),
  ]);

  // 2. 内置 timers/promises 提供无需手写 new Promise 的非阻塞延时等待
  await sleep(50);
  return { pkg: JSON.parse(pkgRaw), readmeLen: readmeRaw.length };
}

console.log(await loadProjectMeta());
03.2 · 并发任务编排：Promise.all / allSettled / race / any 四种组合方法对比

03.2 多个异步任务同时发起时，四种 Promise 组合方法怎么选

当需要同时发起多个互不依赖的异步调用时，如果在 for 循环里逐个写 await，会退化成“等上一个结束才发下一个”的串行等待。根据业务对“部分失败”的容忍度，从下面四个标准组合器中选择：

组合方法 成功与失败触发规则 典型适用场景
Promise.all([...]) 全部成功才返回结果数组；只要有 1 个失败，整体立即抛出该异常。 订单详情页同时拉取「订单主表 + 商品明细」（缺一不可）。
Promise.allSettled([...]) 永不抛出异常；等所有任务结束后，逐项返回 { status: 'fulfilled', value } 或 { status: 'rejected', reason }。 批量给 50 个用户发站内信、首页聚合含非核心推荐模块（允许局部降级）。
Promise.race([...]) 哪个任务最先敲定（无论成功还是失败），就采用谁的结果。 给不支持信号取消的老旧第三方 SDK 调用包裹一层超时竞速。
Promise.any([...]) 哪个任务最先成功就返回谁；全部都失败时才抛出 AggregateError。 同时向主备两个存储源或 CDN 节点探测资源，取最快可用响应。
03.3 · 生产防线：未捕获 Promise 导致进程退出、并发数上限控制与 AbortController 取消机制

03.3 后端必补三件事：防崩错误兜底、并发数限制与超时取消

在浏览器里，某次异步请求漏写了 catch 顶多在控制台印一行红字，页面还能继续点；但在 Node.js 后端（自 Node 15+ 起默认行为），任何一个无人捕获的失败 Promise（UnhandledPromiseRejection）都会直接让整个 Node.js 进程退出——意味着正在这台进程上处理的其他几百个正常用户请求也会瞬间全部断线。

async_error_trap.mjs · 两个极易漏捕的异步异常与进程级兜底 [Node.js 20+] 
async function queryRisk() {
  throw new Error('风控服务连接超时');
}

// ❌ 常见误区 ①：在 try 块里写 return queryRisk() 而漏掉了 await
//    函数直接把 Promise 原样返回了，外层当前 try/catch 根本抓不到它的报错
// ✅ 正确写法：在 try 块内返回 Promise 时务必写成 return await queryRisk()
export async function safeCheck() {
  try {
    return await queryRisk();
  } catch (err) {
    console.warn('风控降级放行:', err.message);
    return { pass: true, degraded: true };
  }
}

// ❌ 常见误区 ②：“发后不管”的异步上报（queryRisk() 不 await 也不 .catch）
//    一旦报错就会触发 unhandledRejection 直接杀死进程
queryRisk().catch((err) => console.error('后台异步上报失败:', err.message));

// 进程级最后防线：在 server.js 入口记录告警日志并安全停机退出
process.on('unhandledRejection', (reason) => {
  console.error('[致命告警] 存在未捕获的 Promise 拒绝:', reason);
});
concurrency_limit.mjs · 限制最大并发数（防止 Promise.all 打挂下游）[Node.js 20+] 
// 若有 1000 个任务直接 Promise.all，会瞬间打满连接池或触发对方 429 限流。
// 下面用 16 行代码实现通用的「固定窗口并发执行器」（工程中也可装 p-limit 库）：
export async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let cursor = 0; // 单线程下共享游标天然无竞争，谁先干完谁领下一个下标

  async function worker() {
    while (cursor < items.length) {
      const index = cursor++;
      results[index] = await fn(items[index], index);
    }
  }
  // 仅启动 Math.min(limit, items.length) 个并发工作流
  const workers = Array.from({ length: Math.min(limit, items.length) }, worker);
  await Promise.all(workers);
  return results;
}

// 用法示例：10 个 ID 最多同时跑 3 个请求，结果顺序与原数组严格一致
const ids = [1, 2, 3, 4, 5, 6];
const res = await mapLimit(ids, 3, async (id) => `user-${id}`);
console.log(res);

超时与主动取消（AbortController 与 AbortSignal）：所有外部调用都必须设超时上限，而且当客户端提前关掉网页时，服务端应该立刻中止正在跑的慢操作以节省资源。现代 Node.js 统一使用标准 AbortController 将取消信号贯穿到底层网络与定时器中：

abort_timeout.mjs · 组合「3 秒自动超时」与「外部手动取消」双信号 [Node.js 20.3+] 
export async function fetchWithCancel(url, clientAbortSignal) {
  // AbortSignal.any (Node 20.3+)：无论是「满 3000ms 超时」还是「外部传入信号触发取消」，都会立即中断底层 Socket
  const signals = [AbortSignal.timeout(3000)];
  if (clientAbortSignal) signals.push(clientAbortSignal);

  try {
    const res = await fetch(url, { signal: AbortSignal.any(signals) });
    return await res.json();
  } catch (err) {
    // 区分是超时触发 (TimeoutError) 还是调用方主动取消 (AbortError)
    if (err.name === 'TimeoutError') throw new Error(`请求下游超时 (>3s): ${url}`);
    if (err.name === 'AbortError') console.log('调用方已主动取消请求，停止等待');
    throw err;
  }
}

// 本地可直接运行验证主动取消：
const ctrl = new AbortController();
setTimeout(() => ctrl.abort(), 50); // 50ms 后主动取消
await fetchWithCancel('https://example.com', ctrl.signal).catch(() => {});
03.4 · 事件发布订阅：EventEmitter 常用方法与单主线程非阻塞原则

03.4 事件发布与订阅（EventEmitter）及主线程保护原则

Promise 适合表达“发起一次、返回一次结果”的操作；而当一个对象会在生命周期内反复触发多次事件（例如 HTTP 服务持续收到请求、客户端连接断开、文件流一段段读出数据）时，Node.js 统一使用内置 node:events 模块的 EventEmitter：

  • emitter.on(事件名, fn) / emitter.off(事件名, fn)：持续监听事件，以及在不用时解绑释放内存（注意：绝不要在每次 HTTP 请求里给全局对象挂 .on 却不解绑，否则会造成监听器内存泄漏）；
  • emitter.once(事件名, fn)：只监听一次，触发后自动移除；
  • emitter.on('error', fn)（必写规范）：'error' 在 EventEmitter 中是特殊事件——如果触发了 emit('error', err) 却没有任何监听器接住它，Node.js 会直接当作未捕获异常让进程退出。
order_events.mjs · 使用 EventEmitter 解耦进程内事件通知 [Node.js 20+] 
import { EventEmitter } from 'node:events';

const orderBus = new EventEmitter();

// 1. 始终先绑定 'error' 事件兜底，防止异常无人接收导致进程崩溃
orderBus.on('error', (err) => console.error('[事件总线异常]:', err.message));

// 2. on 持续监听每次支付事件；once 仅在首单时触发一次后自动解绑
orderBus.on('paid', (orderId, amount) => {
  console.log(`[库存] 订单 ${orderId} 支付 ￥${amount}，已扣减`);
});
orderBus.once('paid', (orderId) => {
  console.log(`[首单礼] 首次支付奖励已发放: ${orderId}`);
});

orderBus.emit('paid', 'ORD-101', 99); // 触发库存 + 首单礼
orderBus.emit('paid', 'ORD-102', 58); // 仅触发库存
为什么永远不要阻塞主线程？在请求处理链路中切勿调用 fs.readFileSync 等以 Sync 结尾的同步函数，也不要跑秒级大循环或回溯正则表达式——因为单个 Node.js 进程靠一条主线程上的事件循环轮流响应成百上千个并发回调，某处同步卡顿 300ms 就等于所有在线用户一起卡顿 300ms。底层调度顺序详见 《核心原理篇 · 02 libuv 事件循环六大阶段与微任务优先级》 ↗。

本章即时场景题（先想答案，再点击展开）

1. 下面的代码明明包了 try / catch，为什么 saveLog() 报错时还是把整个 Node 服务弄崩退出了？
async function handler() { try { return saveLog(); } catch (e) { console.error(e); } }

因为在 try 块里写了 return saveLog() 而没有写 await。handler 只是同步拿到了一个尚在执行中的 Promise 对象并直接退出了 try 作用域；等几毫秒后该 Promise 异步变成 rejected 时，早已不在当前 try / catch 的保护范围内了。若上层调用方也没捕获它，就会触发 unhandledRejection 导致进程退出。修复方法是在 try 块内始终写成 return await saveLog()。

2. 运营导入了一份含 5,000 个商品 ID 的表格，需要逐个调外部接口同步库存，直接写 await Promise.all(ids.map(syncOne)) 会出什么问题？怎么改？

ids.map(syncOne) 会在同一毫秒内瞬间向对方服务器砸出 5,000 个并发连接，轻则被对方网关触发 429 Too Many Requests 封禁 IP，重则耗尽本机端口与内存。应改用本章的 mapLimit(ids, 10, syncOne)（或 p-limit(10)）将同时在途请求数控制在 10 个以内，并对单条失败用 try / catch 收集错误列表以便汇总重试，而不是一条失败就让整批作废。

3. 用 Promise.race([fetch(url), sleep(3000)]) 做超时控制，和用 fetch(url, { signal: AbortSignal.timeout(3000) }) 有什么本质区别？

Promise.race 只是让你的业务代码在 3 秒后“不再等结果了”，但底层的 HTTP 网络请求其实还在后台继续占着连接收发数据；如果下游响应体很大，依然会白白消耗带宽和内存。而传入 AbortSignal.timeout(3000) 会在满 3 秒的瞬间直接关闭底层 Socket 连接并通知内核中止传输，是真正意义上的取消。
