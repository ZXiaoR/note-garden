00.1 · 运行时定位：服务器上的 JavaScript 运行时、与浏览器的差异及五大系统角色

00.1 Node.js 是什么，以及它在系统里干什么

一句话定义：Node.js 是一个让 JavaScript 脱离浏览器、直接在服务器和本地操作系统上运行的跨平台 JavaScript 运行时（Runtime）。它底层基于 Google Chrome 的 V8 引擎（负责解析执行 JS 代码）与跨平台异步库 libuv（负责文件、网络与事件循环调度）构建。

对于熟悉前端开发的读者，最直观的理解方式是对照「同样写 JavaScript，在浏览器里跑和在 Node.js 里跑有什么不同」：

对比维度 浏览器 JavaScript（前端环境） Node.js（服务端与本地环境）
没有了什么 拥有 window、document、localStorage 等 DOM（Document Object Model，文档对象模型）与 BOM（Browser Object Model，浏览器对象模型）接口。 没有页面与界面概念，直接访问 window 或 document 会报 ReferenceError。
多出了什么 出于安全沙箱隔离，网页脚本不能任意读写用户硬盘或监听本机端口。 直接拥有系统级能力：读写磁盘文件（node:fs）、监听端口收发网络请求（node:http / net）、操作原始二进制内存（Buffer）、管理环境变量与子进程（process / child_process）。
完全共用的部分 核心 ECMAScript 语法（解构、箭头函数、Map / Set、Promise、async / await、ES Module import / export）以及现代 Web 标准全局接口（fetch、URL、AbortController、crypto.randomUUID()、TextEncoder）。

在真实互联网系统与日常研发流程中，Node.js 主要承担以下五类核心角色（见下方系统位置图）：

  • ① API（Application Programming Interface，应用程序编程接口）业务后端：直接连 MySQL 与 Redis，开发完整的中小型 Web 后端、管理后台或小程序接口，前后端可共用一套 TypeScript 类型与参数校验规则。
  • ② BFF（Backend For Frontend，服务于前端的后端聚合层）：当移动端一个页面需要拼装商品、评价、优惠券 3 个内部微服务的数据时，由 Node.js 并发请求下游、裁剪无用字段后一次性返回前端，减少弱网下的多次请求往返。
  • ③ SSR（Server-Side Rendering，服务端渲染）：如 Next.js、Nuxt，在服务器上先拉取数据把组件渲染成完整 HTML 字符串返回给浏览器，兼顾首屏展示速度与搜索引擎收录。
  • ④ 实时服务与流式网关：基于单进程维护数万并发长连接的优势，开发在线协作、聊天室（WebSocket）或大模型逐字流式转发网关（SSE，Server-Sent Events，服务器推送事件）。
  • ⑤ CLI（Command-Line Interface，命令行界面）与前端工具链：日常使用的 Vite、Webpack、ESLint、脚手架生成器和自动化批处理脚本，几乎全部运行在 Node.js 之上。
00.2 · 选型边界：什么时候不该用 Node.js，以及与 Go、Java、Python 的对比结论

00.2 什么时候不该用 Node.js（与主流后端语言选型对照）

Node.js 的特长是「I/O（Input/Output，输入与输出）密集型」任务——查数据库、调外部接口、转发文件流时，等待时间由操作系统内核接管，主线程不干等，因此单机少量内存就能撑起高并发连接。
反过来，它的明确短板是「CPU（Central Processing Unit，中央处理器）密集型同步计算」：由于所有请求的 JavaScript 业务代码默认跑在同一个主线程上，如果某个接口直接在主线程里执行视频编解码、高清图片像素滤镜、几十万行 Excel 同步解析或模型本地推理，假设计算耗时 500ms，这半秒钟内整台进程就像关门暂停营业一样，其他几百个并发请求哪怕只是查个健康状态也会全部卡住。

遇到重计算需求时的三条工程出路：
1. 偶发的局部计算（如生成一张带水印海报、解析大文件）：放到 Node.js 内置的 node:worker_threads 工作线程里算，不阻塞主线程（见 06 · 进程与线程）；
2. 耗时长且允许异步出结果（如视频转码、全量报表导出）：接口写入消息队列后立即返回“处理中”，由独立的后台 Worker 慢慢消费（见 07.6 · 后台任务与队列）；
3. 核心业务本身就是高吞吐重计算或 AI 推理：直接选用更契合的后端语言编写该服务，不要强行用 Node.js 硬扛。
选型维度 Node.js（TypeScript） Go Java（Spring 生态） Python

本章即时场景题（先想答案，再点击展开）

1. 移动端App首页需要同时读取「用户信息、未读消息数、推荐商品列表」三个内部微服务的数据并裁剪多余字段，适合用 Node.js 做这层服务吗？为什么？

非常适合，这就是典型的 BFF（服务于前端的后端聚合层）场景。三个下游请求全部是网络 I/O 等待，Node.js 可以用 Promise.all 并发发起，总耗时只取决于最慢的那个接口，且天然擅长快速拼装与裁剪 JSON 结构，前后端还能直接共享一套 TypeScript 接口类型定义。

2. 业务需要做一个「上传 1080P 视频后实时逐帧加水印并重编码为 MP4」的接口，如果直接在 Node.js 请求处理函数里用纯 JS 循环算像素会发生什么？

会导致整个服务在算视频期间完全假死。因为所有请求的 JS 代码共用一个主线程，重度 CPU 运算占满主线程的几秒到几十秒里，其他用户的登录、查询、健康检查请求全部在事件队列里干等超时。正确做法是将上传落盘与转码解耦：接口拿到文件后往消息队列投递一条转码任务立即返回任务 ID，由独立的后台 Worker 调用 C++ 编写的 ffmpeg 子进程或专用计算服务异步处理。

3. 把前端项目里的工具函数直接复制到 Node.js 后端复用时，哪类代码能直接跑，哪类代码会直接报错？

纯逻辑与现代标准接口可以直接跑（如日期格式化、金额精度处理、zod 表单校验规则、fetch 请求封装、URL 解析）；凡是触碰浏览器专属宿主对象的代码都会报 ReferenceError（如读写 window.location、document.cookie、localStorage）——在服务端，配置从 process.env 读，Cookie 和请求路径从每次请求传入的 req 对象上读，持久化数据则存进数据库或 Redis。
