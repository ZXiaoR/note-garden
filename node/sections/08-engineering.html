08.1 · 工程目录架构：企业级 Node.js 服务的标准四层目录（routes / controllers / services / repositories）

08.1 标准后端项目的分层目录结构是怎么划分的

写单文件脚本时把路由和 SQL 混在一起很快，但当项目增长到几十个接口时，混写会导致改一处牵全身、也没法单独写测试。生产级 Node.js 服务普遍采用职责分明的四层目录结构（路由与插件层 → 控制器层 → 业务逻辑层 → 数据访问层）：

order-service/ · 可上线的 TypeScript 后端标准目录树 
order-service/
├── package.json            # 依赖与脚本（声明 "type": "module"）
├── tsconfig.json           # TypeScript 编译与严格类型检查配置
├── Dockerfile              # 多阶段生产容器构建文件
├── .env.example            # 环境变量模板（真实 .env 列入 .gitignore）
├── src/
│   ├── server.ts           # 【进程入口】监听端口、挂载 SIGTERM 优雅停机
│   ├── app.ts              # 【应用组装】注册日志、CORS、错误处理与路由（供测试直接注入）
│   ├── config/
│   │   └── env.ts          # 用 zod 校验 process.env，缺关键配置启动即报错
│   ├── plugins/
│   │   └── auth.ts         # 【横切插件/中间件】JWT 鉴权、数据库连接挂载
│   ├── routes/
│   │   └── order.route.ts  # 【路由层】绑定 URL 路径、入参 Schema 与 Controller
│   ├── controllers/
│   │   └── order.ctrl.ts   # 【控制器层】提取请求参数，调 Service，组装 HTTP 状态码
│   ├── services/
│   │   └── order.svc.ts    # 【业务逻辑层】纯业务计算与事务编排（不碰 req / reply）
│   └── repositories/
│       └── order.repo.ts   # 【数据访问层】集中封装 MySQL SQL 与 Redis 读写
└── test/
    └── order.test.ts       # 【自动化测试】使用内置 node:test 做单元与接口测试
为什么要这样拆？（三条核心工程收益）
  • server.ts 与 app.ts 分离：app.ts 只组装路由而不调用 listen(端口)，跑自动化测试时直接用 app.inject() 内存模拟发请求，速度快且不会报端口冲突。
  • services/ 不接触 HTTP 对象：业务逻辑层只接收普通参数并返回业务对象——将来无论是 HTTP 接口调它、CLI 脚本调它还是消息队列消费者调它，代码一行都不用改。
  • repositories/ 收敛存储细节：所有 SQL 和缓存键名集中在一处，改表结构或换驱动时不会波及上层业务规则。
08.2 · TypeScript 接入与单元测试：原生直跑 .ts（Node 22.18+ / 24+）、tsconfig.json 与 node --test

08.2 接入 TypeScript 与内置 node --test 自动化测试

过去在 Node.js 里跑 TypeScript 要折腾 ts-node 或复杂的构建加载器。如今 Node.js 已内置原生类型剥离（Type Stripping）能力，版本要求与分工非常清晰：

  • 开发时怎么直接跑 TS：在 Node.js 22.18+ / 24+ / 26+ 中，直接执行 node --watch --env-file=.env src/server.ts 即可开箱运行（若在较早的 v22.6 ~ v22.17 上需加 --experimental-strip-types 参数）。
  • 两个必知边界：① Node 运行时只负责“把 : string、interface 等类型标记擦除成空白直接跑 JS”，不做类型错误检查，因此发版与 CI 时仍需执行 tsc --noEmit 检查类型安全；② 原生擦除不支持需要生成额外 JS 代码的旧特性（如 enum、namespace），在 tsconfig.json 中开启 "erasableSyntaxOnly": true（TypeScript 5.8+）即可让编辑器提前标红提醒。生产环境推荐在构建镜像时执行 tsc 编译出纯 dist/*.js 运行，省去启动擦除开销且镜像无需携带开发依赖。
tsconfig.json & package.json · 现代 Node TS 标准配置 [Node.js 22.18+ / TS 5.8+] 
// 安装开发依赖: npm install -D typescript @types/node
// --- tsconfig.json ---
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "NodeNext",           // 对齐 Node.js 原生 ESM 解析规则
    "moduleResolution": "NodeNext",
    "rootDir": "./src",
    "outDir": "./dist",
    "strict": true,                 // 开启全套严格空值与类型检查
    "erasableSyntaxOnly": true,     // 禁止 enum 等不可直接擦除的语法，完美兼容 node 直跑
    "verbatimModuleSyntax": true,   // 强制纯类型导入写 import type { User } from ...
    "skipLibCheck": true
  },
  "include": ["src/**/*"]
}

// --- package.json 中的 scripts 配法 ---
// "dev":       "node --watch --env-file-if-exists=.env src/server.ts"
// "typecheck": "tsc --noEmit"
// "build":     "tsc"
// "start":     "node dist/server.js"
// "test":      "node --test test/*.test.ts"
test/order.test.ts · 用内置 node:test 直接测 TS 业务与接口 [Node.js 22.18+] 
// 无需安装 Jest / Vitest：node --test 原生支持直接运行 .test.ts 测试文件
import { test, describe } from 'node:test';
import assert from 'node:assert/strict';
import Fastify from 'fastify';

// 示例：被测的应用组装函数 buildApp()
function buildApp() {
  const app = Fastify();
  app.post<{ Body: { item: string; price: number } }>('/api/orders', async (req, reply) => {
    if (!req.body.item || req.body.price <= 0) {
      return reply.code(400).send({ message: '价格必须大于 0' });
    }
    return reply.code(201).send({ id: 1, ...req.body });
  });
  return app;
}

describe('POST /api/orders 接口测试', () => {
  test('合法入参返回 201，非法价格拦截返回 400', async () => {
    const app = buildApp();
    // app.inject 在内存里模拟发请求，无需真正占用网卡端口
    const okRes = await app.inject({ method: 'POST', url: '/api/orders', payload: { item: '键盘', price: 299 } });
    assert.equal(okRes.statusCode, 201);

    const badRes = await app.inject({ method: 'POST', url: '/api/orders', payload: { item: '键盘', price: -5 } });
    assert.equal(badRes.statusCode, 400);
    await app.close();
  });
});
08.3 · 可观测与配置基线：环境变量启动校验、pino 结构化脱敏日志与健康检查探针

08.3 配置校验、结构化日志（pino）与健康检查接口

把服务真正放到线上运行前，需要补齐三项基础设施：

  • ① 配置启动即校验（Fail-Fast）：用 zod 在进程启动第一秒校验 process.env——运维若漏配了 JWT_SECRET，容器启动当场报错拦截，绝不带病上线。
  • ② 结构化 JSON 日志与敏感字段脱敏（pino）：线上不要用 console.log 打自由格式文本（多行堆栈混在一起无法在日志平台检索）。Fastify 内置的 pino 每条日志输出单行 JSON（自动附带请求唯一 reqId 与耗时 responseTime），并可通过 redact 自动把密码与 Token 掩码成 [Redacted]。
  • ③ 存活与就绪双健康检查（/healthz 与 /readyz）：网关和 Kubernetes 靠轮询健康接口判断实例状态——/healthz 确认进程事件循环未卡死；/readyz 检查 MySQL / Redis 连通性，且在收到停机信号准备退出期间主动返回 503 通知网关先把新流量切走。
env_logger_health.mjs · 启动配置强校验 + pino 脱敏日志 + 健康检查完整模板 [Node.js 20+] 
import Fastify from 'fastify';
import crypto from 'node:crypto';
import { z } from 'zod';

// 1. 启动时强校验环境变量：缺必填项或格式不对立即打印清晰原因并终止启动
const EnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().int().positive().default(3000),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
});
export const env = EnvSchema.parse(process.env);

// 2. 配置 pino 结构化日志：透传上游网关 x-request-id，并自动脱敏 Authorization 与密码字段
export const app = Fastify({
  genReqId: (req) => req.headers['x-request-id'] || crypto.randomUUID(),
  logger: {
    level: env.LOG_LEVEL,
    redact: ['req.headers.authorization', 'req.headers.cookie', 'body.password'],
  },
});

// 3. 健康检查接口（停机摘流期间 isShuttingDown 置为 true，让负载均衡器停止向本机派单）
let isShuttingDown = false;
export function markShuttingDown() { isShuttingDown = true; }

app.get('/healthz', async () => ({ status: 'ok', uptime: process.uptime() }));

app.get('/readyz', async (_req, reply) => {
  if (isShuttingDown) return reply.code(503).send({ status: 'draining' });
  // 真实项目中在此并行探测: await Promise.all([pool.query('SELECT 1'), redis.ping()]);
  return { status: 'ready' };
});

背后的原理：如果在深层 Service / Repository 函数里不想一层层手动把 request.log 当参数往下传，却仍想让每条日志自动带上当前请求的 traceId，Node.js 内置的 AsyncLocalStorage 是怎么做到的？详见 《核心原理篇 · 06.2 AsyncLocalStorage 异步上下文追踪》 ↗。

08.4 · 部署上线：生产级多阶段 Dockerfile、容器 vs PM2 运行方式与零损优雅停机

08.4 部署上线：Docker 镜像、PM2 与容器运行规范

根据团队基础设施形态，Node.js 服务上线主要有两种标准运行方式（切忌混用）：

  • 方式 A · Docker / Kubernetes 容器化部署（现代主流）：每个容器只跑单个 node 进程（不要在容器里再套 PM2），利用多核与崩溃重启全部交给 K8s 编排多个容器副本（Pod）完成；Dockerfile 的 CMD 必须用 ["node", "dist/server.js"] 直接启动（不要写 CMD npm start，因为 npm 包裹层可能无法及时把 SIGTERM 信号转发给 Node 进程，导致滚动发版时优雅停机失效被强杀）。
  • 方式 B · 云主机（ECS / VPS）直接部署：没有容器编排层时，使用进程管家 PM2 开启 cluster 模式按核数拉起多个 Worker 进程，发版时用 pm2 reload 实现零停机滚动更新（底层即 原理篇 05.2 的 Cluster IPC 滚动替换）。
Dockerfile · 多阶段构建生产最小镜像（非 root 运行）[Node.js 24 LTS] 
# --- 阶段 1：安装全量依赖并编译 TypeScript ---
FROM node:24-alpine AS builder
WORKDIR /app
# 先单独拷贝锁文件利用 Docker 层缓存，源码改动时不重装依赖
COPY package.json package-lock.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# --- 阶段 2：纯净生产运行镜像（不含 TS 编译器与源码）---
FROM node:24-alpine
WORKDIR /app
ENV NODE_ENV=production
# 使用官方镜像自带的低权限 node 用户运行，避免 root 容器逃逸风险
USER node
COPY --chown=node:node --from=builder /app/package.json ./
COPY --chown=node:node --from=builder /app/node_modules ./node_modules
COPY --chown=node:node --from=builder /app/dist ./dist
EXPOSE 3000
# 直接 exec 启动 node，确保第一时间收到容器平台的 SIGTERM 信号
CMD ["node", "dist/server.js"]
server.ts 与 ecosystem.config.cjs · 优雅停机闭环与裸机 PM2 配置 
// --- 1. src/server.ts（完整生产启动与优雅停机顺序）---
import { app, env, markShuttingDown } from './app.js';

await app.listen({ host: '0.0.0.0', port: env.PORT });

async function gracefulShutdown(signal: string) {
  app.log.info(`收到 ${signal}，开始摘流与优雅停机...`);
  markShuttingDown();   // ① /readyz 切 503，通知网关切走新流量
  await app.close();    // ② 停止接新连接，等正在跑的请求全部响应完毕
  // await Promise.all([pool.end(), redis.quit()]); // ③ 安全关闭数据库/缓存连接池
  process.exit(0);
}
process.once('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.once('SIGINT', () => gracefulShutdown('SIGINT'));

08.5 · 线上排障手册：内存泄漏、CPU 100% 飙高与事件循环卡顿怎么快速定位

08.5 线上排障速查：内存越来越大、CPU 飙高怎么定位

线上报警响起时，先不要盲目重启把现场抹掉（多实例下可先把报警的那 1 台实例从负载均衡摘流保留现场），按下面这张三步诊断表直接定位根因：

线上故障现象 第一步：查指标分清方向 第二步：保留现场采样命令 最高发根因与底层原理深挖
1. 内存随运行时间阶梯上涨直至 OOM 重启 看 process.memoryUsage()：
• heapUsed 持续涨 = JS 对象泄漏；
• heapUsed 平稳但 rss / external 暴涨 = 堆外 Buffer 或流积压。		 启动加 --heapsnapshot-signal=SIGUSR2；间隔 5 分钟发两次 kill -USR2 <PID> 抓两份堆快照，进 Chrome DevTools 切 Comparison 对比净增对象。 ① 全局 Map 缓存没设上限或 TTL；② 请求内对全局对象挂 .on() 没解绑；③ 裸 .pipe() 客户端断连漏关流。
➔ 详见 原理篇 04.4 堆快照排查
2. 单核 CPU 飙到 100%，所有接口包括 /healthz 全超时 看 monitorEventLoopDelay 的 P99 延迟飙到几百毫秒以上，而数据库和下游监控全部空闲。 压测复现用 node --cpu-prof app.js（线上动态挂诊断会话），把 .cpuprofile 拖进 Chrome DevTools 看火焰图里横向最宽的平顶函数。 ① 复杂正则遇恶意长字符串触发灾难性回溯（ReDoS）；② 主线程同步 JSON.parse/stringify 几十 MB 超大报文或死循环。
➔ 详见 原理篇 06.3 延迟监控与火焰图
3. CPU 和内存都不高，但接口响应集体变慢甚至挂死 看连接池活跃数、下游 RTT，以及是否存在大量处于 pending 的异步调用。 查结构化错误日志是否有超时告警，检查数据库活跃连接数 SHOW PROCESSLIST。 ① 下游第三方接口卡死且 fetch 没设 AbortSignal.timeout；② 数据库事务报错漏调 conn.release() 借光连接池；③ 慢文件/加解密占满 libuv 默认 4 线程池（原理篇 02.3）。

本章即时场景题（先想答案，再点击展开）

1. 同事在 Kubernetes 容器的 Dockerfile 里写了 RUN npm install -g pm2 并用 pm2-runtime start app.js -i 4 启动，为什么在容器化环境里不推荐这样做？

在 Kubernetes 中，容器编排器本身就已经承担了“进程守护、崩溃重启、健康探针摘流、按 CPU 负载水平扩缩容（HPA）”的全部职责。如果在 1 个容器里再用 PM2 跑 4 个子进程：① 某个子进程卡死或频繁崩溃被 PM2 内部掩盖重启，K8s 探针感知不到异常；② 容器内存配额需乘以 4 且各子进程争抢同一份 cgroup CPU 时间片；③ 信号转发与标准输出日志采集多绕了一层。容器化最佳实践是“单容器单 node 进程”，需要 4 核并发就直接把 Deployment 的 replicas 设为 4。

2. 本地用 Node.js 24 直接执行 node src/server.ts 正常启动了，是不是意味着项目里可以把 typescript 依赖卸掉、也不用在 CI 里跑 tsc 了？

绝对不能省掉 tsc --noEmit。Node.js 内置的 Type Stripping 为了做到毫秒级极速启动，只做词法扫描把类型注解直接抹成空格——哪怕你写了 const port: number = "hello" 这种明显的类型错误，node src/server.ts 也会照跑不误直到运行时出 Bug。因此本地编辑器和 CI 合入流水线必须保留 tsc --noEmit 把关类型安全。

3. 排查安全审计时发现线上日志平台里搜得到用户的明文登录密码和 Bearer eyJ... 令牌，应该在哪一层根治？

靠口头叮嘱开发人员“不要打印 req.headers 或 req.body”迟早会漏。应在初始化全局 pino 日志实例时配置自动脱敏路径 redact: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token', '*.secret']——这样哪怕某处排障日志把整个请求对象传进了 request.log.info({ req, body })，落盘输出前敏感字段也会被统一替换为 "[Redacted]"。
