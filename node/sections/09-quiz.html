09.1 · 全链路实战检验：10 道高频业务故障与架构设计自测题（点击题目展开解析）

先独立思考，再点开参考方案

01. 一个接口计算量很大（纯 JS 汇总 20 万行数据耗时 1.5 秒），结果只要有人点它，连其他用户的登录和健康检查接口都跟着超时，怎么办？

原因：所有请求的 JS 代码共用单个主线程事件循环；该接口霸占主线程同步算 1.5 秒期间，事件循环无法推进，其他请求哪怕只需 1ms 也只能排队干等。
三层解法：① 先看能否把聚合计算下推给数据库 SQL / 缓存预计算；② 必须在 Node 内算且要同步返回时，放进常驻 worker_threads 线程池（如 piscina）隔离计算；③ 若耗时达数秒以上，改为「接口投递消息队列立即返回任务号 + 前端轮询或通知下载」（回顾 06.3 / 原理篇 02）。

02. 上传小图片一直正常，运营刚上传了一个 2GB 的宣传片视频，Node 服务内存瞬间暴涨并直接 OOM 重启了，怎么修？

原因：代码里把整个请求体一次性缓存在了内存中（例如用了 toBuffer() 或全量拼接 chunks），2GB 数据直接冲破容器内存配额或 V8 堆上限。
标准改法：① 后端中转场景改用 @fastify/multipart 获取可读流 part.file，通过 await pipeline(part.file, writeStream) 边收边往磁盘或对象存储流式转发，借助背压机制把内存稳定压在几十 KB 以内，并设好 fileSize 上限；② 生产大文件更推荐由后端签发对象存储（OSS / S3）预签名 URL，让前端直接分片传云端，不占应用服务器带宽（回顾 07.3 / 原理篇 03.2）。

03. 做了个转发大模型流式回答的 SSE 接口，用户刚看开头就关掉了页面，为什么后台日志显示大模型请求还在继续跑并扣费？

原因：浏览器断开的只是「浏览器 ⇄ Node 服务」这半截下行 TCP 连接，Node 发往大模型 API 的那条上游 fetch 请求默认完全独立，会一直把剩余几千个 Token 全收完才结束。
标准改法：每次请求新建 const ctrl = new AbortController() 传给上游 fetch(url, { signal: ctrl.signal })，同时监听 req.on('close', () => { if (!res.writableEnded) ctrl.abort(); })，在用户关页瞬间主动切断上游连接止损；别忘了配 X-Accel-Buffering: no 防止 Nginx 缓冲卡流（回顾 07.4）。

04. 服务刚启动时内存只有 70MB，平稳运行一天后涨到了 1.6GB 濒临崩溃，怎么一步步定位出是哪行代码漏了？

① 先分堆内还是堆外：打印 process.memoryUsage()——若 heapUsed 在垃圾回收后仍阶梯式爬升，是 V8 堆内 JS 对象泄漏；若只有 rss / external 涨，优先查未用 pipeline 销毁的异常流。
② 抓两份快照做差分：用 --heapsnapshot-signal=SIGUSR2（或 v8.writeHeapSnapshot()）间隔 5~10 分钟导出两份 .heapsnapshot，导入 Chrome DevTools 切到 Comparison 对比视图，按 Size Delta / Retained Size 排序，点开底部 Retainers 引用链直达持有引用的变量名与源码文件。
③ 优先排查三大常客：没设容量上限与过期的模块级 Map / 数组 缓存、请求内给全局 EventEmitter 挂 .on() 忘了 .off()、长生命周期闭包意外抓住了大对象（回顾 08.5 / 原理篇 04.4）。

05. 每次线上滚动发版替换旧容器的那几秒钟，总会有少量用户请求收到 502 Bad Gateway，怎么做到真正的零损发版？

需要打通「信号接收 → 网关摘流 → 存量排空」三环：
① 修启动命令：Dockerfile 用 CMD ["node", "dist/server.js"] 直接启动（不用 CMD npm start），确保 Node 直接收到容器平台发来的 SIGTERM。
② 探针配合摘流：收到 SIGTERM 第一时间把就绪探针 /readyz 切为返回 503（在 K8s 中可配 preStop: sleep 3 等待网关摘流生效，防止在途新请求刚发过来就撞上端口关闭）。
③ 排空后再关库：调用 await app.close() 拒收新连接并等存量请求写完响应后，再去关闭 MySQL / Redis 连接池，最后调 process.exit(0)（回顾 08.4）。

06. 为了方便查日志，同事写了个模块变量 let currentUserId，在鉴权中间件赋值、在数据库层读取打印，上线后为什么经常把张三的操作打到李四头上？

原因：Node.js 在单线程上交错执行多个并发请求。张三的请求过了鉴权把 currentUserId 设成 张三，紧接着在 await pool.execute() 处挂起让出主线程；等待期间李四的请求进来把同一个变量改成了 李四；等张三的 SQL 返回恢复执行时，读到的就变成李四了。
正确做法：① 优先直接使用挂载在当前请求对象上的 request.user 与 request.log；② 若跨多层深调用不想透传参数，使用官方内置的 AsyncLocalStorage 为每条异步调用链绑定独立隔离的上下文存储（回顾 08.3 / 原理篇 06.2）。

07. 需要调用外部物流接口批量查询 2,000 个运单，对方限流每秒最多 20 次且偶发超时，代码应该怎么设计？

不能直接 Promise.all 一股脑全发出去，需组合四层保护：
① 并发与速率控制：使用 mapLimit(orders, 10, ...)（或带时间窗口配额的 p-throttle / Bottleneck）控住并发在途数；
② 单次硬超时：每次 fetch 传入独立的 AbortSignal.timeout(3000)；
③ 有选择的退避重试：仅对超时、网络断连、429 和 502/503/504 做 2 次指数退避加随机抖动重试（400/404 直接失败）；
④ 局部容错汇总：单条彻底失败后捕获记录单号，不中断整批任务，最后输出成功数与待人工复核列表（回顾 03.3 / 07.5）。

08. 单实例跑得好好的定时对账脚本（node-cron 每天 0 点跑），扩容到 3 台容器实例后，每天 0 点准时产生 3 份重复对账单，怎么改？

原因：3 台无共享状态的容器各自都在内存里跑着定时器，到 00:00:00 时会同时触发执行 3 遍。
两种标准改法：① 加 Redis 分布式互斥锁：任务开始前执行 SET lock:daily-reconcile <实例ID> NX EX 600，只有返回 OK 的那 1 台实例真正干活，其余 2 台直接跳过；② 架构升级：使用 BullMQ 定时可重复任务（Repeatable Job）或 Kubernetes 独立的 CronJob 资源单独拉起一次性任务容器执行，与无状态 Web 容器彻底分离（回顾 07.6）。

09. 服务偶发毫无征兆地直接退出重启，退出码为 1，查业务路由都写了 try / catch，可能是什么漏网之鱼杀死了进程？

重点排查这三处路由 try / catch 管不到的死角：
① “发后不管”的浮游 Promise：路由里写了 sendAuditLog(data) 既没 await 也没挂 .catch()，或者在 try 块里写了 return asyncFn() 漏了 await，出错时触发 unhandledRejection 默认直接终止进程；
② 未监听 'error' 事件的 EventEmitter / Stream / Redis 客户端：连接断开触发 emit('error') 时若无人监听，直接抛未捕获异常崩进程；
③ setTimeout / setInterval 回调内部抛错：定时器回调脱离了原 async 函数的调用栈，内部必须自己包一层 try / catch（回顾 03.3 / 03.4）。

10. 线上所有要查 MySQL 的接口突然全部转圈挂死，但查无需数据库的 /healthz 秒回 200，MySQL 服务器负载也很低，怎么回事？

/healthz 秒回说明 Node 主线程事件循环完全没卡死；MySQL 负载很低说明也不是慢 SQL 锁表——最典型的元凶是应用层数据库连接池泄露耗尽（Connection Leak）。
全局搜索代码里所有调用了 await pool.getConnection() 的地方：大概率在某个手动事务或条件分支里提前 return 或抛错跳出，却没有把 conn.release() 放在 finally 块里。假设连接池上限是 10，只要触发 10 次该分支把连接全借走不还，第 11 个请求就会在借连接队列里无限干等。顺手在连接池配置上加 acquireTimeout / 查询超时避免无限死等（回顾 07.1）。
