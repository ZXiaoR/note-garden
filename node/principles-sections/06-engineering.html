06.1 · 中间件执行模型：Koa 洋葱模型原理与 koa-compose 核心实现

06.1 洋葱模型（Onion Middleware）原理与 koa-compose 防重入实现

在 Web 框架（如 Koa）中，日志记录、权限校验与统一异常捕获通常通过中间件串联。Koa 使用 koa-compose 将中间件数组组合为递归嵌套的 Promise 调用链：每个中间件中 await next() 之前的代码按注册顺序依次执行（请求进入阶段），待最内层业务逻辑完成后，再按相反顺序依次恢复执行各中间件 await next() 之后的代码（响应返回阶段）。

koa_compose.js · 15 行 koa-compose 核心调度与防重入源码 
function compose(middlewares) {
  return function (ctx, next) {
    let index = -1; // 闭包游标：记录当前已执行到的中间件最大下标
    return dispatch(0);

    function dispatch(i) {
      // 防重入校验：若同一个中间件内部调用了两次 next()，则 i <= index 成立
      if (i <= index) return Promise.reject(new Error('next() called multiple times'));
      index = i;
      let fn = middlewares[i];
      if (i === middlewares.length) fn = next;
      if (!fn) return Promise.resolve();
      try {
        // 将下一个中间件封装为 () => dispatch(i + 1) 传给当前中间件的 next 参数
        return Promise.resolve(fn(ctx, () => dispatch(i + 1)));
      } catch (err) {
        return Promise.reject(err);
      }
    }
  };
}
compose 实现中的三个关键设计：
  • 1. Promise.resolve 统一包装：无论中间件编写为普通同步函数还是 async 函数，其返回值都被包装为 Promise，保证外层可统一使用 await next() 等待。
  • 2. i <= index 防重入保护：若在同一个中间件函数内调用两次 next()，第二次调用传入的下标 i 仍等于当前 index，函数会立即返回 rejected Promise，防止下游业务逻辑被重复执行。
  • 3. 最外层异常收敛：在最外层（第 0 个）中间件中编写 try { await next(); } catch (err) { ... }，即可集中捕获后续任意深度中间件抛出的同步或异步异常。
06.2 · 异步上下文透传：AsyncLocalStorage 全链路 TraceID 传递机制

06.2 AsyncLocalStorage 异步上下文隔离与全链路日志追踪

由于 Node.js 在单个主线程上交替执行成百上千个并发请求的异步回调，如果将请求的 traceId 存放在模块全局变量中，后到达的请求会立即覆盖前一个请求的数据。为此 Node.js 内置了 AsyncLocalStorage（位于 node:async_hooks 模块）：它会在当前异步调用链派生出的每一个 Promise、定时器与 I/O 回调上自动关联并恢复专属的存储对象（Store），无需修改业务函数签名即可安全获取当前请求的上下文。

vs trace_context.mjs · 全局变量串号误区与 AsyncLocalStorage 正确用法 
import { AsyncLocalStorage } from 'node:async_hooks';
import crypto from 'node:crypto';

// ❌ 错误写法：用模块级变量 let currentTraceId 保存请求 ID，并发等待 I/O 时会被后续请求覆盖
// ✅ 正确写法：创建 AsyncLocalStorage 实例，在请求入口调用 als.run(store, callback)
const als = new AsyncLocalStorage();

function logInfo(msg) {
  const store = als.getStore(); // 任意深度的下游函数可直接读取当前请求的专属 store
  console.log(`[traceId=${store?.traceId}] ${msg}`);
}

function handleRequest(user) {
  const store = { traceId: crypto.randomUUID().slice(0, 8), user };
  als.run(store, async () => {
    logInfo(`收到 ${user} 请求`);
    await new Promise((r) => setTimeout(r, 20));
    logInfo(`数据库查询完成 (${user} 上下文保持独立)`);
  });
}

handleRequest('Alice');
handleRequest('Bob');
AsyncLocalStorage 上下文传递原理：

• 资源创建时捕获（Capture）：在 als.run(store, fn) 回调执行期间，每当底层创建新的异步资源（如 Promise、setTimeout 或文件/网络请求句柄），运行时会将当前活跃的 store 引用挂载到该异步资源实例上；
• 回调执行时恢复（Enter / Exit）：当该异步资源就绪并被事件循环唤醒执行回调前，运行时自动将当前活跃存储切换为该资源绑定的 store，并在回调执行完毕退栈时还原，从而实现多请求并发交错下的上下文隔离。

06.4 · 核心知识点自测：Node.js 运行时与工程实践 18 题参考解析

Node.js 核心原理与工程实践 18 问参考解析

01. Node.js 的线程模型是怎样的？为什么单主线程能支撑高并发 I/O？存在哪些局限？

① 线程模型：开发者的 JavaScript 业务代码运行在单个主线程上，但 Node.js 进程底层同时包含 libuv 工作线程池（默认 4 线程，处理文件读写、DNS lookup 与加密压缩）以及 V8 的后台垃圾回收和 JIT 编译线程。② 高并发原理：Web 服务的大部分耗时集中在等待网络或磁盘 I/O。Node.js 通过事件驱动与非阻塞 I/O（底层使用 Linux epoll、macOS kqueue、Windows IOCP）将慢速 I/O 委托给操作系统内核与工作线程池，主线程无需阻塞等待，避免了传统多线程模型中每个连接数 MB 线程栈的内存开销与上下文切换成本。③ 局限性：单进程默认只使用单颗 CPU 核心（需配合 Cluster 扩展至多核），且主线程若执行长耗时同步计算会阻塞后续所有并发请求。

02. CommonJS 和 ES Module 的核心区别是什么？遇到循环依赖（A ⇄ B）时各自如何处理？

① 导出机制：CommonJS 导出的是运行时值的浅拷贝（缓存于 Module._cache）；ES Module 导出的是编译期静态解析的只读实时内存引用（Live Binding），模块内部修改变量后外部可同步读取到新值。② 加载时机：CJS 在运行到 require() 时同步加载（将代码包裹进 5 参数函数执行）；ESM 在编译期静态分析依赖树并按“构造 → 实例化 → 求值”三阶段异步加载，支持静态 Tree-Shaking 与顶层 await。③ 循环依赖处理：CJS 在首次进入模块时即把空 exports 登记入缓存，循环引用时拿到的是对方当前已执行部分的半成品对象；ESM 在实例化阶段已预先绑定导入导出内存槽，函数声明因提升可正常调用，但若在顶层同步读取尚未执行初始化的 export let / const 变量则会触发暂时性死区（TDZ）ReferenceError。

03. 为什么在 CommonJS 模块中直接写 exports = { a: 1 } 无法导出属性，而需要写 module.exports = { a: 1 }？

Node.js 在编译 CommonJS 模块时，会将模块代码包裹进函数 (function(exports, require, module, __filename, __dirname) { ... }) 中执行。初始状态下形参 exports 是一个指向 module.exports 同一内存地址的引用变量。执行 exports.a = 1 是顺着引用修改共享对象；而直接执行 exports = { a: 1 } 会让形参变量 exports 重新指向新对象，切断了与 module.exports 的关联。由于模块加载器最终固定返回 module.exports，外部拿到的仍是原来的空对象 {}。

04. 请说明 Node.js (libuv) 事件循环的六个阶段及其各自负责的任务。

uv_run 按固定顺序循环执行 6 个阶段：① timers（定时器阶段）：检查小顶堆，执行已到期的 setTimeout 与 setInterval 回调；② pending callbacks（待定回调）：执行上一轮循环推迟的系统级 I/O 错误回调（如 TCP ECONNREFUSED）；③ idle, prepare：供 libuv 内部在轮询前做状态准备；④ poll（轮询阶段）：计算阻塞超时时间并调用 epoll_wait，执行已就绪的网络与文件 I/O 回调；⑤ check（检查阶段）：专门执行 setImmediate() 注册的回调；⑥ close callbacks（关闭回调）：执行资源关闭回调（如 socket.on('close')）。

05. setTimeout(fn, 0) 和 setImmediate(fn) 的执行顺序如何判断？为什么在 fs.readFile 回调内顺序是固定的？

① 在主模块顶层调用时顺序不固定：Node.js 将 setTimeout(fn, 0) 的最小延迟设为 1ms。当同步代码执行完毕进入事件循环第 ① 站 timers 阶段时，若进程启动耗时已满 1ms 则先执行 setTimeout；若不足 1ms 则跳过 timers，继续向下走到第 ⑤ 站 check 阶段先执行 setImmediate。② 在 fs.readFile 等 I/O 回调内部调用时，setImmediate 始终先于 setTimeout 执行：因为 I/O 回调本身运行在第 ④ 站 poll 阶段，poll 阶段结束后的紧邻下一站即为第 ⑤ 站 check（执行 setImmediate），而 setTimeout 需等待下一轮循环回到第 ① 站 timers 阶段才会被执行。

06. process.nextTick 和 Promise.then 微任务的优先级顺序是什么？Node v11 前后的执行时机有何变化？

① 优先级顺序：process.nextTick 保存在 Node.js 独立维护的 nextTickQueue 中，其优先级高于 V8 维护的 Promise.then / queueMicrotask 微任务队列（每次清空微任务时总是先将 nextTickQueue 全部清空，再清空 Promise 微任务队列）。② Node v11+ 行为对齐：在 Node v10 及更早版本中，需等某个阶段队列中的所有宏任务执行完才清空微任务；从 Node v11 起与浏览器规范对齐——每执行完任意阶段的单个宏任务回调，返回 C++ 边界时立即清空 nextTick 与 Promise 微任务队列。

07. Node.js 中哪些异步操作走操作系统内核 epoll？哪些走 libuv 默认 4 线程的工作线程池？

• 走 OS 内核多路复用（epoll / kqueue / IOCP）：全部网络套接字 I/O（tcp / udp / http / https）以及基于 c-ares 实现的 dns.resolve4 / resolve6，不占用 libuv 工作线程池。
• 走 libuv 工作线程池（默认 4 线程，由 UV_THREADPOOL_SIZE 控制）：所有异步文件操作 fs.*、系统级域名解析 dns.lookup()、以及计算密集型异步 C++ 接口（crypto.pbkdf2 / scrypt / randomBytes、zlib）。
• 工程注意事项：http.get('http://域名') 默认调用 dns.lookup 占用工作线程池。若慢速磁盘读写或加密计算占满 4 个工作线程，未做缓存的外部域名请求也会在线程池队列中等待。生产环境可通过设置 UV_THREADPOOL_SIZE=64 并配置应用层 DNS 缓存进行优化。

08. Buffer 的内存分配在哪个区域？什么是 8KB Slab 内存池？Buffer.alloc 与 allocUnsafe 有何区别？

Buffer 的底层二进制数据分配在 V8 堆外的 C++ 内存区（计入 arrayBuffers / external）。为减少小数据块频繁向操作系统申请内存的开销，Node.js 预分配了一块 8KB (8192 Bytes) 的共享 ArrayBuffer 内存池（Slab）。当调用 Buffer.allocUnsafe(size) 或 Buffer.from() 且请求大小满足 size < 4096 (Buffer.poolSize >>> 1) 时，直接从该 8KB 共享池中按 8 字节对齐移动游标切片（分配速度快但包含未清零的旧内存数据，且若长期保存小切片会导致整块 8KB 内存无法释放）；而 Buffer.alloc(size) 则分配独立且已全部清零的内存块。

09. 什么是 Stream 的背压（Backpressure）机制？为什么生产环境推荐使用 stream.pipeline 替代 .pipe()？

① 背压机制：用于协调上游 Readable 读取速度高于下游 Writable 消费速度时的内存积压问题。当下游可写流内部缓冲区积压达到水位线阈值 highWaterMark（普通流默认 16KB，文件流默认 64KB）时，writable.write(chunk) 返回 false，通知上游调用 readable.pause() 暂停读取；待下游将缓冲区数据排空并触发 'drain' 事件后，再调用 readable.resume() 恢复读取。② 推荐使用 stream.pipeline 的原因：传统的 a.pipe(b) 在下游发生异常或客户端中途断开连接时，不会自动关闭并销毁上游流，容易引起文件描述符（FD）与内存泄漏；pipeline 能够统一传播错误，并在任一环节终止时自动销毁整条链路上的所有流实例。

10. V8 为什么要将堆内存划分为新生代和老生代？请说明 Scavenge 算法与对象晋升条件。

基于“弱分代假说”（绝大多数对象生命周期很短）：① 新生代（New Space，1~64MB）存放短生命周期对象，采用 Scavenge（Cheney 半空间复制）算法，将空间平分为 From-Space 和 To-Space；回收时仅将 From 中存活的对象紧凑复制到 To（同时消除内存碎片），随后将两区角色互换。② 晋升至老生代的两项条件：对象已经历过 1 次 Scavenge 回收仍存活，或复制到 To-Space 时该空间的占用率已超过 25%。③ 老生代（Old Space）对象存活率高、容量大，采用并发与增量三色标记 + Mark-Sweep（标记清除） + Mark-Compact（按需标记整理消除碎片）。

11. 什么是 V8 的隐藏类（Hidden Class）与内联缓存（IC）？编写代码时如何避免触发逆优化？

V8 在底层为每个对象维护隐藏类（Map）以记录各属性的固定内存偏移量，并配合内联缓存（IC）将动态属性查找优化为固定偏移寻址。编码规范：① 在构造函数中按固定顺序初始化所有对象属性，避免隐藏类分叉；② 避免使用 delete obj.prop（会使对象退化为慢速字典模式，可将属性赋值为 null 或 undefined）；③ 保持热点函数入参的对象结构一致（维持单态 Monomorphic IC，避免传入超过 4 种不同形状的对象导致超多态退化）。

12. 线上 Node.js 服务出现内存持续上涨，常见原因有哪些？如何通过堆快照定位到具体代码？

① 四类常见原因：无容量上限的全局变量或模块级 Map 缓存；在请求处理函数中对全局 EventEmitter 重复绑定 .on() 监听器且未解绑；长生命周期闭包引用了外层大对象；未使用 pipeline 销毁的异常流或长期处于 pending 状态的 Promise。② 排查步骤：先通过 process.memoryUsage() 区分是堆内（heapUsed）还是堆外（external / arrayBuffers）增长；通过 --heapsnapshot-signal=SIGUSR2 或 v8.writeHeapSnapshot() 间隔数分钟采集两份堆快照并导入 Chrome DevTools；切换至 Comparison 对比视图，按 Retained Size（保留大小）增量排序，展开底部 Retainers 引用树即可回溯到持有引用的变量与代码位置。

13. child_process 的 spawn、exec、execFile、fork 四者有何区别？如何防范命令注入？

① spawn 是基础流式接口，默认不启动 Shell，以 Stream 流形式返回子进程输出，适合大数据量或长耗时任务；② execFile 不启动 Shell，直接执行二进制文件并将参数作为独立数组传入，回调返回缓冲结果，可避免 Shell 元字符解析，是调用外部程序的安全方式；③ exec 会先启动 /bin/sh 解析整条命令字符串，且默认有 1MB maxBuffer 上限（不可直接拼接外部输入参数，否则存在命令注入风险）；④ fork 专门用于派生新的 Node.js 子进程并自动建立父子 IPC 通信通道。

14. Cluster 模式下多个 Worker 子进程为什么能同时监听同一个 8080 端口而不报端口冲突？

Node.js 在底层对 net.Server.prototype.listen 进行了主从判断：当 Worker 子进程调用 listen(8080) 时，不会调用操作系统的端口绑定接口，而是通过 IPC 向 Primary 主进程发送注册请求。整台机器上真正绑定并监听 :8080 端口的只有 Primary 主进程；当新 TCP 连接到达时，主进程 accept 获取客户端 Socket 文件描述符（FD），默认按 Round-Robin（轮询）策略挑选一个空闲 Worker，通过 Unix Domain Socket 将该 Socket FD 跨进程传递给 Worker 处理。

15. worker_threads 工作线程与 Cluster 多进程有什么核心区别？各自适用什么场景？

① Cluster（多进程）：每个 Worker 是独立的操作系统进程，拥有隔离的内存页表和 V8 实例，进程间通过 IPC 序列化复制通信，故障隔离性强（单进程退出不影响其他进程），适合在服务外层按 CPU 核数扩展 HTTP 与 I/O 并发处理能力。② worker_threads（多线程）：在同一进程内创建多个线程（各自拥有独立 V8 Isolate 和 Event Loop），内存开销低且支持通过 SharedArrayBuffer 共享物理内存或零拷贝转移 ArrayBuffer 所有权，适合隔离执行 CPU 密集型计算任务。

16. 请简述 Koa 洋葱模型（koa-compose）的实现原理，以及如何防止多次调用 next()？

koa-compose 通过闭包递归函数 dispatch(i)，将第 i+1 个中间件包装为 () => dispatch(i + 1) 作为 next 参数传入第 i 个中间件，并使用 Promise.resolve() 统一包裹返回值。这样当前中间件在 await next() 处等待下游中间件全部执行完毕后，再恢复执行下半部分逻辑，形成“先进后出”的洋葱模型。内部维护闭包变量 let index = -1，每次调用时检查若 i <= index 则立即返回 Promise.reject，从而防止单个中间件内部重复调用 next() 导致下游逻辑被执行多次。

17. 在单线程并发处理多个异步请求时，Node.js 如何无侵入地传递全链路 TraceID？

使用官方内置的 AsyncLocalStorage（位于 node:async_hooks 模块）。在请求入口中间件中调用 als.run({ traceId }, async () => { ... })，运行时会在当前调用链创建出的每一个异步资源（Promise、Timer、I/O 请求）上自动绑定该存储对象引用，并在异步回调执行时自动恢复上下文。下游任意深度的业务函数或日志工具只需调用 als.getStore().traceId 即可获取当前请求的专属 ID，不会发生跨请求串号。

18. 为什么捕获 uncaughtException 后仍建议重启进程？如何实现 Node.js 服务的平滑停机？

① 异常退出原因：触发 uncaughtException 表示调用栈在非预期位置中断，此时内存中的业务状态、事务或连接池可能处于不一致的中间态，继续运行容易引发数据错误或资源泄漏。标准做法是在回调中记录错误日志、调用 server.close() 停止接收新请求，并在存量请求处理完毕（或达到超时阈值）后调用 process.exit(1)，由外部进程管理器拉起新进程。② 平滑停机（Graceful Shutdown）：进程监听 SIGTERM 信号，收到信号后先调用 server.close() 停止接收新连接，等待正在处理的存量请求与数据库操作正常完成后，再调用 process.exit(0) 安全退出。
