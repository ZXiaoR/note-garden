02.1 · 事件循环阶段流转：uv_run 六大阶段与 setTimeout / setImmediate 执行顺序

02.1 libuv 事件循环六大阶段（uv_run）与 poll 阶段阻塞唤醒机制

在 Node.js 后端运行环境中，主线程需要协同处理定时器到期、TCP 异常回调、网络与文件 I/O 读写、setImmediate 任务以及句柄关闭清理。为此 libuv 将单轮事件循环划分为按固定顺序循环执行的 6 个阶段（Phases），每个阶段维护各自独立的先进先出（FIFO）回调队列。

timeout_vs_immediate.js · 顶层调用与 I/O 回调内部调用的执行顺序对比 
const fs = require('node:fs');

// 【场景 A：主模块顶层】──► 输出顺序受进程启动耗时影响，不固定
setTimeout(() => console.log('A1: top setTimeout(0)'), 0);
setImmediate(() => console.log('A2: top setImmediate'));

// 【场景 B：I/O 回调内部】──► B2 (setImmediate) 始终先于 B1 (setTimeout) 输出
fs.readFile(__filename, () => {
  setTimeout(() => console.log('B1: I/O setTimeout(0)'), 0);
  setImmediate(() => console.log('B2: I/O setImmediate'));
});
// 场景 B 固定输出: B2: I/O setImmediate ➔ B1: I/O setTimeout(0)
执行顺序差异解析：顶层调用与 I/O 回调内部调用
  • 1. 场景 A（顶层调用顺序不固定）：Node.js 将 setTimeout(fn, 0) 的最小延迟规范化为 1ms。当进入事件循环第 ① 站 timers 阶段时，若主线程初始化耗时已满 1ms 则先执行 A1；若不足 1ms 则跳过 timers，继续向下走到第 ⑤ 站 check 阶段先执行 A2。
  • 2. 场景 B（I/O 回调内 setImmediate 始终先执行）：fs.readFile 的回调函数本身在第 ④ 站 poll 阶段执行。poll 阶段结束后的紧邻下一站正是第 ⑤ 站 check 阶段（专门执行 setImmediate），而 setTimeout 则需要等下一轮循环回到第 ① 站 timers 阶段才会执行。
深入 libuv C 源码：deps/uv/src/unix/core.c 中 uv_run() 主循环与 poll 阻塞超时计算实现

当服务端处于空闲等待请求状态时，Node.js 进程不会退出且 CPU 占用率为 0%，原因在于主线程阻塞停留在第 ④ 阶段 uv__io_poll（底层调用 Linux epoll_wait）上等待内核事件唤醒：

deps/uv/src/unix/core.c · uv_run 核心主循环精简源码 
int uv_run(uv_loop_t* loop, uv_run_mode mode) {
  while (r != 0 && loop->stop_flag == 0) {
    uv__update_time(loop);               // 0. 更新当前单调时钟毫秒数
    uv__run_timers(loop);                // ① timers 阶段：在小顶堆中找出所有 <= loop->time 的定时器执行
    ran_pending = uv__run_pending(loop); // ② pending 阶段：执行上一轮推迟的 I/O 回调
    uv__run_idle(loop);                  // ③ idle 阶段
    uv__run_prepare(loop);               // ③ prepare 阶段

    // 计算 poll 阶段在 epoll_wait 上的最大阻塞等待时长 (timeout)：
    // - 若 idle / pending / check(setImmediate) 队列非空 ──► timeout = 0 (不阻塞，立即向下推进)
    // - 否则取 timers 小顶堆中最近一个定时器的剩余到期时间差
    timeout = uv_backend_timeout(loop);
    uv__io_poll(loop, timeout);          // ④ poll 阶段：调用 epoll_wait(timeout) 等待唤醒并执行 I/O 回调

    uv__run_check(loop);                 // ⑤ check 阶段：执行所有 setImmediate 回调
    uv__run_closing_handles(loop);       // ⑥ close 阶段：执行 uv_close 关闭句柄回调
  }
}
02.2 · 微任务调度规则：process.nextTick 与 Promise 队列优先级及执行顺序推演

02.2 微任务队列优先级（nextTick > Promise）及异步代码执行顺序

分析包含微任务与宏任务的异步代码输出顺序时，遵循以下三条调度规则：
• 规则 1（同步代码最先执行）：主模块顶层代码、new Promise(executor) 构造函数体、以及 async 函数中遇到第一个 await 之前的代码，均属于同步代码，在当前调用栈立即执行。
• 规则 2（微任务队列优先级）：每当同步代码或单个宏任务回调执行完毕，先清空 process.nextTick 队列，再清空 Promise.then / await 后续代码 / queueMicrotask 队列。
• 规则 3（宏任务按六大阶段推进）：微任务全部清空后，按 libuv 六大阶段顺序（timers → poll → check）依次执行宏任务回调。

eventloop_order.js · 同步代码、微任务与事件循环阶段综合执行示例 
const fs = require('node:fs');

console.log('1. sync start');

async function async1() {
  console.log('2. async1 start'); // await 之前的代码同步执行
  await Promise.resolve();
  console.log('5. after await (Promise 微任务)');
}
async1();

fs.readFile(__filename, () => {
  console.log('6. poll I/O callback');
  setTimeout(() => console.log('9. timer inside I/O'), 0);
  setImmediate(() => console.log('8. immediate inside I/O'));
  process.nextTick(() => console.log('7. nextTick inside I/O'));
});

process.nextTick(() => console.log('4. top nextTick'));
console.log('3. sync end');
// 输出顺序: 1 ➔ 2 ➔ 3 ➔ 4 ➔ 5 ➔ 6 ➔ 7 ➔ 8 ➔ 9
vs nexttick_starvation.js · 递归微任务饥饿问题与正确异步拆分写法 
// ❌ 错误写法：递归调用 process.nextTick
//    由于 nextTickQueue 必须清空后才能进入下一阶段，这会导致 I/O 与定时器长期无法执行
function badLoop() {
  process.nextTick(badLoop);
}

// ✅ 正确写法 A：拆分长任务时使用 setImmediate，每轮让出 poll I/O 阶段
function safeLoop() {
  setImmediate(safeLoop);
}

// ✅ 正确写法 B：确保构造函数完成后再派发事件（nextTick 的典型适用场景）
class Server extends EventEmitter {
  constructor() {
    super();
    // 等外部调用方同步执行完 server.on('ready', fn) 后，再触发事件
    process.nextTick(() => this.emit('ready'));
  }
}
02.3 · 异步底层双通道：操作系统内核多路复用（epoll/kqueue）与 libuv 工作线程池

02.3 内核事件多路复用与 libuv 工作线程池（UV_THREADPOOL_SIZE = 4）

操作系统的 epoll（Linux）与 kqueue（macOS）主要针对网络 Socket（TCP/UDP）和管道提供非阻塞事件通知；对于本地磁盘文件读写、以及 C 标准库同步实现的 getaddrinfo 域名解析，无法直接通过 epoll 实现异步回调。因此 libuv 内置了一个默认包含 4 个线程的 C++ 工作线程池，专门在后台执行这类阻塞型调用：

底层执行通道 涵盖的 Node.js 核心模块与 API 运行机制与工程注意事项
通道 A：OS 内核事件多路复用
（epoll / kqueue / IOCP）		 • 全部网络套接字 I/O：net (TCP)、dgram (UDP)、http / https
• 纯网络 DNS 查询：dns.resolve4() / resolve6()（基于 c-ares）		 不占用 libuv 工作线程池。由操作系统内核直接管理 Socket 文件描述符，单进程可并发维持数万个网络连接。
通道 B：libuv 工作线程池
（默认 4 线程，UV_THREADPOOL_SIZE 上限 1024）		 • 文件 I/O：所有异步 fs.* 方法
• 系统 DNS 解析：dns.lookup()（http.get('http://域名') 默认调用）
• 计算密集型 C++ API：crypto.pbkdf2 / scrypt、zlib 异步压缩		 线程池排队问题：当 4 个线程被慢速磁盘读写或耗时加密计算占满时，未配置 DNS 缓存的外部 HTTP 域名请求也会在线程池队列中等待，导致请求响应延迟升高。
threadpool_proof.js · 验证 libuv 默认 4 线程池的并发批次表现 
// 可在启动时通过环境变量扩容: UV_THREADPOOL_SIZE=8 node threadpool_proof.js
const crypto = require('node:crypto');
const start = Date.now();

for (let i = 1; i <= 6; i++) {
  crypto.pbkdf2('secret', 'salt', 100000, 512, 'sha512', () => {
    console.log(`任务 #${i} 完成耗时: ${Date.now() - start} ms`);
  });
}
// 输出表现：任务 #1~#4 在约 180ms 同时完成（占满默认 4 个工作线程）；
// 任务 #5、#6 需等待前一批线程释放，在约 360ms 完成
生产环境线程池优化建议：
  1. 按需扩容线程池：对于包含大量文件读写或加解密的服务，可在启动进程前设置环境变量 UV_THREADPOOL_SIZE=64（必须在首次调用线程池前生效）。
  2. 配置应用层 DNS 缓存：高频请求外部域名时，引入 cacheable-lookup 或使用走网络异步的 dns.resolve4，避免每次请求调用 dns.lookup 争抢工作线程。
  3. 隔离业务侧 CPU 计算：自定义的 JavaScript 重计算任务应交由独立的 worker_threads（详见第 05 章），避免占用系统 I/O 线程池。
