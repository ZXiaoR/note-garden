04.1 · V8 执行优化机制：JIT 编译流水线、隐藏类（Hidden Class）与内联缓存（IC）

04.1 V8 JIT 编译管线（Ignition + TurboFan）、隐藏类（Map）与内联缓存（Inline Cache） 深挖

这节回答实战篇哪个问题：对应 实战篇 05.2 高吞吐 JSON 接口 —— 动态类型的 JavaScript 读写对象属性为什么能跑出接近静态语言的性能？日常写代码时为何不建议随意 delete obj.key？

JavaScript 支持在运行时动态增删对象属性。如果每次读取属性 obj.x 都执行一次哈希表查找，属性访问开销会显著高于静态类型语言。为此 V8 在底层为每个对象维护了一张隐藏类（Hidden Class，源码中称为 Map），用于记录各属性在内存中的固定偏移量，并配合内联缓存（Inline Cache, IC）与 TurboFan JIT 编译优化：当同类对象的属性结构（Shape）保持一致时，后续属性访问可直接通过固定内存偏移量寻址。

vs hidden_class.js · 隐藏类分叉退化与单态复用写法对照 
// ❌ 错误写法：按不同顺序动态挂载属性，并使用 delete 删除属性
const p1 = {}; p1.x = 1; p1.y = 2; // 隐藏类转换链: C0 ➔ C1(x) ➔ C2(x,y)
const p2 = {}; p2.y = 2; p2.x = 1; // 属性顺序不同，分叉生成独立隐藏类 C3(y) ➔ C4(y,x)
delete p1.x;                       // 导致对象退化为慢速哈希字典模式 (Slow Properties)

// ✅ 正确写法：在构造函数中按固定顺序初始化属性，用赋 null 代替 delete
class Point {
  constructor(x, y) {
    this.x = x; // 所有实例共享同一个隐藏类 Map，维持单态内联缓存 (Monomorphic IC)
    this.y = y; // 若需清空属性值，直接赋值为 null，保持对象结构不变
  }
}
V8 编译流水线与逆优化（Deoptimization）机制：
  • JIT 编译流水线：源码解析为抽象语法树（AST） ➔ Ignition 解释器生成字节码并收集运行时类型反馈 ➔ 热点函数交由 TurboFan 编译器生成优化后的原生机器码。
  • 单态（Monomorphic）与超多态（Megamorphic）：若热点函数接收的参数始终为同一种隐藏类，内联缓存可稳定命中；若传入超过 4 种不同结构的对象，内联缓存将退化为全局查找，且已生成的机器码会触发逆优化（Deopt）回退至字节码执行。
04.2 · 进程内存结构与分代模型：process.memoryUsage 五项指标、GC Roots 可达性与 V8 堆分区

04.2 进程内存结构、GC Roots 可达性判定与 V8 堆内存分代布局 常问

这节回答实战篇哪个问题：对应 实战篇 08.5 线上排障 —— 监控面板里的 rss、heapUsed、external 各自对应哪块内存？V8 是怎么判定垃圾对象、为什么要把堆切成新生代和老生代的？

① 理解垃圾回收的第一步：V8 怎么知道哪个对象是“垃圾”？（GC Roots 可达性分析）
V8 并不是靠统计引用次数来回收内存（因为 `a.next = b; b.next = a` 循环引用会导致引用计数永远不为 0），而是采用可达性分析（Reachability）：
垃圾回收器每次从一组固定的根对象（GC Roots，包括：① 当前正在执行的函数调用栈里的局部变量与参数；② 全局对象 globalThis；③ 活跃的定时器、C++ 句柄与内置模块缓存）出发，顺着对象属性指针一路往下找。凡是在这条引用链上能被访问到的对象就是存活对象（Reachable）；凡是从任何 GC Root 出发都找不到的“孤岛对象”，就会被判定为不可达垃圾（Unreachable）并予以回收。

memory_usage.js · process.memoryUsage() 五项内存指标含义 
const buf = Buffer.alloc(50 * 1024 * 1024); // 分配 50MB 堆外 Buffer
const m = process.memoryUsage();

console.table({
  rss:          `${(m.rss / 1048576).toFixed(1)} MB`,          // ① 进程常驻物理内存总量 (含V8堆+堆外+C++栈)
  heapTotal:    `${(m.heapTotal / 1048576).toFixed(1)} MB`,    // ② V8 已向操作系统申请的堆内存总容量
  heapUsed:     `${(m.heapUsed / 1048576).toFixed(1)} MB`,     // ③ V8 堆内 JS 对象实际使用量 (排查JS对象泄漏)
  external:     `${(m.external / 1048576).toFixed(1)} MB`,     // ④ V8 绑定对象关联的堆外 C++ 内存 (含 Buffer)
  arrayBuffers: `${(m.arrayBuffers / 1048576).toFixed(1)} MB`  // ⑤ Buffer 与 ArrayBuffer 占用的堆外内存 (50MB)
});
堆内内存（V8 Heap）与堆外内存的边界：

V8 的垃圾回收器主要管理 heapTotal / heapUsed（V8 堆内的普通对象、数组、闭包、字符串）；而上一章讲到的 Buffer 底层物理字节块则存放在 V8 堆外的 C++ 内存中（计入 arrayBuffers / external，当上层 JS 视图卡片被 V8 GC 回收时连带释放）。
• 排查方向判断：若监控发现 heapUsed 在 GC 后仍呈阶梯式上涨，说明存在 V8 堆内 JS 对象泄漏；若 heapUsed 平稳但 rss 与 external 持续增长，则应重点检查未消费的 Stream 缓冲或堆外 Buffer 滞留。

② 为什么 V8 要把堆内存分成「新生代」和「老生代」？（弱分代假说）
在 Web 服务中，90% 以上的对象（例如处理一次 HTTP 请求时创建的临时 JSON 对象、局部数组、拼接字符串）都是“朝生夕死”的——从创建到请求结束只需要几毫秒；只有极少数对象（如全局配置、连接池、内存缓存）会长期存活。
如果把短命对象和长寿对象混在同一个几 GB 的大池子里每次全盘扫描，效率极低。因此 V8 将堆内存按对象年龄划分为三个核心区域，采用“新老分治”策略：

V8 堆内存分区 默认容量范围 存放哪些对象 对应的垃圾回收器与特点
1. 新生代（New Space）
（平分为 From 与 To 两个半区）		 1MB ~ 64MB
（空间小）		 所有刚创建出来的普通小对象（new Object、局部数组、短字符串等）第一时间都分配在这里。 • 副垃圾回收器（Minor GC / Scavenge 算法）；
• 触发极频繁，但由于只复制极少数（通常 <10%）存活对象，每次回收耗时仅 1~2ms。
2. 老生代（Old Space） 约 2GB ~ 4GB
（可通过 --max-old-space-size 调大）		 在新生代中历经多次回收依然存活下来的“长寿对象”（如全局缓存、模块导出对象、长连接池）。 • 主垃圾回收器（Major GC / 标记-清除与标记-整理算法）；
• 空间大、存活率高，采用后台并发三色标记 + 增量清除，触发频率低。
3. 大对象空间（Large Object Space） 按需分配 单个体积超过新生代半区容量的大数组或大字符串（例如几 MB 的 JSON 对象）。 • 直接在此分配，不经过新生代（避免在新生代 `From/To` 之间来回复制大块内存的开销），由 Major GC 统一回收。
04.3 · 分代回收算法详解：新生代 Scavenge 半空间复制与晋升、老生代三色标记与写屏障

04.3 新生代 Scavenge 复制算法与老生代 三色标记 + 写屏障 全流程拆解 深挖

这节回答实战篇哪个问题：对应 实战篇 05.4 与 08.5 内存治理 —— 服务每秒创建销毁上万个短命请求对象为什么耗时不到 2ms？老生代并发标记时 JS 代码还在改引用，V8 怎么靠写屏障保证不误删活对象？

一、新生代 Minor GC：Scavenge（Cheney 半空间复制算法）是怎么一步步工作的？
新生代虽然总大小只有几十 MB，但里面绝大部分对象在几毫秒后就会变成垃圾。为了做到“分配极快、回收极快且永远不产生内存碎片”，V8 将新生代一分为二，切成两个完全等大的半区——From-Space（当前正在使用的半区）与 To-Space（平时完全闲置的空白半区），按以下 4 个步骤循环运作：

  • Step 1 · 平时顺序分配（碰撞指针）：新对象不断往 From-Space 里紧密排列写入，只需把分配游标往后移动即可，速度与栈分配几乎一样快；此时 To-Space 完全空着。
  • Step 2 · From-Space 写满触发 Scavenge，只把“活对象”搬去 To-Space：当 From-Space 装满时，暂停执行约 1 毫秒，从 GC Roots 出发找出 From-Space 里还活着的少量对象（如图中的 存活A、存活B），将它们挨个紧凑地复制到 To-Space 的最开头（中间死掉的垃圾对象根本不管，复制完后自然消除了所有内存空隙）。
  • Step 3 · 搬家途中检查“晋升（Promotion）”条件（满足任一即直接搬去老生代）：
    • 条件 ①（年龄达标）：如果某个活对象之前已经经历过 1 次 Scavenge 回收，这次是第 2 次活下来，说明它是长寿对象，不再复制到 To-Space，而是直接迁入老生代（Old Space）；
    • 条件 ②（To-Space 占用超过 25% 水位线）：如果把对象往 To-Space 复制时，发现 To-Space 已经被占用了超过 25%，后续活对象也直接晋升去老生代——为什么是 25%？因为下一步 To-Space 马上就要翻转变成新的 From-Space 用来接收新对象，如果一上来就已经占了七八成，刚运行几毫秒又会立刻塞满触发 GC。
  • Step 4 · 清空原 From-Space 并翻转角色（Flip）：活对象全部安置好后，原 From-Space 里剩下的全是死垃圾，整块直接一键清空；最后把 From-Space 和 To-Space 两个半区的身份对调，继续接收新对象。

二、老生代 Major GC：为什么不能再用 Scavenge？「三色标记 + 清除/整理 + 写屏障」是怎么配合的？
老生代容量高达 2GB ~ 4GB，且里面的对象绝大部分都是长期存活的。如果还用新生代那种“平分两半、来回复制”的算法，不仅会白白浪费一半（1~2GB）内存，而且每次复制几百 MB 活对象会导致程序严重卡顿。
因此，老生代改用原地标记与回收策略，整個过程由以下 3 个紧密衔接的机制组成：

  • 机制 ① · 三色标记法（Tri-color Marking：⚪白 ➔ 🔘灰 ➔ ⚫黑）找出谁死谁活：
    为了在不暂停整个程序的情况下渐进式遍历对象图，V8 给堆内每个对象维护了三种标记状态：
    • ⚪ 白色（未访问 / 候选垃圾）：GC 开始前，所有对象默认全部是白色；如果到标记全部结束时某个对象依然是白色，说明没有任何路径能连到它，即为待回收垃圾。
    • 🔘 灰色（已发现、但子引用未扫完的“波峰队列”）：从 GC Roots 出发直接引用的第一批对象先被涂成灰色放入待扫描队列；代表“我自己肯定活着，但我属性指向的下级对象还没检查完”。
    • ⚫ 黑色（确认存活且子引用已全部扫完）：每次从灰色队列取出一个对象，把它直接引用的白色子对象全部涂成灰色推入队列，然后把该对象自身涂成黑色。当灰色队列彻底清空时，所有活着的对象都变成了黑色，剩下的白色对象就是垃圾。
  • 机制 ② · 标记-清除（Mark-Sweep）与标记-整理（Mark-Compact）按需配合：
    标记完成后，老生代并不会每次都去搬动对象：
    • 平时优先用 Mark-Sweep（原地清除，极快）：黑色活对象留在原地一动不动，只把白色死对象的内存块地址登记到空闲链表（Free List）中，下次分配新对象时直接从链表里找一块够大的空隙塞进去。
    • 碎片过多时才触发 Mark-Compact（平移整理，消除碎片）：多次清除后内存会像瑞士奶酪一样布满零碎空洞；当需要分配一个较大对象而找不到连续空隙时，V8 才会启动整理——把所有黑色活对象统一向内存页的左侧紧密平移，空出右侧整片连续空间。
  • 机制 ③ · 增量标记（Incremental）与写屏障（Write Barrier）如何防止漏标误删？
    如果一次性把 2GB 老生代全部标完，JS 主线程会被暂停几百毫秒（称为全停顿 Stop-The-World）。为此 V8（Orinoco 引擎）采用并发标记（后台线程并行扫描）+ 增量标记（主线程每标 2~5ms 就切回执行一段 JS 代码）。
    但这带来一个核心问题：当 GC 暂停、切回执行 JS 代码时，如果 JS 把一个“已经扫描完的⚫黑色对象 A”指向了一个“还没被扫描的⚪白色对象 D”（同时断开原来灰色对象对 D 的引用），由于黑色对象不会再被重新扫描，D 岂不是会一直保持白色而被误删？
    V8 的解决方案就是写屏障（Write Barrier）：引擎在每次执行属性赋值 A.child = D 时插入极其轻量的一行拦截检查——一旦发现“⚫黑色对象引用了⚪白色对象”，写屏障立即介入将白色对象 D 强制涂成🔘灰色放入待扫描队列，从而确保绝不会漏标任何一个存活对象。

这节回答实战篇哪个问题：对应 实战篇 08.5 线上排障 与 09 场景自测第 04 题 —— 服务运行一天后内存越来越大，具体怎么采两份堆快照在 Chrome DevTools 里揪出泄漏的那行代码？

当对象已不再被业务逻辑需要，但仍被 GC Root（如全局对象、模块级变量、活跃闭包或未清理的定时器）直接或间接引用时，垃圾回收器无法释放该对象，从而形成内存泄漏。以下是工程中最常见的四类泄漏写法及其修复方式：
