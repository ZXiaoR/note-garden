05.1 · 子进程底层机制：spawn 核心基座、四种 API 封装关系、IPC 管道与命令注入防护

05.1 node:child_process 底层调用关系、IPC 通道原理与安全规范

① 先看清四个函数的底层关系：只有 spawn 是地基，其余三个全是基于它的封装。
打开 Node.js 源码（lib/child_process.js）会发现，spawn、execFile、exec、fork 并不是四个平起平坐的独立系统调用——最底层只有 spawn 调用了 C++ 层的 uv_spawn（在 Linux/macOS 上执行 fork() + execvp() 创建操作系统子进程），其余三个方法都是围绕 spawn 做的不同默认配置包装：

API 方法 等价的底层 spawn 封装逻辑 是否启动 Shell 数据返回形式 核心特点与适用场景
1. spawn(file, args)
（最底层基座）		 直接调用 uv_spawn，建立父子进程 stdin / stdout / stderr 三条流管道 否（默认 shell: false） Stream 流式实时返回
（无内存大小上限）		 每产生一块输出就触发一次 stdout.on('data')，适合输出体积巨大或持续运行的子进程（如实时读取视频转码、日志流）。
2. execFile(file, args, cb)
（调用外部程序首选）		 spawn(file, args) + 在内存中把 stdout/stderr 流拼接为完整 Buffer/String 后触发回调 否（直接执行目标二进制程序） 攒齐后一次性回调
（默认上限 maxBuffer = 1MB）		 安全且高效：不拉起额外的 /bin/sh 进程，参数作为独立数组元素直接传给目标程序，天然免疫 Shell 命令注入。
3. exec(command, cb)
（仅用于固定 Shell 脚本）		 execFile('/bin/sh', ['-c', command], cb)（Windows 下调用 cmd.exe /d /s /c） 是（先启动 Shell 解释器） 攒齐后一次性回调
（默认上限 maxBuffer = 1MB）		 因为启动了 Shell，所以支持管道符 a | b、通配符 *.log 与重定向；但绝不可直接拼接用户输入字符串。
4. fork(jsModulePath)
（专用于派生 Node 子进程）		 spawn(process.execPath, [jsModulePath], { stdio: ['pipe', 'pipe', 'pipe', 'ipc'] }) 否（直接启动新 Node 进程） 内置双向 IPC 通道
（send() / on('message')）		 除了标准输入输出外，额外创建第 4 条文件描述符通道（Unix Domain Socket），不仅能收发 JSON 消息，还能跨进程传递 TCP Socket 句柄（Cluster 的基石）。
vs child_process_safe.js · 为什么 exec 拼接字符串会导致命令注入 
import { exec, execFile } from 'node:child_process';
const userInput = 'main; rm -rf /tmp/test';

// ❌ 错误写法：exec 会启动 /bin/sh -c "git branch --list main; rm -rf /tmp/test"
//    Shell 遇到分号 ; 会将其拆成两条独立命令依次执行，导致服务器文件被删
exec(`git branch --list ${userInput}`, (err, stdout) => {});

// ✅ 正确写法：execFile 不经过 Shell，直接调用操作系统 execvp("git", [...])
//    git 会把 "main; rm -rf /tmp/test" 当作一个整体分支名去查找，只会提示分支不存在
execFile('git', ['branch', '--list', userInput], (err, stdout) => {
  console.log(stdout);
});
fork_ipc_fd.js · fork() 父子进程通过 IPC 传递普通消息与 TCP 连接句柄 
// 父进程创建子进程后，底层自动通过环境变量 NODE_CHANNEL_FD 传入 IPC 管道描述符：
// 1. 传递普通 JSON 数据：
child.send({ task: 'compute', id: 101 });

// 2. 传递底层 TCP Socket 句柄（第二个参数 sendHandle）：

child.send('socket', clientSocket);
05.2 · 多进程共享端口与零停机发版：Cluster 拦截 listen() 原理、Round-Robin 分发与滚动重启

05.2 Cluster 多进程共享 8080 端口机制与零停机平滑重启

① 揭开核心疑问：正常情况下两个进程同时监听 8080 端口会报 EADDRINUSE 错误，为什么 Cluster 里写 8 个 Worker 调用 server.listen(8080) 却完全正常？
因为 Node.js 在底层对 net.Server.prototype.listen 做了主从偷梁换柱——整台服务器上真正向操作系统申请绑定 8080 端口的只有 Primary 主进程一个，所有 Worker 子进程的 listen(8080) 其实是一次“向主进程报名”的虚假调用，完整 4 步流转如下：

  • Step 1 · Worker 报名（拦截 listen）：当 Worker 子进程执行 server.listen(8080) 时，Node.js 检测到当前 cluster.isWorker === true，直接跳过操作系统的端口绑定调用，改为通过 IPC 通道给主进程发一条内部消息 { act: 'queryServer', port: 8080 }。
  • Step 2 · 主进程唯一绑定端口：Primary 主进程收到报名后，在主进程内部创建一个底层 TCP 监听句柄并向操作系统真正绑定 :8080 端口（若已绑定过则直接复用），然后把 Worker 登记到该端口的可用工作进程列表中。
  • Step 3 · 客户端连入与 Round-Robin 轮询挑人：当外部客户端向 :8080 发起 TCP 连接时，Primary 主进程负责调用 accept() 接收连接，拿到代表该客户端的 Socket 文件描述符（FD），然后按 Round-Robin（轮询） 算法从登记列表里挑出一个空闲的 Worker。
  • Step 4 · IPC 移交 Socket 句柄，Worker 直接读写响应：主进程通过 IPC 管道（SCM_RIGHTS）把该客户端 Socket FD 发送给被选中的 Worker。Worker 接管句柄后直接与客户端收发 HTTP 报文，后续业务数据不再经过主进程中转，因此主进程绝不会成为带宽瓶颈。

② 生产级进阶：如何基于 Cluster 实现“零停机平滑发版（Zero-Downtime Reload）”？
线上更新代码时，如果直接重启整个服务，正在处理中的用户请求会被强行断开。PM2 的 pm2 reload 底层正是利用 Cluster 实现了“先启新进程、再退旧进程”的滚动替换闭环：

cluster_zero_downtime.mjs · 零停机滚动重启与崩溃自愈完整代码 
import cluster from 'node:cluster';
import http from 'node:http';
import os from 'node:os';

if (cluster.isPrimary) {
  for (let i = 0; i < os.availableParallelism(); i++) cluster.fork();

  // 1. 崩溃自愈：某个 Worker 意外退出（且非主动平滑断开）时，立即补齐新 Worker
  cluster.on('exit', (worker) => {
    if (!worker.exitedAfterDisconnect) cluster.fork();
  });

  // 2. 收到 SIGUSR2 热重载信号时，逐个滚动替换旧 Worker（零停机发版核心逻辑）：
  process.on('SIGUSR2', async () => {
    for (const oldWorker of Object.values(cluster.workers)) {
      const newWorker = cluster.fork(); // ① 先派生运行新代码的 Worker
      await new Promise((r) => newWorker.once('listening', r)); // ② 等新进程就绪
      oldWorker.disconnect();           // ③ 通知旧进程停止接新活，处理完存量后退出
    }
  });
} else {
  const server = http.createServer((req, res) => res.end(`PID ${process.pid}`));
  server.listen(8080);
}
为什么不让多个 Worker 直接共享监听 Socket 去抢 accept()？

Node.js 早期曾尝试让所有 Worker 直接挂在同一个底层监听 Socket 上由操作系统内核唤醒。但在 Linux 下，内核为了减少上下文切换，往往优先唤醒最后休眠的 1~2 个进程（LIFO 饥饿现象），导致 8 核机器上 2 个 Worker 占满 100% CPU，其余 6 个几乎分不到请求。
因此 Node.js 将默认调度策略改为主进程统一 accept + Round-Robin 轮询分发，确保每个 Worker 分到的连接数严格均衡。

05.3 · 多线程底层模型：worker_threads 多 V8 Isolate 架构、三种内存传输方式与 Atomics 同步

05.3 node:worker_threads 进程内多 Isolate 架构与三种跨线程内存通信机制

① worker_threads 启动后，进程内部到底长什么样？（什么独享、什么共享？）
与开启新进程的 Cluster 不同，new Worker() 是在当前同一个操作系统进程内部新建一条内核线程。为了保证 JavaScript 变量不会发生多线程同时修改的混乱，Node.js 采用了“V8 引擎实例隔离 + 进程底层资源共享”的设计：

  • 每个线程各自独享（互不干扰）：每个 Worker 线程都拥有自己独立的 V8 Isolate 实例（独立的 JS 堆内存、独立的 GC、独立的全局对象 globalThis）和自己独立的 libuv 事件循环（Event Loop）。因此 Worker 里跑死循环 CPU 计算，绝对不会卡住主线程的 Event Loop。
  • 整个进程共同享有：所有线程处于同一个操作系统虚拟内存地址空间内（因此可以通过指针直接共享同一块物理内存，基础开销仅几 MB），并共用同一个底层 libuv Worker 线程池。

② 主线程与 Worker 之间传数据时，三种传输方式（拷贝 vs 过户 vs 共享）怎么选？
因为两个线程的 V8 JS 堆是隔离的，普通对象 { a: 1 } 不能直接共享引用。Node.js 提供了三种成本截然不同的跨线程传递方式：

mode1_and_2.mjs · 方式①深拷贝 vs 方式② transferList 零拷贝过户 
// --- 方式 ①：默认结构化克隆（深拷贝，适合传几 KB 的普通配置或小结果）---
// 底层将对象序列化再反序列化，若传 100MB Buffer 会产生 100MB 额外内存拷贝开销
worker.postMessage({ type: 'resize', width: 800 });

// --- 方式 ②：transferList 所有权零拷贝转移（适合单向移交大块二进制数据）---
const bigAb = new ArrayBuffer(100 * 1024 * 1024); // 100MB 物理内存
// 将 bigAb 放入第二个参数数组（transferList）中，底层直接将内存指针过户给 Worker：
worker.postMessage(bigAb, [bigAb]);

// 过户耗时接近 0ms（零拷贝），但过户后当前线程立即失去该内存的访问权：
console.log(bigAb.byteLength); // 输出: 0 (已变为 Detached 脱离状态，防止两边同时改)
mode3_shared_atomics.mjs · 方式③ SharedArrayBuffer + Atomics 原子读写 
import { Worker, isMainThread, workerData } from 'node:worker_threads';

if (isMainThread) {
  // --- 方式 ③：SharedArrayBuffer（多个线程同时读写同一块物理内存，无需过户）---
  const sharedBuf = new SharedArrayBuffer(4); // 分配 4 字节共享内存
  const view = new Int32Array(sharedBuf);     // 套上 32 位整数视图卡片

  new Worker(new URL(import.meta.url), { workerData: sharedBuf });
} else {
  const view = new Int32Array(workerData);
  // ❌ 错误写法：view[0]++ 分为「读-改-写」三步指令，多线程同时算会互相覆盖丢数据
  // ✅ 正确写法：使用 Atomics.add 执行 CPU 硬件级原子加 1，保证并发绝对安全
  Atomics.add(view, 0, 1);
}
对比维度 Cluster（多进程集群） worker_threads（进程内多线程）
底层实体与开销 独立的操作系统进程（独立页表与全部运行时，每个进程起步约 30MB+ 内存） 同一进程内的轻量线程（共享进程地址空间，每个线程额外开销仅数 MB）
故障隔离半径 进程级强隔离：某个 Worker 进程崩溃或 OOM 退出，其他进程完全不受影响 同进程命运共同体：若某个 Worker 线程引发未捕获异常或进程级 OOM，整个进程会一起退出
数据共享能力 只能通过 IPC 管道序列化拷贝（或传递 Socket FD），无法直接共享大块内存变量 支持 transferList 零拷贝移交与 SharedArrayBuffer + Atomics 共享物理内存
生产工程选型 用于 Web 服务最外层扩展多核 HTTP 吞吐量（如 8 核服务器通过 PM2 启动 8 个进程共享 8080 端口） 用于卸载单个进程内的 CPU 密集型计算任务（如图片压缩、PDF 生成、大 JSON/Excel 解析、加解密）
