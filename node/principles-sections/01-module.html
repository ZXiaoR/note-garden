01.1 · 模块加载与导出机制：CommonJS 运行时值拷贝与 ES Module 编译期实时绑定

01.1 CommonJS（运行时值拷贝）与 ES Module（编译期静态实时绑定） 常问

这节回答实战篇哪个问题：对应 实战篇 02.1 模块化日常写法 —— 同样是把变量导出给别的文件用，require 与 import 在内存绑定时机上有什么本质差异？为什么在 CJS 里写 exports = { add } 外部拿到的是空对象？

Node.js 支持两套模块化规范：早期内置的 CommonJS（使用 require / module.exports，文件扩展名通常为 .cjs 或默认 .js） 与语言标准 ES Module（使用 import / export，扩展名为 .mjs 或在 package.json 中声明 "type": "module"）。
两者的核心区别在于：CommonJS 在代码运行到 require() 时同步加载模块，并导出那一刻的对象属性拷贝；而 ES Module 在编译阶段静态解析依赖树，导出指向原模块变量内存槽位的只读实时引用（Live Binding）。

counter_cjs.cjs · CommonJS 导出运行时的值拷贝 
// --- counter.cjs ---
let count = 1;
function inc() { count++; }
module.exports = { count, inc }; // 导出瞬间将 count=1 的值复制进导出对象

// --- main.cjs ---
const { count, inc } = require('./counter.cjs');
console.log(count); // 输出: 1
inc();              // 模块内变量变为 2，但已导出的拷贝对象不受影响
console.log(count); // 输出: 1
counter_esm.mjs · ES Module 导出实时内存引用 
// --- counter.mjs ---
export let count = 1;
export function inc() { count++; }

// --- main.mjs ---
import { count, inc } from './counter.mjs';
console.log(count); // 输出: 1
inc();              // 修改同一个内存槽位的数据
console.log(count); // 输出: 2（外部读取到实时更新后的值）
// count = 99;      // ❌ TypeError: Assignment to constant variable (导入方只读)
对比维度 CommonJS (require / module.exports) ES Module (import / export)
导出语义 运行时值的浅拷贝（导出后原模块修改基础类型变量不影响外部） 编译期静态实时只读绑定（Live Binding）（指向同一内存槽，内部修改外部同步可见）
加载时机 运行时同步加载：支持动态拼接路径 require('./' + name)，不利于静态 Tree-Shaking 编译期静态解析 + 异步加载：支持打包工具静态 Tree-Shaking 与顶层 await
顶层作用域 顶层 this === module.exports；通过包装函数注入 __dirname / __filename 默认严格模式，顶层 this === undefined；使用 import.meta.dirname（Node 20.11+）
互操作性 Node 22.12+ 默认支持同步 require(esm)（前提是目标 ESM 不含顶层 await） ESM 可直接 import cjs from './a.cjs'（将 module.exports 作为默认导出）
vs exports_vs_module_exports.cjs · 形参重赋值误区与正确导出写法 
// 包装函数内部隐含初始关系：let exports = module.exports = {};

// ❌ 错误写法：直接给形参 exports 赋新对象，切断了与 module.exports 的引用关系
//    由于 require() 最终只返回 module.exports，外部拿到的是空对象 {}
exports = { add: (a, b) => a + b };

// ✅ 正确写法 A：顺着引用往原对象上挂载属性
exports.add = (a, b) => a + b;

// ✅ 正确写法 B：直接替换 module.exports 对象本身
module.exports = { add: (a, b) => a + b };
常见误区说明：exports 与 module.exports 的引用关系
在 CommonJS 包装函数中，exports 只是传入函数的形参变量，初始时与 module.exports 指向同一个空对象 {}。通过 exports.key = val 可以修改该共享对象；但如果直接执行 exports = { ... }，只会让形参变量指向新内存地址，而模块加载器第 ⑤ 步固定返回 module.exports。
01.2 · 循环依赖处理机制：CommonJS 半成品缓存导出与 ES Module 静态内存连线

01.2 循环依赖（A ⇄ B）对比：CommonJS 半成品对象与 ESM 实时引用 深挖

这节回答实战篇哪个问题：对应 实战篇 02.1 模块化 —— 项目中两个文件不小心互相引用（A 引 B、B 又引 A）时，为什么 Node.js 不会陷入死循环，但有时会读到 undefined 或报暂时性死区（TDZ）错误？

当模块 A 引用模块 B，而模块 B 又反过来引用模块 A 时，Node.js 不会陷入无限递归死循环，因为模块在首次加载进入前就会被登记到缓存中。但由于两套规范的加载阶段不同，在循环引用点读取到的值存在明显差异：

cycle_cjs.cjs · CommonJS 循环依赖：读取已执行部分的半成品对象 
// --- a.cjs (入口: node a.cjs) ---
exports.done = false;            // ① 先挂载属性 done = false
const b = require('./b.cjs');   // ② 暂停 a.cjs，同步进入 b.cjs 执行
exports.done = true;             // ⑤ b.cjs 执行完毕返回，将 a.done 改为 true
console.log('在 a 中, b.done =', b.done);

// --- b.cjs ---
const a = require('./a.cjs');   // ③ 命中 _cache，拿到 a 当前的半成品 {done: false}
console.log('在 b 中, a.done =', a.done); // ④ 输出: false
exports.done = true;
// 完整输出: 在 b 中, a.done = false ➔ 在 a 中, b.done = true
cycle_esm.mjs · ES Module 循环依赖：函数声明提升与暂时性死区（TDZ） 
// --- a.mjs (入口: node a.mjs) ---
import { bVal } from './b.mjs';  // ① 编译期静态建图，求值阶段先深度优先执行 b.mjs
export function fnA() { return 'ok'; } // function 声明在实例化阶段已完成提升
export const aVal = 'hello';

// --- b.mjs ---
import { fnA, aVal } from './a.mjs';
console.log(fnA());              // ✅ 输出: 'ok'（函数声明在实例化阶段已就绪）
// console.log(aVal);            // ❌ 错误写法：a.mjs 尚未求值，同步读取 const/let
                                 //    会触发 ReferenceError (暂时性死区 TDZ)
export const bVal = 'world';
循环依赖机制总结：
• CommonJS（边执行边导出）：进入 a.cjs 时先在 Module._cache 中注册该模块的 exports 对象。当 b.cjs 反过来调用 require('./a.cjs') 时，直接从缓存中拿到当前只执行了一半的导出对象（后续尚未执行到的属性值为 undefined）。
• ES Module（先绑定内存槽再求值）：实例化阶段已将所有导入与导出标识符连向同一内存槽。求值阶段先执行 b.mjs 时，a.mjs 的 export function 因函数提升可直接调用；但若在模块顶层同步读取尚未执行初始化的 export let / const 变量，则会触发暂时性死区（Temporal Dead Zone, TDZ）ReferenceError。
01.3 · 工程包配置规范：package.json 条件导出（Conditional Exports）与现代 Node LTS 内置能力

01.3 package.json 条件导出配置与现代 Node.js 原生工具链 深挖

这节回答实战篇哪个问题：对应 实战篇 02.2 package.json 与 08.2 TypeScript 接入 —— 写公共包时怎么让同一份包同时支持外部 import 和 require，以及如何配置内部私有路径别名？

在发布需要同时兼容 import（ESM）和 require（CJS）的公共库时，可通过 package.json 的 exports 条件导出字段按调用方式映射不同的入口文件，并利用 imports 定义项目内部私有路径别名。

package.json · 双模块条件导出与内部路径映射示例 
{
  "name": "my-modern-sdk",
  "type": "module", // 声明当前包下 .js 文件默认按 ES Module 规范解析
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",   // types 条件需放在最前，供 TypeScript 类型解析
      "import": "./dist/index.mjs",   // 外部使用 import 时加载该文件
      "require": "./dist/index.cjs"  // 外部使用 require() 时加载该文件
    }
  },
  "imports": {
    "#db/*": "./src/internal/db/*.js" // 必须以 # 开头，提供原生内部路径别名
  }
}
Node.js 22 / 24 / 26 LTS 常用原生工程特性：
  • 内置模块 node: 协议前缀：编写 import fs from 'node:fs/promises' 时跳过文件目录查找，直接加载内核模块，并防止被 node_modules 中的同名第三方包覆盖。
  • 原生执行 TypeScript（Node 22.18+ / 24+ 默认免参数）：直接执行 node app.ts 即可在运行时剥离可擦除类型注解并运行（v22.6 ~ v22.17 需加 --experimental-strip-types）。
  • 原生环境变量加载与文件监听：使用 node --env-file=.env --watch app.js，无需额外部署 dotenv 与 nodemon。
  • 模块封装保护：一旦声明了 exports 字段，外部调用方将无法深层引入未在 exports 中列出的内部私有文件路径（触发 ERR_PACKAGE_PATH_NOT_EXPORTED）。
