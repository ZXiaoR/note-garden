⚡ 03.1 Buffer 内存模型、8KB Slab 共享内存池与 alloc / allocUnsafe 机制

① 先立核心心智模型：Buffer 变量本身不是那块物理内存，而是一张“视图描述卡片”。
初学者看代码时常会疑惑：为什么变量本身已经叫 Buffer 了，访问 b1.buffer 却又能拿出另一个对象？这是因为在 Node.js（及 V8 引擎）底层，二进制内存被拆成了上下两层结构：

  • 下层 · 物理字节条（ArrayBuffer）：真正向操作系统申请的一段连续原始字节内存（例如一整条 8192 Bytes 的内存块）。它只负责存数据，本身不能直接用 [0] 下标读写。
  • 上层 · 视图描述卡片（Buffer 实例，继承自 Uint8Array）：我们代码里拿到的 b1、b2 其实是轻量级“观察窗口卡片”，卡片自身只记录 3 个核心字段：
    1. buffer（指针）：指向底下那整条物理 ArrayBuffer；
    2. byteOffset（起始偏移量）：这张卡片从物理内存条的第几个字节开始看（如从第 0 字节或第 104 字节开始）；
    3. byteLength（可见长度）：这张卡片能读写多少个字节（如 100 字节）。

② 为什么要设计 8KB (8192 Bytes) Slab 共享内存池？
在网络服务中，每秒都会产生成千上万个几十到几百字节的小数据包。如果每次创建 100 字节的 Buffer 都向操作系统单独申请一块物理 ArrayBuffer，系统调用与垃圾回收开销极大。
既然多个 Buffer 视图卡片可以指向同一条物理 ArrayBuffer（只要各自的 byteOffset 互不重叠即可），Node.js 启动时便预先申请一整条 8192 Bytes (8KB) 的全局共享 ArrayBuffer（称为 Slab 内存池），并用一个全局游标变量 poolOffset 记录当前用到了第几个字节。后续创建小 Buffer 时，只需在池子上移动游标、切出一张新的视图卡片即可。

🧪 buffer_pool.js · 观察两个小 Buffer 如何共享同一块 8KB 物理内存 
// 1. 共享池默认总大小 Buffer.poolSize = 8192 字节 (8KB)
console.log(Buffer.poolSize);               // 输出: 8192

// 2. 连续调用 allocUnsafe 创建两个 100 字节的小 Buffer：
const b1 = Buffer.allocUnsafe(100);
const b2 = Buffer.allocUnsafe(100);

// 观察两张视图卡片的 3 个核心属性：
console.log(b1.buffer === b2.buffer);       // 输出: true (指向同一条 8192B 物理内存)
console.log(b1.buffer.byteLength);          // 输出: 8192 (底层整块池子的总长度)
console.log(b1.byteOffset, b1.byteLength);  // 输出: 0   100 (假定池刚初始化，占用 0..99)
console.log(b2.byteOffset, b2.byteLength);  // 输出: 104 100 (按 8 字节对齐，占用 104..203)

// 3. 对比 Buffer.alloc(100)：不走 8KB 共享池，单独分配一块恰好 100B 且全为 0 的物理内存
const safeBuf = Buffer.alloc(100);
console.log(safeBuf.buffer === b1.buffer);  // 输出: false (独享自己的 100B ArrayBuffer)
console.log(safeBuf.buffer.byteLength);     // 输出: 100
📖 游标 poolOffset 切分与推进的 4 个步骤：
  • Step 1 · 建池（createPool）：分配一块 8192B 的 ArrayBuffer，游标初始化为 poolOffset = 0。
  • Step 2 · 切出 b1(100B)：b1 记录 byteOffset = 0, byteLength = 100（占用下标 0..99），游标推进至 100。
  • Step 3 · 8 字节内存对齐（为什么 b2 从 104 开始？）：64 位 CPU 按 8 字节（64 bit）字长对齐读取内存最快。每次切完后，Node.js 会把 poolOffset 向上凑整到 8 的整数倍（位运算 (100 + 7) & ~7 = 104），中间跳过 4 个字节（100..103）作为对齐留白，因此 b2 从 104 开始（占用 104..203），再加 4 字节对齐（204..207）后游标停在 208。
  • Step 4 · 剩余空间不足时换新池：若当前池子剩余空间（8192 - poolOffset）不够装下本次请求的 size，则直接调用 createPool() 申请一块全新的 8192B 池子并将 poolOffset 归零。

③ 哪些 API 会走 8KB 共享内存池？为什么分界线是 4096 Bytes (4KB)？
因为共享池总大小只有 8192 Bytes，如果允许 5KB、6KB 的较大请求也进池，一个请求就会占掉大半个池子，导致旧池子剩余的几 KB 装不下后续请求而被迫直接丢弃换新池，反而造成内存浪费。因此 Node.js 规定：只有请求大小严格小于池容量的一半（即 size < (Buffer.poolSize >>> 1)，小于 4096 字节）时，才允许进入共享池：

创建方式 / API 是否走 8KB 共享池 内存是否清零 底层分配行为与适用场景
Buffer.alloc(size) ❌ 永不走池（无论大小） ✅ 全部初始化为 0x00 直接向底层申请一块长度为 size 且已清零的独立 ArrayBuffer。日常业务开发最推荐的默认安全写法。
Buffer.allocUnsafe(size)
（当 size < 4096B 时）		 ✅ 走 8KB 共享池 ❌ 未清零（含旧残留字节） 直接从全局 8KB 共享池当前 poolOffset 处切出视图返回，省去系统调用与清零开销；必须在紧接着的代码里将整块区域写满新数据。
Buffer.allocUnsafe(size)
（当 size >= 4096B 时）		 ❌ 不走共享池 ❌ 未清零 因大于等于 4KB 阈值，直接单独申请一块长度为 size 的未清零独立 ArrayBuffer。
Buffer.from(str)
或 Buffer.concat(list)		 ✅ 总字节数 < 4096B 时走 8KB 共享池 ✅ 立即被传入的字符串/数组完整覆写 内部先调用池化分配切出空间，随后立即将字符串编码字节完整写入该切片，既享受了共享池的高性能，又不会泄露旧内存数据。
Buffer.allocUnsafeSlow(size) ❌ 强制不走池 ❌ 未清零 哪怕只有 10 个字节也强制单独申请独立 ArrayBuffer——专用于需要长期驻留在全局缓存中的小 Buffer，防止它拖住整块 8KB 共享池无法释放。
⚠️ 注意事项 ① · allocUnsafe 未写满即发送导致旧内存数据泄露 
// ❌ 错误写法：申请了 64 字节未清零池化切片，只写入 5 字节就把整个 buf 发出去
// 后面的第 5..63 字节里可能残留着刚才其他请求留下的密钥或隐私字符串
const unsafeBuf = Buffer.allocUnsafe(64);
const written = unsafeBuf.write('hello');
// socket.write(unsafeBuf); // 危险：把未覆写的 59 字节旧内存一并发给了客户端

// ✅ 正确写法 A：直接用 Buffer.alloc(64)（默认全 0）或 Buffer.from('hello')
const safeBuf = Buffer.alloc(64);

// ✅ 正确写法 B：若使用 allocUnsafe，只截取实际写入的 [0, written) 区间发送
const validSlice = unsafeBuf.subarray(0, written);
⚠️ 注意事项 ② · 长期缓存小切片导致整块 8KB 共享池无法被 GC 回收 
const globalCache = [];

// ❌ 错误写法：subarray(0, 16) 只是新建了一张 16B 的视图卡片，
// 它的 .buffer 依然强引用着底下整块 8KB ArrayBuffer，放进全局数组会导致 8KB 无法回收
function cacheHeaderBad(packetBuf) {
  globalCache.push(packetBuf.subarray(0, 16));
}

// ✅ 正确写法：需要长期缓存小片段时，用 Uint8Array.prototype.slice 拷贝出独立的 16B 内存
function cacheHeaderGood(packetBuf) {
  const independentCopy = Buffer.from(Uint8Array.prototype.slice.call(packetBuf, 0, 16));
  globalCache.push(independentCopy); // 仅占 16B 独立内存，原 8KB 池可正常释放
}
🔍 展开查看 Node.js 源码（lib/buffer.js）：createPool() 与 allocate(size) 真实实现
📜 node/lib/buffer.js · 8KB Slab 共享池分配与 8 字节对齐核心源码 
Buffer.poolSize = 8 * 1024; // 默认 8192 Bytes
let poolSize, poolOffset, allocPool;

function createPool() {
  poolSize = Buffer.poolSize;
  allocPool = createUnsafeArrayBuffer(poolSize); // 向底层申请未清零的 8192B ArrayBuffer
  poolOffset = 0;                                // 游标归零
}
createPool(); // Node.js 启动时立即预分配第一个 8KB 池

function alignPool() {
  // 位运算向上取 8 的整数倍：若 poolOffset 为 100，(100 + 7) & ~7 === 104
  if (poolOffset & 0x7) {
    poolOffset |= 0x7;
    poolOffset++;
  }
}

function allocate(size) {
  // 1. 若请求字节数 < 4096 (即 poolSize >>> 1)，进入 8KB 共享池分配分支：
  if (size < (Buffer.poolSize >>> 1)) {
    if (size > (poolSize - poolOffset))
      createPool(); // 当前池剩余空间不足时，申请一个新的 8KB 池
    const b = new FastBuffer(allocPool, poolOffset, size); // 创建指向共享池的视图卡片
    poolOffset += size;
    alignPool();    // 游标做 8 字节对齐，供下一次分配使用
    return b;
  }
  // 2. 若请求字节数 >= 4096，不走共享池，单独分配一块未清零的 ArrayBuffer
  return createUnsafeBuffer(size);
}
🌊 03.2 · 流式缓冲与限流状态机：_readableState / _writableState 与背压控制机制

🚰 03.2 Stream 内部缓冲状态机、highWaterMark 水位线与背压（Backpressure）流转

在流式传输中，当上游磁盘读取速度（如 500MB/s）远快于下游客户端网络接收速度（如 1MB/s）时，若不对上游限速，未发送的数据块会在可写流内部持续积压直至内存溢出。
从底层对象结构来看，每个 Readable 实例内部维护一个 _readableState 状态对象，每个 Writable 实例内部维护一个 _writableState 状态对象（Duplex 双工流则同时拥有这两个相互独立的状态对象）。背压（Backpressure）的本质就是围绕这两个状态对象中的队列长度 length 与水位线阈值 highWaterMark 进行的布尔信号反馈：

底层状态对象与核心字段 默认值 / 数据结构 在背压（Backpressure）流转中的具体作用
_readableState.buffer BufferList 双向链表 暂存已从底层数据源（如磁盘 fd）读出、但尚未被下游消费的数据块，避免数组头部弹出时的 O(N) 搬移开销。
_readableState.flowing null / true / false 标识可读流当前模式：true 为自动持续推送数据的流动模式；调用 readable.pause() 后变为 false，停止向底层读取。
_writableState.length number（字节数或对象数） 记录当前可写流内部待写入底层内核的缓冲队列累计字节数；每次调用 writable.write(chunk) 时累加。
_writableState.highWaterMark 普通流 16KB / 文件流 64KB / 对象流 16 可写流缓冲区的安全水位线上限。当写入后满足 state.length >= state.highWaterMark 时，write() 立即返回 false 并设置 needDrain = true；待队列排空至 0 时触发 'drain' 事件。
🔧 manual_backpressure.js · write 返回值检查、pause 暂停与 drain 恢复原理 
readable.on('data', (chunk) => {
  // 1. 向下游写入数据块，并根据返回值判断写缓冲是否已满
  const canContinue = writable.write(chunk);

  // 2. 返回 false 表示下游缓冲区已达到 highWaterMark 水位线
  if (!canContinue) {
    readable.pause(); // 暂停从上游可读流继续读取
  }
});

// 3. 当下游将积压的写缓冲区排空后，自动触发 'drain' 事件：
writable.on('drain', () => {
  readable.resume();  // 恢复上游可读流继续读取
});
❌ vs ✅ stream_pipeline.mjs · 传统 .pipe() 缺陷与 stream.pipeline 标准写法 
import { pipeline } from 'node:stream/promises';
import fs from 'node:fs';
import zlib from 'node:zlib';

// ❌ 错误写法：直接使用裸 .pipe() 串联流
//    若下游客户端中途断开，上游文件流不会自动关闭，容易造成文件描述符 (FD) 泄漏
// fs.createReadStream('a.log').pipe(zlib.createGzip()).pipe(res);

// ✅ 正确写法：使用 pipeline 自动管理背压，并在任一环节报错或关闭时自动销毁全部流
await pipeline(
  fs.createReadStream('./huge-2gb.log'),
  zlib.createGzip(),
  fs.createWriteStream('./huge-2gb.log.gz')
);
