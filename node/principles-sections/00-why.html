🧭 00.1 · 并发模型演进：传统多线程阻塞 I/O 与单线程事件驱动架构对比

💡 00.1 高并发 I/O 瓶颈与 Node.js 的事件驱动非阻塞模型

在传统的“一请求一线程”同步阻塞服务器中，当线程发起磁盘读取或数据库查询时，整个操作系统线程会被挂起等待 I/O 返回。由于 Web 服务的大部分耗时集中在 I/O 等待上，若每个线程栈默认占用 2MB 内存，面对上万个并发连接时，仅线程栈的物理内存开销与内核上下文切换成本就会成为系统瓶颈。
Node.js 采用单线程事件循环（Event Loop）配合非阻塞 I/O 的设计：将 JavaScript 代码运行在单个主线程上，把慢速的网络与文件 I/O 委托给底层的 libuv 异步库与操作系统内核，待 I/O 完成后再通过回调函数通知主线程继续处理。

核心机制 ① · 异步非阻塞 Ch.01~02
主线程负责事件调度，I/O 交由内核与线程池

主线程发起 I/O 请求后立即返回并继续处理后续连接；网络 Socket 读写由操作系统内核 epoll / kqueue 监控，文件与加密操作由 libuv 工作线程池在后台执行。

核心机制 ② · 流与分代内存 Ch.03~04
Buffer 8KB 内存池 + Stream 背压 + V8 分代 GC

单进程内的所有请求共享同一个 V8 堆。通过堆外 8KB 池化 Buffer 与 Stream 水位线背压机制，可以用几十 KB 的固定内存缓冲区平稳转发 GB 级文件。

核心机制 ③ · 多核扩展与工程化 Ch.05~06
Cluster 多进程共享端口 + 工作线程 + 上下文透传

生产环境通过 Cluster 多进程模式充分利用多核 CPU，使用 worker_threads 隔离 CPU 密集型计算，并通过 AsyncLocalStorage 实现异步调用链路的上下文透传。

🟢 non_blocking_io.mjs · 异步非阻塞读取与 Error-First 回调示例 
import fs from 'node:fs'; // 引入内置文件系统模块（推荐带 node: 前缀）

console.log('1. [请求A] 发起异步读取，交由 libuv 后台线程执行');

// 参数依次为：文件路径、字符编码、错误优先回调函数 (err, data)
fs.readFile('./package.json', 'utf8', (err, data) => {
  if (err) return console.error(err); // 成功时 err 为 null
  console.log(`3. [请求A] 读取完成，执行回调 (${data.length} 字节)`);
});

console.log('2. [请求B] 主线程不阻塞，立即继续处理后续逻辑');
// 输出顺序: 1 ➔ 2 ➔ 3
📖 基础概念说明：线程分工与错误优先回调（Error-First Callback）
  • 进程内的线程分工：开发者的 JavaScript 代码运行在 1 个主线程上；但 Node.js 进程底层同时包含 libuv 工作线程池（默认 4 个 C++ 线程，负责文件 I/O、DNS lookup 与加密计算） 以及 V8 后台线程（负责并发垃圾回收与 JIT 编译）。
  • 回调函数的参数约定 (err, data)：Node.js 回调接口统一将第 1 个参数保留给错误对象 err（无错误时为 null），第 2 个参数 data 存放成功返回的结果。

❌ vs ✅ event_loop_rule.js · 请求链路中同步阻塞与异步非阻塞写法对照 
// ❌ 错误写法：在 HTTP 请求处理函数中调用 *Sync 同步方法
//    读取期间主线程被挂起，其他所有并发请求均无法响应
app.get('/bad', (req, res) => {
  const tpl = fs.readFileSync('./page.html', 'utf8');
  res.end(tpl);
});

// ✅ 正确写法：请求链路内统一使用 fs/promises 异步 API 或 Stream 流
app.get('/good', async (req, res) => {
  const tpl = await fs.promises.readFile('./page.html', 'utf8');
  res.end(tpl);
});
⚠️ 工程设计原则：避免阻塞主线程事件循环（Don't Block the Event Loop）
Node.js 支撑高并发的前提是每个请求在主线程上的同步 CPU 执行时间保持在微秒至毫秒级。以 Sync 结尾的同步 API（如 fs.readFileSync）仅限在服务启动初始化配置时使用；在请求处理链路中应统一使用异步 API，避免因慢 I/O、复杂回溯正则（ReDoS）或超大 JSON 同步解析阻塞整个进程。
