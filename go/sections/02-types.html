📐 02.1 · 为什么子切片 append 一个元素会悄悄篡改原数组？容量不够时是怎么扩容的？

🔪 02.1 slice 切片：24 字节描述符、共享底层陷阱与平滑扩容规则

固定长度数组 [4]int 是纯值类型（传参整块拷贝 32B）；而日常使用的 []int 切片（Slice）本身并不存储元素，它只是一个指向底层连续数组的 24 字节轻量级视图表头（{ array 指针 8B, len 长度 8B, cap 容量 8B }）：

📈 append 容量不够时怎么扩容？（小翻倍、大变慢）
  • 容量够用（len < cap）：直接在原底层数组尾部覆盖写入（所以上图 b := a[1:3] 的容量是 3，执行 append(b, 99) 会直接覆盖掉 a[3]！可用三索引切片 a[1:3:3] 锁死容量来防范）。
  • 容量不够（触发扩容搬家）：分配一块更大的新数组，把老元素拷过去并返回新表头：
    • 小切片（旧容量 < 256）：直接翻倍（2x），避免频繁分配；
    • 大切片（旧容量 >= 256，Go 1.18+）：增长率从 2x 平滑衰减到 1.25x（每次涨约 1/4），防止大切片翻倍浪费成吨内存。
⚠️ slice_traps.go · nil 切片 vs 空切片 & 大切片内存泄漏 
// 1. nil 切片 vs 空切片（JSON 序列化行为不同！）
var s1 []int         // nil 切片 (ptr=nil)     → JSON: null
s2 := []int{}        // 空切片 (ptr=zerobase)  → JSON: []
s3 := make([]int, 0) // 空切片 (ptr=zerobase)  → JSON: []

// 2. 大切片截取小片段导致 10MB 底层数组无法被 GC 回收！
func readHeader(huge10MB []byte) []byte {
    // ❌ 错误：直接 return huge10MB[:16] 会钉死整块 10MB 数组
    // ✅ 正确：拷贝出独立的 16 字节新切片，释放大数组
    return bytes.Clone(huge10MB[:16])
}
🔍 深入源码：为什么 append([]int{1, 2}, 3, 4, 5) 的最终 cap 是 6 而不是 5？（预估公式 + 内存对齐取整）

面试中常遇到这类“算出来的容量和实际打印的 cap(s) 不一样”的追问。因为 runtime/slice.go 的扩容分两步走——先算期望容量，再向 Go 内存分配器（详见 05.3 节）申请规整大小的内存块：

🔥 runtime/slice.go · nextslicecap 预估 + roundupsize 对齐取整 
s := []int{1, 2}       // oldLen=2, oldCap=2
s = append(s, 3, 4, 5) // 期望 newLen=5

// 【第①步：预估容量 nextslicecap (Go 1.18+)】
// 1. 若 newLen > 2*oldCap (5 > 4)：直接令 newcap = newLen = 5
// 2. 若 oldCap < 256：newcap = 2 * oldCap（翻倍）
// 3. 若 oldCap >= 256：循环 newcap += (newcap + 3*256) >> 2（即 1.25*newcap + 192 平滑过渡）

// 【第②步：内存规格向上对齐 roundupsize (★决定最终 cap)】
// Go 内存分配器不做任意字节分配，而是按固定规格档位（8B, 16B, 24B, 32B, 48B, 64B...）切块：
// 所需字节 = newcap * 8B = 5 * 8 = 40 Bytes → 向上对齐到最近的 48 Bytes 档位
// 最终真实容量 cap = 48B / 8B = 6！
🗂️ 02.2 · map 的桶里为什么把 8 个 Key 和 8 个 Value 分开存？Go 1.24 又改了什么？

🧭 02.2 map 哈希表：hmap + bmap、翻倍/等量渐进扩容与 Go 1.24 Swiss Table

Go 的 map 底层是指向 runtime.hmap 的指针。在 Go 1.0~1.23 中采用拉链法变体（每个桶 bmap 装 8 对 KV + 溢出桶链表）；而在 Go 1.24+ 中正式升级为基于开放寻址与位运算加速的 Swiss Table（runtime/maps）：

📖 图解三步寻址（手机端速读）：① 计算 Key 的 64 位哈希，用低 B 位定位到 buckets 数组中的第几个桶 bmap；② 用高 8 位（tophash）在桶头 tophash[8] 数组里快速比对指纹，指纹匹配才去比对真正的 Key；③ 桶内 8 个 Key 紧挨着排完再排 8 个 Value（而非 k0,v0,k1,v1 交错），这样 map[int64]int8 无需每对都补 7 字节对齐空洞，单桶立省 56 字节！
核心机制 / 陷阱 底层根因与面试标准回答
① 翻倍扩容 vs 等量扩容 • 翻倍扩容（B → B+1）：当负载因子 count / 2^B > 6.5 时触发，旧桶按第 B+1 位 bit 分流到 X/Y 两个新桶。
• 等量扩容（sameSizeGrow，B 不变）：负载因子未超 6.5，但溢出桶过多（noverflow >= 2^min(B,15)，因大量增删导致空洞碎片），原地紧凑重排斩断长溢出链。
② 渐进式驱逐搬迁 绝不一次性搬完所有桶：每次执行写或删操作时顺带搬迁 1~2 个旧桶，分摊延迟毛刺；扩容期间读操作先查新桶，未搬完则去 oldbuckets 查。
③ Go 1.24+ Swiss Table Go 1.24 将底层更换为 Swiss Table（开放寻址 + 每组 8 槽配备 64-bit 控制字，用位运算单指令并行比对 8 个哈希指纹），消除溢出桶指针；在微基准测试中最高提速 20%~60%，真实生产大型应用整体 CPU 平均节省约 1%~1.5%。
④ 四大必背陷阱 1. 向 nil map 读返回零值，写直接 panic；2. 不可取地址 &m[k]（扩容后地址会变，且不能直接写 m[k].Field = x）；3. 遍历起点每次随机化；4. 并发读写触发 fatal("concurrent map writes")，无法被 recover() 捕获！
⏱️ 02.3 · defer 为什么能改命名返回值？recover() 为什么跨协程就会失效？

🪃 02.3 defer / panic / recover：三大执行铁律与异常捕获边界

🎯 defer_rules.go · LIFO 栈序、参数即时求值与改返回值 
// 铁律①：多个 defer 按【后进先出 LIFO】执行
// 铁律②：函数参数在【注册 defer 当场】求值；闭包则捕获变量引用
func demoParam() {
    x := 10
    defer fmt.Println("A(当场求值):", x)            // 固定打 10
    defer func() { fmt.Println("B(闭包引用):", x) }() // 打 20
    x = 20
}

// 铁律③：return a 拆解为三步：
//   Step 1: 给返回值变量赋值 (res = 1)
//   Step 2: 执行 defer（若为【命名返回值】，defer 可直接篡改它！）
//   Step 3: 汇编 RET 指令返回
func calc() (res int) {
    defer func() { res += 100 }()
    return 1 // 最终返回 101！
}
🚨 recover() 两条保命边界：
① 必须在 defer func() { recover() }() 匿名函数内直接调用（嵌套再包一层普通函数调用无效）；
② 不能跨协程捕获——每个新建的 go func() 必须自带独立的 defer-recover 保护罩，否则子协程 panic 会直接带崩整个进程！
⚡ 性能定心丸：早年版本常告诫“热路径别用 defer”，但自 Go 1.14+ 引入编译器内联展开后，常规 defer 开销已从 ~35ns 降至 ~1ns（等同普通函数调用），解锁与关资源请放心使用 defer！
🔍 深入底层：defer 三代性能演进与 Go 1.14 开放编码（Open-coded Defer）原理
  • Go 1.12 前（堆分配 ~35ns）：每次执行 defer 都要调 deferproc 在堆上分配 _defer 结构体挂入协程链表，函数返回时调 deferreturn 逐个出栈执行，触发堆分配与 GC 压力。
  • Go 1.13（栈分配 ~25ns）：非循环内的显式 defer 改为编译器在当前函数栈帧上分配 _defer，消除了堆分配。
  • Go 1.14+（开放编码 Open-coded Defer ~1.5ns）：当函数内 defer 数量 <= 8 且不在循环语句内时，编译器不再生成 _defer 结构体，而是直接在栈上用 1 字节位掩码（deferBits，每位代表一个 defer 是否已激活）记录状态，并在每个 return 语句前直接内联展开延迟函数调用！
🧩 02.4 · 为什么函数返回了值为 nil 的错误指针，外层 if err != nil 却恒为真？

🎭 02.4 interface 双结构（eface vs iface）、nil 接口大坑与 %w 错误链

🚨 nil_interface_trap.go · eface/iface 与 nil 判等大坑 
// 1. 空接口 any       → eface { _type *_type, data unsafe.Pointer } (16B)
// 2. 带方法接口 error → iface { tab   *itab,  data unsafe.Pointer } (16B)
// ★ 判等铁律：只有当【类型指针 _type/tab】和【数据指针 data】双双为 nil 时，接口才 == nil！

type MyError struct{ Msg string }
func (e *MyError) Error() string { return e.Msg }

func badCall() error {
    var p *MyError = nil
    return p   // ❌ 大坑！返回 iface{ tab: *MyError, data: nil } != nil！
}
func goodCall() error {
    return nil // ✅ 正确：无错误时永远显式 return nil (tab=nil, data=nil)
}
🔗 error_wrapping.go · %w 错误包装链与 errors.Is / As 
var ErrNotFound = errors.New("record not found")

func QueryOrder(id int) error {
    // 用 %w 包装底层错误（自动实现 Unwrap() 链；若不想暴露底层改用 %v）
    return fmt.Errorf("query order %d: %w", id, ErrNotFound)
}

// 消费端判断：
err := QueryOrder(99)
// ① errors.Is：递归沿 Unwrap() 链比对是否等于目标【哨兵错误值】
if errors.Is(err, ErrNotFound) { ... }

// ② errors.As：递归沿 Unwrap() 链提取匹配的【自定义错误结构体指针】
var netErr *net.OpError
if errors.As(err, &netErr) { ... }
