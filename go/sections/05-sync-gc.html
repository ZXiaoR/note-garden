🔒 05.1 · sync.Mutex 为什么既要支持自旋插队，又要在等待超 1ms 时切到饥饿模式？

⚙️ 05.1 sync.Mutex：32 位 state 位图、正常/饥饿双模式与自旋 4 大苛刻条件

sync.Mutex 仅占 8 字节（state int32 + sema uint32）。它并非简单的操作系统内核锁，而是结合了用户态 CAS 自旋 + 信号量睡眠队列 + 1ms 饥饿保护的自适应混合锁：

📐 sync/mutex.go · 32 位 state 字段的 4 个位域 
// 高 29 位 (Bits 3..31)        | Bit 2    | Bit 1  | Bit 0
// [ WaiterCount 阻塞等待协程数 ] | Starving | Woken  | Locked
//         state >> 3          |  (4:饥饿) | (2:唤醒)| (1:已锁)

// ★ 自旋（Spinning）必须同时满足的 4 大苛刻条件：
// 1. 处于【正常模式】且是多核 CPU (ncpu > 1)
// 2. 当前自旋次数 < 4 (每轮执行 30 次 CPU PAUSE 指令)
// 3. GOMAXPROCS > 1 且至少有另一个正在运行的 P
// 4. 当前 P 的本地队列 runq 为空（没别的活急着干）
锁模式 核心行为与切换阈值（Go 1.9+）
正常模式
（高吞吐优先）		 新调 Lock() 的协程正好在 CPU 上，可先自旋 CAS 插队抢锁，省去睡眠唤醒开销；但排队的老协程可能被反复插队饿死。
饥饿模式
（等待 > 1ms）		 一旦队头老协程等待超 1ms，立即切为饥饿模式：Unlock 将锁直接手递手移交队头，新来者禁止自旋直接排入队尾！当队头是最后一个等待者或等待 < 1ms 时切回正常模式。
🚨 Mutex 三大夺命坑：① 不可重入（同一 G 连续两次 mu.Lock() 当场死锁）；② 严禁值拷贝（含 Mutex 的结构体传参必须传指针 *T，否则连带锁状态一起复制，可用 go vet 检查）；③ RWMutex 写锁防饿死（有写锁等待时会阻塞后续所有新来的 RLock 读请求）。
🧰 05.2 · 为什么 sync.Once 不能只用一句 CAS(0, 1) 实现？sync.Map 为什么读不用加锁？

⚡ 05.2 atomic / WaitGroup / sync.Once / sync.Map 底层原理精要

并发原语 适用场景 源码实现亮点与面试必问细节
sync/atomic 计数器、状态标志位、无锁配置热替换 由 CPU 硬件级指令（LOCK CMPXCHG）保证，纳秒级开销；Go 1.19+ 提供泛型类型安全封装 atomic.Int64 / atomic.Pointer[T]。
sync.WaitGroup 等待一组并发子任务全部完成 高 32 位存剩余任务数 counter、低 32 位存等待者数 waiter。铁律：wg.Add(n) 必须在 go func() 之前调用，防止主协程先执行 Wait() 提前放行。
sync.Once 单例初始化、配置懒加载（全局仅跑 1 次） 为什么不能只写 if CAS(&done, 0, 1) { f() }？因为若协程 A 抢赢 CAS 还在慢速执行 f()，协程 B 看到已是 1 就会直接拿到未初始化完的半成品！因此源码采用 atomic.Load == 0 快路径 + Mutex 慢路径阻塞等待 + defer atomic.Store(&done, 1)。
sync.Map 读多写少，或各协程操作不相交的 Key 内部维护read（只读原子字典，命中则完全无锁） + dirty（加锁全量字典）。每次读穿透 read 计一次 misses++，当 misses >= len(dirty) 时直接将 dirty 原子提升（Promote）为新的 read！频繁写场景仍推荐分片锁或 map + RWMutex。

🔬 05.5 GC 四阶段、GOGC + GOMEMLIMIT 黄金组合与编译期逃逸分析

① GC 周期两处极短 STW 与 GOMEMLIMIT 救星
  • 两处亚毫秒 STW：仅在开始的 Mark Setup（开启写屏障，~10-50μs） 和结束的 Mark Termination（关闭写屏障，~50-200μs） 停顿；中间并发标记若分配过快会触发 Mark Assist（谁分配快谁帮忙标记）。
  • GOGC=100 + GOMEMLIMIT（Go 1.19+）：默认堆比上次存活堆翻倍（+100%）触发 GC；在容器中配 GOMEMLIMIT=6.8GiB（容器上限的 80%~85%），逼近软上限时自动提前 GC，彻底告别翻倍 OOM！
🔍 escape_analysis.go · 编译期逃逸分析五大常见场景 
// 诊断命令：go build -gcflags="-m -l" .
func escapeCases() *User {
    u1 := User{ID: 1}        // ✅ 不逃逸：纯局部使用，留栈上零 GC 压力
    u2 := &User{ID: 2}       // ❌ 逃逸①：返回局部变量指针
    fmt.Println(u1)          // ❌ 逃逸②：传给 any(interface{}) 触发反射
    s := make([]int, 100000) // ❌ 逃逸③：对象过大超出栈帧容量(>64KB)
    n := getDynamicLen()
    s2 := make([]int, n)     // ❌ 逃逸④：切片长度在编译期未知
    _, _ = s, s2
    return u2
}
