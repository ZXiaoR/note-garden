🔄 04.1 · 当已有接收协程阻塞在 <-ch 时，发送者写的数据还会进环形缓冲区 buf 吗？

🧬 04.1 runtime.hchan 底层结构与 sendDirect 跨协程栈直接拷贝优化

Rob Pike 名言：“不要通过共享内存来通信，而要通过通信来共享内存。” 调用 make(chan int, 4) 会在堆上分配一个 hchan 结构体并返回指针。它内部由环形缓冲区 buf、阻塞协程等待队列 sendq / recvq（节点类型为 sudog，即把休眠协程 G 与其收发变量栈地址打包成的等待节点）以及一把互斥锁 lock 组成：

📖 图解左中区：hchan 三大件与 sudog
  • 环形缓冲区 buf：用定长数组配合写游标 sendx、读游标 recvx 构成环形队列（到尾自动取模回绕）。
  • 等待节点 sudog：当协程因 Channel 空/满而阻塞时，Runtime 会把该协程指针 g 和它要读写的变量地址 elem 包装成一个 sudog 结构体，挂入读等待链表 recvq 或写等待链表 sendq。
  • 内置互斥锁 lock：Channel 并非无锁结构，每次收发都会先加 hchan.lock 保护内部字段。
📖 图解右半区：发送 ch <- x 的三条分支与跨栈直拷
  • 分支① recvq 已有等待者（sendDirect 跨栈直拷）：弹出等待的 sudog，完全绕过 buf，直接将发送者栈上的 x 拷进接收者栈上的接收变量 sg.elem（因为接收者正处于 _Gwaiting 休眠态，栈不会扩容移动，跨栈直写安全且省去一次进出缓冲区的拷贝），随后调 goready() 唤醒接收者。
  • 分支② buf 还有空位：把数据拷进 buf[sendx]，游标后移，立即返回。
  • 分支③ buf 已满（或无缓冲）：将当前协程打包成 sudog 挂入 sendq，调 gopark() 休眠让出 M。
📊 04.2 · 向 nil channel 和已关闭 channel 进行读写关分别会发生什么？

🚦 04.2 Channel 三种状态的收/发/关完整真值表与优雅关闭黄金法则

操作类型 ① nil Channel（未 make） ② 正常开启的 Channel ③ 已关闭的 Channel（close(ch) 后）
发送 ch <- v 永久阻塞（gopark 永不唤醒） 成功写入/交接，或满时阻塞 💥 立即 panic: send on closed channel
接收 v, ok := <-ch 永久阻塞（常用于 select 中动态置 ch = nil 屏蔽某分支！） 成功读取（ok=true），或空时阻塞 ✅ 永不阻塞：先读完缓冲剩余元素（ok=true），缓冲排空后立即返回类型零值且 ok=false
关闭 close(ch) 💥 立即 panic: close of nil channel 成功置 closed=1，唤醒所有等待者 💥 立即 panic: close of closed channel
🚨 Channel 关闭铁律：永远由发送方（Sender）关闭 channel，绝不由接收方关！若有多个发送者协程，由 sync.WaitGroup 等所有发送者全部退出后由协调协程统一关闭，或额外引入信号通道 stopCh 配合 sync.Once 广播停写。
🎲 04.3 · 如果两个协程同时用 select 监听同一对 ch1, ch2，为什么不会发生交叉加锁死锁？

🎛️ 04.3 select 底层实现：pollorder 随机洗牌防饥饿与 lockorder 地址排序防死锁

🐹 select_worker.go · 标准超时与优雅取消模板 
func worker(ctx context.Context, jobCh <-chan Job) error {
    // ★ 用 NewTicker 代替循环内 time.After，防止旧版本 Timer 内存泄漏
    ticker := time.NewTicker(5 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case job, ok := <-jobCh:
            if !ok { return nil } // 通道已关闭且排空，优雅退出
            handle(job)
        case <-ticker.C:
            reportHeartbeat()
        case <-ctx.Done():        // 上游超时或取消（close 广播）
            return ctx.Err()
        }
    }
}
🔍 源码级揭秘：runtime.selectgo 四步执行流
  1. pollorder（随机洗牌防饿死）：用 fastrandn 随机打乱所有 case 的检查顺序，防止排在前面的高频 case 把后面的 case 饿死。
  2. lockorder（地址排序防死锁 ★必考）：将所有 case 涉及的 hchan 按内存虚拟地址从小到大进行堆排序，严格按此顺序依次加锁（解锁时逆序），彻底消除多协程交叉加锁的 AB-BA 死锁！
  3. 第一轮非阻塞扫描：按 pollorder 检查是否有就绪分支，有则立即解锁执行；若全未就绪且有 default，走 default。
  4. 挂起与唤醒摘除：将当前 G 挂入所有 case 的等待队列并 gopark()；任一分支唤醒后，再次按 lockorder 加锁并将自己从其余未触发队列中摘除。
