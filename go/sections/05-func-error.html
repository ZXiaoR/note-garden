05.1 · 函数用法：(结果, error) 多返回值、可变参数 ...T 与闭包

05.1 函数特性：多返回值、可变参数与闭包

与 JavaScript 一样，Go 的函数也是一等公民（可赋给变量、传参或作为返回值，这就是后面 HTTP 中间件的基础）。日常最常用的是多返回值、可变参数 ...T（对应 JS 的剩余参数 ...args）和闭包：

func_multi_varargs.go · 多返回值与可变参数展开 [Go 1.22+] 
package main

import "fmt"

// 1. 多返回值：惯例把业务结果放前面，error 放在最后一个返回值
func Divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, fmt.Errorf("除数不能为 0")
    }
    return a / b, nil
}

// 2. 可变参数 (...int)：函数内部将其视为 []int 切片
func SumAll(nums ...int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}

func main() {
    res, err := Divide(10, 4)
    arr := []int{1, 2, 3}
    // 把已有切片展开传给可变参数时，在切片名后加 ...（JS 写在前面 ...arr，Go 写在后面 arr...）
    fmt.Println(res, err, SumAll(arr...)) // 2.5 <nil> 6
}
func_closure.go · 闭包持有外部局部变量状态 [Go 1.22+] 
package main

import "fmt"

// 闭包（Closure）：返回的匿名函数捕获了外部变量 count，生命周期随之延续
func NewCounter() func() int {
    count := 0
    return func() int {
        count++
        return count
    }
}

func main() {
    next := NewCounter()
    fmt.Println(next(), next(), next()) // 1 2 3
}
05.2 · 延迟调用 defer：后进先出（LIFO）栈顺序、return 三步拆解与求值时机

05.2 延迟调用（defer）：成对释放资源

在 JS 里释放资源要靠 try { ... } finally { close() }，文件一多缩进很深；Go 提供了 defer 关键字——拿到文件、HTTP 响应体或互斥锁后下一行立刻注册 defer xxx.Close()，无论函数后续从哪一个分支提前 return 甚至发生 panic，都会在退出函数前自动执行清理。掌握它的三个要点即可：① 多个 defer 按 LIFO（Last In, First Out，后进先出）栈顺序倒序执行；② 在返回值赋值之后、函数真正退出之前执行；③ 普通参数在注册那一行当场求值：

defer_lifo_file.go · 先判错再注册 defer，避免循环内堆积 [Go 1.22+] 
package main

import (
    "io"
    "os"
)

func CopyFile(srcPath, dstPath string) error {
    src, err := os.Open(srcPath)
    if err != nil {
        return err // ★ 必须先判断 err == nil 再写 defer，否则 src 为 nil 会空指针 panic
    }
    defer src.Close() // ① 压栈底（最后关）

    dst, err := os.Create(dstPath)
    if err != nil {
        return err // 提前返回时，已注册的 src.Close() 依然会自动执行
    }
    defer dst.Close() // ② 压栈顶（最先关）

    _, err = io.Copy(dst, src)
    return err
}

func main() {}
defer_return_eval.go · 直接传参当场求值 vs 闭包延迟读取 [Go 1.22+] 
package main

import "fmt"

func main() {
    x := 1
    defer fmt.Println("直接传参 x =", x)             // 注册时当场求值，存下 x=1
    defer func() { fmt.Println("闭包读取 x =", x) }() // 函数退出时才读，读到最新 x=2
    x = 2
    // 输出顺序（LIFO）：先打 "闭包读取 x = 2"，后打 "直接传参 x = 1"
}
05.3 · 生产级错误处理：业务错误定义、%w 分层包装与统一映射 HTTP 状态码

05.3 业务错误怎么定义、分层传递并转成 HTTP 状态码

Go 的内置接口只有一个方法：type error interface { Error() string }。在真实后端项目（repo → service → handler 三层结构）中，如果每层都只写 return err 会丢掉出错位置，如果每层都既打日志又往上返回又会导致同一个报错在日志里刷屏三次。行业标准做法遵循「底层转换领域错误 → 中间层用 `%w` 补充上下文往上抛 → 最外层 Handler 统一打印并映射 HTTP 状态码」：

layered_error_http.go · 从数据层包装到 HTTP 状态码映射的完整闭环 [Go 1.22+] 
package main

import (
    "encoding/json"
    "errors"
    "fmt"
    "log"
    "net/http"
    "net/http/httptest"
)

// ==================== 1. 定义层：可判等的哨兵错误 + 带业务码的结构化错误 ====================
var (
    ErrNotFound          = errors.New("resource not found")
    ErrInsufficientStock = errors.New("insufficient stock")
)

type BizError struct {
    Status  int    // 对应 HTTP 状态码 (400 / 409 / ...)
    Code    string // 前端可读的稳定业务错误码，如 "STOCK_NOT_ENOUGH"
    Message string // 可直接展示给用户的安全提示文案
    Cause   error  // 底层原始错误（仅供服务端日志排查，不返回给前端）
}

func (e *BizError) Error() string { return fmt.Sprintf("%s: %v", e.Code, e.Cause) }
func (e *BizError) Unwrap() error { return e.Cause } // 实现 Unwrap 后支持 errors.Is / As 穿透

// ==================== 2. 数据层与业务层：用 fmt.Errorf("...: %w", err) 逐层附加上下文 ====================
func repoFindStock(skuID int64) (int, error) {
    if skuID == 404 {
        return 0, fmt.Errorf("repo.FindStock(sku=%d): %w", skuID, ErrNotFound)
    }
    return 0, nil // 模拟查到当前剩余库存为 0
}

func svcCreateOrder(skuID int64, count int) error {
    stock, err := repoFindStock(skuID)
    if err != nil {
        return fmt.Errorf("svc.CreateOrder: %w", err) // 不打日志，补充上下文继续上抛
    }
    if stock < count {
        return &BizError{
            Status:  http.StatusConflict, // 409
            Code:    "STOCK_NOT_ENOUGH",
            Message: "手慢了，该商品库存不足",
            Cause:   ErrInsufficientStock,
        }
    }
    return nil
}

// ==================== 3. 出口层（Handler）：集中打印日志并转成 HTTP 状态码 ====================
func writeHTTPError(w http.ResponseWriter, err error) {
    w.Header().Set("Content-Type", "application/json; charset=utf-8")

    // 优先用 errors.As 提取结构化业务错误 BizError
    var bizErr *BizError
    if errors.As(err, &bizErr) {
        w.WriteHeader(bizErr.Status)
        _ = json.NewEncoder(w).Encode(map[string]string{"code": bizErr.Code, "msg": bizErr.Message})
        return
    }
    // 其次用 errors.Is 穿透多层 %w 判断领域哨兵错误
    if errors.Is(err, ErrNotFound) {
        w.WriteHeader(http.StatusNotFound) // 404
        _ = json.NewEncoder(w).Encode(map[string]string{"code": "NOT_FOUND", "msg": "请求的资源不存在"})
        return
    }
    // 兜底未知系统错误：服务端日志记录完整内部链路，对前端统一脱敏返回 500
    log.Printf("[ERROR] internal failure: %v", err)
    w.WriteHeader(http.StatusInternalServerError)
    _ = json.NewEncoder(w).Encode(map[string]string{"code": "INTERNAL_ERROR", "msg": "服务繁忙，请稍后重试"})
}

func main() {
    rec := httptest.NewRecorder()
    writeHTTPError(rec, svcCreateOrder(1001, 2))
    fmt.Println(rec.Code, rec.Body.String())
    // 输出: 409 {"code":"STOCK_NOT_ENOUGH","msg":"手慢了，该商品库存不足"}
}
05.4 · 崩溃与恢复边界：panic / recover 何时用、何时禁用与跨协程盲区

05.4 panic 与 recover 何时用

panic 会立刻中断当前函数执行流、沿调用栈逆序运行已注册的 defer，若直到协程顶部都没人调用 recover() 拦截，整个 Go 服务进程就会直接崩溃退出。因此工程上有清晰的使用边界：

两条使用边界与两条语法约束
  • 绝不拿 panic 当普通业务 throw 用：参数校验不过、数据库查无此人、第三方超时都是预期内分支，一律返回 error。
  • 仅有的两处合法用法：① 启动阶段强依赖自检失败（如 main() 初始化时连不上核心配置或写错静态正则 regexp.MustCompile，主动失败拒绝带病启动）；② 顶层入口兜底恢复（在 HTTP 全局中间件和独立后台子协程入口写 defer + recover()，防止某行意外的切片越界或空指针把整台机器上的其他正常请求一起拖死）。
  • 两条硬约束：① recover() 必须写在 defer 直接调用的函数体内才生效；② recover() 只能救当前这一个协程——在子协程 go fn() 里炸出的 panic，父协程的 recover() 完全拦不住。
safe_goroutine.go · 安全启动后台协程的封装模板 [Go 1.22+] 
package main

import (
    "fmt"
    "log"
    "runtime/debug"
    "time"
)

// 凡是业务中手动开启的后台协程，推荐统一套一层带 recover 兜底的 SafeGo：
func SafeGo(fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("[PANIC RECOVERED] err=%v\n%s", r, debug.Stack())
            }
        }()
        fn()
    }()
}

func main() {
    SafeGo(func() {
        var s []int
        fmt.Println(s[0]) // 模拟意外越界 panic，被 SafeGo 拦下打印堆栈，主进程不崩
    })
    time.Sleep(50 * time.Millisecond)
    fmt.Println("主服务依然健康运行")
}

本章即时场景题（先想答案，再点击展开）

1. 同事写了 func check() error { var err *BizError = nil; if ok { return err }; ... }，结果正常分支返回后外层 if err != nil 居然判定为有错，为什么？

这是 Go 最经典的接口判空误区：error 是一个接口（内部包含「动态类型指针 + 数据指针」两格）。把 (*BizError)(nil) 返回给 error 接口时，虽然数据指针是 nil，但类型指针那格被填上了 *BizError，导致整个接口不等于 nil（图解见 原理篇 02.4）。规范写法：没有错误时永远直接写字面量 return nil，切勿返回带具体类型的空指针变量。

2. 一个定时任务需要遍历打开 5000 个日志文件处理，直接在 for 循环里写 f, err := os.Open(p); defer f.Close() 会出什么线上问题？

defer 是在整个函数退出时才执行，而不是在单轮 for 循环结束时执行。5000 个文件句柄会一直攒在内存里不释放，直接触发操作系统进程句柄上限报错 too many open files。解法：把单次循环体抽成一个小函数 processOneFile(path)，在那个小函数里用 defer f.Close()，每处理完 1 个文件返回时立刻关闭句柄。

3. 数据库报了 Error 1062: Duplicate entry '1380000' for key 'uk_phone'，为什么不能在 Handler 里直接 http.Error(w, err.Error(), 500) 原样吐给前端？

一是安全风险：原样输出底层错误会把数据库类型、表名、索引名甚至内部 IP 暴露给外部攻击者；二是语义不对：手机号已注册属于客户端业务冲突而非服务端崩溃。正确做法是在 repo 层识别唯一索引冲突转为 ErrDuplicatePhone，在 Handler 层映射为 409 Conflict 并返回友好提示 "该手机号已注册"。
