03 为什么引入协程 & GMP 调度器底层全景 M:N SCHEDULER × SIGURG PREEMPTION
❓ 03.1 · 既然操作系统已经有内核线程了，为什么 Go 还要自己造一套 Goroutine？

🚀 03.1 OS 内核线程三大痛点 vs Goroutine 2KB 动态连续栈

在互联网高并发服务中，95% 的时间都花在等待网络 IO（查 DB、调 RPC、读 Redis）上。如果采用传统的“一请求一 OS 线程（1:1 模型）”，会在栈与内核资源上限、内核态上下文切换、阻塞线程挂起三大瓶颈上迅速撞墙：

核心维度 OS 内核线程（Thread · 1:1） Go 协程（Goroutine · M:N） 数量级差距与工程意义
初始栈与资源上限 默认保留 1 MB ~ 8 MB 虚拟地址空间（含 Guard Page，触碰缺页分配物理页后不可缩容）+ 独立内核栈（8~16KB） 仅 2 KB 起步，按需 2 倍动态扩容（最大 1GB）、GC 时自动缩容回收 数万并发下线程会撞上 threads-max、max_map_count 与脏栈页内存上限；Goroutine 200MB 即可轻松开出 10 万+ 并发
创建与切换成本 陷入内核态（Ring 3 → Ring 0），保存 16+ 通用/SIMD 寄存器并跑内核调度器，耗时 1 ~ 2 μs 纯用户态切换（借由每个线程内置的调度专用栈 g0），仅保存 PC/SP/BP 三个核心寄存器，耗时 ~100 ~ 200 ns 上下文切换快 10 倍以上，CPU 算力真正花在业务代码上
IO 阻塞代价 调阻塞 read 时整条 OS 线程被挂起，加剧线程数膨胀与调度抖动 底层集成 netpoller（epoll/kqueue）：协程挂起让出，底层线程立刻切换跑下一个协程 用同步顺序代码的直观心智，跑出异步非阻塞事件驱动的极致吞吐
💡 进阶考点：为什么 Go 1.4 把协程栈从“分段栈”改成了“连续栈”？
• Go 1.3 分段栈痛点——热分裂（Hot Split）：用链表拼接多个小栈块；若在一个 for 循环内恰好处于栈满临界点调函数，每次迭代都会触发“分配新栈块 → 返回立即释放”，性能雪崩！
• Go 1.4+ 连续栈：栈满时直接分配一块 2 倍大的连续新内存，把旧栈完整拷贝过去并修正栈内指针偏移量，后续循环调用零分裂开销！
⚙️ 03.2 · 早期 Go 1.0 只有 G 和 M，为什么要大动干戈引入中间层 P？

🗺️ 03.2 GMP 四大核心组件、为什么需要 P 与调度流转全景图

Go 调度器由三个核心字母组成：G（Goroutine，待执行的协程任务与 2KB 栈）、M（Machine，真正上 CPU 干活的 OS 内核线程）、P（Processor，持有本地运行队列与内存缓存的逻辑处理器，数量默认等于 CPU 核数 GOMAXPROCS）。
在早期 Go 1.0 的 G-M 模型中，所有线程 M 争抢唯一一把全局队列锁，且每个 M 都挂着一份本地内存缓存池（mcache，详见 05.3 节）——一旦系统调用阻塞产生大量 M，闲置缓存池随 M 数量膨胀，白白吃掉大量内存。Go 1.1 引入中间层 P，规定 M 必须绑定 P 才能执行 G，一举把无锁本地队列和 mcache 全部收敛到固定数量的 P 上！

📖 图解左半区：P0 本地高速调度流
  • VIP 插队槽 runnext：新建的 go func() 或刚被 Channel 唤醒的 G 优先放进单槽位 runnext，利用热缓存立刻执行。
  • 本地无锁队列 runq[256]：老 G 被挤进长度 256 的环形数组；若连 256 都塞满了，就摘出一半（128 个）连同新 G 拼成链表迁入全局队列（sched.runq）。
  • g0 调度栈：每个线程 M 都有一个 8KB 的 g0 专用栈，专门用于执行调度、栈扩容和分配内存；切换协程时走 G_cur → g0 → G_next。
📖 图解右半区：偷活干（Work Stealing）与解绑（Handoff）
  • 工作窃取（Work Stealing）：当 P1 的本地队列和全局队列都空了，它会随机挑另一个 P（如 P0），直接从对方 runq 尾部一次性偷走一半的 G，让多核 CPU 满载运转。
  • 系统调用移交（Syscall Handoff）：当 M1 因文件 IO 或 CGO 陷入内核阻塞时，P1 立即与 M1 解绑，换一个空闲线程 M2 绑定继续跑队列里的其他 G；等 M1 从内核醒来后优先抢空闲 P，抢不到就把 G 塞进全局队列自己睡觉。
🔍 03.3 · 线程 M 按什么优先级顺序找活干？Channel 阻塞和系统调用阻塞有什么本质区别？

🧭 03.3 寻找可执行 G 的五步优先级与三大阻塞场景对比

🎯 线程 M 寻找下一个可执行 G 的五步顺序
  1. 定期看一眼全局队列（防饿死）：每调度一定次数先去全局队列拿 1 个 G，防止本地两个协程互相唤醒把全局队列里的 G 饿死。
  2. 查 P 本地队列（最快热路径）：先拿 VIP 槽 P.runnext，若为空再从本地无锁环形队列 P.runq 队头取。
  3. 全局队列批量搬迁：本地彻底空了，加锁从全局队列 sched.runq 搬一批到本地。
  4. 检查网络轮询器 netpoller：非阻塞询问 epoll/kqueue 是否有刚就绪的网络读写协程。
  5. Work Stealing 工作窃取：随机遍历其他 P，从对方队列尾部偷走一半 G；全偷不到才将 M 休眠。
阻塞类型 底层动作与 M / P 状态
① 用户态同步阻塞
(Channel / Mutex / Sleep)		 调用运行时挂起函数 gopark()（将 G 状态改为 _Gwaiting 并解绑让出）；M 和 P 完全不阻塞，百纳秒内切去跑下一个 G。
② 网络 IO 阻塞
(TCP / HTTP / DB 读写)		 FD 交由 netpoller (epoll) 监听，G 调 gopark() 挂在等待描述符上；M 和 P 完全不阻塞。
③ 阻塞式系统调用
(磁盘文件 IO / CGO)		 M 与 G 一起陷入内核阻塞；P 执行 Handoff 与 M 解绑，换新 M 继续跑队列里其他 G。
🔍 深入源码：runtime.schedule() 真实实现与为什么偏偏选质数“61”查全局队列？

如果只按“先查本地队列、本地空了才查全局队列”运行，一旦当前 P 上有两个协程通过 Channel 乒乓互相唤醒，P.runnext 永远非空，全局队列里的 G 就会被永久饿死。为什么选 61？因为它既不太小（太小会频繁抢全局锁拖慢吞吐），也不太大（太大全局 G 等待太久），且61 是质数，不会与业务代码里常见的 2 的幂次（16、32、64）循环步长产生哈希共振：

🐹 runtime/proc.go · schedule() 核心找 G 代码 
func schedule() {
    var gp *g
    // ★ 1. 每调度 61 次（schedtick%61 == 0），优先去全局队列拿 1 个 G
    if _g_.m.p.ptr().schedtick%61 == 0 && sched.runqsize > 0 {
        lock(&sched.lock)
        gp = globrunqget(_g_.m.p.ptr(), 1)
        unlock(&sched.lock)
    }
    // ★ 2. 查 P 本地队列（先取 VIP 槽 runnext，再取 runq 环形队头）
    if gp == nil {
        gp, _ = runqget(_g_.m.p.ptr())
    }
    // ★ 3. findrunnable() 兜底：全局队列批量拿 → netpoller → Work Stealing 偷一半
    if gp == nil {
        gp, _ = findrunnable()
    }
    execute(gp)
}
⚡ 03.4 · 如果一个协程写了个纯算术死循环 for { i++ }，Go 怎么把它从 CPU 上轰下来？

🛡️ 03.4 抢占式调度演进（Go 1.14 SIGURG 信号异步抢占）与 sysmon 后台巡警

① Go 1.13 前：基于栈扩张点的【协作式抢占】

编译器在每个非内联函数开头插入栈空间检查指令（morestack）。当后台线程 sysmon 发现某个 G 运行超 10ms，将其栈边界设为 stackPreempt，等它下次调用函数时触发栈检查让出。
致命死穴：若是一个内部没有任何函数调用的纯算术死循环 for {}，永远走不到检查点，会永久霸占 P 甚至导致 GC STW 挂死全进程！

② Go 1.14+：基于 SIGURG 信号的【异步抢占】

sysmon 发现 G 运行超过 10ms（或 GC 请求 STW）时，直接调用 OS 接口向该线程 M 发送一个 SIGURG 信号。OS 内核强制中断 M 进入 Go 的信号处理函数 sighandler，将寄存器 PC 修改为跳转到 runtime.asyncPreempt，保存上下文后调用 gopreempt_m 把死循环 G 强行塞回全局队列！

🚓 幕后巡警 sysmon 后台监控线程的四大职责：sysmon 直接运行在独立 M 上（无需绑定 P）：① 抢占运行超 10ms 的 G；② 剥离陷入 Syscall 阻塞的 P（Retake）；③ 超过 10ms 无人轮询网络时兜底 poll netpoller；④ 超过 2 分钟未 GC 则强制触发一轮 GC，并调 madvise 归还闲置物理内存。
🎯 面试追问：GOMAXPROCS 在 Docker / K8s 容器里有什么著名大坑？

GOMAXPROCS 默认读取宿主机物理节点的逻辑 CPU 核数（如 64 核），在 Go 1.25 之前不感知容器的 cgroup CPU Quota（如 K8s 限制 Pod 只能用 2 核）！这会导致 2 核容器创建 64 个 P，引发严重的 CFS 周期限流（Throttling）与上下文切换，接口延迟暴增数倍。Go 1.24 及更早版本的生产容器务必引入 go.uber.org/automaxprocs 自动对齐容器配额（注：Go 1.25+ 已原生支持容器 cgroup CPU 配额感知与动态调整）。
