06.1 · 并发起步：用 go 启动轻量级协程，配合 sync.WaitGroup 等待全部完成

06.1 启动协程（go）与等待完成（sync.WaitGroup）

在 Go 中发起并发任务只需在函数调用前加 go 关键字。需要注意：一旦主函数 main() 返回，整个进程会立即退出而不会自动等后台协程跑完。最基础的等待工具是标准库的 sync.WaitGroup（类似无返回值的 Promise.all）：

  • wg.Add(1)：必须在启动 go 之前在外部调用（若写进子协程内部，可能子协程还没来得及跑 Add，主协程的 Wait() 就已经看计数为 0 直接退出了）；
  • defer wg.Done()：写在子协程第一行，退出时自动把计数减 1；传递 wg 给独立函数时必须传指针 *sync.WaitGroup。
goroutine_waitgroup.go · 并发执行任务并等待全部完成 [Go 1.22+] 
package main

import (
    "fmt"
    "sync"
)

func fetchItem(id int, wg *sync.WaitGroup) {
    defer wg.Done()
    fmt.Printf("任务 #%d 完成\n", id)
}

func main() {
    var wg sync.WaitGroup
    for i := 1; i <= 3; i++ {
        wg.Add(1)              // 1. 先在协程外 +1（Go 1.22+ 循环变量 i 每轮独立，闭包直接捕获也安全）
        go fetchItem(i, &wg) // 2. 传 &wg 指针共享同一个计数器
    }
    wg.Wait()                  // 3. 阻塞直到计数器归零
    fmt.Println("全部并发任务结束")
}
06.2 · 协程间通信：无缓冲/有缓冲 channel、发送方关闭原则与 select 多路监听

06.2 通道（channel）与 select 多路监听

Go 推崇 CSP（Communicating Sequential Processes，通信顺序进程）理念——“通过通信来共享数据”。chan T 就是连接多个协程的并发安全管道：

  • 无缓冲通道 make(chan T)：容量为 0，发送方 ch <- v 会阻塞直到接收方 <-ch 来取，用于严格握手同步；
  • 有缓冲通道 make(chan T, cap)：内部自带容量为 cap 的队列，没满时发送方放完立刻返回，适合任务排队削峰；
  • 关闭规则：永远由发送方调用 close(ch) 表示“不再发新数据了”（向已关闭的通道继续发送会直接触发 panic）。
channel_basic.go · 发送、close 通知结束与 for range 读取 [Go 1.22+] 
package main

import "fmt"

func main() {
    jobs := make(chan string, 3)

    go func() {
        jobs <- "订单A"
        jobs <- "订单B"
        close(jobs) // 发送完毕后由生产者关闭通道
    }()

    // for range 会持续读取，直到通道被 close 且缓冲读空后自动退出循环
    for item := range jobs {
        fmt.Println("消费:", item)
    }
}
select_mux.go · 用 select 同时监听结果与 Context 取消（类似 Promise.race）[Go 1.22+] 
package main

import (
    "context"
    "fmt"
    "time"
)

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()

    resCh := make(chan string, 1) // 容量设 1：即便主协程超时先走，子协程写入也不会阻塞泄漏
    go func() {
        time.Sleep(500 * time.Millisecond)
        resCh <- "慢查询结果"
    }()

    select {
    case data := <-resCh:
        fmt.Println("拿到结果:", data)
    case <-ctx.Done():
        fmt.Println("超时退出:", ctx.Err()) // context deadline exceeded
    }
}
06.3 · 共享状态保护与取消信号：Mutex / RWMutex 选型与 context.Context 规范

06.3 互斥锁（Mutex / RWMutex）与上下文（Context）

通道适合做“任务流转与事件通知”，而保护内存缓存、连接池状态或计数器这类驻留共享数据时，直接加锁更清晰高效。写多或读写均衡用完全独占的 sync.Mutex；95% 以上是读、偶尔更新用支持多协程并发读的 sync.RWMutex。而 context.Context 则作为所有 I/O 函数的第 1 个参数（ctx context.Context），负责沿着整条调用链向下游传递超时截止时间、取消信号与请求链路 ID：

rwmutex_cache.go · 用读写锁安全封装并发本地字典缓存 [Go 1.22+] 
package main

import (
    "fmt"
    "sync"
)

type SafeCache struct {
    rw   sync.RWMutex      // 锁含内部状态，严禁值传递复制，方法接收者必须用指针 *SafeCache
    data map[string]string
}

func NewSafeCache() *SafeCache {
    return &SafeCache{data: make(map[string]string)}
}

func (c *SafeCache) Get(k string) (string, bool) {
    c.rw.RLock()         // 读锁：千百个协程可同时读取，互不阻塞
    defer c.rw.RUnlock()
    v, ok := c.data[k]
    return v, ok
}

func (c *SafeCache) Set(k, v string) {
    c.rw.Lock()          // 写锁：独占写入，自动阻塞新来的读写协程
    defer c.rw.Unlock()
    c.data[k] = v
}

func main() {
    c := NewSafeCache()
    c.Set("env", "prod")
    v, ok := c.Get("env")
    fmt.Println(v, ok)
}
context_without_cancel.go · 请求级超时与后台异步剥离取消 [Go 1.22+] 
package main

import (
    "context"
    "fmt"
    "time"
)

type traceKey struct{} // WithValue 的 Key 用私有空结构体，防跨包字符串同名冲突

func main() {
    base := context.WithValue(context.Background(), traceKey{}, "req-9527")

    // 1. 为下游调用设 800ms 超时，且无论成功失败都必须 defer cancel() 释放底层定时器
    reqCtx, cancel := context.WithTimeout(base, 800*time.Millisecond)
    defer cancel()

    // 2. 若要在接口返回后异步写审计日志：不能直接传 reqCtx（接口一返回 reqCtx 就会被取消）
    // Go 1.21+ 用 context.WithoutCancel 既保留 TraceID，又剥离父级取消信号：
    bgCtx := context.WithoutCancel(reqCtx)
    cancel() // 模拟主请求已结束取消

    fmt.Println("reqCtx已取消:", reqCtx.Err() != nil, "bgCtx仍存活且带ID:", bgCtx.Value(traceKey{}))
}
06.4 · 三大生产并发模式：Worker Pool 限流池、errgroup 并发收集错误与带超时扇出扇入

06.4 常用并发模式：Worker Pool、errgroup 与扇出扇入

真实业务里绝不能收到 10000 条数据就无脑 for 循环起 10000 个协程（虽然 Go 撑得住，但下游 MySQL 连接池或第三方接口会被瞬间打挂）。日常开发 90% 的并发编排都落在这三种固定模式里：

worker_pool_fanout.go · 模式 1 & 3：带超时的 Worker Pool 扇出扇入 [Go 1.22+] 
package main

import (
    "context"
    "fmt"
    "sync"
    "time"
)

// 把 20 个任务交给固定 4 个 Worker 并发执行，整体限制 1 秒超时（标准库零依赖）
func RunWorkerPool(ctx context.Context, tasks []int, workers int) []int {
    jobs := make(chan int)
    results := make(chan int, len(tasks))

    // 1. 扇出（Fan-out）：启动固定数量 Worker 抢任务
    var wg sync.WaitGroup
    for range workers {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for n := range jobs {
                select {
                case <-ctx.Done():
                    return // 超时立刻停工退出，防协程泄漏
                case results <- n * 10:
                }
            }
        }()
    }

    // 2. 投递任务（同样监听 ctx.Done 防止超时后死等塞入 jobs）
    go func() {
        defer close(jobs)
        for _, t := range tasks {
            select {
            case <-ctx.Done():
                return
            case jobs <- t:
            }
        }
    }()

    // 3. 扇入（Fan-in）：等所有 Worker 结束后关闭 results，收集结果
    go func() {
        wg.Wait()
        close(results)
    }()

    out := make([]int, 0, len(tasks))
    for r := range results {
        out = append(out, r)
    }
    return out
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel()
    res := RunWorkerPool(ctx, []int{1, 2, 3, 4, 5}, 2)
    fmt.Println("汇总条数:", len(res)) // 5
}
errgroup_demo.go · 模式 2：errgroup 限制并发并收集首个错误 [Go 1.22+] 
// 安装官方扩展包: go get golang.org/x/sync/errgroup
package main

import (
    "context"
    "fmt"

    "golang.org/x/sync/errgroup"
)

// 业务最常用：并发调多个微服务组装详情页，任一报错立刻取消其余请求（类似 Promise.all）
func FetchAll(parentCtx context.Context, ids []int) ([]string, error) {
    // 注意起名为 egCtx，不要覆盖入参 parentCtx！
    g, egCtx := errgroup.WithContext(parentCtx)
    g.SetLimit(10) // ★ 限制最多同时运行 10 个协程

    results := make([]string, len(ids)) // 预分配固定长度，各协程按独立下标写入无需加锁！
    for i, id := range ids {
        g.Go(func() error {
            if egCtx.Err() != nil {
                return egCtx.Err()
            }
            results[i] = fmt.Sprintf("item_%d", id)
            return nil // 若返回非 nil error，errgroup 会自动 cancel(egCtx)
        })
    }

    // Wait 阻塞等全部结束，返回第一个出现的非 nil 错误
    if err := g.Wait(); err != nil {
        return nil, err
    }
    // ⚠️ 坑点提醒：g.Wait() 返回后 egCtx 也会自动变成已取消状态！
    // 后续如果还要查数据库，必须继续传外层的 parentCtx，绝不能传 egCtx！
    return results, nil
}

func main() {
    res, err := FetchAll(context.Background(), []int{101, 102, 103})
    fmt.Println(res, err)
}
06.5 · 两大并发故障：Goroutine 泄漏（没人读的通道 / 漏调 cancel）与数据竞争（-race）

06.5 常见误区：Goroutine 泄漏与数据竞争排查

垃圾回收器（GC）只会回收没人引用的内存对象，绝不会自动杀掉卡在半路阻塞的协程。只要一个协程卡死不退出，它占用的栈内存（至少 2KB）和手里引用的大对象就会一直留在进程里直到内存耗尽（OOM，Out Of Memory，内存溢出）：

1. Goroutine 泄漏的三个最高发现场
  • 向没人读的无缓冲通道发送：主函数里写了 ch := make(chan int)（容量 0），起子协程算完写 ch <- res，但主函数因超时提前 return 走了，子协程永远卡在发送那行。解法：单结果通道一律写成 make(chan int, 1)，或发送处加 select { case ch <- res: case <-ctx.Done(): }。
  • 从永远没人写/没人关的通道读取：生产者遇到错误提前退出却忘了 defer close(jobs)，导致下游所有 Worker 永远卡死在 for range jobs。
  • 忘了调 defer cancel() 或 HTTP 请求不设超时：context.WithTimeout / WithCancel 创建后漏掉 defer cancel()，或调用下游接口没绑超时导致协程永久挂死在网络读上。
race_atomic.go · 2. 数据竞争复现、atomic 原子修复与 -race 检测 [Go 1.22+] 
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

// ❌ 若直接对普通 int 执行并发 count++（读-改-写非原子指令），结果必小于 1000！
//    本地测试执行: go run -race main.go 或 go test -race ./...
//    运行时会直接抓出 WARNING: DATA RACE 并打印读写双方的精确行号！

func main() {
    // ✅ 纯数值计数器：用 Go 1.19+ 泛型原子类型 atomic.Int64（比加 Mutex 锁更轻量）
    var counter atomic.Int64
    var wg sync.WaitGroup

    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter.Add(1)
        }()
    }
    wg.Wait()
    fmt.Println("精确计数:", counter.Load()) // 稳定输出: 1000
}

本章即时场景题（先想答案，再点击展开）

1. 在老项目（go.mod 版本为 Go 1.20）里看到 for _, u := range users { go func() { send(u) }() }，为什么发出去的全是列表里最后一个用户？

在 Go 1.21 及更早版本中，for range 的循环变量 u 在整个循环期间复用同一个内存地址，当异步协程真正被调度执行时，循环早已跑完，所有闭包读到的都是最后一轮的值。Go 1.22 起语言规范已正式改为每轮迭代创建新变量；若维护旧版项目，需把变量作为参数传进匿名函数 go func(user User) { send(user) }(u)。

2. 用 errgroup 并发查完用户信息和优惠券列表后，紧接着用 g, ctx := errgroup.WithContext(r.Context()) 拿到的那个 ctx 去写一条日志进 MySQL，为什么必报错？

因为 errgroup.WithContext 派生出的子 ctx 不仅在出错时取消，在 g.Wait() 全部正常完成后也会立刻自动调用 cancel() 释放内部资源。因此 g.Wait() 之后的任何后续数据库或 Redis 操作，都必须继续使用外层入参 r.Context()，切忌用 ctx 同名遮蔽掉父级上下文。

3. go test -race 这么好用，能不能编译线上正式二进制时也加上 go build -race 一直开着？

不建议在全量高压生产节点常驻开启。竞态检测器基于 ThreadSanitizer 插桩，开启后会使进程内存占用膨胀 5 ~ 10 倍、CPU 执行变慢 2 ~ 20 倍。标准工程实践是在本地单测、CI 流水线（go test -race ./...）以及预发环境或单台灰度实例上开启，把数据竞争拦在上线前。
