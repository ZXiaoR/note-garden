03.1 · 序列容器：定长数组 [N]T 与动态切片 []T 的创建、追加、截取与排序

03.1 定长数组 [N]T 与动态切片 []T 的日常用法

按顺序存放一组同类型元素时，Go 区分了定长数组 [N]T（长度写死在类型里，如 [4]byte，不能追加元素）和动态切片 []T（方括号内不写数字，类似 JS 的 Array，可随时用 append 动态增长，占日常开发的 99%）：

slice_create_append.go · 切片的 3 种创建方式与 append [Go 1.22+] 
package main

import "fmt"

func main() {
    // 方式一：零值声明 (nil 切片, s1 == nil)，不能按下标写 s1[0]=1，但可直接 append
    var s1 []int
    s1 = append(s1, 10, 20) // ★ 注意：append 返回新切片值，必须重新赋回给 s1

    // 方式二：字面量初始化（已知初始元素，或需要非 nil 的空切片 []int{}）
    nums := []int{10, 20}
    nums = append(nums, 30)

    // 方式三：make([]T, 长度 len, 容量 cap) —— 已知大致条数时推荐预留容量
    // 长度设 0、预留容量 100，配合 append 追加可省去中途多次扩容拷贝
    list := make([]string, 0, 100)
    list = append(list, "first")

    fmt.Println(s1, nums, len(list), cap(list)) // [10 20] [10 20 30] 1 100
}
slice_sub_sort.go · 区间截取、独立克隆与 slices 标准库 [Go 1.22+] 
package main

import (
    "fmt"
    "slices"
)

func main() {
    s := []int{30, 10, 40, 20}

    // 1. 区间截取 s[low:high]：左闭右开（含下标 1、2，不含 3，类似 JS slice(1, 3)）
    sub := s[1:3] // [10 40]，len = 3 - 1 = 2，cap = 4 - 1 = 3

    // 2. 独立拷贝（Go 1.21+ 标准库 slices.Clone，生成互不干扰的新底层数组）
    cloned := slices.Clone(sub)

    // 3. 排序与包含判断
    slices.Sort(s)                  // 原地升序: [10 20 30 40]
    found := slices.Contains(s, 20) // true
    fmt.Println(cloned, s, found)
}
03.2 · 键值字典：map[K]V 的初始化、增删改查、comma-ok 判断与遍历

03.2 键值字典 map[K]V 的日常用法

map[KeyType]ValueType 是内置哈希表，查找、写入、删除的平均时间复杂度均为 O(1)。与 JS 对象读取不存在属性返回 undefined 不同，Go 读取不存在的 Key 会返回 Value 类型的零值（例如 0 或 ""），因此需要借助第二个布尔返回值 ok 来区分“真的存了 0”还是“键不存在”：

map_crud.go · 字典初始化、存在性判断与删除 [Go 1.22+] 
package main

import "fmt"

func main() {
    // 1. 写入前必须用 make 或字面量 {} 初始化（只写 var m map[string]int 是 nil，写入会崩）
    scores := make(map[string]int, 16)
    scores["alice"] = 95
    scores["bob"] = 0

    // 2. 用 val, ok := m[k] 区分“存了零值 0”与“Key 不存在”
    if val, ok := scores["bob"]; ok {
        fmt.Println("bob 已交卷，得分:", val) // bob 已交卷，得分: 0
    }

    // 3. 删除键值对（Key 不存在时 delete 静默无操作，不报错）
    delete(scores, "alice")
    fmt.Println("剩余人数:", len(scores)) // 1
}
map_range_set.go · 随机遍历、有序输出与去重集合 [Go 1.22+] 
package main

import (
    "fmt"
    "slices"
)

func main() {
    m := map[string]int{"b": 2, "a": 1, "c": 3}

    // 1. Go 故意在每次 range map 时随机化起始位置，防止业务依赖哈希桶顺序
    // 若需固定顺序输出，先提取 Key 切片排序再遍历：
    keys := make([]string, 0, len(m))
    for k := range m {
        keys = append(keys, k)
    }
    slices.Sort(keys)
    for _, k := range keys {
        fmt.Printf("%s:%d ", k, m[k]) // 稳定输出: a:1 b:2 c:3
    }

    // 2. Go 标准库没有单独的 Set 类型，日常直接用 map[string]bool 去重
    seen := map[string]bool{"u_101": true}
    fmt.Println("\n是否已访问:", seen["u_101"])
}
03.3 · 两大高频线上坑：子切片共享底层数组「改一个变两个」与 map 并发写崩溃

03.3 常见误区：切片共享底层数组与 map 并发写崩溃

在 JavaScript 里，arr.slice(0, 2) 会浅拷贝出一个全新的数组，往新数组 push 绝不会污染原数组；但在 Go 里，切片在内存中拆成「{底层数组地址 ptr, 长度 len, 容量 cap} 描述头」和「底层连续数组」两部分，截取操作 s[a:b] 为了极致性能默认不拷贝数据，而是和原切片共用同一块底层数组——这是 JS 开发者转 Go 最容易踩中的隐蔽 Bug：

slice_share_trap.go · 坑 1：子切片修改与 append 污染原切片 [Go 1.22+] 
package main

import (
    "fmt"
    "slices"
)

func main() {
    all := []int{10, 20, 30, 40}

    // ❌ 隐患写法：直接截取前 2 个元素，此时 sub 的 len=2，但剩余容量 cap=4！
    sub := all[0:2]
    sub[0] = 99            // 现象 A：直接改了共享底层数组，all[0] 跟着变成 99
    sub = append(sub, 888) // 现象 B：因 len(2) < cap(4) 没触发扩容，888 直接覆盖了 all[2]！
    fmt.Println("被污染的 all:", all) // 输出: [99 20 888 40]（原 30 被悄悄篡改）

    // ✅ 安全解法一（最推荐）：需要独立修改时，显式调用 slices.Clone 拷贝新数组
    safeCopy := slices.Clone(all[0:2])
    safeCopy[0] = 777

    // ✅ 安全解法二：三下标切片 all[low:high:max] 把 cap 锁死为 2，迫使 append 分配新数组
    cappedSub := all[0:2:2]
    cappedSub = append(cappedSub, 666) // cap 已满，自动搬去新数组，绝不覆盖 all[2]
    fmt.Println("保持不变的 all:", all, safeCopy, cappedSub)
}
坑 2：内置 map 不是并发安全的，并发写会直接终止整个进程

Node.js 是单线程事件循环，多个异步请求读写同一个全局 Map 不会把进程搞崩；但在 Go 中，每个 HTTP 请求都跑在各自独立的并发协程里：

  • 直接后果：只要有两个并发任务同时对同一个普通 map 执行「一读一写」或「同时写」，Go 运行时内部的状态位检测会立刻抛出 fatal error: concurrent map read and map write 或 concurrent map writes。
  • 注意它不是普通报错：fatal error 属于运行时主动熔断，后续第 05 章讲的 recover() 也无法捕获它，整个后端服务会当场退出重启。
  • 工程规范：① 若全局 map 在进程启动时一次性填好、运行期100% 只读不写，任意多并发读完全安全；② 只要运行期存在修改，必须配合第 06 章的互斥锁 sync.Mutex / 读写锁 sync.RWMutex 保护。

背后的原理：切片的 24 字节表头在函数传参和扩容时到底怎么计算新容量？map 为什么并发写会破坏哈希桶指针？详见 《 核心原理篇 · 02.1 slice 24B 表头与两步扩容规则》 与 《 核心原理篇 · 02.2 map 哈希桶布局与渐进式扩容》。

本章即时场景题（先想答案，再点击展开）

1. 读取一个 50MB 的大日志文件字节切片 rawBytes，从中切出开头 20 个字节 header := rawBytes[:20] 长期保存在全局缓存里，rawBytes 还能被垃圾回收释放吗？

不能被释放，会造成隐蔽的内存驻留浪费。因为 header := rawBytes[:20] 的底层指针仍然指在那块 50MB 的连续底层数组上，只要 header 还活着，整块 50MB 底层数组就一直被引用而无法回收。遇到“从大切片截一小段长期持有”的场景，务必写成 header := slices.Clone(rawBytes[:20])，让小切片搬去独立的 20 字节新数组，原 50MB 大数组即可被顺利回收。

2. 写了一个函数 func addTag(tags []string) { tags = append(tags, "hot") }，在外面传入 myTags := []string{"new"} 调用完后，为什么打印 myTags 还是只有 ["new"]？

因为 Go 传参复制的是那份 {ptr, len, cap} 描述头：函数内的 append 把形参描述头的 len 改成了 2（甚至触发扩容换了新的 ptr），但外部 myTags 手里的原描述头 len 依然是 1（内存图解见 原理篇 01.1）。修改切片长度的函数，标准写法是把新切片作为返回值返回：func addTag(tags []string) []string { return append(tags, "hot") }，调用处写 myTags = addTag(myTags)。

3. 线上服务在低峰期一切正常，一到晚高峰就偶发整机重启，容器日志最后一行是 fatal error: concurrent map writes，怎么定位和修复？

原因：某个包级全局变量（或单例对象内部）持有一个未加锁的普通 map，晚高峰两个并发 HTTP 请求恰好在同一纳秒写了这个 map。
定位与修复：看崩溃日志紧跟的协程调用栈即可直接定位到具体行号，并在本地跑 go test -race ./... 排查同类隐患；修复时用 sync.RWMutex 把读写包起来（见 06.3）。
