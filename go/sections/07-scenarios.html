07.1 连 MySQL：连接池、参数化查询、事务与 sqlx / GORM 取舍

① 需求：安全连接 MySQL 执行条件查询，并在扣减库存生成订单时保证原子事务提交或回滚（SQL 索引、隔离级别与防超卖锁机制详见 《 MySQL · 基础与实战篇》）。
② 方案：Go 标准库 database/sql 自带协程安全的连接池管理，配合官方推荐驱动 github.com/go-sql-driver/mysql（通过 _ 匿名导入触发驱动 init() 注册）。连接串 DSN（Data Source Name，数据源连接串）必加 parseTime=true&loc=Asia%2FShanghai&charset=utf8mb4，并显式配置连接池上限与生命周期：

mysql_tx_demo.go · ③ 代码：连接池调优、参数化查询与防漏回滚事务模板 [Go 1.22+] 
// go get github.com/go-sql-driver/mysql
package main

import (
    "context"
    "database/sql"
    "errors"
    "fmt"
    "time"

    _ "github.com/go-sql-driver/mysql" // 匿名导入：仅执行驱动包 init() 注册 "mysql" 驱动
)

func InitMySQL(dsn string) (*sql.DB, error) {
    // dsn 示例: "app:Pass@tcp(127.0.0.1:3306)/shop?charset=utf8mb4&parseTime=true&loc=Asia%2FShanghai"
    db, err := sql.Open("mysql", dsn) // 注意：sql.Open 只校验格式，并未真正建立网络连接！
    if err != nil {
        return nil, err
    }
    // 连接池四大核心参数（全局复用同一个 *sql.DB 单例，切勿每次请求重新 Open）
    db.SetMaxOpenConns(50)                 // 最大并发打开连接数（默认 0 不限制，高并发会把 MySQL 连爆）
    db.SetMaxIdleConns(25)                 // 最大空闲保活连接数（默认仅 2，设太小会导致频繁建连断连）
    db.SetConnMaxLifetime(5 * time.Minute) // 单连接最大存活时长（须小于 MySQL wait_timeout，防半开死连接）
    db.SetConnMaxIdleTime(2 * time.Minute) // 空闲连接多久未使用则回收

    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()
    return db, db.PingContext(ctx) // PingContext 真正拨号验证账号网络连通性
}

// 1. 参数化单行查询：一律用 ? 占位符防 SQL 注入，注意识别 sql.ErrNoRows
func GetUserBalance(ctx context.Context, db *sql.DB, uid int64) (int64, error) {
    var cents int64
    err := db.QueryRowContext(ctx, "SELECT balance_cents FROM users WHERE id = ?", uid).Scan(&cents)
    if errors.Is(err, sql.ErrNoRows) {
        return 0, fmt.Errorf("用户 %d 不存在", uid)
    }
    return cents, err
}

// 2. 标准事务模板：开启事务后下一行立刻 defer tx.Rollback()（若后面成功 Commit 了，Rollback 会安全空转）
func CreateOrderTx(ctx context.Context, db *sql.DB, skuID int64, qty int) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // ★ 任何中间分支 return err 或 panic，都会自动归还连接并回滚事务！

    res, err := tx.ExecContext(ctx,
        "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?", qty, skuID, qty)
    if err != nil {
        return err
    }
    if affected, _ := res.RowsAffected(); affected == 0 {
        return errors.New("库存不足")
    }
    if _, err := tx.ExecContext(ctx,
        "INSERT INTO orders(sku_id, qty) VALUES(?, ?)", skuID, qty); err != nil {
        return err
    }
    return tx.Commit()
}

func main() {}
数据访问方案 核心特点 实际项目怎么选
标准库 database/sql 零第三方依赖、性能最高，但多列查询需按顺序手写 rows.Scan(&a, &b, ...)，字段多时较繁琐。 查询极少的小服务、CLI 工具或中间件组件。
jmoiron/sqlx
（或代码生成 sqlc）		 直接复用 database/sql，支持手写原生 SQL（Structured Query Language，结构化查询语言）并自动按标签 db:"user_name" 映射到结构体切片 db.Select(&list, sql)。 对 SQL 可控性与性能要求高的核心交易、复杂报表与高并发微服务（强烈推荐）。
GORM
（ORM，Object-Relational Mapping，对象关系映射）		 类似 JS 的 Prisma / TypeORM，链式调用免写常规 CRUD SQL，自带钩子与自动迁移，但重度反射略有开销，复杂联表调试不如原生 SQL 直观。 表数量多、以常规增删改查为主的后台管理系统与快速迭代业务服务（复杂查询仍可用 db.Raw() 写原生 SQL）。

④ 常见坑：使用 db.QueryContext 查多行时，一旦 err == nil 必须立刻 defer rows.Close()，否则该条数据库连接会一直被占住不归还连接池，几十次请求就把 MaxOpenConns 耗光卡死全站；循环读完后还要检查 rows.Err()。数据库允许为 NULL 的列不能直接 Scan 到普通 string（会报错），应改用 sql.NullString 或指针 *string。
⑤ 背后原理：匿名导入 _ "driver" 的包初始化执行顺序见 《 核心原理篇 · 01.3 init() 自底向上初始化》；InnoDB 事务锁与连接池原理见 《MySQL · 核心原理篇》。

07.2 连 Redis：go-redis 实战读写与避坑

① 需求 & ② 方案：使用官方维护的 github.com/redis/go-redis/v9 读写热点缓存与防重锁（缓存双写一致性、穿透/击穿/雪崩与九大业务场景详见 《 Redis · 基础与实战篇》）。进程启动时创建全局复用的 *redis.Client，显式设短读写超时（如 300ms）：

redis_cache_demo.go · ③ 代码：连接池配置、TTL 写入、redis.Nil 判空与 SetNX 防重 [Go 1.22+] 
// go get github.com/redis/go-redis/v9
package main

import (
    "context"
    "errors"
    "fmt"
    "time"

    "github.com/redis/go-redis/v9"
)

func NewRedisClient(addr, pass string) *redis.Client {
    return redis.NewClient(&redis.Options{
        Addr:         addr,
        Password:     pass,
        PoolSize:     50,                     // 连接池最大连接数
        DialTimeout:  1 * time.Second,        // 建连超时
        ReadTimeout:  300 * time.Millisecond, // ★ 缓存层务必设短超时，防 Redis 抖动拖死主站
        WriteTimeout: 300 * time.Millisecond,
    })
}

func DemoCacheAndIdempotent(ctx context.Context, rdb *redis.Client) error {
    // 1. 写入缓存并必设 TTL（Time To Live，过期时间），杜绝无过期僵尸大 Key
    if err := rdb.Set(ctx, "user:42:name", "Alice", 10*time.Minute).Err(); err != nil {
        return err
    }

    // 2. 读取缓存：务必用 errors.Is(err, redis.Nil) 区分“缓存未命中(正常回源)”与“网络故障”
    val, err := rdb.Get(ctx, "user:42:name").Result()
    if errors.Is(err, redis.Nil) {
        fmt.Println("缓存未命中，回源查 MySQL...")
    } else if err != nil {
        return fmt.Errorf("redis 网络异常: %w", err)
    } else {
        fmt.Println("命中缓存:", val)
    }

    // 3. 接口防连点幂等：SET key 1 NX EX 300（仅当键不存在时写入成功返回 true）
    firstClick, err := rdb.SetNX(ctx, "idem:order:tok_99", "1", 5*time.Minute).Result()
    fmt.Println("首次有效提交:", firstClick, err)
    return nil
}

func main() {}

④ 常见坑：把 redis.Nil 当作系统错误直接给前端抛 500 是新手最高发失误；另外热点 Key 过期瞬间可用 singleflight.Group 合并进程内同 Key 并发回源请求。
⑤ 背后原理：singleflight 请求归并与缓存双写竞态时序分别见 《 核心原理篇 · 06.3 singleflight 原理》 与 《Redis · 原理篇 03》。

07.3 · HTTP 洋葱中间件：panic 恢复、访问日志、请求超时与 JWT 鉴权注入

07.3 中间件：日志、鉴权（JWT）、panic 恢复与请求超时

① 需求 & ② 方案：像 Express / Koa 一样，在不污染业务 Handler 的前提下统一完成异常兜底、耗时统计、超时保护与登录态校验。在 Go 标准库中，中间件就是一个签名为 func(next http.Handler) http.Handler 的包装函数。推荐固定外内包裹顺序为：Recovery（最外层防崩） → AccessLog（记录真实状态码与耗时） → Timeout（控制整体预算） → AuthJWT（验签注入用户 ID） → 业务 Handler：

middleware_chain.go · ③ 代码：四大生产核心中间件可直接运行的完整实现 [Go 1.22+] 
// go get github.com/golang-jwt/jwt/v5
package main

import (
    "context"
    "fmt"
    "log"
    "net/http"
    "runtime/debug"
    "strings"
    "time"

    "github.com/golang-jwt/jwt/v5"
)

type uidCtxKey struct{} // 私有 Context Key，存放鉴权通过后的 userID

// 包装 ResponseWriter 以捕获下游写入的真实 HTTP 状态码供日志打印
type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}
// 实现 Unwrap() 让 Go 1.20+ 的 http.ResponseController 能穿透包装拿到原生的 Flusher！
func (r *statusRecorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }

// 1. Panic 恢复中间件（放最外层）
func RecoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Printf("[PANIC] %s %s: %v\n%s", r.Method, r.URL.Path, err, debug.Stack())
                http.Error(w, `{"code":"INTERNAL_ERROR"}`, http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 2. 访问日志中间件
func LoggerMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
        next.ServeHTTP(rec, r)
        log.Printf("%s %s -> %d (%v)", r.Method, r.URL.Path, rec.status, time.Since(start))
    })
}

// 3. 请求上下文超时中间件（下游 DB / Redis / HTTPClient 均会自动感知 r.Context() 到期）
func TimeoutMiddleware(d time.Duration) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ctx, cancel := context.WithTimeout(r.Context(), d)
            defer cancel()
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

// 4. JWT（JSON Web Token，JSON 网络令牌）鉴权中间件（校验 HMAC，Hash-based Message Authentication Code，基于哈希的消息认证码）
func JWTAuthMiddleware(secret []byte) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            raw := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
            tok, err := jwt.Parse(raw, func(t *jwt.Token) (any, error) {
                // ★ 必检签名算法是否为预期的 HMAC，防止攻击者篡改 alg:"none" 绕过验签！
                if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
                    return nil, fmt.Errorf("unexpected alg: %v", t.Header["alg"])
                }
                return secret, nil
            })
            if err != nil || !tok.Valid {
                http.Error(w, `{"code":"UNAUTHORIZED"}`, http.StatusUnauthorized)
                return
            }
            sub, _ := tok.Claims.GetSubject()
            ctx := context.WithValue(r.Context(), uidCtxKey{}, sub)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

func main() {}

④ 常见坑：① 解析 JWT 时如果不校验 t.Method.(*jwt.SigningMethodHMAC)，容易产生算法替换安全漏洞；② 自定义 statusRecorder 包装 ResponseWriter 时记得加上 Unwrap() http.ResponseWriter 方法，否则内层的 SSE 流式接口会找不到 Flusher；③ SSE 流式长连接路由不要挂在短 TimeoutMiddleware(3s) 下，否则推流 3 秒就会被掐断。
⑤ 背后原理：WithValue 单向链表查找与级联取消树原理见 《 核心原理篇 · 06.1 Context 四类结构体》。

07.4 · 外部接口调用：禁用默认 http.Get、长连接池配置、安全退避重试与 Body 排空

07.4 调用第三方接口：带超时的 http.Client 与重试

① 需求 & ② 方案：后端调微信支付、大模型 API 或内部微服务（跨服务稳定性防线详见 《 服务端稳定性七件套》）。生产环境第一准则：永远不要直接调包级函数 http.Get / http.Post！因为它们底层使用的 http.DefaultClient 的 Timeout 默认值是 0（永不超时），一旦外部接口挂起不回包，你的服务协程会在几十秒内全部卡死耗尽内存。应全局创建一个调优好 Timeout 与 Transport 连接池的 *http.Client 单例复用：

http_client_retry.go · ③ 代码：生产级 http.Client 单例 + 带抖动退避重试 [Go 1.22+] 
package main

import (
    "context"
    "fmt"
    "io"
    "net"
    "net/http"
    "time"
)

// 全局复用一个 Client（内部自带 TCP 连接池，并发安全，切勿每次请求 new 一个 Client！）
var apiClient = &http.Client{
    Timeout: 5 * time.Second, // ★ 兜底总超时（含建连 + TLS握手 + 发请求 + 读完响应体）
    Transport: &http.Transport{
        DialContext:         (&net.Dialer{Timeout: 1 * time.Second}).DialContext,
        MaxIdleConns:        200,
        MaxIdleConnsPerHost: 50, // ★ 默认仅 2！高频调同一域名必调大，否则大量连接用完即毁触发 TIME_WAIT
        IdleConnTimeout:     90 * time.Second,
    },
}

// 带 Context 感知与退避的幂等 GET 调用（注意：非幂等扣款接口若无幂等键严禁自动重试！）
func FetchWithRetry(ctx context.Context, url string, maxAttempts int) ([]byte, error) {
    var lastErr error
    for attempt := 0; attempt < maxAttempts; attempt++ {
        if attempt > 0 {
            // 指数退避等待：100ms, 200ms... 期间若父 ctx 已取消则立刻放弃重试
            timer := time.NewTimer(time.Duration(1<<(attempt-1)) * 100 * time.Millisecond)
            select {
            case <-ctx.Done():
                timer.Stop()
                return nil, ctx.Err()
            case <-timer.C:
            }
        }

        req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
        if err != nil {
            return nil, err
        }
        resp, err := apiClient.Do(req)
        if err != nil {
            lastErr = err
            continue // 网络层错误，进入下一轮重试
        }

        // LimitReader 限制最多读 4MB，防止恶意或异常超大报文打爆进程内存
        body, readErr := io.ReadAll(io.LimitReader(resp.Body, 4<<20))
        _ = resp.Body.Close() // ★ 循环内不用 defer，读完当场关闭归还底层 TCP 连接！

        if resp.StatusCode >= 500 {
            lastErr = fmt.Errorf("upstream 5xx: %d", resp.StatusCode)
            continue // 服务端 5xx 可重试；4xx 客户端参数错不重试直接返回
        }
        if resp.StatusCode >= 400 {
            return nil, fmt.Errorf("upstream 4xx: %d: %s", resp.StatusCode, body)
        }
        return body, readErr
    }
    return nil, fmt.Errorf("重试 %d 次仍失败: %w", maxAttempts, lastErr)
}

func main() {}

④ 常见坑：① 标准库 MaxIdleConnsPerHost 默认只有 2，调同一个内网服务并发高时若不调大，95% 的连接用完就被直接关掉无法复用；② 只要 apiClient.Do 返回 err == nil，哪怕你不关心响应内容，也必须读完并 Close() 掉 resp.Body，否则连接既不能复用还会泄漏读协程；③ 带请求体 POST 重试时，io.Reader 第一轮读完就空了，需传入 bytes.NewReader(rawBytes) 每次重建。
⑤ 背后原理：网络套接字如何在阻塞等待回包时不占用系统线程？见 《 核心原理篇 · 03.3 netpoller (epoll) 协程挂起机制》。

07.5 · 流式推送实战：SSE（Server-Sent Events）实时刷出与客户端断连 Context 即停

07.5 SSE 流式输出：边生成边推与断连停止

① 需求 & ② 方案：AI 大模型打字机输出、长耗时任务实时进度推送（协议细节与断线重连详见 《 SSE · 幂等 · 上下文压缩》）。HTTP 默认会把小块写入攒在服务端 4KB 缓冲区里，因此实现 SSE（Server-Sent Events，服务端推送事件）必须做对三件事：① 设置 text/event-stream 与禁用代理缓冲响应头；② 每写完一帧（以双换行 \n\n 结尾）立刻调用 Flush() 把数据推上网卡；③ 监听 <-r.Context().Done()，用户关掉浏览器标签页瞬间立即终止生成任务：

sse_stream.go · ③ 代码：可直接用 curl -N http://localhost:8080/stream 体验的流式服务 [Go 1.22+] 
package main

import (
    "fmt"
    "log"
    "net/http"
    "time"
)

func streamHandler(w http.ResponseWriter, r *http.Request) {
    // 1. 设置 SSE 三大必配响应头（X-Accel-Buffering: no 告诉前置 Nginx 不要攒批缓冲）
    w.Header().Set("Content-Type", "text/event-stream; charset=utf-8")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("X-Accel-Buffering", "no")

    // 2. Go 1.20+ 推荐用 ResponseController 获取刷盘控制（可自动穿透多层中间件包装）
    rc := http.NewResponseController(w)
    // 若全局 http.Server 设了短 WriteTimeout，可为当前 SSE 长连接单独延长写截止时间：
    _ = rc.SetWriteDeadline(time.Now().Add(5 * time.Minute))

    chunks := []string{"你好，", "正在通过 ", "Go SSE ", "边生成边推送。"}
    ticker := time.NewTicker(300 * time.Millisecond)
    defer ticker.Stop()

    for i, token := range chunks {
        select {
        case <-r.Context().Done():
            // 3. 客户端关闭网页或主动 AbortController.abort() 时，TCP 断开会自动触发 Done()
            log.Println("客户端已断开，立即停止下游推理以节省算力")
            return
        case <-ticker.C:
            // SSE 标准帧格式：id / event / data，帧尾必须以两个换行符 \n\n 结束
            _, _ = fmt.Fprintf(w, "id: %d\ndata: {\"text\":%q}\n\n", i+1, token)
            if err := rc.Flush(); err != nil {
                return
            }
        }
    }
    _, _ = fmt.Fprintf(w, "event: done\ndata: [DONE]\n\n")
    _ = rc.Flush()
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /stream", streamHandler)
    log.Println("测试命令: curl -N http://localhost:8080/stream")
    _ = http.ListenAndServe(":8080", mux)
}

④ 常见坑：本地测流式丝滑、一上生产就变成“卡 15 秒一次性蹦出全文”，99% 是前置 Nginx 没关缓冲（加响应头 X-Accel-Buffering: no 即可）；若长时间无新内容输出，建议每 15 秒 推一行注释帧 : ping\n\n 保活防网关闲置断连。
⑤ 背后原理：net/http 服务端检测到客户端 FIN 断连后取消 r.Context() 的传播链路见 《 核心原理篇 · 06.1 cancelCtx 原理》。

07.6 · 异步解耦实战：周期后台任务与 kafka-go 消费组（先处理业务、后手动提交位点）

07.6 后台任务与消费消息队列

① 需求 & ② 方案：订单支付成功后异步发优惠券、或每分钟扫一次超时未支付订单（MQ，Message Queue，消息队列的防丢、防重、保序与积压排障详见 《 消息队列 · 基础与实战篇》）。Go 写常驻消费者有两个核心规范：① 禁用自动提交，改用 FetchMessage 拉取 → 业务幂等落库成功 → 再调 CommitMessages 手动提交 Offset（防业务崩溃丢消息）；② 循环绑定进程停机 ctx，收到退出信号时平滑处理完手头这一条再退出：

mq_consumer_worker.go · ③ 代码：Kafka 手动提交消费循环 + 定时巡检协程 [Go 1.22+] 
// go get github.com/segmentio/kafka-go
package main

import (
    "context"
    "errors"
    "log"
    "time"

    "github.com/segmentio/kafka-go"
)

// 1. 消息队列消费组协程（注意：用 FetchMessage 而非自动提交的 ReadMessage！）
func RunOrderConsumer(ctx context.Context, brokers []string) error {
    reader := kafka.NewReader(kafka.ReaderConfig{
        Brokers: brokers,
        Topic:   "order.events",
        GroupID: "coupon-svc-grp",
    })
    defer reader.Close()

    for {
        msg, err := reader.FetchMessage(ctx) // 停机 ctx 取消时此处立即返回 context.Canceled
        if errors.Is(err, context.Canceled) {
            log.Println("收到停机信号，消费者平滑退出")
            return nil
        }
        if err != nil {
            log.Printf("拉取异常稍后重试: %v", err)
            time.Sleep(time.Second)
            continue
        }

        // 先执行幂等业务逻辑（如按 order_no 唯一索引插发券表）；注意这里用 WithoutCancel 防半路被掐断
        if err := grantCouponIdempotent(context.WithoutCancel(ctx), msg.Value); err != nil {
            log.Printf("处理失败不提交位点(触发重投或转死信): %v", err)
            continue
        }
        // 业务落库成功后再手动提交 Offset
        _ = reader.CommitMessages(context.WithoutCancel(ctx), msg)
    }
}

// 2. 周期后台定时任务：一律用 time.NewTicker + defer Stop()（切勿在局部函数用无法关闭的 time.Tick）
func RunCleanupCron(ctx context.Context) {
    ticker := time.NewTicker(1 * time.Minute)
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            log.Println("执行过期临时文件清理...")
        }
    }
}

func grantCouponIdempotent(_ context.Context, _ []byte) error { return nil }
func main() {}

④ 常见坑：消息至少投递一次（At-least-once）一定会偶发重复，消费逻辑必须配合数据库唯一索引或 Redis 状态表做幂等；单条处理太慢（如调外部慢接口）超过心跳阈值会导致消费组重平衡（Rebalance），应把拉取到的消息分发给第 06 章的本地 Worker Pool 并发加速。
⑤ 背后原理：消费组重平衡与零拷贝落盘原理见 《消息队列 · 核心原理篇》。

07.7 · 命令行工具实战：标准库 flag 子命令解析、标准错误流与退出码规范

07.7 写一个命令行工具（CLI）

① 需求 & ② 方案：写数据迁移脚本、压测小工具或研发效能 CLI。单命令或两三个子命令直接用官方标准库 flag（零依赖、编译极快）；只有像 kubectl / docker 那样有几十个多级嵌套子命令和自动生成 Shell 补全脚本时，再引入社区库 github.com/spf13/cobra。写 CLI 牢记三项规范：正常结果打 os.Stdout、报错信息打 os.Stderr、失败退出返回非零码 os.Exit(1)（方便 Shell && 与 CI 流水线捕获失败）：

migrate_cli.go · ③ 代码：go run migrate_cli.go up -dsn="mysql://..." -dry-run [Go 1.22+] 
package main

import (
    "flag"
    "fmt"
    "os"
)

// 把真正逻辑写在返回 int 退出码的 run() 里，确保函数内注册的 defer 能正常执行！
func run(args []string) int {
    if len(args) == 0 {
        fmt.Fprintln(os.Stderr, "用法: migrate <up|status> [参数]")
        return 2
    }

    switch args[0] {
    case "up":
        fs := flag.NewFlagSet("up", flag.ContinueOnError)
        dsn := fs.String("dsn", os.Getenv("DB_DSN"), "数据库连接串（支持环境变量 DB_DSN）")
        dryRun := fs.Bool("dry-run", false, "仅打印待执行的 SQL 而不实际变更")
        if err := fs.Parse(args[1:]); err != nil {
            return 2
        }
        if *dsn == "" {
            fmt.Fprintln(os.Stderr, "错误: 必须通过 -dsn 或 DB_DSN 指定数据库")
            return 1
        }
        fmt.Printf("执行迁移: dsn=%s dryRun=%v\n", *dsn, *dryRun)
        return 0
    default:
        fmt.Fprintf(os.Stderr, "未知子命令: %s\n", args[0])
        return 2
    }
}

func main() {
    os.Exit(run(os.Args[1:]))
}

④ 常见坑：os.Exit(1) 会立即让操作系统销毁进程，当前栈上注册的所有 defer（如临时文件删除、缓冲刷盘）统统不会执行！因此务必参考上面代码把主逻辑抽进 run() int 函数，只在 main() 最后一行调一次 os.Exit；另外标准库 flag 在遇到第一个非 - 开头的普通位置参数时就会停止解析后面的选项，提醒用户把 -flag 写在位置参数前面。
⑤ 背后原理：静态单二进制跨平台交叉编译原理见 《 核心原理篇 · 00 静态编译链路》。

07.8 · Web 框架选型：Go 1.22+ 增强版标准库 net/http 与 Gin 怎么选

07.8 Gin 等框架和标准库 net/http（Go 1.22+）怎么选

在 Node.js 里几乎没人裸写 node:http，大家都会装 Express / Fastify / NestJS；但在 Go 里你会发现很多大厂基础服务直接裸用标准库 net/http。原因在于 Go 的 net/http 本身就是生产级并发 HTTP/1.1 + HTTP/2 服务器，而且 Go 1.22 正式给官方路由 http.ServeMux 补齐了过去最缺的「HTTP 方法匹配」和「{id} 路径通配符」：

对比维度 标准库 net/http（Go 1.22+） Gin / Echo（主流轻量 Web 框架）
路由与路径参数 原生支持 mux.HandleFunc("GET /orders/{id}", h)，通过 r.PathValue("id") 取值，满足 95% RESTful 需求。 基于基数树（Radix Tree）高性能路由，额外支持路由分组前缀 v1 := r.Group("/api/v1") 统一挂载组级中间件。
参数绑定与校验 需手写几行辅助函数调 json.NewDecoder(r.Body).Decode(&req) 并自行写 if 校验字段。 核心省事点：内置 c.ShouldBindJSON(&req) 配合结构体标签 binding:"required,email,min=1" 一行完成反序列化与字段校验。
Context 兼容性 原生 (w http.ResponseWriter, r *http.Request)，所有第三方监控/追踪库 100% 原生兼容，永无破坏性升级。 使用自封装的 *gin.Context（对象池复用），在里面开后台协程时必须调 c.Copy() 拷贝副本，拿标准库 context.Context 需写 c.Request.Context()。
选型结论 内部微服务、API 网关、AI SSE 流式服务、公共 SDK、希望零外部依赖的项目，直接用 Go 1.22+ 标准库非常清爽。 包含几十上百个 CRUD 表单接口的业务后端、团队多人协作希望少写绑定样板代码时，选 Gin 开发效率更高（如果喜欢路由分组又想要 100% 标准库签名，也可选超轻量的 go-chi/chi）。

本章即时场景题（先想答案，再点击展开）

1. 把 sql.DB 的 SetConnMaxLifetime 设成了 1 小时，而运维给线上 MySQL 配的 wait_timeout 是 10 分钟，每天早上第一批用户请求总是偶发报 invalid connection / broken pipe，为什么？

夜间低峰期连接闲置超过 10 分钟后，MySQL 服务端已经单方面把空闲连接关掉了；而 Go 连接池以为 1 小时没到，早高峰把这条“半死连接”分给第一个业务请求去发 SQL，一写就撞上断连报错。规范：客户端的 SetConnMaxLifetime（例如 5 分钟）必须显著小于数据库服务端的 wait_timeout（及中间云负载均衡的空闲超时）。

2. 给“调用微信统一下单扣款接口”加了 3 次网络超时自动重试，结果网络抖动时用户被扣了两次钱，问题出在哪？

第一次请求其实已经到达微信服务端并扣款成功，只是回包路上网络丢包触发了客户端读超时；如果你没带同一笔业务幂等单号（out_trade_no）就直接盲目重试写接口，就会造成重复扣款。原则：无条件的自动重试只适用于天然幂等的查询请求（GET）；写接口重试前提是上下游已对齐唯一幂等键。

3. 在 Gin 的接口处理函数里写了 go func() { saveLog(c.GetString("trace_id")) }()，为什么高并发下打出的 trace_id 经常串成别人的请求，甚至偶发崩溃？

为了减少 GC 压力，Gin 使用 sync.Pool 对象池复用 *gin.Context——当前 HTTP Handler 一旦返回，这个 c 实例就会立刻被重置并分配给下一个进来的新请求使用！如果后台子协程直接引用原 c，读到的就是别人的数据。解法：在起协程前先把需要的字符串提取到局部变量，或调用 cCp := c.Copy() 传只读副本进协程。
