🚀 03.1 · 轻量级并发单元：Goroutine 创建方式、OS 线程对比与 2KB 动态连续栈

🚀 03.1 Goroutine 并发示例、OS 线程对比与 2KB 动态连续栈

① 场景说明：在后端高并发服务中，95% 的时间都花在等待网络 IO（查数据库、调 RPC、读 Redis）上。如果采用传统的“一个请求开一条操作系统线程（1:1 模型）”，几万并发就会在内存占用和内核上下文切换上遇到瓶颈。而在 Go 中，只需在函数调用前加一个 go 关键字就能启动一个轻量级协程（Goroutine）：

🐹 goroutine_basic.go · 启动协程与 WaitGroup 等待结果 
func main() {
    var wg sync.WaitGroup
    for i := 1; i <= 3; i++ {
        wg.Add(1) // ① 启动子协程前先让计数器 +1
        go func(id int) {
            defer wg.Done() // ② 子协程结束时让计数器 -1
            fmt.Printf("协程 #%d 执行完毕\n", id)
        }(i)
    }
    wg.Wait() // ③ 阻塞等待计数器归零（若不写这行，main 直接退出，子协程来不及跑！）
    // 输出（顺序随机）: 协程 #3 执行完毕 / 协程 #1 执行完毕 / 协程 #2 执行完毕
}
📖 为什么上面这段代码能轻松开出 10 万个协程？
  • 注意新手第一坑：main() 函数本身跑在主协程上；一旦 main() 返回，整个进程立即退出，不会主动等后台子协程，所以需要用 sync.WaitGroup 或 channel 同步等待。
  • 数量级差距：如果把循环改成 100,000 次，开 10 万个 OS 线程会直接耗尽内存报错；而开 10 万个 Goroutine 仅占用约 200 MB 内存。底层差距见下表：
核心维度 OS 内核线程（Thread · 1:1） Go 协程（Goroutine · M:N） 数量级差距与工程意义
初始栈与资源上限 默认保留 1 MB ~ 8 MB 虚拟地址空间（触碰缺页分配物理页后不可缩容）+ 独立内核栈（8~16KB） 仅 2 KB 起步，栈满时按需 2 倍动态扩容（最大 1GB）、GC 时自动缩容回收 数万并发下线程易触发 threads-max 与内存上限；Goroutine 200MB 即可开出 10 万+ 并发
创建与切换成本 陷入内核态（Ring 3 → Ring 0），保存 16+ 通用/SIMD 寄存器并跑内核调度器，耗时 1 ~ 2 μs 纯用户态切换（借由线程内置的调度专用栈 g0），仅保存 PC/SP/BP 三个核心寄存器，耗时 ~100 ~ 200 ns 上下文切换快 10 倍以上，CPU 算力真正花在业务代码上
IO 阻塞代价 调用阻塞 read 时整条 OS 线程被挂起，加剧线程数膨胀与调度抖动 底层集成 netpoller（epoll/kqueue）：协程挂起让出，底层线程立刻切换去跑下一个协程 用同步顺序代码的直观写法，跑出异步非阻塞事件驱动的高吞吐
💡 进阶考点：为什么 Go 1.4 把协程栈从“分段栈”改成了“连续栈”？
• Go 1.3 分段栈痛点——热分裂（Hot Split）：用链表拼接多个小栈块；若在一个 for 循环内恰好处于栈满临界点调用函数，每次迭代都会触发“分配新栈块 → 函数返回立即释放”，导致性能急剧下降。
• Go 1.4+ 连续栈：栈空间不足时，直接分配一块 2 倍大的连续新内存，把旧栈完整拷贝过去并修正栈内指针偏移量，后续循环调用不再反复分配释放。
⚙️ 03.2 · 调度器架构：G / M / P 核心角色分工、引入 P 的原因与调度流转图

🗺️ 03.2 GMP 核心组件、P 的设计作用与调度流转全景图

① 场景说明：我们在代码里用 go func() 创建了成千上万个协程，但机器只有几个 CPU 核心。Go 运行时（Runtime）是怎样在用户态把几万个协程分配给几个操作系统线程去执行的？先记住 G、M、P 三个核心角色的分工：

① G (Goroutine · 待办任务)

你每次写 go fn() 就创建一个 G 结构体。它装着要执行的函数指令、当前 2KB 协程栈以及程序计数器（PC/SP）。

② M (Machine · 打工线程)

真正上 CPU 干活的操作系统内核线程。但 M 自己没有任务队列，它必须先绑定一个 P，才能从 P 里拿 G 出来执行。

③ P (Processor · 本地任务箱)

逻辑处理器（数量默认等于 CPU 核数 GOMAXPROCS）。每个 P 装着无锁本地队列 runq[256] 和无锁内存池 mcache。

📖 为什么早期 Go 1.0 只有 G-M，后来非要引入中间层 P？
  • 痛点① 全局锁竞争严重：没有 P 时，所有线程 M 每次取协程、放协程都要争抢同一把全局队列锁。引入 P 后，每个 P 有独立的本地无锁队列 runq[256] 和优先单槽 runnext，日常取任务无需加全局锁。
  • 痛点② 内存缓存池随线程数暴涨：无锁内存缓存 mcache（详见 05.3 节）原本绑在每个线程 M 上；一旦系统调用阻塞产生上百个 M，就会吃掉大量内存。引入 P 后，mcache 改绑在固定数量的 P 上（默认等于 CPU 核数），彻底消除了内存膨胀。
📖 图解右半区：偷活干（Work Stealing）与解绑（Handoff）
  • 工作窃取（Work Stealing）：当 P1 的本地队列和全局队列都空了，它会随机挑另一个 P（如 P0），直接从对方 runq 尾部一次性偷走一半的 G，避免有的核忙死、有的核闲置。
  • 系统调用移交（Syscall Handoff）：当线程 M1 因磁盘文件 IO 或 CGO 陷入内核阻塞时，P1 会与 M1 解绑，换一个空闲线程 M2 绑定继续跑队列里的其他 G；等 M1 从内核返回后优先抢空闲 P，抢不到就把 G 放进全局队列自己休眠。
🔍 03.3 · 调度策略与阻塞处理：schedule() 查找优先级与三类阻塞场景

🧭 03.3 寻找可执行 G 的五步优先级与三种阻塞场景对比

🎯 线程 M 寻找下一个可执行 G 的五步顺序
  1. 每调度 61 次先看一眼全局队列（防饥饿）：先去全局队列拿 1 个 G，防止本地两个协程互相唤醒导致全局队列里的 G 一直得不到执行。
  2. 查 P 本地队列（最快路径）：先拿优先槽 P.runnext，若为空再从本地无锁环形队列 P.runq 队头取。
  3. 全局队列批量搬迁：本地彻底空了，加锁从全局队列 sched.runq 搬一批到本地。
  4. 检查网络轮询器 netpoller：非阻塞询问 epoll/kqueue 是否有刚就绪的网络读写协程。
  5. Work Stealing 工作窃取：随机遍历其他 P，从对方队列尾部偷走一半 G；全偷不到才将 M 休眠。
阻塞类型 底层动作与 M / P 状态
① 用户态同步阻塞
(Channel / Mutex / Sleep)		 调用运行时挂起函数 gopark()（将 G 状态改为 _Gwaiting 并让出）；M 和 P 完全不阻塞，百纳秒内切去跑下一个 G。
② 网络 IO 阻塞
(TCP / HTTP / DB 读写)		 Socket 文件描述符交由 netpoller (epoll) 监听，G 调 gopark() 挂在等待队列上；M 和 P 完全不阻塞。
③ 阻塞式系统调用
(磁盘文件 IO / CGO)		 M 与 G 一起陷入内核阻塞；P 执行 Handoff 与原 M 解绑，换新 M 继续跑队列里其他 G。
🔍 深入源码：runtime.schedule() 真实实现与为什么选质数“61”查全局队列？

如果只按“先查本地队列、本地空了才查全局队列”运行，一旦当前 P 上有两个协程通过 Channel 乒乓互相唤醒，P.runnext 永远非空，全局队列里的 G 就会一直得不到执行。为什么选 61？因为它既不太小（太小会频繁抢全局锁拖慢吞吐），也不太大（太大全局 G 等待太久），且61 是质数，不会与业务代码里常见的 2 的幂次（16、32、64）循环步长产生周期重合：

🐹 runtime/proc.go · schedule() 核心找 G 代码 
func schedule() {
    var gp *g
    // ★ 1. 每调度 61 次（schedtick%61 == 0），优先去全局队列拿 1 个 G
    if _g_.m.p.ptr().schedtick%61 == 0 && sched.runqsize > 0 {
        lock(&sched.lock)
        gp = globrunqget(_g_.m.p.ptr(), 1)
        unlock(&sched.lock)
    }
    // ★ 2. 查 P 本地队列（先取单槽 runnext，再取 runq 环形队头）
    if gp == nil {
        gp, _ = runqget(_g_.m.p.ptr())
    }
    // ★ 3. findrunnable() 兜底：全局队列批量拿 → netpoller → Work Stealing 偷一半
    if gp == nil {
        gp, _ = findrunnable()
    }
    execute(gp)
}
⚡ 03.4 · 抢占式调度与监控：协作式抢占、Go 1.14 SIGURG 信号异步抢占与 sysmon

🛡️ 03.4 抢占式调度演进（Go 1.14 SIGURG 信号异步抢占）与 sysmon 后台监控线程

🐹 preempt_loop.go · 单核下纯计算死循环抢占验证 
func main() {
    runtime.GOMAXPROCS(1) // 限制只用 1 个逻辑处理器 P

    go func() {
        var i int
        for { i++ } // 内部没有任何函数调用的纯算术死循环！
    }()

    time.Sleep(time.Millisecond)
    fmt.Println("主协程成功抢回 CPU！")
    // ❌ Go 1.13 及以前：永远卡死，打印不出上面这句话！
    // ✅ Go 1.14 及以后：10ms 后死循环被信号强行抢占，正常打印退出！
}
① Go 1.13 前：基于函数调用点的【协作式抢占】

编译器在每个函数开头插入栈扩容检查指令（morestack）。后台监控线程 sysmon 发现某个 G 运行超 10ms 时，只给它打个标记，等它下次调用函数时主动让出。因此遇到左边这种不调任何函数的 for { i++ } 就彻底失效了。

② Go 1.14+：基于 SIGURG 信号的【异步抢占】

sysmon 发现 G 连续运行超 10ms（或 GC 需要 STW）时，直接向该线程 M 发送操作系统 SIGURG 信号。内核打断线程进入信号处理函数，将 PC 寄存器修改为跳转到 runtime.asyncPreempt，保存上下文后把死循环 G 放回全局队列。

🔍 sysmon 后台监控线程的四项主要职责：sysmon 直接运行在独立 M 上（无需绑定 P）：① 抢占运行超 10ms 的 G；② 剥离陷入 Syscall 阻塞的 P（Retake）；③ 超过 10ms 无人轮询网络时兜底 poll netpoller；④ 超过 2 分钟未 GC 则强制触发一轮 GC，并调 madvise 归还闲置物理内存。
🎯 工程避坑：GOMAXPROCS 在 Docker / K8s 容器里有什么常见坑？

GOMAXPROCS 默认读取宿主机物理节点的逻辑 CPU 核数（如 64 核），在 Go 1.25 之前不感知容器的 cgroup CPU 配额限制（如 K8s 限制 Pod 只能用 2 核）。这会导致 2 核容器创建 64 个 P，引发严重的 CFS 周期限流（Throttling）与上下文切换，接口延迟上升数倍。Go 1.24 及更早版本的生产容器建议引入 go.uber.org/automaxprocs 自动对齐容器配额（注：Go 1.25+ 已原生支持容器 cgroup CPU 配额感知与动态调整）。
