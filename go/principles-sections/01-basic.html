🔑 01.1 变量内存模型、值传递机制与 new / make 底层区别

（基础变量声明与数据类型用法见 🌱 基础与实战篇 · 第 01 节）
① 变量内存模型与值传递规则：在 Go 语言中，所有变量的赋值与函数传参统一遵循值传递（Pass-by-Value）规则，即将变量自身内存空间里存储的内容复制一份传递给函数形参。对照下方内存图，变量在内存中的存储方式分为三种：

  • 对照上图看第 1 栏与第 3 栏的核心区别：固定数组 a := [3]int{10, 20, 30} 是把数字直接装在变量 a 自己盒子里；而切片 s := []int{10, 20, 30} 为了避免传参时拷贝大量元素，在内存里拆成了左右两部分——真正的数字放在右边的底层数组（0x200）里，变量 s 自己手里只拿着左边那张记录了 ① 地址 ptr=0x200、② 个数 len=3、③ 容量 cap=3 的 24 字节描述卡片（Header）。
  • 同理，字典 map 和通道 chan 也是采用这种拆分方式：变量本身只保存一个 8 字节指针（指向堆上的 hmap 或 hchan 结构）。
📌 内存语义对比：固定数组（Array [N]T）与动态切片（Slice []T）
对比维度 固定长度数组（Array · [N]T） 动态切片（Slice · []T）
1. 类型系统定义 长度属于类型的一部分：[3]int 与 [4]int 是完全不同的两种类型，不能互相赋值，也不支持 append 长度不属于类型：无论装多少个元素，类型统一为 []int，支持通过 append 动态扩容
2. 内存结构与传参 一体式存储：变量自身直接存放全部元素（占用 N × sizeof(T) 字节）；赋值或传参时将整块数组完整复制一份 拆分式存储：变量自身仅占 24 字节描述卡片 {ptr, len, cap}；赋值或传参只复制这 24 字节卡片，共享底层数组
3. 判等与可哈希性 支持直接用 == 逐元素比对相等，可作为 map 的 Key 不支持用 == 比较两个切片（仅能与 nil 比较 s == nil），不可作为 map 的 Key
② 切片传参过程图解：为什么函数内修改元素（s[0] = 99）外部可见，而直接 append 不影响外部切片长度？
🧪 pass_by_value.go · 数组、指针与切片传参对比 
// 1. 固定数组 [3]int：传参时复制全部 3 个元素，修改不影响外部
func modifyArray(arr [3]int) { arr[0] = 99 }

// 2. 切片 []int：传参时仅复制 24B 描述卡片 {ptr, len, cap}
func modifySlice(s []int) {
    s[0] = 99          // 顺着 ptr 修改共享底层数组的第 0 格（外部可见）
    s = append(s, 40) // 仅把函数内形参卡片的 len 从 3 改成 4（外部原卡片 len 仍为 3）
}

func main() {
    s := make([]int, 3, 4) // len=3, cap=4, 内容为 [10, 20, 30]
    s[0], s[1], s[2] = 10, 20, 30
    modifySlice(s)
    fmt.Println(s, len(s)) // 输出: [99 20 30] len=3
}
📖 切片传参过程拆解（对照下方图解）

调用 modifySlice(s) 时，main 中的原卡片和函数里的形参卡片各自独立，但两张卡片上的 ptr 都指向同一个底层数组 0x200：
• 执行 s[0] = 99：函数顺着 ptr=0x200 把共享底层数组的第 0 格改成了 99，因此 main 也能读到 99。
• 执行 s = append(s, 40)：只把函数内形参卡片上的 len 改成了 4；而 main 手里原卡片上的 len 依然是 3，因此 main 打印时只读取前 3 格 [99, 20, 30]（若希望函数内的 append 结果带回外部，应将新切片作为函数返回值 return s 返回）。

③ 内存分配函数底层对比：new(T) 与 make(T, ...)
🔹 new(T)：分配零值内存，返回指针 *T

对应上图第 2 类（显式指针），适用于任意类型。调用 p := new(int) 会在内存中分配一块 int 大小的空间并置为零值 0，返回指向该空间的指针 *int。

🔸 make(T, ...)：把“描述卡片”和“底层数据区”一起建好，返回 T 本身

对应上图第 3 类（仅适用于 slice / map / chan）。如果只声明 var m map[string]int，变量里的指针是 nil，右边的底层哈希桶根本还没分配；调用 make(map[string]int) 就是把右侧的底层数据区分配并初始化好，再把地址填进描述结构里返回。

🔤 01.2 · 字符串底层：16 字节只读结构体 stringStruct 与 strings.Builder 零拷贝原理

🧬 01.2 string 16 字节只读内存结构与高效拼接原理

在运行时源码 runtime/string.go 中，string 采用与切片相似的一分为二拆分结构，但因为字符串规定底层字节只读、不可扩容，所以比 24 字节的切片卡片少了一个 cap 字段，固定只占 16 个字节（{ str unsafe.Pointer, len int }）：

① 为什么 string 设计为底层字节只读（不可原地修改）？
  • 传参极轻且并发安全：把一个 10MB 的字符串传给多个函数或协程时，只需复制 16 字节的 {str, len} 描述头，所有协程共享同一块只读内存而无需加锁。
  • 可安全用作 map 的 Key：正因为字符串内容不可原地篡改，其哈希值在生命周期内恒定不变。
  • 代价：每次执行 s = s + "a" 或 []byte(s) 类型转换时，默认都需要分配新内存并完整拷贝字节数据。
🔥 strings/builder.go · strings.Builder 零拷贝转 string 原理 
// 为什么循环拼接推荐用 strings.Builder？
// 1. 内部维护一个可扩容的 buf []byte 切片，WriteString 相当于 append(buf, s...)
// 2. 最终调用 .String() 时，直接用 unsafe 将 []byte 的底层数组指针包装成 string，
//    省去了最后一步 []byte -> string 的内存分配与字节拷贝：
func (b *Builder) String() string {
    return unsafe.String(unsafe.SliceData(b.buf), len(b.buf))
}
📦 01.3 · 包加载与依赖算法：init() 自底向上初始化流程与 Go Modules MVS 算法

🛠️ 01.3 包加载与 init() 初始化流程、Go Modules MVS 算法

① 包加载与初始化流程（自顶向下解析依赖，自底向上执行初始化）：当入口包 main 导入 pkgA、而 pkgA 又导入 pkgB 时，运行时会先沿着 import 链向下递归至没有外部依赖的叶子包 pkgB，在包内按 const 常量 → var 全局变量 → init() 函数 的顺序完成初始化，再逐层向上返回，最终进入 main() 函数：

② init() 特性与 Go Modules 最小版本选择算法（MVS）
  • 多个 init() 函数的允许性：同一个包甚至同一个 .go 源文件中可以定义多个 func init()，编译器会按源文件顺序及自上而下的声明顺序依次执行。
  • 匿名导入 import _ "github.com/go-sql-driver/mysql"：在包路径前加下划线 _，表示仅执行该包的 init() 函数（例如向标准库 database/sql 注册 MySQL 驱动）而不直接调用其导出函数。
  • MVS（Minimal Version Selection，最小版本选择）：当模块 A 声明依赖 D >= v1.1.0、模块 B 声明依赖 D >= v1.3.0（而远端最新已发布到 v1.9.0）时，Go 不会盲目拉取最新版 v1.9.0，而是确定性地选择满足所有依赖约束的最低版本 v1.3.0，从而保证任何时间、任何机器上编译出的依赖版本完全一致。
