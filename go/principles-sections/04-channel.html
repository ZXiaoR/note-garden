🔄 04.1 · 通道通信机制：无缓冲 / 有缓冲 Channel、runtime.hchan 结构与跨栈直接拷贝

🧬 04.1 Channel 收发示例、runtime.hchan 结构与 sendDirect 跨栈直接拷贝

① 为什么需要 Channel？多个协程之间如果靠读写同一个全局变量来配合，就必须到处手动加锁。Go 提倡“通过通信来共享内存”——把数据放进类型安全的管道 chan T 里，从一端塞入（ch <- x）、另一端取出（v := <-ch）。先看无缓冲与有缓冲两种最基础的用法：

🐹 channel_basic.go · 无缓冲（当面交接）vs 有缓冲（快递柜） 
// 1. 无缓冲通道（容量=0）：像当面递东西，没人来接就会一直阻塞等待！
ch1 := make(chan int)
go func() {
    ch1 <- 42 // 子协程把 42 塞进管道（会阻塞直到主协程执行 <-ch1）
}()
v := <-ch1    // 主协程从管道取出 42 → 打印 v 输出: 42

// 2. 有缓冲通道（容量=2）：像有 2 个格子的快递柜，没塞满前立刻返回不阻塞！
ch2 := make(chan string, 2)
ch2 <- "A"    // 放进第 1 个格子，不阻塞
ch2 <- "B"    // 放进第 2 个格子，不阻塞（此时再塞第 3 个就会阻塞！）
fmt.Println(<-ch2, <-ch2) // 按先进先出 FIFO 依次取出 → 输出: A B
📖 底层原理导读：make(chan T, cap) 创建了什么？
  • 1. 环形缓冲区 buf：有缓冲通道用来临时存放元素的定长数组（配合写下标 sendx 和读下标 recvx 循环使用）。
  • 2. 两个阻塞等待链表 recvq / sendq：当通道空了却有人来读，或者满了却有人来写时，该协程会被打包成 sudog 节点挂进等待队列休眠。
  • 3. 一把互斥锁 lock：保护上面所有字段的并发安全。对照下方结构图看数据是怎么流转的：
📖 总结：执行发送语句 ch <- x 时，底层按顺序走哪三条分支？
• 分支① recvq 里已经有协程在等读（走右图 sendDirect）：弹出等待的 sudog，完全绕过 buf，直接把发送者栈上的 x 拷进接收者栈上的接收变量 sg.elem，然后调 goready() 唤醒接收者（省去进出缓冲区的一次拷贝）。
• 分支② 没人等读，但环形缓冲区 buf 还有空位（走中图上方）：把 x 拷进 buf[sendx]，游标后移，发送者立刻返回继续往下跑。
• 分支③ 没人等读，且 buf 已满（或无缓冲）：把当前发送协程打包成 sudog 挂入 sendq 链表，调用 gopark() 休眠让出线程 M。
📊 04.2 · 通道状态管理：close(ch) 遍历、三种状态下的操作表现与关闭规范

🚦 04.2 close(ch) 遍历示例、三种状态的收/发/关表现表与关闭规范

🐹 channel_close.go · 关闭通道与 for-range 自动退出 
ch := make(chan int, 2)
ch <- 10
ch <- 20
close(ch) // 发送方发完所有数据后关闭通道（通知接收方“不会再有新数据了”）

// 方式①：for-range 会自动读完缓冲区剩余的 10 和 20，发现通道已关后自动结束循环！
for v := range ch {
    fmt.Println(v) // 依次输出: 10, 20
}

// 方式②：通道排空后再用 v, ok := <-ch 读，不会阻塞，而是立刻返回零值 + false
v, ok := <-ch
fmt.Println(v, ok) // 输出: 0 false
⚠️ Channel 关闭原则：为什么一般由发送方（Sender）关闭通道？
因为一旦向已关闭的 Channel 发送数据（ch <- x）会立刻触发 panic: send on closed channel！而接收方并不知道发送方还会不会继续写。因此工程规范是：单发送者直接由发送方发完调 close(ch)；多发送者则用 sync.WaitGroup 等所有发送协程退出后再统一关闭。
操作类型 ① nil Channel（仅声明未 make） ② 正常开启的 Channel ③ 已关闭的 Channel（close(ch) 后）
发送 ch <- v 永久阻塞（gopark 永不唤醒） 成功写入/交接，或满时阻塞 💥 立即 panic: send on closed channel
接收 v, ok := <-ch 永久阻塞（常用于在 select 中把某分支置为 nil 来动态屏蔽它） 成功读取（ok=true），或空时阻塞 ✅ 永不阻塞：先读完缓冲剩余元素（ok=true），缓冲排空后立即返回类型零值且 ok=false
关闭 close(ch) 💥 立即 panic: close of nil channel 成功置 closed=1，唤醒所有等待者 💥 立即 panic: close of closed channel
🎲 04.3 · 多路通道复用：select 超时控制、pollorder 随机轮询与 lockorder 加锁顺序

🎛️ 04.3 select 多路监听：超时控制、pollorder 随机洗牌与 lockorder 加锁顺序

① 为什么需要 select？如果一个协程既要从 `jobCh` 接收任务，又要监听定时心跳 `ticker.C` 和超时取消信号 `ctx.Done()`，直接写 `<-jobCh` 会把协程卡死在单一通道上。select 就像专门针对 Channel 的 `switch`——同时监听多个通道，哪个通道先就绪就执行哪个分支：

🐹 select_worker.go · 多路监听与超时退出标准模板 
func worker(ctx context.Context, jobCh <-chan Job) error {
    // ★ 循环内定时用 NewTicker（避免在 for 里反复调 time.After 产生冗余定时器）
    ticker := time.NewTicker(5 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case job, ok := <-jobCh:
            if !ok { return nil } // jobCh 已关闭且排空，正常退出
            handle(job)
        case <-ticker.C:
            reportHeartbeat()     // 每 5 秒触发一次心跳
        case <-ctx.Done():        // 上游超时或取消（close 广播唤醒）
            return ctx.Err()
        }
    }
}
🔍 底层原理：runtime.selectgo 是怎么工作的？
  1. pollorder（随机洗牌防饥饿）：每次进入 select 先用伪随机算法打乱所有 case 的检查顺序——所以如果多个通道同时就绪，Go 会随机挑一个执行，防止排在前面的高频通道把后面的通道饿死。
  2. lockorder（按内存地址排序加锁 ★防死锁）：将所有 case 涉及的 hchan 按内存地址从小到大排序后依次加锁（解锁时逆序）。这样即使协程 A 写 select { ch1, ch2 }、协程 B 写 select { ch2, ch1 }，两边加锁顺序也完全一致，不会发生交叉死锁！
  3. 扫描与挂起唤醒：按 pollorder 扫一遍，有就绪的直接解锁执行；全未就绪且没写 default 时，把当前协程挂进所有通道的等待队列休眠，任一通道唤醒后再把自己从其余通道摘除。
