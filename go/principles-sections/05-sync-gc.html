🔒 05.1 · 锁机制底层：sync.Mutex 双模式切换（1ms 阈值）与 sync.RWMutex 读写锁防饥饿原理

⚙️ 05.1 sync.Mutex 双模式切换与 sync.RWMutex 读写锁底层实现

（Mutex 与 RWMutex 的日常使用方法见 🌱 基础与实战篇 · 05.3 节）
① sync.Mutex 抢不到锁时，协程是立刻休眠吗？如果一抢不到锁就立刻进操作系统内核休眠，上下文切换开销太大。因此 sync.Mutex 采用了“先在用户态自旋等几百纳秒（保吞吐）→ 抢不到再休眠排队 → 排队超 1ms 切换饥饿模式（保公平）”的双模式设计：

锁模式 核心行为与切换阈值（Go 1.9+）
① 正常模式
（默认 · 高吞吐优先）		 当持锁者释放锁并唤醒等待队列队头的老协程时，不会直接把锁给它，而是让老协程与此时正在 CPU 上运行的自旋新协程同台竞争。新协程已经在 CPU 上、拥有热寄存器和缓存，大概率能先抢到锁，从而省去上下文切换开销；但代价是队头老协程可能被新来的协程反复插队。
② 饥饿模式
（队头等待 > 1ms）		 一旦队头老协程醒来抢锁失败且累计等待超过 1ms，Mutex 立即切换为饥饿模式：Unlock() 直接将锁所有权移交给队头老协程，新来的协程不再自旋、不能插队，直接排入队尾休眠。当持锁者发现自己是队列最后一个等待者，或等待时间 < 1ms 时，自动切回正常模式。
② sync.RWMutex（读写锁）底层结构与“写锁防饥饿”设计（src/sync/rwmutex.go）
📐 sync/rwmutex.go · RWMutex 核心字段与负值翻转技巧 
const rwmutexMaxReaders = 1 << 30 // 最大并发读者数上限 (约 10 亿)

type RWMutex struct {
    w           Mutex        // 供写者之间互斥竞争的底层 Mutex
    writerSem   uint32       // 存量读者全部退出后，唤醒等待写者的信号量
    readerSem   uint32       // 写者释放锁后，批量唤醒等待读者的信号量
    readerCount atomic.Int32 // 当前读者数量（有写者等待时减去 1<<30 变为负数！）
    readerWait  atomic.Int32 // 写者到来前的“存量读者”个数，归零时唤醒写者
}
🔍 读写锁是怎样兼顾“读并发”与“写不饿死”的？
  • 无写者时（RLock 极速快路径）：读协程只需执行一次原子加法 readerCount.Add(1)，只要结果 >= 0 就直接拿到读锁，无需加互斥锁。
  • 写者到来时（Lock 翻转符号位拦住新读者）：写协程先调 w.Lock() 挡住其他写者，然后执行 r := readerCount.Add(-rwmutexMaxReaders) 将计数器瞬间变为负数，并把当前已在读的存量人数记入 readerWait。
  • 后续新读者排队，存量读者排空后唤醒写者：此后新来的 RLock() 发现 readerCount < 0（说明有写者正在等），就会主动进 readerSem 休眠排队；而已在里面的存量读者每调一次 RUnlock() 就将 readerWait 减 1，最后一个存量读者减到 0 时通过 writerSem 唤醒写者；写者执行完 Unlock() 时再把 readerCount 加回正数并批量唤醒排队的读者。
⚠️ Mutex / RWMutex 三个常见死锁与误区：① 不可重入（同一协程连续两次 Lock() 会死锁）；② 严禁在持有 RLock 的同一协程内再调 Lock 或二次 RLock（假设协程 A 已持有 RLock，此时协程 B 调 Lock() 把 readerCount 变成了负数并等待 A 释放；若 A 此时又去调第二次 RLock()，A 会因为看到负数而阻塞等待 B，B 又在等 A，形成隐蔽的 AB-BA 死锁！）；③ 禁止值拷贝（含锁结构体传参或绑方法必须用指针 *T）。

⚡ 05.2 atomic / sync.Once / WaitGroup / sync.Map 最小示例与底层原理

🐹 sync_primitives.go · atomic 无锁计数与 sync.Once 单例 
// 1. 简单整数并发累加：用 atomic.Int64 (Go 1.19+) 替代 Mutex，CPU 单条指令完成
var total atomic.Int64
total.Add(1)
fmt.Println(total.Load()) // 输出: 1

// 2. 全局只执行 1 次的懒加载初始化：用 sync.Once
var once sync.Once
for i := 0; i < 5; i++ {
    go once.Do(func() {
        fmt.Println("数据库连接池初始化（无论多少协程调，全局只打印 1 次！）")
    })
}
📖 面试高频追问：为什么 sync.Once 不能只写一句 if CAS(&done, 0, 1) { f() }？

如果只用 CAS(0, 1)：假设协程 A 抢赢了 CAS 把标志改成 1，但它的初始化函数 f() 还要跑 50ms；此时协程 B 进来看到标志已经是 1，就会以为初始化完了，直接拿走还没初始化完的空连接池导致 panic！
所以 sync.Once 底层是 atomic.Load == 0 快路径 + Mutex 慢路径阻塞等待 + 等 f() 彻底跑完才执行 atomic.Store(&done, 1)。

并发原语 适用场景 底层实现要点与注意事项
sync/atomic 计数器、状态标志位、无锁配置热替换 由 CPU 硬件级原子指令（如 LOCK CMPXCHG）直接保证，纳秒级开销；推荐使用 Go 1.19+ 的泛型封装 atomic.Int64 / atomic.Bool / atomic.Pointer[T]。
sync.WaitGroup 等待一组并发子任务全部完成 底层用 64 位整数的高 32 位存剩余任务数 counter、低 32 位存等待者数 waiter。注意：wg.Add(n) 必须在 go func() 之前调用，防止子协程还没跑起来主协程就先执行完 Wait() 退出了。
sync.Map 读多写少，或各协程操作不相交的 Key • Go 1.9~1.23（读写分离双字典）：维护 read（只读原子字典，命中完全无锁）+ dirty（加锁全量字典）；每次读穿透 read 计 misses++，当 misses >= len(dirty) 时将 dirty 原子提升为新 read。
• Go 1.24+（并发 Hash-Trie 树）：底层重写为并发哈希前缀树（HashTrieMap），按哈希位逐层分叉并采用细粒度节点锁，消除了整表提升毛刺。
🧱 05.3 · 内存分配架构：TCMalloc 三级缓存体系（mspan → mcache → mcentral → mheap）

🏗️ 05.3 Go 内存分配器全景：TCMalloc 三级缓存（mspan → mcache → mcentral → mheap）

① 场景与核心思路：高并发下成千上万个协程每秒都在创建结构体和切片。如果每次申请几字节内存都要去全局堆抢一把大锁，程序早就卡在锁等待上了。为此，Go 借鉴 Google TCMalloc 设计了“三级快递分拣仓”模型：
1. 先把向操作系统申请来的大块内存（8KB 页），提前裁成 67 种固定尺寸的小格子（mspan，如 8B、16B、32B ... 32KB）；
2. 给每个逻辑处理器 P 的口袋里配一套专属本地缓存（mcache）——因为同一时刻一个 P 只跑一个线程，所以协程创建小对象直接从当前 P.mcache 拿空格子，全程无需加锁！只有当前 P 口袋里的某规格格子用光了，才加细粒度锁去中央仓库（mcentral）和全局总仓（mheap）领新的一批格子：

📖 复习四个核心名词（从底向上怎么管内存？）
  • 基本单元 mspan：把连续的 8KB 内存页切成等大的小槽位（共划分 8B、16B、24B ... 32KB 等 67 种规格），用位图记录哪个槽位空闲。
  • L1 本地无锁缓存 mcache：绑定在每个逻辑处理器 P 上，从 mcache 拿槽位全程不加锁；且每种规格分为含指针 scan 与不含指针 noscan 两份（GC 扫描时直接跳过 noscan）。
  • L2 中央缓存 mcentral 与 L3 页堆 mheap：当 P.mcache 某规格用光时，加规格锁去 mcentral 领一块新 mspan；mcentral 也空了则向全局页堆 mheap（乃至 OS mmap）切页。
📖 mallocgc 按对象大小分流的三条通道
  • ① 微对象 Tiny（< 16B 且不含指针）：如 bool / int8 / 小字符串，多个微变量直接拼进 P.mcache 同一个 16B 槽位里，节省碎片。
  • ② 小对象 Small（16B ~ 32KB，占业务 99%）：向上对齐到 67 档规格之一，直接从当前 P.mcache 对应规格的 mspan 中无锁分配。
  • ③ 大对象 Large（> 32KB）：直接跳过 mcache 和 mcentral，按 8KB 页数向上取整后直接从全局 mheap 分配连续页。
🎨 05.4 · 并发垃圾回收：三色标记算法、并发漏标条件与 Go 1.8 混合写屏障

🧹 05.4 并发三色标记法、漏标充要条件与 Go 1.8 混合写屏障（Hybrid Write Barrier）

① 场景说明：如果垃圾回收（GC）时把所有业务协程暂停（STW），大内存服务一卡就是几十毫秒。Go 为了把 STW 控制在 0.5ms 以内，采用并发三色标记清除法（业务协程与 GC 线程同时跑）。GC 把堆上所有对象按扫描进度分为三种颜色：
• ⚪ 白色（未访问 / 候选垃圾）：GC 开始时所有对象都是白色；等全部扫描结束还保持白色的对象，就会被当作垃圾回收。
• 🔘 灰色（待扫描波面队列）：自己已经被发现存活了，但它内部指向的子对象还没扫描完。
• ⚫ 黑色（确认存活）：自己存活，且它指向的所有子对象也全都扫完了，GC 不会再回头扫它。

📖 图解中部：为什么并发标记会“漏标误删”？

当用户协程与 GC 并发运行时，只有同时发生以下两步才会出现存活对象被误删：
条件①：一个已经扫完的黑色对象 A，新增了一条指向白色对象 C 的引用；
条件②：原本指向 C 的灰色对象 B，删掉了通往 C 的最后一条引用。
此时黑 A 不会再被扫描，灰 B 又找不到 C，导致仍被 A 引用的 C 一直保持白色被当成垃圾回收。只要用写屏障（编译器在写指针时自动插入的一小段钩子代码）打破任意一个条件即可防漏标。

📖 图解右侧：Go 1.8 混合写屏障是怎么省掉“重扫栈 STW”的？

因为协程栈上的局部变量读写太频繁，Go 不在栈上挂写屏障。在 Go 1.5~1.7（仅插入写屏障）中，如果栈上黑对象指向了堆上白对象，必须在 GC 结束前 STW 暂停全进程、重新把几万个协程栈扫一遍（耗时 10~100ms）。
Go 1.8 混合写屏障规定：① GC 开始时把栈上对象全标黑，GC 期间栈上新建对象也一律直接标黑；② 只要堆上任何指针 *slot = ptr 发生修改，同时把被覆盖的旧对象 *slot 和新指向的对象 ptr 双双染灰。这样堆上白对象不可能躲进黑栈里漏标，省去了结束时的重扫栈 STW。

🔍 escape_analysis.go · 变量什么时候会逃逸到堆上？ 
// 诊断命令：go build -gcflags="-m -l" .
func escapeCases() *User {
    u1 := User{ID: 1}        // ✅ 不逃逸：仅函数内部使用，分配在栈上，函数返回立即销毁
    u2 := &User{ID: 2}       // ❌ 逃逸①：返回了局部变量指针，函数退出后外部还要用，必须放堆上
    fmt.Println(u1)          // ❌ 逃逸②：传给 any(interface{}) 参数且内部触发反射
    s := make([]int, 100000) // ❌ 逃逸③：对象过大超出栈帧容量(>64KB)
    n := getDynamicLen()
    s2 := make([]int, n)     // ❌ 逃逸④：切片大小在编译期无法确定
    _, _ = s, s2
    return u2
}
📖 GC 触发时机与容器防 OOM 配置（GOMEMLIMIT）
  • 两处亚毫秒 STW：一轮 GC 只在开始的 Mark Setup（开启写屏障，~10-50μs） 和结束的 Mark Termination（关闭写屏障，~50-200μs） 极短停顿；若并发标记期间业务分配过快，会触发 Mark Assist（辅助标记：分配快的协程顺带帮忙做一点 GC 标记）。
  • 为什么只靠 GOGC=100 在容器里会 OOM？GOGC=100 表示“等当前堆比上次 GC 后的存活堆翻一倍（+100%）时触发下一轮 GC”。如果在 8GB 容器里存活堆涨到了 4.5GB，下次触发要等到 9GB——还没触发就被容器 OOM Kill 了！
  • 推荐配置（Go 1.19+）：保持 GOGC=100，同时设置软上限 GOMEMLIMIT=6.8GiB（容器内存上限的 80%~85%），逼近上限时会自动提前触发 GC。
