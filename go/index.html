0 · 基础语法：类型 / 零值 / 值传递

Go 的设计哲学是「少即是多」：只有 25 个关键字，没有继承、没有异常（泛型也是 1.18 才补上，见 §7），刻意做减法。几条贯穿全篇的基本认知：

  • 静态强类型 + 编译型：编译成单个静态二进制，不依赖运行时环境，部署就是丢一个文件。
  • 零值可用：变量声明后即有确定零值（数值 0、字符串 ""、bool false、指针/slice/map/chan/interface/func 为 nil），不存在"未初始化的随机值"。
  • 一切都是值传递：函数传参永远是拷贝。只不过 slice/map/chan 内部是"指向底层结构的指针+元数据"，拷贝的是这层"表头"，所以看起来像引用传递。

语法速览（从零起步）

变量与常量

var a int = 10          // 完整声明
var b = 10              // 省略类型，自动推导
c := 10                 // 短变量声明（只能在函数内用），最常用
var d, e = 1, "hi"      // 批量声明，可不同类型
var (                   // 分组声明
    name string = "go"
    age  int    = 15
)

const Pi = 3.14         // 常量，编译期确定，不可改
// iota：常量组里的自增计数器，从 0 开始，每行 +1 —— 枚举神器
const (
    Sun = iota          // 0
    Mon                 // 1（沿用上一行表达式 iota）
    Tue                 // 2
)
易错：① := 只能在函数内用，且左边至少有一个新变量。② 声明了的局部变量必须使用，未使用会编译报错（import 同理），这是 Go 强制的代码整洁。用 _（空白标识符）丢弃不想要的值。

基本类型

类别类型
整数int/int8/16/32/64、uint...（int 随平台 32/64 位）
浮点float32 / float64（默认用 float64）
布尔bool（true/false，不能和整数互转）
字符byte（=uint8，一个字节）、rune（=int32，一个 Unicode 码点）
字符串string：只读字节序列、不可变，底层是 {指针,len}
字符串与遍历：string 按字节存 UTF-8。len(s) 是字节数不是字符数；直接 s[i] 取到的是byte。要按"字符"遍历得用 for i, r := range s（r 是 rune），或转 []rune。拼接大量字符串用 strings.Builder，别用 +=（每次都重新分配）。

流程控制：没有 while，只有 for

// if —— 条件不加括号，可带初始化语句（err 只在 if 作用域内）
if v, err := doSomething(); err != nil {
    return err
} else {
    use(v)
}

// for 的三种形态（Go 唯一的循环关键字）
for i := 0; i < 10; i++ { }     // 经典三段式
for sum < 100 { }               // 当 while 用
for { break }                   // 死循环
for i, v := range slice { }     // range 遍历 slice/map/chan/string

// switch —— 默认自动 break，不用写；要贯穿下一个 case 用 fallthrough
switch day {
case Sun, Sat:          // 一个 case 可多值
    fmt.Println("周末")
default:
    fmt.Println("工作日")
}
switch {                // 不写表达式 = switch true，当 if-else 链用
case age < 18: ...
case age < 60: ...
}

函数：多返回值 + 一等公民

// 多返回值：Go 的招牌，错误处理就靠它
func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("除数为零")
    }
    return a / b, nil
}

func sum(nums ...int) int { }   // 可变参数，nums 是 []int
f := func(x int) int { return x * 2 }  // 匿名函数赋给变量
// 闭包：捕获并记住外层变量（注意捕获的是变量本身、不是快照）

指针：有指针，但没有指针运算

x := 10
p := &x        // & 取地址，p 是 *int
*p = 20        // * 解引用，x 现在是 20

Go 保留指针（用于"想改动原值"或避免大结构体拷贝），但不允许指针算术（不能 p++ 移动），也有 GC 兜底，因此比 C 安全得多。nil 指针解引用会 panic。

struct 与方法：用组合代替继承

type User struct {
    Name string
    Age  int
}

// 方法 = 带接收者的函数。值接收者 vs 指针接收者：
func (u User)  Hello()      { }  // 值接收者：拿到的是副本，改不了原值
func (u *User) Grow()       { u.Age++ }  // 指针接收者：能改原值

// 组合（嵌入）代替继承：把一个类型"嵌进"另一个，自动获得其字段和方法
type Admin struct {
    User            // 匿名嵌入，Admin 直接能用 u.Name / u.Hello()
    Level int
}
接收者怎么选？要修改字段、或结构体较大避免拷贝 → 用指针接收者；小结构体只读可用值接收者。经验法则：同一类型的方法集保持一致，要么都用指针接收者（最常见），避免混用。

可见性：靠首字母大小写

Go 没有 public/private 关键字。标识符（变量/函数/类型/字段）首字母大写 = 导出（包外可见，相当于 public），小写 = 私有（仅包内可见）。简单直接。

值传递 vs "看起来像引用"：传 slice 进函数，改元素能生效（共用底层数组），但在函数内 append 触发扩容后，函数外的 slice 看不到新元素（表头是拷贝，扩容后指向了新数组）。要改动可见，得返回新 slice 或传 *[]T。
func modify(s []int) {
    s[0] = 100      // ✅ 外部可见，共用底层数组
    s = append(s, 4) // ⚠️ 若扩容，外部不可见
}

make vs new

new(T)分配一块 T 的零值内存，返回 *T。任意类型都能用。
make(T,...)只用于 slice / map / chan 这三种。做的是"初始化内部结构"（分配底层数组、hash 桶、环形缓冲），返回 T 本身而非指针。

slice 底层与扩容 高频

slice 是个"胖指针"，运行时结构就三个字段：

slice 表头 (24 字节, 64 位)
array → 指向底层数组的指针
len 当前长度（可访问元素数）
cap 容量（底层数组从起点到末尾的长度）

扩容规则（append 且 cap 不够时）：分配更大的新数组、把旧数据拷过去、返回指向新数组的 slice。增长策略（1.18 后更平滑）：

  • 期望容量 > 2×旧容量：直接用期望容量。
  • 旧容量 < 256：翻倍（×2）。
  • 旧容量 ≥ 256：每次约 ×1.25 平滑增长，逼近 1.25 倍而非直接翻倍，避免大 slice 浪费内存。
  • 最后还会按元素大小做内存对齐，实际 cap 往往比算出来的略大。
切片共享陷阱：b := a[1:3] 与 a 共用底层数组，改 b 会影响 a。想彻底独立要 copy 或用三索引切片 a[1:3:3] 限制 cap，让下次 append 必然重新分配。

map 底层

Go 的 map 是哈希表，核心结构 hmap + 桶数组 bmap：

  • 每个桶（bucket）存 8 个键值对，超了就挂 溢出桶（链地址法的变体）。
  • 桶内先存 8 个 tophash（hash 高 8 位），查找时先比 tophash 快速筛掉不匹配的，再比完整 key。
  • key/value 分开连续存放（k0k1..k7 v0v1..v7），省内存对齐的空隙。
  • 渐进式扩容：负载因子 > 6.5 触发翻倍扩容（容量不够），溢出桶太多触发等量扩容（整理碎片）。扩容不是一次搬完，而是每次读写顺带迁移一两个桶（evacuate），摊平停顿。
三个高频坑：① map 无序，range 顺序每次随机（Go 故意加随机种子防止依赖顺序）。② map 非并发安全，并发读写直接 fatal error: concurrent map read and map write（连 recover 都救不了），要加锁或用 sync.Map。③ 不能对 map 的 value 取地址（&m[k] 编译报错），因为扩容会搬迁地址。

defer / panic / recover

  • defer：注册一个延迟调用，函数返回前按后进先出（LIFO）执行，常用于关闭资源、解锁。1.14 起用"开放编码"（open-coded defer）优化，绝大多数场景几乎零开销。
  • 参数即时求值：defer f(x) 中的 x 在 defer 语句执行时就拷贝快照，不是等到真正调用时才取。
  • 与命名返回值：defer 里能修改命名返回值（return 先赋值给返回变量 → 再执行 defer → 才真正返回）。
  • panic/recover：panic 逐层向上展开并执行沿途 defer；只有在 defer 函数内调用 recover() 才能捕获、恢复正常流程。这是 Go 的"异常"机制，但官方主张只用于真正不可恢复的场景，普通错误走 error。
func f() (result int) {   // 命名返回值
    defer func() { result++ }()  // 能改到返回值
    return 10             // 实际返回 11
}

interface / 类型断言

接口是 Go 多态与解耦的核心，隐式实现——只要一个类型实现了接口的全部方法，就自动满足该接口，无需 implements 声明。底层有两种结构：

结构用于字段
iface带方法的接口tab（itab：接口类型+动态类型+方法表）+ data（指向实际数据）
eface空接口 interface{} / any_type（动态类型信息）+ data
nil 接口大坑：一个接口值 类型和数据都为 nil 才等于 nil。把一个"值为 nil 的具体类型指针"赋给接口，接口的 type 字段非空，此时 iface != nil！经典 bug：函数返回 error 接口，实际返回了 var p *MyErr = nil，调用方 if err != nil 判断竟为 true。
var p *MyErr = nil
var err error = p       // err 的 type=*MyErr, data=nil
fmt.Println(err == nil) // false ！

error 处理

Go 没有 try/catch，错误就是普通的值（error 是只有 Error() string 一个方法的接口），靠 if err != nil 显式处理。

  • error vs panic：可预期的失败（文件不存在、网络超时）用 error 返回；不可恢复的程序 bug（数组越界、空指针）才 panic。
  • 包装与解包（1.13+）：fmt.Errorf("...: %w", err) 包装保留链路；errors.Is 判断是否是某个哨兵错误，errors.As 提取特定类型错误。

包（package）与模块管理

包 package：代码组织的基本单位

  • 每个 .go 文件开头必须声明所属包 package xxx；同一目录下的所有文件必须属于同一个包。
  • 可执行程序的入口包必须是 package main，且含一个 func main()；库包用别的名字。
  • import 引入其它包，用"包名.标识符"访问（如 fmt.Println），只能访问首字母大写的导出成员。
  • func init()：包加载时自动执行（在 main 之前），每个包可有多个，用于初始化。导入顺序：被依赖的包先初始化。
import (
    "fmt"                         // 标准库
    "github.com/gin-gonic/gin"    // 第三方，用完整模块路径
    m "math/rand"                 // 起别名，之后用 m.Intn()
    _ "github.com/go-sql-driver/mysql" // 匿名导入：只为触发其 init()（注册驱动），不直接用
)
初学最大困惑：package 后面的名字 ≠ 导入路径！这两个是不同的东西，默认长得一样只是因为大家守约定：
概念是什么例子
包名（package name）文件首行 package xxx 的 xxx，是调用时的前缀package rand → rand.Intn()
导入路径（import path）import "..." 的字符串，用来定位包在哪（= 模块路径 + 目录）"math/rand"
目录名包所在文件夹名，约定与包名相同（但不强制）rand/
口诀：import 的是"去哪找"（路径），代码里写的是"它叫啥"（包名）。规则：① 同一目录所有文件包名必须相同（一个目录 = 一个包，包名按目录定，不按文件）；② 你 import 路径，但引用时用包名做前缀。
露馅的经典例子——路径最后一段 ≠ 包名：
import "gopkg.in/yaml.v2"   // 路径最后一段是 yaml.v2
yaml.Marshal(...)           // 但包名是 yaml，所以前缀用 yaml 而非 yaml.v2 ！
遇到对不上时，显式起别名最稳：import yaml "gopkg.in/yaml.v2"。IDE 自动加别名，就是帮你消除这种"路径段 ≠ 包名"的歧义。

从 GOPATH 到 Go Modules（演进）

阶段机制与痛点
GOPATH 时代（1.11 前）所有代码必须放在 $GOPATH/src 固定目录下，import 路径=相对 GOPATH 的路径。痛点：项目不能随便放、无版本管理（所有项目共用一份依赖、无法锁版本）、依赖地狱。
Go Modules（1.11 引入，1.16 起默认）官方依赖管理方案，彻底摆脱 GOPATH 束缚。项目可放任意目录，用 go.mod 声明模块与依赖版本，支持语义化版本和可复现构建。现在的标准做法。

go.mod 与 go.sum

# go.mod —— 模块的"身份证 + 依赖清单"
module github.com/me/myapp   // 模块路径（也是别人 import 你的前缀）
go 1.22                      // 要求的 Go 版本
require (                    // 直接依赖及其版本
    github.com/gin-gonic/gin v1.9.1
    golang.org/x/text v0.14.0 // indirect（间接依赖）
)
go.mod声明模块路径、Go 版本、依赖及版本号。人可读、可手改（但一般靠命令维护）。
go.sum记录每个依赖的哈希校验值，保证每次下载的依赖内容一致、未被篡改（供应链安全）。两个文件都要提交到 git。
语义化版本（SemVer）：v主版本.次版本.修订号，如 v1.9.1。主版本升级（v2+）视为不兼容，Go 要求把 /v2 加进模块路径（如 .../myapp/v2）——这叫"语义化导入版本"。没打 tag 的提交会生成伪版本号如 v0.0.0-20240101000000-abcdef123456。

常用命令

命令作用
go mod init <模块路径>初始化模块，生成 go.mod
go mod tidy最常用：扫描代码，自动补齐缺的依赖、删掉没用到的，整理 go.mod/go.sum

go build / go run / go test构建 / 运行 / 测试，会按 go.mod 自动拉依赖

关键环境变量

GOPROXY模块代理。国内常设 https://goproxy.cn,direct 加速下载（direct 表示代理没有就直连源站）。

实战：从零搭一个多包项目并本地调用

光看概念容易懵，走一遍一个小项目的完整流程就通了。假设做一个 myapp：

myapp/ ← 项目根目录（放哪都行，不必在 GOPATH） ├── go.mod ← module github.com/me/myapp ├── main.go ← package main（程序入口） ├── internal/ ← 私有代码，只有本模块能 import │ └── greet/ │ └── greet.go ← package greet └── pkg/ └── mathx/ └── mathx.go ← package mathx（可被外部模块复用）

第 1 步：初始化模块。在 myapp/ 目录下执行，模块路径建议用仓库地址（也是别人/自己 import 的前缀）：

cd myapp
go mod init github.com/me/myapp   # 生成 go.mod

第 2 步：写两个子包。注意每个文件第一行的 package 名 = 它所在的目录名（约定），导出的函数首字母大写：

// 文件：pkg/mathx/mathx.go
package mathx                     // 包名 = 目录名 mathx

func Add(a, b int) int { return a + b }   // 大写 = 导出，包外可调
func mul(a, b int) int { return a * b }   // 小写 = 私有，仅包内可用
// 文件：internal/greet/greet.go
package greet

import "fmt"

func Hello(name string) string {
    return fmt.Sprintf("你好, %s!", name)
}

第 3 步：在 main.go 里导入并调用。关键：import 用「模块路径 + 子目录」的完整路径，调用时用包名做前缀：

// 文件：main.go
package main

import (
    "fmt"

    "github.com/me/myapp/internal/greet"  // = 模块路径 + 目录
    "github.com/me/myapp/pkg/mathx"
)

func main() {
    fmt.Println(greet.Hello("Go"))  // 用「包名.函数」调用，不是路径
    fmt.Println(mathx.Add(3, 4))    // → 7
}

第 4 步：运行 / 构建。

go run .          # 在根目录编译并运行整个 main 包（推荐）
go run main.go    # 也行，但多文件时要把它们都列上，不如 go run .
go build          # 生成可执行文件 myapp（Windows 为 myapp.exe），./myapp 运行
go mod tidy       # 若 import 了第三方库，它会自动下载并写进 go.mod/go.sum
两个高频约定目录：
  • internal/ 是编译器级别的私有目录：只有以 internal 父目录为根的代码才能 import 它（这里即 myapp 自己）。别的模块想 import github.com/me/myapp/internal/greet 会编译报错。用来封装不想对外暴露的实现。
  • pkg/ 是惯例（非强制语法）：放可被外部复用的公共库代码。小项目其实可以不要这层，直接把包放根目录下。
本地还没发布的模块怎么互相引用？比如你本地有两个模块想联调、依赖的库还没推到远程：在 go.mod 里加 replace 指向本地路径——replace github.com/me/libx => ../libx，Go 就会用本地目录而非去网上拉。调试私有/未发布依赖的常用手段。
go.mod 和 go.sum 有什么区别？都要提交吗？
go.mod 是依赖清单（有哪些依赖、什么版本）；go.sum 是这些依赖的哈希校验值（保证内容一致、防篡改）。两者都必须提交到版本控制，这样别人 clone 后能复现一模一样的构建。
go get 和 go mod tidy 区别？
go get 主动添加或升级指定的依赖版本；go mod tidy 则是根据当前代码实际 import 来对账——补上缺的、删掉多余的，让 go.mod/go.sum 和代码一致。日常提交前习惯跑一次 tidy。
项目里依赖了同一个库的两个不兼容大版本怎么办？
靠语义化导入版本：v2+ 的模块路径末尾带 /v2、/v3，所以 foo 和 foo/v2 在 Go 看来是两个不同的包，能在同一项目共存、各自独立版本。Go Modules 的"最小版本选择(MVS)"算法再为每个模块选定一个具体版本。

1 · 为什么引入协程（goroutine）

并发不是 Go 独有，但 Go 把它做成了语言级一等公民（go func() 一个关键字就起一个协程）。要理解为什么，得先看传统线程的痛点。

线程模型的三个痛

痛点线程（内核级）goroutine（用户级）
栈内存固定且大，通常 1~8 MB。开十万个线程就要几百 GB，直接爆内存。初始栈仅 2 KB，按需动态伸缩（连续栈，最大 1GB）。开百万协程也就几 GB。
切换成本由内核调度，切换要陷入内核态、保存/恢复大量寄存器与页表，约 1~2 μs。Go runtime 在用户态调度，只存少量寄存器（PC/SP 等），约 几十 ns，快一个数量级。
创建/销毁系统调用，重。runtime 管理，创建就是分配个小结构体，轻。
核心思想：M:N 调度 —— 把 M 个协程复用到 N 个线程上

更关键的一点：阻塞不再浪费线程

传统模型里线程做阻塞 IO（读网络/磁盘）会被内核挂起，白占一个线程。Go runtime 把网络 IO 统一交给 netpoller（epoll/kqueue）：当 goroutine 读一个还没数据的连接时，它被挂起并让出线程，线程立刻去跑别的 goroutine；数据就绪后该 goroutine 再被唤醒。于是少量线程就能扛住海量并发连接——这正是 Go 写高并发服务器得心应手的根本原因。

goroutine 到底是什么

一个 goroutine 在 runtime 里就是一个 g 结构体，保存了它的栈、程序计数器 PC、栈指针 SP、状态等执行上下文。它不是操作系统线程，OS 根本不知道它的存在——对内核而言只看到那几个 M 线程。

协程 vs 线程一句话：线程是内核调度的、抢占式、重；协程是用户态 runtime 调度的、轻量、切换廉价。goroutine 是"跑在线程之上、由 Go 自己调度的执行单元"。
常见追问：①「goroutine 泄漏」——启动了却因 channel 永久阻塞等原因永远不退出，g 结构和栈一直占着内存，用 context 或关闭 channel 让它有退出路径。② main 函数返回则整个程序退出，不等其它 goroutine，要用 sync.WaitGroup 等待。

2 · GMP 调度模型 高频

M:N 调度落地，就是 GMP。理解这三个字母各自的职责，是理解 Go 并发的钥匙。

GGoroutine。要被执行的任务，含栈和上下文。数量可成千上万。
MMachine，即系统线程（内核线程）。真正干活的载体，G 最终要绑在某个 M 上、由某个 CPU 核执行。
PProcessor，逻辑处理器/调度上下文。是 G 和 M 之间的中介与资源：M 必须先拿到一个 P 才能执行 G。P 的数量 = GOMAXPROCS（默认=CPU 核数），它决定了真正并行的 goroutine 数上限。
为什么要有 P？早期 Go（1.1 前）只有 G-M，靠一把全局锁保护全局队列，多线程抢队列锁竞争严重、扩展性差。1.1 引入 P，给每个 P 一个本地运行队列，M 从自己 P 的本地队列取 G，绝大多数时候无锁，这才让调度真正可扩展。P 还持有 mcache 等资源（内存分配无锁）。

调度流程 & work stealing

一次典型的"找 G 来跑"（M 绑着 P 的调度循环 schedule()）：

  1. 为了公平，每调度 61 次会先瞄一眼全局队列取一个 G（防止全局队列里的 G 饿死）。
  2. 否则优先从本地队列 LRQ 取队头 G（无锁，最快）。
  3. 本地空了 → 去全局队列 GRQ 取一批（加锁）。
  4. 全局也空 → 检查 netpoller 有没有 IO 就绪的 G。
  5. 还没有 → work stealing 工作窃取：随机挑一个别的 P，从它本地队列偷走一半 G 过来。
  6. 实在偷不到 → M 与 P 解绑，M 进入休眠（park），P 变空闲。
新建 G 放哪？go func() 创建的新 G 优先放到当前 P 的本地队列（还有个 runnext 槽存"下一个最优先跑的"，利于父子 goroutine 数据局部性）；本地满了（256）就把一半移到全局队列。

G 发生阻塞时，M 和 P 怎么走？ 并发

阻塞类型处理
channel / mutex / sleep（用户态阻塞）G 被打包成 sudog 挂到等待队列，状态转为 waiting，M 不阻塞，直接解绑该 G 去跑下一个。事件就绪后 G 重新入队。纯用户态切换，不涉及内核。
系统调用（如读文件）M 会随 G 陷入内核而阻塞。此时 runtime 让 P 与该 M 解绑（handoff），P 带着本地队列去找/新建另一个 M 继续跑，不浪费 P 的算力。syscall 返回后，原 M 尝试重新获取一个 P；拿不到就把 G 放全局队列、自己休眠。
网络 IO交给 netpoller，G 挂起让出 M，就绪后由 poller 唤醒。这就是"少量线程扛海量连接"。

抢占式调度 & sysmon

如果一个 goroutine 死循环不让出，别的 G 会不会饿死？早期确实会。演进：

  • 协作式抢占（1.14 前）：只在函数调用时检查栈标志决定是否让出。缺陷：for {} 这种没有函数调用的死循环永远无法被抢占，能卡死整个调度（甚至卡住 GC）。
  • 异步抢占（1.14 起）：基于信号。监控线程 sysmon 发现某个 G 运行超过 10ms，就给它所在的 M 发一个 SIGURG 信号，M 的信号处理程序让该 G 让出。这样即使死循环也能被抢占。
sysmon 是什么？一个不绑定 P、独立运行的后台监控线程，周期性（自适应，最快 20μs、最慢 10ms）巡查：① 抢占运行过久的 G；② 把陷入 syscall 太久的 P 从 M 上抢回（retake）；③ 触发强制 GC（超过 2 分钟没 GC）；④ 处理 netpoll 到期事件。相当于调度器的"巡警"。
GOMAXPROCS 设成多少合适？调大能提速吗？
默认=CPU 逻辑核数，通常就是最优。它是并行度上限（同时能跑 G 的 P 数），不是线程数上限。CPU 密集型设成核数即可，调更大只会徒增调度/切换开销；IO 密集型因为 M 会在 syscall 时增多，P 数一般也不用手动加。容器里注意：Go 早期不感知 cgroup 配额，可能读到宿主机核数导致 P 过多，用 automaxprocs 或手动设置。
一个 goroutine 能跑在不同的线程(M)上吗？
能。G 没有和 M 绑定，被阻塞/抢占后重新调度时可能落到另一个 M 上执行。例外是用 runtime.LockOSThread 把 G 锁死在某个 M（如调用要求线程本地状态的 C 库、OpenGL）。

3 · channel 并发

Go 的并发哲学：「不要用共享内存来通信，而要用通信来共享内存」。channel 就是这句话的载体——协程之间传数据的类型安全管道，天生并发安全。

select

select 同时等待多个 channel 操作，哪个先就绪就执行哪个：

  • 多个 case 同时就绪：伪随机挑一个执行（防止饿死，避免总偏向写在前面的）。
  • 都没就绪且有 default：立刻执行 default（非阻塞收发常用这招）。
  • 都没就绪且无 default：阻塞，直到某个 case 就绪。
  • 空的 select{}：永久阻塞当前 goroutine。
select {
case msg := <-ch:      // 谁先来收谁
    handle(msg)
case <-time.After(3 * time.Second):  // 超时控制的经典写法
    return errTimeout
case <-ctx.Done():     // 优雅取消
    return ctx.Err()
default:               // 非阻塞：上面都没就绪就走这
    doOther()
}

常见坑与模式

  • 关闭广播：关闭一个 channel 会唤醒所有在其上等待的接收者，是天然的"一对多通知"，ctx.Done() 就是这么实现取消的。
  • for-range channel：for v := range ch 会一直收直到 channel 被关闭并取空，是消费者的标准写法。
  • 用容量为 1 的 channel 当锁 / 信号量；用 channel 收敛多个 worker 的结果（fan-in / fan-out）。
  • 死锁：所有 goroutine 都在等对方，runtime 检测到 fatal error: all goroutines are asleep - deadlock!。最常见是无缓冲 channel 在同一个 goroutine 里自发自收。
channel 和锁（Mutex）分别什么时候用？
传递数据所有权、协调多个 goroutine 的执行流、发信号/超时/取消 → 用 channel；单纯保护一小段共享状态（计数器、map、缓存字段）、追求极致性能 → 用 Mutex/atomic。一句话：channel 管"通信与编排"，锁管"临界区互斥"。不要为了用 channel 而用 channel。

4 · 锁与同步

共享内存还是免不了要用（性能、简单）。Go 的 sync 包提供锁与同步原语。

sync.Mutex

互斥锁，同一时刻只有一个 goroutine 能持有。底层不是简单的 OS 锁，而是自旋 + 信号量的混合体，核心是一个 state 字段（位标记：是否加锁 / 是否有等待者 / 是否饥饿 / 唤醒标记）+ 一个信号量 sema（阻塞时排队用）。

正常模式 vs 饥饿模式（1.9 起）

正常模式等待者按 FIFO 排队，但新来的 goroutine 会先自旋抢锁（正在 CPU 上、不睡眠），常能直接抢到，吞吐高。缺点：排队的老等待者可能被反复插队"饿着"。
饥饿模式当队头等待者等待超过 1ms，切换到饥饿模式：锁直接移交给队头，新来的不自旋、不抢，老实排队尾。保证公平、防饿死。等待队列清空或等待时间 <1ms 时切回正常模式。
自旋的意义：临界区通常很短，与其让线程睡眠（陷入内核、上下文切换，成本高），不如空转几十个 CPU 周期等锁释放，往往更划算。但 Go 只在满足条件（多核、自旋次数不多、有 P 可用等）时才自旋，避免空转浪费。
易错点：① Mutex 不可重入（同一 goroutine 重复 Lock 会死锁）。② Mutex 是值类型，不能拷贝（拷贝后是两把锁），所以要用指针传递、且 go vet 会检查。③ 解锁最好配 defer mu.Unlock() 防止提前 return 忘了解锁。

sync.RWMutex

读写锁：读读共享，读写/写写互斥。多个读可同时持有，写独占。适合读多写少。注意写锁会阻塞后续读锁以防写者饿死；读极多写极少的场景收益才明显，否则不如直接用 Mutex。

atomic / CAS

sync/atomic 提供原子操作（Add/Load/Store/Swap/CompareAndSwap），由 CPU 指令保证，无需加锁，比 Mutex 更轻。核心是 CAS（Compare-And-Swap）：比较内存值是否等于期望值，相等才写入新值，是无锁编程的基石（Mutex 内部、很多 lock-free 结构都靠它）。

CAS 的 ABA 问题：值从 A→B→A 变回来，CAS 以为"没变过"。解决靠加版本号/标记。另外 CAS 失败要循环重试（自旋），高竞争下会空转，未必比锁快——原子操作适合单个变量的简单更新（计数器、标志位），复杂临界区还得用锁。

WaitGroup / Once / Cond / sync.Map

WaitGroup等一组 goroutine 全部完成。Add(n) 加计数、每个 goroutine 结束 Done()、主协程 Wait() 阻塞到归零。Add 要在 go 之前调用，别在子 goroutine 里 Add。
Onceonce.Do(f) 保证 f 全局只执行一次（单例、懒加载配置），内部用双检 + atomic + Mutex，并发安全。
Cond条件变量，Wait/Signal/Broadcast，用于"等待某条件成立再继续"。用得少，多数场景 channel 更清晰。
sync.Map并发安全的 map，专为读多写少 / key 集合稳定优化：内部 read（无锁，atomic 读）+ dirty（加锁）双 map，读命中 read 就完全无锁。不适合频繁写。普通场景仍推荐 map + RWMutex。
为什么并发读写普通 map 会直接崩，而不是脏数据？
Go runtime 在 map 里内置了并发检测标志（hashWriting），检测到读写冲突时主动 fatal，是"快速失败"设计——宁可当场崩、也不让你带着难以复现的数据竞争 bug 上线。这也是为什么它无法被 recover 捕获。排查用 go run -race 竞态检测器。

5 · 垃圾回收 GC 高频

Go 是自动内存管理，用 并发的三色标记-清除（Tri-color Mark & Sweep）+ 混合写屏障，目标是极短 STW（Stop The World，通常<1ms，甚至几十 μs），而不是最高吞吐。没有分代、没有整理压缩（non-moving）。

三色标记法

白色
未被扫描 / 未被引用
标记结束仍是白 → 被回收
灰色
自己已被标记存活
但引用的对象还没扫完（待处理队列）
黑色
自己和引用的对象
都已扫描完，确定存活

流程：① 初始全白。② 从根对象（栈、全局变量、寄存器）出发，把可达对象染灰入队。③ 从队列取灰对象，把它引用的白对象染灰，自己转黑。④ 重复直到灰队列空。⑤ 剩下的白色对象即垃圾，清除。

为什么需要写屏障？

GC 是并发的（和用户程序 goroutine 同时跑，即"三色不变性"可能被破坏）。如果标记途中，用户代码把一个黑对象指向一个白对象，同时断开了原本指向该白对象的灰对象引用，这个白对象会被漏标而误删——这就是并发标记的核心难题。

写屏障（Write Barrier）就是给"指针赋值"这个操作挂一个钩子，在并发标记期间维持不变性。Go 1.8 起用混合写屏障（Hybrid = Dijkstra 插入屏障 + Yuasa 删除屏障）：

  • 把被覆盖的旧引用对象标灰（删除屏障，防漏标）；
  • 把新写入的引用对象标灰（插入屏障）；
  • 好处：栈上对象无需插入屏障、GC 结束前无需再 STW 重新扫描栈，把 STW 从旧版的可能几十 ms 压到了亚毫秒级。

GC 触发时机 & STW

触发说明
堆内存增长（主）由 GOGC（默认 100）控制：当堆大小达到"上次 GC 后存活堆 ×(1+GOGC/100)"即翻倍时触发。GOGC 调大 → GC 更少但占内存多；调小 → 更频繁但省内存。1.19 起还有 GOMEMLIMIT 软内存上限。

手动runtime.GC() 阻塞式立即回收（一般只在测试/特殊场景用）。

现代 Go 的 GC 周期里 STW 只发生在两个极短的点：开始时的 Mark Setup（开启写屏障、扫描根的准备）和标记结束的 Mark Termination。中间的标记和之后的清除都与用户程序并发进行。

Mark Assist（标记辅助）：若用户程序在 GC 期间分配内存太快、快过后台标记速度，会让分配内存的那个 goroutine 自己也去帮忙做一部分标记工作，形成"谁分配快谁帮忙"的负反馈，防止堆在 GC 完成前失控膨胀。

逃逸分析

并非所有对象都进堆——编译期的逃逸分析决定一个变量分配在栈还是堆。栈上分配随函数返回自动回收、零 GC 压力；只有"逃逸"出函数作用域的才进堆。

  • 会逃逸：函数返回了局部变量的指针；变量被塞进 interface（如 fmt.Println 的 ...any）；闭包捕获并在外部使用；对象太大或大小编译期不确定（大 slice）。
  • 不逃逸：纯局部使用、生命周期不超出函数，就留栈上。

用 go build -gcflags="-m" 可以看每个变量"escapes to heap"还是留栈。减少逃逸 = 减少堆分配 = 减轻 GC，是 Go 性能优化的常规抓手（配合 sync.Pool 复用对象）。

Go 的 GC 为什么不用分代 / 不做压缩整理？
分代假设"新对象容易死"，但 Go 靠逃逸分析把大量短命对象留在了栈上（根本不进堆、随栈回收），进堆的对象分代收益就没那么大，加上分代会让写屏障更复杂。不压缩（non-moving）是为了实现简单、避免移动对象时的额外 STW 和指针修正；代价是可能有内存碎片，靠 tcmalloc 式的多级 size-class 分配器（mcache/mcentral/mheap）来缓解。整体取舍都指向同一个目标：低延迟。
怎么排查 GC / 内存问题？
① GODEBUG=gctrace=1 打印每轮 GC 的耗时、堆大小、STW 时长；② pprof（heap/allocs profile）看谁在疯狂分配；③ -gcflags=-m 看逃逸；④ 优化手段：减少逃逸、复用对象（sync.Pool）、预分配 slice/map 容量、调 GOGC/GOMEMLIMIT。

6 · context 上下文 并发

起了一堆 goroutine，怎么统一取消它们、设超时、传请求级数据？答案是 context。它是 Go 服务端代码的"半壁江山"——几乎所有涉及 IO/RPC 的函数第一个参数都是 ctx context.Context。

解决什么问题

典型场景：一个 HTTP 请求进来，后台 fan-out 出多个 goroutine 去查 DB、调下游。如果客户端断开 / 超时了，这些 goroutine 应该尽快停下来别白干活。context 就是把"取消信号"沿调用链一路传下去的载体。

四个构造函数

函数用途
context.Background()根 context，空的，一般在 main / 请求入口创建
WithCancel(parent)返回可手动取消的 ctx + cancel() 函数
WithTimeout(parent, d)超时自动取消（d 时间后）
WithDeadline(parent, t)到指定时刻自动取消
WithValue(parent, k, v)携带请求级键值数据（如 traceID），不要用来传函数可选参数；key 要用自定义类型（如 type ctxKey int）而非裸 string，避免不同包的 key 碰撞
func handle(ctx context.Context) error {
    // 派生一个 2 秒超时的子 ctx
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()   // ★ 必须调 cancel，否则计时器/资源泄漏

    ch := make(chan result, 1)
    go func() { ch <- queryDB(ctx) }()  // ctx 继续往下传

    select {
    case r := <-ch:
        return r.err
    case <-ctx.Done():          // 超时或被上游取消，Done() 这个 channel 被关闭
        return ctx.Err()        // context deadline exceeded / context canceled
    }
}
原理：ctx.Done() 返回一个 channel，取消时它被 close（关闭 channel 会唤醒所有接收者，天然"一对多广播"）。子 context 监听父 context，父取消则所有后代级联取消，形成一棵取消传播树。
用法铁律：① context 只沿函数参数逐层传递，永远别存进结构体字段；② WithCancel/Timeout/Deadline 返回的 cancel 函数必须调用（通常 defer cancel()），否则泄漏；③ WithValue 只传请求域的元数据（traceID、用户身份），别拿它当函数传参的偷懒手段；④ ctx 作为函数第一个参数，命名 ctx，这是全社区约定。
context 取消是怎么"通知"到底层 goroutine 的？
靠 ctx.Done() 返回的 channel 被 close。goroutine 在 select 里监听它，一旦关闭就走取消分支退出。标准库的网络/DB 操作内部也会监听 ctx，取消时主动中断阻塞调用。它不强制杀死 goroutine——只是发信号，goroutine 要自己配合检查并退出。

7 · 泛型 Generics（1.18）

1.18 之前 Go 没有泛型，写通用容器/算法只能靠 interface{}+ 类型断言（丢失类型安全、有装箱开销）或代码生成。1.18 正式引入类型参数，补上了这块长期短板。

// T 是类型参数，any 是约束（表示任意类型）
func Map[T, U any](s []T, f func(T) U) []U {
    r := make([]U, len(s))
    for i, v := range s {
        r[i] = f(v)
    }
    return r
}

// 用约束限定 T 必须支持 < 比较
type Ordered interface { ~int | ~float64 | ~string }  // | 是类型集合，~ 表示底层类型
func Max[T Ordered](a, b T) T {
    if a > b { return a }
    return b
}

// 调用处（在某个函数内）：
Max(3, 5)            // 类型自动推导为 int → 5
Max("a", "b")        // string → "b"
类型参数[T any]：函数/类型可接受的"类型占位符"，编译期实例化成具体类型
约束 constraint本质是个 interface，规定类型参数必须满足什么（有哪些方法、属于哪些类型集合）
anyinterface{} 的别名（1.18 起），表示任意类型
comparable内置约束，表示支持 ==/!=（可做 map key）
~int"底层类型是 int"，能匹配 type MyInt int 这种自定义类型
什么时候用泛型？容器（List/Set/Tree）、通用工具函数（Map/Filter/Reduce）、数值算法——这些"逻辑相同、只是类型不同"的场景。不要滥用：业务逻辑优先用接口（行为抽象）；泛型是"类型抽象"，能显著减少重复代码时才上。Go 的理念仍是能简单就别泛型。

8 · 数据竞争与内存模型 高频

并发 bug 最隐蔽的一类就是数据竞争（data race）：两个以上 goroutine 并发访问同一内存、至少一个是写、且没有同步。结果是未定义的——可能读到半个值、可能永远读到旧值、可能直接崩。

var count int
for i := 0; i < 1000; i++ {
    go func() { count++ }()   // ❌ 1000 个 goroutine 无同步地写 count
}
// count++ 其实是「读→加→写」三步，并发下互相覆盖，结果远小于 1000

怎么发现：-race 竞态检测器

Go 自带竞态检测器，编译时加 -race，运行时会监控内存访问，发现竞争就打印"WARNING: DATA RACE"+ 双方调用栈。强烈建议在测试/CI 里常开：

go run -race main.go
go test -race ./...
检测器只能发现实际发生过的竞争（依赖当次运行的调度），不能证明"一定没有竞争"；且有性能开销（内存 5~10 倍、速度 2~20 倍），所以只在测试用，别上生产。

Go 内存模型 & happens-before

为什么"不加锁直接读另一个 goroutine 写的变量"不可靠？因为编译器和 CPU 会重排指令、各 CPU 核有自己的缓存。Go 内存模型用 happens-before 规则定义"什么情况下一个 goroutine 的写，保证对另一个 goroutine 可见"。建立 happens-before 的手段就是那些同步原语：

  • channel：一次发送 happens-before 对应的接收完成；channel 的 close happens-before 收到零值。
  • Mutex：Unlock happens-before 下一次 Lock。
  • 一次 go 语句 happens-before 被启动的 goroutine 开始执行；WaitGroup.Wait 返回 happens-after 所有 Done。
一句话：要想"我在 A goroutine 写的，B goroutine 能正确看到"，就必须用 channel / 锁 / atomic 建立同步关系。共享可变状态 + 无同步 = 未定义行为，别靠"应该没事"的侥幸。修复上面的例子：加 sync.Mutex 或用 atomic.AddInt64。

9 · 常见并发模式与坑 并发

坑 ①：for-range 循环变量捕获（1.22 是分水岭）

Go 1.22 之前，for 循环的循环变量在每次迭代复用同一个地址。在循环里 go func(){ use(v) }() 闭包捕获的是变量本身，等 goroutine 真正执行时，循环早跑完了，大家读到的都是最后一个值——这是 Go 最著名的坑之一。
for _, v := range []int{1, 2, 3} {
    go func() { fmt.Println(v) }()   // 1.22 前：很可能全打印 3 3 3
}

// 1.22 前的修复：每轮拷一份
for _, v := range s {
    v := v                    // 遮蔽出一个新变量（老经典写法）
    go func() { fmt.Println(v) }()
}
// 或把 v 作为参数传进去： go func(v int){ ... }(v)
Go 1.22 起：循环变量改为每轮迭代一个新实例，这个坑被语言层面修掉了，上面的原始写法现在也正确。但面试常考、且老代码/老版本仍在，必须知道来龙去脉。

坑 ②：goroutine 泄漏

goroutine 启动了却永远无法退出（阻塞在没人收的 channel、没人关的 channel、或漏传 ctx），它的栈和内存一直占着，累积起来就是内存泄漏。原则：启动一个 goroutine，就要想清楚它在什么条件下退出——用 ctx 取消、关闭 channel、或 WaitGroup 收尾，给它一条确定的退出路径。

模式：WaitGroup + channel 收敛结果（fan-out / fan-in）

var wg sync.WaitGroup
results := make(chan int, len(jobs))
for _, j := range jobs {
    wg.Add(1)
    go func(j Job) {
        defer wg.Done()
        results <- process(j)
    }(j)
}
go func() { wg.Wait(); close(results) }()  // 全干完才关结果 channel
for r := range results { total += r }       // range 到 channel 关闭自然结束

利器：golang.org/x/sync 里的两个高频库

errgroupWaitGroup 的增强：并发跑一组任务，任一个返回 error 就取消其余（配合 ctx），并收集第一个错误。写并发调用比裸 WaitGroup 优雅太多。
errgroup.WithContext(ctx)返回的 group，g.Go(fn) 提交任务，g.Wait() 等全部完成或首个出错。
singleflight解决缓存击穿/重复请求：同一个 key 同时有 N 个请求，只真正执行一次，其余等待并共享同一结果。缓存失效瞬间防止打爆 DB 的神器。

Go 把测试做进了工具链和语言文化：测试文件以 _test.go 结尾、与被测代码同目录同包，函数签名固定，go test 直接跑。无需第三方框架。

11 · 性能优化与进阶杂项

struct 内存对齐（经典优化题）

结构体字段的排列顺序会影响它占多少内存。CPU 按字长对齐访问，编译器会在字段间插入填充字节（padding）凑对齐。把字段按大小从大到小（或相近类型聚在一起）排列，能减少 padding：

type Bad struct {   // 占 24 字节
    a bool    // 1 字节 + 7 填充
    b int64   // 8
    c bool    // 1 字节 + 7 填充
}
type Good struct {  // 占 16 字节（省 1/3）
    b int64   // 8
    a bool    // 1
    c bool    // 1 + 6 填充
}

用 unsafe.Sizeof() 能看实际大小。高频创建的小结构体、或海量元素的 slice，调字段顺序收益明显。

sync.Pool：对象复用，减轻 GC

频繁 new 再丢弃的临时对象（如 buffer、临时结构体）会给 GC 很大压力。sync.Pool 是临时对象缓存池：Get 拿一个（没有就调 New 造），用完 Put 放回复用。

var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
b := bufPool.Get().(*bytes.Buffer)
b.Reset()
defer bufPool.Put(b)
// ... 用 b 拼接
注意：Pool 里的对象随时可能被 GC 清掉（每轮 GC 会清理），所以只能放"可重建、无状态"的临时对象，不能当连接池/长期缓存用。取出来记得 Reset 清残留。

反射 reflect（三定律）

反射让程序在运行时检查类型、读写字段、调方法，是 JSON 序列化、ORM、依赖注入的底层。核心 reflect.Type（类型信息）+ reflect.Value（值）。Rob Pike 的三定律：

  1. 从接口值可以反射出 reflect.Value（reflect.ValueOf(x)）。
  2. 从 reflect.Value 可以还原回接口值（.Interface()）。
  3. 要想通过反射修改一个值，这个 Value 必须是可寻址（settable）的——即传进来的是指针。
反射慢、且绕过编译期类型检查（错误推迟到运行时 panic），能不用就不用。框架底层用它是为了通用性，业务代码里出现大量反射往往是设计信号。

unsafe / cgo（了解即可）

  • unsafe.Pointer：绕过类型系统做指针转换（如 []byte ↔ string 零拷贝），能提速但极危险、破坏内存安全、不受兼容性保证，仅在极致优化且清楚后果时用。
  • cgo：在 Go 里调 C 代码（import "C"）。代价：编译变慢、跨语言调用有开销、丧失跨平台交叉编译的便利、goroutine 调度受影响。能用纯 Go 就别引 cgo。

附 · 高频面试速记

为什么 Go 要引入协程？它比线程好在哪？
线程栈大（MB级）、内核态切换贵（μs级）、数量受限；goroutine 栈 2KB 起、用户态切换（几十 ns）、可开百万。runtime 用 M:N 把海量协程复用到少量线程，且阻塞 IO 交给 netpoller 不占线程，天生适合高并发。
讲讲 GMP。P 为什么存在？
G=任务、M=系统线程、P=逻辑处理器/调度上下文（数=GOMAXPROCS）。M 必须持有 P 才能跑 G。P 给每个处理器一个本地队列，取 G 基本无锁，解决了早期 G-M 全局锁竞争，让调度可扩展；还带 mcache 做无锁内存分配。
goroutine 阻塞在 syscall 时，P 会怎样？
P 与阻塞的 M 解绑（handoff），带着本地队列去找/建另一个 M 继续跑，不浪费算力；syscall 返回后原 M 再尝试抢 P，抢不到就把 G 丢全局队列、自己休眠。channel/网络 IO 这类是纯用户态阻塞，M 根本不阻塞。
Go 怎么防止一个死循环 goroutine 霸占 CPU？
1.14 起异步抢占：sysmon 发现 G 跑超 10ms，给其 M 发 SIGURG 信号强制让出。此前是协作式，只在函数调用点检查，纯死循环抢不了。
无缓冲和有缓冲 channel 区别？向已关闭 channel 收发会怎样？
无缓冲=同步交接，收发双方必须同时就绪；有缓冲=异步，满/空才阻塞。发送已关闭 channel → panic；接收已关闭 channel → 取完剩余值后返回零值且 ok=false；重复关闭/关 nil → panic。由发送方负责关闭。
Mutex 的正常模式和饥饿模式？
正常模式新 goroutine 可自旋抢锁、吞吐高但可能饿死老等待者；某等待者等超 1ms 转饥饿模式，锁直接移交队头、新来的老实排队，保证公平；队列清空后切回。
channel 和 Mutex 怎么选？
传递数据/编排流程/信号取消超时用 channel（通信共享内存）；保护一小段共享状态、追求性能用 Mutex/atomic。别为用 channel 而 channel。
Go 的 GC 原理？STW 为什么这么短？
并发三色标记-清除 + 混合写屏障（1.8）。标记和清除都与用户程序并发，STW 只在 Mark Setup 和 Mark Termination 两个极短点。混合写屏障让栈无需重扫、GC 尾部不再长 STW，压到亚毫秒。
三色标记为什么需要写屏障？
并发标记时用户代码可能把黑对象指向白对象、又断开原引用，导致白对象漏标被误删。写屏障在指针赋值时把相关对象重新染灰，维持不变性。Go 用 Dijkstra 插入+Yuasa 删除的混合写屏障。
逃逸分析是什么？和 GC 有什么关系？
编译期判断变量分配在栈还是堆：不逃出函数就留栈、随返回自动回收、零 GC 压力；返回指针/进 interface/被闭包捕获等会逃逸到堆。减少逃逸即减少堆分配、减轻 GC，是常规优化手段。
slice 作参数，函数内 append 为什么外面看不到？
slice 传的是{指针,len,cap}表头的拷贝。改元素共用底层数组所以可见；append 触发扩容后表头指向新数组、但那是函数内的副本，外部表头仍指旧数组，故不可见。要返回新 slice。
接口值什么时候等于 nil？那个经典坑？
接口 type 和 data 都为 nil 才 ==nil。把值为 nil 的具体指针赋给接口，type 非空，接口就 !=nil。常见于返回 error 时返回了 nil 的 *MyErr，调用方 err!=nil 误判为真。
context 是干嘛的？用法铁律？
沿调用链传递取消信号、超时和请求级数据。Done() 返回的 channel 被 close 即广播取消。铁律：作第一个参数传递不存结构体、cancel 必须调用(defer)、WithValue 只放请求元数据。
什么是数据竞争？怎么发现和修复？
多 goroutine 并发访问同一内存、至少一个写、无同步，结果未定义。用 go test/run -race 检测；修复靠 channel/Mutex/atomic 建立 happens-before。
for 循环里起 goroutine 打印循环变量，为什么全是最后一个值？
1.22 前循环变量每轮复用同一地址，闭包捕获的是变量本身，等 goroutine 执行时循环已结束。修复：循环内 v:=v 拷贝或作参数传入。1.22 起改为每轮新变量，已修掉。
sync.Pool 用来干嘛？有什么注意点？
复用临时对象、减轻 GC。对象随时可能被 GC 清掉，只能放可重建的无状态临时对象（如 buffer），取出要 Reset，别当连接池/长期缓存。
struct 字段顺序为什么影响内存占用？
内存对齐：编译器按字长补 padding。字段从大到小排列可减少填充，用 unsafe.Sizeof 验证。
泛型什么时候用？any/comparable/~ 是什么？
逻辑相同只是类型不同的容器/工具函数/数值算法用泛型。any=interface{}别名；comparable=可用==做map key；~int=底层类型为int。业务逻辑优先用接口。
