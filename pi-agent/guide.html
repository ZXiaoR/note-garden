🔄 01.1 · 双层循环状态机（agent-loop.ts:runLoop）：内层推进工具与即时纠偏，外层消费排队续接

💡 01.1 外层与内层双 while 循环的分工机制及 4 个宿主注入钩子

在最简单的教学 Demo 中，Agent Loop 往往只是一个单层 while (hasToolCalls) 循环。但在真实编码场景中，当 Agent 正在连续执行“读文件 ➔ 改代码 ➔ 跑测试”时，用户随时可能敲入新消息。用户的补充输入在意图上分为截然不同的两类：
一类是紧急纠偏（Steering），例如“停一下，别改数据库表，只改前端校验”，要求在当前正在运行的这个工具刚一结束、紧接着请求模型前立刻插队生效；另一类是延后追加（Follow-up），例如“等你把登录 Bug 彻底修好后，顺便帮我写个单元测试”，要求绝对不能打断当前的修 Bug 思路，必须等当前任务完全收尾后再开启下一轮。
为了在状态机层面严格区分这两种时机，Pi 在 packages/agent/src/agent-loop.ts ↗ 中设计了双层嵌套循环与 4 个宿主注入钩子：

📄 packages/agent/src/agent-loop.ts (L188–L329) · 双层循环与 Steering / Follow-up 调度核心源码 
// 启动时先检查一次是否有用户在等待期间提前敲入的 Steering 消息
let pendingMessages: AgentMessage[] = (await config.getSteeringMessages?.()) || [];

// 【外层循环】：当内层循环将要停止时，检查是否有排队等待的 Follow-up 消息接续
while (true) {
  let hasMoreToolCalls = true;

  // 【内层循环】：只要上一轮还有工具调用，或者有待注入的 Steering 消息，就持续推进
  while (hasMoreToolCalls || pendingMessages.length > 0) {
    let preparedMessages: AgentMessage[] = [];
    if (lastCompletedTurn) {
      // [注入点 1] prepareNextTurn：宿主可在此处执行主动水位线压缩（Compaction）或动态切换模型
      const nextTurnSnapshot = await config.prepareNextTurn?.(lastCompletedTurn);
      if (nextTurnSnapshot) {
        currentContext = nextTurnSnapshot.context ?? currentContext;
        preparedMessages = nextTurnSnapshot.messages ?? [];
      }
      // 压缩耗时较长，若压缩前未读到 Steering，压缩完成后再补读一次（避免单条模式一次吞两条）
      if (pendingMessages.length === 0) {
        pendingMessages = (await config.getSteeringMessages?.()) || [];
      }
      await emit({ type: "turn_start" });
    }

    // 将工具集合变更转为队尾增量声明（保护首部 KV Cache），连同 pendingMessages 推入上下文
    for (const message of declareToolChanges(currentContext, [...preparedMessages, ...pendingMessages])) {
      currentContext.messages.push(message);
      newMessages.push(message);
    }
    pendingMessages = [];

    // [注入点 2] prepareRequest：请求发出前最后一次调整上下文、模型或推理等级（如 jev-router）
    const requestUpdate = await config.prepareRequest?.({ context: currentContext, model: config.model, thinkingLevel: config.reasoning ?? "off" }, signal);
    if (requestUpdate) currentContext = requestUpdate.context ?? currentContext;

    // 发起流式模型请求，实时发出 message_update 并返回最终拼装好的 AssistantMessage
    const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFunction);
    newMessages.push(message);

    const toolCalls = message.content.filter((c): c is ToolCall => c.type === "toolCall");
    hasMoreToolCalls = false;
    if (toolCalls.length > 0) {
      // 若因 max_tokens (stopReason === "length") 截断，整批工具调用直接返错，严禁执行残缺参数
      const executedToolBatch = message.stopReason === "length"
        ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
        : await executeToolCalls(currentContext, message, config, signal, emit);
      hasMoreToolCalls = !executedToolBatch.terminate;
      for (const result of executedToolBatch.messages) {
        currentContext.messages.push(result);
        newMessages.push(result);
      }
    }

    // [注入点 4] finishTurn：本轮模型+工具完成后回调宿主，并立刻拉取内层 Steering 队列
    const decision = await config.finishTurn?.(lastCompletedTurn, signal);
    if (decision?.action === "end") return await emit({ type: "agent_end", messages: newMessages });

    explicitContinuation = decision?.action === "continue";
    pendingMessages = (await config.getSteeringMessages?.()) || [];
  }

  // 【内层循环结束】：此时模型未发起新工具调用且无 Steering，才读取外层 Follow-up 排队消息
  const followUpMessages = (await config.getFollowUpMessages?.()) || [];
  if (followUpMessages.length > 0) {
    pendingMessages = followUpMessages;
    continue; // 续接外层循环，重新进入内层 while
  }
  if (explicitContinuation) { explicitContinuation = false; continue; }
  break;
}

// 1. 流式增量期（toolcall_delta）：允许 partial-json 猜右括号，仅供 UI 实时预览
export function parseStreamingJson<T = any>(partialJson: string | undefined): T {
  if (!partialJson || partialJson.trim() === "") return {} as T;
  try { return JSON.parse(partialJson) as T; } catch {}
  try { return JSON.parse(repairJson(partialJson)) as T; } catch {}
  try { return partialParse(partialJson) as T; } catch { return {} as T; }
}

// 2. 终态落盘期（toolcall_end）：严禁 partialParse 猜括号。
// 仅调 repairJson 修复字符串内未转义换行/控制字符；若结构残缺则抛错交由内核自愈
export function parseToolCallArguments(raw: string | undefined): ParsedToolCallArguments {
  try { return { args: JSON.parse(raw) }; } catch (firstErr) {
    try {
      return { args: JSON.parse(repairJson(raw)) };
    } catch {
      return { args: {}, error: firstErr instanceof Error ? firstErr : new Error(String(firstErr)) };
    }
  }
}

🛡️ 02.1 · 工具容错与自愈机制（agent-loop.ts）：截断拒止、pi-schema Schema 校验与 1:1 toolCallId 错误回填

💡 02.1 工具执行三道防线与 1:1 toolCallId 结构化错误自愈闭环

大模型调用工具时存在三类高频故障：① 输出大段代码时撞上 max_tokens 输出上限（stopReason === "length"），导致工具参数在半截被截断；② 传错了参数类型或漏填必填字段，或者触发了高危命令拦截；③ 参数结构合法，但工具在运行期抛出异常（例如 edit 在文件中找不到 oldText、或者找到了多处相同的 oldText 无法唯一定位）。
如果宿主直接向调用栈外层 throw Error，不仅会导致整个会话崩溃，更致命的是会在消息历史中留下一条没有配对 toolResult 的孤立 toolCall——当用户下一轮继续发消息时，Anthropic 或 OpenAI API 会因为违反“每个 tool_use 必须紧跟 tool_result”的协议约束而直接拒绝请求（HTTP 400）。因此，Pi 在 agent-loop.ts 中设立了三道递进防线，确保任何报错都被转化为携带相同 toolCallId 且标记 isError: true 的结构化消息送回给模型，驱动模型在下一轮内层循环自我修正：

// 【防线 ①】L488：当模型输出因 max_tokens (stopReason === "length") 被截断时，整批拒绝执行
async function failToolCallsFromTruncatedMessage(toolCalls: ToolCall[], emit: AgentEventSink): Promise<ExecutedToolBatch> {
  const messages: ToolResultMessage[] = [];
  for (const toolCall of toolCalls) {
    const result = createErrorToolResult(
      "Tool call skipped because the assistant response was truncated at the token limit; tool arguments may be incomplete."
    );
    messages.push(await emitToolResultOutput(toolCall, result, true, 0, emit));
  }
  return { messages, terminate: false };
}

async function prepareToolCall(currentContext: AgentContext, assistantMessage: AssistantMessage, toolCall: ToolCall, config: AgentLoopConfig, signal?: AbortSignal): Promise<PreparedToolCallOutcome> {
  const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
  if (!tool) return { kind: "immediate", result: createErrorToolResult(`Tool ${toolCall.name} not found`), isError: true };
  try {
    if (toolCall.argumentsError) throw new Error(`Invalid tool call arguments: ${toolCall.argumentsError}`);
    const validatedArgs = validateToolArguments(tool, { ...toolCall, arguments: preparedArgs });
    if (config.beforeToolCall) {
      const beforeResult = await config.beforeToolCall({ assistantMessage, toolCall, args: validatedArgs, context: currentContext }, signal);
      if (beforeResult?.block) return { kind: "immediate", result: createErrorToolResult(beforeResult.reason || "Tool execution was blocked"), isError: true };
    }
    return { kind: "prepared", toolCall, tool, args: validatedArgs };
  } catch (error) {
    return { kind: "immediate", result: createErrorToolResult(error instanceof Error ? error.message : String(error)), isError: true };
  }
}

async function executePreparedToolCall(prepared: PreparedToolCall, signal: AbortSignal | undefined, onUpdate: ToolUpdateSink): Promise<ExecutedToolCallOutcome> {
  const updateEvents: Promise<void>[] = [];
  let acceptingUpdates = true;
  try {
    const result = await prepared.tool.execute(prepared.toolCall.id, prepared.args as never, signal, (partial) => {
      if (acceptingUpdates) updateEvents.push(Promise.resolve(onUpdate(partial)));
    });
    acceptingUpdates = false;
    await Promise.all(updateEvents);
    return { result, isError: result.isError === true, durationMs: 0 };
  } catch (error) {
    acceptingUpdates = false;
    await Promise.all(updateEvents);
    return { result: createErrorToolResult(error instanceof Error ? error.message : String(error)), isError: true, durationMs: 0 };
  }
}

function buildSessionPath(
  entries: SessionEntry[],
  leafId?: string | null,
  byId?: Map<string, SessionEntry>,
): SessionEntry[] {
  const index = buildEntryIndex(entries, byId);
  let current = leafId ? index.get(leafId) : entries[entries.length - 1];

    current = current.parentId ? index.get(current.parentId) : undefined;
  }

}

// 2. 查找最后一次“非纯追加变更（删除工具或同名重定义）”的下标（供 additions 模式定界）
function findLastNonAdditiveToolChange(systemMessages: readonly SystemMessage[]): number {
  const declared = new Set<string>();
  let last = -1;
  for (let i = 0; i < systemMessages.length; i++) {
    if ((systemMessages[i].toolsRemoved?.length ?? 0) > 0) last = i;
    for (const tool of systemMessages[i].toolsAdded ?? []) {
      if (declared.has(tool.name)) last = i; // 曾声明过的工具再次声明（含删后重加）视为非纯追加
      declared.add(tool.name);
    }
  }
  return last;
}

    // 不允许中途追加：全部折叠进顶层 requestTools
    return { requestTools: getCurrentTools(systemMessages), foldedSystemMessages: systemMessages.length };

关注点：用声明式抽象把规划（Todo）、记忆、工具与子 Agent 拼成拓扑。比如 LangChain Deep Agents 的 Middleware 组合，或 DSH 的 Cordis 插件树。但只靠通用 Framework 直接进百万行代码库往往会翻车——因为缺了针对真实工具与长上下文的细节打磨。

🛡️ L3 Agent Harness = 缰绳与防抱死 ABS

关注点：Harness 原意是马具/安全背带——大模型是动力强但易脱缰的烈马，Harness 用确定性工程代码（模糊 Diff、流式截断、1:1 错误自愈、安全切分压缩、Prefix Cache 保护）把不可靠的模型驯服成可靠的工程系统。这也是决定生产级 Agent 上限的胜负手。

🔬 06.2 六大核心工程机制的架构权衡（Trade-offs）与主流开源方案横评

读懂了 Pi 的源码实现后，最重要的收获不是背下它的函数名，而是看清每一个设计背后放弃了什么、换取了什么（Trade-off），以及其他主流框架在同一个分岔路口选择了哪条路：

核心工程决策点 Pi 的设计选择与源码落点 其他主流框架的替代方案 核心 Trade-off（收益 vs 代价）
1. 代码库检索路线
（Agentic Search vs Vector RAG）		 纯实时流式 ripgrep + 目录渐进披露（grep.ts 500字/100条/50KB 三重截断 + AGENTS.md 路由） • Claude Code / Codex：同为实时 rg / glob Agentic Search
• Cursor / 早期 IDE 插件：本地 AST 分块 + 向量库 Embedding 索引		 实时 rg 零索引构建延迟、切分支永不过期、精确符号匹配强，但模糊语义搜索需模型多猜几轮关键词；向量库 首轮语义召回快，但索引易陈旧且维护重。
2. 多步工具调用范式
（JSON Tool Call vs Code-as-Action）		 双轨支持，MCP 默认走 codemode（在 QuickJS Wasm 沙箱内写 JS 批量组合工具并过滤结果） • DeepSeek Harness (DSH)：内置 ptc-runtime（编程式工具调用）
• 传统框架：每步操作均走一次 JSON tool_calls 模型往返		 codemode / PTC 将 10 轮模型往返压缩为 1 次 Wasm 脚本执行，省下 70%+ 中间结果 Token 与延迟；代价是需要维护 Wasm 桥接与 TS 声明生成。
3. 长任务与多智能体拓扑
（Single Loop vs Multi-Subagent）		 默认单主循环 + 6 段式压缩；subagent 与 plan-mode 作为可选扩展按需开启 • Deep Agents / OpenCode：默认内置主 Agent + task 委派独立上下文的 Subagent
• DS SuperAgent：Router + Engine 工单 + 多 Worker 并发		 单主循环 上下文完整、零跨 Agent 传话失真，适合强耦合编码；多 Subagent 隔离广度搜索的脏输出，但存在父子交接信息损耗与额外首字延迟。
4. 会话状态与持久化
（JSONL Tree vs Graph Checkpoint）		 本地只追加 session.jsonl 有向树（id / parentId / leafId + 跨分支 LCA 回溯摘要） • LangGraph / Deep Agents：关系库/KV 存图节点 State Checkpoint
• DSH：session.vN.jsonl[.zstd] 事件流 + deriveMessages() 纯函数投影		 JSONL 树 极简透明、一行 grep/jq 即可排查、天然支持 /tree 分叉回退；LangGraph Checkpoint 支持复杂分布式图节点恢复，但存储层偏重。
5. 大工具集与缓存保护
（Full Schema vs BM25 + Tail Delta）		 MCP 薄暴露 + 内存级 BM25 按需搜索 + 队尾 <system-reminder> 增量声明 • 常规 MCP 客户端：启动时将全部 MCP 工具 Schema 拼入请求头部 tools 数组 Pi 的做法保护了首部 10 万 Token 的 Prefix KV Cache 不因工具动态挂载而失效，且避免百级工具稀释注意力；代价是首次使用隐藏工具需多一步 tool_search。
6. 安全执行与隔离边界
（Host Process vs Container Workspace）		 日常开发跑宿主进程（配信任门禁 + Hook 拦截 + QuickJS 沙箱）；评测跑无网 Docker + UID 65532 降权 • OpenHands SDK：每个会话默认跑在独立的 Docker / 远程容器 Workspace Server 中
• Codex Harness：OS 级 Seatbelt / Landlock 沙箱策略 + app-server 审批		 宿主直接执行 启动零延迟、与开发者本地环境 100% 一致；OpenHands 容器化 Workspace 隔离最彻底、适合云端无人值守批量跑工单，但镜像与环境同步较重。
🚀 06.3 · 演进方向预判：从 Pi 与主流开源方案看 AI Agent 工程化的 5 大未来趋势

🔭 06.3 AI Agent 工程化架构的五大演进方向

趋势 ① · 「薄 Framework + 厚 Harness」成为工业界共识

随着基座模型自身规划与推理能力跃升，早期靠复杂的静态有向图（DAG）替模型硬编码思考步骤的“重编排框架”正在退潮。主循环本身越来越薄（如 Pi 的 packages/agent 仅 6 个文件），而90% 的工程壁垒集中在 L3 Harness 层：如何做到 95% 的 Prefix Cache 命中率、如何让 edit 在缩进漂移时依然精准落盘、如何在跨模型切换时零报错清洗历史。

趋势 ② · 从 JSON Tool Calling 走向 Code-as-Action（编程式工具编排）

无论叫 Pi 的 codemode、DeepSeek Harness 的 ptc-runtime（Programmatic Tool Calling），还是 Anthropic 的代码工具执行，核心方向高度一致：不再让模型用笨重的 JSON 一轮一轮调工具搬运原始数据，而是把工具集暴露为 TypeScript/Python SDK，让模型写一段在毫秒级 Wasm/微沙箱内运行的脚本，一次性完成循环调用、条件分支与数据过滤。

趋势 ③ · 上下文从「静态全量注入」走向「极小路由目录 + 按需拉取 + 离线整理」

即使模型拥有 1M 窗口，无脑塞入几十份长文档与百级工具依然会引发严重的“分心税”与高昂账单。以 Pi 的 <available_skills> 三级披露 + 内存 BM25 检索，以及 Anthropic 的 <1k index.md + 离线 Dreaming 整理（详见本花园 《Anthropic Agent 记忆架构》↗）为代表，“常驻层只放轻量指针，正文靠工具按需拉取”已成为标准范式。

趋势 ④ · 上下游双端协议标准化 + 防作弊评测驱动开发（Eval-Driven）

• 协议标准化：向下通过 MCP 统一接入外部工具，向上通过 JSON-RPC / App-Server 协议（如 Pi 的 modes/rpc 与 output-guard.ts、Codex 的 app-server）让同一个 Harness 内核无缝嵌入终端 TUI、VS Code、Web 与飞书/GitHub 后台工单系统。
• 评测驱动（Eval-Driven）：像 packages/evals 这样通过容器隔离、0o600 + UID 65532 物理防作弊、并跑 without_docs vs with_docs 量化净增益的评测流水线，正在取代主观体感调优，成为合并任何 Prompt 或 Skill 修改的 CI 准入门槛。
