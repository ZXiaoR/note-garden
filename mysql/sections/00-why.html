🧭 先搞清楚目的 · 别把数据库当成一堆孤立的八股名词来背

💡 从第一性原理出发：如果不用数据库，直接读写磁盘文件会死在哪里？

很多同学刚接触 MySQL 时，会被满屏的 B+ 树、ACID、隔离级别、MVCC、间隙锁 (Gap Lock)、CAP / 主从复制 / Redis 一致性 劝退，不知道学这些到底是为了干什么。其实数据库没有任何“凭空发明”的概念——每一个机制，都是被真实的物理硬件限制、高并发冲突与分布式同步痛点一步步逼出来的。

假设你写一个业务系统，最朴素的想法是把数据存成服务器硬盘上的文件。当系统只有你一个人测试、只有 100 条数据时，只要会写基础的增删改查就够了；但只要业务真正上线，你会依次撞上 三堵逃不掉的高墙（慢查询墙 → 单机并发墙 → 分布式与缓存同步墙）：

🌱 入门阶段（起点）
常规的「增删改查」
（表建模 + SQL CRUD）
① 把业务建成结构化表
主键 / 字段类型 / 非空唯一约束
② 写出正确的增删改查
SELECT / INSERT / UPDATE / JOIN
③ 基础事务意识
多步写操作捆成事务一起提交
⚠️ 为什么不能停在入门？
当数据上百万、并发上千、机器变多台时，立刻撞上右侧三大工程主线 ➔
🚀 进阶主线一：单机「查询速度变慢」怎么破？（第 02～03 章 · 存储与索引）
痛点：磁盘慢 + 全表扫描
百万行逐行读盘要几秒 → 引入 16KB 页 + Buffer Pool
武器：B+ 树索引体系
聚簇索引(存行) vs 二级索引(存主键) → 回表、覆盖索引、最左前缀
验证：EXPLAIN 执行计划
为什么建了索引却没走？慢在扫描、回表还是排序？
🛡️ 进阶主线二：单机「高并发读写一致性与死锁」怎么破？（第 04～05 章 · 事务、MVCC 与锁）
① ACID 事务基础
Undo 保原子回滚 · Redo 保持久恢复
② 四大隔离级别
脏读 / 不可重复读 / 幻读（RU / RC / RR / 串行）
③ MVCC 多版本
ReadView + Undo 链表，管「读与写」不阻塞
④ 锁的范围粒度
记录锁 / 间隙锁 / 临键锁，管「写与写」互斥
🌐 进阶主线三：多节点与跨组件「数据同步一致性」怎么选？（第 06 章 · 日志、主从复制与 Redis 同步）
📡 同服务多节点：一主多从读写分离 (CAP)
主库增删改 → binlog → 从库查。选 AP（异步最终一致） 还是 CP（无损半同步 / 强制读主库）？
🧱 跨组件同步：MySQL × Redis 缓存一致性
主流最终一致方案：Cache-Aside（先更库再删缓存） + Canal 订阅 binlog 异步重试删。
STAGE 1 · 入门阶段我们懂什么就够了？

🎯 目标：把单库业务数据存对、查对（应对基础功能开发）

在入门阶段，你不需要一上来就去背页分裂、锁退化或分布式一致性，只需要掌握好 3 件事 就能胜任日常 CRUD 功能开发：

  1. 会设计一张干净的表（第 01 章）：懂得每张表必须有主键（PRIMARY KEY），金额用精确的 DECIMAL 而不用浮点数，合理设置 NOT NULL 与唯一约束。
  2. 会写常规的增删改查 CRUD（第 01 & 03 章）：熟练使用 SELECT / INSERT / UPDATE / DELETE、WHERE 过滤、ORDER BY 排序、LIMIT 分页，以及给高频查询字段建上基础索引。
  3. 有基本的单机事务意识（第 04 章）：知道“扣 A 的钱 + 给 B 加钱”这种多步写操作必须包在 START TRANSACTION ... COMMIT 事务里，不能拆成两条裸 SQL 各自跑。
STAGE 2 · 进阶在干什么？为什么要了解进阶？

🔥 目标：解决「慢查询」「并发错乱/死锁」与「多节点/Redis 同步」（应对生产与面试）

入门解决的是“功能写得出来”，进阶解决的是“数据大了不慢、并发高了不乱、加了从库和 Redis 后数据还一致”。具体对应这 4 类生产必遇问题：

  • 问题 ①（慢查询）：明明建了索引，为什么线上查询还是慢到超时？
    👉 对应 第 02～03 章（B+ 树、回表、覆盖索引、最左前缀与 EXPLAIN）。
  • 问题 ②（并发读写）：高并发下怎么防止超卖/脏数据，又让普通查询不卡死？
    👉 对应 第 04 章（ACID → 隔离级别 → MVCC 历史版本链）：靠 MVCC 让读写不阻塞，靠事务与当前读防超卖。
  • 问题 ③（锁的范围与粒度）：两个接口改的不是同一行，为什么突然死锁？
    👉 对应 第 05 章（行锁 Record / 间隙锁 Gap / 临键锁 Next-Key）：理解不同隔离级别与索引条件下，锁的范围如何扩大或退化。
  • 问题 ④（分布式与异构同步）：一主多从刚写完为什么查不到？MySQL 和 Redis 怎么保持一致？
    👉 对应 第 06 章（内部 2PC、一主多从 CAP 取舍、Cache-Aside 先改库再删缓存 & Binlog 异步订阅）。
👇 现在带着这张地图往下读：从 01 一张表与一条 SQL 的旅程 出发，顺着「存储与索引 → 事务与 MVCC → 锁的范围 → 一主多从与 Redis 同步」一步步推导出整个体系！
