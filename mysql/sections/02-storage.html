02 存储与内存 · 从“硬盘找一行太慢”出发：为什么需要 16 KiB 页、B+ 树与 Buffer Pool？ PAGE · B+ TREE · BUFFER POOL
❓ 02.1 · 面对硬盘上的几百万行数据，InnoDB 是怎么一步步逼出这套存储结构的？

🧭 02.1 三大硬件痛点，逼出 InnoDB 的三大核心存储结构

别急着死记“页是 16 KiB、索引是 B+ 树”。我们先设想：如果让你把 1000 万行 users 存在硬盘文件里，你会遇到哪三个致命痛点？InnoDB 的三大核心组件，正好按顺序一步步解决这三个痛点：

痛点 ①：一行行读硬盘太慢！
硬盘随机 I/O 最怕“零碎小读写”。如果每次只从磁盘读几十字节的一行，找 100 行就要跑 100 次磁盘 I/O。
👉 第一步：引入「16 KiB 页 (Page)」——把相邻的多行打包进一个 16 KiB 的页里，每次按“页”整批读写，摊薄磁盘开销！
痛点 ②：几万个页怎么找目标页？
1000 万行会装满几十万个数据页。如果从第 1 页挨个翻到最后一页（全表扫描），还是慢得无法接受。
👉 第二步：引入「B+ 树」给页建目录——把每个数据页的“最小主键值 + 页号”提出来做成目录页，从根页 3 步就能定位到目标数据页！
痛点 ③：每次查都读盘还是嫌慢！
就算 B+ 树只需走 3 层，如果每秒上万次请求都去磁盘读这 3 个页，硬盘照样被打爆。
👉 第三步：引入「Buffer Pool 内存池」——把热页常驻内存！读优先走内存，写也先改内存页（脏页）+ 记 redo 日志，后台慢慢刷盘。
❓ 02.2 · 16 KiB 数据页与 B+ 树目录是怎么配合快速找行的？

🌳 02.2 第一步 & 第二步：16 KiB 数据页与 B+ 树目录导航

STEP 1 & 2 · 磁盘组织结构

InnoDB 管理和缓存数据的基本单位是页（Page），默认大小为 16 KiB（可在实例初始化时配置；注意这不代表操作系统或硬盘的最小 I/O 单位也是 16 KiB）。

为了在成千上万个页里快速定位，InnoDB 用 B+ 树把页组织起来：非叶子页（目录页）只存“键值 + 子页指针”，叶子页才存真正的索引记录（聚簇索引存完整行）。同一层的页通过双向指针前后链接，范围查询只需先定位起点页，再顺着叶子页双向链表向右滑行即可：

📂 非叶子目录页（16 KiB）· 仅存「最小主键值 + 子页号指针」（不存整行数据，扇出极大！）

id ≥ 101 ──▶ 指向 页#20
id ≥ 201 ──▶ 指向 页#30

💡 范围查询为什么极快？ 比如查 WHERE id BETWEEN 50 AND 150，只需从根页定位到 页#10，读完直接顺着红色的 ⇄ 双向指针滑到 页#20，不用再回根页重新找！
对比结构 适合什么场景 为什么 InnoDB 最终选了 B+ 树？
哈希表 (Hash) 纯等值查找 = 哈希完全无序，无法直接支持 > / < / BETWEEN 范围查询与 ORDER BY 排序。
平衡二叉树 (AVL/红黑树) 内存中的有序查找 每个节点只分 2 个叉（瘦高），1000 万行树高超过 20 层，每次下潜都要读盘的话磁盘 I/O 次数太多。
普通 B 树 (B-Tree) 单点多路有序查找 B 树非叶子节点也存完整行数据，导致一个 16 KiB 目录页装不下几个指针（扇出小、树变高）；且范围扫描要跨层上下回溯，不如 B+ 树叶子双向链表顺滑。
📌 正确的记忆方式：非叶子页只存“键+指针”，单页容纳分支极多（约上千个），树才足够“矮胖”。但树高 ≠ 实际磁盘 I/O 次数：高频目录页大概率常驻在内存 Buffer Pool 中，而二级索引查询还可能发生回表或读取 undo 旧版本。
🔍 进阶图解 ① · “三层 B+ 树存两千万行”是怎么算出来的？为什么逻辑连续 ≠ 物理连续？

面试常背“B+ 树三层能存两千万行”，它其实是一个非叶子页扇出 × 叶子页行数的数量级估算模型：

📐 图 A：3 层 B+ 树容量算术推导（假设 BIGINT 主键 8B + 页号指针 6B ≈ 14B / 条目录项）
第 1 层：根页（1 个页）
16 KiB 扣除页头页尾后除以 14B
≈ 装 1,000 个子页指针
第 2 层：二级目录页（1,000 页）
每页同样装约 1,000 个指针
1000 × 1000 = 100 万个叶子指针
第 3 层：叶子数据页（100 万页）
假设单行 ~1KB（每页装 ~15 行）
100万 × 15 ≈ 1,500 万行记录！
⚠️ 边界结论：如果单行只有 100 字节，每页能装 100 多行，3 层就能装上亿行！真实容量受「键宽、单行大小、页填充率」影响，脱离行大小空谈“一千万行必分表”没有依据。
🧱 图 B：叶子页「逻辑双向链表」≠「磁盘物理连续」（按区 Extent = 1 MiB 分配）
🔗 逻辑视角：靠页头里的 prev / next 页号串联
页#12 (id 1~50) ⇄ 页#89 (分裂新页) ⇄ 页#13 (id 81~120)
💽 物理视角：按「区 Extent = 连续 64 页 (1 MiB)」分配
• 中间插入导致页分裂时，新申请的 页#89 在磁盘上未必紧挨着旧页 #12。
• 为了减少随机 I/O，表变大后 InnoDB 每次按区（Extent，连续 64 个 16KiB 页 = 1 MiB）向磁盘申请空间，提升范围扫描的局部性。
❓ 02.3 · 为什么有了 B+ 树，还需要 Buffer Pool 内存缓冲池？

⚡ 02.3 第三步：Buffer Pool 内存缓冲池 —— 把热页留在内存

STEP 3 · 内存加速核心

有了 16 KiB 页和 B+ 树，InnoDB 又在内存中开辟了 Buffer Pool（缓冲池），避免每次查询和修改都直接读写磁盘：

  • 读数据页：先查 Buffer Pool 哈希表，命中直接读内存页；未命中才从磁盘把那个 16 KiB 页整页加载进 Buffer Pool。
  • 改数据页：直接修改 Buffer Pool 里的内存页，把它标记为脏页（Dirty Page），同时顺序追加写 redo log；后台线程会在合适时机把脏页刷回磁盘数据文件，腾出内存并推进恢复点（checkpoint）。
① ⚡ SQL 执行器发起请求
• SELECT：按页号请求读某页
• UPDATE：直接改内存页 + 写 redo
② 🧠 Buffer Pool（内存页池）
干净页 (Clean)
与磁盘一致，命中直读
脏页 (Dirty)
内存已改，待后台刷盘
COMMIT 时只需刷 Redo 日志，无需每次立刻刷 16KiB 数据页！
③ 💽 磁盘表空间数据文件 (.ibd)
⬅️ 缓存未命中时：从磁盘读入 16KiB 页
➡️ 后台异步 Flush：把脏页刷回磁盘
💡 这里先埋一个问题：内存里的脏页还没刷回磁盘就 COMMIT 了，万一此时断电怎么办？答案是 06 章的 WAL 与 redo 日志。注意：后台刷回脏页到表空间仍可能是随机 I/O，不能把后台刷页直接等同于“随机写全部变成了顺序写”。
🔍 进阶图解 ② · 三条管理链表、5:3 冷热分区 LRU（防全表扫描污染）与 Change Buffer

Buffer Pool 内部靠三条链表管理页帧，并用改进版 5:3 冷热分区 LRU 防止一次全表大扫描把热点页全挤走，同时用 Change Buffer 优化非唯一二级索引的写入：

🌡️ 图 A：Buffer Pool 三条管理链表 & 5:3 冷热分区 LRU（Midpoint 插入防全表扫描冲刷）
① Free List（空闲链表）：刚启动或淘汰后，用来快速找空闲页帧。
② LRU List（冷热淘汰链表）：按访问热度排序，内存满时淘汰冷页。
③ Flush List（脏页链表）：专门挂载已修改的脏页，供后台按 LSN 刷盘。
🔥 Young 热数据区（约占 5/8）
真正高频访问的热点页受保护，不会被一次全表扫描挤走
⬇️ Midpoint
新页插入口
🧊 Old 冷数据区（约占 3/8）
新读入的页先插在 Old 区头部 ──▶ 尾部优先淘汰
💡 为什么全表扫描不会冲掉热缓存？ 因为新读入的页不会直接插到链表最左边（Young 头），而是插在 5:3 交界的 Midpoint（Old 区头部）；必须在 Old 区存活满 1 秒（innodb_old_blocks_time=1000） 后又被访问，才有资格晋升到 Young 热区！
⚡ 图 B：Change Buffer 写缓冲（延迟非唯一二级索引页的随机读盘）
✅ 适用场景：修改「非唯一二级索引」且目标页不在内存时
1. 写操作先把变更暂存进 Change Buffer 即可返回；
2. 省去了立刻去磁盘随机读入那个二级索引页的 I/O；
3. 等后续真正读到该页或后台空闲时，再执行 Merge（合并）！
🚫 两个必考边界（唯一索引 & 8.0 / 8.4 版本差异）
• 唯一索引不能用：写入时必须立刻把索引页读进内存检查唯一性冲突，省不掉读盘；
• MySQL 8.0 默认：innodb_change_buffering = all（开启）；
• MySQL 8.4 默认：改为 none（SSD 普及后随机读极快，Change Buffer 收益下降）。
