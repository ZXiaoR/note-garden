❓ 07.1a · 一条普通 SELECT 从头到尾经历了什么？

📖 07.1a 再走一遍：一次普通 SELECT

  1. Server 解析与优化：Server 解析 SQL，优化器选择访问路径。
  2. 定位数据页：执行器调用 InnoDB，沿索引定位所需页；Buffer Pool 不命中时从磁盘加载页。
  3. MVCC 可见性判断：RC / RR 下按 ReadView 找到可见版本；可能回表、沿 undo 重建旧版本。
  4. 返回结果：按计划完成剩余过滤、连接、排序或聚合，向客户端返回结果。
📌 注意：普通一致性 SELECT 通常不加记录锁，但仍涉及 MDL 等机制，不能说“全程没有任何锁”。
❓ 07.1b · 一条 UPDATE 从头到尾经历了什么？

✍️ 07.1b 再走一遍：一次 UPDATE users SET balance=balance+10 WHERE id=1

  1. 当前读与加锁：找到当前记录，取得需要的锁；冲突时等待或处理错误。
  2. 写日志与改内存页：生成 undo 与 redo，修改 Buffer Pool 中的页。undo 不是等到提交才出现，redo 也不是只在最后才生成。
  3. 内部两阶段提交：Server 收集对应 binlog 事务事件；提交时通过内部 2PC 协调引擎和 binlog。
  4. 完成提交与释锁：按持久化配置完成提交，释放相关事务锁，客户端得到结果。
  5. 后台刷脏页：脏页按刷页策略写回；每次写数据页前都必须满足 WAL，而不是必须等到提交以后才允许刷页。
💡 核心总结：能讲清这五步，就能解释为什么会锁等待、为什么能回滚、为什么提交后数据页不必立即写盘、为什么复制依赖 binlog。不要把概念时序图当作精确到每条 CPU 指令的实现顺序。
🧪 07.2 · 双会话实验：打开两个终端，亲眼看到快照和锁

🧪 07.2 动手验证：两个独立会话下的 MVCC 与锁等待

在自己的测试库使用开头的 users 表，打开两个独立连接。每轮开始时确认上一轮事务已结束。这里给的是预期现象；具体服务器上的结果应由实际执行验证。

实验一：同一快照与当前读的区别

步骤 会话 A 会话 B
准备 先执行 UPDATE users SET balance=100 WHERE id=1; 并提交
1 SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT balance FROM users WHERE id=1;
👉 预期 100		 —
2 — START TRANSACTION;
UPDATE users SET balance=120 WHERE id=1;
COMMIT;
3 SELECT balance FROM users WHERE id=1;
👉 预期仍为 100（若改 RC 则为 120）		 —
4 SELECT balance FROM users WHERE id=1 FOR UPDATE;
👉 预期 120：这是当前锁定读
ROLLBACK;		 —

实验二：同一行更新为什么等待

步骤 会话 A 会话 B
1 START TRANSACTION;
SELECT id FROM users WHERE id=1 FOR UPDATE;		 —
2 保持事务未结束 START TRANSACTION;
UPDATE users SET balance=balance+1 WHERE id=1;
👉 预期等待 A 释放记录锁
3 ROLLBACK; 若尚未超时，更新继续执行；随后 ROLLBACK; 清理实验修改
⚠️ 实验安全守则：不要在生产库为演示故意持锁。实验完在两个会话都结束事务；若遇等待超时，应按实际错误状态清理事务再重试。
