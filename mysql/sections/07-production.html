07.1 · 安全与实例配置：MySQL 8.0 两步法最小权限授权与 my.cnf 核心参数

07.1 账号创建与最小权限控制（RBAC），以及 my.cnf 核心参数

线上业务应用严禁直接连 root 超级管理员账号。在 MySQL 的 RBAC（Role-Based Access Control，基于角色的访问控制） 权限体系中，一个账号的完整身份由 '用户名'@'允许连接的客户端网段' 共同组成（'app_rw'@'10.0.%' 与 'app_rw'@'localhost' 是两个完全独立的账号）。在 MySQL 8.0 / 8.4 中，必须严格分两步执行：先 CREATE USER 创建账号，再 GRANT 授予最小权限：

rbac_minimal.sql · 生产环境标准账号创建与最小权限授权（8.0 / 8.4） 
-- 1. 创建业务读写账号（仅允许内网 10.0.x.x 容器网段连接）
CREATE USER 'app_rw'@'10.0.%' IDENTIFIED BY 'AppPass_2026#';

-- 2. 仅授予 shop_db 库的增删改查权限（不给 DROP / ALTER / GRANT OPTION）
GRANT SELECT, INSERT, UPDATE, DELETE ON `shop_db`.* TO 'app_rw'@'10.0.%';

-- 3. 创建只读报表账号（仅供后台统计服务连接只读从库）
CREATE USER 'bi_ro'@'10.0.%' IDENTIFIED BY 'ReadOnly_2026#';
GRANT SELECT ON `shop_db`.* TO 'bi_ro'@'10.0.%';

-- 4. 审计查看某账号拥有的权限与回收特定权限
SHOW GRANTS FOR 'app_rw'@'10.0.%';
REVOKE DELETE ON `shop_db`.* FROM 'app_rw'@'10.0.%';
my.cnf 核心配置项 工程含义与生产推荐值
innodb_buffer_pool_size InnoDB 数据页与索引页内存缓存池。默认仅 128MB，生产数据库专机务必调大至物理内存的 50% ~ 70%。
innodb_flush_log_at_trx_commit = 1
sync_binlog = 1		 俗称「双 1」安全配置（MySQL 8.0+ 默认已双双为 1）：每次事务提交都强制把 Redo Log 和 Binlog 刷入磁盘物理介质，保证主机断电零数据丢失。
max_connections 实例允许的最大并发连接数（默认 151，生产常设 1000 ~ 2000），需大于“应用实例数 × 单实例连接池上限”。
slow_query_log = ON
long_query_time = 0.5		 开启慢查询日志，记录超过 0.5 秒 的 SQL 供日常调优（见 05.4）。

背后的原理：开启「双 1」后每次提交都要刷盘，MySQL 靠什么机制避免高并发下磁盘 IOPS 崩溃？详见 《核心原理篇 · 06.2 组提交与双写缓冲》。

07.2 后端连接串与连接池配置规范

Go (go-sql-driver/mysql) 与 Java (JDBC) 标准生产连接串格式 
# 1. Go DSN 标准格式（必带 charset=utf8mb4、parseTime=true、loc 时区与三项网络超时）
app_rw:AppPass_2026#@tcp(db.internal:3306)/shop_db?charset=utf8mb4&parseTime=true&loc=Asia%2FShanghai&timeout=3s&readTimeout=5s&writeTimeout=5s

# 2. Java JDBC URL 标准格式（MySQL Connector/J 8.0+）
jdbc:mysql://db.internal:3306/shop_db?characterEncoding=utf8&serverTimezone=Asia/Shanghai&connectTimeout=3000&socketTimeout=5000&rewriteBatchedStatements=true
连接池 / 连接串关键项 推荐配置原则 为什么上线前必须核对这项
连接最大存活时间
（ConnMaxLifetime / maxLifetime）		 必须小于 MySQL 服务端的 wait_timeout（推荐设 3 ~ 5 分钟） MySQL 服务端或云负载均衡网关会自动掐断空闲超过阈值（常为 600 秒）的 TCP 连接。若应用连接池不提前主动回收，凌晨低峰期后第一个请求拿到半关闭死连接就会报 invalid connection / broken pipe。
单实例最大连接数
（SetMaxOpenConns / connectionLimit）		 单 Pod 常设 20 ~ 50（绝非越大越好） 如果 K8s 扩容到 40 个业务 Pod，每个 Pod 配 100 个连接，峰值 4000 个连接会直接击穿数据库的 max_connections 报 Too many connections，且过多并发线程争抢行锁反而拉低吞吐。
读写网络超时
（readTimeout / socketTimeout）		 显式设为 3s ~ 5s（跑批导出服务单独配） 默认无超时会导致数据库卡死或网络黑洞时，应用所有工作协程永久挂起无法快速失败熔断。
07.3 · 大表变更规范：Online DDL 三种算法（INSTANT / INPLACE / COPY）与防 MDL 锁表雪崩

07.3 Online DDL 大表改结构规范（适用 MySQL 8.0 / 8.4）

在千万行级的线上生产表上直接执行裸 ALTER TABLE，最怕两件事：一是触发全表锁写拷贝重建，二是被慢查询卡住触发 MDL（Metadata Lock，元数据锁）排队雪崩，几秒内把全站普通 SELECT 全部堵死。MySQL 8.0 提供了三种 DDL 算法，推荐在语句末尾显式声明 ALGORITHM（若不支持无锁算法会立即报错中止，不会静默退化锁表）：

DDL 算法等级 底层执行方式与耗时 典型支持的表变更操作 生产使用建议
1. INSTANT
（秒级瞬时完成）		 仅修改数据字典元数据，不碰任何 16KB 数据页，1 亿行表也在毫秒级完成 • 新增列（8.0.12 支持末尾加列，8.0.29+ 支持任意位置加列与秒级删列 DROP COLUMN）
• 修改列默认值、重命名列		 日常加字段首选。注意：含全文索引或 COMPRESSED 行格式的表不支持 INSTANT。
2. INPLACE
（原地构建，不拷表）		 直接在 InnoDB 引擎内部构建索引或原地重组，期间允许正常并发读写（LOCK=NONE） • 新增或删除二级索引（ADD INDEX / DROP INDEX）
• 扩展 VARCHAR 长度（未跨 255 字节长度头边界时）		 业务低峰期执行。建大表索引会吃磁盘 I/O，但不会阻塞线上增删改查。
3. COPY
（锁写拷贝重建）		 建临时新表逐行拷贝全表数据，期间阻塞所有并发写入（仅可读），空间翻倍且主从延迟剧增 • 修改列数据类型（如 INT 改 BIGINT）
• 修改表字符集（utf8mb3 改 utf8mb4）、改主键		 千万级大表严禁高峰期直跑，应使用开源工具 gh-ost 在线无锁影子表迁移。
safe_online_ddl.sql · 设短 MDL 锁超时 + 显式指定 ALGORITHM 的安全上线模板 
-- 【保命第一步】先把当前会话等 MDL 元数据锁的超时从默认 1 年缩短为 3 秒！
-- 万一表上正跑着未提交慢查询，3 秒拿不到锁就立刻主动放弃，绝不卡在队列里堵死后面的普通 SELECT
SET SESSION `lock_wait_timeout` = 3;

-- 1. 毫秒级新增列（强制要求走 INSTANT）
ALTER TABLE `orders`
  ADD COLUMN `source_channel` TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '下单渠道',
  ALGORITHM=INSTANT;

-- 2. 在线无锁新建联合索引（强制要求走 INPLACE 且不锁读写 LOCK=NONE）
ALTER TABLE `orders`
  ADD INDEX `idx_channel_created` (`source_channel`, `created_at`),
  ALGORITHM=INPLACE, LOCK=NONE;

背后的原理：为什么一条拿不到 MDL 写锁的 ALTER TABLE 会连后续只读的 SELECT 都全部堵死？详见 《核心原理篇 · 05.1 MDL 元数据锁排队机制》。

07.5 · 数据兜底防线：逻辑备份 vs 物理热备，以及 Binlog 按时间点恢复（PITR）

07.5 备份与恢复：逻辑/物理备份区别与按时间点恢复思路

主从复制防不了人为误删——你在主库手滑执行一条不带 WHERE 的 DELETE FROM orders，几毫秒后所有从库也会同步把表删空。真正能救命的是「定期全量备份 + 持续归档二进制日志（Binlog）」组成的 PITR（Point-In-Time Recovery，按任意时间点恢复） 体系：

备份方式 代表工具与底层原理 适用数据体量与速度 核心参数与注意事项
逻辑备份
（导出 SQL 文本）		 官方自带 mysqldump（或多线程 mydumper）：把库表数据查出来转成可读的 CREATE + INSERT 语句 适合 50 GB 以内中小型库；恢复时需逐条重跑 SQL 重建索引，大库恢复较慢 InnoDB 库必须加 --single-transaction（开启 RR 快照读，全程不锁业务读写）与 --source-data=2（在备份头部注释记下此刻的 Binlog 文件名与位点；8.0.26 前旧名为 --master-data=2）。
物理热备
（直接拷数据文件）		 Percona XtraBackup / MySQL Clone 插件 / 云 RDS 快照：直接拷贝底层 .ibd 16KB 数据页并附带备份期间产生的 Redo Log 适合 100 GB ~ 数 TB 大型生产库；直接还原磁盘文件，恢复速度比逻辑备份快一个数量级 导出产物是二进制表空间文件（跨大版本或只挑单表部分行不如逻辑备份直观），云数据库默认每日全备均采用物理快照。
pitr_workflow.sh · 误删数据后「凌晨全备 + 增量 Binlog」恢复到误删前一秒的 3 步实操 
# 【背景假设】凌晨 03:00 跑过全量备份（当时位点 binlog.000012 pos=157）；
#            下午 14:30:05 有人误删了 orders 表数据。注意：先在全新的临时库 restore_db 操作，别直接覆盖线上库！

# 第 1 步：把凌晨 03:00 的全量备份导入临时库（数据回到 03:00 状态）
mysql -u root -p restore_db < backup_0300.sql

# 第 2 步：解析查看 binlog，找到 14:30:05 那条误删事务开始前的精确位点（假设查出是 pos=98420）
mysqlbinlog --no-defaults --base64-output=DECODE-ROWS -vv \
  --start-datetime="2026-11-28 14:29:00" --stop-datetime="2026-11-28 14:31:00" \
  /var/lib/mysql/binlog.000012 | less

# 第 3 步：截取 [157, 98420) 之间的所有正常增量变更重放进临时库，核对无误后将表导回生产库
mysqlbinlog --no-defaults --start-position=157 --stop-position=98420 \
  /var/lib/mysql/binlog.000012 | mysql -u root -p restore_db

背后的原理：为什么 mysqldump --single-transaction 备份半小时期间别人照常改数据却不会乱？详见 《核心原理篇 · 04.1 MVCC 快照》 与 《06.1 Binlog ROW 格式》。

07.6 · 架构演进避坑：主从复制延迟导致「刚写完马上读到旧数据」与 4 种代码对策

07.6 主从复制与读写分离对代码的影响

线上生产库至少采用「一主一从 / 一主多从」架构：所有写操作（INSERT / UPDATE / DELETE）发往主库（Primary / Source），主库将变更写入 Binlog 异步传给从库（Replica）重放。为了分担主库读压力，团队常开启读写分离（写走主库、普通 SELECT 走从库）——但这会立刻给业务代码带来一个经典 Bug：主从同步存在几毫秒到几百毫秒（大事务时甚至数秒）的复制延迟，导致“刚写完主库马上读从库，读到的是还没同步过来的旧数据”（例如：用户刚付款成功跳回订单详情页，页面查从库仍显示“待支付”；刚发完评论刷新列表看不见自己的评论）。

工程解决策略 代码落地做法 适用场景与优缺点
1. 关键读强制走主库
（Force Primary，最常用）		 后端维护 primaryPool 与 replicaPool（或在 ORM 加 db.Clauses(dbresolver.Write) 注解）：登录校验、支付结果查询、扣款前查状态一律显式走主库 零外部依赖、100% 强一致。只把商品列表、历史报表、热门帖子这类“晚 1 秒更新无所谓”的高频只读接口放去从库即可。
2. 写后短时缓存路由标记 某买家执行写操作后，顺手在 Redis 写 SET master_read:u:1001 1 EX 3；接下来 3 秒内该买家的读请求检测到此标记自动走主库，过期后恢复走从库 适合对“自己刚改的资料自己立刻能看见（Read-Your-Writes）”要求高、但又不想把整个接口全切回主库的业务。
3. 写接口直接返回最新结果 创建订单/发表评论接口成功后，直接把组装好的新记录放在响应 JSON 里给前端局部渲染，别让前端收到成功后再立刻发第二个 GET 请求查从库 最省数据库查询次数，前后端配合改动极小。
4. 等待从库 GTID 位点追平 基于 GTID（Global Transaction Identifier，全局事务标识符）：读从库前调 SELECT WAIT_FOR_EXECUTED_GTID_SET('刚写完的GTID', 0.5)，若 0.5 秒内未追平则降级查主库 常封装在数据库代理中间件内部，对业务代码透明，但从库严重延迟时会增加接口等待耗时。

背后的原理：主从复制的 Dump / I/O / SQL 三个线程怎么配合，半同步复制能消除读延迟吗？详见 《核心原理篇 · 06.3 主从复制三线程与半同步》。

07.7 · 容量演进阶梯：索引与冷热归档 → 表分区 → 分库分表的触发边界与工程代价

07.7 数据量大了怎么办：演进四阶梯与分库分表的代价

很多开发者听说“单表别超 2000 万行”，表刚到几百万行就急着拆成 64 张分表，结果把简单的业务代码改得寸步难行。实际上，在现代 NVMe SSD 与充足内存下，必须严格按改造成本从低到高逐级推进，不到最后一刻绝不轻易分库分表：

演进阶梯（按先后顺序） 核心动作 能撑住的量级 优势与引入代价
第 1 步：索引调优与 SQL 治理 补齐联合/覆盖索引、改写深分页为游标、拆掉大字段附表（垂直拆列） 单表 2000 万 ~ 5000 万 行点查依然 1 ~ 3ms 零架构改造成本，立竿见影。
第 2 步：读写分离 + 缓存 + 冷热归档 热点读挡在 Redis + 只读从库；定时任务将 6 个月前已完结的历史订单分批迁入归档库或分析型数据库（ClickHouse） 90% 以上的中大型公司靠这一步就能长期平稳运行 在线交易热表永远保持在轻巧的一两千万行以内，主库只服务近期活跃订单。
第 3 步：原生表分区（Partition） 单机内对业务透明地把一张逻辑表按时间拆成多个物理 .ibd 分区文件（如按月 RANGE 分区） 亿级流水日志表按月滚动保留 清理整月过期日志只需 ALTER TABLE DROP PARTITION p202501（秒级删文件，远快于 DELETE）；但它仍在同一台机器上，不能突破单机磁盘写 IOPS（Input/Output Operations Per Second，每秒读写次数）与连接数上限。
第 4 步：水平分库分表（Sharding） 按分片键（如 buyer_id % 16）把数据物理分散到多个数据库实例的多张表（orders_00 .. orders_15） 在线活跃热数据单表破亿行，或单机写 TPS/连接数触及硬件天花板 能线性扩展写吞吐与总容量，但业务代码复杂度陡增（见下方四大代价）。
决定水平分库分表前，必须想清楚的 4 个真实代价：
1. 自增主键不能再用了：多张分表各自自增会撞号，必须改用全局趋势递增的分布式 ID（如 Snowflake 雪花算法 64 位整数）。
2. 非分片键查询变极难：订单按 buyer_id 取模分了 16 张表，买家查自己的单飞快；但商家后台按 shop_id 查单、客服按手机号查单不知道数据在哪张表，如果广播扫全部 16 张表会拖垮集群——必须用“基因法（把 buyer_id 尾号嵌进 order_no）”再加一套异构冗余表或同步到 Elasticsearch 查询。
3. 跨库 JOIN、分组统计与深分页失效：翻第 100 页需要向 16 张分表每张各拉取 100 × 20 = 2000 条回中间件内存归并排序。
4. 单机本地事务失效：跨两个分库的修改无法再用简单的 BEGIN ... COMMIT，只能改造成基于本地消息表 / Seata 的最终一致方案。

本章即时场景题（先想答案，再点击展开）

1. Go 服务上线后白天一切正常，但每天早上第一个访问接口的用户总会报一次 invalid connection 错误，可能是什么参数没配对？

应用连接池的 ConnMaxLifetime 设得比 MySQL 服务端的 wait_timeout（或云网关空闲断连时间）更长，甚至没设（默认无限复用）。经过一夜空闲，服务端早已主动关掉了空闲连接，早上第一个请求从池里摸出这条死连接发包就报错。将 SetConnMaxLifetime 设为 3 ~ 5 分钟 即可根治。

2. 用户刚完成实名认证（写主库），页面自动跳转去领新手礼包，礼包接口查从库却提示“您尚未实名认证”，最简单稳妥的改法是什么？

这是典型的主从异步复制延迟导致的写后读不一致。领礼包这种强依赖前置实名状态的写前校验查询，绝不能走只读从库，直接在代码中将该查询显式指定路由到主库连接池（Force Primary）即可 100% 读到刚刚提交的实名状态。

3. 为什么要给所有生产环境开启 Binlog（且格式设为 ROW）并配合每日全备，光靠主从实时同步防删库不行吗？

主从同步只能防“主库硬盘坏了或机器断电”这类硬件故障；一旦研发写错代码跑了不带 WHERE 的 UPDATE / DELETE 或误删表，这条破坏性语句会在一瞬间被忠实同步到所有从库。只有依靠「昨日全量备份 + 截停在误操作前一刻的增量 Binlog 重放（PITR）」，才能把数据救回来。
