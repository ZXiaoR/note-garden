02.1 · 标量类型与字符集：整型显示宽度误区、精确小数 DECIMAL、VARCHAR 与 utf8mb4 规范

02.1 数值类型、字符串类型与 utf8mb4 字符集

合理选择字段类型不仅能节省磁盘空间，还能让单个 16 KiB 数据页装下更多行记录，从而减少磁盘 I/O（Input/Output，输入输出）次数。以下是日常建表最核心的选型对照：

分类 推荐类型 占用字节与范围 选型原则与高频误区说明
自增主键 / 大整数 BIGINT UNSIGNED 固定 8 Bytes
（0 ~ 1.84×10¹⁹）		 业务核心表主键统一用 BIGINT UNSIGNED，避免业务增长突破 INT UNSIGNED 的 42.9 亿上限导致锁表改列。
常规整数 / 状态枚举 INT UNSIGNED
TINYINT UNSIGNED		 INT：4 Bytes
TINYINT：1 Byte (0~255)		 常见误区纠正：INT(1) 与 INT(11) 占用的存储空间和数值范围完全一模一样（都是 4 字节），括号里的数字仅是旧版零填充（ZEROFILL）显示宽度，MySQL 8.0.17+ 已正式废弃整数显示宽度。表示状态/性别请用 1 字节的 TINYINT。
精确金额 / 费率 DECIMAL(p, s)
（或以“分”为单位存 BIGINT）		 变长紧凑二进制编码（如 DECIMAL(12,2) 占 6 Bytes） p 为总有效位数，s 为小数位数。涉及资金严禁使用 FLOAT / DOUBLE（二进制浮点数存在 0.1 + 0.2 != 0.3 精度误差）。
定长与变长字符串 CHAR(N)
VARCHAR(N)		 括号内 N 代表最大字符个数（无论是英文还是中文汉字） • CHAR(N) 适合长度完全固定的字符串（如国家代码 CHAR(2)、MD5 哈希 CHAR(32)）；
• VARCHAR(N) 按实际字符字节数 + 1~2 字节长度头存储。虽然 VARCHAR(20) 与 VARCHAR(255) 存相同字符串在磁盘上占空间一样，但在内存排序和内部临时表分配时，过大的 N 会按最大宽度预留内存，因此应按需设定合理的 N。
长文本 TEXT / LONGTEXT 最多 64 KB / 4 GB（超长自动存入溢出页） 不能设置常规默认值（MySQL 8.0.13+ 支持用括号包裹的表达式默认值）。大文本字段若不常参与列表查询，建议拆分到附属详情表或避免 SELECT *。
字符集与排序规则（Collation）必知边界：
• 为什么绝不要在 MySQL 中写 CHARSET=utf8：MySQL 历史遗留的 utf8（在 8.0 中别名为 utf8mb3）是一个残缺实现，每个字符最多只支持 3 字节，一旦用户输入微信昵称中的 4 字节 Emoji 表情（如 😀）或生僻汉字就会直接报错 Incorrect string value: '\xF0\x9F...'。建库建表请始终使用完整的 4 字节 UTF-8 —— utf8mb4。
• 排序规则后缀含义：MySQL 8.0 默认的 utf8mb4_0900_ai_ci 中，ai 代表不区分重音（Accent Insensitive），ci 代表不区分大小写（Case Insensitive，即查询 WHERE code = 'abc' 会同时命中 'ABC'）。如果某列存储的是严格区分大小写的短链码、Token 或敏感标识符，应将该列显式声明为 COLLATE utf8mb4_0900_as_cs 或二进制比对 COLLATE utf8mb4_bin。
02.2 · 时间与半结构化类型：DATETIME vs TIMESTAMP 的时区边界、JSON 操作符与生成列索引

02.2 DATETIME vs TIMESTAMP 与 JSON 生成列实战

1. 时间日期选型：什么时候用 DATETIME，什么时候用 TIMESTAMP

对比维度 DATETIME（推荐作为业务通用默认） TIMESTAMP（存在 2038 年上限）
占用空间与范围 5 ~ 8 Bytes（含微秒精度）；范围 1000-01-01 ~ 9999-12-31 4 ~ 7 Bytes；范围仅到 1970-01-01 ~ 2038-01-19 03:14:07 UTC（32位秒数溢出）
时区转换行为 不随会话时区变化：按字面年月日时分秒原样存取（只要应用连接串统一指定了 loc=Asia/Shanghai，读写完全可预期）。 写入时将当前会话 time_zone 转换为 UTC 秒数存储，读取时再转回当前会话的 time_zone。
选型建议 绝大多数业务时间字段（创建时间、更新时间、生日、合同到期日、未来排期）首选 DATETIME，彻底规避 2038 年溢出问题。 仅在需要数据库层自动跨多国时区转换且生命周期确定在 2038 年前的场景使用。

2. 原生 JSON 类型、路径提取符号（-> 与 ->>）与生成列索引

MySQL 5.7.8+ 提供了原生二进制编码的 JSON（JavaScript Object Notation，轻量级数据交换格式） 数据类型（支持按路径快速跳读与局部更新，无需像存普通文本那样每次整串解析）。在 SQL 中访问 JSON 内部属性时，首次遇到的专用语法含义如下：

  • 列->'$.路径'（等价于 JSON_EXTRACT(列, '$.路径')）：提取指定路径的值，返回结果仍保持 JSON 格式（若提取的是字符串，外层会带有双引号，如 "vip"）。
  • 列->>'$.路径'（等价于 JSON_UNQUOTE(JSON_EXTRACT(...))）：提取指定路径的值并去掉外层 JSON 双引号，直接返回纯文本字符串（如 vip），在 WHERE 过滤与展示中最常用。
  • 如何给 JSON 内部字段建索引：MySQL 不允许直接对整个 JSON 列建立普通 B+ 树索引，标准做法是定义一个生成列（Generated Column，语法为 GENERATED ALWAYS AS (表达式) VIRTUAL），将需要检索的 JSON 子属性提取出来，然后直接在该生成列上建立普通二级索引（或使用 MySQL 8.0.17+ 的多值索引 CAST(... AS ... ARRAY)）：
json_generated_col.sql · JSON 操作符与虚拟生成列（VIRTUAL）索引实战 
CREATE TABLE `products` (
  `id`    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `title` VARCHAR(100)    NOT NULL,
  `specs` JSON            NOT NULL COMMENT '商品动态规格参数',
  -- 定义虚拟生成列 brand：平时不占磁盘空间，但可在其上直接建立 B+ 树索引
  `brand` VARCHAR(50) GENERATED ALWAYS AS (`specs`->>'$.brand') VIRTUAL,
  KEY `idx_specs_brand` (`brand`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 插入一条包含 JSON 对象的记录
INSERT INTO `products` (`title`, `specs`) VALUES
  ('机械键盘', '{"brand": "Keychron", "switch": "red", "wireless": true}');

-- 查询：无论直接查生成列 brand，还是写 specs->>'$.brand'，优化器都能自动命中 idx_specs_brand 索引
SELECT `id`, `title`, `specs`->>'$.switch' AS `switch_type`
FROM `products`
WHERE `specs`->>'$.brand' = 'Keychron';

-- 原地修改或新增 JSON 内部某个属性（使用 JSON_SET 函数）
UPDATE `products`
SET `specs` = JSON_SET(`specs`, '$.switch', 'brown', '$.stock', 50)
WHERE `id` = 1;
02.3 · 建表规范：五大完整性约束、自增主键 vs 随机 UUID、多表关系与外键取舍

02.3 表约束、主键选型与多表关系建模

1. 五大表完整性约束与主键选型准则

  • PRIMARY KEY（主键约束）：每张 InnoDB 表必须显式定义一个主键（非空且唯一）。强烈推荐使用单调递增的 BIGINT UNSIGNED AUTO_INCREMENT（或趋势递增的雪花算法 ID）作为物理主键，切勿使用随机无序的字符串 UUID（Universally Unique Identifier，通用唯一识别码） 作为聚簇索引主键——因为随机 UUID 会迫使每次新插入都随机落入历史数据页中间，触发频繁的 16KB 页分裂与大量的二级索引空间浪费（如需对外暴露字符串标识，可另建一列 biz_uuid CHAR(36) UNIQUE）。
  • UNIQUE KEY（唯一约束）：保证列或列组合值唯一。注意在 SQL 标准与 MySQL 中，UNIQUE 索引允许存入多个 NULL（因为 NULL 代表未知，不与任何值相等）。
  • NOT NULL 与 DEFAULT：尽量将字段定义为 NOT NULL 并赋予合理默认值（如空字符串 '' 或 0），不仅能避免 COUNT(col) 与算术运算中的 NULL 陷阱，还能省去行记录头中的 NULL 值位图开销。
  • CHECK (条件)（检查约束）：MySQL 8.0.16+ 起已完整支持并强制校验 CHECK 约束（如 CHECK (balance >= 0)；旧版 5.7 虽能写语法但会静默忽略）。

2. 1:1 / 1:N / M:N 关系建模与物理外键工程权衡

关系类型 建表落地方式与外键权衡
一对多（1:N）
如：用户 → 订单		 在“多”的一方（orders 表）添加 user_id BIGINT UNSIGNED NOT NULL，并在 user_id 上建立二级索引。
多对多（M:N）
如：用户 ↔ 角色		 建立独立的中间关联表 user_roles(id, user_id, role_id)，并建立联合唯一索引 UNIQUE KEY uk_user_role (user_id, role_id) 防重。
物理外键 vs 逻辑外键 • 内部管理系统 / 金融强一致核心小表：可使用 FOREIGN KEY 由数据库兜底引用完整性；
• 高并发互联网大表：通常不建物理 FOREIGN KEY 约束，而在应用层服务中保证逻辑外键一致性，原因包括：每次子表写入都需额外对父表记录加共享锁校验、级联删除不可控，以及未来做分库分表或 Online DDL 表迁移时会受外键阻碍。

02.5 日常建表「字段需求 → 选什么类型」速查表

常见业务字段需求 推荐建表写法 千万别选的反例 选型理由与工程避坑说明
表物理主键 ID BIGINT UNSIGNED NOT NULL AUTO_INCREMENT 随机 VARCHAR(36) UUID 或过小的 INT 顺序追加写不触发页分裂，8 字节定长使二级索引最小；分库分表场景可存有序雪花算法 BIGINT。
商品价格 / 钱包金额 DECIMAL(12, 2) NOT NULL DEFAULT 0.00
（或以“分”为单位存 BIGINT）		 FLOAT / DOUBLE 二进制浮点数算 0.1 + 0.2 会有精度尾差导致财务对账差一分钱；DECIMAL 按十进制精确存储。
手机号 / 订单号 / 邮编 VARCHAR(20) NOT NULL DEFAULT ''
（纯定长哈希如 MD5 用 CHAR(32)）		 用 BIGINT 存手机号 手机号、邮编不是用来加减乘除的数值，可能带国际区号 +86 或前导 0，且支持前缀匹配检索。
订单状态 / 开关枚举 TINYINT UNSIGNED NOT NULL DEFAULT 1
（务必在 COMMENT 写清每个数字含义）		 ENUM('unpaid', ...) 或 INT(1) TINYINT 仅占 1 字节；ENUM 修改删除枚举项或中间插入项可能触发锁表重建，且排序默认按内部序号而非字母序易踩坑。
创建时间 / 业务时间 DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
（需毫秒/微秒写 DATETIME(3)）		 TIMESTAMP（有 2038 年溢出上限）或存字符串 DATETIME 范围到 9999 年，配合连接串固定时区读写直观；高并发流水排序建议用微秒精度 DATETIME(3)。
商品动态规格 / 扩展属性 JSON NOT NULL（高频筛选键配 VIRTUAL 生成列索引） 往主表塞 30 个稀疏 ext1..ext30 列，或存纯 TEXT 原生 JSON 校验合法性并支持 JSON_SET 局部修改，无需每新增一个品类属性就跑一次 ALTER TABLE。
帖子长正文 / 富文本详情 拆分到独立详情表 post_contents(post_id, body MEDIUMTEXT) 直接塞在高频列表扫描的主表里并跑 SELECT * TEXT 最大 64KB（超长选 MEDIUMTEXT 16MB）；冷热分离让主表列表查询保持极高缓冲池命中率。

本章即时场景题（先想答案，再点击展开）

1. 同事建表写 status INT(1) NOT NULL 和 user_id INT(11) NOT NULL，认为 INT(1) 只占 1 字节、只能存 1 位数，这个理解对吗？

完全不对。INT 后面的括号数字仅代表早年配合 ZEROFILL 补零时的“显示宽度”，INT(1) 和 INT(11) 在磁盘上都固定占 4 字节，都能存到 21 亿（MySQL 8.0.17+ 已废弃该写法）。想只占 1 字节存状态，必须用 TINYINT UNSIGNED。

2. 社区评论表上线后，用户发了一条带 😂 表情的评论，接口立刻报错 Incorrect string value: '\xF0\x9F\x98\x82...'，是什么原因？

建表或连接串误用了 MySQL 历史遗留的 utf8（即 utf8mb3，单字符最多 3 字节），而 Emoji 表情属于 4 字节 UTF-8 编码。把数据库、表、列以及客户端连接串的字符集统一改为 utf8mb4 即可正常存储。

3. 房产长租合同表有一列 expire_at（合同到期时间，有的签 15 年到 2041 年），如果建成 TIMESTAMP 会出什么问题？

写入 2041 年会直接越界报错。TIMESTAMP 底层存的是 32 位有符号秒数，最大只能表示到 2038-01-19 03:14:07 UTC。凡是涉及未来排期、长期合同或历史生日的业务时间字段，应一律使用上限到 9999 年的 DATETIME。

背后的原理：想了解变长 VARCHAR 与超长 TEXT/JSON 行溢出页在磁盘上的真实字节结构，以及随机 UUID 引发页分裂的底层过程，可按需查阅 《 核心原理篇 · 00.3 行记录格式》 与 《02.2 页分裂与原子 DDL》。
