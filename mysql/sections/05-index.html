05.1 · 索引分类与语法：聚簇/唯一/联合/前缀索引，以及 MySQL 8.0 函数索引与不可见索引

05.1 InnoDB 常见索引类型与创建管理语法

在 InnoDB 中，一张表的数据和索引本质上是一棵或多棵 B+ 树。理解索引调优最关键的一步，是先看清「主键聚簇索引树」和「普通二级索引树」的叶子节点里到底存了什么——搞懂了这两棵树的长相，回表（Bookmark Lookup）与覆盖索引（Covering Index）一眼就能看明白：

create_indexes.sql · 6 类常用索引创建与灰度停用语法 
-- 1. 唯一索引（保证手机号全局不重复）
ALTER TABLE `users` ADD UNIQUE KEY `uk_phone` (`phone`);

-- 2. 联合索引（多列组合排序：先按 city 排，同城按 age 排，同龄按 name 排）
CREATE INDEX `idx_city_age_name` ON `users` (`city`, `age`, `name`);

-- 3. 前缀索引（针对较长的 VARCHAR 列，仅取前 16 个字符建索引以大幅节省空间）
-- 可先用 SELECT COUNT(DISTINCT LEFT(email, 16)) / COUNT(*) FROM users; 评估区分度
CREATE INDEX `idx_email_prefix` ON `users` (`email`(16));

-- 4. 降序索引（MySQL 8.0+ 真正支持按 DESC 物理降序存储，优化 ORDER BY a ASC, b DESC）
CREATE INDEX `idx_city_created_desc` ON `users` (`city` ASC, `created_at` DESC);

-- 5. 函数/表达式索引（MySQL 8.0.13+ 支持，注意表达式外层必须多套一层双括号）
CREATE INDEX `idx_created_month` ON `orders` ((DATE_FORMAT(`created_at`, '%Y-%m')));

-- 6. 不可见索引（MySQL 8.0+ 删索引前的安全灰度开关：隐藏后优化器不再使用它，
-- 若观察线上慢查询暴增，可瞬间切回 VISIBLE 恢复，避免删错索引后耗时数小时重建）
ALTER TABLE `users` ALTER INDEX `idx_city_age` INVISIBLE;
ALTER TABLE `users` ALTER INDEX `idx_city_age` VISIBLE;

对照上图：三句话分清两棵树、回表与覆盖索引

  • 两棵树的叶子页存的不一样：右边的聚簇索引（主键索引 PRIMARY）就是表本身，叶子节点存着包含 name、balance 在内的完整一行数据；而你新建的二级索引（如左树 idx_city_age）为了省空间，叶子节点只抄录了索引列 (city, age) 和对应的主键 id。
  • 路径 ① 什么是回表（为什么慎写 SELECT *）：执行 SELECT * FROM users WHERE city = '杭州' 时，左树查到 '杭州' 后只知道它的主键 id = 8，拿不到余额 balance，于是必须拿着 id = 8 跨到右边主键树里再从根搜一次把整行捞出来——命中 1000 行就要回表查 1000 次主键树。
  • 路径 ② 什么是覆盖索引：如果把 SQL 改成只查需要的列 SELECT id, city, age FROM users WHERE city = '杭州'，左树叶子页里这 3 列全齐了，根本不用碰右边的主键树就直接返回，EXPLAIN 的 Extra 列会出现代表高性能的 Using index。
05.2 · 最左前缀与失效排查：联合索引 (a, b, c) 匹配规则与 7 类索引失效改写对照

05.2 联合索引最左前缀原则与 7 类常见索引失效改写

以联合索引 idx_abc (a, b, c) 为例：B+ 树会先按 a 升序排列；只有当 a 相同时，b 才是有序的；只有当 a 和 b 都相同时，c 才是有序的。这就决定了检索时必须从最左边的列 a 开始连续匹配（注：WHERE b = 2 AND a = 1 把顺序颠倒写没有关系，优化器会自动重排为 a = 1 AND b = 2 命中索引）：

常见索引失效或退化场景 错误 / 低效 SQL 写法 底层失效原因与高效改写方案
1. 违背最左前缀（跳过首列） WHERE b = 2 AND c = 3 缺少首列 a，b 在全局上是乱序的，无法做 B+ 树二分定位。
改写：补充首列条件，或为高频单独查询的 b 建立以 b 开头的索引。
2. 范围查询（> / < / BETWEEN）后的列无法继续做树搜索定位 WHERE a = 1 AND b > 10 AND c = 3 在满足 a = 1 AND b > 10 的区间内，c 是无序的，因此 c = 3 无法用于缩小 B+ 树扫描起始边界。
改写：设计联合索引时遵循“等值列放左边，范围列放右边”，将索引建为 (a, c, b)；注：即便索引是 (a, b, c)，MySQL 5.6+ 的索引条件下推（ICP，Index Condition Pushdown，即 Using index condition）依然能在索引层直接用 c = 3 过滤掉不满足的记录，避免无效回表。
3. 对索引列做函数或算术运算 WHERE DATE(created_at) = '2026-11-15'
WHERE amount + 10 = 100		 B+ 树里存的是列原始值而非函数计算后的结果。
改写：改为等价范围条件 WHERE created_at >= '2026-11-15 00:00:00' AND created_at < '2026-11-16 00:00:00'，以及 WHERE amount = 90。
4. 隐式类型转换（字符串列传数字） phone 列为 VARCHAR(20)，但写成了：
WHERE phone = 13800138000（未加单引号）		 MySQL 比较字符串与数字时，会把字符串转换为浮点数，相当于对索引列套了函数 WHERE CAST(phone AS DOUBLE) = 13800138000，导致全表扫描。
改写：严格保证传入参数类型与列定义一致：WHERE phone = '13800138000'。
5. 两表关联字符集或排序规则不一致 左表 utf8mb4_0900_ai_ci 关联右表 utf8mb4_general_ci 被驱动表关联列被迫执行隐式字符集转换 CONVERT() 导致索引失效。
改写：全库统一使用 utf8mb4 与相同的 COLLATE。
6. 前导通配符模糊匹配 WHERE name LIKE '%小林%' 百分比号在最左侧无法利用字典序前缀定位（LIKE '小林%' 右通配可以正常走 range 索引）。
改写：改用前缀匹配、覆盖索引扫描，或接入全文索引 / Elasticsearch。
7. OR 连接了未建索引的列 WHERE id = 1 OR age = 25（age 无单列索引） 只要 OR 一侧没有索引就必须全表扫描，导致另一侧有索引也白费。
改写：为两侧列都建索引（触发 index_merge）或改写为 UNION ALL。
05.3 · 执行计划诊断：EXPLAIN 核心列（type / key_len / Extra）与 EXPLAIN ANALYZE 实测解读

05.3 EXPLAIN 核心字段速查与慢查询调优

拿到一条慢 SQL 时，第一步是在语句前加上 EXPLAIN（只输出优化器估算计划，不真正执行 SQL）或 MySQL 8.0.18+ 的 EXPLAIN ANALYZE（真正执行 SQL 并输出每个迭代器节点的实测毫秒耗时与实际循环行数）：

explain_demo.sql · 使用 EXPLAIN 与 EXPLAIN ANALYZE 检验索引命中情况 
-- 1. 查看传统表格形式的优化器执行计划
EXPLAIN SELECT `id`, `city`, `age`
FROM `users`
WHERE `city` = '杭州' AND `age` >= 20
ORDER BY `age` ASC LIMIT 20;

-- 2. MySQL 8.0.18+ 树状实测分析（查看 estimated cost vs actual time & rows）
EXPLAIN ANALYZE SELECT `id`, `name`, `balance`
FROM `users`
WHERE `city` = '杭州' AND `age` >= 20;
EXPLAIN 列名 关键取值（从优到劣或常见信号） 判读准则与调优动作
type
（访问类型）		 system > const > eq_ref > ref > range > index > ALL • const / eq_ref：主键或唯一索引等值点查 / 主键关联，最多命中 1 行，性能极佳；
• ref：非唯一普通索引等值查找；range：索引范围扫描（> / < / IN / BETWEEN）；
• index：遍历整棵二级索引树（全索引扫描）；ALL：全表扫描（大表出现 ALL 需重点优化）。
key 与 key_len 实际选中的索引名与使用的索引字节数 通过 key_len 可以精确判断联合索引到底用到了前几列：
• 计算规则：utf8mb4 下每个字符占 4 字节；VARCHAR(N) 额外加 2 字节变长头；若该列允许为 NULL 则再额外加 1 字节。
• 例如示例表 users 中 city VARCHAR(50) NOT NULL（50×4+2 = 202）+ age TINYINT NOT NULL（1），若 key_len = 203 说明 (city, age) 两列全用上了；若 key_len = 202 说明只用到了首列 city。
rows / filtered 估算需扫描的行数 / 过滤后剩余比例 若 rows 极大且与实际数据分布严重不符，可执行 ANALYZE TABLE users; 刷新索引统计信息。

（附加执行信号）		 • Using index（好）
• Using index condition（好）

05.4 · 慢日志排查闭环：慢查询日志开启配置、日志字段判读与 mysqldumpslow 汇总定位

05.4 慢查询日志怎么开，怎么从中找到最该优化的 SQL

线上几十个接口共成百上千条 SQL，我们怎么知道哪条 SQL 慢？答案是开启 MySQL 自带的慢查询日志（Slow Query Log）——只要某条语句执行耗时超过设定阈值（如 0.5 秒），MySQL 就会自动把这条 SQL、耗时、锁等待时间和扫描行数写进日志文件：

slow_log_setup.sql · 在线临时开启与 my.cnf 永久开启配置（8.0 / 8.4） 
-- ========= 1. 在线动态开启（立即对新建连接生效，无需重启实例） =========
SET GLOBAL `slow_query_log` = 'ON';
SET GLOBAL `long_query_time` = 0.5;  -- 执行超过 0.5 秒（500ms）即记入慢日志
-- 查看当前慢日志开关状态与日志文件的磁盘绝对路径：
SHOW VARIABLES LIKE '%slow_query_log%';

# ========= 2. 写入 my.cnf [mysqld] 段永久生效（防实例重启丢失） =========
# slow_query_log      = ON
# slow_query_log_file = /var/lib/mysql/mysql-slow.log
# long_query_time     = 0.5
# log_output          = FILE

# ========= 3. 在宿主机终端用官方 mysqldumpslow 聚合排名 =========
# -s t 按总耗时(Total Time)降序，-t 10 取前 10 类慢 SQL 模板：
mysqldumpslow -s t -t 10 /var/lib/mysql/mysql-slow.log
# -s c 按出现总次数(Count)降序（抓出单次 600ms 但每分钟跑几千次的高频慢查）：
mysqldumpslow -s c -t 10 /var/lib/mysql/mysql-slow.log
一眼读懂慢日志条目里的 4 个关键数字
# Query_time: 1.842105  Lock_time: 0.000112
# Rows_sent: 20         Rows_examined: 920450
SELECT * FROM orders WHERE phone = 13800138000 LIMIT 20;
  • 看 Lock_time 区分“锁等待”还是“真查得慢”：若 Query_time = 3.2s 且 Lock_time = 3.19s，说明 SQL 本身不慢，是被别的长事务锁住了（转去 07.4 排查锁阻塞）。
  • 看 Rows_examined vs Rows_sent 抓缺索引：像上面只返回 20 行给客户端，引擎却扫描了 92 万 行，说明索引没建或发生了隐式类型转换失效——把这条 SQL 拿去跑 EXPLAIN 即可精准修复。
  • 慎开 log_queries_not_using_indexes：该参数会把几百行小配置表的毫秒级全表扫描也全记进来刷爆磁盘，日常排障只按耗时阈值过滤即可（云数据库 RDS 直接在控制台「慢日志明细」查看同样指标）。
05.5 · 应用层高频性能坑：ORM 的 N+1 循环查询成因与 IN 批量预加载改写

05.5 ORM 的 N+1 查询问题与批量查询改写

有时候慢查询日志里一条慢 SQL 都没有（每条 SQL 都走了主键索引，耗时不到 1ms），但订单列表接口响应却要 300ms 甚至把数据库连接池打满。最常见的原因就是后端使用 ORM（Object-Relational Mapping，对象关系映射，如 Go 的 GORM、Node.js 的 Prisma / TypeORM） 或手写循环时踩中了 N+1 查询陷阱：

以“查询某买家的 20 条社区帖子，并附上每条帖子的作者昵称与头像”为例：先发 1 条 SQL 查出 20 条帖子，随后在 for 循环里遍历这 20 条帖子，每圈发 1 条 SQL 去查对应作者，总共发出了 1 + 20 = 21 次跨网络数据库查询（若翻页查 100 条就是 101 次网络往返）。改写思路非常直接——把循环里的单点查询收集起来，合并成 1 条 WHERE id IN (...) 批量查询，在内存 Map 里组装，让总 SQL 数永远固定为 2 条：

反例 vs 正例 SQL 轨迹与 Node.js 批量组装写法 
// ❌ 反例（N+1 查询）：查 20 条帖子触发 1 + 20 = 21 次网络往返
const [posts] = await pool.execute('SELECT id, title, author_id FROM posts LIMIT 20');
for (const post of posts) {
  // 循环内 await 查库：网络 RTT 被串行放大 20 倍！
  const [u] = await pool.execute('SELECT id, name FROM users WHERE id = ?', [post.author_id]);
  post.authorName = u[0]?.name ?? '匿名';
}

// ✅ 正例（两步批量预加载，恒定 2 条 SQL）：
// 第 1 步：查出 20 条帖子（1 次 SQL）
const [postList] = await pool.execute(
  'SELECT id, title, author_id FROM posts ORDER BY id DESC LIMIT 20'
);
// 第 2 步：提取去重后的 author_id 列表，用一条 WHERE id IN (...) 批量查回（1 次 SQL）
const authorIds = [...new Set(postList.map(p => p.author_id))];
if (authorIds.length > 0) {
  const placeholders = authorIds.map(() => '?').join(',');
  const [users] = await pool.execute(
    `SELECT id, name FROM users WHERE id IN (${placeholders})`,
    authorIds
  );
  const userMap = new Map(users.map(u => [u.id, u.name]));
  for (const p of postList) p.authorName = userMap.get(p.author_id) ?? '匿名';
}
Go (GORM Preload) 预加载与工程使用边界

//   注意单次 IN (...) 元素个数建议控制在 500 个以内（超长拆批）。

本章即时场景题（先想答案，再点击展开）

1. 订单表有联合索引 idx_shop_status_time (shop_id, status, created_at)，查询 WHERE shop_id = 88 AND created_at >= '2026-11-01' AND status = 2 能把三列索引都用上吗？

能全部用上。SQL 里 WHERE 子句中三个 AND 条件的书写先后顺序不影响索引匹配——MySQL 优化器会自动重排为 shop_id = 88 AND status = 2 AND created_at >= '2026-11-01'，恰好符合“前两列等值精确匹配 + 第三列范围扫描”的最左前缀最佳形态。

2. 用户表 phone VARCHAR(20) 上建了唯一索引 uk_phone，但线上慢日志里却抓到 SELECT id FROM users WHERE phone = 13800138000 扫描了 200 万行，为什么？

触发了隐式类型转换导致索引失效。phone 列是字符串类型，传入未加引号的数字 13800138000 时，MySQL 规则是将字符串转为数字再比较（等价于在索引列上套了函数 CAST(phone AS DOUBLE) = 13800138000），无法利用字典序 B+ 树定位，只能全表逐行转换比对。传入字符串参数 '13800138000' 即可恢复毫秒级点查。

3. 发现表上有一个几年前建的老索引疑似没人用了，想删掉省磁盘和写开销，但又怕某个冷门定时任务还在用它，怎么安全操作？

利用 MySQL 8.0+ 的不可见索引（Invisible Index）做灰度下线：先执行 ALTER TABLE orders ALTER INDEX idx_old INVISIBLE;，观察几天慢查询日志；若一切平稳再真正 DROP INDEX，万一发现某报表变慢，执行一条 VISIBLE 就能在一毫秒内立刻恢复，省去大表耗时几十分钟重建索引的风险。

背后的原理：想定量推导为什么 3 层 B+ 树能装下两千万行数据，以及加锁查询在唯一索引与普通索引上的锁范围差异，可按需查阅 《 核心原理篇 · 02 B+ 树阶数推导》 与 《05 锁机制与退化规则》。
