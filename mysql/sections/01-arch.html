🏛️ 01.1 · 体系结构：实例逻辑层次（Database ≡ Schema）与 Server 层 / InnoDB 引擎层两层协作

🏛️ 01.1 实例逻辑层次与一条 SQL 的两层执行链路

首先厘清一个经常与其他数据库混淆的术语：在 MySQL 中，Database 与 Schema 是完全同义词（执行 CREATE SCHEMA app_db; 与 CREATE DATABASE app_db; 效果完全相同），因此 MySQL 的逻辑目录是三层结构：实例（MySQL Instance）→ 数据库（Database / Schema）→ 数据表（Table）。在同一个 MySQL 实例下，只要当前账号拥有权限，就可以直接在一条 SQL 中通过 库名.表名（如 SELECT * FROM auth_db.users JOIN order_db.orders ...）跨库关联查询。

当客户端发出一句 SQL 时，请求在 MySQL 内部会依次穿过 Server 层（负责连接管理、词法/语法解析、成本优化与执行器调度，维护归档日志 binlog） 与 存储引擎层（默认 InnoDB，负责真正的内存缓冲池读写、B+ 树索引查找、行锁与 redo / undo 事务日志）：

📌 架构分工核心要点：
1. 为什么区分 Server 层与引擎层日志：binlog（二进制归档日志）位于 Server 层，任何存储引擎都可以使用它做主从复制与时间点恢复；而 redo log（重做日志）与 undo log（回滚日志）是 InnoDB 引擎专有的，用于实现 WAL 崩溃恢复与 MVCC 多版本读。
2. 为什么 MySQL 8.0 彻底删掉了旧的 Query Cache：旧版 Query Cache 以“SQL 文本哈希 → 结果集”缓存，但只要某张表发生任何一次 INSERT / UPDATE / DELETE，该表关联的所有 Query Cache 条目就会全部清空失效，高并发读写下反而成为严重的全局锁瓶颈。注意：删除 Query Cache 并不影响 InnoDB 的 Buffer Pool（缓存 16KB 数据页），后者始终是 MySQL 高性能的核心。
🔐 01.2 · 权限管理：MySQL 8.0 账号身份（'user'@'host'）、两步法授权与最小权限规范

🔐 01.2 账号创建與最小权限控制（RBAC）

在 MySQL 中，一个账号的完整唯一标识由 '用户名'@'允许连接的客户端主机地址' 共同组成（例如 'app_rw'@'10.0.%' 与 'app_rw'@'localhost' 在数据库内部是两个完全独立的账号）。在 MySQL 8.0+ 中，不再允许使用一条 GRANT ... IDENTIFIED BY 隐式创建用户，必须严格分两步执行：先 CREATE USER，再 GRANT 授权：

🛡️ 生产环境标准账号创建与最小权限授权脚本 
-- 1. 创建业务读写账号（仅允许内网 10.0.x.x 网段连接，禁止直接使用 root）
CREATE USER 'app_rw'@'10.0.%' IDENTIFIED BY 'AppPass_2026#';

-- 2. 授予 mydb 库下所有表的增删改查权限（不授予 DROP / GRANT OPTION）
GRANT SELECT, INSERT, UPDATE, DELETE ON `mydb`.* TO 'app_rw'@'10.0.%';

-- 3. 创建只读报表账号（仅供数据分析服务连接从库查询）
CREATE USER 'bi_ro'@'10.0.%' IDENTIFIED BY 'ReadOnly_2026#';
GRANT SELECT ON `mydb`.* TO 'bi_ro'@'10.0.%';

-- 4. 查看某账号拥有的权限与回收特定权限
SHOW GRANTS FOR 'app_rw'@'10.0.%';
REVOKE DELETE ON `mydb`.* FROM 'app_rw'@'10.0.%';

⚙️ 主机匹配符与核心服务端配置（my.cnf）

配置项 / 概念 工程含义与生产推荐值
'user'@'localhost' vs 'user'@'%' 'localhost' 仅允许本机连接；'%' 允许任意远程 IP 连接；生产环境推荐限定为内网子网段如 '10.0.%' 或 '172.16.%'。
bind-address 在 my.cnf 中默认为 127.0.0.1（仅监听本机）；若需其他机器连接，需改为内网网卡 IP 或 0.0.0.0。
innodb_buffer_pool_size InnoDB 数据与索引页缓存大小。默认仅 128MB，生产专机必须显式调大至物理内存的 50% ~ 70%。
slow_query_log = ON
long_query_time = 1		 开启慢查询日志，并将慢查询阈值设为 1 秒（或 0.5 秒），记录所有超时 SQL 以便用 EXPLAIN 调优。
🔌 01.3 · 连接管理：后端标准连接串参数（时区、字符集、超时）与连接池防断连配置

🔌 01.3 后端连接串参数与连接池配置规范

在 Go、Java（JDBC / HikariCP）、Node.js 或 Python 中连接 MySQL 时，连接串中的查询参数直接决定了字符集编码、时间戳解析时区以及网络超时行为：

🔗 Go (go-sql-driver/mysql) 与 Java (JDBC) 标准生产连接串格式 
# 1. Go DSN 标准格式（必加 parseTime=true 与 loc=Asia%2FShanghai，否则 DATETIME 读写相差 8 小时）
app_rw:AppPass_2026#@tcp(db.internal:3306)/mydb?charset=utf8mb4&parseTime=true&loc=Asia%2FShanghai&timeout=3s&readTimeout=5s&writeTimeout=5s

# 2. Java JDBC URL 标准格式（MySQL Connector/J 8.0+）
jdbc:mysql://db.internal:3306/mydb?characterEncoding=utf8&serverTimezone=Asia/Shanghai&connectTimeout=3000&socketTimeout=5000&rewriteBatchedStatements=true
连接池 / 连接串关键项 推荐配置原则 为什么必须这样配
时区参数（loc / serverTimezone） 统一显式指定为 Asia/Shanghai（或全链路 UTC） 若不指定，Go 的 go-sql-driver 默认按 UTC 解析 DATETIME，会导致写入和读出的时间与北京时间偏差 8 小时。
连接最大存活时间（ConnMaxLifetime / maxLifetime） 必须小于 MySQL 服务端的 wait_timeout（建议设为 3 ~ 10 分钟） MySQL 服务端会自动主动断开空闲超过 wait_timeout（默认 8 小时，云数据库或 SLB 网关常设为 600 秒）的连接。若应用连接池不主动提前轮换回收，取到被服务端半关闭的死连接就会报 invalid connection / broken pipe。
批量重写参数（rewriteBatchedStatements=true） JDBC 批量写入开启为 true 开启后驱动会自动把多条单行 INSERT INTO t VALUES (?) 合并改写为一条多值 INSERT INTO t VALUES (?), (?), (?) 发送，批量写入吞吐量可提升 5~10 倍。
