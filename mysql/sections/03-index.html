❓ 03.1 · “建了索引”与“高效使用索引”，差在哪里？

🔑 03.1 聚簇索引、二级索引与回表

结构 叶子保存什么 在 users 表中
聚簇索引 行记录本身，包含用户列与事务相关信息；大字段可能存到页外 按主键 id 组织
二级索引 索引列与主键值 (city, age) 以及 id

按 city 查 name：先在二级索引中找主键 id，再去聚簇索引取 name，后一步叫回表。如果只取 id, city, age，所需列都在二级索引中，就是覆盖索引，通常可以减少回表。

二级索引 idx_city_age (杭州·20 → 拿到主键 id=1) ──回表查聚簇索引──▶ 主键索引 PRIMARY (id=1 → 拿到完整行：小林 / 余额 100)

每张 InnoDB 表只有一个聚簇索引。没有显式主键时，引擎会选第一个所有列都 NOT NULL 的唯一索引；还没有，才生成隐藏行 ID。显式使用较短、稳定的主键，通常也能减少二级索引的空间成本。

📐 联合索引：先按 city 排，再按 age 排

idx_city_age(city, age) 是一棵树。它按组合键排序：同一城市内，年龄再有序。最左前缀说的是索引列的顺序，不是 WHERE 条件的书写顺序。

条件 常规访问方式 为什么
city='杭州' 可按 city 定位 提供了最左列
city='杭州' AND age=20 可按组合键定位 两列连续使用；AND 顺序可交换
city='杭州' AND age>=20 定位城市内的年龄范围 先等值，再范围
age=20 通常无法按最左前缀定位 年龄跨城市不全局有序；仍可能扫描索引或采用 Skip Scan
❓ 03.2 · 范围查询后的列真的“全部失效”吗？什么是索引下推 ICP？

🔬 03.2 范围后的列、索引下推 ICP 与“索引失效”拆解

⚠️ 把“后面的列全部失效”改为准确表述：在 (a,b,c) 中，a=1 AND b>2 AND c=3 通常由 a、b 构造扫描范围；c 仍可能用于索引上的过滤或覆盖查询。“不能继续缩小扫描区间”不等于“这个列没有用”。官方：范围访问 ↗

⚡ 索引下推 ICP：先过滤，再决定是否回表

假设另有索引 (name, age)，查询 name LIKE '小%' AND age=20 并返回 balance。引擎可以在索引记录上先检查可下推的 age 条件，只为通过过滤的记录取完整行。覆盖索引是尽量不取行；ICP 是减少取行次数。（计划中的 Using index condition 是识别信号。）

🔍 进阶 · 索引的成本与边界（自增空洞 & 覆盖索引可见性）

增加索引会占空间，并增加 INSERT、UPDATE、DELETE 的维护开销。自增主键通常让写入位置更集中，但仍可能发生页分裂、热点竞争和自增空洞。自增值不保证连续，也不能作为事务提交顺序。

覆盖索引是查询与索引之间的关系，不是一种独立的索引类型。即使计划显示覆盖，在需要判断 MVCC 可见性等情况下，InnoDB 仍可能访问聚簇记录；“永远零回表”过于绝对。

🛠️ “索引失效”要拆成两个问题

一是能不能形成高效的搜索范围，二是优化器认为值不值得用。即使可以搜索，返回大部分行并反复回表，也可能比全表扫描更贵。

写法 / 场景 准确理解 处理思路
YEAR(created_at)=2026 普通索引通常不能直接支持函数条件的范围搜索 改为 created_at >= '2026-01-01' AND created_at < '2027-01-01'；或评估函数索引
字符串列与数字比较 隐式类型转换可能使原索引顺序无法用于定位 参数类型与列类型一致
LIKE '%关键词' 没有固定前缀，普通 B+ 树难以进行前缀范围定位 按检索语义评估全文索引或搜索服务
!=、IS NULL、OR 不是“一出现就失效”；可能采用范围访问、Index Merge 等 看选择性、统计信息和实际执行计划
❓ 03.3 · 如何判断 SQL 慢在扫描、回表，还是排序？

🔎 03.3 用 EXPLAIN 与 EXPLAIN ANALYZE 验证想法

🔬 explain_verify.sql · 查看计划与实测开销 
EXPLAIN SELECT id, city, age
FROM users
WHERE city = '杭州' AND age >= 20
ORDER BY age LIMIT 20;

-- MySQL 8.0.18+：真正执行查询，查看实际耗时、行数和循环次数
EXPLAIN ANALYZE SELECT id, city, age
FROM users
WHERE city = '杭州' AND age >= 20
ORDER BY age LIMIT 20;

注：起步示例只有三行，优化器选择全表扫描也可能合理。EXPLAIN ANALYZE 会真正执行语句并产生负载；先理解查询范围，再用于验证。

📋 一个可重复的 4 步优化顺序

  1. 明确返回结果与数据规模，先排除查多了、漏条件等问题。
  2. 查看计划和实际耗时：读了多少行，返回多少行，哪些节点循环很多次。
  3. 根据过滤、排序、连接方式设计索引；尽量减少无效扫描和不必要的取列。
  4. 比较改动前后结果与耗时，同时考虑新增索引的写入成本。估算明显失真时再检查统计信息。
字段 / 信号 应该读出什么
type const 常见于主键/非空唯一键常量查找；ref 为非唯一等值访问；range 为范围；index 为全索引扫描；ALL 为全表扫描。不能只按这个字段给 SQL 打分
possible_keys / key 可能使用的查找索引 / 实际选择的索引；出现 key 不代表扫描少
key_len 使用的键长度，可辅助分析联合索引用到了哪一段；不等于索引记录总大小
rows / filtered 估算检查行数 / 过滤后保留百分比，不是实测值
Using index 覆盖访问信号；结合查询列与引擎行为理解
Using index condition 使用了索引条件下推（ICP）
Using filesort 需要额外排序，可能在内存中完成，不一定写磁盘
Using temporary 使用内部临时表，不代表一定发生磁盘临时表
🔍 进阶 · JOIN（Hash Join 版本差异）、filesort 与深分页

JOIN：索引嵌套循环可对外层每行到内层做索引查找。Hash Join 构建哈希结构再探测，适合部分缺少可用连接索引的场景。8.0.18 引入 Hash Join；8.0.20 起旧 BNL 不再使用。不要把 Using join buffer 一律解释成 BNL，也不要只凭表的总行数强制“小表驱动大表”，应看过滤后规模和计划。官方：Hash Join ↗

排序：filesort 可携带要返回的字段，也可能排序键与行定位信息后再取行。实现和选择条件随版本变化，不把旧版本的单个阈值当作 8.0/8.4 的固定规则。先减少参与排序的行与字段，再考虑内存参数。

深分页：LIMIT 100000,20 通常仍需读取并丢弃前面的记录。若业务支持沿游标继续，可用 WHERE id > :last_id ORDER BY id LIMIT 20。非唯一排序字段需加唯一键作为稳定的第二排序条件，并让游标条件与排序一致。
