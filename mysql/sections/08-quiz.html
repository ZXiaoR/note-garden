08.1 · 实战闭卷检验：10 道高频业务落地与线上故障排查题（点击展开解析）

08.1 综合场景自测 10 题

01. 订单列表翻到第 1000 页（LIMIT 20000, 20）很慢要 3 秒怎么办？下拉加载和跳页码分别怎么改？

慢的原因：引擎顺着二级索引扫出 20020 个主键并回表 20020 次取整行，再由 Server 层扔掉前 20000 行。
① App 下拉瀑布流 / 批量导出：改游标分页——建立联合索引 (shop_id, id)，前端传上一页末尾 last_id，查 WHERE shop_id = ? AND id < ? ORDER BY id DESC LIMIT 20，翻到第几万页都是恒定毫秒级。
② PC 后台必须跳页码：改延迟关联——子查询 SELECT id FROM orders WHERE shop_id = ? ORDER BY id DESC LIMIT 20000, 20 走纯覆盖索引零回表拿到 20 个 ID，再与外层原表 INNER JOIN 仅回表 20 次（回顾 06.2）。

02. 用户刚修改了绑定手机号，回到个人资料列表刷新却还显示旧手机号，按什么顺序排查？

按线上最高发顺序查这 3 处：
① 开启了主从读写分离延迟：改手机号写了主库，紧接着列表页去查还没同步完成的只读从库读到了旧值——对写后立即读接口加主库路由标记或直接走主库；
② Redis 缓存漏删或顺序写反：改完库没 DEL 对应用户缓存，或写成了“先删缓存再更库”被并发读把旧手机号脏回填进了缓存；
③ 代码事务未提交：改手机号在显式事务中漏调了 COMMIT，或异常回滚被吞掉没抛错（回顾 06.8 / 07.6）。

03. 同一手机号弱网连点注册出了两条账号怎么彻底防住？如果业务还要求支持账号注销（软删除）后重绑该手机号呢？

① 防并发重复注册：删掉不可靠的“先 SELECT 判断不存在再 INSERT”，直接在数据库建唯一索引 UNIQUE KEY uk_phone (phone)，后端代码捕获错误码 1062 (ER_DUP_ENTRY) 返回友好提示。
② 兼容多次软删除重注册：不要用允许 NULL 的列或布尔 0/1 拼唯一索引，而是新增 deleted_id BIGINT UNSIGNED NOT NULL DEFAULT 0（正常态为 0，注销时更新为该行自身主键 id），建联合唯一索引 UNIQUE KEY (phone, deleted_id)（回顾 06.1 / 06.4）。

04. 明明给查询字段加了索引，SQL 执行还是很慢，你的标准排查清单是什么？

先在该 SQL 前加 EXPLAIN（或 EXPLAIN ANALYZE） 看 type、key、key_len、rows 与 Extra，对照排查：
① 索引根本没选上（key = NULL, type = ALL）：排查是否违背联合索引最左前缀、对索引列套了函数/运算（如 DATE(created_at)）、发生了隐式类型转换（VARCHAR 手机号传了数字）、使用了左模糊 LIKE '%xx'，或范围太宽命中超全表 20%~30% 被优化器主动放弃；
② 选上了索引但依然慢：检查是否深分页回表百万次、Extra 出现大结果集 Using filesort / Using temporary，或统计信息过期（跑 ANALYZE TABLE），又或者在等行锁（看慢日志 Lock_time）（回顾 05.2 / 05.3）。

05. 活动限量 100 件商品卖出了 105 件（超卖），原代码“先 SELECT stock 判断大于 0 再 UPDATE”为什么防不住？怎么改？

出错根因：普通 SELECT 是不加锁的 MVCC 快照读，多个并发请求在同一毫秒读到 stock = 1 都通过校验，先后扣减导致库存变负数。
标准修法：直接合并为单条原子条件更新 UPDATE sku_stock SET stock = stock - ? WHERE sku_id = ? AND stock >= ?（InnoDB 执行 UPDATE 触发当前读并加排他行锁串行扣减），后端判断 affectedRows === 1 才算抢购成功；若需跨多表复杂计算再扣减，则在事务内用 SELECT ... FOR UPDATE 加悲观锁（回顾 04.3 / 06.3）。

06. 慢日志里一条超 500ms 的 SQL 都没有，但查 50 条帖子列表接口却耗时 400ms 且数据库 QPS 奇高，是什么问题？

典型踩中了应用层 ORM 的 N+1 循环查询问题：先发 1 条 SQL 查出 50 条帖子，紧接着在循环里每条帖子单独发 1 条主键查询去拿作者信息和点赞状态，单次请求叠加了 1 + 50 + 50 = 101 次跨网络查库，每条虽只需 1~3ms，合起来却高达几百毫秒。
修法：提取去重后的 author_id 数组，用 1 条 SELECT ... WHERE id IN (?, ?, ...)（或 ORM 的 Preload）一次性批量查回内存 Map 组装，把 101 次查询压回固定的 2~3 次（回顾 05.5）。

07. 下午高峰期在 3000 万行订单表上跑了一条加字段 ALTER TABLE，为什么几秒后连全站普通 SELECT 都全部卡死超时？怎么急救与预防？

事故根因（MDL 锁排队雪崩）：订单表上恰好有一个未提交的慢查询正占着 MDL 读锁；此时发出的 ALTER TABLE 申请排他的 MDL 写锁 被阻塞排队；由于 MDL 锁队列写锁优先，排在这条 ALTER TABLE 后面的所有正常业务 SELECT 连读锁都拿不到，瞬间堵满连接池。
现场急救：立刻 KILL 掉那条卡在 Waiting for table metadata lock 的 ALTER TABLE 会话（或杀掉源头未提交长事务）。
预防规范：任何线上 DDL 前必加 SET SESSION lock_wait_timeout = 3;，并显式声明 ALGORITHM=INSTANT（或 INPLACE, LOCK=NONE）（回顾 07.3）。

08. 订单支付成功既要改订单状态，又要发 MQ 给下游发优惠券，怎么既防重复回调，又保证改库和发消息绝对一致？

用「状态机条件更新 + 同库本地消息表」在一个短事务内一次搞定：
① 开启事务执行 UPDATE orders SET status = 2, paid_at = NOW() WHERE order_no = ? AND status = 1；
② 若 affectedRows === 0，说明已处理过或已超时取消，直接回滚退出（拦截重复回调）；
③ 若 affectedRows === 1，在同一个数据库事务里紧接着向 outbox_messages 表插入一条待发发券消息，然后 COMMIT；
④ 独立后台协程轮询 outbox_messages 异步投递给 MQ，下游发券服务按 order_no 唯一索引做幂等（回顾 06.5 / 06.9）。

09. 运维脚本写错变量执行了 DELETE FROM coupons; 把优惠券表清空了，已开启每日全备和 Binlog，怎么恢复到误删前一秒？

切忌直接在生产原库乱导覆盖，按标准 PITR 三步走：
① 新建一个独立临时恢复库，先把最近一次凌晨全量备份导入，记下全备时刻对应的 Binlog 文件与起始位点；
② 用 mysqlbinlog --base64-output=DECODE-ROWS -vv 定位出误删 DELETE 事务起始前的精确位点（stop-position）；
③ 用 mysqlbinlog --start-position=... --stop-position=... 把全备之后直到误删前一刻的所有正常增量日志重放到临时库，校验行数和金额无误后，将 coupons 表导回线上库（回顾 07.5）。

10. 交易订单表涨到了 5000 万行，列表偶尔变慢，一定要立刻重构做水平分库分表吗？

先别急着分库分表！单表 5000 万行在 3~4 层 B+ 树下索引点查依然是毫秒级，“列表偶尔变慢”十有八九是缺联合索引、隐式转换或深分页导致的。应按成本从低到高评估：
① 先跑 EXPLAIN 修好索引并把深分页改为游标；
② 把报表慢查询切到只读从库，并定时将 6~12 个月前已完结的冷订单归档迁移到历史库，让在线主表回落到一千万行以内；
③ 只有当近几个月的活跃热订单本身就突破 5000万~1亿行、且主库磁盘写 IOPS 与连接数已达单机上限时，才承担跨分片查询与分布式ID的代价引入水平分库分表（回顾 07.7）。

08.2 · 考前与复习速查卡：MySQL 15 个核心问题一句话速记表

08.2 MySQL 15 题一句话速记表

核心问题 一句话标准答案（含实战篇与原理篇双跳转）
1. 金额、时间、字符集怎么选？ 金额用 DECIMAL(12,2) 或 BIGINT 存分（禁 FLOAT/DOUBLE）；业务时间优先 DATETIME（避开 TIMESTAMP 2038 上限）；字符集一律 utf8mb4 支持 Emoji（02.5）。
2. 为什么推荐自增主键而非随机 UUID？ InnoDB 表即主键 B+ 树：自增 ID 顺序追加写页满率高；随机 UUID 会插在历史页中间触发频繁 16KB 页分裂与随机 I/O，且 36 字节主键会让所有二级索引膨胀（02.3 / 原理篇 02.2）。
3. 聚簇索引、二级索引与回表是什么？ 聚簇索引（主键树）叶子存整行数据；二级索引叶子只存「索引列 + 主键 ID」，需拿 ID 再回主键树查整行（回表）；查询列全在索引内免回表即覆盖索引（Using index）（05.1 / 原理篇 02.1）。
4. 联合索引 (a, b, c) 怎么建最有效？ 遵循最左前缀原则（不能跳过 a），等值过滤列放左边、范围列放右边，高频排序列顺带纳入索引消除 Using filesort；严禁对索引列套函数或触发隐式类型转换（05.2）。
5. 为什么 LIMIT 1000000, 20 极慢？ 并非直接跳过，而是先回表 1000020 次取整行再丢弃前 100 万行；下拉加载改游标分页（WHERE id < last_id LIMIT 20），跳页码改覆盖索引子查询延迟关联（06.2）。
6. ORM 的 N+1 问题怎么发现和解决？ 查 1 次主列表后在循环里跑 N 次关联单查，放大网络 RTT；改用 1 条 WHERE id IN (...)（或 ORM Preload）批量查回内存 Map 组装，把 N+1 次压成固定 2 次（05.5）。
7. 高并发扣库存怎么防超卖？ 严禁先普通 SELECT 再 UPDATE；常规用单条条件更新 UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?，复杂多表校验用 SELECT ... FOR UPDATE，万人瞬时抢购前置 Redis 预扣（04.3 / 06.3）。
8. ACID 在 InnoDB 底层分别靠什么实现？ A 原子性靠 Undo Log 回滚；I 隔离性靠 MVCC（快照读）+ 行锁/临键锁（当前读）；D 持久性靠 Redo Log（WAL）+ Doublewrite 双写缓冲；三者共同兜底 C 一致性（04.1 / 原理篇 06.1）。
9. RC 与默认 RR 隔离级别的核心区别？ 快照时机不同：RC 每条普通 SELECT 都重新生成新 ReadView（已提交立即可见，几乎无间隙锁）；RR 只在事务首次 SELECT 生成 ReadView 并全程复用，且当前读加临键锁防幻读（04.2 / 原理篇 04.2）。
10. InnoDB 行锁到底锁的是什么？ 锁加在索引项与索引间隙上（记录锁 + 间隙锁 = 左开右闭的临键锁 Next-Key Lock）；若 UPDATE / FOR UPDATE 没走索引退化全表扫描，会把整张表所有行和间隙全锁死（07.4 / 原理篇 05.2）。
11. Redo Log 与 Binlog 差在哪，为何要两阶段提交？ Redo 是 InnoDB 环形物理重做日志（管崩溃恢复），Binlog 是 Server 层追加逻辑归档日志（管主从复制与 PITR 恢复）；围绕 XID 做两阶段提交（Prepare → 写 Binlog → Commit）确保崩溃恢复后主从数据严格一致（原理篇 06.1）。
12. 大表怎么在线安全加字段或建索引？ 先执行 SET SESSION lock_wait_timeout = 3; 防 MDL 锁排队雪崩；8.0+ 加删列优先指定 ALGORITHM=INSTANT（毫秒级只改元数据），建索引指定 ALGORITHM=INPLACE, LOCK=NONE，改列类型用 gh-ost（07.3）。
13. 读写分离「刚写完读到旧数据」怎么解？ 源于主从异步复制延迟；支付结果/登录等强一致读直接强制路由主库，或写后在 Redis 种 3 秒主库路由标记，或写接口直接把新实体返回给前端渲染（07.6 / 原理篇 06.3）。
14. 改库与删缓存、发 MQ 怎么保证一致？ 缓存用 Cache-Aside（先提交数据库修改，再 DEL 缓存 + 失败重试/TTL 兜底）；发 MQ 用本地消息表（同库单事务同时写订单表与 outbox 表 + 后台轮询投递 + 消费幂等）（06.8 / 06.9）。
15. 单表数据量大了按什么顺序演进？ 严格按「① 索引调优 + 游标分页 → ② 读写分离 + 缓存 + 冷历史订单归档 → ③ 原生表分区 → ④ 活跃热表破五千万~一亿且单机写见顶时再水平分库分表」推进（07.7）。
