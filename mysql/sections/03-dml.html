03.1 · 写操作全集：单行与批量 INSERT、关联 UPDATE、安全 DELETE 与 ON DUPLICATE KEY UPDATE 幂等写入

03.1 标准增删改（INSERT / UPDATE / DELETE）与幂等写入（UPSERT）

SQL 按职责分为四大类：DDL（Data Definition Language，数据定义语言：CREATE / ALTER / DROP / TRUNCATE）、DML（Data Manipulation Language，数据操作语言：INSERT / UPDATE / DELETE）、DQL（Data Query Language，数据查询语言：SELECT） 与 DCL（Data Control Language，数据控制语言：GRANT / REVOKE）。在日常业务开发中，数据写入与修改涵盖了从基础单行/批量操作到唯一键冲突幂等更新（UPSERT，Update + Insert 的合称，存在则更新、不存在则插入）的完整模式：

dml_write_patterns.sql · 批量插入、关联更新、安全删除与 UPSERT 
-- 1. 批量插入（单条 INSERT 传多组 VALUES，比循环单条插入快约 10 倍，减少网络与事务开销）
INSERT INTO `users` (`username`, `city`, `balance`) VALUES
  ('lin',  '杭州', 100.00),
  ('zhou', '杭州', 200.00),
  ('chen', '上海', 300.00);

-- 2. INSERT INTO ... SELECT：将查询统计结果直接批量导入另一张表
INSERT INTO `vip_users_archive` (`user_id`, `username`, `balance`)
SELECT `id`, `username`, `balance` FROM `users` WHERE `balance` >= 1000.00;

-- 3. 条件更新与多表 JOIN 关联更新（根据部门表状态同步更新员工表津贴）
UPDATE `employees` `e`
INNER JOIN `departments` `d` ON `e`.`dept_id` = `d`.`id`
SET `e`.`bonus` = `e`.`bonus` + 500.00
WHERE `d`.`city` = '杭州' AND `e`.`status` = 1;

-- 4. 幂等写入（UPSERT）：若唯一键 (stat_date, item_id) 不存在则插入，已存在则累加
-- 注：MySQL 8.0.20+ 推荐使用 AS new 行别名引用待插入的新值
INSERT INTO `daily_stats` (`stat_date`, `item_id`, `view_cnt`, `pay_amt`)
VALUES ('2026-11-15', 1001, 1, 99.00) AS `new`
ON DUPLICATE KEY UPDATE
  `view_cnt` = `daily_stats`.`view_cnt` + `new`.`view_cnt`,
  `pay_amt`  = `daily_stats`.`pay_amt`  + `new`.`pay_amt`;

-- 5. 清理百万级历史数据时，按索引加 LIMIT 分批小事务删除（防锁表与主从延迟）
DELETE FROM `audit_logs`
WHERE `created_at` < '2025-01-01 00:00:00'
ORDER BY `id` ASC LIMIT 2000;
写操作四大工程细节说明
  • 防误删全表保护开关（sql_safe_updates = 1）：在生产终端手工执行 SQL 时，建议开启 SET sql_safe_updates = 1;（或在连接命令加 mysql --safe-updates）。开启后，任何没写 WHERE 条件（且没写 LIMIT）或 WHERE 条件未走索引的 UPDATE / DELETE 都会被直接拦截报错，避免手滑覆写整表。
  • ON DUPLICATE KEY UPDATE 的受影响行数：如果是纯新增返回受影响行数为 1；如果触发了唯一键冲突并修改了旧值则返回 2；如果冲突但更新前后的值完全相同则返回 0。
  • 为什么不推荐用 REPLACE INTO：当唯一键冲突时，REPLACE INTO 并不是原地 UPDATE，而是先把旧行物理 DELETE 再重新 INSERT 一行新记录。这会导致该行的自增主键 id 被悄悄换掉、未在语句中写出的列被重置为默认值，并迫使所有二级索引重新维护。
  • 为什么大批量 DELETE / UPDATE 要加 LIMIT 拆批：单条修改百万行的大事务会长时间持有大量记录锁与间隙锁，阻塞正常业务写入并撑爆 Undo Log，拆为每次 1000 ~ 5000 行最为稳妥。
03.2 · 单表查询与 NULL 避坑：WHERE 过滤操作符、NULL 三值逻辑（为什么 NOT IN 遇到 NULL 返回空）与排序分页

03.2 单表查询（SELECT / WHERE / ORDER BY / LIMIT）与 NULL 三值逻辑

单表查询涵盖了投影（SELECT）、去重（DISTINCT）、条件过滤（WHERE）、排序（ORDER BY）与分页（LIMIT）。在编写过滤条件时，最核心的基本功是掌握各类操作符的边界语义以及 SQL 特有的 NULL 三值逻辑（TRUE / FALSE / UNKNOWN）：

操作符 / 表达式 标准语法示例 边界语义与避坑要点
比较与安全等于
= / != / <=>		 WHERE city = '杭州'
WHERE phone <=> NULL		 普通等于号 = 和不等于号 !=（或 <>）一旦任意一侧为 NULL，结果永远是 UNKNOWN（不会命中任何行）。MySQL 特有的太空船运算符 <=>（NULL-safe equal） 可安全比较 NULL（NULL <=> NULL 返回 1）。
区间与集合
BETWEEN / IN / NOT IN		 WHERE age BETWEEN 18 AND 30
WHERE status IN (1, 2, 3)		 • BETWEEN a AND b 是闭区间 [a, b]（包含首尾两端点 a 和 b）；
• NOT IN 含 NULL 陷阱：WHERE id NOT IN (10, 20, NULL) 等价于 id != 10 AND id != 20 AND id != NULL，由于 id != NULL 恒为 UNKNOWN，整条查询永远返回 0 行。子查询判不存在时应优先使用 NOT EXISTS。
模糊与正则匹配
LIKE / REGEXP		 WHERE name LIKE '张%'
WHERE code REGEXP '^[A-Z]{2}[0-9]+$'		 LIKE 中 % 匹配任意 0 到多个字符，_ 匹配严格单个字符（若要匹配字面量下划线需转义写为 \_）。注意最左前缀原则：'张%' 可走索引，而左通配 '%张%' 会导致 B+ 树索引失效。
逻辑组合优先级
AND / OR / NOT		 WHERE (city = '杭州' OR city = '上海') AND status = 1 AND 的运算优先级高于 OR。如果漏写括号写成 WHERE city = '杭州' OR city = '上海' AND status = 1，会被数据库解析为 city = '杭州' OR (city = '上海' AND status = 1)，导致杭州已禁用（status = 0）的用户被意外查出。
空值兜底与条件分支
COALESCE / IFNULL / CASE		 COALESCE(nickname, username, '匿名')
CASE WHEN score >= 60 THEN '及格' ELSE '不及格' END		 任何数值与 NULL 做算术运算结果都是 NULL（如 100 + NULL = NULL），做金额累加或拼接前需用标准 SQL 函数 COALESCE(col, 0)（返回参数列表中第一个非 NULL 值）或 IFNULL(col, 0) 兜底。
select_single_table.sql · 去重、条件表达式、NULL 安全处理与排序分页标准写法 
-- 1. 投影、列别名 AS、COALESCE 空值兜底与 CASE WHEN 条件派生列
SELECT
  `id`,
  COALESCE(`nickname`, `username`, '未命名用户') AS `display_name`,
  `balance` + IFNULL(`frozen_balance`, 0.00)     AS `total_assets`,
  CASE
    WHEN `balance` >= 10000.00 THEN '钻石会员'
    WHEN `balance` >= 1000.00  THEN '黄金会员'
    ELSE '普通会员'
  END AS `vip_tier`
FROM `users`
WHERE (`city` = '杭州' OR `city` = '上海')
  AND `phone` IS NOT NULL                  -- 判空必须用 IS NULL / IS NOT NULL，不可写 != NULL
  AND `created_at` BETWEEN '2026-01-01 00:00:00' AND '2026-12-31 23:59:59'
ORDER BY `balance` DESC, `id` ASC          -- 先按余额降序；余额相同时按主键 id 升序保证顺序稳定
LIMIT 20 OFFSET 40;                        -- 跳过前 40 条，取第 41~60 条（等价于 MySQL 简写 LIMIT 40, 20）

-- 2. DISTINCT 多列去重：返回所有不重复的 (city, status) 组合
SELECT DISTINCT `city`, `status` FROM `users`;
03.3 · 分组与聚合：五大聚合函数、GROUP_CONCAT、WHERE 与 HAVING 的本质区别及 COUNT(*) 规范

03.3 分组聚合（GROUP BY）、WHERE vs HAVING 与 COUNT 规范

当需要按某个维度（如按城市、按日期、按商品分类）汇总统计时，使用 GROUP BY 将具有相同分组键的多行折叠为一行，并配合聚合函数（COUNT / SUM / AVG / MAX / MIN / GROUP_CONCAT）计算统计值。初学者最常混淆的是 WHERE 与 HAVING 的过滤时机差异：

对比维度 WHERE 子句 HAVING 子句
执行时机 在 GROUP BY 分组之前，对原表中的每一行逐行过滤 在 GROUP BY 分组并算出聚合值之后，对分组汇总结果做二次过滤
能否使用聚合函数 不能（如写 WHERE COUNT(*) > 5 会直接报语法错误，因为此时尚未分组） 专门用于过滤聚合函数结果（如 HAVING COUNT(*) > 5 AND SUM(pay_amt) >= 1000）
能否走索引与性能 可以直接利用 B+ 树索引提前过滤掉无关数据，减少参与分组排序的行数 在内存/临时表聚合完成后才过滤，无法利用索引减少扫描量
工程编写准则 凡是不依赖聚合函数的普通列过滤条件（如 status = 'PAID'、时间范围），一律写在 WHERE 中提前过滤；只有依赖 COUNT / SUM / AVG 的结果条件才写在 HAVING 中。
groupby_having.sql · 分组统计、条件聚合与 GROUP_CONCAT 
-- 统计 2026 年各城市的：总订单数、已支付订单数、已支付总金额、客单价及前 3 个用户名单
-- 且只保留“已支付总金额 >= 5000 元”的城市：
SELECT
  `city`,
  COUNT(*) AS `total_orders`,
  -- 条件聚合：单次扫描内同时统计满足特定子条件的行数与金额
  COUNT(CASE WHEN `status` = 'PAID' THEN 1 END) AS `paid_orders`,
  SUM(CASE WHEN `status` = 'PAID' THEN `amount` ELSE 0 END) AS `paid_sum`,
  ROUND(AVG(`amount`), 2) AS `avg_amount`,
  -- GROUP_CONCAT：将同一分组内的多行字段值拼接成逗号分隔字符串
  GROUP_CONCAT(DISTINCT `username` ORDER BY `amount` DESC SEPARATOR ', ') AS `buyers`
FROM `orders`
WHERE `created_at` >= '2026-01-01 00:00:00'   -- 分组前走索引过滤时间
GROUP BY `city`
HAVING `paid_sum` >= 5000.00                  -- 分组后过滤聚合结果
ORDER BY `paid_sum` DESC;
  • ONLY_FULL_GROUP_BY 规范（MySQL 5.7.5+ 默认开启）：要求 SELECT 列表中出现的每一列，要么包含在 GROUP BY 分组键中，要么被包裹在聚合函数（如 SUM() / MAX() / COUNT() / ANY_VALUE()）内，从而杜绝从同一分组的多行里随机挑一行非分组列值的不确定行为。
  • COUNT(*) vs COUNT(1) vs COUNT(列名)：COUNT(*) 与 COUNT(1) 均统计符合条件的总行数（包含列值为 NULL 的行），在 MySQL InnoDB 中两者的执行计划和性能完全相同（优化器会自动挑选体积最小的二级索引树进行遍历计数，不会读取整行），按 SQL 标准推荐统一写 COUNT(*)；而 COUNT(列名) 只统计该列非 NULL 的行数。
03.4 · 多表关联与集合：JOIN 类型、LEFT JOIN 中 ON 与 WHERE 的差异、EXISTS 子查询与 UNION ALL

03.4 多表关联（JOIN）、子查询（EXISTS）与集合合并（UNION ALL）

当数据分布在多张关系表中时，可以通过横向列关联（JOIN）、嵌套子查询（IN / EXISTS）或纵向行合并（UNION ALL / UNION）组合查询。其中最关键的实战细节是区分 LEFT JOIN 中过滤条件写在 ON 还是写在 WHERE：

关联 / 集合语法 典型写法示例 集合语义与执行过程解析
内连接 INNER JOIN
（两表交集 A ∩ B）		 FROM users u INNER JOIN orders o ON u.id = o.user_id 只返回左右两张表都能匹配上连接条件的行（没有任何订单的用户不会出现在结果中）。
左外连接 + 条件写在 ON
（保持左表全集）		 FROM users u LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'PAID' 在连接匹配阶段只关联该用户的已支付订单；如果某个用户没有任何已支付订单，左表 users 的该行依然会保留返回（右侧订单列全部补 NULL）。
左外连接 + 右表条件写在 WHERE
（隐式退化为 INNER JOIN）		 FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.status = 'PAID' 先生成包含 NULL 补位行的左连接临时结果，随后执行 WHERE o.status = 'PAID'；由于 NULL = 'PAID' 为假，所有未下单用户的行被 WHERE 全部滤除，导致 LEFT JOIN 退化成了 INNER JOIN。
查找左表独有差集（Anti-Join）
LEFT JOIN ... WHERE 右表主键 IS NULL 或 NOT EXISTS		 SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id) 查询“注册后从未下过单的用户”。使用 NOT EXISTS（或 LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL）不仅能走索引反半连接优化（Anti-Join），还能彻底规避 NOT IN 遇到 NULL 返回空集的隐患。
纵向合并结果集
UNION ALL vs UNION		 SELECT id, amount FROM orders_2025 UNION ALL SELECT id, amount FROM orders_2026 • UNION ALL（首选）：直接将上下两个查询的结果集追加拼接，不做去重、不创建临时表排序，性能极高；
• UNION：拼接后还会对全部列做一次全量去重，开销远高于 UNION ALL，除非明确需要去重否则一律写 UNION ALL。
03.5 · MySQL 8.0+ 分析查询：窗口函数 OVER (PARTITION BY ... ORDER BY ...)、递归 CTE 与 9 步执行顺序

03.5 窗口函数、递归公共表表达式（WITH RECURSIVE）与执行顺序

自 MySQL 8.0 起，原生支持完整的 SQL 标准窗口函数（Window Functions）与公共表表达式（CTE，Common Table Expression）。与普通 GROUP BY 把多行折叠合并成一行不同，窗口函数通过 函数名() OVER (PARTITION BY 分组列 ORDER BY 排序列) 在保留每一行原始明细的同时，为每一行计算出它在所属分组窗口内的排名、累计求和或前后相邻行对比值：

window_and_cte.sql · 分组 Top-N 排名与 WITH RECURSIVE 递归树查询 
-- 1. 经典高频题：用 CTE + 窗口函数查出“每个城市余额排名前 2 的用户”
-- ROW_NUMBER(): 连续唯一序号(1,2,3)；DENSE_RANK(): 并列不跳号(1,1,2)；RANK(): 并列跳号(1,1,3)
WITH `ranked_users` AS (
  SELECT
    `id`, `name`, `city`, `balance`,
    DENSE_RANK() OVER (PARTITION BY `city` ORDER BY `balance` DESC) AS `rk`,
    SUM(`balance`) OVER (PARTITION BY `city`) AS `city_total`
  FROM `users`
)
SELECT * FROM `ranked_users` WHERE `rk` <= 2;

-- 2. 递归 CTE (WITH RECURSIVE)：向下查询某个部门（id=1）及其所有层级的子孙部门
WITH RECURSIVE `dept_tree` AS (
  -- ① 锚点成员（起点）：先查出顶层根节点部门
  SELECT `id`, `name`, `parent_id`, 1 AS `level`
  FROM `departments` WHERE `id` = 1
  UNION ALL
  -- ② 递归成员：拿上一层查出的 dept_tree.id 去匹配下一层的 parent_id
  SELECT `d`.`id`, `d`.`name`, `d`.`parent_id`, `t`.`level` + 1
  FROM `departments` `d`
  INNER JOIN `dept_tree` `t` ON `d`.`parent_id` = `t`.`id`
)
SELECT * FROM `dept_tree`;
SQL 子句的真实逻辑执行顺序

虽然我们书写 SQL 时以 SELECT 开头，但数据库内部是按以下 9 步顺序求值的：

① FROM / JOIN ON ➔ ② WHERE ➔ ③ GROUP BY ➔ ④ HAVING ➔ ⑤ 窗口函数 OVER(...) ➔ ⑥ SELECT (生成列别名) ➔ ⑦ DISTINCT ➔ ⑧ ORDER BY ➔ ⑨ LIMIT / OFFSET
  • 为什么 WHERE 和 HAVING 里不能直接用窗口函数，且 WHERE 里不能引用 SELECT 定义的列别名：因为第 ② 步执行 WHERE 时，第 ⑤ 步的窗口函数和第 ⑥ 步的 SELECT 别名还没有计算出来；而第 ⑧ 步的 ORDER BY 排在第 ⑥ 步之后，所以 ORDER BY 里可以直接使用 SELECT 的列别名。
  • 递归 CTE 安全上限：MySQL 通过系统变量 cte_max_recursion_depth（默认 1000）防止脏数据环路导致无限递归。

本章即时场景题（先想答案，再点击展开）

1. 想查出“所有买家以及他们在 2026 年已支付的订单（没下过单的买家也要保留一行）”，写成 FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.status = 'PAID' 对吗？

不对，没下过单的买家会被全部过滤掉。LEFT JOIN 对没匹配上订单的买家会把右表 o.status 补为 NULL；紧接着外层 WHERE o.status = 'PAID' 判定 NULL = 'PAID' 为 UNKNOWN，导致这些买家行被剔除，隐式退化成了 INNER JOIN。应把右表过滤条件移到 ON 子句里：LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'PAID'。

2. 执行 SELECT * FROM products WHERE category_id NOT IN (SELECT id FROM banned_categories)，只要子查询结果里混进了一条 NULL，会发生什么？

整条 SQL 会返回 0 行空结果。因为 x NOT IN (1, 2, NULL) 等价于 x != 1 AND x != 2 AND x != NULL，其中 x != NULL 永远为 UNKNOWN，导致整个 AND 表达式不可能为 TRUE。排查“不在某集合内”应优先改用 NOT EXISTS (SELECT 1 FROM banned_categories b WHERE b.id = products.category_id)。

3. 运营需要查出“每个商品类目下销量排名前 3 的商品明细”，为什么单靠 GROUP BY category_id 写不出来，该怎么写？

GROUP BY category_id 会把同一个类目下的几百个商品折叠成 1 行汇总值，无法保留前 3 名各自的商品 ID 和名称。在 MySQL 8.0+ 中应使用 CTE 搭配窗口函数：内层算 ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY sales DESC) AS rk，外层直接过滤 WHERE rk <= 3（完整实战见 06.6）。
