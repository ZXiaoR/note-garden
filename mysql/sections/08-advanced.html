🗄️ 08.1 · 行格式、页目录、COUNT 与 SQL 语义边界

🗄️ 08.1 进阶抽屉：有了主线再补细节

📦 行格式 · 一行除了用户列还存什么

以 InnoDB 常见的 COMPACT / DYNAMIC 格式为背景，记录还有记录头、变长字段长度信息、NULL 位图等。聚簇记录还包含事务 ID（DB_TRX_ID，6 字节）与回滚指针（DB_ROLL_PTR，7 字节）；需要引擎生成隐藏行 ID 时，再有 6 字节的 DB_ROW_ID。

变长字段长度信息与 NULL 位图不是每个字段都无条件占一份固定空间。NULL 与空字符串也不同。DYNAMIC 是 8.0/8.4 默认行格式；大变长字段需要页外存储时，行内可保留 20 字节页外指针，并不是所有 TEXT 或 VARCHAR 都一定移到页外。

📄 索引页 · 页目录（Page Directory）怎么找记录

B+ 树索引页包含文件头、页头、边界记录、用户记录、空闲区、页目录与文件尾等。记录按键顺序链接，页目录通过槽定位一小组记录，再在组内查找。这是索引页的说明，不能扩展成“undo 页、溢出页等所有类型的页结构完全相同”。

🔢 COUNT · 数行与数非 NULL 值

COUNT(*) 数结果行，COUNT(1) 同样数行；COUNT(col) 只数该列非 NULL 的行。对 InnoDB，精确计数要符合当前事务可见性，因此不能只读一个全表固定计数器；无条件 COUNT(*) 常会选择较小的二级索引扫描，但仍需考虑可见性。

MyISAM 在特定的无过滤单表全表计数场景可使用保存的行数。不能据此推导“有 WHERE 也总是 O(1)”，更不能为了 COUNT 快就把业务表改成不支持事务的引擎。

⚙️ MyISAM 与 InnoDB · 看能力，不只背对照表

InnoDB 支持事务、MVCC、行级锁和外键约束，是本文主线。MyISAM 不支持事务和外键约束，主要使用表级锁。两者都支持 B-tree 索引；“MyISAM 才支持全文索引”是旧知识，InnoDB 也支持全文索引。

🧭 SQL · 逻辑处理顺序与常见语义边界

入门可按 FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT 理解结果如何形成。这是逻辑模型，不是优化器的物理执行顺序；MySQL 的别名解析还有自身规则。

  • WHERE 过滤分组前的行，HAVING 过滤分组结果；NULL 判断用 IS NULL，不是 = NULL。
  • LEFT JOIN 保留左侧未匹配行；把右表的非空过滤条件放在 WHERE，可能排除这些行，改变连接语义。
  • NOT IN 的子查询含 NULL 时会产生容易误解的 UNKNOWN；按业务语义考虑 NOT EXISTS 并验证 NULL 行为。
  • ORDER BY 要想分页稳定，应能唯一确定顺序；默认不写 ORDER BY，就没有结果顺序保证。
🎯 08.2 · 闭卷自测：7 道核心追问

🎯 08.2 自测 · 先在心里回答，再展开核对

Q1：用主键查一行，是否一定只有一次磁盘 I/O？

不一定。要访问索引路径上的页，但页可能已经缓存；还可能需要旧版本或页外字段。树高是逻辑路径长度，不能直接当作实测磁盘 I/O 次数。

Q2：覆盖索引和 ICP 的区别是什么？

覆盖索引使所需列能从索引取得，通常减少取完整行；ICP 把可在索引判断的条件下推到引擎，先过滤、减少回表。两者解决的问题不同。

Q3：RR 的快照从 BEGIN 时就固定了吗？

通常从首次一致性读建立，后续一致性读复用；WITH CONSISTENT SNAPSHOT 可显式建立。自己的修改可见，锁定读和 DML 访问当前状态，不能套用普通快照读的结论。

Q4：RC 完全没有间隙锁吗？

搜索与索引扫描通常不用，但外键检查和重复键检查仍可能使用。分析锁要交代隔离级别、索引、谓词和实际计划。

Q5：redo、undo、binlog 分别解决什么？

redo 支持崩溃重做；undo 支持回滚与旧版本重建；binlog 用于复制及配合备份恢复。内部 2PC 协调事务引擎与 binlog 的提交决定，持久性还取决于刷盘配置。

Q6：半同步确认之后，从库一定读得到新数据吗？

不一定。确认的是日志已接收并写 relay log 刷盘，不是事务已应用。需要目标从库应用到相应事务，并使用足够新的读取视图；关键读取也可直接走主库。

Q7：更新遇到死锁，重试最后一条 SQL 就可以吗？

死锁受害事务会被回滚，应重试整个业务事务，并处理幂等性和重试上限；锁等待超时与死锁的回滚范围可能不同，要按错误类型处理。
