05 并发互斥 · 锁：谁来加锁？锁长什么样？什么时候看它？ RECORD · GAP · NEXT-KEY LOCK
❓ 05.1 · 这些五花八门的锁，到底是数据库自动生成的，还是我们要写代码自己加？

🔑 05.1 先解开最大疑惑：95% 的锁是 InnoDB「全自动生成」的！

很多同学刚学完记录锁、间隙锁、临键锁、意向锁时都会懵：“难道我写 SQL 时还要手动指定加一把间隙锁吗？”——完全不需要！SQL 里甚至根本没有“手动加间隙锁/临键锁”的语法。

🤖 情况 ①：所有写操作（100% 自动加锁） 无需操心语法
只要你执行 UPDATE、DELETE、INSERT：
• InnoDB 会在底层全自动先给表挂上意向排他锁（IX）；
• 然后根据你的 隔离级别（RC / RR） + WHERE 条件走没走索引，全自动决定在索引上挂 记录锁（Record Lock）、间隙锁（Gap Lock） 还是 临键锁（Next-Key Lock）；
• 等你执行 COMMIT 或 ROLLBACK 时，全自动一次性释放。
🖐️ 情况 ②：读操作（你只按开关，锁型仍自动） 加尾巴触发
• 普通 SELECT ...（快照读）：不加任何行锁！直接走上一章讲的 MVCC 读历史版本（仅在 Server 层自动挂一把极轻的 MDL 读锁防别人删表结构）。
• 加锁读 SELECT ... FOR UPDATE / FOR SHARE（当前读）：当你为了防并发覆写，在 SQL 末尾手动加上 FOR UPDATE 时，相当于按下了“我要加锁”的开关——至于具体锁哪条记录、锁哪个缝隙，依然由 InnoDB 根据 WHERE 条件自动生成！
🚨 既然锁是自动生成的，那程序员「什么时候」才需要懂它、看它？（3 大实战时刻）
① 写「扣库存 / 扣余额 / 防重单」代码时（决定要不要加锁）：
如果你在事务里先用普通 SELECT balance 查出余额 100（MVCC 不加锁），在 Java/Go 代码里算完 100 - 80 = 20 再去 UPDATE，两个并发请求会同时读到 100 并互相覆盖！此时你必须知道：要么写 SELECT ... FOR UPDATE 主动上锁排队，要么直接用一条 UPDATE account SET balance = balance - 80 WHERE id = 1 AND balance >= 80 触发自动行锁。
② 线上报错 Lock wait timeout exceeded，明明「插的是新数据」却被别人卡死时：
最经典的抓狂现场：“我只是 INSERT 一条 id=15 的新记录，数据库里根本还没有 15，我也没跟别人抢同一行，凭什么把我卡住 50 秒超时报错？！”——因为另一个事务正在按范围查或更新 (10, 20) 区间，InnoDB 自动生成了 间隙锁（Gap Lock） 把 11 ~ 19 的空隙全封死了！不懂间隙锁，这类线上阻塞你永远排查不出来。
③ 线上偶发 Deadlock found（死锁）或白天执行 ALTER TABLE 导致全站雪崩时：
两个事务交叉更新两行，或者两个事务同时持有同一个空隙的 Gap Lock 再同时往里 INSERT，就会撞成死锁；又或者有个慢查询忘了提交（一直占着自动生成的 MDL 元数据读锁），此时你执行 ALTER TABLE 加字段，会把后面所有正常的 SELECT 全部堵死！这时候就必须查锁视图抓凶手。
❓ 05.2 · 记录锁、间隙锁、临键锁到底锁在哪儿？一眼看懂索引数轴分布

📏 05.2 先看数轴：一张只有 id = 10, 20, 30 三行数据的表，上面有哪些位置可以锁？

假设表 t_order 里目前只有 3 条记录：id = 10、id = 20、id = 30。InnoDB 的行锁并不是锁在“空气”里，而是锁在 B+ 树索引的「记录点」和「记录之间的空隙」 上：

🟡 记录锁 (Record Lock)
只锁黄色的「实心点」（例如只锁 [id=20]）。别人不能改/删 20，但往两边空隙插 15、25 完全不管。
🔴 间隙锁 (Gap Lock)
只锁粉色的「开区间空隙」（例如只锁 (10, 20)）。唯一作用是禁止别人往这个缝里 INSERT 新行，不锁 10 和 20 本身！
🟢 临键锁 (Next-Key Lock)
间隙锁 + 记录锁合体 = 左开右闭区间（例如 (10, 20]）。既不准别人往 11~19 插新行，也不准别人改 [id=20]！

📋 InnoDB 与 Server 层 6 类锁速查表

锁类型 保护什么 核心要点（怎么触发 & 谁和谁冲突）
记录锁 Record Lock 单条索引记录（如 [20]） 分共享锁 S 和排他锁 X；UPDATE / DELETE / FOR UPDATE 命中唯一索引等值时自动加 X 记录锁。
间隙锁 Gap Lock 两条记录之间的空隙（如 (10, 20)） RR 隔离级别下为防幻读自动生成。注意：两个事务可以对同一个间隙同时加 Gap Lock（互相兼容），因为大家的目标都是“别让别人插进来”！
临键锁 Next-Key Lock 记录 + 它前面的间隙（如 (10, 20]） InnoDB 在 RR 级别下扫描索引时的默认加锁基本单位（遇到唯一索引等值命中等特殊情况会退化为记录锁或间隙锁）。
插入意向锁 Insert Intention INSERT 准备插入某个间隙的动作 执行 INSERT 时自动生成。如果该位置已被别的事务挂了 Gap Lock，INSERT 就会卡住等待！
意向锁 IS / IX 表级锁旗子（挂在表头上） 加行锁前 InnoDB 自动先在表头挂一面旗子，告诉别人“表里某行有锁”，避免别人申请表锁时逐行遍历检查。
元数据锁 MDL 表结构定义（Server 层自动加） 任何增删改查都会自动加 MDL 读锁；ALTER TABLE 会加 MDL 写锁。未提交的长事务会卡死 DDL，进而堵死后续所有查询！
❓ 05.3 · 实战演练：表里只有 id = 10, 20, 30，执行不同 SQL 时到底谁能过、谁会被卡死？

🎬 05.3 三个具体例子（默认 RR 可重复读 + 主键索引）：看 InnoDB 怎么自动变魔术

还是刚才那张只有 id = 10, 20, 30 三行数据的表。我们打开两个终端窗口（左边事务 A 先执行但暂不 COMMIT，右边事务 B 紧接着操作），看看三种最典型的 SQL 分别会自动生成什么锁：

🧪 例子 ①：唯一主键精准命中（id = 20 存在） 👉 自动退化为「记录锁 Record Lock」 只锁 [id=20] 单点
🧑‍💻 事务 A 先执行（不提交）：
BEGIN;
UPDATE t_order SET amount = 99 WHERE id = 20;
-- 或 SELECT * FROM t_order WHERE id = 20 FOR UPDATE; 🤖 InnoDB 自动动作：因为 id 是唯一主键且 20 真实存在，绝不可能有别人再插一个 id=20 进来，所以临键锁自动退化，只在 [id=20] 这一行挂一把记录锁（Record Lock），不锁两边的缝隙！
⚡ 此时事务 B 过来操作会发生什么？
• SELECT * FROM t_order WHERE id = 20;
👉 ✅ 秒过！（普通 SELECT 走 MVCC 读旧版本，不看锁）
• INSERT INTO t_order VALUES (15, ...); 或 (25, ...);
👉 ✅ 秒过！（因为两边的间隙没被锁！）
• UPDATE t_order SET amount = 88 WHERE id = 20;
👉 ❌ 当场卡死等待！（撞上了 [id=20] 的记录锁，直到事务 A 提交）
🧪 例子 ②：查/改一个不存在的 ID（id = 15 不存在） 👉 自动生成「间隙锁 Gap Lock」 锁住开区间 (10, 20) 空隙
🧑‍💻 事务 A 先执行（不提交）：
BEGIN;
UPDATE t_order SET amount = 99 WHERE id = 15;
-- 表里只有 10, 20, 30，受影响行数为 0！ 🤖 InnoDB 自动动作：虽然一行都没改到，但为了防止事务 A 还没提交时别人突然插一条 id=15 造成幻读，InnoDB 找到 15 所在的空隙 (10, 20)，自动给开区间 (10, 20) 挂上一把间隙锁（Gap Lock）！
⚡ 此时事务 B 过来操作会发生什么？
• UPDATE t_order SET amount = 88 WHERE id = 10;（或 id = 20）
👉 ✅ 秒过！（因为开区间 (10, 20) 不包含端点 10 和 20！）
• INSERT INTO t_order VALUES (25, ...);
👉 ✅ 秒过！（25 在 (20, 30) 区间，不在封锁区）
• INSERT INTO t_order VALUES (12, ...);（或插 15、18）
👉 ❌ 当场卡死等待！（11~19 全在 (10, 20) 间隙锁封锁区内，插不进去！）
🧪 例子 ③：范围加锁扫描（WHERE id > 20 FOR UPDATE） 👉 自动挂上「临键锁 Next-Key Lock」 锁住 (20, 30] + (30, +∞)
🧑‍💻 事务 A 先执行（不提交）：
BEGIN;
SELECT * FROM t_order WHERE id > 20 FOR UPDATE; 🤖 InnoDB 自动动作：顺着 B+ 树往右扫所有大于 20 的范围，自动挂上 Next-Key Lock (20, 30]（同时锁住 21~29 的空隙和 [id=30] 这条记录）以及末尾的 (30, +supremum] 正无穷区间！
⚡ 此时事务 B 过来操作会发生什么？
• INSERT INTO t_order VALUES (15, ...);
👉 ✅ 秒过！（15 在 20 左边，没被扫到）
• UPDATE t_order SET amount = 88 WHERE id = 30;
👉 ❌ 当场卡死！（[id=30] 被临键锁的右闭端点锁住了）
• INSERT INTO t_order VALUES (25, ...); 或 (50, ...);
👉 ❌ 全部当场卡死！（大于 20 的所有缝隙全被锁死了，彻底杜绝当前读幻读！）
⚠️ 生产最危险的大坑：「没走索引」会让行锁瞬间锁住全表所有行和所有间隙！
上面 3 个例子之所以锁得很精准，是因为 WHERE id = ... 走了主键索引。如果你写了一条 UPDATE t_order SET amount = 99 WHERE remark = 'test'，而 remark 列没有建索引，InnoDB 只能被迫做全表扫描——在 RR 级别下，它会把整张表里每一条记录和每一个间隙全部挂上 Next-Key Lock，整张表瞬间谁也改不了、谁也插不进！

🔄 死锁是怎么发生的？线上卡住时怎么用 SQL 抓出真凶？

当事务 A 先锁了 id=10 想去锁 id=20，而事务 B 先锁了 id=20 想去锁 id=10（或者两个事务同时对 (10, 20) 加了互相兼容的间隙锁，接着又同时往 (10, 20) 里执行 INSERT 互相等待对方释放间隙锁），就会形成死锁环路。InnoDB 的死锁检测器会立刻挑一个代价小的事务回滚报错，让另一个继续执行。
