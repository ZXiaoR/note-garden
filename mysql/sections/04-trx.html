🛡️ 04.1 事务 ACID 与四大隔离级别（承诺标准）

💸 transfer_tx.sql · 显式事务示例 
START TRANSACTION;
UPDATE users SET balance = balance - 10.00 WHERE id = 1;
UPDATE users SET balance = balance + 10.00 WHERE id = 2;
COMMIT;  -- 失败时由应用按错误情况决定 ROLLBACK / 重试

真实转账还应检查余额、受影响行数和请求幂等性。可用 UPDATE ... WHERE id=1 AND balance>=10.00 做条件扣款，并在同一事务内检查是否成功。默认 autocommit=1 时每条语句各自成为一个事务；许多 DDL 会隐式提交，不能认为所有 SQL 都能跟着事务一起回滚。

ACID 含义 底层靠什么兑现
原子性 A 修改一起提交，或一起回滚 靠 undo log 回滚日志撤销已执行修改
一致性 C 从满足约束的状态变到另一个满足约束的状态 A + I + D 三个手段共同守护的最终目的，加业务规则约束
隔离性 I 控制并发事务之间能观察、干扰到什么 读靠 MVCC 版本链快照，写靠锁（记录锁 / 间隙锁 / 临键锁）
持久性 D 提交成功的修改在故障断电后不丢 靠 redo log (WAL) + binlog 两阶段提交刷盘

🎚️ 四大隔离级别中文叫法 & 并发异常对照表

并发读写时如果不加控制，会按严重程度出现三类现象：
① 脏读 (Dirty Read)：读到了别人还没 COMMIT（甚至随后回滚了）的脏数据。
② 不可重复读 (Non-repeatable Read)：同一事务内两次读同一行，因为别人中途提交了 UPDATE，两次读到的值不一样。
③ 幻读 (Phantom Read)：同一事务内按同一范围条件查询，因为别人中途提交了 INSERT / DELETE，导致满足条件的记录集合凭空多出或少了几行。

中文通用叫法 (英文简称) 脏读 不可重复读 幻读 InnoDB 底层解决机制（怎么做到？）
① 读未提交
READ UNCOMMITTED (RU)		 ❌ 有 ❌ 有 ❌ 有 不建 ReadView 快照，直接读最新内存页上的未提交修改。
② 读已提交
READ COMMITTED (RC)		 ✅ 解决 ❌ 有 ❌ 有 每次 SELECT 都重新拍一张新 ReadView 快照（未提交事务在活跃列表里不可见，故无脏读；但别人提交后下次拍照就能看见）。
③ 可重复读 ⭐默认
REPEATABLE READ (RR)		 ✅ 解决 ✅ 解决 ✅ 解决* 快照读复用首次 SELECT 的 ReadView；当前读靠 Next-Key Lock（记录锁 + Gap 间隙锁）锁住区间缝隙防插入。（*注：快照读与当前读混用时需注意视角切换）
④ 可串行化
SERIALIZABLE		 ✅ 解决 ✅ 解决 ✅ 解决 普通 SELECT 自动转为 SELECT ... FOR SHARE 共享锁，读写互斥排队，牺牲并发度换绝对隔离。
💡 一句话记牢四种隔离级别：中文标准叫法就是「读未提交 (RU)、读已提交 (RC)、可重复读 (RR)、可串行化 (Serializable)」。Oracle / PostgreSQL 默认是读已提交 (RC)，而 MySQL InnoDB 默认是可重复读 (RR)。
❓ 04.2 · 承上启下：MVCC 和前面的「事务、四大隔离级别」到底是什么关系？

🌉 04.2 承上启下：隔离级别是「承诺标准」，MVCC 是兑现 RC / RR 的「底层武器」

🧭 第一性原理推导链：为什么讲完事务和隔离级别，紧接着必须讲 MVCC？
① 提出目标：事务 ACID 的 I（隔离性）
多个事务同时读写一行数据时，不能乱套（不能发生脏读、不可重复读、幻读）。
② 划分档位：4 大隔离级别（What）
SQL 标准定了 RU / RC / RR / Serializable 四个档位，但这只是“对外承诺的效果”，没说代码怎么写。
③ 笨办法的死穴：全靠加锁会卡死
如果为了隔离，别人改 id=1 时连普通 SELECT 都加锁排队（像 Serializable 那样），并发性能直接雪崩！
④ 终极解法：MVCC 登场（How）
为了在 RC（读已提交） 和 RR（可重复读） 下做到「既满足隔离承诺，普通 SELECT 又完全不加锁」，InnoDB 发明了 MVCC！
🎯 四大隔离级别与 MVCC 的精确对应关系：
• 读未提交 (RU)：完全不用 MVCC，直接裸读内存最新页（所以有脏读）。
• 读已提交 (RC) & 可重复读 (RR)：普通 SELECT 全靠 MVCC 实现！两者的唯一区别就是生成 ReadView 快照的时机不同（RC 每次 SELECT 都新拍一张，RR 只在第一次 SELECT 拍一张后面一直复用）。
• 可串行化 (Serializable)：放弃无锁 MVCC，普通 SELECT 全部退化为加共享锁（FOR SHARE）排队。

📸 MVCC 的本质：用「3 个数据结构」代替整表拷贝

搞懂了上面的关系，你就明白为什么必须拆解 MVCC（Multi-Version Concurrency Control，多版本并发控制）了——它是兑现 RC 和 RR 隔离级别的核心引擎。为了做到“别人正在改这一行，我普通 SELECT 不用等锁也能读到一致的旧版本”，InnoDB 用了 3 个实打实的数据结构：

① 每行自带 2 个隐藏列：DB_TRX_ID + DB_ROLL_PTR
• DB_TRX_ID（6 字节）：记录最后一次修改这行数据的事务 ID。
• DB_ROLL_PTR（7 字节）：回滚指针，就像单向链表的 next 指针，指向这行数据在 undo log 里的上一个旧版本。
② Undo Log 历史版本单向链表（Version Chain）
每次 UPDATE 前，先把旧值写进一条 undo log，再用 DB_ROLL_PTR 指针把「数据页最新行 ──▶ Undo 旧版 V2 ──▶ Undo 更老版 V1」串成一条单向链表。
③ ReadView 读视图结构体（一把只有 4 个字段的“水位尺”）
执行普通 SELECT 时瞬间创建的轻量结构体，记录拍照那一刻「哪些事务还没提交 (m_ids)」以及「高低水位事务 ID」，用来顺着链表判断哪一版数据对你可见。

⚡ 读已提交 (RC) vs 可重复读 (RR) 在代码上只差一行

• 读已提交 (RC)：每次执行 SELECT 时，都重新创建一个新的 ReadView。
• 可重复读 (RR)：只在第一次 SELECT 时创建 ReadView，本事务后续所有普通查询都一直复用这同一个 ReadView！

🔒 当前读 vs 快照读：更新时绝不能拿旧余额

普通 SELECT 是快照读（走 MVCC 链表不加锁）；而 SELECT ... FOR UPDATE、SELECT ... FOR SHARE、UPDATE、DELETE 是当前读，必须直接读取并锁定链表头部的最新记录。

⚠️ 为什么长事务会拖垮数据库？只要还有一个老事务的 ReadView 没销毁，比它晚产生的 Undo Log 链表节点就不敢被清理回收，会导致 Undo 表空间暴涨。官方文档 ↗

🪪 04.3 第一步（先懂尺子）：ReadView 的 4 个核心字段、数轴水位尺与四步判定漏斗

InnoDB 源码 read0types.h

要看懂 MVCC 是怎么选版本的，必须先认识 ReadView 这把“可见性尺子”。假设当前时刻系统里：事务 1~49 都已提交；事务 50、60 正在执行还没提交；事务 55、65 开启得晚但已经抢先提交了；本事务自己的 ID 是 70；系统下一个准备发出去的事务 ID 是 80。此时你执行 SELECT 拍下一张 ReadView，它的内部结构如下：

📦 class ReadView { ... } 内存结构（4 个核心成员变量） 拍照瞬间 O(1) 记录边界，绝不拷贝表数据
字段 ① 本事务 ID
m_creator_trx_id
= 70 （只读为 0）
含义：是谁拍了这张 ReadView 快照。
作用：自己事务改的数据（trx_id == 70），自己当然永远能看见！
字段 ② 未提交活跃名单
m_ids (活跃数组)
[ 50, 60 ]
含义：拍照那一刻，系统里已开启但还没 COMMIT 的所有读写事务 ID 有序数组。
作用：名单里的事务一律算“未提交”，不可见！
字段 ③ 低水位 min_trx_id
m_up_limit_id
= 50 （m_ids 最小值）
含义：活跃数组里的最小事务 ID。
作用：凡是 trx_id < 50 的事务，说明拍照前 100% 早已提交，直接放行可见！
字段 ④ 高水位 max_trx_id
m_low_limit_id
= 80 （下个待分配ID）
含义：拍照时系统的下一个待分配事务 ID（注意不是 m_ids 最大值！）。
作用：凡是 trx_id ≥ 80 的，全是拍照后才开启的未来事务，直接拦截不可见！
📏 把全部事务 ID 摊开在一条「水平数轴」上：高低水位线把世界切成了 3 段
🟢 左段：老事务区 trx_id < 50
在低水位 m_up_limit_id (50) 左边，拍照前全部早已提交。
trx=10 ✅可见 trx=30 ✅可见 trx=49 ✅可见
🟡 中段：混合核查区 50 ≤ trx_id < 80
夹在低水位 50 与高水位 80 之间，查它在不在 m_ids[50,60] 里：
50 (在m_ids) ❌ 55 (已提交) ✅ 60 (在m_ids) ❌ 70 (本事务) ✅
🔴 右段：未来事务区 trx_id ≥ 80
在高水位 m_low_limit_id (80) 右边，拍照后才开启，哪怕已提交也不可见！
trx=80 ❌不可见 trx=95 ❌不可见

Step 0 · 初始状态：事务 10 插入一行初始数据并提交 SQL: INSERT INTO users VALUES (1, '小林', 100); COMMIT;（事务 ID = 10）

② 再把数据页里的最新行覆盖成 余额=200，把隐藏列 DB_TRX_ID 改成 20，并把 DB_ROLL_PTR 指向 0x01：

余额 = 200 ｜ DB_TRX_ID = 20 (未提交) ｜ PTR = 0x01
──顺 0x01 找──▶
🕰️ 链表第 2 节（Undo 0x01 · V1）
余额 = 100 ｜ DB_TRX_ID = 10 (已提交) ｜ PTR = NULL
👀 此时你的查询事务 Q 进来执行【第 1 次 SELECT balance WHERE id = 1】：
• 无论你是 RC 还是 RR，第 1 次查询都会拍下快照 ReadView #1：此时未提交的活跃事务有 20 和 30，所以 m_ids = [20, 30]，低水位 = 20。
• 顺链表比对：先看链表第 1 节 trx_id = 20（在 m_ids[20,30] 里，未提交 ❌ 不可见） ──▶ 顺着 0x01 跳到第 2 节 trx_id = 10（10 < 低水位 20，已提交 ✅ 可见）！

范围共享锁挡住 C 的插入。
T5 · 考题3b
【幻读·当前读】 		若事务 A 用加锁当前读查区间：
SELECT * WHERE id > 0
FOR UPDATE;
怎么防止别人往区间插新行？ 		❌ RU / RC 只有「记录锁 (Record Lock)」，没有间隙锁！
RC 只锁住已存在的行，锁不住行与行之间的“空隙”，别人依然能 INSERT id=5 进区间 → 当前读发生幻读。 		✅ 临键锁 Next-Key Lock！
办法：记录锁 + Gap 间隙锁，把已有记录和区间空隙一起锁死，别人 INSERT 直接阻塞等待！ 		✅ 同样加 Next-Key 锁
连普通 SELECT 都加锁排队。
🎯 面试秒答公式（背这一句就够）：
InnoDB 解决隔离级别问题靠两条腿走路 —— ① 普通查询（快照读）靠 MVCC 控制 ReadView 拍照时机（RC 每次拍新照防脏读，RR 复用首张照防不可重复读与快照幻读）；② 加锁读写（当前读）靠 Next-Key Lock（记录锁 + Gap 间隙锁）封死区间缝隙防当前读幻读！
