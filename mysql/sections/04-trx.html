04.1 · 事务基础：ACID 四大特性、autocommit 自动提交边界与 SAVEPOINT 局部回滚

04.1 事务 ACID 特性与显式事务控制语法

事务（Transaction）是将多步数据库读写操作捆绑成一个不可分割的逻辑工作单元。InnoDB 存储引擎完整实现了事务的 ACID 四大特性：原子性（Atomicity，靠 Undo Log 实现要么全成功要么全回滚）、一致性（Consistency，事务前后业务约束守恒）、隔离性（Isolation，靠 MVCC + 锁 防止并发事务互相干扰）、持久性（Durability，靠 Redo Log + Doublewrite 保证提交后掉电不丢）。

💸 transfer_trx.sql · 标准显式事务与 SAVEPOINT 保存点控制 
-- 1. 显式开启事务（START TRANSACTION 与 BEGIN 等价）
-- 如需开启事务瞬间立即拍下一致性读快照，可使用：
-- START TRANSACTION WITH CONSISTENT SNAPSHOT;
START TRANSACTION;

-- 2. 第一步：扣减转出方（id=1）余额 50 元，同时校验余额充足防扣成负数
UPDATE `users` SET `balance` = `balance` - 50.00
WHERE `id` = 1 AND `balance` >= 50.00;

-- 3. 第二步：增加转入方（id=2）余额 50 元
UPDATE `users` SET `balance` = `balance` + 50.00
WHERE `id` = 2;

-- 4. 可选：为非核心支线操作（如写积分日志）设立保存点 SAVEPOINT
SAVEPOINT `sp_bonus`;
INSERT INTO `bonus_logs` (`user_id`, `points`) VALUES (1, 5);
-- 若积分发放失败，可仅回滚到保存点而不影响前面的主转账逻辑：
-- ROLLBACK TO SAVEPOINT sp_bonus;

-- 5. 全部成功后提交事务（若中途异常则执行 ROLLBACK; 整体回滚）
COMMIT;
日常事务控制的 3 个关键注意事项
  • autocommit = 1（默认开启）：如果不写 BEGIN / START TRANSACTION，你发出的每一条单独的 INSERT / UPDATE / DELETE 都会被 MySQL 自动包裹成一个独立的小事务并在执行完毕后立即提交。
  • 与 PostgreSQL 的报错差异：在 MySQL 的同一个 BEGIN ... COMMIT 事务块内，如果中间某条普通 SQL 报错（例如唯一键冲突 Duplicate entry），MySQL 默认只回滚报错的那一条语句，而不会自动中止整个事务；若应用层捕获异常后忘记执行 ROLLBACK 而是直接调了 COMMIT，前面已成功的语句依然会被提交。因此后端代码的 catch / defer 分支中必须显式执行 ROLLBACK（注：唯独发生死锁或 innodb_rollback_on_timeout=ON 时，InnoDB 会主动回滚整个事务）。
  • 严禁在事务块内夹杂远程 RPC / HTTP 调用：先在事务外完成外部第三方校验，最后只把纯粹的 SQL 操作放进毫秒级短事务中提交，防止长事务拖垮行锁与回滚段。
04.2 · 隔离级别：脏读、不可重复读、幻读与四大隔离级别表现对比

04.2 三大并发读异常与四大事务隔离级别

当多个事务同时读写同一批数据时，若缺乏隔离控制，会依次出现三类并发读异常：① 脏读（Dirty Read：读到了其他事务尚未 COMMIT 的未提交修改）、② 不可重复读（Non-Repeatable Read：同一事务内先后两次读同一行，因别的事务提交了 UPDATE 而读到不同的列值）、③ 幻读（Phantom Read：同一事务内按相同范围条件查询，因别的事务提交了 INSERT / DELETE 而导致返回的行数多出或少掉“幻影行”）。

不同于 PostgreSQL 与 Oracle 默认采用 READ COMMITTED，MySQL InnoDB 的默认隔离级别是 REPEATABLE READ（可重复读，简称 RR）：

事务隔离级别 脏读 不可重复读 幻读（InnoDB） 日常表现与工程适用场景
1. READ UNCOMMITTED
（读未提交，简称 RU）		 可能发生 可能发生 可能发生 直接读取数据页上未提交的最新修改，毫无隔离性保障，生产环境不使用。
2. READ COMMITTED
（读已提交，简称 RC）		 已解决 可能发生 可能发生 每条 SELECT 语句执行前都会重新生成一份最新快照，只要别的事务已提交就能立刻读到；且在 RC 下 InnoDB 几乎不加间隙锁（Gap Lock），死锁概率更低，适合大量互联网高并发 OLTP 业务。
3. REPEATABLE READ
（可重复读，MySQL 默认）		 已解决 已解决 已解决（快照读靠 MVCC，当前读靠临键锁） 事务内第一次执行普通 SELECT 时生成快照，并在整个事务期间复用该快照，保证同一事务内无论查多少次结果完全一致，适合对账、财务报表与默认业务场景。
4. SERIALIZABLE
（可串行化）		 已解决 已解决 已解决 InnoDB 会将所有普通 SELECT 自动转化为加共享锁的 SELECT ... FOR SHARE，读写完全互斥阻塞，吞吐量大幅下降。
isolation_cmd.sql · 查看与切换 MySQL 8.0+ 事务隔离级别 
-- 1. 查看全局与当前会话的事务隔离级别（MySQL 8.0+ 变量名为 transaction_isolation）
SELECT @@global.transaction_isolation, @@session.transaction_isolation;

-- 2. 仅切换当前会话的隔离级别为 READ COMMITTED（读已提交）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
04.3 · 并发扣减实战：原子条件更新、FOR UPDATE 悲观锁、乐观锁 CAS 与双会话验证

04.3 高并发防超卖三大标准模式与双终端实验

在高并发抢购扣库存、余额扣减或优惠券领用场景中，切忌在代码里先写一条普通 SELECT balance FROM users WHERE id = 1，在应用内存中算出 new_balance = balance - 50，再执行 UPDATE users SET balance = new_balance WHERE id = 1——因为普通 SELECT 是不加锁的“快照读”，两个并发请求会同时读到相同的旧余额（如 100），各自减 50 后都写回 50，导致 100 元被扣了两次却还剩 50 元（丢失更新 Lost Update）。生产中应根据业务复杂度选择以下三种正确模式之一：

anti_oversold.sql · 高并发扣减库存/余额的三种正确写法 
-- ========= 模式一：单条原子增量 UPDATE（最轻量，90% 简单扣减首选） =========
-- InnoDB 执行 UPDATE 时会自动获取最新 committed 行（当前读）并加行级排他锁，
-- 应用层只需检查返回的 Affected Rows 是否等于 1 即可判断扣减成功：
UPDATE `products`
SET `stock` = `stock` - 1
WHERE `id` = 1001 AND `stock` >= 1;

-- ========= 模式二：SELECT ... FOR UPDATE 悲观排他锁（复杂多表校验） =========
-- 当扣减前必须先读出旧值做复杂的阶梯费率计算或多表联动校验时使用：
START TRANSACTION;
-- FOR UPDATE 触发“当前读”并给 id=1 加排他行锁，其他并发事务在此排队等待
-- MySQL 8.0+ 支持追加 NOWAIT（锁冲突立即报错返回）或 SKIP LOCKED（跳过已锁行）
SELECT `id`, `balance` FROM `users` WHERE `id` = 1 FOR UPDATE;
-- 应用层校验通过后执行更新并提交，释放行锁
UPDATE `users` SET `balance` = `balance` - 50.00 WHERE `id` = 1;
COMMIT;

-- ========= 模式三：version 版本号乐观锁（读多写少、短平快无锁重试） =========
-- 1. 先普通查询拿到当前余额与版本号（假设读出 balance=100, version=3）
-- 2. 更新时校验 version 仍为 3，并将 version + 1；若 Affected Rows = 0 则重试
UPDATE `users`
SET `balance` = `balance` - 50.00, `version` = `version` + 1
WHERE `id` = 1 AND `version` = 3 AND `balance` >= 50.00;

双终端会话实验：亲眼验证「快照读」与「当前读」

打开两个 mysql 终端窗口连接同一个库（假设初始 id=1 的 balance = 100.00），按时间顺序依次执行以下步序，直观感受默认 REPEATABLE READ 下的行为：

时刻 终端会话 A（开启长事务观察） 终端会话 B（并发修改并提交）
T1 BEGIN;
SELECT balance FROM users WHERE id = 1;
读出 100.00（拍下 RR 快照）
T2 UPDATE users SET balance = balance + 50 WHERE id = 1;
自动提交，真实数据已变为 150.00
T3 ① 普通查询（快照读）：
SELECT balance FROM users WHERE id = 1;
依然返回 100.00（可重复读生效）
T4 ② 加锁查询或更新（当前读）：
SELECT balance FROM users WHERE id = 1 FOR UPDATE;
直接读出最新已提交值 150.00；随后 COMMIT;
底层原理延伸：为什么在 T3 时刻普通 SELECT 能读到历史值 100.00，而 T4 时刻加 FOR UPDATE 又能立刻穿透快照读到 150.00？想深入 ReadView 四大水位字段、Undo Log 历史版本链以及 Record Lock / Gap Lock / Next-Key Lock 的加锁退化推导，可点击查看 核心原理篇 · 04 MVCC 与 ReadView 状态机 ↗。
