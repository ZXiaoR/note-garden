06.1 用户注册防重复：唯一索引 + 捕获重复键错误

业务需求：新用户用手机号注册账号（或每人限领 1 张新人券），弱网下用户连点两次注册按钮，绝不能在数据库里插入两条相同手机号的记录。

register_dedup.ts · 表唯一索引 + Node.js / Go 捕获 1062 错误码 
-- 【表设计与索引】在 phone 列建立唯一索引 uk_phone（适用 8.0 / 8.4）
CREATE TABLE `accounts` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `phone`      VARCHAR(20)     NOT NULL COMMENT '注册手机号',
  `nickname`   VARCHAR(50)     NOT NULL DEFAULT '',
  `created_at` DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY `uk_phone` (`phone`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

// 【后端代码（Node.js mysql2）】直接 INSERT，捕获 MySQL 错误码 1062
export async function registerByPhone(phone: string, nickname: string) {
  try {
    const [res] = await pool.execute(
      'INSERT INTO accounts (phone, nickname) VALUES (?, ?)',
      [phone, nickname]
    );
    return { ok: true, userId: res.insertId };
  } catch (err: any) {
    // MySQL 唯一键冲突固定错误号：errno === 1062 (code === 'ER_DUP_ENTRY')
    // Go 对应判断：var me *mysql.MySQLError; errors.As(err, &me) && me.Number == 1062
    if (err?.errno === 1062) {
      return { ok: false, reason: 'PHONE_ALREADY_REGISTERED' };
    }
    throw err;
  }
}
常见坑与工程细节
  • 为什么“先 SELECT 查不存在、再 INSERT”防不住并发：两个请求在同一毫秒到达时，普通 SELECT 都看到结果为 0 行，随后双双执行 INSERT——若没有数据库的 UNIQUE KEY 物理兜底，必然插进两条重复记录。
  • 频繁冲突会导致自增 ID 跳号：在 MySQL 8.0 默认 innodb_autoinc_lock_mode = 2 下，INSERT 因 1062 冲突失败或执行 INSERT IGNORE / ON DUPLICATE KEY UPDATE 时，已经申请消耗掉的自增 id 不会退回（出现 1, 2, 5 跳号）。如果接口属于高频重复上报场景，可先做一次轻量普通查询拦截绝大部分已存在请求，仍用唯一索引兜底最后 1% 的并发竞态。

背后的原理：两条并发 INSERT 撞上同一个唯一索引键时，InnoDB 如何用记录锁与共享锁保证互斥？详见 《核心原理篇 · 05.3 唯一索引加锁与冲突规则》。

06.2 · 百万级列表翻页：LIMIT 1000000, 20 慢查询根因、游标分页与延迟关联

06.2 订单列表分页：深分页改游标与延迟关联

业务需求：电商订单表已有数百万行，App 端买家下滑加载历史订单，或商家运营后台翻到第 50000 页（LIMIT 1000000, 20）时接口耗时数秒甚至超时。根因在于：MySQL 并不是直接跳过前 100 万行，而是顺着二级索引查出前 1000020 个主键 ID，老老实实回表 1000020 次取出整行交给 Server 层，最后把前 100 万行全部丢弃。按产品交互形态对应两种标准解法：

order_pagination.sql · 游标分页（下拉瀑布流）与延迟关联（跳页码） 
-- 【表与联合索引】在 orders 表建立 KEY idx_shop_id (shop_id, id)
-- ❌ 慢查询原写法：先回表 1000020 次取整行，再丢弃前 1000000 行
SELECT `id`, `order_no`, `buyer_id`, `pay_amount`, `status`
FROM `orders`
WHERE `shop_id` = 88 ORDER BY `id` DESC LIMIT 1000000, 20;

-- ✅ 方案一：游标分页 / Seek Method（App 下拉加载与全表分批导出首选，恒定 < 2ms）
-- 前端传回上一页最后一条订单的 id（如 last_id = 420580），直接从该位置顺着 B+ 树往后取 20 条：
SELECT `id`, `order_no`, `buyer_id`, `pay_amount`, `status`
FROM `orders`
WHERE `shop_id` = 88 AND `id` < 420580
ORDER BY `id` DESC LIMIT 20;

-- ✅ 方案二：延迟关联 / Deferred Join（PC 后台必须保留“跳第 N 页”按钮时的改写）
-- 子查询只查主键 id，100% 走覆盖索引（Using index，0 次回表）快速滑过前 100 万个 id，
-- 拿到最终 20 个 id 后再与原表 INNER JOIN，把回表次数从 1000020 次降到仅 20 次：
SELECT `o`.`id`, `o`.`order_no`, `o`.`buyer_id`, `o`.`pay_amount`, `o`.`status`
FROM `orders` `o`
INNER JOIN (
  SELECT `id` FROM `orders`
  WHERE `shop_id` = 88
  ORDER BY `id` DESC LIMIT 1000000, 20
) AS `page_ids` ON `o`.`id` = `page_ids`.`id`
ORDER BY `o`.`id` DESC;
常见坑与复合游标写法
  • 按非唯一字段（如 created_at）做游标分页会漏数据：如果同一秒有 5 笔订单，上一页恰好截断在第 2 笔，下一页写 created_at < last_time 会把同秒剩下的 3 笔漏掉。正确做法是把唯一主键拼进复合游标：索引建 (shop_id, created_at, id)，条件写 WHERE shop_id = ? AND (created_at < ? OR (created_at = ? AND id < ?)) ORDER BY created_at DESC, id DESC LIMIT 20。
  • 延迟关联外层别漏写 ORDER BY：INNER JOIN 后输出顺序不保证与子查询一致，外层末尾记得补上 ORDER BY o.id DESC；同时业务产品侧通常限制最大跳页深度（如仅开放前 100 页，更早历史引导按日期筛选）。

背后的原理：二级索引叶子节点存了什么、为什么每次回表都是一次聚簇树查找？详见 《核心原理篇 · 02.1 B+ 树结构与容量推导》。

06.4 · 注销重注册冲突：软删除标记设计与 UNIQUE KEY (phone, deleted_at) 标准解法

06.4 软删除与唯一索引冲突怎么处理

业务需求：为保留历史订单关联与审计线索，账号注销或商品下架通常不做物理 DELETE，而是做软删除（Soft Delete，又称逻辑删除）。但如果表上有 UNIQUE KEY uk_phone (phone)，用户注销旧号后再用同一个手机号重新注册，就会撞上旧软删记录报 1062 Duplicate entry；若改成联合唯一索引 UNIQUE(phone, is_deleted)（is_deleted 取 0/1），该手机号第二次注销时又会因为出现两条 ('138...', 1) 而报错。

soft_delete_unique.sql · deleted_token（存 0 或已删主键 id）标准解法 
-- 【表设计】用 deleted_id 代替布尔 is_deleted：
-- 活跃记录固定为 0；软删除时将其更新为自身唯一的自增主键 id（或毫秒时间戳）
CREATE TABLE `users` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `phone`      VARCHAR(20)     NOT NULL,
  `deleted_id` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0=正常，>0=已注销(填自身id)',
  `deleted_at` DATETIME        DEFAULT NULL COMMENT '注销时间',
  -- 活跃状态下同一 phone 只能有一条 (phone, 0)；每次注销都是不同的 (phone, id)，支持无限次重绑
  UNIQUE KEY `uk_phone_alive` (`phone`, `deleted_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 1. 正常登录查询（务必带上 deleted_id = 0，正好命中联合唯一索引完整两列）
SELECT `id`, `phone` FROM `users` WHERE `phone` = '13800138000' AND `deleted_id` = 0;

-- 2. 注销账号（软删除）：把 deleted_id 设为自身主键 id，腾出 ('13800138000', 0) 槽位
UPDATE `users`
SET `deleted_id` = `id`, `deleted_at` = NOW()
WHERE `id` = 105 AND `deleted_id` = 0;
为什么不推荐用 deleted_at DEFAULT NULL 拼唯一索引？
  • NULL != NULL 会让活跃记录失去唯一约束：在 MySQL 唯一索引中，多个 NULL 互不相等。如果把活跃记录设为 deleted_at = NULL 并建 UNIQUE(phone, deleted_at)，那么两个未注销的正常用户可以同时插入两条 ('13800138000', NULL) 而不报错，彻底把防重废掉了！因此活跃态必须用非空确定值 0。
  • 防漏写过滤条件：全库引入软删除后，任何业务查询和 JOIN 一旦漏写 AND deleted_id = 0 就会把已删除数据漏给前端；若软删比例极高拖慢索引，更干净的做法是“物理删除原表行 + 同事务写入 users_deleted_archive 历史归档表”。

背后的原理：InnoDB 行记录头如何存放 NULL 位图与删除标记位？详见 《核心原理篇 · 00.3 行记录格式与隐藏列》。

06.5 · 订单生命周期防护：有限状态机建模 + WHERE 旧状态条件更新防乱序覆盖

06.5 订单状态流转：状态机 + 条件更新

业务需求：一笔电商订单会经历「待支付 → 已支付 → 已发货 → 已完成」或「已取消」。线上经常遇到两类并发竞态：① 微信/支付宝异步回调在网络超时时连发两次“支付成功”；② 第 30 分钟整点定时取消任务刚把订单改为“已取消”，晚到半秒的支付回调又到达，不能直接把已取消订单强行覆盖为“已支付”。核心解法是把合法前置状态写进 UPDATE ... WHERE status = 旧状态：

order_state_cas.sql · 订单表索引与带前置状态守卫的幂等更新 
-- 【表与索引】order_no 建唯一索引 uk_order_no (order_no)
-- 1. 支付回调处理：必须同时匹配 order_no 且当前 status = 1 (待支付)
UPDATE `orders`
SET `status` = 2, `trade_no` = ?, `paid_at` = NOW()
WHERE `order_no` = ? AND `status` = 1;

-- 【后端根据 affectedRows 分支裁决】：
-- • affectedRows === 1 ──► 本次成功流转为已支付，继续触发发货/发券
-- • affectedRows === 0 ──► 再查一次当前 status：
--     若已是 2 (已支付)：说明是重复回调，直接返回“处理成功”（幂等通过）
--     若已是 5 (已取消)：说明撞上超时关单后晚到的付款，自动走原路退款流程！
常见坑：绝对不要裸写 SET status = 2 WHERE order_no = ?

如果不带 AND status = 1，一旦订单超时取消并退回了库存，半秒后晚到的支付回调又把订单状态硬改成 2（已支付），就会出现“库存已退给别人买走、但这笔单也变成了已支付”的严重资损。加上前置状态条件后，InnoDB 会在 uk_order_no 唯一索引记录上加排他锁串行执行，“支付”与“取消”必有一方返回 affectedRows = 0。

背后的原理：UPDATE 如何触发当前读并锁住唯一索引记录？详见 《核心原理篇 · 04.3 当前读与锁协同》。

06.6 · 运营数据报表：按天交易额汇总与每类目销量 Top N（窗口函数实战）

06.6 统计报表：按天汇总与每类目 Top N

业务需求：运营看板需要展示两张核心图表：① 最近 7 天每天的已支付订单笔数与实付总额（GMV，Gross Merchandise Volume，商品交易总额）；② 每个商品类目下累计销量排名前 3 的热销商品。

analytics_report.sql · 按天分组汇总与窗口函数分组 Top 3（8.0+） 
-- 【索引设计】orders 建 idx_paid_amt (paid_at, status, pay_amount)；
--            products 建 idx_cat_sales (category_id, sales DESC)

-- 1. 最近 7 天按日汇总（WHERE 用左闭右开时间区间走索引，SELECT/GROUP BY 再提取日期）
SELECT
  DATE(`paid_at`) AS `stat_day`,
  COUNT(*)        AS `order_cnt`,
  SUM(`pay_amount`) AS `total_gmv`
FROM `orders`
WHERE `paid_at` >= '2026-11-21 00:00:00'
  AND `paid_at` <  '2026-11-28 00:00:00'
  AND `status` IN (2, 3, 4)
GROUP BY DATE(`paid_at`)
ORDER BY `stat_day` ASC;

-- 2. 每个商品类目下销量前 3 名（ROW_NUMBER 严格取 3 条，并列也只取 3 条）
WITH `ranked_sku` AS (
  SELECT
    `category_id`, `id`, `title`, `sales`,
    ROW_NUMBER() OVER (PARTITION BY `category_id` ORDER BY `sales` DESC, `id` ASC) AS `rn`
  FROM `products`
  WHERE `status` = 1
)
SELECT `category_id`, `id`, `title`, `sales`, `rn`
FROM `ranked_sku` WHERE `rn` <= 3;
报表查询的 3 个高频坑
  • 别在 WHERE 里写 DATE(paid_at) BETWEEN ...：对 paid_at 套函数会让索引失效变全表扫描；WHERE 保持原始列区间过滤，只在 SELECT / GROUP BY 里算 DATE(paid_at) 即可命中覆盖索引。
  • 某天 0 单时折线图断档：数据库里没订单的那天 GROUP BY 不会凭空造出一行 0，由后端代码按日期数组补齐缺失天的 0 最简单清晰。
  • 千万级大表勿在交易主库实时跑月度/年度全量聚合：重度统计 SQL 应路由到只读从库，或者每天凌晨用定时任务把前一天汇总结果写入按日预聚合表 daily_order_stats，白天看板查预聚合表只需 1 毫秒。

06.7 · 树形层级存储：多级商品分类 / 社区评论回复楼层的邻接表与递归 CTE

06.7 树形分类与评论楼层：邻接表 + 递归 CTE

业务需求：电商三级/多级商品分类（数码 → 电脑外设 → 机械键盘），或社区帖子下的多级嵌套评论回复，如何用一张表存下父子关系，并用一条 SQL 查出完整子树或面包屑导航路径？

comment_tree.sql · 邻接表 parent_id 建模与递归 CTE 查子树（8.0+） 
-- 【表设计与索引】parent_id = 0 表示一级顶层评论；建联合索引 idx_post_parent
CREATE TABLE `comments` (
  `id`        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `post_id`   BIGINT UNSIGNED NOT NULL COMMENT '所属帖子ID',
  `parent_id` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '父评论ID(0为顶层)',
  `content`   VARCHAR(500)    NOT NULL,
  KEY `idx_post_parent` (`post_id`, `parent_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 向下递归查出某条一级评论（id = 500）下的所有子孙回复及嵌套深度（限最多 10 层）
WITH RECURSIVE `reply_tree` AS (
  SELECT `id`, `parent_id`, `content`, 1 AS `depth`, CAST(`id` AS CHAR(200)) AS `path`
  FROM `comments` WHERE `post_id` = 99 AND `id` = 500
  UNION ALL
  SELECT `c`.`id`, `c`.`parent_id`, `c`.`content`, `t`.`depth` + 1,
         CONCAT(`t`.`path`, '/', `c`.`id`)
  FROM `comments` `c`
  INNER JOIN `reply_tree` `t` ON `c`.`post_id` = 99 AND `c`.`parent_id` = `t`.`id`
  WHERE `t`.`depth` < 10
)
SELECT * FROM `reply_tree` ORDER BY `path` ASC;
常见坑与替代建模选型
  • 锚点列必须 CAST 预留宽度：如果锚点查询直接写 CAST(id AS CHAR)，MySQL 会按首行长度定死列宽（如 3 个字符），下一层 CONCAT('500/501') 就会因超长报错 Data too long for column 'path'，务必写明 CAST(id AS CHAR(200))。
  • 防止父子环路死循环：更新分类的 parent_id 时必须在代码里禁止“把节点移动到它自己的子孙节点下”，并在 SQL 中加 WHERE t.depth < 10 兜底。
  • 海量评论为什么常改用“两级扁平模型”或“路径列”：像抖音/小红书评论区通常设计为 root_id（所属一级评论 ID）+ reply_to_user_id 两层拍平展示，翻页只需普通索引 WHERE root_id = ? LIMIT 20，连递归都不需要。

背后的原理：递归迭代每一步如何通过索引嵌套循环关联子行？详见 《核心原理篇 · 03.2 连接算子执行过程》。

06.8 · MySQL × Redis 协同：旁路缓存（Cache-Aside）先更新数据库再删除缓存

06.8 缓存一致性：先更新数据库，再删除缓存

业务需求：商品详情缓存在 Redis 里扛高频读，商家在后台修改了 MySQL 里的商品价格，怎么保证买家尽快看到新价格、不把旧价格长期留在缓存里？标准工程模式是 Cache-Aside（旁路缓存）：读请求先查缓存、未命中查库回填；写请求「先更新 MySQL 事务提交，再删除 Redis 缓存键」（完整时序图与代码防护见 Redis 笔记 · 03.1 旁路缓存与双写一致性 ↗）：

update_price_cache.ts · 先提交 MySQL 修改，再 DEL 失效缓存 
export async function updateProductPrice(skuId: number, newPrice: string) {
  // 1. 先更新 MySQL 权威账本并完成提交（autocommit=1 单语句自动提交）
  await pool.execute(
    'UPDATE products SET price = ?, updated_at = NOW() WHERE id = ?',
    [newPrice, skuId]
  );

  // 2. 再删除 Redis 缓存（而非 SET 更新缓存，防并发写乱序覆盖）
  const cacheKey = `product:detail:${skuId}`;
  try {
    await redis.del(cacheKey);
  } catch (err) {
    // 3. 若删缓存网络抖动报错，投递重试队列（或靠缓存 5~30 分钟 TTL 兜底）
    await retryQueue.push({ action: 'DEL_CACHE', key: cacheKey });
  }
}
两个关键追问（为什么这样定顺序）
  • 为什么删缓存而不直接写新缓存？两个并发改价请求 A（改 100）和 B（改 80），若数据库先 A 后 B，更新缓存却因网络抖动变成先 B 后 A，缓存就会永久停留在错误的 100；而直接 DEL 让下次读按需从数据库加载最新值则无此隐患。
  • 为什么不能「先删缓存、再更数据库」？删缓存只需 0.5ms，更新磁盘事务可能要 10ms——在这 10ms 空窗期内只要来一个并发读请求发现缓存空了，就会去数据库读出未提交前的旧价格重新塞回缓存，大概率造成脏回填。

背后的原理：大型系统如何通过 Canal 订阅 MySQL binlog 异步删缓存做到解耦重试？详见 《核心原理篇 · 06.3 主从复制与缓存双写一致性》。

06.9 · MySQL × 消息队列协同：同库事务写本地消息表（Transactional Outbox）保证不丢消息

06.9 下单与发消息的一致性：本地消息表（Outbox）

业务需求：买家创建订单（写 MySQL）后，必须发一条消息到 Kafka 通知营销服务发积分、通知库存服务锁物流单。如果“先提交订单事务再发 MQ”，进程刚提交完就重启会导致消息漏发；如果“把发 MQ 塞进数据库事务里面”，MQ 网络抖动 3 秒又会把数据库连接池占满拖死全站。最通用的解法是利用 MySQL 本地单库 ACID 事务，把订单记录和待发消息一起写进同一个库的两张表里（完整后台轮询 Relay Worker 代码见 消息队列笔记 · 03.5 本地消息表实战 ↗）：

outbox_tx.sql · 同库本地事务原子写入业务表 + outbox_messages 表 
-- 【本地消息表设计】建联合索引 idx_status_next (status, next_retry_at) 供轮询
CREATE TABLE `outbox_messages` (
  `id`            BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `biz_key`       VARCHAR(64)      NOT NULL COMMENT '业务单号(如order_no)',
  `topic`         VARCHAR(64)      NOT NULL,
  `payload`       JSON             NOT NULL,
  `status`        TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0待发,1已发,2告警',
  `retry_count`   TINYINT UNSIGNED NOT NULL DEFAULT 0,
  `next_retry_at` DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY `idx_status_next` (`status`, `next_retry_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 【下单主链路事务】零外部网络调用，几毫秒内同生共死提交：
START TRANSACTION;
  INSERT INTO `orders` (`order_no`, `user_id`, `pay_amount`, `status`)
  VALUES ('ORD20261128001', 1001, 199.00, 1);

  INSERT INTO `outbox_messages` (`biz_key`, `topic`, `payload`)
  VALUES ('ORD20261128001', 'trade.order.created',
          '{"orderNo":"ORD20261128001","userId":1001,"amount":"199.00"}');
COMMIT;
后台投递与清理的 3 个关键坑
  • 多实例并发轮询防重复捞取：如果部署了多台投递 Worker，捞取待发记录时可使用 MySQL 8.0+ 的 SELECT ... FROM outbox_messages WHERE status = 0 AND next_retry_at <= NOW() LIMIT 100 FOR UPDATE SKIP LOCKED，互不阻塞各自认领一批。
  • 下游消费者必须做幂等：若 Worker 发 MQ 成功但准备将 status 改为 1 时断电重启，恢复后会重发一次该消息，下游必须按 biz_key 唯一索引做消费幂等（呼应 06.1）。
  • 定期归档已发送记录：outbox_messages 每天只留最近 3~7 天已发送记录（分批 DELETE ... LIMIT 2000），防止消息表无限膨胀。

本章即时场景题（先想答案，再点击展开）

1. App 端“我的账单明细”按支付时间倒序下拉加载，为什么游标不能只传上一页最后一条的 paid_at，应该传什么？

同一秒内用户可能产生多笔合并拆单支付（paid_at 完全相同）。如果只写 WHERE paid_at < '2026-11-28 12:00:05'，同一秒内还没展示完的其余账单就会被直接跳过漏掉。必须把自增主键拼成复合游标 (last_paid_at, last_id)，写 WHERE user_id = ? AND (paid_at < ? OR (paid_at = ? AND id < ?)) ORDER BY paid_at DESC, id DESC LIMIT 20。

2. 商品 SKU 编码要求店铺内唯一且支持软删除，同事建了 UNIQUE KEY uk_sku (shop_id, sku_code, deleted_at) 并把未删除行的 deleted_at 设为 NULL，上线后会出什么 Bug？

未删除的活跃商品可以直接插入无数条重复的 sku_code 而不报错。因为 SQL 标准中 NULL 与任何值（包括另一个 NULL）都不相等，MySQL 唯一索引允许存在多行 (88, 'SKU001', NULL)。应新增非空列 deleted_id BIGINT NOT NULL DEFAULT 0（活跃为 0，删除填主键 id），建 UNIQUE KEY (shop_id, sku_code, deleted_id)。

3. 订单超时自动取消任务与用户支付成功回调在同一毫秒并发执行，怎么不借助 Redis 分布式锁就能保证数据不错乱？

依靠订单表唯一索引 uk_order_no 上的条件更新互斥即可：支付回调跑 UPDATE orders SET status = 2 WHERE order_no = ? AND status = 1，超时任务跑 UPDATE orders SET status = 5 WHERE order_no = ? AND status = 1。InnoDB 行级排他锁会让两条语句严格一前一后执行，后执行的一方看到 status 已不再是 1，必然返回 affectedRows = 0；若支付回调拿到 0 且查出已变为取消态，触发自动退款即可闭环。
