00.1 · 核心定位：关系型数据库的一句话定义与「请求 → 应用 → 缓存 → MySQL」系统分层

00.1 MySQL 是什么，以及它在系统里的位置

一句话定义：MySQL 是一个开源的关系型数据库管理系统（RDBMS，Relational Database Management System），用二维表和 SQL（Structured Query Language，结构化查询语言）存取结构化数据，并通过 ACID（Atomicity, Consistency, Isolation, Durability，原子性、一致性、隔离性、持久性）事务保证业务账本准确且断电不丢。

在真实的电商、社区或交易系统里，用户账号、商品库存、订单流水和资金余额这些不能出错、不能丢失的核心数据，最终都存放在 MySQL 的磁盘表里。当日常流量不大时，后端应用直接读写 MySQL 即可（单次索引查询通常只需 1 ~ 5 毫秒）；当遇到首页热帖、商品详情等每秒数万次的高频访问（QPS，Queries Per Second，每秒查询率）时，系统会在 MySQL 前面挡一层内存数据库 Redis 吸收热点读请求，未命中缓存或需要修改真实账本时再落回 MySQL：

背后的原理：想了解一条 SQL 发进 MySQL 后在内部如何穿过 Server 层与 InnoDB 存储引擎层，以及内存缓冲池（Buffer Pool）如何加速磁盘读写，可按需查阅 《 核心原理篇 · 01.1 InnoDB 内存与磁盘架构全景》。

00.2 · 技术选型边界：MySQL vs Redis vs MongoDB vs Elasticsearch vs 消息队列横向对比

00.2 什么时候用 MySQL，什么时候用其他数据组件

后端系统没有一种存储能包打天下。最稳妥的工程架构是「用 MySQL 做业务数据的唯一事实来源（Single Source of Truth），再按读写痛点外挂专用组件」：

组件名称 数据组织模型 核心强项 电商 / 社区典型适用场景 什么时候不该用它硬扛
MySQL
（本篇主角）		 二维关系表 + 行记录 + B+ 树索引 完整 ACID 事务、多字段组合筛选、表关联与数据强一致落盘 用户账号、商品 SKU 与库存、交易订单、支付账单、评论主数据 每秒十万级单商品热点轮询、多词分词模糊搜索、TB 级无结构原始埋点日志
Redis ↗ 内存键值对（String / Hash / ZSet 等） 亚毫秒级响应（< 1ms）、单机十万级并发、原生过期时间（TTL）与原子计数 热门商品详情缓存、登录态 Token、短信验证码频控、实时热帖排行榜、分布式锁 不能做复杂多条件 WHERE 过滤；断电或切主可能丢最后约 1 秒数据，不可单独存钱款账本（详见 Redis 笔记）
MongoDB BSON 半结构化文档（免预定义固定列） 字段结构高度灵活、嵌套对象一次读写、水平分片扩展方便 各品类差异极大的商品详情富文档、游戏角色背包快照、IM 聊天历史归档、爬虫原始数据 涉及跨多张表高频关联对账、严苛金融资金转账（优先选关系型数据库；若仅少量动态扩展字段，MySQL 原生 JSON 列即可胜任）
Elasticsearch 倒排索引（分词词项 → 文档 ID 列表） 中文分词全文检索、近义词纠错、几十个筛选项任意组合搜索与多维聚合 电商商品搜索框（「无线静音机械键盘」）、社区帖子全文检索、运营后台几十个条件任意组合查单 不支持严格跨文档回滚事务，写入有约 1 秒 近实时刷新延迟（refresh_interval），绝不能替代 MySQL 做主库，通常订阅 MySQL 变更同步过去
消息队列 ↗
(Kafka / RocketMQ)		 磁盘顺序追加日志流（Topic / Partition） 异步解耦、突发流量削峰填谷、顺序缓冲与多下游独立订阅 下单成功后异步发优惠券/发短信、大促瞬时请求排队写库、收集全站点击流埋点 不是用来随机按 ID 查改某条业务状态的数据库，而是系统之间的异步事件管道（详见 消息队列笔记）

00.3 本笔记知识地图

整份笔记按照「全景定位 → 快速跑起来 → 建表与 SQL 基本功 → 真实业务场景落地 → 上线防线与底层原理」组织。日常写需求可直接翻第 02 ~ 06 章，准备上线与排障看第 07 ~ 08 章，遇到每节末尾的「背后的原理」链接再按需跳入《核心原理篇》：

本章即时场景题（先想答案，再点击展开）

1. 电商商品搜索框需要支持用户输入「静音无线键盘」分词匹配、错别字容错，并按价格/品牌/销量等十几个条件任意组合筛选，直接用 MySQL LIKE '%关键词%' 合适吗？

不合适。MySQL 的 B+ 树索引无法加速前导通配符 LIKE '%关键词%'（会触发逐行全表扫描），也缺乏灵活的中文分词相关度打分能力。正确做法是：商品主数据依然保存在 MySQL 做权威账本，再通过订阅变更将数据异步同步到 Elasticsearch 承担全文检索与多维筛选。

2. 既然 Redis 读写不到 1 毫秒、每秒能扛 10 万并发，为什么不能干脆去掉 MySQL，把用户的账户余额和已支付订单全存在 Redis 里？

主要有三道硬边界：① 数据安全兜底——Redis 异步复制与每秒刷盘在机器断电或主从切换时可能丢失最后约 1 秒写入，且 Redis 事务报错不支持回滚（Rollback），而资金与订单要求零丢失强一致；② 复杂查询能力——Redis 只能按精确 Key 取值，没法直接跑多条件对账或关联统计 SQL；③ 存储成本——全量历史订单高达数百 GB 至数 TB，纯放内存成本极高。

3. 电商商品除了固定的标题、价格、库存外，手机品类有「屏幕尺寸/芯片」，服装品类有「尺码/面料」，一定要为了这些动态属性额外引入一套 MongoDB 吗？

通常不需要。现代 MySQL 8.0 / 8.4 原生提供二进制编码的 JSON 数据类型，支持局部路径提取与修改，还能通过虚拟生成列（Generated Column）给高频检索的 JSON 子字段建 B+ 树索引（详见 02.2）。在单套 MySQL 里同时管好核心交易字段与动态扩展属性，能省去跨两套数据库的运维和双写一致性负担。
