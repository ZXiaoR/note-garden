06 可靠与高可用 · 三大日志到底记了什么？为什么逼出五道兜底防线？ WAL · 2PC · REPLICATION
❓ 06.1 · 执行一条 UPDATE 时，undo、redo、binlog 这三本账本里到底各自记了什么？

📓 06.1 盯住一条 SQL：看三本日志各自写下什么内容

光背“物理日志、逻辑日志”太抽象。假设表 t_user 里 id = 1（小林）原本的余额是 balance = 100，现在事务 trx_id = 20 执行了一条：

UPDATE t_user SET balance = 200 WHERE id = 1; -- 原值 100 改为 200

这一条语句执行时，MySQL 会在底层同时写 3 本完全不同的账本（由上到下拆开看它们的真实内容）：

① undo log（回滚日志 · InnoDB 引擎层）—— 记的是「怎么改回去的旧值」 逻辑日志 · 管原子性 A 与 MVCC
📝 账本里写的具体内容：
[undo_no=1, trx_id=20, table=t_user, pk=(id=1)] 旧值: balance = 100, prev_roll_ptr = 0x0A1
（大意：如果事务 20 要反悔回滚，请把 t_user 表主键 id=1 的 balance 恢复成 100！）
🎯 为什么必须有它？ 一旦事务执行到一半报错或你敲了 ROLLBACK，就靠它把数据改回 100（原子性 A）；同时，其他并发事务执行普通 SELECT 时，也顺着它串成的版本链读历史旧值（第 4 章的 MVCC）。
② redo log（重做日志 · InnoDB 引擎层）—— 记的是「几号物理页哪个偏移量改成了啥」 物理页日志 · 管崩溃恢复持久性 D
📝 账本里写的具体内容：
[LSN=89020, type=MLOG_4BYTES, space_id=5, page_no=38, offset=0x01A0] 新值: 0x000000C8 (即 200)
（大意：根本不管表名叫啥，直接记“把 5 号表空间、第 38 号 16KB 数据页、偏移量 0x01A0 处的 4 字节改成 200”！）
🎯 为什么必须有它？ 改数据时只改了内存 Buffer Pool 里的第 38 号页（脏页），还没刷回磁盘数据文件。万一突然断电内存清空，重启后 InnoDB 就照着这行紧凑的物理指令，把第 38 号页重新改成 200（Crash-Safe 崩溃恢复）。
⚠️ 特点：它是固定大小的环形文件（写满一圈会擦掉已经刷盘的旧日志），只管救命，不能拿来做长久备份！
③ binlog（归档二进制日志 · MySQL Server 层）—— 记的是「逻辑行变更事件」 逻辑归档日志 · 管主从复制与删库恢复
📝 账本里写的具体内容（默认 ROW 格式）：
[Update_rows_event, server_id=1, pos=1542, table=db.t_user] WHERE @1=1, @2=100 SET @1=1, @2=200
（大意：在 db.t_user 表里，把第 1 列=1、第 2 列=100 的这一行，变成了第 1 列=1、第 2 列=200！）
🎯 为什么有了 redo log 还要 binlog？
1. 层级与历史原因：redo log 是 InnoDB 引擎私有的（只看得懂本机的 38 号物理页）；而 binlog 是 MySQL Server 层生成的通用逻辑日志，发给从库（哪怕从库物理页号完全不同）也能照着执行。
2. 保存方式不同：redo log 循环覆盖写，写满就擦；而 binlog 是不断新建文件追加写（mysql-bin.000001 → 000002），专门用来做 主从复制 和 按时间点恢复数据（PITR）。
日志名称 所属层级 文件写入方式 核心记录格式 一言以蔽之的使命
undo log InnoDB 引擎层 回滚段表空间（用完由 purge 线程回收） 逻辑旧版本记录（反向恢复信息） 防事务反悔（回滚） + 给 MVCC 提供历史版本链
redo log InnoDB 引擎层 固定大小环形循环写（checkpoint 推进擦除） 物理页修改（几号表空间、几号页、偏移量改了啥） 防断电丢内存脏页（启动时快速 Crash-Safe 恢复）
binlog Server 层 文件追加写（写满切新文件，按过期策略清理） 逻辑事件（ROW 行变更 / STATEMENT 语句） 把修改同步给从库（主从复制） + 备份后时间点恢复
❓ 06.2 · 为什么 MySQL 要搞出 WAL、双 1、两阶段提交 (2PC)、Doublewrite 这 5 道兜底防线？

🛡️ 06.2 5 次致命故障，逼出 MySQL 的「5 道兜底防线进化史」

你之所以觉得第 06 章概念多（WAL、刷盘双 1、两阶段提交 2PC、双写缓冲 Doublewrite、半同步复制），是因为数据库工程师在对抗「随时可能拔电源、掉盘、崩溃」的物理世界时，每踩一个死穴，就被迫打上一层新补丁。顺着下面 第 1 关 → 第 5 关 往下看，你就彻底明白为什么一个都不能少：

🚧 第 1 关痛点：每次 COMMIT 直接刷 16KB 数据页太慢，不刷又怕断电丢数据！ 逼出兜底 ①：WAL 预写日志
• 为什么不能直接刷数据页？ 一条更新可能改了 3 个索引页，每个页都是 16KB，而且散落在磁盘不同角落（随机 I/O）。如果每次 COMMIT 都去磁盘随机找这几个 16KB 的大块头覆写，数据库每秒只能处理几百单！
• 🛡️ 兜底手段（WAL，Write-Ahead Logging）：内存里只管改 16KB 脏页（先不急着刷回数据文件），提交时只把几十字节的 redo log 顺序追加写到磁盘末尾（顺序 I/O，快几十倍）！只要日志落盘就算提交成功，脏页等后台慢慢刷。
🚧 第 2 关痛点：写日志调了 write()，结果停在操作系统内存缓存里，整机断电还是丢了！ 逼出兜底 ②：“双 1”刷盘配置
• 漏洞在哪？ MySQL 把日志写出去，首先进的是 操作系统内核缓存（OS Page Cache，也是内存！），必须再调用昂贵的 fsync() 才能真正刻进磁盘介质。
• 🛡️ 兜底手段（“双 1”配置 + 组提交 Group Commit）：生产环境将下面两个参数同时设为 1（俗称“双 1”），并把同一时刻并发提交的十几个事务打包做一次 fsync()（组提交），既保住性能又确保断电不丢单：
参数与档位 提交时日志写到哪儿？ 什么故障会丢数据？
innodb_flush_log_at_trx_commit = 1 ⭐默认
+ sync_binlog = 1 ⭐默认		 每次提交都调 fsync() 把 redo 和 binlog 真正刷进物理磁盘 “双 1”黄金兜底：只要磁盘不物理炸裂，断电/崩溃均不丢已提交事务
innodb_flush_log_at_trx_commit = 2 每次提交只 write() 到 OS 内存缓存，后台约每秒 fsync 一次 MySQL 进程挂掉不丢；但操作系统崩溃或机房断电会丢近期提交
innodb_flush_log_at_trx_commit = 0 提交时连 MySQL 自己的 redo log buffer 都不出，后台每秒写并刷 哪怕只是 MySQL 进程自己 crash，也会丢最近约一秒的提交
🚧 第 3 关痛点：写完 redo 还没写 binlog 时断电，主库和从库数据永久不一致了！ 逼出兜底 ③：内部两阶段提交 (2PC)
• 为什么不能简单“先写 A 再写 B”？
- 假如先写完 redo log，还没写 binlog 就断电：重启后主库靠 redo log 把余额恢复成了 200，但因为 binlog 没录上，从库同步过去永远停在 100！
- 假如先写完 binlog，还没写 redo log 就断电：从库收到 binlog 改成了 200，主库重启后却因为没有 redo log 变回了 100！
• 🛡️ 兜底手段（内部两阶段提交 2PC）：把写 redo log 拆成“准备”和“提交”两步，把 binlog 夹在正中间：
Step ①：redo log 写盘 (prepare)
InnoDB 先把修改写进 redo log 并刷盘，打上 prepare（准备态） 标签和事务 ID XID。
Step ②：binlog 写盘（裁决点！）
Server 层把逻辑事件和同一个 XID 写进 binlog 并刷盘。只要这一步成功，事务就铁定算数！
Step ③：redo log 标为 commit
InnoDB 把刚才那条 redo log 状态改为 commit，释放事务锁。
⚡ 万一卡在中间断电怎么救？ 重启时如果发现某条 redo log 停在 prepare 状态，MySQL 就会拿着它的 XID 去查 binlog：如果 binlog 里还没写完 → 直接用 undo log 回滚；如果 binlog 里已经完整写好了 → 自动帮它补上 commit！主库和从库永远 100% 一致！
🚧 第 4 关痛点：后台刷 16KB 脏页到磁盘时，刚写了前 8KB 就断电，烂成半截页连 redo 都救不活！ 逼出兜底 ④：Doublewrite 双写缓冲
• 为什么连 redo log 都失效了？ Linux 文件系统一页通常是 4KB，而 InnoDB 一页是 16KB（要分 4 次写盘）。如果后台线程刷第 38 号数据页时，刚写了前 8KB 就断电了，这叫「部分写失效 / 半截页（Torn Page）」。因为 redo log 只记了“把第 38 号页偏移量 0x01A0 改成 200”，如果第 38 号页本身已经损坏校验不过，redo log 根本没法在一个烂页上重放！
• 🛡️ 兜底手段（Doublewrite 双写文件）：在把 16KB 脏页写回真正的数据文件之前，先顺序写一份完整的 16KB 副本到磁盘上的 doublewrite 双写文件里，然后再去覆写数据文件。万一覆写数据文件中途断电写烂了，重启时直接从 doublewrite 里把完好无损的 16KB 旧页拷过来修复地基，最后再用 redo log 重放最新数据！
🚧 第 5 关痛点：单机防线再完美，万一主库整块硬盘物理烧毁，异步没传完的 binlog 还是会丢！ 逼出兜底 ⑤：主从复制 & 半同步 (Semi-Sync)
• 主从复制三步链路：主库提交写 binlog ──▶ 从库 IO 线程接收写进 relay log（中继日志） ──▶ 从库 SQL/Worker 线程重放 relay log 提交生效。
• 🛡️ 兜底手段（半同步复制 Semi-Sync）：默认的异步复制下，主库写完自己的磁盘就立刻给客户端返回成功，不管从库收没收到；而开启半同步复制后，主库必须等待至少 1 台从库确认“我已经把这条 binlog 写进我的本地 relay log 磁盘了”，才向客户端返回提交成功——哪怕下一秒主库硬盘炸成灰，从库磁盘里也一定有完整日志！
❓ 06.3 · 生产实战选型：实际公司业务里，日志参数和主从架构到底怎么配？（三档方案）

🛠️ 06.3 绝不一刀切！生产环境「三档业务实战配置方案」

面试官最爱追问的一句话就是：“你把双 1、半同步、异步复制背得很熟，那你们实际项目里到底是怎么配的？”——安全与性能永远是跷跷板，真实互联网大厂会把数据库按业务重要度分成「三档」来配置：

🥇 第一档：支付账务 / 钱包余额 / 核心交易订单库（「一分钱都不能丢」档） 铁律双 1 + 无损半同步 / MGR
⚙️ 日志参数怎么配（满配安全）：
innodb_flush_log_at_trx_commit = 1 -- 每次提交刷 redo
sync_binlog = 1 -- 每次提交刷 binlog
binlog_format = ROW -- 严禁 STATEMENT
innodb_doublewrite = ON -- 开启双写防烂页 核心考量：宁可牺牲一点磁盘 IOPS，也绝不允许任何断电、崩溃导致已支付订单蒸发或余额错账。
📡 主从架构与读写怎么配：
• 主从模式：一主两从（跨机架/同城双中心），开启无损半同步复制（AFTER_SYNC，至少等 1 台从库落盘 relay log 才算提交成功）；银行/头部支付核心直接上 MGR（基于 Paxos 多数派强一致集群）。
• 读写规则：扣款、下单后的实时查询 100% 强制读主库！从库只拿来做异步对账、财务报表和灾备切换。
🥈 第二档：商品 / 用户 / 社区评论 / 常规业务库（「高可用 + 性价比」主力档，占公司 80%） 双 1（或峰值退 2）+ 超时降级半同步
⚙️ 日志参数怎么配（日常双 1，峰值可放宽）：
• 日常标准：现在云厂商（阿里云 RDS / 腾讯云 CDB）底层都是高性能 NVMe SSD + 组提交优化，日常一律保持“双 1”默认开启，性能完全够用。
• 大促峰值放宽（如秒杀点赞、弹幕、发帖）：如果瞬时写入把磁盘 I/O 打满，会把非资金表调成 trx_commit = 2 + sync_binlog = 100（写进 OS 缓存即返回，每 100 组刷一次盘），写入吞吐直接翻几倍！
📡 主从架构与读写怎么配：
• 主从模式：开启带超时退化的半同步复制（比如设置 timeout = 1000ms：正常情况保数据不丢；万一从库网络抖动超过 1 秒，自动降级回异步复制，绝不因为从库挂了把主库拖死！）。
• 从库加速 + 读写分离：从库开启 WRITESET 多线程并行复制（8~16 线程）压低延迟；前面挡一层 Redis 缓存，未命中的读走从库，仅“刚改完自己读自己”走主库。
🥉 第三档：App 埋点 / 操作行为日志 / 监控流水库（「极致写入吞吐、丢 1 秒无所谓」档） 2 + 0（或 0 + 0）+ 纯异步复制
⚙️ 日志参数怎么配（全开写入狂飙模式）：
innodb_flush_log_at_trx_commit = 2 -- (甚至设为 0)
sync_binlog = 0 -- 交给 OS 定时刷盘 核心考量：每秒几万条用户浏览足迹、埋点上报，就算机房突然断电丢了最后 1 秒的几百条浏览记录，对业务 0 影响，但省下了 80% 的磁盘刷盘开销！
📡 主从架构与读写怎么配：
• 主从模式：纯 异步复制，主库只管往前冲，完全不等从库确认。
• 读写分工：主库只负责高频写入（并定时清除 7~30 天前的历史分区）；从库专门挂给大数据团队（通过 Flink CDC / Canal 订阅从库 binlog）实时抽取到 ClickHouse / Elasticsearch 里做搜索和报表分析。
💡 面试满分回答模板：当被问到“你们线上怎么配日志和主从”时，千万别只答一个死参数，而是答：“我们按业务等级分级配置：核心订单/账务库强制开『双 1 + ROW 格式 + 无损半同步』且写后读走主库；普通业务库日常开『双 1 + 超时自动降级半同步 + WRITESET 并行复制 + Redis 挡读』，大促极端峰值非核心表可退化为 trx_commit=2, sync_binlog=100；而埋点流水类表直接用 2 + 0 + 异步复制 换极致写入吞吐。”
❓ 06.4 · 刚写成功为什么从库读不到？一主多从与 MySQL × Redis 缓存一致性怎么兜底？

🌐 06.4 从单机走向分布式：主从延迟应对 & MySQL × Redis 缓存同步

注意区分一个关键细节：即使开了上面的半同步复制，也只代表从库“收到了日志（写进了 relay log）”，不代表从库已经“执行完了日志（Applier 重放提交）”！所以在高并发读写分离或外挂 Redis 缓存时，还要做好业务层兜底：

📡 场景一：MySQL「一主多从」读写分离 —— 刚写完立刻读，怎么防止在从库读到旧数据？ CAP 权衡：AP 最终一致 vs CP 强一致
• 普通场景选 AP（最终一致）：商品列表、评论流等走从库读取，容忍几毫秒到几百毫秒的复制重放延迟，换取极高的读并发吞吐。
• 核心链路选 CP（强一致兜底）：像“付完款立刻跳转到订单详情页”、“扣完余额立刻查余额”这种写后立刻读场景，绝不能直接读异步从库！工业界有 2 种标准解法：
  1. 强制走主库（最简单可靠）：对核心写后读接口（或在写操作后的 1~2 秒窗口内）直接把读请求路由到主库。
  2. GTID 等待机制：主库写完拿到该事务的全局编号 GTID，去从库执行 WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)，确认从库已经重放完这笔事务后再读。
🧱 场景二：跨组件「MySQL × Redis」数据同步 —— 怎么保证数据库和缓存一致？ Cache-Aside + Binlog 异步兜底
方案 A：业务代码双操作（Cache-Aside）
标准顺序：① 先更新 MySQL ──▶ ② 再直接删除 Redis 缓存（下次有人读时未命中，再从 MySQL 查出新值回填）。
• 为什么是“删缓存”而不是“更新缓存”？ 并发写时两次更新缓存一旦乱序就会留下永久脏数据；删掉让下次按需加载最安全。
• 为什么“先改库再删缓存”？ 如果先删缓存，在 MySQL 还没改完的空档期里，并发读请求进来会把数据库里的旧值重新塞回缓存！
方案 B：Canal 订阅 Binlog + MQ 重试兜底
万一第 ② 步“删 Redis 缓存”网络抖动失败了怎么办？
业务代码只管写 MySQL（第 1 步），MySQL 自动生成 binlog；部署 Canal 伪装成从库监听 binlog，一旦发现数据变更就发消息到 MQ 异步删除 Redis 缓存——如果删失败了，MQ 会自动重试直到删成功为止，再用 Redis Key 的 TTL 过期时间做最后一道保底！
