06.1 · 大表变更规范：Online DDL 三种算法（INSTANT / INPLACE / COPY）与 MDL 锁阻塞防范

06.1 大表在线表结构变更（Online DDL）规范

在千万行级的线上生产表上执行 ALTER TABLE 时，最怕引发全表重建或触发 MDL（Metadata Lock，元数据锁）排队雪崩。MySQL 8.0 提供了三种 DDL 执行算法，可以通过在语句末尾显式指定 ALGORITHM=INSTANT / INPLACE 与 LOCK=NONE 来做安全防御（如果某操作不支持所选的无锁算法，MySQL 会立即报错中止，而不会静默退化为锁表重建）：

DDL 算法等级 底层执行方式与耗时 典型支持的表变更操作 生产使用建议
1. INSTANT
（秒级瞬时完成）		 仅修改数据字典中的元数据，完全不触碰任何 16KB 数据页，无论表有 100 行还是 1 亿行均在毫秒级完成 • 新增列（8.0.12 支持末尾加列，8.0.29+ 支持任意位置加列与秒级删列 DROP COLUMN）
• 修改列默认值、重命名表/列		 日常加字段首选。注意：含全文索引的表或行格式为 COMPRESSED 的表不支持 INSTANT。
2. INPLACE
（原地变更，不拷表）		 无需在 Server 层新建临时表拷贝，直接在 InnoDB 引擎内部构建索引或原地重组，期间允许并发读写 DML（LOCK=NONE） • 新增或删除二级索引（ADD INDEX / DROP INDEX）
• 扩展 VARCHAR 长度（未跨 255 字节长度头边界时）		 在业务低峰期执行。建大表索引耗时较长，但不会阻塞正常 SELECT / INSERT / UPDATE。
3. COPY
（锁写拷贝重建）		 创建一张新表并逐行拷贝原表全部数据，期间阻塞所有并发写入（仅可读），磁盘空间翻倍且主从延迟剧烈 • 修改列数据类型（如 INT 改 BIGINT）
• 修改表字符集（如 utf8mb3 改 utf8mb4）
• 修改主键列		 千万级大表严禁在高峰期直接跑 COPY 类 DDL，应使用 gh-ost 或 pt-online-schema-change 工具在线无锁迁移。
safe_online_ddl.sql · 显式声明 ALGORITHM 与 lock_wait_timeout 的安全 DDL 模板 
-- 【安全准则】执行任何线上 DDL 前，先将当前会话获取 MDL 锁的超时时间设为 3 秒（默认是一年 31536000 秒）
-- 防止因表上有未提交慢查询，导致 ALTER TABLE 卡在 Waiting for table metadata lock 并堵死后续所有普通 SELECT
SET SESSION `lock_wait_timeout` = 3;

-- 1. 秒级新增列（强制要求走 INSTANT 算法，若不支持则立即报错而非退化锁表）
ALTER TABLE `users`
  ADD COLUMN `vip_level` TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '会员等级',
  ALGORITHM=INSTANT;

-- 2. 在线无锁新建联合索引（强制要求走 INPLACE 算法且不锁并发读写 LOCK=NONE）
ALTER TABLE `users`
  ADD INDEX `idx_vip_created` (`vip_level`, `created_at`),
  ALGORITHM=INPLACE, LOCK=NONE;
06.2 · 深分页调优：LIMIT 1000000, 20 慢查询根因、游标分页与延迟关联改写方案

06.2 深度分页（LIMIT offset, size）的慢查询成因与两种改写方案

当业务表数据达到数百万行时，执行 SELECT id, name, city, balance FROM users WHERE city = '杭州' ORDER BY id ASC LIMIT 1000000, 20; 往往需要数秒甚至超时。原因是：MySQL 并不是直接跳过前 100 万行，而是顺着二级索引查出前 1000000 + 20 = 1000020 个主键 ID，老老实实回表 1000020 次取出完整行交给 Server 层，最后再把前 100 万行全部丢弃，只保留最后 20 行。消灭这 100 万次无效回表的两种标准方案如下：

deep_page_opt.sql · 方案一（游标分页）与方案二（延迟关联） 
-- ❌ 慢查询原写法：先回表 1000020 次取整行，再丢弃前 1000000 行
SELECT `id`, `name`, `city`, `balance` FROM `users`
WHERE `city` = '杭州' ORDER BY `id` ASC LIMIT 1000000, 20;

-- ✅ 方案一：游标分页 / Seek Method（性能恒定 O(log N)，瀑布流与导出首选）
-- 记住上一页最后一条记录的 id（如 last_id = 1580020），直接按索引定位：
SELECT `id`, `name`, `city`, `balance` FROM `users`
WHERE `city` = '杭州' AND `id` > 1580020
ORDER BY `id` ASC LIMIT 20;

-- ✅ 方案二：延迟关联 / Deferred Join（必须支持任意跳页码时的标准改写）
-- 子查询只查主键 id，100% 走覆盖索引（Using index，0 次回表）跳过前 100 万个 id，
-- 拿到最终 20 个 id 后，再与原表 INNER JOIN 仅回表 20 次取完整列：
SELECT `u`.`id`, `u`.`name`, `u`.`city`, `u`.`balance`
FROM `users` `u`
INNER JOIN (
  SELECT `id` FROM `users`
  WHERE `city` = '杭州'
  ORDER BY `id` ASC LIMIT 1000000, 20
) AS `page_ids` ON `u`.`id` = `page_ids`.`id`;
大表治理递进阶梯（别过早分库分表）

面对单表数据量到达千万级时，应按成本从低到高依次推进，切忌一上来就引入复杂的分库分表：

  1. 第一梯队（索引 + SQL 调优）：消除隐式转换与全表扫描，用覆盖索引/游标分页改写深分页（单表 2000~5000 万行在命中索引时点查依然在 1~3ms 内）。
  2. 第二梯队（读写分离 + 缓存 + 冷热归档）：高频读走 Redis 与只读从库；将 1 年前的历史已完结订单定时分批迁移至归档表或 ClickHouse / 对象存储，让在线主表始终保持轻量。
  3. 第三梯队（垂直拆分与水平分库分表）：只有当在线热数据单表突破 5000 万~1 亿行且单机写 IOPS / 连接数达到物理上限时，才考虑按业务键（如 user_id 哈希取模）做水平分库分表。

06.3 线上锁阻塞排查 SQL 与后端参数化事务实战

lock_inspect.sql · MySQL 8.0+ 一键揪出“谁锁住了谁”的排查 SQL 
-- 1. 联合查询 performance_schema 与 innodb_trx，直接定位阻塞源头会话与 SQL
SELECT
  `r`.`trx_id`              AS `waiting_trx_id`,
  `r`.`trx_mysql_thread_id` AS `waiting_thread`,
  `r`.`trx_query`           AS `waiting_sql`,
  `b`.`trx_id`              AS `blocking_trx_id`,
  `b`.`trx_mysql_thread_id` AS `blocking_thread`,
  `b`.`trx_query`           AS `blocking_current_sql`,
  `b`.`trx_started`         AS `blocking_trx_started`
FROM `performance_schema`.`data_lock_waits` `w`
INNER JOIN `information_schema`.`innodb_trx` `b`
  ON `b`.`trx_id` = `w`.`blocking_engine_transaction_id`
INNER JOIN `information_schema`.`innodb_trx` `r`
  ON `r`.`trx_id` = `w`.`requesting_engine_transaction_id`;

mysql_tx_pool.ts · Node.js (mysql2/promise) 连接池与参数化事务模板 
import mysql, { ResultSetHeader } from 'mysql2/promise';

// 1. 创建全局连接池（切勿每次请求都新建连接）
const pool = mysql.createPool({
  host: '127.0.0.1',
  port: 3306,
  user: 'app_rw',
  password: 'AppPass_2026#',
  database: 'mydb',
  charset: 'utf8mb4',
  timezone: '+08:00',
  connectionLimit: 20,
  maxIdle: 10,
  idleTimeout: 60000,
});

// 2. 标准事务函数：从池中借出同一个 conn 执行 BEGIN / COMMIT / ROLLBACK
export async function transferMoney(fromId: number, toId: number, amount: number) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    // 使用 ? 占位符预编译传参，从根源阻断 SQL 注入
    const [res] = await conn.execute<ResultSetHeader>(
      'UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?',
      [amount, fromId, amount]
    );
    if (res.affectedRows !== 1) throw new Error('INSUFFICIENT_BALANCE');

    await conn.execute(
      'UPDATE users SET balance = balance + ? WHERE id = ?',
      [amount, toId]
    );
    await conn.commit();
  } catch (err) {
    await conn.rollback(); // 任何一步异常必须显式回滚整个事务
    throw err;
  } finally {
    conn.release(); // 务必在 finally 中将连接归还给连接池
  }
}
