❓ 01.1 · 我们要存什么，又如何准确找到它？

📋 01.1 第一步：用一张 users 表贯穿全文

MySQL 是关系型数据库管理系统：用表组织数据，用 SQL 查询和修改数据。数据库可以包含多张表；表由列定义结构，每一行代表一条记录。

🐬 schema_and_dml.sql · 贯穿全文的示例表 
CREATE TABLE users (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  age TINYINT UNSIGNED NOT NULL,
  city VARCHAR(50) NOT NULL,
  balance DECIMAL(12,2) NOT NULL DEFAULT 0.00,
  PRIMARY KEY (id),
  KEY idx_city_age (city, age)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO users (name, age, city, balance) VALUES
  ('小林', 20, '杭州', 100.00),
  ('小周', 25, '杭州', 200.00),
  ('小陈', 30, '上海', 300.00);

SELECT id, name FROM users WHERE city = '杭州' AND age >= 20;
UPDATE users SET balance = balance + 10.00 WHERE id = 1;
概念 先这样理解 示例
主键 唯一标识一行，不能为 NULL；联合主键可以由多列组成 PRIMARY KEY (id)
索引 为查找维护的额外有序结构，读取可能更快，写入和存储有成本 idx_city_age
约束 由数据库检查的数据规则，如唯一性、非空、外键 NOT NULL
存储引擎 负责表的数据存取、索引等机制；本文使用 InnoDB ENGINE=InnoDB
💡 先记住：主键解决“是哪一行”，索引解决“如何更快找”，事务解决“多步修改如何一起成功或失败”。金额示例使用精确的 DECIMAL，避免用浮点数表示需要精确计算的金额。
❓ 01.2 · 谁理解 SQL，谁真正读写数据？

🗺️ 01.2 第二步：Server 层与 InnoDB 引擎层的两层协作

先区分两层：Server 层处理连接、SQL 解析与优化、执行调度；InnoDB 通过存储引擎接口提供数据访问，并实现事务、行锁和恢复机制。优化器需要引擎提供统计信息，两层紧密协作：

⚙️ 第一层：MySQL Server 层 —— 负责连接 · 解析 · 优化 · 执行（归属日志：binlog 归档日志）
① 连接与认证
建立 TCP 会话，校验账号密码与库表权限（8.0 已移除旧 Query Cache）
② 解析与预处理
词法/语法分析生成 AST，检查表名、列名是否存在
③ 优化器 (Optimizer)
基于成本估算（I/O + CPU），决定选哪个索引、怎么排 JOIN 顺序
④ 执行器 (Executor)
按执行计划循环调用存储引擎读写接口，完成过滤与聚合
⬇️ 执行器通过存储引擎 API 逐行/按范围调用 InnoDB ⇄ InnoDB 向优化器反馈索引统计信息
🐬 第二层：InnoDB 存储引擎层 —— 负责真正管数据与并发（归属日志：redo log / undo log）
🌳 B+ 树聚簇 / 二级索引
🧠 Buffer Pool 16KiB 内存页池
📸 MVCC 多版本与行锁/间隙锁
🛡️ WAL Redo 崩溃恢复与 Undo 回滚
📌 两个容易混淆的点：MySQL 8.0 已删除旧的 Query Cache，不代表数据库没有缓存；InnoDB 的 Buffer Pool 仍然缓存数据页。binlog 属于 Server 层；redo、undo 属于 InnoDB。
🔍 进阶 · 连接与权限的边界（空闲连接 ≠ 空闲事务）

连接通常可复用，连接池减少反复建连的成本。权限变更何时影响已有会话，取决于权限范围与具体操作，不能笼统说“改权限对旧连接都不生效”。

⚠️ 警惕“空闲连接 ≠ 空闲事务”：客户端执行了 BEGIN; SELECT ... 后若既不 COMMIT 也不 ROLLBACK，连接在连接池里看似 `Sleep`（空闲），但会话内部仍可能持有活跃事务、行锁/MDL 锁或旧的 ReadView 快照，拖慢后台 undo 清理甚至阻塞 DDL！
