02.1 · B+ 树阶数定量推导：为什么 3 层高 B+ 树可支撑约 2000 万行且最多只需 1~3 次磁盘 I/O

02.1 InnoDB 选择 B+ 树的原因与 3 层 B+ 树容量定量计算 常问

这节回答实战篇哪个问题：对应 实战篇 05.1、06.2 深分页 与 07.7 大表阶梯 —— 为什么两千万行的大表走索引点查只需 1~3 次磁盘 I/O，而深分页 LIMIT 1000000, 20 却慢在百万次回表上？

在机械硬盘或云盘上，一次跨页随机磁盘 I/O 耗时约 0.5 ~ 10ms。如果索引树有 20 层高（如平衡二叉树 AVL / 红黑树，log₂(2000万) ≈ 24 层），查一行数据就要做 24 次磁盘 I/O。为了把树的高度死死压在 3 ~ 4 层以内，InnoDB 采用了高扇出（High Fan-out）的多叉平衡搜索树 —— B+ 树，其核心设计在于：非叶子节点完全不存放真实行数据，只存放轻量的“主键值 + 子页页号（目录项记录）”，让单个 16 KiB 根节点能指向上千个子页：

对比候选结构 结构特征 为什么 InnoDB 主索引选 B+ 树而不选它
B 树（B-Tree） 非叶子节点既存键也存完整的行记录 Value 1. 非叶子节点被大体积的行记录塞满，导致单个 16KB 页能装的子节点指针从 1170 个骤降到十几个，树高大幅增加，磁盘 I/O 次数变多；
2. 叶子节点未串成双向链表，做范围查询时必须频繁跨层中序回溯。
哈希表（Hash） 按哈希函数映射桶槽位，精确等值查找为 O(1) 哈希打散后完全无序，无法支持任何范围查询（WHERE age > 20）、ORDER BY 排序与最左前缀匹配（InnoDB 仅在内存内部自动为高频等值页建立自适应哈希索引 AHI）。
LSM-Tree
（RocksDB / HBase）		 将随机写转为内存 MemTable + 磁盘 SSTable 顺序追加写与后台 Compaction 写入吞吐极高，但读请求可能需要合并查询多层 SSTable（读放大明显）。MySQL 定位于读写均衡且点查/范围读延迟敏感的 OLTP 场景，因此默认采用 B+ 树。
02.2 · 顺序写 vs 页分裂：自增主键 15/16 填充率与随机 UUID 主键引发的三大性能退化

02.2 顺序追加写与随机插入触发的「页分裂（Page Split）」 常问

这节回答实战篇哪个问题：对应 实战篇 02.3 与 07.7 —— 为什么建表主键强烈推荐单调递增的 BIGINT 或雪花算法 ID，而严禁用随机无序的 UUID 字符串？

因为 InnoDB 的聚簇索引要求叶子节点内的所有行记录必须严格按主键值递增顺序存放，所以主键的生成方式直接决定了底层 16 KiB 数据页的写入形态：

单调递增主键（AUTO_INCREMENT / 有序雪花 ID）
  • 紧凑顺序追加：每次新插入的记录主键值一定大于当前最大主键，因此 InnoDB 只需将新记录顺序追加到当前最后一个数据页的末尾。
  • 预留 1/16 页空间（填充因子 15/16）：当当前页写满到 15/16（约预留 1KB 供后续该页内的记录 UPDATE 变长时原地扩展）后，直接顺序申请下一个全新的 16KB 页继续顺序写，几乎不触发历史页分裂。
  • 二级索引极其精简：每个二级索引叶子节点只需附带 8 字节的 BIGINT 主键。
无序随机主键（如 UUID() 字符串 CHAR(36)）
  • 1. 频繁页分裂与数据搬移：新生成的 UUID 随机落在某张早已写满的历史数据页中间；InnoDB 被迫申请一个新页，将原页后半部分记录搬移过去，并修改前后双向链表与父节点目录项，伴随大量额外 Redo Log。
  • 2. 空间碎片率高达 50%：大量数据页分裂后长期处于半满状态，表空间体积膨胀近一倍。
  • 3. Buffer Pool 缓存频繁换出 + 二级索引膨胀：每次插入都要从磁盘随机读取不同的历史页；且表上每一个二级索引的每一行都要多存 36 字节的字符串主键。
02.3 · 元数据内核：MySQL 8.0 统一 InnoDB 数据字典、原子 DDL 实现与隐式提交边界

02.3 MySQL 8.0 原子 DDL 原理与为什么 DDL 不能跨语句回滚 深挖

这节回答实战篇哪个问题：对应 实战篇 02.4 与 07.3 Online DDL —— 为什么 MySQL 8.0 删掉了 .frm 文件后能做到秒级加列与崩溃原子恢复，以及为什么在事务里执行 DDL 会自动隐式提交？

在 MySQL 5.7 及更早版本中，表的元数据被分裂存放在两处：Server 层磁盘上的 .frm / .par / .trg 文件，以及 InnoDB 内部的系统表。如果在执行 DROP TABLE t1, t2 途中数据库掉电崩溃，经常会出现“.frm 文件删掉了但 InnoDB 表空间还在”的元数据不一致故障。

  • MySQL 8.0 统一数据字典与 innodb_ddl_log：MySQL 8.0 彻底废除了所有 .frm 文件，将全部数据字典表（如 mysql.tables、mysql.columns、mysql.indexes）统一存储在系统表空间 mysql.ibd 的 InnoDB 事务表中，并引入了专门的 mysql.innodb_ddl_log（DDL 日志表）。当执行一条 DDL 时，内核将“数据字典表修改 + 物理文件创建/重命名/删除操作日志”捆绑在同一个内部事务中：若中途掉电，重启恢复时会根据 innodb_ddl_log 自动重做或完整回滚这单条 DDL，保证单条 DDL 语句 100% 原子生效或原子回滚（Atomic DDL）。
  • 为什么 MySQL 的 DDL 仍会触发隐式提交（不能像 PostgreSQL 那样放在 BEGIN ... ROLLBACK 里回滚）：因为 MySQL 的原子 DDL 仅针对单条 DDL 语句自身崩溃恢复的原子性；为了清理之前持有的行锁与事务状态并独立记录 innodb_ddl_log，MySQL 在开始执行任何 CREATE / ALTER / DROP / TRUNCATE 语句前，都会在 Server 层先强制执行一次隐式 COMMIT 提交掉当前未结束的用户事务。
