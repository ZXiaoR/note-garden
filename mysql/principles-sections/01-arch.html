01.2 解决「预读失效」与「缓冲池污染」的两阶段冷热 LRU

如果 Buffer Pool 直接使用教科书里的朴素 LRU（即任何刚从磁盘读入的页都直接插到链表最头部），在数据库场景下会立刻遭遇两大灾难：

  1. 灾难一：预读失效（Read-Ahead Failure）—— InnoDB 具有线性预读（顺序访问一个区内的 innodb_read_ahead_threshold=56 个页时，自动异步把下一个 1 MiB 区的 64 个页提前读入内存）与随机预读机制。如果预读进来的页后续根本没被查询真正访问，却直接插到了 LRU 头部，反而会把真正的热点页挤出内存。
  2. 灾难二：缓冲池污染（Buffer Pool Pollution）—— 当某个后台报表或慢查询执行了一次全表扫描（如扫描一张 50 GB 的历史大表），成千上万个只会被读一次的数据页涌入 Buffer Pool。若采用朴素 LRU，这些一次性页面会瞬间霸占整个链表头部，将线上高频访问的核心热数据页全部淘汰出局，导致数据库命中率断崖式暴跌。

InnoDB 的两道防御设计：Midpoint 插入 + 1000ms 驻留晋升门限

  • 第一道防线（隔离预读失效 —— innodb_old_blocks_pct = 37）：将 LRU 链表按 5 : 3 的比例拆分为前半段 Young 热数据区（约占 63%） 和后半段 Old 冷数据区（默认占 37%）。任何从磁盘新读入的数据页（包括预读页），绝对不允许直接进入 Young 热区，而是统一插入到冷热交界处的 Midpoint（即 Old 冷区的头部）。如果预读页一直没人访问，它会很快从 Old 区尾部被自然淘汰，丝毫不影响前面的 Young 热区。
  • 第二道防线（隔离全表扫描污染 —— innodb_old_blocks_time = 1000）：光有 Midpoint 还不够，因为全表扫描在读入一个 16KB 页后，会紧接着依次读取该页内的几百行记录（相当于在几毫秒内连续访问了该页几百次），如果只要在 Old 区被第二次访问就立刻晋升到 Young 热区，全表扫描依然会污染热区。为此，InnoDB 在控制块中记录了该页进入 Old 区的首次访问时间戳：只有当该页在 Old 冷区驻留的时间超过了 innodb_old_blocks_time（默认 1000ms 即 1 秒）之后又被再次访问，才说明它是真正跨越单次扫描的常驻热点页，此时才允许晋升到 Young 热区头部。此外，为了减少 Young 区内部的链表锁争用，只有当被访问页位于 Young 区后 3/4 段时才会将其移到 Young 头部（前 1/4 段访问不移动链表）。
01.3 · 写加速与边界：Change Buffer 异步合并机制、为什么唯一索引不能用，以及 MySQL 8.4 默认值变化

01.3 Change Buffer（写缓冲）与唯一索引的 I/O 边界

当执行一条 INSERT / UPDATE / DELETE 时，如果目标数据页恰好已经在 Buffer Pool 中，直接修改内存页即可；但如果目标二级索引页不在内存中，难道每次都要立刻发起一次同步随机磁盘读 I/O 把那个 16KB 二级索引页读上来吗？为了把随机读转化为异步批量合并，InnoDB 设计了 Change Buffer（早期仅支持插入时称为 Insert Buffer）：

1. Change Buffer 的工作流与 Merge（合并）触发时机

  • 暂存改动（免随机读盘）：当修改某个非唯一二级索引（Non-Unique Secondary Index）且目标索引页不在 Buffer Pool 中时，InnoDB 不从磁盘读取该索引页，而是直接将“需要在某页插入/删除某条索引项”的记录写进内存（同时也持久化在系统表空间 ibdata1 的 Change Buffer B+ 树中）并记下 Redo Log，语句即可立即返回。
  • 何时触发 Merge（将改动真正应用到索引页）：
    1. 最常见触发：后续有查询请求真正把该 16KB 二级索引页从磁盘读入 Buffer Pool 时，顺手将 Change Buffer 中挂在该页名下的所有变更合并上去；
    2. 后台 Master Thread 定期空闲合并，或数据库正常关闭（Shutdown）时。

2. 核心追问：为什么「唯一索引」无法使用 Change Buffer

索引类型 / 场景 能否用 Change Buffer 与原因
唯一索引（UNIQUE KEY） 绝对不能使用。因为插入或修改唯一索引列时，InnoDB 必须当场检查新值是否与已有数据冲突；而要确认磁盘上是否存在该值，就必须把对应的 16KB 索引页先从磁盘读进内存。既然页都已经读进 Buffer Pool 了，直接改内存页即可，根本用不上 Change Buffer。
普通非唯一二级索引（KEY） 可以使用。适合写多读少的业务（如账单流水、操作日志、归档表），写入后短期内不立即读取，攒批 Merge 收益极高；反之若“刚写完立刻高频读取”，立即触发 Merge 反而多了一次维护开销。
MySQL 8.0 vs 8.4 默认值演进 在机械硬盘时代，innodb_change_buffering 默认开启为 all；而在现代高 IOPS 的 NVMe SSD 环境下，随机读延迟已极低且 Change Buffer 曾存在高并发并发合并复杂性，因此 MySQL 8.4 LTS 已将 innodb_change_buffering 的默认值改为 none（默认关闭）。
