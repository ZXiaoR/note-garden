🧬 04.1 · MVCC 三大基石：隐藏列（DB_TRX_ID / DB_ROLL_PTR）、两类 Undo Log 与聚簇索引逆向版本链

🧬 04.1 InnoDB 原地更新下的多版本存储与两类 Undo Log 生命周期

在 🌱 基础与实战篇 · 04 章 中，我们通过双终端实验验证了 READ COMMITTED (RC) 与 REPEATABLE READ (RR) 下普通 SELECT 的可见性差异。与 PostgreSQL「每次更新在数据页内追加一条物理新元组（Append-only Tuple）」的设计不同，InnoDB 采用的是「聚簇索引原地更新最新值 + Undo Log 逆向串联历史差量版本 + ReadView 活跃事务水位快照」的多版本并发控制（MVCC）方案：

  • 聚簇索引记录中的两个事务隐藏列：每一行聚簇索引记录（参考 00 章 00.3 节）都包含 6 字节的 DB_TRX_ID（最后一次插入或修改该行的事务 ID）和 7 字节的 DB_ROLL_PTR（回滚指针，指向该行在 Undo Log 表空间中的上一个历史版本记录）。如果某行被软删除，记录头中的 deleted_flag 位会被标记为 1。
  • 两类不同生命周期的 Undo Log：InnoDB 将回滚日志划分为两类：
    1. Insert Undo Log（TRX_UNDO_INSERT_REC）：记录 INSERT 操作的主键信息。由于新插入的行在事务提交前对其他任何事务都不可见，因此事务一旦提交（Commit），Insert Undo Log 即可立即丢弃释放，无需保留给 MVCC 快照读使用。
    2. Update Undo Log（TRX_UNDO_UPDATE_REC）：记录 UPDATE 和 DELETE 操作修改前的旧列值。由于可能存在更早开启的事务仍需通过 MVCC 读取该行的历史版本，因此事务提交后 Update Undo Log 不能立即删除，而是被挂入 History List，等待后台 Purge 线程检测到「当前系统中最老的活跃 ReadView 都已经不再需要该版本」时，才异步回收对应的 Undo 空间并物理清理标记为 deleted_flag = 1 的聚簇索引记录。
  • 从新到旧单向串联的 Undo 版本链：每当事务对某行执行 UPDATE 时，InnoDB 先把修改前的旧值连同旧的 DB_TRX_ID、DB_ROLL_PTR 写入一条新的 Update Undo Log，随后直接在聚簇索引页内原地覆写（In-place Update）新值，并将聚簇索引行的 DB_TRX_ID 更新为当前事务 ID、将 DB_ROLL_PTR 指向刚才写入的 Undo Log。如此反复，聚簇索引叶子节点永远存放着最新版本（使绝大部分读取最新数据的查询无需额外寻址），而历史版本则通过 DB_ROLL_PTR 串成一条从新到旧的单向链表。
🔍 04.2 · ReadView 可见性状态机：四大水位字段与 C++ 内核 changes_visible() 四步判定漏斗

🔍 04.2 ReadView 结构体的四大水位字段与四步可见性判定算法

当事务执行普通 SELECT（快照读，Snapshot Read）时，InnoDB 会获取一个一致性读视图（ReadView）。ReadView 并不拷贝整张表的数据，它只是一个极其轻量的内存结构体，记录了生成瞬间系统中所有活跃读写事务的状态快照：

ReadView 字段名 C++ 内核类型与含义 水位边界与可见性语义
m_creator_trx_id trx_id_t · 创建者事务 ID 生成该 ReadView 的当前事务自身的事务 ID（若当前事务只是只读事务且未分配事务 ID，则该值为 0）。自己修改的记录对自己永远可见。
m_ids ids_t · 活跃读写事务列表 生成 ReadView 瞬间，系统中已经启动但尚未提交（Active）的所有读写事务 ID 有序数组。
m_up_limit_id trx_id_t · 活跃事务低水位 等于 m_ids 中的最小值（min(m_ids)）。凡是 DB_TRX_ID < m_up_limit_id 的版本，说明在生成视图前必然已经提交，无条件可见。
m_low_limit_id trx_id_t · 系统尚未分配的高水位 等于生成 ReadView 瞬间系统即将分配给下一个新事务的 ID（即当前最大事务 ID + 1，max_trx_id + 1）。凡是 DB_TRX_ID >= m_low_limit_id 的版本，说明是在生成视图之后才开启的事务修改的，无条件不可见。

注意 InnoDB 源码中 m_up_limit_id（低水位，数值最小）与 m_low_limit_id（高水位，数值最大）的命名来源于「对可见性限制程度的高低」。当快照读沿着聚簇索引最新记录开始检查某个版本的 trx_id（即 DB_TRX_ID）时，会按顺序执行以下四步漏斗判定；若当前版本不可见，则顺着 DB_ROLL_PTR 取出 Undo 版本链中的上一个历史版本重新判定，直到找到第一个可见版本为止：

🦀 read0types.h · InnoDB 内核 ReadView::changes_visible() 四步可见性判定逻辑 
// 判断指定数据行版本的 trx_id 对当前 ReadView 是否可见
bool changes_visible(trx_id_t id, const table_name_t& name) const {
    // 1. 如果是当前事务自己修改的记录，或者小于低水位 m_up_limit_id（早已提交），直接可见
    if (id < m_up_limit_id || id == m_creator_trx_id) {
        return true;
    }

    // 2. 如果大于等于高水位 m_low_limit_id（生成 ReadView 之后才开启的事务），直接不可见
    if (id >= m_low_limit_id) {
        return false;
    } else if (m_ids.empty()) {
        // 3. 落在 [m_up_limit_id, m_low_limit_id) 之间，若生成快照时无任何活跃事务，则可见
        return true;
    }

    // 4. 在有序活跃事务数组 m_ids 中执行二分查找：
    //    若命中说明生成快照时该事务尚未提交（不可见 false）；未命中说明当时已提交（可见 true）
    const ids_t::value_type* p = m_ids.data();
    return !std::binary_search(p, p + m_ids.size(), id);
}
⚖️ 04.3 · RC vs RR 本质与幻读边界：ReadView 生成时机差异与「快照读 + UPDATE 当前读」显形推演

⚖️ 04.3 RC 与 RR 的本质差异，以及 RR 下快照读与当前读混用的幻读边界

理解了 ReadView 的判定算法后，READ COMMITTED (RC) 与 REPEATABLE READ (RR) 两个隔离级别的实现差异可以用一句话概括——仅仅是生成 ReadView 的时机不同：

  • READ COMMITTED (RC)：每次执行快照读 SELECT 时，都重新生成一个新的 ReadView。因此，其他事务只要在两次 SELECT 之间完成了提交，它的 trx_id 就会从新 ReadView 的 m_ids 活跃列表中消失，从而在第二次 SELECT 时立即可见。
  • REPEATABLE READ (RR)：只在事务内第一次执行快照读 SELECT 时生成 ReadView，并在整个事务生命周期内一直复用这同一个 ReadView（直到事务提交或回滚）。由于 m_ids 与高水位 m_low_limit_id 固定不变，后续无论其他事务如何修改并提交，对于该复用的 ReadView 而言全都处于不可见状态，从而实现了可重复读。

在技术讨论中常遇到一个问题：InnoDB 的 REPEATABLE READ 到底有没有彻底解决幻读。要严谨回答这个问题，必须区分 InnoDB 的两种读取模式：普通 SELECT（快照读，走 MVCC 与复用的 ReadView）与加锁读/写操作（当前读，跳过 ReadView 直接读取聚簇索引最新已提交版本并加 Next-Key Lock）。如果一个 RR 事务先执行纯快照读，紧接着对其他事务刚刚插入并提交的新行执行了一次无条件或范围 UPDATE（当前读），就会触发如下边界现象：

🧪 rr_phantom_edge.sql · RR 隔离级别下先快照读、再 UPDATE 当前读触发幻影行显形的边界时序 
-- 初始状态：accounts 表中只有 id = 1 一行记录，隔离级别为 REPEATABLE READ

-- 【时刻 T1 · 会话 A (trx_id = 200)】开启事务并首次快照读，生成并冻结 ReadView_A
START TRANSACTION;
SELECT * FROM accounts WHERE id > 0;
-- 返回 1 行 (id = 1)。因为是普通快照读，并未对 id > 0 加任何 Next-Key Lock 间隙锁

-- 【时刻 T2 · 会话 B (trx_id = 205)】插入 id = 2 的新行并提交
INSERT INTO accounts (id, balance) VALUES (2, 1000);
-- 此时 id = 2 的聚簇索引隐藏列 DB_TRX_ID = 205

-- 【时刻 T3 · 会话 A (trx_id = 200)】再次快照读：由于 205 >= ReadView_A.m_low_limit_id，看不到 id = 2
SELECT * FROM accounts WHERE id > 0;
-- 依然只返回 1 行 (id = 1)

-- 【时刻 T4 · 会话 A (trx_id = 200)】执行范围 UPDATE（触发当前读）
UPDATE accounts SET balance = balance + 100 WHERE id > 0;
-- Query OK, 2 rows affected
-- 关键机制：UPDATE 是当前读，它直接读到了会话 B 已提交的 id = 2，并将其 balance 改为 1100，
-- 同时把 id = 2 这行聚簇索引记录的 DB_TRX_ID 从 205 改写为了会话 A 自己的事务 ID (200)

-- 【时刻 T5 · 会话 A (trx_id = 200)】第三次执行普通快照读 SELECT
SELECT * FROM accounts WHERE id > 0;
-- 返回 2 行 (id = 1 和 id = 2)。因为 id = 2 的 DB_TRX_ID (200) == ReadView_A.m_creator_trx_id (200)，
-- 命中了 changes_visible() 的第一条规则（自己修改的记录对自己可见），原本隐藏的新行正式显形
💡 工程实践启示：如何在 RR 下从一开始就封死幻读窗口

上述 T4~T5 出现「第三次普通 SELECT 多出一行」的根源，在于 T1 时刻执行的是不加锁的普通快照读，没有阻挡会话 B 的插入，而 T4 时刻的 UPDATE 当前读又将该行的 DB_TRX_ID 刷新成了当前事务 ID。如果业务需要在事务一开始读取某范围数据并根据读取结果做后续写入决策，应当在 T1 时刻直接使用当前读（SELECT ... FOR UPDATE 或 FOR SHARE），从第一条语句起就用 Next-Key Lock 锁住目标索引区间，避免在同一事务中将初期的快照读结论直接用于后续的范围写操作。
