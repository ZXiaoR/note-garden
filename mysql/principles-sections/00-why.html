00.1 · 表空间层次：Tablespace (.ibd) → Segment（段）→ Extent（区 1MB）→ Page（页 16KB）→ Row（行）

00.1 InnoDB 独立表空间与四级物理存储结构 深挖

这节回答实战篇哪个问题：对应 实战篇 01.2 与 02.4 —— 执行建表后磁盘上的 .ibd 文件内部怎么划分空间，以及为什么 TRUNCATE / DROP 比逐行 DELETE 快得多？

自 MySQL 5.6.6 起，InnoDB 默认开启 innodb_file_per_table = ON（独立表空间模式），每张表的数据与所有索引都存放在数据目录下一个独立的 表名.ibd 文件中。如果磁盘每次只按单行几百字节去读写，磁头寻道与系统调用开销会非常高；如果直接按整个几百 MB 的文件分配，又会造成严重的碎片。因此 InnoDB 在表空间内部设计了“段（Segment）→ 区（Extent）→ 页（Page）→ 行（Row）”四级管理结构：

存储层级 固定大小 / 组成 内核设计目的与分配策略
1. 段（Segment） 由若干个区（Extent）与零散碎片页组成 每棵 B+ 树索引都由两个独立的段构成：叶子节点段（Leaf Node Segment）与非叶子节点段（Non-Leaf Node Segment）；此外还有存放回滚日志的回滚段（Rollback Segment）。
2. 区（Extent） 固定 1 MiB
（等于连续 64 个 16 KiB 页）		 消除磁盘随机 I/O 的空间分配基本单位。当表数据变大时，InnoDB 不再一页一页向操作系统申请空间，而是每次按整整 1 MiB（64 个物理连续页）分配，保证 B+ 树同层相邻叶子页大概率物理连续，使范围扫描接近顺序 I/O。（注：为防止小表浪费空间，每个段最初会先从 32 个碎片页 Fragment Pages 中单页分配，用满 32 页后才切换为按完整区 1 MiB 分配。）
3. 页（Page / Block） 默认 16 KiB（16384 Bytes）
由 innodb_page_size 控制		 InnoDB 磁盘与内存（Buffer Pool）交互的最小基本单位。即使你只执行 SELECT name FROM users WHERE id = 1 读取一行 50 字节的数据，InnoDB 也必须将这行所在的整张 16 KiB 数据页加载进内存缓冲池。
4. 行（Row / Record） 单页至少存放 2 行记录 存放真实用户列数据与隐藏事务元数据。MySQL 5.7 / 8.0 / 8.4 的默认行格式为 DYNAMIC。
00.2 · 16 KiB 数据页解剖：7 大组成部分、单向记录链表与 Page Directory 槽位二分查找

00.2 16 KiB 数据页（INDEX 页）物理布局与页内检索流程 常问

这节回答实战篇哪个问题：对应 实战篇 05.1 —— InnoDB 把一个 16KB 数据页读进内存后，页内几百行记录是单向链表串起来的，它是怎么不用逐行遍历就能二分定位到目标行的？

存放 B+ 树节点的数据页（内核页类型为 FIL_PAGE_INDEX）总大小为 16384 字节，内部由头尾固定元数据与中间相向生长的“用户记录区（User Records）+ 页目录槽位（Page Directory）”共 7 个部分组成：

  • 为什么同层数据页是双向链表，而页内记录却是单向链表：File Header 中包含 FIL_PAGE_PREV（上一页页号）与 FIL_PAGE_NEXT（下一页页号）两个 4 字节指针，使得 B+ 树同层兄弟页构成双向链表（支持正序与倒序范围扫描）。而在单个 16 KiB 页内部，所有行记录从虚拟最小记录 Infimum 到虚拟最大记录 Supremum 通过记录头的 next_record 构成按主键升序排列的单向链表。
  • 既然页内记录是单向变长链表，怎么实现二分查找：直接对变长链表无法按物理地址折半，因此 InnoDB 在页尾设计了定长数组 Page Directory（页目录）：将页内所有有效记录（不含已标记删除的记录）每 4 ~ 8 条划分为一组（第 0 组 Infimum 独占 1 条，最后一组 Supremum 含 1~8 条），只有每组最后那条最大记录的头部 n_owned 字段记录本组条数，并把它的页内 2 字节偏移量存入一个 Slot（槽位）。当在页内查找 id = 15 时：
    1. 第一步（槽位二分查找）：在定长 Slot[] 数组上做标准二分查找，迅速锁定 15 介于 Slot[1] (id=8) 与 Slot[2] (id=25) 之间；
    2. 第二步（组内最多 8 步遍历）：从 Slot[1] 指向的 id=8 出发，顺着 next_record 指针向后走 2 步（id=12 → id=15）即命中目标。
  • File Header 与 File Trailer 双重校验防页断裂：页头 38 字节的 FIL_PAGE_SPACE_OR_CHKSUM 与页尾 8 字节的 File Trailer 都记录了当前页的校验和（Checksum）以及最后修改该页的日志序列号 LSN（Log Sequence Number） 的低 4 字节。每次从磁盘读入 16KB 页时，InnoDB 都会比对页头与页尾的 Checksum 及 LSN 是否完全一致，只要不相等就说明该页在刷盘途中遭遇断电发生了“半页写入（Partial Page Write）”。

00.3 InnoDB 行记录格式与隐藏系统列 深挖

这节回答实战篇哪个问题：对应 实战篇 02.5 与 06.4 —— 为什么建表推荐字段尽量设为 NOT NULL，以及大文本 TEXT / JSON 超长时为什么不会撑爆主数据页？

在聚簇索引叶子节点中，每一条物理行记录都由“记录额外信息头（变长字段长度列表 + NULL 值位图 + 5 字节记录头）”与“记录真实数据（3 个隐藏系统列 + 用户定义列）”连续拼接而成：

行记录组成部分 字节开销 核心内部字段与设计职责
1. 变长字段长度列表 每列 1 ~ 2 Bytes
（逆序存放）		 逆序记录本行所有非 NULL 的变长列（VARCHAR / TEXT / BLOB）的实际字节长度。若列最大可能字节数 ≤ 255 则占 1 字节；若 > 255 且实际长度 > 127 则占 2 字节。
2. NULL 值位图 ⌈允许NULL列数 / 8⌉ Bytes 每个允许为 NULL 的列占 1 个 bit（值为 1 代表该列是 NULL，真实数据区不再占用任何字节）。若全表字段均声明为 NOT NULL，则直接省去该位图。
3. 记录头信息（Record Header） 固定 5 Bytes（40 bits） • delete_mask (1 bit)：执行 DELETE 时并不立即抹除物理字节，而是先将此位置 1 并挂入页内垃圾链表供后续复用；
• record_type (3 bits)：0=普通叶子记录、1=B+树非叶子目录项、2=Infimum、3=Supremum；
• n_owned (4 bits)：Page Directory 分组槽位拥有的记录条数；
• next_record (16 bits)：指向下一条记录的真实数据起始位置（正好位于记录头与真实列之间，向左读头信息、向右读列值）。
4. 三大隐藏系统列 DB_ROW_ID (6B)
DB_TRX_ID (6B)
DB_ROLL_PTR (7B)		 • DB_ROW_ID（6 字节，可选）：仅当表既无 PRIMARY KEY 也无非空 UNIQUE 索引时，InnoDB 才自动生成该 6 字节隐藏聚簇主键；
• DB_TRX_ID（6 字节，必有）：最后一次插入或更新本行记录的事务 ID（用于 MVCC 可见性判断）；
• DB_ROLL_PTR（7 字节，必有）：回滚指针，指向该行在 Undo Log 中的上一个历史版本记录。
COMPACT（5.6 默认）与 DYNAMIC（5.7 / 8.0 / 8.4 默认）在行溢出（Row Overflow）上的核心差异：
因为 InnoDB 规定单个 16 KiB 数据页至少要能装下 2 行记录，所以当某一行包含超长的 VARCHAR / TEXT / BLOB（单行总大小超过约 8098 字节）时，就会触发行溢出（Off-Page Storage）：
• 旧版 COMPACT 行格式：会把大字段的前 768 字节继续留在主数据页内，后面再跟一个 20 字节的溢出页指针，导致主数据页依然很臃肿，每页能装的行数很少；
• 现代默认的 DYNAMIC 行格式：采用完全行溢出策略——一旦触发溢出，把大字段的全部字节都放到独立的溢出页（Uncompressed BLOB Page）中，主数据页内该列仅保留一个 20 字节的指针，从而让聚簇索引叶子页装下更多行，大幅提升缓存命中率。
