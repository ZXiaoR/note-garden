🔒 05.1 · 全局锁与表级锁：FTWRL、MDL 元数据锁排队雪崩、意向锁 IS/IX 与 AUTO-INC 自增锁

🔒 05.1 全局锁与四类表级锁（表锁 / MDL / 意向锁 / AUTO-INC 锁）

如果说 MVCC 与 ReadView 解决了「读-写」并发时的无锁非阻塞读取，那么当多个事务同时执行当前读（SELECT ... FOR UPDATE / FOR SHARE）或写操作（INSERT / UPDATE / DELETE）时，就必须依靠锁机制来保证数据一致性。按锁定的粒度从大到小划分，MySQL 的锁体系分为全局锁、表级锁和 InnoDB 行级锁三个层次。在深入行锁之前，必须先厘清在全局与表级维度维护的四类锁机制：

锁层级与名称 加锁与释放时机 相容性与互斥关系 核心工程用途与线上注意事项
全局读锁 (FTWRL)
FLUSH TABLES WITH READ LOCK		 显式执行命令加锁；执行 UNLOCK TABLES 或客户端断开时释放 整个实例进入只读状态，阻塞所有表的 DML 写入与 DDL 变更 早年用于全库逻辑备份。对纯 InnoDB 库备份时应改用 mysqldump --single-transaction（利用 MVCC 快照一致性备份，完全不锁表）。
表级数据锁
LOCK TABLES t READ/WRITE		 显式执行命令加锁；UNLOCK TABLES 释放 读锁之间共享，写锁与任何读/写锁互斥 颗粒度过大，仅在无行锁的 MyISAM 引擎中使用；InnoDB 日常业务应避免使用显式表锁。
元数据锁 (MDL)
Metadata Lock		 无需显式声明：任何查询或 DML 自动加 MDL 读锁；ALTER TABLE 自动加 MDL 写锁；直到事务提交才释放 MDL 读锁 之间互不阻塞；MDL 写锁 与所有 MDL 读/写锁 互斥 防止查询中途表结构被修改。关键风险：MDL 锁队列具有写锁优先机制，若某表上有未提交的长事务持有 MDL 读锁，此时执行 ALTER TABLE 会卡在等待 MDL 写锁，并把排在该 DDL 之后的所有普通 SELECT 全部堵死。
意向锁 (IS / IX)
Intention Shared / Exclusive		 InnoDB 在对某行加共享行锁（S）或排他行锁（X）前，先自动在表级加 IS 或 IX 锁 IS 与 IX 之间、IX 与 IX 之间全部互相兼容；仅与表级 S / X 锁按规则互斥 意向锁是表级「信号旗」，作用是让想要加表级锁的线程一眼看出「表里当前有没有行被锁住」，无需逐行扫描整张表去检查行锁冲突。
自增锁 (AUTO-INC) 向含 AUTO_INCREMENT 列的表插入数据时触发，受 innodb_autoinc_lock_mode 控制 模式 0（语句结束释放）、模式 1（单行插入轻量互斥量，批量插入锁到语句结束）、模式 2（全程轻量互斥量） MySQL 8.0 默认将 binlog_format 设为 ROW，并将 innodb_autoinc_lock_mode 设为 2（Interleaved 交错模式），并发插入性能最高，但并发批量插入或回滚时自增 ID 允许出现不连续空洞。
📏 05.2 · 行锁四类形态：Record Lock、Gap Lock、Next-Key Lock 与 Insert Intention Lock 冲突关系

📏 05.2 InnoDB 行级锁的四类基本形态与 Gap Lock 并发死锁推演

理解 InnoDB 行锁的第一条基本原理是：InnoDB 的行锁是加在索引项（Index Record）及索引项之间的间隙（Gap）上的。如果一条 UPDATE 或 SELECT ... FOR UPDATE 语句没有命中任何有效索引而走了全表扫描，InnoDB 会把聚簇索引上的每一条记录以及所有间隙全部锁住，在并发表现上等效于锁住了整张表。围绕 B+ 树有序索引构成的数轴，InnoDB 设计了以下四类行级锁形态：

  1. 记录锁（Record Lock，源码宏 LOCK_REC_NOT_GAP）：仅锁定单条索引记录本身（例如精准锁住 id = 20 这一行），不锁定前后的任何间隙。同记录上的 S 锁与 S 锁兼容，X 锁与任何 S/X 锁互斥。
  2. 间隙锁（Gap Lock，源码宏 LOCK_GAP）：仅锁定两条索引记录之间的开区间（例如 (10, 20)），不包含端点记录本身。需要特别注意一条反直觉的规则：Gap Lock 存在的唯一目的是「阻止其他事务向该间隙插入新记录」，因此两个不同事务在同一个间隙上持有的 Gap Lock（无论是 Gap S 锁还是 Gap X 锁）是完全互相兼容、绝不冲突的。
  3. 临键锁（Next-Key Lock，源码宏 LOCK_ORDINARY）：等于 Gap Lock + Record Lock 的组合，锁定一个左开右闭区间（例如 (10, 20]，既锁住 (10, 20) 的间隙不让插入，又锁住 20 这条记录本身不让修改）。在 REPEATABLE READ 隔离级别下，InnoDB 当前读的默认加锁基本单位就是 Next-Key Lock。
  4. 插入意向锁（Insert Intention Lock，源码宏 LOCK_INSERT_INTENTION）：它是一种特殊的间隙锁，当事务执行 INSERT 准备向某个索引间隙（如 (10, 20)）插入一条新记录（如 id = 15）时，会先检测该间隙是否已被其他事务加上了 Gap Lock 或 Next-Key Lock。如果已被锁住，INSERT 就会生成一个插入意向锁并进入阻塞等待状态；但如果多个事务同时向同一个未被锁住的间隙插入不同主键的行（如一个插 14、一个插 16），它们的插入意向锁之间互不阻塞。
🧭 05.3 · 加锁退化法则：唯一索引与普通索引在等值存在、等值不存在及范围查询下的精确锁范围

🧭 05.3 RR 隔离级别下 Next-Key Lock 的加锁与退化规则完整推演

在 REPEATABLE READ 隔离级别下，InnoDB 对扫描到的每一条索引记录默认都会先加上 Next-Key Lock（左开右闭区间）；但在特定条件下，如果更小范围的锁已经足以排除幻读风险，InnoDB 会将 Next-Key Lock 退化（Degrade）为 Record Lock 或 Gap Lock。假设表 users(id PRIMARY KEY, age KEY, name) 中当前共有 3 条记录：(10, 10, 'A')、(20, 20, 'B')、(30, 30, 'C')，下表汇总了 5 种核心查询场景的加锁退化结果（可在 MySQL 8.0 中通过 SELECT * FROM performance_schema.data_locks; 实测验证）：

查询场景分类 示例当前读 SQL 最终加锁范围（performance_schema.data_locks） 内核加锁与退化原理解析
1. 唯一索引 · 等值查询（记录存在） SELECT * FROM users WHERE id = 20 FOR UPDATE; id = 20 的 Record Lock（LOCK_REC_NOT_GAP） 由于主键/唯一索引具有唯一性，其他事务不可能再插入另一条 id = 20 的记录，无需锁住 (10, 20) 间隙，因此 Next-Key Lock (10, 20] 退化为单点记录锁 [20]。
2. 唯一索引 · 等值查询（记录不存在） SELECT * FROM users WHERE id = 15 FOR UPDATE; id = 20 上的 Gap Lock (10, 20)（LOCK_GAP） 定位到第一条大于 15 的记录 id = 20，初始加 Next-Key Lock (10, 20]；由于 20 != 15，无需锁定 id = 20 本身，因此退化为开区间间隙锁 (10, 20)。
3. 普通非唯一索引 · 等值查询（记录存在） SELECT * FROM users WHERE age = 20 FOR UPDATE; • 普通索引 age：Next-Key Lock (10, 20] + Gap Lock (20, 30)
• 聚簇索引 id：id = 20 的 Record Lock		 普通索引允许重复值，命中 age = 20 时先加 Next-Key Lock (10, 20]（同时回表锁住主键 id = 20 的记录锁），随后必须继续向右扫描到第一个不等于 20 的值（age = 30），并对 30 退化加上 Gap Lock (20, 30)，以彻底封死在 20 前后插入新 age = 20 的可能。
4. 唯一索引 · 范围查询（含等号边界） SELECT * FROM users WHERE id >= 20 AND id < 25 FOR UPDATE; • id = 20 的 Record Lock [20]
• id = 30 上的 Gap Lock (20, 30)		 左端点 id = 20 等值命中唯一索引，(10, 20] 退化为单点 Record Lock [20]；随后向右扫描到第一个不满足 < 25 的记录 id = 30，在 MySQL 8.0.18+ 中 (20, 30] 优化退化为 Gap Lock (20, 30)（不锁 id = 30 本身）。
5. 普通索引 · 范围查询 SELECT * FROM users WHERE age >= 20 FOR UPDATE; • 普通索引 age：Next-Key Lock (10, 20]、(20, 30]、(30, +∞]
• 聚簇索引 id：[20]、[30] 的 Record Lock		 注意普通索引的范围查询左端点 age = 20 不会退化为记录锁（因为 (10, 20) 间隙中仍可能插入新的 age = 20），因此 (10, 20] 保持完整的 Next-Key Lock，并一直锁到无穷大伪记录 supremum pseudo-record。
💡 互联网高并发核心库常将隔离级别调为 READ COMMITTED 的原因

从上表可以看到，在默认的 REPEATABLE READ 隔离级别下，任何范围更新或未命中唯一索引的更新都会引入大面积的 Gap Lock 与 Next-Key Lock，大幅提高了并发写入时的锁冲突与死锁概率。而在 READ COMMITTED (RC) + binlog_format = ROW 组合下，除了外键约束检查与唯一键冲突检查（Duplicate-Key Checking）仍需短暂使用 Gap Lock 外，普通的查询与更新全部只加 Record Lock（单点记录锁），完全移除了 Gap Lock，并且 InnoDB 还会开启半一致读（Semi-consistent Read）：当 UPDATE 扫描到一行已被其他事务锁住的记录时，先通过 MVCC 读取该行的最新提交版本判断是否满足 WHERE 条件，若不满足则直接跳过不锁，从而显著提升高并发写吞吐。
