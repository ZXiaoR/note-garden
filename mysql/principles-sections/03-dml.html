03.1 · 优化器与下推：CBO 成本估算（mysql.server_cost / engine_cost）、ICP 与 MRR 多范围读

03.1 CBO 成本模型、索引条件下推（ICP）与多范围读（MRR） 常问

这节回答实战篇哪个问题：对应 实战篇 05.2 与 05.3 EXPLAIN —— 为什么范围查询过宽时明明建了索引优化器却选全表扫描，以及 Using index condition 帮我们省掉了什么？

MySQL 的查询优化器是基于成本的优化器（CBO，Cost-Based Optimizer）。一条查询到底走全表扫描还是走某个二级索引，完全取决于优化器根据持久化统计信息（mysql.innodb_table_stats 与 innodb_index_stats，或通过 index dives 深入采样索引区间首尾页）算出的 Total Cost = I/O Cost + CPU Cost 谁更低：

基准成本常数（存于 mysql.server_cost / engine_cost）
  • io_block_read_cost = 1.0：从磁盘读取一个 16KB 页的基准 I/O 成本；
  • memory_block_read_cost = 0.25：从 Buffer Pool 内存读取一个已缓存 16KB 页的成本（仅为磁盘读的 1/4）；
  • row_evaluate_cost = 0.1：在 Server 层对一条记录检验一次 WHERE 条件的 CPU 成本。
  • 为什么范围过宽时优化器主动弃用二级索引：因为二级索引每命中一行，在最坏情况下都要算一次随机回表读聚簇页（1.0 成本）。一旦估算命中行数超过全表的约 20% ~ 30%，累计回表随机 I/O 成本就会超过直接顺序扫一遍聚簇索引全表，优化器便会主动放弃二级索引改走 ALL。
减少与优化回表的两大引擎特性：ICP 与 MRR
  • 1. 索引条件下推（ICP，Using index condition）：对于联合索引 idx(city, age, name) 和查询 WHERE city = '杭州' AND name LIKE '%林%'，虽然 LIKE '%林%' 无法用于 B+ 树二分定位，但 InnoDB 在扫描完 city = '杭州' 的二级索引项后，先在引擎层直接拿索引里自带的 name 列检验是否匹配 '%林%'，只有匹配的才去回表取整行，可砍掉 90% 以上的无效回表。
  • 2. 多范围读（MRR，Multi-Range Read，即 Using MRR）：因为二级索引按索引列排序，查出的一批主键 id 往往是乱序的（如 id = 980, 12, 5400, 35），直接回表会产生磁盘磁头来回跳跃的随机 I/O。开启 MRR 后，会在内存缓冲区（read_rnd_buffer_size）中先把这批 id 按升序排好（12, 35, 980, 5400），再按主键顺序批量回表读取聚簇索引页，将随机 I/O 转化为近似顺序 I/O。
03.2 · JOIN 算法内核：Index Nested-Loop (NLJ)、Block Nested-Loop (BNL) 与 8.0.18+ Grace Hash Join

03.2 多表连接算子演进与为什么要求“小表驱动大表” 常问

这节回答实战篇哪个问题：对应 实战篇 03.4、05.5 与 06.7 递归树 —— 多表 JOIN 在底层是怎么循环匹配的，被驱动表漏建索引时 MySQL 8.0 的 Hash Join 是怎么救场的？

当执行 SELECT * FROM t1 STRAIGHT_JOIN t2 ON t1.a = t2.a（设驱动表 t1 过滤后有 N 行，被驱动表 t2 有 M 行）时，MySQL 根据被驱动表连接列 t2.a 上是否有可用索引，采取截然不同的物理连接算子：

JOIN 物理算子 触发前提与时间复杂度 内部执行流程与为什么“小结果集做驱动表”更优
1. Index Nested-Loop Join (NLJ)
（索引嵌套循环连接）		 被驱动表连接列有索引
复杂度：O(N × log₂M)		 从驱动表 t1 逐行取出 N 条记录，每次拿 t1.a 到被驱动表 t2 的 B+ 树索引上做一次 O(log₂M) 搜索。
为什么选小表做驱动表：在公式 N + N × log₂M 中，N 是外层乘数且线性增长，而大表行数 M 被套在对数 log₂M 里面（1000 万行的 B+ 树也只有 3 层），因此减小驱动表行数 N 能直接成倍减少内层索引树搜索总次数。
2. Block Nested-Loop Join (BNL)
（块嵌套循环 · 8.0.20 已废弃）		 被驱动表无索引（5.7 及更早版本）
复杂度：O(N × M)		 把驱动表 t1 的数据分块装入内存 join_buffer，每装满一块就全表扫描一遍被驱动表 t2，在内存中做双重循环比对。若 t1 分了 K 块，就要全表扫描 t2 共 K 遍。
3. Hash Join
（哈希连接 · MySQL 8.0.18+ 引入并全面替代 BNL）		 被驱动表无索引且含等值连接条件
复杂度：O(N + M)		 • 阶段一（Build 构建哈希表）：扫描较小的一张表（驱动表 t1），按连接键计算的哈希值在内存 join_buffer_size 中构建哈希表；
• 阶段二（Probe 探测）：仅扫描一遍被驱动表 t2，对每一行计算哈希值去内存哈希表中做 O(1) 探测匹配。
• 内存溢出处理（Grace Hash Join）：若驱动表太大装不进 join_buffer_size，内核会用哈希函数将两张表同步切分为多个磁盘临时分片文件（Chunk Files），再逐对加载到内存中完成分片 Hash Join。
03.3 · Filesort 排序内核：全字段排序（Single-Pass）vs rowid 排序（Two-Pass）与外部归并排序

03.3 ORDER BY 触发 Using filesort 时的内部执行过程 深挖

这节回答实战篇哪个问题：对应 实战篇 05.3 与 06.6 统计报表 —— 当 EXPLAIN 出现 Using filesort 时一定是写磁盘排序吗，为什么带 ORDER BY 的查询严禁写 SELECT *？

当 ORDER BY 的列无法直接复用索引的天然有序性时，EXPLAIN 的 Extra 列会出现 Using filesort（注意名字虽带 file，但只要数据量不超过线程独占的排序内存缓冲区 sort_buffer_size（默认 256 KB），排序就完全在内存中通过快速排序完成；只有超出 sort_buffer_size 时才会借助磁盘临时文件做多路外部归并排序）。

从 Filesort 原理得出的两条 SQL 编写准则：
1. 带 ORDER BY 的查询切忌写 SELECT *：因为一旦查询列总长度超过阈值或挤满 sort_buffer_size，不仅会让内存装不下触发磁盘临时文件外部归并排序（Merge Sort），还会迫使优化器退化为需二次回表的 rowid 排序。
2. ORDER BY ... LIMIT K 的优先队列（堆排序）优化：自 MySQL 5.6 起，当执行 ORDER BY age LIMIT 20 时，无需将全部 10 万行排好序，执行器直接在 sort_buffer 中维护一个容量为 20 的大顶堆/小顶堆（Priority Queue），遍历一遍即可取出 Top 20，完全不会产生磁盘临时文件。
