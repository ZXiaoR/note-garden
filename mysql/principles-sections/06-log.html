06.1 · 三大日志与两阶段提交：Undo / Redo / Binlog 职责对比与基于 XID 的崩溃恢复裁决法则

06.1 三大日志职责对比与一条 UPDATE 的内部两阶段提交（Internal 2PC） 常问

这节回答实战篇哪个问题：对应 实战篇 04.1、06.9 本地消息表 与 07.5 PITR 恢复 —— 断电重启时怎么保证刚提交的订单和本地消息不丢，且主库恢复结果与 Binlog 完全一致？

如果每次执行 UPDATE 都直接把 16 KiB 的 InnoDB 数据页随机刷回磁盘，机械硬盘或 SSD 的随机 I/O 很快就会成为吞吐瓶颈。为此，MySQL 采用了经典的预写式日志（WAL，Write-Ahead Logging）技术：先在内存 Buffer Pool 中修改数据页，并将修改动作顺序追加写入日志文件，随后即可向客户端返回提交成功；至于内存中的脏页（Dirty Page），则由后台线程在低峰期异步批量刷入磁盘。在这套流程中，Undo Log、Redo Log 与 Binlog 各司其职，共同构成了 ACID 中原子性（Atomicity）与持久性（Durability）的底层支柱：

对比维度 Undo Log（回滚日志） Redo Log（重做日志） Binlog（二进制归档日志）
所属架构层 InnoDB 存储引擎层独占 InnoDB 存储引擎层独占 MySQL Server 层通用（所有存储引擎共用）
保障 ACID 维度 原子性 (Atomicity) + 隔离性 (MVCC) 持久性 (Durability)（Crash-Safe 崩溃恢复） 不用于引擎崩溃恢复，专用于主从复制 (Replication) 与时间点备份恢复 (PITR)
日志内容格式 逻辑日志（记录修改前的旧值，回滚时执行反向逻辑操作，并通过 DB_ROLL_PTR 串联 MVCC 历史版本链） 物理+逻辑日志 (Physiological Logging)：对页是物理定位（表空间号 + 页号 Page No），对页内修改是逻辑重放 逻辑日志，支持三种格式：STATEMENT（记原始 SQL）、ROW（默认，记每行修改前后镜像）、MIXED
磁盘写入方式 存放在 Undo 表空间（undo_001 / undo_002），其修改本身也会记入 Redo Log 固定大小环形循环写（由 write pos 当前写入点与 checkpoint 已刷脏页擦除点组成，MySQL 8.0.30+ 由 innodb_redo_log_capacity 控制总容量） 追加写（Append-only），单个文件写满 max_binlog_size 后自动切分生成新编号文件（如 binlog.000001 → binlog.000002）

既然一次事务修改既要写 InnoDB 的 Redo Log，又要写 Server 层的 Binlog，如果采用「先写完 Redo Log 再写 Binlog」或「先写完 Binlog 再写 Redo Log」的单步顺序写，一旦在两份日志之间发生掉电宕机，就会导致主库崩溃恢复后的数据与从库通过 Binlog 回放的数据不一致。为了解决两份日志之间的原子一致性，MySQL 引入了由内部事务 ID（XID）关联的内部两阶段提交（Internal Two-Phase Commit，2PC）：

06.2 · 零丢失持久化：「双 1」刷盘参数、Group Commit 组提交与 Doublewrite Buffer 防半页断裂

06.2 「双 1」刷盘配置、组提交（Group Commit）与双写缓冲区（Doublewrite Buffer） 深挖

这节回答实战篇哪个问题：对应 实战篇 07.1 my.cnf「双 1」参数 —— 开启「双 1」每次提交都强制刷物理磁盘后，高并发下靠什么保持上万 TPS，以及 16KB 页写到一半断电怎么修复？

在两阶段提交中，如果每次事务提交都只是写入操作系统的 Page Cache 而没有调用 fsync() 刷入物理磁盘，一旦操作系统内核崩溃或服务器断电，Page Cache 中的日志仍然会丢失。控制 Redo Log 与 Binlog 刷盘时机的两个核心参数被称为「双 1」配置：

核心参数名 可选取值 内存与磁盘持久化行为 故障丢失窗口与适用场景
innodb_flush_log_at_trx_commit
（控制 Redo Log Buffer 刷盘）		 1（默认） 每次事务提交时，都将 Redo Log Buffer 写入 OS Page Cache 并立即调用 fsync() 刷入物理磁盘 零丢失（最安全），金融账务与核心生产库标准配置。
0 事务提交时不写也不刷，仅依赖后台线程每隔 1 秒把 Redo Log Buffer 写入 OS 并调用 fsync() mysqld 进程崩溃或机器掉电均可能丢失最近 1 秒内的已提交事务。
2 每次事务提交时写入 OS Page Cache（write），但由后台线程每隔 1 秒调用 fsync() 落盘 若仅 mysqld 进程崩溃（OS 未宕机）则不丢数据；仅在整机掉电时丢失最近 1 秒数据。
sync_binlog
（控制 Binlog Cache 刷盘）		 1（8.0 默认） 每次事务提交时，都将 Binlog Cache 写入文件并立即调用 fsync() 刷入物理磁盘 零丢失（最安全），与 innodb_flush_log_at_trx_commit = 1 组成「双 1」配置。
0 每次提交仅 write() 到 OS Page Cache，何时 fsync() 完全交给操作系统决定 整机掉电时丢失未落盘的 Binlog，导致主从失步或无法恢复。
N (如 100) 每次提交都 write() 到 OS Page Cache，但每累计 N 个事务才调用一次 fsync() 在极端 I/O 瓶颈下折中提升吞吐，掉电时最多丢失最近 N 个事务的 Binlog。
1. 组提交（Group Commit）如何化解「双 1」IOPS 瓶颈

开启「双 1」后，每次事务提交都要触发 Redo Log（Prepare 阶段）和 Binlog 的两次物理 fsync()。为了避免高并发下每个事务各自独占调用 fsync()，MySQL 将 Binlog 提交拆分为 Flush 阶段 → Sync 阶段 → Commit 阶段 三个队列，每个阶段由第一个到达的线程担任 Leader，将同一时刻到达队列的一批并发事务（Follower）打包合并：在一次 fsync() 系统调用中同时刷入数十个事务的 Redo Log 或 Binlog，使并发越高时单次 fsync() 分摊的事务数越多，从而在「双 1」强持久性下依然维持数万 TPS 的写入吞吐。

2. 为什么有了 Redo Log 还需要双写缓冲区（Doublewrite Buffer）

InnoDB 页大小为 16 KiB，而 Linux 文件系统块通常为 4 KiB。若后台刷脏页写到一半（如刚写完 4 KiB）时发生掉电，磁盘上的 16 KiB 页就会发生部分页写入断裂（Partial Page Write / Torn Page）。同时，InnoDB 的 Redo Log 采用的是「物理页号 + 页内逻辑修改（Physiological Logging）」而非整页字节镜像，如果磁盘上的 16 KiB 原页本身已经断裂损坏，Redo Log 根本无法在一个损坏的残页上执行逻辑重放。因此刷脏页前先顺序写入磁盘上的 Doublewrite 文件（#ib_16384_0.dblwr）；一旦发现 .ibd 页 Checksum 损坏，先从 Doublewrite 拷回完整无损的 16 KiB 旧页副本，再在上面重放 Redo Log。

06.3 · 高可用与双写架构：主从复制三线程模型、AFTER_SYNC 无损半同步、MGR 与 Redis 缓存一致性

06.3 主从复制三线程模型、无损半同步复制与缓存双写一致性 常问

这节回答实战篇哪个问题：对应 实战篇 06.8 缓存一致性 与 07.6 读写分离 —— 主从复制延迟具体发生在哪一步，半同步复制防住了什么，以及如何订阅 Binlog 兜底删除 Redis 缓存？

  1. 主从复制三线程流水线与并行回放：
    • 主库 Binlog Dump Thread：当从库发起连接时，主库为其创建一个转储线程，读取主库磁盘上的 Binlog 事件并发送给从库。
    • 从库 I/O Thread：接收主库发来的 Binlog 事件，原样顺序写入从库本地的中继日志（Relay Log）。
    • 从库 SQL Thread / Coordinator + Workers：读取 Relay Log 并解析回放。MySQL 5.7/8.0 引入了基于 LOGICAL_CLOCK 与 WriteSet（主键/唯一键冲突哈希集合）的多线程并行复制（MTS）——只要两个事务修改的行没有主键/唯一键交集，即使它们在主库上是先后串行执行的，在从库上也能由多个 Worker 线程并行回放。
  2. 三种复制同步模式对比：
    • 异步复制（Asynchronous，默认）：主库执行完事务立即向客户端返回成功，不关心从库是否收到 Binlog。主库宕机切换时可能丢失尚未传到从库的最新事务。
    • 无损半同步复制（Lossless Semi-Synchronous，rpl_semi_sync_master_wait_point = AFTER_SYNC）：主库在写完本地 Binlog 后、执行引擎层 Commit 之前（AFTER_SYNC）暂停等待，直到至少一个从库的 I/O 线程接收到该 Binlog 并写入 Relay Log 返回 ACK 后，主库才执行引擎层 Commit（此时对主库其他会话才可见）并返回给客户端。相比 5.6 的 AFTER_COMMIT，AFTER_SYNC 消除了主库崩溃前其他会话读到未同步数据的幻影读风险。
    • 组复制（MGR，MySQL Group Replication）：基于分布式 Paxos 协议 的多节点复制插件，事务在提交时由组内多数派节点（Majority Quorum）进行冲突认证（Certify）与广播决议，实现自动选主与故障强一致自愈。
  3. MySQL × Redis 缓存双写一致性标准工程实践：
    • 首选 Cache-Aside（旁路缓存）模式：「先更新 MySQL 数据库，成功后直接删除（Invalidate）Redis 缓存，绝不直接更新缓存」。之所以不采用「先删缓存再更新数据库」，是因为在并发读写下，请求 A 删完缓存还没来得及提交数据库修改时，请求 B 就读到了数据库旧值并重新回填进 Redis，造成缓存长期脏数据；而「先更库、再删缓存」即便在极端时序下发生并发污染，概率也低两个数量级（因为写数据库的耗时远大于读缓存）。
    • 如果第 2 步「删除 Redis 缓存」因为网络抖动失败，可通过 Canal / Debezium 伪装成 MySQL 从库订阅主库的 ROW 格式 Binlog，将变更事件投递到消息队列（Kafka / RocketMQ）进行异步重试失效缓存，实现最终强收敛。
06.4 · 深度自测：15 道贯穿存储、B+ 树、优化器、MVCC、Next-Key Lock 与 WAL 的闭卷问答

06.4 MySQL 核心原理与高并发调优深度自测（15 题闭卷问答）

合上前面的章节，尝试用自己的话回答以下 15 个贯穿存储、索引、优化器、MVCC、锁与日志的底层机制问题，点击卡片即可展开核对参考解析：

01. InnoDB 为什么默认按 16 KiB 的页（Page）而不是按单行（Row）与磁盘交互？页内查找一行记录为什么不需要从头到尾遍历链表？

参考解析：按照局部性原理，每次将 16 KiB 连续字节读入 Buffer Pool 可以将单次随机磁盘 I/O 分摊到数百行记录上。在 16 KiB 页内部，所有记录虽然按主键值顺序组成单向链表，但页尾的 Page Directory（页目录） 会将所有记录每 4~8 条划分为一个分组，并将每组最后一条记录的页内偏移量存入有序槽位数组（Slots）。页内查找时先对固定长度的槽位数组执行二分查找（约 4~6 次比较锁定分组），再在组内向后遍历最多 8 条记录即可命中。

02. InnoDB 一行记录如果没有显式定义 PRIMARY KEY，聚簇索引是如何构建的？三个隐藏系统列各自占多少字节？

参考解析：① 优先使用显式声明的 PRIMARY KEY；② 若无主键，选择第一个所有列均声明为 NOT NULL 的 UNIQUE 唯一索引；③ 若仍不满足，InnoDB 自动生成一个 6 字节的隐藏自增行号 DB_ROW_ID 作为隐式聚簇索引（但全局共用 dict_sys->mutex 分配，高并发存在锁争用）。除此之外，每条聚簇索引记录必定包含 6 字节的事务 ID DB_TRX_ID 和 7 字节的 Undo 回滚指针 DB_ROLL_PTR。

03. 为什么一次意外的全表扫描（如 mysqldump 导出冷表）不会把 Buffer Pool 里的核心热点缓存全部挤出内存？

参考解析：因为 InnoDB 将 LRU 链表按 5:3 切分为 Young 热区（前 5/8） 与 Old 冷区（后 3/8），并采用了两道防护机制：① 中点插入（Midpoint Insertion）：新从磁盘读入的页只能插入到冷区头部 Midpoint，而不会直接进入热区头部；② 冷区停留时间窗口（innodb_old_blocks_time = 1000ms）：新页在冷区被访问时，只有距离首次入链的时间间隔超过 1 秒，才允许晋升到 Young 热区头部。全表扫描在一个 16 KiB 页上连续读取百余行只需不到 1 毫秒，因此扫描过的冷表数据页会全部被锁死在 Old 冷区并迅速从链表尾部淘汰。

04. Change Buffer 的工作原理是什么？为什么唯一索引（Unique Index）的更新无法使用 Change Buffer？

参考解析：当对非唯一二级索引执行写操作且目标二级索引页不在 Buffer Pool 内存中时，InnoDB 不会立即发起随机磁盘 I/O 读取该页，而是先把变更暂存在 Change Buffer 中，等到未来有查询真正将该二级索引页读入内存时再顺便执行 Merge。而唯一索引（Unique Index）在插入或更新时必须先校验新值是否已在表中存在，如果目标页不在内存中，就必须立刻发起随机磁盘 I/O 把二级索引页读入内存检查唯一性；既然页都已经读进内存了，直接修改内存页即可，无需再走 Change Buffer。

05. 请定量推算：一棵高度 h = 3 的 InnoDB B+ 树聚簇索引大约能容纳多少行数据？

参考解析：在 16 KiB 页中扣除页头页尾开销后约剩 15 KiB 可用空间。假设主键为 BIGINT (8B)，在非叶子内节点中每条目录项由「8B 主键 + 6B 子页号 = 14B」加 5B 记录头组成（约 13~19B），单页扇出阶数约为 15360 / 13 ≈ 1170；高度 h = 2 的两层非叶子节点可寻址 1170 × 1170 ≈ 1,368,900 个叶子页。若叶子页单行记录平均长 1 KiB（每页存 16 行），则 3 层 B+ 树可容纳约 136.89 万 × 16 ≈ 2190 万行；若单行仅 500B（每页存 30 行），则可容纳超过 4100 万行。

06. 为什么 InnoDB 表强烈建议使用单调递增的整型主键（如自增 BIGINT 或雪花 ID），而不建议使用随机 UUID 字符串？

参考解析：主要有三方面原因：① 页分裂与空间碎片：递增主键走顺序追加，写满 15/16 直接开辟新页；随机 UUID 每次随机插入已满的旧页中间，频繁触发耗时的页分裂（Page Split），并使数据页平均填充率跌至 50%~65%；② 所有二级索引体积膨胀：InnoDB 所有二级索引叶子节点存储的都是主键值，CHAR(36) UUID 比 8 字节 BIGINT 大 4.5 倍，如果有 4 个二级索引，全表索引体积将膨胀数倍；③ 比较与哈希开销：64 位整数单条 CPU 指令即可完成比较，远快于多字节字符串逐字符校对。

07. 某列明明建了二级索引，为什么当 WHERE 范围过滤出的行数超过全表 20%~30% 时，优化器宁可放弃索引改走全表扫描？

参考解析：因为如果查询不是覆盖索引，走二级索引每命中一行都需要拿主键值去聚簇索引做一次回表（Random I/O）。在 CBO 成本模型中，优化器默认认为每次回表相当于读取一个离散的 16 KiB 页（哪怕同一页被回表 10 次也按 10 次页读取计费）；而全表扫描聚簇索引是按区（Extent）连续顺序读取，只需扫描总页数即可拿到全部列。因此当预估匹配行数达到全表 20%~30% 时，「二级索引扫描 + 海量离散回表」的估算总成本就会反超「聚簇索引全表顺序扫描」。

08. 什么是索引条件下推（ICP，Index Condition Pushdown）？它在 EXPLAIN 中有什么标志？

参考解析：假设有联合索引 idx_a_b_c(a, b, c)，查询条件为 WHERE a = 1 AND b > 10 AND c = 5。根据最左前缀原则，b > 10 之后 c = 5 无法用于 B+ 树二分定位，但在联合索引的叶子节点中已经包含了列 c 的值。开启 ICP 后，Server 层会把 c = 5 下推给 InnoDB 引擎，在遍历二级索引时先在索引内部过滤掉 c != 5 的记录，只对满足 c = 5 的记录执行回表，从而大幅减少无效回表次数。在 EXPLAIN 的 Extra 列中会显示 Using index condition。

09. MySQL 执行 ORDER BY 触发 Using filesort 时，全字段单路排序与 rowid 双路排序是如何切换的？ORDER BY ... LIMIT N 又做了什么优化？

参考解析：优化器会比较 SELECT 查询所需列的总字节长度与系统参数 max_length_for_sort_data（8.0 默认 4096B）：若单行总长不超过阈值，采用全字段单路排序（把所有查询列一起放入 sort_buffer，排完直接返回，无需二次回表）；若单行包含大字段超过阈值，则退化为rowid 双路排序（sort_buffer 中只放「排序字段 + 主键 ID」，排完序后再拿前 N 个主键去聚簇索引二次回表取其余列）。此外，对于带 LIMIT N 的排序，若前 N 行能装入 sort_buffer，MySQL 会采用大小为 N 的优先队列（大根堆/小根堆），无需对全量数据做快速排序即可选出 Top-N。

10. InnoDB 的 ReadView 包含哪四个核心字段？READ COMMITTED 与 REPEATABLE READ 在 MVCC 实现上的唯一区别是什么？

参考解析：ReadView 的四个核心字段为：① m_creator_trx_id（创建该视图的自身事务 ID）；② m_ids（生成视图瞬间系统中活跃未提交的读写事务 ID 列表）；③ m_up_limit_id（m_ids 中的最小值，低水位，小于它的必定已提交可见）；④ m_low_limit_id（系统尚未分配的下一个事务 ID，高水位，大于等于它的必定不可见）。RC 与 RR 在 MVCC 上的唯一区别在于生成 ReadView 的时机：RC 在每次执行普通 SELECT 时都重新生成一个新的 ReadView；而 RR 只在事务内第一次执行普通 SELECT 时生成 ReadView，并在整个事务期间一直复用该视图。

11. 为什么两个并发事务同时执行「先 SELECT ... WHERE id = 15 FOR UPDATE（记录不存在），再 INSERT id = 15/16」会触发死锁？

参考解析：当表中有 id = 10, 20 而 id = 15 不存在时，事务 A 执行 SELECT ... WHERE id = 15 FOR UPDATE 会在 (10, 20) 上获得一把间隙锁（Gap Lock）。由于 InnoDB 的 Gap Lock 之间是完全互相兼容、不互斥的（无论是 Gap S 锁还是 Gap X 锁），此时并发的事务 B 执行相同的加锁查询也会成功获得 (10, 20) 的 Gap Lock。紧接着，事务 A 执行 INSERT 需要获取 (10, 20) 的插入意向锁，被事务 B 的 Gap Lock 阻塞；随后事务 B 也执行 INSERT 请求插入意向锁，又被事务 A 的 Gap Lock 阻塞，形成循环等待死锁。

12. 在 REPEATABLE READ 下，表中主键 id 有 10, 20, 30，普通索引 age 也有 10, 20, 30。分别对 id = 20 和 age = 20 执行 FOR UPDATE，加锁范围有何不同？

参考解析：① 对唯一索引/主键 WHERE id = 20 FOR UPDATE：由于唯一性保证不可能再插入第二个 20，Next-Key Lock (10, 20] 会退化为仅锁住 id = 20 这一行的 Record Lock（记录锁）；② 对非唯一普通索引 WHERE age = 20 FOR UPDATE：由于允许重复插入 age = 20，InnoDB 不仅在二级索引上对 20 加完整的 Next-Key Lock (10, 20]（同时回表锁住主键 id = 20 的记录锁），还必须继续向右扫描到第一个不等于 20 的值（age = 30），并在 (20, 30) 上退化加上一把 Gap Lock，从而锁死 (10, 30) 之间所有插入 age = 20 的可能。

13. 在两阶段提交（2PC）中，如果主机在「Redo Log Prepare 已落盘、Binlog 已落盘，但 Redo Log Commit 尚未写入」时断电，重启后该事务会回滚还是提交？

参考解析：重启后会自动提交（Commit）。MySQL 崩溃恢复时的裁决规则是：扫描 Redo Log，若发现某个事务已经处于完整的 Commit 状态则直接重放；若发现事务仅处于 TRX_PREPARED 状态，则提取该 Redo Log 中的内部事务号 XID 去核查 Binlog——只要在 Binlog 中找到了该 XID 对应的完整记录（说明该 Binlog 随时可能已经被从库拉取回放），主库就必须将该事务判定为已提交并补齐 Commit，以保证主从数据严格一致。

14. 既然 Redo Log 已经持久化落盘，为什么 InnoDB 刷脏页时还需要先写 Doublewrite Buffer（双写缓冲区）？

参考解析：因为 InnoDB 页大小为 16 KiB，而操作系统与磁盘块通常为 4 KiB，刷脏页中途掉电会导致磁盘上的 16 KiB 页只写了一半，发生部分页写入断裂（Partial Page Write / Torn Page）。同时，InnoDB 的 Redo Log 记录的是「物理页定位 + 页内逻辑操作（Physiological Logging）」，它必须以一个物理结构完整无损的旧页作为重放基准；一旦磁盘上的原页本身已经断裂损坏，Redo Log 是无法在残缺页上重放的。通过先将脏页顺序写入磁盘上的 Doublewrite Buffer，当发现 .ibd 页损坏时，即可先从 Doublewrite 恢复出完整的 16 KiB 旧页副本，再重放 Redo Log。

15. 在一张 2000 万行的线上核心表上执行 ALTER TABLE 新增索引，为什么即便使用了 Online DDL（INPLACE），也有可能瞬间把整个数据库的普通 SELECT 全部堵死？如何防御？

参考解析：因为即便是 INPLACE 或 INSTANT 算法，在 DDL 准备阶段（Prepare）和提交阶段（Commit） 依然需要短暂获取表级的 MDL 排他写锁（Metadata Exclusive Lock）。如果此时表上恰好有一个未提交的长事务或慢查询正在持有 MDL 读锁，ALTER TABLE 就会卡在 Waiting for table metadata lock；而由于 MDL 锁等待队列中写锁具有更高优先级，排在该 ALTER TABLE 之后到达的所有普通 SELECT 也会全部被阻塞，瞬间打满应用连接池。防御措施：执行 DDL 前检查 information_schema.innodb_trx 清理长事务，并在当前会话显式设置 SET SESSION lock_wait_timeout = 3;，拿不到 MDL 锁立即超时退出让路。
