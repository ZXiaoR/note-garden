0 · 整体架构：一条 SQL 的旅程

MySQL 的精髓是 Server 层与存储引擎层分离的插件式架构。Server 层负责 SQL 的解析、优化、执行等所有引擎无关的工作；存储引擎层负责数据的真正存取，可插拔（InnoDB、MyISAM、Memory…），我们只讲主流的 InnoDB。

二 · 1 存储结构：B+ 树与页 InnoDB层

为什么是 B+ 树？

数据结构用 B+ 树，以 页(Page) 为单位存储。先看"为什么是 B+ 树"，这几乎必问：

候选结构为什么不用
哈希表O(1) 等值查询很快，但不支持范围查询、排序，MySQL 范围查询极多
二叉搜索树 / 红黑树树太高（logₖ 中 k=2），每层一次磁盘 I/O，几百万数据要几十层 → 磁盘 I/O 爆炸
B 树非叶子节点也存数据 → 单页能放的 key 变少 → 树变高；且范围查询要中序回溯
B+ 树 ✓① 非叶子只存索引 key，一页能放上千个 → 树矮胖，通常 3~4 层就能存千万行；② 数据全在叶子且叶子间双向链表相连 → 范围查询顺序扫描极快

查 id=8：根(10) → 走左 → 中间(5|8) → 叶子，3 次 I/O；查 id≥8：定位到 8 后沿叶子链表往右扫
记忆点：3 层 B+ 树 ≈ 存 2000 万行左右。查任意一行最多 3 次磁盘 I/O（且根节点常驻内存，实际更少）。非叶子只存 key 做导航，数据全在叶子，叶子间双向链表相连 —— 这三点是 B+ 树的全部精髓。

"2000 万" 是怎么算出来的？—— 索引页 vs 数据页

关键在于非叶子节点（索引页）和叶子节点（数据页）存的内容不同，所以一页能容纳的条目数天差地别。注意：一页 16KB 并非全部可用，文件头(38B)+页头(56B)+Infimum/Supremum(26B)+页目录+文件尾(8B) 合计约 128B 固定开销（页目录随记录增长），可用空间约 16256B ≈ 15.9KB。这份开销索引页、数据页都有：

页类型存什么单条大小可用≈16256B 能放
索引页(非叶子)key + 子页指针主键 bigint 8B + 指针 6B ≈ 14B16256 / 14 ≈ 1160 条（约定俗成取 1170）
数据页(叶子)key + 整行数据(含记录头等)假设一行 ≈ 1KB16256 / 1024 ≈ 15~16 行

扣掉页头页尾后，索引页从 1170 降到约 1160、数据页从 16 降到约 15 —— 开销仅占 0.8%，不影响数量级，所以传统上仍用 1170 和 16 这两个整数估算。

因为索引页一条只占 14 字节，一页就能装下 1170 个指针，扇出(fan-out)极大；而数据页要存整行，一页只放得下 16 行。于是逐层相乘：

  • 1 层(只有根)：1 页 → 16 行
  • 2 层：根 1170 个指针 → 1170 个数据页 → 1170 × 16 ≈ 1.87 万行
  • 3 层：1170 × 1170 个数据页 → 1170 × 1170 × 16 ≈ 2190 万行 ✓

注：行越大(如 2KB)，叶子每页放的行越少，总容量按比例下降；主键越小(如 int 4B)，索引页扇出越大，容量上升。所以"2000 万"是个数量级估算，不是精确值。

由此引申：正因为"索引页存 key、数据页存整行"，才要搞清楚一个页内部到底怎么组织这些数据（记录放哪、怎么快速定位、怎么校验完整）—— 见下面的页结构。

页(Page) —— 磁盘 I/O 的最小单位

默认 16KB。InnoDB 读数据不是按行读，而是按页读：哪怕只要一行，也把整页 16KB 加载进内存。页之间通过 File Header 里的指针组成双向链表；页内记录组成单向链表。

页的内部结构（7 个部分）

File Header　38B　页号、上一页/下一页指针、校验和、类型　← 组成页间双向链表
Page Header　56B　本页记录数、槽数量、方向、堆顶位置等
Infimum + Supremum　两条虚拟记录：最小 & 最大边界
User Records　真实数据行（按主键顺序的单向链表）　← 数据主体
Free Space　剩余空闲空间
Page Directory　页目录 / 槽(Slot)　← 页内二分查找靠它
File Trailer　8B　校验和 + LSN，校验刷盘是否完整　← 防"刷一半崩了"
  • Page Directory（页目录）：页内记录是单向链表，若逐条遍历是 O(n)。页目录把记录分成若干组，每组末条记录的位置存进"槽(slot)"，查找时先在槽上二分定位到组，再在组内遍历，把页内查找变成近似 O(log n)。
  • File Trailer：和 File Header 里的校验和呼应。刷盘可能刷到一半宕机（页损坏），靠头尾校验和是否一致来检测。（真正防止部分写的是后面讲的 double write。）
索引页也是这套结构。 InnoDB 里所有页共用上面这同一个 7 部分模板（都 16KB，都有文件头/页头/文件尾）——这正是前面算容量时"索引页也要扣 128B 开销"的原因。索引页与数据页的唯一区别在 User Records 区里放的记录类型不同：
页类型User Records 里放什么record_type
数据页(叶子)完整的行：key + 所有列 + 隐藏列0 普通记录
索引页(非叶子)目录项记录：只有 key + 子页页号1 目录项记录

页头里的 FIL_PAGE_TYPE（页类型）和 PAGE_LEVEL（层高，0=叶子）标识身份。索引页里的目录项记录同样组成单向链表、同样有 Infimum/Supremum 和页目录做二分 —— 查找逻辑与数据页完全一致，只是"记录"瘦身成了 key+页号。

页之上：区 / 段 / 表空间

行 Row→ 页 Page 16KB→ 区 Extent 64页=1MB→ 段 Segment→ 表空间 Tablespace .ibd

引入"区"是为了让 B+ 树叶子节点在物理上连续：如果一页一页随机分配，叶子链表在磁盘上东一块西一块，范围查询就退化成随机 I/O。按区（连续 64 页）分配就能顺序 I/O。段则区分"叶子段/非叶子段"等。

Buffer Pool 与 Change Buffer（内存管理）InnoDB层

为什么需要 Buffer Pool？

根本矛盾：数据在磁盘上，但磁盘太慢。内存随机访问是纳秒级，磁盘（尤其机械盘）随机 I/O 是毫秒级，差了几个数量级。如果每次读写都直接落盘，数据库根本跑不动。

所以 InnoDB 在内存里开辟一块缓存 —— Buffer Pool（默认 128MB，生产常设为物理内存 60~80%），把用到的页缓存进来：

  • 读：先看页在不在 Buffer Pool。命中 → 直接从内存返回（快）；未命中 → 从磁盘读整页进 Buffer Pool，再返回。基于局部性原理，热点页会一直待在内存，命中率通常很高。
  • 写：不直接改磁盘，而是改内存里的页（该页变成脏页，即内存与磁盘不一致），配合 redo log 保证不丢，再由后台线程择机批量刷盘。把大量随机写攒成少量顺序刷 —— 这就是 WAL（Write-Ahead Logging）的基础。

Buffer Pool 里到底放了啥？

它以 16KB 的页为单位管理，缓存的不只是数据页：

Buffer Pool（默认 128MB · 以 16KB 页为单位）
数据页聚簇索引叶子，存整行数据
索引页非叶子节点，存目录项 key+页号
undo 页回滚 + MVCC 历史版本
Change Buffer缓存非唯一二级索引的写，延后 merge
自适应哈希 AHI对热点页建 hash，等值查询直达
锁信息 / 数据字典行锁等运行时信息
🔵 三种「页」都以 16KB 为单位缓存　🟢 三类辅助结构也住在 Buffer Pool 里

另外，每个缓存页还配一个控制块（描述信息），记录该页属于哪个表空间、页号、在 LRU/free 链上的位置、是否是脏页等。控制块和缓存页一一对应，也占 Buffer Pool 空间。

为什么要 LRU？为什么是"改良版"LRU？

为什么要 LRU：内存有限，Buffer Pool 装不下全部数据。当 free 链没有空闲页、又要读新页进来时，必须淘汰一个旧页。淘汰谁？根据局部性原理，最近最少使用（LRU）的页最可能不再用到，淘汰它命中率损失最小。

为什么普通 LRU 不行：朴素 LRU 是"页一被访问就挪到链表头"。但有两个场景会污染它：

  • 全表扫描：一条 select * 不带索引，会把一张大表的所有页一次性读进来，瞬间把真正的热点页全挤到尾部淘汰掉 —— 而这些扫描页可能只用一次。
  • 预读(read-ahead)：InnoDB 预测你可能要用相邻页，提前读进来，但这些页未必真会被用到，一样占着链表头。

改良版 LRU：冷热分区。 InnoDB 把 LRU 链按比例分成两段（innodb_old_blocks_pct 默认 37%）：

LRU 链表（冷热分区）
young 区（热 · 5/8）
真正的热点页常驻
old 区（冷 · 3/8）
新读入的页先进这里（old 区头部）
◀── 淘汰从整条链尾部（old 区尾）进行
  • 新读入的页先放 old 区头部，而不是整个链表的头部。全表扫描/预读的页只会在 old 区打转，用完很快从尾部淘汰，碰不到 young 区的热点页。
  • 怎么升到 young 区？不是"再被访问一次就升"，而是要满足时间窗口：页在 old 区停留超过 innodb_old_blocks_time(默认 1000ms) 后再次被访问，才升到 young 区头部。这样"一次全表扫描里同一页被连续访问多次"也不会误升 —— 因为发生在极短时间内。
  • 为减少频繁挪动，young 区里的页只有在后 1/4 之后被访问才移到头部。

Change Buffer（写缓冲）

对非唯一二级索引的写，如果目标页不在 Buffer Pool，不必为了这次写立刻从磁盘读页进来，而是把改动先记在 Change Buffer 里，等该页因别的查询被读入时再合并(merge)。写多读少场景能显著减少随机 I/O。

为什么只对"非唯一二级索引"？唯一索引写入前必须判重，判重就得把页读进来，读都读了自然直接改，用不上缓冲；聚簇索引改动往往连带整行也没法缓冲。

脏页刷盘时机：① redo log 快写满（推进 checkpoint）；② Buffer Pool 空闲页不足，淘汰的正好是脏页；③ 系统空闲时后台慢慢刷；④ 正常关闭时全部刷完。刷太频繁影响性能，太少则宕机时要靠 redo 恢复的量大、恢复慢。

额外信息三件套

  • 变长字段长度列表：记录 varchar/text 等变长列的实际字节长度，逆序存放。
    为什么需要它？ 定长列（char(10)、int）光看表定义就知道占几字节，读取时按固定宽度切即可。但变长列能存 0 ~ 最大值之间任意长度，而 InnoDB 的行是紧凑存储、列与列之间没有分隔符也不补空 —— 读的时候根本不知道一个 varchar 从哪结束、下一列从哪开始。所以必须把每个变长列这一行的实际长度记下来，才能正确切分数据区。这就是这个列表存在的意义。
    为什么逆序？ 关键在记录头里的 next_record 指针：它不指向记录开头，而是指向"额外信息"与"真实数据"的分界点（即第一个真实列的位置）。从这个点出发：向右读是真实数据（col1、col2…），向左读是额外信息。
    于是把长度列表逆序放，就让 col1 的长度紧贴在分界点左边、col2 的长度再往左… —— 想解析 col1 时，它的长度信息离指针最近，往左顺着读即可，前面的列（更常用）总在离指针最近的位置，CPU 缓存局部性更好、访问更高效。NULL 值列表同理也逆序。

    长度用 1 字节还是 2 字节？ 令 W=字符集单字符最大字节数（ascii=1 / utf8=3 / utf8mb4=4），M=varchar 最大字符数，L=实际字节数。判定：W×M ≤ 255 恒用 1 字节；W×M > 255 时 L≤127 用 1 字节、L>127 用 2 字节（首字节最高位置 1 作标志）。 📖 看例子（一条 SQL 走一遍）

    为什么需要它？ 如果把 NULL 直接存进真实数据区，既浪费空间（NULL 本没有值，却要占一个坑），又难以区分"空字符串"和"NULL"。InnoDB 的做法是：每个允许 NULL 的列分配 1 个二进制位，1=该列为 NULL、0=非 NULL。这样标记为 NULL 的列在真实数据区一个字节都不占 —— 用 1 个 bit 换掉可能几十字节的存储。所以常说"NULL 也占空间"，占的其实是这个位图里的 1 个 bit（不足整字节高位补 0），而非数据区。

覆盖索引 · 索引下推 · 最左前缀

  • 覆盖索引：要查的列全部都在某个二级索引里，直接从索引就能返回，不用回表。explain 的 Extra 出现 Using index 就是它。是最重要的优化手段之一。
  • 最左前缀原则：联合索引 (a,b,c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引。查询必须从最左列开始且不跳列，才能用上。
    为什么会这样？ 联合索引 (a,b,c) 这棵 B+ 树是先按 a 排、a 相同再按 b 排、b 也相同再按 c 排。关键点：b 只在"a 相同"的范围内才有序，c 只在"a、b 都相同"的范围内才有序。所以：
    • 不给定 a，b 在整棵树里是全局无序的 → where b=2 没法二分定位，用不上索引。
    • 给了 a 但跳过 b 直接给 c（where a=1 and c=3）→ 能用 a 定位，但在同一个 a 里 c 是散乱的（因为 c 只在 b 也固定时才有序）→ c 用不上，只能用到 a。
    • 范围查询会中断后续列：where a=1 and b>2 and c=3 → a、b 能用（b 走范围），但 b 一旦是范围，其后的 c 就失序了 → c 不能再用于定位（只能靠 ICP 在索引上过滤）。
    顺序无关：WHERE 里 AND 条件的书写顺序不影响，where b=2 and a=1 一样能用 (a,b) —— 优化器会自动按索引列顺序重排。"最左"指的是索引定义的列顺序，不是 SQL 里写的顺序。📖 看例子（排序 + 各查询能用几列）

    最左前缀 · 联合索引 (a, b, c)

    索引 idx(a,b,c) 里数据的物理排序（先 a、再 b、再 c）：

    (a, b, c) a 全局有序 ↓ b 只在同一个 a 内有序 → c 只在同一个 (a,b) 内有序 ───────── (1, 1, 1) ┐ (1, 1, 2) │ a=1 段：b 有序(1,1,2,2)，每个 b 内 c 有序 (1, 2, 1) │ (1, 2, 3) ┘ (2, 1, 5) ┐ (2, 3, 1) │ a=2 段：b 又从头有序(1,3) (2, 3, 4) ┘

    看第 2 列(b)：整体是 1,1,2,2,1,3 —— 跨 a 看根本不递增，所以脱离 a 无法对 b 二分。这就是"必须带最左列"的根源。

    各类查询能用到索引的哪几列：

    查询条件用到的列说明
    a=1✅ a最左列，可定位
    a=1 AND b=2✅ a, b连续从左用
    a=1 AND b=2 AND c=3✅ a, b, c全用上
    b=2 / c=3❌ 无没带最左列 a，b/c 全局无序
    a=1 AND c=3⚠️ 只 a跳过了 b，c 在 a 段内散乱用不上（c 可由 ICP 过滤但非索引定位）
    a=1 AND b>2 AND c=3⚠️ a, bb 用范围后 c 失序，c 不能定位
    b=2 AND a=1✅ a, b书写顺序无关，优化器重排为 (a,b)
    a=1 ORDER BY b✅ a, b排序也遵循最左前缀，b 在 a=1 内本就有序，免 filesort
    两条铁律：① 从最左列开始、中间不能跳列；② 遇到范围查询(> < between like前缀)，该列还能用，但它后面的列全部失效。据此建索引时应把等值列放前、范围列放后。
  • 索引下推 ICP (Index Condition Pushdown，5.6+)：联合索引中，把本该回表后在 Server 层做的过滤，下推到引擎层在索引上先过滤，减少回表次数。Extra 显示 Using index condition。
ICP 例子：索引 (name,age)，查 where name like '张%' and age=10。没有 ICP：用 name 前缀找到一堆记录，逐条回表再判 age。有 ICP：在索引上就顺便把 age=10 判掉，只对满足的才回表。

"对列做运算/函数就失效"—— 到底为什么？

有人会说："不就是加个 1、取个 date 吗，MySQL 帮我算一下不就行了？"这个直觉只对了一半。真正的原因分两层：

① 根本原因：B+ 树按原值排序，套了函数就用不上这个顺序

索引 idx(c) 是一棵按 c 的原值有序的 B+ 树。查 WHERE c = 5 能二分定位，因为树就是按 c 排的。但查 WHERE c+1 = 5，你要找的是"c+1"这个值，而树不是按 c+1 排序的 —— 有序性对 c+1 不成立，没法二分，只能把每一行的 c 取出来算一遍 c+1 再比较，这就是全表扫描。

索引树按 c 排： 1 2 3 4 5 6 ... ← 查 c=5，二分直接跳过去 ✅ 但按 c+1 呢？ 树没有这个顺序，要逐行算 c+1 才知道 ❌

② 你的观点：情况太多，MySQL 干脆不做自动改写（补充原因）

有人会追问："c+1=5 不就等价于 c=4 吗？MySQL 改写一下不就能用索引了？"—— 理论上对于单调函数确实可以反解。但 MySQL 基本不做这种自动改写，原因正是你说的：

  • 要对任意函数判断是否单调、能否反解、构造逆变换 —— 函数无穷多，情况爆炸；
  • date()、substr()、隐式字符集/类型转换等很多函数根本不可逆或非单调，反解无从谈起；
  • 为少数可优化的特例写一堆兼容逻辑，收益低、还容易出错。

所以优化器取保守策略：只要列被表达式包住，就不信任索引顺序，直接全表扫。你的"兼容太复杂"说的就是这一层。

③ 佐证 & 正确写法

  • 把运算移到常量侧：where c+1=5 → 手动改成 where c=4，索引恢复。（这活儿得你自己干，MySQL 不替你干，正好印证 ②）
  • 函数索引 (MySQL 8.0)：确实要按 date(t) 查，就 CREATE INDEX idx ON t((date(t))) 显式建一棵按 date(t) 排序的树，之后 where date(t)='...' 就能走索引 —— 这说明 MySQL 需要你显式为表达式建序，而不会自动处理 f(c)。
一句话总结：主因是有序性被破坏（树按原值排，函数值无序）；你说的"情况太多难兼容"是优化器不愿自动改写的现实原因。两者叠加，才有"对列做运算就失效"。

优化经验

  • 建联合索引时把区分度高、常用、范围查询的列合理排序（等值列在前，范围列在后，否则范围之后的列用不上）。
  • 尽量用覆盖索引避免回表；select * 是回表 + 无法覆盖的元凶。
  • 长字符串用前缀索引；但前缀索引无法用于覆盖索引和排序。
  • 主键尽量自增：随机主键(如 UUID)会导致 B+ 树页分裂和碎片。

二 · 4 事务 InnoDB层

怎么开启 / 结束事务？要显式自己加吗？

关键在一个参数：autocommit（自动提交），MySQL 默认开启（=1）。它决定了你要不要显式开事务。

① 默认（autocommit=1）：不用显式开，每条语句自成一个事务

自动提交开启时，你执行的每一条单独 SQL 都被自动包成一个事务，执行完立刻提交。所以平时随手写的 UPDATE 其实也在事务里，只是"开启→执行→提交"一气呵成，你没感觉到。

UPDATE t SET v=1 WHERE id=1;   -- 等价于：BEGIN; UPDATE...; COMMIT; 自动完成
UPDATE t SET v=2 WHERE id=2;   -- 又是独立的一个事务

如果你想把多条语句绑成一个事务（要么全成功要么全回滚），就必须显式开启：

② 显式事务：手动 BEGIN … COMMIT / ROLLBACK

BEGIN;                          -- 或 START TRANSACTION，开启事务（此刻起暂停自动提交）
UPDATE acct SET bal=bal-100 WHERE id=1;
UPDATE acct SET bal=bal+100 WHERE id=2;
COMMIT;                         -- 一起提交；中途出错则 ROLLBACK 全部撤销

一旦 BEGIN，autocommit 对这个事务临时失效，直到你 COMMIT/ROLLBACK 才结束、恢复自动提交。转账这种多步必须原子的场景，就得显式开。

③ 另一种方式：把 autocommit 关掉（=0）

SET autocommit = 0;             -- 关闭后：任何一条 DML 都会隐式开启事务
UPDATE ...;                     -- 事务已开启，但不会自动提交
COMMIT;                         -- 必须手动提交，否则一直占着锁
坑：把 autocommit 设 0 后，连 SELECT/UPDATE 都会开启事务且不自动提交，如果忘了 commit，事务会一直挂着 → 长事务：长期持有行锁、MDL 锁、撑大 undo（purge 无法回收），是线上事故常见原因。生产一般保持 autocommit=1，需要事务时显式 BEGIN。
关键字作用
BEGIN / START TRANSACTION显式开启事务
START TRANSACTION WITH CONSISTENT SNAPSHOT开启事务并立即生成 ReadView（RR 下常用于确保从这一刻起的一致性快照）
COMMIT提交：持久化改动、释放行锁、结束事务
ROLLBACK回滚：靠 undo 撤销所有改动
SAVEPOINT s / ROLLBACK TO s保存点 / 回滚到保存点（部分回滚，不结束整个事务）
会"隐式提交"的语句：DDL（CREATE/ALTER/DROP/TRUNCATE）、GRANT、再次 BEGIN 等会自动先提交当前事务。所以在事务中间执行一条 ALTER TABLE，前面的改动会被"偷偷"提交掉，无法再回滚 —— 要留意。

RR 与幻读。 InnoDB 在 RR 级别下：快照读（普通 SELECT）用 MVCC 避免幻读；当前读（select...for update、update/delete）用 Next-Key Lock 避免幻读。所以 InnoDB 的 RR 在大多数场景下已经解决了幻读，这是它区别于标准 SQL 定义的地方。但极端交错场景（先快照读、再当前读同一范围）仍可能出现，不能说 100% 消除。

MVCC（多版本并发控制）重点

MVCC 让读不加锁、读写不冲突，靠三样东西：行里的隐藏列(DB_TRX_ID/DB_ROLL_PTR) + undo 版本链 + ReadView。

① 版本链

每次修改一行，旧值写入 undo log，新行的 DB_ROLL_PTR 指向旧版本，形成一条从新到旧的链。

最新行 ──roll_ptr──▶ undo:版本2 ──roll_ptr──▶ undo:版本1 trx_id=50 trx_id=30 trx_id=10

② ReadView（读视图）

快照读的瞬间生成，核心 4 个字段：

  • m_ids：生成 ReadView 时还活跃(未提交)的事务 ID 集合
  • min_trx_id：m_ids 里最小的
  • max_trx_id：下一个将分配的事务 ID（当前最大+1）
  • creator_trx_id：创建该 ReadView 的事务自己的 ID

③ 可见性判断规则

拿版本链上某行的 DB_TRX_ID（记作 trx）逐版本比对：

  1. trx == creator_trx_id → 可见（自己改的）
  2. trx < min_trx_id → 可见（生成视图前就已提交）
  3. trx ≥ max_trx_id → 不可见（视图生成后才开启的事务）
  4. min_trx_id ≤ trx < max_trx_id：若 trx 在 m_ids 里 → 不可见（当时还没提交）；不在 → 可见（当时已提交）

不可见就顺 DB_ROLL_PTR 找更老的版本，直到找到可见的。

RC 与 RR 的本质区别就一句话：建 ReadView 的时机不同。
· RC：每次 SELECT 都重新建 ReadView → 每次都能看到别人最新提交 → 会不可重复读。
· RR：事务内第一次 SELECT 建一次，之后复用 → 整个事务看到同一快照 → 可重复读。
快照读 vs 当前读：普通 SELECT 是快照读(走 MVCC，读历史版本、不加锁)；SELECT...FOR UPDATE/LOCK IN SHARE MODE、UPDATE、DELETE、INSERT 是当前读(读最新版本并加锁)。
承上启下 → 锁："当前读并加锁"里的"加锁"，展开就是下一章的锁。隔离性其实是两条线合力实现的：快照读靠 MVCC（本章）、当前读靠 锁（下章）。RR 防幻读也是如此 —— 快照读靠 MVCC，当前读靠 Next-Key Lock。所以事务讲到当前读，正好引出锁。

自增锁 AUTO-INC

为什么需要它？

自增列要保证每次插入拿到的值唯一且递增。多个事务同时插入时，若不加保护，可能两个事务读到同一个"当前最大值"，生成重复自增 id。所以 InnoDB 用一把表级的 AUTO-INC 锁，谁插入谁先拿锁、取到下一个值、再放锁 —— 让自增值的分配串行化。

关键特点：它是语句级的，语句一执行完就释放，不像行锁那样等到事务提交（commit）才放。所以持有时间通常很短。

(8.0 之前默认)		能提前确定行数的普通 INSERT，取完值立刻放锁（不等语句结束）；INSERT...SELECT 这种行数未知的仍用表锁折中：单行/批量插并发好，同一语句内的自增值连续

为什么 8.0 默认改成 2？—— 和 binlog 有关

模式 2 会让批量插入的自增值不连续，在早期 statement 格式 binlog 下会导致主从自增值对不上（从库重放语句时分配的值和主库不同）。MySQL 8.0 默认 binlog 用 row 格式（记录每行的实际值而非语句），主从直接按行同步，不再依赖自增分配顺序 —— 所以可以放心用并发更高的模式 2。

面试串联点：这里正好把自增锁 → binlog 格式(statement/row) → 主从复制串起来，能体现你理解锁和日志的关联。

Next-Key Lock 的 (前记录, 本记录] 到底指什么

"本记录 / 前记录"指的是索引上按顺序排列的、相邻的两条已存在记录。假设某索引列上现有三条记录 10、20、30，InnoDB 会用它们把整条数轴切成若干 Next-Key 区间，每段都是"(前一条记录, 这一条记录]"：

(-∞, 10] ← 本记录=10， 前记录=-∞（无穷小伪记录 infimum） (10, 20] ← 本记录=20， 前记录=10 (20, 30] ← 本记录=30， 前记录=20 (30, +∞) ← 本记录=supremum（正无穷伪记录），前记录=30

以区间 (10, 20] 为例拆开看：

部分是谁锁什么作用
本记录 = 20你命中/锁定的那条记录本身Record Lock 锁住"20 这一行"不让 20 被改、被删
前记录 = 10索引顺序里它前面一条已存在的记录Gap Lock 锁住 (10,20) 这段空隙不让别人插入 11~19
合起来 = (10, 20]Record + Gap = Next-Key Lock（左开不含 10、右闭含 20）
为什么左开右闭？ 既要锁住命中的记录 20（右闭，防它被改删），又要锁住它前面的间隙（左开的那段 gap，防插入新值造成幻读）；而 10 不重复锁，因为 10 归它自己的区间 (-∞,10] 管。这样一个个 (前,本] 区间首尾相接、不重不漏地铺满整条索引。

例：RR 下 SELECT * FROM t WHERE id > 15 FOR UPDATE，会锁住 (10,20]、(20,30]、(30,+∞) —— 从 15 落入的那段开始，一直锁到正无穷，别人无法在这些范围里插入或修改，从而防住幻读。

InnoDB 加锁逻辑（面试常问） 重点

  • 行锁加在索引上，不是加在行上。所以走不到索引的查询会退化成锁全表所有行（每行的 Next-Key Lock）—— 这也是"更新语句不带索引会锁表"的真相。
  • RR 下的加锁规律：
    • 唯一索引等值查询、命中：Next-Key 退化成 Record Lock（无需防间隙插入）。
    • 唯一索引等值查询、未命中：退化成 Gap Lock（锁住可能插入的间隙）。
    • 范围查询：用 Next-Key Lock，锁住整个扫描范围的间隙。
    • 非唯一索引等值查询：命中记录的 Next-Key + 右侧间隙的 Gap。
  • RC 下没有间隙锁（只有记录锁），所以 RC 并发更高但有幻读。

加锁逻辑实战 · RR 下 5 种查询各加什么锁

表 t(id INT PRIMARY KEY, k INT, KEY idx_k(k))，现有数据：

id : 5 10 15 20 (id 主键=唯一索引) k : 5 8 15 20 (idx_k 普通=非唯一索引) 主键 id 的 Next-Key 区间： (-∞,5] (5,10] (10,15] (15,20] (20,+∞)

下面全部是 RR 隔离级别、当前读（for update 或 update）。锁都加在索引上。

① 唯一索引等值 · 命中 → 退化 Record Lock

SELECT * FROM t WHERE id = 10 FOR UPDATE;

只锁 id=10 这一行（Record Lock）。因为主键唯一，命中一行就够了，不怕别人在旁边插入相同 id（插不进），所以不需要间隙锁。别人还能插入 id=11、更新 id=15。

② 唯一索引等值 · 未命中 → 退化 Gap Lock

SELECT * FROM t WHERE id = 12 FOR UPDATE;   -- 12 不存在

12 落在区间 (10,15) 里，加 Gap Lock (10,15)。锁住这段间隙，防止别人插入 11~14 让你"再查一次就出现了"（防幻读）。没有 Record Lock（本来就没记录可锁）。

③ 唯一索引范围 → Next-Key（含右边界）

SELECT * FROM t WHERE id >= 10 AND id < 15 FOR UPDATE;

锁 id=10 的 Record + (10,15) 的 Gap，即 Next-Key (5,15) 一带。要防止 10~14 之间被插入或修改。注意 id=15 这行：因为条件是 <15 且 15 是唯一索引确定的上界，通常不会锁到 15 本身（不同版本略有差异）。

④ 非唯一索引等值 → Next-Key + 右侧 Gap

SELECT * FROM t WHERE k = 8 FOR UPDATE;   -- idx_k 是普通索引

非唯一索引可能有多个 k=8，所以要防"再插一个 k=8"。加锁：k=8 的 Next-Key (5,8] + 向右到下一个值的 Gap (8,15)。同时因为要回表，命中行的主键 id 上也加 Record Lock。别人插 k=8 或 k=10 都被挡（8 到 15 之间的间隙被锁）。

⑤ 不走索引 → 锁全表每一行

SELECT * FROM t WHERE k+0 = 8 FOR UPDATE;  -- 对列运算，索引失效

用不上索引 → 全表扫描 → 扫到的每一行都加 Next-Key Lock，等于锁住整张表（所有记录 + 所有间隙）。这就是"更新不带索引会锁表"的真相。务必让 where 走索引。

规律总结：① 主键/唯一索引命中 → 只 Record；② 未命中 → 只 Gap；③ 非唯一索引/范围 → Next-Key(记录+间隙)，还要防右侧插入所以多锁一段右 Gap；④ 不走索引 → 锁全表。RC 隔离级别下把上面所有 Gap/Next-Key 都去掉，只留 Record Lock。

锁什么时候释放？—— 两阶段锁协议(2PL)

核心结论：InnoDB 的行锁遵循两阶段锁协议 —— 锁在事务执行中按需逐步加上，但不是用完就放，而是一直持有到事务 COMMIT 或 ROLLBACK 时才统一释放。

两阶段锁 (2PL)： 加锁阶段 ─────────────▶ 一路对访问到的行加锁，只加不放 ───────────────────── 事务执行中... update A（锁A）... update B（锁B）... ───────────────────── COMMIT / ROLLBACK ──▶ ★ 到这一刻，A、B 的锁一次性全部释放
锁类型释放时机
行锁（Record/Gap/Next-Key）事务 commit / rollback 时统一释放（不是语句结束）
意向锁 IS/IX事务结束
MDL 元数据锁事务结束 —— 长事务会一直占着，导致 DDL(改表结构)被长时间阻塞
AUTO-INC 锁语句结束就释放（前面讲过，不等事务）
表锁 lock tablesunlock tables 或事务结束
全局锁 FTWRLunlock tables 或客户端断开连接
2PL 的实践意义 —— 热点行的更新放到事务最后。 既然行锁要持有到事务结束，那么越早加的锁、被持有的时间越长，越容易阻塞别人。所以事务里应把并发冲突最激烈的那条更新语句放在最后，缩短它占锁的时间。
例：下单要「① 查商品信息 ② 插一条订单 ③ 扣热点商品库存」，应把③（大家抢的热点行）放最后执行，让它的行锁只在 commit 前极短时间内持有，提升并发。
一个例外（RC 下的提前释放）：RC 隔离级别下，UPDATE/DELETE 扫描时对不满足 where 条件的行，加的锁会在判断后立即释放，不用等事务结束；RR 下则倾向保留。所以 RC 加锁范围更小、并发更好（代价是有幻读）。

死锁

两个事务互相持有对方要的锁并等待，谁也不放手。InnoDB 有死锁检测(innodb_deadlock_detect)，检测到会回滚代价小的那个事务(报 Deadlock found)；也可靠 innodb_lock_wait_timeout 超时被动解开。预防：按固定顺序访问、缩小事务、降低隔离级别、加合适索引避免锁范围过大。 📖 看两个具体例子（记录锁 / 间隙锁）

死锁实例 · 用上记录锁 / 间隙锁

表 t(id INT PRIMARY KEY, v INT)，已有记录 id = 10、20，隔离级别 RR。

例1：交叉加记录锁（最经典）

两个事务以相反顺序更新同两行，各自锁住一行后又去要对方的行：

时刻 事务 T1 事务 T2 ─────────────────────────────────────────────────────── t1 UPDATE t SET v=1 WHERE id=10; └ 拿到 id=10 的 Record Lock(X) t2 UPDATE t SET v=1 WHERE id=20; └ 拿到 id=20 的 Record Lock(X) t3 UPDATE t SET v=2 WHERE id=20; └ 要 id=20，被 T2 占着 → 等待 t4 UPDATE t SET v=2 WHERE id=10; └ 要 id=10，被 T1 占着 → 等待 ✗ T1 等 T2、T2 等 T1 → 死锁！InnoDB 回滚其一

根因：加锁顺序相反（T1 是 10→20，T2 是 20→10）。只要统一成"永远先小 id 后大 id"，就不会环等。

例2：间隙锁 + 插入意向锁（RR 下最隐蔽的死锁）

两个事务先查一个不存在的 id（拿到间隙锁），再各自插入。关键前提：间隙锁之间互相兼容（都只是"不许在这段插"，可共存），但 INSERT 需要的插入意向锁会被别人的间隙锁挡住：

时刻 事务 T1 事务 T2 ────────────────────────────────────────────────────────────── t1 SELECT * FROM t WHERE id=15 FOR UPDATE; └ 未命中，拿到 Gap Lock (10,20) t2 SELECT * FROM t WHERE id=15 FOR UPDATE; └ 未命中，也拿到 Gap Lock (10,20) ✔ 间隙锁互相兼容，两人都拿到了 t3 INSERT INTO t VALUES(15,0); └ 需插入意向锁，被 T2 的 gap 挡 → 等待 t4 INSERT INTO t VALUES(15,0); └ 需插入意向锁，被 T1 的 gap 挡 → 等待 ✗ 互相等对方释放间隙锁 → 死锁！
插入意向锁(Insert Intention Lock)：是一种特殊的 Gap Lock，INSERT 前要先申请。它与普通间隙锁冲突（别人锁了这个 gap，我就插不进去要等），但插入意向锁彼此之间不冲突。所以两个事务能同时持有同一个 gap 的间隙锁，却都无法完成插入 —— 这是 RR 下 SELECT...FOR UPDATE 判空再插入这种"先查后插"逻辑高发死锁的原因。

避坑：这类"不存在就插入"的逻辑，改用 INSERT ... ON DUPLICATE KEY UPDATE 或把隔离级别降到 RC（无间隙锁），能避开。

两例对照：例1 是记录锁环等（顺序问题）；例2 是间隙锁共存却互挡插入（RR 特有）。面试问"举个死锁例子"，能说出例2 会很加分，因为它直接用到了间隙锁的兼容性这个细节。

redo logInnoDB持久性 + 崩溃恢复；避免每次提交都随机刷数据页物理日志：某表空间某页某偏移做了什么改动循环写固定文件，WAL 先写日志后刷页；innodb_flush_log_at_trx_commit
undo logInnoDB原子性(回滚) + MVCC 多版本逻辑日志：反向操作(insert↔delete，update存旧值)存于回滚段，本身也受 redo 保护
binlogServer主从复制 + 数据归档/恢复逻辑日志：statement / row / mixed 三种格式追加写不覆盖；sync_binlog

redo log（重做日志）—— WAL 的核心

如果每次事务提交都把随机分布的脏页刷到磁盘，就是大量随机 I/O，极慢。redo log 的思路是 WAL(Write-Ahead Logging)：先顺序写 redo，再择机批量刷脏页。宕机后用 redo 把已提交但没刷盘的页"重做"回来。

  • 物理日志、循环写：一组固定大小文件，写满回到开头覆盖。用 write pos(写位置) 和 checkpoint(已刷盘位置) 两个指针，两者之间是"可覆盖"，追上了就必须先刷脏页(此时会阻塞)。
  • 刷盘策略 innodb_flush_log_at_trx_commit：
    值行为安全性
    1(默认)每次提交都刷到磁盘最安全，不丢；最慢
    0只写 redo buffer，靠后台每秒刷宕机丢最近 1 秒
    2提交时写到 OS page cache，不强制刷盘MySQL 崩溃不丢，OS/机器崩溃丢 1 秒

undo log（回滚日志）

  • 事务里每做一次修改，先把反向操作记进 undo：insert 记 delete、delete 记 insert、update 记旧值。回滚时反向执行。
  • 同时是 MVCC 版本链的存储：旧版本就在 undo 里，靠 DB_ROLL_PTR 串联。
  • undo 不能立刻删，要等没有任何 ReadView 会用到它时，由 purge 线程清理。长事务会让 undo 无法回收而膨胀 —— 这是"长事务危害"的一大原因。

binlog（归档日志）Server层

  • Server 层产生，所有引擎通用。用途：主从复制(从库拉 binlog 重放) 和 基于时间点的恢复。
  • 三种格式：statement(记原始 SQL，紧凑但 now()/uuid() 等主从不一致)、row(记每行改成什么样，安全但大)、mixed(自动选)。生产多用 row。
  • 刷盘 sync_binlog：0=靠 OS，1=每次提交都刷(最安全)，N=每 N 个事务刷一次。
redo vs binlog 三大区别（必背）：① 层：redo 属 InnoDB，binlog 属 Server；② 内容：redo 物理("页怎么改")，binlog 逻辑("做了什么操作")；③ 写法：redo 循环写会覆盖(只做崩溃恢复)，binlog 追加写永久保留(可复制/归档)。

两阶段提交(2PC)与崩溃恢复 高频

为什么需要 2PC？因为一条 update 要同时写 redo(InnoDB) 和 binlog(Server) 两份日志，两者必须一致：不能出现"redo 恢复了数据、binlog 却没记录"（主从不一致），反之亦然。InnoDB 用两阶段提交把它们绑定：

① 写 redo log，标记为 prepare 状态　← InnoDB
▼
② 写 binlog　← Server
▼
③ 写 redo log，标记为 commit 状态　← InnoDB

崩溃恢复时怎么判断？

  1. redo 是 commit 状态 → 直接提交，正常。
  2. redo 是 prepare 状态 → 去看 binlog：
    • binlog 完整 → 提交该事务（说明②已完成，只是没来得及写 commit）。
    • binlog 不完整/没有 → 回滚该事务（②之前就崩了）。

这样保证 redo 与 binlog 要么都生效要么都不生效，主从数据一致。

double write（两次写）— 补充

redo 是"逻辑上的物理日志"，它记录的是"对页的修改"，前提是页本身是完整的。但如果刷盘时发生部分写(partial write)——16KB 页只写了一半就宕机，页已损坏，redo 也无从修复。InnoDB 用 double write buffer：刷脏页时先把页顺序写到一块共享的 double write 区域，再写到真正位置。宕机后若发现页损坏，用 double write 里的完整副本还原。这才是页级"防刷一半"的最终保障（呼应前面 File Trailer 校验和）。

主从延迟：原因与解决

主从延迟 = 从库数据比主库慢一拍。核心原因是主库并发写，从库重放跟不上：

原因解决
从库 SQL 线程单线程重放（老版本）开启并行复制（MTS，按库/按组提交并行重放）
大事务：一个事务改百万行，从库要完整重放一遍拆小事务、避免大批量更新
从库承担大量读、配置比主库差提升从库配置、加从库分摊
大表 DDL、从库锁等待低峰做 DDL、用在线 DDL 工具
读写分离下如何读到最新数据？（延迟导致刚写完从库读不到）几种手段：① 关键读强制走主库；② 用半同步保证从库已收到；③ 判断从库延迟(Seconds_Behind_Master)在阈值内才读从库；④ 从库读不到时降级读主库。

附 · MyISAM vs InnoDB

最经典的引擎对比题。MySQL 5.5 起默认引擎是 InnoDB，MyISAM 基本退役，但对比常被问，因为它能考察你对事务、锁、索引组织的理解。

维度InnoDBMyISAM
事务✅ 支持（ACID）❌ 不支持
锁粒度行锁 + 表锁，并发好只有表锁，写并发差
外键✅ 支持❌ 不支持
索引结构聚簇索引：叶子存整行，索引即数据非聚簇：索引和数据分开存，叶子存数据的地址

附 · count(*) 的坑

count(*) / count(1) / count(字段) 有什么区别？

写法统计什么性能
count(*)所有行（含各列为 NULL 的行）。MySQL 专门优化，不取具体值最快，推荐
count(1)所有行，每行填个常量 1 再计数和 count(*) 几乎一样快
count(主键 id)所有行（主键非空）要取主键值，略慢于 count(*)
count(普通字段)只统计该字段非 NULL 的行（语义就不同！）最慢：要读字段值判 NULL
关键：count(字段) 会漏掉该字段为 NULL 的行，和 count(*) 语义不同，不只是性能问题。统计总行数一律用 count(*)。

为什么 InnoDB 的 count(*) 比 MyISAM 慢？

MyISAM 把表的总行数直接存在磁盘上，`count(*)` 无 where 时直接返回，O(1)。InnoDB 却不行——因为 MVCC：并发事务各有自己的 ReadView，同一时刻不同事务能看到的行数可能不一样，没法存一个统一的数，只能实时一行行数（优化器会挑一棵最小的二级索引来扫，比扫聚簇索引快）。

大表 count 优化：① 能接受近似值就用 EXPLAIN 的 rows 估算；② 用一张计数表随增删维护总数（放事务里保证一致）；③ 用 Redis 等外部计数器（注意一致性）。

附 · join 算法 & filesort 原理

这节补全前面 explain 里 Using join buffer、Using filesort、Using temporary 那几个信号背后的"为什么"。

join 算法

算法怎么工作触发条件
Index Nested-Loop (NLJ)驱动表每行，拿关联值去被驱动表走索引查被驱动表关联列有索引（最理想）
Block Nested-Loop (BNL)把驱动表数据放进 join buffer，批量和被驱动表比，减少被驱动表的重复全表扫被驱动表关联列无索引。Extra=Using join buffer
Hash Join (8.0.18+)对驱动表建哈希表，被驱动表来探测无索引的等值 join，比 BNL 快很多，8.0 已替代 BNL
join 优化两原则：① 小表驱动大表（驱动表越小，外层循环越少）；② 给被驱动表的关联字段加索引，把 BNL 变成 NLJ。STRAIGHT_JOIN 可强制驱动顺序。

filesort：order by 用不上索引时的排序

ORDER BY 若能利用索引的有序性，直接顺序读即可；用不上索引就得在内存/磁盘里排序 → Extra 出现 Using filesort。排序在 sort_buffer 里做，数据小全内存、大则借助磁盘临时文件做归并。它有两种方式：

方式怎么排权衡
单路排序
(全字段排序)		把查询要的所有字段一次性取进 sort_buffer 一起排只回表一次、快；但占 buffer 大，buffer 装不下就多次磁盘归并
双路排序
(rowid 排序)		只取排序字段 + 主键排，排完再回表取其它字段省 buffer；但要回表两次、多一轮随机 I/O

由 max_length_for_sort_data 决定：单行要取的字段总长小于它用单路，否则用双路。优化方向：让 order by 走索引避免 filesort（最有效）、适当调大 sort_buffer_size、只 select 需要的列。

Using temporary：GROUP BY、DISTINCT、UNION 去重时可能用临时表，也是要优化的信号——让 group by 的列走索引（本就有序）就能免临时表。

附 · 一条 SQL 的完整执行链路（总结）

把前面所有章节串成一条线。分两种：查询相对简单，更新最能考察全局。面试答这题，能把这两条链路讲清就基本通关。

一、查询语句 SELECT

以 SELECT * FROM t WHERE id = 10 为例。请求先到 Server 层：连接器建立连接、完成鉴权并读取权限；MySQL 8.0 已删除查询缓存（8.0 之前若命中会直接返回）；接着分析器做词法、语法分析，生成语法树并检查表和列是否存在；优化器据此选择索引、确定执行计划（这里走 id 主键索引）；最后执行器校验权限、调用存储引擎接口取数据。

请求转入 InnoDB 引擎层：先去 Buffer Pool 找目标页，命中就直接用、未命中则从磁盘把整页读进 Buffer Pool；然后沿 B+ 树索引定位到 id=10 的记录；由于普通 SELECT 是快照读，还要走 MVCC——用 ReadView 配合 undo 版本链判断出对当前事务可见的那个版本。最终执行器把结果集返回客户端。

补充：若走二级索引还多一步回表；若要查的列都在索引里则覆盖索引免回表。普通 SELECT 全程不加锁。

二、更新语句 UPDATE（重点）

以 UPDATE t SET v = 2 WHERE id = 10（autocommit=1）为例。前半程——连接器、分析器、优化器、执行器——和查询完全一样，差别在执行器驱动 InnoDB 真正改数据、并写日志、走两阶段提交。

执行器让 InnoDB 更新 id=10 这一行：先在 Buffer Pool 找到（或从磁盘读入）目标页；因为是当前读，给这一行加排他行锁(X)；改之前先写 undo log 记下旧值 v=1（既用于回滚，也作为 MVCC 的历史版本，undo 本身也受 redo 保护）；然后修改 Buffer Pool 里的数据页把 v 改成 2，该页变成脏页；同时写 redo log 记录"这个页怎么改了"，并置为 prepare 状态。

进入提交阶段的两阶段提交(2PC)：先把 redo log 刷盘（prepare，受 innodb_flush_log_at_trx_commit 控制）；再写 binlog 并刷盘（Server 层，受 sync_binlog 控制）；最后把 redo log 置为 commit。事务至此提交完成，释放行锁（遵循 2PL，到这一刻才放）。而那个脏页并不马上落盘，由后台线程按 WAL 思想择机刷回磁盘——先写日志、数据页慢慢刷，把随机写攒成顺序写。

为什么写三种日志？各司其职：
  • undo：存旧值 → 支持回滚和 MVCC 多版本。
  • redo：记页改动 → 崩溃恢复，实现 WAL。
  • binlog：记逻辑操作 → 主从复制和归档。
其中 redo 的 prepare/commit 加上中间的 binlog，构成两阶段提交，保证两份日志一致：崩溃恢复时 redo 是 commit 就提交，是 prepare 就看 binlog 完不完整——完整则提交、不完整则回滚，避免主从不一致。详见 两阶段提交。

一句话口诀（更新）：“一锁、二改、三日志、两阶段、后刷盘” —— 加锁 → 改数据页 → undo/redo/binlog → 2PC 提交 → 后台刷脏页。

2 · 关键字执行顺序（逻辑执行顺序）高频

你写 SQL 的顺序 ≠ MySQL 执行的顺序。理解执行顺序能解释很多现象（如为什么 WHERE 里不能用 SELECT 的别名、为什么 HAVING 能用聚合函数而 WHERE 不能）。

书写顺序：SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT 执行顺序（编号=先后）： ① FROM / JOIN 取数据源、做连接，生成中间表 ② ON 连接条件 ③ WHERE 行过滤（此时还没有分组、没有别名） ④ GROUP BY 分组 ⑤ HAVING 对分组后的结果过滤（可用聚合函数） ⑥ SELECT 选列、算表达式、定义别名 ⑦ DISTINCT 去重 ⑧ ORDER BY 排序（可用 SELECT 里的别名） ⑨ LIMIT 取前 N 行
由执行顺序推出的结论：
  • WHERE(③) 在 SELECT(⑥) 之前 → WHERE 里用不了 SELECT 定义的别名。
  • WHERE 在 GROUP BY 之前 → WHERE 里不能用聚合函数（还没分组）；要对聚合结果过滤得用 HAVING(⑤)。
  • ORDER BY(⑧) 在 SELECT(⑥) 之后 → ORDER BY 可以用别名。
  • LIMIT 最后执行 → 深分页 LIMIT 100000,10 仍要先扫前 10 万行再丢弃，所以慢。

附 · 高频面试速记

为什么用 B+ 树而不是 B 树/Hash？
B+ 非叶子只存 key 更矮胖(3~4层存千万行)、叶子双向链表利于范围查询和排序；Hash 不支持范围和排序。
聚簇索引和二级索引区别？什么是回表？
聚簇索引叶子存整行(按主键组织，一张表一个)；二级索引叶子存"索引列+主键值"。用二级索引查到主键后再去聚簇索引取整行=回表。要查的列全在索引里则"覆盖索引"免回表。
RC 和 RR 隔离级别的本质区别？
MVCC 建 ReadView 时机：RC 每次快照读都新建(看到别人最新提交→不可重复读)；RR 事务首次读建一次并复用(整事务同一快照→可重复读)。
InnoDB 的 RR 解决幻读了吗？
基本解决。快照读靠 MVCC，当前读靠 Next-Key Lock(记录锁+间隙锁)。但先快照读再当前读同一范围的交错场景仍可能出现，非 100%。

redo log 和 binlog 的区别？为什么要两阶段提交？
redo 属 InnoDB/物理/循环写/崩溃恢复；binlog 属 Server/逻辑/追加写/复制归档。两份日志要一致，用 2PC(redo prepare → binlog → redo commit)，崩溃恢复时以 binlog 是否完整决定提交或回滚。
undo log 的两个作用？
① 事务回滚(存反向操作，实现原子性)；② MVCC 版本链的存储载体。由 purge 线程在无 ReadView 引用时清理，长事务会拖住它。
一条 update 的完整流程？
连接→(分析优化)→执行器调 InnoDB→Buffer Pool 找页(无则读盘)→写 undo→改内存页(脏页)→写 redo(prepare)→写 binlog→写 redo(commit)→后台择机刷脏页。
行锁加在哪？为什么不带索引的 update 会锁很多行？
行锁加在索引上。走不到索引时全表扫描，对扫描到的每一行都加 Next-Key Lock，等于锁全表。
什么是索引下推(ICP)？
联合索引中把可在索引上判断的 where 条件下推到引擎层先过滤，减少回表次数。Extra 显示 Using index condition。
