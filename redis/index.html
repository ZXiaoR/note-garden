0 · Redis 为什么这么快

几乎是开场必问。把原因串成一条链：纯内存操作 + 单线程避免上下文切换与锁竞争 + IO 多路复用（epoll）的 Reactor 网络模型 + 针对场景高度优化的数据结构。这条链正好引出后面两节（单线程模型、数据结构）。

Redis 为什么快 —— 四条腿
① 纯内存
数据全在内存，读写是
纳秒级；磁盘随机 IO 毫秒级，差 10 万倍
② 单线程
命令串行执行，

③ IO 多路复用
一个线程用 epoll

④ 高效数据结构
SDS / 跳表 / listpack…

根本前提：Redis 的瓶颈在内存和网络 IO，不在 CPU —— 所以单核跑满就够，多线程反而引入锁开销
原因展开
① 纯内存操作所有数据驻留内存，一次读写就是一次内存寻址（~100ns）。对比磁盘随机 IO（机械盘 ~10ms），天然快几个数量级。这是"快"的根本。
② 单线程模型命令一个接一个串行执行：不需要为共享数据加锁、没有多线程上下文切换开销、也没有死锁/竞态等并发 bug。实现还简单。
③ IO 多路复用单线程却能同时服务海量连接，靠的是 epoll：把成千上万个 socket 注册给内核，内核一有就绪事件就通知，线程只处理"真正有数据"的连接，不为空闲连接空转。
④ 高效数据结构同一种对外类型，底层按数据规模选最省/最快的实现（String 的 int/embstr/raw、ZSet 的 listpack/skiplist…），让每个命令都贴着理论最优复杂度。见下一章。
一句话答：Redis 快是因为数据在内存（根本）、单线程免锁免切换、IO 多路复用扛高并发、数据结构高度优化。关键认知是——它的瓶颈从来不是 CPU，而是内存和网络，所以"单线程"不但不拖后腿，反而省掉了多线程的一切麻烦。

单线程模型 & IO 多路复用

这里要讲清一个高频误区：Redis 的"单线程"指的是命令处理（网络 IO + 执行命令）在一个主线程里串行完成，并不是整个进程只有一个线程 —— 持久化、异步删除等脏活早就交给了其它线程/子进程。

为什么敢用单线程？

  • 瓶颈不在 CPU：Redis 操作都是内存级的，单核每秒就能处理十万级命令，CPU 远没跑满，多开线程提升不了多少吞吐。
  • 免锁免切换：多线程要对共享数据加锁，锁竞争和上下文切换本身就是开销，还容易出并发 bug。单线程把这些全省了。
  • 实现简单：没有并发控制，代码清晰、可维护性高。

IO 多路复用 + Reactor（文件事件处理器）

单线程要同时服务大量客户端，靠的是 IO 多路复用：把所有 socket 交给内核的 epoll（Linux）统一监听，哪个 socket 有数据可读/可写，内核就把它放进就绪队列，线程只处理就绪的事件，绝不为空闲连接阻塞或轮询。Redis 在其上封装了自己的 文件事件处理器（Reactor 模型）：

线程模型的发展：从单线程到多线程 IO

Redis 并非一直纯单线程，但要分清"多线程化的到底是哪部分"。结论先行：从头到尾，命令的执行始终是单线程串行的，多线程化的只是它周边的脏活累活。

版本多线程化了什么命令执行
4.0引入后台线程（bio）：把耗时的"大对象删除"等异步化 —— UNLINK（惰性删除）、FLUSHDB/FLUSHALL ASYNC、AOF fsync、关闭文件等。避免删一个几 GB 的大 key 把主线程卡住。仍单线程
6.0引入多线程 IO：多个 IO 线程并行负责 socket 数据的读取/写回 + 协议解析。因为随着网卡和并发变大，网络 IO（读请求、写响应）成了瓶颈，而非命令本身。仍单线程
6.0 多线程 IO：只并行"读写网络"，不并行"执行命令"

配置：io-threads 默认为 1（即关闭多线程 IO），需手动开启并设为 CPU 核数的一部分（如 4）；默认只多线程化写回，要连读取+解析也多线程需再开 io-threads-do-reads yes。官方建议 4 核以上再开，小机器开了反而亏。
既然多线程好，为什么执行命令不做成多线程？
一旦多线程执行命令，就要对共享的键空间加锁，锁粒度难把控：粗锁退化成串行、细锁又复杂且易出 bug，收益抵不过成本。而瓶颈本就在网络 IO 而非命令执行，所以 Redis 选择"IO 并行、执行串行"——既吃到多核扛网络的红利，又保住单线程无锁的简单与安全。

为什么分界线是 44 字节？ Redis 希望 embstr 这一整块正好装进一个 64 字节的内存分配单元（jemalloc 的常用规格，一次分配、缓存友好）。64 减去 redisObject 头（16B）、sdshdr8 头（len+alloc+flags 共 3B）、结尾 \0（1B），剩 64−16−3−1 = 44 字节给实际内容。所以 ≤44 字节用 embstr（省一次分配），超了就用 raw。
编码会转换，且不可逆：
  • embstr 是只读的：一旦对它做修改（APPEND、SETRANGE 等），哪怕结果仍很短，也会转成 raw（因为 embstr 那块连续内存不方便原地扩展）。
  • int 一旦拼接：对 int 编码的 key 执行 APPEND，它不再是纯整数，会转成 raw。
  • 方向都是 int/embstr → raw，只往"更通用"的方向转，不回退。

为什么要「整体」升级，而不是只把新元素存大？
int16 数组：每格固定 2 字节，第 i 个元素地址 = base + i×2 ┌────┬────┬────┬────┬────┐ │ -5 │ 3 │ 12 │100 │4000│ ← 等宽，随手就能算出"中间那个"在哪 └────┴────┴────┴────┴────┘ 2B 2B 2B 2B 2B
关键在于 intset 是一整块「等宽」的连续数组 —— 所有元素用同一种编码、占同样的字节数。正因为等宽，才能用 base + i×宽度 O(1) 直接算出第 i 个元素的位置，这正是二分查找的前提（二分要能瞬间跳到中间那个元素）。

如果只把 40000 单独存成 4 字节、其余仍是 2 字节，数组就变成「宽窄不一」：想找第 i 个元素得从头一个个累加字节偏移，退化成 O(n) 扫描，二分就废了。所以一旦有元素超出当前编码范围，就必须把整个数组统一升到更宽的编码，保持"等宽"这个不变量。

那为什么平时不直接都用 int64？ 因为绝大多数集合里都是小整数，用 int16 能省 4 倍内存。只在真正放入大数时才升级 —— 常见情况省内存，必要时才付升级代价。不降级同理：要判断能否降级得扫全数组找最大值（O(n)），不划算。

① 怎么实现（节点结构）

每个节点存 score + member，外加一个层数组 level[]：第 i 层有个 forward 指针指向同层的下一个节点。节点有几层，level[] 就有多长。

· 层数插入时随机决定：每往上加一层的概率是 p=1/4（Redis 取值），所以大约 3/4 的节点只有 1 层、越高越少 —— 天然形成"下密上疏"的金字塔，不用旋转/再平衡就近似有序平衡。最大层数上限 32（新版 64）。
· 头节点 head 固定拥有最高层，是每次查找的起点。
· ZSet = skiplist + dict 一起用：skiplist 管"按 score 排序/范围"，dict 存 member→score 做按成员 O(1) 查（如 ZSCORE）。
② 怎么查询（规则 + 走一遍）

规则：从 head 最高层开始，每一层"能往右就往右，不能就下沉" —— 若本层下一个节点的 score ≤ 目标，就前进；否则下沉一层。到 L0 还没命中就是不存在。

查 score = 19： L3: head 的 forward = 27，27 > 19 → 不前进，下沉 L2: head 的 forward = 12，12 ≤ 19 → 走到 12；12 的 forward = 27 > 19 → 下沉 L1: 12 的 forward = 19，19 ≤ 19 → 走到 19 → 命中 ✅ 全程只比较 3 次，跳过了 3、6、9、17 等一堆节点

对比图中查 27：L3 一步就从 head 跳到 27（因为 3~21 都没长到 L3 这么高），而在 L0 要挨个走 8 步。

③ 为什么快
每上升一层，节点数大约减少到 1/4（由概率 p 决定），层数因此约为 log₄n；查找每层最多走几步就下沉，总步数正比于层数 → 平均 O(log n)。本质和二分查找同理：用高层指针一次跳过一大段，把"逐个扫 O(n)"变成"分层跳 O(log n)"。
代价是每个节点要多存几个 forward 指针（空间换时间），但指针不多，内存开销可接受。
ZSet 为什么用跳表而不是红黑树 / B+ 树？
  • 范围查询友好：ZSet 大量 ZRANGE 这类范围操作，跳表最底层就是有序链表，定位后顺着指针扫即可；红黑树做范围要中序遍历，麻烦。
  • 实现简单：跳表靠随机层数维持平衡，代码远比红黑树的旋转简单，易维护、易调试。
  • B+ 树是为磁盘设计的：B+ 树的矮胖是为了减少磁盘 IO，Redis 全在内存，用不上这个优势，反而增加复杂度。

渐进式 rehash

dict（哈希表）里保存了两张哈希表 ht[0]、ht[1]。平时只用 ht[0]；当负载因子过高要扩容、或过低要缩容时，就需要把 ht[0] 的所有键重新哈希到更大/更小的 ht[1]。

什么是负载因子？为什么要扩容/缩容

负载因子 load factor = used / size = 已存元素个数 / 桶数组大小

它衡量哈希表的"拥挤程度"：

  • 太高（快满了）：元素挤在有限的桶里，冲突变多、链表变长，查找从理想的 O(1) 退化成 O(链长)。→ 需要扩容（换更大的桶数组），把链摊平。
  • 太低（很空旷）：桶数组占着大量内存却没几个元素，浪费空间。→ 需要缩容，把桶数组缩小。

Redis 里 dict 的触发阈值（used / size）：

动作触发条件新表大小
扩容（常规）负载因子 ≥ 1，且当前没有子进程在做 RDB/AOF第一个 ≥ used×2 的 2 的幂
扩容（强制）负载因子 ≥ 5（不管有没有子进程，太挤了必须扩）同上
缩容负载因子 < 0.1（低于 10%，由后台定时任务检查）第一个 ≥ used 的 2 的幂
为什么"有子进程时"要把扩容阈值放宽到 5？ RDB 的 bgsave、AOF 重写都靠 fork 子进程 + 写时复制（COW）：父子共享内存页，父进程一改动就要复制一份页。而扩容 rehash 会大面积改动内存（搬迁所有 key），触发海量页复制、内存暴涨。所以 fork 期间尽量不扩容，把阈值抬高到 5，除非实在太挤（≥5）才强制扩。这是"写时复制友好"的一个典型权衡。
为什么不能一次性迁移？ Redis 是单线程。如果字典里有几百万个 key，一次性 rehash 会把主线程卡死几百毫秒甚至几秒，期间所有命令全部阻塞 —— 这是不可接受的。

为什么要两张表 ht[0] / ht[1]？

扩容的本质是：换一个更大的桶数组，把所有 key 按新大小重新哈希、搬过去。但"边对外服务、边慢慢搬"就必须同时保留两块空间 —— 没法在原地把一个数组悄悄变大：

  • ht[0]：原来那张表，还装着没搬完的 key，继续对外服务；
  • ht[1]：新分配的目标表（扩容时更大、缩容时更小），接收搬过来的 key；
  • 迁移期间两张并存，用一个游标 rehashidx 记录"ht[0] 搬到第几个桶了"；
  • 等 ht[0] 全部搬空，释放 ht[0]，让 ht[1] 顶上成为新的 ht[0]，ht[1] 再次置空。

所以平时（没在 rehash）只有 ht[0] 有数据，ht[1] 是空的；只有 rehash 期间 ht[1] 才被用起来。有了这块"中转空间"，才能把一次大搬迁拆成无数次小搬迁。

rehash 进行中：ht[0] 逐桶搬向 ht[1]，rehashidx 指"下一个要搬的桶"
▽ ht[0]（旧表，size=4）— 装没搬完的 key，继续服务
桶0──▶已迁空
桶1──▶已迁空
桶2──▶k3──▶k5　◀ rehashidx = 2（正指这里，待迁）
桶3──▶k4　待迁
逐桶搬迁 ▼
▽ ht[1]（新表，size=8）— 桶0、桶1 已收到搬来的 k1、k2
桶0─▶k1 1─▶k2 2─▶空 … 3~7 待接收 k3/k4/k5 …
游标从 rehashidx=0 一路推进到 ht[0] 最后一个桶；到达即代表搬完，此时 ht[1] 转正、ht[0] 释放。

迁移是怎么一小步一小步推进的：

  • 触发后：给 ht[1] 分配好空间，rehashidx 置 0，进入 rehash 状态。
  • 每次增删改查：顺带把 ht[0] 上 rehashidx 指向的那个桶的所有键迁到 ht[1]，然后 rehashidx++。外加 serverCron 定时任务也会帮着搬一批。
  • 迁移完：ht[1] 变成新的 ht[0]，旧表释放，rehashidx 置 -1。

rehash 期间的读写怎么处理？

  • 查：先查 ht[0]，没有再查 ht[1]（因为 key 可能还没迁过去）。
  • 新增：只写 ht[1]，保证 ht[0] 只减不增，迁移总能结束。
  • 删/改：两张表都可能命中，命中哪张改哪张。
一句话：用"两张表 + 进度指针 + 把迁移摊进每次操作"，把一次会卡死的大 rehash 变成无数次几乎无感的小迁移 —— 典型的"化整为零、避免单线程长阻塞"思路。

ziplist 的"连锁更新"到底是什么？
ziplist 里每个 entry 都记录了前一个 entry 的长度（prevlen），用 1 字节或 5 字节存。如果某个 entry 从 <254 字节增长到 ≥254 字节，它后面那项记录的 prevlen 就要从 1 字节扩成 5 字节，这一扩又可能让再后面一项的 prevlen 跟着扩……像多米诺骨牌一样级联 realloc，最坏 O(n²)。listpack 让每项只记自己的长度，从根上杜绝了这个问题。

② 缓存击穿：热点 key 失效瞬间

某个超热 key（如首页大促商品）到期的一刹那，成千上万并发请求同时发现缓存没了，一起去查 DB 并重建缓存，DB 瞬间被打爆。（和雪崩的区别：击穿是一个热点 key，雪崩是一大批key。）

  • 互斥锁：缓存失效时，只让第一个请求拿到锁去查 DB、重建缓存，其余请求等待或重试，重建好后直接读缓存。保证同一时刻只有一个请求回源。
  • 逻辑过期：热点 key 不设真实 TTL，而是把"逻辑过期时间"存进 value。发现逻辑过期就异步开个线程去重建，当前请求先返回旧值。牺牲一致性换不阻塞。
  • 热点数据永不过期 / 提前续期。

③ 缓存雪崩：大面积失效 / Redis 宕机

两种成因：(a) 大量 key 设了相同的过期时间，同一刻集体失效；(b) Redis 实例整个挂了，所有请求瞬间全压到 DB。

  • 过期时间加随机值：基础 TTL + 随机几分钟，把失效时间打散，避免同时到期。（针对成因 a）
  • Redis 高可用：主从 + 哨兵 / 集群，避免单点宕机。（针对成因 b）
  • 多级缓存：本地缓存(Caffeine) + Redis，Redis 挂了本地还能顶一会。
  • 服务熔断 / 限流 / 降级：兜底，保护 DB 不被打垮。
对比记忆：穿透=查不存在（布隆过滤器 / 缓存空值）；击穿=一个热点失效（互斥锁 / 逻辑过期）；雪崩=一批失效或宕机（随机 TTL / 高可用 / 多级缓存）。

缓存与数据库一致性

只要数据同时存在 DB 和缓存，就有"改了一个、另一个还是旧值"的风险。主流方案是 Cache Aside（旁路缓存）：读时缓存没有就查 DB 回填；写时更新 DB，然后删除缓存。

为什么是"删缓存"而不是"更新缓存"？

  • 省无用功：写完就更新缓存，但这个 key 可能很久没人读，白算白写；删掉让"下次真正读"时再懒加载更划算。
  • 避免并发写覆盖：两个请求都"更新缓存"时，先写 DB 的可能后写缓存，造成缓存是旧值。删除就没有这个顺序问题。看例子
  • 计算型缓存：若缓存是多表聚合算出来的，每次写都重算代价大，删掉更简单。

先更新 DB，再删缓存（推荐）大部分情况没问题。极端场景仍可能不一致（见下），但概率低很多，是业界默认选择。

延迟双删

针对"先删缓存再更新 DB"的读回填旧值问题：更新 DB 后，延迟一小段时间（如 500ms）再删一次缓存，把这期间可能被回填的旧值清掉。延迟时间要略大于"一次读 DB + 写缓存"的耗时。

为什么说只能做到"最终一致"？

即使是推荐的"先更新 DB 再删缓存"，也有个低概率的不一致时序：读请求的回填 与 写请求的删除 恰好交错。看例子

它要求"读查到旧值"和"写删缓存"卡在极窄的时间窗内，且读的回填比写的删除还晚，实际很少发生。所以工程上接受最终一致：给缓存设 TTL 兜底，到期自然纠正。

更强的一致性：订阅 binlog

用 Canal 之类工具伪装成 MySQL 从库，订阅 binlog，DB 一有变更就由消费端去删/更新缓存。好处是和业务代码解耦、不会漏删（失败可重试），是大厂常用的异步一致性方案。

如何选？ 绝大多数业务用"更新 DB + 删缓存 + TTL 兜底"的最终一致就够了；对一致性要求更高的，叠加延迟双删或 binlog 订阅；若要求强一致，那就别用缓存，直接读 DB（或加分布式锁串行化）—— 缓存的本质是用一致性换性能。

写请求A 把 X 从 V1 改成 V2；读请求B 恰好在缓存失效的瞬间进来。

时刻读请求B写请求A（X: V1→V2）DB缓存
t1缓存失效 → 查 DB 得旧值 V1V1空
t2更新 DB → V2V2空

t4把 V1 写回缓存V2V1 ❌
结果：缓存=V1、DB=V2。但要同时满足两个苛刻条件：① 读在 t1 就查到了旧值；② 读的回填(t4)竟然比写的删缓存(t3)还晚。
通常"读 + 回填"很快（毫秒级），几乎总在写的删除之前完成，所以这个交错概率极低。
兜底：给缓存设 TTL，即便真撞上了，到期自动失效、下次读回填最新值 —— 这就是"最终一致"。要更强就上 binlog 订阅或强一致方案。

大 key / 热 key 问题

两个容易混的概念：大 key 是"单个 value 体积大"（如一个存了几百万元素的 Hash、几 MB 的 String）；热 key 是"单个 key 访问量极高"（如爆款商品）。

大 key

危害① 读写耗时长，因单线程而阻塞其它命令；② 序列化后网络传输打满带宽；③ 删除一个大 key（DEL）也会长时间阻塞；④ 数据倾斜（集群里某节点内存暴涨）。
排查redis-cli --bigkeys 扫描、MEMORY USAGE key 看单 key 内存、SCAN + 业务分析。
解决① 拆分：大 Hash 按 field 哈希拆成多个小 Hash；② 删除用 UNLINK 代替 DEL（4.0+，交后台线程异步回收，不阻塞主线程）；③ 压缩 value、只存必要字段。

热 key

危害流量全压在某个节点上（集群下尤其明显），可能打满单节点，热 key 失效还会引发缓存击穿。
发现redis-cli --hotkeys（需 LFU 策略）、MONITOR 抽样、客户端/代理层埋点统计。
解决① 多级缓存：热 key 放一份到应用本地缓存（Caffeine），减少打到 Redis 的量；② 读副本分摊：主从 + 读写分离把读分散到多个从节点；③ key 打散：把热 key 复制成 key#1…key#N 分布到不同节点，读时随机选一个。

3 · 持久化：RDB / AOF / 混合

内存数据库怕宕机丢数据，所以要落盘。两种机制各有取舍：RDB 是某一时刻的内存快照（二进制、体积小、恢复快）；AOF 记录每条写命令（可读、丢数据少）。

RDB —— 内存快照

把某一时刻的全部数据二进制压缩成一个 dump.rdb 文件。两种触发方式：

命令怎么做问题
save主线程直接生成 RDB阻塞所有命令，生产禁用
bgsave（默认）fork 一个子进程去写 RDB，主线程继续服务只在 fork 瞬间短暂阻塞

fork + 写时复制（COW）：bgsave 时子进程和父进程共享同一份内存页（靠页表，不真复制数据）。子进程安心把这份快照写盘；期间如果主进程要修改某个页，内核才把那个页复制一份给主进程改（Copy-On-Write），子进程看到的仍是 fork 那一刻的旧数据。这样既不阻塞写、又能得到一致的快照。

触发时机：配置文件 save 900 1 / 300 10 / 60 10000（多少秒内有多少次写就 bgsave）、主从全量复制、shutdown 时。

AOF —— 追加写命令日志

把每条写命令按协议格式追加到 appendonly.aof。注意 Redis 是"先执行命令、再写日志"（写后日志），和 MySQL 的 WAL（先写 redo 再改数据）正好相反。

为什么"先执行再记日志"？ ① 只有执行成功的命令才记，避免记录错误命令（不用像 MySQL 那样额外做语法检查）；② 不阻塞当前命令的执行。代价：如果命令执行完、还没来得及写 AOF 就宕机，这条会丢；而且写 AOF 在主线程，可能阻塞下一条命令。

三种刷盘策略 appendfsync（写 AOF 其实是先进 OS 缓冲区，何时 fsync 到磁盘由它决定）：

策略fsync 时机丢数据 vs 性能
always每条命令都 fsync最多丢 1 条，但最慢
everysec（默认）每秒 fsync 一次（后台线程）最多丢 1 秒，性能与安全的平衡
no交给操作系统决定最快，但宕机可能丢很多

AOF 重写（bgrewriteaof）：AOF 越追越大，且有冗余（对同一 key 的 100 次 INCR 其实只需最终值）。重写就是 fork 子进程，按当前内存数据生成一份最精简的等价命令集，替换旧 AOF。不是分析旧文件，而是直接读内存现状。

混合持久化（4.0+）

RDB 恢复快但丢数据多，AOF 丢数据少但文件大、恢复慢。混合持久化（aof-use-rdb-preamble yes）取长补短：AOF 重写时，文件开头写成 RDB 格式的全量快照，之后的增量写命令再用 AOF 格式追加。

4 · 过期 key 的删除策略

给 key 设了 TTL（EXPIRE），Redis 把它的过期时间单独存在一个过期字典（expires dict）里。到期后怎么真正删掉？三种理论策略，Redis 采用其中两种的组合。

策略做法CPU内存
定时删除每个 key 都配一个定时器，到点立刻删❌ 差：大量定时器吃 CPU，可能在高峰期抢占主线程✅ 好：到期即删，不占内存
惰性删除不主动删，访问到它时才检查是否过期，过期就删✅ 好：只在访问时花一点❌ 差：没人访问的过期 key 一直占内存
定期删除每隔一段时间随机抽一批检查并删过期的折中：频率/抽样量可调折中：能清掉一部分"没人访问"的

Redis = 惰性删除 + 定期删除，互补：

  • 为什么不用定时删除？ 单线程下，成千上万个定时器既费 CPU 又可能在关键时刻抢占主线程去删 key，得不偿失。
  • 惰性删除解决"被访问到的过期 key"——读到它顺手删掉，几乎零额外成本。
  • 定期删除补上"惰性删除的漏网之鱼"——那些过期了又一直没人访问的 key。默认每秒约 10 次（hz）：每次从过期字典随机抽 20 个检查，删掉其中过期的；如果过期比例超过 25%，就再抽一轮，直到低于阈值或超时（避免一次占用太久）。

主从场景下的过期处理

从节点不会自己删过期 key。 为保证主从数据一致，过期删除统一由主节点负责：主节点删除一个过期 key 后，会向所有从节点传播一条 DEL（或 UNLINK）命令，从节点收到才删。从节点即使发现某 key 逻辑上已过期，也不主动删除，只是在读的时候按过期逻辑对客户端返回空（较新版本行为），但物理删除要等主节点的 DEL —— 这样避免主从因为各自计时误差导致数据不一致。

5 · 内存淘汰策略（maxmemory）

和"过期删除"区分开：过期删除针对设了 TTL 的 key；内存淘汰是内存用量达到 maxmemory 上限时，为了给新数据腾空间而主动删 key（不管有没有设 TTL）。由 maxmemory-policy 配置，共 8 种：

作用范围 ＼ 算法LRU（最久未用）LFU（最少频率，4.0+）random（随机）ttl（将到期）
volatile-*
只淘汰设了 TTL 的 key		volatile-lruvolatile-lfuvolatile-randomvolatile-ttl
优先删最快过期的
allkeys-*
所有 key 都可淘汰		allkeys-lruallkeys-lfuallkeys-random—

外加第 8 种 noeviction（默认）：不淘汰，内存满了之后写命令直接报错，读和删仍可用。

LRU vs LFU

  • LRU（Least Recently Used）：淘汰最久没被访问的。问题：一个 key 偶尔被访问一次（比如被扫描到），就会被误判成"最近用过"而留下，挤掉真正的热点。
  • LFU（Least Frequently Used，4.0 引入）：淘汰访问频率最低的。给每个 key 维护一个访问计数器（带随时间衰减，防止历史热点永远赖着不走）。更能反映"长期热度"，适合有稳定热点的场景。

近似 LRU / 近似 LFU

Redis 不维护一条全局的 LRU 链表（那样每次访问都要移动节点，内存和性能开销大）。它只在每个 key 的 redisObject 里存一个 24 bit 的时间戳（lru 字段）。淘汰时随机采样 maxmemory-samples 个 key（默认 5），从这几个里挑最该淘汰的，放进一个淘汰池逐步淘汰。所以是"近似" LRU —— 用少量采样换取巨大的内存/性能节省，代价是偶尔淘汰得不那么精确。LFU 同理复用这个字段存访问计数。
选型：大多数当缓存用的场景选 allkeys-lru（或有明显热点时用 allkeys-lfu）；如果部分数据是"持久化数据不能丢、只有缓存数据可删"，就给缓存数据设 TTL 并选 volatile-lru；不希望丢任何数据（把 Redis 当存储而非缓存）就用 noeviction + 监控告警。

增量同步（断线重连）

同步建立后，主节点会把每条写命令持续传播给从节点（命令传播）。如果从节点短暂断线又重连，不必重新全量，而是走增量：

  • 复制偏移量 offset：主、从各自记录已复制到的字节偏移量。两者差值就是从节点落后的数据。
  • 复制积压缓冲区 repl_backlog：主节点维护的一个固定大小环形缓冲，持续记录最近传播的写命令。
  • 重连时：从节点发 psync <replid> <offset>，主节点判断：从的 offset 还在 backlog 范围内 → 只补发这段差量（增量）；已经被环形覆盖冲掉了 → 退化为全量同步。

两个常见坑

  • 复制风暴：一主挂了大量从，主节点宕机/重启后所有从同时要求全量同步，主节点 fork + 发 RDB 压力暴增。缓解：用主-从-从级联（让部分从去同步另一个从）分摊。
  • 主从延迟：命令传播是异步的，从节点数据总是略滞后于主。读写分离时可能"刚写完马上读从却读到旧值"。对一致性敏感的读要读主，或等待复制追上。
注意：主从复制本身不提供自动故障转移 —— 主挂了，从不会自动顶上、客户端也不知道该连谁。这正是下一节哨兵要解决的。

7 · 哨兵 Sentinel

主从本身不会自动故障转移 —— 主挂了需要人工切。哨兵（Sentinel）是一组独立进程，专门负责自动监控 + 选主 + 切换 + 通知。生产至少部署 3 个哨兵（奇数，便于投票）。

哨兵的四大职责

监控：定期 PING 主从是否存活 自动故障转移：主挂了选新主并切换 配置中心：告诉客户端当前主节点是谁 通知：故障信息推给管理员/客户端

主观下线 vs 客观下线

概念含义
主观下线 SDOWN单个哨兵在 down-after-milliseconds 内 PING 不通某节点，自己认为它下线了。可能是网络抖动误判。
客观下线 ODOWN当认为主节点主观下线的哨兵数量达到 quorum（法定人数），就判定主节点客观下线 —— 多个哨兵达成共识，才真正触发故障转移。只对主节点有这个概念。

脑裂问题

脑裂：主节点其实没死，只是和哨兵们网络分区了。哨兵以为它死了，选了新主 —— 于是出现两个主。老客户端还在往旧主写，这些写在网络恢复、旧主降级为从时会被新主的数据覆盖而丢失。

缓解：给主节点配 min-replicas-to-write N + min-replicas-max-lag S —— 要求至少 N 个从节点、且延迟不超过 S 秒，主节点才接受写。分区后旧主连不上足够的从，就会主动拒绝写入，从而把脑裂期间的数据损失降到最小。

8 · 集群 Cluster

主从 + 哨兵解决了高可用，但所有数据还是在一台主上（从只是副本）。当数据量或写并发超过单机上限，就需要 分片（sharding）：把数据拆到多个主节点上，每个主再各带自己的从。Redis Cluster 用哈希槽来分片。

16384 个哈希槽

集群固定有 16384 个槽（slot），每个主节点负责其中一段。定位一个 key 的流程：

key ──▶ CRC16(key) % 16384 ──▶ 得到槽号 ──▶ 找到负责该槽的节点 例：3 个主节点　节点A: 槽 0~5460　节点B: 槽 5461~10922　节点C: 槽 10923~16383

扩容/缩容时只需迁移部分槽到新节点，不用像"取模 key 总数"那样全量重哈希。

为什么是 16384（2¹⁴）而不是 65536（2¹⁶）？
核心是心跳包体积：节点间用 Gossip 互发心跳，心跳里要带一个位图标明自己负责哪些槽。16384 个槽位图是 16384/8 = 2KB；若用 65536 则是 8KB，心跳包大 4 倍，在节点间频繁交换时很浪费带宽。而且 Redis 作者认为集群节点数一般不会超过 1000，16384 个槽分给上千节点已经足够均匀，没必要用 65536。另外槽越少，位图压缩率也越高。

Gossip 协议

集群没有中心节点，节点之间通过 Gossip 协议互相通信（消息类型：MEET 邀请入群、PING/PONG 心跳交换状态、FAIL 广播某节点下线）。每个节点都保存整个集群的槽-节点映射，靠 Gossip 最终收敛到一致。

客户端重定向：MOVED / ASK

重定向含义
MOVEDkey 所在的槽已经固定属于另一个节点 → 永久重定向，客户端应更新本地缓存的槽映射，以后直接连对的节点。
ASK槽正在迁移中，这个 key 刚好已迁到目标节点 → 临时重定向这一次请求，不更新本地映射（迁移没完成）。

多 key 操作的限制 + hash tag

限制：MSET、SINTER 等多 key 命令，要求涉及的所有 key 都在同一个槽，否则报错（跨节点没法原子操作）。

hash tag 解决：给 key 加 {...}，只用大括号里的部分计算槽。例如 user:{1001}:name 和 user:{1001}:age 都只按 1001 算槽 → 落到同一个槽，就能一起操作。常用于把"需要一起处理的一组 key"绑到同一节点。

集群的故障转移

集群自带故障转移，不需要额外哨兵：每个主节点的从节点会通过 Gossip 感知主是否 FAIL，若主下线，其从节点发起投票，得到多数主节点认可的从晋升为新主，接管原来的槽。所以生产中每个主都要配至少一个从，否则该主挂了、它负责的槽就不可用（整个集群进入 fail 状态，除非开 cluster-require-full-coverage no）。

三级演进总结：主从复制=数据冗余 + 读写分离（但不自动切）；哨兵=在主从之上加自动故障转移（但数据仍在一台主上）；集群=分片横向扩容 + 自带高可用（数据分散到多主，每主带从）。

9 · 分布式锁

用 Redis 实现跨进程/跨机器的互斥锁。从最朴素的写法一步步补全到生产可用，每一步都在堵上一个坑。

第 1 步：加锁要原子地"设值 + 设过期"

SET lock_key  unique_value  NX  EX 10
# NX：key 不存在才设置成功（抢锁）   EX 10：10 秒后自动过期（防死锁）

必须用这一条命令同时完成"占锁"和"设过期"。如果拆成 SETNX + EXPIRE 两条，万一设完锁、还没来得及设过期就宕机，这锁就永远不释放（死锁）。

第 2 步：防止误删别人的锁

误删场景：线程 A 拿锁，但业务执行超过 10 秒，锁自动过期；线程 B 趁机拿到锁；此时 A 执行完直接 DEL lock_key —— 删掉的是 B 的锁！

解决：加锁时 value 存一个唯一标识（如 UUID + 线程 ID）；释放时先校验 value 是不是自己的，是才删。而"判断 + 删除"这两步又必须原子，否则判断完、删除前锁又过期被别人抢走，还是会误删。用 Lua 脚本保证原子：

-- 释放锁：值匹配才删
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end

第 3 步：锁续期（业务没跑完锁就过期了）

过期时间设短了怕业务没跑完锁就没了，设长了又怕宕机后锁迟迟不释放。Redisson 的 watchdog（看门狗）解决：加锁后默认给 30 秒，并起一个后台定时任务每 10 秒检查一次，若业务还在执行就自动把锁续到 30 秒；直到业务结束或客户端宕机（宕机后不再续期，锁到期自动释放）。

第 4 步：可重入

同一线程要能重复拿同一把锁（比如递归、方法互调）。Redisson 用 Hash 存锁：field = 线程标识，value = 重入次数。同线程再次加锁就把次数 +1，释放时 -1，减到 0 才真正删除 key。

进阶：RedLock 及其争议

以上都基于单个 Redis（主从）。问题：主拿到锁后还没同步给从就宕机，哨兵把从切成主，新主上没有这把锁 → 另一个客户端又能拿到同一把锁，互斥被破坏。

RedLock 算法想解决这个：部署 N 个独立的 Redis 主节点（不主从），客户端依次向全部节点加锁，只有在超过半数（N/2+1）节点都成功、且总耗时小于锁有效期，才算加锁成功。

著名争议（Martin Kleppmann vs antirez）：分布式专家 Martin 撰文质疑 RedLock 在 GC 停顿、进程暂停、时钟漂移下并不安全 —— 比如客户端拿到锁后发生长 GC，锁已过期被别人拿走，它 GC 恢复后却以为自己还持有锁。他主张要安全必须引入fencing token（单调递增版本号）由被保护资源来校验。Redis 作者 antirez 则回应 RedLock 的假设和适用场景。

结论：Redis 锁本质是为性能/效率服务的、允许极小概率失效的锁；要求绝对正确、一丝不能错的强一致场景（如金融扣款），应该用 ZooKeeper / etcd（基于一致性协议）或数据库的唯一约束/乐观锁，而不是 Redis。

Stream 详解

Stream 是 5.0 专为消息队列设计的类型，模型很像一个只能追加的消息日志（append-only log），思路和 Kafka 一脉相承。

① 数据模型：一条条带唯一 ID 的消息
Stream "orders"（一条 append-only 日志） ┌───────────────┬───────────────┬───────────────┬──────────┐ │ 1699-0 │ 1700-0 │ 1700-1 │ ... │ ← 消息 ID（自动递增，全局有序） │ user=1 amt=50 │ user=2 amt=99 │ user=3 amt=12 │ │ ← 每条消息是若干 field-value └───────────────┴───────────────┴───────────────┴──────────┘

每条消息的 ID = 毫秒时间戳-序号（如 1699000000000-0）：同一毫秒内多条就靠序号递增区分，保证整体单调递增、全局有序。消息内容是任意多个 field-value（像个小 Hash）。

② 两种读法：直接读 vs 消费者组

不带组时用 XREAD 从某 ID 之后读，谁读都能读到全部（广播）。真正做 MQ 靠消费者组，它同时提供了"广播"和"负载均衡"两种语义：

消费者组模型：组间广播、组内分摊
Stream：msg1　msg2　msg3　msg4　msg5 …（同一份数据）
▼
消费者组 group1（有自己的 last_delivered_id）
consumerA　←　分到 msg1、msg3
consumerB　←　分到 msg2、msg4
组内分摊：每条只发给组内一个消费者 → 负载均衡
消费者组 group2（独立的 last_delivered_id）
consumerC　←　msg1、msg2、msg3…
和 group1 互不影响，能把全量再消费一遍 → 广播
  • 组间广播：每个组各自维护一个 last_delivered_id（游标，记到本组发到哪了），互不干扰。所以多个业务各建一个组，就能各自消费全量。
  • 组内分摊：同一个组里，一条消息只会投递给其中一个消费者，多个消费者并行处理不同消息，实现负载均衡与横向扩容。
③ 可靠投递：PEL + ACK

这是 Stream 比 List / Pub-Sub 强的关键——消息不会读了就没：

① 消费者用 XREADGROUP 读到消息 → 该消息进入这个消费者的 PEL（Pending Entries List 待确认列表）
▼
② 消费者处理完，发 XACK 确认 → 消息从 PEL 移除，投递闭环完成
▼
③ 若消费者崩溃/没 ACK：消息一直留在 PEL；别的消费者可用 XPENDING 查出、XCLAIM/XAUTOCLAIM 认领并重新处理 → 不丢

代价：ACK 保证了"至少投递一次（at-least-once）"，但重新认领可能导致同一条被处理两次，所以消费端最好做幂等。

④ 常用命令 + 一个最小例子
# 生产：往 orders 追加一条消息（* = 让 Redis 自动生成 ID）
XADD orders * user 1 amount 50        → 返回 "1699000000000-0"

# 建消费者组 g1，从头(0)开始消费
XGROUP CREATE orders g1 0

# 组内消费者 c1 读取新消息（> 表示"还没发给本组的新消息"）
XREADGROUP GROUP g1 c1 COUNT 10 STREAMS orders >

# 处理完确认
XACK orders g1 1699000000000-0

# 查本组还没 ACK 的消息（谁持有、多久了）
XPENDING orders g1

# 认领超时未处理的消息，转给自己重试
XAUTOCLAIM orders g1 c2 60000 0
命令作用
XADD生产消息（可带 MAXLEN 限长，见下）
XLEN / XRANGE看长度 / 按 ID 范围读历史（可回溯就靠它）
XREAD不用组，直接从某 ID 之后读（可阻塞）
XGROUP CREATE创建消费者组
XREADGROUP以"组+消费者"身份消费，读到即入 PEL
XACK确认，移出 PEL
XPENDING查未确认（PEL）情况
XCLAIM / XAUTOCLAIM认领他人超时未处理的消息，做故障转移
⑤ 控制内存：消息要限长
Stream 会把消息持久化留存，不限制的话会一直涨、吃爆内存。生产要用 XADD orders MAXLEN ~ 10000 * ... 限制大致长度（~ 表示近似裁剪，性能更好），或定期 XTRIM。这也是它和 Kafka（数据落磁盘、可存很久）的一大差距。
选型：要求可靠、大堆积、高吞吐、长期留存的正经消息队列，还是上 Kafka / RocketMQ；Redis Stream 适合轻量级、量不大、又想要"消费者组 + ACK 可靠投递"的场景（比 List/Pub-Sub 强很多，但受内存限制）。能不用 Redis 做 MQ 就不用——它的本职是缓存。

附 · 事务 / Lua / Pipeline

事务 MULTI / EXEC / WATCH

MULTI 开启事务，之后的命令先入队不执行，EXEC 时一次性按顺序执行队列里的命令（中间不会被别的客户端命令插入，保证"隔离执行"）。WATCH 用于乐观锁：监视某些 key，若在 EXEC 前被别人改过，则整个事务放弃执行。

为什么 Redis 事务不支持回滚？
  • 入队时的语法错误（命令不存在/参数个数不对）：整个事务拒绝执行（EXEC 直接失败）。
  • 执行时的运行错误（如对 String 执行 LPUSH、类型不匹配）：出错的命令失败，其它命令照常执行，不回滚。
官方理由：运行期错误几乎都是程序 bug（用错类型/命令），应在开发阶段发现，而非线上回滚；不支持回滚让 Redis 保持简单高效。所以 Redis 事务只保证"顺序、不被打断、全入队"，不保证原子性中的"全成功或全失败"，这点和关系型数据库事务有本质区别。

Lua 脚本

把多个命令写进一段 Lua 脚本用 EVAL 执行，Redis 把整个脚本当作一个命令原子地执行（单线程期间不会被打断）。比事务更好用：能在脚本里写条件判断和逻辑（如前面分布式锁的"比较 value 再删"）。注意脚本不能太耗时，否则会阻塞主线程。

Pipeline（管道）

客户端把多条命令一次性打包发给服务端，服务端执行完一次性把所有结果返回，从而把 N 次网络往返（RTT）压成 1 次，大幅提升批量操作吞吐。

Pipeline ≠ 事务：Pipeline 只是把多条命令攒一起发、减少网络往返，命令之间不保证原子、中间可能插入其它客户端的命令，纯粹是网络层优化；事务（MULTI/EXEC）才保证这批命令"顺序执行、不被打断"。两者解决的是不同问题，也可以结合用。

附 · 高频面试速记

Redis 为什么快？单线程为什么不慢？
纯内存 + IO 多路复用 + 单线程免锁免切换 + 高效数据结构；瓶颈在内存/网络而非 CPU。
Redis 是单线程还是多线程？6.0 改了什么？
命令执行始终单线程；4.0 后台线程做异步删除，6.0 多线程 IO 只分担网络读写与协议解析。
ZSet 底层为什么用跳表而不是红黑树？
跳表实现简单、范围查询友好、并发/调整成本低；小数据量时用 listpack。
缓存穿透 / 击穿 / 雪崩的区别与解决？
穿透=查不存在（布隆/空值）；击穿=热点失效（互斥锁/逻辑过期）；雪崩=大量同时失效或宕机（随机 TTL/多级缓存/高可用）。
怎么保证缓存和数据库一致？
Cache Aside 更新 DB + 删缓存；延迟双删；binlog 订阅；追求最终一致。
RDB 和 AOF 的区别？怎么选？
RDB 快照、体积小恢复快、丢数据多；AOF 记命令、丢数据少、体积大；4.0 混合持久化兼顾。
过期 key 怎么删除？内存满了怎么办？
惰性删除 + 定期删除；内存到 maxmemory 触发 8 种淘汰策略（LRU/LFU/random/ttl × allkeys/volatile）。
主从 / 哨兵 / 集群分别解决什么问题？
主从=数据冗余读写分离；哨兵=自动故障转移；集群=分片扩容（16384 槽）。
Redis 分布式锁怎么做才安全？
SET NX EX + 唯一 value + Lua 原子释放 + watchdog 续期；强一致场景慎用（RedLock 争议）。
