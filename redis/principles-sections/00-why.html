⏱️ 00.1 存储介质访问延迟层级与内存引擎的设计取舍 🔥 常问

🎯 这节回答实战篇哪个问题：对应 实战篇 00.1 —— 为什么在磁盘数据库前面加一层内存 Redis，响应速度能从毫秒级直接降到亚毫秒级并扛住十万并发？

要理解 Redis 在内核层面的每一项数据结构设计（为何不做固定大小页缓冲池、为何命令执行流不加互斥锁、为何对小对象做字节级紧凑编码），需要先建立现代服务器各级存储介质的物理访问延迟基准：

存储层级 典型单次访问延迟 放大为人类时间尺度
(设 1 ns = 1 秒)		 对存储引擎内核设计的直接约束
L1 / L2 CPU Cache ~ 1 ns / 4 ns 1 秒 ~ 4 秒 现代 CPU 缓存行（Cache Line）固定为 64 Bytes。将对象元数据头与短字符串紧凑打包进同一个 64B 块（如 embstr 与 listpack），可避免跨缓存行指针跳转引发的 Cache Miss。
L3 Cache / DRAM 主存 ~ 15 ns / 80~100 ns 15 秒 ~ 1.5 分钟 Redis 的核心工作区。单次随机内存寻址约 100 ns，在不发生互斥锁争用与线程上下文切换（单次切换约 1~3 μs，相当于数十次内存寻址）的前提下，单核每秒足以完成数十万至百万次数据结构操作。
同机房 TCP 网络 RTT ~ 200 μs ~ 500 μs 2.3 天 ~ 5.8 天 同机房一次网络收发耗时是单次 DRAM 寻址的 2000 ~ 5000 倍。因此 Redis 的吞吐瓶颈首先出现在网络套接字缓冲区拷贝与系统调用开销，这也是 6.0 引入多线程网络 I/O 的直接动因。
NVMe SSD 随机 4KB 读 ~ 20 μs ~ 100 μs 6 小时 ~ 1.1 天 磁盘关系型引擎（InnoDB / PostgreSQL）必须设计 8~16 KiB 页缓冲池、页锁与预写日志（WAL）来摊薄块设备随机 I/O；而纯内存引擎无需按磁盘页对齐，可直接通过 64 位虚拟地址指针组织变长结构。
机械硬盘（HDD）寻道 ~ 5 ms ~ 10 ms 2 个月 ~ 4 个月 Redis 仅由后台子进程或 bio 线程顺序写入 RDB 快照与 AOF 日志，避免在主线程命令执行路径上触发同步磁盘阻塞。

🧬 00.2 redisDb 全局键空间与过期时间字典的内存拓扑 🔥 常问

🎯 这节回答实战篇哪个问题：对应 实战篇 01.3 —— 执行一条 SET key val EX 300 和 GET key 时，Redis 在内存里把键值对和过期时间存在哪、怎么一步查出来？

在 Redis 源码（server.h）中，服务端全局实例状态由 struct redisServer 维护，其成员 redisDb *db 指向逻辑数据库数组。每个 redisDb 的核心并非二维表，而是两张协同工作的全局哈希字典：主键空间字典 dict *dict（保存全库所有键值对）与过期时间字典 dict *expires（仅保存设置了 TTL 的键及其毫秒级到期时间戳）：

一次完整 GET key 在内核源码（db.c: lookupKeyReadWithFlags）中的执行步骤

  1. 惰性过期前置拦截（expireIfNeeded）：计算 SipHash(key) 后先查 db->expires（若 expires 表本身为空则直接跳过这一步）。若命中且当前毫秒时钟 mstime() > entry->v.s64，说明键已到期——若当前节点是主库（Master），当场将删除动作传播至 AOF 与所有从库，并根据对象复杂度决定同步释放或投入 bio_lazy_free 异步释放，随后直接向客户端返回空；若当前节点是从库（Replica），不修改内存物理字典，但逻辑上同样向读客户端直接返回空值。
  2. 主键空间寻址与统计更新（lookupKey）：在 db->dict 中按桶头单向链表（拉链法解决哈希冲突）比对 SDS 键值，找到目标 dictEntry 后取出 robj *val。
  3. 淘汰元数据刷新：若当前未处于 fork 后台子进程运行期间（避免读操作仅仅因为刷新访问时钟就意外写脏共享内存页触发 COW），更新 val->lru 的 24 位时钟或 LFU 计数，并递增全局命中指标 stat_keyspace_hits。
