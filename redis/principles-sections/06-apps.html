⚖️ 06.1 主从异步切换丢锁、Redlock 争议与 Fencing Token 栅栏校验 🔥 常问

🎯 这节回答实战篇哪个问题：对应 实战篇 04.8 分布式锁 —— 如果主库刚加完锁就断电切主，或者持锁进程发生长时间 GC 停顿导致「两台机器同时以为自己持有锁」，怎样才能彻底保证下游数据库不被写乱？

由于 Redis 主从复制与 Cluster 主备切换本质上是异步复制（Asynchronous Replication）而非基于 Raft / Paxos 多数派落盘的线性一致复制，当客户端 C1 在主库刚执行完 SET lock val NX PX 30000 收到 OK、主库尚未将该命令传播给从库即断电宕机时，从库晋升为新主后并不包含这把锁，客户端 C2 便能再次加锁成功。

为解决单主切换丢锁，antirez 提出了 Redlock 算法：部署 N = 5 台完全独立无主从关系的 Redis Master，客户端记录起始本地时间 T1，依次向 5 台实例用相同 Key/Token 请求加锁，记录结束时间 T2；仅当在至少 3 台（多数派）加锁成功，且加锁总耗时 (T2 - T1) < TTL 时才算获取锁成功，实际有效租约剩余时间为 TTL - (T2 - T1) - 时钟漂移余量。然而分布式系统学者 Martin Kleppmann 指出：在存在进程停顿（如 JVM Full GC / Go STW / 容器 CPU Throttling）或系统时钟跳变的非同步网络模型下，任何单纯依赖客户端侧租约（TTL）的锁都无法单独保证下游存储的绝对互斥：

🎯 这节回答实战篇哪个问题：对应 实战篇 04.9 Stream 消息队列 与 04.10 Lua 脚本 —— 为什么 Stream 存几万条带相同字段名的订单消息能省下大量内存？Lua 脚本在主从复制时有什么约束？

一条 Stream 消息队列往往包含数万条具有相同字段名（如每条订单消息都带 order_id、user_id、amount）且消息 ID 具有极强时间戳前缀规律（如 1732676001012-0、1732676001015-0）的记录。若像普通哈希表那样把每条消息的字段名都重复存一遍，内存很快就会耗尽。Redis 为 Stream 设计了精巧的「rax 前缀压缩基数树 + listpack 同构字段复用宏节点」两层复合引擎：

  • PEL（Pending Entries List）的双 rax 树同步索引：每个消费者组结构体 streamCG 维护一张组全局 pel 基数树（记录组内所有已投递未 XACK 的消息 ID 指向 streamNACK 元数据），同时每个消费者 streamConsumer 内部也持有一张局部 pel 树指向同一个 streamNACK 对象（类似 redisDb 的键对象共享），使按组巡检与按消费者查询待确认消息均保持高效。
  • Lua 脚本的确定性与主从/AOF 复制演进：在早期 Redis 3.2 之前，主从复制与 AOF 重放的是整段 Lua 脚本源码本身（SCRIPT REPLICATION），因此若脚本内先调用了非确定性命令（如 TIME 或 SRANDMEMBER）再去修改键值，会导致从库重放时产生与主库不一致的结果而被内核直接拒绝报错。自 Redis 3.2 引入并在 Redis 5.0+ 设为默认的“效果复制（Effects Replication）”起，服务端不再把含随机逻辑的脚本原样发给从库，而是将脚本本次实际执行产生的一组确定性写命令包裹在 MULTI ... EXEC 事务块中写入 AOF 并同步给从库，彻底解除了随机读之后执行写操作的限制。

01. redisDb 如何组织过期时间？设置了 TTL 的键会把键名 SDS 存两份吗？

redisDb 独立维护主键空间字典 dict 与过期字典 expires。两者对应的 dictEntry->key 指针直接指向同一个物理内存地址上的键名 SDS 对象，零重复字符串开销；且过期字典利用 dictEntry 的 8 字节 union v 直接原位存储 int64_t 毫秒级时间戳，无需额外分配 redisObject。

02. Redis 6.0+ 开启多线程 I/O 后，为什么主线程操作哈希表和跳表依然不需要加锁？

因为引入了阶段同步屏障（Spin Barrier）：主线程先将不同客户端连接互不重叠地分发给各 I/O 线程并行读取 Socket 与解析 RESP 命令，期间主线程自旋等待所有 I/O 线程完成解析后，才由唯一的主线程独自串行遍历执行全部内存命令，最后再交由 I/O 线程并行刷回 Socket。内存数据结构自始至终只被主线程单线程读写。

03. 精确写出 String 类型 embstr 编码与 raw 编码以 44 字节为分界线的推导式。

jemalloc 分配一块刚好对齐单个 CPU Cache Line 的 64 Bytes 连续内存：减去 struct redisObject 元数据头（4b type + 4b encoding + 24b lru + 4B refcount + 8B ptr = 16 Bytes），减去取消对齐填充后的紧凑头 struct sdshdr8（1B len + 1B alloc + 1B flags = 3 Bytes），再减去末尾空字符 '\0'（1 Byte），剩余最大载荷恰好为 64 - 16 - 3 - 1 = 44 Bytes。

04. Redis 7.0 的 listpack 是如何同时消灭 ziplist 连锁更新并保留从后向前遍历能力的？

ziplist 在每个节点头部记录“前驱节点长度 prevlen”，当前驱跨越 254B 阈值时迫使后继头部从 1B 扩为 5B 引发多米诺式连续重分配；listpack 彻底删去前驱长度，改为在每个节点自身末尾存放当前节点总字节数 element-tot-len（每字节最高位标示长度编码是否结束），反向遍历时从末尾向左读取出自身长度即可一步跳到当前节点头部，节点修改完全自包含。

05. ZSet 执行 ZRANK 查询某元素排名为什么是 O(log N) 而不是 O(N)？

因为 zskiplistNode 的每一层结构 zskiplistLevel 除了维护前进指针 *forward 外，还维护了跨度无符号整数 span（记录该层指针跨越了多少个底层节点）。查找目标元素从高层向底层折线下探时，将沿途走过的每一跳 span 直接累加即可算出精确名次，无需扫描底层链表。

06. 哈希表 dict 扩容负载因子阈值为什么在有子进程时从 1 抬升到 5？

在 BGSAVE 或 BGREWRITEAOF 子进程存活期间，父子进程正通过操作系统页表共享只读物理内存页。若此时启动哈希表扩容搬迁，大面积修改桶指针会瞬间触发成千上万次写时复制（Copy-On-Write）缺页异常，导致 4 KiB 物理页被大量复制，引发内存翻倍风险，因此尽量推迟扩容直至子进程结束。

07. 为什么从节点（Replica）发现某 Key 已过期时，向客户端返回空却不自己物理删除它？

为保证主从状态机的严格确定性一致。从节点为只读副本，一切内存字典物理变更均须由主节点驱动：读从库遇到已到期键时先在逻辑上拦截返回 nil 避免读到过期脏数据，而物理内存回收统一等待主节点通过惰性或定期删除触发后发来的显式 DEL / UNLINK 同步指令再执行。

08. LFU 淘汰算法如何仅凭 8-bit 计数器（最大值 255）区分成千上万次访问的热点键？

redisObject.lru 的 24 位在 LFU 模式下被切分为高 16 位分钟级衰减时钟 ldt 与低 8 位概率对数计数器 logc（初始值 5）。每次访问并非线性 +1，而是以概率 1 / ((old_val - 5) × lfu_log_factor + 1) 概率递增，数值越大增长越慢（默认因子 10 下打满 255 约需百万次访问）；且长时间不访问时再按 lfu-decay-time 扣减计数，防止早年旧热点长期霸占内存。

09. 生产环境部署 Redis 为什么要显式关闭 Linux 透明大页（Transparent Huge Pages, THP）？

常规内存页粒度为 4 KiB，而开启 THP 后内核会将大块内存合并为 2 MiB（放大 512 倍）的大页。在 BGSAVE 子进程运行期间，哪怕主线程只是执行了一条 INCR 修改了某页内的 8 个字节，写时复制（COW）都不得不分配并拷贝整整 2 MiB 的物理内存副本，造成单条写命令出现数十毫秒尖刺延迟与内存暴涨。

10. PSYNC 2.0 为什么要设计 replid 和 replid2 两套复制流 ID？

解决主从切换后其余从库退化全量同步的问题。当哨兵将从库 A 提升为新主时，A 将原主库的 replid 存入 replid2 并冻结当时的偏移量于 second_replid_offset，随后生成新 replid。其他从库 B 改连新主 A 时携带的旧主 replid 可与 A 的 replid2 比对成功，只要偏移量仍在积压缓冲范围内即可直接走轻量增量同步。

11. Redis Cluster 为什么用 16384 个槽而非 65536 个？在线迁槽时 ASK 与 MOVED 有何差异？

Gossip 心跳包头携带槽位图 myslots：16384 位仅占 2 KiB，而 65536 位占 8 KiB（浪费 4 倍心跳带宽），且推荐主节点 ≤ 1000 台下 16384 槽已足够均匀。MOVED 代表槽归属已永久变更，客户端收到后更新本地槽映射缓存；ASK 代表槽正处于在线迁移中途，客户端不更新本地缓存，仅针对本次请求向目标节点先发 ASKING 临时开门再重发命令。

12. 为什么即使使用 5 节点 Redlock，面对客户端 GC 停顿仍需配合 Fencing Token 才能保证绝对安全？

客户端 C1 拿到锁后若在发送写数据库请求前发生超过锁 TTL 的长时间 GC STW 停顿，锁在 Redis 端自动过期并被客户端 C2 合法获取且完成写入；随后 C1 从 GC 恢复继续把早已准备好的旧数据发出，就会覆盖 C2 的最新结果。唯有由锁服务颁发全局单调递增序号（Fencing Token），并由下游存储引擎校验拒绝序号小于历史最大值的迟到请求，才能在存储边界彻底拦截过期锁写入。
