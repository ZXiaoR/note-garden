01.1 aeEventLoop 单线程 Reactor 与 Linux epoll 协作机制 常问 epoll 红黑树深挖

这节回答实战篇哪个问题：对应 实战篇 04.3 防重幂等 与 07.1 高危命令禁令 —— 为什么 Redis 单线程执行命令还能支撑十万并发，而敲一条慢命令 KEYS * 就会把所有客户端卡住？

Redis 没有采用早期 Web 服务器“每连接一线程（Thread-per-Connection）”的阻塞模型，而是自研了轻量级跨平台事件驱动库 ae（ae.c / ae_epoll.c）。在 Linux 平台上，ae 底层直接封装内核的 epoll 系统调用，使单个主线程能够同时监听数万个客户端 TCP 套接字（Socket fd），且每次循环只遍历真正有数据到达的活跃连接：

  • 为什么 epoll 能在海量空闲连接下保持 O(1) 事件获取效率：传统的 select / poll 每次调用都需要把包含数万个 fd 的集合从用户态拷贝进内核态，并在线性扫描 O(N) 后返回。而 epoll_create 在内核空间常驻了一棵红黑树（rbr，以 O(log N) 增删查所有被监控的 fd）和一个就绪双向链表（rdllist）。当网卡收到某客户端数据包触发硬件中断并拷贝至 Socket 接收缓冲区时，内核通过注册在红黑树节点上的回调函数 ep_poll_callback 直接将该 fd 挂入 rdllist；Redis 主线程调用 epoll_wait 时只需以 O(1) 检查 rdllist 是否非空并取走就绪事件即可。
  • 文件事件（File Events）与时间事件（Time Events）的单线程融合：Redis 主循环函数 aeMain 在同一个线程里统一调度网络 I/O 事件与后台周期性任务（serverCron，负责主动抽样清理过期键、触发渐进式 rehash 步进、检查 RDB/AOF 子进程退出状态）。为了既不让 epoll_wait 永久死等耽误定时任务，也不忙等空耗 CPU，主线程会先计算距离最近一个时间事件触发还剩多少毫秒 tvp，将其作为 epoll_wait 的最大阻塞超时时间传入。
  • beforesleep 钩子的批处理关键作用：在每一轮进入 epoll_wait 休眠前，主线程都会执行 beforeSleep()，集中完成向所有待回复客户端批量刷出响应缓冲区、处理集群槽状态广播、主动推进快速过期键抽样以及向从库请求 ACK 等工作。

01.2 服务端进程内的多线程分工与无锁同步屏障 常问

这节回答实战篇哪个问题：对应 实战篇 07.1 —— 为什么用 UNLINK 删除大 Key 不会卡住主线程？Redis 6.0+ 开启多线程网络 I/O 后，为什么操作哈希表依然不需要加锁？

在生产机器上对运行中的 Redis 7.x 进程执行 ps -T -p <pid>，可以看到进程内实际包含多个操作系统级线程。理解“Redis 是单线程还是多线程”的精确表述是：内存键值数据结构的读写执行（processCommand）严格由唯一的 Main Thread 串行完成，而阻塞磁盘系统调用、大块内存释放与高带宽 Socket 拷贝则交由两类辅助线程池分担：

线程/子进程类别 引入版本与默认数 源码职责边界与线程间同步机制
① 后台异步任务线程
bio_*（bio.c）		 Redis 4.0+
固定 3 个后台线程		 各自维护一个带互斥锁与条件变量（pthread_cond_t）的生产者-消费者任务队列，专门承接会卡顿主线程的慢系统调用：
• bio_close_file：异步执行 close(fd) 关闭旧 AOF/RDB 大文件；
• bio_aof_fsync：在 appendfsync everysec 模式下每秒后台调用 fsync() 刷盘；
• bio_lazy_free：执行 UNLINK、FLUSHDB ASYNC 或过期大集合异步释放（当集合元素数超过 LAZYFREE_THRESHOLD = 64 时才投入后台队列，小对象直接在主线程原地 free 更省跨线程入队开销）。
② 多线程网络 I/O
io_thd_*（networking.c）		 Redis 6.0+
默认 io-threads 1（仅主线程）		 解决万兆网卡高吞吐场景下 read() / write() 内核态—用户态内存拷贝占掉 70%+ CPU 时间的问题：
• 主线程通过轮询（Round-Robin）将待读客户端挂入各线程专属链表 io_threads_list[id]（互不共享同一 client*，无需给客户端缓冲区加锁）；
• 随后设置原子计数器 io_threads_pending[id] 唤醒各 I/O 线程并行读取 Socket 并完成 RESP 协议切分，主线程在此处自旋等待所有 pending 归零（同步屏障）；
• 屏障通过后，主线程独自按序遍历执行所有解析好的命令并将响应写入各自的回复缓冲，最后再次通过同步屏障分发给 I/O 线程并行调用 write() 写回网卡。
③ 持久化子进程
redis-rdb-bgsave / temp-rewriteaof		 早期版本即支持
按需临时 fork()		 独立子进程（非线程），通过虚拟内存页表共享主进程某一时刻的内存视图生成 RDB 或重写 AOF，任务完成后立即退出并由主线程在 serverCron 中通过 waitpid 回收。
架构权衡总结 —— 为什么 Redis 始终不把阶段 ③（执行内存命令）改成多线程并发：
1. 锁开销抵消并发收益：Redis 支持 Hash / List / Set / ZSet 等复杂嵌套指针结构（如跳表插入需修改多层前后驱指针与跨度 span），若允许多个线程并发修改同一实例字典，必须引入细粒度读写锁或桶锁，高频加解锁、原子 CAS 指令与缓存一致性协议（MESI）失效开销反而会拉低简单命令吞吐；
2. 保持原子语义极简：单线程串行执行使得 INCR、ZINCRBY 以及任意复杂的 Lua 脚本天然具备无死锁的严格串行化隔离级别；当单核 CPU 真正成为瓶颈时，工程上直接通过 Redis Cluster 多分片实例绑定多颗物理核心即可实现无锁水平扩展。
