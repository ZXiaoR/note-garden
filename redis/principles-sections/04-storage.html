为什么 Redis 7.0 要把 AOF 重写架构升级为 Multi-Part AOF

在 Redis 6.x 及更早版本中，执行 BGREWRITEAOF 期间为了不漏掉主线程新收到的写指令，主线程必须把每一条新写命令同时写进「旧 AOF 缓冲区（刷入旧 AOF 文件）」和「AOF 重写缓冲区（aof_rewrite_buf_blocks）」，等子进程写完基准文件后，再通过管道将重写缓冲区发给子进程或由主线程自己追加到新文件尾部——这不仅带来了双倍内存缓冲与双倍磁盘写放大，更会在重写收尾阶段因追加大量积压缓冲而阻塞主线程。

Redis 7.0 的 Multi-Part AOF（MP-AOF）彻底消除了重写缓冲区与管道通信：触发重写时，主线程直接新建一个编号递增的增量文件 2.incr.aof 承接后续实时写命令（旧增量文件 1.incr.aof 立即封存停写）；子进程独立把历史数据重写为新的 2.base.rdb；完成后主线程只需以微秒级原子更新 manifest 清单文件指向 2.base.rdb + 2.incr.aof，并将废弃的 1.base + 1.incr 交由 bio_close_file 后台异步删除。

🧮 04.2 过期抽样清理、主从删除协议与 24-bit 近似 LRU / LFU

1. 定期过期抽样算法（activeExpireCycle）与主从一致性约束

  • 时间片受控的贪心随机抽样：serverCron 每秒默认运行 hz = 10 次慢速周期（同时 beforeSleep 也会运行上限 1ms 的快速周期）。每轮依次遍历各数据库 expires 字典，每次随机抽取 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP = 20 个键检查是否过期并清理；若这 20 个样本中已过期键超过 25%（即 ≥ 5 个），说明当前过期键较密集，立刻在同一数据库继续抽下一批 20 个，直到过期占比回落到 25% 以下或本轮累计耗时触及 CPU 时间上限（最高不超过总 CPU 时间的 25%），从而绝不长时间卡住主线程。
  • 主从复制下的物理删除一致性规则：从节点（Replica）自身不运行主动定期删除，遇到读请求命中已过期键时也只返回 nil 而不修改自身内存字典；只有当主节点通过惰性或定期抽样真正删除了某个过期键时，主节点会向所有从库及 AOF 显式合成并发送一条 DEL（或 UNLINK）指令驱动从库删除，确保主从数据集在任意时刻保持确定性收敛。

2. 复用 redisObject.lru 24-bit 字段的近似 LRU 与概率对数 LFU

若像教科书实现那样为全库几千万个键维护一条全局双向链表，每个键仅前后指针就要多耗费 16 Bytes（与整个 redisObject 头一样大），且每次读命中都要摘除节点移至表头。Redis 的做法是零额外指针开销——直接复用每个 redisObject 已有的 24 bits lru 位域，并在内存中维护一个固定长度仅为 EVPOOL_SIZE = 16 的淘汰候选池数组 EvictionPoolLRU（每次触发淘汰时随机抽样 maxmemory-samples 默认 5 个键塞入候选池按空闲度升序重排，总是驱逐池尾空闲度最高的那一个，跨轮次保留历史候选池使命中精度逼近全局真实 LRU）：

LFU 低 8 位对数概率递增机制（LFULogIncr）：8 个比特无符号整数最大只能表示 255。为了用 0 ~ 255 表征高达百万级的访问热度，每次命中时先执行时间衰减（将当前分钟时钟减去 ldt 除以 lfu-decay-time 扣减 logc），再生成 (0, 1) 均匀随机浮点数 r，仅当 r < 1.0 / ((baseval × lfu_log_factor) + 1)（其中 baseval = max(0, logc - 5)，默认 lfu-log-factor = 10）时才将 logc 加 1：在默认因子 10 下，访问 100 次时 logc ≈ 10，访问 1 万次时 logc ≈ 78，访问 100 万次才逼近上限 255。
