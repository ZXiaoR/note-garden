03.1 · 概率型数据结构原理：布隆过滤器 k 次哈希位带、最优参数公式与布谷鸟过滤器

03.1 布隆过滤器（Bloom Filter）误判率推导与删除难题 深挖

这节回答实战篇哪个问题：对应 实战篇 03.2 防缓存穿透 —— 当需要拦截海量随机伪造 ID 时，1 亿个合法商品 ID 到底该分配多大的布隆位图，如果商品下架了怎么删？

前置拦截缓存穿透的布隆过滤器由一个长度为 m 比特的连续位数组（初始全为 0）与 k 个彼此独立的均匀哈希函数 h1..hk 构成。每插入一个真实存在的键，将其通过 k 个哈希函数取模映射到 k 个比特位并置为 1；查询某键时，只要对应的 k 个位置中有任意一位为 0，则 100% 确定该键从未写入过（零假阴性 / Zero False Negative）；若 k 位全为 1，则可能是其他若干个键恰好分别把这 k 个位置置成了 1，存在可控的假阳性误判率（False Positive Rate，记作 p）。

最优位数组大小 m 与哈希个数 k 的工程核算公式

给定预计写入的唯一元素总量 n 与可接受的最大假阳性误判率 p（工程上常取 p = 0.01 即 1%），使误判率最低的最优参数由以下两式给出：

  • 所需总比特数：m = - (n × ln p) / (ln 2)2 ≈ -2.08 × n × ln p。当 p = 1% 时，平均每个元素仅消耗 m / n ≈ 9.58 bits——存 1 亿（108）个商品 ID 仅需约 114 MiB 内存（若用 Set 存 8 字节整数加哈希桶开销则需超过 3 GiB）。
  • 最优哈希函数个数：k = (m / n) × ln 2 ≈ 0.693 × (m / n)。当 p = 1% 时，最优 k ≈ 7（哈希函数并非越多越好，k 过大反而会让位数组过快被 1 填满，导致误判率回升）。

标准布隆过滤器的不可删除限制与两种演进方案

如上图中的 #5 号比特位可能同时被 sku_101 和 sku_202 共同置为 1。若下架删除 sku_101 时直接把 #5 清零，会导致原本存在的 sku_202 被错误判定为不存在（破坏零漏判承诺）。需要动态删除元素时的解决方案：

  1. 定时全量重建双缓冲：每日凌晨在后台根据数据库最新有效 ID 构建新位图 bf:v2，原子切换指针后异步 UNLINK 旧位图；
  2. 布谷鸟过滤器（Cuckoo Filter，RedisBloom 模块原生提供 CF.ADD / CF.DEL）：不存单比特而是在双候选哈希桶中存放元素的紧凑指纹（Fingerprint，数比特），原生支持 O(1) 安全删除指纹，且在误判率低于 3% 时比计数布隆过滤器（Counting Bloom Filter，每槽扩为 4 bits 计数器导致空间膨胀 4 倍）更节省内存。
03.2 · 双写并发时序对比：为什么「先删缓存再写 DB」高发脏数据，而「先写 DB 再删缓存」极低概率失配

03.2 数据库 × 缓存并发读写交错时序推演与异步补偿架构 常问

这节回答实战篇哪个问题：对应 实战篇 03.1 双写一致性 —— 标准方案「先更数据库、再删缓存」在极端并发或主从读写分离延迟下还会不会脏？为什么工程上推荐用 Binlog 异步重试替代「延迟双删」？

在不引入分布式强一致锁拖垮吞吐量的前提下，任何跨 MySQL 与 Redis 两个独立系统的双写都存在并发时间窗。通过精确对比两个并发请求（写线程 A 将 v=10 改为 v=20，读线程 B 查询该键）的时间线交错概率，可以清楚看出不同顺序的可靠性差异：

关于「先写 DB 再删缓存」极端边界与「延迟双删」的客观分析

  • 为什么「先写 DB、再删缓存」出现脏回填的概率比反过来低几个数量级：在标准方案下，要出现脏数据必须同时满足四个苛刻前提：① 读线程 B 进来的那一刻，缓存恰好刚刚自然过期失效；② B 从 MySQL 读出旧值 v=10；③ 在 B 把 v=10 写回 Redis 内存（通常仅需 0.3ms）之前，写线程 A 居然完整跑完了比写内存慢得多的 MySQL 磁盘事务提交（数毫秒）外加一次 Redis 删除；④ B 发生长尾 GC 卡顿，最后才把 v=10 覆盖写进 Redis。由于“写磁盘事务”天然远慢于“写内存缓存”，步骤 ③ 抢跑在步骤 ④ 之前的概率极低。
  • 读写分离架构下的主从延迟放大与对策：真正容易触发旧值回填的场景是MySQL 开启了一主多从读写分离——写线程 A 更新了 MySQL 主库并删了 Redis，紧接着读线程 B 未命中缓存去查尚未同步完成的 MySQL 从库，读到旧值回填进了缓存。工程解法有二：① 通过订阅从库自身的 Binlog（而非主库 Binlog）来触发删除 Redis 缓存，确保缓存被删时从库一定已经同步到位；② 对刚发生修改的主键在短窗口内强制路由读主库。
  • 为什么延迟双删（DEL -> UPDATE DB -> sleep(N ms) -> DEL）不是银弹：sleep 的休眠时长 N 只能拍脑袋估算，设短了兜不住慢查询或主从延迟，设长了阻塞工作协程（或增加延时任务负担），且第二次删除本身依然可能因网络超时失败，因此在大型生产系统中普遍演进为基于 Binlog + MQ 指数退避重试的确定性补偿架构。
