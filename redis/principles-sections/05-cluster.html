05.1 · 复制协议内核：PSYNC2 双 replid 解决切主重同步问题与两类复制缓冲区内存边界

05.1 PSYNC 2.0 双复制流标识与环形积压缓冲区机制 深挖

这节回答实战篇哪个问题：对应 实战篇 06.1 主从复制 —— 从库网络闪断重连或哨兵切主后，怎么只增量补齐缺失的几秒数据，而不是每次都重新全量拷贝几个 GB 的 RDB？

在早期 Redis 2.8 的 PSYNC 1.0 中，一旦主节点宕机、哨兵将某个从节点晋升为新主节点（生成全新的 runid），其余存活从节点改挂新主时因 runid 不匹配，会全部退化为昂贵的 FULLRESYNC 全量 RDB 同步。为此，Redis 4.0 引入了 PSYNC 2.0，用代表“数据集历史血统”的 40 位随机串 replid 取代实例 runid，并在每个节点内同时维护主副两组复制标识：

① 复制客户端输出缓冲

05.2 · 哨兵共识协议：quorum 与 majority 双门槛辨析、Raft Leader 纪元投票与从库三轮筛选

05.2 Sentinel 故障转移中的两级人数门槛与选主算法 常问

这节回答实战篇哪个问题：对应 实战篇 06.1 Sentinel 哨兵 —— 为什么哨兵至少要部署 3 台奇数节点？主库失联时谁来拍板把哪台从库升为新主库？

Sentinel 自动故障转移包含“判定主库客观下线”→“哨兵内部选出唯一执行者 Leader”→“从存活从库中挑出新 Master”三个严格阶段，其中 quorum（配置项）与 majority（集群哨兵半数以上）的分工是理解高可用容错边界的关键：

  1. SDOWN 到 ODOWN 仅看 quorum：单个哨兵连续 down-after-milliseconds 未收到主库有效 PING 回复时标记为主观下线（SDOWN），随即向其他哨兵发送 SENTINEL is-master-down-by-addr 询问；只要赞成下线的票数达到配置的 quorum（例如 5 台哨兵配了 quorum = 2），即升级为客观下线（ODOWN）。
  2. 真正执行切换的 Sentinel Leader 选举必须同时满足 max(quorum, N/2 + 1)：进入 Raft 变体选举后，每个哨兵把配置纪元 current_epoch 自增 1，遵循同一纪元内先到先得（每台哨兵在同一 epoch 只能投出一张赞成票）原则拉票。候选哨兵必须同时拿到严格过半数（majority = ⌊N/2⌋ + 1，如 5 台需 ≥ 3 票）且 ≥ quorum 的选票才能当选 Leader——这保证了即便网络分区，同一纪元绝不可能同时选出两个哨兵 Leader 并发乱切主。
  3. Leader 从存活 Replica 中挑选新 Master 的三轮比较顺序：先剔除断连超过 (down-after-milliseconds × 10) 的慢从库，随后依次比较：① replica-priority 配置值更小者胜出（配为 0 表示永不参选主库）；② 若优先级相同，比较 slave_repl_offset 复制偏移量更大者胜出（数据离原主库最近，丢数据最少）；③ 若偏移量也完全相等，按实例 runid 字典序最小者兜底决出唯一新主。
05.3 · 分片集群内核：16384 槽与 Gossip 2KB 位图定量权衡、在线槽迁移状态机与 MOVED / ASK

05.3 Cluster Gossip 心跳位图定量分析与在线重分片协议 深挖

这节回答实战篇哪个问题：对应 实战篇 06.2 Cluster 分片 —— 为什么哈希槽总数定为 16384 而不是 65536？集群在线加机器搬迁槽位期间，业务请求怎么做到不停服跳转（MOVED vs ASK）？

CRC16(key) 校验和本身产生的是 16 位整数（范围 0 ~ 65535 共 216 = 65536 个值），但作者 antirez 在设计 Redis Cluster 时特意对 16384（214）取模，核心原因来自去中心化 Gossip 协议心跳包的网络带宽账：

  • 心跳包 myslots 位图体积相差 4 倍：Cluster 没有中心元数据节点，每个节点每秒随机挑几个节点通过集群总线互发 PING / PONG 心跳包，包头结构体 clusterMsg 中必须携带一张定长二进制位图 unsigned char myslots[CLUSTER_SLOTS/8] 来声明自己当前负责哪些槽。当槽数为 16384 时，该位图占 16384 / 8 = 2048 Bytes = 2 KiB；若设为 65536，单次心跳仅这一个字段就暴涨至 8 KiB，在百节点集群高频对等广播下会消耗大量内网带宽。
  • 集群推荐规模上限与位图压缩率：由于 Gossip 协议节点数过多会导致故障收敛变慢，官方建议主节点规模不超过 1000 个。对于 ≤ 1000 个主节点，16384 个槽平均每节点仍可分到十余个槽，负载均衡颗粒度完全充裕；且槽数越少、同一主节点的连续槽区间越集中，RDB/网络传输对稀疏位图的压缩率也越高。
