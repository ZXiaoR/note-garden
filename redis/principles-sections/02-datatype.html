🧬 02.1 redisObject（16 Bytes）与 SDS / embstr 44 字节边界推导

在 Redis 内核中，每次写入键值对都会创建两个对象：Key 固定是底层动态字符串 SDS，而 Value 则统一封装在 16 字节（128 bits）的元数据头 struct redisObject（源码名 robj）中，通过 type 标识对外逻辑类型，通过 encoding 标识底层挂载的物理数据结构：

为什么 SDS（Simple Dynamic String）能同时省内存并消除 C 原生字符串缺陷

  1. __attribute__((__packed__)) 取消结构体对齐填充：从 Redis 3.2 起，SDS 按字符串长度细分出 sdshdr5（已弃用）、sdshdr8（长 ≤ 255B）、sdshdr16、sdshdr32、sdshdr64 五档头部，并加上编译器紧凑修饰符禁止按 4/8 字节补齐空洞。因此 sdshdr8 精确只占 uint8_t len (1B) + uint8_t alloc (1B) + unsigned char flags (1B) = 3 Bytes；再配合默认内存分配器 jemalloc 按 8B, 16B, 32B, 64B... 阶梯切分内存单元的机制，为了不突破 64 Bytes 这一档分配规格，留给字符串有效字节的最大长度恰好是 64 - 16 - 3 - 1 = 44 Bytes（在 Redis 3.0 时代因统一使用未压缩的 8B sdshdr，该分界线曾是 39 Bytes）。
  2. 常数级长度查询、二进制安全与空间预分配：直接读取 len 字段使 STRLEN 从 O(N) 降为 O(1)，且以 len 而非空字符 '\0' 判定边界，中间包含任意二进制 0x00 字节均不会被截断（末尾额外保留的 1 字节 '\0' 仅为了直接兼容少量 C 标准库打印函数）。当执行 APPEND 扩容时，若新长度 < 1 MiB 则成倍预分配（alloc = 2 × newlen），若 ≥ 1 MiB 则每次额外多分配 1 MiB，将连续 N 次拼接的 realloc 次数从 N 次均摊降至对数级。
  3. int 内联整数编码：若写入的字符串能解析为 64 位有符号长整型（long），Redis 直接把上面的 8 字节指针字段 void *ptr 强转为数值本身存储，连 SDS 都不必分配。
📦 02.2 · 紧凑连续内存结构演进：ziplist 连锁更新成因、7.0 listpack 反向遍历原理与 intset 单向升级

📦 02.2 从 ziplist 到 listpack：根除连锁更新（Cascade Update）

为了在小规模 Hash / List / ZSet 中省去双向链表与哈希桶昂贵的前后驱指针（64 位机器上每多两个指针就要多花 16 Bytes，甚至比几字节的整数数据本身还大），Redis 设计了整块连续内存紧凑列表。早期版本采用 ziplist，而在 Redis 7.0 中已全面由 listpack 接管（Hash / ZSet 小数据直接存单个 listpack，List 底层 quicklist 的每个双向链表节点内部也由 ziplist 换成了 listpack）：

逻辑类型 紧凑编码（小规模数据） 标准编码（大规模数据） 单向升级配置阈值（Redis 7.2 默认）
String int（8B 长整型内联）
embstr（单次 malloc ≤ 64B）		 raw（robj 与 SDS 分两次独立分配） 字节长度 > 44 Bytes，或对 int / embstr 执行任意修改指令后单向转为 raw。
Hash listpack（field 与 value 相邻紧挨排列） hashtable（即双表 dict） 键值对数 > hash-max-listpack-entries (512) 或任一字段字节长 > hash-max-listpack-value (64B)。
List listpack（7.0+ 单节点少元素时直接用单块 listpack） quicklist（宏观双向链表 + 每个节点挂载一块容量可控且支持 LZF 压缩的 listpack） 单块超过 list-max-listpack-size (-2 即 8 KiB) 时分裂为包含多个节点的 quicklist。
Set intset（全整数等宽升序数组，支持 O(log N) 二分查找）
listpack（7.2+ 新增短字符串紧凑集）		 hashtable（Value 固定为 NULL 的字典） 全整数且个数 ≤ set-max-intset-entries (512) 用 intset；含非整数但个数 ≤ set-max-listpack-entries (128) 且单值 ≤ 64B 用 listpack；超限转 hashtable。
ZSet listpack（按 score 升序依次紧挨存放 member, score） skiplist + dict（复合结构 `zset`） 元素数 > zset-max-listpack-entries (128) 或任一成员长 > zset-max-listpack-value (64B)。

为什么 intset（整数集合）升级位宽时必须重分配整块数组且只升不降：intset 通过 encoding（INTSET_ENC_INT16 / INT32 / INT64）保证数组内所有整数严格等宽，从而直接按 contents + idx × width 执行 O(log N) 二分查找。一旦插入一个超出当前位宽的大整数（如向 int16_t 数组中插入 65535），若不把已有元素全部扩宽为 int32_t，等宽寻址公式即告失效；而删除该大数后若要判断是否可降级，每次删除都需 O(N) 遍历全表求最大值，得不偿失，因此 Redis 所有紧凑编码升级均为单向不可逆。

🪜 02.3 · 高效索引双核心：zskiplist 跨度指针（O(log N) 算 ZRANK）与 dict 渐进式 Rehash

🪜 02.3 跳表 zskiplist 源码结构与哈希表渐进式 Rehash

1. ZSet 复合结构与跳表节点 span 跨度字段的关键作用

当元素突破阈值后，ZSet 在底层结构体 struct zset 中同时持有一个哈希字典 dict *dict 和一张跳跃表 zskiplist *zsl（两者通过指针共享同一份成员 SDS 对象，不重复拷贝字符串内存）：dict 负责以 O(1) 实现 ZSCORE key member 单点查分，zskiplist 负责以平均 O(log N) 维护有序性与区间扫描。

许多资料只提到跳表每层有前进指针 forward，却忽略了 zskiplistLevel 中另一个至关重要的无符号整数字段 unsigned long span（跨度，记录沿着当前层这一跳跨越了多少个底层节点）：正因为维护了 span，执行 ZRANK 查询某成员是第几名时，无需从表头逐个遍历数节点 O(N)，只需在从高层向底层折线下探的查找路径上，把沿途经过的所有前进指针的 span 累加起来，即可在 O(log N) 时间内直接算出精确排名。

为什么 ZSet 选用跳表而非红黑树或 B+ 树

  • 对比红黑树 / AVL 平衡树：两者单点增删查同为 O(log N)，但当执行高频的 ZRANGE 范围读取时，跳表在 O(log N) 定位到区间起点后，直接沿最底层 L0 双向链表（带 backward 逆向指针支持 REV 倒序）顺序向右走 M 步即可；而平衡二叉树做中序区间遍历需要在父子指针间反复回溯，且插入删除引发的左旋/右旋变色实现远比跳表以 ZSKIPLIST_P = 0.25 概率随机生成层高复杂。
  • 对比 B+ 树：B+ 树将扇出（Fan-out）做大到上百阶是为了让每个节点对齐 16 KiB 磁盘页以减少随机磁盘寻道次数；而纯内存没有机械寻道代价，维护大页节点分裂合并的 CPU 搬移成本反而高于跳表的轻量指针链接。

哈希表负载因子双阈值（1 vs 5）与 COW 协同设计

dict 的负载因子定义为 load_factor = ht[0].used / ht[0].size：

  • 常规状态（无后台 RDB / AOF 重写子进程）：load_factor ≥ 1 即启动扩容；
  • 持久化子进程存活期间：阈值自动抬升至 load_factor ≥ 5。原因在于子进程正利用内核写时复制（Copy-On-Write）与父进程共享内存物理页，若此时触发哈希表扩容搬迁，大量哈希桶指针修改会把成千上万个原本共享的 4 KiB 内存页瞬间“写脏”，迫使操作系统复制整页副本，造成物理内存占用短时间内翻倍；
  • 自动缩容条件：当 load_factor < 0.1（Redis 7.x 优化为更平滑的阈值）时，同样以渐进式 Rehash 缩减为首个 ≥ used 的 2n 大小以归还空闲桶内存。
