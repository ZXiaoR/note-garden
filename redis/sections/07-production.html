🔑 07.1–07.2 · 键空间与命令红线：分段命名、必设 TTL、禁用 KEYS 并改用 SCAN + UNLINK

🔑 07.1 Key 命名规范与禁用高危阻塞命令

1. Key 命名与生命周期两条准则

  • 统一冒号分段全小写：按 业务名:模块名:实体标识[:属性] 组织，例如 mall:order:detail:9001。键名本身也占内存，在不影响可读性的前提下保持精简（单个键名建议 ≤ 64 字节，不含空格和换行）。
  • 凡是缓存与临时状态，一律必设 TTL：上线前搜索代码里所有的 Set / HSet / SAdd / ZAdd，检查是否配了过期时间，防止无人清理的“僵尸键”日积月累把内存耗尽。

2. 严禁在线上执行 KEYS * 与 FLUSHALL，改用 SCAN + UNLINK

因为 Redis 的所有数据读写命令都在同一个主线程里排队串行执行，一旦你在存了 500 万个键的生产库上敲下 KEYS order:* 或同步 DEL 一个百万元素的大集合，主线程就会卡住几百毫秒到几秒钟，期间全站所有正常请求全部超时！

  • 遍历找键用 SCAN：每次只抽查一小批哈希槽位就立刻让出主线程；注意唯一正确的结束条件是返回的游标 nextCursor == 0（即使某次返回的列表为空，只要游标不为 0 就说明还没扫完；大 Hash/Set/ZSet 对应使用 HSCAN / SSCAN / ZSCAN）。
  • 删除键优先用 UNLINK（Redis 4.0+）：主线程只花 O(1) 把键从全局字典摘掉，真正耗时的内存释放自动丢给后台异步线程慢慢回收。
🐹 scan_unlink.go · 线上安全分批扫描并异步清理指定前缀键 [Go · go-redis/v9 · Redis 6.x/7.x] 
func CleanPrefixSafely(ctx context.Context, rdb *redis.Client, pattern string) error {
    var cursor uint64 = 0
    for {
        keys, nextCursor, err := rdb.Scan(ctx, cursor, pattern, 200).Result()
        if err != nil {
            return err
        }
        if len(keys) > 0 {
            // Unlink 非阻塞异步回收内存，避免 Del 大对象卡住主线程
            if err := rdb.Unlink(ctx, keys...).Err(); err != nil {
                return err
            }
        }
        cursor = nextCursor
        if cursor == 0 { // 必须以游标回到 0 作为唯一结束标志
            break
        }
    }
    return nil
}

⚡ 07.3 · 消灭 for 循环慢请求：用 MGET 与 Pipeline 把 N 次网络往返压缩为 1 次

⚡ 07.3 批量操作：别在 for 循环里逐条调 Redis

代码审查时最常见的性能隐患就是在循环里连发几十次 rdb.Get()：虽然 Redis 内存里跑一条命令只要 0.001ms，但来回走一趟网络要 0.5ms，循环 100 次接口就凭空慢了 50ms。

  • 同类型多键读写：优先用原生批量命令 MGET / MSET / HMGET。
  • 不同类型多条命令组合（比如同时执行 INCR + EXPIRE + ZSCORE）：用 Pipeline（管道）一次性打包发出、一次性收回结果（单批次建议控制在 100 ~ 500 条以内，避免单包过大）。
🐹 pipeline_batch.go · 用 Pipeline 一次网络往返完成多命令组合 [Go · go-redis/v9] 
pipe := rdb.Pipeline()
incrCmd := pipe.Incr(ctx, "metrics:pv:20261128")
pipe.Expire(ctx, "metrics:pv:20261128", 48*time.Hour)
bannerCmd := pipe.Get(ctx, "config:home:banner")

// Exec() 才真正发起唯一一次网络请求
_, err := pipe.Exec(ctx)
if err != nil && !errors.Is(err, redis.Nil) {
    return err
}
fmt.Println("今日 PV:", incrCmd.Val(), "Banner:", bannerCmd.Val())

🛡️ 07.4 客户端超时配置、故障降级与序列化选型

1. 连接池超时配置与「Redis 挂了业务怎么降级」

缓存本来是用来加速和保护系统的，绝不能因为 Redis 抖动超时导致整个主站接口直接 500 报错不可用。生产客户端需配置严格的毫秒级读写超时（如 300ms ~ 500ms），并在捕获网络异常时做分级降级：

🐹 prod_client.go · 生产级连接池与快速超时参数 [Go · go-redis/v9] 
rdb := redis.NewClient(&redis.Options{
    Addr:         "10.0.1.11:6379",
    Username:     "mall_svc",
    Password:     "ProdSecret_2026",
    PoolSize:     64,                    // 最大连接数（常取 CPU 核数 * 10 左右）
    MinIdleConns: 16,                    // 保活空闲连接，防突发流量冷建连慢
    DialTimeout:  1 * time.Second,       // 建连超时
    ReadTimeout:  300 * time.Millisecond,// 读超时：快速失败，不拖死上游协程
    WriteTimeout: 300 * time.Millisecond,// 写超时
    MaxRetries:   2,                     // 网络闪断自动重试最多 2 次
})
🐹 fallback_demo.go · Redis 宕机时读缓存接口安全降级写法 [Go] 
func GetBannerWithFallback(ctx context.Context, rdb *redis.Client, dbLimiter *rate.Limiter) (string, error) {
    val, err := rdb.Get(ctx, "config:home:banner").Result()
    if err == nil {
        return val, nil
    }
    if !errors.Is(err, redis.Nil) {
        // Redis 真挂了或超时：打错误日志报警，不要直接 return err 挂掉首页！
        log.Printf("[WARN] Redis 异常触发降级: %v", err)
        if !dbLimiter.Allow() { // 限流保护数据库不被洪峰冲垮
            return defaultStaticBannerJSON, nil // 超出数据库承受力时返回本地静态兜底值
        }
    }
    return queryBannerFromMySQL(ctx)
}

2. 序列化取舍：存业务对象选 JSON String 还是 Hash？

对比维度 序列化为 JSON String（如 SET user:1 "{...}"） 拆字段存 Hash（如 HSET user:1 name "林晓" vip "2"）
读写粒度 整读整写：改 1 个字段也要把整个 JSON 拉回应用层解析修改再全量写回 局部读写：HSET / HINCRBY 直接在服务端改单个字段，省带宽且无并发覆盖
复杂嵌套结构 天然支持多层嵌套对象与数组（如商品详情含多规格 SKU 数组） 不适合嵌套（field 的值只能是扁平字符串，强塞子 JSON 反而别扭）
内存与 TTL 控制 大 JSON 可配合 Snappy/Gzip 压缩；按整个对象设 TTL 扁平字段数适中（≤ 512）时底层用 listpack 极省内存；7.4+ 支持 HEXPIRE 单字段过期
选型结论 90% 读多写少、整存整取的缓存快照首选 JSON String（代码最直观） 高频单字段修改/原子加减的扁平状态首选 Hash（如购物车、用户多维计数）
🔍 07.6–07.7 · 监控与安全：5 个核心指标、SLOWLOG 慢查询、ACL 权限与禁公网裸奔

🔍 07.5 线上监控巡检与安全红线

1. 必盯的 5 个监控指标与 INFO / SLOWLOG 诊断

  • 内存使用率与驱逐数（INFO memory / INFO stats）：盯紧 used_memory / maxmemory（超 80% 预警）、内存碎片率 mem_fragmentation_ratio（正常 1.0 ~ 1.5）以及被强行挤掉的键数量 evicted_keys。
  • 缓存命中率（INFO stats）：计算公式为 keyspace_hits / (keyspace_hits + keyspace_misses)。常规缓存命中率应高于 90%；若突然暴跌到 50% 以下，立刻排查是否发生了缓存穿透或大面积集中过期。
  • 活跃连接数与拒绝连接数（INFO clients）：关注 connected_clients（默认上限 10000）与 rejected_connections，暴涨通常说明某台业务服务没复用全局 Client 导致连接泄漏。
  • 慢查询日志 SLOWLOG GET 10：查看最近执行最慢的 10 条命令（默认记录服务端单线程执行超 10ms = 10000μs 的指令，线上建议调严到 2000μs）。

2. 三条安全底线：禁公网、设密码、配 ACL 最小权限

  • 绝不裸露在公网：历年无数云服务器被挖矿木马入侵，源头都是把无密码的 6379 端口直接暴露在公网！务必配置云安全组仅对内网业务服务器放行，并在配置中指定 bind 127.0.0.1 <内网IP> 与 protected-mode yes。
  • 使用 Redis 6.0+ ACL（Access Control List，访问控制列表）隔离业务权限：不要让所有服务共用最高权限的 default 账号，给业务建专属账号并禁掉 -@dangerous（包含 FLUSHALL / KEYS / CONFIG 等危险命令）：
