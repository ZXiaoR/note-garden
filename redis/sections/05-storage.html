💾 05.1 RDB、AOF 与混合持久化：宕机各会丢多少数据

内存一旦断电数据就会清空。为了让进程重启后能恢复数据，Redis 提供了两类落盘机制：RDB（Redis Database，内存二进制快照）、AOF（Append Only File，追加写命令日志），以及把两者结合起来的混合持久化：

持久化方式 它往磁盘里存什么（类比） 服务器突然断电会丢多少数据？ 文件大小、重启恢复速度与适用场景
RDB 快照
dump.rdb		 每隔几分钟给全库内存拍一张压缩二进制照片（子进程后台执行 BGSAVE） 丢分钟级数据（丢失距上一次成功拍照以来 5~15 分钟内的所有新增修改） 文件最小、重启直接加载进内存恢复最快；适合冷备归档、主从首次全量同步。
AOF 日志
appendonly		 像记流水账一样，每执行一条写命令就往文件末尾追加记录这条命令文本 默认 appendfsync everysec 每秒刷盘一次，最多丢失最后 1 秒写入 纯文本体积大，重启要把成百上千万条历史写命令从头重演一遍，恢复较慢。
混合持久化
4.0+ / 7.0 默认推荐		 重写时先存一份全量 RDB 二进制底座，之后新来的写操作再追加增量 AOF 命令 继承 AOF 的每秒刷盘策略，最多丢失最后 1 秒写入 重启恢复快 + 最多只丢 1 秒，是线上有状态实例的标准默认配置。
⚙️ redis.conf · 混合持久化推荐配置 [Redis 6.x / 7.x] 
# 1. RDB 定时快照（手动备份请用异步 BGSAVE，严禁在线上跑阻塞主线程的 SAVE）
save 3600 1 300 100 60 10000

# 2. 开启 AOF 与混合持久化（Redis 7.0+ 开启 appendonly 后默认即启用混合模式）
appendonly yes
aof-use-rdb-preamble yes

# 3. 刷盘策略：everysec 每秒后台刷盘（always 每条刷盘太慢，no 交给系统太危险）
appendfsync everysec

补充：Redis 7.0 的 AOF 目录变化与断电修复

在 Redis 6.x 中 AOF 是单个 appendonly.aof 文件；升到 Redis 7.0+ 后改为了 appendonlydir/ 文件夹（Multi-Part AOF），拆成基准快照 *.base.rdb、增量日志 *.incr.aof 和清单 *.manifest。若宿主机断电导致末尾留了半截残缺命令无法启动，执行一行官方修复工具即可截断残尾恢复启动： 

redis-check-aof --fix /data/redis/appendonlydir/appendonly.aof.manifest

💡 背后的原理：后台子进程拍几 GB 的 RDB 快照时，为什么主线程还能照常处理写请求而不卡顿？详见 《📘 核心原理篇 · 04.1 fork 写时复制（COW）页表机制》。

🗑️ 05.2 · 内存写满应对：maxmemory 70% 水位线与缓存淘汰策略选型

🗑️ 05.2 内存满了怎么办：maxmemory 与淘汰策略

如果一直往 Redis 塞数据，内存总有写满的一天。生产上必须通过 maxmemory 划定业务数据上限（通常设为机器物理内存的 70% 左右，留出 30% 给后台快照写时复制、主从同步缓冲区和操作系统，防止整机内存耗尽被系统强杀），并通过 maxmemory-policy 指定内存触顶后的处理策略：

Redis 共提供 8 种淘汰策略，日常开发无需死记硬背，按你的实例用途直接对号入座即可（首次了解两个核心缩写：LRU，Least Recently Used，最近最少使用——看谁最久没被访问过；LFU，Least Frequently Used，最不经常使用——看谁历史访问总频次最低）：

你的 Redis 用途 推荐 maxmemory-policy 为什么这样选（附其余策略说明）
① 纯缓存实例（最常见） allkeys-lfu 或 allkeys-lru 在所有键里淘汰冷数据腾地方，写请求永不报 OOM。若偶尔有后台脚本全量扫冷数据，allkeys-lfu（Redis 4.0+）比 allkeys-lru 更稳，不会因为冷键刚被扫过一次就把真正的高频热键挤出去。
② 同一实例混存缓存与持久配置 volatile-lru / volatile-lfu volatile-* 只在设了 TTL 过期时间的键里挑冷数据淘汰，不设 TTL 的长期配置键不会被误删（另有 volatile-ttl 优先踢最快过期的键、*-random 随机踢）。
③ 分布式锁 / Stream 消息队列 noeviction（Redis 默认值） 绝不悄悄删任何键！内存一旦触顶，新写入直接报错返回 OOM 触发监控告警，保证锁和未消费消息不会被静默踢丢。

💡 背后的原理：Redis 怎么只利用每个对象头里仅有的 24 个比特位（3 字节）记住上万次访问频率并自动随时间衰减？详见 《📘 核心原理篇 · 04.2 24-bit 近似 LRU 与对数衰减 LFU》。

🧭 05.3 · 架构设计原则：永远把 Redis 里的数据当成「极端情况下可以丢」来设计

🧭 05.3 核心结论：把 Redis 当成「随时可能丢」来设计业务

学完持久化和内存淘汰后，请记住一条最省心的工程铁律（设计原则）：无论开启了混合持久化还是主从集群，写业务代码时都要假设「Redis 里的数据在极端故障下可能丢掉最后几秒，甚至整库清空重建」——

  • 纯缓存数据：天生不怕丢，未命中时自动走 Cache-Aside 从 MySQL 查出来重新塞回去即可（只需配合 singleflight 防止瞬间击穿数据库）。
  • 计数器、购物车、排行榜等有状态数据：要么像 04.4 那样定时异步落盘到 MySQL，要么在 MySQL 里保留原始积分明细表，万一 Redis 磁盘彻底损坏，随时能跑一个修复脚本从 MySQL 聚合算回排行榜。
