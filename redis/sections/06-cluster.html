06.2 重点：上了高可用与集群后，你的业务代码要改什么？

绝大多数线上 Redis 集群都是云厂商托管或运维搭好的，作为业务开发者，你真正必须清楚的是这三件事会直接影响你写的代码能不能跑对：

影响 ①：主从异步复制延迟 —— 刚写完立刻读从库，可能读到旧数据

主库（Master）收到写命令后，是先给客户端返回成功，再异步把命令同步给从库（Replica）的。如果你开启了“写走主库、读走从库”的读写分离，用户刚改完收货地址，页面下一毫秒刷新恰好路由到还没同步完的从库，就会看到改之前的旧地址。

  • 代码怎么处理：除非单主库的读 CPU 真的扛不住了（单核主库通常能扛近 10 万 QPS），否则常规业务读写全部走主库即可；如果确实开启了从库分担读，对修改后立即展示的敏感接口（支付状态、个人资料页），强制指定读主库。

影响 ②：Cluster 多 Key 命令跨槽报错（CROSSSLOT）与 {Hash Tag}

Redis Cluster 把全部键空间切成了 0 ~ 16383 共 16384 个哈希槽（Hash Slots），每来一个 Key 就计算 CRC16(key) % 16384 决定它存在哪台分片主库上。因此，单机跑得好好的 MGET、MSET、SINTER 或多键 Lua 脚本，一旦涉及的两个 Key 算出来不在同一个槽位，就会直接报错 CROSSSLOT Keys in request don't hash to the same slot！

  • 代码怎么改（{Hash Tag} 花括号局部哈希）：只要在键名里加上一对花括号 {...}，Redis 就只拿第一对非空花括号里面的内容去算槽位。例如把同一用户的两个键命名为 user:{10086}:profile 和 user:{10086}:wallet，它们都会按 "10086" 算槽，必然落在同一台机器上，MGET 和 Lua 就能正常执行了。
  • 数据倾斜大坑：花括号里必须放离散度高的用户 ID 或订单 ID（如 {10086}），千万别把固定的业务前缀包进去写成 {user}:10086、{user}:10087——否则全站几千万个用户键都会算出同一个槽号，全部挤死在同一台分片机器上！

影响 ③：客户端初始化必须切换成对应的连接模式

代码里不能再用单机的 redis.NewClient 去硬连哨兵或 Cluster 里的某一台机器（否则主从切换或槽位重定向时请求会报错），请按线上架构选择对应的客户端构造器：

sentinel_mode.go · 连接 Sentinel 哨兵架构 [Go · go-redis/v9] 
// 填哨兵节点地址与逻辑主库名，切主时 SDK 自动感知重连新主库
rdb := redis.NewFailoverClient(&redis.FailoverOptions{
    MasterName: "mymaster",
    SentinelAddrs: []string{
        "10.0.1.21:26379",
        "10.0.1.22:26379",
        "10.0.1.23:26379",
    },
    Password:       "ProdPass_2026",
    RouteByLatency: false, // 默认全走主库，避免从库延迟读旧值
})
cluster_mode.go · 连接 Cluster 集群与 {Hash Tag} 实操 [Go · go-redis/v9] 
// 使用 NewClusterClient，SDK 自动缓存 16384 槽映射并跟随 MOVED/ASK 跳转
clusterRdb := redis.NewClusterClient(&redis.ClusterOptions{
    Addrs: []string{
        "10.0.1.11:6379", "10.0.1.12:6379", "10.0.1.13:6379",
    },
    Password: "ProdPass_2026",
})

// 多键操作带上离散 {uid} Hash Tag，确保同槽不报 CROSSSLOT
vals, err := clusterRdb.MGet(ctx,
    "user:{10086}:profile",
    "user:{10086}:wallet",
).Result()

deploy_ha_appendix.sh · 主从、哨兵与 3 主 3 从 Cluster 运维模板 
# ==================== 1. 从节点 redis.conf 核心项 ====================
replicaof 10.0.1.11 6379         # Redis 5.0+ 用 replicaof 替代旧版 slaveof
masterauth ProdPass_2026         # 连接主库的密码
requirepass ProdPass_2026        # 主从密码设一致，以便切主后角色互换
replica-read-only yes            # 从库强制只读
repl-backlog-size 128mb          # 主库建议调大复制积压缓冲区（默认仅 1MB），防闪断触发全量同步

# ==================== 2. 哨兵 sentinel.conf（至少部署 3 个奇数实例，端口 26379）====================
port 26379
sentinel monitor mymaster 10.0.1.11 6379 2   # quorum=2：至少 2 台哨兵判失联才触发客观下线
sentinel auth-pass mymaster ProdPass_2026
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
# 主库 redis.conf 建议加防脑裂限制（至少连着 1 台延迟 ≤ 10 秒的从库才允许写）：
# min-replicas-to-write 1
# min-replicas-max-lag 10

# ==================== 3. 创建 3 主 3 从 Redis Cluster ====================
# 各节点开启 cluster-enabled yes，并放行防火墙 6379 数据端口与 16379 总线端口（端口+10000）
redis-cli -a ProdPass_2026 --cluster create \
  10.0.1.11:6379 10.0.1.12:6379 10.0.1.13:6379 \
  10.0.1.14:6379 10.0.1.15:6379 10.0.1.16:6379 \
  --cluster-replicas 1

# 命令行连接集群记得加 -c 参数（自动跟随 MOVED 重定向跳转）
redis-cli -c -h 10.0.1.11 -p 6379 -a ProdPass_2026
