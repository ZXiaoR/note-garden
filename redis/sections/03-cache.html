❓ 03.1 · 缓存穿透、击穿、雪崩有什么区别？分别怎么挡住？

🛡️ 03.1 缓存三大经典问题（都会打到 DB，但触发根因完全不同）

异常类型 一句话本质 标准工程解法
① 缓存穿透 查根本不存在的数据（如 id=-1），缓存和 DB 都没有，每次都穿透打到 DB • 布隆过滤器前置拦截
• 缓存空对象（NULL 设 30~60s 短 TTL）
• 接口层参数合法性校验
② 缓存击穿 单个超热 Key（如秒杀商品）到期瞬间，万级并发同时回源 DB 重建 • 互斥锁（Mutex）：只让第 1 个线程查 DB 重建，其余等待重试
• 逻辑过期：物理永不过期，value 存逻辑时间戳，过期异步重建、先返旧值
③ 缓存雪崩 大批 Key 同时到期 或 Redis 实例宕机，流量洪峰压垮 DB • TTL 加随机打散值（基础时间 + 随机几分钟）
• 高可用集群（哨兵 / Cluster）
• 本地多级缓存（Caffeine）+ 限流降级

❓ 03.2 · 先改 DB 还是先删缓存？为什么是“删”而不是“更新”缓存？

🔄 03.2 缓存与数据库一致性（Cache-Aside 旁路缓存）

只要数据同时存在 MySQL 和 Redis，就要解决同步顺序问题。标准答案是 Cache-Aside：读时未命中查 DB 回填；写时「先更新 DB，再删除缓存」。

错误/备选方案 为什么不行或并发下会出什么问题？
❌ 写 DB + 更新缓存 ① 并发写覆盖：请求 A(写10) 先写 DB，请求 B(写20) 后写 DB 并先更新缓存=20，结果 A 的网络慢最后把缓存覆写成旧值 10！
② 算力浪费：写多读少时频繁更新没人读的缓存白费力气，直接删掉按需懒加载更划算。
⚠️ 先删缓存，再更 DB 高概率脏回填：写请求 A 刚删完缓存、还没来得及改完 DB 时，并发读请求 B 进来发现缓存空了，去 DB 读出旧值 V1 重新灌回缓存，导致缓存长期脏数据！
👉 补救：若非要用此顺序，必须在更完 DB 后做延迟双删（如 sleep 500ms 再删一次）。
✅ 先更 DB，再删缓存
(工业界首选)		 只有当“缓存恰好失效 + 读查到旧值 V1 + 写改完 DB 并删完缓存 + 读最后才把 V1 写回缓存”同时发生才会脏（因为读内存远快于写磁盘，此交错概率极低），配合 TTL 兜底 即可。
🚀 Canal 订阅 binlog 若“删缓存”那一步网络报错失败怎么办？可用 MQ 异步重试删除，或用 Canal 伪装成 MySQL 从库订阅 binlog 异步删除缓存，与业务代码彻底解耦。
❓ 03.3 · 大 Key 与热 Key 有什么危害？怎么排查和根治？

🐘 大 Key（单个 Value 体积过大）

标准：String > 10KB，或 Hash/List/Set/ZSet 元素数 > 5000。
危害：单线程读写/DEL 阻塞其他命令、打满网卡带宽、Cluster 分片内存倾斜。
排查：redis-cli --bigkeys、MEMORY USAGE key。
根治：① 化整为零拆分（大 Hash 按 field 取模拆成多个小 Hash）；② 删除一律用 UNLINK（4.0 后台异步回收，绝不用 DEL）。

🔥 热 Key（单个 Key QPS 极高）

场景：顶流明星八卦、大促爆款商品，单 Key 每秒被查几万次。
危害：流量全打在 Cluster 的同一个分片节点上，把单机网卡/CPU 打死，失效瞬间还会引发缓存击穿。
发现：redis-cli --hotkeys（需开启 LFU）、客户端/Proxy 埋点。
根治：① 升级本地二级缓存（应用内存 Caffeine 挡掉 95% 读）；② Key 加随机后缀打散（复制成 key#1..N 分散到多节点）。
