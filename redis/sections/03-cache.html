🔄 03.1 旁路缓存模式（Cache-Aside）与双写一致性

当同一份数据既持久化在 MySQL 里、又缓存在 Redis 里时，业界最通用的配合方式叫 Cache-Aside（旁路缓存模式）——业务代码自己同时管两边：

  • 读的时候：先查 Redis，命中直接返回；没命中再去查 MySQL，把查出来的结果塞进 Redis（带上过期时间）后返回。
  • 改的时候：先更新 MySQL 数据库，提交成功后再删除（UNLINK / DEL）对应的 Redis 缓存，下次有人读时自然会重新把最新数据加载进缓存。

初学者最常问的两个「为什么」：看图秒懂两种错误写法的并发事故

  • 追问 ①：为什么是「删缓存」而不是直接「把新值写进缓存」？
    一防并发写乱序覆盖（看下方左图：线程 A 先改库为 100，线程 B 后改库为 200，但线程 A 网络卡了一下晚一步才去写 Redis，把原本正确的 200 又覆盖回旧值 100）；二省无效计算（如果商品价格 1 分钟改了 10 次却没人点开详情页，每次都拼装大 JSON 写缓存纯属白忙活，删掉后等真正有人读再算最省资源）。
  • 追问 ②：为什么必须「先更新数据库，再删缓存」，反过来先删缓存不行吗？
    看下方右图：如果先删缓存，写线程 A 刚把缓存删空，还没跑完较慢的 MySQL 磁盘更新（几毫秒），此时读线程 B 进来发现没缓存，去查 MySQL 读到了尚未提交的旧值 100，顺手又把旧值 100 重新填回了 Redis！等线程 A 慢吞吞把数据库改成 200，Redis 里已经常驻脏数据 100 了。

缓存的 TTL（过期时间）到底怎么定？

就算代码里写了「改库后主动删缓存」，万一删缓存那一下刚好遇到网络闪断报错，没有 TTL 的键就会永远停留在旧数据。因此凡是缓存键都必须设兜底 TTL，且统一加上 5% ~ 15% 随机抖动偏移：

业务数据类型 推荐 TTL 档位 配合策略与设定依据
高频访问业务实体
(商品详情、帖子正文、用户资料)		 15 ~ 30 分钟
+ 随机 0 ~ 300 秒		 修改时主动 UNLINK 删缓存保证秒级生效；万一删失败，最长半小时内也能自动过期自愈。
低频变更配置 / 字典
(类目树、省市字典、Banner)		 2 ~ 12 小时
+ 随机偏移		 平时几乎不改，后台运营点「发布」按钮时主动删除对应缓存键即可。
防穿透空值占位符
(查库不存在写入的 __EMPTY__)		 30 ~ 60 秒（短 TTL） 既能挡住瞬时恶意刷不存在 ID，又避免后台随后真新建了该记录时用户长时间查不到。
登录会话 / 临时验证码 登录态 7 天 / 验证码 5 分钟 由产品安全规则决定生命周期，无需随机抖动。

🛡️ 03.2 · 三大缓存异常防护：穿透（空值/布隆）、击穿（singleflight 归并）与雪崩（随机抖动 TTL）

🛡️ 03.2 缓存穿透、击穿与雪崩的识别与代码防护

区分这三个名字很像的故障，只需要看「查的数据在数据库里有没有」以及「是 1 个键过期还是一大片键同时过期」：

异常名称 一句话成因识别 标准工程防护手段
① 缓存穿透
(Penetration)		 一直查缓存和数据库里都根本不存在的 ID（如恶意遍历负数 ID），每次都穿透打到数据库且写不进正常缓存。 1. 接口层参数格式校验；
2. 缓存空值占位符（查库为空时写 "__EMPTY__"，设 45s 短 TTL）；
3. ID 基数极大时前置布隆过滤器（Bloom Filter，位图概率拦截器）。
② 缓存击穿
(Breakdown)		 某 1 个超高并发热点 Key 刚好到点过期的那一瞬间，上万个并发请求同时没命中，一窝蜂冲进数据库查同一条数据。 1. 请求归并（Go singleflight）或互斥锁：同一时刻只放 1 个协程去查库回填，其余并发请求原地共享这 1 次查询结果；
2. 极热活动页设逻辑过期（物理不设 TTL，后台异步单协程刷新）。
③ 缓存雪崩
(Avalanche)		 成千上万个 Key 在同一秒集中过期（如凌晨脚本批量预热设了完全相同的 TTL），或 Redis 整机宕机。 1. TTL 加随机抖动（Jitter）：基础时长 + rand(0, 300s) 打散过期时刻；
2. 部署哨兵或集群高可用 + 应用层限流降级兜底。

下面这段可直接复用的 Go 缓存加载器，用不到 40 行代码把空值防穿透、singleflight 防击穿、随机 TTL 防雪崩三道防线合在了一起：

🐹 safe_cache_loader.go · 空值占位 + singleflight 防击穿 + 随机抖动 TTL [Go 1.22+ · go-redis/v9 · Redis 6.x/7.x] 
// 安装依赖: go get golang.org/x/sync/singleflight
const emptyPlaceholder = "__EMPTY__"

type ProductCache struct {
    rdb   *redis.Client
    group singleflight.Group // 合并同一进程内相同 Key 的并发回源请求
}

func (c *ProductCache) GetProductJSON(ctx context.Context, skuID int64) (string, error) {
    key := fmt.Sprintf("mall:sku:detail:%d", skuID)

    // 1. 先查 Redis
    cached, err := c.rdb.Get(ctx, key).Result()
    if err == nil {
        if cached == emptyPlaceholder {
            return "", ErrProductNotFound // 命中空值标记，直接挡回穿透流量
        }
        return cached, nil
    }

    // 2. 未命中：singleflight 保证万级并发下同一 skuID 只有 1 个协程去查 MySQL
    v, err, _ := c.group.Do(key, func() (any, error) {
        data, dbErr := queryProductFromMySQL(ctx, skuID)
        if errors.Is(dbErr, ErrProductNotFound) {
            // 防穿透：数据库也没有时，写 45 秒短 TTL 空值占位
            _ = c.rdb.Set(ctx, key, emptyPlaceholder, 45*time.Second).Err()
            return "", ErrProductNotFound
        }
        if dbErr != nil {
            return "", dbErr
        }

        // 防雪崩：基础 30 分钟 + 0~300 秒随机抖动，打散集中过期
        jitter := time.Duration(rand.IntN(300)) * time.Second
        _ = c.rdb.Set(ctx, key, data, 30*time.Minute+jitter).Err()
        return data, nil
    })
    if err != nil {
        return "", err
    }
    return v.(string), nil
}

💡 背后的原理：如果恶意攻击每次都换完全不重复的随机假 ID（空值占位拦不住第二次），就需要在内存前置布隆过滤器——它的位图大小和哈希次数怎么算，详见 《📘 核心原理篇 · 03.1 布隆过滤器误判率数学推导》。

🐘 03.3 · 容量与流量倾斜治理：大 Key（BigKey）拆分清理与热 Key（HotKey）多级分流

🐘 03.3 大 Key（BigKey）与热 Key（HotKey）治理

1. 大 Key（单个键值体积过大或元素过多）

  • 参考红线：String 超过 10 KB（严禁超 1 MB）；集合类（Hash / List / Set / ZSet）元素超过 5000 个。
  • 有什么危害：读一次打满网卡带宽、阻塞单线程拖慢其他请求、集群下把某一台分片内存单独撑爆、直接调 DEL 回收内存时卡死实例几百毫秒。
  • 排查命令：低峰期在从库跑 redis-cli --bigkeys -i 0.01，并用 MEMORY USAGE key 看实际字节数。
  • 怎么治：① 大集合按 id % 100 拆成 100 个小桶；② 只缓存必要字段，大文本压缩后存；③ 删除一律用异步 UNLINK key。

2. 热 Key（单个键瞬间涌入数万至十万 QPS）

  • 典型场景：突发娱乐热搜、整点秒杀爆款商品。就算上了 10 台机器的 Redis Cluster，同一个 Key 也只会固定落在其中 1 台机器上，把单机网卡或 CPU 打满。
  • 排查命令：开启 LFU 淘汰策略后执行 redis-cli --hotkeys，或在业务网关/SDK 统计热点键。
  • 怎么治：① 首选进程内本地二级缓存（在每台 Go/Node 业务机器内存里缓存该热键 1 ~ 3 秒，几十台应用服务器直接替 Redis 挡掉 95%+ 读流量）；② 给热键加随机后缀复制成 hot:sku:888#1..N 多份，打散到不同集群分片。
