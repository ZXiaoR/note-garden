🔄 03.1 · 缓存协同模式：Cache-Aside 标准读写闭环与双写最终一致性落地

🔄 03.1 旁路缓存模式（Cache-Aside）与双写协同规范

当同一份业务数据既持久化在 MySQL 中，又缓存在 Redis 中时，应用程序采用最广泛的协作规范是 Cache-Aside（旁路缓存模式）：由业务服务同时对接数据库与缓存，遵循「读请求未命中时回源查库并回填缓存；写请求先更新数据库，成功后删除对应缓存」的顺序。

在工程实践中执行写操作时，之所以选择「删除缓存（Invalidate）」而非「直接覆写更新缓存（Update）」，一是避免两个并发写请求因网络乱序导致旧值覆盖新值，二是在写多读少场景下省去反复序列化计算却无人读取的资源消耗。同时，为了防止第二步“删除缓存”因瞬时网络抖动报错失败，生产系统通常会为所有缓存设置合理的兜底过期时间（TTL），对一致性敏感的核心业务还会引入消息队列重试或通过 Canal 订阅 MySQL binlog 异步删除缓存。

🛡️ 03.2 · 三大缓存异常防护：穿透（空值/布隆）、击穿（singleflight 归并）与雪崩（随机抖动 TTL）

🛡️ 03.2 缓存穿透、击穿与雪崩的识别与代码防护

高并发场景下，缓存层可能因三种不同原因无法拦截请求，导致流量直接回源访问数据库。区分三者最清晰的方式是看“请求查的 Key 在数据库里是否存在、涉及单个热点 Key 还是大批量 Key”：

异常名称 触发场景与成因 标准工程防护手段
① 缓存穿透
(Penetration)		 大量请求查询缓存与数据库中都根本不存在的记录（例如恶意遍历负值或伪造不存在的商品 ID），每次回源都查不到结果因而无法写入正常缓存。 1. 接口入参校验（拦截格式非法 ID）；
2. 缓存空值占位符（查库为空时写入特殊标记如 "__NULL__"，设 30~60s 短 TTL）；
3. 布隆过滤器（Bloom Filter）前置拦截（所有合法 ID 预热进位图，判定不存在的直接拒绝回源）。
② 缓存击穿
(Breakdown)		 单个超高并发热点 Key 在到达过期时间失效的瞬间，成千上万个并发读请求同时发现缓存未命中，一拥而上回源查库重建同一份数据。 1. 进程内请求归并（如 Go singleflight）或分布式互斥锁：同一时刻只放行 1 个协程回源查库并回填缓存，其余同 Key 请求共享该次查询结果；
2. 逻辑过期刷新：物理上不设 Redis TTL，在 Value JSON 内封装逻辑到期时间戳，发现逻辑过期后先立即返回旧值，同时异步派发单协程后台刷新。
③ 缓存雪崩
(Avalanche)		 大批量缓存 Key 在同一时刻集中过期（例如定时任务批量预热写了相同的 TTL），或者 Redis 节点故障不可用，引发全局回源洪峰。 1. 过期时间增加随机抖动值（Jitter）：如基础 30 分钟 + rand(0, 300s) 打散过期时间点；
2. 部署 Sentinel / Cluster 高可用架构；
3. 应用进程本地二级缓存 + 熔断限流降级兜底。

下面这段 Go 生产级缓存读取函数，将空值防穿透、singleflight 请求归并防击穿、以及随机抖动 TTL 防雪崩三项防护完整整合在一个干净的查询闭环中：

🐹 safe_cache_loader.go · 整合空值缓存 + singleflight 防击穿 + 随机 TTL 抖动 
const emptyPlaceholder = "__EMPTY__"

type ProductCache struct {
    rdb   *redis.Client
    group singleflight.Group // golang.org/x/sync/singleflight：合并同一进程内相同 Key 的并发回源
}

func (c *ProductCache) GetProductJSON(ctx context.Context, skuID int64) (string, error) {
    key := fmt.Sprintf("mall:sku:detail:%d", skuID)

    // 1. 优先查询 Redis
    cached, err := c.rdb.Get(ctx, key).Result()
    if err == nil {
        if cached == emptyPlaceholder {
            return "", ErrProductNotFound // 命中空值占位符，直接拦截缓存穿透
        }
        return cached, nil
    }

    // 2. 缓存未命中：使用 singleflight 确保万级并发下同一 skuID 只有 1 个请求穿透查 MySQL
    v, err, _ := c.group.Do(key, func() (any, error) {
        data, dbErr := queryProductFromMySQL(ctx, skuID)
        if errors.Is(dbErr, ErrProductNotFound) {
            // 数据库也不存在：写入 45 秒短 TTL 空值占位，防止重复穿透
            _ = c.rdb.Set(ctx, key, emptyPlaceholder, 45*time.Second).Err()
            return "", ErrProductNotFound
        }
        if dbErr != nil {
            return "", dbErr
        }

        // 正常回填：基础 30 分钟 + 0~300 秒随机偏移，打散大批缓存同时过期导致的雪崩
        jitter := time.Duration(rand.IntN(300)) * time.Second
        _ = c.rdb.Set(ctx, key, data, 30*time.Minute+jitter).Err()
        return data, nil
    })
    if err != nil {
        return "", err
    }
    return v.(string), nil
}
🐘 03.3 · 线上容量与流量倾斜治理：BigKey 拆分清理与 HotKey 多级缓存分流

🐘 03.3 大 Key（BigKey）与热 Key（HotKey）工程治理

1. 大 Key（单个 Value 字节过大或集合元素过多）

  • 参考判定阈值：String 类型 Value 超过 10 KiB（严禁超过 1 MiB）；Hash / List / Set / ZSet 元素数量超过 5000 个。
  • 实际影响：单次读取占用大量网卡出口带宽、主线程处理耗时拉长导致后续请求排队、集群模式下引发单个分片节点内存率先写满、同步执行 DEL 时造成百毫秒级卡顿。
  • 低影响排查工具：在从节点或业务低峰期运行 redis-cli --bigkeys -i 0.01（内部基于 SCAN 并在每轮间休眠 10ms 保护实例），再对可疑键调用 MEMORY USAGE key SAMPLES 5 测量实际字节占用。
  • 拆分与清理方案：
    1. 水平分桶（Sharding）：例如一个存了 50 万用户映射的大 Hash，按 user_id % 100 拆成 100 个小 Hash（每个约 5000 项）；
    2. 冷字段剥离与压缩：仅缓存高频使用的核心字段，长文本用 Snappy / Zstd 压缩后再存入；
    3. 安全删除：统一使用 UNLINK key（若在 4.0 以下旧版本，则先通过 HSCAN / SSCAN 小批量删除内部元素，最后再删空壳 Key）。

2. 热 Key（单个 Key 瞬间承受数万至数十万 QPS）

  • 典型场景：全网突发热点新闻、直播间整点秒杀商品配置、全局热门榜单首页。即便部署了 10 节点的 Redis Cluster，同一个 Key 根据哈希槽算法也只会固定落在其中某 1 台分片节点上，导致单机网卡或 CPU 达到上限。
  • 发现手段：业务 SDK 接入层实时滑动窗口计数监控、代理层热点统计、或在开启 LFU 策略的实例上执行 redis-cli --hotkeys。
  • 分流治理方案：
    1. 升级应用进程内二级缓存（首选）：在 Go（如 ristretto / bigcache）或 Java（Caffeine）应用内存中缓存热点键 1 ~ 3 秒，直接由数十台无状态业务机器的内存吸收 95% 以上的读流量，配合 Redis 7.0 Client-Side Caching（客户端跟踪失效广播）或 Pub/Sub 主动通知更新；
    2. 多副本随机后缀打散：将热点键同步复制为 sku:hot:888#1 至 sku:hot:888#N 共 N 份，读取时随机拼接后缀路由到不同集群分片节点。
