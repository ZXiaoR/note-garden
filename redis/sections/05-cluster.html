❓ 05.1 · 第一级「主从复制」：第一次连怎么全量同步？断线重连怎么只补差量？

📡 05.1 第一级：主从复制（replicaof · 数据冗余 + 读写分离）

主从复制分为三阶段：① 握手建连（PING → AUTH → REPLCONF → PSYNC） → ② 首次全量同步（发 RDB 快照 + 缓冲期间写命令） → ③ 持续命令传播与断线增量重连。

① 首次全量同步（从节点发送 psync ? -1）：
• 主库执行 bgsave 生成 RDB 快照发给从库（从库清空旧数据并加载 RDB）；
• 生成 RDB 期间的新写命令，主库先攒进内存「复制缓冲区 replication buffer」，最后发给从库重放；
• ⚠️ 复制风暴避坑：一主挂太多从节点同时全量同步会打爆主库网卡与磁盘，可用「主 ──▶ 从 ──▶ 从」级联树状同步分摊！
② 断线重连（psync replid offset）—— 靠环形缓冲区 repl_backlog_buffer 决定增量或全量：
offset < 200（旧数据已被环形覆盖）
缓冲起点 = 200 从库 offset = 480 主库最新 = 500
• ✅ 情况 A（增量同步）：从库汇报的 offset (480) 仍在环形缓冲区间 [200, 500] 内 → 主库回 +CONTINUE，只补发 481 ~ 500 的差量命令！
• ❌ 情况 B（退化全量）：断线太久，从库的 offset (150) < 200 已被覆盖 → 主库回 +FULLRESYNC，被迫退化为全量同步！（生产建议调大 repl-backlog-size 至 64MB~128MB）
❓ 05.2 · 第二级「哨兵 Sentinel」：主节点挂了，谁来自动选新主并切换？

🚨 05.2 第二级：哨兵 Sentinel（监控 + 自动选主切换 + 通知）

单纯的主从复制不会自动故障转移。哨兵是独立部署的奇数个进程（至少 3 台），专门盯梢主从健康并在主库宕机时自动切主：

故障转移 4 步 核心判定规则与选举算法
① 主观下线 (SDOWN)
→ 客观下线 (ODOWN)		 单个哨兵 PING 超时判为 SDOWN（主观下线）；当认为主库下线的哨兵数达到配置的 quorum（法定人数） 时，达成共识判为 ODOWN（客观下线，仅针对主库）。
② 哨兵选 Leader 哨兵集群内部通过 Raft 算法 投票选出 1 个 Leader 哨兵（需拿到超半数且 ≥ quorum 票），由它主持本次主从切换。
③ 从节点中挑新主
(面试必考顺序)		 剔除断线失联的从节点后，依次按 3 个条件PK：
1. slave-priority 优先级最高（数值越小越优先）
2. 复制偏移量 offset 最大（离主库数据最全最新）
3. runid 最小（字典序最小）
④ 升主与改挂通知 对新主发 replicaof no one，让其余从节点改挂新主，并通过发布订阅通知客户端新主地址；旧主恢复后降级为新主的从库。
🧠 哨兵脑裂（Split-Brain）怎么导致丢数据？怎么防？
成因：主库没死，只是和哨兵之间网络分区了。哨兵选出了新主，此时集群里同时存在两个主库！老客户端继续往旧主写数据，等网络恢复后旧主被强制降级为从库，清空自己去同步新主——脑裂期间写进旧主的数据全部丢失！
防御参数：在主库配置 min-replicas-to-write N + min-replicas-max-lag S（要求主库至少连着 N 个延迟 ≤ S 秒的从库才允许写，否则旧主被孤立后主动拒绝客户端写入）。
❓ 05.3 · 第三级「Cluster 集群」：单机内存装不下、写并发超上限怎么办？为什么是 16384 个槽？

🧩 05.3 第三级：Redis Cluster 分片集群（16384 哈希槽 + Gossip 去中心化）

主从 + 哨兵解决了高可用，但所有数据依然全塞在一台主节点上。当数据量达到几十上百 GB、或者写 QPS 超过单机上限时，必须用 Redis Cluster 做水平分片：把全集划分为固定的 16384 个哈希槽（Hash Slots），由多个主节点各自负责一段槽位，每个主节点再配从节点自带高可用切换。

路由算法：Slot 槽号 = CRC16(key) % 16384
Master A（带从库）
负责槽：0 ~ 5460
Gossip 协议互发心跳
Master B（带从库）
负责槽：5461 ~ 10922
Gossip 协议互发心跳
Master C（带从库）
负责槽：10923 ~ 16383
Gossip 协议互发心跳
• MOVED 重定向：槽已永久归属目标节点，客户端收到后跳转并更新本地槽映射缓存表；
• ASK 重定向：槽正在在线迁移中，仅本次请求临时跳转目标节点（先发 ASKING），不更新本地映射缓存。
❓ 为什么哈希槽设计成 16384（$2^{14}$）个，而不是 CRC16 上限 65536（$2^{16}$）个？
1. 心跳包体积差 4 倍：节点间每秒通过 Gossip 协议互发 PING/PONG 心跳，包头里携带一张表示自己负责哪些槽的 bitmap 位图。16384 位 = 2KB，而 65536 位 = 8KB，频繁广播 8KB 心跳太浪费带宽。
2. 节点规模上限：Redis Cluster 推荐主节点规模不超过 1000 台（再多 Gossip 心跳风暴会恶化），16384 个槽分给 1000 个节点已经足够均匀，且位图越短压缩率越高。
🏷️ 跨槽多 Key 限制与 {Hash Tag} 解法：
Cluster 下执行 MSET 或 Lua 脚本要求所有 Key 必须在同一个槽，否则报错。只需给 Key 加上大括号 user:{1001}:profile 与 user:{1001}:orders，Redis 就只对 {1001} 内部的字符串算 CRC16，强制让同一用户的多个 Key 落入同一个槽！
