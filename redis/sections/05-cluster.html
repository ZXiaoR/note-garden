📡 05.1 三种部署架构的选型边界与主从复制配置

单节点 Redis 一旦宿主机宕机就会造成服务中断，且单机内存容量与网卡带宽存在物理上限。根据业务的数据总体积、写并发规模以及故障自动恢复要求，生产环境共有三种标准部署形态：

主从复制（Replica）快速配置与状态核验

在 Redis 5.0+ 中，旧指令 SLAVEOF 已更名为语义更清晰的 REPLICAOF <masterip> <masterport>。注意主从两端的密码配置是双向对应的：从库需配 masterauth 以连上主库，主库本身也需配相同的 requirepass，否则主从切换后原主库降级为从库时将因缺少认证凭证而同步失败。

⚙️ replica.conf · 从节点核心配置与 INFO replication 核验 
# === 从节点 (10.0.1.12:6379) 配置文件关键项 ===
replicaof 10.0.1.11 6379
masterauth ProdPass_2026
requirepass ProdPass_2026        # 主从保持一致，方便故障转移后角色互换
replica-read-only yes            # 从库强制只读，防止业务误写从库导致主从数据分叉
repl-backlog-size 128mb          # 主库建议调大复制积压缓冲区（默认仅 1MB），减少网络闪断退化全量同步

# === 连接主库或从库核验同步状态 ===
127.0.0.1:6379> INFO replication
# role:slave / master_link_status:up / master_repl_offset:8492011
🚨 05.2 · Sentinel 哨兵运维：3 节点哨兵配置、脑裂防护参数与 Go FailoverClient 接入

🚨 05.2 Sentinel 哨兵高可用配置与自动切换接入

当业务总数据量在 10 ~ 20 GiB 以内（单台主节点足以装下全量数据）时，1 主 2 从 + 3 节点 Sentinel 哨兵是运维复杂度最低、且支持任意多 Key 命令的生产高可用方案。哨兵必须部署为至少 3 个独立进程（奇数台分散在不同物理机/可用区），防止单台哨兵网络抖动产生误判。

⚙️ sentinel.conf · 哨兵配置与主库防脑裂参数 
# === sentinel.conf (每台哨兵端口通常为 26379) ===
port 26379
# 监控名为 mymaster 的主节点，2 代表至少 2 个哨兵判定失联才触发客观下线 (quorum=2)
sentinel monitor mymaster 10.0.1.11 6379 2
sentinel auth-pass mymaster ProdPass_2026
# 连续 5000ms 未响应 PING 则判为主观下线
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000

# === 主节点 redis.conf 补充：缓解网络分区脑裂丢数据 ===
# 要求主库至少连着 1 个同步延迟 ≤ 10 秒的从库才允许接收写请求
min-replicas-to-write 1
min-replicas-max-lag 10
🐹 sentinel_client.go · 客户端自动感知主库切换 
// 业务代码不再写死某台 Redis IP，而是填写逻辑主库名与 3 台哨兵地址
// 主库切换时，SDK 通过订阅哨兵 +switch-master 事件自动重连新主库
rdb := redis.NewFailoverClient(&redis.FailoverOptions{
    MasterName: "mymaster",
    SentinelAddrs: []string{
        "10.0.1.21:26379",
        "10.0.1.22:26379",
        "10.0.1.23:26379",
    },
    Password:     "ProdPass_2026",
    PoolSize:     64,
    RouteByLatency: false, // 默认读写均走当前 Master 保证强一致
})
🧩 05.3 · Cluster 分片实战：3 主 3 从集群创建、智能客户端路由与 {Hash Tag} 多键约束

🧩 05.3 Redis Cluster 分片集群运维与多 Key 编码规范

当业务缓存规模增长到 数十至上百 GiB，或者写并发超出单核处理极限时，应采用原生 Redis Cluster（最小生产拓扑为 3 主 3 从共 6 个实例，无需额外部署 Sentinel，集群节点间通过内部总线端口 数据端口 + 10000 如 16379 自动完成健康探测与故障切主）。集群将整个键空间划分为 0 ~ 16383 共 16384 个哈希槽（Hash Slots），按 CRC16(key) % 16384 将不同 Key 均匀打散到各主节点。

⌨️ cluster_ops.sh · 创建 3 主 3 从集群、状态巡检与 {Hash Tag} 同槽多键操作 
# 1. 每个节点 redis.conf 开启集群模式（同时务必放行防火墙的 6379 数据端口与 16379 集群总线端口）
#    cluster-enabled yes
#    cluster-config-file nodes-6379.conf
#    cluster-node-timeout 15000

# 2. 一键初始化 3 主 3 从集群（--cluster-replicas 1 表示为每个 Master 自动分配 1 个 Replica）
redis-cli -a ProdPass_2026 --cluster create \
  10.0.1.11:6379 10.0.1.12:6379 10.0.1.13:6379 \
  10.0.1.14:6379 10.0.1.15:6379 10.0.1.16:6379 \
  --cluster-replicas 1

# 3. 命令行连接集群务必加 -c 参数（自动跟随 MOVED / ASK 重定向跳转分片）
redis-cli -c -h 10.0.1.11 -p 6379 -a ProdPass_2026
10.0.1.11:6379> CLUSTER INFO
10.0.1.11:6379> CLUSTER NODES

# 4. 集群下的多 Key 约束：直接 MSET 两个不同槽的 Key 会报错 CROSSSLOT Keys in request don't hash to the same slot
#    解法：使用花括号 {Hash Tag}，Redis 仅对第一对非空 {} 内的子串 "u1001" 计算 CRC16，确保同用户多键落入同一分片槽：
10.0.1.11:6379> MSET user:{u1001}:profile "Alice" user:{u1001}:wallet "5000"
⚠️ 使用 {Hash Tag} 防止数据倾斜的注意事项：花括号内必须填写高基数离散标识（如具体的 {user_id} 或 {order_id}），切勿把固定业务大类名写进花括号（例如错误写成 {order}:1001、{order}:1002），否则几百万个订单键会全部落进同一个哈希槽与同一台分片节点，造成严重的单机倾斜。
