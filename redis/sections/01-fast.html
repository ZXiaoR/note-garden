🔑 01.1 · 键空间基础：企业级 Key 命名约定与键生命周期管理通用指令

🔑 01.1 Key 命名规范与通用键操作全景

在学习具体的数据类型之前，首先需要掌握适用于所有数据类型的顶层键（Key）管理规则。Redis 没有关系型数据库中“表（Table）”的强制约束，所有键值共享同一个扁平的键空间，因此规范的 Key 命名是保障可读性、按前缀统计内存以及配置 ACL 权限的基础：

  • 分段冒号命名法：统一采用 业务线:模块名:实体标识[:子属性] 全小写结构，例如 mall:sku:detail:8801 或 auth:sms:code:13800138000。许多可视化工具（如 Redis Insight）会自动按半角冒号 : 折叠成树形目录。
  • 控制 Key 本身字节长度：Key 自身也是常驻内存的字符串对象，当实例存储数千万个键时，冗长的字段名会带来可观的内存开销。在不损失语义的前提下可使用常见缩写（如 usr 代替 user_account_information），单个 Key 长度建议控制在 64 字节以内，且禁止包含空格、换行符等空白字符。
通用指令语法 时间复杂度 返回值规则与工程用途说明
EXISTS key [key ...] O(1) / 键 返回实际存在的 Key 数量（整数）。判断单键存在时返回 1（存在）或 0（不存在）。
TYPE key O(1) 返回该 Key 对外暴露的数据类型：string、hash、list、set、zset、stream 或 none（键不存在）。
EXPIRE key seconds [NX|XX|GT|LT]
PEXPIRE key milliseconds		 O(1) 为已有 Key 设置秒级（EXPIRE）或毫秒级（PEXPIRE）存活时长。Redis 7.0+ 新增条件选项：NX（仅在当前无过期时间时设置）、GT（仅在新过期时间大于原值时延长）。注意：后续若对该 Key 执行不带 TTL 的 SET 覆写，原有的过期时间会被清除。
TTL key / PTTL key O(1) 查询剩余存活秒数或毫秒数。需熟记两个特殊负数返回值：
• 返回 -1：该 Key 存在，但未设置过期时间（永不过期）；
• 返回 -2：该 Key 不存在（从未写入或已到期清理）。
PERSIST key O(1) 移除 Key 上的过期时间，使其转为长期有效（成功移除返回 1，键不存在或原本就无过期时间返回 0）。
DEL key [key ...] O(1) 或 O(M) 在主线程中同步阻塞释放键内存。删除普通 String 为 O(1)；但删除包含 M 个元素的集合（Hash/List/Set/ZSet）为 O(M)。
UNLINK key [key ...] 主线程 O(1) Redis 4.0+ 生产推荐删除方式：主线程仅以 O(1) 将 Key 从全局字典摘除（对客户端立即不可见），若底层对象元素较多，自动移交后台异步线程释放物理内存，避免阻塞主线程。
🔍 01.2 · 安全遍历：为什么禁用 KEYS *，以及游标命令 SCAN 的正确循环用法

🔍 01.2 使用 SCAN 渐进式遍历替代全量扫描 KEYS

由于 Redis 的所有读写命令都在同一个主线程中按顺序串行执行，一旦某条指令耗时过长，排在它后面的所有客户端请求都必须排队等待。KEYS pattern（如 KEYS order:*）会一次性遍历整个数据库的数百万个键，执行期间整个实例无法响应任何其他读写请求。

在线上环境中查找匹配特定前缀的键时，应统一使用 SCAN cursor [MATCH pattern] [COUNT count] [TYPE type] 渐进式游标遍历：每次调用仅扫描一小批哈希桶并立即交还主线程控制权，客户端根据返回的新游标继续下一轮迭代。

SCAN 游标协议的 3 项使用规则

  1. 起止标志均为游标 0：第一次调用传入游标 0 表示开始新一轮遍历；每次响应返回一个包含两项的数组 [下一次游标字符串, 本批匹配的Key列表]；当返回的下一次游标重新变为 "0" 时，代表全库扫描完毕（不能用“本批返回列表为空”来判断结束，因为某几个哈希桶内可能恰好没有符合 MATCH 前缀的键）。
  2. COUNT 是扫描桶数的提示值而非精确返回条数：默认值为 10，表示单次约检查 10 个哈希槽位，再对槽内元素应用 MATCH 过滤，因此单次返回的 Key 数量可能为 0，也可能略多于 COUNT。日常巡检常设为 COUNT 200 ~ 500。
  3. 集合内部也有对应的同族游标命令：遍历大字典用 HSCAN、大无序集合用 SSCAN、大有序集合用 ZSCAN，替代全量拉取的 HGETALL / SMEMBERS。
🐹 scan_unlink.go · 分批扫描过期前缀并异步清理 
func CleanTempKeys(ctx context.Context, rdb *redis.Client) error {
    var cursor uint64 = 0
    for {
        // 每次扫描约 200 个槽位，过滤 temp:export:* 前缀
        keys, nextCursor, err := rdb.Scan(
            ctx, cursor, "temp:export:*", 200,
        ).Result()
        if err != nil {
            return err
        }

        // 使用 Unlink 替代 Del，大对象自动转交后台线程回收
        if len(keys) > 0 {
            if err := rdb.Unlink(ctx, keys...).Err(); err != nil {
                return err
            }
        }

        // 仅当 nextCursor 回到 0 时，才表示完整遍历结束
        cursor = nextCursor
        if cursor == 0 {
            break
        }
    }
    return nil
}
⚡ 01.3 · 吞吐优化与诊断：Pipeline 管道合并网络 RTT 与 SLOWLOG 慢查询定位

⚡ 01.3 使用 Pipeline 降低网络往返开销与慢日志排查

单条 Redis 内存操作在服务端本身的执行耗时往往不到 1 微秒（μs），但同机房一次跨机器 TCP 网络往返（RTT，Round-Trip Time）通常需要 0.3ms ~ 1ms。如果业务代码在一个 for 循环里串行发送 100 条独立命令，绝大部分时间都消耗在了等待 100 次网络往返上。

Pipeline（管道技术）允许客户端将多条无前后依赖的命令一次性写入客户端输出缓冲区打包发送，服务端依次执行完毕后再将所有响应一次性打包读回，把 N 次网络 RTT 压缩为 1 次 RTT，吞吐量通常能提升一个数量级。

🐹 pipeline_demo.go · go-redis 批量管道读写 
// 单批次建议控制在 100 ~ 500 条以内，避免单包过大撑满网卡缓冲
pipe := rdb.Pipeline()
incrCmd := pipe.Incr(ctx, "metrics:pv:20261127")
pipe.Expire(ctx, "metrics:pv:20261127", 48*time.Hour)
getCmd := pipe.Get(ctx, "config:homepage:banner")

// Exec() 触发唯一一次网络收发，将缓冲队列中的命令一并发出
_, err := pipe.Exec(ctx)
if err != nil && !errors.Is(err, redis.Nil) {
    return err
}
fmt.Println("最新 PV:", incrCmd.Val(), "Banner:", getCmd.Val())

日常实例健康巡检与慢查询诊断指令

  • SLOWLOG GET 10：读取最近 10 条执行耗时超过 slowlog-log-slower-than（默认 10000 微秒 = 10ms）的慢命令。注意慢日志统计的仅是服务端内存命令本身的执行耗时，不含网络传输与排队时间，高并发缓存实例建议将该阈值调严至 1000 ~ 2000（1~2ms）。
  • INFO memory / INFO stats：查看当前实际内存占用（used_memory_human）、内存碎片率（mem_fragmentation_ratio，正常区间为 1.0 ~ 1.5）以及每秒实时 QPS（instantaneous_ops_per_sec）。
  • 谨慎使用 MONITOR：MONITOR 会实时回显实例收到的每一条指令，在高并发线上实例开启会使吞吐量明显下降，仅限短时间故障抓包并及时断开。
