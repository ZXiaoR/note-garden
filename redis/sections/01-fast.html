❓ 01.1 · 单核单线程为什么能扛住每秒 10 万+ QPS？

⚡ 01.1 Redis 为什么快 —— 支撑性能的四条腿

几乎是开场必问。把原因串成一条因果链：① 纯内存操作 + ② 单线程避免上下文切换与锁竞争 + ③ IO 多路复用（epoll）的 Reactor 网络模型 + ④ 针对数据规模高度优化的底层数据结构。

核心支柱 底层机制与数量级对比
① 纯内存操作 所有数据驻留内存，一次读写就是一次内存寻址（~100ns）。对比机械磁盘随机 IO（~10ms），天然快几个数量级，这是“快”的根本前提。
② 单线程执行命令 命令一个接一个串行执行：不需要为共享数据加锁、没有多线程上下文切换开销，也没有死锁/竞态等并发 Bug。
③ IO 多路复用 单线程却能同时服务数万连接，靠的是内核 epoll：把成千上万个 Socket 注册给内核，一有就绪事件才通知，线程只处理“真正有数据”的连接，绝不为空闲连接空转。
④ 高效数据结构 同一种对外类型，底层按数据规模自动选最省内存或最快的结构（如 String 的 int/embstr/raw、ZSet 的 listpack/skiplist），让命令贴着最优复杂度跑。
💡 核心认知：Redis 的性能瓶颈从来在内存容量与网络 IO，而不在 CPU——单核每秒就能跑十万级内存指令，所以命令执行用“单线程”不但不拖后腿，反而省掉了多线程加锁的一切麻烦。

❓ 01.2 · Redis 6.0 引入了多线程，那它还是单线程吗？

🧵 01.2 线程模型演进：只并行“脏活与网络 IO”，绝不并行“执行命令”

这里要讲清一个高频误区：Redis 的“单线程”指的是命令的执行始终在一个主线程里串行完成，并不是整个进程只有一个线程！持久化（fork 子进程）、异步删除（4.0 bio 线程）和网络读写（6.0 IO 线程）早就交给了其他线程分担：

版本 多线程 / 异步化了什么？ 命令执行阶段
4.0 引入后台线程（bio）：把耗时的“大对象删除”等脏活异步化——如 UNLINK（异步删除大 Key）、FLUSHDB ASYNC、AOF fsync 刷盘、关闭文件等，避免删一个几 GB 的大 Key 把主线程卡死。 仍单线程串行
6.0+ 引入多线程 IO（IO Threads）：多个 IO 线程并行负责 Socket 数据的读取/写回 + 协议解析。因为随着网卡带宽和并发变大，网络 IO 读写成了真正的瓶颈。 仍单线程串行 ✅
① 读 Socket + 解析协议
IO Thread 1（并行读）
IO Thread 2（并行读）
IO Thread 3（并行读）
② 执行内存命令
主线程单线程串行执行
✅ 免加锁 · 零竞态冲突
顺序操作内存 dict / skiplist
③ 写回结果到 Socket
IO Thread 1（并行写）
IO Thread 2（并行写）
IO Thread 3（并行写）
🎯 结论：只有阶段 ① 和 ③（读写网络 Socket）是多线程并行，阶段 ②（执行命令操作内存）始终单线程！
⚙️ 生产配置细节：io-threads 默认为 1（即默认关闭多线程 IO），需手动开启（官方建议 4 核以上机器再开）；且默认只多线程化写回响应，若要连读取+解析请求也开启多线程，需额外配置 io-threads-do-reads yes。
❓ 高频追问：既然多线程能提速，为什么阶段 ② 执行命令不做成多线程？

一旦多线程并发执行命令，就必须对底层的共享哈希表、跳表、列表加锁。锁粒度很难把控：粗粒度锁会退化成串行，细粒度锁又极其复杂、容易引入死锁与并发 Bug，还要付出上下文切换开销。而 Redis 的瓶颈本就在网络 IO 而非 CPU 执行，所以选择“网络 IO 并行、命令执行串行”——既吃到了多核分担网络读写的红利，又保住了单线程无锁的极致简单与线程安全。
