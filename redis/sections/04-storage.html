对比维度 📸 RDB（内存二进制快照） 📜 AOF（追加写命令日志）

❓ 为什么 Redis AOF 是“先执行命令、再写日志”，跟 MySQL WAL 正好相反？

① 免去额外的语法与类型检查开销：只有真正执行成功的命令才写入 AOF，不会把错误命令记进日志；② 不阻塞当前命令的执行。代价是：如果刚执行完内存操作还没刷盘就断电会丢这 1 秒数据，且写 AOF 缓冲区在主线程，若磁盘 IO 极度繁忙可能会拖慢下一条命令。

❓ 04.2 · 设了过期时间的 Key 到期怎么删？内存满了又怎么淘汰？

🧹 04.2 过期删除策略（惰性删除 + 定期抽样删除）

为什么不用“每个 Key 配一个定时器到点立刻删（定时删除）”？因为单线程下几百万个定时器会吃光 CPU！所以 Redis 采用 惰性删除 + 定期删除 组合拳：

  • ① 惰性删除（Lazy Expire）：不主动删，只有客户端访问到某 Key 时才检查过期字典（expires dict），若已过期则当场删掉返回空。对 CPU 最友好，但“过期后永远没人访问的冷 Key”会赖在内存里。
  • ② 定期删除（Active Expire）：每秒执行约 10 次（hz 配置）：每次从过期字典里随机抽样 20 个 Key，删掉其中过期的；若本轮过期比例超过 25%，立刻再抽 20 个循环清理（带耗时上限防卡顿主线程）。
⚠️ 主从复制下的过期铁律：从节点（Replica）绝不会自己主动物理删除过期 Key！哪怕从节点发现某 Key 已过期，读请求虽然返回空，但物理删除必须等主节点删完后向从节点发送一条明确的 DEL / UNLINK 指令才删，以此保证主从数据绝对一致。

🗑️ 内存淘汰策略（当内存达到 maxmemory 上限时）

过期删除管的是“到期的 Key”；而当内存真正涨满达到 maxmemory 时，必须触发内存淘汰策略（共 8 种 = 2 种范围 × 4 种算法 + 1 种不淘汰）为新写入腾空间：

外加第 8 种默认策略 noeviction：不淘汰任何 Key，内存满后所有写命令直接报错（OOM），仅读和删除可用。

🔍 为什么 Redis 用“近似 LRU / LFU”而不是维护全局双向链表？
维护几千万 Key 的真实双向链表，每次访问都要移动指针，内存和 CPU 开销太大。Redis 直接复用每个 redisObject 头里的 24-bit lru 字段（LRU 模式下存最后访问时间戳；LFU 模式下高 16 位存衰减分钟时间戳、低 8 位存对数访问频次），淘汰时随机抽样 5 个 Key（maxmemory-samples 5）放进候选池驱逐最冷的那个——用极小代价逼近真实 LRU/LFU！
