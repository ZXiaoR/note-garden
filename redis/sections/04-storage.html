💾 04.1 · 持久化选型与配置：RDB 快照、AOF 追加日志与 4.0+/7.0 混合持久化规范

💾 04.1 三种持久化形态的权衡与生产配置模板

由于 DRAM 内存属于易失性存储介质，进程重启或宿主机断电后内存数据即会清空。当业务不仅把 Redis 当作随时可丢的临时缓存，还存放了购物车、排行榜、分布式限流计数或异步消息队列时，需要合理开启磁盘持久化机制。Redis 提供了全量快照（RDB）、追加写命令日志（AOF）以及结合两者优势的混合持久化（RDB Preamble）：

对比维度 RDB（二进制内存快照） AOF（追加写命令日志） 混合持久化（4.0+ / 7.0 默认推荐）
落盘内容与文件 某一时间点全库内存数据的紧凑二进制快照（dump.rdb） 按执行先后顺序追加记录每一条修改过数据的写指令文本 重写生成基准 RDB 二进制全量头 + 后续实时增量 AOF 指令流
异常宕机最大丢失 丢失距上一次快照以来（通常 5~15 分钟）的所有新增修改 默认 appendfsync everysec 每秒刷盘一次，最多丢失 1 秒写数据 继承 AOF 的刷盘粒度，默认最多丢失 1 秒写数据
磁盘体积与恢复速度 文件体积最小，重启直接按二进制结构加载进内存，恢复最快 文本日志体积较大，重启需模拟客户端逐条重放全部历史写命令，恢复较慢 重启先快速加载基准 RDB，再重放少量尾部增量 AOF，兼顾快恢复与低丢失
适用业务定位 允许分钟级丢失的纯缓存冷备、跨机房定时灾备归档与主从首次全量同步 需要严格保留可读操作审计命令流的传统部署场景 绝大多数线上有状态 Redis 实例的标准首选配置
⚙️ redis.conf · Redis 7.x 混合持久化推荐生产配置 
# 1. RDB 自动触发规则：3600秒≥1次修改 / 300秒≥100次 / 60秒≥10000次
#    注意：手动快照务必使用后台异步 BGSAVE，禁止在线上执行同步阻塞的 SAVE
save 3600 1 300 100 60 10000
dbfilename dump.rdb
dir /data/redis

# 2. 开启 AOF 并启用混合持久化（Redis 7.0 默认已设为 yes）
appendonly yes
aof-use-rdb-preamble yes

# 3. 刷盘频率：everysec 由后台线程每秒调用 fsync，平衡吞吐与 1 秒级安全边界
appendfsync everysec

# 4. AOF 自动重写瘦身条件：体积超过 64MB 且比上次重写后增长满 100% 时触发 BGREWRITEAOF
auto-aof-rewrite-min-size 64mb
auto-aof-rewrite-percentage 100
# 重写期间暂缓主线程 fsync 竞争磁盘 I/O（高写入负载实例常设为 yes，极端情况最多多丢数秒）
no-appendfsync-on-rewrite no

Redis 7.0 Multi-Part AOF 目录与故障修复流程

从 Redis 7.0 开始，AOF 不再是单一的 appendonly.aof 文件，而是统一存放在 appendonlydir/ 子目录中，由三类文件协同管理：

  • 基准文件（*.base.rdb）：执行 BGREWRITEAOF 时生成的时刻快照基准；
  • 增量文件（*.incr.aof）：持续追加后续实时写命令的增量日志；
  • 清单文件（appendonly.aof.manifest）：记录当前生效的 base 与 incr 文件序号。

启动加载与损坏修复规则：只要配置了 appendonly yes，实例重启时优先加载 AOF 清单（因 AOF 数据比定时 RDB 更新）；若宿主机意外掉电导致增量 AOF 末尾出现半截未写完的命令从而拒绝启动，可先备份原目录，再执行官方校验修复命令截断尾部残缺指令： 

redis-check-aof --fix /data/redis/appendonlydir/appendonly.aof.manifest

🗑️ 04.2 内存容量水位规划与 maxmemory-policy 选型

日常运维中需明确区分两组概念：过期删除处理的是“已经到达 TTL 到期时间的键”（Redis 自动通过访问时检查与后台定时抽样清理）；而内存淘汰（Eviction）处理的是“实例已用内存涨满触及 maxmemory 上限，但新写请求仍在持续涌入”的场景。

8 种 maxmemory-policy 内存淘汰策略选型对照表

Redis 的 8 种淘汰策略可以按「候选键范围（allkeys-* 全量键 vs volatile-* 仅设了过期时间的键）」×「驱逐算法（LRU / LFU / Random / TTL）」外加默认不淘汰策略 noeviction 清晰归类：

候选范围 ＼ 算法 LRU（按最近访问时间） LFU（按历史访问频次 4.0+） Random（随机） TTL（按剩余寿命）
allkeys-*
所有键均参与淘汰		 allkeys-lru
通用纯缓存实例常用		 allkeys-lfu
存在突发扫描污染时优选，保留高频热键		 allkeys-random —
volatile-*
仅淘汰设了 TTL 的键		 volatile-lru
同实例混存持久配置(不设TTL)与临时缓存时使用		 volatile-lfu volatile-random volatile-ttl
优先驱逐最快到期的键

第 8 种默认策略 noeviction：不驱逐任何已有数据，当内存达到 maxmemory 后，所有申请额外内存的写命令（如 SET / LPUSH / XADD）直接返回 OOM command not allowed when used memory > 'maxmemory' 错误，仅允许执行 GET / DEL / UNLINK。适合将 Redis 作为绝对不允许静默丢数据的分布式锁、消息队列或状态存储时开启。
