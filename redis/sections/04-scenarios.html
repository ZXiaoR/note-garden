04.1 登录态 / Token（活跃自动续期 + 强制踢下线）

  • 需求：用户登录后生成随机 Token，7 天内免重新登录，期间只要有活跃请求就自动顺延有效期；用户修改密码或后台封禁账号时，能立刻让该用户所有已登录设备的旧 Token 失效。
  • 为什么选这个方案：纯无状态 JWT（JSON Web Token，JSON 网络令牌）一旦签发，在过期前服务端无法主动废止；用 Redis String 存 auth:tk:<token> -> userID，再用一个 Set 存 auth:user_tks:<userID> 记录该用户名下所有活跃 Token，既能亚毫秒级鉴权，又能按人一键清空踢下线。
⌨️ session_token.redis · 登录、鉴权续期与踢下线 [Redis 6.x / 7.x] 
# 1. 登录成功：存 Token 映射（7天=604800秒），并记入该用户的设备集合
SET auth:tk:9f8a7b6c "1001" EX 604800
SADD auth:user_tks:1001 "9f8a7b6c"
EXPIRE auth:user_tks:1001 604800

# 2. 接口鉴权与续期：续期 Token 时同步续期该用户的设备集合（6.2+ 单键可用 GETEX）
GET auth:tk:9f8a7b6c
EXPIRE auth:tk:9f8a7b6c 604800
EXPIRE auth:user_tks:1001 604800

# 3. 单设备主动退出登录：删当前 Token 并从设备集合移除
DEL auth:tk:9f8a7b6c
SREM auth:user_tks:1001 "9f8a7b6c"

# 4. 改密或封号全局踢下线：查出该用户全部活跃 Token 一次性删掉
SMEMBERS auth:user_tks:1001
DEL auth:tk:9f8a7b6c auth:user_tks:1001

const sessionTTL = 7 * 24 * time.Hour

// VerifyAndRenew 校验 Token，剩余寿命不足一半时同步续期 Token 与用户的设备 Set
func VerifyAndRenew(ctx context.Context, rdb *redis.Client, tk string) (string, error) {
    key := "auth:tk:" + tk
    pipe := rdb.Pipeline()
    uidCmd := pipe.Get(ctx, key)
    ttlCmd := pipe.TTL(ctx, key)
    _, _ = pipe.Exec(ctx)

    uid, err := uidCmd.Result()
    if err != nil {
        return "", ErrUnauthorized
    }
    if ttlCmd.Val() > 0 && ttlCmd.Val() < sessionTTL/2 {
        renewPipe := rdb.Pipeline()
        renewPipe.Expire(ctx, key, sessionTTL)
        renewPipe.Expire(ctx, "auth:user_tks:"+uid, sessionTTL)
        _, _ = renewPipe.Exec(ctx)
    }
    return uid, nil
}

// LogoutDevice 单端主动登出：删除当前 Token 并从用户设备集合移除
func LogoutDevice(ctx context.Context, rdb *redis.Client, uid, tk string) error {
    pipe := rdb.Pipeline()
    pipe.Del(ctx, "auth:tk:"+tk)
    pipe.SRem(ctx, "auth:user_tks:"+uid, tk)
    _, err := pipe.Exec(ctx)
    return err
}

// KickUserAllDevices 强制将该用户所有已登录端踢下线
func KickUserAllDevices(ctx context.Context, rdb *redis.Client, uid string) error {
    setKey := "auth:user_tks:" + uid
    tks, err := rdb.SMembers(ctx, setKey).Result()
    if err != nil {
        return err
    }
    keys := []string{setKey}
    for _, tk := range tks {
        keys = append(keys, "auth:tk:"+tk)
    }
    return rdb.Unlink(ctx, keys...).Err()
}

⚠️ 常见坑：① 不要每次只读请求都无脑刷 EXPIRE（会产生大量主从同步流量），剩余寿命小于一半（如剩不到 3.5 天）再续期即可；② 续期单个 Token 时务必在同一个 Pipeline 里同步 EXPIRE 该用户的 auth:user_tks:<uid> 集合（主动登出时 SREM 清理），否则用户持续活跃超过 7 天后，Token 还在但外层设备集合已过期消失，改密踢下线时就会漏掉这些旧 Token。 ｜ 💡 背后的原理：过期字典指针共享与自动清理机制见 《📘 原理篇 · 00.2》。

04.2 短信验证码（5 分钟存码 + 60 秒防重发 + 每日上限）

  • 需求：发送 6 位数字验证码（5 分钟内有效，验证成功立即销毁防二次使用）；限制同一手机号 60 秒内只能点一次发送，且单日最多发 10 条防短信盗刷。
  • 为什么选这个方案：三个带自动过期的 String 键即可覆盖「冷却锁 + 日计数 + 存码」，到期自动清理不留垃圾数据。
⌨️ sms_code.redis · 冷却锁、日限额与一次性核销 [Redis 7.0+] 
# 1. 抢 60 秒发送冷却锁（返回 nil 说明 60 秒内刚发过，直接拦截）
SET sms:cd:13800138000 "1" NX EX 60

# 2. 累加当日发送次数（EXPIRE ... NX 为 7.0+ 语法；6.x 写法：INCR 返回 1 时再调 EXPIRE）
INCR sms:day:20261128:13800138000
EXPIRE sms:day:20261128:13800138000 86400 NX

# 3. 存入 6 位验证码，5 分钟（300 秒）过期
SET sms:code:13800138000 "482910" EX 300

# 4. 校验并原子销毁（Redis 6.2+ GETDEL 读出后立即删除；6.0 可校验通过后 DEL）
GETDEL sms:code:13800138000
🐹 sms_verify.go · 发送频控与防暴力枚举校验 [Go · go-redis/v9] 
func SendSMS(ctx context.Context, rdb *redis.Client, phone, code string) error {
    // 1. 60 秒冷却校验
    ok, err := rdb.SetNX(ctx, "sms:cd:"+phone, "1", 60*time.Second).Result()
    if err != nil || !ok {
        return errors.New("请求过于频繁，请 60 秒后再试")
    }
    // 2. 当日上限校验（≤ 10 次）
    dayKey := fmt.Sprintf("sms:day:%s:%s", time.Now().Format("20060102"), phone)
    cnt, _ := rdb.Incr(ctx, dayKey).Result()
    if cnt == 1 {
        _ = rdb.Expire(ctx, dayKey, 24*time.Hour).Err()
    }
    if cnt > 10 {
        return errors.New("今日验证码发送次数已达上限")
    }
    // 3. 保存验证码并重置错误计数
    _ = rdb.Del(ctx, "sms:err:"+phone).Err()
    return rdb.Set(ctx, "sms:code:"+phone, code, 5*time.Minute).Err()
}

⚠️ 常见坑：① 验证通过后必须立刻删码，防止同一验证码在 5 分钟内被重放；② 校验失败时建议对 sms:err:<phone> 调 INCR，连续输错 5 次直接删掉原验证码强制重发，防止脚本暴力穷举 6 位数字。 ｜ 💡 背后的原理：单线程原子执行条件写入见 《📘 原理篇 · 01.1》。

04.3 防重复提交 / 接口幂等（SET NX EX）

  • 需求：用户在提交订单或发起提现页面因网络卡顿连点三次按钮，或者网关超时自动重试，后端需要保证同一个幂等令牌只真正执行一次下单逻辑。
  • 为什么选这个方案：前端打开确认页时向后端申请（或本地生成 UUID）一个唯一 Idempotency-Key 放在请求头里；后端收到请求先调 SET idem:order:<key> "1" NX EX 300，只有第一个到达的请求能写成功返回 true。
⌨️ idempotent.redis · 一行原子抢占防重键 [Redis 6.x / 7.x] 
# 第 1 次请求到达：键不存在，写入成功返回 OK -> 放行去创建订单
SET idem:order:req_88201 "PROCESSING" NX EX 300

# 10 毫秒后连点的第 2 次请求到达：键已存在，返回 (nil) -> 直接提示「请勿重复提交」
SET idem:order:req_88201 "PROCESSING" NX EX 300
🐹 idempotent.go · 下单防重包装（报错回退锁允许重试）[Go · go-redis/v9] 
func SubmitOrderOnce(ctx context.Context, rdb *redis.Client, idemToken string, createFn func() (string, error)) (string, error) {
    key := "idem:order:" + idemToken
    ok, err := rdb.SetNX(ctx, key, "PROCESSING", 5*time.Minute).Result()
    if err != nil {
        return "", err
    }
    if !ok {
        return "", errors.New("订单正在处理或已提交，请勿重复点击")
    }

    orderNo, bizErr := createFn()
    if bizErr != nil {
        // 关键细节：下游落库明确失败时删掉防重键，允许用户修复问题后重新提交
        _ = rdb.Del(ctx, key).Err()
        return "", bizErr
    }
    return orderNo, nil
}

⚠️ 常见坑：① 如果后续写 MySQL 明确报错回滚了，记得删掉幂等键允许用户正常重试；② Redis 防重挡的是 99.9% 的并发连点，数据库订单表仍应给业务单号建唯一索引（UNIQUE KEY）做最终兜底。 ｜ 💡 背后的原理：单线程 Reactor 串行保证无竞态见 《📘 原理篇 · 01.1》。

04.4 高并发计数器（INCR / HINCRBY + 定时无损回写数据库）

  • 需求：帖子阅读量、文章点赞数每秒几万次增加，不能每次浏览都直接 UPDATE posts SET views = views + 1 锁数据库行；改为在 Redis 实时累加增量，后台每分钟批量刷回 MySQL。
  • 为什么选这个方案：用一个 Hash（post:views:delta）存各帖子的待落盘增量，配合一个 Set（post:views:dirty）记录本轮有哪些帖子被看过，定时任务只需扫变脏的那几百个帖子增量落库，并用负向 HINCRBY -delta 扣减已落盘数，绝不漏计刷盘瞬间新进来的阅读。
⌨️ counter_flush.redis · 内存记增量与安全扣减已落盘值 [Redis 6.x / 7.x] 
# 1. 用户每次点开帖子 5001：增量 +1，并把 5001 记入待刷盘脏集合
HINCRBY post:views:delta 5001 1
SADD post:views:dirty 5001

# 2. 定时任务刷盘：弹出脏 ID，读出当前累计增量（假设读出 120）
SPOP post:views:dirty 50
HGET post:views:delta 5001

# 3. 执行 SQL: UPDATE posts SET views = views + 120 WHERE id = 5001 成功后，扣掉这 120
HINCRBY post:views:delta 5001 -120

func AddPostView(ctx context.Context, rdb *redis.Client, postID string) {
    pipe := rdb.Pipeline()
    pipe.HIncrBy(ctx, "post:views:delta", postID, 1)
    pipe.SAdd(ctx, "post:views:dirty", postID)
    _, _ = pipe.Exec(ctx)
}

func FlushViewsBatch(ctx context.Context, rdb *redis.Client) error {
    ids, err := rdb.SPopN(ctx, "post:views:dirty", 100).Result()
    if err != nil || len(ids) == 0 {
        return err
    }
    for _, id := range ids {
        delta, _ := rdb.HGet(ctx, "post:views:delta", id).Int64()
        if delta <= 0 {
            continue
        }
        if err := addViewsInMySQL(ctx, id, delta); err == nil {
            // 扣减已落盘的 delta，保留刷盘期间新进来的阅读增量
            _ = rdb.HIncrBy(ctx, "post:views:delta", id, -delta).Err()
        } else {
            _ = rdb.SAdd(ctx, "post:views:dirty", id).Err() // 失败放回下轮重试
        }
    }
    return nil
}

⚠️ 常见坑：刷盘时切忌直接 HDEL 把字段删掉，否则读取到删掉这几毫秒内新产生的阅读量就凭空消失了；用 HINCRBY -delta 差额扣减才是并发安全的。 ｜ 💡 背后的原理：小 Hash 的紧凑编码与扩容原理见 《📘 原理篇 · 02.2 / 02.3》。

04.5 接口限流：固定窗口 → 滑动窗口（ZSet）→ 令牌桶（Lua）

  • 需求：限制每个用户或 IP 访问发帖/搜索接口的频率（如每分钟最多 10 次），超过后返回 429 Too Many Requests。
  • 三种方案怎么选（看清各自的优缺点）：
限流方案 Redis 实现方式 优点 核心缺点（面试与线上高频考点）
① 固定窗口 按分钟拼键名 rl:u1:1105，执行 INCR + EXPIRE 60 命令最简单，每个用户只占 1 个整数 String 窗口交界处双倍流量突刺：用户在 00:59 连发 10 次，又在 01:00 连发 10 次，实际 2 秒内放过了 20 次请求。
② 滑动窗口 ZSet 以请求毫秒时间戳为 score，每次删掉 60 秒前旧元素再数 ZCARD 任意连续 60 秒严格不超限，彻底消除边界突刺 每个放行的请求都要在 ZSet 存一条记录，若限额很大（如每分钟允许 5 万次）会占用较多内存。
③ 令牌桶 Hash 只存 {剩余令牌数, 上次补充时间}，用 Lua 按时间差惰性算新令牌并扣减 省内存（固定 2 个字段）+ 速率平滑，还能精细控制突发容量 实现相对复杂一点，需要维护一段十来行的 Lua 原子脚本。
🐹 sliding_window.go · 滑动窗口限流（ZSet + Lua）[Redis 6.x / 7.x] 
// 适合中小配额精准限流（如每分钟最多 10 次）：先清理窗口外旧记录，未超限才写入本次请求
var slidingLua = redis.NewScript(`
local key = KEYS[1]
local now_ms = tonumber(ARGV[1])
local window_ms = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local req_id = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now_ms - window_ms)
if redis.call('ZCARD', key) >= limit then
    return 0
end
redis.call('ZADD', key, now_ms, req_id)
redis.call('PEXPIRE', key, window_ms)
return 1
`)

func AllowSlidingWindow(ctx context.Context, rdb *redis.Client, uid string, limit int) (bool, error) {
    now := time.Now().UnixMilli()
    reqID := fmt.Sprintf("%d-%d", now, rand.IntN(100000))
    res, err := slidingLua.Run(ctx, rdb, []string{"rl:sw:" + uid}, now, 60000, limit, reqID).Int()
    return res == 1, err
}
🐹 token_bucket.go · 令牌桶限流（Hash + Lua 服务端时钟）[Redis 6.x / 7.x] 
// 适合高并发大配额网关限流：直接用 Redis TIME 获取统一时钟，不怕多台业务机时间不准
var tokenBucketLua = redis.NewScript(`
local key = KEYS[1]
local capacity = tonumber(ARGV[1]) -- 桶最大令牌数
local rate = tonumber(ARGV[2])     -- 每秒生成令牌数
local t = redis.call('TIME')
local now_ms = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local data = redis.call('HMGET', key, 'tokens', 'last_ms')
local tokens = tonumber(data[1]) or capacity
local last_ms = tonumber(data[2]) or now_ms

local delta = math.max(0, now_ms - last_ms) / 1000.0 * rate
tokens = math.min(capacity, tokens + delta)
if tokens < 1 then
    return 0
end
redis.call('HSET', key, 'tokens', tokens - 1, 'last_ms', now_ms)
redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
return 1
`)

⚠️ 常见坑：写滑动窗口时一定要先判断 ZCARD < limit 再 ZADD！如果先把每次请求都塞进 ZSet 再判断超限，恶意刷接口的人每秒发 1 万次请求会把你的 ZSet 塞爆并且无限续期。 ｜ 💡 背后的原理：Lua 单线程原子执行机制见 《📘 原理篇 · 06.2》。

04.6 实时排行榜：前 N 名列表与「我的排名」（含同分先后处理）

  • 需求：活动积分榜实时更新，页面上半部分展示全站前 10 名及分数，底部悬浮条展示「我当前排第几名、差上一名多少分」，且积分相同时先达到该分数的人排在前面。
  • 为什么选这个方案：ZSet 的加分、取 Top N 和查单人排名全部是 O(log N)；为了解决“同分按先后排序”且避开小数浮点舍入误差，把分数设计成纯整数拼接 score = 积分 × 1010 + (1010 - 秒级时间戳)，越早拿到该积分的人低 10 位越大，倒序时自然排在前面，读取真实积分时执行 floor(score / 1010) 即可。
⌨️ leaderboard.redis · Top 10 与查询个人名次 [Redis 6.2+ / 7.x] 
# 1. 更新玩家积分（纯整数拼接 500分 × 10^10 + 反向秒数；无需同分决胜时直接用 ZINCRBY）
ZADD rank:act 5008267240000 "u_1001" 5008267239950 "u_1002"

# 2. 查询榜单前 10 名（下标 0 到 9，REV 表示从高分到低分，6.0 旧版用 ZREVRANGE）
ZRANGE rank:act 0 9 REV WITHSCORES

# 3. 查询 u_1001 的倒序名次（返回 0 代表第 1 名）和当前拼接分值
ZREVRANK rank:act "u_1001"
ZSCORE rank:act "u_1001"
🐹 leaderboard.go · 纯整数拼接同分决胜与一次拉取榜单+我的名次 [Go · go-redis/v9] 
const timeScale int64 = 10_000_000_000 // 10^10 秒级基准

// CalcTieBreakScore 纯整数拼接分值（2^53 ≈ 9×10^15 内精确无损，适用原始积分 ≤ 90 万）
func CalcTieBreakScore(points int64, nowSec int64) float64 {
    return float64(points*timeScale + (timeScale - nowSec))
}

func GetTop10AndMyRank(ctx context.Context, rdb *redis.Client, key, myUID string) ([]redis.Z, int64, int64, error) {
    pipe := rdb.Pipeline()
    topCmd := pipe.ZRangeArgsWithScores(ctx, redis.ZRangeArgs{Key: key, Start: 0, Stop: 9, Rev: true})
    rankCmd := pipe.ZRevRank(ctx, key, myUID)
    scoreCmd := pipe.ZScore(ctx, key, myUID)
    _, _ = pipe.Exec(ctx)

    myRank := int64(-1) // -1 表示尚未上榜
    if r, err := rankCmd.Result(); err == nil {
        myRank = r + 1 // 转为从 1 开始的自然名次
    }
    myPoints := int64(math.Floor(scoreCmd.Val() / float64(timeScale)))
    return topCmd.Val(), myRank, myPoints, nil
}

⚠️ 常见坑：① ZREVRANK 从 0 起算，返回给前端前记得 + 1，且用户未上榜时会返回 redis.Nil；② ZSet 的 score 是 IEEE 754 双精度浮点数，能精确表示无损整数的上限是 253（约 9 × 1015）——按 × 1010 拼 10 位秒级时间戳时，原始积分精确上限约为 90 万（若改用活动开始后的相对秒数 × 107，积分上限即可扩至约 9000 万 × 10 = 9 亿）。 ｜ 💡 背后的原理：跳表如何靠 span 跨度瞬间算出第几名，见 《📘 原理篇 · 02.3 跳表 zskiplist》。

04.7 延迟任务：订单 30 分钟未支付自动取消

  • 需求：用户下单后若 30 分钟内未完成支付，自动关闭订单并归还库存；若期间支付成功则取消该定时任务。
  • 为什么选这个方案：把订单号放进 ZSet，score 设为「下单时间 + 1800 秒」的到期时间戳；后台轮询协程用一段极短的 Lua 脚本原子捞出已到期（score <= 当前时间）的订单并从集合移除，多台业务机同时跑也不会抢到同一笔订单。

    redis.call('ZREM', KEYS[1], unpack(items))
end
return items
`)

⚠️ 两个极高频踩坑点：
1. 千万别用 Redis「键过期事件监听（Keyspace Notifications）」来做订单取消！因为它的通知本质是发后即忘的广播，你的服务重启或网络闪断那几秒过期的订单通知会直接永久丢失，而且键多时抽样过期会有数分钟延迟。
2. 弹出订单后如果业务进程刚要调数据库就崩了，这笔订单已不在 ZSet 里——所以生产环境必须配一个每 10 分钟跑一次的低频数据库兜底扫描任务（扫超过 35 分钟仍未支付的漏网之鱼），或者在订单量很大时直接用 RocketMQ 定时消息 / RabbitMQ 死信队列。

04.8 分布式锁：跨机器互斥的 4 项安全准则

  • 需求：部署了 5 台订单服务实例，要求「同一笔订单的退款操作」或「每日凌晨对账定时任务」同一时刻全局只能有 1 台机器在执行。
  • 为什么选这个方案（4 项缺一不可的规范）：单机锁（如 Go sync.Mutex）管不了别的服务器；用 Redis 实现安全锁必须同时满足：① 加锁和设过期时间一步原子完成（SET key token NX PX 30000，防加完锁断电变死锁）；② Value 必须存当前协程独有的随机 UUID（防自己超时后把别人刚拿到的锁误删掉）；③ 解锁用 Lua 脚本原子完成「比对 Value + 删除」；④ 耗时不固定时启动后台看门狗（Watchdog）协程自动续期。

var (
    unlockLua = redis.NewScript(`if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end`)
    renewLua  = redis.NewScript(`if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('PEXPIRE',KEYS[1],ARGV[2]) else return 0 end`)
)

func WithDistLock(ctx context.Context, rdb *redis.Client, key string, ttl time.Duration, fn func(context.Context) error) error {
    token := uuid.NewString()
    ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil || !ok {
        return errors.New("资源正在处理中，请稍后重试")
    }

    bizCtx, cancelBiz := context.WithCancel(ctx)
    stopWatchdog := make(chan struct{})
    go func() {
        ticker := time.NewTicker(ttl / 3)
        defer ticker.Stop()
        for {
            select {
            case <-ticker.C:
                res, err := renewLua.Run(context.Background(), rdb, []string{key}, token, ttl.Milliseconds()).Int()
                if err != nil || res == 0 {
                    cancelBiz() // 续期失败或返回 0（锁已丢失），主动取消业务 Context
                    return
                }
            case <-stopWatchdog:
                return
            }
        }
    }()

    defer func() {
        close(stopWatchdog)
        cancelBiz()
        _, _ = unlockLua.Run(context.Background(), rdb, []string{key}, token).Result()
    }()
    return fn(bizCtx)
}

⚠️ 常见坑：① 绝不能在业务代码里分两步写 if rdb.Get() == token { rdb.Del() }——刚比对完若卡顿 10ms 锁过期易主，下一行 Del() 照样误删别人的锁；② 看门狗续期返回 0 说明锁已经丢了，不能静默忽略，应立即调用 cancelBiz() 通知业务协程停止执行；③ 在主从切主或进程长停顿下，就算取消了 Context 也拦不住已经发在半路上的旧写请求，对资金/库存等强一致写入还需配合下游存储的单调递增版本号或栅栏令牌校验。 ｜ 💡 背后的原理：主从丢锁、Redlock 争议与 Fencing Token 栅栏校验见 《📘 原理篇 · 06.1 Fencing Token》。

04.9 消息队列：从 List 到 Stream 消费组，以及何时该换 Kafka / RabbitMQ

  • 需求：用户注册或支付成功后，异步解耦触发「发新人优惠券 + 发欢迎邮件」，要求支持多台机器分摊消费，且消费者处理中途崩溃不会丢任务。
  • 为什么从 List 演进到 Stream：List (LPUSH + BRPOP) 一旦弹出元素就从 Redis 消失了，消费者没跑完重启就丢消息，且一条消息只能被一个业务拿走（没法让发券服务和邮件服务各自独立消费一份）；Redis 5.0+ 的 Stream 补齐了多消费者组独立广播、组内竞争分摊、PEL（Pending Entries List，已投递待确认列表）+ XACK 确认、以及崩溃超时自动转交（XAUTOCLAIM）。
⚡ stream_mq.redis · 限长生产、消费组拉取、ACK 与故障接管 [Redis 6.2+ / 7.x] 
# 1. 生产消息：MAXLEN ~ 10000 近似裁剪防内存撑爆，* 自动生成递增 ID
XADD mq:orders MAXLEN ~ 10000 * order_id 9001 user_id 1001

# 2. 创建消费组 g1（MKSTREAM 在流不存在时自动建空流）
XGROUP CREATE mq:orders g1 0 MKSTREAM

# 3. 消费者 c1 阻塞最多 2 秒拉取未分配过的新消息（>）
XREADGROUP GROUP g1 c1 COUNT 5 BLOCK 2000 STREAMS mq:orders >

# 4. 消费落库成功后发送 XACK 从 PEL 待确认池移除

# 5. 故障巡检（6.2+）：超时 60 秒未 ACK 的死信由 c2 自动认领重试
XAUTOCLAIM mq:orders g1 c2 60000 0-0 COUNT 10

func ConsumeOrderStream(ctx context.Context, rdb *redis.Client, consumerName string) {
    _ = rdb.XGroupCreateMkStream(ctx, "mq:orders", "g1", "0").Err()
    for {
        streams, err := rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
            Group:    "g1",
            Consumer: consumerName,
            Streams:  []string{"mq:orders", ">"},
            Count:    10,
            Block:    2 * time.Second,
        }).Result()
        if err != nil {
            continue
        }
        for _, msg := range streams[0].Messages {
            // 消费逻辑务必幂等（按 order_id 判重），成功后再 XAck
            if err := grantCouponIdempotent(ctx, msg.Values); err == nil {
                _ = rdb.XAck(ctx, "mq:orders", "g1", msg.ID).Err()
            }
        }
    }
}
⚠️ 选型边界：什么时候 Redis Stream 够用，什么时候必须换 Kafka / RabbitMQ？
• 用 Redis Stream 就够了：中小型项目不想额外维护一套消息队列组件、日消息量在百万级以内、下游正常实时消费无大规模积压、能容忍极端宿主机断电丢失最后 1 秒非账务消息。
• 必须换 Kafka / RabbitMQ / RocketMQ：① 消息积压可能达几十 GB 甚至 TB 级（Redis 全存内存，设了 MAXLEN 积压超限就会把老消息裁掉，不设又会直接把 Redis 内存撑爆宕机；而 Kafka 存廉价磁盘不怕堆积）；② 资金账务级零丢失要求（需同步刷盘 + 多副本确认才向生产者返回成功）；③ 需要复杂的路由交换机、原生多级延迟队列或死信队列（选 RabbitMQ / RocketMQ）。

💡 背后的原理：Stream 如何用前缀压缩基数树 rax + listpack 压缩同构消息字段，详见 《📘 原理篇 · 06.2 Stream 底层存储模型》。

⚖️ 04.10 为什么上面实战都在写 Lua 脚本，而不用 MULTI 事务？

很多刚从 MySQL 转过来的开发者看到 Redis 有 MULTI ... EXEC，会误以为它和关系型数据库事务一样。实际上两者差别很大——把 MULTI、Lua 和负责纯批量网络加速的 Pipeline 放在一张表里对比最清楚：

机制 防其他客户端插队 能否读上一步结果做 if/else 中途某条命令报错会回滚（Rollback）吗？
MULTI / EXEC 事务 是（EXEC 时集中串行跑完） 不能！所有命令在 EXEC 前只是排队暂存，客户端中途拿不到查询结果 不回滚！入队时语法拼错会整批取消；但运行时类型错（如对 Hash 调 INCR）仅该条报错，前后其余命令照常生效。
Lua 脚本
EVAL / EVALSHA		 是（严格单命令级原子） 能！在脚本内直接查出库存/令牌数，满足 if 条件才执行下一步扣减 同样无自动回滚，所以脚本内应先把所有前置校验判断完，最后再执行修改命令。
Pipeline 管道
(详见 07.3)		 否（纯粹打包省网络往返，中间可穿插别人的命令） 不能（一次全发出去再一次收结果） 互不影响，单条报错不阻断其他命令。

实战一句话选型口诀：只要需求里有「先查一下是什么值，满足条件再改/删」（解锁校验 Token、扣库存防超卖、限流判超额、抢延迟订单），直接写十几行以内、无耗时循环的 Lua 脚本，并且把脚本访问的所有键名都通过 KEYS[] 数组传进去（为以后上集群留好兼容）。
