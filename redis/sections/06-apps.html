🔒 06.1 基于 Redis 实现生产级分布式互斥锁的 4 项规范

单机应用内可以使用语言自带的 sync.Mutex 控制并发互斥，但在多实例集群部署下（如定时任务防多节点重复执行、同一用户订单防并发扣款），需要借助外部共享存储协调互斥。使用单实例/哨兵 Redis 实现安全可靠的分布式锁，必须完整满足以下 4 个工程步骤：

设计要素 解决的并发边界问题与实现规范
① 加锁与设过期时间原子合并 绝不能先调 SETNX 再单独调 EXPIRE（若两步之间客户端进程崩溃，该锁将永不过期）。统一使用单条复合指令：SET lock:resource <token> NX PX 30000。
② Value 写入全局唯一持有者令牌 不能将 Value 随便写为固定常数 "1"。若协程 A 因下游接口慢耗时 35 秒，第 30 秒锁自动过期后被协程 B 合法拿到，第 35 秒协程 A 执行完毕若盲目调用 DEL，会误删协程 B 正在持有的锁。因此每次加锁必须生成唯一随机串（如 UUID）。
③ 使用 Lua 脚本原子校验并释放 释放锁时，若在客户端分两步先 GET 比对相等、再发 DEL，在 GET 返回后到 DEL 到达前的间隙锁仍可能恰好过期易主。因此必须通过 Lua 脚本在服务端单次原子完成「读取比对 + 删除」。
④ 后台看门狗（Watchdog）续期 当业务执行耗时存在波动难以预估固定 TTL 时，加锁成功后在客户端启动一个后台定时协程，每隔 TTL / 3（如每 10 秒）通过 Lua 校验自己仍持有该锁后将剩余过期时间重置回 30 秒；一旦业务结束主动解锁或客户端宕机，续期协程自动停止。

-- KEYS[1]: 锁键名 | ARGV[1]: 当前持有者唯一随机 Token
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
🐹 dist_lock.go · 带自动续期的 Go 分布式锁封装 
var (
    unlockLua = redis.NewScript(`if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end`)
    renewLua  = redis.NewScript(`if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('PEXPIRE',KEYS[1],ARGV[2]) else return 0 end`)
)

func WithDistLock(ctx context.Context, rdb *redis.Client, key string, ttl time.Duration, fn func() error) error {
    token := uuid.NewString()
    ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil || !ok {
        return errors.New("资源正被其他节点处理中")
    }

    stopWatchdog := make(chan struct{})
    go func() {
        ticker := time.NewTicker(ttl / 3)
        defer ticker.Stop()
        for {
            select {
            case <-ticker.C:
                _, _ = renewLua.Run(context.Background(), rdb, []string{key}, token, ttl.Milliseconds()).Result()
            case <-stopWatchdog:
                return
            }
        }
    }()

    defer func() {
        close(stopWatchdog)
        _, _ = unlockLua.Run(context.Background(), rdb, []string{key}, token).Result()
    }()
    return fn()
}

补充说明（可重入锁）：若同一业务调用链存在外层方法与内层方法嵌套获取同一把锁的需求（如 Java Redisson 的 RLock），可将底层存储由 String 改为 Hash（key=锁名，field=UUID:线程ID，value=重入计数），通过 Lua 脚本在重入时将计数 HINCRBY +1，解锁时 -1 直至归零才删除整个 Key。

1. MULTI/EXEC 事务、Lua 脚本与 Pipeline 的核心差异

执行方式 网络 RTT 次数 是否防止其他客户端插队 条件分支与错误处理行为
Pipeline 管道 1 次（批量打包） 否（中间可穿插其他连接命令） 纯客户端网络优化，不支持读取前一条结果做条件判断，单条失败不影响其余命令。
MULTI / EXEC 事务
(可配 WATCH 乐观锁)		 多条入队（常结合 Pipeline 发） 是（EXEC 一次性串行执行） 不支持传统数据库回滚（Rollback）：入队期命令拼写错误会整批取消；但运行期类型错误（如对 Hash 调 INCR）仅该条报错，其余命令照常生效且不回滚。不支持在事务内部写 if/else。
Lua 脚本
EVAL / EVALSHA		 1 次（传 SHA1 摘要更省带宽） 是（严格单命令级原子性） 生产条件原子操作首选：可在服务端直接读取上一步结果做 if/else 判断（例如“先校验库存足够且用户未买过，再扣库存并记购买集合”）。注意脚本须简短无阻塞。

2. 使用 Redis 5.0+ Stream 构建带 ACK 确认的轻量消息队列

在中小规模项目中若不想引入整套 Kafka / RocketMQ 运维组件，可以使用 Redis 5.0 引入的 Stream（替代无 ACK 易丢消息的 List 与不存历史消息的 Pub/Sub）。Stream 原生支持多消费者组独立广播、同一组内多消费者负载均衡分摊、以及未确认消息暂存池（PEL，Pending Entries List）故障认领：

⚡ stream_mq_demo.redis · Stream 限长生产、消费者组拉取、XACK 与超时故障转移认领 
# 1. 生产消息：MAXLEN ~ 10000 采用近似裁剪（按整块 listpack 节点高效回收旧消息，防止无限增长占满内存），* 表示由服务端生成时间戳-序号 ID
XADD mq:orders MAXLEN ~ 10000 * order_id 9001 user_id 1001 amount 199.00

# 2. 创建消费者组 g1（0 表示从第一条消息起消费，$ 表示只消费后续新消息；MKSTREAM 在流不存在时自动创建空流）
XGROUP CREATE mq:orders g1 0 MKSTREAM

# 3. 消费者 c1 阻塞式拉取最多 5 条尚未分配给组内任何人的新消息（特殊符号 > 代表未投递过的新消息）
XREADGROUP GROUP g1 c1 COUNT 5 BLOCK 2000 STREAMS mq:orders >

# 4. 业务落库处理成功后（消费端需做好 order_id 幂等去重），发送 XACK 将该消息从 PEL 待确认池移除
XACK mq:orders g1 1732676001000-0

# 5. 故障恢复巡检（Redis 6.2+）：若 c1 崩溃导致某消息在 PEL 中停留超过 60000ms 未 ACK，由存活消费者 c2 自动接管重试
XAUTOCLAIM mq:orders g1 c2 60000 0-0 COUNT 10

☑️ 06.3 基础与实战篇核心场景自测

01. 执行 TTL key 返回 -1 和 -2 分别代表什么含义？

返回 -1 表示该 Key 当前存在，但没有设置过期时间（长期驻留内存，除非手动删除或被 allkeys-* 淘汰策略驱逐）；返回 -2 表示该 Key 不存在（从未创建、已被删除或已到期自动清理）。此外要注意：对已带过期时间的 Key 重新执行不带 EX / PX / KEEPTTL 选项的 SET 覆写，会清除原有的过期时间使其变为 -1。

02. 使用 SCAN 遍历键空间时，能根据返回列表为空判断遍历结束吗？

不能。因为 SCAN 每次按槽位抽查一小批哈希桶后再用 MATCH 过滤，如果当前这批桶恰好为空或没有匹配指定前缀的键，返回的 Key 数组就是空的，但底层尚未扫完。唯一正确的终止条件是返回的下一次游标值（nextCursor）重新回到 0。

03. 存储用户购物车商品与数量，选 JSON String 还是 Hash 更合适？

选 Hash（如 key = cart:user:1001，field = sku_id，value = count）。加购、修改单品数量（HINCRBY）、移除单品（HDEL）均可在服务端直接按单个字段完成，避免每次加减一件商品都把整个购物车 JSON 拉回客户端反序列化再全量覆写。

04. 抽奖业务中，Set 的 SRANDMEMBER 与 SPOP 有何区别？

SRANDMEMBER key [count] 仅随机抽取返回元素，不修改原集合，适合“首页随机推荐一批用户/商品”或允许重复中奖的场景；SPOP key [count] 会随机抽取并将中奖元素从集合中永久移除，天然保证同一个人不会重复抽中多个奖项。

05. 如何用一段简洁代码同时防住缓存穿透、缓存击穿与缓存雪崩？

① 防穿透：数据库查不到记录时写入短 TTL（如 45 秒）的空值标记（或前置布隆过滤器）；② 防击穿：缓存未命中回源处包裹进程内 singleflight 或分布式互斥锁，确保高并发下同一热点 Key 只有 1 个协程回源查库；③ 防雪崩：回填缓存的过期时间统一加上随机偏移量（如 30m + rand(0, 5m)）避免集中失效。

06. 16 GiB 内存机器独立部署 Redis，maxmemory 为什么不能直接设成 16gb？

maxmemory 只统计键值数据本身的开销，而不包含主从复制缓冲区、客户端输入输出缓冲区、jemalloc 内存碎片以及 BGSAVE / BGREWRITEAOF fork 子进程期间写时复制产生的额外内存页副本。一般将 maxmemory 设为物理内存的 70% 左右（约 11~12 GiB），预留 25%~30% 安全水位防止触发操作系统 OOM Killer。

07. Redis Cluster 中执行 MSET 报 CROSSSLOT 错误该如何规范解决？

Cluster 要求单条多 Key 命令或 Lua 脚本访问的所有 Key 必须位于同一个哈希槽。应在键名中引入花括号 {Hash Tag}（如 user:{10086}:info 与 user:{10086}:ext），使 Redis 仅对离散度高的 10086 计算 CRC16，切忌使用固定常量做 Hash Tag 以免引发单分片倾斜。

08. 需要“先判断库存 ≥ N 再扣减并记录购买人”，用 MULTI 事务还是 Lua 脚本？

必须使用 Lua 脚本（EVAL / EVALSHA）。因为 MULTI/EXEC 事务的所有命令在入队阶段只是暂存不执行，客户端无法在事务中途拿到查询结果去做 if stock >= N 分支判断，且运行期报错不回滚；而 Lua 脚本在服务端主线程内一次性原子完成查询、分支校验与扣减更新。
