❓ 06.1 · 用 Redis 实现生产级分布式锁，必须一步步堵上哪 4 个漏洞？

🔒 06.1 分布式锁：从朴素写法到 Redisson 生产级闭环

演进阶段 堵住什么致命漏洞？怎么写？
① 原子占锁+过期 不能拆成 SETNX + EXPIRE 两条命令（中间宕机就永久死锁），必须合二为一：
SET lock_key uuid_threadId NX EX 30
② 防误删别人锁 若线程 A 业务卡顿超过 30s 锁自动释放，线程 B 抢到锁；此时 A 跑完直接 DEL 就会把 B 的锁删掉！
👉 解法：Value 存唯一标识（UUID:threadId），释放时用 Lua 脚本原子执行“比对 Value 相等才 DEL”。
③ 锁自动续期
(Watchdog 看门狗)		 TTL 设短了业务没跑完锁就丢了。Redisson 看门狗：加锁默认 30s，后台每 10s（TTL/3）检查当前线程是否仍持有锁，若是则自动把 TTL 重置回 30s；若客户端宕机则不再续期，到期自然释放。
④ 可重入锁 同一线程内方法嵌套再次拿同一把锁时，用 Hash 结构 存储：key=锁名, field=UUID:threadId, value=重入次数，重入时 +1，释放时 -1，减到 0 才真正 DEL。
📜 unlock_atomic.lua · 原子校验并释放分布式锁 
-- KEYS[1]: 锁名称 | ARGV[1]: 当前线程唯一标识 (UUID:threadId)
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
⚖️ 主从切换丢锁问题与 RedLock 争议（Martin Kleppmann vs antirez）：
主库刚加上锁还没异步复制给从库就宕机，哨兵把从库升为新主，新主上没有这把锁，导致第二个客户端也加锁成功。
• RedLock：部署 5 台独立 Master，向全部节点加锁，超半数（≥3 台）成功且耗时极短才算拿锁。
• 争议与选型结论：若客户端拿锁后发生长时间 Full GC 停顿，锁过期被别人拿走，仍无法保证绝对互斥（除非资源层校验单调递增的 fencing token）。因此：高并发提效防重用 Redis 锁（Redisson）；要求 100% 强一致零差错的账务核心，用数据库唯一约束/悲观锁或 etcd / ZooKeeper。
❓ 06.2 · Redis 做消息队列有哪 3 种方式？为什么 Redis 事务不支持回滚？

📨 06.2 消息队列对比：List vs Pub/Sub vs Stream (5.0+)

方案 核心命令 优缺点与适用边界
List LPUSH + BRPOP 拉出即删，无 ACK 确认机制（消费者崩溃消息就丢），不支持多消费者组广播。
Pub/Sub PUBLISH / SUBSCRIBE 纯内存广播，不持久化历史消息，客户端断线期间的消息直接丢失（Fire-and-Forget）。
Stream
(5.0+ 推荐)		 XADD / XREADGROUP / XACK 借鉴 Kafka：自增消息 ID（时间戳-序号）、组间广播 + 组内负载均衡、未确认消息进入 PEL 待确认列表，支持 XACK 与 XAUTOCLAIM 故障认领（需用 MAXLEN ~ 10000 限长防撑爆内存）。
⚡ stream_mq_demo.redis · Stream 消费者组与 ACK 闭环命令 
# 1. 生产消息并限制队列近似长度 10000
XADD orders MAXLEN ~ 10000 * user 1001 amount 99.00
# 2. 创建消费者组 g1 并由消费者 c1 拉取未消费消息 (>)
XGROUP CREATE orders g1 0 MKSTREAM
XREADGROUP GROUP g1 c1 COUNT 5 STREAMS orders >
# 3. 消费成功后发送 XACK 从 PEL 待确认列表中移除
XACK orders g1 1699000000000-0

🧰 事务（MULTI/EXEC）、Lua 脚本与 Pipeline 管道辨析

机制 核心特性与高频考点
MULTI / EXEC 事务 不支持回滚！入队时语法错误会整个拒绝执行；但执行期运行错误（如对 String 调 LPUSH）只有报错那条失败，其余照常执行且不回滚。如需条件原子操作，请用 Lua 脚本。
Lua 脚本 (EVAL) 整个脚本在主线程里作为单条命令原子执行，绝不被其他客户端插队，且支持写 if/else 分支读取中间结果（不可写死循环或慢逻辑）。
Pipeline 管道 纯网络层优化（≠ 事务）：客户端把多条命令打包一次发过去，把 $N$ 次网络 RTT 压缩成 1 次；但服务端执行时不保证原子性，中间可能穿插其他客户端命令。
🎯 06.3 · 闭卷自测：9 道 Redis 核心追问（先口述回答，再点开抽屉核对）

☑️ 06.3 高频面试速记自检表

01. Redis 为什么快？6.0 多线程改了哪里？

纯内存寻址（~100ns）+ 单线程免锁免上下文切换 + epoll 多路复用 Reactor 模型 + 高度优化的数据结构（SDS/跳表/listpack）。4.0 引入 bio 后台线程异步删大 Key（UNLINK）；6.0 多线程 IO 只并行读写 Socket 与协议解析，命令执行阶段始终单线程串行。

02. String 的 embstr 为什么以 44 字节为界？7.0 为什么用 listpack 替代 ziplist？

jemalloc 分配 64B 内存块，减去 redisObject 头(16B) + sdshdr8 头(3B) + \0(1B) = 44B。旧 ziplist 每项存前一项长度 prevlen，修改会触发级联扩容的“连锁更新”；listpack 只存自身长度，彻底根除连锁更新。

03. ZSet 为什么用跳表 (skiplist + dict) 而不是红黑树或 B+ 树？

dict 支持 $O(1)$ 按成员查分值，skiplist 支持 $O(\log N)$ 排序与范围查。相比红黑树，跳表 L0 层就是双向有序链表，范围遍历（ZRANGE）极简单且靠随机层数免去旋转平衡；B+ 树则是为降低磁盘页随机 IO 设计的，纯内存无需 B+ 树。

04. 渐进式 rehash 是怎么运作的？为什么 fork 期间扩容阈值从 1 提到 5？

同时维护 ht[0] 和 ht[1]，每次增删改查顺带按 rehashidx 搬迁 1 个桶（新增只写 ht[1]，查询先 ht[0] 后 ht[1]）。RDB/AOF 子进程存在时，为避免大面积内存修改触发写时复制（COW）撑爆内存，把扩容负载因子阈值从 1 抬高到 5。

05. 缓存穿透、击穿、雪崩分别怎么解决？

穿透（查不存在）：布隆过滤器前置拦截 + 缓存空对象（短 TTL）；击穿（单热点 Key 过期）：互斥锁回源重建 或 逻辑过期异步刷新；雪崩（大批过期或宕机）：TTL 加随机偏移值 + 高可用集群 + 本地多级缓存。

06. MySQL 与 Redis 如何保持数据一致？

采用 Cache-Aside 最终一致：先更新 MySQL，再删除 Redis 缓存（不更新缓存以防并发写覆盖与无效计算；不先删缓存以防并发读把旧值重新灌回缓存）。进阶可叠加延迟双删或用 Canal 订阅 MySQL binlog + MQ 重试异步删缓存。

07. RDB 和 AOF 各有什么优缺点？4.0 混合持久化怎么做？

RDB 是二进制快照（bgsave fork + COW），恢复极快但丢数据多；AOF 记录写命令（everysec 最多丢 1 秒），但体积大恢复慢。4.0 混合持久化在 AOF 重写时将前半段存为 RDB 快照、后半段追加增量 AOF 命令，兼顾恢复速度与数据安全。

08. 过期删除和内存淘汰有什么区别？从库会自己删过期 Key 吗？

过期删除采用惰性删除 + 定期抽样删除；内存达到 maxmemory 时触发 8 种淘汰策略（常用 allkeys-lru 或 allkeys-lfu，复用 redisObject 的 24-bit lru 字段抽样淘汰）。从库绝不主动物理删除过期 Key，统一等主库发来 DEL/UNLINK 才删。

09. 主从、哨兵、Cluster 各自解决什么问题？分布式锁怎么防误删和过期？

主从：读分流与备份（靠 RDB + repl_backlog 环形缓冲同步）；哨兵：SDOWN→ODOWN + Raft 选主自动故障转移；Cluster：16384 槽水平分片。分布式锁：SET key uuid NX EX 30 + Lua 比对 UUID 原子释放 + Watchdog 看门狗每 10s 自动续期。
