🧭 先搞清楚定位 · Redis 不是为了替代 MySQL，而是为了补齐物理硬件的“速度鸿沟”

💡 从第一性原理出发：为什么磁盘数据库扛不住几十万 QPS 的高并发？

刚学完 MySQL，你一定会问：“既然 MySQL 已经有 B+ 树索引、有 Buffer Pool 内存池、还有事务和锁，为什么几乎所有互联网系统还要在 MySQL 前面再架一层 Redis？”

答案藏在计算机硬件的物理极限与架构分工里：MySQL 的首要使命是“数据绝对可靠、支持复杂关系查询（JOIN/排序/聚合）与严格事务 ACID”，每次写操作都要维护 B+ 树页、写 Redo/Undo/Binlog 日志，单机能抗住几千 QPS 就已经很吃力；而当面对秒杀抢购、热点商品详情、排行榜、分布式锁这种每秒几万到几十万次的极高频简单读写时，必须把数据直接放在纯内存 + 极致简单的数据结构里——这就是 Redis 诞生的第一性原理。

单核每秒十万级 QPS 的秘密

（第 03 章 · 异常与同步）
保护背后的 MySQL 不被打穿
• 三大异常：穿透（查不存在→布隆/空值）/ 击穿（单热 Key 失效→互斥锁）/ 雪崩（大批同时失效）

💾 主线三：数据会丢、内存会满
（第 04 章 · 持久化与淘汰）
内存有限且易失，怎么兜底？
• 断电不丢：RDB 快照（fork + COW 写时复制）+ AOF 命令日志 + 4.0 混合持久化
• 空间清理：过期删除（惰性 + 定期抽样）+ 内存满了触发 8 种 maxmemory 淘汰策略
👉 理解近似 LRU / LFU 为什么不用全局双向链表，而是靠 24-bit 字段抽样淘汰
🌐 主线四：单机挂了 / 装不下
（第 05～06 章 · 集群与分布式锁）
高可用演进与跨进程协调
• 高可用三级跳：主从复制（RDB + repl_backlog）→ 哨兵 Sentinel（自动选主）→ Cluster（16384 槽）
• 分布式能力：分布式锁（SET NX EX + Lua + Watchdog）+ Stream 消息队列 + Lua / Pipeline
👉 看懂主从切换为什么会导致分布式锁丢锁（RedLock 争议）与脑裂怎么防护
STAGE 1 · 入门阶段我们懂什么就够了？

🎯 目标：把 Redis 当成“带过期时间的远程内存字典”用对

  1. 选对 5 种基础数据结构：缓存单值/计数器用 String，存用户各属性/购物车用 Hash，简单队列/时间线用 List，去重/交集抽奖用 Set，排行榜/权重区间用 ZSet。
  2. 写对旁路缓存（Cache-Aside）套路：读请求先查 Redis，没有再查 MySQL 并写入 Redis（一定要带 EXPIRE 过期时间）；写请求先改 MySQL，再删 Redis 缓存。
  3. 会用基本原子指令：用 INCR / DECR 做原子计数/限流，用 SET key val NX EX 10 做最基础的防重/互斥锁。
STAGE 2 · 进阶在干什么？为什么要了解进阶？

🔥 目标：应对「单线程卡顿」「缓存击穿雪崩」「丢数据」与「集群扩容」

  • 为什么明明是内存操作，线上 Redis 突然卡顿几百毫秒？
    👉 因为命令执行是单线程！不懂底层编码与渐进式 rehash，随便塞一个百万元素的大 Key 或执行 DEL / KEYS *，就会把所有人的请求全部堵死。
  • 为什么加了 Redis，大促零点 MySQL 还是瞬间被打崩了？
    👉 因为没防住缓存穿透、击穿（热点 Key 过期瞬间万级回源）和雪崩（同批 TTL 同时失效）。
  • 为什么加了分布式锁还是出现超卖/误删别人的锁？
    👉 不懂唯一 Value + Lua 脚本原子释放 + Watchdog 自动续期，以及主从异步复制切换导致的锁丢失边界。
