02 数据类型实战：5 种基础类型、3 种统计扩展与选型速查 STRING · HASH · LIST · SET · ZSET · BITMAP · HLL · GEO
🎯 学完本章你能做什么：把 Redis 的 8 种常用数据类型和熟悉的 JavaScript 数据结构对应起来，记住每种类型最常用的 5 条命令、典型业务场景与高频踩坑点。

Redis 的键（Key）统一是字符串，而值（Value）原生支持多种内存结构，让你不用每次都把整份数据拉回业务代码里修改再写回。下面按统一的「是什么（JS 类比）→ 5 个常用命令 → 典型场景 → 常见坑 → 底层编码」结构逐一拆解（另一种专门用于可靠消息队列的扩展类型 Stream 将在 04.9 · 消息队列 完整实战）。

🔤 02.1 · String（字符串）：缓存对象、原子计数与条件写入

🔤 02.1 String（字符串）

  • 是什么（类比 JS）：相当于 JS 里的基础变量 let val = "hello" 或 let count = 0。它是二进制安全的字节串（理论上限 512 MB），既能存普通文本、序列化后的 JSON（JavaScript Object Notation，JavaScript 对象表示法）字符串，也能在内容是整数时直接做服务端原子加减。
  • 典型场景：① 整存整取缓存商品详情或用户配置 JSON；② 文章阅读量、点赞数原子计数器；③ 带 5 分钟过期时间的短信验证码。
⌨️ string_top5.redis · String 最常用的 5 个命令 [Redis 6.x / 7.x] 
# 1. SET：写入值，支持组合 EX(秒级过期) 与 NX(仅当键不存在时才写入，常用于防重和加锁)
SET mall:sku:101 "{\"title\":\"机械键盘\",\"price\":299}" EX 1800
SET order:idem:9001 "1" NX EX 300

# 2. GET：读取字符串值
GET mall:sku:101

# 3. MSET / MGET：一次网络往返批量写入或读取多个键（比循环调多次 GET 快得多）
MSET sku:price:101 "299" sku:price:102 "399"
MGET sku:price:101 sku:price:102

# 4. INCR：将整数字符串原子 +1（键不存在时自动从 0 开始算，返回加完后的新值）
INCR article:views:5001

# 5. INCRBY：按指定步长原子加减（传负数即扣减，等价于 DECRBY）
INCRBY sku:stock:101 -2
⚠️ 常见坑：① 对一个原本带有过期时间的键再次执行普通 SET key newVal，会把原有的过期时间直接清空变成永不过期（TTL = -1）！若只想改值并保留原剩余寿命，Redis 6.0+ 请加 KEEPTTL 参数（SET key newVal KEEPTTL）；② 单个 String 值建议控制在 10 KB 以内，避免大对象占满网卡带宽。

💡 背后的原理：String 底层会根据内容自动切换为 int（8 字节整数）、embstr（≤ 44 字节短字符串，单次连续内存分配）或 raw（> 44 字节动态字符串 SDS，Simple Dynamic String） → 《📘 核心原理篇 · 02.1 对象头与 embstr 44B 边界推导》。

🗂️ 02.2 · Hash（哈希字典）：对象单字段读写与电商购物车

🗂️ 02.2 Hash（哈希字典）

  • 是什么（类比 JS）：相当于 JS 里的单层 Map<string, string> 或扁平对象 { nickname: "林晓", points: "120" }。把同一个实体的多个属性收纳在一个 Key 下面，支持按字段名（field）单独读写。
  • 典型场景：① 用户基础资料缓存（单独修改积分或头像，不必把整个 JSON 读出来反序列化再写回；整读整写用 String 还是局部改用 Hash 的完整对比见 07.5）；② 电商购物车（key = cart:user:1001，field = 商品 sku_id，value = 购买件数）。
🛒 hash_top5.redis · Hash 最常用的 5 个命令（以购物车为例）[Redis 6.x / 7.x] 
# 1. HSET：向购物车一次写入一个或多个「商品ID -> 数量」字段
HSET cart:user:1001 sku_801 "1" sku_805 "2"

# 2. HGET / HMGET：读取单个或多个指定商品的数量
HGET cart:user:1001 sku_801
HMGET cart:user:1001 sku_801 sku_805

# 3. HINCRBY：点击购物车「+」号，将 sku_801 的数量原子 +1
HINCRBY cart:user:1001 sku_801 1

# 4. HLEN：查看购物车里一共有几种商品
HLEN cart:user:1001

# 5. HDEL：从购物车移除某件商品
HDEL cart:user:1001 sku_805
⚠️ 常见坑：① 标准的 EXPIRE 只能给整个 Hash 键设过期，不能给里面的单个 field 单独设过期（注：直到 Redis 7.4+ 才新增字段级过期命令 HEXPIRE）；② 如果一个 Hash 里塞了几万个字段，千万别调 HGETALL 一次性全拉出来，会阻塞单线程，应按需调 HMGET 或用 HSCAN 分批遍历。

💡 背后的原理：字段少且值较短时底层存为一块紧凑连续内存 listpack（Redis 7.0+，6.x 为 ziplist），超过阈值（默认 512 个字段或单值 > 64B）自动转为哈希表 hashtable → 《📘 核心原理篇 · 02.2 listpack 紧凑编码》。

📋 02.3 · List（双向列表）：最新动态时间线与简单阻塞队列

📋 02.3 List（双向列表）

  • 是什么（类比 JS）：相当于支持两端高效进出的字符串数组 string[]（左端进出对应 unshift / shift，右端进出对应 push / pop），元素按插入顺序排列且允许重复。和 JS 数组在头部插入需要搬移全部元素不同，Redis List 从左右两头推入和弹出都是 O(1)。
  • 典型场景：① 社区「最新发布的 100 条帖子/动态列表」（固定长度时间线）；② 简单异步任务队列（左进右出 LPUSH + BRPOP，实现 FIFO，First-In, First-Out，先进先出）。
📋 list_top5.redis · List 最常用的 5 个命令 [Redis 6.x / 7.x] 
# 1. LPUSH / RPUSH：从左端（表头）或右端（表尾）推入元素
LPUSH feed:latest "post_101" "post_102"

# 2. LRANGE：按起止下标读取区间（注意：0 到 9 共返回 10 条；-1 表示最后一个元素）
LRANGE feed:latest 0 9

# 3. LTRIM：只保留指定下标区间内的元素，其余自动裁掉（常与 LPUSH 配合维护最新 100 条动态）
LTRIM feed:latest 0 99

# 4. LPOP / RPOP：从左端或右端立即弹出并移除 1 个元素
RPOP task:simple_queue

# 5. BRPOP：阻塞式弹出——若队列为空，连接最多安静等待 5 秒，一有新元素推入立刻唤醒拿走
BRPOP task:simple_queue 5
⚠️ 常见坑：① LRANGE key 0 9 是双闭区间（同时包含下标 0 和 9，共 10 个元素），跟 JS 的 arr.slice(0, 9) 左闭右开不一样；② 列表很长时严禁执行 LRANGE key 0 -1 拉取全量；③ 用 List 做队列没有确认（ACK）机制，BRPOP 弹走瞬间如果消费者进程崩溃，这条任务就彻底丢了。

💡 背后的原理：底层采用 quicklist 结构（用双向链表把多段紧凑连续的 listpack 小数组串起来），既避免大数组扩容拷贝，又省去纯双向链表海量的前后指针内存 → 《📘 核心原理篇 · 02.2 从 ziplist 到 listpack》。

🎯 02.4 · Set（无序集合）：自动去重、共同关注交集与随机抽奖

🎯 02.4 Set（无序集合）

  • 是什么（类比 JS）：相当于 JS 的 new Set<string>()——无序、自动去重、O(1) 判断某个元素在不在里面；比 JS 原生更方便的是，Redis 直接在服务端支持求两个集合的交集、并集、差集和随机抽取。
  • 典型场景：① 帖子点赞用户去重（点过赞不能重复点，且随时查总赞数）；② 社区「我和他的共同关注好友」（求交集）；③ 活动抽奖池。
🎯 set_top5.redis · Set 最常用的 5 个命令 [Redis 6.x / 7.x] 
# 1. SADD：添加成员（已存在的成员会自动忽略并返回 0）
SADD post:likes:8001 "u_10" "u_20" "u_30"

# 2. SISMEMBER / SCARD：判断 u_10 是否点过赞（返回 1/0），以及查看总点赞人数
SISMEMBER post:likes:8001 "u_10"
SCARD post:likes:8001

# 3. SREM：取消点赞（移除指定成员）
SREM post:likes:8001 "u_30"

# 4. SINTER：求两个集合的交集（另有 SUNION 并集、SDIFF 差集）
SADD follow:u_A "u_1" "u_2" "u_3"
SADD follow:u_B "u_2" "u_3" "u_4"
SINTER follow:u_A follow:u_B
# -> 返回共同关注的 u_2 和 u_3

# 5. SRANDMEMBER vs SPOP：随机抽奖
SRANDMEMBER raffle:pool 2   # 随机看 2 个人，【不从池中删掉】（适合首页随机推荐或允许重复中奖）
SPOP raffle:pool 1          # 随机抽出 1 个人并【从池中永久移除】（适合一二三等奖不重复抽取）
⚠️ 常见坑：集合包含几十万成员时，严禁直接调 SMEMBERS 全量读取（用 SSCAN 分批扫），也不要在高峰期对几个几十万人的大集合直接跑 SINTER / SUNION，O(N) 计算会卡住主线程。

💡 背后的原理：当成员全是整数且不超过 512 个时存为紧凑有序数组 intset（Redis 7.2+ 对短字符串小集合也支持 listpack），否则底层使用无序哈希表 hashtable → 《📘 核心原理篇 · 02.3 渐进式 Rehash》。

🏆 02.5 · ZSet（有序集合）：实时排行榜、延迟任务与滑动窗口

🏆 02.5 ZSet（Sorted Set，有序集合）

  • 是什么（类比 JS）：JS 原生没有现成的等价结构——你可以把它理解成「一个去重的 Map<member, score> + 一个永远按数字 score 自动排好序的数组」。每个不重复成员都挂着一个 64 位浮点数分数（score），既能 O(1) 查某个人的分数，又能 O(log N) 取前 N 名或按分数范围切片。
  • 典型场景：① 游戏战力榜 / 电商热销榜 / 社区热搜榜；② 延迟任务队列（把任务到期时间戳存成 score）；③ 滑动窗口限流（把每次请求的毫秒时间戳存成 score）。
🏆 zset_top5.redis · ZSet 最常用的 5 个命令 [Redis 6.2+ / 7.x] 
# 1. ZADD：添加或更新成员及其分数（注意参数顺序是：先写分数 score，再写成员名 member）
ZADD rank:daily 120 "user_A" 350 "user_B" 210 "user_C"

# 2. ZINCRBY：为指定成员原子加分（成员不存在时自动按 0 初始化）
ZINCRBY rank:daily 50 "user_A"

# 3. ZRANGE ... REV：按分数从高到低取前 10 名并附带分数（注：Redis 6.0 旧版写法为 ZREVRANGE rank:daily 0 9 WITHSCORES）
ZRANGE rank:daily 0 9 REV WITHSCORES

# 4. ZSCORE / ZREVRANK：查某人的当前分数，以及从高到低排第几名（0 代表第 1 名）
ZSCORE rank:daily "user_A"
ZREVRANK rank:daily "user_A"

# 5. ZRANGE ... BYSCORE：按分数区间筛选（例如捞出到期时间戳 <= 当前时间 1732760000 的超时订单；6.0 旧版为 ZRANGEBYSCORE）
ZRANGE delay:orders -inf 1732760000 BYSCORE LIMIT 0 20
⚠️ 常见坑：① ZRANGE 默认是从小到大升序，做高分榜千万别漏写 REV，且名次下标从 0 开始算；② 当两个人 score 完全相同时，Redis 默认按成员名字典序排列，若业务要求“同分先达到者排前面”，需在 score 小数位拼入反向时间戳（写法见 04.6）。

💡 背后的原理：元素少时用紧凑数组 listpack；元素多时内部同时组合「哈希表 hashtable + 跳表 zskiplist」——哈希表负责 O(1) 查单人分数，跳表通过多层链表与跨度字段 span 在 O(log N) 内完成范围查询与名次计算 → 《📘 核心原理篇 · 02.3 跳表 zskiplist 源码结构》。

🧮 02.6 · 三种高压缩扩展类型：Bitmap 签到、HyperLogLog 亿级 UV 与 GEO 附近的人

🧮 02.6 Bitmap、HyperLogLog 与 GEO（省内存专精工具）

当面对上千万用户的签到记录、亿级页面的独立访客数，或者按经纬度找附近门店（LBS，Location-Based Service，基于位置的服务）时，用普通 Set 存原始 ID 会消耗大量内存，这时就轮到这三种专精结构出场：

类型 是什么（类比 JS） 核心常用命令 [6.2+ / 7.x] 典型场景、常见坑与底层编码
Bitmap
位图		 按二进制位（bit）读写 0 或 1 的数组，类比 JS 的 Uint8Array 按位打标（8 个状态仅占 1 字节） SETBIT key offset 1
GETBIT key offset
BITCOUNT key
BITPOS key 1
BITOP AND dest k1 k2		 场景：用户月度签到（offset = 日期 - 1）、连续活跃人群交集。
坑：offset 必须是稠密小整数；若把几千万亿大的雪花 ID 直接当 offset，会瞬间撑出数百 MB 全零内存。
底层：直接复用 String 的 SDS 字节数组。
HyperLogLog
基数统计		 只估算“塞进过多少个不重复元素”、却不保存元素本身的概率统计盒（无论塞 1 亿人还是 1000 人，单键最多只占 12 KB） PFADD key u1 u2
PFCOUNT key
PFMERGE dest k1 k2		 场景：文章/活动页亿级 UV（Unique Visitor，独立访客）统计，PFMERGE 可合并 7 天日 UV 算周 UV。
坑：有约 0.81% 标准误差，且无法反查某个具体用户是否来过。
底层：基于 String 实现的 16384 个 6-bit 分桶寄存器。
GEO
地理空间		 存 [经度, 纬度, 名称] 并按球面距离检索的坐标表 GEOADD key lon lat name
GEOPOS key name
GEODIST key m1 m2 km
GEOSEARCH ... BYRADIUS
ZREM key name（删除）		 场景：附近 3 公里内的门店、骑手或附近的人。
坑：没有 GEODEL 命令，删坐标直接调 ZREM；百万级全国门店应按城市拆成多个 Key，防单键过大。
底层：完全复用 ZSet（将二维经纬度编码为 52 位 GeoHash 整数存进 score）。
⚡ ext_types_demo.redis · 签到、UV 去重合并与附近门店查询可直接运行示例 [Redis 6.2+ / 7.x] 
# 1. Bitmap：用户 1001 在 11 月第 1 天(offset=0)和第 28 天(offset=27)签到，统计当月共签到了几天
SETBIT sign:u1001:202611 0 1
SETBIT sign:u1001:202611 27 1
BITCOUNT sign:u1001:202611

# 2. HyperLogLog：记录两天的页面访客，合并算出两日总去重 UV
PFADD uv:page:home:1127 "u1" "u2" "u3"
PFADD uv:page:home:1128 "u2" "u3" "u4"
PFMERGE uv:page:home:2days uv:page:home:1127 uv:page:home:1128
PFCOUNT uv:page:home:2days

# 3. GEO：录入门店经纬度（注意先经度后纬度），搜坐标 (121.48, 31.235) 方圆 3 公里内最近的 5 家店
GEOADD shops:sh 121.4737 31.2304 "人民广场店" 121.4997 31.2397 "陆家嘴店"
GEOSEARCH shops:sh FROMLONLAT 121.4800 31.2350 BYRADIUS 3 km ASC COUNT 5 WITHDIST
🧭 02.7 · 选型速查表：拿到业务需求怎么 5 秒敲定 Redis 数据类型

🧭 02.7 「业务需求 → 选什么类型」一表速查

你的业务需求特征 首选类型 判断理由与关键命令提示
整存整取单个对象 / 简单计数器 / 验证码 / 防重锁 String 结构最简单直接，配合 SET NX EX 与 INCR 覆盖一半日常场景。
对象有十几个字段，需要频繁单独改其中一两个（如购物车） Hash HSET / HINCRBY 直接改局部字段，省去整份 JSON 反复序列化。
按时间先后存固定条数的最新动态（允许重复） List LPUSH + LTRIM 0 99 轻松维护定长最新列表。
存一堆不重复 ID，还要判断在不在里面、求共同好友或抽奖 Set SISMEMBER O(1) 判重，SINTER 求交集，SPOP 不重复抽奖。
任何需要按某个数值（积分、热度、到期时间）自动排序的列表 ZSet 看到「排行榜、Top N、我的名次、按时间窗口/延迟到期筛选」直接选它。
对连续编号（日期、稠密用户 ID）记录「是 / 否」二值状态 Bitmap 签到、打卡首选，比用 Set 省几十倍内存。
几千万上亿访问量只求去重总数，允许不到 1% 的误差 HyperLogLog 12 KB 封顶解决海量 UV 统计，绝不撑爆内存。
按经纬度算两地距离、找附近 N 公里的门店/人 GEO GEOADD + GEOSEARCH 原生支持半径检索与按距离由近到远排序。
需要多实例消费、崩溃不丢消息、带 ACK 确认的轻量消息队列 Stream Redis 5.0+ 专为消息流设计，完整用法见 04.9 · 消息队列实战。
