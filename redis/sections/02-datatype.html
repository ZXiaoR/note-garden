Redis 里每个 Value 都由一个统一的 16 字节外壳 redisObject 包裹：对外暴露的是 type（TYPE key 看到的 5 大类型），底层真正挂载在 *ptr 指针上的则是 encoding（OBJECT ENCODING key 看到的物理数据结构）。核心设计哲学：小数据用紧凑连续内存省空间（embstr / intset / listpack），大数据超阈值后自动单向升级为高效索引结构（raw / hashtable / skiplist）保性能！

🧬 1. redisObject (16B) 与 SDS / embstr 44字节之谜

① 统一外壳 redisObject（固定 16 字节）：
type (4 bit)
对外类型 (5大类)
encoding (4 bit)
底层物理编码
lru (24 bit)
LRU时戳 / LFU频次
refcount (4 B)
引用计数内存回收
*ptr (8 B)
指向真实数据 ▸
② SDS 动态字符串（比 C 原生 char* 好在哪？）：
[ len (已用长度) | alloc (分配总容量) | flags (1B 类型头) | buf[] 字节数组 + '\0' ]
✅ $O(1)$ 获取长度（不扫 \0） · 二进制安全（中间有 \0 也不截断，可存图片/序列化字节） · 空间预分配杜绝缓冲区溢出
③ 为什么 embstr 与 raw 的分界线恰好是 44 字节？
64 B (jemalloc 内存分配单元) − 16 B (redisObject) − 3 B (sdshdr8 头) − 1 B ('\0') = 44 B
≤ 44B 用 embstr：只需 1 次 malloc 分配连续内存（CPU Cache 友好）；> 44B 用 raw：分 2 次独立 malloc

🚀 2. 四大扩展类型 & 为什么 7.0 用 listpack 取代 ziplist？

扩展类型 底层本质 核心实战场景
Bitmap 就是 String 按位操作 (SETBIT) 用户每日签到、月活统计（1个月仅需 4 字节）、布隆过滤器
HyperLogLog 概率基数估算（固定 12KB，误差 0.81%） 亿级页面 UV / 独立 IP 去重计数（PFADD / PFCOUNT）
GEO 底层就是 ZSet（经纬度转 GeoHash 当 score） 附近的人、2km 内门店搜索（GEOSEARCH）
Stream rax 基数树 + listpack 5.0+ 支持消费者组与 ACK 的可靠轻量消息队列
❌ 旧 ziplist：记「前一项长度 prevlen」
[ prevlen (1B / 5B) | encoding | data ]
前项从 < 254B 变 ≥ 254B → 后项 prevlen 被迫从 1B 扩为 5B → 多米诺骨牌「连锁更新」
✅ 7.0 listpack：只记「自己长度 mylen」
[ encoding | data | element-tot-len ]
每项末尾存自己的总长度（同样支持从后往前遍历），改任何一项绝不牵连邻居，彻底消灭连锁更新！
❓ 02.2 · ZSet 为什么用「跳表 skiplist + dict」而不是红黑树或 B+ 树？

🪜 跳表（Skiplist）：多层稀疏索引的有序链表（$O(\log N)$）

ZSet 大数据量时同时组合了 dict + skiplist：dict 存 member → score，保证 ZSCORE 按成员查分值 $O(1)$；skiplist 按 score 从小到大排列，支持 ZRANGE 范围查询 $O(\log N + M)$。

❓ 02.3 · 哈希表有几百万个 Key，扩容时怎么避免卡死单线程？

🔄 渐进式 Rehash：双表 ht[0] / ht[1] + rehashidx 化整为零

当负载因子 used / size ≥ 1（无 RDB/AOF 子进程时）或 ≥ 5（有子进程写时复制期间，避免大面积触发内存页复制）触发扩容。不能一次性搬完几百万 Key，而是把搬迁分摊到后续每一次增删改查和定时任务里：

旧表 ht[0] (size=4)
桶 0：(已迁空)
桶 1：(已迁空)
桶 2：k3 → k5 (rehashidx=2)
桶 3：k4 (待搬迁)
每次 CRUD
顺带搬 1 个桶
━━▸
rehashidx++
新表 ht[1] (size=8)
桶 0：k1 (已迁入)
桶 1：k2 (已迁入)
✨ 新增 Key 只写 ht[1]！
🔍 查询：先查 ht[0] 再查 ht[1]
✅ 搬完最后一个桶后：释放旧 ht[0]，让 ht[1] 转正成为新 ht[0]，并将 rehashidx 置回 -1
🔍 进阶 · intset 为什么“只升级不降级”？为什么必须整体升级？

为什么必须整体升级：intset 是一整块等宽的连续整数数组（int16 / int32 / int64）。正因为每个元素占相同字节，才能用 base + i × width 在 $O(1)$ 算位置并做二分查找（$O(\log N)$）。如果存入一个超过 int16（32767）的数 40000，只把这一个元素存成 4 字节，数组就变成宽窄不一，二分查找立刻作废！所以必须把整个数组重新分配升级到 int32。

为什么不降级：如果删掉大数后想判断是否能降级，每次删除都要遍历全数组找新的最大值（$O(N)$），代价太高且收益极低，因此编码升级一律单向不可逆。
