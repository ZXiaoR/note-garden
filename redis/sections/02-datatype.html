02 五大基础数据类型与四大扩展类型实战指南 STRING · HASH · LIST · SET · ZSET · BITMAP · HLL · GEO
🗂️ 02.1 · String 与 Hash：字符串条件写入、原子计数与结构化对象局部更新

🗂️ 02.1 String（字符串）与 Hash（哈希字典）

Redis 的 Value 并非只有简单的文本字符串，而是原生提供了丰富的内存数据结构，使开发者可以直接在服务端完成字段修改、链表排队、集合交并集与权重排序，无需每次将整份数据拉回应用层反序列化后再写回。最常用于存储实体对象与计数状态的是 String 与 Hash：

1. String：二进制安全字节流、条件写入与原子计数

String 是二进制安全的（单个 Value 上限为 512 MB，日常建议控制在 10 KB 以内），既可以存普通文本与序列化后的 JSON / Protobuf 字节流，也可以在内容为十进制整数或浮点数时直接执行服务端原子加减：

⌨️ string_ops.redis · String 高频命令与参数组合 
# 1. SET 完整复合语法：SET key value [NX | XX] [GET] [EX sec | PX ms | KEEPTTL]
#    NX = 仅当键不存在时写入（常用于防重幂等与互斥锁）；XX = 仅当键已存在时更新；KEEPTTL = 更新值但保留原剩余过期时间
SET idempotent:order:9001 "1" NX EX 600

# 2. 批量读写：一次网络往返获取多个商品价格（时间复杂度 O(K)，K 为键个数）
MSET sku:price:101 "9900" sku:price:102 "15900"
MGET sku:price:101 sku:price:102

# 3. 原子计数：键不存在时自动按 0 初始化后再加减，单线程串行执行天然无并发丢失更新问题
INCR article:views:5001          # +1，返回递增后的新整数值
INCRBY sku:stock:101 -2          # 原子扣减 2 件库存（或用 DECRBY sku:stock:101 2）

2. Hash：在单个 Key 内维护多个 field -> value 键值对

当我们需要缓存一个包含十几个属性的对象（如用户资料 {nickname, avatar, vip_level, points}）或用户购物车（field = sku_id，value = 购买数量）时，如果用单个 JSON String 存储，每次只修改积分 points 都需要把整个 JSON 读出、反序列化、改完再整体覆盖写回；而使用 Hash 可以直接按字段（field）局部读写：

🛒 hash_cart.redis · 用 Hash 实现电商购物车 
# 1. 添加商品到用户 1001 的购物车 (HSET 支持一次写多个字段)
HSET cart:user:1001 sku_801 1 sku_805 2

# 2. 点击「+」号将 sku_801 数量原子 +1
HINCRBY cart:user:1001 sku_801 1

# 3. 查看购物车商品种类数与指定商品数量
HLEN cart:user:1001
HMGET cart:user:1001 sku_801 sku_805

# 4. 移除某件商品；字段较多时用 HSCAN 替代 HGETALL
HDEL cart:user:1001 sku_805
# Redis 7.4+ 原生支持为单个 Hash 字段独立设置过期时间：
HEXPIRE cart:user:1001 86400 FIELDS 1 sku_801

工程选型对比：存对象用 JSON String 还是 Hash

选型方案 适用场景与权衡
JSON String 适合整读整写、极少局部修改或包含多层嵌套数组的对象（如商品详情页聚合快照），代码序列化直接直观。
Hash 字典 适合高频读写单字段、单字段原子增减的扁平结构（如购物车、用户多维计数状态）。在字段数量适中（如 ≤ 128 项）时内存紧凑度极高。
📊 02.2 · 集合与排序容器：List 双端列表、Set 唯一集合运算与 ZSet 实时排行榜

📊 02.2 List、Set 与 ZSet 的核心操作与场景边界

1. List（按插入顺序排列的双向列表，允许重复元素）

List 支持从左端（表头 L*）或右端（表尾 R*）以 O(1) 推入和弹出元素，因此通过不同的方向组合即可构造栈（同端进出 LPUSH + LPOP）或先进先出队列（左进右出 LPUSH + RPOP / BRPOP）。需要注意 LRANGE key start stop 的区间规则与 Go 切片不同，它是「双闭区间」——同时包含 start 和 stop 下标本身，且支持负数下标（-1 表示最后一个元素，-2 表示倒数第二个元素）：

📋 list_timeline.redis · 定长最新动态列表与阻塞弹出 
# 1. 最新消息推入表头，并用 LTRIM 只保留最新的前 100 条（下标 0 到 99 双闭区间，自动淘汰第 100 条之后的旧动态）
LPUSH feed:latest:user_1001 "post_903"
LTRIM feed:latest:user_1001 0 99

# 2. 分页读取第 1 页（前 10 条：下标 0 ~ 9，共 10 个元素；LRANGE key 0 -1 表示取全部元素，大列表慎用）
LRANGE feed:latest:user_1001 0 9

# 3. 阻塞式右端弹出：若队列为空，连接挂起最多等待 5 秒，一旦有新元素推入立即唤醒返回
BRPOP task:light_queue 5

2. Set（无序、自动去重的唯一元素集合）

Set 不仅能在 O(1) 时间内判断某个成员是否已存在（SISMEMBER），还原生支持跨集合的交集（SINTER）、并集（SUNION）、差集（SDIFF）与随机抽取。抽奖业务中需区分两个随机命令的行为差异：SRANDMEMBER key count 仅随机读取不删除原元素（适合可重复中奖或随机推荐池），而 SPOP key count 会随机弹出并从集合中移除该元素（适合一二三等奖不重复抽取）。

🎯 set_social.redis · 独立去重、抽奖池与共同关注交集 
# 1. 添加关注集合（重复写入同一元素会自动忽略并返回 0）
SADD follow:user:A "u_10" "u_20" "u_30"
SADD follow:user:B "u_20" "u_30" "u_40"

# 2. 判断 A 是否关注了 u_20 (O(1))，并计算集合元素总数
SISMEMBER follow:user:A "u_20"
SCARD follow:user:A

# 3. 求 A 与 B 的共同关注交集 -> 返回 ["u_20", "u_30"]（注意大集合交集建议在从库执行或限制规模）
SINTER follow:user:A follow:user:B

3. ZSet（Sorted Set，每个唯一成员关联一个 64 位浮点权重 score）

ZSet 在保持成员唯一性的同时，自动按 score 从小到大维护顺序（当两个成员 score 相同时按成员名字典序排列），单点查分值为 O(1)，插入更新与按名次/分值区间查询均为 O(log N + M)（M 为返回条数）。从 Redis 6.2 起，官方将早期的 ZREVRANGE / ZRANGEBYSCORE 统一收敛到了增强版 ZRANGE 命令中：

🏆 zset_leaderboard.go · 使用 ZSet 实现实时热力排行榜与滑动窗口限流 
// 1. 玩家得分原子累加 50 分（成员不存在时自动创建，等价于 ZINCRBY rank:daily:20261127 50 "player_42"）
newScore, err := rdb.ZIncrBy(ctx, "rank:daily:20261127", 50, "player_42").Result()

// 2. 查询某玩家的降序实时名次（ZRevRank 从 0 开始计，0 代表第一名）
rankZeroBased, err := rdb.ZRevRank(ctx, "rank:daily:20261127", "player_42").Result()

// 3. 获取榜单前 10 名及分数（等价于 Redis 6.2+ 命令：ZRANGE rank:daily:20261127 0 9 REV WITHSCORES）
top10, err := rdb.ZRangeArgsWithScores(ctx, redis.ZRangeArgs{
    Key:   "rank:daily:20261127",
    Start: 0,
    Stop:  9,
    Rev:   true,
}).Result()
for idx, item := range top10 {
    fmt.Printf("第 %d 名: %v (分数: %.0f)\n", idx+1, item.Member, item.Score)
}
🚀 02.3 · 高阶扩展类型：Bitmap 位图、HyperLogLog 基数估算、GEO 地理空间与选型全景表

🚀 02.3 四种扩展数据类型实战与选型决策矩阵

面对海量用户签到、亿级页面独立访客（UV）统计或“附近 3 公里门店”检索时，若直接使用 Set 存原始用户 ID，内存占用会随用户规模线性膨胀。Redis 基于既有结构封装了四种空间效率极高的专用扩展类型：

扩展类型 核心操作指令 空间效率对比 典型业务场景与使用注意点
Bitmap
按位操作		 SETBIT key offset 0|1
GETBIT / BITCOUNT
BITOP AND|OR dest k1 k2		 1 亿连续整数 ID 的二值状态仅占 108 / 8 ≈ 11.9 MiB 用户月度签到、连续活跃统计（如 BITOP AND 求连续 3 天都登录的用户位图）。注意：仅适合稠密连续整数偏移量，若拿稀疏雪花 ID（如 1015）直接当 offset 会瞬间分配数百 MB 空白零字节。
HyperLogLog
基数估算		 PFADD key elem ...
PFCOUNT key [key ...]
PFMERGE dest k1 k2		 无论写入百万还是上亿不重复元素，单键最多固定占 12 KiB 全站/单文章 UV 去重计数（PFMERGE 可将 7 天的日 UV 合并计算出周 UV）。注意点：属于概率统计结构（标准误差 0.81%），不支持反查具体包含哪些元素。
GEO
地理坐标		 GEOADD key lon lat name
GEODIST key m1 m2 km
GEOSEARCH key FROMLONLAT ... BYRADIUS 3 km ASC		 底层复用 ZSet（将二维经纬度编码为 52 位 GeoHash 整数作为 score） 附近骑手、周边门店按距离排序检索。删除某个坐标点直接使用 ZSet 的 ZREM key name；若全国点位达百万级，应按城市或省级行政区拆分 Key，避免单键过大。
Stream
持久化消息流		 XADD / XREADGROUP / XACK 内部采用前缀树 + 紧凑列表块压缩同结构消息字段 轻量可靠异步消息队列，支持多消费者组广播、组内负载均衡与未确认消息列表（PEL），详见第 06 章完整演练。
⚡ ext_types_demo.redis · Bitmap 月度签到、HyperLogLog UV 合并与 GEO 搜索 
# 1. Bitmap：记录用户 10086 在 2026 年 11 月第 1 天(offset=0)和第 27 天(offset=26)签到，并统计当月总签到天数
SETBIT sign:u10086:202611 0 1
SETBIT sign:u10086:202611 26 1
BITCOUNT sign:u10086:202611

# 2. HyperLogLog：统计两天的文章 UV 并合并计算两日总独立访客数
PFADD uv:article:99:20261126 "u1" "u2" "u3"
PFADD uv:article:99:20261127 "u2" "u3" "u4"
PFMERGE uv:article:99:2days uv:article:99:20261126 uv:article:99:20261127
PFCOUNT uv:article:99:2days

# 3. GEO：录入门店经纬度，查询距离指定坐标半径 3 公里内最近的 5 家门店（Redis 6.2+ GEOSEARCH）
GEOADD shops:shanghai 121.4737 31.2304 "人民广场店" 121.4997 31.2397 "陆家嘴店"
GEOSEARCH shops:shanghai FROMLONLAT 121.4800 31.2350 BYRADIUS 3 km ASC COUNT 5 WITHDIST
📘 底层内存实现直达：同一种对外类型在小规模数据与大规模数据时，Redis 内部会自动选用不同的物理编码（例如 String 的 embstr 44 字节边界、Redis 7.0 用 listpack 替代 ziplist 消除连锁更新、ZSet 的跳表跨度指针与哈希表渐进式 rehash）。想深入内存字节级布局可前往 《📘 核心原理篇 · 02 对象头、SDS、listpack、跳表与渐进式 Rehash》。
