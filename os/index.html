0 · 操作系统是什么

操作系统（OS）是介于硬件和应用程序之间的一层软件，核心就干两件事：

  • 资源管理者：管理 CPU、内存、磁盘、网卡等有限硬件资源，在众多进程间分配、调度、回收，做到公平又高效。
  • 硬件抽象层 / 虚拟机：把裸硬件包装成好用的抽象——进程（虚拟 CPU）、虚拟内存（虚拟内存条）、文件（虚拟磁盘），应用不用直接跟寄存器和扇区打交道。

内核（Kernel）vs 操作系统：内核是 OS 最核心、常驻内存、拥有最高权限的部分（进程调度/内存/文件/驱动）。狭义"操作系统"≈ 内核；广义还包括 shell、GUI、系统工具等外围。宏内核（Linux：驱动、文件系统都塞进内核，性能好但耦合高）vs 微内核（只留最核心功能在内核态，其余做成用户态服务，稳定但通信开销大）。

1 · 用户态 / 内核态 高频

为什么要分两个态？因为不能让任意程序直接操作硬件、改别人的内存——那样一个程序崩了或使坏就能拖垮整个系统。于是 CPU 提供了特权级（Ring）：

  • 内核态（Ring 0）：能执行特权指令（操作 I/O 端口、改页表、关中断），能访问所有内存和硬件。内核代码跑在这。
  • 用户态（Ring 3）：只能执行普通指令、只能访问自己进程的虚拟内存。想干"越权"的事（读文件、发网络包、申请内存），必须请内核代劳。
怎么从用户态进内核态？只有三条路：① 系统调用（主动，软中断/syscall 指令）；② 中断（外部设备，如网卡收包、时钟）；③ 异常（被动，如缺页、除零）。三者本质都是"陷入（trap）"内核，CPU 切到内核栈、跳到内核预设的处理入口。
为什么说态切换有开销？切换要保存用户态上下文（寄存器）、切到内核栈、执行完再恢复、还可能刷新流水线。虽然比进程切换轻（不换页表、不换地址空间），但频繁 syscall 依然是性能敏感点——这正是零拷贝（§32）、epoll（§31）、批量系统调用要减少的东西。
用户态到内核态切换，和进程上下文切换是一回事吗？
不是。态切换（模式切换）只是同一个进程内 CPU 特权级的改变，不切换地址空间、页表还是那份，很轻。进程上下文切换是换到另一个进程去跑，要换页表、刷 TLB、换内核栈，重得多。一次系统调用只发生态切换，不一定发生进程切换。

2 · 系统调用 syscall

系统调用是用户程序请求内核服务的唯一合法接口。你平时调的 read()/write()/fork() 是 C 库（glibc）封装的函数，它们内部最终会执行一条陷入指令进入内核。

一次系统调用发生了什么（x86-64）

  1. 把系统调用号放进 rax，参数放进 rdi/rsi/rdx... 等寄存器。
  2. 执行 syscall 指令（老机制是软中断 int 0x80），CPU 切到内核态、跳到内核入口 entry_SYSCALL_64。
  3. 内核用系统调用号查系统调用表（sys_call_table），找到对应内核函数执行（如 sys_read）。
  4. 执行完把返回值放回寄存器，执行 sysret 切回用户态，glibc 继续往下走。

文件操作open / read / write / close / lseek / stat
内存brk / mmap / munmap

库函数 ≠ 系统调用：printf 是库函数，内部带缓冲区，攒够了才调一次 write 系统调用；malloc 也是库函数，小内存自己从内存池切，池不够才调 brk/mmap。能少陷入内核就少陷入，这是很多"用户态缓冲"设计的动机。

3 · 中断 / 异常 / 陷阱

三者都会让 CPU 暂停当前流程、陷入内核去处理，区别在于触发来源：

类型来源是否同步例子
中断 Interrupt（硬中断）外部硬件异步发来异步（跟当前指令无关）时钟中断、网卡收包、键盘按键、磁盘完成
异常 Exception（故障/终止）CPU 执行指令时内部出错同步缺页 page fault、除零、非法指令、段错误
陷阱 Trap（软中断）程序主动触发同步系统调用、断点调试

Linux 中断处理：上半部 / 下半部 Linux

中断处理要快（处理期间可能关中断，拖久了会丢中断）。Linux 把它拆成两半：

  • 上半部（Top Half，硬中断）：紧急、必须马上做的（比如把网卡数据从寄存器搬到内存），执行极短，关中断运行。
  • 下半部（Bottom Half，软中断/tasklet/workqueue）：耗时的后续处理（协议栈解析等）延后做，开中断，可被打断。top 里看到的 si（softirq）就是它。
面试常问：为什么要拆上下半部？因为硬中断处理期间通常屏蔽同类中断，如果在里面干重活，会长时间无法响应新中断（丢包、卡顿）。拆开后上半部秒退恢复响应，重活交给下半部慢慢干，兼顾实时性与吞吐。

4 · 进程与 PCB 高频

进程 = 一个正在运行的程序实例。程序是躺在磁盘上的静态代码，进程是它被加载进内存、分到资源、跑起来后的动态实体。进程是操作系统进行资源分配的基本单位（地址空间、打开的文件、信号等都以进程为单位）。

PCB：进程控制块

内核用一个结构体描述每个进程，即 PCB（Process Control Block），Linux 里就是 task_struct。它是"进程存在的唯一标志"，内容包括：

  • 标识：PID、PPID（父进程）、用户/组 ID。
  • 状态：运行/就绪/阻塞等（见 §5）。
  • CPU 上下文：各寄存器、程序计数器 PC、栈指针——切换时保存/恢复的就是它。
  • 内存信息：mm_struct（页表指针、各内存区域）。
  • 打开的文件：文件描述符表。
  • 调度信息：优先级、时间片、vruntime（CFS）。

堆和栈的区别（高频）：栈由编译器/系统自动管理（函数进出自动分配回收），空间小（默认 8MB）、快、局部变量；堆手动管理（malloc/free），空间大、灵活但慢、可能碎片和泄漏。栈向下长、堆向上长，中间那片空档留给二者伸展和 mmap。

6 · 线程 高频

线程 = 进程内的一条执行流，是 CPU 调度的基本单位。一个进程可以有多个线程，它们共享进程的地址空间和资源（代码、堆、全局变量、打开的文件），但各自独立的栈、寄存器、PC、栈指针——因为每条执行流的调用链和"当前执行到哪"都是独立的。

为什么要线程？

  • 更轻的并发：创建/切换比进程便宜（不用换地址空间和页表）。
  • 共享数据方便：同进程线程直接读写共享内存，无需 IPC。
  • 利用多核：一个进程的多个线程可同时跑在多个核上。

Linux 的线程实现 Linux：Linux 内核不严格区分进程和线程，统一用 task_struct 描述，都叫"任务(task)"。线程就是和别的任务共享地址空间等资源的 task。创建时都走 clone()，区别只在传的 flag：fork 不共享（拷贝），创建线程时传 CLONE_VM|CLONE_FILES|... 表示共享内存/文件。这就是"线程是轻量级进程(LWP)"的由来。用户库 NPTL 是 1:1 模型（一个用户线程对应一个内核线程）。

多进程 vs 多线程，实际怎么选？
要稳定隔离、互不影响（如 Nginx master/worker、Chrome 每个 tab 一进程）→ 多进程；要频繁共享大量数据、并发高→ 多线程。多进程更健壮（一个崩不拖累别的）但内存占用大、通信麻烦；多线程高效但一处内存越界可能全崩、且要小心锁。

8 · 上下文切换

CPU 从一个执行流切到另一个，要保存当前的"现场"、恢复目标的"现场"，这就是上下文切换。三种粒度、成本递减：

切换类型要保存/恢复什么成本
进程切换寄存器 + 切换页表（CR3） + 刷新 TLB + 内核栈最高（TLB 刷新后要重新建立映射，缓存也凉了）
线程切换（同进程）寄存器 + 内核栈；页表不变、TLB 不刷中等
模式切换（用户↔内核）只切特权级和栈，不换进程最低
为什么进程切换贵在 TLB？页表切换后，TLB（页表缓存）里全是旧进程的映射，得失效重建，之后一段时间访存都要走完整的多级页表翻译，慢。现代 CPU 用 PCID/ASID（地址空间标识）给 TLB 项打进程标签，避免全量刷新，缓解了这个问题。
切换的诱因：时间片用完、被更高优先级抢占、主动阻塞（等 I/O/锁）、系统调用中让出。vmstat 里的 cs 就是每秒上下文切换次数——数值异常高往往意味着锁竞争激烈或线程开太多。

9 · fork / exec / 写时复制 Linux

Linux 创建新进程的经典组合：fork() 复制出一个子进程，exec() 把它替换成另一个程序。

pid_t pid = fork();          // 复制当前进程
if (pid == 0) {              // 返回 0 → 我是子进程
    execve("/bin/ls", ...);  // 用 ls 程序把自己整个替换掉
} else if (pid > 0) {        // 返回子进程 PID → 我是父进程
    waitpid(pid, &status, 0);// 等子进程结束并回收
}
fork 一次返回两次：在父进程里返回子进程 PID（>0），在子进程里返回 0，出错返回 -1。就是靠这个返回值区分"我现在是谁"。子进程拷贝了父进程几乎所有东西（地址空间、打开的文件描述符），但有独立 PID。

写时复制 COW（Copy-On-Write）高频

如果 fork 真的把父进程整个地址空间物理拷贝一份，太浪费——何况很多时候 fork 完马上就 exec 换成别的程序，拷了也白拷。所以 Linux 用 写时复制：

  1. fork 时不真拷贝物理内存，父子进程的页表都指向同一批物理页，并把这些页标记为只读。
  2. 父子谁都只读时相安无事，共享同一份。
  3. 一旦有人写某页 → 触发缺页异常 → 内核这才为它复制一份该页、改成可写，双方从此各写各的。
好处：fork 变得极快（只拷页表、不拷数据），且只在真正写的时候按页复制，很多页从头到尾都不用复制。Redis 的 RDB 持久化正是靠 fork 出子进程 + COW，让子进程用"快照那一刻"的数据落盘，父进程照常服务（见 Redis 笔记）。

10 · 存储层次结构 高频

进内存管理之前，先建立硬件底座——为什么会有寄存器、L1/L2/L3 缓存、内存、磁盘这么多层？因为存储有条铁律：越快 → 越贵 → 容量越小；越慢 → 越便宜 → 容量越大。没有一种介质能同时做到"又快又大又便宜"，于是把它们分层堆叠，让数据在层与层之间流动，用小容量的快设备撑起大容量的快体验。

CPU 缓存：L1 / L2 / L3

这几层由硬件全自动管理，操作系统和程序员都不直接控制：

  • L1 通常再分 L1d（数据）和 L1i（指令），每个 CPU 核独占，最快最小。
  • L2 一般每核独占；L3 通常多核共享，最大。
  • 查找顺序：寄存器 → L1 → L2 → L3 → 物理内存，命中就返回，逐层往下找（miss 才去下一层）。
缓存行 Cache Line：缓存不是按字节搬，而是一次搬一整块，通常 64 字节。你读一个 int，它旁边的 60 字节会被一起拉进缓存——这正是空间局部性的硬件体现，也是"数组顺序遍历比跳着访问快得多"的原因。
两个高频延伸：① 伪共享 False Sharing——两个核各改一个变量，但它俩恰好落在同一缓存行，一个核写就让另一个核的缓存行失效、来回同步，性能暴跌；解决靠填充对齐到不同缓存行。② 缓存一致性 MESI——多核各有缓存副本，靠 MESI（Modified/Exclusive/Shared/Invalid）协议保证一致，这也是并发"可见性"问题（§21）的硬件根源。

串起来：一次数据访问走过的层

CPU 要一个数据 x → 寄存器有吗？→ L1 → L2 → L3 有吗？ (硬件自动查，命中即返回) → 都没有 → CPU 发出的是【虚拟地址】 → MMU 查 TLB / 多级页表，翻译成【物理地址】 (§12-14) → 该页在物理内存吗？ 在 → 从 DRAM 取（顺便把整条缓存行填进各级 Cache） 不在 → 缺页异常：从硬盘(文件/swap)加载进内存 → 再取 (§14)
记住这条金线：数据永远在"快而小"和"慢而大"之间流动，系统想尽办法让热数据待在上层。本笔记后面所有性能话题——TLB（§13）、缺页换页（§14）、局部性/抖动（§16）、零拷贝（§32）——都是这条金线的不同侧面。

11 · 为什么要虚拟内存 高频

如果程序直接用物理地址会有三个致命问题：① 进程之间没有隔离，A 能改 B 的内存；② 物理内存不够用（跑不了比内存大的程序）；③ 地址不确定，程序装载到哪就得改哪，无法多开。虚拟内存一次性解决：

进程看到的虚拟地址空间
每个进程都以为自己独占
一整块连续内存（如 64 位下 128TB）
MMU + 页表 翻译 ▶
物理内存 + 磁盘（swap）
实际零散分布
不够就换到磁盘
  • 隔离与保护：每个进程一套独立页表，访问不到别人的物理页；页表项还带权限位（只读/可执行），越权就报段错误。
  • 打破物理限制：程序用的是虚拟地址，暂时用不到的页可以先不加载或换到磁盘（swap），于是能跑比物理内存大的程序。
  • 连续假象：虚拟地址连续，物理页可以东一块西一块，解决外部碎片，也方便加载。
虚拟地址→物理地址：CPU 发出的都是虚拟地址，由硬件 MMU（内存管理单元）查页表翻译成物理地址。翻译失败（页不在内存/越权）就触发缺页异常或段错误交给内核。

12 · 分段 / 分页 / 段页式

方式思路优点缺点
分段按逻辑切（代码段/数据段/栈段），每段长度不等符合程序逻辑、便于共享和保护段长不等 → 外部碎片严重
分页按固定大小切（通常 4KB），虚拟页 ↔ 物理页帧无外部碎片、管理简单有内部碎片（最后一页填不满）；页表占空间
段页式先分段、段内再分页（现代主流）兼得两者优点地址翻译多一层
分页的核心概念：虚拟内存切成页(page)，物理内存切成同样大小的页帧(page frame)，页表记录"虚拟页号 → 物理页帧号"的映射。一个虚拟地址 = 页号 + 页内偏移；翻译时用页号查页表得到页帧号，页内偏移直接拼上去。Linux 默认页大小 4KB，也支持 2MB/1GB 的大页(HugePage)——大页能减少页表项和 TLB miss，适合数据库等大内存应用。
内部碎片 vs 外部碎片：内部——分配的块比实际需要大，块内部有浪费（分页的最后一页）。外部——空闲内存总量够，但都是零散小块，凑不出一段连续的大块（分段的老问题）。分页用固定大小消灭了外部碎片。

13 · 多级页表 & TLB 高频

问题：页表太大了

32 位、4KB 页、每个页表项 4 字节，单级页表要 2^20 × 4B = 4MB——而且每个进程都要一份，还大多是空的。64 位下更是天文数字。解决办法是多级页表：只为真正用到的地址区间建立下级页表，没用到的整块不建，省内存。

虚拟地址（x86-64，4 级页表） ┌──────┬──────┬──────┬──────┬────────────┐ │ PGD │ PUD │ PMD │ PTE │ 页内偏移 │ └──┬───┴──┬───┴──┬───┴──┬───┴────────────┘ │ │ │ └─→ 页表项 → 物理页帧号 │ │ └────────→ 逐级查找，每级一张表 │ └───────────────→ 未用到的分支整块不建 = 省内存 └──────────────────────→ CR3 寄存器指向顶级页表基址
代价：多级页表把"一次查表"变成"查 N 次表"，N 级页表访问一次内存要额外做 N 次访存，慢。用 TLB 来救。

TLB：页表的缓存（快表）

TLB（Translation Lookaside Buffer）是 MMU 里的一块小而快的缓存，存最近用过的"虚拟页号 → 物理页帧号"映射。

  • TLB 命中：直接拿到物理页帧号，一次访存搞定，飞快。
  • TLB 未命中：老老实实走多级页表翻译（page table walk），拿到后填回 TLB。
  • 命中率极高（靠局部性，见 §16），所以大多数访存不受多级页表拖累。
为什么进程切换要刷 TLB？TLB 里存的是虚拟页号，不同进程同一个虚拟页号映射到不同物理页，切进程后旧映射全失效，必须刷（或用 PCID 打标签避免全刷）。这也是进程切换比线程切换贵的原因之一（见 §8）。

14 · 缺页与页面置换 高频

缺页异常（Page Fault）

访问的虚拟页不在物理内存（还没加载、或被换到 swap）时，MMU 触发缺页异常，陷入内核处理：

  1. 检查地址是否合法（在进程的合法内存区域内），非法 → 段错误 SIGSEGV。
  2. 合法但没加载 → 找一个空闲页帧，从磁盘（文件/swap）把数据读进来，更新页表。
  3. 没有空闲页帧 → 用页面置换算法选一个"受害者页"换出去（脏页要先写回磁盘），腾出位置。
  4. 返回，重新执行刚才那条访存指令，这次成功。
缺页分两种：次缺页(minor)——页其实在内存里（如共享库已被别人加载、COW），只需建立映射，快；主缺页(major)——真要从磁盘读，慢。ps 里的 min_flt/maj_flt 就是它俩的计数。

页面置换算法

算法规则特点
OPT 最优换出"未来最久不用"的页理论最优，但要预知未来，无法实现，仅作基准
FIFO换出最早进来的页简单，但会有 Belady 异常（页帧变多缺页反而增多）
LRU 最近最少使用换出最久没被访问的页效果好、最常提；但要记录每页访问时间，硬件开销大
Clock 时钟/二次机会环形扫描 + 访问位，给最近用过的页"第二次机会"LRU 的低成本近似，实际系统（含 Linux）多用其改进版
Belady 异常：正常想法是"内存越大缺页越少"，但 FIFO 在特定访问序列下，增加页帧数缺页次数反而增加。LRU 和 OPT 属于"栈式算法"，不会有这个异常。这是 FIFO 的经典考点。
Linux 实际用的 Linux：近似 LRU 的双链表（active/inactive）方案：维护活跃链表和不活跃链表，页被访问就往活跃端移，回收时从不活跃链表尾部选受害者。配合 swappiness 参数调节"宁可换出匿名页还是回收文件缓存页"的倾向。

15 · Linux 内存分配 Linux

内核层：伙伴系统 + slab

伙伴系统
Buddy		管理物理页帧，以 2 的幂个连续页为单位（1,2,4,8…页）分配，解决外部碎片。释放时若相邻的"伙伴"也空闲就合并成更大块。
slab / slub伙伴系统最小也要一整页，但内核老要分配很多小对象（task_struct、inode）。slab 在伙伴系统之上做小对象缓存池：预先切好同类对象、复用已释放的，避免频繁向伙伴系统申请、减少内部碎片。

用户层：malloc 背后是什么 高频

malloc 是 C 库函数，不是系统调用。它向内核批发大块内存、自己零售：

  • 小内存（默认 < 128KB）：用 brk 系统调用抬高堆顶指针，从堆上切。释放时不一定立刻还给内核，留着复用（减少系统调用）。
  • 大内存（≥ 128KB）：用 mmap 直接向内核映射一块匿名内存，free 时 munmap 还回去。
为什么分两种？brk 管理的堆是连续的，只能从顶部收缩，中间的空闲块还不了内核（易碎片），但复用快、适合大量小分配；mmap 每块独立、能单独归还，适合大块。这也是为什么频繁分配释放小对象时，进程占用的内存（RSS）降不下来——被 malloc 留着复用了。
OOM Killer Linux：物理内存 + swap 都耗尽时，内核启动 OOM Killer，按"占用大、优先级低"的评分（oom_score）挑一个进程杀掉释放内存。服务器上常见"进程莫名被杀"就是它干的，dmesg 里能看到日志。

16 · 局部性原理 & 抖动

局部性原理是整个存储层次（寄存器→缓存→内存→磁盘）和 TLB、页面置换能高效工作的根本前提：

  • 时间局部性：刚访问过的数据/指令，很可能不久后再次被访问（循环变量、热点函数）。
  • 空间局部性：访问了某地址，附近的地址很可能接着被访问（数组顺序遍历、指令顺序执行）。
写代码怎么用它？数组按行遍历（顺着内存）比按列快很多（缓存行命中）；结构体把常一起用的字段放一起。这也是为什么"缓存"这个思想到处都是——CPU 缓存、TLB、页缓存、Redis，全靠局部性吃饭。

抖动 Thrashing

如果分给进程的页帧太少，装不下它的工作集（当前活跃使用的那批页），就会刚换出的页马上又要用、又换进来，CPU 大部分时间耗在换页 I/O 上、几乎不干正事——这就是抖动/颠簸。

怎么办？① 用工作集模型估算每个进程需要的页帧，保证够；② 内存实在不够就挂起部分进程（降低并发度），把页帧让给活跃进程。现象上：系统极卡、磁盘狂转、CPU 利用率看着不高（都在等换页 I/O）。

17 · 管道

进程各有独立地址空间，不能直接读对方内存，必须靠内核提供的 IPC（进程间通信）机制。先看最简单的管道：

类型特点
匿名管道 pipe()内核里的一块环形缓冲区，半双工（单向）、只能用于有亲缘关系的进程（父子，靠 fork 继承 fd）。shell 里的 ls | grep 就是它。
命名管道 FIFO以文件形式存在（mkfifo），任意两个进程都能用它通信，不要求亲缘关系。
管道的本质：内核缓冲区 + "像文件一样读写"的接口。写满会阻塞写端，读空会阻塞读端（天然的流量控制）。数据一次性，读走就没了，且是字节流没有消息边界。

18 · 消息队列 / 共享内存 / 信号量

机制原理特点
消息队列内核维护的消息链表，进程按消息收发有消息边界（不像管道是字节流）、可按类型读；但单条大小和总量有限
共享内存
Shared Memory		两个进程把同一块物理内存映射到各自地址空间最快的 IPC——数据不经过内核拷贝，直接读写同一块内存。但需自己用信号量做同步
信号量
Semaphore		一个计数器 + P(减/等待)、V(加/释放)原子操作本质是同步/互斥工具而非传数据，常给共享内存配套用
为什么共享内存最快？其它 IPC（管道、消息队列、socket）都要经过内核缓冲区，数据至少两次拷贝（用户→内核→用户）。共享内存映射的是同一份物理页，进程读写直达，无需内核中转，所以最快——代价是同步得自己管。
Linux 进程间通信有哪些方式？各自适用场景？
管道/FIFO：简单的单向数据流（shell 管道）。消息队列：需要消息边界、按类型收发。共享内存 + 信号量：大数据量、高性能，最快。信号：通知类事件（Ctrl+C、子进程结束）。socket：跨主机通信，也可本机（Unix domain socket）。按"要不要跨主机、数据量大小、要不要消息边界、性能要求"来选。

19 · 信号 signal

信号是一种异步通知机制（"软件中断"），用来告诉进程"发生了某件事"。它不传数据，只传"发生了几号事件"。

SIGINT (2)Ctrl+C，请求中断，可被捕获
SIGKILL (9)kill -9，强杀，不可被捕获/忽略
SIGTERM (15)请求终止（kill 默认），可捕获做优雅退出
SIGSEGV (11)段错误，非法内存访问
SIGCHLD (17)子进程结束，父进程可借此回收（防僵尸）
SIGSTOP / SIGCONT暂停 / 继续，SIGSTOP 同样不可捕获

进程收到信号后有三种反应：执行默认动作（多数是终止）、忽略、或捕获（注册信号处理函数 signal/sigaction 自定义处理）。SIGKILL 和 SIGSTOP 是唯二不能捕获也不能忽略的——保证系统总有办法杀死/暂停任何进程。

优雅关闭：服务程序通常捕获 SIGTERM，收到后停止接新请求、处理完手头的、关闭连接再退出。kill -9（SIGKILL）则是立即强杀，来不及清理，尽量少用。

20 · Socket

Socket 是最通用的 IPC——既能跨主机（走 TCP/IP，网络通信的基础），也能本机进程间通信（Unix domain socket，比走网络协议栈快，Nginx、Docker、MySQL 本地连接都用它）。

为什么 socket 通用？它把通信双方抽象成"读写一个文件描述符"，屏蔽了对方在本机还是远端。服务端 socket→bind→listen→accept，客户端 socket→connect，之后就 read/write。网络部分的细节（TCP 三次握手、拥塞控制等）属于计算机网络专题，这里只需知道它是进程通信的一种、且和文件描述符/epoll 直接挂钩（见 §31）。

21 · 竞态与临界区 高频

多个执行流并发访问共享资源，最终结果依赖于它们的执行时序——这就是竞态条件（Race Condition）。经典例子 count++ 其实是三步（读→加→写），两个线程交错执行就可能丢更新。

// 线程A、B 各执行 1000 次 count++，期望 2000，实际常小于 2000
读 count(=5) ┐         ┌ 读 count(=5)   ← B 读到的还是旧值
加 1 →6      │  交错   │
写回 6 ──────┘         └ 加1→6，写回 6   ← 两次自增只生效一次

并发问题的三个要素

  • 原子性：一组操作要么全做完、要么全不做，中间不被打断（count++ 不是原子的）。
  • 可见性：一个线程改了共享变量，别的线程能立刻看到（CPU 缓存可能让别人看到旧值）。
  • 有序性：编译器和 CPU 可能重排指令，多线程下可能出问题（需内存屏障）。

临界区：访问共享资源、必须互斥执行的那段代码。解决竞态的核心就是保证同一时刻只有一个执行流进入临界区——这就要靠锁等同步原语。

好的同步方案要满足：① 互斥（同时最多一个进临界区）；② 空闲让进（没人用时想进的能进）；③ 有限等待（不能无限期排队饿死）；④ 让权等待（进不去就让出 CPU，别空转）。

22 · 锁与同步原语 高频

原语机制适用
互斥锁 Mutex拿不到锁就阻塞睡眠，让出 CPU，被唤醒再抢临界区较长、可能等较久
自旋锁 Spinlock拿不到锁就忙等（空转），反复试，不睡眠临界区极短、多核；单核上自旋无意义
读写锁 RWLock读读共享、读写/写写互斥读多写少
信号量 Semaphore计数器，可允许 N 个同时进入（Mutex 是 N=1 的特例）控制并发数、资源池
条件变量 Cond让线程在某条件不满足时睡眠等待，条件满足由别人唤醒配合 Mutex，等待特定条件（如队列非空）
互斥锁 vs 自旋锁怎么选？关键看临界区时长和切换成本：临界区很短（几条指令）→ 自旋锁，忙等几下就拿到，比"睡眠+唤醒"两次上下文切换划算；临界区长或会阻塞 → 互斥锁，睡觉让出 CPU 给别人干活。自旋锁里绝不能睡眠或做耗时操作，否则别的核陪着空转烧 CPU。

底层基石：原子操作与 CAS

锁本身也要"抢"，靠的是 CPU 提供的原子指令。最常见的是 CAS（Compare-And-Swap）：比较内存值==预期?则改成新值:不改，整个过程原子。无锁数据结构、乐观锁、自旋锁都建立在 CAS 之上。ABA 问题：值从 A 变 B 又变回 A，CAS 以为没变过，加版本号解决。

用户态快锁 futex Linux：传统锁每次加解锁都陷入内核，慢。Linux 的 futex（Fast Userspace Mutex）在无竞争时全程在用户态用 CAS 搞定，只有真正发生竞争、需要睡眠/唤醒时才陷入内核。glibc 的 pthread_mutex 就基于 futex，这是"锁大多数时候很便宜"的原因。

23 · 经典同步问题

生产者-消费者

生产者往缓冲区放、消费者取，需要：缓冲区满时生产者等、空时消费者等，且对缓冲区的操作互斥。用两个信号量 + 一个互斥锁：empty（空位数）、full（数据数）、mutex（保护缓冲区）。这就是消息队列、线程池任务队列、Kafka 的底层模型。

生产者：P(empty); P(mutex); 放数据; V(mutex); V(full);
消费者：P(full);  P(mutex); 取数据; V(mutex); V(empty);
顺序不能错：必须先 P 资源信号量（empty/full），再 P 互斥锁 mutex。若反过来先拿 mutex 再 P(empty)，缓冲区满时生产者会抱着 mutex 睡死，消费者也拿不到 mutex 取数据 → 死锁。

读者-写者

允许多个读者同时读，但写者必须独占。核心是"第一个读者加写锁、最后一个读者放写锁"。有读者优先（写者可能饿死）和写者优先之分——读写锁（§22）就是它的封装。

哲学家就餐

5 个哲学家围桌，每人需同时拿起左右两根筷子才能吃。若所有人同时拿起左筷再等右筷 → 全体死锁。解法：① 限制最多 4 人同时拿筷；② 奇偶哲学家拿筷顺序相反（破坏循环等待）；③ 只有左右两筷都空闲才允许拿（一次拿两根）。这是死锁的经典教学模型。

24 · 死锁 高频

死锁：两个或多个进程互相持有对方需要的资源、都在等对方释放，谁也走不了、永久僵住。

产生的四个必要条件（缺一不可）

互斥资源同一时刻只能被一个进程占用
持有并等待已持有资源，还在等待新资源，且不释放已持有的
不可剥夺资源只能由持有者主动释放，不能被强抢
循环等待存在一个进程-资源的环形等待链（A等B、B等C、C等A）

处理策略

策略做法
预防（破坏必要条件）破坏其一即可：① 一次性申请全部资源（破坏"持有并等待"）；② 允许抢占（破坏"不可剥夺"）；③ 资源按固定顺序申请（破坏"循环等待"，最常用、最实用）
避免银行家算法：每次分配前判断分配后系统是否仍处于"安全状态"（存在一个能让所有进程都跑完的分配序列），不安全就不分配
检测 + 解除允许死锁发生，定期用资源分配图检测环；发现后靠"杀进程/回滚/抢资源"解除
鸵鸟策略假装看不见——死锁概率低时，重启了事。通用 OS（含 Linux）实际多用这个
工程上最实用的一招：固定加锁顺序。所有线程都按同一个顺序申请多把锁（比如永远先锁 A 再锁 B），就不可能出现环形等待，从根上杜绝死锁。转账场景"锁两个账户"时，按账户 ID 大小排序加锁是经典做法。
活锁 vs 饥饿：活锁——进程没阻塞，但都在不停重试同一个动作、互相谦让，状态一直变却没进展（两人过道互相让路）。饥饿——某进程因优先级低总排不上，长期得不到资源。死锁是"卡死不动"，活锁是"忙着但没进展"。

25 · 调度目标与时机

就绪队列里一堆进程/线程都想上 CPU，调度器决定下一个跑谁、跑多久。这是一场多目标权衡：

指标含义
CPU 利用率 / 吞吐量让 CPU 别闲着 / 单位时间完成的任务数（偏重后台批处理）
周转时间从提交到完成的总时间
响应时间从请求到首次响应的时间（偏重交互式，用户体验的关键）
公平性别让谁饿死，合理分配
抢占式 vs 非抢占式：非抢占——进程一旦上 CPU 就跑到主动让出（结束或阻塞），简单但一个长任务会拖垮响应。抢占式——时间片用完或更高优先级就绪时，内核强制换下当前进程。现代通用 OS（Linux/Windows）都是抢占式，保证交互流畅。

调度时机：进程结束、主动阻塞（等 I/O）、时间片用完、有更高优先级进程就绪、从内核态返回用户态时。

算法规则优缺点
FCFS 先来先服务按到达顺序，非抢占公平简单；但一个长任务在前会让后面短任务等很久（护航效应）
SJF/SRTF 短作业优先选运行时间最短的（抢占版=最短剩余时间优先）平均周转最优；但要预知运行时间，且长任务可能饿死
优先级调度按优先级高低选灵活；低优先级可能饿死 → 用老化(aging)随等待时间提升优先级来缓解

MLFQ 的巧思：它假设"短任务/交互任务优先级应该高"。新来的任务先给高优先级试跑，如果它很快就阻塞（典型交互/IO 型）→ 留在高优先级享受快响应；如果它一直占满时间片（典型 CPU 密集型）→ 逐级降到低优先级慢慢跑。既不需要预知运行时间，又自动区分了任务类型。

27 · Linux CFS 完全公平调度 Linux 高频

Linux 2.6.23 起普通进程用 CFS（Completely Fair Scheduler，完全公平调度器）。核心思想：让每个进程获得尽量公平的 CPU 时间，抛弃了固定时间片，改用 vruntime（虚拟运行时间）。

  • 每个进程记一个 vruntime，表示它"已经跑了多久"（按权重归一化）。调度器总是选 vruntime 最小的进程去跑——谁跑得少就补谁，从而公平。
  • 进程运行时 vruntime 增长；优先级（nice 值）影响增长速度：优先级高（nice 小、权重大）的进程 vruntime 长得慢，于是能更频繁被选中、拿到更多 CPU。
  • 用红黑树按 vruntime 排序组织就绪队列，取最小值 O(log n)，最左节点就是下一个要跑的。
红黑树（按 vruntime 排序）
最左节点 = vruntime 最小 → 下一个被调度
运行后 vruntime 增大 → 重新插入树中排队
nice 值决定权重：nice 越小权重越大，vruntime 增速越慢 → 分到更多 CPU
为什么用 vruntime 而不是固定时间片？固定时间片下，进程多了每个响应就慢。CFS 定义一个调度周期，让所有就绪进程在这个周期内都能跑一次，每个分到的时间按权重比例算——进程越多每份越小但依然公平，天然适应负载变化。实时任务另有 SCHED_FIFO/SCHED_RR 策略，优先级高于普通 CFS 任务。

磁盘比内存慢几个数量级（见 §10），所以 Linux 用空闲内存做文件的缓存——Page Cache 页缓存。普通的文件读写默认都要经过它，这是理解"数据库为什么要 fsync""Kafka 为什么快"的关键一环。

读：预读 + 命中

  • 命中：数据已在 page cache → 直接从内存拷给用户，不碰磁盘（热文件反复读几乎零 I/O）。
  • 未命中：从磁盘读入、顺便缓存起来；还会预读（readahead）——顺序读时提前把后面几页也读进来，利用空间局部性。

写：回写（write-back）

write 默认只把数据写进 page cache、标记为"脏页"就返回，并没真落盘。内核的回写线程（flusher）之后异步刷盘。触发刷盘的时机：脏页比例超阈值（dirty_ratio）、脏页存在太久（dirty_expire）、内存吃紧、或进程主动 fsync。

好处与风险：回写让写操作飞快、还能合并多次小写、顺序化刷盘。但代价是——数据只在 page cache 还没落盘时掉电/宕机，就丢了。这就是所有数据库都要面对的持久化问题。

fsync：强制落盘

fsync(fd)把该文件的脏页 + 元数据强制刷到磁盘，返回才保证落盘。数据库靠它保证持久化（如 MySQL redo log、Redis AOF 的 appendfsync）
fdatasync只刷数据（不含不影响读取的元数据），比 fsync 少一次元数据写，更快
O_DIRECT打开文件时指定，绕过 page cache 直接读写磁盘。数据库（如 InnoDB）常用它，因为自己有 buffer pool，不想被内核再缓存一层（双重缓存浪费内存）

mmap：把文件映射进内存

mmap 把文件直接映射到进程虚拟地址空间，之后像读写内存一样读写文件，省掉 read/write 那次"内核↔用户"拷贝（映射的就是 page cache 里的页）。缺页时才按需从磁盘加载。这也是零拷贝（§32）的手段之一。

面试串联：① free 命令里的 buff/cache 就是 page cache，它"占用"的内存在需要时可被回收，所以别被"内存快满了"吓到。② Kafka 快：顺序写 page cache（不立即刷盘）+ 消费时用 sendfile 从 page cache 直接发网卡（零拷贝），全程少碰磁盘、少拷贝。③ 数据库的两难：每次 fsync 保证不丢但慢，攒着批量刷快但可能丢——各家用 redo log / WAL + 组提交来平衡。
write 返回了，数据一定落盘了吗？
不一定。默认 write 只写到 page cache 就返回，数据还是脏页，靠内核异步回写，中间掉电会丢。要确保落盘必须显式调 fsync/fdatasync，或用 O_SYNC 打开。这就是数据库持久化的核心难点。

30 · I/O 五种模型 高频

一次网络读，数据要经历两个阶段：① 等待数据就绪（数据从网卡到达内核缓冲区）；② 拷贝数据（从内核缓冲区拷到用户缓冲区）。五种模型的区别就在这两阶段谁等、怎么等：

非阻塞 NIO不阻塞（轮询）阻塞read 没数据立即返回错误，得反复轮询（忙等浪费 CPU）
I/O 多路复用阻塞在 select/epoll阻塞一个线程用 select/poll/epoll 同时监听大量 fd，谁就绪处理谁。高并发的基石
信号驱动不阻塞（信号通知）阻塞数据就绪时内核发 SIGIO 通知，用得少
异步 AIO不阻塞不阻塞内核把两个阶段全干完，完成后才通知你。真正的异步，Linux 支持有限（io_uring 才成熟）

水平触发 LT vs 边缘触发 ET：LT（默认）——只要 fd 还有数据没读完，每次 epoll_wait 都持续通知，编程简单不易漏。ET——只在状态从无到有变化时通知一次，必须一次性把数据读干净（循环 read 到 EAGAIN），否则剩下的不再通知。ET 通知次数少、效率高，但编程要求高，Nginx 用 ET。
为什么 Redis 单线程还能扛高并发？
因为 Redis 用 epoll 做 I/O 多路复用：单个线程用 epoll 同时监听成千上万个连接，谁的数据就绪就处理谁，全程不阻塞在某个连接上。加上操作都是纯内存（快）、避免了多线程锁竞争和上下文切换，单线程反而简单高效。详见 Redis 笔记。

Reactor 模型：epoll 的上层用法 高频

epoll 只是"能同时监听一堆 fd"的机制，真正落地成服务器要有个套路把它组织起来——这就是 Reactor 模型：一个 Reactor 阻塞在 epoll_wait 上等事件，事件来了按类型分发（dispatch）给对应的 handler 处理。三种典型结构：

结构做法代表
单 Reactor 单线程一个线程既 epoll_wait 收事件，又处理业务Redis（命令执行本身单线程）
单 Reactor 多线程Reactor 线程只管 I/O 收发，业务逻辑丢线程池处理业务耗时的场景
主从 Reactor 多线程主 Reactor 只管 accept 新连接，分给多个从 Reactor，每个从 Reactor 各管一批连接的读写Nginx（多 worker）、Netty 默认
Reactor vs Proactor：Reactor 基于同步 I/O 多路复用（epoll）——它通知你"数据就绪了，你自己来读"。Proactor 基于异步 I/O（AIO）——内核把数据读好放进你的缓冲区，再通知你"读完了直接用"。对应 §30 的同步/异步之分。Linux 下 AIO 生态不成熟，所以主流高性能框架（Netty/Redis/Nginx）几乎都是 Reactor + epoll。

32 · 零拷贝 zero-copy 高频

传统"读文件→发网络"（如静态文件服务器）要经历4 次拷贝 + 4 次上下文切换，其中两次是无谓的 CPU 拷贝：

传统 read + write： 磁盘 ─DMA→ [内核缓冲区] ─CPU拷贝→ [用户缓冲区] ─CPU拷贝→ [socket缓冲区] ─DMA→ 网卡 ① ②(多余) ③(多余) ④ 每次 read/write 还各有一次用户↔内核态切换，共 4 次上下文切换

数据只是"过一遍用户态"就原样发走，中间那两次用户态拷贝纯属浪费。零拷贝就是省掉这些不必要的 CPU 拷贝和态切换：

技术做法
mmap + write用 mmap 把文件映射到用户空间，省掉"内核→用户"这次拷贝（用户和内核共享映射）。仍有一次内核内拷贝
sendfile数据全程在内核态流转，不进用户空间。文件→内核缓冲区→socket 缓冲区→网卡。用户态只发一条指令
sendfile + DMA gather / splice更进一步，连"内核缓冲区→socket 缓冲区"也省了，只传递描述符，实现真正的零 CPU 拷贝
谁在用？Kafka 用 sendfile 把日志文件直接发给消费者（高吞吐的关键之一）；Nginx 发静态文件用 sendfile；Netty 的 FileRegion 也是。面试串联：问到 Kafka/Nginx 为什么快，"零拷贝减少了数据拷贝和上下文切换"是标准答案。

33 · 磁盘调度

机械硬盘寻道（磁头移动）最耗时，磁盘调度算法就是优化磁头移动顺序来减少总寻道时间：

算法规则特点
FCFS按请求到达顺序公平但磁头可能来回乱跑
SSTF 最短寻道优先每次选离当前磁头最近的寻道短；但近处请求不断则远处饿死
SCAN 电梯算法磁头单向扫到头再折返，途经的顺路处理像电梯，避免饿死，最常用思想
C-SCAN扫到头直接回到起点重新单向扫（不反向服务）响应更均匀
SSD 时代还重要吗？固态硬盘没有机械寻道，随机访问和顺序访问差距小得多，磁盘调度的意义大幅下降。Linux 对 SSD/NVMe 默认用 none（不排序，multi-queue 直接下发）或 mq-deadline。所以这块了解思想即可，机械盘上才关键。

把前面的知识点串成一条完整链路——你在 shell 敲 ./a.out 回车，到程序跑完，操作系统做了什么：

1. 创建进程
shell 调 fork() 复制自己（COW，不真拷内存 §9），再 execve() 把子进程替换成 a.out：加载代码段/数据段，建立新页表，堆栈就位（§4）
▼
2. 调度上 CPU
新进程进就绪队列，CFS 按 vruntime 挑中它（§27），发生上下文切换切到它的地址空间（§8）
▼
3. 访存触发缺页
首次访问某页，页还没在物理内存 → 缺页异常，内核分配页帧、从磁盘加载、填页表、填 TLB（§12-14）
▼
4. 申请内存 / 读文件
malloc 不够时 brk/mmap 陷入内核要内存（§15）；read 文件走系统调用陷入内核（§2），可能阻塞等 I/O → 让出 CPU，调度别的进程
▼
5. I/O 就绪被唤醒
磁盘/网卡完成，发硬中断（§3），内核唤醒等待的进程回到就绪队列，等待再次被调度
▼
6. 退出与回收
main 返回调 exit，进程变僵尸态等父进程 wait 回收 PCB（§5）；内存页、fd 全部释放归还

附 · 性能排查速查 Linux 高频

"线上 CPU 飙高 / 内存涨 / 服务卡顿，你怎么排查？"——把前面的概念落到工具上。先看几个最容易混的指标：

load average：不是 CPU 使用率

uptime/top 顶部的 1/5/15 分钟负载，是这段时间内平均处于运行(R) + 不可中断(D) 状态的任务数。

load 和 CPU 使用率的区别（必问）：CPU 使用率只看"CPU 在忙没忙"；load 还算上了等磁盘 I/O 的 D 状态任务。所以磁盘卡住时，一堆任务卡在 D 态，load 很高但 CPU 使用率不高——这正是判断"到底是 CPU 瓶颈还是 I/O 瓶颈"的关键线索。经验判断：load 持续 > CPU 核数，说明任务在排队。

top 里的 CPU 几个百分比

us用户态耗时。高 → 应用自身在狂算，用 perf 找热点函数
sy内核态耗时。高 → 系统调用/上下文切换频繁（锁竞争、fork 过多）
wa等待 I/O 的时间。高 → 磁盘是瓶颈，转去看 iostat
si/hi软/硬中断耗时。高 → 网络包量大（网卡中断），看是否需要多队列/RPS
id空闲

常用工具速查

工具看什么
top / htop整体 CPU/内存、各进程占用、load
vmstat 1r(运行队列长度) b(阻塞数) si/so(换页,非0说明在用 swap 了) cs(上下文切换) in(中断)
iostat -x 1磁盘 %util(繁忙程度,接近100%=打满) await(平均 I/O 延迟)
free -h内存;注意 buff/cache 是 page cache(可回收,别当成内存不够,见 §29)
pidstat 1按进程/线程看 CPU、I/O、缺页
strace -p <pid>跟踪进程的系统调用,查它卡在哪个 syscall(如卡在 read/futex)
perf top / 火焰图找 CPU 热点函数,us 高时的利器
lsof -p <pid>进程打开的文件/fd(排查 fd 泄漏、"删了文件空间没释放"，见 §28)
套路举例：① CPU 高 → top 看 us 还是 sy：us 高用 perf 抓热点函数；sy 高看 vmstat 的 cs（上下文切换/锁竞争）。② 服务卡顿但 CPU 不高 → 看 load 和 top 的 wa，大概率 I/O，转 iostat 看 %util/await。③ 内存持续涨 → free 看是真占用还是 buff/cache；pmap/pidstat 定位进程；警惕被 OOM Killer 杀（§15，dmesg 里查）。④ 进程僵住 → strace 看卡在哪个系统调用，D 状态多半在等 I/O。

附 · 高频面试速记

问题一句话答案
进程 vs 线程进程是资源分配单位（独立地址空间），线程是 CPU 调度单位（共享进程资源、独立栈和寄存器）；进程切换要换页表刷 TLB，更贵。
用户态 vs 内核态CPU 特权级之分。内核态能执行特权指令、访问所有资源；用户态受限，要越权只能通过系统调用/中断/异常陷入内核。
存储层次结构寄存器→L1/L2/L3→内存→SSD→硬盘，越上层越快越小越贵。靠局部性把热数据往上层挪。内存比机械盘快约百万倍，所以减少磁盘 I/O 是性能第一要务。缓存按 64 字节缓存行搬运。
物理/虚拟内存/硬盘物理内存=真实内存条；虚拟内存=OS 给每进程画的独占大饼，虚拟地址经页表+MMU 翻译到物理地址；硬盘既做持久化，又做 swap 兜底（内存不够时换出页）。
为什么要虚拟内存进程隔离与保护、打破物理内存大小限制、提供连续地址假象。靠页表 + MMU 把虚拟地址翻译成物理地址。
多级页表 + TLB多级页表按需建表省内存，但查表变慢；TLB 缓存常用映射，靠局部性命中，抵消多级开销。
缺页处理 / 置换访问不在内存的页触发缺页异常，内核加载该页；没空闲页帧就按 LRU/Clock 换出受害者。FIFO 有 Belady 异常。
写时复制 COWfork 时父子共享只读物理页，谁写谁才复制该页。让 fork 快、省内存（Redis RDB 靠它）。
死锁四条件 / 破解互斥、持有并等待、不可剥夺、循环等待。工程上最实用：按固定顺序申请锁破坏循环等待。
互斥锁 vs 自旋锁临界区短用自旋（忙等省切换），长用互斥（睡眠让出 CPU）。自旋锁里不能睡眠。
僵尸 vs 孤儿进程僵尸：子死父没 wait 回收，残留 PCB（有害）；孤儿：父先死，子被 init 收养（无害）。
select/poll/epollepoll 用红黑树常驻 fd（不重复拷贝）+ 就绪回调链表（O(1) 找就绪），适合海量连接。LT 默认，ET 高效但要读干净。
五种 I/O 模型阻塞/非阻塞/多路复用/信号驱动/异步。前四种同步（用户参与数据拷贝），只有 AIO 是真异步。多路复用本质是同步阻塞。
Reactor 模型基于 epoll 的事件分发架构：单Reactor单线程(Redis)、单Reactor多线程、主从Reactor(Nginx/Netty)。Reactor=同步+epoll，Proactor=异步+AIO。
Page Cache / write文件读写默认走 page cache；write 只写缓存标脏页就返回，靠回写异步刷盘，掉电会丢。要落盘必须 fsync；数据库常用 O_DIRECT 绕过。
文件描述符三张表fd 表(每进程)→打开文件表(全局,含 offset)→inode。fork 后父子共享打开文件表项→共享 offset；dup2 实现重定向。
load vs CPU 使用率load 含运行(R)+不可中断(D,等I/O)任务数；CPU 使用率只看 CPU 忙不忙。I/O 卡时 load 高但 CPU 不高——用来区分 CPU 瓶颈还是 I/O 瓶颈。
零拷贝sendfile/mmap 减少数据在内核↔用户间的多余拷贝和上下文切换。Kafka、Nginx 高吞吐的关键。
Linux CFS按 vruntime（虚拟运行时间）红黑树排序，总选最小的跑，实现完全公平；nice 值调节权重。
中断上下半部上半部（硬中断）紧急、极短、关中断；下半部（软中断）延后干重活、开中断。兼顾实时性与吞吐。
fork 返回值父进程里返回子 PID，子进程里返回 0，出错返回 -1。靠它区分身份。
