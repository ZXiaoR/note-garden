❓ 02.1 · 程序和进程有什么区别？内核靠什么管住进程？进程的内存布局长什么样？

📦 02.1 进程与 PCB（Linux task_struct）及虚拟地址空间布局

程序（Program）是静静躺在磁盘上的可执行二进制文件（如 ELF 格式的 ./a.out）；而进程（Process）是程序被加载进内存、分配了系统资源、正在运行的一个动态实例。一句话定性：进程是操作系统进行「资源分配」的基本单位（独立的虚拟地址空间、打开的文件描述符表、信号处理等都归进程所有）。

🪪 PCB 进程控制块（Linux struct task_struct） 进程存在的唯一标志

内核创建进程时，首先在内核空间分配一个 task_struct 结构体（约几 KB，由 Slab 分配器管理），里面装满了该进程的全部身家：

① 身份标识：pid（内核任务/线程 ID）、tgid（线程组 ID，即用户看到的进程 PID）、ppid（父进程）、cred（UID/GID 权限凭证）。
② 状态与调度：__state（R/S/D/Z/T 状态）、优先级 prio / nice、调度实体 sched_entity（含 CFS 的 vruntime）。
③ CPU 硬件上下文：thread_struct（当进程被切换下 CPU 时，保存它的寄存器、程序计数器 PC/RIP、内核栈指针 RSP）。
④ 内存描述符：struct mm_struct *mm —— 指向该进程的虚拟内存区链表/红黑树（VMA）与顶级页表基址（pgd，加载进 CR3）。
⑤ 打开文件与信号：struct files_struct *files（进程 fd 表）、signal_struct（信号处理表）、当前工作目录 fs_struct。
🗺️ 进程虚拟地址空间布局（x86-64，48位 256TB） 高地址 ──▶ 低地址
🛡️ 内核空间 Kernel Space (高 128 TB) 所有进程页表共享同一份内核映射
⬇️ 栈区 Stack（向下增长，默认上限 8MB） 局部变量、函数调用帧、返回地址
↕️ 文件映射与匿名映射区 (mmap / vDSO) 动态库 .so、大块 malloc(初始 ≥128KB)
⬆️ 堆区 Heap（向上增长，靠 brk 扩张） 小块 malloc / new 动态分配
📦 BSS 段（未初始化全局/静态变量） 磁盘不占空间，加载时映射零页清零
📝 Data 数据段（已初始化全局/静态变量） 可读写，初始值来自可执行文件
🔒 Text 代码段 &只读常量区 (.rodata) 存机器指令与字符串常量（只读防篡改）
💡 高频必答：1. 堆（Heap）和栈（Stack）有什么区别？ 2. 为什么所有进程要共享映射同一份内核空间（以及开启 KPTI 后的变化）？
• 栈 vs 堆：栈由编译器自动分配释放（移动 RSP 栈顶指针即可，速度快、无碎片，但空间小默认 8MB，递归太深会 Stack Overflow）；堆由程序员手动 malloc/free 或语言 GC 管理（空间大、生命周期灵活，但分配相对慢、易产生内存碎片与内存泄漏）。
• 为什么每个进程高地址都映射同一份内核空间？在经典设计（或开启 nopti）下，当进程执行 syscall 从用户态陷入内核态时，由于内核空间已映射在当前进程页表的高地址区，CPU 只需把特权级切到 Ring 0 就能直接访问内核代码和当前进程数据，无需切换 CR3 页表（用户态 Ring 3 因页表项权限位 U/S=0 限制，直接访问高地址会触发 SIGSEGV）。
• 📌 与 01.2 KPTI（内核页表隔离）的衔接：自 Meltdown 漏洞补丁 KPTI 默认开启后，为防止用户态侧信道窥探内核内存，用户态页表的高地址区只保留极少量的内核入口跳板代码（Trampoline，如 entry_SYSCALL_64 与中断入口）；陷入 Ring 0 后，入口代码会立即将 CR3 切换到包含完整内核映射的内核页表（借助硬件 PCID 避免全量刷空 TLB）。

状态码 内核名称 精准含义与生产故障信号
R TASK_RUNNING 运行态 + 就绪态合体：既包括正在 CPU 上跑的，也包括排在运行队列（Runqueue）里等待 CPU 的。
S TASK_INTERRUPTIBLE 可中断睡眠（最常见）：在等网络 socket 数据、sleep 或 futex 锁，收到信号（如 kill）可以立刻被唤醒响应。
D TASK_UNINTERRUPTIBLE
(及 TASK_KILLABLE)		 不可中断睡眠：正在内核深处跟硬件打交道（如等待磁盘 DMA 同步读写、NFS 网络存储挂死）。传统 TASK_UNINTERRUPTIBLE 屏蔽所有信号，连 kill -9 都无法立刻终止它（需等底层 I/O 返回）；线上出现大量 D 态进程且 load average 飙升，通常说明磁盘或存储网络发生阻塞。
💡 进阶补充：Linux 2.6.25 起引入了 TASK_KILLABLE（TASK_UNINTERRUPTIBLE | TASK_WAKEKILL），在 ps/top 中同样显示为 D，但允许响应 SIGKILL 等致命信号（现代 NFS 客户端与部分 VFS 锁路径已采用该状态以支持 kill -9 脱困）。
Z EXIT_ZOMBIE 僵尸态（Zombie）：子进程已经执行完 exit() 死了（内存和文件都已释放），但父进程还没调用 wait()/waitpid() 读取它的退出码（收尸），导致内核不敢释放它那几 KB 的 task_struct PCB，白白霸占一个 PID 号！
T / t TASK_STOPPED / TRACED 暂停/跟踪态：收到 SIGSTOP（如终端按 Ctrl+Z 挂起后台）或被 gdb / strace 断点暂停。
🚨 必考辨析：僵尸进程（Zombie）vs 孤儿进程（Orphan）—— 怎么杀僵尸？容器里为什么容易爆僵尸？
1. 孤儿进程（无害）：父进程先死了，子进程还活着 → 子进程会被 init / systemd（PID = 1，或容器/子收割进程）自动收养，等子进程结束时由 PID 1 负责调用 wait 回收。
2. 僵尸进程（有害）：子进程死了，父进程还活着却不调 wait/waitpid 也不处理 SIGCHLD 信号 → 残留 PCB 占着 PID，积累多了会导致全系统 fork: Resource temporarily unavailable（PID 耗尽，查看 /proc/sys/kernel/pid_max）！
3. 为什么 kill -9 僵尸PID 没用？怎么清理？因为僵尸进程已经死了，你无法再杀一个死人！正确清理方法：给它的父进程发 kill -SIGCHLD 父PID，或者直接 kill 掉不称职的父进程——父进程一死，这群僵尸就变成“孤儿僵尸”过继给 PID 1 (init)，init 会瞬间调用 wait 把它们全部清理干净！
4. 🐳 容器（Docker/K8s）高频坑：容器里你的业务主进程往往直接作为 容器内的 PID 1 运行。如果你的业务进程（或子进程）拉起了孙子进程且没有写 wait() 回收逻辑，容器中又没有真正的 init，就会在容器里堆积成千上万个僵尸进程！解法：Dockerfile 使用 tini / dumb-init 作为 ENTRYPOINT（或 docker run --init），让专门的轻量级 init 进程当 PID 1 替你回收僵尸。
❓ 02.3 · 进程、线程、协程到底怎么区分？同一进程的多线程共享什么、独占什么？

🧵 02.3 线程本质与「进程 vs 线程 vs 协程」终极对比 高频必考

早期只有进程时，干多件事就得 fork 多个进程——但进程之间虚拟内存完全隔离，传点数据都得走昂贵的 IPC，切换还要刷页表。于是人们把“资源所有权”和“CPU 执行流”拆开：进程只管占着那套房子（虚拟内存、文件句柄），而在房子里跑的多条独立执行流就是「线程（Thread）」——线程是 CPU 调度的基本单位！

🏠 同进程多线程「共享」什么？（房子里的公共设施）
  • 整套虚拟地址空间（页表 mm_struct）：代码段（Text）、已初始化/未初始化数据段（Data/BSS，即全局变量与静态变量）、堆内存（Heap）、动态库映射区。
  • 进程级内核资源：打开的文件描述符表（fd table）、当前工作目录、用户/组 ID、进程 PID、信号的处理函数配置（Signal Dispositions）。
🎒 每个线程「独占」什么？（每条执行流随身背的包）
  • 独立的调用栈（Stack）：包括用户态栈（存各自函数的局部变量、参数、返回地址）和独立的内核栈。（注意：线程栈在同一个虚拟地址空间里，若指针越界传出去，别的线程其实也能访问到，但逻辑上各自独立！）
  • 独立的 CPU 寄存器上下文：程序计数器 PC/RIP（当前执行到哪行指令）、栈指针 SP、通用寄存器。
  • 线程专属元数据：线程 ID（TID）、线程局部存储（TLS / __thread）、独立的 errno、独立的信号屏蔽字（Signal Mask）与调度优先级。

📊 进程 vs 线程 vs 协程（Coroutine / Goroutine）三维全景对照表

对比维度 进程 (Process) 内核级线程 (Thread / KLT) 用户态协程 (Coroutine / Goroutine)
核心定位 资源分配的基本单位 操作系统 CPU 调度的基本单位 用户态运行时调度的轻量级执行流

最佳适用场景 要求高强隔离与稳定性（浏览器 Tab、PostgreSQL backend） CPU 密集型计算（吃满多核）或常规多核并行服务 海量高并发 I/O 密集型业务（网关、微服务、长连接推送）
🐧 Linux 内核的秘密：在 Linux 内核眼里，其实根本没有“线程”这个特殊结构！
Linux 采用「轻量级进程（LWP）」+ 用户态 NPTL 1:1 模型：内核里无论进程还是线程，统统都是一个 struct task_struct，并且底层全部调用同一个 clone() 系统调用创建！
• 当你调 fork() 创建新进程时：相当于调 clone(SIGCHLD, 0)，内核把父进程的虚拟内存描述符 mm_struct、文件表 files_struct 等独立复制一份；
• 当你调 pthread_create() 创建新线程时：相当于调 clone(CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, ...)，新造出来的 task_struct 直接把指针指向父任务的同一个 mm_struct 和 files_struct！在内核看来，线程就是一群共享了同一套房子的 task_struct！
❓ 02.4 · 进程切换到底慢在哪里？fork() 一次返回两次和写时复制 (COW) 是怎么工作的？

⚡ 02.4 上下文切换成本拆解 & fork() / execve() 写时复制 (COW)

1️⃣ 三种切换粒度的真实成本对比

切换类型 硬件与内核做了什么？ 隐藏的“隐形性能杀手”在哪？
① 特权模式切换
(用户态 ↔ 内核态)		 同一线程内，Ring 3 ↔ Ring 0，保存通用寄存器到内核栈。 开销最小（~百纳秒），主要损耗在指令流水线冲刷与 KPTI 页表切换。
② 同进程线程切换
(Thread A → Thread B)		 陷入内核，保存 Thread A 的 CPU 寄存器与内核栈指针，恢复 Thread B 的寄存器与栈；CR3 页表基址不变！ TLB 快表不失效！但若切到不同逻辑核或访问不同数据，L1/L2 Cache 热度可能下降（~1 μs）。
③ 跨进程上下文切换
(Process A → Process B)		 除保存/恢复寄存器与内核栈外，必须把新进程的顶级页表地址写入 CR3 寄存器，切换整个虚拟地址空间！ 最贵在 TLB 刷新与 Cache 变冷！一旦换了 CR3，旧进程的 TLB 地址映射缓存失效（现代 CPU 引入 PCID/ASID 给 TLB 条目打进程标签以避免全刷），且 L1/L2/L3 缓存里全是旧进程的数据，新进程刚跑起来时处处触发 Cache Miss 和 Page Table Walk！

2️⃣ Linux 创建进程的黄金搭档：fork() + execve() + 写时复制 (COW) 高频必考

在 Linux 中，除了 0 号/1 号祖先进程外，所有新进程都是由父进程先调 fork() “克隆自己”，再在子进程里调 execve() “偷梁换柱加载新程序”造出来的：

🐧 fork_exec_demo.c · 为什么 fork() 调用一次，却会返回两次？ 
pid_t pid = fork();  // 克隆当前进程：内核复制 PCB 与页表，父子从下一行同时往下跑！

if (pid == 0) {
    // ① 返回 0 ──▶ 说明当前执行流是【子进程】（子进程调 getpid() 拿自己 PID，getppid() 拿父 PID）
    execve("/bin/ls", argv, envp); // 用 /bin/ls 的代码段/数据段彻底替换当前虚拟内存，一去不复返
} else if (pid > 0) {
    // ② 返回 > 0（子进程真实的 PID）──▶ 说明当前执行流是【父进程】
    waitpid(pid, &status, 0);      // 父进程等待子进程结束并回收 PCB，防止产生僵尸进程
}
🧬 写时复制（Copy-On-Write, COW）三步物理推演：为什么 fork() 不直接拷贝物理内存？
Step 1 · 刚 fork() 完瞬间
内核只把父进程的页表（PTE）复制一份给子进程，0 字节拷贝物理内存！父子页表指向完全相同的物理页帧，但内核偷偷把双方的页表项权限全部改成「只读 (Read-Only)」。
Step 2 · 父或子尝试修改某页
只要双方只读就永远共享同一份物理内存；一旦父进程（或子进程）往某一个 4KB 页写入数据，MMU 发现该页是只读的，当场触发写保护缺页异常（Page Fault）陷入内核！
Step 3 · 按需分配新页并解绑
内核在缺页处理中发现它是 COW 页，这才只把这一个被修改的 4KB 物理页拷贝一份新副本，让写入方指向新页并恢复双方为「可写」，未修改的其余百万个页继续共享！
🔥 生产必考联动（Redis RDB 快照与 THP 透明大页延迟抖动）：
• 为什么 Redis `bgsave` 能不阻塞主线程？因为主线程调 fork() 时只复制页表，子进程拿着 fork 那一刻的只读内存快照写 RDB 文件，主线程继续处理客户端读写（只对被修改的热点页触发 COW 复制）。
• ⚠️ 两个隐藏工程坑：① 如果 Redis 实例较大（如几十 GB），光是复制几百万个页表项就要耗时几十到上百毫秒，期间主线程仍会停顿；② 如果开启了透明大页（Transparent Huge Pages, THP，单页 2MB）：在旧内核（< 5.8）中，COW 写保护缺页会直接复制整整 2MB 物理大页（写放大 512 倍）；Linux 5.8+ 优化为匿名 THP 在 COW 缺页时先拆分成 512 个 4KB 页（split_huge_pmd）再拷贝，但拆分大页的页表锁开销、后台 khugepaged 线程扫描合并 4KB 页时的锁争用、以及分配连续 2MB 物理页触发的内存规整（Direct Compaction），依然会在高并发写场景下引发明显的延迟毛刺。因此生产部署 Redis / MySQL 仍建议关闭 THP（echo never > /sys/kernel/mm/transparent_hugepage/enabled）。
