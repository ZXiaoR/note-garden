❓ 03.1 · 为什么要有 L1/L2/L3、内存、硬盘这么多层？什么是 64B 缓存行与伪共享？

🏔️ 03.1 存储层次金字塔、64B 缓存行（Cache Line）与伪共享 高频必考

进入内存管理之前，必须先建立硬件物理直觉——为什么计算机里会有寄存器、L1/L2/L3 缓存、DRAM 内存、SSD、机械盘这么多层？因为半导体物理有一条铁律：越快 → 造价越贵 → 容量越小；越慢 → 造价越便宜 → 容量越大。没有任何一种介质能同时做到“又快、又大、又便宜且断电不丢”，于是工程师把它们分层堆叠成金字塔，靠局部性原理把热数据留在上层快设备里：

存储层级 典型容量 真实访问延迟 放大成人类感知时间 由谁管理？
寄存器 Register 几百 Bytes ~0.3 ns (1 周期) ⏱️ 1 秒（伸手拿桌上的笔） 编译器（寄存器分配）
L1 Cache (L1d/L1i) 32 ~ 64 KB / 核 ~1 ns (~4 周期) ⏱️ 3 秒（转身拿书架上的书） CPU 硬件全自动（每核独占）
L2 Cache 256 KB ~ 2 MB / 核 ~4 ns (~12 周期) ⏱️ 12 秒（走到隔壁房间拿） CPU 硬件全自动（每核独占）
L3 Cache (LLC) 几十 MB（多核共享） ~15 ns (~40 周期) ⏱️ 45 秒（去同楼层茶水间） CPU 硬件全自动（多核共享）
物理内存 DRAM 16 GB ~ 几百 GB ~80 - 100 ns 🚶 5 分钟（下楼去小区便利店） 操作系统内核（页表/伙伴系统）
NVMe / SATA SSD 几百 GB ~ 几 TB ~20 - 100 μs 🚗 1 ~ 3 天（自驾去外省） OS 文件系统 / 块设备层
HDD 机械硬盘 几 TB ~ 二十几 TB ~5 - 10 ms (寻道) 🚀 6 ~ 10 个月（坐飞船去火星） OS 文件系统 / 磁盘调度器
⚡ CPU 缓存必考三剑客：64B 缓存行（Cache Line）· 伪共享（False Sharing）· MESI 一致性
① 64 字节缓存行 (Cache Line)
CPU 缓存和内存之间搬运数据不是按单字节搬，而是每次整块搬运 64 Bytes！你读 arr[0]（4字节），紧挨着的 arr[1]~arr[15] 会顺便被拉进 L1 Cache——这就是为什么二维数组按行遍历比按列遍历快几倍！
② 伪共享 (False Sharing) 灾难
结构体里紧挨着两个独立变量 struct { long a, b; }，落在同一个 64B 缓存行里。Core 1 狂改 a、Core 2 狂改 b，每次写都会让对方核上的整条缓存行强制失效（Invalid），两核缓存乒乓失效，性能暴跌 10 倍！
👉 解法：加填充字节对齐到 64B（如 Java @Contended、Go cpu.CacheLinePad、C++ alignas(64)）。
③ MESI 协议与 Store Buffer
多核各自有 L1/L2，靠硬件 MESI 状态机（Modified已改 / Exclusive独占 / Shared共享 / Invalid失效）通过总线嗅探保持一致；又为了不等别的核确认失效，CPU 引入了异步的 Store Buffer 与 Invalidate Queue，这也是并发编程出现“可见性与指令重排”（需内存屏障）的硬件根源！
❓ 03.2 · 为什么要搞虚拟内存？分段、分页、段页式和内部/外部碎片怎么区分？

🎭 03.2 为什么需要虚拟内存？分段、分页与段页式对比 高频必考

如果让程序直接读写主板上的物理内存地址，会立刻撞上三个致命问题：① 毫无安全隔离，进程 A 一个野指针就能改掉进程 B 或内核的数据；② 物理内存不够用，16GB 内存跑不了总和 30GB 的几个程序；③ 运行地址不固定且有外部碎片，程序每次加载到物理内存不同位置都要重写所有跳转地址。

于是操作系统引入了 虚拟内存（Virtual Memory）：给每个进程画一张“你独占一整块连续超大内存”的大饼（64 位下用户态高达 128TB），进程指令里发出的全都是「虚拟地址」，由 CPU 硬件里的 MMU（内存管理单元） 查「页表」实时翻译成真正的「物理地址」！

① 进程视角：连续虚拟页 (Page)
进程 A 和进程 B 都可以访问虚拟地址 0x401000。
• 隔离保护：各自的页表将其映射到完全不同的物理页帧，互不可见；页表项带 R/W/X 权限位，写只读页直接触发段错误。
• 共享内存：若把两个进程的页表指向同一个物理页（如 glibc 动态库代码段），又能省下大量物理内存！
② 硬件翻译：MMU + 页表 + DRAM
虚拟空间按固定大小切成 4KB 虚拟页（Page），物理内存条也切成 4KB 物理页帧（Page Frame）。
• 消除外部碎片：虚拟地址连续的 10 个页，在物理内存条上可以东一页、西一页完全零散存放，只要页表连得上就行！
③ 突破容量：按需加载 + 磁盘 Swap
• 按需调页：没访问到的虚拟页根本不分配物理内存；
• 换入换出 (Swap)：物理内存吃紧时，内核把长期不用的冷匿名页换出到磁盘 swap 分区，要用时再触发缺页换回来。

📐 分段 vs 分页 vs 段页式 & 内部碎片 vs 外部碎片

管理方式 切分粒度与寻址思路 核心优点 致命缺点（碎片类型）
分段 (Segmentation) 按程序逻辑模块切（代码段、数据段、栈段），段号 + 段内偏移，每段长度不一。 符合程序员逻辑直觉，方便按整段设置只读/可执行权限与共享。 段长短不一，反复分配释放后留下一堆夹缝空洞 ──▶ 严重的「外部碎片」，换入换出整段大内存极慢。
分页 (Paging) 不管逻辑，一律按固定尺寸（Linux 默认 4 KB）切块，虚拟页号 + 12位页内偏移。 彻底消灭外部碎片！任何空闲物理页帧都能塞进任何一个虚拟页；换页粒度固定为 4KB。 假如你只存 100B 数据也要分一整页 4KB，页内剩余空间浪费 ──▶ 存在少量「内部碎片」（最多浪费不超 1 页）。
段页式 先按逻辑切成段，每个段内部再按 4KB 切成页（x86 早期做法；64位 Linux 将所有段基址全设为 0 扁平化，实质上纯用分页！） 兼具逻辑隔离与物理零外部碎片。 硬件地址翻译多一次查段表开销。
❓ 03.3 · 为什么不能用单级页表？x86-64 四级页表是怎么切分 48 位地址的？TLB 又起什么作用？

🗂️ 03.3 多级页表（x86-64 四级页表）与 TLB 快表加速 高频必考

先算一笔账：为什么不能用一张简单的一维数组（单级页表）？
在 32 位系统下（4GB 空间，4KB 一页，共 $2^{20} \approx 100\text{万}$ 个页，每项 4B），单级页表必须连续占 4 MB——如果跑 100 个进程，光页表就吃掉 400MB！到了 64 位系统（x86-64 使用低 48 位虚拟地址 = 256 TB，共 $2^{36}$ 个 4KB 页，每项 8B），如果建单级页表，光一个进程的页表就要占 $2^{36} \times 8\text{B} = 512\text{ GB}$ 物理内存！这根本不可能实现！

💡 多级页表的降维打击思路（按需建表，像书的「章→节→小节」目录）：
既然绝大多数进程只用到了 256TB 里的几十分之一，其余大片虚拟地址全是空的，那我们就把页表拆成 4 级树状目录——只要某个一级目录项（覆盖 512GB）完全没用到，它下面的二级、三级、四级子页表就根本不用分配内存！

📐 x86-64 四级页表黄金切分公式：9 + 9 + 9 + 9 + 12 = 48 bits（每级页表刚好占 1 个 4KB 页 = 512 项 × 8B）
PGD (全局目录)
9 bits [47:39]
2⁹=512项 · CR3指向它
PUD (上级目录)
9 bits [38:30]
每项管 1 GB (1G大页)
PMD (中间目录)
9 bits [29:21]
每项管 2 MB (2M大页)
PTE (页表项)
9 bits [20:12]
存 4KB 物理页帧号 PFN
Offset (页内偏移)
12 bits [11:0]
2¹² = 4096B (直拼物理页)
🐢 多级页表的代价：访存次数暴增 4 倍！
页表本身也是存在物理内存 DRAM 里的！如果没有缓存，CPU 读一个变量，MMU 得先去内存读 PGD ──▶ PUD ──▶ PMD ──▶ PTE（4 次内存访问），拿到物理地址后再做第 5 次 内存访问取真正的数据（这一过程叫 Page Table Walk），慢得没法用！
⚡ 救星 TLB（快表 / 页表硬件缓存）：
CPU 在 MMU 内部做了一块极快的硬件相联缓存 TLB（Translation Lookaside Buffer），专门缓存最近用过的「虚拟页号 VPN ──▶ 物理页帧号 PFN」映射：
• TLB 命中（>99% 概率）：0 次查页表，1 次物理访存直接拿数据！
• TLB Miss：硬件自动走 4 级页表遍历，查到后填入 TLB。
📌 注：Linux 4.14+ 在支持 LA57 的新 CPU 上可扩展为 5 级页表（多一层 P4D，9+9+9+9+9+12 = 57 bits），将虚拟寻址空间从 256TB 推高至 128PB。另外，数据库常开启 2MB 大页（HugePage，由 PMD 直接指向 2MB 物理页，少查一级 PTE），不仅页表体积缩小 512 倍，更能大幅降低 TLB Miss！
❓ 03.4 · 为什么 malloc(10GB) 能瞬间成功且不占物理内存？缺页异常和页面置换是怎么配合的？

🚨 03.4 延迟分配（Lazy Allocation）、缺页异常与页面置换算法 高频必考

🪄 颠覆直觉的真相：malloc() 申请内存时，内核其实根本没给你分配半个字节的物理内存！

当你的程序调用 char *p = malloc(1024 * 1024 * 1024);（申请 1GB）时，内核通过 mmap/brk 仅仅在进程的 mm_struct 里新建了一个虚拟内存区间结构体（vm_area_struct，记录“虚拟地址 0x7f... 到 0x7f...+1GB 合法可用”），此时页表项全是空的（Present = 0），物理内存占用（RES/RSS）增加为 0，只有虚拟内存（VIRT）涨了 1GB！

🟢 次缺页异常 (Minor / Soft Page Fault)
触发场景（不碰磁盘，微秒级极快）：
① 你第一次真正往 p[0] = 'a' 写数据时，MMU 发现页表项为空，触发缺页异常 ──▶ 内核这才从伙伴系统分配一个真正的 4KB 物理页帧并建立映射（这就叫延迟分配 / Demand Paging）；
② fork() 后的写时复制（COW）；
③ 访问已被别的进程加载进内存的共享库 .so，只需改页表映射。
🔴 主缺页异常 (Major / Hard Page Fault)
触发场景（必须读磁盘，毫秒级极慢）：
① 首次执行某段代码或 mmap 读取文件，且该页不在内核 Page Cache 中，必须发起磁盘 I/O 把数据从硬盘读进物理内存页；
② 进程某个匿名内存页之前因为物理内存不足被换出到了磁盘 swap 分区，现在重新访问它，必须从磁盘 swap 读回来！
（用 pidstat -r 1 查看 minflt/s 与 majflt/s，若 majflt/s 飙高说明正在频繁读盘换页！）

♻️ 物理内存满了换谁出去？四大经典页面置换算法 + Linux 双链表 LRU

置换算法 淘汰规则 优缺点与必考陷阱
OPT（最佳置换） 淘汰“未来最长时间内不会被访问”的页 缺页率理论最低，但需要“预知未来”，操作系统无法实现，仅作为衡量其他算法的基准线。
FIFO（先进先出） 淘汰“最早进入内存”的页（队列） 实现最简单，但完全不顾高频热点页，且存在著名的 Belady 异常（给进程分配的物理页帧数增多，缺页次数反而诡异增加！）。
LRU（最近最少使用） 淘汰“最长时间没有被访问过”的页 利用时间局部性，效果极好且无 Belady 异常；但纯正 LRU 要求每次访存指令都更新链表时间戳，硬件代价太高，且怕偶发的全盘大扫描污染缓存。
Clock（时钟 / 二次机会） 环形链表 + 页表项硬件 Accessed 访问位（0/1） 指针扫过时：若 A=1 则清零给它“第二次机会”跳过；若 A=0 则直接淘汰。是 LRU 的低成本硬件近似实现。
Linux 真实实现：
Active / Inactive 双链表		 维护活跃链表 (Active) 与 非活跃链表 (Inactive)（类似 MySQL 冷热分区 LRU！） 新页先入 Inactive 链表；只有被再次访问（二次触碰 mark_page_accessed）才晋升到 Active 链表！回收时从 Inactive 尾部淘汰，完美防止单次大文件扫描把热内存页冲刷殆尽！（配合 /proc/sys/vm/swappiness 调节换出匿名页与回收 Page Cache 的倾向，默认 60，数据库服务器常调为 1 ~ 10 或关闭 swap）。
❓ 03.5 · 内核的伙伴系统与 Slab 管什么？用户态 malloc 底层怎么切？VIRT / RES / PSS 看哪个？

🧱 03.5 Linux 内存分配全栈（Buddy + Slab + malloc）、VIRT/RES/PSS 与抖动

🛡️ 第一层：Linux 内核态怎么管物理内存？
① 伙伴系统 (Buddy System) —— 按「页」管大块，防外部碎片：
把所有空闲物理页按 $2^0, 2^1, 2^2 \dots 2^{10}$ 个连续页（即 4KB, 8KB, 16KB ... 4MB，共 11 条空闲链表）组织。要 4KB 若没有，就把 8KB 对半劈成两个“伙伴”；释放时若相邻伙伴也空闲，立刻合并回大块，消灭外部碎片！
② Slab / Slub 分配器 —— 按「字节」管内核小对象，防内部碎片：
内核频繁创建 task_struct、inode、dentry 等几百字节的小结构体，直接向伙伴系统要一整页 4KB 太浪费。Slub（现代 Linux 默认）向伙伴系统批发整页，预先切成固定大小的对象槽位池，用完放回池中免初始化直接复用！
🧑💻 第二层：用户态 malloc() 背后怎么向内核要内存？
malloc 是 glibc 的 ptmalloc2 库函数（类似还有 Google tcmalloc、Redis 用的 jemalloc），按申请大小走两条路：
• 小内存（默认 < 128 KB，M_MMAP_THRESHOLD）：调用 brk() / sbrk() 把堆顶指针往高地址推。free() 时不会立刻归还给内核，而是放回 malloc 自己的空闲链表（bins/arena）留着下次复用（所以频繁 malloc/free 小对象会导致进程 RES 居高不下）！
• 大内存（默认 ≥ 128 KB）：直接调用 mmap() 在文件映射区开辟一块独立匿名虚拟内存；free() 时调 munmap() 立刻归还给操作系统！
💡 为什么不能全用 `brk` 或全用 `mmap`？
brk 堆是连续的，如果堆顶有 1 个小对象没释放，底下几百 MB 空洞也无法收缩归还内核（易内存膨胀）；而全用 mmap 每次释放后下次再用又会触发缺页异常 + 内核清零，太慢！两者结合才是绝配。
📊 排查内存必懂：top 里的 `VIRT`、`RES (RSS)`、`SHR` 与 `PSS`：
• VIRT (VSZ)：进程申请的虚拟内存总量（画的大饼，含未触碰的空页，参考意义不大）。
• RES (RSS)：当前真正驻留在物理内存条里的大小（含共享库 SHR）。
• PSS（Proportional Set Size，查 /proc/pid/smaps_rollup）：把共享库内存按共享进程数均摊后的真实物理内存占用——算多进程总内存时看 PSS 才不会重复计算！
• 💀 OOM Killer：当物理内存 + swap 彻底耗尽时，内核触发 OOM Killer，根据每个进程的 oom_score（综合 RSS 占比与 oom_score_adj 权重）挑一个内存大户发送 SIGKILL (9) 强杀（容器内超 memory.limit_in_bytes 同样触发 Cgroup OOM Killed，退出码 137，查 dmesg -T | grep -i oom）。
🌪️ 局部性原理（Locality）与「内存抖动 Thrashing」：
• 时间局部性：刚访问过的变量/函数马上还会用；空间局部性：访问了某地址，它紧挨着的后续地址马上也会用（写代码优先顺序遍历数组、紧凑排列热字段）。
• 抖动/颠簸（Thrashing）：如果同时跑的进程太多，每个进程分到的物理页帧还装不下它的活跃工作集（Working Set），就会陷入“刚换出到磁盘的页，下一条指令又要读回来”的死循环——此时磁盘 IO 100% 狂转、vmstat 的 si/so 飙升、系统彻底卡死，而 CPU 有效计算利用率却趋近于 0！
