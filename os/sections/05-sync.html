⏱️ 30 秒口述版（本章核心）：并发编程需解决原子性、可见性、有序性三大问题。多核且临界区极短（几十纳秒）适合自旋锁（Spinlock，持锁期间不可睡眠）；临界区较长适合互斥锁（Mutex）。现代 Linux Mutex 基于 futex + 自适应自旋，无竞争时直接在用户态通过硬件 CAS 完成（0 次系统调用）。死锁需同时满足互斥、持有并等待、不可剥夺、循环等待四条件，工程上最常用的预防手段是按固定全局顺序加锁以破坏循环等待。
❓ 05.1 · 两个线程各跑 10000 次 count++，为什么结果小于 20000？并发到底难在哪三个问题？

💥 05.1 竞态条件（Race Condition）、并发三要素与临界区准则

当多个线程/进程并发读写同一份共享数据，且最终结果取决于它们谁先谁后的微妙执行时序时，就发生了竞态条件（Race Condition）。最经典的例子就是一行看似简单的 count++，编译成汇编其实有 3 条独立机器指令（从内存读到寄存器 MOV ──▶ 寄存器加一 ADD ──▶ 写回内存 MOV），随时可能在中间被时钟中断切走或与另一颗 CPU 核交错：

🎬 案发现场（初始 count = 5，两个核同时执行一次 count++）：
• CPU Core 1 (线程 A)：① 读 count(=5) 到 eax ──▶ ② eax + 1 = 6 ──▶ ③ 把 6 写回内存
• CPU Core 2 (线程 B)：     ① 读 count(=5) 到 ebx（A还没写回！）──▶ ② ebx + 1 = 6 ──▶ ③ 把 6 写回内存（覆盖了 A 的结果，白加一次！）
① 原子性 (Atomicity)
痛点：高级语言的一行代码往往对应多条 CPU 指令，执行到一半被切走就会暴露出半成品状态。
解法：硬件原子指令（LOCK 前缀 / CAS）或加互斥锁保护临界区。
② 可见性 (Visibility)
痛点：线程 A 改了变量可能还停在 CPU 寄存器或异步 Store Buffer 里，线程 B 在另一颗核上一直读到旧缓存值。
解法：锁、原子变量或内存屏障强制刷写缓存并令远端缓存失效。
③ 有序性 (Ordering)
痛点：编译器优化和 CPU 乱序执行会把无单线程依赖的指令重排（如双重检查锁单例模式先赋地址、后初始化对象字段）。
解法：内存屏障（Memory Barrier / Acquire-Release 语义）禁止越界重排。
📌 临界区（Critical Section）同步机制必须遵守的「四大准则」：
访问共享资源的那段代码叫临界区。任何合格的同步机制必须满足：① 忙则等待（互斥）：同一时刻最多只准一个执行流进入临界区；② 空闲让进：临界区没人时，必须允许请求进入的线程立刻进入；③ 有限等待：请求进入的线程必须在有限时间内排上号，绝不能无限期饿死；④ 让权等待（原则上）：当线程长时间进不了临界区时，应当主动让出 CPU 睡眠，别在 CPU 上死循环空转浪费算力。
❓ 05.2 · 互斥锁和自旋锁怎么选？条件变量为什么要写 while 循环？Linux 的 futex 快在哪里？

🔒 05.2 五大同步原语、底层 CAS 原子指令与 Linux futex 高频必考

同步原语 抢不到锁时怎么办？ 最佳适用场景与核心铁律
互斥锁 (Mutex) 抢不到锁就阻塞睡眠（让出 CPU），挂入等待队列，等持锁者释放后再被唤醒。 适合临界区耗时较长、包含 I/O 或竞争激烈的场景。代价是睡眠+唤醒需要 2 次内核态上下文切换（约几微秒）。
自旋锁 (Spinlock) 抢不到锁不睡觉、不让出 CPU，在原地死循环忙等（while 轮询），一释放立刻抢到。 适合多核 CPU + 临界区极短（几十纳秒、几条指令）的场景，省掉两次上下文切换开销。
⚠️ 铁律：① 单核 CPU 上无抢占自旋毫无意义；② 持有自旋锁期间严禁调用任何可能睡眠阻塞的函数！
读写锁 (RWLock) 分为读锁（共享 S）和写锁（排他 X）：读读并发共享，读写互斥，写写互斥。 适合读多写少的缓存/配置表。需注意“读者源源不断涌入导致写者饿死”问题（工业界常采用写者优先或公平队列）。
信号量 (Semaphore) 内部维护计数器 $N$，允许最多 $N$ 个线程同时进入（$N=1$ 时退化为二元信号量，类似 Mutex）。 适合限流器、数据库连接池槽位控制、生产者消费者模型（注意：Mutex 必须由加锁线程自己解锁，而信号量可以由线程 A P(wait)、线程 B V(post)！）。
条件变量 (Condition Variable) 配合 Mutex 使用：条件不满足时调 cond_wait(&cond, &mutex) 原子地释放 Mutex 并睡眠；别人改完状态调 signal/broadcast 唤醒它重新拿锁。 ⚠️ 必考铁律：cond_wait 必须写在 while (!ready) 循环里，绝不能用 if (!ready)！因为存在操作系统层面的虚假唤醒（Spurious Wakeup），或者被唤醒到重新抢到锁的空档期里资源已经被第三个线程抢先拿走了，醒来必须再次核验条件！
⚙️ 锁的地基：硬件原子指令 CAS 与 ABA 问题
锁本身也是个变量，怎么保证“抢锁”这个动作本身是原子的？靠 CPU 硬件指令 CAS(V, Expected, New)（x86 下是 LOCK CMPXCHG，锁定缓存行/总线）：
• 逻辑：硬件一次性判断“内存当前值 *V 是否等于预期旧值 Expected？相等则更新为 New 返回成功，不等则放弃返回失败”。所有自旋锁、无锁队列、乐观锁都建立在 CAS 之上！
• 🚨 ABA 漏洞与解法：线程 1 读出值是 A；挂起期间线程 2 把 A 改成 B，又把 B 改回 A；线程 1 醒来执行 CAS 发现还是 A 就误以为没人动过（在无锁链表里会导致节点指针错乱）！解法：给值配一个单调递增的「版本号/时间戳」，每次变成 (1A) → (2B) → (3A)，带版本号做双字 CAS（如 Java AtomicStampedReference）。
🚀 Linux `futex` + 自适应自旋：为什么现代 Mutex 极快？
如果每次调 pthread_mutex_lock 都要陷入内核态，性能就太差了。Linux 发明了 futex（Fast Userspace Mutex，快速用户态互斥锁），配合现代运行时（如 glibc / Go sync.Mutex / Java synchronized）走三级火箭：
1. 无竞争时（快路径）：直接对用户态一个 32 位整型变量做一次 用户态 CAS，成功即拿锁返回——0 次系统调用，全程停留在 Ring 3，仅耗时几纳秒！
2. 轻度竞争时（自适应自旋 Adaptive Spinning）：若发现锁被占，但持锁线程正在另一颗 CPU 核上跑，当前线程先在用户态自旋几十次等它放锁，省掉睡眠开销。
3. 重度竞争时（慢路径）：自旋还拿不到，才调用 futex(FUTEX_WAIT) 系统调用真正陷入内核挂起睡眠！
❓ 05.3 · 生产者消费者模型里，为什么先 P(mutex) 再 P(empty) 会当场死锁？

🧩 05.3 三大经典同步模型（生产者-消费者 · 读者-写者 · 哲学家就餐）

🏭 producer_consumer.c · 两个信号量 + 一把互斥锁的标准模板（阻塞队列 / Kafka 底层模型） 
sem_t empty = N;   // 空槽位数量信号量（初值 = 缓冲区容量 N）
sem_t full  = 0;   // 已填充数据数量信号量（初值 = 0）
mutex_t mutex = 1; // 保护环形缓冲区指针读写的互斥锁

// 🟢 生产者线程                           // 🔵 消费者线程
P(empty);  // ① 必须先申请空位！           P(full);   // ① 必须先确认有数据！
P(mutex);  // ② 再加互斥锁进临界区         P(mutex);  // ② 再加互斥锁进临界区
  put_item_into_buffer(item);                item = get_item_from_buffer();
V(mutex);  // ③ 释放互斥锁                 V(mutex);  // ③ 释放互斥锁
V(full);   // ④ 通知消费者“数据+1”         V(empty);  // ④ 通知生产者“空位+1”
🚨 必考陷阱：为什么生产者里的 `P(empty)` 和 `P(mutex)` 顺序不能颠倒？
假如缓冲区已经满了（empty = 0），生产者如果先执行 P(mutex) 拿到了互斥锁，再去执行 P(empty) 就会抱着 mutex 锁阻塞睡眠。此时消费者想来取数据腾出空位，但消费者执行到 P(mutex) 时发现锁在睡眠的生产者手里，消费者也随之阻塞——双方互等，直接触发死锁（同理，V(mutex) 和 V(full) 都是释放操作，顺序颠倒不会死锁，但先放 mutex 锁能让临界区占用时间更短）。

📖 模型二：读者-写者问题

允许多个读者同时读，但写者必须独占：用计数器 read_count 记录当前读者数——第 1 个进来的读者负责替所有读者加写锁 P(rw_mutex)，最后 1 个离开的读者负责释放写锁 V(rw_mutex)。若防止写者饿死，再加一把排队锁拦截后续新读者（写者优先）。

🥢 模型三：哲学家就餐问题

5 个哲学家围坐，每人必须同时拿到左右两根筷子才能吃饭。若 5 人同时拿起左筷等右筷 → 全体死锁！三大破局法：① 限制最多 4 人同时拿筷；② 奇偶编号哲学家拿筷顺序相反（奇数先左后右，偶数先右后左，破坏循环等待，最推荐！）；③ 用互斥锁保护“一次性同时拿起左右两根筷子”。

❓ 05.4 · 死锁产生的四个必要条件是什么？工程上最实用的防死锁手段是什么？什么是优先级反转？

💀 05.4 死锁四大必要条件、工程破局策略与优先级反转 高频必考

死锁（Deadlock）是指两个或多个执行流各自持有部分资源，又互相等待对方手里的资源，导致所有相关执行流永久卡死。死锁的发生必须同时满足以下 4 个必要条件（缺一不可，因此只要破坏其中任意一个就能预防死锁）：

四个必要条件 条件含义 如何破坏该条件（预防死锁）？
① 互斥条件
(Mutual Exclusion)		 资源同一时刻只能被一个线程占用。 一般无法破坏（锁本来就是为了互斥；除非改用无锁 CAS 或只读共享）。
② 持有并等待
(Hold and Wait)		 线程已经持有了至少一个资源，又去申请新资源，且等待期间死死攥着已有资源不放。 ① 一次性原子申请所需的全部资源；或 ② 申请新锁失败（trylock 超时）时，主动释放手里已拿到的锁退避重试。
③ 不可剥夺
(No Preemption)		 线程已获得的资源在自己用完主动释放前，不能被别人强行抢走。 由系统支持超时强行回滚/剥夺（如 MySQL InnoDB 检测到死锁后强行回滚代价小的事务）。
④ 循环等待
(Circular Wait)		 存在一条头尾相接的等待环路：T1 等 T2 ──▶ T2 等 T3 ──▶ T3 等 T1。 ⭐ 工程上最实用、低开销的预防手段：按固定全局顺序加锁（Lock Ordering）。
💸 transfer_lock_order.go · 工程防死锁铁律：转账锁两个账户时，始终按账户 ID 从小到大加锁 
// ❌ 错误写法：A转给B 先锁A再锁B；同时 B转给A 先锁B再锁A ──▶ 极易形成环形死锁
// ✅ 正确写法：不管谁转给谁，先按账户 ID 大小排序，始终【先锁 ID 小的，再锁 ID 大的】
func Transfer(from, to *Account, amount int) {
    first, second := from, to
    if from.ID > to.ID {
        first, second = to, from  // 强制统一加锁顺序，从根源上破坏「循环等待」条件
    }
    first.Mu.Lock()
    defer first.Mu.Unlock()
    second.Mu.Lock()
    defer second.Mu.Unlock()
    // 安全执行扣款与加款...
}
🧭 死锁四大处理流派 & 活锁 vs 饥饿：
• 处理流派：① 预防（破坏四条件之一，如固定加锁顺序）；② 避免（银行家算法，分配前预演是否存在安全序列，操作系统实际极少用）；③ 检测与解除（资源分配图找环，杀进程/回滚事务）；④ 鸵鸟策略（Linux/Windows 内核对偶发死锁直接忽略，交给用户处理）。
• 活锁 (Livelock) vs 饥饿 (Starvation)：死锁是“大家都卡死睡觉”；活锁是“大家都醒着不停谦让退避重试（如两人迎面撞上同时往左让又同时往右让），CPU 忙得冒烟却毫无进展”（解法：引入随机退避时间 Random Backoff，如 Raft 选举超时）；饥饿是低优先级线程长期抢不到锁或 CPU。
🚀 进阶必考：什么是「优先级反转 (Priority Inversion)」？（火星探路者号死机真凶）
假设有高（H）、中（M）、低（L）三个优先级的线程：
1. 低优先级 L 先拿到了互斥锁 Mutex；
2. 高优先级 H 醒来抢 Mutex 拿不到，被迫阻塞等待 L 放锁；
3. 此时中优先级 M（不需要这把锁的计算任务）就绪了！因为 M 优先级比 L 高，M 直接抢占了 L 的 CPU 一直跑，导致 L 根本没机会上 CPU 执行完临界区放锁，结果最高优先级的 H 反而被中优先级的 M 间接卡死了！
👉 解法：优先级继承（Priority Inheritance）——当高优先级 H 等待低优先级 L 手里的锁时，内核临时把 L 的优先级直接拔高到和 H 一样高，让 L 不被 M 抢占，火速跑完放锁后再恢复原优先级！
