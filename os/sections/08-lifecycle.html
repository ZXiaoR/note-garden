❓ 09.1 · 当你在终端敲下 `./a.out` 回车，到程序跑完退出，前 8 章的机制是怎么串成一条线的？

🎬 09.1 全链路大串联：一个程序从诞生到消亡的 6 步内核旅程

把前 8 章的知识点串成一条完整的生命周期线——当你在 Bash Shell 里敲下 ./a.out 回车时，Linux 内核在幕后依次完成了这 6 个步骤：

Step 1 · 克隆进程与就绪入队（第 02 章 · fork COW + Runqueue）：
Shell 进程先调 fork() 创建子进程（从 Slab 分配 task_struct PCB，利用 写时复制 COW 只复制父进程页表并将页表项标为只读，不拷贝物理内存），随后将子进程状态设为 TASK_RUNNING (R) 插入 CPU 就绪队列红黑树等待调度。
Step 2 · 调度上 CPU 与偷梁换柱（第 06 & 02 章 · CFS/EEVDF 调度 + execve）：
CFS / EEVDF 调度器挑中子进程并完成上下文切换（切换 CR3 页表与内核栈）；子进程获得 CPU 后立即调用 execve("./a.out") 陷入内核，解析 ELF 二进制文件头，释放继承自 Shell 的旧页表映射，为代码段（Text）、数据段（Data/BSS）、堆和栈建立新的虚拟内存区域（vm_area_struct），并将用户态指令指针 RIP 指向入口 _start / main（此时代码页尚未读入物理内存）。
Step 3 · 按需缺页调入物理内存（第 03 章 · Page Fault + TLB）：
execve 返回用户态 Ring 3 后，CPU 去取入口的第一条指令（虚拟地址），MMU 查 TLB 和四级页表发现页表项为空（Present = 0），触发缺页异常（Page Fault）陷入内核；内核从伙伴系统（Buddy）分配一个 4KB 物理页帧，从磁盘（或 Page Cache）把这页代码读进来，更新页表并填入 TLB 快表，返回用户态重新执行该指令。
Step 4 · 动态分配内存与并发加锁（第 03 & 05 章 · malloc + futex）：
程序调 malloc() 申请内存（小块走 brk、大块初始 ≥128KB 走 mmap 延迟分配，真正写入时才触发次缺页分配物理页）；若通过 clone() 创建了多个工作线程抢一把 Mutex，无竞争时在用户态靠 CAS 快速完成，竞争激烈时才调 futex 陷入内核挂起。
Step 5 · 文件 / 网络 I/O 与中断唤醒（第 01 & 07 章 · Page Cache + epoll + 中断上下半部）：
程序调 read/write 走 syscall 陷入内核，查文件描述符三张表读写内核 Page Cache；若用 epoll_wait 等网络包且数据未到，进程转为可中断睡眠 S 态让出 CPU。等网卡 DMA 收完包触发硬中断（上半部）──▶ 软中断 NET_RX_SOFTIRQ（下半部）走完协议栈后，触发回调把该 Socket 塞进 epoll 就绪链表，并将进程重新唤醒回 R 态就绪队列。
Step 6 · 谢幕退出与父进程回收（第 02 & 04 章 · exit_group + Z 僵尸态 + SIGCHLD）：
main 返回后调用 exit_group() 系统调用：内核关闭它打开的所有 fd、释放虚拟内存页表与物理页帧，只留下空壳 task_struct（状态变为 EXIT_ZOMBIE (Z)），并向父进程 Shell 发送 SIGCHLD 信号；Shell 调用 wait4() 读走退出状态码后，这具 PCB 被归还给 Slab 分配器，进程生命周期正式结束。

🛠️ 09.2 生产实战：Linux 线上性能排查 SOP（load vs CPU% · free · 八大神器） 高频必考

🚨 必考误区 ①：`load average`（平均负载）≠ CPU 使用率！
uptime / top 顶部的 1 / 5 / 15 分钟 load average，统计的是单位时间内处于「可运行态 R」+「不可中断睡眠态 D（等磁盘/NFS I/O）」的平均任务数！
• 为什么 Linux 要把等磁盘的 `D` 态也算进 Load？因为它们代表着“系统正在承受的总体工作需求”。
• 🔥 黄金排障推论：假设一台 8 核服务器，load average 飙到了 40，但 top 看 CPU 使用率 %us 只有 5%——发生了什么？说明根本不是 CPU 算力不够，而是磁盘 I/O 或 NFS 存储卡死了（观察 `%wa` 极高，大批线程卡在 `D` 状态排队等磁盘）！
🚨 必考误区 ②：`free -h` 里 `free` 只剩 200MB 就是内存快爆了吗？
完全不是！Linux 的信条是“空闲的内存就是浪费的内存”，它会把没用的物理内存全拿去做 buff/cache（即第 07 章的 Page Cache 页缓存 + 可回收 Slab `SReclaimable`）。
• 看哪个指标才准？必须看最右边的 available（真实可用内存）！因为一旦新进程需要申请内存，内核瞬间就能把 buff/cache 里的干净缓存页回收腾出来。
• 只有当 available 趋近于 0，且 vmstat 1 里的 si / so（每秒 Swap 换入/换出）持续非 0 时，才说明物理内存真的见底、开始发生换页抖动了！

⚡ 09.3 考前 5 分钟速记表 & 闭卷自测问答

高频考题 满分一句话核心答案
用户态 vs 内核态 & 怎么切换？ CPU 硬件特权级（Ring 3 vs Ring 0）。用户态受限，只能通过 ① 系统调用、② 异常（如缺页）、③ 外围硬件中断 陷入内核态；高频读时间靠 vDSO 映射只读页实现零陷入。
进程 vs 线程 vs 协程 进程是资源分配单位（独立页表/虚拟内存，切换需换 CR3 刷 TLB 最重）；线程是 CPU 调度单位（共享进程内存，独占栈/寄存器）；协程是用户态调度流（栈 KB 级，Ring 3 切换仅几十 ns）。
僵尸进程 vs 孤儿进程 僵尸（Z，有害）：子进程死了父进程没调 wait 回收，残留 PCB 占 PID（杀僵尸需给父进程发 SIGCHLD 或杀父进程；容器需配 tini 当 PID 1）；孤儿（无害）：父先死，子被 PID 1 收养。
为什么进程切换比线程切换慢？ 同进程线程切换共用一套 mm_struct，不换页表；跨进程切换必须更新 CR3 页表基址寄存器，导致 TLB 快表失效且 CPU L1/L2 Cache 局部性变冷。
fork() 写时复制 (COW) 与大页坑 fork 时只复制页表并将父子页表项标为只读，真正写某页时才触发缺页异常复制物理页；若开启 2MB 透明大页 (THP)，旧内核（<5.8）改 1 字节会复制整页 2MB，新内核（5.8+）虽先拆成 4KB 页再复制，但大页拆分锁、khugepaged 后台扫描合并与内存规整仍会导致 Redis RDB 期间延迟毛刺。
64B 缓存行与伪共享 (False Sharing) CPU Cache 按 64 Bytes 缓存行整块搬运；若两个核高频修改落在同一缓存行里的两个独立变量，会导致缓存行在多核间按 MESI 协议反复失效，靠 64B 对齐填充（Padding）解决。
为什么需要虚拟内存？ ① 进程内存安全隔离；② 提供连续地址空间假象（消除外部碎片）；③ 突破物理内存容量限制（按需调页 + 冷页 Swap 换出 + 共享库物理页复用）。
x86-64 四级页表与 TLB 单级页表占空间太大，48 位虚拟地址按 9+9+9+9+12 拆成四级页表（PGD→PUD→PMD→PTE→4KB页内偏移）按需建表省内存；再用硬件 TLB 快表缓存热门映射抵消 4 次查表访存。
malloc 底层原理与延迟分配 初始默认 < 128KB 调 brk 从堆切（释放回内存池复用），初始 ≥ 128KB 调 mmap 匿名映射（释放即还内核，64位下该阈值会动态上调至最高 32MB）。malloc 只分配虚拟地址（涨 VIRT），首次写入触发次缺页异常才分配物理页（涨 RES）。
哪种进程间通信 (IPC) 最快？ 共享内存（Shared Memory）最快：因为管道/消息队列/Socket 都要经内核缓冲区做 2 次拷贝，而共享内存让两进程页表直指同一块物理页，0 次内核拷贝（需配合信号量同步）。
互斥锁 Mutex vs 自旋锁 Spinlock 临界区极短（几十纳秒）且多核用自旋锁（忙等省掉两次切换，持锁期间严禁睡眠）；临界区长用 Mutex。现代 Linux Mutex 基于 futex + 自适应自旋，无竞争时全程在用户态 CAS 完成。
死锁四条件与最实用预防法 互斥、持有并等待、不可剥夺、循环等待（四者缺一不可）。工程上最实用方案：强制按固定全局顺序加锁（如按账户 ID 从小到大加锁），从根源上破坏循环等待。
Linux CFS 调度器核心原理 按权重归一化的虚拟运行时间 vruntime 组织红黑树，每次 $O(1)$ 取最左节点（vruntime 最小）上 CPU；高优先级（nice 值小）权重大、vruntime 涨得慢，分得更多 CPU（Linux 6.6+ 演进为 EEVDF）。
硬链接 vs 软链接 & 文件三张表 硬链接共享同一 inode（i_nlink+1，删原文件不影响）；软链接是存目标路径字符串的独立小文件。进程 fd 背后的三张表：进程 fd 表 ──▶ 系统打开文件表（含 offset）──▶ inode 表。
select / poll / epoll 核心区别 select/poll 每次调用都要把全部 fd 拷入内核并 $O(N)$ 线性遍历；epoll 用红黑树常驻内核（免重复拷贝）+ 网卡中断回调将就绪 fd 挂入就绪链表（$O(1)$ 获取）。ET 模式只通知一次，必须配非阻塞 fd + 循环读到 `EAGAIN`。
什么是零拷贝 (Zero-Copy)？ 传统 read+write 需 4 次切换 + 4 次拷贝（2 DMA + 2 CPU）；sendfile + SG-DMA 让数据从内核 Page Cache 直接由网卡 DMA 发走，降为 2 次切换 + 0 次 CPU 拷贝（Kafka/Nginx 核心加速手段）。
目录的 `r / w / x` 权限与删文件条件 目录 r 决定能否 ls 看文件名列表，目录 x 决定能否 cd 进入及访问子文件 inode，目录 w（配 x）决定能否新建或删除文件（哪怕文件本身 0000 只读，只要对父目录有 wx 就能 rm 删掉；/tmp 靠 Sticky 粘滞位 1777 防止删别人文件）。
统计日志 Top 10 IP 与查端口占用命令 • 日志 Top 10 IP：awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10
• 查端口占用与 TCP 状态：ss -tulpn | grep :8080（或 lsof -i:8080）；ss -s 查看各 TCP 状态汇总；后台重定向必写 nohup ./app > app.log 2>&1 &（先改 fd=1 再让 fd=2 复制 fd=1）。

🎯 8 道深度闭卷自测题（先在心里作答，再点击展开核对边界）

Q1：一次系统调用一定会发生「进程上下文切换」吗？

不一定！系统调用必然发生的是「用户态 ↔ 内核态的模式切换（Mode Switch）」，依然在同一个进程内，不换页表。只有当系统调用在内核里因为等 I/O 或等锁无法继续（或返回用户态前发现时间片耗尽被抢占），主动调用了 schedule() 时，才会发生进程上下文切换。

Q2：为什么 `kill -9` 杀不死 `D` 状态和 `Z` 状态的进程？

• Z（僵尸态）：进程已经终止（内存和资源早已释放），只剩个 PCB 空壳等父进程调用 wait() 回收，无法再对已终止进程发信号（应给父进程发 SIGCHLD 或终止父进程让 PID 1 接管回收）。
• D（不可中断睡眠）：进程正在内核驱动里等待磁盘 DMA 或远程存储硬件完成，传统 TASK_UNINTERRUPTIBLE 为防止硬件状态不一致屏蔽了所有信号，SIGKILL 必须等硬件 I/O 返回后才能被处理（注：Linux 2.6.25 起新增了 TASK_KILLABLE，在 ps/top 中同样显示为 D，但允许 NFS 等路径响应 SIGKILL 终止）。

Q3：既然有了多级页表能省内存，为什么大内存数据库还要开启 2MB 大页 (HugePage)，而却要关闭透明大页 (THP)？

• 开启静态 HugePage（2MB）的好处：50GB 内存如果按 4KB 分页需要 1300 万个页表项，TLB 缓存装不下，频繁触发 TLB Miss；改用 2MB 大页后页表项缩减 512 倍（仅 2.5 万项），大幅提升 TLB 命中率且锁定在物理内存不被 Swap。
• 关闭透明大页（THP）的原因：① khugepaged 后台扫描并将 4KB 页合并为 2MB 大页时会持有锁并争抢 CPU/内存带宽，且分配连续 2MB 页易触发直接内存规整（Direct Compaction）停顿；② 在 fork() 写时复制（如 Redis RDB）场景下，旧内核（< 5.8）修改 1 字节会直接复制整页 2MB，而 5.8+ 内核虽改为先拆分成 4KB 页（split_huge_pmd）再复制，但缺页拆分锁与后台合并依然会引发明显延迟毛刺。

Q4：为什么条件变量 `pthread_cond_wait` 必须写在 `while` 循环里，用 `if` 会出什么 Bug？

两个原因：① 操作系统底层实现（如 futex 被信号打断或多核竞争）允许在没有人调 signal 的情况下发生虚假唤醒（Spurious Wakeup）；② 即使是真的被生产者唤醒，从“被唤醒”到“重新抢回 Mutex 锁”之间有时间差，队列里的那个元素可能已经被别的消费者线程抢先取走了！因此醒来拿到锁后必须用 while (queue.empty()) 再次检查条件。

Q5：`epoll` 是同步 I/O 还是异步 I/O？为什么 `epoll` 的 ET 模式必须配非阻塞 Socket？

• 定性：epoll 是同步 I/O！因为它只负责阶段①（通知你哪个 fd 就绪了），阶段②（把数据从内核缓冲区拷贝到用户态缓冲区）依然需要用户线程自己调 read() 阻塞完成；真正的异步 I/O 是 Linux 5.1+ 的 io_uring。
• 为什么 ET 必配非阻塞：ET 只在数据到来时通知一次，你必须用 while 循环一直 read() 直到返回 EAGAIN 才算读空；若用阻塞 Socket，最后一次读空后的 read() 会把整个事件循环线程永久卡死！

Q6：既然 `sendfile` 零拷贝比 `mmap` 少一次 CPU 拷贝，为什么 RocketMQ 不用 `sendfile` 而坚持用 `mmap`？

因为 sendfile(sock_fd, file_fd) 的数据全程在内核态直接发往网卡，用户态代码根本拿不到文件里面的字节内容！Kafka 只是把整段消息原样透传给消费者，所以用 sendfile 极快；而 RocketMQ 需要在用户态读取消息内容做消息过滤（Tag/SQL 过滤）、建二级索引以及处理小消息随机读，因此选择 mmap + write 让用户态直接映射访问 Page Cache。

Q7：调用 `write()` 返回成功了，如果此时进程崩溃 vs 整机断电，数据会丢吗？

• 如果只是你的应用程序进程崩溃（如 `kill -9` 或段错误）：数据不会丢！因为 write() 已经把数据拷进了操作系统内核的 Page Cache，进程虽然死了，但内核还活着，内核的回写线程（flusher）照样会把这页脏页刷进磁盘！
• 如果是操作系统内核 Panic 或整机拔电源断电：数据会丢！因为 Page Cache 也是 DRAM 内存，断电即失；要想防整机断电，必须在 write() 后调用 fsync() / fdatasync() 强制刷入物理磁盘介质。

Q8：线上服务器 `load average` 高达 30（8核机器），但 `top` 看 CPU 使用率只有 10%，怎么回事？

因为 Linux 的 load average 不仅统计正在跑和排队等 CPU 的 R 态任务，还把处于不可中断睡眠 D 态（等待磁盘 I/O 或 NFS 网络存储响应）的任务也算了进去！CPU 利用率低而 Load 极高，说明有 30 个线程全部卡在内核磁盘 I/O 上动弹不得——立刻看 top 的 %wa，并用 iostat -xz 1 和 ps aux | awk '$8 ~ /D/' 定位卡死的磁盘与进程。
