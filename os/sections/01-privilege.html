❓ 01.1 · 操作系统到底夹在什么位置？它核心就干哪两件事？

🖥️ 01.1 操作系统是什么：资源大管家 × 硬件抽象层

操作系统（OS）是介于底层物理硬件与上层应用程序之间的一层系统软件。剥离掉所有花哨的外壳，它核心只干两件事：

  • 向下当「资源管理者」：管住 CPU、物理内存、磁盘、网卡等有限硬件资源，在成百上千个进程之间分配、调度、隔离与回收，做到既公平又高效。
  • 向上当「硬件抽象层 / 虚拟机」：把裸露、难用的物理硬件包装成干净统一的抽象——把 CPU 抽象成进程/线程（虚拟 CPU），把内存条抽象成虚拟地址空间（虚拟内存），把磁盘和网卡抽象成文件与 Socket（文件描述符 fd），让程序员不用直接跟寄存器和磁盘扇区打交道。
🧑💻 第一层：应用程序（运行在「用户态 Ring 3」· 受限沙箱）
🌐 浏览器 / 前端 Node 服务
🐬 MySQL / Redis / Kafka
🐹 你写的 Go / Java / C++ 程序
📚 C 标准库 (glibc 封装)
⬇️ 主动请求：系统调用 syscall（唯一合法入口） ⇄ ⬆️ 被动打断：异常 Exception / 信号 Signal
🛡️ 第二层：操作系统内核 Kernel（运行在「内核态 Ring 0」· 最高特权）
⚙️ 进程/线程管理与 CFS 调度
🧠 虚拟内存、页表与伙伴系统
📂 VFS 虚拟文件系统与 PageCache
🌐 TCP/IP 协议栈与设备驱动
⬇️ 驱动程序下发指令 / DMA 传输 ⇄ ⬆️ 硬件外部中断 Interrupt（网卡收包 / 磁盘就绪 / 时钟滴答）
🔌 第三层：物理硬件底座 —— CPU 核心 & MMU · DRAM 物理内存条 · NVMe SSD / 磁盘 · 网卡 NIC
📌 内核（Kernel）vs 操作系统，以及「宏内核 vs 微内核」：
• 内核 vs OS：内核是操作系统最核心、常驻内存、拥有最高硬件权限的部分；狭义 OS ≈ 内核，广义 OS 还包括 Shell、GUI、系统工具和标准库。
• 宏内核（Monolithic Kernel，如 Linux / Unix）：把进程调度、内存管理、文件系统、网络协议栈、设备驱动全部塞进同一个内核态地址空间。优点是模块间直接函数调用、性能极高；缺点是一个驱动写崩了可能导致整个内核 Panic（现代 Linux 支持动态加载内核模块 LKM 兼具灵活性）。
• 微内核（Microkernel，如 Mach / QNX / 鸿蒙微内核）：内核态只留最基本的调度、内存映射和进程间通信（IPC），把文件系统、驱动、网络协议栈全踢到用户态作为独立服务运行。优点是隔离极好、高可靠；缺点是模块间频繁跨进程 IPC + 态切换，通信开销较大。
❓ 01.2 · 为什么 CPU 非要分用户态和内核态？怎么从用户态进入内核态？

🔐 01.2 用户态 vs 内核态（CPU 硬件特权级 Ring 0 / Ring 3） 高频必考

为什么要分两个态？因为如果允许任何应用程序直接操作硬件、随意修改页表寄存器（CR3）或关中断，那么一个写出了 Bug 的程序或恶意代码就能直接篡改别的进程的内存、甚至锁死整台服务器。为此，CPU 在硬件层面设计了特权环（Privilege Rings）（x86 有 Ring 0 ~ Ring 3 四级，Linux 只用到了 Ring 0 和 Ring 3）：

特权状态 CPU 特权级 能访问什么 / 能执行什么指令 想越权办事怎么办？
内核态 (Kernel Mode) Ring 0（最高权限） 能执行全部指令（含特权指令：invlpg 刷 TLB、改 CR3 页表、cli/sti 开关中断、I/O 端口读写），可访问全部虚拟/物理内存与硬件。 操作系统内核代码运行在此状态，代表用户进程执行底层敏感操作。
用户态 (User Mode) Ring 3（受限权限） 只能执行普通算术与跳转指令，只能访问自己进程虚拟地址空间的「用户区」；一旦在 Ring 3 强行执行特权指令或访问内核地址，CPU 硬件直接抛 #GP 异常杀进程（段错误）。 想读文件、发网络包、申请物理内存页、创建线程，必须通过系统调用陷入内核态，请内核代劳。
💡 怎么从用户态进入内核态？（只有唯一的三条路）：
① 系统调用（Syscall，主动）：用户代码主动执行 syscall 指令请求内核服务（如读写文件、fork）。
② 异常（Exception，被动同步）：CPU 执行当前用户态指令时内部受阻或出错（如访问未分配物理页触发缺页异常 Page Fault、除零错误），被迫陷入内核。
③ 外围设备中断（Interrupt，被动异步）：外部硬件完成任务后主动通知 CPU（如网卡收到数据包、磁盘 DMA 读完、时钟中断），打断当前用户态程序进入内核中断处理程序。
这三条路本质上都是 “陷入内核（Trap into Kernel）”：CPU 硬件自动保存用户态 RIP/RSP/RFLAGS、将特权级从 Ring 3 提升到 Ring 0、切换到该线程的内核栈，并跳转到内核预设的中断/系统调用入口函数。
🔍 高频追问 · 用户态切内核态（模式切换）和进程上下文切换是一回事吗？为什么还是怕频繁切换？

完全不是一回事！
• 模式切换（Mode Switch，用户态 ↔ 内核态）：依然在同一个进程/线程内部！只是 CPU 特权级在 Ring 3 与 Ring 0 之间切换、栈指针从用户栈切到该线程自己的内核栈，不用切换虚拟地址空间（CR3 页表通常逻辑不变），单次耗时约几十到百余纳秒。
• 进程上下文切换（Context Switch，进程 A → 进程 B）：要把 CPU 交给另一个进程！不仅要先陷入内核态，还要保存当前进程 PCB 内核栈上下文、切换 CR3 页表基址寄存器、导致 TLB 快表与 CPU 缓存局部性失效，比单纯的模式切换重得多（微秒级）。

⚠️ 既然模式切换不换进程，为什么高性能系统还是极力减少 syscall？
因为每次 syscall 仍需保存/恢复通用寄存器、冲刷部分 CPU 指令流水线；尤其在 Meltdown 漏洞补丁 KPTI（内核页表隔离） 开启后，用户态与内核态各自使用不同的页表，进出内核态也需要切换页表（虽有 PCID 缓解，仍有约百纳秒级开销）。每秒百万次小 read/write 光态切换就会吃掉大量 CPU——这正是 用户态缓冲（printf/bufio）、epoll 批量监听、sendfile 零拷贝、io_uring 要消灭的开销！
❓ 01.3 · 调一次 read() 背后 CPU 发生了什么？为什么 gettimeofday() 不用陷入内核？

📞 01.3 系统调用（Syscall）：从 glibc 封装到内核 sys_call_table

你平时在 C / Go / Python 里调用的 open()、read()、write()、fork()，其实是标准库（如 glibc）封装好的函数；它们把参数塞进指定寄存器后，执行一条硬件指令真正陷入内核。

🔬 x86-64 架构下一次系统调用（以 read(fd, buf, count) 为例）的 4 步流转：
① 用户态传参 (Ring 3)
把系统调用号（__NR_read = 0）放进 rax，参数依次放进 rdi, rsi, rdx, r10, r8, r9 寄存器。
② 硬件陷入指令 syscall
CPU 自动把返回地址存入 rcx、标志位存入 r11，切到 Ring 0，从专用 MSR 寄存器（IA32_LSTAR）跳进内核入口 entry_SYSCALL_64。
③ 查表执行 (Ring 0)
切换到线程内核栈，保存寄存器现场（pt_regs），按 rax 下标查 sys_call_table 调用 ksys_read()。
④ 返回用户态 sysret
检查是否有待处理信号或抢占调度请求；把返回值放进 rax，执行 sysret 恢复 Ring 3 继续往下跑。
💡 为什么 64 位用 syscall 替代了 32 位老旧的软中断 int 0x80？ 因为 int 0x80 需要去内存里查中断描述符表（IDT）、做复杂的段权限检查与压栈，慢得多；而专用指令 syscall / sysret 直接读 CPU 内部 MSR 寄存器跳转，速度提升了好几倍！
系统调用类别 高频代表 Syscall 与标准库函数（Library Call）的区别
进程/线程控制 fork / vfork / clone / execve / exit_group / wait4 pthread_create 是库函数，底层调用 clone()。
文件与磁盘 I/O openat / read / write / close / lseek / fsync / stat printf / fwrite 是 C 库函数，自带用户态缓冲区（FILE*），攒够一批才调一次 write() 减少陷入内核次数！
虚拟内存管理 brk / mmap / munmap / mprotect / madvise malloc / free 是库函数（管理用户态内存池），池空了才调 brk 或 mmap 向内核批发内存。
进程通信与同步 pipe2 / shmget / futex / kill / sigaction / eventfd pthread_mutex_lock 无锁竞争时在用户态 CAS 完成，冲突时才调 futex 陷入内核睡眠。
网络与多路复用 socket / bind / listen / accept4 / epoll_create1 / epoll_ctl / epoll_wait / sendfile 高并发网络框架（Netty / Go netpoller / Redis）全部直接建立在这组系统调用之上。
🔍 进阶必考 · 为什么打日志高频调用 gettimeofday() / clock_gettime() 不会陷入内核？（vDSO 机制）

线上服务每秒打几万条日志，每条都要获取当前系统时间戳。如果每次查时间都要执行 syscall 陷入内核态，CPU 早就被态切换拖垮了！Linux 为此设计了 vDSO（virtual Dynamic Shared Object，虚拟动态共享库）：

  • 核心原理：内核把存放系统时间变量的内存页，以及读取该时间的函数代码（如 __vdso_clock_gettime），以「只读」方式直接映射到每个进程的用户态虚拟地址空间里（用 ldd /bin/ls 看到的 linux-vdso.so.1 就是它）。
  • 零陷入效果：内核在时钟中断里更新这页内存的时间值；用户进程调用 gettimeofday() 或 clock_gettime() 时，本质上只是在用户态执行了一次普通函数调用 + 读了一块只读共享内存，全程停留在 Ring 3，0 次系统调用、0 次态切换！
❓ 01.4 · 中断、异常、陷阱怎么区分？为什么 Linux 要把中断拆成「上半部」和「下半部」？

⚡ 01.4 中断 / 异常 / 陷阱 & Linux 硬中断（上半部）与软中断（下半部）

三者都会让 CPU 暂停当前正在跑的指令流、陷入内核去执行处理函数，核心区别在于触发来源与是否同步：

名称 触发来源 同步 / 异步 典型例子
中断 (Interrupt / 硬中断) 外部硬件设备主动发信号给 CPU 引脚 异步（随时发生，与当前执行哪条指令无关） 网卡收到数据包、磁盘 DMA 读写完成、硬件时钟定时滴答（Timer）、键盘敲击。
异常 (Exception)
(含故障 Fault / 终止 Abort)		 CPU 执行当前指令时内部受阻或出错 同步（执行到那条指令必然触发） 缺页异常（Page Fault，修复后重新执行原指令）、除零错误、非法指令、段错误（SIGSEGV）。
陷阱 (Trap / 软中断指令) 用户程序主动执行陷入指令 同步（有意识主动调用） 系统调用（syscall / int 0x80）、调试器断点指令（int 3）。

🔪 Linux 中断处理核心设计：为什么要拆成「上半部 (Top Half)」和「下半部 (Bottom Half)」？ Linux 核心

想象网卡突然收到一个数据包，发硬中断给 CPU。硬中断处理期间通常会屏蔽当前 CPU 上的同类中断（关中断）——如果内核在硬中断里慢吞吞地校验 IP 头、重组 TCP 分片、唤醒用户进程，耗时太长会导致后续涌入的网络包因为中断被屏蔽而直接丢包，鼠标键盘也会卡顿！因此 Linux 把中断一劈为二：

⚡ 上半部 (Top Half · 硬中断 `hi`) 关中断 · 极快秒退
• 干什么：只做最紧急、跟硬件强相关的动作（例如：把网卡 RingBuffer 寄存器状态记下来、清硬件中断标志位、触发下半部软中断标志），然后立刻退出恢复响应！
• 铁律：运行在中断上下文，绝不能睡眠阻塞，执行时间必须控制在微秒级。
🐢 下半部 (Bottom Half · 软中断 `si` 等) 开中断 · 延后干重活
• 干什么：把耗时的重活（如走完整 TCP/IP 协议栈拆包、拷贝 sk_buff、唤醒 epoll_wait 进程）延后执行。
• 优势：执行期间开启硬中断，随时允许新的硬中断插队进来，兼顾了硬件实时响应与大吞吐处理（top 里的 %si 就是软中断耗时，负载高时由 ksoftirqd/n 内核线程接管）。
🧩 进阶辨析：Linux 下半部的 3 种具体机制（面试加分项）：
1. 软中断 (Softirq)：编译期静态分配（共 10 种，如网络收发 NET_RX_SOFTIRQ、块设备 BLOCK_SOFTIRQ）。同一个 softirq 可在多个 CPU 核上并行跑，性能最高但需自己保并发安全，处于中断上下文，不可睡眠。
2. Tasklet：基于 softirq 实现，区别是同一个 tasklet 同一时刻只会在一个 CPU 上跑，写驱动更省心，同样不可睡眠。
3. 工作队列 (Workqueue)：把任务交给专门的内核线程（kworker）去跑——因为它运行在进程上下文，所以它是下半部三兄弟里唯一可以睡眠阻塞（如申请内存、等锁、做磁盘 I/O）的机制！
💡 补充：现代高吞吐网卡还会配合 NAPI（中断 + 轮询混合）——来第一个包时触发硬中断关闭接收中断，随后软中断一次性批量轮询拉走几百个包，拉空后再重新开硬中断，彻底消灭十万 QPS 下的“中断风暴”！
