❓ 06.1 · 调度器为什么难设计？「周转时间」和「响应时间」为什么天生对着干？

⚖️ 06.1 调度目标权衡、两类任务画像与抢占时机

当就绪队列（Runqueue）里排着几十个嗷嗷待哺的线程，CPU 核却只有几颗时，调度器（Scheduler）必须决定：下一个让谁上 CPU？让它跑多久？这本质上是一场不可能同时拉满的“多目标跷跷板”：

核心指标 / 概念 计算公式与精准定义 调优取向与内在矛盾
周转时间 (Turnaround) 完成时刻 - 提交时刻（含排队等待 + 实际运行时间） 批处理/离线计算任务最看重：希望总耗时越短、单位时间吞吐量越高越好（讨厌频繁切换）。
响应时间 (Response) 首次上 CPU 响应时刻 - 请求提交时刻 交互式/在线服务最看重：用户点一下鼠标或发一个 HTTP 请求，必须几毫秒内立刻给反应（需要高频抢占切换，但这会增加上下文切换损耗、拉长总周转时间！）。
I/O 密集型 vs CPU 密集型 • I/O 密集型（交互/Web/数据库）：跑几微秒就阻塞等网卡/磁盘；
• CPU 密集型（视频转码/AI 推理）：一跑起来就死占 CPU 算个不停。 		黄金调度铁律：必须优先照顾 I/O 密集型任务！因为它一旦被唤醒，只需占用极短的 CPU 就能发出下一次磁盘/网络请求，然后立刻主动让出 CPU 让硬件并行干活、让计算任务接着算！
📌 抢占式（Preemptive）vs 非抢占式 & Linux 的触发调度时机：
现代通用操作系统（Linux / Windows / macOS）全部采用抢占式调度。在 Linux 中，调度分为两类：
• 主动调度：进程在内核态因等待 I/O、等待 futex 锁、sleep 或执行 exit() 无法继续时，自己直接调用 schedule() 让出 CPU。
• 抢占式调度（被动）：当时钟中断滴答（Tick）发现当前进程运行时间超标，或者一个更高优先级的睡眠进程刚被唤醒时，内核并不会在中断上下文里立刻强行切栈，而是先把当前进程 thread_info 里的 TIF_NEED_RESCHED（需要重调度标志位）设为 1；等中断处理结束、或系统调用即将返回用户态的前一刹那，内核检查到该标志位为 1，立即调用 schedule() 把它换下 CPU！
❓ 06.2 · 从 FCFS 到多级反馈队列 (MLFQ)，五大经典调度算法是怎么一步步填坑进化的？

🪜 06.2 五大经典调度算法演进对照表

调度算法 核心规则 解决的痛点 / 优势 暴露的新问题（为什么还要演进？）
① 先来先服务 (FCFS) 按到达先后排队，非抢占，谁先来谁跑到死。 实现最简单、绝对零切换开销。 护航效应（Convoy Effect）：一个耗时 10 秒的大计算任务排在队头，后面 100 个只需 1ms 的网络请求全得陪它干等 10 秒！
② 短作业优先 (SJF / SRTF) 每次挑预计运行时间最短（抢占版为剩余时间最短 SRTF）的先跑。 数学证明平均周转时间全局最优！ ① 操作系统根本无法提前预知一个进程还要跑多久；② 短任务源源不断涌入会导致长任务永久饿死（Starvation）。
③ 优先级调度 (Priority) 给每个进程标优先级，高优先级先跑。 能区分核心系统任务与后台杂活。 低优先级仍可能饿死 ──▶ 必须引入「老化（Aging）」机制：随着等待时间增加，动态调高老实排队者的优先级。
④ 时间片轮转 (RR) 所有就绪进程轮流跑一个固定时间片（如 4ms），用完排到队尾。 绝对公平、交互响应时间极佳，不会饿死。 时间片大小极难定：设太大退化成 FCFS 响应慢；设太小（如 0.1ms）CPU 全耗在上下文切换和刷 TLB 上了！
⑤ 多级反馈队列 (MLFQ)
经典集大成者		 设 $Q_0, Q_1, Q_2$ 多层优先级递减队列，越往下的队列优先级越低、但单次时间片越长。 无需预知运行时间，自动识别并优待短任务/IO任务！ 需要定期把所有任务提回顶层队列（Priority Boost），防止长任务饿死或恶意程序在时间片耗尽前 1ms 故意发起假 I/O 欺骗调度器。
💡 一眼看穿「多级反馈队列 MLFQ」的巧思：
1. 新任务来了先当贵宾：一律放进最高优先级队列 $Q_0$（时间片短，如 2ms）。如果它是交互/IO 型短任务，跑 0.5ms 就去等网络了，下次醒来还留在 $Q_0$ 享受秒级响应！
2. 占满时间片就降级：如果它在 $Q_0$ 把 2ms 时间片全吃光了还没停，说明它是CPU 密集型长任务，立刻把它降级到下一层 $Q_1$（优先级变低，但给它 4ms/8ms 的更长时间片，减少无谓切换）！
❓ 06.3 · Linux CFS 调度器是怎么用「vruntime + 红黑树」实现完全公平的？睡眠醒来的进程怎么处理？

🐧 06.3 Linux CFS 完全公平调度器（`vruntime` + 红黑树）与 EEVDF 演进 高频必考

Linux 2.6.23 ~ 6.5 对普通进程（SCHED_NORMAL）默认采用 CFS（Completely Fair Scheduler，完全公平调度器）。它彻底抛弃了传统“固定时间片 + 多级队列”的复杂启发式规则，只用一个极其优雅的核心账本——vruntime（Virtual Runtime，虚拟运行时间）：

🌳 CFS 两大核心支柱：① 权重归一化的 vruntime 公式 × ② 红黑树（`rb_root_cached`）
vruntime += 实际物理运行时间 Δexec × ( 默认基准权重 NICE_0_LOAD [1024] ÷ 当前进程权重 weight )
👉 直觉翻译：进程的 nice 值范围是 -20（最高优先级，权重 88761） ~ +19（最低优先级，权重 15），默认 nice = 0（权重 1024）。
• 高优先级进程（nice 小、权重大）：分母大 ──▶ 同样在物理 CPU 上跑 10ms，它的 vruntime 涨得极慢！
• 低优先级进程（nice 大、权重小）：分母小 ──▶ 跑 10ms，它的 vruntime 蹭蹭往上涨！
🎯 调度铁律：永远挑「vruntime 最小」的跑！
CFS 把每个 CPU 核就绪队列里的所有可运行任务，按 vruntime 从小到大塞进一棵红黑树（Red-Black Tree）：
• 谁在红黑树最左边（vruntime 最小），说明谁“欠的 CPU 账最多、最委屈”，下一个就调度谁上 CPU！
• 随着它在 CPU 上运行，它的 vruntime 不断变大，随后被放回红黑树右侧，让别的 vruntime 小的任务上来跑——高优先级任务因为 vruntime 涨得慢，总会排在左边被优先选中！
⚡ 源码级细节：取最左节点是 $O(\log N)$ 还是 $O(1)$？
• 插入/调整红黑树：复杂度是 $O(\log N)$。
• 挑下一个任务（pick_next_task_fair）：内核用了一个极巧的 struct rb_root_cached，专门用一个指针 rb_leftmost 缓存了整棵红黑树最左边的节点——所以每次调度器挑下一个任务是 直接读缓存指针 $O(1)$！
• 睡眠唤醒防霸榜（min_vruntime）：一个睡了 3 小时的 I/O 进程醒来时，它原本的 vruntime 比大家小几万倍；如果直接按原值放进去，它会独占 CPU 几个小时把别人全饿死！因此 CFS 维护了队列单调递增的 min_vruntime，醒来时把它的 vruntime 拉平到 max(原值, min_vruntime - 适量唤醒补偿半周期)，既让它醒来能立刻插队抢占响应，又绝不让它秋后算总账霸占 CPU！
🔍 进阶拓展 · Linux 6.6+ 最新的 EEVDF 调度器、CPU 亲和性 / NUMA 与 K8s 容器 CPU 限流 (Throttling)
  • Linux 6.6+ 的演进 —— EEVDF（Earliest Eligible Virtual Deadline First）：CFS 虽然保证了吞吐公平，但对“延迟敏感型短任务”缺少截止时间概念。Linux 6.6 正式用 EEVDF 替换了 CFS 内部挑选逻辑：保留了 vruntime 与红黑树，但在选任务时只从“已欠账（Eligible）”的任务中挑「虚拟截止时间（Virtual Deadline）最早」的任务执行，短请求或设置了低 latency-nice 的任务能更快上 CPU！
  • 多核负载均衡、CPU 亲和性（Affinity）与 NUMA：每个 CPU 核有自己独立的运行队列 rq，减少多核抢锁；调度器尽量让同一线程留在上次跑过的核上（软亲和性，保护 L1/L2 Cache 与 TLB 热度），也可通过 taskset / sched_setaffinity 绑核。多路服务器需注意 NUMA（非统一内存访问），跨 Socket 访问远端节点的内存延迟会贵一倍。
  • 🐳 K8s / Docker 容器为什么 CPU 利用率才 30%，接口延迟却突然暴增？（CFS Bandwidth Control 限流坑）：
    容器设置的 resources.limits.cpu: "2" 底层对应 Cgroup 的 cpu.cfs_period_us = 100ms 与 cpu.cfs_quota_us = 200ms。如果你的 Go/Java 服务开了 16 个工作线程，在某个 100ms 周期的前 12.5ms（$16 \times 12.5 = 200\text{ms}$） 里就把 200ms 配额全烧光了，剩下的 87.5ms 内整个容器的所有线程会被内核 CFS 强制冻结节流（Throttled，查 `/sys/fs/cgroup/cpu/cpu.stat` 的 `nr_throttled`），导致 P99 延迟毛刺飙升！解法：在容器内通过 automaxprocs 让运行时线程数对齐容器配额，或适当调高 CPU Limit。
