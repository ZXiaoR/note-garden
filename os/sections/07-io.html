07文件怎样读写 · 缓存、落盘与等待多个连接先理解过程

📂 07.1 打开文件以后，为什么会拿到一个编号？

文件名帮助内核找到文件。程序请求打开文件后，内核建立这次打开所需的状态，并给程序一个小整数编号，以后读写时就用这个编号引用它。这个编号叫文件描述符。

可以把它理解成这次打开的取件号：它不是文件内容，也不是磁盘地址；同一个编号在另一个进程里，可能指向不同对象。文件、管道和网络连接等对象都可以通过这类编号使用。

  1. 打开文件，取得编号。
  2. 用编号请求读取，把得到的数据放进程序的缓冲区。
  3. 处理数据；需要时继续读取。
  4. 用完关闭，释放这次打开的引用。

📚 07.2 为什么第二次读可能更快？为什么写完还可能怕断电？

第 00 章讲过，硬盘比内存条慢上千倍。如果每次程序调用 read / write 都直接去读写慢吞吞的硬盘，电脑就会非常卡。为此，操作系统内核会在内存条里专门划出一块区域，用来缓存硬盘文件的内容——这就叫「页缓存（Page Cache）」：

🗺️ 图解「页缓存 (Page Cache)」读写链路：为什么写成功 ≠ 已经落入硬盘？
① 你的程序内存
调 read(fd) 读文字
或调 write(fd) 存结果
──写入──▶
◀──读取──
② 内核「页缓存 Page Cache」
（住在内存条里 · 纳秒级快 · 断电即空！）
• 读文件：第 1 次从右边硬盘读进这里；第 2 次读直接从这里拿，不用再去慢硬盘！
• 写文件：普通 write 只要写到这里（标为“未刷盘脏页”），就立刻告诉程序“写入成功”！
──后台稍后刷盘──▶
或调 fsync 立即刷盘
③ 物理硬盘 (SSD/HDD)
（永久仓库 · 断电不丢）
只有真正刷进这里的数据，拔掉电源才不会丢

看懂这张图就能明白：普通 write 返回成功时，数据其实还停留在中间的内存条（页缓存）里，等内核后台每隔几秒成批写去硬盘。如果在这几秒内整台机器突然拔电源断电，还没写进硬盘的那部分就会丢失；所以像数据库记账这类绝不能丢的数据，写完后还会额外调用一次 fsync（强制把页缓存里的修改立刻刷进右边硬盘）。

📮 07.3 同时等待一万个连接：为什么需要「多路复用 (`epoll`)」？

07.1 提到过，不仅打开硬盘上的文件会拿到文件描述符编号 fd，每一个连进来的客户端网络连接（Socket）在内核里也同样是一个编号 fd。
但读「网络连接的 fd」和读「本地硬盘文件的 fd」有一个很大不同：本地文件随时在硬盘上，读一下很快就能拿到；而如果服务器同时连着一万个客户端（一万个 Socket fd），大部分连接在多数时间里并没有发数据过来，只有少数几个连接真正有数据可读：

🗺️ 图解管理 10,000 个网络连接：笨办法（死等/挨个问） vs 聪明办法（`epoll` 就绪通知）
🐢 笨办法：1 个线程死盯 1 个连接，或者挨个敲门问 1 万次
[连接 fd=3: 没说话💤] ◀── 线程卡死在这傻等！
[连接 fd=4: 发来数据✉️] ◀── 没人管，干着急！
[连接 fd=5 ~ 10000: 全在发呆💤]
• 如果让 1 个线程死等 `fd=3`，那 `fd=4` 发来消息也完全顾不上；
• 如果给 1 万个连接配 1 万个线程，内存和切换开销当场把服务器撑爆；
• 如果让 1 个线程从 `fd=3` 到 `fd=10000` 挨个问一遍“有数据吗？”（早期 select/poll 做法），9999 次都是白问！
🚀 聪明办法：多路复用 `epoll`（1 个线程只处理“亮灯的就绪名单”）
① 1万个 fd 登记在内核 ──▶ 网卡收到 fd=4, fd=89 的包
② 内核自动把 [fd=4, fd=89] 放进【就绪名单】
③ 叫醒你唯一的线程 ──▶ 只读 4 号和 89 号，不用问其余 9998 个！
• 核心效果：把 1 万个连接交给内核集中盯梢；平时你的线程安心睡觉，谁来数据内核就把谁的编号递给你，用 1 个线程就能轻松管住上万个连接。

这就是I/O 多路复用：它的思路确实很像“事件订阅”——先向内核订阅“我关心哪几个连接 fd 的可读事件”（epoll_ctl），然后等通知（epoll_wait）。
但要注意它和普通“消息订阅”的一个关键区别：epoll 只负责当“门铃”（通知你 4号、89号连接 现在有数据到了），它不会把数据内容直接塞到你手里；你的线程醒来后，还得自己调 read(4) 去内核缓冲区把数据取出来。

🚚 07.4 原样转发文件：怎样减少中间搬运（零拷贝）？

现在把前面两节合在一起看一个最常见的场景：别人通过网络连上你的服务器，想下载硬盘上的那篇文字文件。
• 普通做法（来回搬运）：先调 read 把文件从内核的页缓存（07.2）搬进你程序的内存里，你程序一字不改，紧接着又调 write 把这段文字从你的程序搬回内核的网络发送区（07.3）发走——数据白白进出你的程序折腾了两趟。
• 零拷贝做法（如 sendfile）：既然你的程序根本不需要修改文件里的字，那就直接吩咐内核一句：“请把几号文件 fd 缓存里的数据，直接发给几号网络 fd”——数据全程在内核与网卡之间走完，0 次经过用户程序搬运，这就是零拷贝（Zero-Copy）。

先分清这四节的递进关系：07.1 打开任何文件或网络连接都拿编号 fd ──▶ 07.2 本地文件靠「页缓存」加速读写 ──▶ 07.3 海量网络 fd 靠「epoll」集中等待 ──▶ 07.4 把本地文件 fd 原样发往网络 fd 靠「零拷贝」省去中间搬运。
🧩 想一想：收到连接“可以读”的通知，是不是程序已经拿到了完整请求？

不是。程序仍需尝试读取并按协议组织数据，可能只得到部分内容。通知的是可以尝试的条件，不是完整业务处理的结果。
