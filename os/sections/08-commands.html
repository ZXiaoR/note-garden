❓ 08.1 · 对一个只读文件（0400）能执行 rm 删除吗？目录的 r / w / x 权限和普通文件有什么不同？

🔐 08.1 文件与目录权限（rwx / 特殊权限位）及高频查找打包命令 高频必考

执行 ls -l 时看到的第一列如 -rwxr-xr-- 共 10 个字符：第 1 位代表文件类型（- 普通文件、d 目录、l 软链接、s 套接字、p 管道、c/b 字符/块设备），后面 9 位按 3 位一组分别对应 属主（User u）、属组（Group g）、其他人（Others o） 的 r(4) / w(2) / x(1) 权限：

权限位 (八进制) 对「普通文件」的真实含义 对「目录 (Directory)」的真实含义（面试常考陷阱）
r (读 = 4) 可以读取文件的字节内容（如 cat / less / vim）。 可以读取目录里的文件名列表（即允许执行 ls dir/）。
w (写 = 2) 可以修改或截断文件的内容（但不含删除该文件本身）。 决定能否在该目录下新建、删除、重命名文件（需同时具备目录 x 权限）！
👉 经典结论：哪怕一个文件本身权限是 0000（谁都不可读写），只要你对它所在的父目录有 wx 权限，你照样能用 rm -f 把它删掉（因为删除本质是修改父目录的 dentry 目录项）！
x (执行 = 1) 可以把该文件作为程序加载执行（./a.out）。 决定能否 cd 进入该目录，以及能否访问该目录下任何子文件的 inode 元数据！如果目录只有 r 没有 x，ls -l 只能看到文件名，大小和时间全显示为 ? 且无法打开里面任何文件。
🛡️ 进阶必知：三大特殊权限位（SUID / SGID / Sticky Bit）与默认掩码 `umask`
① SUID（4000，属主 x 位显示为 s）：
典型代表：/usr/bin/passwd（-rwsr-xr-x）。普通用户没有写 /etc/shadow 密码文件的权限，但给 passwd 程序加上 SUID 后，任何用户运行它时，进程的有效用户 ID（euid）会临时提升为文件属主（root），从而顺利改密。
② Sticky Bit 粘滞位（1000，末尾显示为 t）：
典型代表：/tmp 目录（drwxrwxrwt，即 1777）。大家都能在 /tmp 里建文件，但如果按普通目录规则，别人也能把你的文件删了；加上 Sticky 粘滞位后，目录下的文件只有「文件属主自己」或「root」才能删除。
③ 默认权限掩码 umask（常为 0022）：
新建普通文件最大基准权限是 0666（默认不给执行位），新建目录最大基准是 0777。减去 umask 0022 后，新建文件默认权限为 0644 (rw-r--r--)，新建目录默认权限为 0755 (rwxr-xr-x)。

⚔️ 08.2 文本三剑客（grep · awk · sed）与日志分析组合拳 高频必考

线上排查日志或面试手写 Shell 时，不需要死背几十个冷门参数，记住「三剑客分工 + 排序去重管道流水线」就能解决绝大多数文本统计问题：

工具 一句话核心定位 最常用的黄金参数与内置变量
grep
（按行过滤查找）		 “找哪几行”：按正则匹配筛选包含指定模式的行 • -i 忽略大小写 · -n 显示行号 · -v 反向排除（如 grep -v grep） · -r 递归目录 · -E 扩展正则（等价于 egrep，支持 "ERROR|FATAL"） · -c 只统计匹配行数
• 查报错上下文利器：-C 5（显示匹配行前后各 5 行）、-A 5（After 后 5 行）、-B 5（Before 前 5 行）。
awk
（按列切分与聚合）		 “取哪几列 & 做统计”：自带哈希表与循环的列处理引擎 • -F ':' 指定分隔符（默认按任意空白符切分）
• 内置变量：$1, $2...（第 1、2 列）、$0（整行）、$NF（最后一列）、NR（当前行号）、NF（当前行总列数）
• 聚合模式：awk '{sum+=$10} END {print sum/NR}'（用哈希数组 count[$1]++ 可直接做分组计数）。
sed
（流式编辑替换）		 “改/删文本内容”：按行增删改替换文本流 • sed 's/old/new/g' file（把每行所有 old 替换为 new，只预览不改原文件）
• sed -i 's/8080/9090/g' app.conf（-i 直接原地修改文件；macOS 下需写 sed -i ''）
• sed -n '100,200p' app.log（只打印第 100 到 200 行） · sed '/^#/d'（删除所有 # 开头的注释行）。
管道搭档
sort / uniq / tail		 “排序 · 去重计数 · 实时盯梢” • sort -n（按数值大小排，不加 -n 会按字典序把 10 排在 2 前面！） · -r（降序） · -k 2（按第 2 列排）
• uniq -c（合并相邻重复行并在前面打印出现次数 —— 注意：uniq 前必须先 sort，否则不相邻的重复行合并不了！）
• tail -f app.log（实时追踪文件追加内容；若日志会按天切割重建，用 tail -F 按文件名持续追踪）。
🏆 interview_log_oneliners.sh · 面试必考 4 大日志与文本统计手写一行流 
# 题 1：从 Nginx access.log（第1列为客户端IP）中找出访问量最高的 Top 10 IP 及其请求次数
awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10

# 题 2：纯用 awk 哈希数组一步完成 Top 10 IP 统计（无需全量外部 sort，大文件下内存与速度更优）
awk '{cnt[$1]++} END {for (ip in cnt) print cnt[ip], ip}' access.log | sort -nr | head -n 10

# 题 3：筛选出状态码为 500（假设第9列为状态码、第7列为URL）的请求，统计报错最多的前 5 个接口
awk '$9 == 500 {print $7}' access.log | sort | uniq -c | sort -nr | head -n 5

# 题 4：实时滚动查看线上日志中的 ERROR/Exception，并高亮展示报错前后各 10 行堆栈上下文
tail -F /var/log/app/server.log | grep --line-buffered -E -C 10 "ERROR|Exception|panic"
❓ 08.3 · 怎么看 8080 端口被哪个进程占了？为什么线上高并发服务器推荐用 ss 替代 netstat？

🌐 08.3 网络连接、端口占用与抓包诊断（ss · lsof · tcpdump · curl）

当出现“启动服务报 Address already in use”、“怀疑连接池泄漏 / TIME_WAIT 过多”或“接口偶发超时”时，按以下工具链逐层排查：

⚡ 为什么现代 Linux 强烈推荐用 `ss` 替代老旧的 `netstat`？
• netstat 的缺陷：它通过逐行遍历读取 /proc/net/tcp 文本文件来获取连接信息。当单机有 10 万个并发 TCP 连接或几万个 TIME_WAIT 时，netstat 光读文件解析就要卡顿好几秒甚至消耗大量 CPU。
• ss（Socket Statistics）的优势：直接通过内核 tcp_diag Netlink 套接字从内核空间二进制导出状态，即使有十万连接也能毫秒级返回，而且参数与 netstat 高度兼容（如 -t TCP、-u UDP、-l 监听中、-p 显示进程、-n 不解析域名直接显示数字 IP:端口）。
🦈 线上抓包铁律：`tcpdump` 必加 `-nn` 与 `-w`
• 必加 -nn：禁止把 IP 反查成域名、禁止把端口号（如 80/443）转成服务名（http/https）——否则每抓一个包都要发 DNS 反查请求，既慢又污染抓包结果。
• 生产抓包建议写文件：线上高流量时用 -c 1000 限制抓包数量，并用 -w dump.pcap 直接保存原始二进制包，拉回本地用图形化 Wireshark 分析三次握手、重传与对端 RST。

# ① 查谁占用了 8080 端口（两种最常用写法，推荐加 sudo 才能看到非当前用户的进程 PID）
ss -tulpn | grep :8080
lsof -i :8080

# ② 面试常考：一键统计当前机器各个 TCP 状态（ESTABLISHED / TIME_WAIT / CLOSE_WAIT）的连接总数
ss -tan | awk 'NR>1 {state[$1]++} END {for (s in state) print s, state[s]}'
ss -s   # 或者直接用 ss -s 秒级查看内核汇总好的 TCP 各状态计数！

# ③ tcpdump 抓包：抓 eth0 网卡上与 10.0.0.5 交互且端口为 3306 的包，最多抓 500 个存入 mysql.pcap
tcpdump -nn -i eth0 host 10.0.0.5 and port 3306 -c 500 -w mysql.pcap
tcpdump -nn -A -s 0 port 8080   # -A 以 ASCII 打印包体明文（适合直接看内部 HTTP 请求头与响应）

# ④ curl 拆解一次 HTTP 请求在 DNS、TCP 握手、TLS 握手、首字节等待 (TTFB) 各阶段耗时（排障利器）
curl -o /dev/null -s -w "DNS:%{time_namelookup}s | TCP:%{time_connect}s | TLS:%{time_appconnect}s | TTFB:%{time_starttransfer}s | Total:%{time_total}s\n" https://example.com

# ⑤ 测试远端 IP:端口 TCP 连通性（替代废弃的 telnet）与查 DNS 解析链路
nc -zv 10.0.0.8 6379
dig +short example.com
❓ 08.4 · 为什么光加 `&` 后台运行，关掉 SSH 窗口进程还是死了？`> log 2>&1` 和 `2>&1 > log` 为什么不等价？

⚙️ 08.4 进程后台运行（nohup vs systemd）、重定向顺序陷阱与 /proc 探秘

🔌 为什么 `./app &` 关掉终端还是会死？
• & 只是把进程放到当前 Shell 会话的后台运行（不再占用终端标准输入，忽略 Ctrl+C 的 SIGINT）；
• 但当你直接关闭 SSH 终端窗口时，Shell 会向会话下所有子进程发送 SIGHUP（挂断信号，Hangup），导致后台进程被默认终止！
• 解法：① 临时任务用 nohup ./app > app.log 2>&1 &（nohup 让进程忽略 SIGHUP 信号）或在 tmux / screen 会话里跑；② 生产服务一律交由 systemd（systemctl start app）或容器 托管守护。
🚨 经典重定向考题：为什么 `2>&1` 必须写在 `> app.log` 后面？
结合第 07 章的文件描述符表，Shell 解析重定向是严格从左往右执行 dup2() 的：
• ✅ > app.log 2>&1：先让 fd=1 (stdout) 指向 app.log，再让 fd=2 (stderr) 复制 fd=1 当前指向的目标（即 app.log），于是标准输出和标准错误都进了文件。
• ❌ 2>&1 > app.log：先让 fd=2 复制当时 fd=1 的目标（此时 fd=1 还指着屏幕终端！），随后才把 fd=1 改指到 app.log——结果 stderr 依然打在屏幕上，根本没进日志文件！
