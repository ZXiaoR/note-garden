01权限与系统调用原理篇
🧭 本章主线：从操作系统的上下分工出发，看懂 CPU 硬件特权级（Ring 0 / Ring 3）与 CR3 + 页表 是如何隔离进程的，再拆解系统调用 syscall 的 4 步流转与中断上下半部。
❓ 01.1 · 操作系统到底夹在什么位置？它核心就干哪两件事？

🖥️ 01.1 操作系统是什么：资源大管家 × 硬件抽象层

操作系统（OS）是介于底层物理硬件与上层应用程序之间的一层系统软件。剥离掉所有花哨的外壳，它核心只干两件事：

  • 向下当「资源管理者」：管住 CPU、物理内存、磁盘、网卡等有限硬件资源，在成百上千个进程之间分配、调度、隔离与回收，做到既公平又高效。
  • 向上当「硬件抽象层 / 虚拟机」：把裸露、难用的物理硬件包装成干净统一的抽象——把 CPU 抽象成进程/线程（虚拟 CPU），把内存条抽象成虚拟地址空间（虚拟内存），把磁盘和网卡抽象成文件与 Socket（文件描述符 fd），让程序员不用直接跟寄存器和磁盘扇区打交道。
🧑💻 第一层：应用程序（运行在「用户态 Ring 3」· 受限沙箱）
🌐 浏览器 / 前端 Node 服务
🐬 MySQL / Redis / Kafka
🐹 你写的 Go / Java / C++ 程序
📚 C 标准库 (glibc 封装)
⬇️ 主动请求：系统调用 syscall（请求内核服务） ⇄ ⬆️ 被动打断：异常 Exception / 硬件中断 Interrupt
🛡️ 第二层：操作系统内核 Kernel（运行在「内核态 Ring 0」· 最高特权）
⚙️ 进程/线程管理与 CFS 调度
🧠 虚拟内存、页表与伙伴系统
📂 VFS 虚拟文件系统与 PageCache
🌐 TCP/IP 协议栈与设备驱动
⬇️ 驱动程序下发指令 / DMA 传输 ⇄ ⬆️ 硬件外部中断 Interrupt（网卡收包 / 磁盘就绪 / 时钟滴答）
🔌 第三层：物理硬件底座 —— CPU 核心 & MMU · DRAM 物理内存条 · NVMe SSD / 磁盘 · 网卡 NIC
📎 进阶阅读 · 内核、完整操作系统，以及宏内核与微内核
📌 先理清两个基础概念：「内核 vs 操作系统」以及「宏内核 vs 微内核」
• 内核（Kernel）vs 操作系统（OS）—— 核心程序与完整发行版的区别：
  ◦ 内核（Kernel）：操作系统最底层的核心程序，开机后常驻内存，拥有最高硬件权限（Ring 0），负责管理 CPU 调度、虚拟内存、文件系统和硬件驱动（例如狭义的 Linux 指的就是 Linux 内核）。
  ◦ 操作系统（广义 OS）：光有内核，用户还没法直接使用。在内核外围加上命令行 Shell、图形界面（GUI）、系统工具和标准库（如 glibc），打包成完整的系统（如 Ubuntu、CentOS、macOS、Windows），才构成广义的操作系统。
• 宏内核 vs 微内核 —— 核心区别在于：「把多少系统功能放进最高权限的内核态（Ring 0）运行？」
🏢 宏内核（Monolithic Kernel · 代表：Linux / Unix）
• 做法：把进程调度、内存管理、文件系统、网络协议栈、设备驱动全部放进同一个内核态（Ring 0）地址空间里运行。
• 优势（性能高）：各个模块在同一个地址空间内，比如网络模块需要读写文件，直接进行内部函数调用即可，没有跨进程通信开销。
• 代价（隔离弱）：所有模块共享最高权限内存，一旦某个第三方设备驱动出现空指针等严重 Bug，会直接导致整个内核崩溃（Kernel Panic）。（注：现代 Linux 支持动态加载内核模块 LKM，但模块加载后依然运行在 Ring 0）。
🏘️ 微内核（Microkernel · 代表：QNX 车机 / 鸿蒙微内核）
• 做法：Ring 0 内核态里只保留最基础的 CPU 调度、内存映射和进程间通信（IPC）；把文件系统、网络协议栈、设备驱动全部移到普通用户态（Ring 3），作为独立的普通进程运行。
• 优势（稳定性高）：各个服务彼此隔离，就算声卡或网卡驱动崩溃，也只是挂掉一个用户态进程，拉起重启即可，不会导致整机死机（适合车载、航天等高可靠场景）。
• 代价（通信开销大）：模块之间隔在不同进程里，网络模块找文件系统需要通过内核转发消息（频繁跨进程通信 IPC + 用户态/内核态切换），整体吞吐性能不如宏内核。
❓ 01.2 · 为什么 CPU 非要分用户态和内核态？怎么从用户态进入内核态？

🔐 01.2 用户态 vs 内核态（CPU 硬件特权级 Ring 0 / Ring 3） 重点回顾

假设程序要读 hello.txt。如果它能随意向硬盘发指令，就可能绕过文件权限。CPU 因此区分执行权限：普通程序通常在用户态运行，内核代码在内核态运行。在 x86 上，常用 Ring 3 和 Ring 0 表示这两种权限。
程序调用 read() 请求内核处理；内核检查参数并执行读取，再把结果交回来。这里换的是权限，执行任务不一定改变。只有需要等待或发生调度时，CPU 才可能交给别的任务。

读图要点：普通程序不能自行更换页表来读取别人的私有内存。模式切换回答“现在执行的是哪种权限的代码”；任务切换回答“现在由谁使用 CPU”。启用 KPTI 时，同一任务进出内核也可能切换页表，所以不能仅靠 CR3 是否变化来区分两者。
特权状态 CPU 特权级 能访问什么 / 能执行什么指令 想越权办事怎么办？
内核态 (Kernel Mode) Ring 0（最高权限） 能执行全部指令（含特权指令：invlpg 刷 TLB、改 CR3 页表、cli/sti 开关中断、I/O 端口读写），可访问全部虚拟/物理内存与硬件。 操作系统内核代码运行在此状态，代表用户进程执行底层敏感操作。
用户态 (User Mode) Ring 3（受限权限） 可执行普通指令并访问获准映射的内存，只能访问自己进程虚拟地址空间的「用户区」；一旦在 Ring 3 强行执行特权指令或访问内核地址，CPU 触发异常（如 #GP 或页故障），内核按原因处理；非法访问通常导致 SIGSEGV。 想读文件、发网络包、申请物理内存页、创建线程，必须通过系统调用陷入内核态，请内核代劳。
💡 怎么从用户态进入内核态？（先区分三类入口）：
① 系统调用（Syscall，主动）：用户代码主动执行 syscall 指令请求内核服务（如读写文件、fork）。
② 异常（Exception，被动同步）：CPU 执行当前用户态指令时内部受阻或出错（如访问未分配物理页触发缺页异常 Page Fault、除零错误），被迫陷入内核。
③ 外围设备中断（Interrupt，被动异步）：外部硬件完成任务后主动通知 CPU（如网卡收到数据包、磁盘 DMA 读完、时钟中断），打断当前用户态程序进入内核中断处理程序。
这三条路本质上都是 “陷入内核（Trap into Kernel）”：硬件与内核入口代码共同完成现场保存、权限转换和必要的栈切换，转入预设入口。具体分工因入口而异；x86-64 的 syscall 指令不会自动保存用户 RSP 或切换到内核栈。
📎 进阶阅读 · 模式切换、任务切换与页表切换

模式切换：在用户态与内核态之间改变执行权限，例如同一线程发起系统调用并返回。上下文切换：保存一个任务的执行状态，恢复另一个任务的状态。

同一进程的线程通常共享地址空间；跨进程切换通常还需切换地址空间。启用 KPTI 时，进出内核也需要切换用户/内核页表。PCID 等硬件机制可以保留带标签的 TLB 条目，因此切页表不等于每次清空全部 TLB；CPU 数据缓存也不会因切换进程就全部失效。

系统调用仍有入口、参数检查和返回等开销。把很多小块写入合并成一次较大的写入，通常能减少系统调用次数。具体耗时依赖硬件、内核配置和工作负载，不宜记成固定纳秒数。

❓ 01.3 · 调一次 read() 背后 CPU 发生了什么？为什么 gettimeofday() 不用陷入内核？

📞 01.3 系统调用（Syscall）：从 glibc 封装到内核 sys_call_table

既然普通程序跑在受限的用户态（Ring 3），不能直接碰硬盘和网卡，那你平时写代码调用的 open()、read()、write() 是怎么把文件读出来的？
其实它们就像去银行柜台办业务：你在柜台外（Ring 3）不能自己进金库拿钱，但标准库（如 C 语言的 glibc）帮你把“要办第几号业务（系统调用号）”和“参数（读哪个文件 fd、读多少字节）”填进固定的 CPU 寄存器里，然后执行一条专门的硬件指令 syscall 呼叫柜台里面（Ring 0）的内核代办：

🔬 x86-64 下一次系统调用（以 read(fd, buf, count) 为例）的 4 步流转：
① 填单传参 (Ring 3)
把业务编号（read 的系统调用号是 0）放进 rax 寄存器；把三个参数（fd, buf, count）依次放进 rdi, rsi, rdx 寄存器。
② 硬件切入内核 (syscall)
执行 syscall 指令：CPU 自动记下刚才用户代码跑到哪一行（存入 rcx），将权限从 Ring 3 切到 Ring 0，跳进内核总入口函数 entry_SYSCALL_64。
③ 内核查表办事 (Ring 0)
切换到该线程的内核栈并保存寄存器现场；内核有一张全局函数指针数组叫 sys_call_table，按系统调用号分派到 read 的内核处理路径。不同版本可能使用包装函数或不同的分派实现，不必把某个函数名当成固定接口。
④ 递回结果退出 (sysret)
读完数据后，把返回值（读到的字节数）放进 rax 寄存器，执行 sysret 指令把权限降回 Ring 3，回到刚才用户代码的下一行继续往下跑。
📎 进阶阅读 · syscall 与 int 0x80 的区别
💡 补充：为什么 64 位系统用专用指令 syscall 替代了 32 位时代的软件中断指令 int 0x80？
因为老旧的 int 0x80 走的是通用中断流程，每次都要去内存里的中断描述符表（IDT，一张记录“中断号 → 处理函数地址”的表）里查第 0x80 项并做多次权限校验；而 64 位 CPU 专门为系统调用设计了硬件快车道指令 syscall / sysret，直接从 CPU 内部的专用寄存器读取内核入口地址跳转，省去了查内存表的开销。
系统调用类别 高频代表 Syscall 与标准库函数（Library Call）的区别
进程/线程控制 fork / vfork / clone / execve / exit_group / wait4 pthread_create 是库函数，底层调用 clone()。
文件与磁盘 I/O openat / read / write / close / lseek / fsync / stat printf / fwrite 是 C 库函数，自带用户态缓冲区（FILE*），攒够一批才调一次 write() 减少陷入内核次数！
虚拟内存管理 brk / mmap / munmap / mprotect / madvise malloc / free 是库函数（管理用户态内存池），池空了才调 brk 或 mmap 向内核批发内存。
进程通信与同步 pipe2 / shmget / futex / kill / sigaction / eventfd pthread_mutex_lock 无锁竞争时在用户态 CAS 完成，冲突时才调 futex 陷入内核睡眠。
网络与多路复用 socket / bind / listen / accept4 / epoll_create1 / epoll_ctl / epoll_wait / sendfile 高并发网络框架（Netty / Go netpoller / Redis）全部直接建立在这组系统调用之上。
📎 进阶阅读 · vDSO 为什么能减少获取时间的系统调用

Linux 把部分函数代码和相关数据映射到用户空间。库函数在条件允许时使用 vDSO，读取内核维护的时间基准、硬件计数器等信息，在用户态计算时间，避免每次进入内核。

这不是简单读取一个定时更新的时间戳。是否走 vDSO 取决于架构、时钟类型和系统支持，不支持时仍会退回系统调用。

❓ 01.4 · 中断、异常、陷阱怎么区分？为什么 Linux 要把中断拆成「上半部」和「下半部」？

⚡ 01.4 中断 / 异常 / 陷阱 & Linux 硬中断（上半部）与软中断（下半部）

三者都会让 CPU 暂停当前正在跑的指令流、陷入内核去执行处理函数，核心区别在于触发来源与是否同步：

名称 触发来源 同步 / 异步 典型例子
中断 (Interrupt / 硬中断) 外部硬件设备主动发信号给 CPU 引脚 异步（随时发生，与当前执行哪条指令无关） 网卡收到数据包、磁盘 DMA 读写完成、硬件时钟定时滴答（Timer）、键盘敲击。
异常 (Exception)
(含故障 Fault / 终止 Abort)		 CPU 执行当前指令时内部受阻或出错 同步（执行到那条指令必然触发） 缺页异常（Page Fault，修复后重新执行原指令）、除零错误、非法指令、段错误（SIGSEGV）。
陷阱 (Trap / 软件中断指令 int n) 用户程序主动执行陷入指令 同步（有意识主动调用） 系统调用（syscall / int 0x80）、调试器断点指令（int 3）。
（注：中文资料常把 int n 译作“软中断指令”，注意别与下文内核中断下半部的 softirq 软中断混淆，二者同名不同义）

🔪 Linux 中断处理设计：为什么要拆成「上半部 (Top Half)」和「下半部 (Bottom Half)」？ Linux 核心

当网卡收到一个数据包时，会向 CPU 发送硬件中断。而 CPU 在执行硬中断处理函数期间，默认会暂时屏蔽当前 CPU 核上的同类型中断（关中断）——如果内核在硬中断里把所有事情都做完（比如校验 IP 头、重组 TCP 分片、拷贝数据、唤醒用户进程），耗时太长，这期间新到达的网卡数据包就会因为中断被屏蔽而丢包，鼠标键盘等交互也会卡顿。
为了解决“硬中断不能久留，但网络拆包等工作又很耗时”的矛盾，Linux 把中断处理拆成了两半：

⚡ 上半部 (Top Half · 硬中断 hi) 关中断 · 快速登记
• 负责什么：只做最紧急、必须关着中断完成的硬件操作（例如：记下网卡 DMA 环形缓冲区的状态、清除硬件中断标志位、打一个“有软中断待处理”的标记），然后立刻退出并恢复中断响应。
• 限制：运行在中断上下文，不能睡眠阻塞，执行时间通常在微秒级。
🐢 下半部 (Bottom Half · 软中断 si 等) 开中断 · 延后处理
• 负责什么：把比较耗时的后续工作（如完整的 TCP/IP 协议栈拆包、拷贝 sk_buff、唤醒阻塞在 epoll_wait 上的进程）延后到这里执行。
• 优势：执行期间开启硬中断，随时允许新的硬件中断打断它，从而兼顾了硬件实时响应与数据处理吞吐量（top 里的 %si 就是软中断耗时，负载高时由 ksoftirqd/n 内核线程接管）。
📎 进阶阅读 · softirq、tasklet、工作队列与 NAPI
🧩 进阶辨析：Linux 下半部的 3 种具体实现机制（面试常问区别）：
1. 软中断 (Softirq)：内核编译期静态定义（共 10 种，如网络收发 NET_RX_SOFTIRQ、块设备 BLOCK_SOFTIRQ）。同一个 softirq 处理函数可以在多个 CPU 核上同时运行，并发性能最高，但需要自己处理多核加锁；处于中断上下文，不能睡眠。
2. Tasklet：基于 softirq 封装，区别是内核保证了同一个 tasklet 同一时刻只会在一个 CPU 核上运行，驱动开发者不用操心多核并发重入问题；同样处于中断上下文，不能睡眠。
3. 工作队列 (Workqueue)：把任务放进队列，交给专门的内核线程（kworker）去执行——因为它运行在正常的进程上下文里，所以它是三种下半部机制中唯一可以睡眠阻塞（如申请内存、等待互斥锁、执行磁盘 I/O）的机制。
💡 补充：现代网卡还会配合 NAPI（中断 + 轮询混合模式）——收到第一个包时触发硬中断并关闭该网卡的接收硬中断，随后由软中断一次性批量轮询拉走几百个包，等队列拉空后再重新开启硬中断，避免高并发收包时产生大量硬中断。
📝 本章先记住：用户态与内核态区分权限；系统调用不一定更换执行任务。
