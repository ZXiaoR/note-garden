🚰 04.1 IPC 基本思路与管道（匿名管道 pipe vs 命名管道 FIFO）

上一章讲过：每个进程的用户态虚拟空间（低 128TB）是完全隔离的，进程 A 没法直接读写进程 B 的变量。那跨进程通信（IPC）靠什么打通？只有两条物理路径：
① 借道「共享的内核空间」中转：既然所有进程的高 128TB 都映射着同一个内核空间，那就让进程 A 调系统调用把数据拷进内核缓冲区，进程 B 再从内核缓冲区拷回自己的用户空间（管道、消息队列、Socket 全是这条路，需 2 次内核↔用户拷贝）。
② 直接映射「同一块物理内存页」：请内核把两个进程的页表项直接指向同一块物理页帧（即共享内存 Shared Memory，建立后0 次内核拷贝，省去经内核缓冲区中转的拷贝！）。

管道类型 创建与存在形式 核心机制与边界（面试必背）
匿名管道 (Pipe)
int pipe(int fd[2])		 纯内核内存中的环形缓冲区（Linux 默认 16 页 = 64 KiB），磁盘上无任何文件实体；返回读端 fd[0] 与写端 fd[1]。 • 只能用于有亲缘关系的进程（父子/兄弟）：靠父进程先 pipe() 再 fork() 让子进程继承同一对 fd（Shell 里的 ps aux | grep nginx 就是它！）。
• 半双工字节流：默认单向流动（一端只读、一端只写），无消息边界，读走即销毁。
• 自带阻塞流控与原子写保证：缓冲区写满阻塞写进程，读空阻塞读进程；单次写入 ≤ PIPE_BUF (4 KiB) 时内核保证原子写入不交错。
命名管道 (FIFO)
mkfifo("my_pipe", 0666)		 在文件系统目录树里创建一个类型为 p 的特殊文件节点（有真实 inode 和路径名，但数据依然只走内核内存缓冲区，不落磁盘！）。 • 打破亲缘限制：本机任意两个毫不相干的进程，只要按路径名 open("my_pipe") 就能通过同一个内核环形缓冲区收发字节流。

⚡ 04.2 消息队列、共享内存（减少数据中转）、信号量与 Linux 六大 IPC 选型 重点回顾

🐢 传统内核中转 IPC（管道 / 消息队列 / Socket）
进程 A 用户空间 ──①拷贝──▶ 内核缓冲区 ──②拷贝──▶ 进程 B 用户空间
每次收发都必须执行 write + read 系统调用，经历 2 次上下文/特权态切换 + 2 次 CPU 内存拷贝，传几百 MB 大数据时开销巨大。
🚀 共享内存（Shared Memory，shmget / mmap）—— 省去经内核缓冲区中转的拷贝 IPC！
进程 A 虚拟页 ──▶ 【同一块物理内存页帧】 ◀── 进程 B 虚拟页
一旦映射建立，进程 A 往指针写数据，进程 B 读指针瞬间就能看到，全程 0 次系统调用、0 次内核拷贝！（PostgreSQL 的 shared_buffers、Chrome 渲染进程向 GPU 进程传大图全靠它）。
IPC 机制 核心原理 核心优势 局限与注意事项
管道 (Pipe/FIFO) 内核环形字节流缓冲区 简单、自带读写阻塞同步，天然融入 Shell 与文件描述符体系。 无消息边界（纯字节流），需 2 次拷贝，吞吐受限。
消息队列 (Message Queue) 保存在内核中的消息链表（SysV msgget / POSIX mq_open） 自带消息边界与消息类型，接收方可按类型优先级挑选消息，不必按 FIFO 顺序硬读。 每次读写仍需用户↔内核拷贝；内核对单条消息大小（MSGMAX）和队列总字节数（MSGMNB）有严格上限，不适合传大数据。
共享内存 (Shared Memory) 多进程页表映射同一块物理内存（shmget/shmat 或 mmap） 所有 IPC 中速度省去经内核缓冲区中转的拷贝（零内核拷贝），适合高频大数据量交换。 本身不提供同步机制：并发读写会出现数据竞争，需配合信号量、互斥锁或原子操作使用。
信号量 (Semaphore) 内核维护的原子计数器 + P(wait减1) / V(post加1) 原语 专门用来做跨进程互斥与同步协调（常与共享内存配合）。 只传“能不能进”的信号计数，不传业务数据。
信号 (Signal) 进程 PCB 上的位图标志（异步软件通知） 轻量的异步事件通知（如通知进程优雅退出、子进程结束）。 几乎不携带业务数据（仅一个信号编号 signo）。
Socket 套接字 内核网络协议栈缓冲区 或 本机 Unix Domain Socket (UDS) 支持跨物理机器网络通信的 IPC；本机 UDS 绕过 TCP/IP 网络栈，可直接传递数据甚至跨进程传递文件描述符 fd（SCM_RIGHTS）。 跨机器走网络栈延迟较高；本机通信优先用 UDS（如 mysql.sock、docker.sock）。
🐧 现代 Linux 内核进阶补充：把一切通知都变成 fd 的三神器（eventfd / timerfd / signalfd）：
传统 IPC（如信号、信号量）的一个明显局限是不能放进 epoll 里和网络 Socket 一起统一监听。为此现代 Linux 引入了 eventfd（一个只占 8 字节 uint64 计数器的超轻量内核通知对象，比创建一对 64KB 的 pipe 省内存得多）、timerfd（定时器转 fd）与 signalfd（信号转 fd）——让高并发 Reactor 引擎只需一个 epoll_wait 就能统管网络、跨线程唤醒、定时器与系统信号。

📡 04.3 信号（Signal 异步事件通知）与本机 / 跨机 Socket

信号（Signal）是操作系统发给进程的异步事件通知（软件层面的中断）。当别的进程调用 kill(pid, sig) 或内核检测到异常时，内核会在目标进程 task_struct 的待处理信号位图（pending）上把对应比特位置 1；当目标进程下一次从内核态准备返回用户态时，检查位图并触发响应（① 执行默认动作、② 忽略、③ 跳进用户通过 sigaction() 注册的自定义捕获函数）：

信号名称 (编号) 触发方式 能否捕获 / 忽略？ 生产实战含义与处理规范
SIGINT (2) 终端按下 Ctrl + C ✅ 可捕获 / 忽略 请求前台进程中断，命令行工具常捕获它清理临时文件后退出。
SIGTERM (15) kill <pid>（默认信号）或 K8s 销毁 Pod 第一步 ✅ 可捕获 / 忽略 优雅退出（Graceful Shutdown）标准信号！微服务捕获它后：先从注册中心摘流 ──▶ 停止接收新请求 ──▶ 等手头正在跑的事务/请求处理完 ──▶ 刷盘关闭连接后主动退出。
SIGKILL (9) kill -9 <pid> 或 OOM Killer 强杀 ❌ 不可捕获 / 忽略 内核级强制终止：进程没有机会执行清理逻辑，直接由内核回收资源——可能导致内存缓冲区数据丢失、事务中断或临时文件残留。
SIGSEGV (11) 解引用空指针 / 越界写只读内存页 ✅ 可捕获（打栈） MMU 硬件异常转成的段错误（Segmentation Fault），默认终止并生成 core dump 供 gdb 排查。
SIGPIPE (13) 向对方已关闭（RST）的 Socket / 管道继续 write ✅ 可捕获 / 忽略 网络编程常见坑：默认动作是直接终止当前进程。因此后端网络服务器启动时通常会设置 signal(SIGPIPE, SIG_IGN) 忽略它，让 write() 正常返回 EPIPE 错误码。
SIGCHLD (17) 子进程退出或暂停时内核发给父进程 ✅ 可捕获（默认忽略） 父进程在捕获函数里循环调用 waitpid(-1, NULL, WNOHANG) 异步回收子进程，防止产生僵尸进程。
SIGSTOP (19) 暂停进程执行（SIGCONT(18) 恢复） ❌ 不可捕获 / 忽略 与 SIGKILL (9) 一样不可被用户捕获或忽略，确保管理员能随时暂停或终止失控进程。
⚠️ 资深面试必问陷阱：为什么在 Signal 信号处理函数里，严禁调用 printf()、malloc()、free()？
因为信号是异步随时打断主线程的！假设你的主线程正在执行 malloc() 分配内存，刚刚拿到了 ptmalloc 内部的全局堆锁（Arena Lock）；恰在此时，一个 SIGTERM 信号劈头打断了主线程，CPU 跳进你写的信号处理函数——如果你在信号处理函数里又调用了 printf() 或 malloc()，它会尝试再次申请同一把已经被主线程持有的堆锁！主线程在等信号处理函数返回才能放锁，信号处理函数在等主线程放锁，当场触发单线程自死锁（Self-Deadlock），进程永久卡死！
👉 正确做法：信号处理函数里只能调用 POSIX 认证的异步信号安全函数（Async-Signal-Safe，如原始系统调用 write()），或者仅仅设置一个 volatile sig_atomic_t stop_flag = 1;（或往 eventfd / self-pipe 写 1 字节），让主事件循环自己优雅退出！
