❓ 07.1 · 为什么 inode 里不存文件名？为什么 rm 删了 50GB 日志文件，df -h 看磁盘还是满的？

📂 07.1 从文件名到 fd：程序怎样找到一个文件

Linux 哲学是“一切皆文件”：无论是普通磁盘文件、目录、管道、Socket 套接字还是硬件设备，内核都在顶层抽象了一层 VFS（Virtual File System，虚拟文件系统），向上层暴露完全统一的 open / read / write / close 接口。而在底层文件系统（如 ext4 / xfs）中，文件的「元数据」与「真正的数据内容」是严格分开存储的：

⚠️ 注意：inode 里唯独不存「文件名」！

底层本质与 inode 在目录里新增一条目录项，直接指向原文件完全相同的 inode 号，并将该 inode 的硬链接计数 i_nlink + 1（地位完全平等）。 创建一个全新的独立小文件（拥有自己独立的 inode 号），它的数据块里存的仅仅是目标文件的路径字符串（类似 Windows 快捷方式）。
删除原文件 a.txt 后 完全不受影响！rm a.txt 只是删了 a.txt 目录项并让 i_nlink - 1；只要 i_nlink > 0，通过 b.txt 照样正常读写数据。 软链接当场失效（变成悬空死链 Dangling Link）！再次打开会报错 No such file or directory。
跨分区 / 链接目录 ❌ 不能跨文件系统分区（不同分区有各自的 inode 编号空间）；❌ 不允许给目录建硬链接（防止目录树出现环路导致 find 死循环）。 ✅ 可以跨文件系统分区；✅ 可以对目录创建软链接（线上发布切换版本目录 current -> v1.2 常用）。
🚨 经典生产排障：磁盘满了，运维执行 rm -f access.log 删掉了 50GB 的大日志，为什么 df -h 看磁盘空间一点没释放，而 du -sh 却找不到这个大文件？
• 根因：一个文件的数据块要想真正被文件系统回收，必须同时满足两个归零条件：① 磁盘硬链接数 i_nlink == 0（没有任何目录项指向它）；② 不再有打开文件、内存映射等引用阻止回收（不能把 inode 引用计数简单当成打开 fd 的数量）！
• 你执行 rm 只是做到了 i_nlink = 0（所以遍历目录的 du 看不见它了），但 Nginx / Java 进程还一直打开着这个日志文件往里写（仍有打开引用），内核根本不敢释放那 50GB 磁盘块！
• 排查与不重启救急解法：① 用 lsof | grep deleted 找出是哪个 PID 还占着已删除的文件；② 以后清理正在写的日志千万别直接 rm，而是执行 : > access.log 或 truncate -s 0 access.log（直接把原文件截断清空为 0 字节，瞬间释放磁盘且无需重启服务）！

🗂️ 进程调用 open() 拿到的整数 fd，背后是内核哪「三张表」？

表 ①：进程级「文件描述符表」
归属：每个进程独占一张（files_struct）。
实质是个指针数组，下标就是小整数 fd（0=stdin, 1=stdout, 2=stderr），内容是指向第二张表的指针。
表 ②：系统级「打开文件表 (struct file)」
归属：全系统内核共享。
每次调用 open() 都会新建一项。里面记录最核心的当前读写偏移量 f_pos (offset)、打开模式（O_RDONLY/O_APPEND）以及指向第三张表的指针。
表 ③：系统级「inode 表 (struct inode)」
归属：全系统内核共享。
不管一个文件被打开多少次，它在内存里的 inode 永远只有唯一一份，记录文件大小与磁盘块映射。
🎯 理解这三张表，即可串联 3 道经典面试题：
1. fork() 后父子进程写同一个 fd 会互相覆盖吗？不会。因为 fork 复制了表①（进程 fd 表），但父子的 fd 指针指向表②里的同一个 struct file 项，共享同一个读写偏移量 offset，父写完 10 字节，子接着从第 11 字节往后写。
2. 同一进程（或两进程）各自调用一次 open("a.txt") 呢？会在表②生成两个独立的 struct file 项，各自拥有独立的 offset，此时同时从头写就会互相覆盖（除非加了 O_APPEND 每次写前由内核原子移到文件末尾）。
3. Shell 重定向 ./app > out.log 2>&1 是怎么实现的？靠系统调用 dup2(oldfd, newfd)：先把 fd=1 (stdout) 指向 out.log 的表②项，再执行 dup2(1, 2) 把 fd=2 (stderr) 的指针也拷成跟 fd=1 一样，于是标准输出和标准错误就指向了同一个 struct file。

🧠 07.2 Page Cache（内核页缓存）、脏页异步回写与 fsync / O_DIRECT

磁盘比内存慢几千到几万倍，所以 Linux 内核会自动把所有空闲的物理内存利用起来，作为磁盘文件的缓存层——这就是 Page Cache（页缓存，即 free -h 命令看到的 buff/cache）。默认情况下，任何普通的 read() / write() 系统调用都只跟内存里的 Page Cache 打交道，并不直接碰物理磁盘！

③ 物理磁盘 / SSD

刷盘与绕过机制 底层行为 在 MySQL / Redis / Kafka 中的真实应用
后台回写线程 (Write-back) write() 标完脏页即返回；由内核 flusher 线程在满足以下任一条件时异步刷盘：① 脏页满 30 秒（dirty_expire_centisecs=3000）；② 脏页占内存超阈值（dirty_background_ratio=10%）。 Kafka 高吞吐核心密码之一：消息直接顺序写入 OS Page Cache 即返回，靠操作系统批量合并顺序刷盘 + sendfile 直接从 Page Cache 发给消费者！
fsync(fd) vs fdatasync(fd) • fsync(fd)：强制把该文件的脏数据页 + inode 元数据（修改时间/大小）同步到持久存储后才返回；实际 I/O 次数由文件系统与设备决定。
• fdatasync(fd)：只要文件大小没变，只刷脏数据页、不刷非关键元数据，比 fsync 少一次磁盘元数据寻道，性能更高！ 		MySQL 的“双 1”（innodb_flush_log_at_trx_commit=1 & sync_binlog=1）与 Redis 的 appendfsync everysec/always，本质都是在控制什么时候调 fsync/fdatasync！
直接 I/O (O_DIRECT) open() 时带上 O_DIRECT 标志：彻底绕过内核 Page Cache，用户态内存直接通过 DMA 读写物理磁盘！ 为什么 MySQL InnoDB 数据文件要用 O_DIRECT？因为 InnoDB 自己在用户态已经有几十 GB 的 Buffer Pool 和 LRU 机制了！如果再走一遍内核 Page Cache，同一份 16KB 数据页在内存里存两份（双重缓存 Double Caching），纯属浪费一半内存！

🌐 07.3 多个连接，怎样一起等？从五种 I/O 模型到 epoll 重点回顾

一次网络读取（如 read(socket_fd)）在内核里严格分为两个阶段：
阶段 ①（等待数据就绪）：等待远程网卡把数据包发过来，通过 DMA 放进内核 Socket 接收缓冲区（sk_buff）；
阶段 ②（数据拷贝）：把数据从内核缓冲区拷贝到用户态缓冲区。
所谓五种 I/O 模型，区别全在这两个阶段“谁来等、怎么拷”（尤其要注意：epoll 属于 I/O 多路复用，它只负责在阶段①通知你“哪些连接现在有数据可读”，阶段②仍需用户线程自己调用 read/write 把数据从内核拷出来，因此本质仍是同步 I/O）：

I/O 模型 阶段①：等数据就绪 阶段②：内核→用户拷贝 定性与高并发评价
① 阻塞 I/O (BIO) 🔴 线程挂起阻塞 🔴 线程阻塞拷贝 同步阻塞：最简单，但 1 个连接必须配 1 个独立线程（C10K 时开 1 万个线程直接把内存和上下文切换撑爆）。
② 非阻塞 I/O (NIO) 🟢 不阻塞（立即返回 EAGAIN，用户轮询） 🔴 线程阻塞拷贝 同步非阻塞：阶段①不睡，但如果让用户线程死循环调 read() 轮询，会把 CPU 空转烧到 100%，没人单用它。
③ I/O 多路复用
(select/poll/epoll)		 🟡 集中阻塞在 epoll_wait 等一批 fd 🔴 线程自己调 read 阻塞拷贝 本质仍是「同步 I/O」：（因为阶段②还是用户线程自己调 read 同步把数据从内核拷出来），但它能用 1 个线程同时监听数万个连接，谁就绪才读谁，是现代高并发网络服务的基石。
④ 信号驱动 I/O 🟢 不阻塞（就绪时发 SIGIO） 🔴 线程阻塞拷贝 同步 I/O：TCP 下信号产生过于频繁，实战极少使用。
⑤ 异步 I/O (AIO / io_uring) 🟢 不阻塞 🟢 不阻塞（内核完成拷贝） 真正的「异步 I/O」：用户发起请求后即可返回，内核把阶段①等数据和阶段②拷进用户缓冲区全部完成后，再通知用户直接使用。Linux 5.1+ 的 io_uring 核心是通过用户态与内核态共享的提交队列（SQ）/ 完成队列（CQ）环形缓冲区批量收发请求以省去系统调用开销（开启 IORING_SETUP_SQPOLL 内核轮询模式可实现零系统调用；若需进一步实现零拷贝，需额外使用对应的零拷贝操作，例如 IORING_OP_SEND_ZC；注册固定缓冲区本身并不保证零拷贝）。

🔥 I/O 多路复用三代演进：select vs poll vs epoll

对比维度 select poll epoll（Linux 2.6+ 高并发主流方案）
底层数据结构 固定长度位图 fd_set（硬上限 1024 个 fd） 动态数组/链表 struct pollfd（破除了 1024 上限） 内核 struct eventpoll 对象：一棵红黑树（rbr） + 一条双向就绪链表（rdllist）
fd 集合拷贝开销 开销大：每次调 select 都要把整个 fd 集合从用户态拷贝进内核态，返回时还会修改原集合需重置。 同 select：每次调 poll 仍要把全部 pollfd 数组从用户态拷入内核。 无重复拷贝：调 epoll_ctl 把 fd 一次性注册进内核红黑树常驻，之后每次调 epoll_wait 无需重复传入 fd 列表。
查找就绪 fd 复杂度 O(N) 全量线性轮询：不管有几个活跃，内核和用户都得把 1024 个位全扫一遍。 O(N) 全量线性轮询：10 万个连接里只有 1 个来数据，也得遍历 10 万次！ 按就绪事件处理：注册时建立监听关系，事件回调将就绪项加入就绪链表。等待时不必每轮扫描全部监听 fd；取回和处理 K 个就绪事件仍需相应工作，不能把整个过程统称为 O(1)。
🔬 epoll 内核底层是怎么实现的？（3 个系统调用 × 红黑树 + 就绪链表 × 回调机制）

为什么 epoll 能在监听 10 万个连接时既不用每次重复拷贝 fd 集合，也不用线性轮询？因为它在内核里维护了一个专门的管家对象 struct eventpoll，由以下三步紧密配合完成：

① 登记名单：epoll_create + epoll_ctl
struct eventpoll {
  rb_root rbr; // 🌲 红黑树(存所有监听fd)
  list_head rdllist; // 📋 双向就绪链表
}
• epoll_create：在内核创建 eventpoll 对象（含一棵空的红黑树 rbr 和一条空的就绪链表 rdllist）。
• epoll_ctl(ADD)：把要监听的 Socket fd 封装成 epitem 节点插入红黑树（增删改查均为 O(log N)，可高效管理数十万连接且天然去重），同时向该 Socket 的等待队列注册一个回调函数 ep_poll_callback。
② 硬件来信：网卡 DMA ──▶ 触发回调 ep_poll_callback
网卡收包 (fd=4) ──DMA──▶ Socket 接收缓冲区
──▶ 触发 ep_poll_callback
──▶ 把 [fd=4] 挂入 就绪链表 rdllist
• 当远端给 fd=4 发来数据时，网卡通过 DMA 写入内存并触发中断，协议栈把数据放入 fd=4 的接收缓冲区。
• 随后内核自动调用当初挂在 fd=4 上的 ep_poll_callback：直接把红黑树里 fd=4 对应的节点指针追加到双向就绪链表 rdllist 中（同一个节点既是红黑树节点，也能串进就绪链表，无需额外分配内存）。
③ 坐享其成：epoll_wait 只检查 rdllist
rdllist 为空？ ──▶ 线程挂起睡眠💤
rdllist 非空！ ──▶ 唤醒线程 & 拷出 [fd=4]
• 用户线程调用 epoll_wait 时，内核根本不去遍历那棵有 10 万个节点的红黑树，而是只看一眼就绪链表 rdllist 里有没有节点。
• 若为空就让出 CPU 睡觉；一旦步骤②的回调把就绪节点挂进 rdllist，立刻唤醒该线程，把链表里那 K 个真正就绪的事件拷回用户态。
⚡ epoll 两种触发模式：水平触发 (LT) vs 边缘触发 (ET)
• 水平触发 LT（Level-Triggered，默认）：只要内核接收缓冲区里还有未读完的数据，每次调 epoll_wait 都会持续通知你（编程简单不易漏事件；Redis、以及 Netty 的标准 Java NIO 传输 NioEventLoopGroup 采用 LT）。
• 边缘触发 ET（Edge-Triggered，EPOLLET）：只在缓冲区状态「从无到有 / 有新数据到达」时通知一次。即使你只读了 50B 还剩 50B 在里面，下次 epoll_wait 也不会再通知（Nginx、Go netpoller、以及 Netty 原生 Linux 传输 EpollEventLoopGroup 默认采用 ET）。
🚨 为什么 ET 模式必须搭配「非阻塞 Socket (O_NONBLOCK)」？
因为 ET 只通知一次，收到通知后必须用 while 循环调 read() 把缓冲区读空（直到返回 EAGAIN / EWOULDBLOCK 为止）。如果使用阻塞 Socket，当最后一次循环把数据读完、再多调一次 read() 确认读空时，线程就会阻塞在最后那次 read() 调用上，导致该 Reactor 事件循环线程无法继续处理其他连接。
🏛️ 基于 epoll 的三种 Reactor 高并发服务器架构
1. 单 Reactor 单线程（代表：Redis 6.0 前）：1 个线程包揽 epoll_wait + accept + 读写 + 内存命令执行。无锁零切换，但怕慢命令阻塞全局。
2. 单 Reactor 多线程（代表：Redis 6.0+ 多线程 I/O）：1 个主线程管 epoll 与命令执行，把耗时的 Socket read/write 字节拷贝与协议解析分发给多个 I/O 线程并行干。
3. 主从 Reactor 多线程（代表：Netty BossGroup + WorkerGroup）：
• Main Reactor（Boss）：只干一件事——监听服务端端口 accept() 接收新连接，然后把新连接轮询注册给 Sub Reactor；
• Sub Reactor（Worker）：每个 Worker 线程各自跑一个独立的 epoll_wait，负责管好名下那批连接的读写，耗时业务再丢给业务线程池！
（💡 补充：Nginx 通常由多个 Worker 进程各自接收并处理连接，Master 管理进程与配置；它不是由 Master 接收连接再分派给 Worker 的上述模型。其缓解 accept/epoll 惊群效应靠的是内核 SO_REUSEPORT 端口复用负载均衡与 EPOLLEXCLUSIVE 独占唤醒标志）。
❓ 07.4 · 传统读文件发网络为什么要 4 次拷贝 + 4 次切换？mmap 和 sendfile 分别省掉哪次 CPU 拷贝？

🚀 07.4 零拷贝（Zero-Copy：mmap vs sendfile vs splice）与磁盘调度 重点回顾

思考一个最常见的场景：Nginx 静态文件服务器或 Kafka 消费者拉取磁盘上的消息日志——要把磁盘文件里的数据原封不动通过网卡发出去。如果用最朴素的 read(file_fd, buf) + write(sock_fd, buf)，数据明明不需要在用户态做任何修改，却被迫在用户态和内核态之间来回折腾了 4 次用户态/内核态切换 + 4 次数据拷贝（2 次 DMA 硬件拷贝 + 2 次无谓的 CPU 拷贝）：

🐢 传统 read() + write()：4 次特权态切换 + 4 次拷贝（其中 ②、③ 两次 CPU 拷贝纯属浪费！）
磁盘 ──①DMA拷贝──▶ [内核 PageCache] ──②CPU拷贝(多余!)──▶ [用户态 buf] ──③CPU拷贝(多余!)──▶ [内核 Socket缓冲区] ──④DMA拷贝──▶ 网卡
🚀 零拷贝 sendfile() + DMA Scatter/Gather (SG-DMA)：2 次切换 + 2 次 DMA 拷贝 + 0 次 CPU 拷贝！
磁盘 ──①DMA拷贝──▶ [内核 PageCache] ──(仅把内存地址+长度描述符追加到 Socket 缓冲区，0字节CPU拷贝!)──▶ ──②SG-DMA直接汇聚拷贝──▶ 网卡
文件传输方案 态切换次数 数据拷贝总次数 底层原理与中间件选型（Kafka vs RocketMQ）
① 传统 read + write 4 次 4 次 (2 DMA + 2 CPU) 数据必须进出用户态缓冲区，CPU 和内存带宽双双浪费。
② mmap + write 4 次 3 次 (2 DMA + 1 CPU) mmap 把内核 Page Cache 直接映射到用户虚拟地址空间，省掉了“PageCache → 用户态”那次拷贝；write 时 CPU 直接把数据从 Page Cache 拷进 Socket 缓冲区。
👉 RocketMQ 选它：适合小块数据（CommitLog 固定 1GB 映射）且需要在用户态读取/处理消息内容的场景。
③ sendfile (Linux 2.1) 2 次 3 次 (2 DMA + 1 CPU) 用一条 sendfile(out_fd, in_fd) 系统调用替代 read+write（切换减半为 2 次），数据全程不进用户态，只在内核态由 CPU 从 Page Cache 拷到 Socket 缓冲区。
④ sendfile + SG-DMA
(Linux 2.4+ 网卡支持)		 2 次 2 次 (2 DMA + 0 CPU!) 只要网卡支持 Scatter/Gather DMA，连内核内部的 CPU 拷贝都省了——只把 Page Cache 的物理地址和长度描述符传给 Socket，网卡 DMA 自己去 Page Cache 拿数据发走！
👉 Kafka 与 Nginx 选它：大批量纯转发静态文件或消息日志，吞吐量飙到网卡物理极限！（缺点：数据不经过用户态，无法在用户态加密或改内容，HTTPS 下需配合内核 kTLS）。
⑤ splice (Linux 2.6.17+) 2 次 2 次 (2 DMA + 0 CPU!) 在任意两个 fd 之间（至少一端必须是内核管道 Pipe）通过共享管道环形缓冲区的页面指针实现零 CPU 拷贝转发。
📎 进阶阅读 · 机械硬盘与 SSD 的调度差异
💿 补充：机械硬盘调度算法（FCFS / SSTF / SCAN / C-SCAN）在 SSD 时代还重要吗？
• 机械硬盘（HDD）时代：最慢的是磁头机械移动（寻道时间 ~10ms），因此设计了：① FCFS（先来先服务，磁头乱跑）；② SSTF（最短寻道时间优先，远处磁道易饿死）；③ SCAN（电梯算法，磁头单向扫到底再折返，最经典）；④ C-SCAN（循环电梯，扫到底直接回起点重新单向扫，响应更均匀）。
• 现代 NVMe SSD 时代：固态硬盘由闪存芯片构成，没有任何机械磁头寻道开销，且支持多队列高并发随机访问！如果在 SSD 上还用复杂的电梯算法去合并排序并加全局队列锁，反而会拖慢 CPU！因此现代 Linux 针对 NVMe SSD 引入了 Multi-Queue 块设备层（blk-mq），默认调度器直接设为 none（不排序直发硬件队列）或 mq-deadline。
