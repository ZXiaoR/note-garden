❓ 06.1 · 调度器为什么难设计？「周转时间」和「响应时间」为什么天生对着干？

⚖️ 06.1 调度目标权衡、两类任务画像与抢占时机

当就绪队列（Runqueue）里排着多个等待执行的线程，而 CPU 核心数有限时，调度器（Scheduler）需要决定：下一个让谁上 CPU？让它运行多久？这需要在几个相互矛盾的目标之间做权衡：

核心指标 / 概念 计算公式与精准定义 调优取向与内在矛盾
周转时间 (Turnaround) 完成时刻 - 提交时刻（含排队等待 + 实际运行时间） 批处理/离线计算任务最看重：希望总耗时越短、单位时间吞吐量越高越好（讨厌频繁切换）。
响应时间 (Response) 首次上 CPU 响应时刻 - 请求提交时刻 交互式/在线服务最看重：用户点一下鼠标或发一个 HTTP 请求，必须几毫秒内立刻给反应（需要高频抢占切换，但这会增加上下文切换损耗、拉长总周转时间！）。
I/O 密集型 vs CPU 密集型 • I/O 密集型（交互/Web/数据库）：跑几微秒就阻塞等网卡/磁盘；
• CPU 密集型（视频转码/AI 推理）：一跑起来就死占 CPU 算个不停。 		常见调度取向：兼顾 I/O 任务被唤醒后的响应。因为它一旦被唤醒，只需占用极短的 CPU 就能发出下一次磁盘/网络请求，然后立刻主动让出 CPU 让硬件并行干活、让计算任务接着算！
📌 抢占式（Preemptive）vs 非抢占式 & Linux 的触发调度时机：
现代通用操作系统（Linux / Windows / macOS）全部采用抢占式调度。在 Linux 中，调度分为两类：
• 主动调度：进程在内核态因等待 I/O、等待 futex 锁、sleep 或执行 exit() 无法继续时，自己直接调用 schedule() 让出 CPU。
• 抢占式调度（被动）：当时钟中断滴答（Tick）发现当前进程运行时间超标，或者一个更高优先级的睡眠进程刚被唤醒时，内核并不会在中断上下文里立刻强行切栈，而是先把当前进程 thread_info 里的 TIF_NEED_RESCHED（需要重调度标志位）设为 1；等中断处理结束、或系统调用即将返回用户态的前一刹那，内核检查到该标志位为 1，立即调用 schedule() 把它换下 CPU！
❓ 06.2 · 从 FCFS 到多级反馈队列 (MLFQ)，五大经典调度算法是怎么一步步填坑进化的？

🪜 06.2 五大经典调度算法演进对照表

调度算法 核心规则 解决的问题 / 核心优势 暴露的新问题（为什么还要演进？）
① 先来先服务 (FCFS) 按到达先后排队，非抢占，谁先来谁跑到结束。 实现最简单、无额外切换开销。 护航效应（Convoy Effect）：一个耗时 10 秒的大计算任务排在队头，后面 100 个只需 1ms 的网络请求全得陪它干等 10 秒。
② 短作业优先 (SJF / SRTF) 每次挑预计运行时间最短（抢占版为剩余时间最短 SRTF）的先跑。 数学证明平均周转时间理论最优。 ① 操作系统无法提前预知一个进程还要跑多久；② 短任务源源不断涌入会导致长任务饥饿（Starvation）。
③ 优先级调度 (Priority) 给每个进程标优先级，高优先级先跑。 能区分核心系统任务与后台杂活。 低优先级仍可能饿死 ──▶ 需引入「老化（Aging）」机制：随着等待时间增加，动态调高排队者的优先级。
④ 时间片轮转 (RR) 所有就绪进程轮流跑一个固定时间片（如 4ms），用完排到队尾。 公平性好、交互响应时间可预期，不会饿死。 时间片大小需要权衡：设太大退化成 FCFS 响应慢；设太小（如 0.1ms）CPU 耗时在上下文切换和刷 TLB 上占比过高。
⑤ 多级反馈队列 (MLFQ)
经典集大成者		 设 Q0, Q1, Q2 多层优先级递减队列，越往下的队列优先级越低、但单次时间片越长。 无需预知运行时间，自动识别并优待短任务/IO任务！ 需要定期把所有任务提回顶层队列（Priority Boost），防止长任务饿死或恶意程序在时间片耗尽前 1ms 故意发起假 I/O 欺骗调度器。
💡 一眼看穿「多级反馈队列 MLFQ」的巧思：
1. 新任务来了先当贵宾：一律放进最高优先级队列 Q0（时间片短，如 2ms）。如果它是交互/IO 型短任务，跑 0.5ms 就去等网络了，下次醒来还留在 Q0 享受秒级响应！
2. 占满时间片就降级：如果它在 Q0 把 2ms 时间片全吃光了还没停，说明它是CPU 密集型长任务，立刻把它降级到下一层 Q1（优先级变低，但给它 4ms/8ms 的更长时间片，减少无谓切换）！
❓ 06.3 · Linux CFS 调度器是怎么用「vruntime + 红黑树」实现完全公平的？睡眠醒来的进程怎么处理？

🐧 06.3 Linux CFS 完全公平调度器（vruntime + 红黑树）与 EEVDF 演进 重点回顾

先想象两个同等权重、一直有工作可做的线程：如果只有一个 CPU，公平调度希望它们长期获得接近的 CPU 份额。传统 CFS 用“虚拟运行时间”记账，优先考虑相对少运行的任务；权重越大，运行同样久时账本增长越慢。这是理解方向，实际还要处理任务唤醒、调度层级与抢占等情况。
下面先介绍传统 CFS；Linux 6.6 开始引入 EEVDF，不能把旧 CFS 的选取规则直接套到所有新内核。

🌳 CFS 两大核心支柱：① 权重归一化的 vruntime 公式 × ② 红黑树（rb_root_cached）
vruntime += 实际物理运行时间 Δexec × ( 默认基准权重 NICE_0_LOAD [1024] ÷ 当前进程权重 weight )
👉 直觉翻译：进程的 nice 值范围是 -20（最高优先级，权重 88761） ~ +19（最低优先级，权重 15），默认 nice = 0（权重 1024）。
• 高优先级进程（nice 小、权重大）：分母大 ──▶ 同样在物理 CPU 上跑 10ms，它的 vruntime 涨得极慢！
• 低优先级进程（nice 大、权重小）：分母小 ──▶ 跑 10ms，它的 vruntime 蹭蹭往上涨！
🎯 调度铁律：永远挑「vruntime 最小」的跑！
CFS 把每个 CPU 核就绪队列里的所有可运行任务，按 vruntime 从小到大塞进一棵红黑树（Red-Black Tree）：
• 谁在红黑树最左边（vruntime 最小），说明谁“欠的 CPU 账最多、最委屈”，下一个就调度谁上 CPU！
• 随着它在 CPU 上运行，它的 vruntime 不断变大，随后被放回红黑树右侧，让别的 vruntime 小的任务上来跑——高优先级任务因为 vruntime 涨得慢，总会排在左边被优先选中！
⚡ 源码级细节：取最左节点是 O(log N) 还是 O(1)？
• 插入/调整红黑树：复杂度是 O(log N)。
• 挑下一个任务（pick_next_task_fair）：内核用了一个极巧的 struct rb_root_cached，专门用一个指针 rb_leftmost 缓存了整棵红黑树最左边的节点——所以每次调度器挑下一个任务是 直接读缓存指针 O(1)！
• 睡眠唤醒补偿（min_vruntime）：一个睡眠了很久的 I/O 进程醒来时，它原本的 vruntime 比其他进程小很多；如果直接按原值放回红黑树，它会长时间连续占用 CPU 导致其他进程饥饿。因此 CFS 维护了就绪队列单调递增的 min_vruntime，醒来时把它的 vruntime 更新为 max(原值, min_vruntime - 唤醒补偿半周期)，既让刚唤醒的交互/IO 任务能优先获得 CPU，又避免它长时间独占。
🔍 进阶拓展 · Linux 6.6+ 最新的 EEVDF 调度器、CPU 亲和性 / NUMA 与 K8s 容器 CPU 限流 (Throttling)
  • Linux 6.6+ 的演进 —— EEVDF（Earliest Eligible Virtual Deadline First）：CFS 保证了吞吐公平，但缺少“任务多快必须得到服务”的截止时间概念（早期社区讨论的 latency-nice 补丁最终并未合入主线）。Linux 6.6 正式用 EEVDF 替换了 CFS 内部挑选逻辑：保留了 vruntime 与红黑树（增维护子树最小 deadline 增强红黑树），选任务时只从“已欠账（Eligible，lag ≥ 0）”的任务中挑「虚拟截止时间（Virtual Deadline = vei + slice / wi）最早」的任务执行。因此延迟敏感型短任务依靠更短的请求时间片（slice，后续版本可通过 sched_setattr() 的 sched_runtime 自定义）即可算出更早的虚拟截止时间，从而更快上 CPU。
  • 多核负载均衡、CPU 亲和性（Affinity）与 NUMA：每个 CPU 核有自己独立的运行队列 rq，减少多核抢锁；调度器尽量让同一线程留在上次跑过的核上（软亲和性，保护 L1/L2 Cache 与 TLB 热度），也可通过 taskset / sched_setaffinity 绑核。多路服务器需注意 NUMA（非统一内存访问），跨 Socket 访问远端节点的内存延迟显著高于本地节点。
  • 🐳 K8s / Docker 容器为什么 CPU 利用率才 30%，接口延迟却突然暴增？（CFS Bandwidth Control 限流坑）：
    容器设置的 resources.limits.cpu: "2" 底层对应 cgroup v2 的 cpu.max = "200000 100000"（或旧版 cgroup v1 的 cpu.cfs_quota_us = 200ms / cpu.cfs_period_us = 100ms）。如果你的服务按宿主机核数开了 16 个工作线程，在某个 100ms 周期的前 12.5ms（16 × 12.5 = 200ms） 里就把 200ms 配额全用完了，剩下的 87.5ms 内整个容器的所有线程会被内核强制节流冻结（Throttled，查 cgroup v2 /sys/fs/cgroup/cpu.stat 或 v1 /sys/fs/cgroup/cpu/cpu.stat 的 nr_throttled），导致 P99 延迟毛刺飙升。解法：让语言运行时线程数对齐容器 CPU 配额（Go 1.25+ 的 GOMAXPROCS 已原生自动感知容器 cgroup CPU 配额；旧版本 Go 可引入 uber-go/automaxprocs，Java 10+ 默认开启 -XX:+UseContainerSupport），或适当放宽 CPU Limit。
