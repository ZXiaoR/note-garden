0 · 消息队列是什么

消息队列（Message Queue，MQ）就是一个专门用来存放和转发"消息"的中间件。一句话类比：它就是应用之间的快递驿站——发送方（生产者 Producer）把包裹（消息 Message）放进驿站，接收方（消费者 Consumer）有空了再来取，两边不用同时在场、不用互相等。

生产者 Producer
订单服务
──发送 send──▶
消息队列 Broker
暂存消息，先进先出
──消费 poll──▶
消费者 Consumer
积分/短信/物流服务
生产者只管"发出去就走"，消费者按自己节奏"来拿"，中间靠 Broker 解耦

它最本质的能力，就是把一次「你调我、我调你」的同步调用，变成「我把事情写进队列就返回，别人自己去队列里取」的异步流转。就这一个动作的转变，撑起了后面所有的好处和麻烦。

MQ 的三大要素：① 消息 Message：要传递的数据（一般 = 消息头 + 消息体 body）；② Broker：MQ 服务器本体，负责收、存、发消息；③ Topic / 队列：Broker 内部对消息的逻辑分类，生产者往某个 Topic 发，消费者从某个 Topic 收。

1 · 为什么要用 MQ 高频

这是最经典的开场面试题。答案就三个词：解耦、异步、削峰。用一个"用户下单"的例子从头串一遍最清楚。

好处一：解耦（Decoupling）

下单成功后，要做的事越来越多：加积分、发短信、通知物流、写数据仓库…… 如果订单服务直接一个个去调这些下游：

❌ 没有 MQ（强耦合）

下单 ──▶ 调积分服务 ──▶ 调短信服务 ──▶ 调物流服务 ──▶ 调风控服务 新增一个"优惠券服务"？ → 改订单服务代码、重新上线 某个下游挂了？ → 下单跟着报错

✅ 用 MQ（解耦）

下单 ──▶ 发一条"订单已创建"消息 ──▶ 返回 │ ┌────────┬───────┼────────┬────────┐ 积分 短信 物流 风控 优惠券 （谁关心谁自己来订阅，订单服务完全不认识它们）

订单服务只负责"广播一件事发生了"，不关心谁在听、有几个在听。新增下游只要去订阅这个 Topic，订单服务一行代码都不用改。这就是解耦。

好处二：异步（Asynchronization）

还是上面的例子，假设各步骤耗时：下单 20ms、积分 50ms、短信 300ms、物流 100ms。

串行同步用户要等 20+50+300+100 = 470ms 才看到"下单成功"
用 MQ 异步下单 20ms + 发消息 5ms ≈ 25ms 就返回，积分/短信/物流在后台慢慢消费

把非核心、能容忍延迟的流程丢进 MQ 异步做，主链路响应时间大幅缩短，用户体验直接起飞。

注意区分核心链路："扣库存、扣款"这种必须实时、必须成功的步骤不能异步化（用户得当场知道成没成）。只有"发短信、加积分"这种失败了也能补、晚一点也没关系的才适合丢 MQ。别把主链路也异步了。

好处三：削峰 / 削峰填谷（Peak Shaving）

秒杀场景：某一秒涌入 1 万个请求，但数据库每秒只能扛 2 千次写。直接打过去，数据库瞬间被打垮。

洪峰流量
1s 内 10000 请求
──全丢进队列──▶
MQ 缓冲池
先攒着，10000 条排队
──匀速拉取──▶
消费者/DB
稳定按 2000/s 处理
MQ 像水库：上游洪水先蓄起来，下游按能力匀速放水，5 秒消化完，DB 全程不崩

MQ 把瞬时高峰用队列缓冲成平缓的匀速流，代价是下游处理有一点延迟（几秒），但换来系统不被打垮。这就是削峰。

一句话总结解耦/异步/削峰的区别？
解耦关注的是"服务之间不再互相依赖"（架构灵活性）；异步关注的是"主链路响应更快"（用户体验/性能）；削峰关注的是"扛住瞬时高并发"（系统稳定性）。三者其实是同一个"中间加一层缓冲队列"动作在不同视角下的收益。

2 · 用了 MQ 会带来什么问题

MQ 不是银弹。引入它等于往系统里加了一个重量级中间件，随之而来的新问题，恰好就是后面第四章要逐个攻克的面试考点：

系统可用性下降MQ 一旦挂了，整条链路瘫痪。所以 MQ 自己必须高可用（集群 + 副本，§17）。
系统复杂度上升要考虑消息丢失（§7）、重复消费（§8）、顺序错乱（§9）、消息堆积（§10）——本来没有的问题，全冒出来了。
一致性问题下单成功但消息没发出去、或消息发了但下游处理失败，数据就不一致了。需要事务消息（§12）等手段兜底。
面试话术："引入 MQ 带来了解耦、异步、削峰三大收益，但也引入了可用性、复杂度、一致性三大挑战。所以选型和使用时要针对性地解决不丢、不重、有序、不堆积这几个核心问题。" —— 这句话能把整个 MQ 面试串起来。

3 · 两种模型：队列 vs 发布订阅 高频

所有 MQ 的消费模式，本质都是这两种模型的组合。搞懂它俩，再看任何 MQ 都不迷糊。

① 点对点（Point-to-Point，队列模型）

一条消息只会被一个消费者处理掉。多个消费者监听同一个队列，就是在抢消息，抢到的处理完消息就没了。适合任务分发 / 负载均衡。

Producer ──▶ [ 队列 Queue ] ──▶ Consumer A （抢到 msg1） └─▶ Consumer B （抢到 msg2） └─▶ Consumer C （抢到 msg3） 每条消息只被一个人拿走，处理越快的拿得越多 → 天然负载均衡

② 发布/订阅（Publish/Subscribe，主题模型）

一条消息会被所有订阅者各收到一份。生产者发到 Topic，每个订阅者都拿到完整的一份拷贝，互不影响。适合一份数据多方消费（积分、短信、风控都要这条下单消息）。

Producer ──▶ [ Topic ] ──▶ 订阅者A：收到完整一份 ├─▶ 订阅者B：收到完整一份 └─▶ 订阅者C：收到完整一份 一发多收，每个订阅方都是全量
现代 MQ 怎么统一这两种模型？用消费者组（Consumer Group）这个概念一网打尽（Kafka/RocketMQ 都这么干）：
  • 组内：一条消息只发给组里的一个消费者 → 表现为点对点（负载均衡）。
  • 组间：每个组都能各收到一份完整数据 → 表现为发布订阅。
所以"下单消息"发一次，"积分组""短信组"各收到一份（组间=发布订阅）；而积分组内 3 个实例分摊消费（组内=点对点）。一套机制满足两种需求。
RabbitMQ 里没有"消费者组"，它怎么实现发布订阅？
RabbitMQ 靠 Exchange（交换机）+ 多个 Queue 实现：生产者发到 Exchange，Exchange 按规则把消息复制路由到 N 个绑定的队列，每个下游服务用自己的队列消费——一个队列 = 一个"订阅者"。而队列内多个消费者是抢消息（点对点）。详见 §20。这和 Kafka 用"分区+消费者组"是两种不同的实现思路，但达到的效果一样。

4 · 核心概念全景 高频

这些术语是看懂后面所有内容的基础。以 Kafka 为主线（最具代表性），先建立一张全景图：

Broker（一台 Kafka 服务器）
Topic: order（逻辑主题）
├ Partition-0：msg0 msg1 msg2 …（一个有序的追加日志）
├ Partition-1：msg0 msg1 msg2 …
└ Partition-2：msg0 msg1 msg2 …
Topic 逻辑上是一个主题，物理上被拆成多个 Partition 分散到不同 Broker → 这就是水平扩展的关键
概念是什么为什么需要它
Topic 主题消息的逻辑分类，一类业务一个 Topic（订单、支付…）让生产/消费按业务隔离
Partition 分区Topic 的物理切片，每个分区是一个只能往后追加、内部严格有序的日志文件一个 Topic 拆多片分到多台机器，并行读写 → 高吞吐；也是并行度上限
Offset 偏移量消息在分区内的唯一递增编号（第几条）消费者靠记住"我消费到哪个 offset 了"来续传
Producer 生产者发消息的一方，决定消息进哪个分区（按 key 哈希 / 轮询）—
Consumer 消费者收消息的一方，主动拉取（pull）并提交 offset—
Consumer Group 消费者组一组消费者共同消费一个 Topic，组内一个分区只能被一个消费者消费组内负载均衡 + 组间发布订阅（§3）
Replica 副本每个分区有 1 个 Leader + N 个 Follower 副本，分散在不同 BrokerBroker 挂了数据不丢 → 高可用（§17）
Broker一个 Kafka 进程/节点，多个 Broker 组成集群—
ZooKeeper / KRaft集群元数据管理、Controller 选举（新版 Kafka 用自研 KRaft 替代 ZK）谁是 Leader、集群有哪些节点，得有地方记
最容易记混的一句话：Kafka 的顺序性只保证在单个分区内（分区是个有序日志），跨分区不保证顺序。所以"要求全局有序"和"分区"天生矛盾——这是 §9 顺序性问题的根子。
分区数是不是越多越好？
不是。分区多 → 并行度高、吞吐大，但也有代价：① 每个分区是若干文件，分区太多导致打开的文件句柄多、磁盘随机 I/O 变多；② Leader 选举、Rebalance（§18）时要协调的分区更多，故障恢复更慢；③ 端到端延迟可能升高。经验值：单 Topic 分区数一般设为消费者实例数的整数倍，几十到几百量级，而非上万。

5 · Kafka / RocketMQ / RabbitMQ 架构速览

Kafka —— 为吞吐量而生

LinkedIn 出品，Scala 编写。核心理念：把消息当日志（Log）来存，顺序写磁盘 + 分区并行 + 零拷贝，把吞吐量做到极致（百万级 TPS）。天生为大数据管道、日志采集、流处理设计。

Producer → Broker 集群（Topic 拆成多 Partition，每 Partition 多副本）→ Consumer Group 元数据：早期靠 ZooKeeper，新版用 KRaft（去 ZK）

RocketMQ —— 为业务而生

阿里出品，Java 编写，从早期 Kafka 思想演化而来，但更贴合电商/金融业务：原生支持事务消息、延迟消息、消息回溯、顺序消息，运维友好。存储上用一个 CommitLog 顺序写所有消息 + ConsumeQueue 做索引（§19）。

NameServer（轻量注册中心，替代 ZK） Producer → Broker（Master/Slave 主从）→ Consumer 特色：Topic 下是 Queue（类比 Kafka 的 Partition）

RabbitMQ —— 为灵活路由而生

基于 AMQP 协议，Erlang 编写（天生适合高并发网络）。最大特点是灵活的路由：靠 Exchange（交换机） 按各种规则把消息分发到队列（§20）。吞吐量不如前两者（万级 TPS），但延迟低、功能成熟、中小项目开箱即用。

Producer → Exchange（direct/topic/fanout/headers 四种路由）→ Queue → Consumer 不分区，靠 Exchange+Binding 做灵活分发

7 · 消息不丢：生产 / 存储 / 消费三段 高频

"如何保证消息不丢失"是 MQ 第一考题。答题框架就一句：一条消息从生产到消费要过三道关，每一道都可能丢，逐段兜住就不丢。

① 生产端 → Broker
网络丢包 / 没到
▶
② Broker 存储
还在内存没落盘就宕机
▶
③ Broker → 消费端
还没处理完就提交了

第一段：生产者发送丢失

消息发出去，可能因网络问题根本没到 Broker，或到了 Broker 还没存好。对策：用带确认（ack）的可靠发送，别用"发了不管"的模式。

  • Kafka：设置 acks=all（或 -1），要求 Leader 和所有 ISR 副本都写入后才返回成功；配合失败重试 retries。acks=0（发了不等）和 acks=1（只等 Leader）都可能丢。
  • RocketMQ：用同步发送 send() 并检查返回的 SendStatus，失败重试；别用 oneway。
  • 通用：能用事务消息（§12）就能彻底解决"本地操作成功但消息没发出去"的问题。
坑：acks=1 看似安全，但如果 Leader 刚写完还没同步给 Follower 就宕机，新选出的 Leader 上就没这条消息 → 丢了。要"零丢失"必须 acks=all + min.insync.replicas≥2（§17）。

第二段：Broker 存储丢失

消息到了 Broker，但为了性能，MQ 通常先写内存页缓存（PageCache），异步刷盘。如果刷盘前机器断电/宕机，内存里的消息就没了。两个对策：

  • 刷盘策略：改成同步刷盘（写完落到磁盘才返回）。可靠但性能降。RocketMQ 有 SYNC_FLUSH/ASYNC_FLUSH 配置。
  • 多副本（更关键）：一份消息在多台 Broker 上有副本（Kafka ISR / RocketMQ 主从），单机磁盘坏了/宕机，别的副本还在。这是比同步刷盘更实际的"不丢"手段。

第三段：消费者消费丢失 最常丢

消费端最容易丢的坑：拿到消息后先提交了 offset（告诉 Broker"我消费完了"），结果业务还没处理完就崩了 → 这条消息 Broker 认为已消费，不会再投递 → 丢失。

❌ 错误：自动提交 / 先提交后处理 
poll(msg)
commitOffset()   // 先提交
process(msg)     // 处理时崩了 → 消息丢
✅ 正确：处理完再手动提交 
poll(msg)
process(msg)     // 先处理
commitOffset()   // 成功后才提交

关掉自动提交（Kafka enable.auto.commit=false），业务处理成功后再手动提交 offset。这样即使处理到一半崩了，offset 没提交，重启后会重新拉到这条消息再处理一遍。

注意这会带来"重复消费"：先处理后提交，万一处理成功了、提交前崩了，重启会再消费一次。所以"不丢"和"不重"是一对权衡——绝大多数系统选择"宁可重复也不丢失"，然后用幂等（§8）来解决重复。
用一句话概括消息零丢失的完整方案？
生产端 acks=all + 重试（确保到 Broker）→ Broker 多副本 + 同步刷盘/min.insync.replicas≥2（确保存住）→ 消费端 手动提交、处理成功后再提交 offset（确保处理完）。三段全兜住，再叠加幂等兜重复，就是生产级可靠方案。

8 · 消息不重复 & 幂等 & Exactly-once 高频

上一节说了，为了不丢消息，我们宁可重复。那消息为什么会重复、又怎么处理重复？

为什么会重复

  • 生产端重复：发送成功了但 ack 因网络超时没收到，生产者以为失败 → 重试再发一条。
  • 消费端重复：消费成功但提交 offset 前崩了/超时，重启后 Broker 重投（§7 的先处理后提交）。

三种投递语义

At-most-once
最多一次		可能丢，不会重。对应"发了不管"。几乎没人用于重要业务。
At-least-once
至少一次		不会丢，可能重。绝大多数 MQ 的默认保证。配合幂等使用。
Exactly-once
精确一次		不丢不重，理想态。端到端实现代价很大，Kafka 靠幂等生产者+事务在其内部流处理场景支持，但跨到外部系统仍需业务幂等兜底。
结论：不要幻想 MQ 帮你做到完美的 Exactly-once。工程上的标准答案是 「At-least-once（不丢）+ 消费端幂等」≈ 业务层面的 Exactly-once。重点全在消费端幂等。

消费端幂等怎么做（重点）

幂等 = 同一条消息处理一次和处理多次，结果一样。核心思路：给每条消息一个全局唯一 ID（业务唯一键 / MsgId），处理前先判重。

方案做法适用
数据库唯一索引把唯一 ID 建唯一约束，重复插入直接报唯一键冲突，捕获后忽略写库类操作，最稳
Redis 去重表处理前 SETNX msgId，已存在则说明处理过，跳过高并发、可容忍极小概率误差
状态机 / 乐观锁用业务状态兜底，如"待支付→已支付"，重复的支付消息发现已是"已支付"直接返回有明确状态流转的业务
用 Redis 判重的经典坑："先查 Redis 有没有 → 没有则处理 → 处理完写 Redis"这三步非原子，并发下两条重复消息可能都查到"没有"。要用 SETNX（原子的"不存在才设置"）把判重和占位合成一步，或直接依赖数据库唯一索引。
唯一 ID 用什么生成？用 MQ 自带的 MsgId 行不行？
优先用业务唯一键（如订单号、"用户ID+操作类型+业务时间"），因为它在业务上天然唯一、跨重发也不变。MQ 自带的 MsgId 有时在生产者重试时会变（生成新消息），不一定可靠。RocketMQ 提供了可自定义的 Key，可用作幂等键。总之：幂等键要能唯一标识"这次业务操作"，而不是"这条物理消息"。

9 · 消息顺序性 高频

场景：一个订单的三条消息"创建 → 支付 → 发货"必须按顺序被消费，如果"发货"先于"创建"被处理就乱套了。

为什么会乱序

  1. 分区打散：同一订单的三条消息被发到了不同分区，不同分区被不同消费者并行消费，先后无法保证。
  2. 消费端并发：即使消息按序到了，消费者用多线程处理，也会乱。

解决：把"要保序的消息"锁进同一条流水线

生产端
同一 orderId 的消息
用 orderId 做 key 哈希
──同 key 同分区──▶
Broker
全进 Partition-2
分区内严格有序
──单线程──▶
消费端
该分区单线程顺序消费
  • 生产端保证同一分区：发送时用业务键（如 orderId）做分区 key，Kafka/RocketMQ 会把相同 key 哈希到同一分区，天然有序进入。
  • 消费端保证顺序处理：一个分区只被一个消费者、且单线程处理（或按 key 把消息路由到同一个线程的队列里）。RocketMQ 提供 MessageListenerOrderly 顺序消费监听器。
关键权衡：全局有序 vs 分区有序。要全局严格有序，就只能用单分区 + 单消费者，等于放弃了并行，吞吐大跌。所以实践中几乎都用「局部有序」——只保证同一业务实体（同一订单）内有序，不同订单之间无所谓顺序。这样既保序又能并行。能接受局部有序就别追求全局有序。
顺序消费时，中间一条消息处理失败了怎么办？
这是顺序消费的硬伤：为了保序，不能跳过失败消息去处理后面的（否则顺序就断了）。通常做法是阻塞重试当前消息（RocketMQ 顺序消费失败会返回 SUSPEND，稍后重试同一条），直到成功或到达重试上限再进死信。代价是队头阻塞——一条卡住，后面全等着。所以顺序消费要特别注意消费逻辑的健壮性。

10 · 消息堆积 / 积压处理 高频

消息堆积 = 生产速度 > 消费速度，消息在 Broker 里越攒越多（几百万上千万条）。常见于消费端变慢（下游 DB 慢、消费逻辑重）或流量突增。

先定位原因，再对症下药

消费者挂了/变慢看消费端日志、监控 消费延迟（Lag = 最新 offset − 已消费 offset）。是 bug 就修，是慢就优化。
消费能力不足正常流量就是大 → 需要扩容消费能力。

紧急扩容的标准套路

核心约束：Kafka/RocketMQ 里一个分区最多被消费者组内一个消费者消费。所以消费者实例数 ≤ 分区数，光加消费者、分区不够也没用。
  1. 分区够 → 直接加消费者：消费者实例数加到接近分区数，并行度立刻上去。
  2. 分区不够 → 加分区 + 加消费者：临时扩分区，同时扩消费者。
  3. 终极方案（分区来不及加时）：临时写一个"搬运"消费者，它不处理业务，只飞快地把积压消息转发到一个分区数更多的新 Topic，再用大量消费者去消费新 Topic。相当于给积压消息临时开了个"多车道"。
预防 > 救火：① 监控消费 Lag，设告警；② 消费端做好批量处理、异步化；③ Kafka 天生磁盘存储、堆积能力极强（TB 级不慌），选型时若预期会有大堆积，优先 Kafka。
消息堆积久了会因为过期被删掉吗？
会。MQ 消息不是永久保留的，有保留策略（retention）：Kafka 默认保留 7 天或到达大小上限就删（无论是否被消费）。所以堆积如果超过保留期，还没消费的消息会被清理掉 → 丢数据。处理积压要抢在保留期内，必要时临时调大 retention。

11 · 延迟 / 定时消息

需求：下单后30 分钟未支付则自动取消。做法是下单时发一条"延迟 30 分钟"的消息，到点了消费者才收到，去检查订单状态。

MQ延迟消息实现
RocketMQ原生支持。老版支持 18 个固定延迟等级（1s/5s/…/2h）；新版支持任意时刻定时消息。发送时设 setDelayTimeLevel 即可。
RabbitMQ两种：① TTL + 死信队列（消息设过期时间，过期后进死信队列被消费）；② 官方 延迟插件 rabbitmq_delayed_message_exchange。
Kafka不原生支持。需自己实现：如按延迟档位建多个 Topic + 定时任务轮询搬运，或消费到未到期消息时 sleep/重新入队。较麻烦。
RocketMQ 延迟消息原理（简版）：发送时若带延迟等级，Broker 会把消息暂存到一个内部的 SCHEDULE_TOPIC_XXXX 定时主题（按等级分队列），由一个定时任务扫描，到期后再把消息投递回真正的目标 Topic，消费者这才收到。本质是"先存到一边，到点再搬回来"。

12 · 事务消息（分布式事务）高频

经典难题：本地数据库操作 和 发送 MQ 消息 要么都成功、要么都失败。比如"扣款成功"必须保证"通知积分服务的消息"也发出去，不能扣了款消息却丢了，也不能没扣款却发了消息。

为什么普通写法会出问题？ 
// 顺序一：先写库后发消息
扣款();           // 成功
sendMQ();         // ❌ 这步失败/宕机 → 扣了款但下游收不到

// 顺序二：先发消息后写库
sendMQ();         // 成功
扣款();           // ❌ 这步失败 → 消息发了但其实没扣款
两个操作跨了数据库和 MQ 两个系统，没法用本地事务包住。

RocketMQ 事务消息：两阶段 + 回查

RocketMQ 用半消息（Half Message）+ 事务回查优雅地解决了它：

① 发送半消息 生产者先发一条"半消息"到 Broker。半消息对消费者不可见（存着但不投递）。
▼
② 执行本地事务 Broker 回 ack 后，生产者执行本地事务（扣款）。
▼
③ 提交 / 回滚 本地事务成功 → 告诉 Broker Commit（半消息转为正式消息，投递给消费者）；失败 → Rollback（删除半消息）。
▼ 若第③步的通知也丢了呢？
④ 事务回查 Broker 迟迟收不到半消息的 Commit/Rollback，会主动回调生产者问："这个本地事务到底成没成？"生产者查一下本地状态再答复。彻底兜底。
本质：把"发消息"这个动作也变成一个可提交/可回滚的两阶段操作，并用回查机制解决"提交通知丢失"的极端情况，从而让本地事务和消息发送达成最终一致。这是分布式事务里"可靠消息最终一致性"方案的教科书实现。
事务消息保证了"消费者一定成功消费"吗？
不保证。事务消息只解决发送端的"本地事务与消息发送的原子性"（消息一定发得出去）。消费端处理失败是另一回事，靠消费重试 + 幂等 + 死信队列解决。别把两件事混为一谈。

13 · 死信队列 · 重试 · 消息回溯

消费重试

消费失败（抛异常/返回失败）时，MQ 不会立刻丢弃，而是过一会儿重新投递。RocketMQ 有阶梯式重试（重试间隔逐次拉长，默认最多 16 次）。给下游一个"缓过来"的机会（如 DB 短暂抖动）。

死信队列（Dead Letter Queue, DLQ）

如果重试到达上限还是失败（如消息本身格式错误、永远处理不了），继续重试没意义，就把它移到一个专门的"死信队列"里，不再自动投递。

正常消费 ──失败──▶ 重试1 ──失败──▶ 重试2 ... ──▶ 重试到上限 │ ▼ 【死信队列 DLQ】 （人工介入排查 / 后续补偿处理）
死信队列的价值：① 不阻塞正常消息（坏消息挪走，别卡住队列）；② 不丢失（存起来而非直接扔）；③ 便于人工排查和补偿。RabbitMQ 靠 x-dead-letter-exchange 配置，RocketMQ 有自动生成的 %DLQ% 死信 Topic。

消息回溯 / 重放

因为 Kafka/RocketMQ 消息消费后不立即删除（保留一段时间），消费者只是移动 offset。所以可以把 offset 往回调，重新消费历史消息——用于消费逻辑有 bug 修复后重跑、或新加一个下游要补历史数据。这是"日志型" MQ 相比传统队列的一大优势。

14 · 推 vs 拉（Push / Pull）

消息从 Broker 到消费者，有两种驱动方式：

Push（Broker 主动推）Pull（消费者主动拉）
实时性高，有消息立刻推取决于拉取频率
问题推太快压垮慢消费者（无法按消费能力调节）没消息时空轮询浪费资源
批量/速率控制难由消费者控制消费者自己决定拉多少、多快 → 天然限流
主流选择：Pull 为主。Kafka、RocketMQ 都用消费者主动拉，因为能让消费者按自己的处理能力取消息，不会被压垮（对削峰至关重要）。为了解决 Pull 的"空轮询"，用长轮询（Long Polling）：拉取时如果没消息，Broker 先 hold 住这个请求一小段时间，期间来了消息立刻返回，兼顾实时性和低空耗。RabbitMQ 则默认 Push（basic.consume），靠 QoS prefetch 限制未确认消息数来防止压垮。

15 · Kafka 为什么这么快 原理 高频

Kafka 单机能扛几十万甚至百万级 TPS，靠的是几个环环相扣的设计。这几乎是 MQ 原理题的天花板考点。

① 顺序写磁盘（而非随机写）

直觉里"磁盘慢"，但那是随机 I/O慢。Kafka 每个分区是一个只追加（append-only）的日志文件，消息永远往文件末尾顺序写。顺序写磁盘的速度接近甚至超过随机写内存（省去了磁盘寻道时间）。这是它敢用磁盘做存储还这么快的根基。

② 利用操作系统页缓存（PageCache）

Kafka 不自己在 JVM 堆里维护缓存，而是直接读写操作系统的 PageCache（内核内存）。写消息先进 PageCache（由 OS 择机刷盘），读消息大概率直接命中 PageCache。好处：① 避开 JVM GC 压力和对象开销；② 进程重启缓存还在（PageCache 属于内核，不随进程走）。

③ 零拷贝（Zero-Copy）高频

消费者读消息时，要把磁盘文件数据发到网卡。传统方式要在内核态和用户态之间来回拷贝 4 次、切换 4 次：

传统：磁盘→内核PageCache→用户缓冲区→内核Socket缓冲区→网卡 （4 次拷贝，2 次多余） 零拷贝：磁盘→内核PageCache──────────────────▶网卡 （sendfile，数据不进用户态）

Kafka 用 sendfile 系统调用（Java 的 FileChannel.transferTo），让数据直接从 PageCache 送到网卡，不经过用户态、不做多余拷贝。省掉的拷贝和上下文切换，在高吞吐下是巨大的性能提升。

④ 批量 + 压缩

生产者攒一批消息（batch）一次性发送，而不是一条一发，摊薄网络和系统调用开销；还可对整批压缩（gzip/snappy/lz4），减少网络和磁盘 I/O。消费端也批量拉取。

⑤ 分区并行

Topic 拆成多个分区分散在多台 Broker，读写天然并行，吞吐随分区数水平扩展。

一句话背诵：Kafka 快 = 顺序写（磁盘当顺序日志用）+ 页缓存（借 OS 内存、避 GC）+ 零拷贝（sendfile 省拷贝）+ 批量压缩（摊薄开销）+ 分区并行（水平扩展）。
零拷贝为什么能"零"？到底省了哪几次？
传统 read+write 流程：① 磁盘→内核 PageCache（DMA 拷贝，省不掉）② PageCache→用户缓冲区（CPU 拷贝，多余）③ 用户缓冲区→Socket 缓冲区（CPU 拷贝，多余）④ Socket→网卡（DMA，省不掉）。sendfile 直接让数据在内核内部从 PageCache 送到网卡（新版网卡支持 DMA gather 后连 PageCache→Socket 的 CPU 拷贝都省了），砍掉了②③两次用户态-内核态之间的 CPU 拷贝和相应的上下文切换。"零"指的是零 CPU 拷贝到用户态，不是字面上一次拷贝都没有。

16 · Kafka 存储结构（Segment / 索引）原理

一个分区是一个"无限长"的日志，但不可能存成一个巨大文件（没法删旧的、没法快速定位）。Kafka 把每个分区切成多个段（Segment）：

Partition 目录/ ├── 00000000000000000000.log ← 消息数据（Segment 1，从 offset 0 开始） ├── 00000000000000000000.index ← 偏移量索引（offset → 文件物理位置） ├── 00000000000000000000.timeindex← 时间索引（时间戳 → offset） ├── 00000000000000368769.log ← Segment 2（从 offset 368769 开始） ├── 00000000000000368769.index └── ...
  • .log：真正的消息，顺序追加。写满（默认 1GB）就新开一个 Segment。
  • .index：稀疏偏移量索引，记录"某个 offset → 在 .log 文件里的物理字节位置"。不是每条都记（稀疏），省空间。
  • 文件名 = 该 Segment 第一条消息的 offset，所以查某个 offset 时，先二分查找定位到哪个 Segment，再查 .index 找到大致位置，最后在 .log 里顺序扫一小段。
分段的两大好处：① 方便删除过期数据——直接删掉整个旧 Segment 文件即可（顺序删，不用在大文件里抠）；② 方便快速定位——文件名有序 + 稀疏索引，查任意 offset 都很快（O(log n) 定位段 + 小范围顺序扫）。

17 · 副本机制 ISR / HW / LEO 原理 高频

Broker 会宕机，磁盘会坏。Kafka 靠多副本保证分区数据不丢、服务不断：每个分区有 1 个 Leader + N 个 Follower，分散在不同 Broker。

Broker1
P0-Leader
读写都走它
Broker2
P0-Follower
只同步，不对外
Broker3
P0-Follower
只同步
生产/消费只和 Leader 交互；Follower 不停从 Leader 拉消息保持同步。Leader 挂了从 Follower 里选新 Leader

三个关键概念

LEOLog End Offset，副本下一条要写入的 offset，即当前最新位置。
HWHigh Watermark 高水位，= 所有 ISR 副本中最小的 LEO。消费者只能看到 HW 之前的消息（保证读到的消息一定已在所有同步副本上都有备份）。
ISRIn-Sync Replicas 同步副本集合，指跟 Leader 保持同步的副本（含 Leader）。落后太多的 Follower 会被踢出 ISR；追上了再回来。
HW 保证了"读一致性"：只有当一条消息被所有 ISR 副本都复制后，HW 才前移、这条消息才对消费者可见。这样即使 Leader 挂了，新 Leader（从 ISR 里选）上也一定有这条消息，消费者不会读到"后来消失"的消息。

它和"不丢消息"怎么联动

  • 生产者 acks=all：要求消息写入所有 ISR 副本才算成功。
  • min.insync.replicas=2：ISR 里至少要有 2 个副本存活，否则生产者报错拒绝写入——防止"ISR 只剩 Leader 一个时还在写，Leader 一挂就丢"。
  • 二者配合 = Kafka 零丢失的标准配置。
为什么 Kafka 选 Leader 时优先从 ISR 里选，而不是所有副本里选？
因为 ISR 里的副本是跟 Leader 数据同步的，选它们当 Leader 数据最全、丢失最少。如果允许从落后的非 ISR 副本里选（叫 unclean.leader.election，默认关闭），虽然能在 ISR 全挂时快速恢复可用性，但那个副本落后的数据就永久丢了——这是典型的可用性 vs 一致性（CAP）权衡：默认关闭 = 优先保证不丢数据（宁可分区暂时不可用）。

18 · 消费者组 & Rebalance 原理 高频

消费者组是 Kafka 实现"负载均衡 + 发布订阅"的核心（§3）。规则：一个分区在同一个组内只能分给一个消费者，一个消费者可以吃多个分区。

Topic 有 4 个分区 P0 P1 P2 P3，消费者组内： 2 个消费者 → C0 吃 P0 P1，C1 吃 P2 P3 （均分） 4 个消费者 → 一人一个，正好 （最优） 5 个消费者 → 有 1 个分不到分区，空闲 （消费者 > 分区，多的没用）

什么是 Rebalance（重平衡）

当组内消费者数量变化（新增/宕机/超时）、分区数量变化、订阅的 Topic 变化时，需要重新分配"谁消费哪些分区"，这个过程叫 Rebalance。

Rebalance 的痛点——"消费世界暂停"（Stop The World）：重平衡期间，整个组的所有消费者都要暂停消费，等重新分配完才恢复。如果频繁 Rebalance，消费就一直断断续续，甚至可能引发重复消费。所以要尽量避免不必要的 Rebalance。

常见的"意外 Rebalance"及规避

消费超时被踢消费者两次 poll 间隔超过 max.poll.interval.ms（默认 5 分钟）→ 被判定死亡触发 Rebalance。规避：别一次 poll 太多消息导致处理超时，或调大该值 / 减小 max.poll.records。
心跳超时消费者后台心跳超过 session.timeout.ms 没到 → 被踢。规避：合理设置心跳与超时时间。
GC 停顿过长、网络抖动，也会导致心跳/poll 超时触发 Rebalance。
分区分配策略：Range（按范围，可能不均）、RoundRobin（轮询，较均）、Sticky（粘性，尽量保持原有分配、减少变动，推荐）。新版还有增量协作式 Rebalance（Cooperative），只调整发生变化的部分分区，不再全组 STW，大幅降低影响。

19 · RocketMQ 存储原理 原理

RocketMQ 的存储和 Kafka 思路不同，是理解"另一种权衡"的好例子。核心是三个文件：

CommitLog 所有 Topic、所有队列的消息混在一起，顺序写入同一个 CommitLog（一个 Broker 就一份）。这保证了极致的顺序写。
▼ 但消费时要按 Topic/Queue 读，混在一起怎么找？
ConsumeQueue 每个 Topic 的每个 Queue 一个，是消息在 CommitLog 里位置的索引（存 offset+size+tag hash）。消费者读它，按图索骥去 CommitLog 取消息。相当于"目录"。
▼
IndexFile 按消息 Key 建的哈希索引，支持按 key 快速查消息（用于消息查询/排查），非消费必需。

Kafka vs RocketMQ 存储对比

KafkaRocketMQ
数据文件每个分区一个 .log（分散）全 Broker 一个 CommitLog（集中）
写入分区各自顺序写（分区多时=多个顺序写，趋于随机）永远只往一个 CommitLog 顺序写（更纯粹的顺序写）
读取直接读分区文件先读 ConsumeQueue 索引，再回 CommitLog 取（多一次跳转，靠 PageCache 缓解）
Topic/分区多时性能下降明显（文件多、随机 I/O）性能更稳（写入始终集中顺序）
取舍总结：Kafka 分区独立存储，少量 Topic 时吞吐更高，但 Topic/分区非常多时性能下滑；RocketMQ 用"集中 CommitLog + 索引"换来海量 Topic 下依然稳定，更契合电商那种 Topic 成百上千的业务场景。没有绝对优劣，是场景取舍。

20 · RabbitMQ 路由原理 原理

RabbitMQ 的灵魂是 Exchange（交换机）。生产者从不直接把消息发给队列，而是发给 Exchange，由 Exchange 按路由规则 + 绑定（Binding）决定消息进哪些队列。

Producer
带 routing key 发送
▶
Exchange 交换机
按类型+绑定路由
▶
Queue(s)
Consumer 从队列取

四种 Exchange 类型

类型路由规则典型用途
Directrouting key 完全匹配绑定的 key 才进队列精确点对点分发（按日志级别 error/info 分流）
Fanout广播：无视 key，发给所有绑定的队列发布订阅（一份消息多方消费）
Topicrouting key 按通配符匹配（* 一个词、# 多个词，如 order.*）灵活的多维度分发（最常用）
Headers按消息 header 属性匹配（不看 routing key）少用，规则复杂时
RabbitMQ 高可用——镜像队列（Mirrored Queue）：普通队列只在一个节点上，节点挂了队列就没了。镜像队列把队列在多个节点上各存一份镜像（一主多从），主挂了从顶上，保证队列数据不丢。新版推荐用更现代的 Quorum Queue（基于 Raft 一致性协议）替代镜像队列。
RabbitMQ 靠什么保证消息可靠不丢？
三管齐下，和 §7 三段论一致：① 生产端 Publisher Confirm（发布确认）——Broker 收到消息后回 ack，没收到就重发；② Broker 端 队列和消息都设持久化（durable + persistent） + 镜像/Quorum 队列，防宕机丢；③ 消费端 手动 ack（manual acknowledgment）——处理成功才 ack，失败/宕机则消息重新入队。

Kafka 生产者（Java）—— 对应 §7 不丢 / §9 顺序

Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092,broker2:9092");
props.put("key.serializer",   "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

// —— 不丢消息的关键配置（§7）——
props.put("acks", "all");            // 所有 ISR 副本都写入才算成功
props.put("retries", 3);            // 发送失败自动重试
props.put("enable.idempotence", true); // 幂等生产者：重试也不会在 Broker 端产生重复

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// key = orderId：相同订单哈希到同一分区 → 分区内有序（§9）
String orderId = "ORDER_1001";
ProducerRecord<String, String> record =
    new ProducerRecord<>("order-topic", orderId, "订单已创建");

// 同步发送并检查结果（异步则在 callback 里判断 exception）
try {
    RecordMetadata meta = producer.send(record).get();
    System.out.printf("发送成功 partition=%d offset=%d%n",
        meta.partition(), meta.offset());
} catch (Exception e) {
    // 记录 + 重发 / 落库补偿，别静默吞掉
}
producer.close();

Kafka 消费者（Java）—— 对应 §7 手动提交 / §8 幂等

Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092");
props.put("group.id", "points-group");        // 消费者组（§3/§18）
props.put("key.deserializer",   "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");

// —— 不丢消息的关键：关闭自动提交，处理完再手动提交（§7）——
props.put("enable.auto.commit", "false");
props.put("max.poll.records", 100);           // 一次别拉太多，避免处理超时触发 Rebalance（§18）

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("order-topic"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        // 幂等：先按业务唯一键判重（§8），已处理过就跳过
        if (alreadyHandled(r.key())) continue;
        process(r.value());       // 真正的业务处理
        markHandled(r.key());     // 落库/写 Redis 标记
    }
    consumer.commitSync();        // ✅ 处理成功后才提交 offset
}

Kafka 生产 + 消费（Go，segmentio/kafka-go）

// 生产者
w := &kafka.Writer{
    Addr:         kafka.TCP("broker1:9092"),
    Topic:        "order-topic",
    Balancer:     &kafka.Hash{},   // 按 key 哈希分区 → 同 key 同分区（§9）
    RequiredAcks: kafka.RequireAll, // acks=all，不丢（§7）
}
err := w.WriteMessages(context.Background(), kafka.Message{
    Key:   []byte("ORDER_1001"),   // orderId 做 key
    Value: []byte("订单已创建"),
})

// 消费者：手动提交
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"broker1:9092"},
    GroupID: "points-group",       // 消费者组
    Topic:   "order-topic",
})
for {
    m, err := r.FetchMessage(context.Background()) // 拉取但不自动提交
    if err != nil { break }
    if alreadyHandled(string(m.Key)) { r.CommitMessages(context.Background(), m); continue }
    process(m.Value)                               // 先处理
    r.CommitMessages(context.Background(), m)       // ✅ 成功后再提交（§7）
}

RocketMQ 生产者（Java）—— 含事务消息 §12 / 延迟消息 §11

// 普通同步发送：检查 SendStatus 才算可靠（§7）
DefaultMQProducer producer = new DefaultMQProducer("order-producer-group");
producer.setNamesrvAddr("namesrv:9876");
producer.start();

Message msg = new Message("OrderTopic", "TagA", "ORDER_1001",
                          "订单已创建".getBytes());
// 延迟消息：延迟等级 3 ≈ 10s（§11），到点消费者才收到
msg.setDelayTimeLevel(3);
SendResult result = producer.send(msg);
assert result.getSendStatus() == SendStatus.SEND_OK;

// —— 事务消息（§12）：半消息 + 本地事务 + 回查 ——
TransactionMQProducer txProducer = new TransactionMQProducer("tx-group");
txProducer.setTransactionListener(new TransactionListener() {
    @Override public LocalTransactionState executeLocalTransaction(Message m, Object arg) {
        try { deduct(); return LocalTransactionState.COMMIT_MESSAGE; }   // 本地事务成功→提交
        catch (Exception e) { return LocalTransactionState.ROLLBACK_MESSAGE; }
    }
    @Override public LocalTransactionState checkLocalTransaction(MessageExt m) {
        // Broker 回查：查本地事务到底成没成（§12 第④步）
        return isDeducted(m.getKeys()) ? LocalTransactionState.COMMIT_MESSAGE
                                       : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});

RocketMQ 消费者（Java）—— 并发 vs 顺序 §9 / 幂等 §8

DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("points-consumer-group");
consumer.setNamesrvAddr("namesrv:9876");
consumer.subscribe("OrderTopic", "*");

// 顺序消费：MessageListenerOrderly，同一队列单线程按序处理（§9）
consumer.registerMessageListener((MessageListenerOrderly) (msgs, ctx) -> {
    for (MessageExt m : msgs) {
        if (alreadyHandled(m.getKeys())) continue; // 幂等判重（§8）
        process(m.getBody());
        markHandled(m.getKeys());
    }
    return ConsumeOrderlyStatus.SUCCESS;           // 失败返回 SUSPEND → 阻塞重试当前队列
});
consumer.start();
并发消费把监听器换成 MessageListenerConcurrently、返回 ConsumeConcurrentlyStatus.RECONSUME_LATER 触发重试；多次失败自动进 %DLQ% 死信 Topic（§13）。要顺序就用 Orderly，要吞吐就用 Concurrently——这正是 §9 里"顺序 vs 并行"权衡的代码体现。

附 · 选型决策速查

要极致吞吐、日志采集、大数据/流处理？ → Kafka（顺序写+零拷贝+堆积能力强）
电商/金融业务，要事务消息、延迟消息、顺序消息、海量 Topic？ → RocketMQ（业务功能最全，金融级可靠）
体量不大、要灵活路由或极低延迟、想开箱即用？ → RabbitMQ（Exchange 路由灵活，µs 级延迟）

高频面试速记

问题一句话答案
为什么用 MQ？解耦（服务不互相依赖）、异步（主链路更快）、削峰（缓冲高并发）。
用 MQ 有什么缺点？可用性下降、复杂度上升、一致性变难（丢/重/乱序都得处理）。
如何保证消息不丢？三段：生产 acks=all+重试 → Broker 多副本+同步刷盘 → 消费手动提交(处理完再提交)。
如何保证不重复消费？做不到绝对不重，用At-least-once + 消费端幂等（唯一键判重/DB 唯一索引/SETNX）。
如何保证顺序？同一业务键→同一分区（生产端 key 哈希）+ 该分区单线程消费。追求局部有序而非全局有序。
消息堆积怎么办？先定位原因；分区够就加消费者，不够就加分区/搬到多分区新 Topic 加速消费。
Kafka 为什么快？顺序写 + 页缓存 + 零拷贝(sendfile) + 批量压缩 + 分区并行。
零拷贝省了什么？省掉内核↔用户态之间 2 次多余 CPU 拷贝和上下文切换，数据从 PageCache 直达网卡。
ISR / HW / LEO？ISR=同步副本集；LEO=下条写入位置；HW=所有 ISR 最小 LEO，消费者只能看到 HW 之前。
什么是 Rebalance？危害？组内消费者/分区变化时重新分配分区；期间全组停止消费(STW)，要尽量避免频繁触发。
事务消息原理？RocketMQ 半消息(不可见)→执行本地事务→Commit/Rollback→Broker 回查兜底，达成最终一致。
延迟消息谁支持？RocketMQ 原生；RabbitMQ 靠 TTL+死信/插件；Kafka 不原生需自实现。
死信队列作用？重试到上限仍失败的消息挪到 DLQ，不阻塞正常消息、不丢失、便于人工补偿。
Push 还是 Pull？Kafka/RocketMQ 用 Pull（消费者按能力拉，防压垮）+ 长轮询解决空转；RabbitMQ 默认 Push。
三大 MQ 怎么选？吞吐/日志→Kafka；业务功能全/金融→RocketMQ；灵活路由/低延迟/小项目→RabbitMQ。
