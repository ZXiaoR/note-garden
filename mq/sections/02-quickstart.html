🐳 02.1 · 本地环境搭建：Docker Compose 一键启动 Kafka 3.8（KRaft 模式）与 Web UI

🐳 02.1 启动单节点 Kafka 与可视化控制台

早期版本的 Kafka 必须额外先搭一套 ZooKeeper 才能运行；从 Kafka 3.3+ 起正式内置了 KRaft（Kafka Raft Metadata mode，基于 Raft 共识算法的内置元数据模式），Kafka 4.0 更已彻底移除 ZooKeeper。本地练习直接用官方 apache/kafka:3.8.0 镜像搭配可视化面板 kafka-ui，新建一个空目录保存以下 docker-compose.yml 后执行 docker compose up -d 即可：

🐳 docker-compose.yml · 单节点 Kafka (KRaft) + Kafka Web UI [Kafka 3.8 / 兼容 4.0] 
services:
  kafka:
    image: apache/kafka:3.8.0
    container_name: local-kafka
    ports:
      - "9092:9092"   # 供宿主机上的 Go / Node.js 代码连接 (localhost:9092)
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      # 双监听器：INTERNAL 供 Docker 容器内 Web UI 访问，EXTERNAL 供宿主机代码访问
      KAFKA_LISTENERS: INTERNAL://:29092,EXTERNAL://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:29092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      # 单节点开发环境必须把内部 Topic 副本数设为 1（生产多节点默认是 3）
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1

  kafka-ui:
    image: provectuslabs/kafka-ui:v0.7.2
    container_name: local-kafka-ui
    ports:
      - "8080:8080"   # 浏览器访问 http://localhost:8080 查看 Topic、分区与消息
    depends_on:
      - kafka
    environment:
      KAFKA_CLUSTERS_0_NAME: local-kraft
      KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:29092

💡 启动约 10 秒后，浏览器打开 http://localhost:8080，即可在图形界面看到在线的 1 台 Broker 节点。注意单机环境下 KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1 不可省略，否则消费组提交 Offset 时会因为默认寻找 3 台副本而报错。

⌨️ 02.2 · 命令行实操：建 Topic、发消息、消费消息与查看消费组 Lag

⌨️ 02.2 先用 4 条命令走通完整收发闭环

官方镜像已将管理脚本放在容器内的 /opt/kafka/bin/ 目录。打开终端依次执行下面 4 步，亲眼看到消息写入与 Offset 变化：

⌨️ quickstart_cli.sh · 建 Topic、生产、消费与查看积压 Lag [Kafka 3.x / 4.x] 
# 1. 创建名为 order.events 的 Topic，指定 3 个分区、单机 1 个副本
docker exec -it local-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic order.events --partitions 3 --replication-factor 1

# 查看刚创建的 Topic 详情（确认 Partition 0 / 1 / 2 均已就绪）
docker exec -it local-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic order.events

# 2. 发送几条带 Key 的测试消息（按冒号分隔 Key:Value，输入完按 Ctrl+C 退出）
docker exec -it local-kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic order.events \
  --property parse.key=true --property key.separator=:
# 依次粘贴下面三行回车：
# ORD_101:{"orderNo":"ORD_101","amount":99}
# ORD_102:{"orderNo":"ORD_102","amount":199}
# ORD_103:{"orderNo":"ORD_103","amount":299}

# 3. 以消费组 demo-cli-grp 从头消费消息（打印所属分区、Offset、Key 和 Value）
docker exec -it local-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic order.events \
  --group demo-cli-grp --from-beginning \
  --property print.partition=true --property print.offset=true --property print.key=true

# 4. 另开一个终端查看消费组进度与积压量 LAG（LAG = LOG-END-OFFSET - CURRENT-OFFSET）
docker exec -it local-kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group demo-cli-grp
🚀 02.3 · 第一段代码：Go (segmentio/kafka-go) 与 Node.js (kafkajs) 最小收发示例

🚀 02.3 用代码连上本地 Kafka 收发消息

下面分别给出 Go（采用纯 Go 实现、零 C 依赖的 github.com/segmentio/kafka-go v0.4.47，后续实战章节均以它为主）与 Node.js（采用 kafkajs v2.2.4）的最小生产者 + 消费者闭环代码，连接本机 localhost:9092 直接运行即可：

🐹 main.go · Go 最小生产与消费组示例 [kafka-go v0.4.47] 
// go mod init mq-demo && go get github.com/segmentio/kafka-go@v0.4.47
package main

import (
    "context"
    "fmt"
    "log"
    "time"

    "github.com/segmentio/kafka-go"
)

func main() {
    ctx := context.Background()

    // 1. 生产者：向 order.events 发送 1 条消息
    writer := &kafka.Writer{
        Addr:     kafka.TCP("localhost:9092"),
        Topic:    "order.events",
        Balancer: &kafka.Hash{}, // 按 Key 哈希选分区
    }
    err := writer.WriteMessages(ctx, kafka.Message{
        Key:   []byte("ORD_2001"),
        Value: []byte(`{"orderNo":"ORD_2001","event":"PAID"}`),
    })
    if err != nil {
        log.Fatal("发送失败:", err)
    }
    _ = writer.Close()
    fmt.Println("✅ 消息发送成功")

    // 2. 消费者组：读取刚发出的消息
    reader := kafka.NewReader(kafka.ReaderConfig{
        Brokers:     []string{"localhost:9092"},
        Topic:       "order.events",
        GroupID:     "coupon-service-grp",
        StartOffset: kafka.FirstOffset, // 新消费组首次从头读
    })
    defer reader.Close()

    readCtx, cancel := context.WithTimeout(ctx, 10*time.Second)
    defer cancel()

    msg, err := reader.ReadMessage(readCtx)
    if err != nil {
        log.Fatal("消费失败:", err)
    }
    fmt.Printf("📥 收到消息: 分区=%d offset=%d key=%s val=%s\n",
        msg.Partition, msg.Offset, string(msg.Key), string(msg.Value))
}
🟢 demo.mjs · Node.js 最小生产与消费示例 [kafkajs v2.2.4] 
// npm init -y && npm install kafkajs@2.2.4
import { Kafka } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'order-demo-app',
  brokers: ['localhost:9092'],
});

async function main() {
  // 1. 生产者发送消息
  const producer = kafka.producer();
  await producer.connect();
  await producer.send({
    topic: 'order.events',
    messages: [
      { key: 'ORD_2002', value: JSON.stringify({ orderNo: 'ORD_2002', event: 'PAID' }) },
    ],
  });
  await producer.disconnect();
  console.log('✅ Node 生产者发送成功');

  // 2. 消费者组订阅并消费
  const consumer = kafka.consumer({ groupId: 'sms-service-grp' });
  await consumer.connect();
  await consumer.subscribe({ topic: 'order.events', fromBeginning: true });

  await consumer.run({
    eachMessage: async ({ partition, message }) => {
      console.log(
        `📥 收到: 分区=${partition} offset=${message.offset} key=${message.key} val=${message.value}`
      );
    },
  });
}

main().catch(console.error);
🧪 02.4 · 动手实验：用三个终端亲眼验证「同组竞争分摊」与「跨组独立广播」

🧪 02.4 5 分钟动手实验：把抽象概念变成体感

刚才我们建的 order.events 有 3 个分区（P0 / P1 / P2）。现在打开 4 个终端窗口做两个小实验，验证第 01 章讲的消费者组规则：

🧪 group_lab.sh · 实验步骤：2 个同组消费者 + 1 个异组消费者对照观察 
# 【终端 1 & 终端 2】分别执行完全相同的命令：启动两个同属于 coupon-grp 的消费者
docker exec -it local-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic order.events --group coupon-grp \
  --property print.partition=true --property print.key=true

# 【终端 3】启动一个属于不同消费组 sms-grp 的消费者
docker exec -it local-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic order.events --group sms-grp \
  --property print.partition=true --property print.key=true

# 【终端 4】查看 coupon-grp 分区分配情况，然后用 producer 连续发 6 条不同 Key 的消息
docker exec -it local-kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group coupon-grp
  • 预期现象 ①（组内分摊）：在 --describe --group coupon-grp 的输出里，你会看到 CONSUMER-ID 列把 3 个分区自动拆成了 1 台负责 2 个分区（如 P0, P1）、另 1 台负责 1 个分区（如 P2）；当你连发 6 条消息时，终端 1 和终端 2 加起来正好收到这 6 条，没有任何一条重复。
  • 预期现象 ②（组间广播）：与此同时，终端 3（sms-grp）独自把这 6 条消息一条不落全收到了——这就是一份订单事件同时驱动发券与发短信的工作方式。

💡 背后的原理：为什么终端 1、2、3 平时静静挂在那里不占 CPU，而你在终端 4 一敲回车它们毫秒级就跳出消息？底层靠的是「客户端主动 Pull + Broker 长轮询挂起唤醒」，详见 《📘 核心原理篇 · 00 推与拉：Pull + 长轮询》。

☑️ 本章即时场景题（先想答案，再点击展开）

1. 同事先往 Topic 里发了 10 条测试消息，随后才第一次启动自己的 Go 消费者（未设 StartOffset），结果一条都没收到，为什么？

因为对于之前从未提交过 Offset 的全新消费组，客户端默认从最新末尾（latest / kafka.LastOffset）开始监听，只收启动之后新进来的消息，防止新服务一上线意外把过去 7 天几千万条老订单全重跑一遍。本地调试想读历史消息，需显式加 --from-beginning 或在 Go 中设 StartOffset: kafka.FirstOffset。

2. 在上面的动手实验里，如果你再开第 4、第 5 个同样叫 coupon-grp 的终端，--describe 里会看到什么？

因为 order.events 一共只有 3 个分区，当 coupon-grp 里的消费者达到 4 个时，前 3 个终端各自领到 1 个分区，第 4 个终端不会出现在分区分配行里（处于空闲待命状态）；只有当你按 Ctrl+C 关掉前面某一个终端后，Kafka 触发重平衡才会把空出来的那个分区自动交给第 4 个终端。
