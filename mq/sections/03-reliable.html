03 可靠性生命线 · 怎么保证消息「一分不丢」（三段论）与「绝不重算」（幂等 & EOS）？ ZERO-LOSS · IDEMPOTENCY · EXACTLY-ONCE
❓ 03.1 · 面试第一必考题：“如何保证消息队列一条消息都不丢？”标准三段论怎么答才滴水不漏？

🛡️ 03.1 消息不丢失：把「生产 → 存储 → 消费」三道关卡逐段焊死

不要笼统地回答“加 ACK 和持久化”。一条消息从诞生到真正落库生效，一共跨越三个阶段，任何一个阶段掉链子都会丢数据。满分回答必须沿着「第一关：生产发送 ──▶ 第二关：Broker 存储 ──▶ 第三关：消费提交」逐段给出可落地的配置与代码铁律：

🚧 第一关：生产端 → Broker（防网络抖动、超时丢包） 核心：确认机制 (ACK) + 失败重试/落库兜底
• 严禁使用 oneway（发了不管）或忽略返回结果！必须同步等待返回，或在异步 Callback 回调里捕获异常并重试。
• Kafka 生产配置：必须设置 acks = all（或 -1）（Kafka 3.0+ 已默认开启），要求 Leader 且所有 ISR 同步副本都写入成功才回 ACK；同时配好 retries 与 delivery.timeout.ms。
• RocketMQ 生产配置：使用同步 producer.send(msg) 并校验 SendStatus.SEND_OK（异步发送必须实现 SendCallback.onException 重试或写本地补偿表），更严谨的跨库场景直接上事务消息（第 05 章）。
• RabbitMQ 生产配置：开启 Publisher Confirm（发布确认模式） 确认消息到达 Exchange，并开启 mandatory=true + ReturnsCallback 防止 Exchange 路由不到任何 Queue 时静默丢弃！
⚠️ 为什么 acks=1 依然会丢消息？ acks=1 只等 Leader 自己写进 PageCache 就向生产者返回成功；如果此时 Follower 还没来得及拉取，Leader 突然断电宕机，新选出的 Leader 上根本没有这条消息，数据当场蒸发！
🚧 第二关：Broker 存储阶段（防单机掉电丢内存 PageCache、防磁盘物理损坏） 核心：多副本冗余 + 刷盘策略 + 禁脏选主
为了高吞吐，MQ 收到消息通常先写进操作系统内存（PageCache）再异步刷盘；单机断电或硬盘坏了就会丢内存里的未刷盘数据。生产上靠「多副本 + 刷盘策略」双保险兜底：
• Kafka 零丢失黄金四件套：
  ① Topic 副本数 replication.factor >= 3（跨机架部署）；
  ② 最小同步副本数 min.insync.replicas >= 2（配合生产端 acks=all，保证每条消息至少同时落进 2 台机器的内存，防止 ISR 缩成只剩 Leader 1 台时单点挂机丢数）；
  ③ 严禁非同步副本选主 unclean.leader.election.enable = false（宁可短暂不可写，也绝不选落后副本上来丢数据）。
• RocketMQ 存储零丢失：核心资金链路开启 同步刷盘（flushDiskType = SYNC_FLUSH） + 主从同步复制（brokerRole = SYNC_MASTER）或 DLedger Raft 多副本。
• RabbitMQ 存储零丢失：Exchange 设 durable=true + Queue 设 durable=true + Message 设 deliveryMode=2（持久化），集群层面直接用基于 Raft 的 Quorum Queue（仲裁队列）。
🚧 第三关：Broker → 消费端（线上 80% 的丢消息事故都发生在这里！） 铁律：关掉自动提交，必须「先完成业务，再手动 ACK」
❌ 两种典型的消费端自杀式丢消息：
死法 A（开启自动提交 / 先提交后处理）：刚拉到消息就提交了 Offset，结果业务写库报错或容器 OOM 重启，Broker 以为你处理完了，永远不再重投！
死法 B（拉到消息后丢进自建异步线程池就立刻 ACK）：主线程立刻回了 ACK，但异步线程池队列满了拒绝，或机器重启导致内存线程池里的消息全丢！
✅ 唯一正确的姿势（先干完活，再签字画押）：
1. 关闭自动提交（Kafka 设 enable.auto.commit = false；RabbitMQ 设 AcknowledgeMode.MANUAL）；
2. 在当前消费线程同步执行完业务逻辑并落库成功；
3. 最后一步才调用 commitSync() / basicAck() / 返回 CONSUME_SUCCESS！
❓ 03.2 · 为什么保证了“不丢”就一定会遇到“重复”？Kafka 的幂等生产者（PID + Seq）到底防住了什么？

♻️ 03.2 不丢与不重的博弈：三种投递语义 & Kafka 幂等生产者底层机制

在分布式网络中，当你按 03.1 的要求做到了“不丢消息”（生产超时重试 + 消费先处理后提交），重复消息就成了必然会发生的物理现象：

  • 生产端重试导致 Broker 重复写入：Producer 发消息给 Broker，Broker 已经写盘成功了，但回给 Producer 的 ACK 在半路网络抖动丢了；Producer 超时后重发，Broker 就存了两条一模一样的消息。
  • 消费端重启/Rebalance 导致重复投递：Consumer 业务刚执行成功（比如已经给用户加了 100 积分），正准备调 commitSync() 提交 Offset 时机器突然断电或触发了 Rebalance；新接手的消费者从旧 Offset 重新拉取，又给用户加了一次 100 积分！
投递语义 核心含义 工程定位与实现方式
① 最多一次
At-most-once		 消息绝不重复，但可能丢失 生产端 acks=0 发了不管，或消费端先提交 Offset 再处理。仅用于完全不怕丢的监控日志。
② 至少一次 ⭐主流基底
At-least-once		 消息绝不丢失，但可能重复 生产端 acks=all + 重试，消费端先处理后手动提交。所有主流 MQ 的基础可靠语义。
③ 精确一次 ⭐业务目标
Exactly-once (EOS)		 消息既不丢失，也不重复生效 工业界黄金公式：At-least-once（MQ 保不丢） + 消费端业务幂等（业务防重算） = 端到端 Exactly-Once！
🔍 进阶深挖 · Kafka 的 enable.idempotence=true（PID + Sequence Number）是怎么工作的？它能代替消费端业务幂等吗？

面试官非常喜欢追问：“既然 Kafka 有幂等生产者（enable.idempotence = true，Kafka 3.0+ 默认开启），是不是消费端就不用写幂等代码了？”——绝对不能代替！必须搞懂它的工作原理和作用边界：

⚙️ Kafka 幂等生产者底层机制：PID（Producer ID） + Sequence Number（单调递增序列号）
  1. 分配 PID 与递增序号：每个开启幂等的 Producer 初始化时，Broker 会为它分配一个全局唯一的 PID。Producer 往每个 (Topic, Partition) 发送的每一批消息，都会附带一个从 0 开始严格递增的 Seq 序列号。
  2. Broker 端缓存判重与防乱序：Broker 端在内存中为每个 (PID, Partition) 维护最近 5 个 Batch 的序列号状态：
    • 若收到 Seq == Broker期望的 LastSeq + 1 👉 正常追加写入；
    • 若收到 Seq <= LastSeq 👉 说明是网络超时引起的重复重试包，Broker 直接丢弃并返回成功（消除生产端重试造成的重复落盘）；
    • 若收到 Seq > LastSeq + 1 👉 说明中间有批次没到（乱序），抛出 OutOfOrderSequenceException，这就顺带保证了即使开启管道并发 max.in.flight.requests.per.connection <= 5，重试也绝不会把分区内的消息顺序搞乱！
🚫 为什么它不能代替「消费端业务幂等」？（3 大边界限制）：
1. 仅限单次会话（单 PID）：如果 Producer 进程重启，Broker 会分配一个新的 PID，旧会话重试的幂等上下文就断了；
2. 仅防网关/网络层重试：如果上游业务代码自己因为 Bug 调了两次 producer.send()，在 Kafka 看来这是两条合法的新消息（Seq 分别是 1 和 2）；
3. 拦不住消费端重复拉取：如果 Consumer 已经写完 MySQL，但在提交 Offset 前 Crash 或 Rebalance，重启后依然会再拉取消费一遍！
👉 结论：无论 MQ 内部多强，消费端落库/扣款时必须实现业务幂等！
❓ 03.3 · 消费端业务幂等到底怎么写代码？为什么很多人写的 Redis SETNX 幂等会在崩溃时丢消息？

🛠️ 03.3 消费端幂等 3 大标准落地方案 & 避坑指南

幂等（Idempotency）的数学定义是 \(f(f(x)) = f(x)\)——同一条业务消息无论被投递 1 次还是 10 次，对数据库状态的影响完全相同。落地时第一步是确定「业务唯一幂等键（Idempotent Key）」（如 order_no、pay_serial_no，优先用业务唯一单号，不要盲目信 MQ 自动生成的物理 msgId，因为上游业务重发时 msgId 会变）：

🥇 方案一：数据库唯一索引 / 本地事务防重表（最稳妥、金融账务首选） 100% 物理兜底
• 做法 A（业务表自带唯一键）：比如消费“创建订单/支付流水”消息，直接在表中对 order_no 建 UNIQUE KEY uk_order_no (order_no)。重复消息插入时直接触发 DuplicateKeyException，捕获该异常后直接视为消费成功并提交 Offset。
• 做法 B（扣余额/加积分 + 独立防重流水表同事务）：给用户加积分是 UPDATE points = points + 10，没有天然唯一插入怎么办？在同一个 MySQL 数据库里建一张 mq_consume_log (biz_key PRIMARY KEY, status, create_time)，把「① 插入 mq_consume_log ──▶ ② UPDATE 加积分」包在同一个本地数据库事务里！如果重复消息进来，第 ① 步主键冲突直接回滚事务，积分绝不会多加一分！
🥈 方案二：业务状态机 / 乐观锁条件更新（更新类业务最优雅写法） 零额外表开销
许多业务本身就有严格的单向状态流转：10-待支付 ──▶ 20-已支付 ──▶ 30-已发货。消费“支付成功”消息时，不要裸写 UPDATE，而是把前置状态写进 WHERE 条件里：
UPDATE t_order SET status = 20 WHERE order_no = 'ORD_1001' AND status = 10; 第一条消息把 status 改成了 20（受影响行数 = 1）；第二条重复消息再来时，因为 status 已经不是 10 了，受影响行数为 0，天然幂等！
🥉 方案三：Redis 防重表 —— 警惕面试最爱考的两个「Redis 判重死穴」！ 高并发前置过滤 + 数据库兜底
❌ 死穴 1：先 GET 查不在，再 SET（非原子并发穿透）
两条重复消息同时到达两个实例，同时执行 GET 都发现不存在，于是同时去执行业务！
❌ 死穴 2：一上来就 SETNX，发现存在就直接 ACK 跳过（崩溃丢消息！）
如果线程 A 刚执行完 SETNX 占位成功，还没来得及写数据库就 OOM 崩溃了；等你重启重投这条消息时，发现 Redis 里已经有这个 Key 了，如果直接跳过并提交 Offset，这条消息就永远没有写进数据库，彻底丢了！
✅ 正确的 Redis「三态状态机 + DB 唯一键」组合拳：
1. 收到消息执行 SET biz_key "PROCESSING" NX EX 30（原子抢占处理中锁，带 30 秒租约）；
2. 若抢锁失败：看当前值是 "DONE" 则直接 ACK 跳过；若是 "PROCESSING" 则说明有另一个线程正在跑，稍后重试（切勿直接 ACK）；
3. 抢锁成功后执行 DB 事务（DB 依然保留唯一索引做终极兜底），若报错则在 catch 中主动 DEL biz_key 让下次重试能进来；
4. DB 成功后将 Redis 值更新为 SET biz_key "DONE" EX 86400，最后提交 Offset！
