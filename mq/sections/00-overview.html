00.1 · 一屏看懂定位：消息队列的定义、快递驿站类比与同步调用三大痛点

00.1 消息队列是什么，以及它解决什么问题

一句话定义：MQ（Message Queue，消息队列）是部署在后端服务之间的异步消息中转组件——上游服务把任务或事件作为一条「消息」写进队列即可立即返回，下游服务再按自己的处理节奏从队列中取出执行。

用日常生活里的小区快递驿站打个比方：如果没有驿站，快递员每送一件包裹都必须站在楼下打电话，等收件人下楼签收后才能去送下一单（这就是同步直接调用）；有了快递驿站后，快递员把包裹放上驿站货架就能立刻骑车去跑下一单，收件人下班回家再按取件码慢慢拿（这就是经过消息队列的异步流转）。

放到真实的「电商用户下单」链路里看：如果订单服务用 RPC（Remote Procedure Call，远程过程调用）或 HTTP 同步依次调用积分、短信、物流服务，会同时遇到代码强耦合（加一个发券服务就得改订单代码）、接口响应慢（串行累加几百毫秒）和突发洪峰冲垮数据库三个痛点；在应用服务之间加一层 MQ，就能一次性获得解耦、异步、削峰三项核心收益：

  • 解耦（Decoupling，看架构依赖）：订单服务只管往 order.paid 发一条「订单已支付」事件；明天新增「大数据画像」或「发新人券」服务，直接自行订阅即可，订单服务一行代码不用改，短信网关短暂抖动也不会拖垮下单。
  • 异步（Asynchronization，看接口响应耗时）：把发短信、加积分等无需用户当场等待的支线剥离到后台，接口耗时从 470ms 降到 25ms。
  • 削峰填谷（Peak Shaving，看突发流量保护）：秒杀瞬时涌入 10,000 QPS（Queries Per Second，每秒查询率），MQ 先把请求悉数接住暂存，下游消费者按 MySQL 能承受的 2,000 QPS 匀速拉取落库，5 秒消化完毕而不宕机。

00.3 · 选型边界：什么时候不该用 MQ、引入的三大代价与四方方案对比

00.3 什么时候不该用 MQ，以及它与其他方案的边界

三种明确「不该用 MQ」的场景
  1. 调用方需要立刻拿到确定结果：例如用户登录校验密码、收银台同步扣减账户余额——用户正盯着屏幕等成功还是失败，必须同步调用直接返回。
  2. 系统很小、流量很低：内部管理后台日均几百单，直接调函数或单库事务清清楚楚，硬加一套 Kafka 集群纯属徒增运维负担。
  3. 要求跨系统实时强一致：MQ 天生只能做到「几毫秒到几秒后的最终一致」，不能替代单库 ACID（Atomicity, Consistency, Isolation, Durability，原子性、一致性、隔离性、持久性）强事务。
引入 MQ 必须承担的「三大代价」
  1. 系统可用性依赖增加：链路中间多了一层基础设施，一旦 MQ 集群故障且未做高可用，整条异步业务都会停摆（见 04.1 与原理篇多副本机制）。
  2. 工程复杂度上升：原本一次函数调用只有成功或报错，换成发消息后必须处理消息丢失、重复消费、顺序错乱、消息积压四个新问题（见 04–05 章）。
  3. 数据一致性挑战：本地数据库改成功了但消息没发出去怎么办？需要用本地消息表或事务消息兜底（见 03.5）。

直接 RPC vs 定时任务 vs Redis Stream vs 专业 MQ 对比表

方案 实时性与吞吐 可靠性与堆积能力 最适合什么场景
直接 RPC / HTTP 实时同步返回（毫秒级），受最慢下游拖累 无中间缓冲，下游挂机直接报错，无法削峰 登录鉴权、查询详情、实时扣款等必须当场拿到返回值的主链路操作。
定时任务（Cron 扫表） 分钟级延迟，高频扫大表消耗数据库 I/O 数据本来就在数据库里，不额外丢数据 每日凌晨财务对账、低频兜底补偿扫描（不适合高实时事件触发）。
Redis Stream 亚毫秒级极快，单核数万 QPS 纯内存存储成本高，不适合百万级以上堆积；AOF 秒级刷盘极端断电可能丢 1 秒数据 已有 Redis 的中小型项目、日消息百万级以内、不想额外维护一套重型 MQ 组件（详见 Redis 笔记 04.9）。
专业 MQ（Kafka 等） 毫秒级异步投递，单机十万至百万 TPS（Transactions Per Second，每秒事务/消息数） 磁盘顺序持久化 + 多副本同步，支持 GB~TB 级海量堆积与历史回溯 核心业务异步解耦、高并发秒杀削峰、全站日志埋点管道、跨系统可靠事件同步。
市面三大主流 MQ 各一句话定位（本篇主线使用 Kafka，详细对比见 06 · 三大 MQ 选型）：
• Apache Kafka：为百万级高吞吐、TB 级磁盘堆积与日志/大数据流管道而生，生态最广。
• Apache RocketMQ：为核心电商金融交易而生，原生内置事务消息、任意定时消息与重试死信队列。
• RabbitMQ：为微秒级超低延迟与复杂通配符路由而生，中小型微服务开箱即用。

00.4 本笔记知识地图

整份笔记按照「全景定位 → 核心积木与跑通代码 → 七大真实业务场景 → 可靠保序与上线规范」层层推进，涉及底层内核原理时再按需从各节末尾跳入《 核心原理篇》：

本章即时场景题（先想答案，再点击展开）

1. 用户在下单页点击「立即支付」，订单服务需要校验优惠券是否有效并锁定库存，这一步该放进 MQ 异步做吗？

不该。校验优惠券有效性和锁定商品库存直接决定「这笔订单能不能成功生成、应付多少钱」，用户正在前端等待确切结果，必须走同步调用或本地事务当场完成；只有下单成功后的「发短信通知、增加会员成长值、推送数仓」这类允许晚几秒完成的支线逻辑，才适合放进 MQ 异步解耦。

2. 一个内部审批系统每天只产生约 3,000 条站内信通知，团队目前只用了 MySQL 和 Redis，值得专门部署一套 Kafka 集群吗？

不值得。日均几千条消息没有高并发吞吐和海量磁盘堆积诉求，额外部署和监控一套 Kafka 集群运维成本过高。如果仅需异步重试，直接复用现有的 Redis Stream（支持消费组与 XACK 确认）甚至数据库任务表配轻量轮询就已经完全够用。

3. 同事说：“把下游调用全改成发 MQ 就高枕无忧了，系统复杂度反而更低。”这句话忽略了哪些工程代价？

忽略了引入 MQ 的三大固有代价：① 基础设施单点风险（MQ 挂了整条异步链路中断）；② 消息传递不确定性（网络重试会带来重复消息、多分区并发会打乱顺序、下游变慢会造成积压）；③ 最终一致性兜底成本（必须额外设计写库与发消息的一致性方案以及消费端幂等逻辑）。
