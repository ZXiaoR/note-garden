🎬 08.1 · 全篇串联：跟着一笔订单消息走完从生产入队到过期清理的 7 步一生

🎬 08.1 全链路大串联：一条订单消息的 7 步完整一生

Step 1 · 本地事务与生产路由（03.5 / 05.1）：订单服务通过本地消息表确保订单与待发事件原子落库，Producer 指定业务键 Key = "ORD_1001" 哈希锁定目标分区 Partition-2（保同单有序），以 acks=all 发送。
Step 2 · Broker 幂等判重与顺序写页缓存（原理篇 01 / 03.1）：Partition-2 的 Leader 副本校验序列号无重复后，将消息批次顺序追加写入当前活跃日志段对应的操作系统 PageCache，并更新稀疏偏移量索引。
Step 3 · 多副本同步与高水位推进（04.1 / 原理篇 04）：ISR 同步副本集合中的 Follower 拉取该消息落入各自内存；满足 min.insync.replicas >= 2 后 Leader 推进高水位 HW 并向 Producer 返回确认成功，消息正式对消费者可见。
Step 4 · 长轮询拉取与零拷贝传输（03.1 / 原理篇 00 / 03.1）：发券组与短信组各自负责 Partition-2 的消费者实例通过长轮询拉取；Broker 调用 sendfile 零拷贝将页缓存字节流直推网卡。
Step 5 · 消费端幂等校验与业务执行（04.2 / 05.1）：消费者拿到消息后，先凭 eventId 或 orderNo 经数据库唯一索引 / 状态机条件更新完成幂等防重，再串行执行发券或改状态逻辑。
Step 6 · 手动提交 Offset 与异常死信兜底（03.7 / 04.1）：业务落库成功后手动提交 Offset 到内部 __consumer_offsets；若连续退避重试超限仍报错，则转入 .dlq 死信队列触发告警并放行后续消息。
Step 7 · 历史回溯与分段过期回收（05.2 / 原理篇 03.2）：保留期内（默认 7 天）随时支持按时间重置 Offset 回溯重跑；到期后按整段旧 Segment 文件 O(1) 物理删除回收磁盘。

01. 客服反馈有用户只付了一笔订单，账户里却收到了两张一样的满减优惠券，怎么排查和修复？

排查两步走：
① 先去 Kafka UI 或日志按 orderNo 搜消息：看上游订单服务是不是因为没做本地防重发了两条不同 eventId 的支付消息，还是只有 1 条消息被消费了两次（如发券服务刚发版重启、消费慢触发 Rebalance 或提交 Offset 超时重投）。
② 根因必在发券消费端缺少业务幂等：只要是 At-least-once 投递，重投随时会发生。
根治修复：在用户领券表增加联合唯一索引 UNIQUE KEY uk_order_coupon (order_no, coupon_tpl_id)，捕获唯一键冲突错误（MySQL 1062）直接视为成功并提交 Offset（回顾 04.2）。

02. 订单列表同步到查询库时，偶尔出现订单明明已支付，状态却被改回「待支付」，为什么？怎么解决？

原因：同一笔订单的「已创建（待支付）」与「已支付」两条变更消息发生了乱序消费——要么生产端没把 orderNo 设为消息 Key 打散到了不同分区，要么消费端拉出消息后丢进了无序并发协程池。
双重解决：① 传输层：生产端固定设置 Key = orderNo 路由进同一分区，消费端单分区串行（或按 orderNo 哈希固定通道）处理；② 存储层兜底：更新 SQL 带上状态机或递增版本号条件（如 WHERE order_no=? AND version < ?），即使极端重放乱序也绝不会发生状态倒退（回顾 03.4 / 05.1）。

03. 早上到公司发现监控告警：核心消费组 Lag 涨到了 200 万条，按什么顺序处理？

1. 敲命令诊断现场：执行 kafka-consumer-groups.sh --describe --group xxx。
2. 先分清死活与倾斜：若 CONSUMER-ID 为空说明全挂了，看报错拉起；若一直在 PreparingRebalance 说明单批超时被踢，调小单批条数并降级慢外部调用；若只有 1 个分区积压说明热点 Key 倾斜。
3. 扩容清零：若当前消费者数小于分区数（如 24 分区只开了 4 台），直接扩满到 24 台并改批量写库；若原本只有 4 个分区且已跑满 4 台、要求半小时追平，则新建 40 分区临时 Topic，把原 4 台改为纯内存转发搬运工，同时起 40 台新消费者并发消化，期间留意调大日志保留时间防过期误删（回顾 05.2）。

04. 用户钱扣成功了、MySQL 订单表也是「已支付」，但下游仓库一直没收到发货消息，怎么回事？

典型根因：上游写了朴素的「先提交本地数据库事务，再调 writer.WriteMessages 发 Kafka」，结果在事务刚提交完那一刻遇上网络闪断、Broker 切主或容器重启，且代码没处理发送报错，导致写库成功但消息漏发。
应急补救：查出订单表状态为 PAID 但超过 5 分钟未生成发货单的记录，通过管理接口补发一次事件（下游有幂等可安全重发）。
彻底根治：改为本地消息表（Transactional Outbox）（同库事务写订单 + 写 outbox_messages，后台协程轮询投递直至确认成功），或切换 RocketMQ 事务消息（回顾 03.5）。

05. 某异步导出报表消费组每隔 5 分钟就触发一次 Rebalance，同一份大报表被反复生成好几遍，怎么修？

原因：单份百万行报表生成耗时超过了 max.poll.interval.ms（默认 5 分钟），消费者迟迟没去发起下一次拉取，被 Coordinator 误判卡死踢出组；未提交 Offset 的任务随即被分给另一台机器从头重做，形成死循环。
修复方案：① 将单次拉取条数设为 1，并根据最大导出耗时将超时阈值调大（如 20 分钟）；② 优化导出 SQL 分页流式写入对象存储；③ 落库状态前先检查任务表是否已完成保障幂等（回顾 03.2 / 07.3）。

06. 整点秒杀瞬时涌入 20,000 QPS 抢 500 件商品，数据库最高只能扛 1,000 TPS，全链路怎么设计？

① 入口拦截与预扣：网关限流防刷后，在 Redis 里用 Lua 脚本原子校验用户限购并扣减 500 件预热库存（97.5% 没抢到的请求在内存层小于 1ms 直接拦截返回“已售罄”，根本不进 MQ 和数据库）；
② 入队削峰：真正抢到名额的 500 个请求写入 Kafka seckill.order.requests 后立即向前端返回 reqId（前端显示“排队生成订单中”并轮询结果）；
③ 消费端匀速落库：消费者使用 rate.Limiter 控制在 500 TPS 安全水位平缓创建 MySQL 订单并手动提交 Offset（回顾 03.2）。

07. 团队基础设施只有 Kafka 和 Redis，现在要做「订单 30 分钟未支付自动取消」，怎么落地最稳？

因为 Kafka 没有原生任意延迟消息，最稳妥省心的组合是 Redis ZSet + Kafka + 低频扫库兜底：
① 下单成功时执行 ZADD delay:unpaid <下单时间戳+1800> <orderNo>（用户中途支付成功可顺手 ZREM）；
② 后台调度协程每秒用 Lua 脚本原子执行 ZRANGEBYSCORE + ZREM 弹出已到期单号，投递进 Kafka trade.order.cancel Topic；
③ 关单消费组并发执行 UPDATE orders SET status='CANCELED' WHERE order_no=? AND status='UNPAID'，影响行数为 1 时释放库存；
④ 配一个每 10 分钟跑一次的低频数据库扫描任务，兜底进程在弹出 ZSet 后、发进 Kafka 前极端断电漏掉的订单（回顾 03.6）。

08. 消费端遇到一条上游传错格式的脏消息一直反序列化报错，导致整个分区的后续消息全卡住了怎么办？

这就是典型的「毒丸消息（Poison Pill）」。
① 区分错误类型：像 JSON 语法损坏、必填字段缺失这类确定性永久错误，重试 100 次也绝不可能成功，根本无需退避重试，应捕获后直接携带原消息与报错堆栈写入死信队列 Topic（.dlq）；对网络超时类瞬态错误，最多经 .retry Topic 退避重试 3 次后仍失败同样转入 .dlq。
② 确认成功写入 .dlq 后，立即手动提交原分区 Offset 放行后面堆积的正常业务消息，并由 .dlq 监控告警通知研发人工修复重放（回顾 03.7）。

09. 发消息时如果忘了把 kafka-go 的 RequiredAcks 显式设为 RequireAll，而消费端用了 ReadMessage，有哪两处丢消息隐患？

① 生产端隐患：未显式指定 kafka.RequireAll 时，消息未等同步副本确认即返回，Leader 单机断电会丢掉尚未被 Follower 拉走的页缓存数据；
② 消费端隐患：kafka-go 的 ReadMessage 会在把消息交给业务代码之前就标记自动提交 Offset——一旦紧接着写数据库报错或容器重启，这条消息不会再被重投，直接丢失。应统一改用 FetchMessage + 落库成功后调 CommitMessages（回顾 03.1 / 04.1）。

10. 需要给正在运行的 trade.order.paid 消息新增优惠明细并附上 4 MB 的电子合同文件，已有 3 个部门在消费，怎么安全上线？

① 大文件剥离：4 MB 电子合同绝不塞进 Kafka 消息体（会超默认 1 MiB 限制且拖垮页缓存），先传 OSS/S3 对象存储，消息里只放 contractFileKey 字符串；
② 字段向后兼容：保留所有原有字段名和类型不动，仅在 JSON 顶层或 data 内新增可选字段（discountItems、contractFileKey）；老的 2 个不需要合同的部门一行代码不用改、无需同步发版，需要合同的部门平滑升级读取新字段即可（回顾 07.2）。

⚡ 08.3 消息队列 15 题一句话速记表

核心问题 一句话标准答案（含对应章节跳转）
1. 为什么要用 MQ？ 解耦（上游发事件不绑定下游代码）、异步（剥离非核心支线降低接口耗时）、削峰填谷（队列蓄水把瞬时洪峰变匀速流保护数据库）（00.1）。
2. 引入 MQ 有什么代价？ 可用性依赖增加（多一层故障点）、工程复杂度上升（需处理丢/重/乱序/积压）、跨系统最终一致性挑战（00.3）。
3. 消费者组如何兼顾两种模型？ 组内竞争分摊（1 个分区同一时刻只分给组内 1 台消费者，有效消费者数 <= 分区数）；组间独立广播（不同 GroupID 各自消费一份全量）（01.2）。
4. 三大 MQ 与 Redis Stream 怎么选？ 百万吞吐日志/流管道选 Kafka；核心交易/原生事务定时选 RocketMQ；微秒低延迟/复杂路由选 RabbitMQ；日百万级以内轻量项目用 Redis Stream 就够（06.3）。
5. 如何保证消息不丢？ 生产端 acks=all + 重试捕获；Broker 端 replication.factor=3 + min.insync.replicas=2 + 禁脏选主；消费端关自动提交，业务落库后再手动提交 Offset（04.1）。
6. 如何解决重复消费？ 遵循 At-least-once + 消费端业务幂等：按业务唯一单号用数据库唯一索引 / 状态机条件更新 / Redis PROCESSING+DONE 状态机兜底（04.2）。
7. 如何保证消息顺序性？ 放弃单分区全局有序，用局部有序：生产端把 orderNo 作 Key 哈希进同一分区 + 防重试超车 + 消费端单分区串行或按 Key 固定通道处理（05.1）。
8. 线上百万/千万级积压怎么处理？ 先敲 --describe 排除消费全挂或慢超时重平衡；消费者数未满直接扩满实例；老分区不够则将原消费者改为纯内存转发器，打入 10 倍分区的临时 Topic 起 10 倍机器泄洪（05.2）。
9. 为什么选 Pull + 长轮询？ Push 易压垮慢消费者；Pull 让消费端自主控速，配合长轮询（无消息时 Broker 挂起请求，来新消息立即唤醒返回）兼顾控速与毫秒级实时性（原理篇 00）。
10. 写库与发消息怎么保证一致？ Kafka 用本地消息表（同库单事务写业务表与 outbox 表 + 后台轮询投递）；RocketMQ 用半消息暂存 + 本地事务 + Broker 定时状态反查（03.5 / 原理篇 02.1）。
11. 延迟关单怎么实现？ Kafka 无原生任意延迟，常用 Redis ZSet 到期弹出 + Kafka；RocketMQ 5.0 用分层时间轮原生支持任意定时；RabbitMQ 用延迟插件或同档位 TTL+DLX（避开队头阻塞）（03.6 / 原理篇 02.2）。
12. Kafka 凭什么单机百万吞吐？ 磁盘顺序追加写 + 操作系统 PageCache（避开 JVM GC）+ sendfile 零拷贝（0 次 CPU 拷贝）+ 端到端批量压缩 + 多分区水平并行（原理篇 03.1）。
13. Kafka 与 RocketMQ 存储差在哪？ Kafka 每个分区独立 Segment (.log + .index 稀疏索引)，少量大流极快；RocketMQ 全机共写 1 个 CommitLog + 20B 定长 ConsumeQueue，几千个 Topic 不退化为随机写（原理篇 03.2）。
14. ISR、HW、LEO 与 Leader Epoch？ ISR 是同步副本集（按 30s 时间判定）；LEO 是下一待写偏移量；HW 是 ISR 最小 LEO（消费者可见边界）；Leader Epoch 修复 Follower 重启按滞后 HW 盲目截断丢数据漏洞（原理篇 04）。
15. 怎么避免频繁 Rebalance 停顿？ 调小单批拉取条数防止超 max.poll.interval.ms（5 分钟）被踢，配置 group.instance.id 静态成员与 CooperativeStickyAssignor 增量协作重平衡（07.3 / 原理篇 05）。
