07.1 · 容量与路由规划：Topic 命名规范、初始分区数估算与消息 Key 选择准则

07.1 Topic 命名、分区数与消息 Key 规范

规划维度 推荐工程标准 常见反例与潜在问题
① Topic 命名 采用全小写三段式：<业务域>.<资源实体>.<事件/类型>（如 trade.order.paid、telemetry.app.click）；生产集群建议关闭 auto.create.topics.enable=false，统一走审批/脚本创建。 取名 test1、msg_queue 语义不明；开启自动建 Topic 后，代码拼错一个字母就会静默建出无人消费的幽灵 Topic。
② 分区数怎么定 按公式估算：max(峰值生产吞吐 ÷ 单分区写能力, 峰值消费吞吐 ÷ 单消费者处理能力)，并取预期消费者实例数的整数倍。
• 普通业务事件：初始 6 或 12 个分区足够；
• 高并发日志流：初始 12～32 个分区。		 两个极端都要避开：① 只建 1 个分区导致未来无法水平加消费者扩容；② 一上来无脑建 500 个分区——注意分区数只能增不能减，单机分区成千上万会让磁盘顺序写退化为随机 I/O，还会拖慢故障选主与重平衡。
③ 消息 Key 怎么选 • 需要局部保序：用高基数业务唯一标识（order_no、user_id、sku_id）；
• 无需保序（纯吞吐）：Key 留空走轮询均衡。		 用低基数枚举值当 Key（如按 platform="iOS" 或 status="PAID" 做 Key），会导致 80% 流量全砸进某一个分区造成严重热点积压。
07.2 · 消息契约设计：大小上限、JSON vs Protobuf 选型与不停机向后兼容

07.2 消息体大小、序列化格式与字段兼容

  • 消息体大小控制（拒绝大消息）：Kafka 默认单批最大限制约 1 MiB（max.message.bytes），生产推荐单条消息保持在 1 KB ~ 64 KB 以内。如果需要传递 5 MB 的电子发票 PDF、导出报表或高分辨率图片，严禁把文件 Base64 塞进消息体（会打爆 Broker 页缓存与网卡），标准做法是先把文件传到对象存储（OSS / S3），消息里只传文件的路径 URL 与哈希摘要。
  • 序列化格式选型（JSON vs Protobuf）：
    • JSON：文本可读性好，在 Kafka UI 网页和命令行里一眼就能看清字段值，排障效率高；开启 LZ4 批量压缩后体积也很紧凑，90% 常规业务事件首选。
    • Protobuf（Protocol Buffers，协议缓冲区）：Google 跨语言二进制编码，带严格 .proto 契约校验，序列化耗时与体积均比未压缩 JSON 小一半以上，适合每秒数十万条的埋点、风控特征流与大型跨语言微服务。
  • 字段兼容与版本号（防上线炸下游）：在多消费组架构中，生产者与下游三四个团队不可能在同一秒发版，消息结构必须自带信封元数据并遵守平滑演进三原则：
order_event_envelope.json · 推荐的生产级消息信封结构与向后兼容三原则 
{
  "eventId": "evt_01J8Z9K3M4P5Q6R7",   // 必带：全局唯一事件 ID，供所有下游做消费幂等
  "eventType": "ORDER_PAID",            // 必带：事件语义类型
  "schemaVersion": 2,                   // 必带：契约版本号（破坏性变更时递增）
  "occurredAt": 1795838400000,          // 必带：业务发生毫秒时间戳，方便监控端到端延迟与防旧覆盖
  "data": {
    "orderNo": "ORD_20261128_01",
    "amountCent": 19900,                // 原则 ①：绝不原地改旧字段类型（如把整数分改成字符串元）
    "discountCent": 2000                // 原则 ②：只追加可选新字段；旧消费者默认忽略未知字段，新消费者对缺失字段给零值
                                        // 原则 ③：废弃旧字段前，必须确认所有下游消费组均已发版不再读取该字段
  }
}
07.3 · 防踢出消费组：区分心跳超时与 max.poll.interval.ms 消费处理超时

07.3 消费超时与被踢出消费组（max.poll.interval.ms）

线上最隐蔽的一类故障是：消费者进程明明活得好好的、CPU 和内存都很正常，却每隔几分钟就被踢出消费组触发 Rebalance（分区重平衡），交出分区后未提交的消息又被别的实例拉去重跑一遍，陷入「越重跑越慢、越慢越被踢」的死循环。根源在于没分清 Kafka 的两个超时时钟：

超时参数 / 调优项 典型默认值 监控什么 & 生产怎么配才不会被误踢
① 消费处理最大间隔
max.poll.interval.ms
配合 max.poll.records		 间隔 5 分钟
单批 500 条		 最常见的被踢元凶！它衡量「两次拉取请求之间的最大业务处理耗时」。假如一次拉了 500 条，下游外部接口变慢每条花 0.7 秒，共跑了 350 秒（超 5 分钟），Broker 就判定消费协程卡死直接踢人！
调优：调小单批条数（50~100）、给下游 HTTP/SQL 设严格超时（如 3s），长耗时导出任务将间隔调大至 15~30 分钟。
② 进程存活心跳超时
session.timeout.ms
heartbeat.interval.ms		 会话 45s
心跳 3s		 由客户端后台独立心跳线程定时发送，专门检测机器宕机或网络中断。保持 heartbeat <= 1/3 * session.timeout 即可，切勿把 session.timeout.ms 改得过小（如 6s），否则轻微网络抖动就会误踢。
③ 静态成员资格
group.instance.id		 默认未开启 K8s 容器滚动发版重启时，若给每个 Pod 配置固定的 group.instance.id，只要新容器在 session.timeout.ms 内启动连回，Broker 直接把原分区还给它，发版全程零无谓重平衡。
④ 增量协作重平衡策略
CooperativeStickyAssignor		 旧版默认 Eager 全量回收 使用支持协作重平衡的客户端策略时，扩缩容只迁移变动的那一两个分区，其余未变动分区不中断消费。

背后的原理：GroupCoordinator 与客户端班长（Consumer Leader）是怎么通过两阶段握手完成分区重新分配的？为什么传统重平衡会导致全组消费停顿（STW）？详见 《 核心原理篇 · 05 Rebalance 原理》。

07.4 · 上线核对与可观测性：防御三件套自查与 5 项必配监控告警

07.4 防御三件套核查与核心监控告警

代码合入前必查「消费防御三件套」
  1. 手动提交 + 有限退避重试是否配好？（关闭自动提交，下游瞬时报错走退避重试，不在原地无休眠死循环）。
  2. 死信队列（DLQ）是否兜底？（超过最大重试次数的毒丸消息自动转入 .dlq 放行主分区，不让 1 条坏数据堵死全站）。
  3. 消费端业务幂等是否实现？（唯一索引、条件状态更新或 Redis 三态锁至少落地一种，重跑历史数据不翻车）。
生产必配的 5 项监控告警指标
  1. Consumer Lag（消费积压量与持续时长）：不仅看绝对条数，更要看「连续 5 分钟只涨不降」告警。
  2. Producer Error Rate（生产发送失败率）：大于 0 立即告警，排查网络、磁盘满或 min.isr 不足。
  3. Consume Latency P99（单条消费耗时）：识别下游慢 SQL/慢接口，提前防超时踢出组。
  4. Rebalance Rate（消费组重平衡次数）：非发版期间重平衡次数突增，说明存在慢消费被踢或容器反复重启。
  5. DLQ Message Count（死信队列新增条数）：只要 > 0 立即发即时通讯告警，当天人工介入排查修复。

本章即时场景题（先想答案，再点击展开）

1. 上游订单团队想把 amount 字段从整数分（19900）直接改成带小数点的字符串元（"199.00"）直接发版上线，会发生什么？正确的改法是什么？

直接发版会导致下游 Go / Java 静态类型消费者全部反序列化报错（如 json: cannot unmarshal string into Go struct field .amount of type int64），新产生的订单事件全数掉进死信队列或卡住分区。
正确改法：保留原 amount（或 amountCent）整数不变，新增一个可选字段 amountYuanStr: "199.00"；等所有下游消费组都平滑升级读取新字段后，再在下个大版本清理旧字段。

2. 业务需要异步生成 8 MB 的年度账单 PDF 发邮件给用户，生产端直接把 8 MB PDF 字节流塞进 Kafka Value 发送，结果直接报错拒收，该怎么重构？

触发了 Kafka 单批最大消息限制（默认 1 MiB，报 MessageSizeTooLargeException）。不要去盲目把 Broker 上限改成 20 MB，正确做法是：生成账单后先把 PDF 上传到对象存储（OSS / S3 / MinIO），往 Kafka 里只发一条几百字节的 JSON（含 userId 与 pdfObjectKey），邮件消费者收到后拉取文件流或拼出签名下载链接发信。

3. 监控报警某消费组非发版时段每小时触发十几次 Rebalance，看服务器内存和网络都很平稳，第一步该怀疑什么？

第一步看消费单批耗时是否超过了 max.poll.interval.ms（默认 5 分钟）。比如代码里调了一个没设超时时间的第三方 HTTP 接口，偶发卡住几分钟导致未能按时发起下一轮拉取，被 Coordinator 判定假死踢出消费组。
