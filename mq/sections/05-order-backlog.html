📏 05.1 · 局部顺序保证：为什么会乱序，以及用同一订单号作 Key 的保序代码

📏 05.1 同一订单号作 Key 保证局部有序

同一笔订单依次产生 创建 → 支付 → 发货 三条事件，或数据库同步依次产生 INSERT → UPDATE → DELETE，一旦下游先执行了后一条就会把状态冲乱。先看清哪 3 个环节会把顺序打乱，再逐一锁住：

乱序点 ①：无 Key 轮询进不同分区
创建 进了 P0、支付 进了 P1，两个消费者各自拉取，快慢不一必然乱序。
✅ 解法：指定 Key = orderNo 哈希进同一分区。
乱序点 ②：异步管道重试超车
第 1 条网络超时准备重发时，同一连接上的第 2 条先写成功了。
✅ 解法：同步按序发送，或开启幂等生产者（in.flight <= 5）。
乱序点 ③：消费端丢进无序协程池
从同一分区按序拉出两条消息，却起两个无序 goroutine 并发跑。
✅ 解法：单分区单协程串行，或按 orderNo 哈希到固定内存单队列。

为什么不做「全局有序」？想让整个 Topic 所有订单严格全局有序，只能把 Topic 设为 1 个分区 + 1 台消费者，吞吐直接退化回单机。而实际业务里订单 A 和订单 B 谁先处理互不影响，只需同一笔 orderNo 内部有序——这就是兼顾多分区高并发与业务正确性的局部有序（Partition Order）：

🐹 order_sequence.go · 生产端指定 orderNo 作 Key + 消费端单分区严格按序执行 [Go · kafka-go v0.4.47] 
// 1. 生产端：Balancer 必须使用 &kafka.Hash{}（对 Key 计算哈希取模，保证相同 orderNo 100% 落入同一分区）
func NewOrderSequenceWriter(brokers []string) *kafka.Writer {
    return &kafka.Writer{
        Addr:         kafka.TCP(brokers...),
        Topic:        "trade.order.lifecycle",
        Balancer:     &kafka.Hash{},    // 关键！相同 Key 固定路由至同一 Partition
        RequiredAcks: kafka.RequireAll,
        Async:        false,            // 同步顺序发送，前一条确认成功后再发下一条，杜绝重试超车
    }
}

func SendOrderStep(ctx context.Context, w *kafka.Writer, orderNo, step string) error {
    body := []byte(fmt.Sprintf(`{"orderNo":%q,"step":%q}`, orderNo, step))
    return w.WriteMessages(ctx, kafka.Message{
        Key:   []byte(orderNo), // 同一笔订单的 CREATED / PAID / SHIPPED 全部传同一个 orderNo
        Value: body,
    })
}

// 2. 消费端：单 Reader 串行处理分配给自己的分区，不启动无序 goroutine，处理完前一条再拉下一条
func ConsumeOrderInSequence(ctx context.Context, brokers []string, applyStep func(context.Context, []byte) error) {
    r := kafka.NewReader(kafka.ReaderConfig{
        Brokers: brokers,
        Topic:   "trade.order.lifecycle",
        GroupID: "order-state-sync-grp",
    })
    defer r.Close()

    for {
        msg, err := r.FetchMessage(ctx)
        if err != nil {
            return
        }
        // 同步串行处理（若单协程不够快，可开 8 个固定 chan，按 hash(orderNo)%8 分发保证同单仍在同一 chan，但须待批次内全部完成后再统一提交最大连续 Offset）
        for attempt := 1; attempt <= 5; attempt++ {
            if err = applyStep(ctx, msg.Value); err == nil {
                break
            }
            time.Sleep(time.Duration(attempt) * 200 * time.Millisecond)
        }
        if err != nil {
            // ⚠️ 顺序消费队头阻塞兜底：5 次仍失败则将该 orderNo 记入数据库异常冻结表拦截同单后续事件并告警，防止卡死整个分区
            recordFrozenOrder(ctx, string(msg.Key), msg.Value, err)
        }
        _ = r.CommitMessages(ctx, msg)
    }
}

🚒 05.2 积压排查：看 Lag、定病根、扩容恢复

消费积压量 Lag = 分区最新写入位置（LOG-END-OFFSET） − 消费组已提交位置（CURRENT-OFFSET）。收到积压告警时别急着盲目重启，先敲下面第 ① 条命令看现场，对照诊断表 3 分钟定位根因：

🔎 mq_ops_troubleshooting.sh · 查看 Lag、扩分区与按时间点重置 Offset 排障命令 [Kafka 3.x / 4.0] 
# ① 第一时间执行：查看消费组每个分区的 CURRENT-OFFSET、LOG-END-OFFSET、LAG 与当前挂载的 CONSUMER-ID
/opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server broker1:9092 \
  --describe --group order-state-sync-grp

# 典型输出解读：
# GROUP                 TOPIC            PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG     CONSUMER-ID
# order-state-sync-grp  trade.order.paid 0          120500          120502          2       consumer-1-8a9f...
# order-state-sync-grp  trade.order.paid 1          118000          698000          580000  consumer-2-3b1c...

# ② 列出消费组当前状态（Stable=正常消费中 | PreparingRebalance=正在重平衡卡顿 | Empty=消费者全挂了！）
/opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server broker1:9092 \

  --alter --topic trade.order.paid --partitions 24

# ④ 故障修复后按时间回溯重放（需先停掉该组消费者；先用 --dry-run 预览目标 Offset，核对无误再换 --execute）
/opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server broker1:9092 \
  --group order-state-sync-grp --topic trade.order.paid \
  --reset-offsets --to-datetime 2026-11-28T14:00:00.000 --dry-run

🩺 第二步：怎么一眼分清是「消费挂了」还是「消费太慢」？

--describe 看到的现象 真实根因判断 立刻执行的恢复动作
现象 A：CONSUMER-ID 全是 -，状态为 Empty，且 CURRENT-OFFSET 一动不动 消费者进程全挂了（发版启动失败、配置连错集群或容器反复 CrashLoop）。 看容器启动日志与崩溃堆栈，修复后拉起消费者实例即可开始追赶。
现象 B：状态一直在 PreparingRebalance 来回跳，Offset 极慢推进且日志重复 单批处理超时被反复踢出消费组（超过 max.poll.interval.ms 陷入重平衡死循环）。 调小单次拉取条数、给慢 HTTP/SQL 加超时或临时降级非核心调用（详见 07.3）。
现象 C：5 个分区 LAG=0，唯独 Partition 1 单边暴涨几十万 消息 Key 数据倾斜（热 Key）（如所有游客订单的 Key 都传了空串 "guest" 挤进同一分区），或负责 P1 的那台机器网卡/CPU 异常。 排查该台消费者宿主机监控；若是 Key 倾斜，给无单号数据拼上随机后缀打散。
现象 D：所有分区 LAG 均匀上涨，CURRENT-OFFSET 在走但追不上写入 纯粹的消费速率 < 生产速率（大促流量翻倍，或下游 MySQL 缺索引变慢）。 先排查下游慢 SQL 并将单条插入改为批量写库（Batch Insert），再按下述扩容方案加并发。

🚀 第三步：怎么扩容把积压快速清零？

根据第 01 章学过的「同一消费组有效消费者数 ≤ 分区数」，分两种情况处理：

  • 常规积压（当前消费者实例数 < 分区数，如 24 个分区只跑了 4 台消费者）：直接把消费者容器扩容到 24 台（1 台吃 1 个分区），吞吐立刻翻 6 倍。
  • 极端积压（原来只有 4 个分区 + 4 台消费者，老分区里已经积压了 3,000 万条，要求半小时内追平）：此时光加消费者没用（第 5 台分不到分区），光给原 Topic 扩分区也没法把已经写进老 4 个分区的旧积压数据挪走。标准应急方案是「新建 10 倍分区的临时 Topic 中转泄洪」：

☑️ 本章即时场景题（先想答案，再点击展开）

1. 生产端已经用 orderNo 作 Key 写进了同一个分区，为什么线上偶尔还是出现同一笔订单「先收到发货、后收到支付」？

重点查两处：① 消费端代码内部开了无序并发协程池（最常见，从分区顺序拉出两条消息后同时起了两个 go func()，发货协程跑得更快先落库了）；② 生产端开启了异步无幂等并发重发（前一条支付消息遇到网络超时在后台等重试时，后一条发货消息先写入了分区）。

2. 执行 kafka-consumer-groups.sh --describe 时看到 8 个分区里有 7 个 LAG = 0，只有 Partition 3 的 LAG = 450,000，为什么加消费者实例完全解决不了？

因为 1 个分区最多只能被组内 1 台消费者消费，哪怕加到 100 台机器，Partition 3 依然只有 1 台机器在跑。这是典型的热点 Key 倾斜（大量消息带了相同的默认 Key 如空字符串或同一个大商户 ID 全部哈希到了 P3），应当打散热点 Key 或在消费 P3 的实例内做批量写库加速。

3. 周末某非核心消费组挂了两天没人发现，Broker 配的保留时间 retention.hours=24，周一修好启动后那两天的部分老消息已经被磁盘过期清理掉了，怎么补救？

已经被清理的日志段无法在 Kafka 里找回。等业务低峰期，根据丢失的时间段去上游源头数据库（如查询周六至周日创建但下游积分表缺失记录的订单），跑一个一次性补偿脚本把漏掉的事件重新投递进 Topic 即可（因为消费端有幂等，不怕时间范围稍微重叠）。
