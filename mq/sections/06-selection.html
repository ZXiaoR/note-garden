🏗️ 06.1 · 架构基因拆解：为什么市面上同时存在 Kafka、RocketMQ 与 RabbitMQ

🏗️ 06.1 三大主流 MQ 的架构定位与取舍

没有一款消息队列能在所有指标上同时拿第一，因为「百万级高吞吐」「丰富的交易级内置特性（事务/定时/万级 Topic）」「微秒级低延迟与复杂路由」在底层存储和网络模型上天然存在取舍：

① Apache Kafka —— 百万级吞吐与大数据流管道标准 Scala/Java · 单机百万 TPS · KRaft 去 ZK
• 设计重心：把消息彻底抽象为分布式追加日志（Append-Only Log）。依靠分区顺序写、操作系统页缓存、sendfile 零拷贝与批量压缩，单机吞吐可达百万级/秒，磁盘堆积 TB 级历史数据毫不费力。
• 元数据架构：Kafka 3.3+ 生产就绪、4.0 彻底移除外部 ZooKeeper，改用内置 Raft 共识协议的 KRaft 控制平面管理分区元数据（详见 原理篇 06.2）。
② Apache RocketMQ —— 核心电商交易与金融业务全能型 Java · 十万级 TPS · 原生事务 / 定时 / 重试
• 设计重心：针对电商交易补齐了 Kafka 不擅长的两块短板——一是原生内置分布式事务消息、任意时刻定时消息、Tag 二级过滤与 16 级重试死信队列；二是存储上让整台 Broker 所有 Topic 共写唯一一个 CommitLog 文件（配轻量 ConsumeQueue 索引，详见 原理篇 03.2），即使业务建了几千个 Topic 也不会退化为磁盘随机写。
• 路由协调：使用极简无状态的 NameServer 集群（节点间互不通信，Broker 定时向所有 NameServer 上报心跳）替代重型注册中心。
③ RabbitMQ —— 微秒级低延迟与灵活交换机路由 Erlang · 万级 TPS · µs 级延迟 · AMQP
• 设计重心：基于 AMQP（Advanced Message Queuing Protocol，高级消息队列协议） 与 Erlang 语言实现。它的核心不是分区大日志，而是在 Broker 内部前置了一层灵活的 Exchange（交换机）——生产者只把带路由键（Routing Key）的消息发给交换机，交换机按绑定规则实时分发到不同队列（Queue）。
🔀 06.2 · RabbitMQ 核心机制：4 种 Exchange 交换机路由规则与 Quorum 仲裁队列

🔀 06.2 RabbitMQ 交换机路由与高可用队列

在 RabbitMQ 里没有 Kafka 的「消费者组」概念——它靠「1 个 Exchange 绑定多个独立 Queue」实现多业务广播，靠「多个消费者监听同一个 Queue」实现竞争分摊。4 种内置交换机的匹配规则如下：

Exchange 类型 路由匹配规则 典型业务场景
Direct（直连） Routing Key == Binding Key 完全相等时，投递到对应队列。 按明确标识精准分流（如把 error 日志发告警队列，info 发归档队列）。
Fanout（扇出广播） 忽略 Routing Key，绑定在该交换机上的所有队列无条件各复制一份（最快）。 纯粹的一对多事件广播（如注册成功同时推给发券队列、欢迎邮件队列）。
Topic（通配符，最常用） 以点号 . 分词（如 order.pay.shanghai）：
• * 匹配恰好 1 个词；
• # 匹配 0 个或多个词。		 多维按需订阅：绑定 order.# 收全部订单事件；绑定 *.pay.* 只收各城市支付事件。
Headers（头部属性） 不看 Routing Key，匹配消息 Headers 键值对（x-match: all / any）。 开销较大极少使用，基本都可被 Topic 交换机替代。

🛡️ RabbitMQ 集群高可用标准：旧版「经典镜像队列（Classic Mirrored Queue）」已在 RabbitMQ 4.0 移除；生产环境一律声明基于 Raft 一致性协议的 Quorum Queue（仲裁队列），过半节点落盘即确认，兼顾防丢与防脑裂。

🎯 一句话选型拍板结论：
• 海量日志、用户埋点、CDC 数据管道、流计算生态 👉 选 Kafka（如果普通业务后端团队不想维护多套 MQ，用「Kafka + 本地消息表 + Redis ZSet 延迟」这套黄金组合也能稳稳覆盖绝大多数交易需求）。
• 大型电商、金融支付核心交易中台（Topic 上千且重度依赖原生事务消息与定时关单） 👉 选 RocketMQ。
• 企业内部微服务需要复杂通配符路由或微秒级实时指令下发 👉 选 RabbitMQ。
• 中小型项目日消息量在百万条以内、没有大规模积压诉求、不想多招运维盯一套 MQ 集群 👉 根本不用引入新组件，直接用现有的 Redis Stream 就够了！

☑️ 本章即时场景题（先想答案，再点击展开）

1. 公司准备搭建全站统一的用户点击埋点与容器日志收集总线，峰值约 40 万条/秒，下游要同时喂给 Flink 实时大屏与 ClickHouse，选哪款最合适？

选 Apache Kafka。40 万条/秒属于典型的大吞吐流式管道场景，无需复杂路由和单条事务反查，Kafka 的批量压缩、sendfile 零拷贝、TB 级磁盘堆积能力以及与 Flink / ClickHouse 的原生连接器支持都是行业事实标准。

2. 一个创业团队的 SaaS 后台已有 MySQL 和 Redis 7，现在想把「用户修改头像后异步生成缩略图（每天约 2 万次）」做成队列任务，该上 Kafka、RabbitMQ 还是 Redis Stream？

直接用 Redis Stream。日均 2 万次平均每秒不到 1 条，XADD + XREADGROUP + XACK + XAUTOCLAIM 已经完整具备多 Worker 分摊和崩溃重试能力，零新增基础设施运维负担；等将来日消息涨到千万级或需要数天历史消息回放时再平滑升级到 Kafka 也不迟。
