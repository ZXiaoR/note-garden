06 存储与零拷贝原理 · Kafka 为什么能扛百万 TPS？顺序写、零拷贝与 RocketMQ 存储对比 PAGE CACHE · ZERO-COPY · COMMITLOG
❓ 06.1 · 原理题天花板：“Kafka 明明把消息全写进磁盘，为什么单机还能扛百万级 TPS？”

⚡ 06.1 拆解 Kafka 百万级吞吐的「5 大底层加速引擎」

很多人有个刻板印象觉得“写磁盘一定很慢”。其实慢的是磁盘随机 I/O（磁头到处寻道），而磁盘顺序追加写的吞吐量高达 600MB/s～数 GB/s，甚至比随机写内存还要快！Kafka 正是围绕“极致顺序 I/O + 借力操作系统内核”打造了五环相扣的加速体系：

① 磁盘顺序追加写 (Append-Only)
每个 Partition 都是一个只允许在文件末尾追加、绝不原地修改的日志文件，彻底消除磁盘随机寻道开销，把随机写转化为 \(O(1)\) 顺序写。
② 借力 OS PageCache（页缓存）
不在 JVM 堆内建大缓存（避开 Java 对象头膨胀与 Full GC 停顿），直接读写操作系统内核的 PageCache；热消费直接命中内存，且 Broker 进程重启缓存不丢！
③ 端到端攒批 + 压缩 + 分区并行
Producer 内存攒成大 RecordBatch 并整批压缩（LZ4/Zstd）后发送，Broker 原样落盘，Consumer 批量拉取，将网络 RTT 与系统调用开销摊薄百倍。
🚀 核心王牌：零拷贝（Zero-Copy）—— 把磁盘/PageCache 里的消息发往网卡，到底省了哪几次拷贝？ 零 CPU 拷贝 · FileChannel.transferTo
❌ 传统 I/O（File.read() + Socket.write()）：
4 次上下文切换 + 4 次数据拷贝（含 2 次无用 CPU 拷贝）
1. 磁盘 ──(DMA 拷贝①)──▶ 内核 PageCache
2. PageCache ──(CPU 拷贝② · 多余!)──▶ JVM 用户态缓冲区
3. JVM 用户缓冲区 ──(CPU 拷贝③ · 多余!)──▶ 内核 Socket 缓冲区
4. Socket 缓冲区 ──(DMA 拷贝④)──▶ 网卡 NIC 发送
痛点：Broker 只是原样转发消息，根本不需要修改数据，却把数据白白搬进 JVM 用户态又搬回内核态！
✅ Kafka 零拷贝（Linux sendfile + 网卡 SG-DMA）：
仅 2 次上下文切换 + 2 次 DMA 拷贝（0 次 CPU 拷贝！）
1. 磁盘 ──(DMA 拷贝①)──▶ 内核 PageCache（若热数据已在 PageCache 则连这步都省了！）
2. 向 Socket 缓冲区仅追加「文件地址与长度描述符」（零数据拷贝）
3. PageCache ──(SG-DMA 引擎直读拷贝②)──▶ 网卡 NIC 发送
💡 记住定义：“零拷贝”指的是「内核态与用户态之间 0 次 CPU 拷贝」，数据全程不进 JVM 内存！
🔍 进阶必问 · 既然 sendfile 比 mmap 少一次 CPU 拷贝，为什么 RocketMQ 不用 sendfile 而偏偏选了 mmap？

这是区分“背八股”和“真懂架构”的经典追问！两种零拷贝技术的核心差异在于「应用程序在用户态能不能拿到消息的具体内容」：

零拷贝方式 拷贝与切换次数 核心优缺点与为什么 Kafka / RocketMQ 各自选它？
sendfile
（Kafka 消费读取使用）		 2 次切换 + 0 次 CPU 拷贝
（PageCache 直达网卡）		 • 返回值限制：sendfile(out_fd, in_fd, offset, count) 在内核里直接把字节流推给网卡，只向用户态返回“成功发送了多少字节（int）”，JVM 代码完全摸不到消息内容！
• 为什么适合 Kafka？Kafka 的分区文件里存的就是当前 Topic 的纯消息，不需要在 Broker 端解析内容，直接按字节区间吐给网卡即可（注：若 Kafka 开启了 SSL/TLS 加密，因必须在用户态加密，sendfile 零拷贝会自动退化失效）。
mmap + write
（RocketMQ CommitLog 读写使用）		 4 次切换 + 1 次 CPU 拷贝
（PageCache ──CPU──▶ Socket 缓冲区）		 • 核心优势：mmap（Java MappedByteBuffer）把内核 PageCache 直接映射到用户态虚拟地址空间，Broker 代码可以在不触发额外用户态拷贝的前提下，直接在内存里读取、解析消息头、做 Tag / SQL92 属性过滤，或者在写入前预热页缓存！
• 为什么适合 RocketMQ？RocketMQ 所有 Topic 混写在定长 1GB 的 CommitLog 中，且经常需要在服务端读取消息属性或返回具体内容给逻辑层处理，mmap 是最契合的选择。
❓ 06.2 · 磁盘上的消息文件到底长什么样？Kafka 的「Segment 稀疏索引」和 RocketMQ 的「CommitLog + ConsumeQueue」是怎么权衡的？

💽 06.2 两大存储架构巅峰对决：Kafka 分区独立存储 vs RocketMQ 集中混合存储

同样是顺序写磁盘，Kafka 和 RocketMQ 在底层文件组织上做出了截然不同的设计，这也直接决定了它们在「少量大吞吐 Topic」与「成千上万个业务 Topic」下的性能表现：

📂 一、Kafka 存储结构：每个 Partition 独立目录，按 Segment 分段 + 稀疏索引 (.index) 文件名二分 + 稀疏索引定位

如果一个 Partition 的所有消息存成一个几百 GB 的巨型文件，既没法高效删除过期历史数据，也没法快速定位某个 Offset。因此 Kafka 把每个 Partition 切分成多个固定大小（默认 1GB）的 Segment（日志段），每个 Segment 包含三胞胎文件（文件名就是该段第 1 条消息的起始 Offset）：

📁 order-topic-0/（分区目录）
├── 00000000000000000000.log (消息数据)
├── 00000000000000000000.index (偏移量稀疏索引)
├── 00000000000000000000.timeindex (时间戳索引)
├── 00000000000000368769.log (第2段: 368769起)
└── 00000000000000368769.index
🔎 查 offset = 368800 的三步极速定位：
1. 文件名二分查找：对比 Segment 文件名，瞬间锁定在 0000...368769 这一段；
2. .index 稀疏索引二分查找：因为每隔 4KB 消息才建一条索引项（省内存，通过 mmap 常驻内存），二分找到最接近且 <= 368800 的物理文件字节偏移量（如 offset=368795 → pos=12400）；
3. .log 小范围顺序扫描：从物理位置 12400 往后顺序扫几条即可拿到 368800！
🚀 二、RocketMQ 存储结构：全机单一 CommitLog 顺序写 + 20字节定长 ConsumeQueue 索引 海量 Topic 不退化
① CommitLog（主体数据本）
整台 Broker 上所有 Topic、所有队列的消息全部混在一起，顺序追加写入同一个 CommitLog（每文件定长 1GB）。哪怕有 1 万个 Topic，磁盘磁头也永远只在一个文件末尾顺序写！
② ConsumeQueue（20B 消费目录）
消息写进 CommitLog 后，后台 ReputMessageService 异步分发构建每个 Queue 的轻量索引文件。每条索引严格定长 20 字节：
[8B CommitLog物理偏移 + 4B 消息长度 + 8B Tag哈希码]。
👉 Tag 过滤为什么极快？消费者拉取时先在内存里比对这 8 字节 Tag HashCode，不匹配连 CommitLog 都不读！
③ IndexFile（按 Key 哈希索引）
基于磁盘文件实现的哈希表（Header + 500 万个 Hash 槽 + 2000 万个冲突链表条目），专门支持在控制台输入业务单号 orderId（Message Key）秒级反查消息轨迹。
对比维度 Kafka（分区独立 .log 文件） RocketMQ（单一 CommitLog + ConsumeQueue）
写入特点 每个 Partition 各自顺序写；Topic 少时吞吐极高，但分区上千时退化为随机写。 所有 Topic 永远汇聚成单流顺序写 1 个 CommitLog，万级 Topic 下写入依然稳如泰山。
读取特点 一次直读：定位到 Partition 的 .log 后直接通过 sendfile 顺序流式读出。 两跳读取：先顺序读 ConsumeQueue 拿到 8B 物理地址，再去 CommitLog 读取消息体（靠定长 20B 索引全进 PageCache 加上 SSD 弥补随机读）。
