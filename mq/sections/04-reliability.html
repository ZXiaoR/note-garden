🛡️ 04.1 · 消息不丢失三段闭环：生产发送、Broker 多副本存储与消费手动提交配置

🛡️ 04.1 消息不丢失：把「生产 → Broker → 消费」三段逐一配齐

一条消息从业务发出到真正落库生效，一共跨越三个阶段，任何一个阶段漏配参数都可能在断电或重启时丢数据。工程上必须沿着「第一段：生产发送 → 第二段：Broker 存储 → 第三段：消费提交」逐段加固：

① 生产端 → Broker（防网络闪断丢包） acks=all + 错误捕获重试/补偿
• 禁止发后不管（acks=0）或忽略发送返回值：同步发送必须检查返回的 error，异步发送必须在错误回调中重试或写入本地消息表兜底。
• 为什么 acks=1 依然会丢消息？acks=1 只等 Leader 副本写进自己内存页缓存就向生产者返回成功；如果此刻 Follower 备份副本还没来得及拉取，Leader 机器突然断电，新选出的 Leader 上根本没有这条消息。因此核心账务必须设为 acks=all（或 -1，Kafka 3.0+ 原生客户端默认已是 all，注意 kafka-go 默认是 RequireNone/One，必须显式指定 kafka.RequireAll！）。
② Broker 存储阶段（防单机断电丢页缓存、防硬盘物理损坏） 3 副本 + min.insync.replicas=2
Kafka 收到消息后先写入操作系统内存页缓存（PageCache）再异步刷盘，单机掉电会丢未刷盘内存，因此生产集群靠多副本冗余三件套保障：
1. replication.factor = 3：每个分区在 3 台不同机器上各存一份副本；
2. min.insync.replicas = 2：配合生产端 acks=all，强制要求每条消息至少同时写入 Leader + 至少 1 台同步 Follower（共 2 台机器内存）才算成功——否则当 Follower 全掉线导致同步副本集合 ISR（In-Sync Replicas，同步副本集合） 只剩 Leader 1 台时，acks=all 会悄悄退化成单机写入；
3. unclean.leader.election.enable = false（Kafka 1.0+ 默认值）：禁止落后掉队的非同步副本被选为新 Leader 覆盖丢数据。
③ Broker → 消费端（线上 80% 的丢消息事故都发生在这里） 关自动提交 · 先完成业务再手动 Commit
• 误区 A（开启自动提交 / 先提交后处理）：拉出消息就提交了 Offset，结果写数据库报错或容器 OOM（Out Of Memory，内存溢出）重启，Broker 以为你处理完了，永远不再重投。
• 误区 B（拉出消息丢进内存异步协程池就立刻提交）：主循环刚把消息塞进 go func() 就调了 CommitMessages，一旦容器发版重启，还在内存协程里没跑完的消息瞬间蒸发。
• 正确做法：关闭自动提交（enable.auto.commit=false），在当前消费流程同步执行完业务落库后，最后一步才手动提交 Offset。

// 2. Go 生产端：显式指定 RequireAll (acks=all) + 有限重试 + 同步等待错误返回
func NewReliableWriter(brokers []string) *kafka.Writer {
    return &kafka.Writer{
        Addr:         kafka.TCP(brokers...),
        Topic:        "trade.order.paid",
        Balancer:     &kafka.Hash{},
        RequiredAcks: kafka.RequireAll, // 核心！显式要求所有 ISR 同步副本写入成功
        MaxAttempts:  5,                // 网络闪断自动重试最多 5 次
        Async:        false,            // 同步阻塞等待 Broker 确认
    }
}

// 3. Go 消费端：FetchMessage 拉取（不自动提交） -> 业务落库成功 -> CommitMessages 手动提交
func RunReliableConsumer(ctx context.Context, brokers []string, handleBiz func(context.Context, kafka.Message) error) {
    r := kafka.NewReader(kafka.ReaderConfig{
        Brokers:        brokers,
        Topic:          "trade.order.paid",
        GroupID:        "points-service-grp",
        CommitInterval: 0, // 0 表示禁用后台定时自动刷盘提交，完全由代码手动控制
    })
    defer r.Close()

    for {
        msg, err := r.FetchMessage(ctx)
        if err != nil {
            return
        }
        // 必须先在当前协程把业务逻辑和数据库事务彻底跑成功
        if err := handleBiz(ctx, msg); err != nil {
            // 处理失败切勿 Commit！走退避重试或转入 DLQ（见 03.7）
            continue
        }
        // 业务落库成功后再签字提交 Offset（即使这一步崩溃，重启也只是重投一次，由 04.2 幂等兜底）
        _ = r.CommitMessages(ctx, msg)
    }
}

♻️ 04.2 · 消费端幂等实战：唯一索引、状态机乐观锁与 Redis SET NX 三种写法

♻️ 04.2 消费端幂等：防重复执行的 3 套标准代码

在分布式网络里，只要按 04.1 做到了「不丢消息」（生产超时重发 + 消费先落库后提交 Offset），重复投递就一定会发生：比如消费者刚给用户加完 100 积分，还没来得及执行下一行 CommitMessages 容器就重启了，新实例接管分区后会把同一条消息再拉出来执行一遍。

因此生产消费逻辑必须满足幂等性（Idempotency，即 f(f(x)) = f(x)，同一业务消息执行 1 次与执行 N 次结果完全一致）。第一步是选取稳定的业务唯一幂等键（如 order_no、支付流水号或上游生成的 event_id，不要依赖重发会改变的临时连接序号），然后按场景三选一落地：

写法 ①：数据库唯一索引 / 同事务防重表（账务与加积分首选，100% 物理兜底）

插入订单用表本身的 UNIQUE KEY (order_no)；如果是 UPDATE user_points SET balance = balance + 100 这种累加操作，就在同一个数据库建一张 mq_consume_log (event_id PRIMARY KEY)，把「插防重表 + 加积分」包在同一个本地事务里——重复消息进来时第一句主键冲突报错回滚，积分绝不会多加：

🐹 idem_unique_key.go · 写法一：同事务插入唯一键防重表 + 累加积分 [Go + MySQL] 
import "github.com/go-sql-driver/mysql"

func AddPointsIdempotent(ctx context.Context, db *sql.DB, eventID string, userID, points int64) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // 1. 先向防重表插入唯一 event_id（建表主键: event_id VARCHAR(64) PRIMARY KEY）
    _, err = tx.ExecContext(ctx, `INSERT INTO mq_consume_log (event_id) VALUES (?)`, eventID)
    if err != nil {
        // MySQL 错误码 1062 = Duplicate entry（说明之前已经成功处理过了，直接视为成功放行提交 Offset！）
        if me, ok := err.(*mysql.MySQLError); ok && me.Number == 1062 {
            return nil
        }
        return err
    }

    // 2. 只有首次插入成功的事务，才会走到下面执行真正的加积分
    if _, err = tx.ExecContext(ctx,
        `UPDATE user_points SET balance = balance + ? WHERE user_id = ?`, points, userID,
    ); err != nil {
        return err
    }
    return tx.Commit()
}

写法 ②：业务状态机 / 乐观锁条件更新（状态流转类业务最简洁，零额外表）

订单状态天然遵循 UNPAID（待支付） → PAID（已支付） → SHIPPED（已发货） 单向流转。更新时在 WHERE 里限定前置状态即可天然防重：

🐹 idem_state_machine.go · 写法二：带前置状态的单条原子条件更新 [Go + SQL] 
func MarkOrderPaidIdempotent(ctx context.Context, db *sql.DB, orderNo string) error {
    // 只有当前处于 UNPAID 时才会改成 PAID；重复消息再来时 status 已是 PAID，受影响行数为 0，天然幂等
    res, err := db.ExecContext(ctx,
        `UPDATE orders SET status = 'PAID', paid_at = NOW() WHERE order_no = ? AND status = 'UNPAID'`,
        orderNo,
    )
    if err != nil {
        return err
    }
    rows, _ := res.RowsAffected()
    if rows == 0 {
        // 已经处理过（或已取消），幂等安全返回 nil 以提交 Offset
        return nil
    }
    return nil
}

写法 ③：Redis SET NX 三态状态机（调第三方发短信等无本地 DB 事务场景）

⚠️ 避坑重点：千万不能简单写成「一上来 SETNX，发现 Key 已存在就直接跳过并提交 Offset」——因为万一上次刚执行完 SETNX 还没发出短信进程就崩溃了，重启重投时看到 Key 存在直接跳过，这条短信就永远漏发了！正确写法是区分 PROCESSING（处理中租约）与 DONE（已完成）：

🐹 idem_redis_nx.go · 写法三：Redis PROCESSING / DONE 状态机防崩溃漏处理 [Go · go-redis/v9] 
func SendSMSIdempotent(ctx context.Context, rdb *redis.Client, eventID, phone string) error {
    key := "idem:sms:" + eventID

    // 1. 原子抢占 30 秒处理租约：SET idem:sms:<id> "PROCESSING" NX EX 30
    ok, err := rdb.SetNX(ctx, key, "PROCESSING", 30*time.Second).Result()
    if err != nil {
        return err
    }
    if !ok {
        // 抢占失败：查一下究竟是已经彻底成功了，还是别的协程正在跑
        state, _ := rdb.Get(ctx, key).Result()
        if state == "DONE" {
            return nil // 已确认发过短信，安全跳过并提交 Offset
        }
        return errors.New("任务正在处理中，稍后重试（切勿直接提交 Offset）")
    }

    // 2. 调用外部短信网关；若失败则主动删掉 PROCESSING 锁，让下次重试能正常进来
    if err := callSMSProvider(ctx, phone); err != nil {
        _ = rdb.Del(ctx, key).Err()
        return err
    }

    // 3. 真正发送成功，将标记升级为 DONE 并保留 24 小时防重
    _ = rdb.Set(ctx, key, "DONE", 24*time.Hour).Err()
    return nil
}
📌 04.3 · 结论速查：Kafka 幂等生产者与 EOS（精确一次语义）能做什么、不能做什么

📌 04.3 Kafka 幂等生产者与 EOS：工程结论与配置

看文档时常会遇到「Kafka 支持幂等生产者和 EOS（Exactly-Once Semantics，精确一次语义）」。实际开发只需记住以下两条工程结论，不必混淆概念：

  • 结论 ①：幂等生产者（enable.idempotence = true，Kafka 3.0+ 官方 Java/librdkafka 客户端已默认开启）
    • 它防住了什么：防止同一个 Producer 实例在网络超时重发时，把同一批消息往 Broker 分区里重复写两遍，同时保证单连接最多 5 个未确认批次（max.in.flight.requests.per.connection <= 5）重试时不乱序。
    • 它防不住什么（为什么消费端仍必须写 04.2 的业务幂等）：① Producer 进程重启后重发；② 上游业务代码因为 Bug 调了两次发送函数；③ 消费者写完 MySQL 但在提交 Offset 前崩溃导致的重复消费。
  • 结论 ②：Kafka 事务 / EOS（transactional.id + 消费端 isolation.level = read_committed）
    • 仅适用于 「从 Kafka 读 → 内存计算 → 写回 Kafka」的流处理闭环（如 Flink / Kafka Streams）。只要你的消费者是去写外部 MySQL、改 Redis 或发短信，Kafka 事务管不到外部数据库，标准答案永远是：At-least-once（04.1 三段防丢） + 消费端业务幂等（04.2）。

☑️ 本章即时场景题（先想答案，再点击展开）

1. 生产端已经配了 acks=all，但 Topic 的 min.insync.replicas 保持了默认值 1，集群遇到什么故障时照样会丢消息？

当两台 Follower 因为网络抖动暂时掉队被移出 ISR 同步集合，导致 ISR 里只剩 Leader 自己 1 台机器时：由于 min.insync.replicas=1 允许继续写入，acks=all 此时只写进 Leader 1 台机器就会返回成功；紧接着若 Leader 硬盘损坏或断电未刷盘，数据依然丢失。所以必须同时设 replication.factor=3 且 min.insync.replicas=2。

2. 同事为了加快消费速度，在消费循环里一拿到消息就起一个 go handleOrder(msg) 协程异步写库，紧接着主循环立刻调 CommitMessages，这有什么风险？

一旦服务发版滚动重启、容器 OOM 或 handleOrder 内部遇到数据库死锁报错，Offset 却早已被主循环提前提交给了 Kafka。重启后消费者直接从后面的新 Offset 开始拉取，之前还在内存协程里没落库的那批订单消息就静默永久丢失了。

3. 为什么在已开启 Kafka 幂等生产者（enable.idempotence=true）的线上环境，用户还是偶尔收到两张相同的支付返利券？

因为幂等生产者只管「Producer 到 Broker 写入不重」，完全管不到「Broker 到 Consumer 投递不重」。只要发券服务某次滚动发布重启或消费慢触发了重平衡，已经落库发了券但还没来得及提交 Offset 的那几条消息就会被再次投递；发券表若没对 (order_no, coupon_type) 加唯一索引，就会发第二张券。
