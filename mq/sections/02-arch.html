❓ 02.1 · Kafka、RocketMQ、RabbitMQ 为什么同时存在？它们各自的架构基因差在哪？

🏗️ 02.1 三大主流 MQ 架构基因拆解：它们不是互相替代，而是各有所长

市面上没有一款“全能第一”的消息队列，因为「极致吞吐量」「复杂业务特性（事务/定时/海量 Topic）」「微秒级低延迟与花式路由」在底层存储和网络模型上天然存在取舍：

① Apache Kafka —— 「为百万级极致吞吐与大数据流处理而生」 Scala/Java · 单机百万 TPS · KRaft 架构
• 核心理念：LinkedIn 出品，彻底把消息当成分布式追加日志（Append-Only Commit Log）来存。依靠分区独立文件顺序写 + OS PageCache + sendfile 零拷贝 + 批量压缩，把单机吞吐拉满到百万级/秒，且磁盘堆积 TB 级数据毫无压力。
• 元数据演进（高频考点）：早期版本依赖外部 ZooKeeper 存元数据和选 Controller；Kafka 3.3+ 正式生产可用、4.0 彻底移除 ZooKeeper，改用内置基于 Raft 协议的 KRaft 控制平面，分区切主速度提升十倍以上。
Producer ──(Batch+压缩)──▶ Broker 集群 [Topic 拆多 Partition · Leader/Follower ISR 副本] ──(Zero-Copy Pull)──▶ Consumer Group
② Apache RocketMQ —— 「为金融级交易、电商订单与丰富业务特性而生」 Java · 十万级 TPS · 原生事务/定时/Tag过滤
• 核心理念：阿里出品（历经双十一万亿级消息锤炼）。它发现了 Kafka 在电商场景下的两个痛点：一是当业务 Topic 多达几千个时，Kafka 分区文件过多导致顺序写退化为随机写；二是缺少业务急需的分布式事务消息、任意定时消息、Tag 二级过滤与死信重试队列。
• 架构破局：用极简无状态的 NameServer 集群（节点间互不通信，Broker 每 30s 向所有 NameServer 发心跳）替代笨重的 ZK；存储上全 Broker 所有 Topic 共享唯一一个 CommitLog 顺序写 + 轻量 ConsumeQueue 索引（第 06 章详解）；RocketMQ 5.0 更引入了 Proxy 无状态代理与存算分离。
NameServer (轻量路由注册中心) ◀──心跳/拉路由──▶ Producer ──▶ Broker [单一 CommitLog + 多 ConsumeQueue] ──▶ Consumer
③ RabbitMQ —— 「为微秒级超低延迟与复杂灵活路由而生」 Erlang · 万级 TPS · µs 级微秒延迟 · AMQP
• 核心理念：基于标准 AMQP 协议，用天生高并发低延迟的 Erlang 语言编写。它的灵魂不是“分区大日志”，而是在 Broker 内部加了一层极其灵活的 Exchange（交换机）——生产者只管把消息带着 Routing Key 发给交换机，交换机按绑定规则（Binding）实时路由到不同队列。
Producer ──(带 RoutingKey)──▶ Exchange 交换机 ──(按 Binding 规则匹配分发)──▶ Queue 队列 ──(Push + QoS)──▶ Consumer
❓ 02.2 · RabbitMQ 的生产者为什么从不直接发消息给 Queue？4 种 Exchange 交换机怎么选？

🔀 02.2 RabbitMQ 路由原理：4 种 Exchange 交换机与 Quorum 队列高可用

在 RabbitMQ 中，生产者永远只把消息发给 Exchange（交换机）。交换机本身不存消息，它就像快递分拣中心，根据消息携带的 Routing Key（路由键）和队列绑定的 Binding Key，按以下 4 种交换机类型决定把消息塞进哪些队列：

Exchange 类型 路由匹配规则 典型业务场景举例
① Direct
直连交换机		 Routing Key == Binding Key 一字不差完全相等时，才投递到对应队列。 按明确标识精准分流（如把 error 日志路由给告警队列，把 info 路由给归档队列）。
② Fanout
扇出广播交换机		 完全无视 Routing Key！只要绑定在该交换机上的队列，每个队列无条件复制一份（最快）。 标准的发布/订阅广播（如用户注册成功，同时广播给发券队列、欢迎信队列、风控队列）。
③ Topic ⭐最常用
主题通配符交换机		 Key 用点号 . 分词（如 order.pay.shanghai），支持通配符：
• * 匹配恰好 1 个词；
• # 匹配 0 个或多个词。		 多维灵活订阅：绑定 order.# 的数仓队列收所有订单事件；绑定 *.pay.* 的财务队列只收支付事件。
④ Headers
头部属性交换机		 不看 Routing Key，而是匹配消息头 Headers 里的键值对属性（支持 x-match: all / any）。 极少使用（性能较差，基本都可被 Topic 替代）。
🛡️ RabbitMQ 集群高可用演进（普通集群 → 镜像队列 → Quorum 队列）：
• 普通集群模式：各节点只同步元数据（队列名和交换机定义），队列里的消息实体只存在创建它的那 1 台节点上；如果该节点宕机，队列消息暂时不可用。
• 经典镜像队列（Classic Mirrored Queue）：把队列主从复制到多台节点，但在 RabbitMQ 3.x 后期已标记废弃（全量同步阻塞大、脑裂风险高）。
• 现代标准 —— 仲裁队列（Quorum Queue，RabbitMQ 3.8+ / 4.0 主推）：基于 Raft 一致性协议的多副本持久化队列，过半节点写入即确认，彻底解决脑裂与数据丢失问题！

📈 选 Kafka 的场景
日志采集、用户行为埋点、监控指标管道、Flink/Spark 实时流计算——追求百万级吞吐、TB 级堆积与大数据生态无缝对接。
🛒 选 RocketMQ 的场景
电商订单、金融支付、核心交易中台——Topic 数量多，重度依赖事务消息、定时关单、顺序消费、Tag 过滤与死信兜底。
⚡ 选 RabbitMQ 的场景
中小型业务系统、企业内部微服务、需要复杂通配符/多维路由或微秒级极低延迟通知，开箱即用、运维省心。
