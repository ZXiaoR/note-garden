📣 03.1 · 场景一：下单/注册后异步发券与发短信（多消费组各自消费一份）

📣 03.1 下单后异步发券、发短信

  • 需求：用户支付订单成功后，需要给账户发放满减返利券，同时发送支付成功通知短信；未来还可能增加会员积分统计，且不能拖慢支付回调主接口。
  • 为什么用 MQ：把发券、发短信从支付主链路剥离为后台异步执行，主接口耗时保持在毫秒级；各下游各自订阅事件，未来加积分服务无需改动支付代码。
  • 方案设计：
    • Topic：trade.order.paid（分区数设为 6，留足并发余量）
    • 消息 Key：order_no（如 "ORD_20261128_01"）
    • 消费者组：发券服务配置 GroupID = "coupon-svc-grp"，短信服务配置 GroupID = "sms-svc-grp"（两组各自独立收到每一笔支付事件）
🐹 order_fanout.go · 支付事件发布 + 多消费组独立订阅手动提交 [Go · kafka-go v0.4.47] 
package ordermq

import (
    "context"
    "encoding/json"
    "log"

    "github.com/segmentio/kafka-go"
)

type OrderPaidEvent struct {
    EventID string `json:"eventId"` // 全局唯一事件 ID，供下游做防重幂等
    OrderNo string `json:"orderNo"`
    UserID  int64  `json:"userId"`
    Amount  int64  `json:"amountCent"`
}

// 1. 支付服务：发布「订单已支付」事件（全局复用同一个 *kafka.Writer）
func PublishOrderPaid(ctx context.Context, w *kafka.Writer, evt OrderPaidEvent) error {
    body, err := json.Marshal(evt)
    if err != nil {
        return err
    }
    return w.WriteMessages(ctx, kafka.Message{
        Key:   []byte(evt.OrderNo),
        Value: body,
    })
}

// 2. 通用消费循环：发券服务传 groupID="coupon-svc-grp"，短信服务传 groupID="sms-svc-grp"
func StartOrderPaidWorker(ctx context.Context, brokers []string, groupID string, handle func(context.Context, OrderPaidEvent) error) {
    r := kafka.NewReader(kafka.ReaderConfig{
        Brokers: brokers,
        Topic:   "trade.order.paid",
        GroupID: groupID,
    })
    defer r.Close()

    for {
        // 使用 FetchMessage 而非 ReadMessage（ReadMessage 会在读到瞬间自动提交 Offset！）
        msg, err := r.FetchMessage(ctx)
        if err != nil {
            return
        }
        var evt OrderPaidEvent
        if err := json.Unmarshal(msg.Value, &evt); err == nil {
            if err := handle(ctx, evt); err != nil {
                log.Printf("[%s] 处理失败稍后重试 order=%s: %v", groupID, evt.OrderNo, err)
                continue // 实际生产转入 03.7 阶梯重试 Topic，避免卡住当前分区
            }
        }
        // 业务真正成功后，才手动提交 Offset
        _ = r.CommitMessages(ctx, msg)
    }
}
⚠️ 两个高频踩坑点：
1. 切忌在同一个消费者函数里串行写 发券() + 发短信()：一旦发券成功但短信接口超时报错触发重试，若发券没做严格幂等就会白送多张券，且慢速外部短信会把快速内部发券堵死——一个独立业务动作配一个独立 GroupID。
2. kafka-go 中 r.ReadMessage(ctx) 默认开启了自动提交，拉出消息瞬间就算没处理完也会提交 Offset；生产业务一律改用 r.FetchMessage(ctx) + 处理成功后调 r.CommitMessages(ctx, msg)。

💡 背后的原理：多个消费组同时拉取同一份分区文件时，Broker 如何靠内核页缓存（PageCache）让多方零磁盘寻道读取？详见 《📘 核心原理篇 · 00 推与拉》 与 《03.1 PageCache 与零拷贝》。

🌊 03.2 · 场景二：秒杀流量削峰与耗时任务排队（网关快速入队 + 消费端限速执行）

🌊 03.2 秒杀削峰与耗时任务异步排队

  • 需求 A（秒杀削峰）：整点秒杀 1,000 件商品，第 1 秒涌入 30,000 次下单请求，而底层 MySQL 订单库最高只能承受 1,500 TPS 写入。
  • 需求 B（耗时任务排队）：运营在后台点击「导出全年百万行订单 Excel」或用户上传视频触发「转码加水印」，单次处理耗时 20～60 秒，同步等待会导致 HTTP 网关 504 超时且并发数一高直接打满服务器内存。
  • 为什么用 MQ：把瞬时高并发请求或长耗时重任务先变成轻量的队列消息存下来，前端立即拿到「排队中 / 任务 ID（taskId）」去轮询状态；后端消费 Worker 按数据库或 CPU 承受上限主动限速匀速处理。
  • 方案设计：
    • Topic：秒杀用 seckill.order.requests（12 分区）；导出任务用 job.export.tasks（4 分区）
    • 消息 Key：user_id 或 task_id
    • 消费者组：seckill-order-writer-grp（进程内加令牌桶限流器 rate.Limiter 严格控制写库速率）
🐹 seckill_peak_shaving.go · 入口快速入队返回排队态 + 消费端限速落库 [Go · kafka-go + x/time/rate] 
// go get golang.org/x/time/rate
package seckill

import (
    "context"
    "encoding/json"

    "github.com/segmentio/kafka-go"
    "golang.org/x/time/rate"
)

type SeckillReq struct {
    ReqID  string `json:"reqId"`
    UserID int64  `json:"userId"`
    SkuID  int64  `json:"skuId"`
}

// 1. HTTP 接口层：Redis 原子预扣库存通过后，5ms 写入 Kafka 立即向前端返回 reqId（状态：排队中）
func EnqueueSeckill(ctx context.Context, w *kafka.Writer, req SeckillReq) error {
    payload, _ := json.Marshal(req)
    return w.WriteMessages(ctx, kafka.Message{
        Key:   []byte(req.ReqID),
        Value: payload,
    })
}

// 2. 消费端 Worker：按数据库安全水位限速（如共 3 台实例，每台限速 400 TPS，合计 1200 TPS 平稳写库）
func ConsumeSeckillWithRateLimit(ctx context.Context, r *kafka.Reader, createOrderInDB func(context.Context, SeckillReq) error) {
    limiter := rate.NewLimiter(rate.Limit(400), 50) // 每秒最多 400 次，桶突发容量 50

    for {
        msg, err := r.FetchMessage(ctx)
        if err != nil {
            return
        }
        // 超过数据库承载速率时在此平滑等待，不会把下游 MySQL 打挂
        if err := limiter.Wait(ctx); err != nil {
            return
        }
        var req SeckillReq
        _ = json.Unmarshal(msg.Value, &req)
        if err := createOrderInDB(ctx, req); err == nil {
            _ = r.CommitMessages(ctx, msg)
        }
    }
}

⚠️ 常见坑：① 改成入队削峰后，接口返回的只是「已受理排队」，前端必须轮询 GET /seckill/result?reqId=xxx 查看最终是否下单成功；② 做耗时导出/转码排队时，如果单条消息执行超过 5 分钟（Kafka 默认 max.poll.interval.ms），Broker 会判定消费者假死并将其踢出消费组，导致该重任务被别的机器重复拉走再跑一遍——务必调小单批拉取数并调大超时阈值（详见 07.3 防踢调参）。 ｜ 💡 背后的原理：为什么 Pull 模型天生不怕流量洪峰冲垮消费者？见 《📘 核心原理篇 · 00 推与拉》。

📊 03.3 · 场景三：日志与埋点高吞吐采集（批量攒包 + 压缩异步发送）

📊 03.3 日志与用户行为埋点采集

  • 需求：App 首页曝光、按钮点击埋点与微服务访问日志每秒产生 50,000 条记录，需要收集后导入 ClickHouse 或大数据数仓做漏斗分析。
  • 为什么用 MQ：业务服务器磁盘小且不能直连压垮数仓；Kafka 单机可抗百万级写入并充当海量日志缓冲管道。
  • 方案设计：
    • Topic：telemetry.user.clicks（12～24 分区，设 retention.hours=72 保留 3 天自动清理）
    • 消息 Key：留空使用轮询负载均衡（&kafka.RoundRobin{}），让所有分区流量绝对均匀
    • 吞吐优先配置：开启内存攒批（BatchSize / BatchTimeout）+ LZ4 压缩 + 异步发送 + RequireOne 确认（允许极端断电丢极少量埋点，换取十倍吞吐与零接口阻塞）
🐹 telemetry_batch_writer.go · 埋点日志异步攒批与 LZ4 压缩配置 [Go · kafka-go v0.4.47] 
func NewTelemetryWriter(brokers []string) *kafka.Writer {
    return &kafka.Writer{
        Addr:         kafka.TCP(brokers...),
        Topic:        "telemetry.user.clicks",
        Balancer:     &kafka.RoundRobin{}, // 无需保序，均匀打散到所有分区
        BatchSize:    500,                 // 凑够 500 条发一次网络请求
        BatchBytes:   1 << 20,             // 或凑够 1 MiB 发一次
        BatchTimeout: 50 * time.Millisecond, // 流量低时最多等 50ms 立即发出
        Compression:  kafka.Lz4,           // JSON 文本经 LZ4 压缩通常可省 70%+ 带宽
        RequiredAcks: kafka.RequireOne,    // Leader 写入即确认（非账务日志高吞吐档位）
        Async:        true,                // WriteMessages 写入内存缓冲即返回，不阻塞业务请求
    }
}
// 注意：服务收到 SIGTERM 优雅退出时，务必调用 writer.Close() 把内存里最后半批日志刷出去！

⚠️ 常见坑：① 千万别把日志配置（Async: true + RequireOne）照抄到订单扣款业务上，否则机器断电会丢账；② 开启 Async: true 后，进程重启停机前若不调 writer.Close()，还在内存缓冲区排队的最后几十毫秒日志会丢失。 ｜ 💡 背后的原理：为什么开启批量压缩后，Kafka 连解压都不用做就能原样落盘并零拷贝推给消费者？详见 《📘 核心原理篇 · 03.1 百万吞吐五大加速引擎》。

🔄 03.4 · 场景四：异构数据同步（数据库变更事件 → 刷新搜索索引与删除缓存）

🔄 03.4 数据同步：数据库变更 → 搜索索引 / 缓存

  • 需求：商家在后台修改了商品价格或上下架状态并落入 MySQL 后，需要把最新商品信息同步到 Elasticsearch 供全站全文搜索，并删除 Redis 里的旧商品详情缓存（见 Redis 笔记 03.1 Cache-Aside）。
  • 为什么用 MQ：如果在改价接口里同步双写 MySQL + Elasticsearch + Redis，任一组件抖动就会导致三方数据不一致；通过把数据库变更转为有序事件流（业务主动发，或用 Debezium / Canal 订阅 MySQL Binlog 自动投递，即 CDC，Change Data Capture，变更数据捕获），搜索与缓存各自独立订阅并支持失败重试。
  • 方案设计：
    • Topic：catalog.product.changed（8 分区）
    • 消息 Key（核心！）：必须填商品主键 sku_id，确保同一个商品的「改价 100 → 改价 80」严格进同一个分区按顺序消费
    • 消费者组：es-indexer-grp（更新搜索索引）、redis-invalidator-grp（删除并重试清理缓存）

🤝 03.5 · 场景五：下单写库与发消息的一致性（本地消息表 Outbox vs RocketMQ 事务消息）

🤝 03.5 下单与发消息的一致性：本地消息表实战

在订单支付场景里，我们需要同时完成「① 修改本地 MySQL 订单为已支付」和「② 向 Kafka 发送支付消息」。为什么不能直接写两行代码？因为跨了两个系统，怎么排顺序都有漏洞：

  • ❌ 先写 MySQL 提交，再发 MQ：刚提交完事务进程崩溃或网络闪断，消息没发出去 👉 钱扣了，下游永远收不到通知。
  • ❌ 先发 MQ，再写 MySQL 提交：消息一发出就被下游消费发了券，结果本地数据库唯一键冲突回滚了 👉 单没下成，白发了优惠券。
  • ❌ 在数据库事务 BEGIN...COMMIT 里同步调 MQ：发 MQ 网络卡顿 2 秒会把数据库行锁与连接占住 2 秒拖垮连接池；且发完 MQ 后若在 COMMIT 那一瞬间断电回滚，已经发出去的消息同样撤不回来。

在使用 Kafka 时，最通用的工业级解法是本地消息表（Transactional Outbox，事务发件箱模式）——在同一个业务数据库里建一张 outbox_messages 表，利用 MySQL 自身的单库 ACID 事务保证「业务表修改」和「待发消息记录」100% 同生共死，再由后台协程轮询投递：

🐹 outbox_tx.go · 本地消息表建表 SQL + Go 同事务双写与后台轮询投递 [Go · database/sql + kafka-go] 
/* 建表 SQL（与 orders 表在同一个 MySQL 库）：
CREATE TABLE outbox_messages (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  topic       VARCHAR(128) NOT NULL,
  msg_key     VARCHAR(64)  NOT NULL,
  payload     JSON         NOT NULL,
  status      VARCHAR(16)  NOT NULL DEFAULT 'PENDING', -- PENDING / SENT
  retry_count INT          NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_status_id (status, id)
); */

// Step 1: 订单服务在同一个本地事务里「改订单 + 插本地消息表」
func CreateOrderWithOutbox(ctx context.Context, db *sql.DB, orderNo string, userID, amount int64) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    if _, err = tx.ExecContext(ctx,
        `INSERT INTO orders (order_no, user_id, amount, status) VALUES (?, ?, ?, 'PAID')`,
        orderNo, userID, amount,
    ); err != nil {
        return err
    }

    payload, _ := json.Marshal(map[string]any{"orderNo": orderNo, "userId": userID, "amount": amount})
    if _, err = tx.ExecContext(ctx,
        `INSERT INTO outbox_messages (topic, msg_key, payload, status) VALUES ('trade.order.paid', ?, ?, 'PENDING')`,
        orderNo, payload,
    ); err != nil {
        return err
    }
    return tx.Commit() // 要么两张表同时成功，要么同时回滚
}

// Step 2: 后台 Relay 协程每 500ms 扫描一批未发送消息投递 Kafka（多实例下配合 FOR UPDATE SKIP LOCKED）
func RelayPendingOutboxOnce(ctx context.Context, db *sql.DB, w *kafka.Writer) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    rows, err := tx.QueryContext(ctx,
        `SELECT id, topic, msg_key, payload FROM outbox_messages WHERE status='PENDING' ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED`)
    if err != nil {
        return err
    }
    defer rows.Close()

    var sentIDs []int64
    for rows.Next() {
        var id int64
        var topic, key string
        var body []byte
        _ = rows.Scan(&id, &topic, &key, &body)
        if err := w.WriteMessages(ctx, kafka.Message{Topic: topic, Key: []byte(key), Value: body}); err == nil {
            sentIDs = append(sentIDs, id)
        }
    }
    for _, id := range sentIDs {
        _, _ = tx.ExecContext(ctx, `UPDATE outbox_messages SET status='SENT' WHERE id=?`, id)
    }
    return tx.Commit()
}
🚀 另一种主流做法 —— RocketMQ 原生事务消息：
如果团队选型的是 RocketMQ，无需自己在业务库建 outbox_messages 表。RocketMQ 原生提供了「先发对消费者隐身的半消息（Half Message）→ 执行本地 DB 事务 → 发 Commit 转正（若断电未发则由 Broker 主动回调反查 DB 状态）」机制，达成完全相同的最终一致性效果。
⚠️ 共同边界：无论是本地消息表还是 RocketMQ 事务消息，都属于最终一致性方案——Relay 发成功但改 SENT 前崩溃会重发一次，因此下游消费者必须做幂等（见 04.2）；且下游若消费报错不会回滚上游已支付的订单，而是走 03.7 重试与死信 补偿。

💡 背后的原理：RocketMQ 的半消息具体存在哪里、Broker 定时事务反查是如何运转的？详见 《📘 核心原理篇 · 02.1 事务消息半消息与反查实现》。

⏱️ 03.6 · 场景六：延迟任务（订单 30 分钟超时取消与四大技术方案对比）

⏱️ 03.6 延迟任务：订单超时未支付自动取消

  • 需求：用户提交订单后锁定库存，若 30 分钟仍未付款，系统自动关闭订单并释放库存；不能每分钟跑 SELECT * FROM orders 扫千万级全表。
  • 核心事实：Kafka 没有原生的任意延迟/定时消息功能！因为 Kafka 的 Partition 是严格按写入时间顺序追加的只读日志段，无法低开销地在文件中间插入任意到期时刻的消息并排序投递。
  • 工程选型对比（按基础设施现状四选一）：
实现方案 具体做法 优缺点与核心注意事项
① RocketMQ 定时消息
大体量交易首选		 发送消息时直接指定投递时间戳（RocketMQ 5.0 DeliverTimeStamp，4.x 指定 delayLevel=16 即 30m），到期后消费者才收得到。 开箱即用、高可靠磁盘持久化，支持百万级待关单积压；需团队已部署 RocketMQ。
② RabbitMQ 延迟方案 方案 A：无消费者的缓冲队列设 TTL + 绑定 DLX（Dead Letter Exchange，死信交换机）；
方案 B：安装官方 rabbitmq_delayed_message_exchange 插件。		 ⚠️ 方案 A 有严重的队头阻塞坑：RabbitMQ 只检查队列第 1 条消息是否过期——若前一条设 30m、后一条设 1m，1m 的消息会被堵满 30m 才出来！混用不同时长务必选插件或按时长拆独立队列。
③ Redis ZSet + Kafka
Kafka 栈最常用组合		 下单时 ZADD delay:unpaid <now+1800> <orderNo>；后台轻量协程每秒用 Lua 原子弹出已到期单号，转发进 Kafka trade.order.cancel 由消费组并发关单。 不用额外部署第二种 MQ，支持任意秒级精度且支付成功可顺手 ZREM 提前移除；完整 Lua 代码见 Redis 笔记 04.7。
④ Kafka 固定档位延迟 Topic 专门建 order.delay.30m Topic（同 Topic 内所有消息固定延迟 30m，天然先入先到期）；转发器读到头部消息若还没满 30m 就 Sleep 剩余秒数，到期后写入真实 order.cancel Topic。 纯 Kafka 零外部依赖，但每个延迟档位都必须建独立 Topic，无法支持任意自定义时刻；且等待期间需注意调用 Pause 或短轮询防触发消费超时重平衡。

// 消费到期关单事件：用户可能在第 29 分 59 秒刚付完款，因此关单 SQL 必须校验 status='UNPAID'
func HandleOrderTimeoutCancel(ctx context.Context, db *sql.DB, orderNo string) error {
    res, err := db.ExecContext(ctx,
        `UPDATE orders SET status = 'CANCELED', canceled_at = NOW() WHERE order_no = ? AND status = 'UNPAID'`,
        orderNo,
    )
    if err != nil {
        return err
    }
    affected, _ := res.RowsAffected()
    if affected == 1 {
        // 确实将未支付订单改为了已取消，此时才去归还锁定库存（若 affected==0 说明已支付或已取消过，直接忽略）
        return releaseLockedStock(ctx, db, orderNo)
    }
    return nil
}

🛟 03.7 · 场景七：失败重试与死信队列（阶梯重试 Topic + DLQ 隔离兜底）

🛟 03.7 失败重试与死信队列（DLQ）

  • 需求：消费订单消息调用电子发票服务时，偶尔遇到对方网关抖动超时，或者某条消息因历史脏数据导致解析必报错（俗称「毒丸消息 Poison Pill」）。
  • 为什么不能原地死循环重试：Kafka 单分区按序推进，如果第 100 号脏消息一直报错不提交 Offset，后面第 101～100,000 号正常用户的发票全都会被它死死堵住。
  • 方案设计（应用层阶梯重试 Topic + DLQ）：
    • RocketMQ 原生内置了 %RETRY%（16 级退避）与 %DLQ%；而 Kafka 服务端没有内置重试与死信队列，需要在消费端代码里用独立 Topic 实现：
    • 主 Topic：invoice.issue ──(第 1～3 次失败带重试次数 Header)──▶ 重试 Topic：invoice.issue.retry ──(超过 3 次仍失败)──▶ 死信 Topic：invoice.issue.dlq，转存成功后立即提交原分区 Offset 放行后续正常消息，并对 .dlq 配置监控告警人工修复重放。
🐹 retry_and_dlq.go · Kafka 消费失败自动升级重试计数与超限转入 DLQ [Go · kafka-go v0.4.47] 
import "strconv"

const maxRetry = 3

func ConsumeWithDLQ(ctx context.Context, r *kafka.Reader, routeWriter *kafka.Writer, bizFn func([]byte) error) {
    for {
        msg, err := r.FetchMessage(ctx)
        if err != nil {
            return
        }
        if bizErr := bizFn(msg.Value); bizErr != nil {
            retries := getRetryHeader(msg.Headers) + 1
            targetTopic := "invoice.issue.retry"
            if retries > maxRetry {
                targetTopic = "invoice.issue.dlq" // 超过上限：隔离进死信队列并触发告警
            }
            // 将原消息连同最新重试次数、报错原因转发至 retry 或 dlq Topic
            fwdErr := routeWriter.WriteMessages(ctx, kafka.Message{
                Topic: targetTopic,
                Key:   msg.Key,
                Value: msg.Value,
                Headers: []kafka.Header{
                    {Key: "x-retry-count", Value: []byte(strconv.Itoa(retries))},
                    {Key: "x-last-error", Value: []byte(bizErr.Error())},
                },
            })
            if fwdErr != nil {
                continue // 连重试/死信队列都没写进去时，切勿提交原 Offset，防止丢消息
            }
        }
        // 业务成功，或已安全转交至 retry / dlq 后，提交当前分区 Offset 继续处理下一条
        _ = r.CommitMessages(ctx, msg)
    }
}

func getRetryHeader(headers []kafka.Header) int {
    for _, h := range headers {
        if h.Key == "x-retry-count" {
            n, _ := strconv.Atoi(string(h.Value))
            return n
        }
    }
    return 0
}

如果下午 2:00 发版引入了一个计算逻辑 Bug（代码没报错，但把积分少算了一半），死信队列不会抓到它。此时只需修复代码重新上线，在停掉消费组后用命令行把该组的 Offset 重置回下午 2:00（见 05.2 回溯命令），配合消费幂等就能把这期间的消息完整重算修复。

☑️ 本章即时场景题（先想答案，再点击展开）

1. 在本地消息表（Outbox）方案中，如果后台 Relay 协程已经把消息成功发到了 Kafka，但刚要执行 UPDATE outbox_messages SET status='SENT' 时机器断电了，会发生什么？怎么防？

机器重启后，那条记录在数据库里仍然是 PENDING 状态，Relay 协程会把它再往 Kafka 发送一遍（产生重复消息）。这完全符合预期——本地消息表追求的是「至少投递成功一次（At-least-once）」，只要下游消费者按事件唯一 ID 或订单号做好业务幂等（04.2），第二次收到时直接忽略即可。

2. 团队用的是 RabbitMQ，同事在一个公共延迟队列上混发「30 分钟超时关单」和「10 秒支付结果轮询」两种 TTL 消息，上线后会出现什么故障？

会出现严重的队头阻塞：10 秒轮询消息排在 30 分钟关单消息后面时，RabbitMQ 只检查队头第 1 条消息是否过期，导致原本 10 秒就该触发的消息全部被卡住整整 30 分钟才集中爆发。应当按固定 TTL 时长拆成两个独立缓冲队列，或改用 rabbitmq_delayed_message_exchange 延迟交换机插件。

3. 为什么「订单需要保持严格先后顺序」的场景（如同一单的创建→支付→退款）不能直接用上面的异步重试 Topic 方案？

因为如果把失败的「创建订单」消息挪去 .retry 队列并提交了主分区 Offset，主分区紧接着就会先消费「支付订单」——由于订单还没创建出来，「支付」也会跟着报错或状态错乱。强顺序场景遇到失败只能在当前分区有限次短暂退避重试，仍失败则将该订单号记入异常锁定表拦截同单后续消息并告警（见 05.1）。

4. 做用户点击埋点采集时，产品经理说允许极端故障丢千分之一的埋点，但绝不能拖慢商品详情页接口耗时，kafka.Writer 哪三个参数最关键？

① Async: true（异步写入内存缓冲立即返回，不阻塞接口协程）；② BatchSize / BatchTimeout + Compression: kafka.Lz4（攒批压缩大幅降低网络 I/O）；③ RequiredAcks: kafka.RequireOne（只需 Leader 写入即确认，不必等所有副本同步）。
