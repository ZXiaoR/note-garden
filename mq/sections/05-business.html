05 高阶业务特性 · 事务消息（半消息+回查 vs 本地消息表）、延迟消息与死信回溯 TX MESSAGE · TIMING WHEEL · DLQ
❓ 05.1 · 为什么「写本地 MySQL 数据库」和「发 MQ 消息」无论是谁先谁后都会翻车？怎么做到 100% 原子一致？

🤝 05.1 事务消息（分布式事务）：让「本地数据库修改」与「MQ 消息发送」同生共死

假设用户下单支付：订单服务需要在本地 MySQL 执行 UPDATE 订单状态 = 已支付，同时发一条 MQ 消息通知积分服务加积分。因为这两个动作跨了 MySQL 和 MQ 两个独立中间件，无论你怎么排先后顺序，普通写法都有致命漏洞：

❌ 错误 ①：先写 DB 提交，再发 MQ
本地 DB 刚提交成功，服务突然宕机或网络闪断，MQ 没发出去 👉 钱扣了，积分永远没加上！
❌ 错误 ②：先发 MQ，再写 DB 提交
MQ 消息刚发出去就被下游消费了，结果本地 DB 写库报错回滚 👉 没扣上钱，却白送了积分！
❌ 错误 ③：把发 MQ 包在 DB 事务里
发 MQ 网络卡顿 3 秒，导致数据库行锁和连接被白白占住 3 秒（拖垮连接池）；且发完 MQ 后若 DB COMMIT 瞬间断电，消息依然撤不回来！

要彻底解决这个“跨库+跨 MQ”的一致性问题，工业界有两大标准落地武器（面试把这两个一起讲出来直接拉满）：

⚔️ 武器一：RocketMQ 原生事务消息 —— 「两阶段半消息 (Half Message) + 事务状态回查」 核心：先探路暂存，确认后再对消费者可见
Step ①：发送半消息 (Half Msg)
Producer 先发一条半消息给 Broker。Broker 把它转存进内部系统主题 RMQ_SYS_TRANS_HALF_TOPIC，此时对下游消费者完全不可见！
Step ②：执行本地 DB 事务
收到半消息写入成功的 ACK 后（若连半消息都发不出去，直接终止不写库！），Producer 执行 executeLocalTransaction 改本地数据库。
Step ③：二阶段 Commit / Rollback
• 本地事务成功 👉 发 COMMIT，Broker 把半消息搬回真正的目标 Topic，消费者立即可见；
• 本地事务失败 👉 发 ROLLBACK，Broker 写入 Op 删除标记丢弃半消息。
Step ④：超时事务回查（灵魂兜底！）
万一 Step ② 写完库正要发 Step ③ 时机器断电或网络丢包？Broker 定时扫描未决半消息，主动回调生产者组任一实例的 checkLocalTransaction 查 DB 订单状态来补发 Commit/Rollback！
⚔️ 武器二：本地消息表（Transactional Outbox 模式）—— 用的是 Kafka / RabbitMQ 怎么办？ 任何 MQ 通用 · 跨系统最终一致
如果公司用的是不支持半消息回查的 Kafka 或 RabbitMQ，怎么实现同等可靠的事务消息？答案是把“跨系统分布式事务”降维转化为“本地单库事务”：
1. 同库同事务双写：在订单数据库里建一张本地消息表 local_message_outbox (id, topic, payload, status='PENDING', retry_count)。在同一个 MySQL 本地事务里：BEGIN; ① UPDATE 订单已支付; ② INSERT INTO local_message_outbox; COMMIT;（靠 MySQL 自己的 ACID 保证订单与待发消息 100% 同生共死！）。
2. 异步中继投递（Relay / CDC）：事务提交后，由后台定时任务轮询 status='PENDING' 的记录（或者用 Canal / Debezium 实时监听 local_message_outbox 的 Binlog）把消息发往 Kafka；收到 Kafka 的 acks=all 确认后，再把表里状态改为 SENT。
⚠️ 必考误区辨析：事务消息能保证“下游消费者一定消费成功并回滚上游”吗？
不能！事务消息（无论是 RocketMQ 半消息还是本地消息表）属于「最大努力通知 / 最终一致性柔事务」：它 100% 保证的是上游本地事务成功 ⇔ 消息一定可靠发进 MQ。至于下游消费者拿到消息后如果因为 DB 抖动处理失败，绝不会反过来回滚上游已经提交的订单，而是靠下游的消费重试（16次阶梯重试）+ 死信队列人工/自动补偿来达成最终一致！
❓ 05.2 · “用户下单 30 分钟未支付自动关单”为什么不用定时扫全表，而用延迟消息？底层的时间轮是怎么转的？

⏱️ 05.2 延迟 / 定时消息：从 18 级定时队列到分层时间轮（Timing Wheel）

如果每分钟跑一个定时任务去 SELECT * FROM t_order WHERE status='UNPAID' AND create_time < now()-30m 扫千万级订单表，既会打爆数据库 I/O，又有最高 1 分钟的时间误差。更优雅的做法是在下单瞬间发一条「30 分钟后才对消费者可见的延迟消息」，到点精准触发检查关单。三大 MQ 的实现机制与坑点对比如下：

🚀 RocketMQ 延迟消息：4.x 内部 18 级队列 ──▶ 5.0 分层时间轮（任意毫秒级定时） 原生支持 · 最成熟
🕰️ RocketMQ 4.x：18 个固定延迟等级
• 为什么不支持任意时间？如果每条消息过期时间都不同，Broker 就要对千万条消息做全局排序（内存和 CPU 会炸）。
• 巧妙解法：限制只支持 18 个固定档位（1s / 5s / 10s / ... / 30m / 2h）。Broker 收到带 delayLevel=16 (30m) 的消息后，先修改 Topic 暂存进内部系统主题 SCHEDULE_TOPIC_XXXX 的第 16 号队列（同一个队列内延迟时长相同，天然按到达顺序到期！）；后台 Timer 线程按序扫描队列头部，到期后再还原真实 Topic 写回 CommitLog 投递给消费者。
⚙️ RocketMQ 5.0：TimerWheel + TimerLog 时间轮
• 为了支持任意时刻定时消息（如指定明天上午 10:08:23 触发），RocketMQ 5.0 引入了时间轮（Timing Wheel）存储引擎：
• 就像钟表表盘有 3600 个秒针槽位（Slot），每个槽位只存一个指向磁盘 TimerLog 链表头的指针。写入任意定时消息都是 \(O(1)\) 定位槽位 + 顺序追加写 TimerLog；指针每秒走一格，把当前格子里到期的消息链表捞出来投递（若超过一圈则通过多级时间轮或卷动重入），彻底突破了 18 级限制！
🐰 RabbitMQ 延迟消息：警惕「TTL + 死信队列 (DLX)」的必考队头阻塞大坑！ 面试高频踩坑点
• 方式 A（TTL + 死信交换机 DLX）：建一个没有任何消费者监听的普通缓冲队列，给队列或消息设置过期时间 TTL = 30分钟，并绑定死信交换机（x-dead-letter-exchange）。30 分钟后消息过期变成“死信”，被自动路由到真正的关单消费队列。
• ⚠️ 致命陷阱（队头阻塞 Head-of-Line Blocking）：RabbitMQ 只会检查队列最头部（第 1 条）消息是否过期！假如你在同一个队列里先发了一条 TTL = 30分钟 的消息 A，紧接着又发了一条 TTL = 1分钟 的消息 B——1 分钟到点时消息 B 绝对不会触发过期，它会一直被前面的消息 A 死死堵住，直到 30 分钟后跟 A 一起出来！
• ✅ 破局方案：① 要么像 RocketMQ 4.x 一样按固定延迟时长拆分成多个独立队列（30 分钟一个队列，1 分钟一个队列）；② 要么安装官方 rabbitmq_delayed_message_exchange 延迟插件，让消息暂存在交换机的 Mnesia 表中按时投递，不再被队列头部阻塞。
❓ 05.3 · 下游数据库报错导致消费失败时，消息去哪儿了？什么是死信队列（DLQ）与消息回溯？

🛟 05.3 最后一道防线：阶梯退避重试、死信队列（DLQ）与历史回溯重放

当消费者执行业务抛异常时，不能直接把消息扔掉，也不能原地每秒重试一万次把本来就抖动的下游彻底打死。一套成熟的消费容错闭环包含 3 个机制：

① 正常消费失败
返回 RECONSUME_LATER 或抛异常
──发回重试队列──▶
② 阶梯退避重试队列
%RETRY%+消费者组名
(10s → 30s → 1m ... 最多16次)
──超16次仍败──▶
③ 死信队列 (DLQ)
%DLQ%+消费者组名
(告警 + 人工/脚本补偿)

📮 死信队列（Dead Letter Queue）的三大工程价值

  1. 隔离坏消息（防阻塞）：把脏数据、代码 Bug 无法处理的“毒丸消息（Poison Pill）”挪走，绝不卡死正常业务消息的消费流水线。
  2. 兜底防丢失：重试达到上限（如 RocketMQ 默认 16 次，约经历 4 小时 46 分钟）后不丢弃，持久化保存在专属死信 Topic 中。
  3. 可观测与重放修复：线上必须对 %DLQ% 配置监控告警；研发修复 Bug 后，可在控制台一键将死信重发回正常队列。

⏪ 消息回溯（Message Replay / Offset Reset）

与传统队列“消费完立刻物理删除消息”不同，Kafka 和 RocketMQ 消费完消息后文件依然保留在磁盘上，消费只是把游标 Offset 往右挪了一格。
实战威力：如果今天下午上线了一个消费端 Bug，导致下午 2:00～3:00 的积分全算错了，你只需要修好代码，然后通过命令行或控制台把该消费者组的 Offset 重置回下午 2:00 的时间戳（--to-datetime），就能把这 1 小时的历史消息完完整整重跑一遍！
