🤝 02.1 · 分布式事务消息内核：RocketMQ 半消息暂存转发与 Broker 定时状态反查

🤝 02.1 RocketMQ 事务消息：两阶段半消息与反查实现 🔥 常问

🎯 这节回答实战篇哪个问题：对应 实战篇 03.5 下单与发消息的一致性 —— 如果不想在业务 MySQL 里建 outbox_messages 本地消息表，RocketMQ 在 Broker 内部是如何实现「先发消息暂存隐身，等本地数据库提交后再放行」的？

因为磁盘日志一旦写入目标队列被消费者拉走就无法撤回，RocketMQ 采用「狸猫换太子（偷换 Topic 暂存）+ 二阶段确认/定时反查」四步闭环解决了跨库与发消息的原子性问题：

Step ①：发送半消息（隐身暂存）
Producer 发送事务消息给 Broker。Broker 将原目标 Topic 与队列号备份到扩展属性里，把 Topic 改写为内部系统主题 RMQ_SYS_TRANS_HALF_TOPIC 顺序落盘——下游业务消费者没有订阅该内部主题，因此完全不可见。
Step ②：执行本地 DB 事务
收到半消息落盘成功 ACK 后（若连半消息都写不进 MQ，直接放弃不改数据库），Producer 回调本地 executeLocalTransaction 执行数据库订单扣款事务。
Step ③：Commit / Rollback
• 本地事务提交成功 👉 发 COMMIT：Broker 从半消息主题读出原消息，恢复真实业务 Topic 重新追加写入 CommitLog（消费者立即可见），并向 RMQ_SYS_TRANS_OP_HALF_TOPIC 写一条 d 删除标记。
• 本地事务回滚 👉 发 ROLLBACK：只写 d 删除标记丢弃半消息。
Step ④：超时事务状态反查
万一 Step ② 刚提交完数据库就断电、没发出 Step ③ 怎么办？Broker 后台定时对比半消息表与 Op 标记表，挑出超时未决的半消息，主动向同一生产者组任一存活实例发起 checkLocalTransaction 反查数据库真实订单状态补齐 Commit 或 Rollback（默认最多反查 15 次）。
📄 附：RocketMQ 事务消息生产者回调接口参考代码（Java SDK 标准形态）
☕ RocketMQTxDemo.java · executeLocalTransaction 与 checkLocalTransaction 接口闭环 
TransactionMQProducer txProducer = new TransactionMQProducer("tx-order-producer-grp");
txProducer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderRepo.markPaidInDB(msg.getKeys());        // Step ②：改本地 MySQL
            return LocalTransactionState.COMMIT_MESSAGE;  // Step ③：通知转正
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // Step ④：网络闪断未收到二阶段指令时，Broker 回调此方法查 DB 订单状态兜底
        return orderRepo.isOrderPaid(msg.getKeys())
            ? LocalTransactionState.COMMIT_MESSAGE : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});
⏱️ 02.2 · 定时引擎内核：从 18 个固定延迟等级队列到分层时间轮（Timing Wheel）

⏱️ 02.2 延迟消息底层是如何避免百万消息全局排序的 🔬 深挖

🎯 这节回答实战篇哪个问题：对应 实战篇 03.6 延迟任务 —— 如果每秒涌入上万笔任意时刻到期的定时消息，直接塞进小顶堆（O(log N)）或数据库排序会把内存与磁盘随机 I/O 拖垮，现代 MQ 内部是怎么做到 O(1) 写入与准点触发的？

① 一代方案：RocketMQ 4.x 的 18 级固定队列

为了规避全局排序，4.x 硬性规定只开放 18 个固定延迟档位（1s / 5s / 10s / 30s / 1m ... 30m / 2h），在内部主题 SCHEDULE_TOPIC_XXXX 下建 18 个独立队列。
• 为什么不用排序？因为进入第 16 号队列的所有消息延迟时长全都是固定的 30 分钟——先写进去的一定先到期！后台每个队列只需配 1 个定时任务顺序盯住队列头部，到期后还原真实 Topic 写回 CommitLog 即可。
• 局限：不支持自定义任意时刻（如“明天上午 9:17:00 准时开售通知”）。

② 二代方案：RocketMQ 5.0 TimerWheel + TimerLog 时间轮

时间轮（Timing Wheel，同样用于 Kafka 内部 Purgatory 超时管理与 Netty 定时器）把时间映射成一个环形钟表数组：
• 表盘固定划分如 7200 个秒级槽位（Slot，定长数组常驻内存），每个槽位只存一个指向磁盘追加文件 TimerLog 最新一条记录的尾指针。
• 写入 O(1) 且纯顺序 I/O：收到 30 分钟后到期的消息，直接算出目标槽位下标，在 TimerLog 末尾顺序追加一条记录（内含指向上一条同槽记录的物理偏移指针，构成磁盘单向链表），再更新槽位头指针。
• 触发与跨圈滚动：后台秒针每秒往前走一格，顺着当前槽位的指针链把该秒所有到期消息捞出来投递（超出单圈跨度的长延迟消息在到期扫描时减去一圈时长重新挂入下层槽位，即分层/卷动时间轮）。
