00.1 · 消费通信模型：Push 主动推送与 Pull 主动拉取的权衡及长轮询机制

00.1 为什么 Kafka 与 RocketMQ 都选了「Pull + 长轮询」 常问

这节回答实战篇哪个问题：对应 实战篇 02.4 动手实验 与 03.2 秒杀削峰 —— 为什么消费者平时阻塞等待几乎不占 CPU，新消息一写入却能毫秒级收到，而且秒杀洪峰灌入百万条消息时消费者也不会被冲垮？

Broker 把队列里的消息交给消费者，在网络协议层只有服务端主动推（Push）和客户端主动拉（Pull）两条路线，两者各有天然优劣：

分发模式 核心优势 固有短板 主流中间件的工程改进方案
Push 模式
（Broker 主动推）		 端到端延迟极低：Broker 一收到消息立刻通过长连接推送给消费者，可达微秒级响应。 缺乏天然背压（Backpressure），易压垮慢消费者：Broker 不清楚下游数据库能不能扛住，大促洪峰来时全速推送会直接把消费者内存打爆（OOM）。 RabbitMQ 采用 Push，但必须搭配 basicQos(prefetchCount=N) 滑动窗口限流：消费者手上未确认（Unacked）的消息达到 N 条时，Broker 暂停向它推送。
Pull 模式
（Consumer 主动拉）		 消费速率完全自主可控：消费者处理完一批再去拉下一批（也方便在拉取后做批量落库），天然适应削峰场景。 朴素轮询的两难：队列为空时若死循环发起请求会白白空耗 CPU 与网卡；若每次固定休眠 2 秒再拉又会平白引入最高 2 秒延迟。 Kafka 与 RocketMQ 采用 Pull + 长轮询（Long Polling），同时消除空转开销与休眠延迟。

长轮询（Long Polling）在 Broker 内部是如何工作的？

  1. 有足够数据时立即返回：消费者携带目标分区的起始 Offset、最小期望字节数 fetch.min.bytes（默认 1 Byte）与最大等待时间 fetch.max.wait.ms（默认 500ms）发送 FetchRequest；若当前分区已有可读新消息，Broker 直接通过零拷贝立即返回。
  2. 无新数据时挂起进时间轮（不空转、不占工作线程）：若当前分区没有新消息，Broker 不会立即返回空包，而是将该拉取请求封装进内部的延迟操作池（Kafka 中称为 Purgatory 炼狱组件，底层基于分层时间轮）挂起等待。
  3. 双条件唤醒：① 只要在 500ms 窗口内生产者往该分区写入了新消息并推进了高水位 HW，Broker 立刻唤醒挂起的请求毫秒级返回数据；② 若等满 500ms 仍无新消息，才返回空响应让客户端发起下一轮长轮询。
00.2 · 消费协议演进：SDK 回调式“伪 Push”封装与 RocketMQ 5.0 无状态 Pop 模式

00.2 为什么叫 PushConsumer 底层却是 Pull，以及 Pop 模式演进 深挖

这节回答实战篇哪个问题：对应 实战篇 01.2 消费者数 ≤ 分区数 与 06.3 选型表 —— 传统分区独占绑定有什么局限，为什么新一代云原生 MQ 引入了无状态 Pop 消费？

  • 客户端“伪 Push”语法糖：在 RocketMQ 中最常用的类名叫 DefaultMQPushConsumer（Node.js kafkajs 的 consumer.run({ eachMessage }) 同理），它并不是 Broker 主动推，而是客户端 SDK 在后台起了一个循环长轮询线程拉回消息后，自动回调你注册的处理函数——对业务开发者保留了事件驱动的易用体验，底层依然保有 Pull 的流控安全性。
  • 传统 Pull 分区独占模型的痛点：在经典 Kafka / RocketMQ 4.x 中，1 个分区固定绑定给组内唯一个消费者实例。万一某台消费者机器出现亚健康（如磁盘 I/O 夯住但心跳线程还活着没断开），它名下的分区就会彻底停滞积压，组内其他空闲健康的消费者完全帮不上忙；而且消费者实例数受死于分区数上限。
  • RocketMQ 5.0 无状态 Pop 消费（及 Kafka KIP-932 Share Groups 共享组方向）：消费者不再与具体队列死死绑定，任何空闲消费者都可以向 Broker 发 Pop 请求领取任意队列的消息；Broker 发消息的同时为该条消息设置一段不可见时间（InvisibleTime，类似可见性租约）——超时未收到 Ack 则自动恢复可见交由其他健康实例重试。这样彻底解除了「消费者数 ≤ 分区数」限制，也消除了客户端重平衡停顿。
