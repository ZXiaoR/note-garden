03.1 · 百万吞吐内核：顺序追加写、OS PageCache 与 sendfile / mmap 零拷贝机制

03.1 为什么消息全写进磁盘，单机还能扛百万级 TPS 常问

这节回答实战篇哪个问题：对应 实战篇 03.3 日志与埋点高吞吐采集 与 03.1 多消费组读取 —— 为什么写磁盘的 Kafka 比很多纯内存队列吞吐还要高？sendfile 零拷贝到底省掉了哪几次拷贝？

机械硬盘或固态硬盘真正慢的是随机寻道读写；一旦改成纯文件末尾顺序追加写（Sequential Append-Only），现代磁盘顺序吞吐可达数百 MB/s 至数 GB/s。Kafka 围绕操作系统内核构建了五环相扣的加速链路：

  1. 磁盘顺序追加写：每个分区文件只允许在末尾追加，绝不原地修改已写入字节，将随机 I/O 彻底转化为 O(1) 顺序追加。
  2. 借力操作系统 PageCache（内核页缓存）：不在 JVM（Java Virtual Machine，Java 虚拟机）堆内存里自建大对象缓存，避免对象头内存膨胀与 Full GC（Garbage Collection，垃圾回收）长停顿；写入直接进内核页缓存由操作系统后台刷盘，实时追尾的消费者读取时接近 100% 直接命中内存页缓存，且 Broker 进程重启页缓存不丢失。
  3. 端到端整批压缩透传：Producer 将几百条消息打包成一个压缩的 RecordBatch，Broker 无需解压原样校验落盘，Consumer 整批拉回后再在客户端解压，单次系统调用与网络开销摊薄上百倍。
  4. 多分区水平并行：不同分区的 Leader 分布在不同 Broker 节点与磁盘上并行读写。
  5. sendfile 零拷贝（Zero-Copy）网络发送：消除内核态与用户态之间无意义的来回搬运。

进阶辨析：既然 sendfile 比 mmap 少一次 CPU 拷贝，为什么 RocketMQ 选了 mmap？

系统调用 切换与拷贝开销 核心差异与 Kafka / RocketMQ 选型原因
sendfile
（Kafka 消费读取）		 2 次切换 + 0 次 CPU 拷贝
（PageCache 直达网卡）		 sendfile(out_fd, in_fd, offset, count) 在内核里直接把字节流推向网卡，只向用户态返回发送了多少字节（整数），应用层代码完全拿不到消息内容。Kafka 分区文件存的就是目标 Topic 的原始批次，无需在服务端解析过滤，原样吐给网卡最快（注：若开启 TLS/SSL 加密，因需在用户态加密，sendfile 会自动退化回常规读取）。
mmap + write
（RocketMQ 读写）		 4 次切换 + 1 次 CPU 拷贝
（PageCache → Socket 缓冲）		 mmap（Memory Map，内存映射文件）把内核 PageCache 直接映射到用户态虚拟地址空间，Broker 代码可以在用户态直接读取消息头属性、执行服务端 SQL92/Tag 过滤、做内存页预热（Warmup）与锁页（mlock）。RocketMQ 所有 Topic 混写在定长 1 GB CommitLog 中且需要服务端解析消息逻辑，因此 mmap 更契合。
03.2 · 磁盘文件布局对比：Kafka 分区 Segment 稀疏索引 vs RocketMQ 单一 CommitLog

03.2 两大存储文件结构对比与万级 Topic 权衡 深挖

这节回答实战篇哪个问题：对应 实战篇 06.1 / 06.3 选型表 与 07.1 分区规划 —— 磁盘上的消息文件到底长什么样？为什么单集群建几千个 Topic 时 Kafka 吞吐会明显下降而 RocketMQ 依然平稳？

一、Kafka：每个 Partition 独立目录 + 稀疏索引

每个分区拆成多个默认 1 GB 的日志段（Segment），文件名就是该段第 1 条消息的起始 Offset（如 00000000000000368769.log），配套 .index（偏移量稀疏索引）与 .timeindex（时间戳索引）。

• 查 offset=368800 三步定位：① 按 Segment 文件名二分锁定所属段；② 在 mmap 映射的 .index 稀疏索引（每写满 4 KB 消息才建一条索引项，极省内存）中二分找到最近的小于等于该 Offset 的物理字节位置；③ 从该位置往后顺序扫几 KB 即命中目标。
• 短板：当 Broker 上同时有几千个活跃分区文件并发追加写时，在底层同一块物理磁盘上会交错退化为实质上的随机写。

二、RocketMQ：单一 CommitLog + 20B ConsumeQueue

整台 Broker 上所有 Topic、所有队列的消息全部混写进唯一一个 CommitLog 日志流（每文件定长 1 GB），再由后台 ReputMessageService 异步分发构建每个消费队列的轻量目录文件 ConsumeQueue（外加按业务 Key 哈希查询的 IndexFile）。

• 定长 20 字节索引设计：ConsumeQueue 每条记录严格固定 20 Bytes = [8B CommitLog物理偏移 + 4B 消息长度 + 8B Tag哈希码]。消费者先在全驻留页缓存的 20B 索引里匹配 8 字节 Tag 哈希，命中后再按 8B 地址去 CommitLog 读取消息体。
• 收益与代价：哪怕建 10,000 个 Topic 写入也永远是单文件纯顺序写；代价是消费变成“先读索引再读数据”的两跳读取，且无法直接使用 sendfile。
