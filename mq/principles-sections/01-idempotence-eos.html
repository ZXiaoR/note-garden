⚙️ 01.1 PID + Sequence Number 是如何实现单分区判重与防乱序的 🔥 常问

🎯 这节回答实战篇哪个问题：对应 实战篇 04.3 幂等生产者结论 —— 开启 enable.idempotence=true 后，Broker 底层究竟靠什么数据结构拦住网络重发包，又为什么它允许单连接同时在途发送 5 个批次却绝不乱序？

消息传递共有三种标准语义：At-most-once（最多一次，发后不管可丢不重）、At-least-once（至少一次，超时重发不丢但可重）、Exactly-once（精确一次，不丢不重）。在网络抖动导致 Broker 已写盘但返回的确认包半路丢失时，Producer 超时重发就会在分区里写出两条重复记录。Kafka 0.11+ 引入并在 3.0+ 默认开启的幂等生产者，用极轻量的两级编号消除了这一层重复：

  1. 初始化分配 PID（Producer ID，生产者唯一标识）：每个开启幂等的 Producer 实例启动连接时，向 Broker 申请一个全局唯一递增的 64 位整数 PID（对业务代码完全透明）。
  2. 按分区维护单调递增 Sequence Number（批次序列号）：Producer 在内存中为发往每一个 (Topic, Partition) 的消息批次（RecordBatch）附带一个从 0 开始严格加 1 递增的 32 位整数 Seq。
  3. Broker 端 5 槽位滑动窗口校验：Leader 副本在内存（并随快照持久化）为每个 (PID, Partition) 缓存最近收到的 5 个批次序列号状态，设上一批成功写入的最大序号为 LastSeq：
    • 当新到达批次的 Seq == LastSeq + 1 👉 严格连续，正常追加写入日志并更新 LastSeq；
    • 当新到达批次的 Seq <= LastSeq（且命中最近 5 个批次窗口） 👉 说明这是因 ACK 丢包触发的网络重发旧包，Broker 直接静默丢弃数据，但向 Producer 返回写入成功响应，从而消除重复落盘；
    • 当新到达批次的 Seq > LastSeq + 1 👉 说明前序批次尚未到达（发生了管道超车乱序），Broker 直接拒绝并返回 OutOfOrderSequenceException 触发客户端按序重排重发——这就解释了为什么只要满足 max.in.flight.requests.per.connection <= 5，即使开启异步管道并发也能保证分区内严格有序。
🚫 再次明确它的物理边界（面试高频追问点）：
由于 PID 是进程级临时身份且没有跨会话持久化绑定业务数据：① Producer 容器重启后会领到全新的 PID，旧会话未决重发无法跨重启去重；② 同一条消息发往不同分区各自独立编号，不防跨分区重复；③ 上游代码逻辑 Bug 调用两次 send() 会被分配 Seq=1 和 Seq=2 视为两条合法新消息。因此消费端修改外部数据库时，实战篇 04.2 的业务幂等 永远不可省略。
🔬 01.2 · 流处理精确一次（EOS）：TransactionCoordinator 两阶段提交与 LSO 隔离水位

🔬 01.2 跨分区事务与流计算 EOS 的底层两阶段提交 🔬 深挖

🎯 这节回答实战篇哪个问题：对应 实战篇 04.3 结论 ② —— 在 Flink / Kafka Streams「从 Topic A 读 → 计算 → 写回 Topic B / C」场景下，Kafka 是怎么跨越多个分区做到「消费进度提交」与「多分区结果写入」同生共死的？

  1. 静态绑定 transactional.id 与递增纪元 producer_epoch（防僵尸实例）：开发者显式配置固定的 transactional.id。当旧实例假死卡顿、新实例用相同 transactional.id 启动时，服务端 TransactionCoordinator（事务协调器） 会把它的 epoch 加 1——旧僵尸实例恢复后再发来的任何写入请求都会因 epoch 过期被直接围栏拦截（Fencing）。
  2. 日志先原样落盘，靠控制标记（Control Marker）决定可见性：事务开启后，Producer 写往多个目标分区的数据以及提交给 __consumer_offsets 的消费位点，其实已经直接追加写进了各自的分区日志文件，只是还处于“未决事务”状态。
  3. 两阶段提交写 COMMIT / ABORT 标记：调用 commitTransaction() 时，TransactionCoordinator 先在内部事务日志 __transaction_state 持久化写入 PREPARE_COMMIT，随后向本次涉及的所有分区追加写入一条特殊的控制记录（COMMIT 或 ABORT Marker），全部写完后标记事务完成。
  4. 消费端 read_committed 与 LSO（Last Stable Offset，最后稳定偏移量）：配置了 isolation.level = read_committed 的下游消费者，最多只能读到 LSO（即分区内最早一条尚未完结事务的起始位置，LSO <= HW）之前的消息，并自动在客户端过滤掉带有 ABORT 标记的已回滚批次。
