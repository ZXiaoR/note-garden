01 超时治理底层：HTTP 四阶段拆分、预算递减与流式 IdleReader 实现 PILLAR 01 · TIMEOUT

在 Go 标准库中，http.Client{Timeout: 15 * time.Second} 控制的是从发起 DNS 解析到整个响应 Body 全部读完的总耗时。这个配置对普通 JSON 短接口很方便，但一碰到 SSE 流式生成就会引发矛盾：设 15 秒会把正常输出 40 秒的长篇代码截断；设 120 秒又会导致目标节点死机时连接白白挂起两分钟。正确的做法是把总超时设为 0，拆分为底层 Transport 阶段超时 + 流式滚动空闲超时。

FIG 1.0 · CALL-CHAIN DEADLINE PROPAGATION & STREAMING TTFT / IDLE WINDOWS

四个必须分清的底层超时与预算取小原则

  • NetDialer.Timeout（1~2s）：三次握手建连上限。若目标机器宕机或防火墙丢包，2 秒立刻失败，绝不等内核默认 75~127 秒。
  • TLSHandshakeTimeout（2~3s）：防止对端 TCP 通但进程假死卡在 TLS 握手。
  • ResponseHeaderTimeout（10~15s）：请求发完到收到 HTTP 200 OK 响应头的上限——在 SSE 场景下，如果服务端收到上游首 Token 才刷出 Header，它天然就是首字超时（TTFT Timeout）。
  • 局部上限与父预算取小：调 MySQL 时写 dbCtx, cancel := context.WithTimeout(reqCtx, 500*time.Millisecond)。Go 的 WithTimeout 内部会自动取 min(父 reqCtx 剩余时间, 500ms)——既防止慢 SQL 吃光整条链路的 5 秒预算，又保证上游一旦超时取消，下游 SQL 立刻跟着中止。

// 2. 包装 resp.Body：每读到一块数据就往后顺延 15s，半途卡死立刻触发 cancel
type idleTimeoutReader struct {
    rc          io.ReadCloser
    idleTimeout time.Duration
    timer       *time.Timer
}

func WrapIdleTimeout(ctx context.Context, cancel context.CancelFunc, rc io.ReadCloser, idle time.Duration) io.ReadCloser {
    r := &idleTimeoutReader{rc: rc, idleTimeout: idle}
    r.timer = time.AfterFunc(idle, cancel) // 连续 idle 无数据则取消请求 Context
    return r
}

func (r *idleTimeoutReader) Read(p []byte) (int, error) {
    r.timer.Reset(r.idleTimeout) // 每次进入读取重置空闲窗口
    n, err := r.rc.Read(p)
    if n > 0 {
        r.timer.Reset(r.idleTimeout)
    }
    return n, err
}

func (r *idleTimeoutReader) Close() error {
    r.timer.Stop()
    return r.rc.Close()
}
02 重试治理：级联放大效应、剩余预算预判与 Retry Budget 控制 PILLAR 02 & 03

很多故障复盘报告里都会出现同一个场景：下游数据库或模型网关只是短暂抖动了 3 秒，结果监控看到流量瞬间暴涨几十倍直接把下游彻底打死——根源就是多层嵌套重试 + 无抖动同步重发 + 不看剩余超时盲目重试。

生产级重试必须同时满足的 4 个硬条件

  1. 单层收敛原则：5 层调用链如果每层都配“失败重试 2 次（共执行 3 次）”，最底层承受的流量是 35 = 243 倍。规范要求只在最贴近外部依赖的客户端做重试，网关与上游业务层通过响应头识别并禁止二次重试。
  2. 剩余时间预判（Deadline Check）：如果父 Context 只剩 400ms 就超时了，而退避等待计算出来要 sleep(900ms)，此时睡眠毫无意义，应直接放弃重试立即返回错误。
  3. 进程级重试预算（Retry Budget）：参考 Google SRE 做法，维护一个滑动比率计数器，限制重试请求总量不得超过正常请求量的 10%。当下游全面宕机时，重试配额迅速耗尽，自动退化为“每请求只试 1 次”，从数学上杜绝重试风暴。
  4. 写操作强制绑定幂等键：重试发送的是完全相同的 Idempotency-Key（详见 幂等状态机实现）。
Go · 遵守 Retry-After + 剩余时间预判 + 重试预算 
func DoWithBudgetRetry(ctx context.Context, budget *TokenBucket, fn func() (*http.Response, error)) (*http.Response, error) {
    budget.Deposit(0.1) // 每 10 个正常请求存入 1 个重试额度（上限 10% 重试率）
    for attempt := 0; attempt < 3; attempt++ {
        resp, err := fn()
        if err == nil && resp.StatusCode < 500 && resp.StatusCode != 429 {
            return resp, nil // 成功，或 400/401/403 客户端错误直接原样返回，绝不重试
        }
        if attempt == 2 || !budget.TryWithdraw(1.0) {
            return resp, err // 已达最大次数，或全局 10% 重试预算已耗尽，停止放大
        }
        wait := parseRetryAfterOrFullJitter(resp, attempt) // 优先读 Retry-After，否则 rand(0, 500ms*2^attempt)
        if dl, ok := ctx.Deadline(); ok && time.Until(dl) <= wait {
            return resp, context.DeadlineExceeded // 剩余时间连退避等待都不够，立刻放弃
        }
        select {
        case <-time.After(wait):
        case <-ctx.Done():
            return nil, ctx.Err()
        }
    }
    return nil, errors.New("unreachable")
}

04 分布式限流实现：四大算法取舍与 Redis Lua 预扣结算式 TPM 令牌桶 PILLAR 05 · RATE LIMIT

四大限流算法里：固定窗口在整分交界处有 2 倍突发毛刺；滑动窗口（Redis ZSET）适合低频高精度防刷（如每手机号每小时 5 条短信），但高 QPS 下每个请求存一条成员太占内存；漏桶强行匀速流出，不支持突发；因此网关与 AI 配额最常用的是令牌桶（Token Bucket）——在 Redis 里只需存 tokens（当前余量）和 last_ms（上次补充时间戳）两个数字，空间复杂度恒为 O(1)。

AI 场景的工程难点：请求发出去之前，只知道输入大概占多少 Token，不知道模型最终会吐多少输出 Token。如果等生成完再扣，10 个并发大请求已经把供应商配额打穿了；因此生产中采用「请求前按预估上限原子预扣（Reserve）→ 流结束后按真实 usage 多退少补（Reconcile）」两阶段 Lua 脚本：

Redis Lua · 支持 TPM 预扣与结算退还的原子令牌桶 
-- KEYS[1]: rate:tpm:{tenant_id}
-- ARGV[1]: capacity (桶最大容量, 如 60000 Token)
-- ARGV[2]: refill_per_ms (每毫秒补充速率, 如 60000/60000 = 1.0 Token/ms)
-- ARGV[3]: now_ms (当前毫秒时间戳, 建议用 redis.call('TIME') 统一时钟防多机时钟漂移)
-- ARGV[4]: delta_tokens (正数表示请求前预扣, 负数表示流结束后退还多扣的差额)

local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now_ms   = tonumber(ARGV[3])
local delta    = tonumber(ARGV[4])

local data = redis.call('HMGET', KEYS[1], 'tokens', 'last_ms')
local tokens  = tonumber(data[1]) or capacity
local last_ms = tonumber(data[2]) or now_ms

-- 1. 惰性补充：按距离上次访问流逝的毫秒数补满令牌（不超桶上限）
local elapsed = math.max(0, now_ms - last_ms)
tokens = math.min(capacity, tokens + elapsed * rate)

-- 2. 结算阶段（delta < 0，例如预扣了 4000，实际只用了 1200，传入 -2800 退回桶内）
if delta <= 0 then
  tokens = math.min(capacity, tokens - delta)
  redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_ms', now_ms)
  redis.call('PEXPIRE', KEYS[1], 120000)
  return {1, math.floor(tokens), 0}
end

-- 3. 预扣阶段（delta > 0）：余额不足时精确算出还差多少毫秒能攒够，供外层填 Retry-After 响应头
if tokens < delta then
  local retry_after_ms = math.ceil((delta - tokens) / rate)
  redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_ms', now_ms)
  return {0, math.floor(tokens), retry_after_ms} -- 外层收到 0 返回 HTTP 429 + Retry-After
end

tokens = tokens - delta
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_ms', now_ms)
redis.call('PEXPIRE', KEYS[1], 120000)
return {1, math.floor(tokens), 0}
05 零停机发布：Expand-Contract 双写演进实例与 SSE 双信号排水机制 ZERO-DOWNTIME P0

滚动发版（Rolling Update）期间，集群里会同时跑着 旧版 Pod v1 和 新版 Pod v2，且它们读写的是同一个数据库。如果直接执行 ALTER TABLE orders CHANGE store_id origin_store_id BIGINT，发版瞬间仍在运行的 v1 Pod 执行 SELECT store_id 会立刻全部报 Unknown column 故障，而且一旦 v2 有 Bug 想回滚，数据库已经被改名了根本退不回去。

Go · 解决 http.Server.Shutdown 不通知 SSE 长连接的双信号优雅排水实现 
// 关键底层机制：Go 标准库的 srv.Shutdown(ctx) 只会关闭 Listener 停止接新单，
// 并【不会】主动取消正在运行的请求 r.Context()！如果 SSE 流要跑 90s，而 K8s terminationGracePeriodSeconds=45s，
// 傻等就会在第 45s 被 SIGKILL 硬杀。正确做法是用 drainCh 广播“即将停机”，让 SSE 在安全边界主动发送重连帧并落盘断点。

var (
    isReady = atomic.Bool{}
    drainCh = make(chan struct{}) // close(drainCh) 会瞬间唤醒所有在线的 SSE Handler
)

func SSEHandler(w http.ResponseWriter, r *http.Request) {
    flusher := w.(http.Flusher)
    seq := 0
    for {
        select {
        case <-r.Context().Done():
            return // 客户端自己点了停止
        case <-drainCh:
            // 收到发版停机广播：把已生成进度刷盘，并通知前端带 Last-Event-ID 无缝重连到新 Pod
            fmt.Fprintf(w, "id: %d\nevent: reconnect\ndata: {\"offset\":%d}\n\n", seq, seq)
            flusher.Flush()
            return
        case tok, ok := <-streamCh:
            if !ok {
                return
            }
            seq++
            fmt.Fprintf(w, "id: %d\nevent: delta\ndata: %s\n\n", seq, tok)
            flusher.Flush()
        }
    }
}

// 停机编排顺序（对应 K8s terminationGracePeriodSeconds: 45）
func GracefulShutdown(srv *http.Server) {
    isReady.Store(false)        // Step 1 (T+0s): /readyz 返 503，K8s Endpoints 摘除本 Pod
    time.Sleep(5 * time.Second) // Step 2 (T+5s): 等待 kube-proxy / Ingress 路由表同步完毕，不再有在途新连接
    close(drainCh)              // Step 3 (T+5s): 通知长连接 SSE 发送 reconnect 事件优雅交接
    ctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
    defer cancel()
    _ = srv.Shutdown(ctx)       // Step 4 (T+30s 内): 等待剩余短事务 HTTP 请求与后台 Worker 全部收尾退出
}
06 业务安全代码防线：ORM 强制租户隔离与 Dialer.Control 防 SSRF 绕过 SECURITY P0

安全防线如果写成“代码规范要求大家记得校验门店 ID、记得拦截 `127.0.0.1`”，上线后一定会被漏掉或绕过：新同事写个根据主键查详情的接口忘了带 `store_id` 就是水平越权（IDOR）；攻击者注册一个域名先解析到公网 IP 骗过 URL 检查、1 秒后把 DNS 改回 `169.254.169.254`（DNS Rebinding 重绑定攻击）或用十进制整数 `http://2130706433/` 就能轻松绕过字符串黑名单。两类问题都必须沉到框架底层强制拦截：

🪪 防 IDOR · GORM 全局插件强制注入 store_id 
// 注册到 GORM Query / Update / Delete 生命周期：
// 业务写 db.WithContext(ctx).First(&order, 10087) 时，

func enforceTenantCallback(db *gorm.DB) {
    if db.Statement.Schema == nil {
        return
    }
    if _, hasStore := db.Statement.Schema.FieldsByDBName["store_id"]; !hasStore {
        return // 系统全局字典表跳过

    storeID, ok := StoreIDFromContext(db.Statement.Context)

        return
    }
    db.Statement.AddClause(clause.Where{
        Exprs: []clause.Expression{clause.Eq{
            Column: clause.Column{Table: clause.CurrentTable, Name: "store_id"},
            Value:  storeID,
        }},
    })
}

07 SLO 错误预算告警与「接口自检三问」代码改造对比 PILLAR 07 & CASE STUDY

1. 为什么看 P99 与错误预算燃烧率，不看平均值与 CPU

• 平均值的欺骗性：99 个请求耗时 10ms，1 个请求死锁卡满 10,000ms，算出来的平均耗时只有 110ms 看似极快，但实际上每 100 次点击就有 1 次卡死（若一个页面调 5 个接口，用户遇到卡死的概率高达 1 − 0.995 ≈ 4.9%），只有 p95 / p99 能暴露长尾故障。
• 错误预算与燃烧率（Burn Rate）告警：若月度 SLO 为 99.9%，意味着一个月允许 43.2 分钟故障预算。如果当前 1 小时内的错误率速度会在 3 小时内烧光整月预算（燃烧率 > 14.4x），才触发电话/短信强告警；单机 CPU 短暂冲到 85% 但请求延迟与成功率完全正常时只记工单不半夜叫人，避免“狼来了”告警疲劳。

2. 写完任何写接口后的「自检三问」

  1. 同一请求重复来两次会怎样？
    （网络超时重试或连点 → 查唯一幂等键与结果重放）
  2. 两个人同一毫秒并发来会怎样？
    （先查再改必超卖 → 查原子条件更新 WHERE remain >= 1 或锁）

func RedeemCardBad(ctx context.Context, req RedeemReq) error {
    // 漏洞 3 (越权): 直接用前端传的 CardID 查，B 店员能核销 A 店顾客的卡！
    var card MemberCard
    db.First(&card, req.CardID)
    if card.RemainTimes < 1 {
        return ErrInsufficientTimes
    }
    // 漏洞 2 (并发超卖): 先读到内存减 1 再写回，两个并发请求同时读到 1，扣完剩 0 却核销了两次！
    // 漏洞 1 (无幂等): 网关超时重试一次，直接多扣顾客一次卡！
    card.RemainTimes -= 1
    db.Save(&card)
    // 致命隐患: 若事务里还顺手调了缓慢的发微信通知 HTTP 接口，长事务直接锁死行并耗尽连接池
    wechat.SendNotify(card.UserOpenID)
    return nil
}
改造后：三问全过的生产级「次卡核销」代码 
func RedeemCardProd(ctx context.Context, storeID int64, idemKey string, cardID int64) error {
    // 事务内只做极快的纯内存/DB 原子操作，严禁夹杂外部 RPC / LLM 调用！
    return db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // 1. 过第一问 (幂等): 插入带 uk(store_id, idem_key) 唯一索引的核销流水与 Outbox 消息
        logRow := RedeemLog{StoreID: storeID, IdemKey: idemKey, CardID: cardID}
        if err := tx.Create(&logRow).Error; isDuplicateKey(err) {
            return nil // 重试请求命中唯一索引，幂等返回成功
        } else if err != nil {
            return err
        }
        // 2. 过第二、三问 (防并发超卖 + 防越权): 单条原子 SQL 同时校验 store_id 与 remain_times >= 1
        res := tx.Model(&MemberCard{}).
            Where("id = ? AND store_id = ? AND remain_times >= 1", cardID, storeID).
            UpdateColumn("remain_times", gorm.Expr("remain_times - 1"))
        if res.Error != nil {
            return res.Error
        }
        if res.RowsAffected == 0 {
            return ErrInsufficientOrForbidden // 触发事务回滚，上面插入的流水自动撤销
        }
        // 3. 异步通知走同事务 Outbox 表，事务提交后由后台 Worker 投递微信通知
        return tx.Create(&OutboxEvent{Topic: "card.redeemed", BizID: logRow.ID}).Error
    })
}
