05.1 · 客户端存储选型：Cookie、localStorage、sessionStorage 与 IndexedDB 对比

05.1 浏览器四大本地存储方式对比与使用示例

网页经常需要在用户电脑本地保存一些数据，例如深色模式主题偏好、未提交的表单草稿或登录会话标识。浏览器提供了四种主要的客户端存储机制，它们在容量、过期生命周期以及是否随网络请求自动发送上各有分工：

存储机制 典型容量上限 数据生命周期 是否随每次 HTTP 请求自动发送？ 日常工程适用场景
Cookie 约 4 KB 可通过 Max-Age / Expires 设置过期时间；未设置则关闭浏览器后失效 是（自动放入 Cookie 请求头） 仅用于存放服务端需要识别的小体积会话标识（如 session_id）。切勿塞入大量业务数据以免拖慢每次接口请求。
localStorage 约 5 MB（按源隔离） 永久保存（除非代码主动调用 removeItem 或用户手动清理浏览器数据） 否（仅保留在本地） 保存跨会话持久化的前端配置，如深色/浅色主题设置、手账桌面材质偏好、搜索历史记录。
sessionStorage 约 5 MB（按标签页隔离） 当前标签页有效（刷新页面仍保留，但一旦关闭该标签页即自动清空） 否（仅保留在本地） 保存单次流程中的分步表单草稿、列表页滚动条位置或临时筛选条件。
IndexedDB 数百 MB 乃至数 GB（视磁盘剩余空间） 永久保存（异步事务型对象数据库，支持索引查询与二进制 Blob） 否（仅保留在本地） 在线文档离线编辑缓存、海量聊天记录本地检索、大体积富媒体资源离线包。
storage_helper.js · 使用 localStorage 安全存取 JSON 对象（注意它只支持存字符串） 
// 注意：localStorage 和 sessionStorage 的键值都只能是字符串！
// 存入 JavaScript 对象前需用 JSON.stringify 转为字符串；读取时需用 JSON.parse 还原
const userPrefs = { theme: 'poster', fontSize: 15 };
localStorage.setItem('garden_prefs', JSON.stringify(userPrefs));

// 读取并加上 try...catch 防御用户手动篡改本地存储导致的解析报错
function loadPrefs() {
  try {
    const raw = localStorage.getItem('garden_prefs');
    return raw ? JSON.parse(raw) : { theme: 'mat', fontSize: 14 };
  } catch (e) {
    return { theme: 'mat', fontSize: 14 };
  }
}
05.2 · 静态资源缓存规范：为什么带哈希的 JS/CSS 配一年强缓存，而 index.html 配每次验证？

05.2 生产环境 HTTP 缓存最佳实践

当网站部署上线后，我们既希望用户的浏览器尽可能复用已下载过的 CSS、JS 和图片以实现秒开，又希望当我们发布新版本代码时用户不会因为旧缓存而一直看到老页面。现代前端工程通过「文件名内容哈希 + 差异化 Cache-Control 响应头」完美兼顾这两点：

入口文档 · index.html Cache-Control: no-cache
允许本地缓存，但每次使用前向服务器做 ETag 验证

注意：no-cache 的真正含义不是“不缓存”，而是“每次复用缓存前必须带 If-None-Match 询问服务器文件有没有变”。若未发版则服务端返回极轻量的 304 Not Modified；一旦发版则立刻返回最新 HTML。

带指纹静态文件 · app.8f3a1c.js max-age=31536000, immutable
直接强缓存一年，期间连验证请求都不必发

打包工具会根据文件内容计算出哈希指纹（如 8f3a1c）。只要代码没改，文件名就不变，浏览器直接从本地秒读；一旦代码修改，打包后会生成新文件名 app.9b2d4e.js，由最新的 index.html 引入。

05.3 · 跨域联调排障：同源判定规则（协议 + 主机 + 端口）与两种标准跨域解决方案

05.3 什么是同源策略？遇到 CORS 跨域报错怎么解决？

为了防止恶意网站在后台用脚本偷读你在其他网站（如网银或邮箱）的数据，浏览器实施了同源策略（Same-Origin Policy）：默认只允许网页脚本自由读取同源（协议 protocol + 主机域名 hostname + 端口号 port 三者完全一致）的接口响应。

当前网页为 https://www.example.com/index.html，请求目标 URL 是否同源？ 原因说明
https://www.example.com/api/users 同源 协议（https）、主机（www.example.com）、默认端口（443）全部相同，仅路径不同。
http://www.example.com/api/users 🔴 跨源 协议不同（https vs http）。
https://api.example.com/users 🔴 跨源 主机名不同（子域名 www vs api 属于不同源）。
https://www.example.com:8080/api/users 🔴 跨源 端口不同（默认 443 vs 8080）。

在前后端分离开发中，前端本地开发服务常跑在 http://localhost:5173，而后端接口跑在 http://localhost:8080，由于端口不同会触发浏览器的跨域拦截。工程中有两种标准解决方式：

方案 ① · 后端服务配置 CORS 响应头（允许指定前端源访问） 
# 后端在 HTTP 响应头中明确告知浏览器：允许该前端源读取响应
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization

# 若前端 fetch 开启了 credentials: 'include' 携带 Cookie：
# 1. Allow-Origin 必须写具体源，严禁写通配符 *
# 2. 必须额外返回下方响应头：
Access-Control-Allow-Credentials: true
方案 ② · 开发环境用 Vite / Nginx 反向代理转为同源请求 
// vite.config.js：让浏览器直接请求同源的 /api/xxx，
// 由本地 Node 开发服务器在后台转发给 8080 端口（服务器间通信无同源限制）
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true
      }
    }
  }
};
