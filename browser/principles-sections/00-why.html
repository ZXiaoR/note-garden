00.1 · 架构演进：早期单进程浏览器的三大工程瓶颈与 Chromium 多进程沙箱隔离模型

00.1 从单进程架构瓶颈到 Chromium 多进程分工

在 2008 年 Chrome 诞生之前，早期的桌面浏览器普遍采用单进程多线程架构：浏览器主界面、网络请求、HTML/CSS 渲染、JavaScript 执行以及第三方插件全部运行在同一个操作系统进程的地址空间内。随着 Web 应用日益复杂，单进程模型暴露出三个难以克服的工程瓶颈：

瓶颈 ① · 稳定性与容错 Crash Isolation
单个页面崩溃或死循环拖垮整个浏览器

单进程内任意一个标签页触发底层内存越界或主线程无限死循环，都会导致整个浏览器进程崩溃或所有标签页同时卡死。

瓶颈 ② · 安全与侧信道攻击 OS Sandbox
共享虚拟地址空间难以防御底层漏洞

不同网站的脚本在同一进程内存空间运行，一旦渲染引擎出现内存漏洞或遭遇 Spectre 幽灵侧信道攻击，恶意页面即可跨站读取其他标签页的隐私数据。

瓶颈 ③ · 内存回收碎片 Memory Reclaim
关闭复杂页面后内存难以彻底归还系统

多个标签页交错分配堆内存会产生严重内存碎片；而多进程架构下，关闭标签页直接终止对应渲染进程，操作系统即可瞬间回收其全部物理内存页。

理解上图中的渲染进程双线程协作（主线程 vs 合成线程），就能解释为什么有些页面在 JavaScript 卡死时仍然可以流畅滚动：当用户用手指滑动屏幕或滚动鼠标滚轮时，Browser 主进程先将输入事件发送给渲染进程的合成线程（Compositor Thread）；只要页面对应区域没有绑定非被动的滚动阻塞监听（即使用了 passive: true），合成线程无需等待繁忙的主线程，直接利用已栅格化好的图块生成新的合成帧交给 GPU 进程上屏。

00.2 站点隔离（Site Isolation）与 Mojo IPC 通信机制

在面试与工程分析中，一个常见误区是认为“每打开一个浏览器标签页（Tab），就会固定创建一个渲染进程”。实际上，现代 Chromium 采用的是以站点（Site，即协议 + 注册级根域名 eTLD+1）为边界的进程分配模型（Process-per-Site-Instance）：

页面打开场景 渲染进程（Renderer）分配结果 底层机制与安全考量
场景 ①：包含跨站 <iframe> 的单个标签页 1 个标签页拆分为多个渲染进程（Out-of-Process iframes, OOPIF） 若 https://news.com 页面内嵌了 https://pay.bank.com 的支付 iframe，站点隔离（Site Isolation）会强制将主页面与跨站 iframe 放入两个独立的渲染进程，即使主页面触发 V8 内存读取漏洞也无法偷取 iframe 进程内存中的银行凭据。
场景 ②：从页面 A 通过 window.open 打开同站页面 B 2 个标签页共享同一个渲染进程（属于同一浏览上下文组） 由于页面 A 与页面 B 属于同一站点且持有同步脚本引用（window.opener），必须放在同一渲染进程中才能支持同步跨窗口 DOM 访问；若链接加上 rel="noopener" 则允许分配到新进程。
场景 ③：受操作系统沙箱（OS Sandbox）限制的渲染进程 禁止直接发起系统调用访问磁盘、网卡或屏幕 渲染进程运行在高度受限的操作系统沙箱（如 Linux seccomp-bpf + Namespace、macOS Seatbelt、Windows Restricted Token）内。它要读取本地文件、发送网络包或申请 GPU 显存，必须通过 Mojo IPC 消息管道委托给外部服务进程代办。
Mojo IPC 如何避免大体积数据跨进程拷贝开销？
当 Network Service 下载完一张 5MB 的高清图片或数兆字节的 HTML 流时，如果通过普通管道在进程间逐字节拷贝，CPU 开销会非常高。Chromium 的 Mojo IPC 区分两类通道：小体积控制指令走基于操作系统的命名管道/域套接字（MessagePipe）；而大体积响应体与光栅化位图则走基于共享内存页（Shared Memory Buffer）的环形数据管线（DataPipe），只通过 IPC 传递共享内存句柄与偏移量，实现跨进程零拷贝传递。
