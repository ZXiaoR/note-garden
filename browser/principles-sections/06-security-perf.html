🛡️ 06.1 · 跨域协议底层：同源与同站（eTLD+1）边界，以及简单请求 vs OPTIONS 预检请求时序

🛡️ 06.1 同源 vs 同站辨析与 CORS 预检请求（Preflight）机制

在现代浏览器安全模型中，「同源（Same-Origin）」与「同站（Same-Site）」是两个截然不同的判定维度，分别控制着不同的安全机制：

  • 同源（Same-Origin = scheme + hostname + port 完全一致）：控制 fetch / XHR 响应读取权限（CORS）、localStorage / IndexedDB 隔离以及跨窗口 DOM 访问。例如 https://a.example.com 与 https://b.example.com 属于跨源（Cross-Origin）。
  • 同站（Same-Site = scheme + 有效顶级域名加一级域名 eTLD+1 一致）：控制 SameSite Cookie 是否跨站携带以及 Chromium 站点隔离进程分配。例如 https://a.example.com 与 https://b.example.com:8443 共享同一个根站点 example.com，因此它们虽然跨源，但属于同站（Same-Site）（注意：.github.io、.com.cn 登记在公共后缀列表 Public Suffix List 中，整体算作 eTLD，因此 a.github.io 与 b.github.io 属于跨站）。

当脚本发起跨源请求时，浏览器会根据请求是否可能对传统服务器产生未预期的副作用，将其分为简单请求（Simple Request）和需预检请求（Preflighted Request）：

💡 两个高频结论：
1. 对于简单请求，CORS 拦截发生在“响应回来之后”而非“请求发出之前”：服务器实际上已经收到了该请求并执行了逻辑，只是因为响应头缺少 Access-Control-Allow-Origin，浏览器拒绝将响应体交给页面 JS 读取。因此，CORS 绝不能代替服务端的权限校验与 CSRF 防御。
2. 如何减少每次 POST JSON 都多发一次 OPTIONS 预检的 1-RTT 开销？后端在预检响应中配置 Access-Control-Max-Age: 86400，浏览器会将该 URL 的预检授权结果缓存在专用的 Preflight Cache 中 24 小时，期间再次请求直接发真实报文。
⚔️ 06.2 · 安全攻防矩阵：XSS（注入恶意代码偷数据）与 CSRF（借用已登录 Cookie 冒充操作）原理与纵深防御

⚔️ 06.2 XSS 与 CSRF 攻击原理及浏览器级防御手段

可以用一句话区分 Web 安全最核心的两类漏洞：CSRF 是黑客骗你的浏览器去发一个非本意的请求（黑客拿不到响应，只利用你浏览器自动带上的 Cookie 执行转账/改密）；而 XSS 是黑客成功把一段恶意 JS 代码注入到了目标网站页面里执行（一旦执行，等同于完全控制了你的当前页面）。

安全威胁 核心子类型与攻击路径 浏览器安全机制与工程纵深防御（必答）
① XSS
（跨站脚本攻击）		 • 存储型：恶意评论含 <script> 存入数据库，所有浏览该帖的用户自动中招；
• 反射型：诱导点击含恶意脚本参数的 URL，服务端未转义直拼 HTML 返回；
• DOM 型：前端 JS 直接将 URL 参数赋给 innerHTML / eval 执行。 		1. 输出转义与安全 API：对用户输入做 HTML 实体转义（< 转 &lt;），前端优先用 textContent 或 React/Vue 默认文本绑定（禁用危险的 v-html / dangerouslySetInnerHTML）；
2. 开启 CSP（Content-Security-Policy） 响应头：如 script-src 'self' 'nonce-r4nd0m'，从浏览器底层禁止执行一切未带合法 nonce 签名或非白名单域名的内联脚本；
3. 敏感 Cookie 设置 HttpOnly：禁止 document.cookie 读取会话 Cookie，防止 XSS 窃取登录态。
② CSRF
（跨站请求伪造）		 用户在 bank.com 登录后未退出，又点开了黑客网站 evil.com；evil.com 页面自动用隐藏表单向 bank.com/transfer 发起 POST 请求，浏览器默认会自动附带 bank.com 的 Cookie。 1. SameSite Cookie 属性（现代浏览器默认 Lax）：设置为 SameSite=Strict（完全禁止跨站带 Cookie）或 SameSite=Lax（仅顶级导航 GET 允许，跨站 POST 表单与 fetch 均自动剥离 Cookie）；
2. CSRF Token 校验（或双重 Cookie）：由前端 JS 在自定义请求头（如 X-CSRF-Token）或请求体中携带随机令牌（黑客跨站页面受同源策略限制无法读取该 Token）；
3. 服务端校验 Origin / Referer 请求头。
📊 06.3 · 性能量化标准：Core Web Vitals 三大核心指标（LCP / INP / CLS）达标阈值、采集代码与针对性调优

📊 06.3 Core Web Vitals 性能指标体系与工程优化

早期的 DOMContentLoaded 或 load 事件只能反映文档解析或资源下载何时结束，无法真实反映用户眼睛何时看到主要内容、手指点击是否流畅、页面排版有没有乱跳。为此，现代 Web 性能工程统一采用 Core Web Vitals（核心网页指标） 来量化真实用户体验：

核心指标 优秀阈值 (Good) 精确衡量什么体验？ 针对性工程优化手段
① LCP
最大内容绘制
(Largest Contentful Paint)		 <= 2.5 s 首屏加载速度：从导航开始到视口内最大的一块可视内容（通常是首屏大图、视频封面或大标题段落）完成渲染的时间。 • 缩短服务端 TTFB（使用 CDN 与缓存）；
• 为首屏大图加上 <link rel="preload" as="image"> 或 fetchpriority="high"（切勿对首屏 LCP 大图加 loading="lazy"）；
• 内联首屏关键 CSS，脚本加 defer。
② INP
交互到下一次绘制
(Interaction to Next Paint)		 <= 200 ms 交互响应流畅度（已正式取代旧指标 FID）：衡量页面整个生命周期内所有点击、触摸和按键交互从触发到下一帧视觉画面真正绘制上屏的最差延迟（P98）。 • 拆解超过 50ms 的主线程长任务（使用 scheduler.yield() 让出主线程）；
• 点击后立即给出轻量视觉反馈（如 loading 态），将非紧急计算推迟或移入 Web Worker；
• 避免在事件回调中触发大面积同步重排。
③ CLS
累积布局偏移
(Cumulative Layout Shift)		 <= 0.1 视觉稳定性：统计页面生命周期内所有非用户交互引起的元素意外位置移动分值总和（影响面积比例 × 移动距离比例）。 • 所有 <img>、<video> 与广告位容器必须显式指定 width + height 或 CSS aspect-ratio 提前占位；
• 自定义 Web 字体使用 font-display: optional 或匹配度量回退字体；
• 动画一律使用 transform 替代修改 top / height。

在浏览器底层，这三项指标的数据源来自原生的 PerformanceObserver API；但在真实生产环境搭建前端性能监控（RUM，Real User Monitoring）时，如果直接手写裸 PerformanceObserver，会遇到许多复杂的边界条件（例如：页面一开始在后台标签页打开导致 LCP 虚高、从 bfcache 往返缓存恢复页面时的二次统计、CLS 按最大 5 秒会话窗口聚合而非全生命周期无限累加、以及 INP 在几十次点击中取 P98 分位数等）。
因此，业界生产环境统一使用 Google Chrome 团队官方维护的轻量标准库 web-vitals（压缩后仅约 2 KB）进行采集，并配合浏览器的 navigator.sendBeacon() 在页面隐藏时可靠上报：

🚀 生产标准方案 · 使用 Google 官方 web-vitals 库 + sendBeacon 上报 
// 安装：npm install web-vitals
// 如需直接定位具体是哪个 DOM 节点或哪段脚本慢，可从 'web-vitals/attribution' 导入
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

function reportToAnalytics(metric) {
  // metric 包含：{ name: 'LCP', value: 1420, rating: 'good', delta, id, navigationType }
  const body = JSON.stringify(metric);

  // 优先使用 sendBeacon：即使在用户关闭标签页瞬间触发，浏览器也会在后台保证发送成功且不阻塞卸载
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/rum-metrics', body);
  } else {
    fetch('/api/rum-metrics', { body, method: 'POST', keepalive: true });
  }
}

// 一键注册核心指标监听（库内部已自动处理后台标签页过滤、bfcache 恢复与 CLS 会话窗口）
onLCP(reportToAnalytics);
onINP(reportToAnalytics);
onCLS(reportToAnalytics);
onFCP(reportToAnalytics);
onTTFB(reportToAnalytics);
🔬 底层原理对照 · web-vitals 库内部封装的原生 PerformanceObserver 
// 1. 底层 LCP 数据源：随着首屏大图加载会触发多次候选记录，取交互/隐藏前最后一次即为 LCP
new PerformanceObserver((entryList) => {
  const entries = entryList.getEntries();
  const lastEntry = entries[entries.length - 1];
  console.log('LCP 候选值 (ms)：', Math.round(lastEntry.startTime), lastEntry.element);
}).observe({ type: 'largest-contentful-paint', buffered: true });

// 2. 底层 CLS 数据源：仅统计用户近期无点击/输入（!hadRecentInput）500ms 以外的意外移位
let clsScore = 0;
new PerformanceObserver((entryList) => {
  for (const entry of entryList.getEntries()) {
    if (!entry.hadRecentInput) {
      clsScore += entry.value;
      console.log('检测到意外布局偏移，累计分值：', clsScore.toFixed(4));
    }
  }
}).observe({ type: 'layout-shift', buffered: true });
🧰 性能量化工具生态全景（实验室数据 Lab Data vs 真实用户数据 Field Data）：
1. 真实用户监控（Field / RUM）：前端集成 Google 官方 web-vitals（或直接使用已内置它的 Sentry Performance / 阿里云 ARMS / Datadog RUM SDK），将用户真实设备上的分位数上报至后台分析。
2. 实验室自动化测评（Lab / CI）：本地与 CI 流水线使用 Chrome 内置的 Lighthouse（或 @lhci/cli）、Playwright + chrome-devtools-mcp，在固定网络节流（Throttling）与 CPU 降速倍率下对每次发版做回归压测。
