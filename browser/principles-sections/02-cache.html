02.1 · 缓存决策链路：Service Worker → Memory Cache → Disk Cache 查找顺序与强缓存 / 协商缓存状态机

02.1 浏览器缓存查找优先级与 RFC 9111 状态机图解

当渲染进程准备加载一份资源时，请求并不会直接发往网卡，而是依次经过四层缓存机制的筛选：① Service Worker 拦截（若已注册）→ ② 渲染进程内存缓存（Memory Cache）→ ③ 网络服务磁盘缓存（Disk Cache）→ ④ Push Cache / 发起真实网络请求。
在 HTTP 规范（RFC 9111）层面，磁盘与内存缓存遵循统一的「强缓存新鲜度检查（Freshness）→ 条件请求协商验证（Validation）」两阶段状态机：

Memory Cache vs Disk Cache 底层差异
  • Memory Cache（渲染进程内存内，0ms 读取）：位于当前渲染进程的虚拟内存中，专门缓存当前页面已经加载过的图片、字体与脚本（包括已解码的图像位图）。一旦关闭该标签页，渲染进程销毁，Memory Cache 立即释放。
  • Disk Cache（网络服务管理，落盘持久化）：位于操作系统磁盘目录中，跨标签页、跨浏览器重启共享。当系统可用物理内存紧张或文件体积过大时，资源只进 Disk Cache 不进 Memory Cache。
新鲜度寿命与 Age 计算公式（避免客户端时钟偏差）
  • 为什么废弃 Expires 改用 Cache-Control: max-age=N？因为 Expires 是一个绝对 GMT 时间戳，一旦用户电脑本地系统时钟被调快或调慢，强缓存判断就会彻底失效；而 max-age 是相对秒数。
  • 共享缓存耗时扣除：若响应先在 CDN 节点缓存了 200 秒（响应头带 Age: 200），且 max-age=600，则到达浏览器后剩余新鲜度仅为 600 - 200 = 400 秒，而非从落地本机起重新算 600 秒。
02.2 · 协商缓存深度辨析：为什么有了 Last-Modified 还要引入 ETag？强/弱 ETag 与高级缓存指令

02.2 ETag 对比 Last-Modified 的三大优势与 Cache-Control 指令全景

当强缓存过期或响应头配置了 Cache-Control: no-cache 时，浏览器会携带本地缓存的验证器发起条件请求。当响应同时包含 ETag 和 Last-Modified 时，服务器必须优先以 If-None-Match (ETag) 的比对结果为准，因为 Last-Modified 存在三个固有缺陷：

缺陷场景 Last-Modified / If-Modified-Since 表现 ETag / If-None-Match 解决方案
① 秒级以下高频修改 HTTP 日期格式精确到秒（Second）。若文件在 1 秒内被修改了两次，Last-Modified 时间戳不变，导致浏览器误判为未修改而漏更。 ETag 由文件内容摘要或修订版本号生成，1 毫秒内修改 100 次也会产生 100 个不同的 ETag。
② 重新打包但内容未变 CI/CD 重新构建或执行 touch 命令更新了文件修改时间，但实际代码只字未改，Last-Modified 改变导致全量重传 200。 基于内容哈希的 ETag 保持不变，精准返回 304 Not Modified 节省带宽。
③ 强验证与弱验证区分 仅能对比时间戳，无法表达“语义等价”或字节范围请求（Range Requests）校验。 支持强 ETag（"v1-a8f3"，要求字节完全一致，可用于断点续传）与弱 ETag（W/"v1-a8f3"，Nginx 开启动态 gzip 压缩时自动降级为弱 ETag）。
Cache-Control 关键指令 作用对象 精确语义与工程配合
max-age=600, s-maxage=3600 浏览器 vs CDN 代理 s-maxage 专门覆盖 CDN 等共享缓存（Shared Cache，public）的新鲜度寿命（此处 CDN 缓存 1 小时，而用户浏览器缓存 10 分钟）。
private vs public 缓存可见性边界 包含用户个人信息的接口响应必须标记 private，仅允许用户的浏览器私有缓存保存，严禁中间 CDN 或网关缓存给其他用户读取。
stale-while-revalidate=86400 过期后平滑更新（SWR） 强缓存过期后的 86400 秒内，若再次请求，浏览器先立即返回旧缓存保证页面 0ms 渲染，同时在后台异步发起网络请求更新本地缓存供下次使用。
02.3 · 可编程网络代理：Service Worker 生命周期与 Cache Storage 拦截策略

02.3 Service Worker 与 HTTP 缓存的协作边界

Service Worker 是运行在浏览器后台独立线程中的可编程网络代理（Programmable Network Proxy）。出于安全考虑，它只能在 HTTPS 或 localhost 环境下注册。一旦激活并接管页面，页面发出的每一次请求都会触发 Service Worker 的 fetch 事件，开发者可以用代码结合 caches (Cache Storage) 实现精细的缓存策略：

sw.js · 在 Service Worker 中实现「静态资源缓存优先、API 接口网络优先并降级离线缓存」 
const CACHE_NAME = 'garden-shell-v1';

// 1. 安装阶段 (install)：预缓存核心静态外壳资源
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(['/', '/assets/plop-garden.css']))
  );
});

// 2. 拦截请求阶段 (fetch)：注意 Cache Storage 不会自动根据 HTTP max-age 过期，完全由代码控制
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cachedResp) => {
      // 命中 Cache Storage 则直接返回；未命中则退回下层的浏览器 HTTP 缓存（Memory/Disk Cache）与网络
      return cachedResp || fetch(event.request);
    })
  );
});
