01.1 · 导航全链路：从地址栏回车到 CommitNavigation 交接的跨进程时序

01.1 从输入网址到「提交导航」的六个阶段

当用户在地址栏输入 URL 并按下回车时，并不是立即销毁当前页面并启动新渲染进程——因为在收到服务器响应头之前，浏览器还不知道这个地址返回的是一个 HTML 网页、一个需要触发文件下载的压缩包（Content-Disposition: attachment），还是一个 301/302 重定向。整个导航阶段先由 Browser 主进程与 Network Service 在后台完成，直到确认响应是可渲染的 HTML 文档后，才执行提交导航（CommitNavigation）切入新渲染进程：

性能优化特性：预热渲染进程（Spare Renderer）与往返缓存（bfcache）
1. Spare Renderer：为了消除第 6 步创建新渲染进程的操作系统开销，Browser 主进程在用户发起网络请求的同时，就会在后台预先启动或复用一个备用渲染进程；一旦收到响应头即可在 0ms 内立即提交导航。
2. 往返缓存（Back/Forward Cache，简称 bfcache）：当用户从页面 A 跳转到页面 B 时，只要页面 A 没有注册已被废弃的 unload 事件（推荐使用 pagehide 替代）且无未关闭的 WebSocket/IndexedDB 锁，浏览器不会销毁页面 A 的 DOM 树与 V8 堆内存，而是将其整个冻结保存在内存中；用户点击“后退”按钮时直接瞬间恢复快照，完全不经过网络请求与重新解析。
01.2 · 连接建立耗时剖析：DNS 解析顺序、TCP 三次握手与 TLS 1.2 (2-RTT) vs TLS 1.3 (1-RTT) 演进

01.2 DNS 解析链路与 TCP + TLS 安全握手 RTT 推导

当 Network Service 检查本地 HTTP 强缓存未命中且连接池中没有可复用的活跃连接时，必须先将域名解析为 IP 地址，并完成底层传输层与安全层握手。每一趟客户端与服务器之间的网络往返耗时称为 1 个 RTT（Round-Trip Time）：

① DNS 域名解析的 6 级查找顺序
  1. 浏览器内置 DNS 缓存（可在 chrome://net-internals/#dns 查看）；
  2. 操作系统本地缓存与 hosts 文件（调用系统解析库如 getaddrinfo，除非开启了 DoH 加密 DNS）；
  3. 本地递归 DNS 服务器（Local DNS，如运营商或 223.5.5.5）：若缓存命中则直接返回；
  4. 若 Local DNS 未命中，则由其依次向 根域名服务器（.）→ 顶级域名服务器（.com）→ 权威域名服务器（example.com） 发起迭代查询，拿到目标 IP（或 CDN 的 CNAME 别名记录）后返回给浏览器。
② TCP 三次握手与 TLS 1.2 vs TLS 1.3 往返对比
  • TCP 三次握手（耗费 1.5 RTT，第 3 次 ACK 可顺带发送首包，故感知耗时为 1 RTT）：客户端发 SYN(seq=x) ➔ 服务端回 SYN+ACK(seq=y, ack=x+1) ➔ 客户端回 ACK(ack=y+1) 确认双方收发能力正常。
  • TLS 1.2 握手（额外耗费 2 RTT）：第 1 个 RTT 交换 ClientHello / ServerHello 与证书；第 2 个 RTT 协商预主密钥（ECDHE 公钥参数）与 Finished 校验，总建连需 3 RTT。
  • TLS 1.3 握手（压缩至 1 RTT，会话恢复支持 0-RTT）：客户端在第一个 ClientHello 包中直接预猜并附带 ECDHE 密钥共享参数（Key Share），服务端一次返回证书与协商结果，总建连降至 2 RTT。
01.3 · 协议演进对比：HTTP/1.1 应用层队头阻塞、HTTP/2 二进制分帧多路复用与 HTTP/3 QUIC 传输层革新

01.3 HTTP/1.1、HTTP/2 与 HTTP/3 (QUIC) 核心机制对比

一个现代网页往往包含数十个脚本、样式表与图片请求。三代 HTTP 协议的核心演进主线，就是围绕如何消除不同层级的「队头阻塞（Head-of-Line Blocking，简称 HOL Blocking）」展开的：

对比维度 HTTP/1.1 HTTP/2 (H2) HTTP/3 (H3 over QUIC)
底层传输协议 TCP（+ TLS） TCP（+ TLS 1.2+，通过 ALPN 协商） UDP + QUIC 协议（内置 TLS 1.3）
连接并发与复用 同一 TCP 连接同一时刻只能处理 1 个请求-响应；浏览器被迫对同一域名开启最多 6 条并发 TCP 连接。 单域名仅需 1 条 TCP 连接：引入二进制分帧层（Binary Framing），将不同请求拆成带流编号（Stream ID）的帧交错传输，接收端按编号重组（多路复用）。 在 UDP 之上由 QUIC 原生实现互相独立的并发数据流（Streams），单个连接内多路复用。
队头阻塞瓶颈 🔴 存在 HTTP 应用层队头阻塞：前一个请求未收完响应，同一连接上的后续请求只能排队干等。 🟡 解决了应用层阻塞，但仍存在 TCP 传输层队头阻塞：一旦单个 TCP 数据包在弱网丢包，内核 TCP 协议栈会卡住整条连接等待重传，阻塞该连接上所有其他 Stream。 彻底消除传输层队头阻塞：丢包重传以单个 QUIC Stream 为粒度，流 A 丢包重传时，流 B 和流 C 的数据帧照常交付给渲染进程。
首部压缩算法 无压缩（纯文本重复发送冗长的 Cookie / User-Agent） HPACK（静态表 + 动态表 + 哈夫曼编码，动态表更新依赖帧顺序） QPACK（专为无序到达的 QUIC 流设计的首部压缩）
建连耗时与网络切换 TCP 1 RTT + TLS 1~2 RTT；手机从 Wi-Fi 切到 5G 时源 IP 改变，TCP 四元组失效必须断连重握。 同左（基于 TCP 四元组绑定连接）。 首次建连仅需 1 RTT（合并传输与加密握手），恢复连接 0-RTT；基于 64 位连接 ID（Connection ID）识别会话，Wi-Fi 切蜂窝网络时实现无缝连接迁移。
为什么升级到 HTTP/2 后，过去前端常用的“雪碧图（CSS Sprites）”和“域名分片（Domain Sharding）”反而不再推荐？
在 HTTP/1.1 时代，为了绕过“单域名最多 6 个并发连接”的限制，工程上常把静态资源分散到 s1.example.com ~ s4.example.com，或将几十个小图标拼成一张雪碧图。而在 HTTP/2 和 HTTP/3 下，单连接即可无上限并行传输上百个小文件；此时再做域名分片反而会破坏单连接复用与 HPACK 压缩字典，凭空增加多次 DNS 与 TLS 握手开销。
