🔄 05.1 WHATWG 事件循环模型：多任务队列与微任务检查点

需要注意一个面试高频细节：事件循环（Event Loop）并不是由 ECMAScript（JavaScript 语言标准）定义的，而是由 WHATWG HTML 标准规范定义的宿主调度机制（V8 引擎只负责维护调用栈与微任务队列，而何时取任务、何时渲染画面由 Blink 宿主事件循环决定）。

① 宏任务（Tasks）：按任务源划分的多个优先级队列

规范中称为 Task（俗称宏任务），包括：<script> 整体代码、setTimeout / setInterval、用户点击/滚动 I/O 事件、MessageChannel、网络响应回调等。
关键机制：浏览器并非把所有宏任务塞进同一个先进先出队列，而是为不同任务源（Task Source）维护多个队列。每轮事件循环开始时，浏览器调度器会优先从用户交互队列（如鼠标点击、键盘输入）取任务，其次才是网络和定时器队列，从而保证用户操作优先得到响应。

② 微任务检查点（Microtask Checkpoint）：不清空绝不继续

微任务（Microtasks）仅包含三类：Promise.then / catch / finally（含 await 后续体）、queueMicrotask()、以及监听 DOM 树变动的 MutationObserver。
关键机制：每当调用栈（JS Execution Stack）变空——无论是跑完一个宏任务，还是在渲染前跑完一个 requestAnimationFrame 回调——引擎都会立刻进入微任务检查点，用一个 while 循环把微任务队列里的所有任务（包括微任务执行期间新追加的子微任务）彻底清空。若微任务无限递归追加微任务，将直接卡死主线程导致无法进入页面渲染。

另一个常见误区是认为“每执行完一个宏任务 + 清空微任务，浏览器就会立刻重新渲染一次页面”。事实并非如此：在 60Hz 刷新率的屏幕上，硬件每 16.67ms（120Hz 下为 8.33ms）才发出一次垂直同步信号（VSync）。如果两个 setTimeout 宏任务各耗时 1ms，在这 16.67ms 窗口内浏览器可以连续跑完好几个宏任务，直到VSync 到来且页面确实有视觉变动（存在渲染机会 Rendering Opportunity）时，才会进入下图的更新渲染（Update the rendering）阶段：

常见高频疑问 / 对比项 底层机制与时序结论 工程实践指导
requestAnimationFrame (rAF) vs requestIdleCallback (rIC) rAF 在每一帧计算样式与布局（Style & Layout）之前必然执行；而 rIC 仅当一帧跑完任务和渲染后时间仍有结余（小于 16.7ms）时才执行。 严禁在 rIC 里修改 DOM：因为此时本帧的 Layout 和 Paint 已经结束，在 rIC 里改 DOM 会使刚刚算好的布局作废并导致下一帧耗时失控；rIC 仅用于低优先级日志上报或预取。
同一帧里调用两次修改背景色：
box.style.bg = 'red'; box.style.bg = 'blue'; 会闪现红色吗？		 绝对不会闪现红色。因为这两行赋值都在同一个宏任务（阶段 ①）里同步执行完，直到进入阶段 ⑤（Style & Paint）时浏览器才读取最终状态绘制一次蓝色。 若确实需要先渲染红色、下一帧再过渡到蓝色，需将第二次修改放入嵌套的双层 requestAnimationFrame 中。
setTimeout(fn, 0) 为什么在嵌套超过 5 层后最短延迟变成 4ms？ HTML 标准明确规定：当定时器嵌套层级（Nesting Level）超过 5 层时，为了防止代码写死循环定时器耗尽 CPU 电量，浏览器强制将最小延迟钳制为 >= 4ms。 若在浏览器中需要做零延迟的宏任务时间切片（如 React Scheduler），应使用不受 4ms 限制的 MessageChannel 或现代原生的 scheduler.yield()。
