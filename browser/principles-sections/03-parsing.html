03.1 · 流式解析器原理：Bytes → Tokens → Nodes → DOM Tree 管线与投机性预加载扫描器

03.1 HTML5 状态机流式解析与预加载扫描器（Preload Scanner）

渲染进程并不需要等整个 HTML 文件下载完毕才开始工作。一旦 Network Service 通过 Mojo DataPipe 送来第一批字节块（Chunk），主线程的 HTML 解析器就会以流式增量方式（Streaming Parsing）推进以下四步转换：

① 字节解码 → 状态机词法分析（Tokenizer）→ 栈式建树
  • 为什么 HTML 不能用普通的正则表达式或通用 XML 语法分析器解析？因为 HTML 语言规范允许大量容错省略（如未闭合标签 <p>1<p>2、属性未加引号），且 <script> 内部可能包含任意 < 字符。因此 WHATWG 规范将其定义为包含 80 个状态的有限状态机（Finite State Machine）。
  • 栈式树构建（Tree Construction）：解析器维护一个未闭合元素栈（Stack of Open Elements）：遇到 StartTag: div 则创建 HTMLDivElement 挂入父节点并压栈；遇到 EndTag: div 则弹出栈顶元素。
② 为什么主解析器被脚本阻塞时，后面的图片还能并行下载？
  • 当主 HTML 解析器遇到顶部的同步 <script src="a.js"> 而暂停建树时，如果什么都不做，底下几十张图片和样式表就只能干等。
  • 为此，现代浏览器全部内置了一个极其轻量的投机性预加载扫描器（Preload Scanner / Speculative Parser）：当主解析器暂停时，它会快速向后扫描原始 HTML 文本中的 <img src>、<link rel="stylesheet"> 和 <script src>，提前通知 Network Service 在后台并行下载（约提升 20% 页面加载速度）。
03.2 · 样式计算引擎：CSSOM 规则哈希索引、选择器「从右向左」匹配算法与层叠权重

03.2 CSS 选择器为什么从右向左匹配？CSS 到底阻塞什么？

在解析 HTML 的同时，浏览器会将外部样式表（.css）与内联 <style> 解析为CSS 对象模型（CSSOM / StyleSheetContents）。围绕 CSS 处理，有两个高频底层原理问题：

① 为什么选择器 .nav ul li a 是从右向左（a → li → ul → .nav）匹配的？

假设一个页面有 2000 个 DOM 节点和 500 条 CSS 规则。如果从左向右匹配 .nav ul li a，引擎需要先找到 `.nav`，再向下遍历其整棵子树里所有的 `ul`、`li`，走到最深处的叶子节点才发现它只是个 `span` 而不是 `a`，绝大部分向下遍历都做了无用功。
而从右向左（先看最右侧的关键选择器 Key Selector a）：Blink 会把所有规则按最右侧选择器建立哈希桶（ID 桶、Class 桶、Tag 桶）。判定一个节点时，先看它是不是 <a>——若不是，一步即可排除（O(1) 剪枝）；若是，只需沿着唯一确定的 parentNode 指针向上回溯父节点即可。

② 外部 CSS 加载究竟阻塞什么？不阻塞什么？
  • CSS 不会阻塞 DOM 树的解析构建：当 <head> 里的外部 CSS 还在下载时，HTML 解析器完全可以继续向下解析标签生成 DOM 节点。
  • CSS 会严格阻塞页面首次渲染（Render-Blocking）：在 CSSOM 构建完成前，浏览器不会将 DOM 绘制上屏，以防止用户先看到毫无样式的裸排版再突然闪变成带样式排版（FOUC，无样式内容闪烁）。
  • CSS 会阻塞排在它后面的同步 <script> 执行（从而间接阻塞后续 HTML 解析）：因为后面的 JS 脚本随时可能调用 getComputedStyle(el) 读取元素的样式，所以 JS 必须等待前面的 CSS 下载并构建完 CSSOM 后才能执行。
