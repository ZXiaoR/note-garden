🖼️ 04.1 Blink + Viz 渲染流水线的六个核心阶段

当 DOM 树与 CSSOM 规则准备就绪后，Chromium 的渲染引擎（Blink）与合成器（CC / Viz）通过主线程 → 合成线程 → 光栅线程池 → GPU 进程的四级流水线，将内存中的树结构转化为屏幕上的像素帧：

为什么第 ② 步的布局树（Layout Tree，早期常统称为 Render Tree）与 DOM 树不是一一对应的？

  • 在 DOM 树中存在、但不在 Layout 树中的节点：<head>、<script> 以及任何设置了 display: none 的元素，由于不占据任何几何空间，会被完全剔除出 Layout 树（注意：visibility: hidden 和 opacity: 0 仍然占据几何空间，因此保留在 Layout 树中）。
  • 不在 DOM 树中、但会出现在 Layout 树中的节点：CSS 伪元素（如 ::before、::after）以及多行文本自动折行生成的匿名行盒（Anonymous Inline/Block Boxes），虽然在 DOM 中没有对应标签，但会在 Layout 树中生成独立的布局节点。

⚡ 04.2 重排（Reflow）、重绘（Repaint）与直接合成（Composite）对比

当页面初次渲染完成后，JavaScript 或 CSS 动画对元素样式的每一次修改，都会根据受影响的属性种类走完不同长度的流水线。理解这三条路径的成本差异，是前端渲染性能调优的核心：

更新级别 经历的流水线阶段 常见触发属性或 API 性能开销与线程占用分析
① 重排 / 回流
（Reflow / Layout）		 Style ➔ Layout ➔ Layer ➔ Paint ➔ Raster ➔ Composite（全流程重跑） 修改 width / height / margin / padding / top / left / font-size、增删 DOM 节点、改变窗口大小 🔴 开销最大（重排必触发重绘）：元素的几何尺寸或位置改变会牵一发而动全身，导致父子节点及后续兄弟节点在主线程重新计算坐标。
② 重绘
（Repaint / Paint）		 Style ➔ Paint ➔ Raster ➔ Composite（跳过 Layout 与分层） 修改 color / background-color / border-color / visibility / box-shadow 🟡 开销中等（重绘不一定触发重排）：元素几何位置和宽高完全没变，但像素外观改变，需在主线程重新记录绘制指令并重新光栅化对应图块。
③ 仅合成
（Composite-only）		 Style ➔ Composite（完全跳过 Layout、Paint 与重新光栅化） 在独立合成层上修改 transform（平移/缩放/旋转） 与 opacity（透明度） 🟢 开销最低（硬件加速快车道）：图块纹理早已在 GPU 显存中，CSS 动画甚至可完全由合成线程与 GPU 通过矩阵变换直接合成新帧，主线程耗时为 0。
⚠️ 警惕一：强制同步布局（Forced Synchronous Layout / 布局抖动）

现代浏览器为了减少重排，会将同一轮 JS 任务中的多次样式修改放入队列延迟批量计算。但如果你在循环中刚写完 el.style.width = ...，紧接着立刻读取 el.offsetWidth / offsetTop / scrollTop / getBoundingClientRect()，浏览器为了给你返回最新尺寸，会被迫放弃批量合并，在 JS 执行中途立即强制同步执行一次 Layout。解决原则：读写分离（先集中读完所有几何属性存入变量，再集中修改样式）。

⚠️ 警惕二：独立合成层提升条件与「层爆炸（Layer Explosion）」

拥有 3D 变换（translate3d / translateZ(0)）、<video> / <canvas>、transform / opacity 过渡动画或显式声明 will-change: transform 的元素会被提升为独立合成层（Compositing Layer）。
切勿滥用 will-change：每一个独立合成层都需要单独分配 GPU 显存纹理；而且若一个低 z-index 元素提升为合成层，压在它上方的其他普通元素也会被浏览器隐式提升（Implicit Compositing）为独立合成层，引发“层爆炸”耗尽移动端显存。
