AI 工程基础杂谈：SSE 底层、接口幂等性与 Agent 上下文压缩

系统梳理 AI 应用开发中最常遇到的三项底层工程主题：第一部分拆解 SSE 协议帧结构、前后端流式对接链路与弃用原生 EventSource 的工程原因；第二部分由断线重试引出接口幂等性、防重辨析与六类生产级实现方案；第三部分聚焦 Agent 上下文压缩的触发时机、分业务选型、冷热启动与会话恢复机制，以及可量化的线上评估指标。

01 SSE 协议底层机制：HTTP 长连接、分块传输与事件帧格式 PART I · SSE PROTOCOL

SSE（Server-Sent Events，服务端推送事件）并不是一种独立于 HTTP 之外的新传输层协议，而是建立在标准 HTTP（HTTP/1.1 或 HTTP/2）之上的轻量级单向流式文本协议。大语言模型推理是按 Token 逐个自回归生成的，完整回复可能需要 5~30 秒，如果等全部生成完再返回，用户只能面对漫长的白屏等待；通过 SSE，服务端每拿到一个新 Token 就能立刻刷出到浏览器，将首字延迟（TTFT）压缩到毫秒至百毫秒级。

📡 1. 底层传输的三个 HTTP 关键要素

  • 声明流式 MIME 类型：服务端返回 Content-Type: text/event-stream; charset=utf-8，告诉客户端和中间代理“这是一个持续不断的 UTF-8 文本事件流，不要等关闭连接才开始解析”。
  • 分块传输编码（Chunked Transfer Encoding）：在 HTTP/1.1 中，服务端事先不知道模型最终会输出多少字节，因此不会发送 Content-Length，而是设置 Transfer-Encoding: chunked，把响应体拆成若干带十六进制长度前缀的数据块逐段发出，直到发送一个长度为 0 的终止块才结束响应（HTTP/2 则直接复用帧级别的 DATA Frame 持续发送，直到设置 END_STREAM 标志）。
  • 禁用缓存与中间层缓冲：必须带上 Cache-Control: no-cache 与 Connection: keep-alive；在 Nginx 反向代理后部署时，还必须加上 X-Accel-Buffering: no，否则 Nginx 默认会攒满 4KB~8KB 缓冲区才转发一次，导致前端看到的是一坨一坨蹦出来而不是平滑打字机效果。

📦 2. SSE 文本事件帧规范（4 个保留字段 + 注释行）

SSE 的载荷是纯文本，每行以 \n（或 \r\n）结尾，两条事件之间严格以一个空行（即 \n\n）作为完整事件的边界：

字段名 语义与工程用途
data: 事件主体内容，通常序列化为 JSON 字符串。同一事件中若有多行 data:，客户端规范会用 \n 将它们自动拼接。
event: 自定义事件类型（如 delta、tool_call、done）。省略时默认为 message。
id: 当前事件序号。浏览器原生客户端断线重连时会自动在请求头带上 Last-Event-ID，用于断点续传。
retry: 建议客户端断线后的重连等待时间（毫秒，如 retry: 3000）。
: 注释 以冒号开头的行会被解析器忽略，生产中常每 15~30 秒发送 : keep-alive\n\n 防止网关/防火墙因空闲超时切断 TCP 连接。

⚖️ 3. 实时推送技术选型对比：为什么大模型流式输出首选 SSE

协议 / 方式 通信方向 底层与网关兼容性 在 AI 应用中的适用定位
SSE 单向（服务端 → 客户端） 纯 HTTP，天然兼容现有鉴权、CORS、负载均衡与 CDN 文本/结构化 LLM 对话首选：用户发一次 Prompt，模型单向流式吐出 Token，协议轻量、无升级握手负担。

02 前后端流式对接全景：端到端时序、即时刷出与断连取消 END-TO-END FLOW

一条生产可用的 AI SSE 链路通常会经过 浏览器 → 反向代理（Nginx / API 网关）→ 业务后端（Node.js / Go / Python）→ 上游模型接口 四段。只要中间任意一段开启了响应缓冲，或者后端忘了感知客户端主动断连，就会出现“前端卡死最后一次性吐出”或“用户早关页面了，后端还在花钱跑完 4000 个 Token”的问题。

🐹 后端侧 · Go (net/http + http.Flusher) 
func ChatStreamHandler(w http.ResponseWriter, r *http.Request) {
    // 1. 声明 SSE 响应头并关闭 Nginx 缓冲
    w.Header().Set("Content-Type", "text/event-stream; charset=utf-8")
    w.Header().Set("Cache-Control", "no-cache, no-transform")
    w.Header().Set("Connection", "keep-alive")
    w.Header().Set("X-Accel-Buffering", "no")

    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "streaming unsupported", http.StatusInternalServerError)
        return
    }

    // 2. 绑定请求 Context：前端一旦 abort，ctx.Done() 立即触发
    ctx := r.Context()
    tokenCh := llmClient.StreamChat(ctx, reqBody)
    heartbeat := time.NewTicker(15 * time.Second)
    defer heartbeat.Stop()

    for {
        select {
        case <-ctx.Done():
            // 客户端主动断开，立刻退出并停止上游 Token 计费
            return
        case <-heartbeat.C:
            fmt.Fprint(w, ": keep-alive\n\n")
            flusher.Flush()
        case chunk, open := <-tokenCh:
            if !open {
                fmt.Fprint(w, "event: done\ndata: [DONE]\n\n")
                flusher.Flush()
                return
            }
            fmt.Fprintf(w, "event: delta\ndata: %s\n\n", chunk.JSON)
            flusher.Flush() // 每次写入后必须手动 Flush 刷出内核缓冲
        }
    }
}
🟢 后端侧 · Node.js (Express / HTTP) 
app.post('/api/chat/stream', async (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream; charset=utf-8');
  res.setHeader('Cache-Control', 'no-cache, no-transform');
  res.setHeader('Connection', 'keep-alive');
  res.setHeader('X-Accel-Buffering', 'no');
  res.flushHeaders(); // 立刻发送响应头建立流通道

  const upstreamCtrl = new AbortController();
  req.on('close', () => {
    // 前端断开时中止上游 LLM 请求
    upstreamCtrl.abort();
  });

  try {
    const stream = await llm.stream(req.body, { signal: upstreamCtrl.signal });
    for await (const delta of stream) {
      res.write(`event: delta\ndata: ${JSON.stringify(delta)}\n\n`);
      // 若启用了 compression 中间件，需跳过该路由或调用 res.flush()
    }
    res.write('event: done\ndata: [DONE]\n\n');
  } finally {
    res.end();
  }
});
03 浏览器原生 EventSource 的工作机制与 AI 场景弃用原因 WHY NOT EVENTSOURCE

浏览器其实原生内置了专门消费 SSE 的 EventSource API（属于 HTML5 规范）。用它对接简单的行情推送或站内通知非常省事：只需 new EventSource('/api/events')，浏览器就会自动帮你解析 \n\n 边界、按 event: 类型触发监听器，并在网络闪断后按 retry: 间隔自动重连、携带 Last-Event-ID 请求头。

🧩 浏览器原生 EventSource 最小示例（适合只读通知流） 
const es = new EventSource('/api/notifications/stream', { withCredentials: true });

// 监听默认 message 事件（未指定 event: 字段时触发）
es.onmessage = (e) => console.log('default:', e.data);

// 监听自定义事件（服务端发送 event: alert）
es.addEventListener('alert', (e) => {
  console.log('alert:', JSON.parse(e.data), 'id=', e.lastEventId);
});

// 注意：无法在 onerror 中拿到 HTTP 状态码（如 401/429），且默认会自动重连
es.onerror = () => {
  if (es.readyState === EventSource.CLOSED) console.log('连接已关闭');
};

然而，在 ChatGPT、Claude、Gemini 以及各类企业级 AI Agent 产品中，前端几乎不会直接使用原生 EventSource，核心原因集中在以下 5 个难以绕过的协议与 API 限制：

LIMIT 01 · 仅支持 GET

无法发送 POST 请求体（Request Body）

EventSource 规范写死了只能发 GET 请求。而 AI 对话接口通常需要在 Body 中提交多轮上下文数组、系统提示词、工具定义、模型参数甚至 Base64 图片。如果强行塞进 URL Query，不仅会迅速撞上浏览器和网关的 URL 长度上限（常见 2KB~8KB），还会让用户提问原文直接暴露在代理日志与浏览器历史中。

LIMIT 02 · 无法自定义请求头

不支持 Authorization、Idempotency-Key 等 Header

现代前后端分离应用普遍使用 JWT（Authorization: Bearer ...）、租户标识（X-Tenant-Id）或幂等键（Idempotency-Key）放在请求头中。EventSource 不提供设置自定义 Header 的入口，只支持 withCredentials 带上同源 Cookie；如果把 Token 拼进 URL 参数，极易通过 Referer 或网关访问日志泄露。

LIMIT 03 · 僵化的自动重连

断线静默重连易触发 LLM 重复扣费与重复生成

EventSource 遇到网络抖动或服务端未显式关闭的流结束，会按固定策略自动重发同一请求。对“行情广播”这是好事，但对“触发大模型生成”的请求，静默重连意味着重新调用一次大模型——用户看到回复重新从头吐一遍，后台还白白多付一次 Token 费用。这也是后文必须引入幂等性设计的直接诱因。

LIMIT 04 · 弱错误处理 & 连接池

拿不到 HTTP 状态码，且受 HTTP/1.1 并发连接限制

当服务端返回 401（登录过期需刷新 Token）、429（限流需展示退避倒计时）或 400（参数校验失败 JSON）时，EventSource.onerror 只能收到一个空的 Event 对象，既拿不到状态码也读不到错误响应体。此外在 HTTP/1.1 下，浏览器对同一域名最多保持 6 个 TCP 长连接，多标签页常驻 EventSource 容易挤占正常接口请求（开启 HTTP/2 多路复用可缓解此项）。

04 现代 AI 前端流式实践：fetch + ReadableStream 解析与边界处理 PRODUCTION PATTERN

正因为上述限制，业界标准做法是后端继续输出标准 SSE 文本格式，前端改用 fetch() 发起 POST 请求，再通过响应体提供的 ReadableStream（response.body.getReader()）逐块读取字节流，并配合 TextDecoder 与行缓冲区解析 SSE 帧（工程中也可直接使用成熟封装如 @microsoft/fetch-event-source、eventsource-parser 或 Vercel AI SDK）。

⚡ 前端侧 · fetch + ReadableStream + TextDecoder 生产级 SSE 解析器 
export async function streamChat(payload, { token, idempotencyKey, signal, onDelta }) {
  const res = await fetch('/api/chat/stream', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Accept': 'text/event-stream',
      'Authorization': `Bearer ${token}`,
      'Idempotency-Key': idempotencyKey, // 携带幂等键，防止重试重复生成
    },
    body: JSON.stringify(payload),
    signal, // 绑定 AbortController.signal，点击“停止生成”即刻断流
  });

  // 1. 精确处理 401 / 429 / 500 等非 2xx 状态码与 JSON 错误体
  if (!res.ok) {
    const errBody = await res.text();
    throw new Error(`HTTP ${res.status}: ${errBody}`);
  }

  const reader = res.body.getReader();
  // 2. 必须开启 stream: true，避免多字节 UTF-8 中文字符在 Chunk 边界被截断乱码
  const decoder = new TextDecoder('utf-8');
  let buffer = '';

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    // 3. TCP 分包与粘包：一次 read() 可能包含半条事件，也可能包含多条事件
    const frames = buffer.split(/\r?\n\r?\n/);
    buffer = frames.pop() ?? ''; // 留存末尾未闭合的半截帧等待下一块拼接

    for (const frame of frames) {
      const dataLines = frame
        .split(/\r?\n/)
        .filter((line) => line.startsWith('data:'))
        .map((line) => line.slice(5).trimStart());

      if (!dataLines.length) continue;
      const raw = dataLines.join('\n');
      if (raw === '[DONE]') return;
      onDelta(JSON.parse(raw));
    }
  }
}

📌 手写流式解析器最容易忽略的两个边界细节

  • UTF-8 多字节截断问题：一个中文字符占 3 个字节，网络分包很可能正好切在第 1 和第 2 字节之间。如果 decoder.decode(value) 忘了传 { stream: true }，边界处的汉字就会变成 （Replacement Character）。
  • TCP 粘包与半包问题：服务端每发一次 flush() 并不保证前端 reader.read() 恰好收到一条完整 JSON。必须维护一个跨 Chunk 的 buffer，严格按 \n\n 切分事件帧，并把数组最后一块（可能尚未收齐）保留回 buffer。
05 幂等性核心定义：数学本质、HTTP 语义与防重概念辨析 PART II · IDEMPOTENCY

在前面聊到 SSE 断线重试时，我们已经碰到了一个经典的分布式系统难题：客户端发出了请求，但因为网络超时没收到回包，于是发起重试——服务端怎么保证同一个操作执行 1 次和执行 10 次的结果完全一样？这就是幂等性（Idempotency）要解决的核心问题。

📐 1. 从数学公式到工程定义

在数学中，幂等表示为 f(f(x)) = f(x)（例如取绝对值 abs(-5) = 5，再取一次依然是 5）。落到软件工程里：

同一个业务操作被重复调用 1 次或 N 次，对系统最终状态产生的改变完全一致，且不会产生额外的副作用（如重复扣款、重复建单、重复发邮件）。

注意区分「结果一致」与「响应一致」：严格意义上的幂等强调的是服务端状态（Side Effects）一致。例如 DELETE /orders/101 第一次返回 200 OK，第二次返回 404 Not Found，只要订单 101 被删一次后不会误删其他数据，它依然是幂等的；而在支付或 AI 生成 API 中，为了对调用方更友好，通常会进一步把第一次成功的响应缓存下来，重试时直接返回相同的成功结果。

🌐 2. 天然幂等与非幂等操作对照

操作类型 是否天然幂等 说明与典型反例
SELECT / GET 天然幂等 只读查询，不修改服务端状态。
UPDATE set status = 2 天然幂等 按唯一主键覆盖为固定目标值（对应 HTTP PUT）。
DELETE where id = 10 天然幂等 按主键删除，删多少次最终都是“不存在”。
INSERT / POST 非幂等 每次执行都会新建一条自增 ID 记录（如重复下单、重复扣费）。
UPDATE set balance = balance - 100 非幂等 增量/相对计算类更新，每执行一次余额都会再少 100。

⚖️ 3. 幂等 vs 防重：经常一起提，但承诺不同

对比维度 防重（Anti-Duplicate） 幂等（Idempotency）
核心目标 拦截短时间内的重复点击或并发提交 同一操作执行 1 次和 N 次，系统最终状态完全一致
重复处理 直接拒绝并提示“请勿重复提交” 返回首次成功结果，或安全忽略且不产生额外副作用
时间窗口 短周期（按钮禁用、Redis 短 TTL 锁） 跨重试周期持久化（唯一索引 / 幂等表 / 状态机）
两者关系 防重是幂等的前置防线，但短时防重锁过期后重试仍会重复执行；完整方案通常是短时防重抗并发 + 持久幂等兜底。

🔗 4. 关联知识链与「唯一键」落地本质

分布式可靠性因果链：网络不可靠 → 上游需要超时重试 / MQ 采用 At-Least-Once 投递 → 必然出现重复请求 → 入口先做防重挡连点，底层靠幂等（配合原子锁、唯一约束或分布式事务补偿）保证业务层近似 Exactly-Once。

代码落地是否都依赖唯一键？
• 新建与增量类操作（INSERT、扣余额、发消息、调写工具）：几乎都必须落到一个唯一键（前端 UUID、预生成单号、MQ msg_id 或业务联合唯一索引），用来识别“这笔意图是否已执行”。
• 修改与删除类操作（UPDATE / DELETE）：不一定需要新造请求键，可直接靠绝对值覆盖或主键 + 单向状态机 / 版本号 CAS 保证重复执行不越界。

06 高频适用场景：为什么分布式与 AI 工程离不开幂等设计 WHEN TO USE

只要存在“网络不确定性 + 自动/人工重试”，同一份请求就有可能到达服务端多次。最典型的陷阱是“假超时”：请求到达服务端并已经把数据库改完了，但返回响应时网络抖动丢包，客户端以为失败于是重发。下面四类场景必须强制做幂等防护：

🤖 1. AI 与 Agent 工程场景

  • Agent Tool Calling 外部副作用：大模型编排调用 create_ticket、send_email、issue_refund 时，若工具执行成功但回包超时，Agent 框架重跑该 Step 就会发出两封邮件或退两次款。
  • 对话发送连点与断线重试：用户弱网连点发送按钮，或流式连接中断重连，重复触发一次高成本模型推理并插入两条相同的对话记录。
  • 异步知识库入库 / 媒体生成：文档切分写入向量库（Qdrant Point Upsert 需基于确定性 ID）、视频生成 Webhook 回调重复推送。

💳 2. 资金交易与核心业务写接口

  • 支付、扣款与退款：余额扣减、第三方支付回调通知（支付宝/微信/Stripe 会在未收到 200 OK 时按阶梯频率持续重推）。
  • 订单与库存：创建订单、扣减库存、发放优惠券与积分，任何一次重复执行都会直接造成资损。

📨 3. 消息队列（MQ）消费者

  • At-Least-Once 投递语义：Kafka、RocketMQ、RabbitMQ 为了不丢消息，默认保证“至少投递一次”。当 Consumer 处理完业务但在提交 Offset/ACK 前崩溃，或触发 Rebalance 时，同一条消息必然被重新投递给其他节点消费。

🔁 4. 微服务 RPC 与网关自动重试

  • 上游框架重试策略：Nginx、Envoy、gRPC 或业务 HTTP Client 往往配置了超时自动重试（如 max_retries = 3）。如果下游写接口没有做幂等保护，一次短暂的 Full GC 或慢 SQL 就会把单次操作放大成 3 次重复写入。
07 幂等的六大工程实现方案与 Idempotency-Key 状态机 IMPLEMENTATION

所有幂等方案的底层逻辑其实都可以归结为同一件事：为每一次业务意图分配一个全局唯一的身份凭证（幂等键），并在持久化或原子存储中记录它的执行状态。不同业务形态对应以下 6 种常见实现手段：

实现方案 核心机制 优点与注意事项 典型适用场景
1. Idempotency-Key 状态机
API 行业通用规范		 客户端生成 UUID 放入请求头，服务端维护 PROCESSING → COMPLETED / FAILED 状态机并缓存首次响应结果。 优：对调用方透明，支持结果重放。
注：需校验请求体哈希，防止同一 Key 误用于不同参数。		 支付 API（Stripe 规范）、AI 生成接口、Agent 写工具。
2. 数据库唯一索引
Unique Constraint		 在业务单号或请求号字段建 UNIQUE KEY，并发写入时由数据库引擎原子拦截冲突（Duplicate Key Error）。 优：强一致兜底，零并发竞态。
注：仅适用于 INSERT 类场景，捕获冲突后应查出原记录返回。		 创建订单、发券记录、外部回调落库。
3. 乐观锁 / 状态机 CAS
Compare-And-Swap		 更新语句带上前置条件：UPDATE ... SET status='PAID', ver=ver+1 WHERE id=? AND status='UNPAID' AND ver=?，判断影响行数是否为 1。 优：无需额外建表，并发性能好。
注：适用于单向流转的状态更新，不适合创建类接口。		 订单状态流转、余额/库存扣减（配合流水表）。
4. 独立去重表 + 本地事务
Dedup Table		 在同一个 DB 事务内，先 INSERT INTO mq_dedup(msg_id)，再执行业务变更，两者同成同败。 优：与业务库强一致，彻底解决 MQ 重复消费。
注：需定期按时间分区清理过期去重记录。		 Kafka / RocketMQ 消费端、分布式回调处理。
5. Redis SET NX EX 防重锁
Distributed Lock		 请求进入前尝试 SET idem:{key} 1 NX EX 300，抢锁成功才放行；并发重复请求直接拦截。 优：抗高并发极强，保护下游数据库。
注：Redis 存在过期淘汰和主从切换丢锁风险，仅作前置拦截，资金类仍需 DB 兜底。		 按钮防连点、高并发秒杀入口、AI 流式请求前置挡板。
6. 预申请 Token 令牌
Pre-fetch Token		 打开表单页先向服务端申请一次性 Token 存入 Redis；提交时用 Lua 原子校验并删除 Token。 优：专门治理前端表单重复提交。
注：多一次网络往返，不太适合无界面后端 RPC 调用。		 Web 表单提交、人工审批确认页。

🗄️ 生产级 Idempotency-Key 数据表结构（MySQL / PostgreSQL 通用设计） 
CREATE TABLE idempotency_records (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id       VARCHAR(64)  NOT NULL,
  idem_key        VARCHAR(128) NOT NULL,  -- 客户端传入的 Idempotency-Key
  request_hash    CHAR(64)     NOT NULL,  -- SHA-256(method + path + body)
  status          VARCHAR(16)  NOT NULL,  -- PROCESSING | COMPLETED | FAILED
  http_status     INT          NULL,      -- 缓存首次执行的 HTTP 状态码
  response_body   MEDIUMTEXT   NULL,      -- 缓存首次响应 JSON 快照

  expires_at      DATETIME     NOT NULL,  -- 过期时间（如 24h 后定期清理）
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_tenant_idem_key (tenant_id, idem_key),
  KEY idx_expires_at (expires_at)
);

🔍 工程边界辨析：日常前端开发很少传 UUID 的原因与适用边界

很多前端工程师在常规业务开发中几乎没有手动生成过 UUID 传给后端，这并不意味着系统缺少幂等保护，而是不同业务场景选择了成本更低的分层兜底方式：

层级 1 · UI 交互防重

按钮 Loading 与防抖节流

后台管理、表单和大屏等常规场景，提交时置灰按钮即可拦截绝大多数人工连点；即便极低概率因网络超时多建一条普通记录，人工修正成本也很低，无需引入全链路幂等表。

层级 2 · 后端与协议隐式兜底

业务唯一键、状态机与预下单

多数接口天然具备去重条件：收藏/绑定依赖数据库联合唯一索引，审批/取消订单依赖状态机 CAS（WHERE status='PENDING'），电商结算由后端先生成 order_no 返回给前端；Web3 链上交互则由协议层 nonce 天然保证同一笔交易不会重复上链。

层级 3 · 前端生成幂等键

无天然主键的高成本写请求

当接口同时满足「创建型 POST 且无法靠内容去重」、「高成本或强外部副作用」、「存在弱网/网关自动重试」三个条件时，就必须由客户端在触发意图的那一刻生成 UUID 透传。

典型代表：IM 聊天发消息（用户连续发两句“在吗”合法，但弱网重发同一句必须靠前端 client_msg_id 去重）、开放支付 API（如 Stripe 要求调用方传 Idempotency-Key），以及下面展开的 AI 流式对话与 Agent 写工具调用。
08 串联落地：AI 对话流与 Agent Tool Calling 的幂等实践 AI ENGINEERING PRACTICE

把前半部分的 SSE 流式对接 与后半部分的 幂等设计 合在一起，就能覆盖真实 AI 产品中两个最棘手的可靠性问题：

💬 1. AI 流式对话防重与断点恢复

  1. 前端生成 client_msg_id：用户每次按下回车发送消息时，前端立即生成 UUID 作为 Idempotency-Key。只要用户没有发新消息，弱网重试必须复用同一个 Key。
  2. 服务端先落库占位：服务端以 (conversation_id, client_msg_id) 唯一键写入一条状态为 streaming 的消息记录，再向上游模型发起流式请求。
  3. 同 Key 重试时的优雅处理：若原请求仍在生成（streaming），返回 409 或订阅同一条 Redis Stream / 内存广播流续接输出；若已完成（completed），直接返回已落库的完整回复，不再二次消耗 Token。

🛠️ 2. Agent Tool Calling 工具分级幂等

  1. 显式区分只读工具与写副作用工具：查询类工具（如 search_knowledge、get_order）天然幂等，可安全开启超时自动重试；写操作工具（如 create_ticket、send_webhook）必须在工具元数据中标记 side_effect: true。
  2. 确定性工具幂等键：由 Agent 运行时自动派生 tool_idem_key = sha256(run_id + step_index + tool_name + canonical_json(args)) 透传给下游业务接口。
  3. 高危写操作加人工确认：涉及真实资金或不可逆外部通知的工具，在幂等键之外叠加人工审批闸门（Human-in-the-Loop），防止模型幻觉本身触发错误指令。

✅ 生产上线自检清单

  • SSE 链路：是否设置 X-Accel-Buffering: no 并关闭该路由的 Gzip 整包压缩？
  • SSE 成本：后端是否监听 ctx.Done() / req.on('close') 及时取消上游 LLM 推理？
  • 前端解析：TextDecoder 是否开启 { stream: true } 且正确维护跨 Chunk 缓冲区？
  • 幂等兜底：是否避免只靠 Redis SET NX 裸奔，核心写链路具备数据库唯一索引或状态机兜底？
  • 死锁防护：PROCESSING 状态是否带有超时租约（locked_until），防止进程崩溃后永久卡死？
  • 参数校验：是否对 Idempotency-Key 绑定请求体哈希，防止调用方误用旧 Key 覆盖新请求？
09 Agent 上下文压缩时机、分业务方案与受保护红线 PART III · COMPACTION

在长程 Agent 对话或工具循环中，上下文窗口并非等到 95% 塞不下才需要压缩。实测中，大多数模型在上下文占满 50%~70% 且混杂大量历史报错与冗余工具输出时，就会出现注意力衰减（Context Rot）——指令遵循率下降、重复调用已执行过的工具，同时每轮推理延迟与输入费用同步抬升。压缩策略的设计需要围绕触发点、成本递进机制、业务选型与受保护红线四个维度展开。

📐 水位线精确计算公式（避免单轮中途撑爆）： 水位不是直接除以模型窗口总长，而是按 可用窗口 = 窗口总长 − 预留空间 计算，其中 预留空间 = 最大输出长度 (max_output_tokens) + 下一轮工具返回预估量。若不扣除预留，极易在某一轮生成半截触发截断或报错。

⏱️ 1. 五类主流压缩触发点对比

触发策略 典型阈值与工作方式 核心优势 潜在局限
双水位线触发
生产首选基准		 软水位（65%~70% 窗口）触发后台异步预压缩；硬水位（80%~85%）强制切换快照或截断。 兼顾低延迟与防溢出，用户基本无感知卡顿。 需维护主上下文与异步摘要快照的版本一致性。

🪜 2. 五级压缩机制阶梯（按工程与 Token 成本从低到高）

  1. 不进上下文（零额外推理）：大体积工具结果（长日志、整页 HTML、大 SQL 结果）直接落盘或入库，上下文只放摘要与读取句柄 ID，需要时再用工具按需读回。
  2. 规则裁剪（低成本）：清理早期工具输出并保留占位提示（如“结果已省略，可用工具重查”）；对重复内容去重；长日志只保留头尾与报错行。
  3. 结构化摘要（中成本，禁写散文）：用固定 Schema 抽取：① 用户目标与硬约束（保留原话 + 来源轮次）；② 已做决定及原因；③ 已完成与待办；④ 关键实体（ID/路径/数字/配置）；⑤ 试过但失败 / 已否决的方案（防止模型重复踩坑）；⑥ 未解决问题。
  4. 外部长期记忆（跨会话）：跨天偏好与情景片段写入外部记忆库，按需检索召回。
  5. 子 Agent 上下文隔离（高隔离）：把大量代码搜索、文档翻阅等脏活交给子 Agent 在独立窗口完成，只将精炼结论带回主上下文。

🚧 4. 压缩红线：绝对不能破坏的受保护内容

  • 顶部静态前缀（System Prompt + 工具 Schema）：改动顶部会直接击穿模型侧 Prefix Cache，使后续每轮重新全量计费。
  • 用户原始目标与硬约束（Hard Constraints）：如“禁止修改生产库”“输出必须为严格 JSON”。必须放在独立固定槽位原样保留，不可交给摘要模型自由改写。
  • 权限、身份与安全边界：如当前员工所属门店范围、租户隔离边界与角色权限，严禁在压缩中被省略或模糊。
  • 最近 3~5 轮完整原文与成对 Tool 结构：严禁按字节或条数硬切把 assistant(tool_use) 与 tool(tool_result) 切开，否则模型 API 会直接返回 400 协议错误。
  • 精确锚点实体：订单/任务 ID、精确文件路径、错误码、版本号与金额数字。压缩完成后可做一次实体核对，缺漏则自动补回。

🎯 5. 工程落地：用户先闲聊或中途改需求时，如何提取目标与硬约束

真实场景中用户往往先闲聊（“你好/在吗”）才说正事，或在第 5 轮追加限制、第 15 轮切换新话题，因此不能死板钉死第 1 句 messages[0]。工程上需先将业务硬参数（登录 Token 权限、表单勾选项、仓库 AGENTS.md 规范）由代码直接硬拼进受保护前缀，再把对话中产生的目标与约束建模为可演进的 SessionState，按成本从低到高选用三种抓取方式：

方式 1 · 懒抽取（最省钱）

压缩触发时统一提炼

短对话全量原文都在上下文里，模型自带判断力，无需每轮花钱抽目标。直到首次踩到 70% 软水位时，再由摘要器过滤闲聊、提炼 current_goal 与 constraints[]，后续只做增量 Patch。

方式 2 · 工作单工具

主模型调 update_task_state

为复杂任务 Agent 注册轻量状态工具（类似 TodoWrite）：约定纯闲聊不调用，明确任务/追加约束/切换话题时顺手更新工作单。零额外模型费用，且可直接渲染给用户确认纠偏。

方式 3 · 旁路小模型

每轮异步意图与槽位抽取

适合客服/门店接诊/CRM：后台用便宜小模型异步判定 chitchat / goal_defined / constraint_added / topic_switched，不阻塞主回复并实时沉淀结构化客户档案。

10 会话恢复、冷启动与热启动机制：双轨存储与锯齿压缩 SESSION LIFECYCLE

上线后的 Agent 很少是“一口气聊完就销毁”的，用户经常刷新页面、隔几小时再回来，或者服务端重启发布。理解热启动、冷启动与会话恢复的区别，决定了首字延迟和输入 Token 账单的控制上限：

HOT / WARM START

🔥 热启动（KV Cache 仍在）

会话仍在服务端内存/Redis 中，且模型推理侧的 Prefix Cache（KV Cache）尚未过期（常见 TTL 为 5~60 分钟）。此时只需追加最新一轮消息，前面数万 Token 直接命中缓存，TTFT 极低且输入费用享 0.5~5 折。

COLD START

❄️ 冷启动（全量 Prefill）

全新会话或隔了较长时间重新打开，推理侧 KV Cache 已淘汰。服务端需从磁盘/数据库加载 System Prompt、长期记忆目录与历史摘要，模型端必须重新跑一次全量 Prefill 计算，首轮延迟与输入成本都会明显跳高。

SESSION RECOVERY

♻️ 会话恢复（双轨 Checkpoint）

采用「全量原始日志 + 压缩快照 Checkpoint」双轨落盘：DB/JSONL 永久保留原始对话供审计与前端展示；每次压缩生成带版本号的 Checkpoint。恢复时只加载最新 Checkpoint + 其后增量消息，毫秒级重建上下文。

🔎 1. 如何判定进入「会话恢复」与加载组装顺序

三个恢复触发信号：① 客户端显式恢复（点开历史会话或 --resume）；② 请求带 session_id 但服务端内存/Redis 已无热状态（进程重启、换实例或缓存过期）；③ now - last_active_at 超过阈值（如 30 分钟或跨天）。此时厂商 Prompt Cache 多半已失效，重新组装上下文几乎没有额外缓存损失，反而是最便宜的压缩时机。

恢复时的 4 步组装顺序：
1. 当前最新版本的 System Prompt + 工具定义（不用历史旧版）；
2. 该会话已落盘的结构化摘要（无则现场生成并持久化）；
3. 从长期记忆中按需检索的相关事实；
4. 最近 N 轮完整原文（严格保证 tool_call / tool_result 成对）。

🛡️ 2. 会话恢复时必须重新校验的 4 项边界状态

  • 权限与身份重验：员工可能已调换门店或被回收权限，必须以当前请求 Token 为准，绝不轻信历史会话里的旧身份。
  • 未确认的写操作卡片：上次挂起未确认的审批/下单卡片，恢复时需检查是否过期，过期直接置为失效避免误提交。
  • 中断的流式回答：若上次 SSE 在半途断流，恢复时需显式标记为“已中断”，不将其当作完整回答喂给下一轮推理。
  • 时效性工具数据：库存、预约状态、余额等历史工具输出已过时，提示模型在决策前按需调用工具重新查询。

🏗️ 3. 根治摘要漂移的「状态与事实分离」三层架构

单纯靠“每次重写整份摘要”会让软信息变淡，单纯靠“分段向量检索”又容易漏召回或搞混时间因果。生产级推荐三层合用——常驻的只有「现在在干什么」，历史原文与业务事实一律按需取：

分层 存放内容与更新原则 是否常驻上下文 防失真关键做法
工作状态层 结构化工作摘要（目标、硬约束原话、待办、已否决方案） 常驻 按字段增量合并更新（Patch），标明来源轮次（如“第 5 轮”）
情景存档层 按任务阶段/话题切分的早期对话分段摘要 + 原始全文 按需检索 摘要作索引、命中取原文；结果带时间戳按时间排序
业务事实层 客户档案、订单、库存等实时业务数据（MySQL 等） 工具查库 单一真值源（Single Source of Truth），不靠摘要记忆

11 工程常见误区与四组量化评估指标 METRICS & TRADEOFFS

⚠️ 1. 压缩实现中最常见的 5 个工程误区

  1. 高频小步压缩反向烧钱：每多 1 轮就改写最前面的摘要，导致 Prefix Cache 命中率归零。应采用锯齿状策略：自然追加到 70% 后再一次性压回 20%。
  2. 摘要套摘要产生“传话失真”：对旧摘要反复再压缩，3 轮后硬约束丢光且滋生幻觉。应采用固定结构化 Schema 覆写，并锁定不可变约束槽位。
  3. 同步压缩阻塞主回复：踩到阈值时同步调摘要模型，用户发一句话干等 5~8 秒。应在软水位做后台异步预压缩，下一轮无缝切换。
  4. 按条数硬切破坏 Tool 配对：截断必须以完整的“用户提问 → 工具调用 → 全部工具结果 → 最终回复”为原子单元。
  5. 只压对话不压工具输出：Coding/Research 场景 70%+ Token 来自工具返回体，优先做 Tool Output 裁剪与外部化收益远大于对话摘要。

📊 2. 实际开发怎么权衡：盯住这 4 组量化指标

  • 成本与缓存效率：核心看 Prefix Cache 命中率 = cached_input / total_input（健康线通常 ≥ 70%）；压缩自身消耗的摘要模型费用应控制在单任务总成本的 5%~10% 以内。
  • 延迟体验：监控 P50 / P95 TTFT（首字延迟），观察触发压缩当轮是否出现明显延迟尖刺，用于验证异步预压缩是否生效。
  • 上下文质量（防压过头）：对比压缩前后的任务完成率，并重点统计约束遗忘率与重复工具调用率（若模型反复读刚才读过的文件，说明压得太狠）。
  • 上下文构成画像：统计 System / 对话 / Tool Outputs 三者占比；若 Tool Outputs 超过 60%，优先优化工具结果裁剪与外部化，而非纠结对话摘要 Prompt。

// 1. 每轮 LLM 调用结束后记录的观测指标（直接从模型响应 usage 与计时器采集）
interface TurnMetric {
  turnId: number;
  ttftMs: number;             // 从发请求到收到第一个 SSE delta 的耗时
  promptTokens: number;       // 本轮总输入 Token
  cachedTokens: number;       // 命中 Prefix Cache 的输入 Token（OpenAI/Anthropic/Gemini usage 均返回）
  toolOutputTokens: number;   // 本轮上下文里 role="tool" 消息累计占用的 Token
  compactionCostUsd: number;  // 本轮若触发摘要压缩，摘要模型额外花费（未触发为 0）
  turnCostUsd: number;        // 本轮主模型花费
  triggeredCompaction: boolean;
}

// 2. 重复工具调用检测器：用来量化“是不是压过头导致模型失忆重读”
class CompactionTracker {
  private metrics: TurnMetric[] = [];
  private seenReadTools = new Set<string>(); // 记录已调用过的只读工具签名
  private totalToolCalls = 0;
  private redundantToolCalls = 0;

  recordToolCall(toolName: string, args: Record<string, unknown>, isReadOnly: boolean) {
    this.totalToolCalls++;
    if (!isReadOnly) return;
    // 按 key 排序序列化，确保相同参数生成相同签名
    const sig = `${toolName}:${JSON.stringify(args, Object.keys(args).sort())}`;
    if (this.seenReadTools.has(sig)) {
      this.redundantToolCalls++; // 压缩后又重读同一文件/查同一条记录 → 失忆信号
    } else {
      this.seenReadTools.add(sig);
    }
  }

  recordTurn(m: TurnMetric) {
    this.metrics.push(m);
  }

  // 3. 聚合输出四组核心健康度指标，直接上报 Prometheus / 日志看板
  evaluateHealth() {
    const sum = (fn: (m: TurnMetric) => number) => this.metrics.reduce((a, b) => a + fn(b), 0);
    const totalPrompt = sum((m) => m.promptTokens) || 1;
    const totalCost = sum((m) => m.turnCostUsd) || 1e-6;

    const sortedTtft = this.metrics.map((m) => m.ttftMs).sort((a, b) => a - b);
    const p95TtftMs = sortedTtft[Math.floor(sortedTtft.length * 0.95)] ?? 0;

    const prefixCacheHitRate = sum((m) => m.cachedTokens) / totalPrompt;
    const compactionOverhead = sum((m) => m.compactionCostUsd) / totalCost;
    const toolOutputRatio = sum((m) => m.toolOutputTokens) / totalPrompt;
    const redundantToolRate = this.totalToolCalls ? this.redundantToolCalls / this.totalToolCalls : 0;

    return {
      prefixCacheHitRate: +(prefixCacheHitRate * 100).toFixed(1), // 目标 ≥ 70%
      compactionOverhead: +(compactionOverhead * 100).toFixed(1), // 目标 ≤ 10%
      p95TtftMs,                                                   // 检查压缩当轮有无尖刺
      redundantToolRate: +(redundantToolRate * 100).toFixed(1),   // 过高说明压丢了关键事实
      toolOutputRatio: +(toolOutputRatio * 100).toFixed(1),       // > 60% 优先裁剪工具输出
    };
  }
}

// 4. 锯齿状双水位线触发器（扣除最大输出与下一轮工具返回预留后计算有效水位）
function decideCompactionAction(
  currentTokens: number,
  maxWindow: number,
  reservedOutputTokens: number,
  estimatedNextToolTokens: number,
  hasAsyncSnapshot: boolean
) {
  const effectiveWindow = Math.max(1, maxWindow - reservedOutputTokens - estimatedNextToolTokens);
  const ratio = currentTokens / effectiveWindow;
  if (ratio >= 0.85) {
    // 硬水位：立刻切换到已准备好的异步快照；若还没算完则同步降级压缩回 ~20%
    return hasAsyncSnapshot ? 'SWITCH_TO_SNAPSHOT' : 'SYNC_COMPACT_NOW';
  }
  if (ratio >= 0.70 && !hasAsyncSnapshot) {
    // 软水位：先轻压缩旧工具结果，并在后台异步生成 Checkpoint 快照供后续切换
    return 'START_ASYNC_COMPACT';
  }
  return 'APPEND_ONLY'; // 20%~70% 区间只追加不改前缀，最大化 Prefix Cache 命中
}

🎤 面试速答提炼（三大核心追问话术）

  • 压缩时机与机制：“先用 窗口总长 − 输出预留 − 下一轮工具返回预估 算有效水位：到 70% 先轻裁剪旧工具结果，到 85% 再做结构化摘要；单条工具结果过大直接落盘留句柄，阶段结束把过程收成结论。机制按成本递增：落盘留句柄 → 裁剪 → 结构化摘要（含失败尝试与来源轮次）→ 长期记忆 → 子 Agent 隔离，并攒到水位批量压以保护 Prompt Cache。”
  • 会话恢复与冷热启动：“会话持久化落库并带 session_id，当服务端无热状态或空闲超时触发恢复时，用最新系统提示 + 已有摘要 + 记忆检索 + 最近 N 轮原文组装，同时重验当前权限、过期写操作卡片、中断流式回答与时效性工具数据。此时 Prompt Cache 多半已过期，也是成本最低的压缩窗口。”
  • 防摘要漂移（状态与事实分离）：“上下文只常驻按字段增量合并的结构化工作状态，业务事实一律通过工具查库保证单一真值源，更早对话按阶段存档，用摘要作检索索引、命中后回读原文并按时间戳排序。”
