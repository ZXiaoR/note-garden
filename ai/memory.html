01 核心背景：Anthropic 记忆三铁律 × Google 91.3 万次会话“分心税” 2026-11-06 FRONTIER REPORT

📌 Anthropic《The components of agent memory》三大工程铁律

为什么 Agent 聊久了要么撑爆上下文、要么新旧记忆冲突、要么被无关信息带偏？Anthropic 公开了 Claude 的记忆层工程实践：放弃无脑把历史聊天切碎塞进向量库，改用「极小常驻目录 + Wiki 双链真值库 + 离线 Dreaming 整理」：

Anthropic 记忆三铁律 核心工程约束与反直觉结论
① 环境可读的不记 凡是能查代码库、读配置文件、查 DB 实时拿到的事实严禁存入记忆；记忆只存“无法从环境直接读出的隐性策略、踩坑经验与架构规则”。
② 常驻层必须极小 注入 System Prompt 的只有 root/index.md（词条名 + 一句话摘要 <1k tokens），正文靠 Wiki 双链与混合检索按需拉取。
③ 强模型离线做梦 后台异步回看会话日志（Dreaming），让强模型自主判断记什么、同名覆写（Upsert）哪个冲突旧词条，效果远胜人工写死提取规则。

💡 两大厂报告合看的核心启示：

• 为什么不能全塞 Prompt？常驻上下文越臃肿、陈旧信息越多，Agent 越容易像看到遗留 TODO 一样分心跑偏，白烧 77% 预算。
• 为什么不能只增不删？传统向量库只 Insert 不 Update，旧错误假设永远留在库里干扰检索。

1. 三代 Agent 记忆存储范式硬核对比

对比维度 ❌ 单文件 (MEMORY.md) ❌ 传统碎块化 RAG ✅ Anthropic Wiki 结构
组织形态 单文件尾部无限追加 按 500 字死板切块入向量库 目录 index.md + 单主题单页 + [[双链]]

3. RRF（倒数排名融合）免调参公式

BM25 关键词检索分数无上限（擅长搜报错码/函数名），Vector 余弦相似度在 [-1, 1]（擅长搜模糊意图）。RRF 只看各自排第几名，不看绝对分：

RRF_Score(d) = 1 / (60 + rank_BM25) + 1 / (60 + rank_Vector)
💻 agent-wiki-memory.ts · 核心三件套实现 
export interface WikiPage {
  slug: string;          // 唯一词条 ID，如 "auth-token-gotchas"
  title: string;
  summary: string;       // 一句话摘要（仅此项进入常驻 index.md）
  content: string;       // Markdown 正文，内含 [[other-slug]] 双链
  linksTo: string[];     // 解析出的出链列表
  embedding?: number[];
}

export class AgentWikiMemory {
  private pages = new Map<string, WikiPage>();

  /** 【铁律 1】生成极小的常驻目录 (<1k tokens) */
  buildTinyIndexPrompt(): string {
    const items = [...this.pages.values()]
      .map(p => `- [[${p.slug}]] (${p.title}): ${p.summary}`);
    return [
      "## 长期记忆目录 (正文未加载，按需调 read_wiki 或 search_wiki)",
      ...items
    ].join("\n");
  }

  /** 【工具 A】精准读取单页 + 暴露 [[slug]] 双链供多跳跳转 */
  readWiki(slug: string): string {
    const p = this.pages.get(slug);
    if (!p) return `未找到 [[${slug}]]，请用 search_wiki 检索。`;
    const links = p.linksTo.length
      ? `\n\n🔗 关联词条: ${p.linksTo.map(s => `[[${s}]]`).join(", ")}` : "";
    return `# ${p.title}\n\n${p.content}${links}`;
  }

  /** 【工具 B】混合检索：BM25 + Vector + RRF 倒数排名融合 */
  async hybridSearch(query: string, topK = 5) {
    const bm25Hits = this.bm25Index.search(query, topK * 2);
    const qVec = await this.embedder.embed(query);
    const vecHits = [...this.pages.values()]
      .map(p => ({ slug: p.slug, score: this.cosine(qVec, p.embedding!) }))
      .sort((a, b) => b.score - a.score).slice(0, topK * 2);

    const K = 60, rrf = new Map<string, number>();
    bm25Hits.forEach((h, r) => rrf.set(h.slug, (rrf.get(h.slug) ?? 0) + 1 / (K + r + 1)));
    vecHits.forEach((h, r) => rrf.set(h.slug, (rrf.get(h.slug) ?? 0) + 1 / (K + r + 1)));

    return [...rrf.entries()].sort((a, b) => b[1] - a[1]).slice(0, topK);
  }

  /** 【离线做梦环】过滤环境事实，同名覆写 (UPSERT) 冲突旧词条 */
  async runOfflineDreaming(sessionLog: string, strongLLM: any) {
    const patches = await strongLLM.generatePatches({
      currentIndex: this.buildTinyIndexPrompt(),
      sessionLog,
      rules: [
        "1. 凡是能从代码/配置/DB直接读出的事实，严禁写入记忆！",
        "2. 若新会话推翻旧结论，直接同名覆写(UPSERT)对应 slug。"
      ]
    });
    for (const p of patches) await this.upsertPage(p);
  }
}
💡 批注 1：为什么先搜再读？
hybridSearch 只定位 Top-K 词条与摘要；真正阅读调 readWiki(slug) 拿完整正文与出链列表，防止残缺切片误导推理。
💡 批注 2：双链怎么自动解析？
每次 upsertPage 时用正则 /\[\[([a-z0-9-_]+)\]\]/g 自动提取正文双链存入 linksTo，无需额外维护图数据库。
04 生产落地的 6 大弊端与工程解药 (Trade-offs & Mitigations) ARCHITECT'S CRITICAL VIEW
PITFALL 01 · 覆写失忆

“做梦做歪”导致永久失忆

Wiki 强调原地覆写（Upsert）。若离线模型把“临时调试指令”误判成“永久新规”直接覆写旧页，正确经验会被永久抹除。

💊 解药：底层配 Git 版本控制，每次做梦即 git commit，支持 Diff 审计与回滚。
PITFALL 02 · 滞后窗口

离线做梦的异步滞后窗口

Dreaming 是异步跑的。用户在窗口 A 刚纠正错误，1 分钟后开窗口 B 干同样的活——此时还没做梦，Wiki 未更新，照样犯错。

💊 解药：加一层轻量 Hot Buffer 热缓冲，临时挂最近 3 次未归档会话的纠偏摘要。
PITFALL 03 · 工具调用税

多跳检索带来额外往返延迟

以前塞满 Prompt 1 次请求答完；现在变成 看目录→搜→读A→跳双链B→答，多出 3~4 轮工具往返，首字延迟显著增加。

💊 解药：支持数组批量读 read_wiki(["a","b"])，并在搜索结果里预取一跳双链摘要。
PITFALL 04 · 强模依赖

极度依赖旗舰强模型

小模型在线阶段经常“懒得查 Wiki”直接瞎编；离线阶段分不清环境事实与策略，最后又把代码片段塞进记忆库。

💊 解药：在线可用中等模型，但离线 Dreaming 整理环必须绑定旗舰强模型。
PITFALL 05 · 目录膨胀

长期运行后目录膨胀坍塌

假设 index.md < 1k tokens，但跑半年攒下 600 个词条后，目录本身膨胀到几万字，重新退化成大上下文污染。

💊 解药：引入 记忆衰减 GC，统计检索命中率，冷门词条移出常驻目录仅靠检索兜底。
PITFALL 06 · 并发写冲突

多会话并发做梦覆盖丢失

当团队共享记忆库或多子 Agent 并发结束会话时，多个离线 Dreaming 进程同时覆写同一篇 Wiki 会导致 Lost Update。

💊 解药：Dreaming 写入走 单消费者消息队列串行合并 或加 CAS 乐观锁。

☑️ 生产落地 5 步自检清单

  • ✅ 常驻目录 root/index.md 是否严格控制在 1,000 Tokens 以内？
  • ✅ 环境可读的实时状态（文件路径、表结构、当前配置）是否已从记忆库剔除？
  • ✅ 检索层是否同时配齐了 BM25 关键词 + Vector 语义 的 RRF 倒数排名融合？
  • ✅ 底层 Wiki 词条文件是否接入了 Git 自动 Commit 以防做梦误覆写？
  • ✅ 是否增加了轻量 Hot Buffer 热缓冲 弥补异步离线做梦的滞后窗口？
