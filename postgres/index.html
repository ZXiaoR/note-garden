0 · PostgreSQL 是什么 & 进程架构

PostgreSQL 是一个开源的对象-关系型数据库（ORDBMS），以严格遵循 SQL 标准、功能强大（丰富的数据类型、索引类型、窗口函数、CTE、扩展生态）著称，被称为"最先进的开源数据库"。

进程模型：多进程，不是多线程 PG 特色

与 MySQL 每连接一个线程不同，PostgreSQL 每个客户端连接由 postmaster（主进程）fork 出一个独立的后端进程（backend process）来服务。进程隔离性好、稳定（一个连接崩溃不影响别人），但每连接开销较大——所以生产环境几乎总要搭 连接池（PgBouncer）。

┌─────────────┐ 客户端连接 ──────▶│ postmaster │ 监听端口、fork 子进程、崩溃恢复 └──────┬──────┘ ┌──────────────────┼──────────────────┐ ┌────▼────┐ ┌────▼────┐ ┌────▼─────────┐ │backend 1│ │backend 2│ ... │ 后台辅助进程 │ │(会话进程)│ │(会话进程)│ ├──────────────┤ └────┬────┘ └────┬────┘ │ WAL Writer │ 刷 WAL │ │ │ Bgwriter │ 刷脏页 └────────┬─────────┘ │ Checkpointer │ 检查点 ▼ │ Autovacuum │ 自动清理死元组 ┌───────────────────────┐ │ Stats/Archiver ... │ │ Shared Buffers (共享内存)│◀────────┘ │ 数据页缓存 · WAL 缓冲 │ └───────────┬───────────┘ ▼ 刷盘 ┌───────────────────────┐ │ 磁盘：数据文件 · WAL 日志 │ └───────────────────────┘
组件作用
postmaster主进程，监听连接、fork backend、管理后台进程、崩溃恢复
backend 进程每个连接一个，执行该会话的所有 SQL
Shared Buffers共享内存里的数据页缓存（类似 MySQL 的 Buffer Pool），默认较小，生产要调大
WAL Writer把 WAL（预写日志）缓冲刷到磁盘
Bgwriter / Checkpointer把内存中的脏页写回磁盘 / 定期做检查点
Autovacuum⭐后台自动回收 MVCC 产生的死元组（见 第 10 章）
PostgreSQL 和 MySQL 最大的架构区别？
① 进程 vs 线程：PG 每连接一个进程，MySQL 每连接一个线程；② PG 是"单一存储引擎"深度优化，MySQL 是插件式引擎（InnoDB/MyISAM）；③ MVCC 实现不同：PG 把旧版本行直接留在数据表里、靠 VACUUM 回收；InnoDB 旧版本放 undo log。这点衍生出 PG 特有的"表膨胀"和 VACUUM 运维。

id serial PRIMARY KEY
-- 推荐：SQL 标准写法（PG 10+）

JSONB vs JSON ⭐面试高频

jsonjsonb（推荐）
存储原样存文本解析成二进制结构
写入快（不解析）略慢（要解析）
查询/取字段慢（每次重新解析）⭐快

-- jsonb 操作符
SELECT data->>'name' FROM t;            -- 取字段为 text
SELECT * FROM t WHERE data @> '{"vip":true}';  -- 包含
CREATE INDEX idx ON t USING GIN (data);        -- GIN 索引加速
一句话：除非你要原样保存用户提交的 JSON 文本，否则一律用 jsonb。
什么时候该用 jsonb，什么时候该老老实实拆列？
字段结构稳定、需要频繁查询/关联/约束的 → 拆成正式列（享受强类型、约束、索引、统计信息）。字段稀疏、schema 多变、整体读写的（如配置、埋点属性、第三方回包）→ jsonb。别把 jsonb 当成偷懒不建模的借口。

3 · DDL & 约束

CREATE TABLE users (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email     text        NOT NULL UNIQUE,
    age       int         CHECK (age >= 0),
    status    text        DEFAULT 'active',
    full_name text GENERATED ALWAYS AS (first || ' ' || last) STORED, -- 生成列
    created_at timestamptz DEFAULT now()
);

ALTER TABLE users ADD COLUMN phone text;          -- 加列
ALTER TABLE users ALTER COLUMN age SET NOT NULL;   -- 改约束
ALTER TABLE users RENAME COLUMN phone TO mobile;   -- 改名
DROP TABLE users;

约束一览

约束作用
PRIMARY KEY主键 = 唯一 + 非空，一表一个，自动建唯一索引
UNIQUE唯一（允许多个 NULL，因为 NULL≠NULL）
NOT NULL非空
CHECK自定义条件校验，如 CHECK (price > 0)
DEFAULT默认值
FOREIGN KEY外键，见 下一章
DDL 也在事务里！ PG 的 DDL（CREATE/ALTER/DROP）是事务性的，可以 BEGIN ... ALTER ... ROLLBACK——这是相对 MySQL（DDL 隐式提交）的一大优点，迁移脚本失败能整体回滚。
给大表加一列会锁表很久吗？
加一个带非易变默认值的列，PG 11+ 只改元数据、不重写全表，很快。但加列时若默认值是易变函数、或 ALTER COLUMN ... TYPE 改类型，会重写整表并持有 ACCESS EXCLUSIVE 锁，大表上很危险，要用灰度手法（加列→回填→加约束 NOT VALID 再 VALIDATE）。

4 · 表间关系

关系实现例子
一对一 1:1从表主键同时是外键（或唯一外键）用户 - 用户详情
一对多 1:N"多"的一方存外键用户 - 订单
多对多 M:N中间表存两个外键学生 - 课程（选课表）
-- 一对多：订单表引用用户
CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id  bigint REFERENCES users(id) ON DELETE CASCADE,
    amount   numeric(10,2)
);

外键的级联动作 ON DELETE / ON UPDATE

动作父行被删/改时
CASCADE子行跟着删/改
SET NULL子行外键置 NULL
RESTRICT / NO ACTION有子行则禁止删（默认）
范式速记：1NF 列不可再分 → 2NF 消除对主键的部分依赖 → 3NF 消除传递依赖。实战常适度反范式（冗余字段换查询性能），但要清楚代价是维护一致性。

5 · DML & 查询进阶 扩充

基础增删改 + PG 特色

INSERT INTO users(email) VALUES('a@x.com') RETURNING id;  -- ⭐插入后直接返回

-- ⭐UPSERT：存在则更新，不存在则插入
INSERT INTO users(email, status) VALUES('a@x.com','vip')
ON CONFLICT (email) DO UPDATE SET status = EXCLUDED.status;

UPDATE orders SET amount = amount*0.9 WHERE user_id = 1 RETURNING *;
DELETE FROM orders WHERE amount = 0;

JOIN 四种类型

INNER JOIN 两表都匹配的行 A ∩ B LEFT JOIN 左表全保留，右无则 NULL A（含不匹配） RIGHT JOIN 右表全保留 B（含不匹配） FULL JOIN 两边都保留 A ∪ B CROSS JOIN 笛卡尔积（无 ON） A × B

聚合：GROUP BY / HAVING

SELECT user_id, count(*), sum(amount)
FROM orders
GROUP BY user_id
HAVING sum(amount) > 1000;   -- HAVING 过滤分组后的结果（WHERE 过滤分组前的行）

窗口函数 ⭐PG 王牌，面试高频

普通聚合会把多行"压成一行"；窗口函数在保留每一行的同时，对一个"窗口"内的行做计算。语法核心是 OVER (PARTITION BY ... ORDER BY ...)。

-- 每个用户内，按金额排名（不压行）
SELECT user_id, amount,
       row_number() OVER (PARTITION BY user_id ORDER BY amount DESC) AS rn,
       rank()       OVER (PARTITION BY user_id ORDER BY amount DESC) AS rk,
       sum(amount)  OVER (PARTITION BY user_id) AS user_total
FROM orders;
函数作用
row_number()行号，连续不重复（1,2,3,4）
rank()排名，并列跳号（1,1,3）
dense_rank()排名，并列不跳号（1,1,2）
lag()/lead()取前一行/后一行的值（算环比、差值）
经典题："取每个分组里最新/最大的一条" → row_number() OVER(PARTITION BY 分组 ORDER BY 时间 DESC) 然后外层 WHERE rn = 1。

CTE：WITH 公共表表达式 + 递归

-- 普通 CTE：给子查询命名，提升可读性
WITH big_orders AS (
    SELECT user_id, sum(amount) t FROM orders GROUP BY user_id HAVING sum(amount)>1000
)
SELECT u.email, b.t FROM users u JOIN big_orders b ON u.id=b.user_id;

-- ⭐递归 CTE：查组织架构 / 树形结构 / 无限级分类
WITH RECURSIVE sub AS (
    SELECT id, name, parent_id FROM dept WHERE id = 1     -- 锚点
    UNION ALL
    SELECT d.id, d.name, d.parent_id
    FROM dept d JOIN sub ON d.parent_id = sub.id          -- 递归
)
SELECT * FROM sub;
WHERE、GROUP BY、HAVING、窗口函数、ORDER BY 的执行顺序？
FROM/JOIN → WHERE（行过滤）→ GROUP BY → HAVING（组过滤）→ 窗口函数 → SELECT → DISTINCT → ORDER BY → LIMIT。所以窗口函数不能直接写在 WHERE 里（那时还没算），要套一层子查询/CTE 再过滤。

6 · 事务 & MVCC & 隔离级别 重点扩充

ACID & 基本用法

A 原子性 全成功或全失败（靠 undo/回滚） C 一致性 约束不被破坏（结果目标） I 隔离性 并发事务互不干扰（靠 MVCC+锁） D 持久性 提交后不丢（靠 WAL） 
BEGIN;
  UPDATE account SET bal = bal-100 WHERE id=1;
  SAVEPOINT s1;                 -- 保存点
  UPDATE account SET bal = bal+100 WHERE id=2;
  ROLLBACK TO s1;              -- 回滚到保存点（部分回滚）
COMMIT;

MVCC：多版本并发控制 ⭐PG 核心，必考

目标：读不阻塞写，写不阻塞读。原理：每行数据带两个隐藏系统列——

隐藏列含义
xmin创建（插入/更新产生）这行版本的事务 ID
xmax删除/更新使这行版本失效的事务 ID（还有效时为 0）

更新 = 把旧行标记 xmax + 插入一条新版本行。旧版本不立刻删除，仍物理留在表里，供还需要它的老事务读取。每个事务开始时拿一个快照（snapshot），靠比较 xmin/xmax 和快照判断"这一版本我能不能看见"。

同一行 id=1 的多个版本（更新两次后）： 版本V1 xmin=100 xmax=105 bal=1000 ← 已被事务105改掉（旧） 版本V2 xmin=105 xmax=108 bal=900 ← 又被事务108改掉（旧） 版本V3 xmin=108 xmax=0 bal=800 ← 当前有效版本 事务 T（快照只看得到已提交的<108）→ 看到 V2；新事务 → 看到 V3 死掉的 V1/V2 = "死元组(dead tuple)"，等 VACUUM 回收
PG 的 MVCC 代价 → 表膨胀：旧版本堆在表里，更新/删除频繁的表会越来越大，必须靠 VACUUM 回收空间。这是 PG 和 InnoDB（旧版本放独立 undo log）最本质的区别，也是 PG 运维的核心话题。

四种隔离级别 & 并发问题

隔离级别脏读不可重复读幻读序列化异常
Read UncommittedPG 中❌不会*可能可能可能
Read Committed（默认）❌可能可能可能
Repeatable Read❌❌❌*可能
Serializable❌❌❌❌

* PG 特色：① PG 没有真正的"读未提交"，写了也当 Read Committed 用，所以脏读永不发生。② PG 的 Repeatable Read 用快照隔离，连幻读也一起挡掉了（比 SQL 标准要求的更强）。

  • 脏读：读到别人未提交的数据
  • 不可重复读：同一行两次读值不同（别人改了并提交）
  • 幻读：同一查询两次返回的行数不同（别人插了新行）
  • 序列化异常：多个事务并发的结果，无法对应任何一种串行执行顺序
BEGIN ISOLATION LEVEL REPEATABLE READ;  -- 设置隔离级别
Serializable 怎么实现的？ PG 用 SSI（可串行化快照隔离）：不是加读锁，而是监控事务间的读写依赖，一旦发现可能破坏可串行性的"危险环"，就让其中一个事务报错回滚（could not serialize access）。所以用 Serializable 的应用必须准备好重试。
Read Committed 下同一事务两次查询结果可能不同，为什么？
因为 Read Committed 下每条语句都拿一个新快照（看到语句开始那刻已提交的数据）。期间别的事务提交了改动，第二条语句就看得见 → 不可重复读/幻读。要整个事务内视图一致，用 Repeatable Read（事务级快照，只在事务开始时取一次）。
更新同一行时，两个事务会怎样？
写写冲突要靠行锁：先改的事务持有行锁，后者阻塞等待。等前者提交后：Read Committed 下后者会基于最新值重新执行（不报错）；Repeatable Read/Serializable 下后者会报 could not serialize access due to concurrent update 需重试。

7 · 锁 新增

MVCC 解决了大多数读写并发（读不加锁），但写写并发仍要靠锁。

行级锁（显式加）

语法含义场景
FOR UPDATE排他行锁，别人不能改/加同类锁先查后改，防并发覆盖
FOR SHARE共享行锁，别人可读不可改保证读到的行事务内不被改
FOR UPDATE SKIP LOCKED跳过已被锁的行⭐任务队列抢单，不阻塞
FOR UPDATE NOWAIT锁不到立即报错不想等
-- 悲观锁：库存扣减经典写法
BEGIN;
  SELECT stock FROM product WHERE id=1 FOR UPDATE;  -- 锁住这行
  UPDATE product SET stock=stock-1 WHERE id=1;
COMMIT;

表级锁 & 死锁

DDL、VACUUM FULL 等会加表锁（最强是 ACCESS EXCLUSIVE，连读都挡）。死锁：A 持锁1 等锁2，B 持锁2 等锁1。PG 有死锁检测，会自动选一个事务回滚报 deadlock detected。

防死锁：① 让所有事务按固定顺序访问资源；② 事务尽量短小；③ 减少交互式长事务。

乐观锁 vs 悲观锁

悲观锁乐观锁
思路先加锁再操作（FOR UPDATE）不加锁，提交时用版本号/CAS 校验
实现数据库行锁UPDATE ... SET v=v+1 WHERE id=? AND v=?，看影响行数
适用写冲突多写冲突少（冲突了就重试）

8 · 索引 扩充

PG 默认索引是 B-tree，但它提供的索引类型远比常规数据库丰富——这是面试区分度所在。

六种索引类型 ⭐PG 特色

类型适合典型场景
B-tree（默认）= < > BETWEEN 排序绝大多数场景、主键、范围查询
Hash只等值 =等值查询（PG 10+ 才支持崩溃安全，实践中 B-tree 已够用，少用）
GIN一个字段含多个值时的包含查询⭐jsonb、数组、全文检索
GiST几何/范围/相似度地理位置（PostGIS）、范围类型重叠
SP-GiST非平衡树结构IP 前缀、四叉树等特殊结构
BRIN物理有序的超大表⭐时序/日志表（只存块范围，索引极小）

索引变体

-- 复合索引（遵守最左前缀）
CREATE INDEX ON orders (user_id, created_at);
-- 唯一索引
CREATE UNIQUE INDEX ON users (email);
-- ⭐部分索引：只给满足条件的行建，索引更小
CREATE INDEX ON orders (user_id) WHERE status = 'active';
-- ⭐表达式索引：对函数结果建索引
CREATE INDEX ON users (lower(email));
-- ⭐覆盖索引：INCLUDE 把额外列塞进索引，实现 Index Only Scan
CREATE INDEX ON orders (user_id) INCLUDE (amount);
-- ⭐不锁表建索引（生产必用，但更慢）
CREATE INDEX CONCURRENTLY ON orders (user_id);

索引失效常见场景 ⭐面试必问

  • 对索引列用函数/运算：WHERE lower(name)=...（除非建了表达式索引）
  • 复合索引不满足最左前缀：索引 (a,b)，只查 b 用不上
  • LIKE '%xx' 以通配符开头（'xx%' 可以走）
  • 类型隐式转换：列是 text 却用数字比
  • 低区分度列（如性别）+ 大量匹配行 → 优化器算了算不如全表扫，主动放弃索引（这是正确决策，不是失效）
  • OR 条件某一侧无索引 → 可能全表扫（可用 UNION 或 BitmapOr 改写）
什么是回表？PG 里怎么理解？
二级索引叶子只存索引列 + 行位置（PG 里是 ctid，物理位置）。查到后要拿 ctid 回堆表（heap）取整行，这就是回表。用覆盖索引（INCLUDE / Index Only Scan）可避免回表。注意：PG 的 Index Only Scan 还要查 visibility map 确认这页所有行都可见，否则仍要回表——所以刚大批更新过、没 VACUUM 的表，Index Only Scan 会退化。
建索引的代价是什么？
① 占额外磁盘；② 拖慢写入（每次增删改都要维护索引）；③ PG 里更新还可能因索引导致无法走 HOT 优化（见 VACUUM 章），加剧膨胀。所以索引不是越多越好，按查询需要建。

9 · 执行计划 EXPLAIN & 优化 新增

EXPLAIN            SELECT ...   -- 只看计划（估算，不执行）
EXPLAIN ANALYZE    SELECT ...   -- ⭐真正执行并给出实际耗时/行数
EXPLAIN (ANALYZE, BUFFERS) ...  -- 还看缓存命中/磁盘读

怎么读计划

Seq Scan on orders  (cost=0.00..18.50 rows=850 width=32)
                          │        │        └ 每行字节
                          │        └ 估算返回行数
      启动成本 ───────────┘   └───── 总成本（任意单位，越小越好）

看 EXPLAIN ANALYZE 时，重点对比"估算 rows" vs "实际 rows"：差得离谱说明统计信息过时，ANALYZE 表名 更新统计后计划往往就对了。

常见节点

扫描方式含义
Seq Scan全表扫描（小表 or 要读大部分行时反而更优）
Index Scan走索引 + 回表取行
Index Only Scan⭐只读索引不回表（覆盖索引）
Bitmap Index/Heap Scan命中行较多时，先攒位图再批量回表，减少随机 IO
Join 方式适合
Nested Loop一边行数很少
Hash Join大表等值连接，无序
Merge Join两边都已按连接键有序
优化排查清单：① EXPLAIN ANALYZE 找最慢节点；② 估算/实际行数偏差大 → ANALYZE；③ 该走索引却 Seq Scan → 查索引是否失效、区分度、统计信息；④ 装 pg_stat_statements 扩展找出全库最耗时的 SQL。
为什么有索引优化器还选全表扫描？
优化器基于成本决策：当查询要返回表中很大比例的行时，走索引意味着大量随机 IO + 回表，反而比顺序全表扫更慢。所以此时选 Seq Scan 是正确的。若你确信统计信息过时导致误判，先 ANALYZE。

10 · VACUUM & 表膨胀 新增 · PG 独有必考

承接 MVCC：更新/删除会留下死元组（dead tuple），它们占着空间却没人再读。VACUUM 就是回收它们的清道夫。

命令做什么是否锁表
VACUUM标记死元组空间可复用（空间还给表自己，不还给操作系统）❌ 不阻塞读写
VACUUM FULL重写整表、把空间真正还给 OS⭐ACCESS EXCLUSIVE 全表锁，生产慎用
ANALYZE更新统计信息（给优化器用）❌
autovacuum后台进程，自动触发上面的 VACUUM+ANALYZE❌

三个必须知道的概念

① 表膨胀（Bloat）

死元组没及时回收 → 表和索引物理体积远大于实际数据 → 扫描变慢、缓存效率下降。高频更新表要保证 autovacuum 跟得上，必要时调低触发阈值。

② 事务 ID 回卷（Transaction ID Wraparound）⭐经典事故题

PG 事务 ID 是 32 位（约 42 亿），会用完并"回卷"。MVCC 靠比较事务 ID 判断可见性，一旦回卷，老数据可能突然"看不见"→ 灾难。VACUUM 会把足够老的行 freeze（冻结） 成"对所有事务永远可见"，从而防止回卷。如果 autovacuum 长期没跑，PG 会强制警告甚至停库保护。

③ HOT 更新（Heap-Only Tuple）

优化：如果更新没有改到任何索引列，且同一页有空间，新版本就放同页且不更新索引，减少索引膨胀。这也是"别建无用索引"的又一理由——索引越多越难触发 HOT。

面试要点：被问"PG 有什么运维坑" → 答 MVCC 导致表膨胀 + 事务 ID 回卷，都要靠 VACUUM/autovacuum 治理。这是 PG 区别于其他库最有辨识度的答案。
删了很多行，为什么表文件大小没变小？
普通 VACUUM 只把空间标记为"可复用"留给这张表后续插入，不把磁盘还给操作系统。要真正缩小文件得用 VACUUM FULL（会锁表重写）或 pg_repack（在线重组，不长时间锁表，生产推荐）。

11 · 拓展知识

视图 & 物化视图

视图 VIEW物化视图 MATERIALIZED VIEW
本质存的是一段查询，每次查实时执行把结果物理存下来
数据新鲜度永远最新要 REFRESH 才更新
性能取决于底层查询⭐快（预计算），适合重报表

函数 / 存储过程 / 触发器

  • 函数（PL/pgSQL）：把逻辑封装在库内，CREATE FUNCTION ... RETURNS ...
  • 存储过程（PG 11+ CREATE PROCEDURE）：可在内部管理事务（COMMIT/ROLLBACK），函数不行
  • 触发器：在 INSERT/UPDATE/DELETE 前后自动执行函数，如自动维护 updated_at、审计日志

WAL（预写日志）

Write-Ahead Log：改数据前先把变更写 WAL 并落盘，再改内存页（脏页稍后异步刷）。作用：① 持久性/崩溃恢复（宕机后重放 WAL）；② 流复制的数据源；③ 时间点恢复（PITR）。类比 MySQL 的 redo log。

表分区（Partitioning）

把大表按范围/列表/哈希拆成子表，查询时只扫相关分区（分区裁剪），也方便按分区归档删除。

CREATE TABLE logs (id bigint, ts timestamptz) PARTITION BY RANGE (ts);
CREATE TABLE logs_2026 PARTITION OF logs FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

备份 & 高可用

  • pg_dump / pg_restore：逻辑备份（导出 SQL），适合单库迁移
  • pg_basebackup：物理备份，配合 WAL 归档做 PITR
  • 流复制（Streaming Replication）：主库把 WAL 实时传给备库，实现读写分离 + 故障切换（主备同步/异步可选）
  • 扩展（Extension）：CREATE EXTENSION 装 PostGIS（地理）、pg_stat_statements（慢查询）、pgvector（向量检索）等

高频面试速记 🎯

  • PG vs 常规库最大特色：多进程模型、MVCC 旧版本留在表里（→ 表膨胀 → 靠 VACUUM）、索引类型丰富（GIN/GiST/BRIN）、DDL 事务化、窗口函数/CTE 强。
  • MVCC：每行带 xmin/xmax，更新=旧行标记+插新行，靠快照判可见性；读不阻塞写。
  • 隔离级别：默认 Read Committed；PG 无真正读未提交（无脏读）；Repeatable Read 用快照连幻读一起挡；Serializable 用 SSI，要准备重试。
  • VACUUM：回收死元组防膨胀 + freeze 防事务 ID 回卷；VACUUM FULL 锁表慎用，在线用 pg_repack。
  • 索引：默认 B-tree；jsonb/数组/全文用 GIN；超大时序表用 BRIN；覆盖索引 INCLUDE → Index Only Scan；生产建索引用 CONCURRENTLY。
  • 索引失效：函数运算列、非最左前缀、前导 %、类型转换、低区分度。
  • EXPLAIN ANALYZE：比估算 vs 实际行数；行数偏差大先 ANALYZE；关注 Seq/Index/Bitmap Scan 和 Nested Loop/Hash/Merge Join。
  • 取每组最新一条：row_number() OVER(PARTITION BY .. ORDER BY .. DESC) + 外层 WHERE rn=1。
  • UPSERT：INSERT ... ON CONFLICT ... DO UPDATE；抢单队列：FOR UPDATE SKIP LOCKED。
  • 金额用 numeric 不用 float；时间跨时区用 timestamptz；字符串直接用 text。
