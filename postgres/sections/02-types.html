🧬 02.1 · 标量类型：整数自增、精确十进制金额、文本、带时区时间戳与类型转换语法

🧬 02.1 核心标量数据类型选型表

在设计 PostgreSQL 表结构时，选择合适的数据类型既能节省存储空间，也能利用数据库层的类型约束提前拦截脏数据。下表汇总了日常建表最常用的标量类型与选型建议：

数据类别 类型名称与字节数 选型规范与日常注意事项
整数与自增 smallint (2B) / integer (4B) / bigint (8B) integer 上限约为 21.4 亿（231 - 1）。业务主键、订单流水或埋点表建议统一优先使用 bigint，避免数据量增长后在线修改主键列类型引发全表重写。
GENERATED ALWAYS AS IDENTITY vs serial 推荐使用 SQL 标准语法 bigint GENERATED ALWAYS AS IDENTITY。早期写法 serial / bigserial 是语法宏，在导出备份或管理序列（SEQUENCE）权限时不如标准语法清晰，且默认无法阻止手动插入显式 ID 导致序列冲突。
小数与金额 numeric(p, s) / decimal(p, s) 十进制精确存储（p 为总有效位数，s 为小数位数，如 numeric(12, 2)）。凡涉及金额、账户余额、税率与账务计算均应使用此类型，不会产生精度误差。
real (4B) / double precision (8B) 遵循 IEEE 754 标准的二进制浮点数，计算速度快但存在二进制舍入误差（如 0.1 + 0.2 不严格等于 0.3），仅用于科学计算或监控指标，不用于存储金额。
字符串文本 text vs varchar(n) 在 PostgreSQL 中，text 与 varchar(n) 底层使用完全相同的可变长结构体（varlena），读写性能一致。若无特殊长度限制可直接使用 text；若需限制长度，可使用 varchar(100) 或 text CHECK (length(col) <= 100)（后者后续调大上限无需锁表改类型）。
char(n) 定长字符串，内容不足 n 个字符时会自动在末尾填充空格，既浪费空间又容易在字符串比较时引发歧义，日常开发不建议使用。
时间与日期 timestamptz（8B，推荐） 全称 timestamp with time zone。写入时统一转换为 UTC 微秒时间戳落盘，查询输出时自动按当前会话的 TimeZone 设置转换为对应时区时间，跨时区与现代业务系统首选。
timestamp / date / time / interval timestamp（不带时区）不保存时区上下文，服务器迁移时区时容易引发时间偏移；date 存纯日期（如生日），interval 表示时间跨度（如 now() - INTERVAL '7 days'）。
布尔与唯一标识 boolean (1B) / uuid (16B) boolean 取值为 true / false / NULL；uuid 原生以 16 字节二进制存储（比存 36 字符文本节省一半空间，且 PG 13+ 内置 gen_random_uuid() 函数，PG 17+ 原生支持按时间有序的 uuidv7 生态）。
📖 语法说明：双冒号类型转换操作符 ::
在阅读 PostgreSQL 代码时，经常会看到形如 '2026-11-15'::date、'123'::int 或 '{"a":1}'::jsonb 的写法。这里的双冒号 值::目标类型 是 PostgreSQL 提供的简写类型转换语法，完全等价于 SQL 标准的 CAST('123' AS int)，书写更加简洁直观。
📦 02.2 · 特色类型：JSONB 结构化文档、原生数组 text[] 与范围类型 tstzrange 的日常读写

📦 02.2 JSONB、数组与范围类型的日常操作

PostgreSQL 提供了两种 JSON 类型：json（原封不动保存原始文本，每次查询都要重新解析）与 jsonb（写入时解析为二进制结构化存储，去除多余空格与重复键，支持按键偏移快速读取与建立 GIN 索引）。在日常业务开发中，除极少数需要严格保留原始空格或键顺序的审计日志外，统一选用 jsonb。

🔍 JSONB 与数组的常用操作符对照表

操作符 / 函数 调用示例 返回类型与含义说明
-> profile -> 'address' 按对象键名（或数组下标）提取子元素，返回值仍为带引号的 jsonb 类型（用于继续链式向下取值）。
->> profile ->> 'city' 提取字段并直接转为纯文本 text 类型（去掉外层 JSON 双引号，适合用于展示或字符串比较）。
@>（包含） profile @> '{"vip": true}' 判断左侧 jsonb（或数组 tags @> ARRAY['go']）是否完整包含右侧的子结构，可直接命中 GIN 索引。
? / ?| / ?& profile ? 'phone' 判断 jsonb 顶层是否存在指定键名 'phone'（?| 为存在任意一个键，?& 为同时存在所有键）。
jsonb_set() / || jsonb_set(profile, '{vip}', 'true') 局部修改嵌套路径的值，或使用连接符 profile || '{"level": 2}'::jsonb 合并更新顶层键值，以及用 profile - 'temp_key' 删除指定键。
&&（重叠） tags && ARRAY['pg', 'sql'] 判断两个数组是否存在至少一个公共元素，或判断两个时间范围 tstzrange 是否存在时段重叠。
🐘 jsonb_array_range.sql · 特色类型建表与查询实战 
-- 1. 建表：同时包含 IDENTITY 自增、text[] 数组与 jsonb 扩展属性
CREATE TABLE user_profiles (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text   NOT NULL UNIQUE,
  tags       text[] NOT NULL DEFAULT '{}',
  profile    jsonb  NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 2. 插入带数组与嵌套 JSON 的数据
INSERT INTO user_profiles (email, tags, profile)
VALUES (
  'alice@example.com',
  ARRAY['golang', 'postgres'],
  '{"vip": true, "level": 3, "address": {"city": "Shanghai"}}'
);

-- 3. 提取嵌套字段 ( -> 返回 jsonb, ->> 返回 text ) 与包含过滤 (@>)
SELECT email,
       profile -> 'address' ->> 'city' AS city
FROM user_profiles
WHERE profile @> '{"vip": true, "level": 3}'
  AND tags @> ARRAY['postgres'];

-- 4. 局部修改 JSONB 中的字段值并追加数组元素
UPDATE user_profiles
SET profile = jsonb_set(profile, '{address,city}', '"Beijing"'),
    tags    = array_append(tags, 'ai')
WHERE email = 'alice@example.com';
⚖️ 建模边界建议：什么时候用独立关系列，什么时候用 jsonb？
• 优先拆为独立关系列：核心业务状态、高频用于 JOIN 关联或 ORDER BY 排序的字段、需要外键或非空唯一约束的字段，拆成独立列能让查询优化器收集精确的列级统计信息。
• 适合放入 jsonb：不同品类商品的动态扩展规格、用户个性化偏好配置、第三方回调报文存档等半结构化稀疏属性。

🧱 02.3 DDL 建表约束、事务性 DDL 与多表关系建模

1. 建表约束、生成列与外键级联示例

🐘 ddl_constraints_and_relations.sql 
-- 开启事务包裹 DDL：若中途任意语句报错，整组建表/改表可原子回滚
BEGIN;

CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text   NOT NULL UNIQUE,
  age        int    CHECK (age >= 0 AND age <= 150),
  first_name text   NOT NULL,
  last_name  text   NOT NULL,
  -- STORED 生成列：由其他列自动拼接计算并持久化存储
  full_name  text   GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED
);

-- 一对多关系 (1:N)：一个客户拥有多笔订单，外键建在“多”的一方
CREATE TABLE customer_orders (
  id          bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint        NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  amount      numeric(12,2) NOT NULL CHECK (amount >= 0),
  created_at  timestamptz   NOT NULL DEFAULT now()
);

-- 为外键列显式创建索引（PostgreSQL 不会自动为外键列建索引）
CREATE INDEX idx_cust_orders_cid ON customer_orders (customer_id);

COMMIT;

2. 三种表间关系设计与外键删除策略

关系类型 / 外键动作 建表实现方式与行为说明
一对一 (1:1) 子表的主键同时作为指向父表的外键，或者在外键列上添加 UNIQUE 唯一约束（例如将不常读取的实名认证长字段拆分到 user_kyc 扩展表）。
一对多 (1:N) 在“多”的子表上定义外键列（如 customer_orders.customer_id 引用 customers.id）。注意：PostgreSQL 只会自动为主键和 UNIQUE 列建索引，不会自动为外键列建索引，请务必手动为外键列建立索引以加速关联查询与父表删除检查。
多对多 (M:N) 建立独立的中间关联表（如 student_courses），包含两个外键列并声明为复合主键 PRIMARY KEY (student_id, course_id)。
ON DELETE RESTRICT / NO ACTION（默认） 当尝试删除父表记录时，如果子表中仍存在引用该记录的行，数据库直接报错拒绝删除，防止产生孤儿数据（账务与订单表常用）。
ON DELETE CASCADE / SET NULL 父表记录删除时：CASCADE 自动级联删除子表关联行（适合从属明细表）；SET NULL 将子表外键列置为 NULL。

🛠️ 02.4 DDL 表结构日常管理与 DELETE / TRUNCATE / DROP 对比

🐘 pg_ddl_ops.sql · PostgreSQL 表结构修改、复制与清空语法 
-- 1. 修改表结构（新增列 / 改类型 USING 显式转换 / 改默认值 / 重命名列 / 删列）
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS phone varchar(20),
  ALTER COLUMN balance TYPE numeric(14, 2),
  ALTER COLUMN status SET DEFAULT 1,
  DROP COLUMN IF EXISTS legacy_flag;

ALTER TABLE users RENAME COLUMN nick TO nickname;

-- 2. 复制表结构（INCLUDING ALL 会连同主键、索引、约束、默认值与注释一并复制）
CREATE TABLE users_template (LIKE users INCLUDING ALL);

-- 3. 快速清空整表并重置自增序列（RESTART IDENTITY）
TRUNCATE TABLE users_template RESTART IDENTITY CASCADE;
DROP TABLE IF EXISTS users_template;
对比维度 DELETE FROM t TRUNCATE TABLE t DROP TABLE t
操作效果 支持 WHERE 按条件逐行标记删除（生成死元组 Dead Tuple），保留表结构 快速分配一个全新的空底层物理数据文件（relfilenode），清空全表行，保留表结构 彻底删除表元数据、索引与底层数据文件
事务回滚支持 支持事务回滚（ROLLBACK） PostgreSQL 特色：同样支持在事务内 ROLLBACK 回滚恢复（因旧物理文件直到事务提交才真正删除） 支持在事务内 ROLLBACK 回滚恢复（Transactional DDL）
序列与空间释放 不重置序列；死元组占用的磁盘空间需等待 VACUUM 清理复用 加 RESTART IDENTITY 可重置自增序列；提交后立即将磁盘空间归还操作系统 提交后立即释放全部磁盘空间
