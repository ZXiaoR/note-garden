❓ 02.1 · 为什么在 PG 里字符串推荐直接用 text？JSON 和 JSONB 底层差在哪？

🧬 02.1 核心数据类型选型表（避坑指南）

PostgreSQL 的类型系统极其严谨且丰富。掌握下面这张选型表，能帮你避开 90% 的建表坏味道：

大类 类型名称 底层原理与生产选型建议
整数与自增 smallint / integer / bigint 分别占 2 / 4 / 8 字节。业务主键或增长较快的流水表一律优先用 bigint，防止 21 亿溢出后锁表改类型。
GENERATED ALWAYS AS IDENTITY vs serial ⭐ PG 10+ 强烈推荐 SQL 标准写法 bigint GENERATED ALWAYS AS IDENTITY。旧写法 serial / bigserial 只是宏语法糖，底层创建的 SEQUENCE 权限与归属在 pg_dump 或切表时容易脱节，且无法禁止手动显式塞 ID。
小数与金额 numeric(p, s) / decimal ⭐ 十进制精确存储，涉及金额、账务、费率必用，绝不丢失精度。
real / double precision IEEE 754 二进制浮点数（4 / 8 字节），存在二进制舍入误差（如 0.1 + 0.2 ≠ 0.3），仅用于科学计算或指标监控，严禁存钱。
字符串 text vs varchar(n) ⭐ PG 特色：两者在底层完全共用同一个 C 结构 varlena，性能 100% 相同！ varchar(n) 反而多一步长度检查开销。除非业务有硬性标准约束，否则在 PG 中直接用 text（如需限长也可加 CHECK (length(col) <= 100)，日后放宽上限无需重写表）。
char(n) 定长字符串，不足会自动补空格，既费空间又容易引发尾部空格比较 Bug，生产基本不用。
时间与日期 timestamptz（推荐） ⭐ timestamp with time zone（8 字节）：落盘统一转为 UTC 微秒时间戳存储，读取时自动按当前会话 TimeZone 转换。全球化与跨时区系统首选。
timestamp / date / time timestamp 不存时区上下文，服务器或客户端改时区极易算错时间差，仅适合纯本地日历字面量。
PG 王牌特色类型 uuid 原生 16 字节二进制存储（比存 36 字符文本省一半空间），内置 gen_random_uuid()（PG 13+ 免装扩展）。
int[] / text[] 数组 ⭐ 一等公民数组类型：如文章标签 tags text[]，支持 @>（包含）、&&（重叠）操作符并可直接建 GIN 倒排索引，免去为简单标签建关联中间表。
int4range / tstzrange ⭐ 范围类型（Range Types）：一个字段直接表示区间 [2026-11-12 09:00, 2026-11-12 10:30)，配合 GiST 排他约束可在数据库层根绝“会议室/酒店房间时间段双重预订”。
json / jsonb ⭐ 见下方专项拆解：生产几乎一律选二进制结构化存储的 jsonb。

🔥 面试高频：JSONB vs JSON 深度对比与 GIN 索引实战

对比维度 json（文本原样） ⭐ jsonb（二进制分解）
底层存储 把原始 JSON 字符串原封不动存下 解析为二进制树形结构（含键偏移字典）
写入速度 快（无需语法树拆解） 略慢一点点（写入时完成解析与去重）
查询与取字段 慢（每次读取都要重新完整解析） ⭐ 极快（按二进制偏移直接跳读）
空格/键序/重复键 完全保留原始格式与重复键 去除多余空白、键按序重排、重复键只留最后一个
索引与局部更新 不支持 GIN 索引，不支持 jsonb_set ⭐ 支持 GIN 倒排索引与 @> 包含检索
💡 超大字段怎么存？（TOAST 机制）：
PG 数据页固定为 8 KiB，不允许单行跨页。当你的 text 或 jsonb 超过约 2 KiB 时，PG 会自动触发 TOAST（The Oversized-Attribute Storage Technique）：先用 LZ4 / pglz 压缩，若仍超标则自动切成块存进附属的隐藏 TOAST 表，主表只留一个 18 字节指针！如果只 SELECT id, status 而不查大字段列，PG 根本不会去读 TOAST 表，性能极高（所以严禁无脑 SELECT *）。
🐘 jsonb_and_identity.sql · 标准建表与 JSONB 查询 
-- 1. 推荐：IDENTITY 标准自增 + jsonb + 数组
CREATE TABLE user_profiles (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text NOT NULL UNIQUE,
  tags       text[] DEFAULT '{}',
  profile    jsonb  NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 2. JSONB 核心操作符：-> 返回 jsonb，->> 返回 text
SELECT profile->'address'->>'city' AS city
FROM user_profiles
WHERE profile @> '{"vip": true, "level": 3}'   -- @> 是否包含子 JSON
  AND profile ? 'phone'                        -- ? 是否存在顶层键
  AND tags @> ARRAY['golang', 'postgres'];    -- 数组包含

-- 3. 建立 GIN 倒排索引加速 @> 与 ? 查询
CREATE INDEX idx_profiles_gin ON user_profiles USING GIN (profile);
CREATE INDEX idx_tags_gin     ON user_profiles USING GIN (tags);
❓ 面试自测：既然 JSONB 这么强，还支持 GIN 索引，什么时候该用 JSONB、什么时候必须老老实实拆成独立列？
  • 必须拆成正式关系列：字段结构稳定、需要高频做范围过滤/排序/JOIN 关联、需要外键或非空唯一约束、需要优化器收集精确的列级统计信息（直方图）来做执行计划估算的字段。
  • 适合放进 jsonb：稀疏属性（如不同品类的商品扩展参数）、Schema 频繁动态变化的用研埋点/用户偏好设置、第三方 Webhook 原始回包存档。切忌为了偷懒不写迁移脚本而把核心业务表做成“单列大 JSONB”，否则不仅丧失类型约束，每次局部修改 `jsonb` 都会引发整行新版本重写与 TOAST 膨胀。
❓ 02.2 · 为什么说 PG 的 DDL 比 MySQL 安全得多？给上亿行的大表加列或加约束怎么避免锁表事故？

🧱 02.2 DDL 约束、事务性 DDL、大表无锁变更与表关系

1. 常用 DDL 与六大约束

🐘 DDL 建表、生成列与外键级联 
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text   NOT NULL UNIQUE,
  age        int    CHECK (age >= 0),
  first_name text   NOT NULL,
  last_name  text   NOT NULL,
  -- STORED 生成列：自动计算并落盘
  full_name  text   GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED
);

-- 一对多关系 (1:N)：订单表外键指向用户表
CREATE TABLE orders (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  amount   numeric(12, 2) NOT NULL CHECK (amount >= 0)
);
⭐ PG 独门优势：DDL 也是事务性的（Transactional DDL）！
在 MySQL 中，任何 ALTER / CREATE / DROP 都会触发隐式提交（Implicit Commit），脚本跑到一半报错无法回滚；而在 PostgreSQL 中，系统目录表（Catalog，如 pg_class、pg_attribute）本身也受 MVCC 保护，你可以直接写：
BEGIN; ALTER TABLE ...; DROP TABLE ...; ROLLBACK;（除 CREATE DATABASE、VACUUM、CREATE INDEX CONCURRENTLY 等少数命令外，全部可原子回滚！）。

2. 表间关系（1:1 / 1:N / M:N）与外键级联

关系 / 外键策略 落地实现与行为说明
一对一 (1:1) 子表的主键同时作为外键，或外键列加 UNIQUE 约束（如 users 与 user_kyc_detail）。
一对多 (1:N) 在“多”的一方存外键（如 orders.user_id 引用 users.id）。切记：PG 不会自动给外键列建索引，关联查询或删父表前务必手动给外键列建索引！
多对多 (M:N) 拆出中间关联表，存放两个外键并组成联合主键 PRIMARY KEY (student_id, course_id)。
ON DELETE CASCADE / SET NULL / RESTRICT 父表行删除时：CASCADE 级联删子行；SET NULL 将子行外键置空；RESTRICT / NO ACTION（默认）若有子行则报错拒绝删除。
🛡️ 生产救命指南：大表 Online DDL 如何避免锁表？
  • 加列带默认值：在 PG 11+ 中，ALTER TABLE t ADD COLUMN status int DEFAULT 1; 只要默认值是非易变常量（Non-volatile），只会更新系统表元数据 pg_attribute，0 秒完成、不重写全表！（但若是 random() 等易变函数或 ALTER COLUMN TYPE 改类型，则会持有最高级 ACCESS EXCLUSIVE 锁重写全表）。
  • 千万不要让 ALTER TABLE 长时间等锁堵死线上读写：生产执行 DDL 前务必先加锁超时保护：SET lock_timeout = '2s';（拿不到锁立即放弃，避免排在慢查询后面把后续所有普通 SELECT 全部堵死在锁队列里！）。
  • 无锁加 CHECK / 外键 / NOT NULL 约束：先执行 ALTER TABLE orders ADD CONSTRAINT chk_amt CHECK (amount >= 0) NOT VALID;（瞬间完成，仅约束新写入行），再执行 ALTER TABLE orders VALIDATE CONSTRAINT chk_amt;（只持弱锁 SHARE UPDATE EXCLUSIVE 在线校验老数据，完全不阻塞读写！）。
