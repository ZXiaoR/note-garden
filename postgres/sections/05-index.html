❓ 05.1 · 为什么 PostgreSQL 被称为“索引博物馆”？GIN 倒排索引和 BRIN 块范围索引分别解决什么极限场景？

🗂️ 05.1 PG 六大索引引擎全景选型（面试王牌区分点）

PostgreSQL 默认创建的索引是 B-tree，但它把索引做成了可插拔访问方法（Access Method），原生内置了 6 种各怀绝技的索引结构：

索引类型 支持的操作符 / 能力 典型业务场景与工程要点
1. B-tree（默认） =, <, <=, >, >=, BETWEEN, IN, IS NULL, 前缀 LIKE 'abc%', 排序 绝大多数标量高基数列的默认首选。底层采用 Lehman-Yao 高并发 B-Tree 变体，支持并发读写不阻塞。
2. GIN
（广义倒排索引）		 @>, <@, ?, ?|, ?&, &&, @@（全文检索） ⭐ 一列包含多个子元素时的绝对王牌：jsonb 内部字段查询、int[]/text[] 数组包含/交集、tsvector 全文检索，或配合 pg_trgm 扩展加速任意位置模糊查询 LIKE '%keyword%'！
3. GiST
（广义搜索树）		 几何包含/距离 <->、范围重叠 &&、排他约束 EXCLUDE ⭐ PostGIS 地理空间索引（查附近 5km 的门店）、范围类型区间重叠检测（如 EXCLUDE USING gist (room_id WITH =, during WITH &&) 防止会议室时段冲突）。
4. SP-GiST 非平衡空间分割树（四叉树、K-D 树、前缀树 Radix Tree） 适合具有明显前缀聚集或空间聚集特征的数据，如 IP 地址段（inet）、电话号码前缀、邮编检索。
5. BRIN
（块范围索引）		 范围过滤 =, <, >（基于连续物理页块的 min/max 过滤） ⭐ 海量只追加（Append-Only）时序/账单/监控日志表神器：只记录每 pages_per_range（默认 128 页 = 1MB）的最大最小值，百亿行大表的索引只有几 MB！
6. Hash 仅支持纯等值比较 =（不支持范围与排序） PG 10+ 起支持写 WAL（崩溃安全）。仅当被索引的字符串/URL 极长（数百字节）且只做纯等值查询时，Hash 索引体积比 B-tree 更紧凑。

🛠️ 四大工程级索引变体与生产无锁建索引（必背 SQL）

🐘 advanced_indexes.sql · 四大高阶索引 
-- 1. 部分索引 (Partial Index)：只给热数据建索引，体积锐减 95%！
-- 例：99% 历史订单都是 completed，业务只高频轮询 pending 订单
CREATE INDEX idx_orders_pending ON orders (created_at)
WHERE status = 'pending';

-- 2. 表达式索引 (Expression Index)：对函数计算结果建索引
CREATE UNIQUE INDEX idx_users_lower_email ON users (lower(email));

-- 3. 覆盖索引 (Covering Index · INCLUDE)：把非搜索列附带在叶子节点
-- 查询 SELECT amount, status FROM orders WHERE user_id = 10 时
-- 直接走 Index Only Scan 免回表！
CREATE INDEX idx_orders_user_cov ON orders (user_id)
INCLUDE (amount, status);

-- 4. ⭐ 生产铁律：在线不阻塞读写建索引 (CONCURRENTLY)
CREATE INDEX CONCURRENTLY idx_orders_uid ON orders (user_id);
⚡ 索引失效 6 大常见场景：
  1. 对索引列做函数或算术运算：WHERE lower(email) = 'a@b.com' 或 WHERE amount + 10 > 100（除非建了对应表达式索引）。
  2. 违背复合索引最左前缀：建了 (user_id, status)，单查 WHERE status = 'paid' 无法高效走树搜索。
  3. 前导通配符模糊匹配：LIKE '%abc' 无法走 B-tree（解决方案：反转字符串建函数索引，或用 pg_trgm + GIN 索引）。
  4. 隐式类型转换：如手机号列是 text，却传数字 WHERE mobile = 13800000000。
  5. 区分度过低 / 返回行数占比过大：当优化器估算匹配行数超过全表约 10%～20% 时，走索引随机回表比顺序扫全表更慢，优化器会主动正确地选择 Seq Scan。
  6. OR 两侧有一侧无索引：导致退化为全表扫描。
❓ 面试自测：在 PG 里建了覆盖索引（INCLUDE），为什么有时候 EXPLAIN 发现 Index Only Scan 依然产生了大量 Heap Fetches（回表）？

这是 PostgreSQL 与 MySQL 覆盖索引最本质的区别！
因为 PG 的索引里不保存事务可见性信息（xmin/xmax 只存在堆表数据页里）。为了支持 Index Only Scan，PG 引入了可见性映射表（Visibility Map, VM）——每个 8KB 堆表页在 VM 中占 1 个比特位，如果该页上的所有元组对当前所有事务都全部可见（没有未清理的改动），VM 对应位就被标为 1。
执行 Index Only Scan 时，PG 会先看目标页在 VM 里是不是 1：若是 1 则直接从索引拿数据返回（零回表）；若那张表刚经历了大批量更新/写入、而 VACUUM 还没来得及跑去刷新 VM 位图，PG 就不得不乖乖拿 ctid 回堆表检查可见性（表现为 EXPLAIN ANALYZE 中的 Heap Fetches: N 很高）！解决办法就是及时触发 VACUUM 表名。

1. 四大扫描方式（Scan Nodes）何时出现？

扫描节点 执行机制与适用边界
Seq Scan 顺序全表扫描：小表或查询返回全表较大比例行数时，顺序磁盘读反而比随机跳索引更快。
Index Scan 索引扫描 + 逐行回表：扫一条索引记录就立刻拿 ctid 去堆表取一行。适合命中行数极少的点查或需要直接利用索引顺序做 ORDER BY ... LIMIT 的场景。
Index Only Scan ⭐ 覆盖索引只读索引：查询列全在索引里且对应页在 Visibility Map 中全可见，无需回表。
Bitmap Index Scan + Bitmap Heap Scan ⭐ 位图批量扫描（中等匹配量神器）：当命中几十到几万行时，如果用普通 Index Scan 会产生大量随机磁盘 IO；PG 会先扫索引把命中的页号标记在内存位图里，按物理页号从小到大排序后再顺序去堆表批量捞取，还能把多个单列索引通过 BitmapAnd / BitmapOr 组合使用！

2. 三大表连接算法（Join Nodes）与调优清单

Join 算法 复杂度与最佳搭档场景
Nested Loop
（嵌套循环连接）		 外层驱动表每取一行，就去内层被驱动表查一次（若内表有索引则为 $O(N \log M)$）。适合驱动表结果集极小、内表连接键有索引的场景。
Hash Join
（哈希连接）		 把较小的一张表在内存（work_mem）里建成 Hash 表，再扫大表探测匹配（$O(N + M)$）。适合两张大表做等值连接且无序的场景（注意避免 Batches > 1 溢出磁盘）。
Merge Join
（归并连接）		 左右两表都已经按连接键排好序（比如都有索引），像拉拉链一样双指针并排走一遍。适合超大表且连接键已有序或支持非等值连接。
🎯 慢 SQL 四步必杀排查法：
① 比对估算 rows 与实际 actual rows：如果估算 1 行、实际跑出 50 万行，说明统计信息严重失真导致优化器错选了 Nested Loop，立即执行 ANALYZE 表名;！
② 看 Buffers: shared hit vs read：hit 是直接命中共享内存，read 是去底层 OS/磁盘读页；若 temp read/written 出现，说明排序或 Hash Join 撑爆了 work_mem 落了临时磁盘文件！
③ 注意 loops=N 倍数：子节点的 actual time 是单次循环平均耗时，真实总耗时必须乘以 loops！
④ 开启 pg_stat_statements 扩展：按 total_exec_time DESC 揪出全库最耗 CPU 和 IO 的 Top 10 慢 SQL。
