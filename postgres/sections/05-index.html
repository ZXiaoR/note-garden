05 日常索引创建、组合索引设计与慢查询初步排查 B-TREE × GIN & BRIN × INCLUDE × EXPLAIN ANALYZE
05.1 · 索引选型：六类内置索引适用场景与部分索引、表达式索引、INCLUDE 覆盖索引创建语法

05.1 索引类型选型与高阶索引创建语法

在 PostgreSQL 中执行 CREATE INDEX 时，如果不指定类型，默认创建的是 B-tree 索引。同时，针对 JSONB 文档、数组、地理位置以及超大规模时序日志表，PostgreSQL 内置了多种专用索引访问方法：

索引类型 支持的操作符 / 查询模式 日常适用场景与选型建议
1. B-tree（默认） =, <, <=, >, >=, BETWEEN, IN, IS NULL, 前缀匹配 LIKE 'abc%', ORDER BY 90% 以上单值标量列的首选：主键、外键、用户邮箱、订单状态、时间戳范围查询与排序。
2. GIN
（广义倒排索引）		 @>, <@, ?, ?|, ?&, &&, @@（全文检索） 当一个字段内部包含多个元素时使用：如 jsonb 嵌套键值包含查询、text[] / int[] 数组交集与包含、全文检索，或配合 pg_trgm 插件加速前导模糊查询 LIKE '%关键词%'。
3. BRIN
（块范围索引）		 按物理存储顺序过滤 =, <, > 按时间顺序只追加写入（Append-Only）的亿级日志/账单流水表：只记录连续数据页块的最小与最大值，索引体积通常仅几 MB（比 B-tree 小数百倍）。
4. GiST / SP-GiST / Hash 几何距离 <->、范围重叠 &&、排他约束 EXCLUDE、超长字符串纯等值 = GiST 用于 PostGIS 地理坐标与时间区间防重叠约束（如禁止同一会议室预订重叠时段）；SP-GiST 用于 IP 网段/前缀树；Hash 用于超长 URL 的纯等值查询。
create_indexes.sql · 常见索引与高阶变体创建示例 
-- 1. 复合 B-tree 索引：按 (user_id, created_at DESC) 加速用户历史订单分页
CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at DESC);

-- 2. 部分索引 (Partial Index)：带 WHERE 条件，只给热数据建索引
-- 例：99% 订单已完成，业务仅高频轮询未支付订单，索引体积缩小 95% 以上
CREATE INDEX idx_orders_pending
  ON orders (created_at) WHERE status = 'pending';

-- 3. 表达式索引 (Expression Index)：对函数计算结果建唯一索引
CREATE UNIQUE INDEX idx_users_lower_email
  ON users (lower(email));

-- 4. 覆盖索引 (INCLUDE)：将非过滤列附带在索引叶子节点，省去回表读数据页
CREATE INDEX idx_orders_user_cov
  ON orders (user_id) INCLUDE (amount, status);

-- 5. GIN 倒排索引：加速 JSONB 包含查询 (@>) 与数组检索
CREATE INDEX idx_profiles_gin ON user_profiles USING GIN (profile);
高阶索引语法说明：WHERE 部分索引与 INCLUDE 覆盖索引
  • 部分索引（Partial Index）：在 CREATE INDEX 末尾加上 WHERE 条件，数据库只会把满足该条件的行放进索引树。除了加快特定状态查询，还常用于实现“软删除表中的唯一约束”：CREATE UNIQUE INDEX idx_email_active ON users (email) WHERE deleted_at IS NULL;（允许已注销用户的邮箱被重新注册，但未注销用户中邮箱唯一）。
  • 覆盖索引（INCLUDE 子句）：当高频执行 SELECT amount, status FROM orders WHERE user_id = 10 时，把只用于展示、不参与过滤排序的 amount, status 放入 INCLUDE，数据库直接从索引叶子节点即可拿齐所需字段（走 Index Only Scan），无需再去读取主表数据页。
05.2 · 索引命中规则：复合索引列顺序设计与 6 类常见索引失效写法改写对照

05.2 复合索引设计原则与常见失效场景改写

复合 B-tree 索引（例如建立在 (user_id, status, created_at) 上的索引）按照从左到右的列顺序逐层排序：先按第 1 列 user_id 排序，当 user_id 相同时再按第 2 列 status 排序，依此类推。因此设计复合索引时应遵循“等值过滤列放前面，范围过滤或排序列放后面”的原则，并在编写 SQL 时避开以下 6 类导致索引无法高效命中的写法：

未命中索引原因 导致全表扫描的低效写法 命中索引的推荐改写方案
1. 在索引列上套函数或做算术运算 WHERE date_trunc('day', created_at) = '2026-11-15'
或 WHERE amount + 10 > 100		 将计算移到常量一侧，改为范围比较：
WHERE created_at >= '2026-11-15' AND created_at < '2026-11-16'
或建立对应的函数表达式索引。
2. 违背复合索引最左前缀 索引为 (user_id, status)，查询只写：
WHERE status = 'paid'（缺少最左列 user_id）		 查询条件包含最左列 user_id；若确实存在高频单查 status 的需求，需单独评估是否建立索引。
3. 前导通配符模糊查询 WHERE title LIKE '%数据库%'
（普通 B-tree 只能加速右侧通配 '数据库%'）		 启用内置三元组扩展 CREATE EXTENSION pg_trgm;，并建立 GIN 索引：
CREATE INDEX ON books USING GIN (title gin_trgm_ops);
4. 隐式类型不匹配 mobile 列为 text，查询传入整数：
WHERE mobile = 13800000000		 始终保证传入参数类型与列定义严格一致：
WHERE mobile = '13800000000'
5. 查询条件与部分索引不匹配 建立了部分索引 WHERE status = 'pending'，但查询未带 WHERE status = 'pending' 查询语句的 WHERE 子句必须显式包含部分索引定义时的过滤条件，优化器才能确认该索引覆盖完整结果。
6. 返回行数占全表比例过高 大表上执行 WHERE status != 'cancelled'（命中全表 85% 的行） 这是优化器的正常且正确行为：当预计返回行数超过全表约 10%~20% 时，顺序扫描全表（Seq Scan）比走索引随机回表更快，应通过 LIMIT 或缩小时间范围减少扫描量。
05.3 · 慢查询诊断：使用 EXPLAIN (ANALYZE, BUFFERS) 读懂四种扫描节点与关键指标

05.3 使用 EXPLAIN (ANALYZE, BUFFERS) 分析慢查询

排查慢 SQL 时，在查询语句前加上 EXPLAIN 可以查看优化器预估的执行计划（不会真正执行语句）；加上 EXPLAIN (ANALYZE, BUFFERS) 则会真正执行一次该 SQL，并输出每个步骤的真实耗时、实际返回行数与缓冲页读取次数（注意：若对 UPDATE / DELETE 执行 EXPLAIN ANALYZE，请包裹在 BEGIN; ... ROLLBACK; 中以免修改真实数据）。

explain_analyze_buffers.sql · 执行计划输出与字段解读 
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount FROM orders WHERE user_id = 42;

1. 四类常见扫描节点（Scan Nodes）

扫描节点名称 执行方式与出现场景
Seq Scan 顺序全表扫描：从头到尾读取表的数据页。出现在无可用索引、表体积很小（仅几页）或命中行数占比很大的情况。
Index Scan 索引扫描 + 逐行回表：在索引树中找到一条匹配项后，立即根据物理位置去表数据页读取整行。适合返回行数很少的点查或带 ORDER BY ... LIMIT 的查询。
Index Only Scan 纯索引覆盖扫描：查询所需的所有列均包含在索引中，且对应数据页对所有事务可见，直接从索引返回结果，无需读取表数据页。
Bitmap Index Scan + Bitmap Heap Scan 位图批量扫描：当命中行数较多（几十至数万行）时，先扫描索引将命中的数据页号记录在内存位图中，按物理页号从小到大排序后再顺序读取表数据页，将随机磁盘 I/O 转化为顺序 I/O，并支持通过 BitmapAnd / BitmapOr 组合多个独立单列索引。

2. 读懂括号内的核心指标

输出指标 物理含义与排障关注点
cost=启动成本..总成本 优化器按代价公式算出的相对开销评分（非毫秒数），用于比较不同候选方案的优劣。
rows=25 vs actual rows=28 前者是优化器根据统计信息预估的行数，后者是真实执行返回的行数。若两者相差几个数量级（如预估 1 行、实际 50 万行），说明统计信息过期，需执行 ANALYZE 表名; 更新统计信息。
actual time=0.045..0.112 与 loops=1 单次循环返回第一行的耗时与返回全部行的耗时（单位毫秒）。若 loops > 1，该节点的真实总耗时需乘以 loops 次数。
Buffers: shared hit=20 read=1 shared hit 表示直接从内存缓存池命中了 20 个 8KB 页；read 表示从操作系统缓存或磁盘读取了 1 个页；若出现 temp read/written，说明排序或哈希操作超出了 work_mem 内存限制，发生了临时文件落盘。
