❓ 06.1 · 为什么删了 80% 的数据，磁盘空间却一字节都没变小？什么是 PG 最致命的“事务 ID 回卷停库”事故？

🧹 06.1 PG 运维命脉：VACUUM 家族、表膨胀、XID 回卷与 HOT 优化

承接第 04 章的堆表 MVCC：每次 UPDATE / DELETE 都会在表里留下死元组（Dead Tuple）。如果不及时清理，不仅磁盘空间暴涨（表膨胀 Bloat），还会引发致命的32 位事务 ID 回卷（Wraparound）。负责这四大职责的清道夫就是 VACUUM：

清理命令 / 工具 底层做什么 是否把空间还给 OS 锁级别与生产建议
VACUUM
（标准清理）		 扫描堆表与索引，清除死元组，将其占用的页内槽位登记到 空闲空间映射表（FSM） 供该表后续插入/更新复用，并更新可见性映射（VM）。 ❌ 不还给操作系统（表文件大小通常不变） ✅ SHARE UPDATE EXCLUSIVE，不阻塞正常读写，生产安全。
VACUUM FULL 新建一个物理文件，把活元组紧凑地重新拷贝一遍，再删掉旧文件，彻底消除碎片。 ✅ 真正归还磁盘空间给 OS 🚨 持有最高级 ACCESS EXCLUSIVE 全表锁，期间连 SELECT 都卡死，且需额外一倍磁盘空间，生产白天严禁直接跑！
⭐ pg_repack
（社区生产神器）		 通过影子表 + 触发器记录增量变更，在线完成整表与索引的紧凑重建，最后仅在切换瞬间拿极短锁。 ✅ 真正归还磁盘空间给 OS ✅ 几乎不阻塞线上读写，治理严重表膨胀的生产标准答案。
ANALYZE 抽样扫描表，更新 pg_statistic 中的列数据分布直方图与基数，供优化器计算 EXPLAIN 成本。 无 ✅ 完全不阻塞读写；大批导入数据后务必跑一次。
autovacuum 后台守护进程，当表中死元组超过 autovacuum_vacuum_threshold (50) + scale_factor (0.2) × 总行数 时自动触发 VACUUM + ANALYZE。 ❌（复用表内空间） ⚠️ 对几千万行的大表，默认 20% 比例太高（要攒够几百万死元组才触发），大表必须单独调低表级 scale_factor = 0.01~0.02！

1. 视图 VIEW vs 物化视图 MATERIALIZED VIEW

维度 普通视图 VIEW ⭐ 物化视图 MATERIALIZED VIEW
存储本质 只存 SQL 定义，每次查询实时展开执行 把查询结果真正物化落盘成一张物理表（可建索引！）
数据实时性 永远最新 需执行 REFRESH MATERIALIZED VIEW CONCURRENTLY mv_name; 刷新（带 CONCURRENTLY 刷新期间不阻塞读，要求有唯一索引）
适用场景 简化多表关联 SQL、权限列屏蔽 复杂大宽表聚合报表、Dashboard 毫秒级查询加速

3. WAL 预写日志、备份恢复与高可用复制

核心机制 核心原理与面试必知细节
WAL 预写日志
(pg_wal/)		 修改数据页前必须先把变更记入 WAL 并刷盘（对应 MySQL 的 Redo Log + Binlog 合体）。注意：PG 开启了 full_page_writes = on（每次 Checkpoint 后某个 8KB 页第一次被修改时，先把整个 8KB 页完整写进 WAL，防止操作系统 4KB 写一半断电导致“页撕裂 Torn Page”无法恢复！）。
物理流复制 vs 逻辑复制 • 物理流复制（Streaming Replication）：主库 `wal_sender` 把字节级 WAL 实时发给从库 `wal_receiver` 重放（主从全库二进制完全一致，用于高可用故障切换 Patroni + 读写分离）。
• 逻辑复制（Logical Replication）：基于发布/订阅（`PUBLICATION / SUBSCRIPTION`）解析 WAL 为行级变更，支持只同步指定表、跨大版本升级、多主汇总。
备份与 PITR pg_dump / pg_restore 做逻辑导出；生产大库用 pg_basebackup 物理全量备份 + 持续归档 WAL 日志，实现任意秒级的 时间点恢复（PITR）。
四大王牌扩展 pg_stat_statements（慢 SQL 统计）、PostGIS（地理信息）、pgvector（AI 向量检索）、pg_repack（在线清膨胀）。
🎯 06.3 · 上考场前最后 3 分钟：PostgreSQL 高频考点速记与 9 道闭卷自测

🏆 06.3 高频面试速记卡片 & 9 道核心闭卷自测题

📌 十句话串起整本 PostgreSQL 手帐：
  1. 架构与连接：每连接 fork 一个独立 backend 进程 + Shared Buffers (8KB 页)；高并发生产环境必须前置 PgBouncer（Transaction 池化模式）。
  2. 层级与类型：四层结构（实例→库→Schema→表）；金额用 numeric，变长文本直接用 text，时间用 timestamptz，自增用 GENERATED ALWAYS AS IDENTITY，动态属性用 jsonb（二进制树 + GIN 索引）。
  3. DDL 优势：支持事务性 DDL（可 BEGIN ... ALTER ... ROLLBACK）；大表加常量默认列免重写，加约束用 NOT VALID + VALIDATE CONSTRAINT 免锁表。
  4. 王牌 SQL：RETURNING 免二次查、ON CONFLICT DO UPDATE 原子 UPSERT、OVER(PARTITION BY ... ORDER BY ...) 窗口函数分组排名、WITH RECURSIVE 递归查树。
  5. 堆表 MVCC：表是无序堆表（ctid 物理寻址），每行带 xmin/xmax，UPDATE = 旧行标 xmax + 插新行版本；回滚 $O(1)$ 极快，但留下死元组与表膨胀。
  6. 隔离级别：默认 Read Committed（语句级快照）；无脏读；Repeatable Read 靠事务级快照天然挡幻读（写写冲突直接报错要求重试）；Serializable 采用无读锁的 SSI。
  7. 行锁与抢单：行锁记在元组头 xmax + infomask 上，绝不撑爆内存；任务队列并发抢单用 FOR UPDATE SKIP LOCKED。
  8. 六大索引：默认 B-tree；多值包含（JSONB/数组/全文）用 GIN；空间/范围排他用 GiST；百亿按序时序表用 BRIN；覆盖索引用 INCLUDE（需 VACUUM 维护 Visibility Map 才真正免回表）；生产建索引必加 CONCURRENTLY。
  9. EXPLAIN 调优：用 EXPLAIN (ANALYZE, BUFFERS) 对比估算 rows 与实际 actual rows，偏差大先跑 ANALYZE；理解 Bitmap Index/Heap Scan 排序页号转顺序 IO 的妙处。
  10. VACUUM 三大使命：回收死元组防膨胀（在线缩磁盘用 pg_repack，慎用锁全表的 VACUUM FULL）、更新 VM/FSM、Freeze 冻结老 XID 防止 32 位事务 ID 回卷停库；未改索引列且同页有空位可走 HOT 页内更新。
自测 01 · PostgreSQL 的 MVCC 与 MySQL InnoDB 的 MVCC 本质区别是什么？各自有什么优缺点？
InnoDB 是“原地更新数据页 + 把旧版本写进 Undo Log 回滚段”；PostgreSQL 是“堆表内追加写新版本（旧元组标 xmax，新元组标 xmin 并用 ctid 串联）”。
PG 优点：大事务回滚只需在 pg_xact 标记状态，无需重放 Undo，瞬间完成；读旧版本无需顺着漫长的回滚段临时拼装。
PG 缺点：高频更新会产生大量死元组导致表与索引膨胀（Bloat），必须依赖 autovacuum 持续清理；且若未命中 HOT 优化，更新一行需为所有索引追加新条目。
自测 02 · 什么是 HOT（Heap-Only Tuple）更新？怎么提高高频更新表的 HOT 命中率？
当 UPDATE 满足两个条件：① 没有修改任何被索引包含的列；② 旧版本所在的同一个 8KB 堆表页内有足够剩余空间放下新版本时，PG 不会去修改任何外部索引，而是让外部索引继续指向老的根元组 ctid，页内通过 HOT 链 跳到新元组。这既消除了索引写放大，又允许普通查询顺手做页内垃圾剪枝（Page Pruning）。
调优手段：1）删掉不必要的冗余索引；2）将高频更新表的填充因子调低：ALTER TABLE t SET (fillfactor = 80);（每页预留 20% 空闲空间专门给同页 HOT 更新用）。
自测 03 · 什么是事务 ID 回卷（Transaction ID Wraparound）？线上遇到年龄告警怎么处理？
PG 普通事务 ID（XID）是 32 位无符号整数（约 42.9 亿），采用环形模算术比较先后：任意 XID 往后约 21 亿个事务被视为“未来不可见”，往前约 21 亿被视为“过去可见”。如果一张老表上的行经历了超过 21 亿次新事务仍未被 VACUUM FREEZE 标记为“永久冻结可见”，新事务就会把这批老数据误判为“来自未来的事务”而瞬间看不见（数据隐身事故）！
排查与处理：通过 SELECT relname, age(relfrozenxid) FROM pg_class ORDER BY 2 DESC; 定位高龄表，检查是否有未提交长事务（pg_stat_activity）、废弃复制槽（pg_replication_slots）或未决两阶段事务（pg_prepared_xacts）卡住了最早可见快照 xmin；清理阻塞源后手动执行 VACUUM FREEZE 表名;。
自测 04 · 什么时候用 B-tree、什么时候用 GIN、什么时候用 BRIN？
• B-tree：单值标量列的等值（=）、范围（<, >, BETWEEN）、排序（ORDER BY）与前缀匹配（LIKE 'abc%'）。
• GIN（倒排索引）：一个字段内含多个子元素、需要按子元素反查行时——如 jsonb 包含查询（@>, ?）、数组交集/包含（&&, @>）、全文检索或 pg_trgm 任意位置模糊查询。
• BRIN（块范围索引）：按时间/自增顺序只追加写入（Append-Only）的亿级日志、监控、物联网流水表，体积僅几 MB，靠连续物理页块的 [min, max] 极值秒级跳过无关数据块。
自测 05 · 生产环境给上千万行的大表建索引或加字段，有哪些保命铁律？
1）建索引必须加 CONCURRENTLY：CREATE INDEX CONCURRENTLY idx_name ON tbl(col);（注意不能放进事务块里跑，且若中途失败会留下 INVALID 索引，需先 DROP INDEX CONCURRENTLY 再重建）。
2）执行任何 ALTER TABLE 前先设锁等待超时：SET lock_timeout = '2s';，防止 DDL 等慢查询释放锁时把后续所有业务读请求全部阻塞在锁等待队列里。
3）加外键或 CHECK 约束分两步走：先 ADD CONSTRAINT ... NOT VALID（瞬间完成），再 VALIDATE CONSTRAINT（不阻塞读写在线校验）。
