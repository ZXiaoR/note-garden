04 事务控制、保存点与并发加锁实战 TRANSACTION × SAVEPOINT × ISOLATION × SKIP LOCKED
04.1 · 事务控制：BEGIN / COMMIT / ROLLBACK、事务块报错中止规则与 SAVEPOINT 局部回滚

04.1 事务生命周期与报错中止规则

在 PostgreSQL 中，如果不显式开启事务，每一条独立的 SQL 语句都会自动包裹在它自己的隐式事务中（执行成功即自动提交）。当需要让多条读写语句“要么全部成功，要么全部撤销”时，使用 BEGIN 开启显式事务块，最后以 COMMIT 提交或 ROLLBACK 回滚。

transaction_and_savepoint.sql · 事务与保存点局部回滚 
-- 1. 开启事务（可同时指定事务隔离级别或只读模式）
BEGIN;

  -- 步骤 A：扣减买家账户余额
  UPDATE accounts SET balance = balance - 100.00 WHERE id = 1;

  -- 2. 在可能失败的非核心步骤前打一个保存点 (SAVEPOINT)
  SAVEPOINT sp_coupon;

  -- 步骤 B：尝试写入优惠券使用记录（若此处触发唯一键冲突报错）
  INSERT INTO coupon_usages (user_id, coupon_code) VALUES (1, 'VIP2026');

  -- 若步骤 B 报错，只需回滚到 sp_coupon 保存点，即可恢复事务正常状态
  ROLLBACK TO SAVEPOINT sp_coupon;

  -- 步骤 C：继续完成核心转账并正常提交整个事务
  UPDATE accounts SET balance = balance + 100.00 WHERE id = 2;

COMMIT;
与 MySQL 的重要行为差异：事务内单条语句报错后的状态
  • 在 MySQL 中：事务内某一条 SQL 语句语法错误或唯一键冲突报错后，应用层如果忽略该异常继续发送下一条 SQL 并执行 COMMIT，其余成功的语句依然会被提交。
  • 在 PostgreSQL 中：严格遵循原子性语义——只要显式事务块内任意一条 SQL 语句执行报错，整个事务会立即进入 ABORTED（已中止）状态。此时如果继续发送任何普通 SQL，数据库都会直接拒绝并提示 ERROR: current transaction is aborted, commands ignored until end of transaction block，即使最后执行 COMMIT 也会被自动转为 ROLLBACK。
  • 如何在事务内做局部容错？ 如果某一步操作允许失败而不希望终止整个主事务，优先使用 ON CONFLICT DO NOTHING；若必须捕获一般性错误，则在执行该语句前声明 SAVEPOINT 名称，报错后执行 ROLLBACK TO SAVEPOINT 名称 即可清除中止状态并继续后续操作。
04.2 · 隔离级别：Read Committed（默认）与 Repeatable Read 的日常读写行为差异

04.2 四种事务隔离级别与并发更新行为

SQL 标准定义了四种事务隔离级别。在 PostgreSQL 中，Read Uncommitted 在内部直接等价于 Read Committed，因此在任何隔离级别下都不会发生脏读（不会读到其他未提交事务修改的数据）：

隔离级别 开启语法 读操作看到的快照范围 并发更新同一行时的行为表现
1. 读已提交
Read Committed
（PostgreSQL 默认）		 BEGIN;
（默认无需额外声明）		 每条语句独立获取最新快照：在同一事务内前后执行两次相同的 SELECT，如果中间有其他事务提交了修改，第二次 SELECT 会看到新提交的数据。 若事务 A 正在更新第 1 行尚未提交，事务 B 也来更新第 1 行：事务 B 会等待事务 A 结束；当事务 A 提交后，事务 B 会读取事务 A 提交后的最新版本重新评估 WHERE 条件并继续完成更新（不报错）。
2. 可重复读
Repeatable Read		 BEGIN ISOLATION LEVEL REPEATABLE READ; 整个事务共享同一个快照：事务内第一条查询语句开始执行时固定数据快照，后续所有查询始终看到这一刻之前已提交的数据（无不可重复读，也无幻读）。 若事务 A 已提交对第 1 行的修改，正在等待或尝试更新同一行的事务 B 不会覆盖修改，而是立即报错中止：ERROR: could not serialize access due to concurrent update，由应用层捕获该错误并重试整个事务。
3. 可串行化
Serializable		 BEGIN ISOLATION LEVEL SERIALIZABLE; 在可重复读快照基础上，额外监控事务间的读写依赖关系，保证并发执行结果与某种串行顺序完全等价。 除了拦截直接更新同一行的冲突外，若检测到两个并发事务互相读取对方将要修改的数据集（写偏序异常），其中一个事务在提交时会收到序列化失败报错并需重试。
04.3 · 并发加锁：SELECT ... FOR UPDATE 悲观行锁、乐观锁版本号与 SKIP LOCKED 任务队列

04.3 行级锁语法与 SKIP LOCKED 任务抢单实战

在默认的 Read Committed 隔离级别下，如果业务代码采用“先 SELECT 查出余额、在应用内存中计算新余额、再执行 UPDATE 写回”的两步写法，两个并发请求会读到相同的初始余额，导致后提交的事务覆盖先提交事务的扣款结果（丢失更新）。解决并发修改冲突有三种标准工程模式：

三种并发更新保护模式与锁选项对照

加锁 / 并发模式 适用场景与行为说明
模式 1：单条原子更新
SET bal = bal - 100		 直接在一条 UPDATE ... WHERE id = 1 AND bal >= 100 RETURNING bal 中完成计算与校验，由数据库自动加行锁，最简单高效。
模式 2：悲观行锁
SELECT ... FOR UPDATE		 当更新前必须在事务内执行复杂校验逻辑时，在查询末尾加上 FOR UPDATE 锁住目标行，阻止其他事务修改该行直到当前事务提交。
模式 3：乐观锁版本号
WHERE version = 旧版本		 表中增加 version int 列，更新时带上 SET version = version + 1 WHERE id = 1 AND version = 5；若受影响行数为 0 说明已被他人修改。
FOR UPDATE NOWAIT 尝试加行锁时，如果目标行已被其他事务锁住，不阻塞等待，立即抛出锁获取失败错误返回，防止大量连接排队卡死。
FOR UPDATE SKIP LOCKED 扫描候选行时，自动跳过已经被其他并发事务锁住的行，直接锁定第一条空闲行，非常适合多 Worker 并发消费数据库任务表。
skip_locked_queue.sql · 基于 SKIP LOCKED 的并发任务出队 
-- 场景 A：事务内使用 FOR UPDATE 悲观锁完成先查后改
BEGIN;
  SELECT balance FROM accounts WHERE id = 10 FOR UPDATE;
  -- 应用层校验通过后执行扣款
  UPDATE accounts SET balance = balance - 50 WHERE id = 10;
COMMIT;

-- 场景 B：多个后台 Worker 并发从任务表领取 1 条待处理任务
-- SKIP LOCKED 会自动跳过正在被其他 Worker 锁定的行，零阻塞等待
UPDATE job_queue
SET status     = 'running',
    worker_id  = 'worker-01',
    started_at = now()
WHERE id = (
  SELECT id FROM job_queue
  WHERE status = 'pending'
  ORDER BY priority DESC, created_at ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING id, payload, started_at;
