❓ 04.1 · 为什么 PostgreSQL 更新一行数据时“不改原地，而是直接再插一行新版本”？它的 MVCC 和 MySQL 到底差在哪？

🧬 04.1 核心必考：PostgreSQL 堆表多版本并发控制（Append-Only MVCC）

MVCC（Multi-Version Concurrency Control）的核心目标是实现“读不阻塞写，写不阻塞读”。与 MySQL InnoDB 将旧版本剥离到独立的 Undo Log 不同，PostgreSQL 直接把同一行数据的多个历史版本并排存放在主数据表（Heap Table 8KB 数据页）里，每个元组（Tuple）头部自带以下关键隐藏系统列（你可以直接 SELECT ctid, xmin, xmax, * FROM account; 看到它们！）：

隐藏系统列 物理含义 在 INSERT / UPDATE / DELETE 中的状态变化
ctid 物理坐标 (页号, 页内槽位号) 例如 (0, 1) 代表第 0 号 8KB 页的第 1 条记录。注意：只要发生非原地更新，这行的 ctid 就会改变！旧版本的头部指针 t_ctid 会指向新版本的 ctid 形成版本链。
xmin 创建该版本的事务 ID (XID) 事务 100 执行 INSERT 时，新元组的 xmin = 100。
xmax 删除/更新使该版本失效的事务 ID 当前最新有效行 xmax = 0；当事务 105 执行 DELETE 时，把该行 xmax 设为 105；当事务 105 执行 UPDATE 时，把旧版本 xmax 设为 105，同时插入一条 xmin = 105, xmax = 0 的新版本元组！
t_infomask
(Hint Bits)		 事务提交状态提示位 判断 xmin/xmax 对应事务是已提交还是已回滚，本来要查全局提交日志 pg_xact (CLOG)；第一个查完 CLOG 的会话会顺手把结果标在元组头的 Hint Bits 上，后续查询直接看元组头即可，免去反复查 CLOG！
⚖️ 架构权衡：PG 堆表追加写 MVCC 的优缺点
  • 两大优势：① 无论多大的事务，ROLLBACK 回滚都是瞬间完成的（只需在 pg_xact 里把该事务 ID 标为 ABORTED，无需像 MySQL 那样逐行重放 Undo Log）；② 不会发生 Undo Log 撑爆回滚段的问题。
  • 两大代价：① 表膨胀（Table Bloat）：高频 UPDATE/DELETE 的表会在数据页里堆积大量死元组，必须依靠 VACUUM / autovacuum 及时清理；② 若更新修改了索引列（未能触发同页 HOT 优化），则该表上的所有索引都要追加一条指向新 ctid 的索引项，写放大比 InnoDB 更明显。

隔离级别 脏读 不可重复读 幻读 序列化异常 PG 底层实现机制
Read Uncommitted ❌ 不会 可能 可能 可能 PG 中直接映射为 Read Committed，从根本上不存在脏读。
⭐ Read Committed
（PG 默认级别）		 ❌ 不会 可能 可能 可能 语句级快照（Statement-level Snapshot）：事务内每条 SQL 开始执行时重新获取一次最新快照。

🔥 面试高频：两个并发事务同时 UPDATE 同一行会怎样？（First-Updater-Wins）
假设事务 A 已执行 UPDATE account SET bal = bal - 100 WHERE id = 1; 但尚未提交，此时事务 B 也来更新 id = 1：
  1. 事务 B 会因为等待事务 A 的行锁而阻塞。
  2. 若事务 A 回滚，事务 B 立即拿到锁继续更新。
  3. 若事务 A 提交：
    • 在默认 Read Committed (RC) 下：事务 B 顺着 ctid 链找到 A 刚提交的最新版本行，重新评估 WHERE 条件，若仍满足则基于新行继续更新（不报错）。
    • 在 Repeatable Read (RR) / Serializable 下：为了防止丢失更新（Lost Update），PG 立刻中断事务 B 并抛出错误：ERROR: could not serialize access due to concurrent update，要求客户端捕获异常并重试整个事务！
🐘 transaction_and_savepoint.sql 
-- 1. 显式指定隔离级别开启事务
BEGIN ISOLATION LEVEL REPEATABLE READ;
  UPDATE account SET bal = bal - 100 WHERE id = 1;

  -- 2. 保存点 (Savepoint)：支持局部回滚（子事务 Subtransaction）
  SAVEPOINT sp_bonus;
  UPDATE account SET bal = bal + 50 WHERE id = 2;
  ROLLBACK TO SAVEPOINT sp_bonus; -- 仅撤销上一句，事务继续有效
COMMIT;

-- ⚠️ 注意：PG 中只要事务内任意一条 SQL 报错，整个事务即进入
-- ABORTED 状态（后续任何 SQL 均报 current transaction is aborted），
-- 除非提前打了 SAVEPOINT，否则必须 ROLLBACK！
❓ 04.3 · 为什么 PG 锁住 100 万行也不会撑爆内存锁表？如何用 FOR UPDATE SKIP LOCKED 写出高并发任务抢单队列？

🔐 04.3 行级锁四模式、SKIP LOCKED 任务队列、表锁与死锁

PostgreSQL 的行级锁有一个极其精妙的设计：行锁并不存在共享内存的全局锁表里，而是直接把加锁事务 ID 写进磁盘/缓冲池数据行头部的 xmax + infomask 标记位中！这意味着即使一个事务锁住 1000 万行，也不会像其他数据库那样发生“锁升级（Lock Escalation）”或撑爆内存锁表。

1. 显式行锁语法与并发抢单选项

行锁语法 锁强度与适用场景
FOR UPDATE 最强排他行锁：阻塞其他事务的 UPDATE / DELETE / FOR UPDATE / FOR SHARE。用于先查后改防并发覆盖。
FOR NO KEY UPDATE 非主键排他锁：UPDATE 未改主键/唯一键时自动加此锁，允许子表外键检查的 FOR KEY SHARE 并发通过！
FOR SHARE / FOR KEY SHARE 共享行锁：多个会话可同时持有，阻止别人修改或删除该行。
⭐ FOR UPDATE SKIP LOCKED 跳过已锁定的行，绝不阻塞等待：多个 Worker 并发从表中抢待处理任务的神器！
FOR UPDATE NOWAIT 若目标行已被锁，不等待、立即抛错返回，避免连接堆积。

2. 经典实战：基于 SKIP LOCKED 的高并发抢单/任务出队

🐘 skip_locked_queue.sql · 并发安全抢任务 
-- 多个 Worker 并发执行：锁住 1 条未被别人锁住的 pending 任务，
-- 原子改为 running 并直接返回任务详情（吞吐量极高且零冲突等待）
UPDATE job_queue
SET status = 'running',
    worker_id = 'worker-01',
    started_at = now()
WHERE id = (
  SELECT id FROM job_queue
  WHERE status = 'pending'
  ORDER BY priority DESC, created_at ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
⚠️ 表级锁与死锁（Deadlock）排查：
• 表级锁最高等级 ACCESS EXCLUSIVE：由 DROP TABLE、TRUNCATE、VACUUM FULL、改列类型触发，连普通 SELECT 都会被阻塞！
• 死锁检测：当事务等待锁超过 deadlock_timeout（默认 1s）时，PG 才启动等待图环路检测（因为平时没阻塞没必要耗 CPU 检环），发现死锁环则自动回滚其中一个事务并报错 ERROR: deadlock detected。
• 防死锁三铁律：① 批量更新按主键升序排序（ORDER BY id）再加锁；② 保持小事务，严禁在事务内夹杂外部 RPC 调用；③ 并发低冲突场景优先用乐观锁（UPDATE t SET val=..., ver=ver+1 WHERE id=1 AND ver=3）。
🔎 线上锁等待与阻塞源头一键排查 SQL 
-- 一键查出“谁阻塞了谁”以及双方正在执行的 SQL
SELECT
  blocked.pid AS blocked_pid,
  blocked.query AS blocked_sql,
  pg_blocking_pids(blocked.pid) AS blocker_pids,
  now() - blocked.query_start AS wait_duration
FROM pg_stat_activity blocked
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
