⚡ 03.1 标准增删改、RETURNING 原子返回与 ON CONFLICT (UPSERT)

在日常业务开发中，数据写入不仅包含基础的单行/批量插入、条件修改和删除，还经常遇到“修改后立刻拿到最新行数据”或“唯一键冲突时原子转为更新”的需求。PostgreSQL 提供了原生的单条原子 SQL 语法，免去了在应用层“先 SELECT 判断、再 INSERT/UPDATE”带来的多次网络往返与并发竞态问题：

🐘 dml_write_and_upsert.sql · 批量插入、关联更新、RETURNING 与 UPSERT 
-- 1. 批量插入 + RETURNING：一次性插入多行并直接返回生成的自增 id 与创建时间
INSERT INTO users (email, city, login_count) VALUES
  ('alice@example.com', '杭州', 1),
  ('bob@example.com',   '上海', 1)
RETURNING id, email, created_at;

-- 2. 多表关联更新（UPDATE ... FROM ...）：根据部门表状态批量调整员工薪资并返回新值
UPDATE employees e
SET salary = e.salary + 500.00,
    updated_at = now()
FROM departments d
WHERE e.dept_id = d.id AND d.city = '杭州'
RETURNING e.id, e.name, e.salary;

-- 3. ON CONFLICT DO UPDATE (UPSERT)：唯一键 email 冲突时原子转为累加更新
INSERT INTO users (email, login_count)
VALUES ('alice@example.com', 1)
ON CONFLICT (email) DO UPDATE
  SET login_count = users.login_count + EXCLUDED.login_count,
      updated_at  = now()
RETURNING id, email, login_count;

-- 4. ON CONFLICT DO NOTHING（冲突静默跳过）与 DELETE + RETURNING（删除并返回原记录）
INSERT INTO users (email) VALUES ('alice@example.com') ON CONFLICT (email) DO NOTHING;
DELETE FROM expired_tokens WHERE token_id = 42 RETURNING *;
📖 写操作关键语法拆解
  • RETURNING 子句：可附加在任何 INSERT、UPDATE 或 DELETE 末尾，直接将本次实际插入、修改后或刚删除的行字段作为查询结果集返回给客户端，省去二次查询。
  • 冲突目标 ON CONFLICT (email)：括号内的列必须已经建有主键（PRIMARY KEY）或唯一索引（UNIQUE），用来告诉数据库以哪个唯一约束作为冲突判定依据。
  • 内置虚拟表 EXCLUDED：在 DO UPDATE SET ... 子句中，users.login_count 代表表里原本已经存在的那行旧数据；而 EXCLUDED.login_count 代表本次 VALUES (...) 原本试图插入但因冲突被拒绝的新数据。
  • 多表关联更新语法差异：注意 PostgreSQL 的关联更新写法是 UPDATE 目标表 SET ... FROM 关联表 WHERE ...（不同于 MySQL 的 UPDATE a JOIN b ON ... SET ...）。
🔎 03.2 · 单表查询与 NULL 避坑：WHERE 操作符、ILIKE、NULL 三值逻辑、NULLS LAST 排序与 DISTINCT ON

🔎 03.2 单表查询（SELECT / WHERE / ORDER BY / LIMIT）与 NULL 三值逻辑

单表查询涵盖了列投影（SELECT）、去重（DISTINCT / DISTINCT ON）、条件过滤（WHERE）、排序（ORDER BY）与分页（LIMIT ... OFFSET ...）。编写过滤条件时，最核心的基本功是掌握操作符边界以及 SQL 标准中的 NULL 三值逻辑（TRUE / FALSE / UNKNOWN）：

操作符 / 特性 PostgreSQL 标准写法 边界语义与避坑要点
比较与 NULL 安全判等
= / != / IS NOT DISTINCT FROM		 WHERE phone IS NULL
WHERE a IS NOT DISTINCT FROM b		 普通 = 和 != 只要任意一侧为 NULL，结果恒为 UNKNOWN（查不出任何行）。若需把两个 NULL 视为相等进行比较，使用 SQL 标准语法 a IS NOT DISTINCT FROM b。
区间与集合陷阱
BETWEEN / IN / NOT IN		 WHERE amount BETWEEN 100 AND 500
WHERE status IN ('paid', 'shipped')		 • BETWEEN a AND b 是包含首尾端点的闭区间 [a, b]；
• NOT IN 含 NULL 陷阱：WHERE id NOT IN (1, 2, NULL) 等价于 id != 1 AND id != 2 AND id != NULL，结果恒为 UNKNOWN，整条查询永远返回 0 行。子查询判不存在应改用 NOT EXISTS。
大小写敏感与不敏感模糊匹配
LIKE / ILIKE / ~		 WHERE email ILIKE '%@gmail.com'
WHERE code ~ '^[A-Z]{2}[0-9]+$'		 PostgreSQL 的 LIKE 默认严格区分大小写；若需忽略大小写匹配，直接使用 PG 原生关键字 ILIKE；正则匹配使用运算符 ~（区分大小写）或 ~*（忽略大小写）。
排序时的 NULL 位置控制
NULLS FIRST / NULLS LAST		 ORDER BY last_login_at DESC NULLS LAST 在 PostgreSQL 中，NULL 默认被视为“比任何值都大”，因此 ORDER BY col DESC 时所有 NULL 行默认会排在最前面。按时间或积分降序排列时，加上 NULLS LAST 可将空值行放到末尾。
PG 特色按组去重取首行
DISTINCT ON (分组列)		 SELECT DISTINCT ON (user_id) * FROM orders ORDER BY user_id, created_at DESC 普通 DISTINCT 对整行所有列去重；而 DISTINCT ON (user_id) 会按 user_id 分组，并根据 ORDER BY 顺序直接保留每个用户的第一行记录，语法极其简洁。
🐘 select_single_table.sql · COALESCE、CASE WHEN、NULLS LAST 与 DISTINCT ON 实战 
-- 1. 单表标准查询：COALESCE 空值兜底、CASE WHEN 派生列、括号明确 AND/OR 优先级与 NULLS LAST 分页
SELECT
  id,
  coalesce(nickname, email, '匿名用户') AS display_name,
  balance + coalesce(bonus, 0.00)       AS total_balance,
  CASE
    WHEN balance >= 10000 THEN '钻石'
    WHEN balance >= 1000  THEN '黄金'
    ELSE '普通'
  END AS tier
FROM users
WHERE (city = '杭州' OR city = '上海')
  AND email ILIKE '%@example.com'
  AND deleted_at IS NULL
ORDER BY last_login_at DESC NULLS LAST, id ASC
LIMIT 20 OFFSET 40;

-- 2. DISTINCT ON (user_id)：一行 SQL 取出每个用户最新的一笔订单
SELECT DISTINCT ON (user_id) user_id, id AS latest_order_id, amount, created_at
FROM orders
ORDER BY user_id, created_at DESC;
📊 03.3 · 分组与聚合：COUNT/SUM/AVG、string_agg/array_agg、FILTER 子句以及 WHERE 与 HAVING 的区别

📊 03.3 分组聚合（GROUP BY）、FILTER 子句与 WHERE vs HAVING

对比维度 WHERE 子句 HAVING 子句
过滤阶段 在 GROUP BY 分组前逐行过滤原始表记录 在 GROUP BY 聚合计算后过滤分组汇总结果
聚合函数支持 不可包含聚合函数（此时尚未执行分组汇总） 专门用于筛选聚合结果（如 HAVING sum(amount) >= 5000）
索引利用 可直接利用索引提前裁剪扫描行数，普通列条件应始终优先放入 WHERE 聚合完成后在内存中过滤，不走原表索引
PG 高级聚合函数 除标准 count / sum / avg / max / min 外，PG 原生支持 string_agg(col, ', ')（拼接字符串）、array_agg(col)（聚合成数组）、jsonb_agg(col)（聚合成 JSON 数组）以及 FILTER (WHERE ...) 条件聚合。
🐘 groupby_having_filter.sql · FILTER 条件聚合与 string_agg 
-- 统计 2026 年每个用户的总订单数、已支付单数、已支付总额与商品名称列表
-- 仅保留已支付总额 >= 1000 的用户：
SELECT
  user_id,
  count(*) AS total_orders,
  count(*) FILTER (WHERE status = 'paid') AS paid_orders,
  coalesce(sum(amount) FILTER (WHERE status = 'paid'), 0) AS paid_sum,
  string_agg(DISTINCT item_name, ', ' ORDER BY item_name) AS items
FROM orders
WHERE created_at >= '2026-01-01 00:00:00+08'
GROUP BY user_id
HAVING coalesce(sum(amount) FILTER (WHERE status = 'paid'), 0) >= 1000
ORDER BY paid_sum DESC;
🔗 03.4 · 多表关联与集合：五种标准 JOIN、ON vs WHERE 过滤差异、LEFT JOIN LATERAL 与 UNION ALL

🔗 03.4 多表关联、LATERAL 横向子查询与集合运算

JOIN / 集合类型 集合语义与典型适用场景
INNER JOIN 交集（A ∩ B）：仅返回左右两张表都能匹配上连接条件的行。
LEFT JOIN
（注意 ON vs WHERE）		 左表全集：保留左表所有行，右表无匹配时补 NULL。注意：对右表的过滤条件必须写在 ON 子句中；若写在 WHERE 中会滤掉补 NULL 的行，使左连接退化为 INNER JOIN。
FULL OUTER JOIN 并集（A ∪ B）：左右两表的所有行全部保留，各自无匹配的一侧补 NULL。常用于双渠道账单核对（一条语句同时找出左边多出的账单与右边多出的账单）。
LEFT JOIN LATERAL 横向关联子查询：普通 JOIN 右侧的子查询不能引用左表的列；加上关键字 LATERAL 后，右侧子查询可以直接引用左表当前行的字段（类似对左表每一行执行一次带 LIMIT 的内层索引查询）。
UNION ALL / INTERSECT / EXCEPT 纵向集合运算：UNION ALL 直接追加合并（不去重，性能最高，优于去重的 UNION）；INTERSECT 求两个查询结果的交集；EXCEPT 求差集。
🐘 lateral_and_anti_join.sql · LATERAL 取每组前 N 条与 NOT EXISTS 
-- 1. LEFT JOIN LATERAL：为每个用户直接走索引取出最新的 2 笔订单
-- （右侧子查询中可直接引用左表的 u.id）
SELECT u.id, u.email, recent.order_id, recent.amount
FROM users u
LEFT JOIN LATERAL (
  SELECT o.id AS order_id, o.amount
  FROM orders o
  WHERE o.user_id = u.id
  ORDER BY o.created_at DESC
  LIMIT 2
) recent ON true;

-- 2. NOT EXISTS 反半连接（Anti-Join）：安全查询从未下过单的用户
SELECT u.id, u.email
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);
🪟 03.5 · 分析与递归：窗口函数 OVER (PARTITION BY ... ORDER BY ...)、WITH RECURSIVE 与 9 步执行顺序

🪟 03.5 窗口函数（Window Functions）与递归 CTE

标准的 GROUP BY 分组聚合会将每个分组的多行数据合并折叠为一行汇总结果，无法同时展示原始明细列；而窗口函数（函数() OVER (PARTITION BY 分组列 ORDER BY 排序列)）在不减少原表行数的前提下，为每一行开启一个独立的计算视窗，从而算出该行在所属分组内的排名、占比、滚动累加值或与前后相邻行的差值。

1. 五类常用窗口函数行为对照

窗口函数 并列值处理规则与典型用途
row_number() 连续唯一行号（1, 2, 3, 4）：即使排序字段值相同也按先后分配唯一序号，常用于“每组只取严格 1 条记录”。
rank() 并列跳号排名（1, 1, 3, 4）：两个并列第 1 名后，下一名序号跳到第 3 名。
dense_rank() 并列连续排名（1, 1, 2, 3）：并列后不跳号，适合查询“每个部门薪资排名前 3 档的所有员工”。
lag(col, n, def) / lead(col, n, def) 取同分组内前第 n 行 / 后第 n 行的值（若无前/后行则返回默认值 def），无需自连接即可计算环比增长率或相邻两次操作的时间间隔。
sum(col) OVER (...) 若 OVER() 内不写 ORDER BY，计算整个分组的总和；若写了 ORDER BY，默认计算从分组首行到当前行的滚动累计值。
🐘 window_and_recursive_cte.sql · 窗口函数与递归查树 
-- 场景 1：使用 CTE + row_number() 取出每个用户金额最高的一笔订单
WITH ranked_orders AS (
  SELECT id, user_id, amount,
         row_number() OVER (
           PARTITION BY user_id ORDER BY amount DESC, id DESC
         ) AS rn
  FROM orders
)
SELECT id, user_id, amount FROM ranked_orders WHERE rn = 1;

-- 场景 2：WITH RECURSIVE 递归查询多级部门树（从根节点 id=1 向下展开）
WITH RECURSIVE dept_tree AS (
  -- ① 锚点成员 (Anchor)：只执行一次，找出起始根节点
  SELECT id, name, parent_id, 1 AS depth, name AS full_path
  FROM departments WHERE id = 1
  UNION ALL
  -- ② 递归成员 (Recursive)：用上一轮产出的结果 tree 关联原表 d 查找子节点
  SELECT d.id, d.name, d.parent_id, tree.depth + 1,
         tree.full_path || ' / ' || d.name
  FROM departments d
  JOIN dept_tree tree ON d.parent_id = tree.id
)
SELECT id, name, depth, full_path FROM dept_tree;
📖 概念澄清：SQL 子句的逻辑执行顺序（为什么 WHERE 里不能直接写窗口函数）
一条查询语句在数据库内部的逻辑求值顺序依次为：
① FROM / JOIN ➔ ② WHERE（行级过滤）➔ ③ GROUP BY（分组汇总）➔ ④ HAVING（分组后过滤）➔ ⑤ 窗口函数 OVER(...) ➔ ⑥ SELECT 投影 ➔ ⑦ DISTINCT / DISTINCT ON ➔ ⑧ ORDER BY ➔ ⑨ LIMIT / OFFSET。
由于第 ② 步执行 WHERE 时，第 ⑤ 步的窗口函数尚未计算，因此不能直接写 WHERE row_number() OVER (...) = 1，而是先在 WITH 子句（公共表表达式 CTE）或子查询中算出别名 rn，再在外层查询中执行 WHERE rn = 1。
