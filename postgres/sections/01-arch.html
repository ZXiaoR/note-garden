01.1 · 逻辑层级：Cluster → Database → Schema → Table 四层结构与搜索路径 search_path

01.1 四级目录层级模型与 Schema 命名空间

从 MySQL 转向 PostgreSQL 时，最先遇到的结构差异是数据库（Database）与模式（Schema）的关系。在 MySQL 中，CREATE SCHEMA 与 CREATE DATABASE 是同义词，属于“实例 → 库 → 表”三层结构；而在 PostgreSQL 中，逻辑结构严格划分为四层：

四级结构的核心边界与工程选型

  • 第 1 层 · 实例集群（Cluster）：由一套启动进程管理的整个数据目录（$PGDATA），监听同一个端口（如 5432）。
  • 第 2 层 · 数据库（Database）：物理与会话完全隔离的容器。客户端建立连接时必须指定连入某一个具体的 Database，不同 Database 之间不能直接写 SELECT * FROM db1.t1 JOIN db2.t2。
  • 第 3 层 · 模式（Schema）：同一个 Database 内部的命名空间（文件夹）。每个新库默认自带一个名为 public 的模式。一个业务系统的多个子模块（如用户模块 auth、订单模块 billing）推荐建成同一个 Database 下的不同 Schema，既能避免表名冲突、按模块控制权限，又能直接在同一个事务里跨 Schema 做关联查询与外键引用。
  • 第 4 层 · 数据库对象（Table / View / Index / Sequence / Function）：具体的数据表、视图、索引和序列均归属于某个 Schema 下，完整限定名为 schema名.表名（如 billing.orders）。
schema_and_search_path.sql · 模式创建与搜索路径 
-- 1. 在当前数据库下创建两个业务模块 Schema
CREATE SCHEMA IF NOT EXISTS auth;
CREATE SCHEMA IF NOT EXISTS billing;

-- 2. 使用 Schema.表名 在指定模式下建表并跨模式建立外键
CREATE TABLE auth.users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text   NOT NULL UNIQUE
);

CREATE TABLE billing.orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES auth.users(id),
  amount  numeric(10, 2) NOT NULL
);

-- 3. 查看与修改 search_path（不写 Schema 前缀时的默认查找顺序）
SHOW search_path;  -- 默认返回: "$user", public
SET search_path TO billing, auth, public;

-- 设置后，直接写 SELECT * FROM orders 会优先去 billing 下查找
SELECT u.email, o.amount
FROM auth.users u
JOIN billing.orders o ON o.user_id = u.id;
01.2 · 权限与配置：角色（Role）与用户管理、最小权限赋权及两大核心配置文件

01.2 角色权限管理与核心配置文件

PostgreSQL 采用统一的角色（Role）模型来管理账号与权限组：一个带有登录权限（LOGIN）的 Role 就是传统意义上的“数据库用户（User）”；不带登录权限的 Role 则相当于“权限角色组（Group）”，可以把一组权限赋予组角色，再把组角色授予具体用户。

role_and_grant.sql · 创建应用账号与最小权限赋权 
-- 1. 创建带登录密码的业务应用账号（等同于 CREATE USER）
CREATE ROLE app_rw WITH LOGIN PASSWORD 'StrongPass_2026';

-- 2. 授予连接数据库、进入 billing 模式的权限（缺一不可）
GRANT CONNECT ON DATABASE app_prod TO app_rw;
GRANT USAGE ON SCHEMA billing TO app_rw;

-- 3. 授予模式下现有所有表的增删改查权限与序列使用权限
GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA billing TO app_rw;
GRANT USAGE, SELECT
  ON ALL SEQUENCES IN SCHEMA billing TO app_rw;

-- 4. 设置默认权限：让未来在 billing 下新建的表也自动对 app_rw 授权
ALTER DEFAULT PRIVILEGES IN SCHEMA billing
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;

数据目录（$PGDATA）下的两大核心配置文件

配置文件 核心职责与常用配置项
1. postgresql.conf
（实例主参数文件）		 控制监听地址、端口、内存与日志策略：
• listen_addresses = '*'：允许远程网卡连接（默认仅 localhost）；
• max_connections = 200：最大并发后端进程连接数；
• shared_buffers = 4GB：共享数据页缓存大小（通常设为物理内存的 25%~40%）；
• log_min_duration_statement = 500：记录执行耗时超过 500ms 的慢 SQL。
2. pg_hba.conf
（客户端认证白名单）		 Host-Based Authentication，按顺序匹配“连接类型 + 数据库 + 用户 + 客户端网段 + 认证算法”：
• 例如 host all all 10.0.0.0/8 scram-sha-256 表示允许内网 10.x 网段使用安全的 SCRAM-SHA-256 哈希密码认证登录。
• 修改后无需重启实例，执行 SELECT pg_reload_conf(); 即可热加载生效。
01.3 · 连接管理：标准连接串 URL 格式、应用层连接池与 PgBouncer 的日常定位

01.3 标准连接串格式与连接池配置规范

在 Go、Node.js、Java 或 Python 等后端服务中连接 PostgreSQL 时，通常通过标准的 PostgreSQL Connection URI 传入连接信息与超时参数：

标准 PostgreSQL 连接串格式与常用查询参数 
# 标准格式：postgresql://用户名:密码@主机名:端口/数据库名?参数名=参数值
postgresql://app_rw:StrongPass_2026@db.internal:5432/app_prod?sslmode=require&connect_timeout=5&application_name=order-service&options=-c%20statement_timeout%3D3000
连接参数 / 概念 推荐配置值示例 工程作用说明
application_name order-service 将当前微服务名称上报给数据库。排查慢查询或锁等待时，可在 pg_stat_activity 视图中直接看到是哪个业务服务发出的请求。
statement_timeout 3000（即 3 秒） 单条 SQL 最大允许执行时长。超时后服务端主动中止该语句，防止慢查询无限期占用数据库连接与 CPU。
idle_in_transaction_session_timeout 10000（即 10 秒） 防止应用代码开启事务 BEGIN 后因逻辑 Bug 或外部接口卡住而忘记 COMMIT/ROLLBACK，超时自动断开释放行锁。
应用层连接池 & PgBouncer 单实例连接池 10~20；多实例前置 PgBouncer PostgreSQL 服务端采用“一连接一进程”模型，每个连接进程会占用约 5~15MB 内存。因此业务代码必须使用连接池复用连接；当微服务容器实例扩展到上百个时，建议在数据库前部署轻量级连接池中间件 PgBouncer，将数千个应用连接收敛到百余个真实数据库进程上。
