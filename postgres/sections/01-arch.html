❓ 01.1 · 为什么 PostgreSQL 坚持用“多进程”而不是 MySQL 的“多线程”？生产环境为什么一定要挂 PgBouncer？

🏛️ 01.1 进程模型：多进程（Process-per-Connection）架构全拆解

PostgreSQL 是一个开源的对象-关系型数据库（ORDBMS），以严格遵循 SQL 标准、复杂查询优化器强大和扩展生态丰富著称。在进程模型上，它与 MySQL（单进程多线程）截然不同：每个客户端连接到达时，主守护进程 postmaster 会 fork() 出一个独立的后端进程（postgres backend process）专门服务该会话。

  • 多进程的核心优势（故障隔离）：某个连接因为复杂扩展（如 C 插件）或极端 SQL 触发段错误崩溃时，不会直接把整个数据库地址空间搞挂，postmaster 可以安全接管并执行恢复。
  • 多进程的工程代价（连接开销 → 必配 PgBouncer）：每个 backend 进程独享一份私有内存（work_mem、temp_buffers、系统表缓存 Catalog Cache，单连接常占 5～15 MB），且新建连接要经历 fork() 开销。因此当业务有上千个微服务实例直连时，严禁把 max_connections 盲目调到几千，而是必须在前面部署轻量级连接池 PgBouncer（推荐使用 transaction 事务级池化模式，把几千个客户端连接复用在 100～200 个真实 PG 进程上）。
核心组件 职责与生产调优关键点
postmaster 主进程 数据库实例总管：监听 5432 端口、为新连接 fork 后端进程、启动后台守护进程，并在后端异常崩溃时负责共享内存重置与 WAL 崩溃恢复。
backend 会话进程 每个客户端连接独占一个进程，负责完成该连接上 SQL 的解析（Parser）、重写（Rewriter）、优化器规划（Planner）与执行（Executor）。注意：work_mem（默认 4MB）是每个排序/哈希算子都可以分配一份，并非整个连接上限！
Shared Buffers 所有进程共享的数据页缓存池（页大小默认 8 KiB），地位等同于 MySQL 的 Buffer Pool。默认仅 128MB，生产环境通常调至机器内存的 25%～40%（剩余留给 OS Page Cache，因为 PG 依赖双层缓存）。
WAL Writer 定期将共享内存 WAL Buffers 中的预写日志刷入磁盘 pg_wal/，保障事务提交的持久性（Durability）。
Bgwriter & Checkpointer Bgwriter 后台平滑把少量脏页写回磁盘，避免查询进程自己找空页时被迫刷盘；Checkpointer 按时间（checkpoint_timeout）或 WAL 量（max_wal_size）将所有脏页落盘并推进恢复起点。
⭐ Autovacuum PG 运维命脉：定期唤醒 Worker 进程扫描表，回收 MVCC 留下的死元组空间、更新可见性映射（VM）与统计信息（ANALYZE），并冻结（Freeze）老事务 ID 防止 32 位事务号回卷（详见第 06 章）。
❓ 01.2 · PG 里的 Database 和 Schema 有什么区别？为什么跨库不能直接写 JOIN？

🛠️ 01.2 四级目录层级、安装启动与 psql 元命令速查

🧭 概念澄清：PostgreSQL 的四层逻辑结构（对比 MySQL 的三层扁平结构）
在 MySQL 中，CREATE SCHEMA 等同于 CREATE DATABASE，同一实例下不同库可以直接 SELECT * FROM db1.t1 JOIN db2.t2。
而在 PostgreSQL 中，严格划分为四层：实例集群（Cluster） → 数据库（Database，物理隔离） → 模式（Schema，命名空间，默认 public） → 表/视图/函数。不同 Database 之间连接隔离、不能直接写 SQL JOIN（跨库需借用 postgres_fdw 外部表）；一个项目内的多模块分治，推荐放在同一个 Database 下的不同 Schema 中（如 SELECT * FROM auth.users JOIN billing.orders ...），通过 SET search_path TO auth, public; 控制默认查找顺序。

💻 安装与连接常用命令

# macOS Homebrew 安装与后台启动
brew install postgresql@16
brew services start postgresql@16

# 命令行连接（默认连接同名库/当前系统用户）
psql postgres
psql -h localhost -p 5432 -U myuser -d mydb

# 查看当前连接的库、用户、Schema 搜索路径
SELECT current_database(), current_user;
SHOW search_path;

❓ 面试自测：PostgreSQL 和 MySQL 最核心的三大架构区别是什么？
  1. 并发模型（多进程 vs 多线程）：PG 每个连接由 postmaster fork 独立 backend 进程，故障隔离好但单连接开销大，高并发必配 PgBouncer；MySQL 每连接一个线程。
  2. 存储引擎与表组织（单一堆表引擎 vs 插件式聚簇索引）：PG 没有插件式引擎概念，表统一采用无序堆表（Heap）+ ctid 物理寻址；MySQL InnoDB 表即主键 B+ 树（索引组织表）。
  3. MVCC 多版本落盘位置（堆表内追加 vs Undo Log）：PG 把旧版本直接留在数据表页里（靠 xmin/xmax 标记），靠后台 VACUUM 异步清理死元组；InnoDB 把旧版本放进独立的 undo log 回滚段。这一点直接衍生出 PG 特有的“表膨胀”、“HOT 更新”与“事务 ID 回卷”运维体系。
