🔥 06.1 · HOT (Heap-Only Tuple) 页内更新链与实时页内剪枝（Page Pruning）

🔥 06.1 HOT 页内更新与实时页内剪枝（On-Access Page Pruning）

在 PostgreSQL 的堆表架构下，一次普通的 UPDATE 默认会产生双倍放大：不仅要在堆表中插入一条新元组，还要为这张表上的每一个索引都追加一条指向新元组 ctid 的索引记录（即使被更新的列根本不在索引里）。为了攻克这一痛点，PostgreSQL 8.3 引入了极为关键的 HOT（Heap-Only Tuple，仅堆元组）优化机制。

触发 HOT 更新的两大充要条件与 LP_REDIRECT 转发链

  1. 条件一（未动索引列）：本次 UPDATE 语句没有修改任何被索引引用的列（包括主键、唯一索引、普通索引、部分索引的谓词列以及表达式索引涉及的列）。
  2. 条件二（同页放得下）：旧版本元组所在的同一个 8 KiB 数据页内，仍有足够的剩余空闲空间容纳更新后的新元组。

一旦同时满足这两个条件，内核就会走 HOT 路径：完全不去触碰任何外部 B-tree 索引。所有外部索引依然指向该页最初的根行指针槽位（Root Line Pointer，例如槽位 1），而在数据页内部通过元组头的 HEAP_HOT_UPDATED 与 HEAP_ONLY_TUPLE 标志构建一条页内 HOT 链。更妙的是，后续任何普通查询在访问该数据页时，只要顺手发现页内存在已对所有活跃事务不可见的中间旧版本，无需等待后台 autovacuum，当场就能触发轻量级的 实时页内剪枝（On-Access Page Pruning），把根槽位改为 LP_REDIRECT 直接指向最新元组，并立刻回收中间旧版本占用的页内字节空间。

♻️ 06.2 · 32 位 XID 环形回卷、VACUUM FREEZE 与四大膨胀阻塞源

♻️ 06.2 32 位 XID 环形回卷、VACUUM FREEZE 与死元组膨胀根因

32 位 XID TransactionIdPrecedes 环形比较算法与元组冻结（Freeze）

如果把元组头里的 t_xmin（4B）和 t_xmax（4B）直接扩充为 8 字节的 64 位整数，每一行元组就会永久多出 8 字节开销，百亿行大表平白膨胀上百 GB。因此 PostgreSQL 至今在磁盘元组头中保留了 32 位无符号事务 ID（共 232 ≈ 42.9 亿 个编号，其中 0=Invalid、1=Bootstrap、2=Frozen，普通事务从 3 开始分配），并使用模 232 算术来比较两个 XID 的先后：

🔄 TransactionIdPrecedes · 32 位事务 ID 模 2^32 环形先后比较算法（src/backend/access/transam/transam.c） 
// 比较两个 32 位无符号事务 ID (id1 是否在 id2 之前发生)：
bool TransactionIdPrecedes(TransactionId id1, TransactionId id2) {
    int32 diff = (int32) (id1 - id2);
    return (diff < 0); // 与当前 XID 向后距离小于 2^31 (约 21.4 亿) 的视为过去，大于 2^31 的视为未来
}

这就意味着：假定某一行数据是由 XID = 100 插入的，只要系统继续往前推进了超过 231（约 21.47 亿）个写事务，当新事务来到 XID = 2147483749 时，100 - 2147483749 在 32 位有符号整数下发生溢出变成正数，内核就会认为 XID = 100 是一个尚未发生的未来事务，导致这行早已提交的历史数据在查询中瞬间消失（即 XID Wraparound 事务回卷故障）。

为了彻底消除这一风险，VACUUM 进程在后台扫描数据页时，只要发现某条已提交元组的 t_xmin 年龄超过了 vacuum_freeze_min_age（默认 5000 万个事务），就会将其元组头中的 t_infomask 打上 HEAP_XMIN_FROZEN（即 HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID 组合位）。任何被打上冻结标记的元组，无论未来事务 ID 绕环多少圈，都被无条件判定为「永恒的过去，对所有事务可见」。当整张表的 XID 年龄达到 autovacuum_freeze_max_age（默认 2 亿）时，即使关闭了普通 autovacuum，内核也会强制拉起不可取消的 anti-wraparound autovacuum 推进该表的 relfrozenxid。

阻止死元组回收与 relfrozenxid 推进的「四大元凶」

在生产运维中，有时你会发现对一张膨胀严重的表手动执行 VACUUM VERBOSE table_name，日志却提示 0dead item identifiers removed, X dead row versions cannot be removed yet, oldest xmin: 123456。这是因为全局死元组回收水位线（OldestXmin）被卡住了，常见根因有且仅有以下四类：

阻塞源类型 为什么会卡住全局 OldestXmin 排查系统视图与处置方案
1. 未提交的长事务 / idle in transaction 某个会话在 Repeatable Read 下开启了事务（或正在跑数小时的大报表），它随时可能读取该事务启动时刻之后的旧版本，导致整个实例在此之后产生的所有死元组都无法回收 查 pg_stat_activity 中 backend_xmin IS NOT NULL 且 age(backend_xmin) 最大的会话；配置 idle_in_transaction_session_timeout = '60s' 自动清理僵尸事务
2. 废弃或断开的复制槽（Replication Slots） 物理备库开启了 hot_standby_feedback = on，或者逻辑订阅端下线后遗留了 active = false 的复制槽，主库为了照顾下游仍牢牢锁住旧 xmin / catalog_xmin 查 pg_replication_slots 的 xmin 与 catalog_xmin；对废弃槽调用 pg_drop_replication_slot('slot_name')，并配置 max_slot_wal_keep_size 保底
3. 孤儿两阶段提交事务（Orphaned 2PC Prepared Xacts） 分布式事务执行了 PREPARE TRANSACTION 'gid' 后，协调者崩溃未发 COMMIT PREPARED，该事务永久悬停在内存中 查 pg_prepared_xacts 视图（关注 age(transaction)）；确认业务状态后执行 ROLLBACK PREPARED 'gid';
4. 跨事务游标与延迟索引构建 连接池会话中遗留了未关闭的 DECLARE ... CURSOR WITH HOLD，或别的表正在跑长达数小时的 CREATE INDEX CONCURRENTLY 查 pg_cursors 视图；在 PgBouncer Transaction Pooling 下清理会话级游标
📦 VACUUM vs VACUUM FULL vs pg_repack 空间回收边界：
标准 VACUUM（不带 FULL）不阻塞任何读写 DML，但它只是把死元组占用的页内空间清理后登记到附属的 空闲空间映射表（Free Space Map，后缀 _fsm，内部是一棵三层二叉最大堆树，每个数据页用 1 字节以 32 字节为步长记录剩余空间）中，供本表后续 INSERT / UPDATE 复用，不会把已分配的数据页归还给操作系统文件系统（除非表末尾恰好有连续全空页且能瞬间拿到排他锁截断）。
若表因历史故障已膨胀至 200 GB（有效数据仅 20 GB），想要把 180 GB 磁盘空间真正归还给操作系统：切忌在业务高峰期直接跑 VACUUM FULL（它会申请 8 级最强排他锁 AccessExclusiveLock 重写全表，彻底冻结读写）。生产标准做法是使用社区成熟的在线缩表工具 pg_repack：它先创建一张与原表结构一致的影子新表，通过触发器（或逻辑解码）记录重放期间的增量变更，全量拷贝并建好索引后，仅在最后毫秒级切换新旧表 relfilenode 时短暂加锁。
📝 06.3 · WAL 预写日志、Full Page Writes 防页撕裂与流复制架构

📝 06.3 WAL 预写日志、full_page_writes 防页撕裂与流复制

LSN（日志序列号）、pd_lsn 与预写式法则（Write-Ahead Logging）

PostgreSQL 的一切持久性保证都建立在 WAL（Write-Ahead Log，位于 pg_wal/ 目录，默认每个切片文件 16 MB）之上。每一条 WAL 记录在整个数据库簇生命周期内的字节偏移量被称为 LSN（Log Sequence Number，64 位整数，显示为 XXXX/YYYYYYYY 格式，可通过 pg_current_wal_lsn() 查看）。

  • 先写日志后刷脏页原则（WAL Rule）：每当后台进程修改了 Shared Buffers 中的某个 8 KiB 数据页，它不仅会生成一条 WAL 记录放入 WAL Buffers，还会把这条 WAL 记录的结束位置写入该数据页头部的 pd_lsn 字段。当 BgWriter 或 Checkpointer 准备把一个脏数据页刷回磁盘前，内核必须校验：当前已经安全落盘的 WAL LSN 位置必须大于等于该数据页头的 pd_lsn；否则必须先把对应的 WAL 刷盘，绝不允许未落盘日志的脏页提前写入数据文件。
  • 为什么需要 full_page_writes = on？（防御操作系统 4 KiB 页撕裂 Torn Page）：PostgreSQL 的数据页是 8 KiB，而 Linux 文件系统块与底层 SSD 硬件页通常是 4 KiB。如果在刷写一个 8 KiB 数据页的瞬间发生断电，磁盘上可能出现前 4 KiB 是新数据、后 4 KiB 还是旧数据的「半页撕裂（Torn Page）」。由于标准 WAL 记录里保存的是基于完整旧页的物理字节增量，面对一个损坏撕裂的半页根本无法重放（Redo）恢复。因此，PostgreSQL 默认开启 full_page_writes = on：每次 Checkpoint 之后，任意一个 8 KiB 数据页第一次被修改时，内核会将这整张 8 KiB 数据页的完整镜像（Full Page Image, FPI）直接写入 WAL 中。崩溃重启时若遇到撕裂页，直接用 WAL 中的完整 8 KiB 镜像覆盖修复，随后再重放后续增量 WAL。

物理流复制（Physical Streaming Replication）与逻辑复制（Logical Replication）对比

对比维度 物理流复制（Physical Streaming Replication） 逻辑复制（Logical Replication，Publication / Subscription）
传输内容 直接传输底层 WAL 字节流（包含哪张表哪个块号哪个偏移量改了哪些字节） 通过解码插件（pgoutput）将 WAL 解析为逻辑行变更事件（INSERT / UPDATE / DELETE 元组值）
粒度与跨版本能力 整实例级（Cluster-wide）逐字节镜像；主备库大版本号与硬件架构必须完全一致 支持按单表、按指定列、按行过滤条件（PG 15+ WHERE）选择性复制；支持跨大版本零停机升级（如 PG 13 → PG 16）
备库可写性与索引 备库只读（Hot Standby），主库建索引备库自动同步拥有 订阅端是一台完全独立可写的实例，可在订阅端针对报表分析需求建立与主库不同的专属索引
同步提交等级（synchronous_commit） 支持五级精细调节：off（异步刷本地 WAL）→ local（仅主库本地刷盘）→ remote_write（备库接收写入 OS 缓存）→ on（默认同步模式，备库 WAL 落盘即返回）→ remote_apply（备库不仅落盘且已完成 Redo 回放，读备库立即可见，实现零延迟读写分离）
🎯 06.4 · PostgreSQL 原理与架构深度自测（15 题闭卷检验）

🎯 06.4 PostgreSQL 核心原理与架构调优闭卷自测（15 题）

以下 15 道核心原理与架构调优题串联了本篇从存储页布局、进程内存、MVCC 快照、索引算法到垃圾回收与崩溃恢复的完整知识链路。建议先在脑海中组织回答，再点击展开核对内核级解析：

01. 对比 MySQL InnoDB，为什么说 PostgreSQL 的堆表架构在「读历史版本」上更快，但在「按主键点查」和「高频更新」上面临不同挑战？

解析：InnoDB 是索引组织表（IOT），新版本原地覆盖并把旧版本写入 Undo Log，因此读取老快照时需要顺着回滚段逐跳逆向重构，长事务下历史读会变慢；而 PostgreSQL 是堆表（Heap），新旧版本并排存在 8 KiB 数据页内，读历史版本只需根据快照过滤 t_xmin / t_xmax，无需回滚计算。代价是：1）PG 的主键也是二级索引，按主键点查需要「B-tree 查 ctid + 堆表取数据」两步；2）每次跨页的非 HOT 更新都会改变元组的物理 ctid，迫使表上所有索引都追加一条新索引项，且必须依赖 VACUUM 异步回收死元组。

02. 8 KiB 数据页内部为什么采用「行指针数组向下生长、元组数据从页尾向上生长」的双向对向布局？

解析：为了将「外部逻辑寻址」与「页内物理搬移」彻底解耦。外部 B-tree 索引只存储 6 字节的 ctid = (块号, 页内行指针槽号)，从不记录元组在页内的真实字节偏移。当页内发生死元组清理或页内紧凑整理（Defragmentation）时，内核可以在页尾自由移动存活元组的位置以合并碎片，随后只需修改页头对应的 4 字节 ItemIdData (lp_off) 偏移量即可，外部所有索引无需做任何修改。

03. 什么是 TOAST 机制？如果一张表包含一个 5 MB 的 TEXT 大字段，查询时不读取该列，为什么不会拖慢全表扫描？

解析：PostgreSQL 不允许单条元组跨越 8 KiB 页边界。当变长列超过约 2 KB（TOAST_TUPLE_THRESHOLD）时，TOAST 机制会先用 pglz / lz4 压缩该列；若仍超标则将其按约 2 KB 切片存入独立的附属表 pg_toast.pg_toast_<oid> 中，原主表元组内仅保留一个 18 字节的轻量级 TOAST 指针。因此，只要查询语句明确指定列名（不写 SELECT *）且未访问该大字段，执行器在扫描主表时根本不会去读取和解压 TOAST 表，从而保持极高的页密度与扫描速度。

04. 为什么把 work_mem 盲目调大到 1GB 极其危险？它与 shared_buffers 的内存分配模型有何本质区别？

解析：shared_buffers 是整个 PostgreSQL 实例在启动时一次性分配的全局共享内存（无论有多少并发连接都只有一份）；而 work_mem 是每个后台进程内每一个排序（Sort）或哈希（Hash Join / HashAggregate）算子节点独立申请的私有内存上限。一条复杂 SQL 若包含 5 个哈希/排序算子，且开启了 4 个并行 Worker，单条 SQL 最高就能消耗 5 × 4 × work_mem；若此时有 100 个并发会话同时执行，总内存需求会瞬间达到数百 GB，直接触发 Linux 内核 OOM Killer 杀掉 postmaster 主进程。

05. 为什么在大批量导入数据（如 COPY 1000 万行）之后，第一次执行纯只读的 SELECT COUNT(*) 会产生极其密集的磁盘写 I/O？

解析：因为事务提交时为了极速响应，只修改了 pg_xact (CLOG) 中 2 个 bit 的事务状态，并未去修改那 1000 万行数据所在数据页上的元组头。当第一次执行 SELECT COUNT(*) 扫描这些数据页时，读进程发现元组头的 t_infomask 尚未打上 HEAP_XMIN_COMMITTED 提示位（Hint Bits），就会去查询 pg_xact 并顺手将 HEAP_XMIN_COMMITTED 回写到每个元组头中，导致所有被读过的数据页全部变成脏页并触发大量写盘。导入后立即执行一次 VACUUM ANALYZE 可以一次性完成提示位标记、生成可见性映射表（_vm）并收集统计信息。

06. 在 PostgreSQL 中，JSONB 与 JSON 的底层存储与访问复杂度有何差异？

解析：JSON 类型仅原样保存原始文本字符串，每次提取字段都必须从头做词法解析（O(N)）；而 JSONB 在写入时已解析为紧凑的二进制树：每个对象层级头部都带有一个定长 4 字节的 JEntry 目录数组，且所有键（Key）在写入时已按「先比字节长度、同长度再比 ASCII 字典序」去重排好序。因此读取 data->'target_key' 时，内核直接在 JEntry 数组上做 O(log K) 二分查找，比对时甚至先看长度是否相等，长度不等连字符串内容都不用碰，查中后直接按偏移量一步跳到对应的 Value 位置。

07. 为什么 PostgreSQL 支持几乎所有 DDL（建表、加列、改类型、删表）放入 BEGIN ... ROLLBACK 中原子回滚，而 MySQL 却会隐式提交？

解析：因为 PostgreSQL 的数据字典本身就是一组受标准 MVCC 保护的普通系统表（如 pg_class、pg_attribute、pg_index）。执行 CREATE TABLE 或 ALTER TABLE 本质上是在当前事务 XID 下向这些系统表执行 INSERT / UPDATE / DELETE；对于 DROP TABLE 或 TRUNCATE，内核也不会当场调用操作系统 unlink() 删除物理文件，而是先将其 relfilenode 登记到当前事务的「待删除文件列表」中。一旦执行 ROLLBACK，系统表中的元数据元组因 t_xmin 回滚而自动对所有事务不可见，待删除队列被丢弃，从而实现纯粹的事务性 DDL。

08. 同样是一张 1000 万行的表，WHERE a = 1 和 WHERE b = 1 各自都命中 10 万行（选择率均为 1%），为什么优化器对列 a 走 Index Scan，对列 b 却走 Bitmap Heap Scan？

解析：关键在于统计信息 pg_stats.correlation（物理线性相关系数）。列 a（如自增 ID 或创建时间）的物理存储顺序与索引顺序高度一致（correlation ≈ 1.0），命中 10 万行只需连续顺序读取约 1000 个相邻数据页，因此直接走 Index Scan 最快；而列 b（如随机分布的用户状态或哈希值）的 correlation ≈ 0.0，10 万行均匀散落在全表近 10 万个不同数据页上，若走普通 Index Scan 会触发 10 万次跨页随机 I/O，因此优化器改走 Bitmap Index Scan + Bitmap Heap Scan，先在内存中按物理页号排好序再批量顺序跳读。

09. 并发执行同一条 UPDATE accounts SET balance = balance - 30 WHERE id = 1 AND balance >= 30，在 Read Committed 和 Repeatable Read 下分别会发生什么？

解析：当事务 B 等待事务 A 提交后被唤醒时：1）在默认的 Read Committed 下，事务 B 触发 EvalPlanQual (EPQ) 机制，顺着旧版本的 t_ctid 指针找到事务 A 刚提交的最新元组版本，重新校验一次 WHERE balance >= 30 条件，若仍满足则基于新版本继续扣减；2）在 Repeatable Read 或 Serializable 下，遵循 First-Updater-Wins 原则，检测到目标元组已被并发事务修改后立即抛出 SQLSTATE 40001 (could not serialize access due to concurrent update)，要求应用层重试事务。

10. PostgreSQL 的行级锁（如 FOR UPDATE / FOR SHARE）存放在哪里？为什么在 PG 中一个事务锁住 500 万行也不会发生「行锁升级为表锁（Lock Escalation）」？

解析：PostgreSQL 的行级锁不存储在有限的共享内存锁哈希表中，而是直接记录在 8 KiB 数据页内每一条元组的头部（将加锁事务的 XID 或多事务组合 MultiXactId 写入 t_xmax，并在 t_infomask 中置位锁类型标志）。因为锁信息随数据页一起持久化并可换出内存，所以无论单个事务锁定多少行，都不会撑爆共享内存锁表，内核也永远不需要把行锁粗化升级为表锁。

11. 既然 PostgreSQL 的 B-tree 索引项中只存了「键值 + ctid」而没有存 t_xmin / t_xmax，它是如何实现免回表的 Index Only Scan 的？

解析：依靠每个表附属的可见性映射表（Visibility Map，后缀 _vm）。_vm 为每个 8 KiB 数据页维护 2 个 bit（其中第 1 位是 ALL_VISIBLE）。当 VACUUM 清理完某个数据页并确认页内所有元组对当前及未来所有事务均可见后，会将该页的 ALL_VISIBLE 位置为 1。Index Only Scan 从索引拿到 ctid 后，先查内存中的 _vm 位图：若目标页为 1 则直接返回索引列值（免回表）；若该页近期被修改过导致位图为 0，则必须回表检查元组头（体现在 EXPLAIN ANALYZE 的 Heap Fetches 计数中）。

12. 什么是 HOT（Heap-Only Tuple）更新？高频更新的表应该如何配置以最大化 HOT 比例？

解析：当一次 UPDATE 既没有修改任何索引列，且旧元组所在的同一个 8 KiB 数据页内仍有足够空间存放新元组时，就会触发 HOT 更新：外部所有 B-tree 索引完全不用修改（继续指向页内最初的根槽位），新旧版本在页内构成短链，并且支持在后续普通查询访问该页时当场执行实时页内剪枝（Page Pruning）回收死空间。对于高频更新非索引列的表，应通过 ALTER TABLE ... SET (fillfactor = 80); 在每个数据页预留 10%~20% 的空闲空间，确保更新始终能留在同页内走 HOT 路径。

13. 什么是 32 位事务 ID 回卷（XID Wraparound）？VACUUM FREEZE 是如何解决这个问题的？

解析：为了节省元组头空间，t_xmin / t_xmax 采用 32 位无符号整数（约 42.9 亿），并通过模 232 环形算法比较先后：与当前 XID 向后距离小于 231（约 21.4 亿）的视为过去，大于 231 的视为未来。如果一行已提交的老元组经历了超过 21.4 亿次新写事务仍未被处理，它就会跨过半环分界线被误判为「未来未提交事务」而瞬间不可见。为此，VACUUM 会在老元组年龄达到阈值时将其元组头的 t_infomask 置位 HEAP_XMIN_FROZEN（冻结），被冻结的元组不再参与环形年龄计算，永远对所有事务可见。

14. 线上某张核心表空间持续暴涨，手动执行 VACUUM VERBOSE 发现大量死元组显示 cannot be removed yet，应该按什么顺序排查？

解析：说明全局回收水位线 OldestXmin 被某个老快照卡住了，按以下四步排查：
1）查 pg_stat_activity 中 backend_xmin IS NOT NULL 的长事务或 idle in transaction 僵尸连接；
2）查 pg_replication_slots 中是否存在 active = false 的废弃复制槽或落后严重的备库锁住了 xmin / catalog_xmin；
3）查 pg_prepared_xacts 中是否有未决的孤儿两阶段提交事务（PREPARE TRANSACTION）；
4）查 pg_cursors 或是否有其他大表正在跑耗时数小时的 CREATE INDEX CONCURRENTLY。

15. 为什么 PostgreSQL 的 WAL 日志默认必须开启 full_page_writes = on？关闭它会有什么风险？

解析：因为 PostgreSQL 的数据页大小是 8 KiB，而 Linux 操作系统与底层磁盘硬件的原子写入粒度通常是 4 KiB。若在刷写 8 KiB 脏页途中发生掉电或内核崩溃，磁盘上会出现前 4 KiB 已更新、后 4 KiB 仍是旧数据的「页撕裂（Torn Page）」，此时仅靠增量 WAL 日志无法在损坏的半页上完成 Redo 恢复。开启 full_page_writes = on 后，每次 Checkpoint 之后每个数据页第一次被修改时，都会把整张 8 KiB 完整页面镜像写入 WAL；崩溃恢复时直接用该完整镜像覆盖修复撕裂页，从而保证 100% 的数据完整性。
