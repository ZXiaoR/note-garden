🏛️ 01.1 · 进程与内存拓扑：postmaster 守护进程、Backend 私有内存乘数效应与后台进程协作

🏛️ 01.1 多进程架构与私有/共享内存边界拆解

PostgreSQL 实例启动时，由主守护进程 postgres（传统名称为 postmaster）通过 mmap 或 System V IPC 分配一块全局共享内存区（Shared Memory），随后派生出多个各司其职的后台守护进程。每当客户端通过 TCP 5432 端口完成认证，postmaster 便调用 fork() 启动一个独立的 Backend 会话进程专门处理该连接上的所有 SQL 请求：

⚠️ 内存调优关键误区：work_mem 的乘数放大效应与 Catalog Cache 膨胀
  • work_mem（默认 4MB）不是单个连接的总上限，而是单个执行算子（Operator）的上限：一条复杂分析 SQL 如果包含 4 个 Sort 或 Hash Join 节点，并且开启了 4 个并行 Worker 进程，那么单条 SQL 就可能瞬时申请 4 个算子 × 4 个进程 × work_mem 的内存。若将全局 work_mem 盲目调大到 256MB，上百个并发查询同时执行时极易触发操作系统 OOM Killer 强杀数据库进程。正确做法是全局保持 16MB~64MB，仅在特定报表会话内临时执行 SET LOCAL work_mem = '256MB';。
  • 系统目录缓存（Catalog Cache / relcache）只增不减：每个 Backend 进程都会在私有内存中缓存它访问过的表结构与统计信息元数据。如果单个库里有数万张分区表且使用长连接，每个 Backend 进程的 catcache 都可能膨胀到上百 MB。
⏱️ 01.2 · 缓冲池淘汰：BufferDesc 描述符数组、Clock-Sweep 时钟扫描算法与双层缓存机制

⏱️ 01.2 Shared Buffers 时钟扫描算法与双层缓存

Shared Buffers 被划分为成千上万个固定 8 KiB 的缓冲槽（Buffer Slot），每个槽位配有一个 64 字节的元数据头 BufferDesc（缓冲描述符），内部维护两个核心计数值：

1. pin_count 与 usage_count 状态流转

  • 引用计数 refcount (pin_count)：记录当前正在读写该 8KB 页的 Backend 进程数。只要 pin_count > 0，说明有进程正在使用该页，该页被钉住（Pinned），绝不允许被淘汰替换。
  • 访问热度计数 usage_count（取值范围 0 ~ 5）：每当一个缓冲页被任意会话访问一次，其 usage_count 加 1（上限封顶为 BM_MAX_USAGE_COUNT = 5，防止早期高频访问的历史冷页积攒几万分后永远无法被淘汰）。
  • Clock-Sweep（时钟指针扫描）替换流程：当 Backend 需要读入新磁盘页且空闲链表（freelist）为空时，全局时钟指针 nextVictimBuffer 依次扫描各个 BufferDesc：
    1. 若当前槽位 pin_count > 0，直接跳过检查下一格；
    2. 若 pin_count == 0 且 usage_count > 0，将其 usage_count 减 1（给热页第二次机会），指针继续前移；
    3. 一旦遇到 pin_count == 0 且 usage_count == 0 的缓冲页，即选中为淘汰牺牲页（Victim Buffer）。

2. 双层缓存架构下 shared_buffers 推荐设为 25%~40% 的内核原因

存储引擎 磁盘 I/O 方式 内存分配策略差异根因
MySQL InnoDB 默认开启 O_DIRECT 绕过操作系统缓存 InnoDB 自行管理预读与脏页刷盘，不依赖 OS Page Cache，因此可将 innodb_buffer_pool_size 设为物理内存的 60%~80%。
PostgreSQL 标准缓冲 I/O（经由 OS Page Cache 双层缓存） PG 读取磁盘页时，数据会先进入操作系统内核的 Page Cache，再拷入 Shared Buffers；当某页从 Shared Buffers 淘汰后，往往仍驻留在 OS Page Cache 中（即 EXPLAIN 中的 shared read 未必发生真实物理磁盘 I/O），且 PG 十分依赖操作系统的顺序预读（Read-Ahead）与写合并，因此预留 60% 左右物理内存给 OS Page Cache 与进程私有内存综合吞吐最优。
🛡️ 01.3 · 连接池内核：高并发直连下的 ProcArrayLock 争用与 PgBouncer 三级池化模式对比

🛡️ 01.3 高并发连接瓶颈与 PgBouncer 池化模式剖析

当应用集群直连 PostgreSQL 的活躍进程数达到上千个时，除了进程私有内存消耗外，更严重的性能衰减来自内核全局进程数组锁（ProcArrayLock）争用与快照生成开销：每次生成事务快照 GetSnapshotData() 时，都需要遍历全局活跃进程数组 PGPROC 收集所有未提交事务 ID；连接数越多，数组越长、CPU L1/L2 缓存缺失越严重。通过前置单进程事件驱动的 PgBouncer，可将数千客户端连接收敛复用在 100~200 个真实 Backend 进程上：

PgBouncer 池化模式 后端进程借出与归还生命周期 连接收敛效果 会话状态与预处理语句（Prepared Statements）兼容性
1. session
（会话级池化，默认）		 客户端连上时分配一个 PG 进程，直到客户端主动断开连接才归还池中。 仅省去频繁 fork() 新进程的开销，无法减少同时在线的后端进程总数。 100% 兼容所有会话级特性（SET 变量、临时表、LISTEN/NOTIFY、咨询锁）。
2. transaction
（事务级池化，生产主力）		 客户端发送 BEGIN（或单条语句）时才从池中借出 PG 进程；一旦执行完 COMMIT / ROLLBACK，立即将该 PG 进程放回池中供其他客户端复用。 极高：可将 5000 个微服务空闲/忙时连接压缩到 100~200 个真实数据库进程。 不同事务可能落到不同的后端进程上。因此不能依赖跨事务的会话级 SET、会话级临时表；对于驱动层的命名预处理语句（Named Prepared Statements），需升级至 PgBouncer 1.21+ 开启 max_prepared_statements > 0 由 PgBouncer 自动重写映射，或在驱动中禁用协议级缓存。
3. statement
（语句级池化）		 每执行完一条单独的 SQL 语句就立即归还连接。 最高，但适用面极窄。 不支持多语句显式事务（发送 BEGIN 会直接报错拒绝），仅适用于纯单语句自动提交的只读查询场景。
