🧭 00.1 PostgreSQL 与 MySQL InnoDB 的三大底层架构分水岭

关系型数据库在工程实现上面临两个最基础的物理存储问题：第一，一张表的数据行在磁盘页面上按什么顺序组织？第二，当更新一行数据时，历史旧版本存放在哪里？ PostgreSQL 与 MySQL（InnoDB 存储引擎）在这两个问题上做出了截然不同的设计抉择，并由此衍生出两者在读写性能、索引维护与空间治理上的全部差异：

抉择 ① · 表组织形式 Heap vs IOT
无序追加堆表 vs 主键聚簇 B+ 树

InnoDB 表本身就是一棵按主键排序的 B+ 树（索引组织表 IOT），整行数据存在主键叶子节点中；而 PostgreSQL 的表是无序追加的堆表（Heap Table），每一行通过物理坐标 ctid = (页号, 页内槽位号) 寻址，主键索引与普通二级索引地位平等，叶子节点均直接存放 ctid。

抉择 ② · 多版本存放位置 In-Page vs Undo
堆表内追加新元组 vs 独立 Undo 回滚段

InnoDB 原地覆写数据页并将旧版本剥离到独立的 Undo Log；PostgreSQL 采用追加写多版本（Append-Only MVCC）：UPDATE 操作将旧元组标记失效事务号 xmax，同时在堆表中直接插入一条新版本元组（xmin）。因此 PG 的事务回滚是 O(1) 瞬时完成的，但也引出了死元组堆积与 VACUUM 垃圾回收机制。

抉择 ③ · 二级索引维护 ctid vs PK Value
一步物理跳读 vs 二次主键树搜索

InnoDB 二级索引存主键值，回表需再去主键 B+ 树搜索 3~4 层；PG 所有索引直接存 6 字节 ctid，回表只需一步物理页面读取，但一旦更新导致行物理坐标 ctid 跨页变化（未命中 HOT 优化），表上所有索引都需要追加指向新 ctid 的条目。

内核维度 🐘 PostgreSQL (16 / 17 内核机制) 🐬 MySQL (8.0 / 8.4 InnoDB 内核机制)
1. 并发执行模型 多进程模型（Process-per-Connection）：主进程 postmaster 为每个会话 fork() 独立 backend 进程，进程间通过共享内存（Shared Buffers）与信号量协同，单进程崩溃不影响全局地址空间。 单进程多线程模型（Thread-per-Connection）：所有会话线程共享同一进程虚拟地址空间，线程创建与上下文切换较轻，但内存越界 Bug 会导致整实例崩溃。
2. 数据页与聚簇性 默认 8 KiB 堆表页，行按空闲空间映射（FSM）无序存放；可通过 CLUSTER 命令按某索引一次性物理重排，但后续写入不维持顺序。 默认 16 KiB 索引页，表数据强制按主键顺序聚簇在主键 B+ 树叶子节点，随机 UUID 主键会导致频繁页分裂。
3. 二级索引回表代价 索引叶子节点存 6B ctid (BlockNumber 4B + OffsetNumber 2B)，回表为 O(1) 物理块偏移直读；但索引本身不存事务可见性信息，覆盖索引需查可见性映射表（VM）。 二级索引叶子节点存主键值，回表需在主键聚簇树上执行 O(log N) 二次树查找；二级索引页头记有最大事务 ID PAGE_MAX_TRX_ID 辅助可见性判断。
4. 更新写放大与 HOT 若未修改任何索引列且同页剩余空间充足，触发 HOT (Heap-Only Tuple) 页内链式更新，无需修改外部索引；否则表上所有索引均需插入新项。 若更新未涉及主键与某二级索引列，则该二级索引完全无需改动，仅在聚簇索引页原地修改并写 Undo Log。
5. MVCC 与大事务回滚 旧版本留在堆表页内，由 23B 元组头的 t_xmin / t_xmax 与提交日志 pg_xact (CLOG) 控制可见性；大事务 ROLLBACK 仅修改 CLOG 中的 2 个比特位，瞬时完成。 旧版本写入回滚段 Undo Log 并通过 roll_pointer 串联；大事务回滚需逐行逆向重放 Undo Log 恢复原数据页，耗时较长。
6. 空间回收与膨胀治理 依赖后台 autovacuum 或页内剪枝（Page Pruning）清理死元组并更新 FSM/VM，以及通过 VACUUM FREEZE 冻结老事务号防止 32 位 XID 回卷。 由后台 Purge 线程异步清理不再被任何活跃 ReadView 引用的 Undo Log 及带删除标记（deleted_flag）的记录。
7. 隔离级别与防幻读 默认 Read Committed；Repeatable Read 靠事务级快照屏蔽幻读，写写冲突遵循 First-Updater-Wins 直接抛错；Serializable 采用无读锁的 SSI（SIREAD 谓词锁检测读写反依赖环）。 默认 Repeatable Read；快照读靠 ReadView，当前读（UPDATE / FOR UPDATE）靠 Next-Key Lock（记录锁 + 间隙锁 Gap Lock）阻塞区间插入防幻读。
8. 行锁存储位置 不占用共享内存锁表：直接将加锁事务 XID（或 MultiXactId）写入数据页元组头的 t_xmax 与 t_infomask 标记位，单事务锁千万行也不会发生锁升级。 行锁作为锁结构对象存储在内存全局锁哈希表（Lock Manager）中，锁数量巨大时会消耗可观的内存空间。
9. 预写日志与防页撕裂 单层统一日志 WAL (pg_wal)；通过 full_page_writes = on（检查点后首次修改某页时将完整 8KB 页写入 WAL）防御操作系统 4KB 落盘中断导致的页撕裂。 引擎层物理逻辑日志 Redo Log + Server 层逻辑日志 Binlog（两阶段提交 2PC）；通过独立双写缓冲区 Doublewrite Buffer 防御 16KB 页撕裂。
10. 查询优化器与连接算法 完备的 CBO 优化器：支持 Nested Loop、双阶段 Hash Join、Merge Join、多索引位图合并（BitmapAnd/Or）、基因算法（GEQO）与 LLVM JIT 表达式编译。 长期以 Index Nested-Loop Join 为主，8.0.18+ 引入内存/溢出 Hash Join，暂不支持 Merge Join。
📐 00.2 · 物理页面布局：8 KiB 堆表页内部结构、行指针数组 ItemIdData 与元组双向相向生长机制

📐 00.2 8 KiB 数据页物理布局与 Line Pointer 间接寻址

在 PostgreSQL 中，无论是堆表还是索引，磁盘与共享内存之间读写的最小基本单位都是固定大小的页面（Page / Block，默认 BLCKSZ = 8192 Bytes = 8 KiB）。打开源码 src/include/storage/bufpage.h，一个标准的 8KB 数据页由四部分组成，并采用“行指针从前往后增长、真实数据元组从后往前增长”的双向相向填充结构：

页头核心字段（PageHeaderData） 字节大小 内核作用与崩溃恢复 / 并发意义
pd_lsn (PageXLogRecPtr) 8 Bytes 记录最后一次修改该数据页的 WAL 日志序列号（Log Sequence Number, LSN）。缓冲池刷脏页落盘前，必须校验 WAL Writer 已将大于等于该 pd_lsn 的预写日志刷入磁盘（即 WAL-before-Data 原则）。
pd_checksum + pd_flags 2B + 2B 16 位页面 CRC 校验和（开启 data_checksums 后用于检测磁盘静默位翻转损坏）与页面状态标志位（如 PD_HAS_FREE_LINES、PD_ALL_VISIBLE）。
pd_lower / pd_upper / pd_special 2B + 2B + 2B pd_lower 指向行指针数组的末尾（空闲空间起点）；pd_upper 指向最新写入元组的起始位置（空闲空间终点）。两者的差值 pd_upper - pd_lower 即为当前页面剩余可用字节数。
pd_prune_xid 4 Bytes 记录当前页面内最早产生的死元组或更新链的事务 XID，用于告诉后续读取该页的会话：“当前页内存在可立即顺手剪枝回收（Page Pruning）的历史垃圾元组”。
🗜️ 00.3 · 大字段存储：变长结构体 varlena 头部编码与 TOAST（压缩 + 附属表 2KB 切片）机制

🗜️ 00.3 变长结构 varlena 与 TOAST 超大字段切片原理

由于 PostgreSQL 数据页固定为 8 KiB，且内核规定单条物理元组不允许跨页存储，如果用户向 text、jsonb 或 bytea 列写入一段 500 KB 的长文，数据页该如何容纳？答案是 varlena（Variable-Length Attribute）多态头部编码配合 TOAST（The Oversized-Attribute Storage Technique）机制：

1. varlena 的三种物理头部形态

  • 短变长头（varattrib_1b，仅 1 Byte 头）：当字符串或 jsonb 长度小于等于 126 Bytes 时，无需浪费 4 字节存长度，仅用 1 字节头部保存长度与标志位，紧凑存储于主表页内。
  • 标准未压缩/页内压缩头（varattrib_4b，4 Bytes 头）：最高 2 比特标记是否经过压缩（pglz 或 PG 14+ 引入的高速 lz4），低 30 比特记录字节长度（最大支持 1 GB）。
  • 线外 TOAST 指针头（varattrib_1b_e，固定 18 Bytes）：当单行总大小超过触发阈值 TOAST_TUPLE_THRESHOLD（默认约 2 KiB，即一页至少保证能放 4 行）时，内核会按从大到小的顺序对变长列执行压缩；若压缩后整行仍大于 2 KiB，则将该大字段切分为每个约 2000 Bytes 的块（Chunks），存入系统自动创建的附属表 pg_toast.pg_toast_<oid> 中，主表原位置仅保留一个 18 字节的 varatt_external 指针（含原始长度、压缩后长度、va_valueid 与附属表 OID）。

2. 四种列级 TOAST 存储策略（ALTER TABLE ... SET STORAGE）

存储策略 允许压缩？ 允许移入 TOAST 表？ 适用场景与性能特征
EXTENDED
（默认策略）		 允许 允许 text / jsonb / bytea 的默认策略：超阈值先尝试压缩，仍超标则移出主表存入附属 TOAST 表。
EXTERNAL 不压缩 允许 适合本身已经压缩过的数据（如 JPEG/ZIP 二进制或需高频截取子串的长文本）：省去 CPU 解压开销，直接线外切片存储。
MAIN 允许 尽量留在主表 优先页内压缩留在主表页中，仅当压缩后整行依然放不进单个 8KB 页时才被迫移入 TOAST 表。
PLAIN 不压缩 禁止 定长标量类型（int / bigint / timestamptz）固定使用此策略，始终内联存放在主表页。
💡 工程启示：为什么在含大字段的表上应避免写 SELECT *？
当大字段已移入线外 TOAST 表时，如果 SQL 只查询 SELECT id, status FROM articles，执行器只需扫描紧凑的主表页，完全不会去触碰附属 TOAST 表及其 B-tree 索引；而一旦写成 SELECT *，每命中一行都要拿着 18 字节指针额外去 TOAST 表执行一次索引查找并重组切片、解压内存，I/O 与 CPU 开销相差数倍。
