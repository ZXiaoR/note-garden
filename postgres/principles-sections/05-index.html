05.1 · B-tree (nbtree) 内核：Lehman-Yao 高并发算法、重复键去重与自底向上清理

05.1 Lehman-Yao 高并发 B-tree 与去重清理机制

PostgreSQL 的默认 B-tree 索引实现（源码位于 src/backend/access/nbtree/）并非教科书里的基础 B+Tree，而是基于 Lehman & Yao (1981) 高并发 B-link Tree 算法，并融合了现代版本的多项工业级改良。

1. 并发页面分裂期间的无锁读取机制（High Key 与右向兄弟链接）

在传统 B+Tree 中，当叶子页分裂为左右两页并向父节点插入新路由键时，为了防止并发读事务迷路，往往需要自顶向下加锁（Crabbing / Latch Coupling）。而 PostgreSQL 的 nbtree 在每个索引页中额外引入了两个关键设计：

  • 上界高键（High Key，固定存放在页内槽位 PageGetItemId(page, 1)）：明确记录当前索引页允许存放的最大键值上界。
  • 右向兄弟指针（btpo_next）：当页 P 分裂为左页 P 和右页 P' 时，内核先在同一个原子操作中把后半部分数据搬到右页 P'，更新左页 P 的 High Key，并让左页 P 的 btpo_next 指向右页 P'，随后立即释放页锁，再去异步更新父节点。
  • 读操作自愈右移：如果在父节点还没来得及更新的极短时间窗内，一个并发读事务顺着旧父节点指针落到了左页 P，它只需将搜索目标值与左页 P 的 High Key 比较；一旦发现目标值大于 High Key，读事务无需回溯父节点，直接顺着 btpo_next 向右横移一格即可找到右页 P'。这保证了索引读操作在任何时候都只需锁住单个当前页，且永远不会与自底向上的页面分裂发生死锁。

2. PG 13+ 重复键去重（Deduplication）与 PG 14+ 自底向上死元组删除

  • B-tree 重复键倒排压缩（PG 13+）：对于低基数或中基数列（如状态码、城市 ID、外键 ID），旧版 B-tree 会为每一行都存储一条完整的索引项（包含重复的键值 + 6B ctid + 对齐开销，至少 16 字节）。自 PG 13 起，当索引页即将发生分裂时，内核会自动触发 Deduplication（去重压缩）：将相同的键值合并为一条投递列表元组（Posting List Tuple：仅保存 1 份键值 + 紧凑排列的 ctid[] 数组），使非唯一索引体积普遍缩减 50% ~ 75%。
  • 自底向上索引死元组删除（Bottom-Up Index Deletion，PG 14+）：由于 PostgreSQL 的堆表每次更新若发生跨页（非 HOT 更新），就必须向表上的所有索引插入一条指向新 ctid 的索引项。为了防止索引页被高频更新迅速撑爆分裂，PG 14 引入了主动防膨胀机制：当向 B-tree 叶子页插入新索引项即将触发页面分裂时，内核会先挑选该页中存在重复键的索引项，回表检查它们指向的堆元组是否已死亡（Dead Tuple），当场清理掉死索引项以腾出空间，从而在不依赖后台 VACUUM 的情况下消除绝大多数由高频更新引起的非必要索引分裂。

05.2 B-tree、GIN 倒排树与 BRIN 极值块映射的物理结构对比

针对不同形态的数据访问模式，PostgreSQL 提供了开放的索引访问方法接口（Index Access Method API）。理解 B-tree、GIN（通用倒排索引）与 BRIN（块范围索引） 的物理页面拓扑，是解决复杂检索与写入延迟毛刺的关键：

生产调优：消除 GIN 索引的写入延迟毛刺（gin_pending_list_limit）：
由于一行 JSONB 文档可能包含 50 个键值对，如果每次 INSERT 都同步去修改 GIN 的 Entry B-tree 中的 50 个节点，写入吞吐量会急剧下降。为此 GIN 默认开启了 fastupdate = on：新插入的词元先顺序追加到一个无序的 Pending List（待处理链表）中；但这带来了两个副作用：
1. 任何 SELECT 查询除了查 GIN 主树外，还必须额外顺序扫描整个 Pending List；
2. 当 Pending List 累积达到阈值 gin_pending_list_limit（默认 4MB）时，恰好触发阈值的那条普通用户 INSERT / UPDATE 语句会被迫同步承担将 4MB 待处理列表合并刷入主树的重任，导致该次写入偶发数百毫秒的延迟毛刺。在延迟敏感型 OLTP 表上，建议通过 ALTER INDEX idx_name SET (gin_pending_list_limit = 1024); 将阈值调小至 1MB，或为该表调积极 autovacuum 以在后台高频异步清空 Pending List。
05.3 · Index Only Scan 与 Visibility Map，以及 Bitmap Scan 有损退化

05.3 可见性映射表（_vm）与位图扫描 exact / lossy 退化机制

可见性映射表（Visibility Map, _vm）与 Index Only Scan 免回表原理

在阅读 EXPLAIN ANALYZE 时，很多工程师会疑惑：既然元组的可见性信息（t_xmin / t_xmax）只存在堆表（Heap）的元组头里，而 B-tree 索引项里只存了「键值 + ctid」，那为什么 Index Only Scan 可以不回表就判断该索引项对当前事务可见？

答案在于每个表文件旁边的附属派生文件 —— 可见性映射表（Visibility Map，文件名后缀 _vm）：

  • 每个 8 KiB 数据页在 _vm 中仅占 2 个比特位：第 1 位是 ALL_VISIBLE（标记该数据页上的所有元组对当前及未来任何事务全都可见，不存在任何未提交修改或待清理的死元组）；第 2 位是 ALL_FROZEN（标记该页所有元组均已完成 XID 冻结，VACUUM 甚至无需再扫描它）。
  • 由于每个页只占 2 bit，一张 100 GB 的大表，其 _vm 文件也只有大约 3.2 MB，可以常驻在内存缓存中。
  • 当执行 Index Only Scan 从索引中拿到一条 (key, ctid=(block_no, offset)) 时，执行器先去内存里的 _vm 查一下第 block_no 号数据页的 ALL_VISIBLE 位是否为 1：
    • 若为 1：无需访问堆表数据页，直接将索引中的列值返回给客户端（Heap Fetches: 0）。
    • 若为 0（说明该页近期发生过 INSERT / UPDATE / DELETE 且尚未被 VACUUM 清扫标记）：必须老老实实回表读取该数据页检查元组头 t_xmin / t_xmax，并在执行计划中累加 Heap Fetches 计数。

Bitmap Index Scan + Bitmap Heap Scan 的 exact 与 lossy（有损页级退化）

当查询命中几千至几十万行（或者需要把多个索引的条件做 BitmapAnd / BitmapOr 交并集）时，如果直接用普通 Index Scan 按索引顺序一条条回表，会在磁盘上产生大量跨页跳跃的随机 I/O，并且同一个数据页可能被反复读多次。此时优化器会选择两阶段位图扫描：

  1. 阶段一（Bitmap Index Scan）：先遍历索引，不立即回表，而是在内存中建立一张按物理页号排序的位图（TIDBitmap），记录哪些数据页的哪些行槽位命中了条件。
  2. 阶段二（Bitmap Heap Scan）：按照物理页号从小到大的顺序依次读取数据页，把随机 I/O 转化为近似顺序的批量跳读。
  3. 内存溢出时的有损退化（lossy blocks）：TIDBitmap 占用的最大内存受 work_mem 限制。一旦命中的行数过多导致位图超出 work_mem，内核会将部分哈希桶从「精确记录到每一行（exact）」降级为「只用 1 个 bit 记录某一个 8 KiB 数据页整体命中（lossy）」。对于被降级为 lossy 的数据页，Bitmap Heap Scan 读取该页后必须通过 Recheck Cond 对页内的每一行重新校验一次过滤条件。如果在 EXPLAIN ANALYZE 中看到 Heap Blocks: exact=1200 lossy=45000，说明 work_mem 偏小，适当调大会话级 work_mem 即可消除 lossy 重检开销。
