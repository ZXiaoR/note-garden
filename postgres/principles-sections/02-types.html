02.1 JSONB 二进制内存布局与二分跳读原理

为什么普通 json 类型提取一个深层字段需要从头到尾扫描字符串（O(N) 词法解析），而 jsonb 能够以微秒级直接跳读目标字段？查看源码 src/include/utils/jsonb.h 可以发现，jsonb 在写入时已将 JSON 对象编译为一棵带定长头部索引目录（JEntry 数组）的扁平化二进制树：

JSONB 局部更新的底层代价：整列重写与 TOAST 写放大
虽然 jsonb 的读取是 O(log K) 跳读，但由于 PostgreSQL 采用堆表追加写 MVCC，且 JsonbContainer 是紧凑连续存储的二进制块，执行 UPDATE t SET profile = jsonb_set(profile, '{level}', '4') 修改一个 100 KB 的大 jsonb 中的 1 个字节时，无法在磁盘上只原地改动那 1 个字节，而是必须生成一整份新的 100 KB jsonb 写入新的 TOAST 切片。因此对于每秒高频递增的计数器或状态字段，应拆分为独立的普通关系列（可利用同页 HOT 更新），不要塞进大体积的 jsonb 文档中。
02.2 · 事务性 DDL 原理：系统目录表（pg_class / pg_attribute）的 MVCC 多版本机制与缓存失效广播（sinval）

02.2 事务性 DDL 的实现机制：系统表 MVCC 与延迟物理删除

在许多传统数据库中，表结构定义存储在特殊的非事务元数据文件或内存字典里，执行 ALTER TABLE 或 DROP TABLE 会强制隐式提交当前事务。而在 PostgreSQL 中，所有描述数据库对象元数据的系统目录表（System Catalogs，如记录表的 pg_class、记录列的 pg_attribute、记录索引的 pg_index）本身就是标准的 MVCC 堆表：

1. 一条 DDL 在内核中的事务与文件生命周期

  1. 系统表行级 MVCC 修改：当事务 T200 执行 ALTER TABLE users ADD COLUMN bio text; 时，本质上是向系统表 pg_attribute 插入了一条 xmin = 200 的新元组，并更新了 pg_class 中该表的列数元组。在 T200 提交前，其他会话根据 MVCC 可见性规则根本看不到这行元数据。
  2. 逻辑 OID 与物理文件 relfilenode 解耦：每张表在 pg_class 中有一个不变的对象标识 oid，而它对应磁盘上的真实物理文件名为 relfilenode（如 base/16384/24576）。当在事务内执行 DROP TABLE 或 TRUNCATE 时，内核并不会立刻调用操作系统的 unlink() 删除物理磁盘文件，而是先在系统表中将旧元组标记 xmax = 200，并把待删除的 relfilenode 登记到当前事务的待删文件队列（pendingDeletes）中：
    • 若事务最终执行 ROLLBACK：xmin/xmax为 200 的系统表改动自动失效，原物理文件完好无损，回滚瞬间完成；
    • 若事务最终执行 COMMIT：写完提交 WAL 记录后，才真正由内核批量删除旧 relfilenode 物理文件。
  3. 跨进程元数据缓存同步（sinval 队列）：由于每个 Backend 进程都在私有内存中维护了表结构缓存（relcache / catcache），当事务提交修改了系统表时，会向共享内存中的 共享失效消息队列（Shared Invalidation Message Queue, sinval） 写入失效通知，其他会话在开始下一条语句时读取该队列并刷新本地元数据缓存。

2. 不可放入事务块回滚的命令边界清单

不支持放在 BEGIN 块内的命令 底层限制原因
CREATE DATABASE / DROP DATABASE / CREATE TABLESPACE 涉及在操作系统层面跨目录复制整个模板库文件夹（cp -r base/1 ...）或删除整个数据库目录，无法通过单库内的系统表 MVCC 跟踪。
CREATE INDEX CONCURRENTLY / REINDEX CONCURRENTLY 在线无锁建索引需要主动拆分为多个内部事务提交，并跨事务等待全库所有早期活跃事务结束，因此不能被外层显式事务包裹。
VACUUM / CLUSTER 后台空间回收需要按页面粒度随时提交可见性修改并释放推进最老事务水位线，不支持跨全表回滚。
ALTER TYPE ... ADD VALUE（特定场景） PG 12+ 已允许在事务块内添加枚举值，但新添加的枚举值在当前事务提交前不能立即写入已存在的表（防止回滚后留下幽灵枚举引用）。
02.3 · 元数据快速加列：pg_attribute.attmissingval 如何让上亿行大表 ADD COLUMN DEFAULT 免于重写

02.3 ADD COLUMN ... DEFAULT 免全表重写的内核实现

在 PostgreSQL 11 之前（以及早期版本的其他数据库中），执行 ALTER TABLE orders ADD COLUMN flag int NOT NULL DEFAULT 1; 必须把整张表的所有 8KB 数据页全部读出来、在每一行末尾拼上新字段值 1 并写入新的磁盘文件，上亿行大表会锁表数十分钟。从 PostgreSQL 11 起，这一操作变成了毫秒级的纯元数据修改：

内核机制 / 改表操作 是否重写物理表文件？ 底层读取与系统表实现原理
1. 加列带非易变默认值
ADD COLUMN c int DEFAULT 1
或 DEFAULT now()		 不重写（0 秒完成） 系统表 pg_attribute 新增了两个关键字段：atthasmissing = true 与 attmissingval = {1}（即使默认表达式是 now() 等稳定函数，也会在执行 ALTER 的那一刻求值一次存入 attmissingval）。此后读取老数据行时，内核发现该行的物理列数 t_natts 小于表定义列数，直接从 attmissingval 取出默认值返回，完全无需触碰老数据页。
2. 加列带易变函数默认值
DEFAULT random() 或 gen_random_uuid()		 必须重写全表
（长时持有排他锁）		 因为易变函数（VOLATILE）要求历史每一行都生成各自不同的随机值，无法共用单个 attmissingval 常量，内核只能遍历重写全表每一行。
3. 修改列数据类型
ALTER COLUMN c TYPE bigint		 绝大多数重写全表
（有 2 类免重写特例）		 将 int (4B) 改为 bigint (8B) 会改变元组内字节偏移，必须分配新 relfilenode 重写全表。
免重写特例：① varchar(50) 放宽为 varchar(100) 或 text（底层同为 varlena）；② numeric(10,2) 放宽整数位为 numeric(14,2)（小数精度不变）。
