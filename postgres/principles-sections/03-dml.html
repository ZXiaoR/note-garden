03.1 · 优化器代价模型：四阶段查询编译管线与 Seq Scan vs Index Scan 的成本估算公式推导

03.1 查询编译管线与基于成本的优化器（CBO）代价公式

当一条 SQL 文本发往 Backend 进程后，依次经过 ① 词法/语法解析器（Parser，生成抽象语法树 Parse Tree）→ ② 查询重写器（Rewriter，展开视图定义与规则系统）→ ③ 查询规划与优化器（Planner / Optimizer，枚举扫描路径、连接顺序与连接算法，选出总估算成本最低的计划树 Plan Tree）→ ④ 执行器（Executor，按火山迭代器模型拉取元组）。其中，优化器比较不同执行路径的核心标尺是由基准代价参数构成的数学成本公式：

核心代价参数（postgresql.conf） 默认值 物理意义与现代 SSD 生产调优建议
seq_page_cost 1.0 顺序读取一个 8KB 磁盘页的基准代价（定义为 1.0，其余所有成本参数均以此为参照标尺）。
random_page_cost 4.0 随机读取一个 8KB 磁盘页的代价。默认值 4.0 是按机械硬盘（HDD 寻道时间长）标定的；在现代 NVMe / 云盘 SSD 环境下，随机读与顺序读差距极小，生产环境强烈建议将其调低至 1.1 ~ 1.5，否则优化器会因为高估随机回表成本而过早放弃索引扫描退化为全表扫描。
cpu_tuple_cost / cpu_operator_cost 0.01 / 0.0025 CPU 处理一条堆表元组与执行一次操作符/函数（如 WHERE a = 1）的相对成本。
effective_cache_size 4GB 告诉优化器“Shared Buffers + OS Page Cache 大约共有多少内存可用于缓存数据页”（不会真正分配内存）。建议设为机器物理内存的 50%~75%，值越大，优化器越倾向于认为索引页已在内存中而积极使用 Index Scan。
03.2 · 统计信息内部结构：MCV 高频值、等高直方图、物理相关度 correlation 与多列相关性失真治理

03.2 pg_statistic 统计信息与多列扩展统计

执行 ANALYZE 时，内核默认从表中随机抽样 300 × default_statistics_target(100) = 30,000 行数据，为每一列计算出四项关键分布指标存入系统表 pg_statistic（可通过视图 pg_stats 直接查询）：

  • ① 空值比例 null_frac 与唯一值基数 n_distinct：若 n_distinct > 0 表示估算出的固定去重值个数；若 n_distinct < 0（如 -1.0）表示唯一值占总行数的比例（主键列即为 -1）。
  • ② 高频值列表 most_common_vals (MCV) 与频率 most_common_freqs：记录出现频率最高的前 100 个具体值及其占比。优化器估算等值条件 WHERE status = 'paid' 时，直接查 MCV 数组即可获得精确到小数点后四位的选择率。
  • ③ 排除高频值后的等频直方图 histogram_bounds：将除 MCV 以外的剩余数据切分为 100 个行数相等的桶，记录每个桶的边界值，专门用于估算范围查询 WHERE amount BETWEEN 100 AND 500 的命中比例。
  • ④ 物理顺序相关度 correlation（取值 -1.0 ~ +1.0）：衡量“该列逻辑排序顺序”与“磁盘页面物理存放顺序（ctid）”的一致性。越接近 +1.0 或 -1.0（如自增 id 或按序插入的 created_at），范围索引扫描回表越接近顺序 I/O，Index Scan 成本越低，且越适合建立 BRIN 块范围索引。
create_statistics.sql · 解决多列条件关联导致的估算失真 
-- 问题背景：优化器默认假设不同列之间是“统计独立”的，
-- 联合条件 WHERE province = '浙江省' AND city = '杭州市' 的选择率
-- 会被直接相乘 P(浙江) * P(杭州)，导致预估行数比实际少几十倍，
-- 从而误选 Nested Loop 引发严重慢查询。

-- 解决方案：创建多列扩展统计信息 (Extended Statistics)
CREATE STATISTICS stts_addr_dep (dependencies, ndistinct, mcv)
  ON province, city FROM user_addresses;

-- 重新收集统计信息后，优化器即可识别两列的函数依赖关系
ANALYZE user_addresses;
03.3 · 连接执行器：Nested Loop / Merge Join / Hash Join 内部机制与 Batches > 1 分桶溢出原理

03.3 三大表连接算法与双阶段 Hybrid Hash Join

连接算法 时间复杂度与前置条件 执行器内部运作机制与调优关键点
1. Nested Loop
（嵌套循环连接）		 无索引 O(N × M)；
内表有索引 O(N × log M)		 外表（Outer）每产出一行，就拿连接键去内表（Inner）探测一次。PG 9.1+ 支持 Materialize（物化内表）与 Memoize（PG 14+ 缓存内表探测结果）：当外表连接键存在大量重复值时，Memoize 算子将内表查询结果缓存在哈希表中，避免重复扫内表索引。
2. Merge Join
（排序归并连接）		 已排序 O(N + M)；
支持 = 及范围连接		 要求左右两表的数据流均已按连接键排好序（可直接利用两侧 B-tree 索引顺序，或先加 Sort 算子）。执行时用双指针同步向前滑动比对，内存占用极小且稳定，适合两张超大表在连接键上均有索引的场景。
3. Hash Join
（双阶段混合哈希连接）		 平均 O(N + M)；
仅支持等值连接 =		 • 阶段一（Build 构建阶段）：扫描行数较少的内表，在私有内存 work_mem 中按连接键的哈希值构建内存哈希表（Hash Node）。
• 阶段二（Probe 探测阶段）：流式扫描外表每一行，计算相同哈希函数去内存哈希桶中匹配输出。
• 内存不足时的分批溢出（Grace / Hybrid Hash Join）：若内表数据量超过 work_mem，执行器会将哈希空间划分为 2k 个批次（Batches: 4 / 8 / 16...），只把 Batch #0 留在内存中处理，其余批次的内外表元组按哈希号分别写入磁盘临时文件（pg_pgsql_tmp/），随后逐批读回内存完成连接。一旦在 EXPLAIN ANALYZE 中看到 Hash: Buckets: ... Batches: 16 (originally 1) 且伴随 temp read/written，说明 work_mem 过小导致了磁盘读写往返，适当调大当前会话的 work_mem 即可将 Batches 降回 1 实现纯内存连接。
