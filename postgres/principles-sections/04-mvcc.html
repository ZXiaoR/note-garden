04.1 · 元组头解剖：23 字节 HeapTupleHeaderData、CLOG 与 Hint Bits 延迟标记

04.1 23 字节元组头物理位域与堆内多版本正向链

PostgreSQL 没有使用单独的回滚段（Rollback Segment / Undo Log）来保存旧版本数据，而是将所有历史版本与当前版本直接并排存放在同一个数据表（Heap）的 8 KiB 数据页中。为了判断某一行物理元组对当前事务是否可见，内核在每一条元组的头部都嵌入了固定 23 字节的 HeapTupleHeaderData 元数据（加上最少 1 字节填充对齐后为 24 字节偏移）。

元组头核心字段职责与 pg_xact (CLOG) 提交日志

  • t_xmin（4 字节）：插入该元组版本的事务 ID（XID）。对于 INSERT 而言它是创建者的 XID；对于 UPDATE 生成的新元组 V2 而言，它的 t_xmin 等于执行该 UPDATE 的事务 XID。
  • t_xmax（4 字节，复用字段）：当元组未被删除、未被更新且未被加行锁时，t_xmax = 0。一旦发生 DELETE 或 UPDATE，旧元组的 t_xmax 会被写入执行删除/更新的事务 XID；如果只是对元组加了行级锁（如 SELECT ... FOR SHARE / FOR UPDATE），t_xmax 同样会被写入加锁事务的 XID 或 MultiXactId，并通过 t_infomask 中的 HEAP_XMAX_LOCK_ONLY 位区分「仅加锁」与「真正删除」。
  • t_cid（4 字节）：Command ID（命令序号）。同一个事务内部先后执行多条 SQL 时，每条命令递增一次 t_cid，用于防止同一事务内的游标或子查询读到本条语句自身刚插入的元组（即预防 Halloween Problem 万圣节问题）。
  • t_ctid（6 字节，4B 块号 + 2B 页内槽号）：记录当前元组的物理坐标，或者指向被 UPDATE 后的下一个新版本元组坐标。当且仅当 t_xmax = 0 或 t_ctid 指向自身时，代表该元组是版本链的末端。
CLOG (pg_xact) 提交日志与 Hint Bits 提示位延迟落盘机制：
当事务 T1 (XID = 100) 执行 COMMIT 时，如果去修改它写过的成千上万个数据页上的元组状态，提交延迟会变得不可接受。因此 PostgreSQL 在提交时只做两件事：把提交日志刷入 WAL，并在全局提交状态数组 pg_xact（旧称 CLOG，每个事务仅占 2 bit：00=IN_PROGRESS、01=COMMITTED、10=ABORTED、11=SUB_COMMITTED）中将 XID=100 标记为已提交。
随后，当第一个后续事务（哪怕只是一条纯只读的 SELECT）访问到 XID=100 插入的元组时，发现该元组 t_infomask 中还没有设置提交提示位（HEAP_XMIN_COMMITTED 或 HEAP_XMIN_INVALID），就会去查一次 pg_xact。查明已提交后，这个 SELECT 进程会顺手把结果回写到该元组头的 t_infomask 提示位（Hint Bits）中，并将所在的 8 KiB 数据页标记为脏页（Dirty Page）。这样后续所有读者只需看一眼元组头的位标记即可判定可见性，无需再查 pg_xact。这就是为什么在大批量导入数据后，第一次执行全表 SELECT COUNT(*) 会触发大量物理写盘的根本原因。
04.2 · 事务快照与可见性判断：SnapshotData 三元组与 EvalPlanQual 并发重评

04.2 事务快照 SnapshotData 三元组与 EvalPlanQual 机制

当事务获取快照（在 Read Committed 下每条 SQL 语句开始时获取一次，在 Repeatable Read / Serializable 下事务内第一条语句开始时获取并复用到底）时，后台进程会扫描共享内存中的 ProcArray，生成一份 SnapshotData 三元组（可通过内置函数 pg_current_snapshot() 查看，格式为 xmin:xmax:xip_list）：

快照字段 内核定义（以快照 100:108:102,105 为例） 可见性快速裁决规则
snapshot.xmin 拍下快照瞬间，所有仍处于活跃未提交状态的最老事务 XID（示例中为 100） 任何 XID < 100 的事务在拍快照前必定已结束（只需看它是提交还是回滚即可，若已提交则一定可见）
snapshot.xmax 拍下快照瞬间，下一个即将分配的事务 XID（即当前最大已分配 XID + 1，示例中为 108） 任何 XID >= 108 的事务都是在拍下快照之后才启动的未来事务，其产生的修改对当前快照一律不可见
snapshot.xip_list 拍下快照瞬间，介于 [xmin, xmax) 区间内所有正在运行（未提交）的事务 XID 列表（如 102, 105） 对于落在 [100, 108) 之间的事务：若在 xip_list 中，说明拍快照时它还没提交，不可见；若不在列表中且已提交，则可见
HeapTupleSatisfiesMVCC · 元组可见性判定核心布尔逻辑（src/backend/access/heap/heapam_visibility.c） 
// 给定一条物理元组 tuple 与当前查询快照 snapshot，判断 tuple 是否对当前语句可见：
bool HeapTupleSatisfiesMVCC(HeapTuple tuple, Snapshot snapshot) {
    // 第一关：检查创建者 t_xmin 是否可见
    if (!XidVisibleInSnapshot(tuple->t_xmin, snapshot)) {
        return false; // 插入该元组的事务未提交、已回滚，或属于快照之后的未来事务 -> 不可见
    }

    // 第二关：此时 t_xmin 必定已提交且对当前快照可见，接着检查删除/更新者 t_xmax
    if (tuple->t_xmax == 0 || (tuple->t_infomask & HEAP_XMAX_INVALID)) {
        return true;  // 从未被删除/更新，或者当初尝试删除它的事务已经回滚 -> 可见
    }
    if (tuple->t_infomask & HEAP_XMAX_LOCK_ONLY) {
        return true;  // t_xmax 只是加了行级锁（如 FOR SHARE / FOR UPDATE），并未删除数据 -> 可见
    }

    // 第三关：t_xmax 确实是一个删除或更新事务，检查该删除事务对当前快照是否生效
    if (!XidVisibleInSnapshot(tuple->t_xmax, snapshot)) {
        return true;  // 删除该元组的事务还没提交，或是在当前快照拍下之后才提交的 -> 旧版本依然可见
    }

    return false;     // 删除该元组的事务在拍下快照前就已提交 -> 该元组已死，对当前快照不可见
}

Read Committed 下的写冲突裁决：EvalPlanQual (EPQ) 机制

当两个并发事务同时修改同一行时（例如账户初始 balance = 100，会话 A 与会话 B 同时执行 UPDATE accounts SET balance = balance - 30 WHERE id = 1 AND balance >= 30），PostgreSQL 根据隔离级别采取截然不同的策略：

  • Read Committed（读已提交，默认）—— EvalPlanQual 顺藤摸瓜重评：会话 B 在试图更新元组 V1 时发现其 t_xmax 已被会话 A 锁定，于是阻塞等待。当会话 A 提交并生成新版本 V2（balance = 70）后，会话 B 被唤醒。此时会话 B 不会报错，也不会傻乎乎地基于旧版本 V1（100）去减 30，而是顺着 V1 的 t_ctid 指针找到会话 A 刚提交的最新版本 V2（70），把 V2 代入专门的 EvalPlanQual 子执行器中，重新检验一次 WHERE id = 1 AND balance >= 30 条件。因为 70 >= 30 依然成立，会话 B 基于 V2 执行扣减，生成 V3（balance = 40）；若会话 A 当初把余额改成了 20，则会话 B 重评 WHERE 失败，静默返回 UPDATE 0。
  • Repeatable Read / Serializable —— First-Updater-Wins 立即抛错：当会话 B 等待会话 A 提交后被唤醒时，内核检测到目标元组已被快照启动之后的并发事务修改，拒绝执行 EPQ 重评，直接抛出 ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)，强制客户端捕获异常并重试整个事务，从而从根源上杜绝丢失更新。
04.3 · SSI 可串行化快照隔离、行级锁 MultiXact 与死锁检测

04.3 SSI 谓词锁与元组头行级锁机制

写偏序（Write Skew）异常与 SSI 谓词锁的无阻塞检测机制

在传统的实现中（如早期数据库或 MySQL InnoDB），SERIALIZABLE 往往通过把所有普通 SELECT 强制降级为加共享间隙锁（SELECT ... FOR SHARE + Next-Key Lock）来实现，这会导致读写严重阻塞。PostgreSQL 9.1 引入了学术界里程碑式的 可串行化快照隔离（Serializable Snapshot Isolation, SSI）：读仍然完全不阻塞写，写也完全不阻塞读。

  • 经典写偏序（Write Skew）场景：医院值班表规定「至少保留 1 名医生在岗」。当前 Alice 和 Bob 都在岗（共 2 人）。事务 T1 与 T2 同时以 Repeatable Read 启动，各自执行 SELECT count(*) FROM doctors WHERE on_call = true，都读到 2；接着 T1 将 Alice 改为离岗（UPDATE ... WHERE name = 'Alice'），T2 将 Bob 改为离岗（UPDATE ... WHERE name = 'Bob'）。由于两人修改的是完全不同的两行记录，没有任何行级写锁冲突，在 Repeatable Read 下两个事务都会成功提交，导致在岗医生变为 0，违背业务不变量。
  • SSI 的 SIREAD 谓词锁与危险结构检测：在 Serializable 级别下，当 T1 和 T2 执行 SELECT 时，内核会在共享内存中记录轻量级的非阻塞 SIREAD 谓词锁（Predicate Lock，可根据内存压力从元组级自动粗化升级为页级或表级）。当 T1 修改 Alice 时，内核发现「T2 刚才通过 SIREAD 读过包含 Alice 的谓词范围，而 T1 现在改写了它」，于是登记一条从 T2 指向 T1 的 读写反依赖边（rw-antidependency: T2 --rw--> T1）。同理，当 T2 修改 Bob 时，又产生了一条 T1 --rw--> T2 的边。一旦内核检测到连续两条相邻的 rw-antidependency 边形成环路，就会在后提交的事务执行 COMMIT 时将其拦截并抛出 40001 序列化失败异常。

四种行级锁模式、MultiXactId 与死锁检测（deadlock_timeout）

PostgreSQL 为了支持外键并发检查（当父表的一行被更新非主键列时，不阻塞子表引用该父表主键的 INSERT），提供了比标准共享/排他锁更精细的四级显式行锁体系：

行级锁语法 隐式触发场景 相容与冲突关系
FOR KEY SHARE（最弱共享锁） 子表插入/更新外键列时，自动对父表被引用的行加此锁 只阻止父表行被 DELETE 或修改主键值，允许父表行被 FOR NO KEY UPDATE 更新普通列
FOR SHARE（标准共享锁） 应用显式声明需要冻结整行不被任何更新改动 与 FOR KEY SHARE / FOR SHARE 相容；阻止任何形式的 UPDATE / DELETE
FOR NO KEY UPDATE（弱排他锁） 任何未修改主键/唯一索引列的普通 UPDATE 自动获取 与 FOR KEY SHARE 相容（这就是为什么更新父表普通列不会卡死子表外键插入）；与其他修改锁互斥
FOR UPDATE（最强排他锁） DELETE 语句，或修改了唯一键列的 UPDATE 语句自动获取 与上述所有四种行锁全部互斥
元组头行锁存储与 MultiXactId 组合事务锁机制：
许多数据库把行锁存放在内存锁哈希表中，一旦单事务锁住百万行就会触发锁表内存溢出（Lock Escalation 锁升级为表锁）。PostgreSQL 采取了巧妙的设计：行级锁直接利用数据页元组头的 t_xmax 与 t_infomask 存储在磁盘数据页上，因此在 PG 中即使一个事务锁定 1 亿行，也绝不会耗尽共享内存锁表，更不存在「行锁自动升级为表锁」的现象。
如果多个并发事务同时对同一行加共享锁（FOR KEY SHARE / FOR SHARE），单个 4 字节的 t_xmax 会写入一个组合 ID —— MultiXactId，并将真实的多个成员事务 XID 列表记录在 pg_multixact/ 子目录中。此外，当事务等待锁超过 deadlock_timeout（默认 1s）时，后台进程才会唤醒死锁检测算法（构造 Wait-For Graph 有向等待图寻找环路），从而让 99.9% 在几毫秒内就能拿到的正常锁等待省去死锁图遍历开销。
