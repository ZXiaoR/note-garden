07.1 · 容器安全三条底线：禁止默认 root 裸跑、禁止构建期埋密钥、禁止暴露 docker.sock

07.1 容器上线安全三条底线

  • 底线 ①：业务进程一律切换为非 root 普通用户运行。如果不写 USER 指令，容器内的默认进程身份就是 UID 为 0 的 root——默认情况下容器内的 root 与宿主机上的真正 root 其实是同一个内核 UID！一旦发生挂载目录越权或内核逃逸漏洞，攻击者直接拿到宿主机最高权限。务必在 Dockerfile 末尾加上 USER node 或自建无登录权限的 USER appuser。
  • 底线 ②：敏感凭证只在运行期注入，绝不打入镜像。数据库密码、云 AK/SK、私钥通过 compose.yaml 的 env_file、Docker Secrets 或 K8s Secret 在启动瞬间挂载，保证镜像本身脱敏可安全推送仓库。
  • 底线 ③：绝不把 /var/run/docker.sock 挂载给面向公网的业务容器。谁能读写 docker.sock 套接字，谁就能调用守护进程在宿主机上以特权模式挂载根目录 docker run -v /:/host --privileged，等同于直接交出宿主机 root 密码。

背后的原理：Docker 默认是怎么裁掉容器内 root 的危险内核能力（如加载内核模块、改系统时钟）的？详见 《核心原理篇 · 04.2 Capabilities 与 Seccomp 沙箱》。

07.2 · 资源配额防线：必设内存与 CPU 上限，警惕运行时读错宿主机物理内存

07.2 必配内存与 CPU 上限（防单点泄漏拖死整机）

默认情况下，Docker 容器对宿主机 CPU 和内存没有任何上限限制！如果一台 8 GB 服务器同时跑着你的 Node.js 接口和 MySQL，某天一个导出大 Excel 接口发生内存泄漏飙到 7 GB，宿主机物理内存耗尽触发内核 OOM Killer，甚至可能优先把占内存最大的 MySQL 主库杀掉导致全站瘫痪。因此线上每个业务容器都必须显式配置资源上限：

compose.yaml · 生产服务资源限额与日志轮转一体化配置 
services:
  api:
    image: shop-api:v1.2.0
    # 1. 限制最多用 2 核 CPU 与 1GB 内存（对应 docker run --cpus=2 -m 1g）
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1024M
        reservations:
          memory: 256M
    # 2. 限制单容器日志最多保留 3 个 50MB 文件（总上限 150MB，永不爆盘！）
    logging:
      driver: "json-file"
      options:
        max-size: "50m"
        max-file: "3"
    # 3. 注入轻量 tini 充当 PID 1 回收僵尸子进程并转发停止信号
    init: true
两个与资源限额相关的隐蔽坑
  • 容器内调 os.cpus() 或读 /proc/meminfo 看到的仍是宿主机规格！在 64 核 128G 宿主机上开一个限制了 1 核 1G 的容器，旧代码如果按 os.cpus().length 起 64 个工作进程，会瞬间挤爆内存与上下文切换。现代 Node 20+/Go 1.19+/JDK 17+ 运行时自身已自动读取 Cgroups 限额，但手写集群逻辑切忌盲信 os.cpus()（Node 可用 os.availableParallelism()）。
  • 语言堆上限预留 20%~25% 余量：若容器设 memory: 1024M，Node.js 建议配 NODE_OPTIONS="--max-old-space-size=768"（Go 设 GOMEMLIMIT=800MiB），让语言自身的垃圾回收器（GC）在触碰内核 1024M 死亡红线前主动回收内存。

背后的原理：CPU 平均使用率才 30%，为什么设了 cpus: "1.0" 后接口 P99 延迟偶尔出现百毫秒毛刺？详见 《核心原理篇 · 01.1 Cgroups CFS 周期节流》。

07.3 & 07.4 · 日志轮转与优雅停机：stdout 标准日志采集、SIGTERM 10 秒倒计时与 init: true

07.3 日志轮转防爆盘与 07.4 PID 1 优雅停机规范

  • 容器内应用不要自己往磁盘写滚动日志文件：容器化标准实践是将日志直接打印到标准输出/标准错误（stdout / stderr），由 Docker 日志驱动统一收集并配置 max-size: "50m" + max-file: "3" 自动轮转（既支持 docker logs 直接查看，又防止写满容器可写层）。
  • 为什么 docker stop 经常要干等整整 10 秒才退出？执行 docker stop 时，Docker 先向容器内的 PID 1 号主进程发送温和的 SIGTERM(15) 信号，给应用 10 秒钟（stop_grace_period）关闭监听端口、把正在处理的 HTTP 请求和数据库事务跑完再退出；若 10 秒后还没退，才发 SIGKILL(9) 强制断电。每次都卡满 10 秒通常有两个原因：
    1. Dockerfile 写了 Shell 字符串格式 CMD node app.js（或 npm start），导致 /bin/sh 成了 PID 1 且不把 SIGTERM 转发给子进程 → 改为数组格式 CMD ["node", "app.js"]；
    2. 应用还会拉起 ffmpeg / chromium 等外部子进程，主进程没写 waitpid() 回收导致产生大量 僵尸进程 → 在 docker run 加 --init（Compose 加 init: true），由官方内置极轻量 tini 担任 PID 1 自动转发信号并清理僵尸进程。
07.5 · 基础设施演进阶梯：单机 Compose → 云无服务器容器 → Kubernetes (K8s) 的代价与边界

07.5 部署规模大了怎么办：从 Compose 到 K8s 的演进阶梯

阶段与机器规模 推荐部署形态 能解决的问题与升级到下一阶的代价
第 1 阶：单机 ~ 2 台云主机
（日活数万以内项目）		 Docker Compose + 云托管数据库（RDS） 架构最清晰、零额外控制面成本；配合前置云负载均衡挂两台无状态 API 机器即可实现高可用。
第 2 阶：免运维弹性扩缩容
（中小研发团队首选）		 Serverless 容器托管服务
（如 AWS ECS Fargate / Google Cloud Run / 阿里云 SAE）		 直接把你打好的标准 Docker 镜像交上去，云平台自动管多实例滚动零停机发版、HTTPS 网关与流量扩缩容，无需雇专职 K8s 运维。
第 3 阶：十几个微服务 / 多机集群 托管 Kubernetes（ACK / EKS / GKE） 统一的跨机调度、自愈漂移、服务网格与细粒度金丝雀发布；代价是必须配套 Ingress 网关、CSI 存储卷、Prometheus 监控与 YAML 治理体系，切勿在只有 1 台机器时盲目自建 K8s。

本章即时场景题（先想答案，再点击展开）

1. 给 Node.js 容器限制了 memory: 512M，同时启动参数写了 --max-old-space-size=512，为什么高负载下还是偶尔被内核 OOM Killer 以 Exit 137 杀掉？

V8 的 --max-old-space-size=512 仅限制了 JS 老生代堆内存，而整个 Node 进程的实际物理内存（RSS）还包括新生代半空间、堆外 Buffer（文件/网络流缓冲区）以及 C++ 代码栈！两者设为相等时，还没等 V8 触发满堆 GC，总 RSS 就先突破了容器 512M 红线被内核强杀。应把老生代设为容器上限的 75% 左右（如 384）。

2. 写了一个每天清理临时目录的管理面板容器，为了能在网页上点按钮重启别的容器，同事给它挂了 -v /var/run/docker.sock:/var/run/docker.sock，有什么安全风险？

等同于把整台宿主机的 root 最高控制权交给了这个 Web 容器！一旦这个管理面板出现任何鉴权绕过或命令注入漏洞，攻击者调用 docker.sock API 创建一个挂载宿主机 / 根目录的特权容器，10 秒内就能改写宿主机的 /etc/shadow 或植入 SSH 公钥接管整台服务器。

3. 为什么每次执行 docker compose restart api 都要整整卡住 10 秒钟才重启完成？

restart 内部先执行 stop 再 start。卡满整整 10 秒，说明容器内的 PID 1 进程没有正确捕获并响应 SIGTERM 退出信号（最常见于用了 Shell 字符串格式 CMD 或外层套了 npm start / sh start.sh 脚本未加 exec），导致 Docker 苦等 10 秒宽限期超时后才发 SIGKILL 强杀。将脚本最后一行改为 exec node server.js 或改用数组格式 CMD 即可秒级优雅重启。
