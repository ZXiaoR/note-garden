03.1 数据持久化：命名卷（Volume）与绑定挂载（Bind Mount）怎么选

每个容器启动时，Docker 只是在只读镜像层顶上薄薄盖了一层「容器可写层（Writable Layer）」。一旦你为了改端口或升小版本执行了 docker rm mysql84，这层可写层会连同容器一起被彻底销毁，里面没挂载出来的表数据瞬间清零。要想让数据脱离容器生命周期永久留存，必须把容器内的关键目录挂载到宿主机磁盘上，日常主要分两种方式：

挂载类型 语法特征（注意冒号左侧） 最佳适用场景 核心特性与避坑细节
1. 命名数据卷
（Named Volume）		 左侧是纯名字（不带 / 或 ./）：
-v mysql_data:/var/lib/mysql		 MySQL / PostgreSQL / Redis / Kafka 的数据存储目录首选 由 Docker 统一托管在 /var/lib/docker/volumes/ 下：① 跨平台文件 I/O 性能最好（尤其在 macOS/Windows 上远快于绑目录）；② 若目标卷为空，首次启动会自动把镜像内该目录自带的初始文件拷进去。
2. 绑定挂载
（Bind Mount）		 左侧是宿主机路径（以 / 或 ./ 开头）：
-v ./my.cnf:/etc/mysql/conf.d/my.cnf:ro		 向容器注入配置文件（nginx.conf / my.cnf）、本地开发挂载源码热更新 宿主机目录有啥，容器里就实时看到啥。防坑提醒：如果宿主机 ./conf 是个空文件夹，直接绑到容器 /etc/nginx 上会把容器原有的默认配置全部遮盖清空导致启动报错！配置文件推荐单文件挂载并加 :ro（只读）。
3. 内存临时盘
（tmpfs）		 --tmpfs /app/tmp:rw,size=64m 存放解密后的临时密钥或高速缓存中间文件 只存于宿主机物理内存中，永不落磁盘，容器停止立刻挥发。
volume_ops.sh · 命名数据卷管理与组合挂载标准写法 
# 同时组合两种挂载：数据目录用「命名卷」保安全高性能，自定义配置用「只读绑定挂载」方便编辑
docker run -d --name mysql84 -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=Secret_2026 \
  -v mysql84_data:/var/lib/mysql \
  -v $(pwd)/my.cnf:/etc/mysql/conf.d/custom.cnf:ro \
  mysql:8.4

# 查看本机所有数据卷及具体存放在宿主机的哪个目录
docker volume ls
docker volume inspect mysql84_data
03.2 · 破解网络头号误区：容器独立 localhost 边界、自定义 Bridge 自动 DNS 与连接宿主机

03.2 容器网络通信：独立回环地址边界与自定义网桥 DNS 互通

新手把后端项目打成容器后，十有八九会撞上同一个报错：connect ECONNREFUSED 127.0.0.1:3306。明明 MySQL 容器已经映射了 -p 3306:3306，在宿主机用 DBeaver 连 127.0.0.1:3306 好好的，为什么放进业务容器就死活连不上了？

答案看一眼下图就全通了：每个容器都有自己独立隔离的虚拟网卡和回环地址——在 go-api 容器里面写 127.0.0.1，访问的是 go-api 容器它自己（里面当然没装 MySQL），根本没有出容器门！ 正确的做法是创建一个自定义 Bridge（网桥）网络，把两个容器放进同一个网桥里，Docker 内置 DNS 就会自动把容器名（如 mysql84）解析成它的容器内网 IP，代码连接串直接填 mysql84:3306 即可：

custom_network.sh · 创建自定义网桥并让应用按容器名连 MySQL 
# 1. 创建一个自定义网桥（注意：Docker 默认自带的 bridge 网桥不支持按容器名 DNS 解析！
#    必须自己建一个网桥，或使用下一章的 Docker Compose 自动创建专属网桥）
docker network create app-net

# 2. 启动 MySQL 加入 app-net（若宿主机不需要连它，甚至连 -p 3306:3306 都不用写）
docker run -d --name mysql84 --network app-net \
  -e MYSQL_ROOT_PASSWORD=Secret_2026 mysql:8.4

# 3. 启动业务容器加入同一个 app-net，数据库地址直接写 mysql84:3306 即可连通！
docker run -d --name go-api --network app-net -p 8080:8080 \
  -e DB_HOST=mysql84 -e DB_PORT=3306 my-go-api:v1.0.0
三种常见互通场景速查
  • 容器 A 访问容器 B（最常用）：放进同一个自定义 Bridge 网络，填 容器名:容器内部原始端口（注意：哪怕 MySQL 映射了 -p 13306:3306，容器之间内网直连依然填 mysql84:3306 而非 13306！）。
  • 容器内访问宿主机上裸跑的服务：macOS / Windows 直接连域名 host.docker.internal:端口；Linux 服务端在 docker run 时补加参数 --add-host=host.docker.internal:host-gateway 即可使用同一域名。
  • --network host（共享宿主机网络）：仅在 Linux 上完全生效，容器不再隔离端口、直接占用宿主机网卡，仅用于极致网络性能网关或抓包工具。

本章即时场景题（先想答案，再点击展开）

1. Redis 容器启动命令写了 -p 16379:6379 --name redis7 --network app-net，同一个 app-net 里的 Node.js 容器去连 Redis 时，端口该填 16379 还是 6379？

必须填 redis7:6379。-p 16379:6379 只是给容器外面的宿主机开的转发入口；处在同一个 app-net 二层虚拟网桥内的两个容器是直接点对点通信的，访问的是 redis7 容器内部真正监听的原始端口 6379。

2. 两个容器启动时都没写 --network（默认都在自带的 bridge 网络里），为什么在容器 A 里 ping 172.17.0.2 能通，但 ping mysql84 却报 bad address？

出于历史向后兼容原因，Docker 安装后自带的那个默认 bridge（docker0）网桥不开启自动容器名 DNS 解析；只有你通过 docker network create 自建的网桥（或用 docker compose 自动创建的项目专属网桥）才内置了 127.0.0.11 动态 DNS 服务器，支持直接按容器名互访。

3. 本地开发前端项目跑了 docker run -v $(pwd):/app my-web，为什么容器启动后突然报 Cannot find module 'vite'，明明打镜像时已经 npm install 过了？

宿主机当前目录覆盖了容器内的 /app。如果宿主机目录里还没装依赖（或者装的是 macOS 架构的 node_modules），Bind Mount 挂载上去就会把打镜像时存放在 /app/node_modules 里的 Linux 依赖全部遮挡或搞坏。可在启动时额外加一个匿名卷 -v /app/node_modules 保护容器内的依赖目录不被宿主机覆盖。

背后的原理：数据包是怎么穿过虚拟网线 veth pair 进出容器的，以及 -p 端口映射为什么会绕过 Linux 的 ufw 防火墙导致数据库裸奔公网？可查阅 《 核心原理篇 · 03 容器虚拟网络与 iptables NAT》。
