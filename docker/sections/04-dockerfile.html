04.1 · 指令语法拆解：COPY vs ADD、ARG vs ENV、ENTRYPOINT vs CMD 与 Exec 数组格式

04.1 Dockerfile 核心指令与三组必知辨析

Dockerfile 是一份纯文本构建食谱：从第一行 FROM 选定基础镜像底盘开始，后续每一条 RUN / COPY 指令都会在上一层之上叠出一个新的只读镜像层。日常写配置最容易混淆的是以下三组指令：

易混指令组 本质区别 工程编写准则
COPY vs ADD COPY 只做诚实透明的本地文件拷贝；ADD 遇到本地 .tar.gz 会自动解压，且支持填远程 URL。 99% 场景一律用 COPY，意图明确不产生意外解压行为。
ARG vs ENV ARG 仅在构建期（docker build --build-arg）有效，容器跑起来后消失；ENV 会永久写进镜像并带入运行期容器环境变量。 构建版本号、编译代理地址用 ARG；运行期时区 TZ、NODE_ENV=production 用 ENV。注意：密码密钥绝不要写进 ARG 或 ENV（用 docker history 能明文看到）。
ENTRYPOINT vs CMD ENTRYPOINT 定义容器固定的主可执行程序；CMD 提供默认参数（若 docker run 末尾传了新参数，会把 CMD 替换掉）。 启动命令务必写 JSON 数组 Exec 格式（CMD ["node", "dist/server.js"]）！若写成裸字符串 Shell 格式（CMD node dist/server.js），Docker 会包一层 /bin/sh -c 充当 PID 1，导致业务进程收不到 docker stop 的优雅退出信号。
EXPOSE 8080 的真相 仅仅是一句声明文档（告诉使用者该镜像内部默认监听 8080 端口），并不会自动打开宿主机端口！ 宿主机想访问它，启动时仍然必须显式写 -p 宿主机端口:8080。
04.2 · 构建提速 50 倍：层缓存失效连锁反应、「先拷依赖清单再拷源码」与 .dockerignore

04.2 分层缓存加速法则与必配的 .dockerignore

现代 Docker 默认使用 BuildKit 构建引擎，它会逐行检查指令与所拷文件的哈希校验和：一旦某一层的文件发生了哪怕 1 个字节的变化，从这一层往下的所有后续指令缓存全部连带失效，必须重新执行。

因此黄金排序法则是：「越不常变的内容放越上面，最常修改的业务源码放最下面」——先只拷贝依赖描述文件（go.mod / go.sum 或 package.json / package-lock.json）执行下载安装，最后再 COPY . . 拷贝业务源码。只要你没增删第三方库，平时改业务代码重打镜像直接秒跳过依赖下载：

Dockerfile · 反例（每次重装依赖）vs 正例（命中层缓存） 
# ❌ 反例：一上来先把整个项目拷进去
# 只要改了一行 controller 代码，COPY . . 层变化，导致下一行 npm ci 每次都重跑 2 分钟！
WORKDIR /app
COPY . .
RUN npm ci

# ============================================================
# ✅ 正例：先单独拷依赖锁文件装包，最后再拷业务源码
WORKDIR /app
# 1. 只要 package*.json 没变，下面这步构建永远 0.1 秒直接命中 CACHED！
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# 2. 频繁修改的业务源码放在最后拷贝
COPY . .
CMD ["node", "src/index.js"]
.dockerignore · 放在项目根目录（防泄漏密钥与加速构建上下文） 
# 1. 排除巨型本地依赖与构建产物（防止把本机 800MB node_modules 传给守护进程）
node_modules
dist
build
vendor

# 2. 排除版本控制与本地 IDE 目录（防 .git 变动无故击穿 COPY . . 缓存）
.git
.gitignore
.vscode
.idea

# 3. 【安全红线】严禁将本地 .env 私钥证书随 COPY . . 打进镜像层！
.env
.env.*
*.pem
*.key
04.3 · 镜像体积从 900MB 压到 20MB：多阶段构建（Multi-stage Build）原理与模板

04.3 多阶段构建：编译环境与运行环境彻底分离

编译 Go、TypeScript 或前端 React/Vue 项目时，我们需要庞大臃肿的编译器、SDK 和全量开发依赖（动辄 800 MB ~ 1.2 GB）；但线上真正运行的时候，其实只需要编译出来的那一个十几 MB 的二进制文件或 dist/ 静态文件夹。在同一个 Dockerfile 里写多个 FROM ... AS 阶段名，用 COPY --from=builder 只把最终产物挑进一个极小的运行底盘里，前面的编译阶段就会被自动丢弃，不会进入最终镜像：

build_cmd.sh · 执行构建并检查最终镜像体积 
# 在包含 Dockerfile 的项目根目录执行（注意末尾的 . 代表将当前目录作为构建上下文）
docker build -t my-order-api:v1.0.0 .

# 查看构建出的镜像体积与每一层的大小明细（Go / Node / 前端完整生产级 Dockerfile 见第 06 章）
docker images my-order-api:v1.0.0
docker history my-order-api:v1.0.0

本章即时场景题（先想答案，再点击展开）

1. 同事为了清理安装包节省镜像体积，分两行写了 RUN apt-get update && apt-get install -y curl 和第二行 RUN rm -rf /var/lib/apt/lists/*，第二行的删除真的减小最终镜像体积了吗？

完全没有减小，甚至还多叠了一层元数据！因为每一条 RUN 都会固化为一个不可修改的只读层：第一条 RUN 产生的几十 MB 缓存文件已经永久冻结在上一层里了，第二条 RUN rm 只是在新的一层打上了“隐藏标记（Whiteout）”。必须在同一条 RUN 指令内用 && 把安装和清理连起来写完，才不会把垃圾带进该层快照。

2. 新手在桌面目录 ~/Desktop（里面有 15 GB 电影和照片）建了个小项目跑 docker build -t demo .，为什么刚敲回车还没跑第一行指令就卡住转圈好几分钟？

命令末尾那个不起眼的 . 代表构建上下文（Build Context）目录。docker 客户端在开始构建前，默认会把 . 目录下的所有子文件打包发给后台 dockerd 守护进程——把 15 GB 无关文件全扫了一遍！务必在独立的空项目文件夹内构建，并配好 .dockerignore。

3. 为了安全不想把数据库密码明文写在代码里，同事在 Dockerfile 里写了 ARG DB_PASS 在构建时传入，构建完再 RUN unset DB_PASS，这样镜像推上仓库后别人就看不到密码了吗？

别人敲一行 docker history --no-trunc 镜像名 就能把密码看得清清楚楚！所有构建历史指令与 ARG 取值都会记录在镜像元数据中。任何数据库密码、JWT 私钥、API Key 一律不在构建期传入，而是在容器启动运行期通过 -e、--env-file 或挂载 Secret 文件动态注入。
