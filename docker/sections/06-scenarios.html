06.1 本地开发中间件全家桶：一行命令拉起 MySQL + Redis + Kafka

业务需求：新换一台电脑或拉取电商/社区项目跑本地联调时，需要同时用到 MySQL、Redis 和 Kafka 消息队列。把下面这份 dev-infra/compose.yaml 存下来，以后任何项目只需敲一行 docker compose up -d 即可在 15 秒内全部就绪：

dev-infra/compose.yaml · 本地联调三大件标准配置 
name: local-infra
services:
  mysql:
    image: mysql:8.4
    ports: ["127.0.0.1:3306:3306"]
    environment:
      MYSQL_ROOT_PASSWORD: Secret_2026
      MYSQL_DATABASE: shop_db
      TZ: Asia/Shanghai
    command: ["--character-set-server=utf8mb4", "--collation-server=utf8mb4_0900_ai_ci"]
    volumes: ["mysql_data:/var/lib/mysql"]

  redis:
    image: redis:7.2-alpine
    ports: ["127.0.0.1:6379:6379"]
    command: ["redis-server", "--appendonly", "yes"]
    volumes: ["redis_data:/data"]

  kafka:
    image: apache/kafka:3.8.0
    ports: ["127.0.0.1:9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1

volumes:
  mysql_data:
  redis_data:
关键细节与常见坑
  • 为什么端口写成 127.0.0.1:3306:3306 而不是 3306:3306？只写 3306:3306 等同于 0.0.0.0:3306:3306——你在咖啡厅连公共 Wi-Fi 时，局域网里的其他人也能直接扫到你的测试数据库端口！加上 127.0.0.1: 仅允许本机回环访问，安全得多。
  • 平时不写代码时怎么省内存？敲 docker compose stop 即可暂停释放全部内存，下次敲 docker compose start 2 秒恢复且数据全在。

背后的原理：0.0.0.0 与 127.0.0.1 端口绑定在内核 NAT 表上有何区别？详见 《核心原理篇 · 03.2 iptables DNAT 端口转发》。

06.2 · Go 服务生产镜像：CGO 静态编译 + HTTPS 根证书 + 时区 + 非 root 用户（~24MB）

06.2 Go 后端服务生产级 Dockerfile 模板

业务需求：将 Go HTTP 服务打包成轻量安全的生产镜像，避免上线后调微信支付 HTTPS 接口报证书错误、打日志时间慢 8 小时或以高危 root 身份裸跑。

Dockerfile (Go 1.23 多阶段构建标准模板) 
# ========= 阶段一：编译静态二进制 =========
FROM golang:1.23-alpine AS builder
WORKDIR /src
ENV GOPROXY=https://goproxy.cn,direct

# 先单独拷 go.mod/go.sum 下载依赖，充分利用层缓存
COPY go.mod go.sum ./
RUN go mod download

# 再拷源码，关闭 CGO 编译纯静态二进制，-ldflags="-s -w" 剥离调试符号减小体积
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/server ./cmd/server

# ========= 阶段二：极简安全运行镜像 =========
FROM alpine:3.20
# 必装 ca-certificates（调外部 HTTPS 必需）与 tzdata（东八区时区必需）
RUN apk --no-cache add ca-certificates tzdata \
    && adduser -D -u 10001 appuser
ENV TZ=Asia/Shanghai

WORKDIR /app
COPY --from=builder /out/server /app/server
USER appuser
EXPOSE 8080
ENTRYPOINT ["/app/server"]
Go 容器化的 3 个经典线上坑
  • 漏关 CGO_ENABLED=0 报 not found：如果在 Debian 构建阶段没设 CGO_ENABLED=0，编出的二进制会动态链接 glibc，拷进 alpine（只有 musl）启动会匪夷所思地报 exec /app/server: no such file or directory。
  • 漏装 ca-certificates：精简镜像默认没有根证书库，任何向外发起的 HTTPS 请求都会报 x509: certificate signed by unknown authority。
  • 漏装 tzdata：只写 ENV TZ=Asia/Shanghai 却没装时区数据包，time.LoadLocation 依然找不到东八区回退到 UTC。

背后的原理：容器设置了 --cpus=2 后，Go 进程里的 GOMAXPROCS 怎么感知配额？详见 《核心原理篇 · 01.2 Cgroups 运行时感知》。

06.3 · Node.js / TypeScript 生产镜像：剔除 devDependencies + 非 root 运行 + 信号直达

06.3 Node.js (TypeScript) 服务生产级 Dockerfile 模板

Dockerfile (Node 22 LTS + TypeScript 多阶段模板) 
# ========= 阶段一：安装全量依赖并把 TS 编译为 JS =========
FROM node:22-bookworm-slim AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# ========= 阶段二：生产运行镜像（仅保留运行期依赖与 dist 产物） =========
FROM node:22-bookworm-slim
ENV NODE_ENV=production TZ=Asia/Shanghai
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=builder /app/dist ./dist

# 直接使用官方镜像内置的低权限账号 node，并直接启动 node 而非 npm start！
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
为什么最后一行的 CMD 千万别写 ["npm", "start"]？
  • npm 不会完整转发优雅停机信号：如果用 npm start 做 PID 1，执行 docker stop 时系统发来的 SIGTERM 被外层 npm 拦下，里面的 node 代码里写的 process.on('SIGTERM', ...) 收不到通知，无法排空正在处理的订单请求，只能干等 10 秒被强制杀死！直接写 ["node", "dist/server.js"] 最干净。
  • 用 npm ci 代替 npm install：npm ci 严格按 package-lock.json 确定性安装，锁文件不一致立即报错，保证本地与线上依赖版本分毫不差。

背后的原理：为什么容器内 PID 1 进程在 Linux 内核里的信号行为很特殊？详见 《核心原理篇 · 00.2 PID Namespace 与信号规则》。

06.4 · 前端单页应用部署：Node 打包 dist + Nginx 托管（防 History 路由刷新 404 与 /api 反代）

06.4 前端 SPA (React / Vue) + Nginx 反向代理一键打包

Dockerfile · 前端构建并封装进 25MB Nginx 镜像 
FROM node:22-bookworm-slim AS builder
WORKDIR /web
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
# 拷入自定义 Nginx 配置与构建好的纯静态资源 dist/
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /web/dist /usr/share/nginx/html
EXPOSE 80
nginx.conf · History 路由兜底与容器内网 /api 反代 
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  # 1. 前端路由兜底：访问 /orders/123 找不到物理文件时回退给 index.html，防刷新 404
  location / {
    try_files $uri $uri/ /index.html;
  }

  # 2. 同域反向代理后端容器 api:8080，彻底免除浏览器 CORS 跨域配置
  location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
  }
}
06.5 · 单机生产安全防线：全栈编排只暴露 Nginx 80/443，严防 -p 绕过 ufw 防火墙

06.5 全栈上线编排：数据库内网隐藏与 ufw 防火墙大坑

高发线上安全事故：许多开发者在 Ubuntu 云服务器上开了 ufw allow 80,443 防火墙，以为 3306 / 6379 已经被挡住了，于是放心写了 ports: ["3306:3306"]——结果第二天数据库就被公网扫描器勒索了！原因是：Docker 的 -p 端口映射会直接操作内核更早执行的 iptables PREROUTING (DNAT) 链，直接绕过宿主机 ufw 的 INPUT 过滤规则向全公网敞开大门！

生产全栈编排黄金准则：整份生产 compose.yaml 里，只有最外层的入口网关（Nginx / Caddy）配置 ports: ["80:80", "443:443"]；里面的 api、mysql、redis 一律不写 ports:（它们在 Compose 内网里照常按服务名互通，若运维偶尔需要本机调试数据库，最多写成 127.0.0.1:3306:3306 再走 SSH 隧道连接）。

06.6 · 跨芯片架构发版：解决 Mac M1~M4 (arm64) 镜像推到云服务器 (amd64) 报 exec format error

06.6 解决跨架构报错 exec format error：Buildx 多架构构建

业务需求：你在 Apple Silicon Mac（linux/arm64 架构）本机执行 docker build 打好镜像推上仓库，到阿里云 x86_64 服务器（linux/amd64 架构）拉下来一跑立刻秒退报错：exec /app/server: exec format error。这是因为默认打出的镜像指令集架构跟构建机器一致，CPU 指令集不兼容！用内置的 docker buildx 指定目标平台即可一键解决：

multiarch_build.sh · 在 Mac 上构建 Linux x86_64 或双架构通用镜像 
# 方式 A：明确只给线上 x86_64 Linux 服务器使用（构建并加载到本地或直接 --push）
docker buildx build --platform linux/amd64 -t registry.example.com/team/api:v1.2.0 --push .

# 方式 B（团队推荐）：同时构建 amd64 + arm64 双架构 Manifest 清单推上仓库
# 此后无论 Mac 开发机还是 x86 云服务器执行 docker pull，都会自动匹配拉取对应架构层！
docker buildx create --name multi-builder --use  # 首次创建一次多架构构建器即可
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/team/api:v1.2.0 --push .
06.7 · 磁盘告警急救：No space left on device 定位三板斧与安全清理日志

06.7 服务器报 No space left on device 怎么快速定位与止血

disk_rescue.sh · 先查谁占了空间，再针对性无损释放 
# 1. 一眼看清是镜像、容器、数据卷还是 BuildKit 构建缓存吃满了磁盘
docker system df

# 2. 清理所有无用的停止容器、未引用网络、悬空镜像与过期构建缓存（绝不触碰运行中容器与 Volume 数据卷）
docker system prune -f
docker builder prune -f

# 3. 如果 docker system df 没占多少，但 /var/lib/docker 依然有 100GB，
#    99% 是某个没配日志轮转的容器打出了几十 GB 的 *-json.log！揪出大日志并在线截断清空：
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -hr | head -n 5
# 【注意】严禁直接 rm 正在被 dockerd 打开的日志文件（空间不会释放），必须用 truncate 置零：
sudo truncate -s 0 /var/lib/docker/containers/<容器长ID>/<容器长ID>-json.log
为什么直接 rm 大日志文件磁盘还是 100%？

Linux 文件系统中，只要后台 dockerd 进程还持有该日志文件的打开文件描述符（File Descriptor），执行 rm 只是删掉了目录项链接，磁盘物理块并不会释放（直到重启容器或重启 Docker）。而使用 truncate -s 0 直接把原文件长度截断为 0 字节，无需重启容器即可在 1 秒内把几十 GB 磁盘空间立刻归还给操作系统！止血后记得补上 07.3 的日志轮转配置治本。

06.8 · 单机生产发布SOP：基于不可变版本 Tag 的更新与 10 秒一键回退

06.8 单机生产发版更新与 10 秒快速回滚

deploy_rollback.sh · compose.yaml 引用 APP_TAG 变量实现秒级发版与回退 
# 在 compose.yaml 中将业务镜像写为：image: registry.example.com/team/api:${APP_TAG:-v1.2.0}

# 1. 发版 v1.3.0：先提前 pull 新镜像（下载期间旧容器照常对外服务，停机窗口缩短到 1 秒内！）
export APP_TAG=v1.3.0
docker compose pull api
docker compose up -d --no-deps api

# 2. 万一上线发现 v1.3.0 有严重 Bug，因本地仍缓存着上一版镜像，切回版本号 2 秒完成回滚：
export APP_TAG=v1.2.0
docker compose up -d --no-deps api

本章即时场景题（先想答案，再点击展开）

1. Go 项目在 Debian 镜像里 go build 编出二进制拷进 alpine 运行，文件明明在 /app/server 且有 x 权限，启动却报 no such file or directory，为什么？

Linux 内核在加载动态链接可执行文件时，如果找不到它头部声明的动态链接器（Debian 编出的默认找 /lib64/ld-linux-x86-64.so.2，而 Alpine 只有 musl），报出的错误文案正是极具迷惑性的 no such file or directory！编译时加上 CGO_ENABLED=0 生成无外部 C 库依赖的纯静态二进制即可解决。

2. 云服务器已经在系统里跑了 ufw enable 只放行了 22 和 80 端口，紧接着同事跑了 docker run -d -p 6379:6379 redis:7.2（没设密码），这个 Redis 在公网能被连上吗？

能被全公网直接免密连上！因为 Docker -p 6379:6379 写入的是 iptables nat PREROUTING 和 DOCKER 转发链，数据包还没走到 ufw 所在的 INPUT 链就已经被直接转发进了 Redis 容器。内网组件要么不加 -p，要么严格绑定本机回环 -p 127.0.0.1:6379:6379。

3. 发版时为什么推荐先单独敲 docker compose pull api 下好新镜像，再敲 docker compose up -d api？

如果新镜像有 300 MB、网络下载要 40 秒，先 pull 可以保证下载全程旧容器毫发无损继续处理线上请求，随后 up -d 只需花不到 1 秒完成旧停新起切换，把单机更新闪断缩到最短。
