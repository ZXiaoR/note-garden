05.1 · 声明式编排：Compose V2 标准文件名、自动创建专属网桥与核心字段全景

05.1 用一份 compose.yaml 管好整套后端服务

当一个项目同时包含后端 API、MySQL 和 Redis 时，手敲 3 条带十几项参数的 docker run 既难记又没法提交 Git 共享给队友。Docker Compose（现已内置为官方子命令 docker compose，中间是空格，不再是旧版带横杠的独立脚本 docker-compose）让你把所有容器、数据卷和网络声明在一份 compose.yaml 文件里（注：Compose V2 规范已废弃顶层的 version: '3.8' 字段，直接从 services: 开始写即可）。

更省心的是：执行 docker compose up -d 时，它会自动为当前项目创建一个专属自定义网桥，同一文件下的所有服务天然支持直接用服务名（如 mysql:3306、redis:6379）互相访问！

compose.yaml · 含健康检查等待（service_healthy）的应用 + MySQL + Redis 标准编排模板 
services:
  # 1. 自研后端服务：自动先构建当前目录 Dockerfile，等数据库真正就绪后再启动
  api:
    build: .
    image: shop-api:v1.0.0
    ports:
      - "8080:8080"
    env_file:
      - .env                     # 从本地 .env 读取密码配置，不把密钥硬编码进 YAML
    environment:
      DB_HOST: mysql             # 直接填下方服务名 mysql，内置 DNS 自动解析
      REDIS_ADDR: redis:6379
    depends_on:
      mysql:
        condition: service_healthy  # 关键！等 mysql 通过健康检查才启动 api
      redis:
        condition: service_healthy
    restart: unless-stopped

  # 2. MySQL 8.4 数据库服务（配 mysqladmin ping 健康探针）
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-Secret_2026}
      MYSQL_DATABASE: shop_db
      TZ: Asia/Shanghai
    volumes:
      - mysql_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p$${MYSQL_ROOT_PASSWORD}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 15s

  # 3. Redis 7.2 缓存服务
  redis:
    image: redis:7.2-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

# 顶层声明命名数据卷（容器重建时数据永久保留）
volumes:
  mysql_data:
  redis_data:
05.2 · 解决启动抢跑报错：「容器已启动 Started」不等于「数据库已就绪 Healthy」

05.2 启动顺序控制：depends_on 与 service_healthy 健康检查

很多开发者写了简单的列表格式 depends_on: - mysql，结果第一次执行 docker compose up -d 时，api 容器还是秒崩报 Connection refused。原因是：默认的 depends_on 只管“把 mysql 容器进程拉起来（service_started）”就立刻启动 api；但 MySQL 首次初始化系统表空间往往需要 8~15 秒才能真正开口监听 3306 端口！

两道防护配合最稳妥：① 在 compose.yaml 中像上面模板那样给数据库配 healthcheck 并声明 condition: service_healthy；② 后端代码自身的数据库连接池初始化也保留 3~5 次指数退避重试，应对云数据库网络闪断。

05.3 · 日常编排指令与删库红线：up -d --build、单服务滚动更新与严禁误敲 down -v

05.3 Compose 日常高频命令与 down -v 删库红线

Compose 高频命令 真实行为与线上安全提示
docker compose up -d --build 改完业务代码后最常用的一条命令：重新构建发生变动的镜像，并只重建配置或镜像变了的那个容器（没变的 MySQL/Redis 保持原样不中断）。
docker compose ps / docker compose logs -f api 查看当前项目所有容器的健康状态（healthy）/ 仅实时追踪 api 服务的日志。
docker compose exec mysql mysql -uroot -p 直接按服务名 mysql 进入数据库容器终端，连具体容器名叫什么都不用关心。
docker compose down（安全停服） 停止并移除当前项目的容器与网络，但完整保留 volumes: 里的所有命名数据卷，下次 up -d 数据原封不动恢复。
docker compose down -v（高危清库！） 多了一个 -v（--volumes），会把当前项目声明的所有命名数据卷（包括 mysql_data 数据库文件）一并物理删除！仅限本地想彻底重置干净测试库时使用，生产服务器严禁敲 -v。

本章即时场景题（先想答案，再点击展开）

1. 我只修改了 compose.yaml 里 api 服务的某一个环境变量，没有停整个项目，直接再敲一次 docker compose up -d，旁边的 mysql 容器会被重启吗？

不会重启。Docker Compose 采用声明式状态比对（Reconciliation）：它会对比当前运行容器与最新 compose.yaml 的配置哈希，发现 mysql 没有任何变更就会显示 Running 原地跳过，只精准重建 api 一个容器。

2. 在 compose.yaml 的 healthcheck.test 命令字符串里为什么要写成双美元符号 $${MYSQL_ROOT_PASSWORD} 而不是单 $？

如果只写单 $MYSQL_ROOT_PASSWORD，docker compose 在宿主机解析 YAML 文件时就会尝试用宿主机终端的同名变量去替换它（若宿主机没设该变量就会被替换成空字符串）；写成 $$ 则会转义保留一个 $ 传进容器内部 Shell，去读取容器自身的环境变量。

3. 同一台开发机上有两个不同文件夹的项目，各自的 compose.yaml 里都有一个服务叫 mysql、数据卷叫 mysql_data，同时跑起来会互相冲突覆盖吗？

默认不会冲突（只要注意宿主机映射端口 -p 不同即可）。因为 Compose 会自动拿所在文件夹的名字作为项目前缀（Project Name），分别创建 proj_a_mysql_data 和 proj_b_mysql_data 两个完全隔离的数据卷与专属网络（也可通过顶层 name: my-shop 显式固定项目前缀）。
