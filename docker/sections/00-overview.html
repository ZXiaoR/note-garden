00.1 · 核心定位：容器化引擎的一句话定义、「镜像 / 容器 / 仓库」关系与开发交付全景

00.1 Docker 是什么，以及它在研发流程里的位置

一句话定义：Docker 是一个开源的应用容器引擎，它把应用程序代码连同运行所需的系统库、依赖包和默认配置一起打包成标准的只读镜像（Image），在任何机器上都能秒级启动彼此隔离的容器（Container）进程。

没有 Docker 之前，你在花园其他笔记里装一套本地环境要装 MySQL 8.4、Redis 7.2、Kafka，不同操作系统命令不同、动态库版本冲突，项目上线时经常遇到“我电脑上明明能跑，放到服务器上就报错”。有了 Docker 之后，无论是官方中间件还是你自己写的 Go / Node.js 服务，都变成了统一的“集装箱”交付。先记住贯穿全文的三个核心概念：

  • 镜像（Image）≈ 只读安装包 / 模具：由多层只读文件叠成（例如 mysql:8.4 镜像里装好了 Linux 基础库与 MySQL 服务端程序），自身静态不运行，一份镜像可以启动任意多个容器。
  • 容器（Container）≈ 正在运行的进程实例：用镜像作为模板启动出来的隔离运行环境（等价于面向对象里“类 Class”实例化出的“对象 Object”），拥有自己独立的网络端口视角与可写临时层。
  • 镜像仓库（Registry）≈ 存放镜像的应用商店：用来上传（push）和下载（pull）镜像的远端服务，公开最常用的是官方 Docker Hub，企业内部私服常用阿里云 ACR（Container Registry，容器镜像服务）、Harbor 或 GitHub Container Registry（ghcr.io）。

背后的原理：容器没有安装完整的客户机操作系统，为什么里面的进程却以为自己独占了一台干净的 Linux 机器？可按需查阅 《 核心原理篇 · 00.1 容器 vs 虚拟机与 Linux Namespace 隔离》。

00.2 · 横向选型边界：裸机安装 vs 虚拟机（VM）vs Docker vs Compose vs Kubernetes

00.2 什么时候用 Docker，什么时候选虚拟机或 Kubernetes

运行与编排方式 隔离粒度与启动速度 资源额外损耗 最适合的实际场景 什么时候不合适
裸机直接安装
(apt / brew / msi)		 无隔离，共用宿主机全局目录与端口 零损耗（直接调物理硬件） 极致磁盘 I/O 敏感的超大型生产数据库专机、硬件驱动服务 一台机器同时跑 Node 18 与 Node 22 项目、频繁重装测试多版本中间件
传统虚拟机（VM）
(VMware / 云 ECS)		 硬件级强隔离（独立完整 Guest OS 内核），启动需数十秒~几分钟 高（每台 VM 独占数 GB 内存与完整系统盘） 跨不同操作系统内核（如 Linux 宿主机跑 Windows）、多租户公有云强安全隔离 为了隔离十几个微服务各自开十几台虚拟机，内存与运维成本过高
Docker 单容器
(docker run)		 进程级隔离（共享宿主机 Linux 内核），百毫秒~秒级启动 极低（本质就是宿主机上的一个普通受限进程） 临时拉起单个 MySQL / Redis 调试、跑一次性构建或命令行脚本 同时管理 5 个相互依赖的容器，手敲几十行命令行参数极易出错
Docker Compose
(compose.yaml)		 单机多容器编排，一键启停整套应用栈 极低（自带内网 DNS 与启动顺序控制） 本地全栈开发环境、中小型项目单机生产部署（1~3 台服务器以内首选） 无法自动跨 20 台服务器做故障漂移、自动弹性扩缩容与跨机负载均衡
Kubernetes（K8s） 跨多台机器的集群容器编排系统 控制平面与网络插件本身需额外消耗数核 CPU 与内存 数十个微服务、多台服务器集群高可用自愈、流量洪峰自动水平扩容 只有一两台机器的个人项目或早期创业团队——过早上 K8s 运维负担远超收益

00.3 本笔记知识地图

整份笔记顺着日常真实进阶路线推进：先「把官方镜像稳稳跑起来（00~03）」，再「把自己的项目优雅打包编排起来（04~06）」，最后「补齐生产安全防线与 Linux 容器内核原理（07~08 + 原理篇）」：

本章即时场景题（先想答案，再点击展开）

1. 同事跑了 docker rm mysql84 把容器删掉了，他担心地问：“是不是刚下载了 5 分钟的 mysql:8.4 镜像也被删没了，下次还得重下？”

镜像还在本机，不需要重新下载。“镜像（Image）”是只读模板，“容器（Container）”是用镜像跑起来的实例；docker rm 只删除容器实例，只要没执行 docker rmi mysql:8.4，下次再跑 docker run 1 秒内就能直接用本地镜像拉起新容器（注：但若没挂载数据卷，旧容器里新建的表数据会随容器删除而丢失，详见 03.1）。

2. 团队只有一个 4 核 8G 云服务器，上面跑着 Nginx、Go 后端、MySQL 和 Redis 共 4 个服务，有必要为了用容器而搭一套 Kubernetes（K8s）集群吗？

完全没必要，甚至会白白吃掉近一半内存。K8s 自身的控制面组件就会常驻消耗 2GB+ 内存和大量运维精力。1~2 台服务器的项目直接用一份 Docker Compose（compose.yaml） 就能优雅搞定一键编排、内网隔离与自动重启，等未来业务增长到多机集群弹性扩缩容时再迁移 K8s 也完全平滑（因为镜像是通用的）。

3. 我有一台 Ubuntu Linux 云服务器，能在它上面直接用 Docker 运行一个原生的 Windows .exe 桌面程序容器吗？

不能。Docker 容器不像虚拟机那样自带独立操作系统内核，而是直接共享宿主机的内核——Linux 宿主机上的容器只能运行调用 Linux 内核系统调用的程序（注：之所以在 macOS 和 Windows 电脑上能跑 Linux 容器，是因为 Docker Desktop / OrbStack 在后台悄悄起了一个极轻量的 Linux 虚拟机充当宿主机）。
