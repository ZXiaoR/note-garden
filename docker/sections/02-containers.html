02.1 · 镜像选型规范：完整镜像名三段结构、禁用裸 :latest 与 Alpine / Slim / Distroless 对比

02.1 镜像命名规范与基础镜像三大家族选型

一个完整的镜像标识由三段构成：[仓库域名]/[命名空间/镜像名]:[版本标签 Tag]。例如 ghcr.io/org/api:v1.4.2；当省略仓库域名与命名空间只写 redis:7.2-alpine 时，等价于从官方默认库拉取 docker.io/library/redis:7.2-alpine；当连冒号标签都省略（只写 redis）时，Docker 会自动补上 :latest。

工程规范：生产环境严禁裸写 :latest 标签
:latest 并不是“永远稳定兼容版”，而是镜像作者最后一次没带版本号推上去的浮动标签（可能昨天还是 MySQL 8.0，今天服务器扩容拉新节点就变成了不兼容的 MySQL 9.0）。无论是中间件还是自研应用，一律显式锁定版本号（如 mysql:8.4.3、node:22-bookworm-slim）。
基础镜像变体后缀 典型基础体积 底层 C 标准库与包管理器 优势与选型避坑建议
标准完整版
（如 node:22、python:3.12）		 800 MB ~ 1.1 GB Debian + glibc + apt（预装 git/gcc/curl 等大量编译工具） 适合作为多阶段构建的阶段一编译镜像（Builder）；直接拿来跑线上容器体积过大且攻击面广。
-slim 精简版（稳妥首选）
（如 node:22-bookworm-slim）		 150 ~ 220 MB Debian + 标准 glibc（删掉了编译器和文档） Node.js / Python 生产运行首选！既有标准 glibc 100% 兼容各种 C++ 原生扩展（如 sharp、bcrypt、Prisma 引擎），体积又缩小了 75%。
-alpine 极小版
（如 nginx:1.27-alpine）		 7 ~ 50 MB Alpine Linux + 轻量 musl libc + apk Nginx / Redis / 纯静态编译 Go 二进制首选。常见坑：musl libc 与标准 glibc 二进制不兼容（若把未关 CGO 的 Go 程序或依赖 glibc 预编译包的 Python/Node 库放进 Alpine 会报 not found），且 DNS 解析偶有细微差异。
distroless / scratch
（Google 无发行版镜像）		 2 ~ 20 MB 连 Shell（sh/bash）和包管理器都没有，只含根证书与时区 金融/高安全要求下跑 Go / Rust 静态二进制最安全（黑客即使拿下应用漏洞也弹不出 Shell），缺点是线上不能 docker exec 进去敲命令排障。
02.2 · 容器排障基本功：容器退出码（0 / 1 / 137 / 139）一眼定因与排障五件套

02.2 容器秒退与卡死排查：看懂退出码与排障五件套

容器的核心规则是：「主进程（容器内的 PID 1）活着，容器就活着；主进程一旦退出，容器立刻变成 Exited 停止状态」。当你发现刚启动的容器在 docker ps 里找不到了，第一步是敲 docker ps -a 看它的 STATUS 退出码（Exit Code）：

debug_five_tools.sh · 日常排障最高频的 5 条命令 
# 1. 列出所有容器（含已崩溃停止的容器，看 STATUS 里的 Exited (code)）
docker ps -a

# 2. 实时追踪容器最后 100 行标准输出/报错日志（秒退容器也能照常看日志！）
docker logs -f --tail 100 my-app

# 3. 进入正在运行的容器交互式终端（Alpine 镜像没有 bash，把 bash 换成 sh）
docker exec -it my-app sh

# 4. 查看容器详细底层配置（如查是否因 OOM 内存超限被杀、挂载路径、内网 IP）
docker inspect my-app --format 'OOMKilled={{.State.OOMKilled}} Exit={{.State.ExitCode}}'

# 5. 像 Linux top 一样实时监控全机所有容器的 CPU%、内存占用与网络流量
docker stats
常见退出状态码 故障根因与第一排查动作
Exited (0) 正常结束退出。最常见于跑了个后台脚本或误用了 docker run ubuntu（没前台常驻进程，跑完即退）。
Exited (1) 业务代码自身报错崩溃（如缺配置文件、连不上数据库抛未捕获异常）。立刻敲 docker logs my-app 看报错堆栈。
Exited (126 / 127) 126 为启动脚本无可执行权限（需 chmod +x）；127 为找不到启动命令（命令拼错或动态链接库缺失）。
Exited (137)
(128 + 9 SIGKILL)		 进程被强制信号 SIGKILL(9) 杀死：要么是容器内存超限触发内核 OOM Killer（OOMKilled=true），要么是 docker stop 超 10 秒未退被强杀。

本章即时场景题（先想答案，再点击展开）

1. 容器刚启动 3 秒就挂了，想进去看一眼报错日志，敲 docker exec -it my-app sh 却提示 Container is not running，该怎么查原因？

容器停止后里面已经没有活着的进程空间了，所以不能 exec 进去；但停止的容器并没有被删除，它的标准输出日志和内部文件都完好无损！直接敲 docker logs --tail 100 my-app 就能看到崩溃报错；如果想看它里面的某个日志文件，用 docker cp my-app:/path/err.log . 拷出来即可。

2. 线上监控报警某个 Node.js 容器每隔半天就自动重启一次，docker ps -a 看到上一次退出状态是 Exited (137)，第一步怀疑什么？

137 = 128 + 9，代表进程收到了不可捕获的强制杀死信号 SIGKILL(9)。排除人为敲 docker kill 后，95% 是因为代码内存泄漏或突发大文件加载超出了容器的内存上限，被 Linux 内核 OOM Killer 直接击毙。执行 docker inspect my-app --format '{{.State.OOMKilled}}' 返回 true 即可实锤。

3. 为什么本机下载了 node:22-bookworm-slim（200MB）后，再下载另一个同样基于 bookworm-slim 的自研镜像时，前面那 200MB 瞬间显示 Already exists 秒下完？

因为 Docker 镜像采用分层只读内容寻址存储。不同镜像只要共享相同的基础镜像层（SHA256 摘要相同），宿主机磁盘和内存里只存唯一一份副本，拉取和存储时直接复用已有底层。

背后的原理：多容器共享同一份只读镜像层、各自改动又互不污染是怎么做到的？以及 Exit 137 在内核里是怎么判定的？可查阅 《 核心原理篇 · 02 Overlay2 联合文件系统》 与 《01 Cgroups 内存 OOM 机制》。
