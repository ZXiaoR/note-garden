02.1 Overlay2 四目录联合挂载、Copy-on-Write 与 Whiteout 机制 常问

这节回答实战篇哪个问题：对应 实战篇 02.1、03.1 与 04.3 —— 为什么用同一个 200MB 镜像启动 20 个容器不会占满 4GB 磁盘？为什么数据库文件绝不能直接写在容器层里？以及为什么 Dockerfile 里跨 RUN 指令删除临时文件完全省不了体积？

Docker 默认使用的存储驱动是 Linux 内核原生的 overlay2（基于 OverlayFS，Overlay Filesystem，叠层联合文件系统）。它的核心思想就像把多张半透明胶片叠在一起从顶部往下看：底下几张胶片是所有容器共享、绝对只读的镜像层（lowerdir），只有最上面薄薄一张胶片是当前容器独占的可写层（upperdir），内核将它们合并挂载成容器看到的统一根目录视图（merged）：

看懂这张图，实战篇里的三个高频困惑就迎刃而解了：

  1. 为什么多容器极省磁盘与内存？不仅磁盘上的 lowerdir 只存一份，更重要的是因为不同容器读取同一个镜像层里的动态链接库（比如 libc.so.6 或 node 二进制）时指向宿主机磁盘上的同一个 inode，Linux 内核连内存里的 Page Cache 代码页都是跨容器共享一份的！
  2. 为什么 MySQL / Redis 数据目录必须挂载 Volume 绕开 overlay2？因为 CoW（Copy-on-Write，写时复制） 是“文件级”而非“块级”复制！假如镜像下层有一个 1GB 的数据文件，容器启动后哪怕只调用 write() 修改其中 4KB 的一个页，overlay2 在 open(O_WRONLY) 阶段也必须阻塞住进程，先把整个 1GB 文件从 lowerdir 完整拷贝（copy_up）到 upperdir 后才能落盘，首次写延迟高达数秒且磁盘占用瞬间翻倍。而 Docker Volume 本质上是宿主机原生文件系统（ext4 / xfs）子目录的 Bind Mount，读写直通底层块设备，彻底绕开 overlay2。
  3. 为什么下一条 RUN rm -rf /var/lib/apt/lists/* 减不了上一层的体积？因为 lowerdir 是不可变的（Immutable）。当你在新的一层删除下层已存在的文件 foo.tar.gz 时，overlay2 只能在当前层的 upperdir 里创建一个主次设备号均为 0, 0 的特殊字符设备文件（即 Whiteout 涂白遮罩文件），告诉 merged 视图“别把这个名字露出来”——底下那层 200MB 的 foo.tar.gz 依然原封不动地躺着并随镜像一起推送下载！所以清理缓存必须用 && 合并在同一条 RUN 指令内，或者直接用多阶段构建只 COPY --from=builder 最终产物。

02.2 OCI 镜像四元组结构、SHA256 寻址与 BuildKit 并行 DAG 深挖

这节回答实战篇哪个问题：对应 实战篇 04.2 与 06.6 —— 为什么官方镜像敲同一个 docker pull redis:7.2 在 Apple M 系列芯片和云端 x86 服务器上能自动拉对架构，以及现代 BuildKit 比老式串行构建快在哪里？

按照 OCI Image Spec，镜像在远端 Registry 仓库里并非一个孤立的大压缩包，而是基于 内容可寻址存储（Content-Addressable Storage，所有对象均以其内容的 sha256 哈希摘要唯一定位） 组织的四级树状索引：

  1. Image Index（又称 Manifest List，多架构总目录）：当你拉取 redis:7.2 时，客户端最先下载的是一份只有几 KB 的 JSON 索引清单，里面按 os + architecture 列出了 linux/amd64、linux/arm64/v8 等各架构对应的具体 Manifest sha256 地址。containerd 匹配本机 CPU 架构后，才会去下载匹配的那一支——假如你本地在 Apple Silicon 上直接 docker build 没有用 buildx --platform 生成这份多架构索引，推上去就只有单一的 arm64 分支，Linux amd64 服务器拉下来启动便会立即报 exec format error。
  2. Image Manifest（单架构配置与层清单）：记录该架构镜像对应的 1 个 Config 摘要，以及按顺序排列的 N 个只读层 Layer Blob 摘要。
  3. Image Config（镜像元数据 JSON）：存放 ENV 环境变量、WORKDIR、ENTRYPOINT / CMD、USER 以及每一层解压后的校验和（diff_ids）——这就是为什么 Dockerfile 里的 ENV / CMD / EXPOSE 指令并不生成新的文件系统 tar.gz 大层，只是更新这份几 KB 的配置 JSON。
  4. Layer Blobs（文件系统增量压缩包）：每一层是一个 tar+gzip（或更快的 zstd）压缩包。两个毫无关系的业务镜像只要都基于 debian:bookworm-slim，底层基础层的 sha256 完全一致，拉取和推送时自动跳过已有层（显示 Already exists / Layer already exists）。

自 Docker 23.0 起默认启用的新一代构建引擎 BuildKit，将传统的“从上往下逐行串行执行 Dockerfile”改造为编译器式的 LLB（Low-Level Builder，底层构建中间表示） 有向无环图（DAG，Directed Acyclic Graph）：

  • 互不依赖的阶段自动并行构建：在包含“前端构建阶段 + 后端编译阶段 + 最终运行阶段”的多阶段 Dockerfile 中，BuildKit 分析依赖图后会同时并行跑前端打包与后端编译；甚至如果某个中间阶段在最终 FROM 阶段根本没被引用，BuildKit 会直接跳过不执行它。
  • 按需传输构建上下文与跨次缓存挂载：传统引擎每次构建先把整个项目目录打包发给守护进程，而 BuildKit 只增量同步真正被 COPY 引用的变更文件，并新增了不打入镜像层的专用编译缓存挂载（如 RUN --mount=type=cache,target=/go/pkg/mod go build ...）和安全密钥挂载（RUN --mount=type=secret,id=npmrc ...，私钥永不落入任何镜像层历史）。
