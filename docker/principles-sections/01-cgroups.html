01.1 · 限流与强杀：为什么 CPU 利用率才 40% 接口却出现百毫秒毛刺？为什么退出码是 137？

01.1 CPU CFS 时间片预算与内存 OOM Killer 触发链路 常问

这节回答实战篇哪个问题：对应 实战篇 02.2 与 07.2 —— 给容器配了 --cpus="2.0" -m 512m 后，内核究竟怎么限制 CPU 与内存？为什么监控看到平均 CPU 不高但请求 P99 延迟突然飙高，以及容器超出内存上限时发生了什么？

如果说 Namespace 是给进程戴上眼罩（视图隔离），那么 Cgroups（Control Groups，控制组） 就是给进程套上配额账本（计量与限流）。生产排障中最常遇到的两大高频现场，分别来自 CPU 子系统与 Memory 子系统：

一、CPU 限制不是“绑死两颗核”，而是按 100ms 周期发放时间片支票

当你声明 --cpus="2.0"（或 Kubernetes 里的 limits.cpu: "2"）时，并不是只允许容器跑在物理第 0、1 号核上（绑核是 --cpuset-cpus="0,1" 的职责），而是通过 Linux 内核 CFS（Completely Fair Scheduler，完全公平调度器） 的带宽控制参数生效：

  • 结算周期（cfs_period_us）：默认固定为 100,000 微秒（100ms）。
  • 周期配额（cfs_quota_us）：--cpus="2.0" 对应配额 200,000 微秒（200ms）（在 Cgroups v2 中合并写入单行文件 cpu.max：200000 100000）。
  • 引发 P99 毛刺的元凶 —— 多核并发透支与 CFS Throttling（节流冻结）：假设宿主机有 16 核，你的 Go / Java 服务在某一瞬间涌入一批并发请求，同时唤醒了 8 个工作线程在 8 颗物理核上满载并行计算。仅需 200ms ÷ 8 核 = 25ms 的真实墙钟时间（Wall-Clock Time），这 200ms 的 CPU 时间预算就被彻底花光了！随后在当前 100ms 周期剩下的 整整 75ms 内，内核会把该容器的所有线程全部移出运行队列强制挂起（Throttled），直到下一个 100ms 周期开始才解冻。监控按 1 分钟平均下来 CPU 使用率也许只有 45%，但落在这 75ms 冻结窗口里的在线请求平白多等了 75ms 甚至跨周期叠加，直接制造出诡异的 P99 延迟尖峰。

二、内存限制：Page Cache 可回收，匿名堆内存超限直通 Exit 137

当你设置 -m 512m（Cgroups v2 对应 memory.max = 536870912）时，内核将该容器的两类内存统一计入这 512MB 账本：

  1. 文件页缓存（Page Cache）：容器读写磁盘文件时内核顺手缓存的数据页。当容器总内存逼近 512MB 时，内核内存回收机制会优先自动丢弃或回写干净的 Page Cache，腾出空间给业务进程，不会触发 OOM（这也是为什么用 docker stats 看内存常年贴近上限却安然无恙——早期工具常把未扣除的可回收 Cache 混在一起展示，现代 Docker CLI 已默认扣除 inactive_file）。
  2. 匿名页（Anonymous Pages，即进程堆栈 RSS）：Go 切片、Node.js V8 堆、Java 堆外内存等无法直接丢弃的数据。一旦匿名页持续增长顶满 512MB，且无法换出（生产环境通常关闭 Swap 或设 --memory-swap=512m 禁用容器交换分区）也无可回收的 Page Cache，内核即刻唤醒该 Cgroup 范围内的 OOM Killer（Out-Of-Memory Killer，内存溢出查杀器），挑出内存占用分（oom_score）最高的子进程直接发送不可捕获的 SIGKILL (信号编号 9)。按照 POSIX 退出码规范 128 + 信号编号 = 128 + 9 = 137，docker inspect 中便会留下 "OOMKilled": true, "ExitCode": 137 的铁证。
bash · 线上排查容器 CPU 被节流（Throttled）与 OOM 强杀记录 
# 1. 在容器内（Cgroups v2 环境，如 Ubuntu 22.04+ / Debian 12+）查看 CPU 节流次数与累计冻结微秒数
docker exec my-api cat /sys/fs/cgroup/cpu.stat
# usage_usec 48291040
# nr_periods 12450
# nr_throttled 892          <-- 被强制冻结了 892 个周期！（占比 > 5% 即需调高 CPU limit 或限制工作线程数）
# throttled_usec 41205800   <-- 累计被挂起等待的线程时间

# 2. 检查容器是否因内存触顶被内核 OOM Killer 击杀，并核对宿主机内核日志
docker inspect -f 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' my-api
sudo dmesg -T | grep -i -E 'killed process|oom-kill' | tail -n 5
01.2 · 层级统一与 /proc 陷阱：Cgroups v2 改了什么？为什么容器里 top 看到的是 64 核？

01.2 Cgroups v1 与 v2 架构对比及语言运行时容器感知 深挖

这节回答实战篇哪个问题：对应 实战篇 06.2 与 07.2 —— 为什么在 64 核宿主机上给容器限额 2 核后，容器内跑 nproc / free -m 看到的依然是宿主机 64 核与 128GB 内存，导致早期 Go / Java / Node.js 应用频繁被节流或 OOM？

对比维度 Cgroups v1（CentOS 7 / Ubuntu 18.04 默认） Cgroups v2（Ubuntu 22.04+ / Rocky 9+ / Docker 20.10+ 默认）
目录树结构 多棵独立层级树：/sys/fs/cgroup/cpu/、/sys/fs/cgroup/memory/、blkio/ 各自挂一棵树，同一进程可以属于不同子系统的不同节点，管理混乱。 单一统一层级树（Unified Hierarchy）：所有控制器收拢在同一棵 /sys/fs/cgroup/ 树下，进程只能挂在叶子节点上，彻底消除跨子系统状态割裂。
异步磁盘回写限速 失效痛点：容器把数据写进内存 Page Cache 后，由内核后台线程异步刷盘；v1 的 blkio 无法把异步回写账算回原容器，导致某容器狂写日志拖垮整机磁盘 I/O。 联动核算：Memory 与 IO 控制器在同一棵树上协同追踪脏页归属，真正做到限制容器缓冲异步写（Buffered I/O）带宽。
柔性内存水位与压力指标 主要靠硬上限 memory.limit_in_bytes，触线直接强回或 OOM，缺少提前感知指标。 新增 memory.high（高水位柔性节流，超线先减速回收而不杀进程） 与 PSI（Pressure Stall Information，压力停顿信息）（精确统计 CPU/内存/IO 等待占比）。
Rootless 无特权容器 几乎无法安全地将 Cgroups 配额委托给非 root 普通用户。 原生支持安全子树委托（Delegation），普通用户跑 Rootless Docker 也能完整限制容器 CPU 与内存。

为什么容器内读 /proc/cpuinfo 和 /proc/meminfo 会被“欺骗”？因为 Linux 的 /proc 伪文件系统诞生于容器时代之前，并没有对应的 Proc Namespace 对硬件统计文件做虚拟化裁剪。当你在容器里运行 free -m 或老版本语言的 os.cpus() / runtime.NumCPU() 时，它们读取的是宿主机全局的 /proc/meminfo（比如 128GB）和调度器可见逻辑核（比如 64 核）！这在生产环境曾引发两类经典事故：

  • CPU 线程膨胀引发剧烈 CFS 节流：在 64 核宿主机上给 Go 容器分配 --cpus="2.0"，旧版 Go 启动时读到 64 核于是设 GOMAXPROCS=64，瞬间拉起几十个系统线程争抢 200ms 配额，上下文切换与 CFS 冻结耗时远超业务本身。现代进展：Go 1.25 起运行时已原生支持读取 Cgroups CPU 配额自动收敛 GOMAXPROCS（Go 1.24 及更早版本建议显式配置环境变量 GOMAXPROCS=2 或引入 uber-go/automaxprocs）；Node.js PM2 / Cluster 模式同理切勿盲写 os.cpus().length，应改读 os.availableParallelism()（Node.js 19.4+ 已支持感知 Cgroups 配额）。
  • 堆内存上限误判引发 OOM 137：如果运行时按宿主机 128GB 内存的 1/4 去规划 GC（Garbage Collection，垃圾回收）上限，而容器实际只有 512MB，不等触发全量 GC 容器就已经被内核 OOM Killer 一刀秒杀。现代进展：JDK 8u191+ / JDK 11+ 默认开启 UseContainerSupport，Node.js 20+ 亦支持读取 Cgroups v1/v2 的 memory.max，但为留出堆外缓冲区与原生 C++ 插件余量，生产上仍推荐显式配置老生代或软内存阈值（约为容器内存限额的 75% ~ 80%）。
