00.1 · 架构本质：Hypervisor 硬件虚拟化 vs 共享宿主机内核的受限进程

00.1 共享内核架构与 clone / unshare / setns 系统调用 常问

这节回答实战篇哪个问题：对应 实战篇 00.1 与 00.2 —— 为什么虚拟机启动要几十秒、镜像动辄数 GB，而 Docker 容器能在百毫秒级拉起、镜像只有几十 MB，且为什么 Linux 容器不能直接运行 Windows 内核程序？

打开 Linux 内核源码，你找不到任何叫 struct container 的数据结构。传统虚拟机依靠 Hypervisor（虚拟机监控器，如 KVM / VMware） 模拟出一整套虚拟 CPU、虚拟网卡与磁盘控制器，每台虚拟机里面都必须完整启动一个独立的 Guest OS Kernel（客户机操作系统内核）；而 Docker 容器完全不虚拟化硬件，也不启动新内核，所有容器直接共享宿主机同一个 Linux 内核，只打包用户态运行库（glibc / musl、基础工具与业务代码）：

这一架构直接解释了三个工程事实：第一，启动容器就是调用内核创建新进程，省去了 BIOS 自检与操作系统引导，因此百毫秒即可就绪；第二，所谓“Ubuntu 容器镜像”或“Alpine 容器镜像”，里面根本不包含 Linux 内核，只包含各自的包管理器（apt / apk）和 C 标准库（glibc / musl），系统调用全部直接落到宿主机内核上，所以 macOS 和 Windows 运行 Linux 容器时，Docker Desktop 必须在后台偷偷跑一台轻量 Linux 虚拟机；第三，因为共享同一个内核，一旦宿主机内核存在提权漏洞，容器逃逸风险高于硬件虚拟化。

在底层实现上，runc 操作 Linux Namespace 只依赖三个核心系统调用：

  • clone(fn, stack, flags, arg)（创建新容器时用）：创建子进程的同时，传入 CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC 等标志位，让子进程一出生就拥有独立的命名空间视图。
  • setns(fd, nstype)（执行 docker exec 时用）：敲下 docker exec -it my-app sh 时，并没有启动新容器，而是打开目标容器进程在 /proc/<pid>/ns/ 下的命名空间文件描述符，调用 setns() 把新创建的 sh 进程“塞进”目标容器已有的 Namespace 与 Cgroups 里——所以退出 exec 终端完全不会影响容器主进程。
  • unshare(flags)（脱离当前命名空间）：不创建新进程，直接让当前调用进程脱离原有的某个共享命名空间并新建一份独立视图（命令行工具 unshare --pid --fork --mount-proc bash 可在宿主机上徒手模拟容器隔离）。

00.2 Linux Namespace 全景表与 PID 1 的内核信号保护机制 常问

这节回答实战篇哪个问题：对应 实战篇 06.3 与 07.4 —— 为什么容器里执行 ps aux 只能看到自己的进程，以及为什么用 Shell 模式启动容器会导致 docker stop 卡死 10 秒后被 SIGKILL 强杀？

Namespace（命名空间） 负责的是“你能看见什么”的视图裁剪。现代 Docker 容器默认启用前 5 项 + Cgroup 命名空间（User 命名空间需开启 Rootless 模式或显式配置）：

Namespace 类型 clone() 标志位 / 内核版本 隔离的内核资源视图与实战现象
1. Mount (mnt) CLONE_NEWNS（Linux 2.4.19） 文件系统挂载点视图（历史上第一个诞生的 Namespace，故宏名叫 NEWNS）。配合 pivot_root 让容器拥有独立的根目录 /，互看不见宿主机目录。
2. UTS CLONE_NEWUTS（Linux 2.6.19） 主机名（Hostname）与 NIS 域名（UTS 即 UNIX Time-Sharing System）。这就是为什么每个容器提示符默认显示自己的 12 位容器短 ID。
3. IPC CLONE_NEWIPC（Linux 2.6.19） 进程间通信资源（IPC，Inter-Process Communication），隔离 System V 消息队列、信号量与 POSIX 共享内存（如 PostgreSQL/Chrome 容器重度依赖 /dev/shm）。
4. PID CLONE_NEWPID（Linux 2.6.24） 进程号编号空间。同一个业务进程具有双重视角：在宿主机根命名空间里它的 PID 可能是 28491，但在容器自己的 PID Namespace 里它就是至高无上的 PID 1。
5. Network (net) CLONE_NEWNET（Linux 2.6.29） 网络协议栈全套隔离：独立网卡（lo / eth0）、独立 IP 地址、独立路由表、独立 iptables 规则与独立 TCP/UDP 端口号监听表（所以 10 个 Nginx 容器都能在各自内部监听 80 端口而不冲突）。
6. User CLONE_NEWUSER（Linux 3.8） UID / GID 用户映射。支持把容器内的 root (UID 0) 映射为宿主机上的普通低权限账号（如 UID 100000），是 Rootless Docker 防御容器逃逸的核心防线。
补充：Cgroup / Time CLONE_NEWCGROUP (4.6) / CLONE_NEWTIME (5.6) Cgroup Namespace 隐藏宿主机完整 cgroup 路径，让容器内看到的 /proc/self/cgroup 以自身为根；Time Namespace 支持单容器独立偏移系统单调时钟与启动时间。
内核深坑：为什么容器内的 PID 1 天生“刀枪不入”，导致 docker stop 优雅停机失效？
在 Linux 内核（kernel/signal.c）中，每个 PID Namespace 的 PID 1 进程都会被打上 SIGNAL_UNKILLABLE 内核标记（因为在传统 Linux 系统里 PID 1 是 systemd / init，一旦误杀整机即刻 Kernel Panic）。这带来了两条与普通进程截然不同的信号核心规则：
1. 默认忽略所有未显式注册处理函数（Signal Handler）的信号：普通进程收到 SIGTERM 若没写捕获逻辑，内核默认动作是终止它；但对于 PID 1，只要代码里没有主动调用 sigaction(SIGTERM, ...) 注册监听器，内核会直接丢弃从外部（含宿主机 docker stop）发来的 SIGTERM！
2. 连 /bin/sh 这种壳进程也不会转发信号：如果你写了 CMD "node server.js"（Shell 格式），容器里的 PID 1 其实是 /bin/sh -c，真正的 node 是 PID 7。执行 docker stop 时，dockerd 向 PID 1 (/bin/sh) 发送 SIGTERM，/bin/sh 既不退出也不把信号转发给子进程 node；苦等 10 秒超时后，宿主机从父级 PID Namespace 强行降下跨命名空间不可豁免的 SIGKILL (9)，直接腰斩连接。
标准解法：始终使用 JSON 数组的 Exec 格式（ENTRYPOINT ["./app"]）让业务进程直任 PID 1 并在代码里监听 SIGTERM；若多子进程无法回收僵尸进程，启用 docker run --init（或在 Compose 中设 init: true），由微型守护进程 tini 担任 PID 1 负责转发信号并调用 waitpid() 回收孤儿僵尸进程。
bash · 在 Linux 宿主机上亲手查看任意容器的 Namespace 句柄号 
# 1. 查出容器主进程在宿主机根命名空间里的真实 PID
HOST_PID=$(docker inspect -f '{{.State.Pid}}' my-nginx)
echo "Host PID: $HOST_PID"

# 2. 查看该进程挂载的命名空间符号链接（方括号内的 inode 编号相同即代表共享同一命名空间）
sudo ls -l /proc/$HOST_PID/ns
