04.1 · 运行时拆解：为什么宿主机 ps 里每个容器都跟着一个 containerd-shim，却看不见 runc？

04.1 containerd-shim 垫片机制与 runc 一次性启动原理 常问

这节回答实战篇哪个问题：对应 实战篇 01.2 与 06.8 —— 敲下 docker run 背后经历了哪些进程接力？为什么升级或重启 dockerd 守护进程时可以做到不杀掉线上正在跑的业务容器？以及为什么 Kubernetes 1.24 宣布“弃用 dockershim”后大家打的 Docker 镜像照样在 K8s 上无缝运行？

在宿主机上执行 ps -ef --forest | grep -A 3 containerd-shim，你会发现一个反直觉的现象：真正干脏活创建容器的底层运行时 runc 根本不在进程树里，取而代之的是每一个运行中的容器头顶都挂着一个专属的父进程 containerd-shim-runc-v2。整套五级分工各有精确边界：

组件名称 生命周期 核心职责与解耦收益
1. docker CLI 命令执行完即退 纯客户端，把命令行参数拼装成 HTTP REST 请求发往 /var/run/docker.sock。
2. dockerd 全局单实例常驻 Docker 高层守护进程：负责对外暴露 API、管理 Docker 网络（docker0/DNS）、管理数据卷与触发 BuildKit 构建，把真正的容器启停与镜像拉取委托给下层 containerd。
3. containerd 全局单实例常驻 CNCF 毕业的工业级高层容器运行时：负责拉取 OCI 镜像层、管理快照存储。Kubernetes 1.24+ 弃用 dockershim 后，正是让节点上的 kubelet 跳过 dockerd 直接通过 CRI（Container Runtime Interface，容器运行时接口）调 containerd——因为 Docker 构建出来的镜像严格遵守 OCI 开放标准，K8s 照样原生运行，零兼容性影响。
4. containerd-shim 每容器 1 个常驻
（内存仅数 MB）		 垫片父进程（架构精髓），承担三大不可替代职责：
① 保持标准流管道打开：替后台（-d）容器持续持有 stdin / stdout / stderr 文件描述符，哪怕上层 dockerd 或 containerd 崩溃重启，容器写日志也不会收到 SIGPIPE 崩溃（支撑 "live-restore": true 无损热升级）；
② 允许 runc 跑完即退：避免每个容器常驻一个较重的 Go 运行时进程；
③ 收集退出状态码：通过 prctl(PR_SET_CHILD_SUBREAPER) 担任子进程收割者，容器主进程退出时精准拿到 Exit Code 回报给 containerd。
5. runc 创完容器即退出 OCI Runtime Spec 标准参考实现。读取 config.json，调用 clone() 建 Namespace、把子进程写入 Cgroups、调 pivot_root 切换根文件系统、加载 Seccomp/Capabilities 策略，最后 execve() 变身为你的业务进程（如 nginx），runc 引导控制进程随即功成身退。
04.2 · 安全防线：为什么默认容器里的 root 用户既改不了系统时间也挂不了宿主机磁盘？

04.2 pivot_root 切根、Capabilities 权能裁剪与 Seccomp 拦截 深挖

这节回答实战篇哪个问题：对应 实战篇 07.1 —— 既然默认容器内显示自己是 uid=0(root)，为什么在里面敲 date -s 改时间或 mount /dev/sda1 挂宿主机硬盘会报 Operation not permitted，而一旦加上 --privileged 就等于交出整台宿主机控制权？

因为共享同一个 Linux 内核，光靠 Namespace 遮住视线远远不够挡住内核级破坏。runc 在把控制权交给容器进程前，依次叠加了三道纵深安全闸门：

  1. 第一道闸：用 pivot_root 替代古老的 chroot 切换根目录
    很多入门资料误以为容器用 chroot 隔离文件系统——实际上 chroot 只是修改当前进程路径解析的起始点，整个宿主机根挂载树依然挂在当前命名空间里，拥有 root 权限的进程只需几行 C 代码利用文件描述符切换就能轻松实现 chroot 逃逸。runc 真正使用的是在独立 Mount Namespace 内调用 pivot_root(new_root, put_old)，把整个挂载命名空间的根切换到 overlay2 的 merged 目录，随后立即调用 umount2(put_old, MNT_DETACH) 将旧的宿主机根文件系统彻底卸载剥离，从根源斩断路径回溯。
  2. 第二道闸：Linux Capabilities（内核权能细分） 剥夺超级管理员特权
    自 Linux 2.2 起，内核将过去无所不能的 root (UID 0) 拆解成了 40 余项细粒度的独立权能开关。Docker 默认容器即使以 root 运行，也只保留了绑定低位端口（CAP_NET_BIND_SERVICE）、修改文件属主（CAP_CHOWN）等 14 项基础权能，默认直接剥夺了：
    • CAP_SYS_TIME（修改宿主机全局内核时钟 —— 因为内核时间未默认按容器隔离，改了全机容器跟着错乱）；
    • CAP_SYS_MODULE（加载/卸载内核驱动模块 insmod —— 一旦放开可直接注入内核 Rootkit）；
    • CAP_SYS_ADMIN（挂载文件系统 mount、操作命名空间等高危总开关）；
    • CAP_NET_ADMIN（修改网卡路由表、抓包篡改宿主机/容器网络配置）。
    加固最佳实践：生产无状态 Web 服务完全可以进一步执行 --cap-drop=ALL --security-opt=no-new-privileges:true 把剩余 14 项也全部卸掉；如果某个网络工具仅需改路由，按需最小授予 --cap-add=NET_ADMIN，绝不要图省事开 --privileged（--privileged 会一次性把全部 40+ 项 Capabilities 全开、关闭 AppArmor/Seccomp，并把宿主机磁盘块设备 /dev/sda* 原样映射进容器，容器内两行 mkdir /mnt/host && mount /dev/sda1 /mnt/host 即可读写宿主机 /etc/shadow 与 SSH 公钥）。
  3. 第三道闸：Seccomp（Secure Computing Mode，安全计算模式） 系统调用白名单过滤
    Linux x86_64 内核暴露了 300 多个系统调用（Syscall），普通业务程序一辈子只用得到其中几十个，而历年内核提权漏洞往往出在生僻系统调用上。Docker 默认为每个容器挂载一份基于 BPF（Berkeley Packet Filter，伯克利包过滤器） 的默认 Seccomp 配置文件，在内核态入口处直接拦截禁止 reboot、swapon、kexec_load、unshare、keyctl、bpf、perf_event_open 等 40 多个高危系统调用（返回 EPERM），将内核受攻击面压缩到最小。
