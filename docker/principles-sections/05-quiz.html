05.1 · 闭卷核对：不看正文，用自己的话把下面 12 个内核机制讲清楚

05.1 12 道 Docker 与容器运行时内核自测题

先合上笔记在脑海里组织答案，再点开折叠面板核对关键点与跳回对应小节：

Q01 · 一句话区分 Linux Namespace 与 Cgroups 的职责边界，并说出 Docker 默认使用了哪几类 Namespace？

答：Namespace 负责“能看见什么”的资源视图隔离，Cgroups 负责“最多能用多少”的硬件配额计量与限流。Docker 默认启用 Mount (mnt)、PID、Network (net)、IPC、UTS 与 Cgroup 命名空间（开启 Rootless 时额外启用 User 命名空间）。详见 00.2 节。

Q02 · 执行 docker exec -it app sh 时，内核调用的是哪一个系统调用？为什么敲 exit 退出不会把容器停掉？

答：调用的是 setns() 系统调用——打开目标容器主进程在 /proc/<pid>/ns/ 下的命名空间文件描述符，将新建的 sh 子进程加入到该容器已有的 Namespace 与 Cgroups 中。因为容器生命周期绑定在容器的 PID 1 主进程上，exec 进去的 sh 只是普通旁路进程（如容器内 PID 18），它退出丝毫不影响 PID 1。详见 00.1 节。

Q03 · 为什么容器里用 Shell 模式启动进程（CMD "node app.js"）会导致 docker stop 卡满 10 秒才被强杀？

答：两层原因叠加：① Shell 格式会让 /bin/sh -c 成为容器 PID 1，而 /bin/sh 不会把收到的 SIGTERM 转发给子进程 node；② Linux 内核为每个 PID Namespace 的 PID 1 打上了 SIGNAL_UNKILLABLE 标记，默认忽略一切未显式注册 Signal Handler 的信号（包括 SIGTERM）。等待 10 秒宽限期超时后，宿主机只能从父 PID Namespace 发送不可豁免的 SIGKILL (9) 强杀。详见 00.2 节。

Q04 · 给容器配了 --cpus="2.0"，监控显示每分钟平均 CPU 利用率仅 40%，为什么接口 P99 延迟却出现近 80ms 的周期毛刺？

答：--cpus="2.0" 底层是 CFS 带宽控制：每 100ms（cfs_period_us）发放 200ms（cfs_quota_us）CPU 时间预算。若应用内部唤醒了 8 个并发线程同时跑在 8 颗核上，仅需 200ms ÷ 8 = 25ms 墙钟时间就把 200ms 配额透支殆尽，随后该容器所有线程在剩余 75ms 内被内核强制冻结（Throttled），导致落在该窗口的请求平白卡顿 75ms。可通过检查 /sys/fs/cgroup/cpu.stat 中的 nr_throttled 验证，并调优容器工作线程数（如收敛 GOMAXPROCS）或适度放宽 CPU 上限。详见 01.1 节。

Q05 · 容器读写大文件导致 Page Cache 塞满内存限额（如 512MB）时，会直接触发 OOM Killer（Exit 137）吗？

答：不会直接 OOM。Cgroups 内存账本虽同时统计文件缓存（Page Cache）与进程匿名堆内存（RSS），但当总用量触碰 memory.max 时，内核内存回收机制会优先自动丢弃或回写可回收的 Page Cache；只有当不可丢弃的匿名页（堆栈内存泄漏或并发大对象）自身撑满 512MB 且无处回收时，才会触发 Cgroup OOM Killer 发送 SIGKILL (128+9=137)。详见 01.1 节。

Q06 · 为什么在容器内读取 /proc/meminfo 或旧版语言的 CPU 核数接口会拿到宿主机的 64 核与 128GB？

答：因为 Linux 内核没有专门针对 /proc 硬件统计文件的 Namespace，容器内的 /proc/cpuinfo 与 /proc/meminfo 默认直接反映宿主机全局视图。必须由语言运行时主动读取 /sys/fs/cgroup/cpu.max 与 memory.max（如 Go 1.25+ 原生容器感知 GOMAXPROCS、JDK 11+ UseContainerSupport、Node.js 20+）或显式传入环境变量限制线程数与堆上限。详见 01.2 节。

Q07 · 解释 Overlay2 的 lowerdir / upperdir / merged 关系，以及为什么数据库绝不能直接把数据写在容器层里？

答：lowerdir 是多容器共享的只读镜像层，upperdir 是单容器独占的可写层，merged 是对容器呈现的联合挂载根视图。当容器首次修改 lowerdir 中的文件时，Overlay2 触发文件级 Copy-on-Write (copy_up)——哪怕只改 1 个字节，也必须把整个大文件从 lowerdir 完整拷贝到 upperdir，产生严重的写放大与阻塞延迟，且删容器即丢失；而 Docker Volume 直接 Bind Mount 宿主机原生文件系统目录，彻底绕过 Overlay2。详见 02.1 节。

Q08 · 在 Dockerfile 第 3 层下载了 300MB 安装包，在第 4 层写了 RUN rm -f pkg.tar.gz，为什么最终镜像一分钱都没变小？

答：因为第 3 层已经成为不可变的只读 lowerdir 层。第 4 层执行 rm 时，Overlay2 只是在第 4 层写入一个主次设备号为 0,0 的 Whiteout 字符设备遮罩文件，在最终 merged 视图里把该名字藏起来，但第 3 层那 300MB 的 tar.gz 数据块依然随镜像一起分发。必须在同一条 RUN 里下载安装完立刻 && rm，或使用多阶段构建。详见 02.1 节。

Q09 · 同一自定义网桥下的两个容器互访时，数据包经过哪几类内核虚拟网络设备？

答：从源容器 Network Namespace 内的虚拟网卡 eth0 发出，穿过跨命名空间的虚拟跳线 veth pair 到达宿主机根命名空间，进入内核二层虚拟交换机 Linux Bridge（br-xxx），网桥按 MAC 转发表直接从目标容器对应的另一根 veth pair 送入目标容器的 eth0，全程同网段二层转发。详见 03.1 节。

Q10 · 为什么云服务器开了 ufw 防火墙封禁 6379 端口，执行 docker run -p 6379:6379 redis 后公网依然能直连进去？

答：-p 6379:6379 在 Netfilter 最前端的 nat 表 PREROUTING 链插入了 DNAT 规则，入站包在路由判决前目的 IP 就已被改写为容器私网 IP（如 172.17.0.2），随后走内核 FORWARD 转发链直通容器，完全绕过了 ufw 默认把守的本机 INPUT 链。应改为 -p 127.0.0.1:6379:6379、不映射端口走容器内网，或在 DOCKER-USER 链/云安全组设防。详见 03.2 节。

Q11 · 为什么 runc 创建完容器就立刻退出，而每个容器头顶都要留一个常驻的 containerd-shim 进程？

答：让 runc 跑完即退可省去大量容器重复驻留完整运行时内存；而轻量的 containerd-shim 承担三件事：① 持续持有后台容器的 stdin/stdout/stderr 文件句柄，确保重启升级 dockerd / containerd 时容器不会因管道断开（SIGPIPE）崩溃；② 担任子进程收割者回收孤儿进程；③ 捕获容器主进程退出码并异步回报给 containerd。详见 04.1 节。

Q12 · 为什么严禁在生产环境随意加 --privileged？它究竟拆掉了哪几道内核安全防线？

答：默认容器受三道安全闸保护（pivot_root 卸载宿主机根 + 剥夺 CAP_SYS_ADMIN / CAP_SYS_MODULE 等高危 Linux Capabilities + Seccomp BPF 拦截 40 余个高危系统调用）。一旦加上 --privileged，会赋予容器全部 40+ 项 Capabilities、关闭 Seccomp 与 AppArmor，并将宿主机所有物理磁盘设备（如 /dev/sda1）暴露进容器 /dev，攻击者在容器内一行 mount 命令即可直接读写篡改宿主机根磁盘完成逃逸。详见 04.2 节。
