03.1 · 虚拟交换机：两个各自关在独立 Network Namespace 里的容器，数据包怎么走通？

03.1 veth pair 虚拟网线与宿主机网桥二层转发路径 常问

这节回答实战篇哪个问题：对应 实战篇 03.2 —— 为什么容器里访问 127.0.0.1 永远只指向容器自己的回环网卡，而同一网桥下的两个容器却能像插在同一台交换机上一样直接互通？

每个开启默认 Bridge 模式的容器都拥有自己独立的 Network Namespace——里面的回环网卡 lo (127.0.0.1) 完全自闭。为了把孤岛般的容器命名空间连回宿主机网络栈，Linux 内核提供了两样关键虚拟网络设备：成对出现的跨命名空间虚拟网线 veth pair（Virtual Ethernet Pair，虚拟以太网设备对） 与 内核二层虚拟交换机 Linux Bridge（如 docker0 或自定义 br-xxx）：

veth pair 就像一根两端带水晶头的虚拟跳线：从一端塞进去的以太网帧，会原封不动地立刻从另一端冒出来。每启动一个 Bridge 容器，Docker 就会创建一对 veth，把其中一头放进容器的 Network Namespace 并改名为 eth0，把另一头留在宿主机根命名空间（即你在宿主机敲 ip addr 看到的一堆 veth8a3f1c2@if24）并插到虚拟交换机 docker0 / br-xxx 上：

  • 同网桥容器互访（二层交换，不经过 NAT）：容器 A（172.18.0.2）请求容器 B（172.18.0.3:3306），命中同子网直连路由，通过 ARP 广播学到 B 的 MAC 地址后，帧从 A 的 eth0 经 veth pair A 进入宿主机网桥 br-app，网桥查 MAC 转发表直接从 veth pair B 送进 B 的 eth0，全程二层内存拷贝，延迟仅微秒级。
  • --network host 模式为何性能略高但有端口冲突？开启 Host 网络模式时，runc 直接不传 CLONE_NEWNET 标志位，容器直接共用宿主机根 Network Namespace 里的物理网卡，省去了 veth pair + 网桥 + iptables NAT 转发损耗（适合高吞吐网关或网络监控 Agent），但代价是失去端口隔离，两个容器不能同时监听 80 端口。
03.2 · 防火墙盲区：为什么宿主机开了 ufw 封禁 3306，外部依然能连进 -p 3306:3306 的容器？

03.2 iptables DNAT/SNAT 路径、防火墙绕过原因与内嵌 DNS 深挖

这节回答实战篇哪个问题：对应 实战篇 01.3、06.1 与 06.5 —— 为什么云服务器明明在 ufw 里只放行了 22 / 80 / 443，一旦敲了 docker run -p 3306:3306 mysql 数据库还是会裸奔在公网上？以及为什么自定义网桥能解析服务名而默认 docker0 不能？

一、容器出外网与外部连容器的 NAT（Network Address Translation，网络地址转换） 链

  • 容器主动访问外网（POSTROUTING MASQUERADE / SNAT）：容器私网 IP 172.18.0.2 在公网上不可路由。数据包把网关 172.18.0.1 作为下一跳交给宿主机内核（需开启 net.ipv4.ip_forward = 1），在离开宿主机物理网卡前的 Netfilter nat 表 POSTROUTING 链上命中 MASQUERADE 规则，把源 IP 替换成宿主机公网/内网 IP 发出，并在内核连接跟踪表（conntrack）记录映射以便回包原路逆向还原。
  • 外部访问容器映射端口（PREROUTING DNAT 绕过 INPUT 链！）：当你执行 -p 3306:3306（等价于 -p 0.0.0.0:3306:3306）时，dockerd 在 Netfilter 最前端的 nat 表 PREROUTING 链插入一条 DNAT 规则，数据包刚进物理网卡，目的 IP 就从“宿主机 IP:3306”被改写成了“容器私网 IP 172.18.0.3:3306”。紧接着经过内核路由判决：由于目的 IP 已经不再是宿主机本机，数据包根本不会走宿主机防火墙 ufw / firewalld 默认把守的 INPUT 链，而是拐弯直接走 FORWARD 链直达容器！
生产防裸奔双保险：
1. 除非是公网入口反向代理（Nginx/Caddy），一切中间件或仅本机访问的调试端口严禁裸写 -p 3306:3306：在单机场景改绑回环地址 -p 127.0.0.1:3306:3306（生成的 DNAT 规则会限定非本机网卡入站不匹配），在 Compose 内部干脆去掉数据库 ports: 让后端直接走内网访问。
2. 若必须在宿主机层面做源 IP 白名单过滤：不要写进 INPUT 链，而是写入 Docker 专门预留且优先级高于容器转发规则的 iptables -I DOCKER-USER ... 链，或依赖云厂商安全组（Security Group，工作在云宿主机虚拟网卡外部，不受容器内部 iptables 影响）。

二、为什么自定义网桥能按容器名 DNS 互通，默认 docker0 却不行？

你随便进入一个挂在默认 bridge (docker0) 上的容器执行 cat /etc/resolv.conf，会看到 Docker 只是把宿主机的公共 DNS（如 8.8.8.8 或局域网网关）原样拷了进去，公共 DNS 当然不认识你取的容器名 mysql（这是 Docker 早期为兼容老旧 --link 机制保留的历史包袱）。而只要挂在自定义网桥（含 docker compose 自动创建的项目网络）上，容器内的 /etc/resolv.conf 会统一变成：

bash · 自定义网桥容器内的 /etc/resolv.conf 与内嵌 DNS 转发机制 
# 在 Compose 容器内查看 DNS 配置
docker exec my-api cat /etc/resolv.conf
# nameserver 127.0.0.11
# options ndots:0

# 底层流向：容器内 netns 的 iptables OUTPUT 链将发往 127.0.0.11:53 的查询
# DNAT 转发到 dockerd 内嵌在容器命名空间套接字上的 Embedded DNS Server：
#   - 若查询名命中同网桥下的容器名/服务别名（如 mysql、redis） -> 直接返回私网 IP 172.18.0.3
#   - 若查询外部公网域名（如 api.weixin.qq.com）            -> 递归转发给宿主机上游 DNS
