🏗️ 03.1 多人实时互动三种拓扑与 Simulcast 大小流机制

假设一个视频派对房间内有 N 位开摄像头的连麦用户（设单路高清视频码率为 1 Mbps），三种多人架构在客户端带宽与服务器成本上呈现完全不同的量级关系：

架构方案 单终端上行流 单终端下行流 服务端算力负载 核心工程权衡与生产定位
Mesh N - 1 路 N - 1 路 O(1)（仅跑信令） 全房间连接数达 O(N2)，且最慢的一位弱网观众会通过拥塞反馈把发送端全局画质拉低；适合 1v1 视频匹配。
MCU 1 路 1 路合成画面 极高（全量解码 + GPU 拼图 + 重编码） 增加 80~150ms 转码延迟，且前端无法单独拖拽某个人的小窗或做声浪高亮；主要用于连麦 PK 旁路合流转推 CDN 直播与云端录制。
SFU + Simulcast 1 组大小流
(约 1.35x 码率)		 N - 1 路按需分层流 极低（纯网络 I/O 改写 RTP 包头转发） 推流端通过 sendEncodings: [{rid:'h'}, {rid:'m', scaleResolutionDownBy:2}, {rid:'l', scaleResolutionDownBy:4}] 同时发高/中/低三层流；SFU 切层时向推流端发 PLI 请求目标层 I 帧 实现无花屏切换，是语聊房与多人派对的标准底座。
🎯 03.2 · 进阶对比与复盘：Simulcast vs SVC 分层编码、WHIP/WHEP 演进与 6 道核心机制自测卡

🎯 03.2 Simulcast vs SVC 演进与核心机制自测卡片

🔭 分层编码与信令标准化演进（Simulcast / SVC / WHIP）：
• Simulcast（联播大小流）vs SVC（可伸缩视频编码，如 VP9-SVC / AV1-SVC）：Simulcast 独立编码高、中、低 3 条互不依赖的码流（总上行带宽约为单高清流的 1.35x），SFU 切层时必须等目标层的下一个 I 帧；而 SVC 在同一条码流内部划分为基础层（Base Layer）与增强层（Enhancement Layer），只多占约 1.15x 带宽且支持任意帧边界平滑剥离。
• WHIP 与 WHEP 标准：IETF 制定的基于单次 HTTP POST 交换 SDP 的极简推流（WHIP）与拉流（WHEP）标准，正逐步替代传统 OBS 的 RTMP 推流，让直播推流到观看全链路进入亚秒级延迟。
自测 1：两个人建立一次 WebRTC 通话，从点击呼叫到画面上屏经历了哪四个核心环节？

① 媒体采集与绑定：双方调用 getUserMedia（开启 3A 回声降噪与 ideal 约束）拿到音视频轨并通过 addTrack 注入 RTCPeerConnection；② 信令交换 SDP 名片：主叫方 createOffer → setLocalDescription 经 WebSocket 发给被叫方，被叫方 setRemoteDescription → createAnswer → setLocalDescription 回传，敲定编解码器（Opus / H.264）、BUNDLE 单口复用与 DTLS 证书指纹；③ Trickle ICE 地址穿透：双方并行向 STUN/TURN 收集 host / srflx / relay 三类候选增量互发，在远端 SDP 设置完成前收到的候选先暂存进队列再调用 addIceCandidate，ICE 按优先级选出最优连通对；④ 加密传输与上屏：完成 DTLS 握手导出对称密钥，SRTP 加密媒体流送达触发对端 ontrack，挂载到带 autoplay playsinline 的 <video> 渲染首帧。

自测 2：既然免费的 STUN 服务器就能查出公网 IP:Port，为什么生产环境还必须部署 TURN？

STUN 只能反射出「客户端访问 STUN 服务器那一刻路由器分配的公网 IP:Port」。在家庭锥形 NAT 下，访问任何外部主机都复用同一个出口端口，对端直接往该端口发包即可打通 P2P；但在对称型 NAT（Symmetric NAT，广泛存在于 4G/5G 移动运营商网关与企业防火墙）下，路由器采用「目标 IP:Port 一变就重新分配新外部端口」策略——客户端转头连接对端 Peer B 时出口已变成全新端口，刚才通过 STUN 查到并告知对端的旧端口完全失效，且入站防火墙会丢弃陌生包。这部分约占真实线上流量的 15% ~ 20%，必须依靠拥有固定公网地址的 TURN（及 443 端口 TURNS）双向中继才能把接通率推向 99%+。

自测 3：高丢包、高抖动的跨国弱网下，WebRTC 底层靠哪些协同机制保证声音不断、画面不花屏？

① 传输层基于 UDP 规避 TCP 丢单包阻塞后续所有新帧的队头阻塞；② 接收端维护自适应 JitterBuffer 吸收延迟抖动并按序列号重排乱序包；③ 丢包恢复按延迟分级——低 RTT 走 RTCP NACK 精准重传丢失包，跨洲高 RTT 或随机丢包走 FEC 前向纠错冗余包零等待恢复，参考帧损坏时发 PLI 请求编码器立即插入完整 I 帧 消除花屏；④ 发送端运行 GCC 拥塞控制，基于 TWCC 到达时间梯度提前感知路由器排队并下调视频码率与分辨率，极端弱网下严格执行「保 Opus 音频、降视频画质」。

自测 4：从 1v1 视频匹配扩展到 8 人视频派对房，为什么不能继续 P2P？SFU 与 MCU 如何取舍？

8 人若用 P2P Mesh 全互联，每部手机需同时编码上行推送 7 路视频并解码下行 7 路视频，移动端上行带宽瞬间打满且严重发热掉帧。多人互动房间主流选 SFU + Simulcast 三层大小流：推流端只需向 SFU 发送一次（含 720p/360p/180p 层），SFU 不做耗费 CPU 的解码重编码，只做零转码路由分发——主讲大屏发高清层，九宫格小窗或 4G 弱网观众只发 180p 小流，延迟低且前端 Vue 组件可自由定制每个麦位的 UI 挂件；而 MCU 在服务端混流重编码算力昂贵，通常仅用于将主播 PK 画面旁路合成为单路流转推给 CDN 供场外数万观众看单向直播或云端录制留存。

自测 5：在 Vue 3 与移动端 H5 中开发实时视频组件，有哪些关键的前端工程规范？

① 响应式代理隔离：RTCPeerConnection 与 MediaStream 必须用 shallowRef 持有，避免 Vue 深层 Proxy 破坏原生内部插槽；② ICE 候选时序队列：setRemoteDescription 完成前到达的 ice-candidate 先缓存进数组，完成后再批量冲刷防 InvalidStateError；③ 移动端播放器规范：本机预览必加 muted 防啸叫，所有 <video> 必加 playsinline 防 iOS 全屏劫持，并捕获 play() 的 NotAllowedError 引导用户轻触解锁声音；④ 1v1 连续切人优化：换人时复用已开启的本地 MediaStream 仅重建 RTCPeerConnection，消除每次唤醒硬件镜头的半秒黑屏；⑤ 生命周期防泄漏：组件卸载时清理统计定时器、调用 pc.close() 并遍历执行 track.stop() 熄灭摄像头指示灯。

自测 6：为什么实时 AI 语音对话与数字人系统普遍采用 WebRTC 替代 WebSocket 传输音频？

传统「前端切片录音发 WebSocket → 后端 ASR → LLM → TTS 切片回传播放」方案存在三大短板：链路串行延迟常超 1.5~3s、跨国 TCP 丢包易卡顿、且前端用普通 AudioContext 播放 TTS 时缺少与麦克风联动的硬件级 AEC 回声消除（AI 说话声极易被手机麦克风录回去误触发打断）。改用 WebRTC（如 OpenAI Realtime API / LiveKit Agents）后，语音走原生 SRTP 音频轨直接获得浏览器内置的 Opus 编码、JitterBuffer 与 3A 回声消除，同时复用同一连接里的 RTCDataChannel 毫秒级同步实时字幕、Function Calling 工具调用与服务端 VAD 插话打断指令，端到端响应可压进 300~500ms。
