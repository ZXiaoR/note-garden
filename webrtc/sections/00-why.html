🧭 00.1 · 整体定位：RTC 与 WebRTC 的关系，以及它和日常 HTTP / WebSocket 开发的区别

🧭 00.1 RTC 与 WebRTC 的核心定位

平时我们在网页里刷长视频（点播）或看赛事大直播时，画面比现场晚 3 到 10 秒传到手机上并不会影响观看体验，因为观众只是单向接收画面。但在微信视频聊天、海外 1v1 随机视频匹配、多人语聊房、以及和 AI 语音伴侣实时对话这类场景下，双方需要「边说边听、随时插话」。心理学与通信工程测试表明，当双向对话的端到端延迟超过 400ms 时，人就会明显感觉到抢话与冷场；这种将端到端延迟控制在 80 ~ 300ms 以内 的双向实时互动技术，统称为 RTC（Real-Time Communication，实时通信）。

WebRTC（Web Real-Time Communication，网页实时通信）并不是某个第三方 npm 前端框架，而是 Google 在 2011 年开源、随后由 W3C 与 IETF 共同制定的浏览器原生标准与内置音视频引擎。现代浏览器（Chrome、Safari、Edge、Firefox 及移动端 WebView）出厂时就已经在底层 C++ 引擎中内置了一整套音视频通话系统，并向前端暴露出原生 JavaScript 接口。与前端日常最熟悉的 WebSocket 相比，WebRTC 有三点核心差异：

差异 ① · 传输路径 P2P Direct
支持浏览器对浏览器直接连线

WebSocket 所有数据都必须去中心服务器绕一圈；而 WebRTC 在两人连上线后，音视频流可直接在两台手机/电脑之间点对点对传（P2P），减少中转延迟并节省服务器带宽。

差异 ② · 底层协议 UDP First
优先保证当下画面声音的实时性

WebSocket 基于 TCP，丢 1 个旧包就会卡住后面已到的 20 个新语音包排队等待重传；WebRTC 默认基于 UDP，允许跳过过期的旧帧，优先播放最新到达的声音与画面。

差异 ③ · 内置引擎 Media Engine
自带采集降噪、压缩与弱网调节

WebSocket 只是一条裸字节管道；而 WebRTC 在浏览器内部自带了回声消除、背景降噪、硬件视频编码压缩以及网速变差时自动调低画质的全套处理流水线。

🗺️ 00.2 · 全景主线：打通一次视频通话经历的五个阶段与常见缩写角色分工

🗺️ 00.2 一次完整 RTC 通话的五步主线与名词对照

初学者看音视频资料时容易混乱，往往是因为 SDP、ICE、STUN、TURN、SRTP、SFU 等缩写混在一起出现。其实把一次实时通话按先后顺序摊开，始终遵循清晰的五个阶段——而且最核心的一条分界线是：前期借用你自己的 WebSocket 后端牵线搭桥，连上线后音视频直接走 UDP 媒体通道传输。

把两个在各自家里连着 Wi-Fi 的手机用户想象成住在两个封闭小区里的住户，下面这张表就能把 RTC 里的全部常见角色一次对号入座：

核心术语 出场阶段 生活类比与真实职责 前端日常代码里做什么
MediaStream 与编码 ① 采集压缩 打包行李：调用摄像头和麦克风拿到画面声音，先消除回声杂音，再把每秒上百 MB 的原始画面压缩成几百 KB。 调用 getUserMedia() 申请权限，控制闭麦、关画面与切镜头。
信令服 (Signaling) ② 信令换名片 中间媒人：两部手机连上前互不认识，需要借助双方都连着的 WebSocket 业务服务器帮忙转交名片与地址。 用项目现有的 WebSocket 收发进房、匹配成功、挂断与协商消息。
SDP（会话描述协议） ② 信令换名片 个人能力名片：一段纯文本，写明「我有音频和视频，支持 H.264 画面与 Opus 声音，这是我的加密指纹」。 调用 createOffer / createAnswer 生成名片并通过信令传给对端。
NAT / STUN / TURN ③ 寻址穿透 查公网门牌与驿站中转：手机只知内网号（如 192.168.1.5），去问公网上的 STUN 服务查出自家路由器的公网地址尝试直连；若被防火墙拦住打不通，则由 TURN 中转服务器帮忙转发。 在 new RTCPeerConnection({ iceServers }) 中填入后端下发的 STUN/TURN 地址与临时凭证。
ICE Candidate ③ 寻址穿透 候选路线单：浏览器搜集到的每一条潜在通信地址（局域网 IP、STUN 查出的公网 IP、TURN 中转 IP）。 监听 onicecandidate 发给对方，收到对方的候选调用 addIceCandidate。
SRTP / JitterBuffer ④ 加密抗弱网 加密车队与缓冲池：SRTP 给音视频包加密防窃听；JitterBuffer 把网络颠簸乱序到达的数据包排齐后再送去播放。 浏览器底层自动完成；前端可通过 getStats() 读取延迟与丢包率展示弱网提示。
SFU（选择性转发网关） ⑤ 多人扩展 多人房间分拣站：超过 3~4 人的语聊房不再两两直连，每人只发 1 份流给 SFU 服务器，由它按需转发给房间其他人。 多人连麦场景通常接入 LiveKit、声网（Agora）或即构（ZEGO）等 SDK 与 SFU 交互。
📝 00.3 · 第一个程序：无需任何后端，25 行代码跑通本地摄像头采集、预览与开关画面

📝 00.3 编写第一个本地摄像头预览网页

体验 WebRTC 的第一步完全不需要搭建服务器。新建一个 hello-camera.html 文件，用 VS Code 的 Live Server（或终端执行 python3 -m http.server 8000 后访问 http://localhost:8000/hello-camera.html）打开，点击按钮并允许权限，就能在网页里看到自己的实时画面：

📄 hello-camera.html · 最小本地摄像头采集与开关示例 
<!DOCTYPE html>
<html lang="zh-CN">
<body>
  <!-- 本地预览必须加 muted 静音，防止自己扬声器外放的声音再被麦克风录进去啸叫 -->
  <video id="local-video" autoplay muted playsinline
         style="width: 360px; background: #111; border-radius: 10px;"></video>
  <div style="margin-top: 10px;">
    <button id="start-btn">1. 开启摄像头</button>
    <button id="stop-btn">2. 彻底关闭硬件</button>
  </div>

  <script>
    let localStream = null;
    const videoEl = document.getElementById('local-video');

    document.getElementById('start-btn').addEventListener('click', async () => {
      // 向浏览器申请摄像头画面与麦克风声音，返回 MediaStream 媒体流对象
      localStream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
      videoEl.srcObject = localStream; // 将实时流直接绑定到 video 元素播放
    });

    document.getElementById('stop-btn').addEventListener('click', () => {
      localStream?.getTracks().forEach(track => track.stop());
      videoEl.srcObject = null;
    });
  </script>
</body>
</html>
📖 逐行关键细节拆解（零基础对照）
  • 为什么必须通过 localhost 或 https:// 访问：为了保护用户隐私，浏览器规定只有在「安全上下文（Secure Context）」下才暴露 navigator.mediaDevices；若直接用局域网明文 http://192.168.x.x 打开，该对象为 undefined。
  • videoEl.srcObject = localStream：普通点播视频给 videoEl.src 赋一个 .mp4 网址字符串；而实时媒体流在内存里持续产生画面帧，因此直接赋值给 srcObject 属性。
  • 本地预览必加 muted：muted 只会让本机浏览器不把你自己的声音从喇叭放出来，并不会影响麦克风采集发给远端对方；如果不加，你的声音从音箱出来又进麦克风循环放大，一秒内就会产生刺耳的回声啸叫。
  • playsinline：在 iOS Safari / 微信内置浏览器中必加，告知系统在网页原有位置内联播放，不要一接通就强行弹起全屏系统播放器挡住页面按钮。
🛠️ 00.4 · 调试工作台：台式机无摄像头模拟参数与 Chrome 内置 WebRTC 诊断面板

🛠️ 00.4 本地开发与诊断工具：虚拟设备参数与 chrome://webrtc-internals

日常在公司用台式机开发或一个人联调双人通话时，经常遇到「电脑没有外接摄像头」或「连接断了但在普通 Network 面板里看不到 UDP 音视频包」的情况，下面三项浏览器内置能力是音视频前端最常用的调试手段：

调试工具 / 能力 开启方式 主要观测内容与开发用途
1. chrome://webrtc-internals 在 Chrome / Edge 地址栏直接输入该内部地址回车 WebRTC 官方黑匣子面板：自动记录当前所有 RTCPeerConnection 实例的 API 调用时间线（createOffer / setRemoteDescription / addIceCandidate）、完整的本地与远端 SDP 文本、选中的 ICE 候选地址对，以及实时的发送/接收码率、帧率、RTT 延迟和丢包率折线图。
2. Chrome 内置虚拟摄像头与麦克风 终端带参启动 Chrome：--use-fake-device-for-media-stream --use-fake-ui-for-media-stream 无需真实硬件摄像头，Chrome 会自动生成一个带旋转绿圈计时器的测试视频画面与滴答音频流，并自动跳过权限弹窗，适合在无摄像头的开发机或自动化 E2E 测试中使用。
3. DevTools → Network (WS) 打开 F12 → Network，筛选 WS（WebSocket）标签并点开 Messages 虽然正式通话后的 UDP 媒体包不显示在 Network 面板里，但前期所有的信令交互消息（进房、offer、answer、ice-candidate）都能在 WS → Messages 里逐条检查收发顺序。
